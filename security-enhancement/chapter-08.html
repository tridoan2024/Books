Chapter 8: Atomic Credential Operations

A security patch that eliminates plaintext storage (Chapter 7) can be undermined by a race condition in the write operation itself. Finding 30 (CWE-367, CVSS 4.7) documents exactly this: the plainTextStorage.update() function writes credentials with writeFileSync and then sets permissions with chmodSync. Between those two calls, the file exists on disk with whatever permissions the process's umask allows -- potentially world-readable.

This is a textbook Time-of-Check-to-Time-of-Use (TOCTOU) vulnerability. The "check" is the intended permission (0o600), the "use" is the actual file creation (default umask), and the gap between them is a window where any process on the system can read freshly written OAuth tokens.

This chapter goes beyond fixing the TOCTOU race. We implement the atomic write pattern -- a crash-safe, race-free approach to credential file updates that eliminates three classes of vulnerability simultaneously: the permission window, partial writes from crashes, and data corruption from concurrent updates.

8.1 The Vulnerability: Write-Then-Chmod

The current credential write implementation in plainTextStorage.ts follows a two-step pattern:

// utils/secureStorage/plainTextStorage.ts:57-61
async update(
  updater: (data: Record<string, unknown>) => Record<string, unknown>,
): Promise<void> {
  const storagePath = getStoragePath()
  const dir = dirname(storagePath)
  if (!existsSync(dir)) {
    mkdirSync(dir, { recursive: true, mode: 0o700 })
  }
  const existing = await this.read()
  const updated = updater(existing ?? {})
  writeFileSync_DEPRECATED(storagePath, jsonStringify(updated), {
    encoding: 'utf8',
    flush: false,
  })
  chmodSync(storagePath, 0o600)
}

Measuring the Window

The window between writeFileSync and chmodSync is typically microseconds -- but that metric is misleading. The question is not "how long is the window?" but "can an attacker reliably exploit it?"

On Linux, inotify provides filesystem event notification. A monitoring process watching ~/.claude/ receives an IN_CREATE or IN_CLOSE_WRITE event the moment the file is created. The attacker's response time to this event is limited only by the kernel scheduler -- typically under 100 microseconds on a modern system. The window is wide enough.

# Attacker's monitoring loop (conceptual)
inotifywait -m -e close_write ~/.claude/ | while read dir event file; do
  if [[ "$file" == ".credentials.json" ]]; then
    cat "$dir/$file"  # Read before chmod fires
  fi
done

On macOS, the equivalent is FSEvents or kqueue with NOTE_WRITE. The timing characteristics are similar.

Three Problems, Not One

The write-then-chmod pattern actually contains three distinct problems:

Problem CWE Consequence
Permission window CWE-367 (TOCTOU) Credential exposure between write and chmod
Non-atomic write CWE-367 (TOCTOU) Partial file on crash (corrupted JSON)
No flush guarantee CWE-404 (Improper Resource Shutdown) Data loss on power failure (flush: false)

The flush: false flag in the writeFileSync call is particularly concerning. Without flushing, the data may reside only in the OS page cache, not on physical storage. A system crash (kernel panic, power failure) could result in a zero-length or partially-written credential file, corrupting the authentication state.

8.2 The Atomic Write Pattern

The atomic write pattern solves all three problems with a single approach: write to a temporary file with correct permissions, flush to disk, then rename into place.

graph TD
    START["Credential Update"] --> CREATE["Create temp file<br/>openSync(tmpPath, 'w', 0o600)<br/>Permissions correct from birth"]
    CREATE --> WRITE["Write JSON to temp file<br/>writeSync(fd, data)"]
    WRITE --> FLUSH["Flush to disk<br/>fsyncSync(fd)"]
    FLUSH --> CLOSE["Close file descriptor<br/>closeSync(fd)"]
    CLOSE --> RENAME["Atomic rename<br/>renameSync(tmpPath, targetPath)"]
    RENAME --> DONE["Done: credential file updated<br/>atomically with correct permissions"]

    CREATE -.->|"On error"| CLEANUP["Delete temp file<br/>unlinkSync(tmpPath)"]
    WRITE -.->|"On error"| CLEANUP
    FLUSH -.->|"On error"| CLEANUP

    style RENAME fill:#2d6a2d,color:#fff
    style CLEANUP fill:#8b4513,color:#fff

Why This Works: The Three Guarantees

Guarantee 1: No permission window. The openSync(tmpPath, 'w', 0o600) call creates the file with the correct permissions from the moment it exists on disk. The mode parameter to open() is applied atomically during file creation -- there is no gap where the file exists with different permissions. The umask is irrelevant because the open() mode is ANDed with ~umask, but we set it explicitly.

Actually, that is not quite right. The mode parameter is indeed subject to the process's umask. If umask is 0o022, then open(path, O_WRONLY|O_CREAT, 0o600) creates the file with 0o600 & ~0o022 = 0o600 -- but only because 0o022 does not mask any bits in 0o600. If we wanted 0o660 and umask was 0o022, we would get 0o640. For the credential file case, 0o600 with any standard umask produces 0o600. However, to be defensive against unusual umask settings:

// Set umask to 0 temporarily for this operation
const oldUmask = process.umask(0o077)
try {
  const fd = openSync(tmpPath, 'w', 0o600)
  // ... write, flush, close, rename ...
} finally {
  process.umask(oldUmask)
}

This ensures the temp file gets exactly 0o600 regardless of the process's inherited umask.

Guarantee 2: No partial writes. The renameSync call is atomic on POSIX filesystems when the source and destination are on the same filesystem. At any point in time, targetPath either contains the complete old data or the complete new data -- never a partial write. If the process crashes between writeSync and renameSync, the temp file is orphaned but the target file retains its previous content.

Guarantee 3: Durability. The fsyncSync call forces the operating system to flush file data from the page cache to physical storage. After fsyncSync returns, the data is on disk even if the system loses power. Without fsync, data may reside only in volatile memory.

The Complete Implementation

The patched update() method from the Security Action Report:

async update(
  updater: (data: Record<string, unknown>) => Record<string, unknown>,
): Promise<void> {
  const storagePath = getStoragePath()
  const dir = dirname(storagePath)
  if (!existsSync(dir)) {
    mkdirSync(dir, { recursive: true, mode: 0o700 })
  }
  const existing = await this.read()
  const updated = updater(existing ?? {})

  // Atomic write with correct permissions from creation.
  // Eliminates the TOCTOU window between writeFileSync and chmodSync
  // where the file exists with default (potentially 0o644) permissions.
  const tmpPath = storagePath + '.tmp.' + process.pid
  try {
    // Create file with restrictive permissions from the start
    const fd = openSync(tmpPath, 'w', 0o600)
    try {
      writeSync(fd, jsonStringify(updated), 0, 'utf8')
      fsyncSync(fd)
    } finally {
      closeSync(fd)
    }
    // Atomic rename: permissions are already 0o600 on the new file
    renameSync(tmpPath, storagePath)
  } catch (err) {
    try { unlinkSync(tmpPath) } catch { /* ignore cleanup failure */ }
    throw err
  }
}

8.4 Deep Dive: O_CREAT|O_EXCL for Exclusive Creation

The openSync(tmpPath, 'w', 0o600) call in the patch creates the file if it does not exist. But what if a temp file from a previous crashed invocation already exists? The 'w' flag truncates an existing file, which is correct for our use case. However, there is a subtlety: if an attacker pre-creates a file at the temp path (a symlink attack), the open() call follows the symlink and writes to the attacker's chosen location.

For maximum security, the temp file creation should use O_CREAT|O_EXCL:

import { constants } from 'fs'

// O_CREAT | O_EXCL | O_WRONLY: create exclusively, fail if exists
const flags = constants.O_CREAT | constants.O_EXCL | constants.O_WRONLY
const fd = openSync(tmpPath, flags, 0o600)

O_EXCL guarantees that the open() call creates a new file. If a file (or symlink) already exists at that path, the call fails with EEXIST. This eliminates the symlink attack vector entirely.

The trade-off is that a crashed previous invocation leaves an orphaned temp file that blocks future writes. The solution: attempt O_CREAT|O_EXCL first; on EEXIST, delete the stale temp file and retry once:

function openExclusiveOrRetry(path: string, mode: number): number {
  const flags = constants.O_CREAT | constants.O_EXCL | constants.O_WRONLY
  try {
    return openSync(path, flags, mode)
  } catch (err: any) {
    if (err.code !== 'EEXIST') throw err
    // Stale temp file from crashed previous invocation -- remove and retry
    unlinkSync(path)
    return openSync(path, flags, mode)
  }
}

Temp File Naming Strategy

The current patch uses storagePath + '.tmp.' + process.pid as the temp file name. The PID provides uniqueness within a single machine's running processes. However, PIDs are recycled -- a PID from a crashed process may be reused by a new, unrelated process. For stronger uniqueness:

import { randomBytes } from 'crypto'

const nonce = randomBytes(8).toString('hex')
const tmpPath = `${storagePath}.tmp.${process.pid}.${nonce}`

The random nonce eliminates PID recycling as a concern and prevents an attacker from predicting the temp file name (which would be needed for a pre-creation attack if O_EXCL is not used).

8.5 The fsync Requirement

The fsyncSync(fd) call is the most expensive operation in the atomic write pattern -- it can take 1-10ms on SSD and 10-50ms on HDD. Why is it necessary?

Without fsync, the kernel may reorder operations. The rename could be persisted to disk before the file contents are persisted. If the system crashes after the rename is persisted but before the contents are written, the credential file contains garbage:

Timeline without fsync:
1. write(fd, data)       → data in page cache (not on disk)
2. rename(tmp, target)   → rename in journal (on disk)
3. [SYSTEM CRASH]
4. After reboot: target file exists but contains zero bytes

With fsync:

Timeline with fsync:
1. write(fd, data)       → data in page cache
2. fsync(fd)             → data forced to disk
3. rename(tmp, target)   → rename in journal (on disk)
4. [SYSTEM CRASH]
5. After reboot: target file contains complete data

fsync on the Directory

For complete durability, the directory entry for the renamed file should also be synced. On POSIX systems, rename() modifies the directory that contains the file. The directory entry update is also subject to reordering:

// After rename, fsync the parent directory to ensure
// the directory entry is persisted
const dirFd = openSync(dir, constants.O_RDONLY | constants.O_DIRECTORY)
try {
  fsyncSync(dirFd)
} finally {
  closeSync(dirFd)
}

This is the pattern used by databases (SQLite, PostgreSQL) for crash-safe file operations. For credential storage, where writes happen a few times per session and the data is small, the performance cost is negligible.

Platform-Specific fsync Behavior

Platform fsync Behavior Gotcha
Linux (ext4) Flushes file data and metadata Barrier writes may be disabled on some systems
Linux (btrfs) Copy-on-write; fsync creates a new extent Old data blocks retained until overwritten
macOS (APFS) Flushes to stable storage F_FULLFSYNC ioctl provides stronger guarantee than fsync
Windows (NTFS) FlushFileBuffers() equivalent May not flush disk write cache without FILE_FLAG_WRITE_THROUGH

On macOS, fsyncSync calls fsync(2), which APFS maps to a barrier flush. For applications requiring the strongest guarantee (financial transactions, database WAL), fcntl(fd, F_FULLFSYNC) should be used instead. For credential storage, standard fsync is sufficient -- the credential file is written at most a few times per session, and the durability window is seconds, not milliseconds.

8.6 Concurrent Update Safety

What happens when two Claude Code processes update credentials simultaneously? The current implementation has a read-modify-write race independent of the permission TOCTOU:

sequenceDiagram
    participant P1 as Process 1
    participant P2 as Process 2
    participant FS as Filesystem

    P1->>FS: read() → {tokenA: "old"}
    P2->>FS: read() → {tokenA: "old"}
    P1->>P1: updater({tokenA: "old"}) → {tokenA: "new1"}
    P2->>P2: updater({tokenA: "old"}) → {tokenA: "new2"}
    P1->>FS: write({tokenA: "new1"})
    P2->>FS: write({tokenA: "new2"})
    Note over FS: Final state: {tokenA: "new2"}<br/>Process 1's update is lost

The atomic rename does not solve this -- it ensures each individual write is atomic, but the read-modify-write sequence across two processes can still lose updates. This is a lost-update problem (CWE-362: Concurrent Execution Using Shared Resource with Improper Synchronization).

File Locking

POSIX advisory file locking can serialize access:

import { flockSync } from 'fs-ext' // or implement via fcntl

async update(
  updater: (data: Record<string, unknown>) => Record<string, unknown>,
): Promise<void> {
  const storagePath = getStoragePath()
  const lockPath = storagePath + '.lock'
  const lockFd = openSync(lockPath, 'w', 0o600)
  try {
    // Acquire exclusive lock (blocks if another process holds it)
    flockSync(lockFd, 'ex')

    // Critical section: read, modify, write
    const existing = await this.read()
    const updated = updater(existing ?? {})
    await this.writeAtomic(storagePath, updated)
  } finally {
    // Release lock
    flockSync(lockFd, 'un')
    closeSync(lockFd)
  }
}

Node.js does not provide flock in the standard library. Options include:

  1. proper-lockfile npm package: Cross-platform file locking with stale lock detection
  2. fs-ext npm package: Provides flock() bindings
  3. Custom implementation using O_EXCL: Create a lock file with O_CREAT|O_EXCL; delete on release

For Claude Code's use case, where credential updates are infrequent (at most a few per session) and the critical section is short (read JSON, modify, write), the simplest approach is a retry loop with O_CREAT|O_EXCL:

const MAX_LOCK_RETRIES = 5
const LOCK_RETRY_DELAY_MS = 100

async function withCredentialLock<T>(fn: () => Promise<T>): Promise<T> {
  const lockPath = getStoragePath() + '.lock'

  for (let attempt = 0; attempt < MAX_LOCK_RETRIES; attempt++) {
    try {
      // Attempt to create lock file exclusively
      const lockFd = openSync(
        lockPath,
        constants.O_CREAT | constants.O_EXCL | constants.O_WRONLY,
        0o600,
      )
      closeSync(lockFd)

      try {
        return await fn()
      } finally {
        try { unlinkSync(lockPath) } catch { /* ignore */ }
      }
    } catch (err: any) {
      if (err.code !== 'EEXIST') throw err
      // Lock held by another process -- check staleness
      try {
        const lockStat = statSync(lockPath)
        const ageMs = Date.now() - lockStat.mtimeMs
        if (ageMs > 30000) {
          // Stale lock (>30s) -- process probably crashed
          unlinkSync(lockPath)
          continue
        }
      } catch { /* lock may have been released between check and stat */ }
      await new Promise(resolve => setTimeout(resolve, LOCK_RETRY_DELAY_MS))
    }
  }
  throw new Error('Failed to acquire credential lock after retries')
}

8.7 Credential Migration Race Condition

Finding 39 in the audit report identifies a related TOCTOU in credential migration. When credentials are migrated from an old storage location to a new one (e.g., from plaintext to encrypted), the sequence is: read from old location, write to new location, delete old location. Two processes performing migration simultaneously can corrupt or lose credentials.

The atomic write pattern combined with file locking eliminates this race:

async function migrateCredentials(): Promise<void> {
  await withCredentialLock(async () => {
    const oldPath = getLegacyStoragePath() // ~/.claude/.credentials.json
    const newStorage = getSecureStorage()

    if (!existsSync(oldPath)) return // Already migrated

    // Read from old location
    const data = JSON.parse(readFileSync(oldPath, 'utf8'))

    // Write to new location (atomic write internally)
    await newStorage.write(data)

    // Verify write succeeded before deleting old file
    const readBack = await newStorage.read()
    if (!readBack) {
      throw new Error('Migration verification failed: could not read back credentials')
    }

    // Securely delete old plaintext file
    secureDeleteFile(oldPath)
  })
}

The verify-before-delete step is critical. Without it, a write failure silently destroys the only copy of the credentials. The lock ensures that only one process performs the migration, and the atomic write ensures the new file is either completely written or not at all.

8.8 Applying the Pattern to Other Sensitive Files

The atomic write pattern is not specific to credentials. Any file that contains sensitive data and must survive crashes should use it. In Claude Code's codebase, several other files benefit from the same treatment:

File Content Current Write Method Risk
.credentials.json OAuth tokens writeFileSync + chmodSync Finding 30 (TOCTOU)
settings.local.json User preferences writeFileSync Partial write on crash
history.jsonl Conversation history appendFileSync Discussed in Chapter 9
paste-cache/*.txt Pasted content writeFileSync May contain secrets

A shared utility function extracts the pattern:

// utils/atomicWrite.ts
import {
  openSync, writeSync, closeSync, fsyncSync,
  renameSync, unlinkSync, constants,
} from 'fs'
import { randomBytes } from 'crypto'

export function atomicWriteFileSync(
  targetPath: string,
  data: string | Buffer,
  options: { mode?: number; encoding?: BufferEncoding } = {},
): void {
  const { mode = 0o644, encoding = 'utf8' } = options
  const nonce = randomBytes(8).toString('hex')
  const tmpPath = `${targetPath}.tmp.${process.pid}.${nonce}`

  try {
    const fd = openSync(
      tmpPath,
      constants.O_CREAT | constants.O_EXCL | constants.O_WRONLY,
      mode,
    )
    try {
      if (typeof data === 'string') {
        writeSync(fd, data, 0, encoding)
      } else {
        writeSync(fd, data)
      }
      fsyncSync(fd)
    } finally {
      closeSync(fd)
    }
    renameSync(tmpPath, targetPath)
  } catch (err) {
    try { unlinkSync(tmpPath) } catch { /* ignore */ }
    throw err
  }
}

// Secure credential write

// Settings write (less sensitive, standard permissions)

8.9 The O_TMPFILE Optimization (Linux)

Linux 3.11 introduced O_TMPFILE, which creates an anonymous file in a specified directory with no directory entry. The file is visible only through the file descriptor. This eliminates the need for temp file name generation and the cleanup-on-failure path:

// C equivalent (for understanding)
int fd = open("/path/to/dir", O_TMPFILE | O_WRONLY, 0600);
write(fd, data, len);
fsync(fd);
// Create directory entry atomically via /proc/self/fd
linkat(AT_FDCWD, "/proc/self/fd/" + fd, AT_FDCWD, "/path/to/file", AT_SYMLINK_FOLLOW);
close(fd);

In Node.js, O_TMPFILE is available via the constants object on supported Linux kernels:

import { constants } from 'fs'

// O_TMPFILE may not be defined on all platforms
const O_TMPFILE = constants.O_TMPFILE ?? 0o20000000

if (process.platform === 'linux' && O_TMPFILE) {
  // Use O_TMPFILE for anonymous temp file
  const fd = openSync(dir, O_TMPFILE | constants.O_WRONLY, 0o600)
  writeSync(fd, data)
  fsyncSync(fd)
  // Link into directory via procfs
  execFileSync('ln', ['-f', `/proc/self/fd/${fd}`, storagePath])
  closeSync(fd)
}

Advantages of O_TMPFILE: - No temp file visible on disk at any point (anonymous until linked) - No cleanup required on failure (file disappears when fd is closed) - No temp file name collision possible

Disadvantages: - Linux-only (not available on macOS or Windows) - Requires /proc to be mounted (not available in some container configurations) - The linkat from /proc/self/fd/ is not a standard rename -- it creates a new hard link

For a cross-platform codebase like Claude Code, the temp-file-and-rename pattern is the pragmatic choice. O_TMPFILE can be used as an optimization on Linux when available, falling back to the standard pattern otherwise.
