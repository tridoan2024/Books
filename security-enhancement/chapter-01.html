Chapter 1: The Security Landscape of Claude Code

The first rule of securing a production system is knowing exactly what you are defending against. Not theoretical threats from a whiteboard exercise, but concrete vulnerabilities with measured severity, documented locations, and quantified blast radii. This chapter presents the results of a comprehensive security source review of Claude Code's 512,000-line TypeScript codebase -- 50 vulnerabilities spanning every layer from plugin ingestion to shell execution. Before writing a single patch, you need this map.

1.1 Scope and Methodology

The security review covered the entire Claude Code CLI source tree: 1,884 files of TypeScript/TSX running on the Bun runtime. Four specialized analysis agents operated in parallel -- a static scanner, a design reviewer, a supply chain scanner, and a patch engineer -- each producing findings that were cross-validated and de-duplicated into the final 50-vulnerability catalog.

The assessment targeted six major subsystems:

Subsystem Files Reviewed Primary Risk
Plugin/Extension System plugins/, utils/plugins/, utils/dxt/ Supply chain, code execution
Credential Storage utils/secureStorage/ Plaintext secrets, TOCTOU
Authentication & Tokens bridge/, services/oauth/, utils/auth.ts JWT forgery, token persistence
Subagent Execution tools/AgentTool/, services/mcp/ Process isolation, privilege escalation
Network & Remote server/, remote/, upstreamproxy/ SSRF, permission bypass, WebSocket
Bash Security tools/BashTool/ Parser differential, injection

The review methodology followed a hybrid approach: automated pattern matching against known CWE signatures, manual data-flow tracing through security-critical paths, and architectural analysis of trust boundaries. Every finding was scored using CVSS v3.1 base metrics with environmental adjustments for CLI tool deployment contexts.

CVSS Scoring for CLI Tools

Standard CVSS scoring assumes network-accessible services. A CLI tool operating on a developer's machine requires adjusted environmental metrics. Consider how attack vectors differ:

  • Network vector (N) applies when the tool processes data from remote sources -- marketplace plugins, bridge sessions, WebSocket connections
  • Local vector (L) applies when exploitation requires filesystem access -- credential files, conversation history, debug logs
  • Adjacent vector (A) applies to same-machine attacks -- cross-process memory access, shared environment variables

The 50 findings distribute across these vectors:

Attack Vector Count Percentage Example
Network 18 36% Plugin download without signature (CVSS 9.1)
Local 26 52% Plaintext credential storage (CVSS 7.1)
Adjacent 6 12% Proxy token on heap after unlink (CVSS 5.3)

This distribution reveals an important truth about CLI tool security: the majority of risk is local. The developer's own machine is both the deployment target and the attack surface. As we'll explore in Chapter 2, these local vulnerabilities chain together into dependency groups that amplify their individual severities.

1.3 The Two Critical Findings

The two CRITICAL-severity findings both involve the same root cause: unsigned plugin code execution.

Finding 1: No Cryptographic Signature Verification for Plugins (CVSS 9.1)

Location: plugins/ (system-wide) CWE: CWE-494 -- Download of Code Without Integrity Check OWASP: A08:2021 -- Software and Data Integrity Failures

The plugin system downloads ZIP archives from marketplace registries and executes their contents with full CLI process privileges. While SHA-256 hash verification confirms the download was not corrupted during transit, no mechanism exists to verify that the plugin was published by its claimed author or hasn't been replaced by a malicious actor who compromised the registry.

The data flow is:

Marketplace API --> download plugin ZIP --> hash verify (integrity only)
  --> extract with path traversal protection --> register plugin
  --> plugin executes with CLI privileges

The hash check answers "did I download what the server sent?" but not "did the server send what the author published?" A compromised CDN, a MITM on the download URL, or a rogue marketplace entry can inject arbitrary code that passes integrity checks because the hash was computed over the malicious payload.

Finding 2: No Signature Verification for Downloaded Plugins (CVSS 8.1)

Location: utils/plugins/pluginLoader.ts, utils/plugins/marketplaceManager.ts CWE: CWE-494 OWASP: A08:2021

This finding is the implementation-level companion to Finding 1. The marketplace JSON is fetched via axios.get() with zero integrity validation. The GCS marketplace ZIP is downloaded without SHA-256 verification against a known-good hash. The .gcs-sha sentinel file is written by the same extraction process, creating a TOCTOU condition.

Together, these two findings represent the highest blast radius in the codebase: a compromised marketplace or CDN can deliver arbitrary code to every developer who installs or updates plugins. As we'll analyze in Chapter 2, this forms the root of the Plugin Supply Chain dependency chain, which cascades through five additional findings.

1.4 The Eight HIGH-Severity Findings

The HIGH tier contains the vulnerabilities most likely to cause immediate damage in production deployments.

Subagent Execution Without Process Isolation (CVSS 7.8)

Location: tools/AgentTool/runAgent.ts:248 CWE: CWE-269 -- Improper Privilege Management

Subagents, including those spawned by third-party plugins, execute in the same Node.js/Bun process as the parent CLI. They share AppState, tool pools, and environment. The only isolation is tool-name filtering at runAgent.ts:465-479 -- advisory, not enforced at the process level. A malicious subagent can read ~/.claude/.credentials.json, exfiltrate tokens via network tools, and fork child agents to establish persistence.

ZIP Path Traversal via Symlinks (CVSS 7.5)

Location: utils/plugins/zipCache.ts, utils/dxt/zip.ts CWE: CWE-22 -- Path Traversal

ZIP extraction validates against .. path components but follows symlinks without validating that resolved paths remain within the extraction root. At zipCache.ts:292-300, the comment reads "Skip symlinked directories (follow symlinked files)" -- but symlink targets are not validated against the extraction boundary. A crafted ZIP with a symlink pointing to ~/.ssh/authorized_keys could write files to arbitrary locations.

JWT Decoded Without Signature Verification (CVSS 7.5)

Location: bridge/jwtUtils.ts:21 CWE: CWE-347 -- Improper Verification of Cryptographic Signature

The decodeJwtPayload() function performs Buffer.from(parts[1], 'base64url').toString('utf8') -- base64 decode of the payload -- without verifying the signature in parts[2]. No JWKS endpoint is fetched, no public key is loaded. The decoded exp claim is used to schedule token refresh timers. An attacker who can MITM the bridge connection could forge a JWT with a far-future exp, suppressing refresh and keeping a revoked token active indefinitely.

// bridge/jwtUtils.ts:21 -- VULNERABLE
export function decodeJwtPayload(token: string): unknown | null {
  const jwt = token.startsWith('sk-ant-si-')
    ? token.slice('sk-ant-si-'.length)
    : token
  const parts = jwt.split('.')
  if (parts.length !== 3 || !parts[1]) return null
  try {
    return jsonParse(Buffer.from(parts[1], 'base64url').toString('utf8'))
  } catch {
    return null
  }
}

Notice what is absent: no call to crypto.verify(), no JWKS fetch, no public key parameter. The function name -- decodeJwtPayload -- is honest about what it does, but the callers treat the output as verified data.

MCP Server Tools Without Process Sandbox (CVSS 7.5)

Location: services/mcp/ CWE: CWE-250 -- Execution with Unnecessary Privileges

MCP server tool calls execute within the CLI process's full security context. While a permission prompt is shown, approved tools run with complete filesystem, network, and shell access. A malicious MCP server registered in a marketplace could define tools that appear benign (e.g., format_code) but execute arbitrary commands when approved.

Plaintext Credential Storage (CVSS 7.1 + 7.1 + 6.5)

Locations: utils/secureStorage/index.ts:9, utils/secureStorage/plainTextStorage.ts:57, utils/secureStorage/index.ts:16 CWE: CWE-256, CWE-312, CWE-922

Three separate findings target the same architectural gap: on non-macOS platforms, OAuth tokens and API keys are stored as plaintext JSON at ~/.claude/.credentials.json with only chmod 0600 protection. The code is explicit about this:

// utils/secureStorage/index.ts:9
export function getSecureStorage(): SecureStorage {
  if (process.platform === "darwin") {
    return createFallbackStorage(macOsKeychainStorage, plainTextStorage)
  }
  // TODO: add libsecret support for Linux
  return plainTextStorage
}

The TODO comment has been in the codebase through the review period. Every Linux user, every Docker container, every CI/CD pipeline uses plaintext credential storage.

Conversation History in Plaintext (CVSS 7.0)

Location: history.ts:115 CWE: CWE-312

All conversation history -- including pasted API keys, tokens, and passwords -- persists in plaintext JSONL at ~/.claude/history.jsonl. Small pastes (under 1024 chars) are stored inline. Larger pastes go to ~/.claude/paste-cache/{sha256}.txt. No TTL, no automatic purging, no secret detection. The file permissions are 0600, providing the same insufficient protection as credential storage.

Finding 11 deserves particular attention. The entire bash security validation chain -- 100+ injection patterns, heredoc analysis, zsh exploit blocking -- depends on a custom shell-quote parser for initial tokenization. If this parser misparses a command differently than the actual shell, all downstream validators operate on incorrect tokens. Six dedicated misparsing validators (validateCarriageReturn, validateBackslashEscapedOperators, validateMalformedTokens, etc.) are reactive patches for known divergences. The architecture is fundamentally fragile: a single unknown parser bug bypasses everything. As we'll see in Chapter 21, adding tree-sitter-bash as a secondary parser for cross-validation is the architectural answer.

1.7 Risk Quantification

Raw CVSS scores tell you severity. Risk quantification tells you what to fix first. Three dimensions matter for a CLI tool deployed on developer machines:

Blast Radius

How many users are affected if a vulnerability is exploited?

Blast Radius Vulnerability Users Affected
All users Plugin signature (CVSS 9.1) Every CLI installation
All Linux users Plaintext credentials (CVSS 7.1) ~40% of installations
Bridge users JWT no-verify (CVSS 7.5) Enterprise deployments

The blast radius analysis reveals that 20% of findings (the two CRITICALs and eight HIGHs) account for approximately 80% of the affected user population. This is not unusual -- it follows the Pareto distribution common in security risk catalogs -- but it has direct implications for remediation sequencing. As we'll detail in Chapter 3, the implementation roadmap prioritizes by blast radius first, then by exploitability.

The low-barrier attacks are particularly concerning for CI/CD environments. Container escape or shared filesystem access -- both common in build systems -- provides sufficient access to steal credentials from the plaintext storage path. Organizations running Claude Code in CI pipelines should treat Findings 7, 8, and 10 as immediate blockers.

The medium-barrier attacks require network positioning, making them relevant for enterprise deployments where corporate proxies inspect TLS traffic. Finding 5 (JWT without signature verification) becomes especially dangerous in environments with mandatory MITM proxies, because the proxy is already in position to modify the JWT payload.

1.8 The Architecture Behind the Vulnerabilities

Understanding why these vulnerabilities exist requires examining Claude Code's architecture. The system is a 512K-line TypeScript codebase running on the Bun runtime, using React/Ink for terminal UI and Commander.js for CLI parsing. Four trust boundaries exist in this architecture:

  1. Input Validation -- bashSecurity.ts (100+ patterns), pathValidation.ts, schema validation for MCP results, SHA-256 hash verification for plugins
  2. Permission & Policy -- toolPermission/ allow/deny rules, shouldUseSandbox.ts, MCP tool approval prompts, policy rate limits
  3. Secure Storage -- macOS Keychain (primary), plaintext JSON fallback (non-macOS)
  4. Shell Execution -- sandboxed shell process with path-validated access

The vulnerabilities concentrate at boundary transitions:

  • Boundary 1 gaps: Plugin downloads cross the input validation boundary with integrity checks but no authenticity checks (Findings 1, 2). ZIP extraction crosses with path traversal checks but no symlink resolution (Finding 4).
  • Boundary 2 gaps: Subagents cross the permission boundary with name-based tool filtering instead of process isolation (Finding 3). The dangerouslySkipPermissions flag can be forwarded to remote servers (Finding 12).
  • Boundary 3 gaps: On non-macOS platforms, the secure storage boundary does not exist -- credentials go directly to plaintext files (Findings 7, 8, 10).
  • Boundary 4 gaps: The bash security boundary depends on a single parser that may diverge from real shell behavior (Finding 11).

OWASP Top 10 Coverage

The most dense coverage gaps cluster around three OWASP categories:

A02:2021 -- Cryptographic Failures carries five findings totaling a combined CVSS of 36.2. This category encompasses both the plaintext storage issues (no encryption at rest) and the JWT verification gap (no signature checking). For a tool that handles API keys and session tokens, cryptographic failures represent the most fundamental security gap. The remediation spans Phases 2 and 3 of the roadmap.

A08:2021 -- Software and Data Integrity Failures carries four findings including both CRITICALs. The complete absence of code signing for plugins places Claude Code in the worst-case position for this category. Any tool that downloads and executes third-party code without signature verification fails A08 categorically. Phase 1 of the roadmap addresses this directly.

A04:2021 -- Insecure Design carries three findings (3, 6, 14) that together describe a system where third-party code executes with full host privileges. The subagent isolation gap is a design-level issue -- it cannot be fixed with a patch to a single function. It requires a new architecture for how untrusted code executes. Phase 4 addresses this with the process isolation redesign.

Enterprise Adoption Implications

For organizations evaluating Claude Code for developer workflows, the compliance analysis produces three categories:

Deploy now with compensating controls: The bash security subsystem (100+ injection patterns, sandbox enforcement) is robust. The OAuth PKCE implementation is correct (Finding 50 confirms this). The permission system provides meaningful access control for local use.

Deploy after Phase 2: Once credential storage is encrypted across platforms, the tool meets baseline requirements for SOC 2 CC6.1 and HIPAA 164.312(a)(2)(iv). This unlocks deployment in regulated industries.

Deploy after Phase 4: Process isolation for third-party plugins and MCP servers is required for environments where untrusted extensions may be installed. Until Phase 4, restricting to first-party plugins is a viable compensating control.

1.10 What Comes Next

This chapter has mapped the battlefield. You know the 50 vulnerabilities, their severities, their locations, and their compliance implications. But individual findings do not exist in isolation.

Chapter 2 dissects the seven dependency chains -- groups of vulnerabilities that interact with each other through shared code paths, shared data, or shared trust assumptions. A fix for one vulnerability in a chain can cascade to reduce risk across the entire group. Conversely, leaving the root of a chain unpatched means downstream fixes provide only partial protection.

Chapter 3 translates these chains into an implementation roadmap: seven phases, ordered by risk and dependency relationships, with resource estimates for the 35 direct patches and 15 architecture solutions.

The remaining 19 chapters of this book provide the exact code changes, test cases, and verification procedures for every finding in the catalog. Each chapter takes one dependency chain or remediation phase and walks through the complete fix -- from understanding the vulnerable code to deploying the hardened version to verifying it works.

This is not theory. This is a 50-item punch list with working patches. Let's get to work.
