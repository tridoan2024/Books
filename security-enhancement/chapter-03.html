Chapter 3: Implementation Roadmap

You have the vulnerability map from Chapter 1. You have the dependency chains from Chapter 2. Now you need a plan that accounts for risk ordering, implementation dependencies, and resource constraints. This chapter defines the seven-phase remediation plan: 35 direct patches and 15 architecture solutions, sequenced to maximize risk reduction per engineering hour invested.

3.1 Roadmap Design Principles

Five principles drive the phase sequencing:

Principle 1: Highest blast radius first. The Plugin Supply Chain chain (Findings 1, 2, 4, 15) affects every CLI user who installs marketplace plugins. It is Phase 1 regardless of implementation complexity.

Principle 2: Prerequisites before dependents. Credential storage encryption (Phase 2) must precede token lifecycle hardening (Phase 3) because rotating tokens into a plaintext backend provides minimal security improvement.

Principle 3: Direct patches before architecture changes. Within each phase, deploy direct patches (code-level fixes that do not change interfaces or data flows) before architecture solutions (changes to system design, new infrastructure, cross-team coordination). Direct patches provide immediate risk reduction while architecture work proceeds.

Principle 4: Defense in depth at every phase. Each phase should leave the system in a strictly better security state, even if subsequent phases are delayed or deprioritized. No phase should introduce regression risk.

Principle 5: Testable milestones. Each phase has defined success metrics that can be verified without human judgment: specific tests that pass, specific attack scenarios that fail, specific compliance checkboxes that clear.

The ZIP extraction fix is self-contained and can be deployed immediately:

// utils/plugins/zipCache.ts -- extractZipToDirectory()
import { realpath, unlink } from 'fs/promises'
import { resolve, sep } from 'path'

const canonicalTarget = await realpath(targetDir)
const targetPrefix = canonicalTarget + sep

for (const [relPath, data] of Object.entries(files)) {
  const fullPath = join(canonicalTarget, relPath)
  const resolvedPath = resolve(fullPath)

  // Pre-write: verify resolved path stays within extraction root
  if (!resolvedPath.startsWith(targetPrefix) && resolvedPath !== canonicalTarget) {
    throw new Error(
      `Zip entry escapes target directory: ${relPath} resolves to ${resolvedPath}`
    )
  }

  await getFsImplementation().mkdir(dirname(fullPath))
  await writeFile(fullPath, data)

  // Post-write: catch symlink TOCTOU where parent dir replaced between mkdir and write
  const realWrittenPath = await realpath(fullPath)
  if (!realWrittenPath.startsWith(targetPrefix)) {
    await unlink(fullPath).catch(() => {})
    throw new Error(
      `Zip extraction TOCTOU: ${relPath} wrote to ${realWrittenPath} outside target`
    )
  }
}

Verification: - Unit: ZIP entry with ../../etc/passwd rejected before write - Unit: ZIP entry resolving outside target via symlink rejected - Unit: Normal ZIP with nested directories extracts successfully - Unit: Post-write realpath check detects symlink TOCTOU

The atomic write fix eliminates the TOCTOU window between writeFileSync and chmodSync:

// utils/secureStorage/plainTextStorage.ts -- update()
import { openSync, writeSync, closeSync, fsyncSync, renameSync, unlinkSync } from 'fs'

async update(
  updater: (data: Record<string, unknown>) => Record<string, unknown>,
): Promise<void> {
  const storagePath = getStoragePath()
  const dir = dirname(storagePath)
  if (!existsSync(dir)) {
    mkdirSync(dir, { recursive: true, mode: 0o700 })
  }
  const existing = await this.read()
  const updated = updater(existing ?? {})

  // Atomic write: file created with 0o600 from the start
  const tmpPath = storagePath + '.tmp.' + process.pid
  try {
    const fd = openSync(tmpPath, 'w', 0o600)
    try {
      writeSync(fd, jsonStringify(updated), 0, 'utf8')
      fsyncSync(fd)
    } finally {
      closeSync(fd)
    }
    renameSync(tmpPath, storagePath)
  } catch (err) {
    try { unlinkSync(tmpPath) } catch { /* ignore */ }
    throw err
  }
}

Verification: - Unit: update() creates file with 0o600 permissions atomically (no 0o644 window) - Unit: update() uses atomic rename (no half-written credential file) - Unit: update() cleans up temp file on write failure - Integration: stat() after update() confirms mode 0o600

The clampTokenRefreshDelay() function is the highest-leverage patch in this phase:

// bridge/jwtUtils.ts
const MAX_TOKEN_LIFETIME_MS = 24 * 60 * 60 * 1000 // 24 hours
const MIN_REFRESH_DELAY_MS = 10_000 // 10 seconds

function clampTokenRefreshDelay(rawDelayMs: number): number {
  if (rawDelayMs <= 0) return 0
  if (rawDelayMs < MIN_REFRESH_DELAY_MS) return MIN_REFRESH_DELAY_MS
  if (rawDelayMs > MAX_TOKEN_LIFETIME_MS) return MAX_TOKEN_LIFETIME_MS
  return rawDelayMs
}

Combined with Number.isFinite() validation and reasonable range checks on the exp claim:

export function decodeJwtExpiry(token: string): number | null {
  const payload = decodeJwtPayload(token)
  if (
    payload !== null &&
    typeof payload === 'object' &&
    'exp' in payload &&
    typeof payload.exp === 'number' &&
    Number.isFinite(payload.exp)
  ) {
    const MIN_REASONABLE_EXP = 1577836800 // 2020-01-01
    const MAX_REASONABLE_EXP = Math.floor(Date.now() / 1000) + 365 * 24 * 60 * 60
    if (payload.exp < MIN_REASONABLE_EXP || payload.exp > MAX_REASONABLE_EXP) {
      return null
    }
    return payload.exp
  }
  return null
}

Verification: - Unit: clampTokenRefreshDelay(0) returns 0 - Unit: clampTokenRefreshDelay(5000) returns MIN_REFRESH_DELAY_MS (10000) - Unit: clampTokenRefreshDelay(48 * 3600 * 1000) returns MAX_TOKEN_LIFETIME_MS - Unit: decodeJwtExpiry rejects NaN and Infinity exp claims - Unit: decodeJwtExpiry rejects exp before 2020 and more than 1 year in the future - Unit: Token prefix no longer appears in debug output

The fork depth enforcement replaces the single-layer boilerplate check:

const MAX_FORK_DEPTH = 3
const FORK_DEPTH_TAG = 'fork-depth'

export function getForkDepth(messages: MessageType[]): number {
  let maxDepth = 0
  for (const m of messages) {
    if (m.type !== 'user') continue
    const content = m.message.content
    if (!Array.isArray(content)) continue
    for (const block of content) {
      if (block.type !== 'text') continue
      const match = block.text.match(
        new RegExp(`<${FORK_DEPTH_TAG}>(\\d+)</${FORK_DEPTH_TAG}>`),
      )
      if (match) {
        const depth = parseInt(match[1], 10)
        if (depth > maxDepth) maxDepth = depth
      }
    }
  }
  return maxDepth
}

export function canFork(
  messages: MessageType[],
): { allowed: true } | { allowed: false; reason: string } {
  const depth = getForkDepth(messages)
  if (depth >= MAX_FORK_DEPTH) {
    return {
      allowed: false,
      reason: `Maximum fork depth (${MAX_FORK_DEPTH}) reached. Cannot create nested subagent at depth ${depth + 1}.`,
    }
  }
  return { allowed: true }
}

// Patterns that indicate secrets in pasted content
const SECRET_PATTERNS = [
  /(?:sk|pk|api[_-]?key|token|secret|password|bearer)\s*[:=]\s*\S{20,}/gi,
  /(?:AKIA|ABIA|ACCA|ASIA)[A-Z0-9]{16}/g,  // AWS access key
  /ghp_[A-Za-z0-9_]{36}/g,                   // GitHub PAT
  /gho_[A-Za-z0-9_]{36}/g,                   // GitHub OAuth
  /sk-[A-Za-z0-9]{20,}/g,                    // OpenAI/Anthropic keys
  /-----BEGIN (?:RSA |EC )?PRIVATE KEY-----/g,
]

function redactSecrets(text: string): string {
  let redacted = text
  for (const pattern of SECRET_PATTERNS) {
    redacted = redacted.replace(pattern, '[REDACTED]')
  }
  return redacted
}

3.13 Rollback Strategy

Every patch and architecture change must be independently rollbackable. The rollback strategy varies by fix type:

Direct patches: Feature-flagged behind environment variables. Rolling back means setting the flag:

const USE_SECURE_ZIP_EXTRACTION = process.env.CLAUDE_LEGACY_ZIP !== '1'

Architecture solutions: Blue-green deployment with fallback to previous storage backend:

// Credential storage migration with rollback
const storage = getSecureStorage()
try {
  await storage.write(credentials)
} catch (err) {
  // Fallback to previous storage on migration failure
  logForDebugging(`Secure storage write failed, falling back: ${err.message}`)
  await legacyStorage.write(credentials)
}

Cross-team changes (signing infrastructure, JWKS endpoints): Version negotiation where the client accepts both signed and unsigned plugins during a transition period, with unsigned acceptance sunset after a defined date.
