Chapter 2: Vulnerability Dependency Chain Analysis

Individual vulnerabilities are dangerous. Vulnerability chains are catastrophic. A MEDIUM-severity path traversal in ZIP extraction becomes a full code execution primitive when combined with an unsigned plugin download. A LOW-severity token override via environment variable becomes persistent unauthorized access when combined with a JWT that is decoded but never signature-verified.

This chapter dissects the seven dependency chains identified in Claude Code's vulnerability catalog. Each chain represents a group of findings that interact through shared code paths, shared data flows, or shared trust assumptions. Understanding these chains is prerequisite to the implementation roadmap in Chapter 3 -- you cannot sequence fixes correctly without knowing which vulnerabilities are load-bearing for others.

2.1 What Is a Dependency Chain?

A vulnerability dependency chain exists when exploiting one finding either enables or amplifies another. The relationship can be:

  • Sequential: Finding A must be exploited before Finding B becomes reachable (e.g., unsigned plugin download enables path traversal in extraction)
  • Amplifying: Finding A increases the blast radius of Finding B (e.g., plaintext credential storage makes token theft trivially easy once filesystem access is gained)
  • Compensating: Fixing Finding A partially mitigates Finding B even without a direct patch (e.g., process isolation for subagents limits damage from missing MCP sandboxing)

The seven chains span the entire vulnerability catalog. Some findings appear in multiple chains -- these are the highest-leverage fix targets. Others are chain-terminal findings that represent the final impact of an exploitation path.

2.2 Chain 1: Plugin Supply Chain

Severity: CRITICAL Findings: #1 (CVSS 9.1), #2 (CVSS 8.1), #4 (CVSS 7.5), #15 (CVSS 6.1), #25 (CVSS 5.3), #29 (CVSS 4.8) Affected Files: plugins/, utils/plugins/pluginLoader.ts, utils/plugins/marketplaceManager.ts, utils/plugins/zipCache.ts, utils/dxt/zip.ts, utils/plugins/pluginVersioning.ts Blast Radius: Full code execution on every developer machine that installs marketplace plugins

This is the highest-risk chain in the codebase. It flows from marketplace download through extraction to execution with no authenticity verification at any point.

The Attack Path

sequenceDiagram
    participant Attacker
    participant CDN as Marketplace CDN
    participant CLI as Claude Code CLI
    participant FS as Developer Filesystem

    Attacker->>CDN: Compromise marketplace entry or MITM download
    CDN->>CLI: Malicious plugin ZIP (valid hash, no signature)
    CLI->>CLI: SHA-256 hash check passes (computed over malicious payload)
    CLI->>FS: Extract ZIP
    Note over CLI,FS: #4: Symlinks followed without boundary check
    Note over CLI,FS: #15: No canonical path resolution
    CLI->>CLI: Register plugin
    Note over CLI: #29: Version uses 12-char git SHA (collision risk)
    CLI->>CLI: Plugin executes with full process privileges
    Note over CLI: Shell access, filesystem access, network access, credential access

The chain has five links:

  1. Root (Findings 1 + 2): No cryptographic signature verification. The marketplace JSON is fetched via axios.get() with no integrity check. Plugin ZIPs are downloaded without signature verification against a known author key. Hash checks confirm the download was not corrupted but do not verify authenticity.

  2. Extraction (Findings 4 + 15): Even if the ZIP contents were validated for authenticity, the extraction path has its own vulnerabilities. zipCache.ts:292-300 follows symlinks without validating that targets remain within the extraction root. The join() path construction does not canonicalize, allowing symlink-based escapes.

  3. Validation Gap (Finding 25): ZIP bomb detection occurs during extraction but not pre-download. There is no pre-flight check on the ZIP size from Content-Length headers. A multi-gigabyte ZIP bomb could consume disk and memory during extraction.

  4. Version Weakness (Finding 29): Plugin versions use 12-character git SHAs. While a 12-char hex prefix provides 48 bits of entropy (making random collisions improbable), targeted collision attacks against shortened hashes are well-documented. With sufficient compute, an attacker could produce a malicious commit with the same 12-character prefix as a legitimate plugin version.

Cascade Effect

Fixing Finding 1 (cryptographic plugin signing) provides the highest cascade reduction in the entire codebase. With signature verification in place:

  • Finding 2 is fully mitigated (signature covers the download)
  • Finding 4 is partially mitigated (a signed, authentic plugin is unlikely to contain malicious symlinks)
  • Finding 15 is partially mitigated (same reasoning)
  • Finding 25 is partially mitigated (signed plugins have known expected sizes)
  • Finding 29 is partially mitigated (signatures provide stronger version binding than hashes)

However, Findings 4 and 15 still require independent fixes because the path traversal defense should be robust against any ZIP input, not just malicious plugins. Defense in depth requires that extraction is safe regardless of whether the source is trusted. As we'll detail in Chapter 5, the three-layer defense for ZIP extraction (pre-extraction validation, canonical path resolution, post-write TOCTOU verification) should be implemented even after signing infrastructure is in place.

Implementation Dependency

Findings 4 and 15 can be fixed independently with direct patches to zipCache.ts. The fix is a realpath-based boundary check:

// Secure extraction with canonical path resolution
const canonicalTarget = await realpath(targetDir)
const targetPrefix = canonicalTarget + sep

for (const [relPath, data] of Object.entries(files)) {
  const fullPath = join(canonicalTarget, relPath)
  const resolvedPath = resolve(fullPath)

  // Reject any path that escapes the extraction root
  if (!resolvedPath.startsWith(targetPrefix) && resolvedPath !== canonicalTarget) {
    throw new Error(
      `Zip entry escapes target directory: ${relPath} resolves to ${resolvedPath}`
    )
  }

  // Post-write verification catches symlink TOCTOU
  await writeFile(fullPath, data)
  const realWrittenPath = await realpath(fullPath)
  if (!realWrittenPath.startsWith(targetPrefix)) {
    await unlink(fullPath).catch(() => {})
    throw new Error(
      `Zip extraction TOCTOU: ${relPath} wrote to ${realWrittenPath} outside target`
    )
  }
}

Findings 1 and 2 require architecture changes (ECDSA signing infrastructure, marketplace integration, key management) and are addressed in Chapters 4 and 5.

2.3 Chain 2: Credential Storage

Severity: HIGH Findings: #7 (CVSS 7.1), #8 (CVSS 7.1), #10 (CVSS 6.5), #20 (CVSS 5.5), #30 (CVSS 4.7), #37 (CVSS 3.7), #39 (CVSS 3.3) Affected Files: utils/secureStorage/index.ts, utils/secureStorage/plainTextStorage.ts, utils/secureStorage/macOsKeychainStorage.ts, utils/secureStorage/fallbackStorage.ts Blast Radius: OAuth tokens, API keys, and trusted device tokens exposed on all non-macOS platforms and macOS fallback scenarios

This chain targets the credential lifecycle from storage to retrieval, with every link weakening the protection of the most sensitive data in the system.

The Storage Decision Tree

The current credential storage architecture makes a single platform check:

flowchart TD
    A["getSecureStorage()"] --> B{"process.platform === 'darwin'?"}
    B -->|Yes| C["createFallbackStorage(keychain, plaintext)"]
    B -->|No| D["plainTextStorage<br/>#7: CWE-256 CVSS 7.1"]
    C --> E{"Keychain write succeeds?"}
    E -->|Yes| F["macOS Keychain<br/>(secure)"]
    E -->|No| G["plainTextStorage fallback<br/>#8: CWE-312 CVSS 7.1"]
    D --> H["~/.claude/.credentials.json<br/>chmod 0600<br/>Plaintext JSON"]
    G --> H
    H --> I{"writeFileSync then chmodSync"}
    I --> J["#30: TOCTOU race<br/>Permission window between write and chmod"]

Every non-macOS platform -- Linux desktops, WSL, Windows, Docker containers, CI/CD runners -- takes the plaintext path. On macOS, Docker containers and SSH sessions typically fail the keychain path and silently fall back to plaintext.

Chain Links

  1. Root (Findings 7 + 10): getSecureStorage() at index.ts:9 returns plainTextStorage for all non-macOS platforms. The TODO comment "add libsecret support for Linux" confirms this is a known gap. OAuth tokens and API keys are stored as JSON with only chmod 0600 protection.

  2. Fallback Amplifier (Finding 8): On macOS, when keychain fails (Docker, SSH, CI), fallbackStorage.ts silently activates plaintext storage. The createFallbackStorage wrapper logs a warning but proceeds. The fallback path at plainTextStorage.ts:57 writes credentials with writeFileSync then applies chmodSync(0o600) -- creating a TOCTOU window.

  3. TOCTOU Race (Finding 30): The write-then-chmod pattern at plainTextStorage.ts:57 creates a window where the file exists with default permissions (potentially 0o644) before chmodSync applies 0o600. Any process monitoring the directory can read credentials during this window.

  4. Keychain Injection (Finding 20): The macOS keychain read path at macOsKeychainStorage.ts:39 constructs shell commands with credential data. If a service name contains shell metacharacters, command injection is possible in the sync fallback path.

  5. Process Argument Leak (Finding 37): The keychain fallback path at macOsKeychainStorage.ts:118 passes credentials as command-line arguments, making them visible in ps output and /proc/*/cmdline.

  6. Migration Race (Finding 39): fallbackStorage.ts:37 implements credential migration from primary to fallback storage with a race condition -- concurrent migrations can corrupt the credential file.

Cascade Effect

Fixing Finding 7 (implementing libsecret for Linux and Windows Credential Manager for Windows) eliminates Findings 10 and 8 for their primary platforms. The plaintext path becomes a last-resort fallback rather than the default for 40%+ of installations.

Fixing Finding 30 (atomic credential writes with O_CREAT|O_EXCL, fsync, and rename) eliminates the TOCTOU window regardless of which storage backend is active:

// Atomic write: create temp file with correct permissions, then rename
const tmpPath = storagePath + '.tmp.' + process.pid
const fd = openSync(tmpPath, 'w', 0o600)
try {
  writeSync(fd, jsonStringify(updated), 0, 'utf8')
  fsyncSync(fd)
} finally {
  closeSync(fd)
}
renameSync(tmpPath, storagePath)

The credential storage chain has a strong dependency on the Auth Token Lifecycle chain (Chain 3). Secure credential storage is prerequisite to safe token rotation -- if the storage is plaintext, rotating tokens provides minimal additional security because both old and new tokens are equally exposed. This dependency drives the phase ordering in Chapter 3: credential storage (Phase 2) must precede token lifecycle hardening (Phase 3).

2.4 Chain 3: Auth Token Lifecycle

Severity: HIGH Findings: #5 (CVSS 7.5), #13 (CVSS 6.5), #16 (CVSS 5.9), #32 (CVSS 4.3), #34 (CVSS 4.3), #41 (CVSS 3.1) Affected Files: bridge/jwtUtils.ts, utils/auth.ts, bridge/trustedDevice.ts Blast Radius: JWT tokens decoded without signature verification, env var tokens that never refresh, token prefixes leaked in debug logs

This chain targets the complete lifecycle of authentication tokens from issuance through verification, refresh, and eventual expiration.

The Token Flow

sequenceDiagram
    participant Server as Auth Server
    participant CLI as Claude Code
    participant JWT as jwtUtils.ts
    participant Auth as auth.ts
    participant Trust as trustedDevice.ts
    participant Log as Debug Logs

    Note over JWT: #5: Base64 decode ONLY<br/>No signature verification

        Trust->>Trust: Read from keychain

    end

    CLI->>Log: logForDebugging()
    Note over Log: #32: token.slice(0,15) logged<br/>#41: JWT prefix in debug output

Chain Links

  1. Root (Finding 5): decodeJwtPayload() at jwtUtils.ts:21 performs base64 decoding without signature verification. The exp claim from the unverified payload directly controls token refresh scheduling. An attacker who can modify the JWT in transit (via corporate proxy, compromised DNS, or MITM on the bridge connection) can forge arbitrary claims.

  2. Timer Manipulation (Finding 16): The schedule() function computes delayMs = expiry * 1000 - Date.now() - refreshBufferMs directly from the unverified exp claim. A far-future exp (year 2100) sets a delay of ~74 years, effectively suppressing token refresh forever. A near-past exp triggers constant refresh attempts (DoS). No bounds checking exists on the computed delay.

  3. Token Persistence (Finding 13): Tokens provided via ANTHROPIC_API_KEY environment variable at auth.ts:1260 never expire and never refresh. Even if the server revokes the token, the CLI continues using it until the process exits. In CI/CD pipelines, this means leaked tokens remain valid indefinitely.

  4. Device Token Override (Finding 34): The CLAUDE_DEVICE_TOKEN environment variable at trustedDevice.ts:46 overrides the keychain-stored device trust token. Combined with Finding 13, an attacker who sets this env var gains persistent device-level trust without keychain access.

  5. Debug Log Leakage (Findings 32 + 41): Token prefixes appear in debug output at jwtUtils.ts:112 and jwtUtils.ts:110 via token.slice(0, 15). While 15 characters of a token prefix have limited direct value, they confirm token format, aid in targeted attacks, and may violate compliance requirements for credential logging.

Cascade Effect

The primary fix for this chain is the clampTokenRefreshDelay() defense at the schedule function. This bounds the refresh delay to a safe range regardless of the JWT payload:

const MAX_TOKEN_LIFETIME_MS = 24 * 60 * 60 * 1000 // 24 hours
const MIN_REFRESH_DELAY_MS = 10_000 // 10 seconds

function clampTokenRefreshDelay(rawDelayMs: number): number {
  if (rawDelayMs <= 0) return 0
  if (rawDelayMs < MIN_REFRESH_DELAY_MS) return MIN_REFRESH_DELAY_MS
  if (rawDelayMs > MAX_TOKEN_LIFETIME_MS) return MAX_TOKEN_LIFETIME_MS
  return rawDelayMs
}

This single function mitigates Findings 5 and 16 simultaneously. The ideal fix (client-side JWKS-based signature verification) requires server-side changes to publish a JWKS endpoint, making it a longer-term solution explored in Chapter 10. The clamp is an immediate compensating control that limits damage even without signature verification.

Removing token.slice(0, 15) from debug log statements (Findings 32, 41) is a zero-risk, zero-dependency fix that can be applied in any phase.

2.5 Chain 4: Subagent Isolation

Severity: HIGH Findings: #3 (CVSS 7.8), #6 (CVSS 7.5), #14 (CVSS 6.2) Affected Files: tools/AgentTool/runAgent.ts, tools/AgentTool/forkSubagent.ts, services/mcp/ Blast Radius: Subagents and MCP server tools execute with full parent process privileges; recursive forking possible

This is the shortest chain but carries severe consequences. Three findings combine to create a scenario where a malicious plugin can achieve persistent, escalating access through the agent system.

The Exploitation Scenario

    A["Malicious plugin defines agent"] --> B["runAgent() loads agent<br/>in parent process<br/>#3: CWE-269 CVSS 7.8"]
    B --> C["Agent inherits all tools<br/>Name-based filtering only<br/>Not process-level isolation"]
    C --> D["Agent accesses shared AppState<br/>Can read credentials, history"]

    J["MCP server tool approved"] --> K["Tool executes in CLI process<br/>#6: CWE-250 CVSS 7.5"]

Chain Links

  1. Root (Finding 3): runAgent.ts:248 runs subagents in the parent Bun process. At lines 332-338, the agent shares AppState. At lines 465-479, tool restriction is name-based filtering -- not process-level isolation. At lines 567-575, agent frontmatter hooks execute in the parent context. A malicious subagent has full access to credentials, filesystem, network, and the tool registry.

  2. MCP Amplifier (Finding 6): MCP server tools execute within the CLI process's security context with no sandboxing. The services/mcp/channelPermissions.ts implements permission prompts but not isolation. Once a user approves an MCP tool, it runs with complete CLI privileges. Combined with Finding 3, an MCP server can spawn agents that inherit the same unrestricted access.

  3. Recursive Forking (Finding 14): forkSubagent.ts:311 implements fork depth checking via isInForkChild(), which only detects a single-layer boilerplate tag. The function answers "am I in a fork child?" but not "how deep am I?" A child agent retains the AgentTool, enabling recursive forking. Each fork inherits the full tool set. The only limit is memory exhaustion.

Cascade Effect

This chain has a strong dependency on Chain 1 (Plugin Supply Chain). If plugin signing is implemented (Findings 1, 2), the probability of a malicious plugin being installed drops significantly. However, the subagent isolation fix is still necessary because:

  1. Legitimate plugins may be compromised through supply chain attacks
  2. MCP servers from the marketplace may contain vulnerabilities
  3. Defense in depth requires isolation regardless of source trust

The fix architecture involves three layers:

  • Process isolation (Finding 3): child_process.fork() with IPC channels for plugin-sourced agents
  • Fork depth enforcement (Finding 14): MAX_FORK_DEPTH=3 with cryptographic depth tracking via fork-depth tags
  • MCP sandboxing (Finding 6): seccomp-bpf profiles for Linux, sandbox-exec for macOS, capability-based restrictions per MCP server

The implementation order matters: fork depth enforcement (a direct patch, ~4-6 hours) should be deployed before process isolation (an architecture change, ~40+ hours) because it provides immediate protection against recursive fork bombs.

Chain Links

  1. Root (Finding 9): All conversation history including pasted secrets persists in plaintext JSONL at ~/.claude/history.jsonl. The history.ts:115 path stores small pastes inline, large pastes in ~/.claude/paste-cache/{sha256}.txt. No secret detection, no redaction, no TTL, no purging.

  2. Hardcoded Telemetry Token (Findings 24 + 26): services/analytics/datadog.ts:13-14 contains a hardcoded Datadog client token. This token enables 64+ event types to be sent to a third-party analytics service. The token is visible in source code, making it extractable.

  3. Third-Party Data Sharing (Finding 33): Telemetry data is sent to Datadog at datadog.ts:160 without explicit user consent UI. While an opt-out mechanism exists, it is not prominently surfaced during onboarding.

  4. Remote Configuration (Finding 38): The analytics pipeline is partially controlled by GrowthBook remote configuration at firstPartyEventLogger.ts:95. A compromised GrowthBook endpoint could enable additional data collection without CLI-side code changes.

  5. Debug Log Leakage (Finding 43): Debug logs at utils/debug.ts:221 may contain token prefixes, session IDs, and URLs. These logs persist on disk without rotation or sanitization.

  6. Incomplete Opt-Out (Finding 49): Analytics opt-out at services/analytics/config.ts:19 does not cover all data flows, leaving some telemetry active even when the user has opted out.

Cascade Effect

The conversation history fix (Finding 9) has the highest impact: implementing automatic secret detection and redaction prevents the most sensitive data from ever reaching disk. This reduces the value of all downstream data channels.

The telemetry fixes (Findings 24, 26, 33) require both code changes (token rotation, data minimization) and process changes (explicit consent UI). These are addressed in Chapter 19.

2.7 Chain 6: Bridge Remote Session

Severity: MEDIUM Findings: #12 (CVSS 6.5), #17 (CVSS 5.9), #18 (CVSS 5.9), #21 (CVSS 5.5), #22 (CVSS 5.4), #23 (CVSS 5.3), #28 (CVSS 5.0), #31 (CVSS 4.4), #42 (CVSS 3.1), #44 (CVSS 2.5), #45 (CVSS 3.2) Affected Files: server/createDirectConnectSession.ts, remote/SessionsWebSocket.ts, upstreamproxy/relay.ts, upstreamproxy/upstreamproxy.ts, tools/WebFetchTool/utils.ts, services/api/client.ts Blast Radius: Enterprise users with remote/bridge sessions and upstream proxy configurations

This is the largest chain by affected file count, connecting remote session management through WebSocket communication to upstream proxy infrastructure. The attack scenario involves a compromised proxy intercepting and manipulating bridge sessions.

The Attack Scenario

The chain enables a multi-step attack:

  1. Attacker compromises the upstream proxy or performs DNS spoofing on the proxy endpoint
  2. CA bundle is downloaded without certificate pinning (#18), allowing a forged CA to be installed
  3. The proxy intercepts the bridge WebSocket connection (#21, no client-side origin validation)
  4. Proxy credentials are visible in WebSocket headers (#22) and persist in memory (#23, #31)
  5. The dangerouslySkipPermissions flag is forwarded to the remote server (#12)
  6. Custom headers are injectable via environment variables (#28)
  7. The compromised session operates with no permission guardrails

Key Fix Points

The highest-leverage fix in this chain is the localhost restriction for dangerouslySkipPermissions:

// server/createDirectConnectSession.ts -- SECURE
const parsedServerUrl = new URL(serverUrl)
const isLocalServer =
  parsedServerUrl.hostname === 'localhost' ||
  parsedServerUrl.hostname === '127.0.0.1' ||
  parsedServerUrl.hostname === '::1'

if (dangerouslySkipPermissions && !isLocalServer) {
  throw new DirectConnectError(
    'dangerouslySkipPermissions is only allowed for localhost connections. ' +
      `Refusing to send to remote server: ${parsedServerUrl.hostname}`
  )
}

This single check (Finding 12) prevents the most dangerous part of the chain -- sending permission bypass flags to remote servers. The remaining findings in this chain are defense-in-depth improvements that should be implemented but are not individually exploitable without the permission bypass.

The CA certificate pinning fix (Finding 18) at upstreamproxy/upstreamproxy.ts:254 validates downloaded certificates against known fingerprints, preventing proxy CA impersonation. The SSRF guard (Finding 17) at WebFetchTool/utils.ts:262 blocks DNS rebinding attacks where a permitted domain resolves to internal IP addresses.

2.8 Chain 7: Bash Security Bypass

Severity: MEDIUM Findings: #11 (CVSS 6.8), #19 (CVSS 5.9), #27 (CVSS 5.0), #35 (CVSS 4.0), #46 (CVSS 3.1) Affected Files: tools/BashTool/bashSecurity.ts, tools/BashTool/bashPermissions.ts, tools/BashTool/modeValidation.ts, tools/FileWriteTool/FileWriteTool.ts Blast Radius: All CLI users via the bash execution path

This chain targets the command validation pipeline -- the most security-critical path in the entire codebase. The existing defenses are substantial (100+ injection patterns, 40+ validators), but the architecture has a fundamental fragility: it depends on a single parser that may diverge from real shell behavior.

The Parser Differential Problem

Chain Links

  1. Root (Finding 11): bashSecurity.ts:27 calls tryParseShellCommand() which uses the custom shell-quote parser. On parse failure, line 29 returns an empty array. Six dedicated misparsing validators cover known divergences, but they are reactive -- they cannot anticipate unknown parser bugs. The 450+ lines of heredoc handling in isSafeHeredoc increase the parser attack surface.

  2. ReDoS (Finding 19): Complex regex patterns in bashPermissions.ts:760 for environment variable stripping are susceptible to catastrophic backtracking. A crafted input could freeze the permission pipeline, effectively creating a denial-of-service against the security validation itself.

  3. TOCTOU in File Write (Finding 27): FileWriteTool/FileWriteTool.ts:267 has a race condition between the read-state check (verifying what the file currently contains) and the write operation. Between these two operations, the file could be replaced by a symlink or modified by another process.

  4. Accept Edits Mode (Finding 35): modeValidation.ts:37 auto-allows filesystem commands (including destructive operations like rm, mv, chmod) in acceptEdits mode without prompting the user. This bypasses the permission system for an entire class of dangerous operations.

  5. Inherent Risk Acknowledgment (Finding 46): This INFO-level finding at bashSecurity.ts:1 acknowledges that regex-based security validation cannot achieve the same correctness guarantees as a proper AST-based parser. It is the informational companion to Finding 11.

Cascade Effect

This chain is unique in that no single fix eliminates the root vulnerability. The parser differential problem (Finding 11) is architectural -- it requires adding a secondary parser (tree-sitter-bash) for cross-validation and implementing fuzz testing to discover unknown divergences. This is the most complex fix in the entire remediation plan.

However, the compensating controls are effective:

  • Fixing Finding 19 (replacing ReDoS-susceptible regex with iterative parsing) ensures the permission pipeline cannot be frozen
  • Fixing Finding 27 (atomic file operations in FileWriteTool) closes the TOCTOU window
  • Fixing Finding 35 (splitting acceptEdits mode for destructive vs. non-destructive operations) restores user prompts for dangerous commands

2.9 Cross-Chain Dependencies

Three critical dependency relationships span across chains:

Chain 1 (Plugin Supply Chain) --> Chain 4 (Subagent Isolation)

A malicious plugin (Chain 1) that defines a subagent exploits the lack of process isolation (Chain 4). Fixing Chain 1 reduces the probability of malicious plugins; fixing Chain 4 limits the damage if one gets through. Both chains must be hardened.

Chain 2 (Credential Storage) --> Chain 3 (Auth Token Lifecycle)

Token rotation (Chain 3) is only as secure as the storage where rotated tokens are kept (Chain 2). Implementing token rotation on a plaintext storage backend means both old and new tokens are equally exposed. This drives the phase ordering: credential storage encryption must precede token lifecycle hardening.

Chain 5 (Data Exfiltration) --> Chain 2 (Credential Storage)

Plaintext conversation history (Chain 5, Finding 9) may contain credentials. Even if the credential storage is encrypted (Chain 2), secrets pasted during sessions remain exposed in history files. Both chains must be independently secured.

2.10 Prioritization Framework

Given the seven chains and their dependencies, the prioritization framework for Chapter 3's implementation roadmap follows this logic:

  1. Fix the highest blast radius first: Plugin Supply Chain (Chain 1) affects every user who installs plugins
  2. Fix prerequisites before dependents: Credential Storage (Chain 2) before Token Lifecycle (Chain 3)
  3. Fix enablers before amplifiers: Plugin signing (Chain 1) before subagent isolation (Chain 4)
  4. Fix high-urgency before low-urgency: Direct patches with known exploits before defense-in-depth improvements
  5. Batch by affected subsystem: Group fixes that touch the same files to minimize merge conflicts and regression risk

This prioritization produces the seven-phase roadmap detailed in Chapter 3, where each phase addresses one or more complete dependency chains while respecting the inter-chain dependencies documented in this chapter.
