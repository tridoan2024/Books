Chapter 4: Cryptographic Plugin Signing

The plugin supply chain is the highest-blast-radius attack surface in Claude Code. A compromised marketplace plugin executes arbitrary code on every developer machine that installs it --- no sandbox, no isolation, no signature verification. This chapter implements ECDSA-P256 code signing from scratch: the cryptographic primitives, the certificate authority infrastructure, the marketplace integration points, and the verification pipeline that stands between a downloaded ZIP archive and execution on a developer's workstation.

Findings 1 and 2 from the security assessment rated this vulnerability at CVSS 9.1 and 8.1 respectively --- CRITICAL severity. The attack chain flows: marketplace download, no signature verification, ZIP extraction, plugin loads into CLI process, MCP server spawned in-process, full tool access. Every step in this chain trusts the previous step. Cryptographic signing breaks this transitive trust by introducing an independently verifiable proof of authenticity at the earliest possible point.

4.1 The Vulnerability: CWE-494 in Production

CWE-494 (Download of Code Without Integrity Check) describes software that downloads and executes code from a remote source without verifying that the code has not been modified in transit or at the source. In Claude Code, two distinct code paths exhibit this vulnerability.

The first is in pluginLoader.ts, where loadPluginFromMarketplaceEntry() downloads a ZIP archive and extracts it without any cryptographic verification:

// VULNERABLE: pluginLoader.ts - loadPluginFromMarketplaceEntry()
// Downloads and extracts ZIP without verifying authenticity:
const zipBuf = await getFsImplementation().readFileBytes(zipPath)
const files = await unzipFile(zipBuf)
// ... extracts directly, no signature check

The second is in marketplaceManager.ts, where the marketplace JSON index is fetched via axios.get() with no integrity check. The GCS .gcs-sha sentinel file --- ostensibly an integrity mechanism --- is written by the same extraction process that handles the download, creating a TOCTOU (Time of Check to Time of Use) race condition. The sentinel verifies that extraction completed, not that the content is authentic.

The schema definition in schemas.ts reinforces the gap: PluginMarketplaceEntrySchema has no signature field. The LoadedPlugin type has no signature verification state. The type system itself encodes the assumption that plugins are trustworthy.

Attack Scenarios

Three realistic attack scenarios exploit this vulnerability:

Marketplace compromise. An attacker gains write access to the GCS bucket hosting marketplace plugins. They replace a popular plugin's ZIP with a modified version containing a malicious postinstall script. Every developer who installs or updates the plugin executes the attacker's code.

DNS hijacking. An attacker redirects the marketplace domain to a server they control. The CLI fetches a crafted marketplace JSON index listing plugins with attacker-controlled download URLs. Since no signature verification occurs, the attacker's plugins install identically to legitimate ones.

Dependency confusion. An attacker publishes a plugin with the same name as a popular internal plugin on a third-party marketplace. If the CLI's marketplace resolution order checks third-party sources before internal ones, the malicious plugin takes priority.

All three attacks are defeated by cryptographic signing. The attacker can modify the ZIP, redirect the download, or impersonate the publisher --- but they cannot produce a valid signature without the publisher's private key.

4.2 Cryptographic Primitives: Why ECDSA-P256

The signing scheme must satisfy four constraints: security strength sufficient for a code signing use case (at least 128-bit security level), performance acceptable for CLI startup (verification in under 50ms), key size small enough to embed in marketplace JSON without bloating responses, and compatibility with Node.js/Bun crypto APIs without external dependencies.

Algorithm Security Level Signature Size Verification Speed Node.js Native
RSA-2048 112-bit 256 bytes ~0.5ms Yes
RSA-4096 128-bit 512 bytes ~1.5ms Yes
ECDSA-P256 128-bit 64 bytes (DER: ~72) ~0.3ms Yes
Ed25519 128-bit 64 bytes ~0.1ms Yes (Node 18+)
ECDSA-P384 192-bit 96 bytes (DER: ~104) ~0.5ms Yes

ECDSA-P256 (also called secp256r1 or prime256v1) is the right choice for this use case. Ed25519 is faster and simpler but has weaker ecosystem support for certificate chains --- we need a CA infrastructure, not just standalone key pairs. RSA-4096 provides equivalent security but with 7x larger signatures and slower verification. P-384 is overkill; 128-bit security is the standard target for code signing in 2026.

The signing algorithm is ECDSA-P256-SHA256: the ZIP archive's SHA-256 digest is computed, then signed with the publisher's P-256 private key. Verification recomputes the digest from the downloaded ZIP and verifies the signature against the publisher's public key.

4.3 Implementation: The Signing Module

The implementation lives in a new file, utils/plugins/pluginSignature.ts. This is an architecture solution, not a direct patch --- it requires changes across four or more files and introduces a new module that the plugin loader calls before extraction.

Type Definitions

The signature metadata travels alongside the plugin in the marketplace entry JSON:

// utils/plugins/pluginSignature.ts

import { createHash, createVerify } from 'crypto'

export type PluginSignature = {
  /** Base64-encoded ECDSA signature over the ZIP file bytes */
  signature: string
  /** Identifier for the public key used to sign */
  keyId: string
  /** Algorithm identifier — only ecdsa-p256-sha256 supported */
  algorithm: 'ecdsa-p256-sha256'
}

export type SignatureVerificationResult = {
  verified: boolean
  error?: string
  keyId?: string
  digestHex?: string
}

export type SignaturePolicy = 'enforce' | 'warn' | 'off'

Three fields. The signature is the raw ECDSA output, base64-encoded for JSON transport. The keyId identifies which public key to use for verification --- this enables key rotation without breaking existing signatures. The algorithm is a fixed literal, enforcing that clients reject unknown algorithms rather than silently downgrading.

The SignaturePolicy type controls how verification failures are handled:

  • enforce: Unsigned or invalid plugins are rejected with an error. This is the production target.
  • warn: Unsigned or invalid plugins trigger a console warning but are allowed to install. This is the migration mode.
  • off: No verification performed. This exists for air-gapped environments with local-only plugins.

Trusted Key Registry

The verification function needs public keys. These come from two sources: Anthropic's marketplace signing key (built into the binary) and third-party publisher keys (accumulated via TOFU --- Trust On First Use).

/**
 * Registry of trusted public keys for plugin signature verification.
 * Keys are PEM-encoded ECDSA P-256 public keys.
 */
const TRUSTED_KEYS: Record<string, string> = {
  // Built-in Anthropic marketplace key — shipped with every CLI release.
  // Rotated annually. Previous key retained for 6 months after rotation.
  // 'anthropic-marketplace-2026': '-----BEGIN PUBLIC KEY-----\n...'
}

export function getTrustedKey(keyId: string): string | undefined {
  return TRUSTED_KEYS[keyId]
}

export function registerTrustedKey(keyId: string, pem: string): void {
  TRUSTED_KEYS[keyId] = pem
}

The registerTrustedKey function is the TOFU entry point. When a user installs a third-party plugin for the first time with policy=warn, the CLI stores the plugin author's public key in ~/.claude/plugins/trusted-keys.json. On subsequent installs or updates, the stored key is loaded via registerTrustedKey and the signature is verified against it. This mirrors SSH's known_hosts model --- trust the key on first contact, alert if it changes.

Core Verification Function

The verification function is deliberately simple. Complexity in cryptographic code is a vulnerability.

export function computeZipDigest(zipData: Buffer | Uint8Array): string {
  return createHash('sha256').update(zipData).digest('hex')
}

export function verifyPluginSignature(
  zipData: Buffer | Uint8Array,
  sig: PluginSignature,
): SignatureVerificationResult {
  const digestHex = computeZipDigest(zipData)

  // Reject unknown algorithms — fail closed, not open
  if (sig.algorithm !== 'ecdsa-p256-sha256') {
    return {
      verified: false,
      error: `Unsupported algorithm: ${sig.algorithm}`,
      digestHex,
    }
  }

  // Lookup the public key for this keyId
  const publicKeyPem = getTrustedKey(sig.keyId)
  if (!publicKeyPem) {
    return {
      verified: false,
      error: `Unknown signing key: ${sig.keyId}`,
      keyId: sig.keyId,
      digestHex,
    }
  }

  // Decode the base64 signature
  let sigBuf: Buffer
  try {
    sigBuf = Buffer.from(sig.signature, 'base64')
  } catch {
    return {
      verified: false,
      error: 'Malformed base64 signature',
      keyId: sig.keyId,
      digestHex,
    }
  }

  // Verify: recompute SHA-256 of ZIP bytes, check ECDSA signature
  try {
    const verifier = createVerify('SHA256')
    verifier.update(
      zipData instanceof Buffer ? zipData : Buffer.from(zipData),
    )
    const isValid = verifier.verify(
      { key: publicKeyPem, dsaEncoding: 'der' },
      sigBuf,
    )
    return {
      verified: isValid,
      error: isValid ? undefined : 'Signature mismatch',
      keyId: sig.keyId,
      digestHex,
    }
  } catch (err) {
    return {
      verified: false,
      error: `Verification error: ${
        err instanceof Error ? err.message : String(err)
      }`,
      keyId: sig.keyId,
      digestHex,
    }
  }
}

Every failure path returns a structured result rather than throwing an exception. This is deliberate: the caller (the plugin loader) needs the failure reason to decide whether to warn or reject, and exception-based control flow in cryptographic code leads to information leaks through timing differences in catch blocks.

The dsaEncoding: 'der' parameter specifies DER encoding for the ECDSA signature, which is the standard format for ECDSA over P-256. The alternative (IEEE P1363 format) would require explicit conversion and adds no security benefit.

Policy Enforcement

The policy function reads from an environment variable, defaulting to warn during the migration period:

export function getSignaturePolicy(): SignaturePolicy {
  const p = process.env.CLAUDE_PLUGIN_SIGNATURE_POLICY
  if (p === 'enforce' || p === 'warn' || p === 'off') return p
  return 'warn' // Default: warn during migration, enforce after
}

The migration plan: ship with warn default for two release cycles, announce the change in release notes, then switch the default to enforce. Third-party publishers who have not adopted signing will have their plugins show warnings before they stop installing entirely.

4.4 Schema Integration

The marketplace entry schema needs a signature field. The current PluginMarketplaceEntrySchema in schemas.ts defines the structure of each plugin listing in the marketplace JSON index. Adding the signature as an optional field maintains backward compatibility:

// schemas.ts — addition to PluginMarketplaceEntrySchema
import { z } from 'zod'

const PluginSignatureSchema = z.object({
  signature: z.string().min(1),
  keyId: z.string().min(1),
  algorithm: z.literal('ecdsa-p256-sha256'),
})

// Add to existing PluginMarketplaceEntrySchema:
// signature: PluginSignatureSchema.optional()

The z.literal('ecdsa-p256-sha256') constraint is important. If a future version adds support for a new algorithm, it must be added explicitly to a union type. This prevents downgrade attacks where an attacker forces the use of a weaker algorithm by setting the algorithm field to a value the client does not recognize but does not reject.

The LoadedPlugin type also needs a verification state:

export type PluginVerificationState =
  | { status: 'verified'; keyId: string; digestHex: string }
  | { status: 'unsigned' }
  | { status: 'failed'; error: string; digestHex?: string }

// Add to LoadedPlugin type:
// signatureVerification: PluginVerificationState

This state propagates through the plugin lifecycle. Security-sensitive features (like granting a plugin agent elevated tool access) can check signatureVerification.status === 'verified' before proceeding. As discussed in Chapter 14 (Fork Depth & Resource Limits), verified plugins could receive higher resource limits than unverified ones.

4.5 Loader Integration: The Verification Checkpoint

The plugin loader is where verification occurs. The call to verifyPluginSignature must happen after the ZIP is downloaded but before it is extracted. This is the critical ordering constraint.

flowchart TD
    DL["Download ZIP from marketplace"] --> VER{"Verify signature"}
    VER -->|Valid| EXT["Extract ZIP to plugin directory"]
    VER -->|Invalid + enforce| REJ["Reject: throw PluginError"]
    VER -->|Invalid + warn| WARN["Log warning, extract anyway"]
    VER -->|No signature + enforce| REJ
    VER -->|No signature + warn| WARN
    VER -->|Policy = off| EXT
    EXT --> LOAD["Load plugin manifest"]
    LOAD --> RUN["Register plugin tools/agents"]

The integration in loadPluginFromMarketplaceEntry():

// pluginLoader.ts — after ZIP download, before extraction

import {
  verifyPluginSignature,
  getSignaturePolicy,
  type SignaturePolicy,
} from './pluginSignature.js'

async function verifyAndExtract(
  zipBuf: Buffer,
  marketplaceEntry: PluginMarketplaceEntry,
  targetDir: string,
): Promise<PluginVerificationState> {
  const policy = getSignaturePolicy()

  if (policy === 'off') {
    await extractZipToDirectory(zipBuf, targetDir)
    return { status: 'unsigned' }
  }

  const sig = marketplaceEntry.signature
  if (!sig) {
    if (policy === 'enforce') {
      throw new PluginError(
        `Plugin ${marketplaceEntry.name} is unsigned. ` +
          'Set CLAUDE_PLUGIN_SIGNATURE_POLICY=warn to allow unsigned plugins.',
      )
    }
    logForDebugging(
      `[plugin] WARNING: ${marketplaceEntry.name} is unsigned — ` +
        'signature verification skipped',
      { level: 'warn' },
    )
    await extractZipToDirectory(zipBuf, targetDir)
    return { status: 'unsigned' }
  }

  const result = verifyPluginSignature(zipBuf, sig)

  if (result.verified) {
    await extractZipToDirectory(zipBuf, targetDir)
    return {
      status: 'verified',
      keyId: sig.keyId,
      digestHex: result.digestHex!,
    }
  }

  // Signature verification failed
  if (policy === 'enforce') {
    throw new PluginError(
      `Plugin ${marketplaceEntry.name} signature verification failed: ` +
        `${result.error}. Digest: ${result.digestHex}`,
    )
  }

  // policy === 'warn'
  logForDebugging(
    `[plugin] WARNING: ${marketplaceEntry.name} signature invalid: ` +
      `${result.error}. Installing anyway (policy=warn).`,
    { level: 'warn' },
  )
  await extractZipToDirectory(zipBuf, targetDir)
  return { status: 'failed', error: result.error!, digestHex: result.digestHex }
}

Note the ordering: verifyPluginSignature is called on the raw zipBuf before extractZipToDirectory. The ZIP is verified as a sealed unit. After extraction, the individual files are no longer cryptographically bound to the signature --- an attacker who can modify extracted files on disk (Chapter 5's path traversal defense) could bypass a post-extraction verification. Pre-extraction verification is the only safe ordering.

4.6 Certificate Authority Infrastructure

A signing key without a trust anchor is just a key pair. The CA infrastructure provides the trust anchor --- the mechanism by which users and the CLI know that a given public key actually belongs to the claimed publisher.

Three-Tier Trust Model

    end

    subgraph "Trust Tier 2: CA-Issued"

        CA --> PK1["Publisher A Cert<br/>keyId: publisher-a-2026"]
        CA --> PK2["Publisher B Cert<br/>keyId: publisher-b-2026"]

    end

    AK -.- |"Highest trust"| CA
    CA -.- |"Verified identity"| PK1
    TK1 -.- |"Lowest trust<br/>User accepted"| PK1

Tier 1: Built-in keys. Anthropic's own marketplace signing key is compiled into the CLI binary. This key signs all first-party plugins. It cannot be overridden by configuration. Rotation happens via CLI updates --- the new key is added, and the old key is retained for six months to allow cached plugins to verify.

Tier 2: CA-issued certificates. Verified third-party publishers submit a Certificate Signing Request (CSR) to Anthropic's plugin CA. After identity verification (domain ownership, publisher account validation), the CA issues a signing certificate. The certificate's public key is published in the marketplace entry. The CLI verifies the certificate chain: plugin signature -> publisher certificate -> Anthropic CA root.

Tier 3: TOFU. For plugins distributed outside the official marketplace (git repos, direct URLs), the CLI uses Trust On First Use. On first install, the plugin's signing key fingerprint is stored in ~/.claude/plugins/trusted-keys.json. On subsequent installs, the key must match. A key change triggers a prominent warning --- the SSH known_hosts model.

Key Rotation

Key rotation is the operational complexity that most signing schemes underestimate. The rotation protocol:

  1. New key pair generated 30 days before rotation date.
  2. New public key added to TRUSTED_KEYS in a CLI release (old key retained).
  3. Marketplace begins signing new uploads with the new key.
  4. Old key remains valid for 180 days after rotation.
  5. After 180 days, old key removed from TRUSTED_KEYS in a CLI release.

The 180-day overlap window accommodates developers who do not update their CLI frequently. A plugin signed with the old key continues to verify until the developer updates to a CLI version that has dropped the old key.

Revocation

Certificate revocation handles the case where a publisher's private key is compromised. Two mechanisms:

Marketplace blocklist. The existing getBlockedMarketplaces() function is extended to include revoked keyId values. The CLI checks this list before attempting verification. A revoked key produces a verification failure regardless of signature validity.

Short-lived certificates. Publisher certificates are issued with a 90-day validity period. A compromised key becomes unusable after the certificate expires, even without active revocation. Publishers must re-certify quarterly, which also serves as a periodic identity verification.

4.7 Marketplace JSON Integrity

Finding 2 identifies a subtler problem: the marketplace JSON index itself is not integrity-protected. An attacker who can modify the index can redirect plugin download URLs, change version numbers, or inject entirely new plugin entries --- all without touching the individual plugin ZIPs.

The defense is SHA-256 pinning of the marketplace index:

// marketplaceManager.ts — integrity check for marketplace JSON

import { createHash } from 'crypto'

/**
 * Verify marketplace JSON response integrity.
 * The expected hash is either:
 * 1. Pinned in the CLI binary (for the official marketplace)
 * 2. Provided via CLAUDE_MARKETPLACE_INDEX_HASH env var (for enterprise)
 */
function verifyMarketplaceIntegrity(
  responseBody: string,
  expectedHash?: string,
): boolean {
  if (!expectedHash) return true // No pinning configured

  const actualHash = createHash('sha256')
    .update(responseBody)
    .digest('hex')

  if (actualHash !== expectedHash) {
    logForDebugging(
      `[marketplace] Index integrity check failed. ` +
        `Expected: ${expectedHash.slice(0, 16)}... ` +
        `Got: ${actualHash.slice(0, 16)}...`,
      { level: 'warn' },
    )
    return false
  }
  return true
}

This creates a chicken-and-egg problem: the hash changes every time a plugin is added or updated. The solution is to separate the marketplace index into two parts: a stable root document (signed by the Anthropic CA key, changes rarely) and a volatile entries document (signed per-update, hash published in the root document). The CLI verifies the root document's signature, then uses the hash from the root to verify the entries document.

4.8 The Signing Pipeline: Author to User

From the plugin author's perspective, signing must be frictionless or it will not be adopted. The signing pipeline integrates into the existing dxt (Developer Extension Toolkit) build process.

Author Workflow

# 1. Generate a signing key pair (one-time)
dxt keygen --algorithm ecdsa-p256-sha256 --output ~/.dxt/signing-key.pem

# 2. Submit public key to Anthropic CA (one-time)
dxt certify --key ~/.dxt/signing-key.pem --publisher "acme-corp"
# -> Outputs certificate after identity verification

# 3. Build and sign plugin (every release)
dxt build --sign --key ~/.dxt/signing-key.pem
# -> Produces plugin.zip + plugin.zip.sig + manifest with signature block

The dxt build --sign command computes SHA-256(plugin.zip), signs the digest with the author's private key, and embeds the signature in the manifest JSON that accompanies the upload.

Verification Performance Budget

Signing must not degrade the CLI startup experience. The performance budget:

Operation Target Actual (P256)
SHA-256 of 5MB ZIP < 10ms ~3ms
ECDSA-P256 verify < 5ms ~0.3ms
Key lookup < 1ms < 0.1ms
Total per plugin < 20ms ~3.5ms

For a user with 10 installed plugins, total verification overhead is ~35ms. This is imperceptible. The dominant cost is the SHA-256 digest of the ZIP bytes, not the ECDSA verification. For very large plugins (50MB+), the digest could take 30-50ms, but the ZIP bomb defense in Chapter 6 caps archive size at 50MB compressed, bounding the worst case.

4.9 Compensating Controls During Migration

The migration from unsigned to signed plugins cannot happen atomically. During the transition period (estimated two release cycles, approximately 8 weeks), compensating controls reduce risk:

Strict marketplace allowlist. The existing isSourceAllowedByPolicy() function restricts plugin installation to configured marketplaces. During migration, only the official Anthropic marketplace is allowed by default. Third-party marketplaces require explicit user opt-in via configuration.

Marketplace blocklist. getBlockedMarketplaces() blocks known-compromised or decommissioned sources. This is a server-side list that the CLI fetches periodically, allowing rapid response to marketplace compromises.

Name impersonation detection. isBlockedOfficialName() detects homograph and impersonation attacks where a third-party plugin uses a name deceptively similar to an official plugin.

These compensating controls are defense-in-depth. They reduce risk but do not eliminate it. Only cryptographic verification, as implemented in this chapter, provides a definitive proof of plugin authenticity.

4.11 Relationship to Subsequent Defenses

Cryptographic signing is the first layer of the Plugin Supply Chain defense. It answers the question "did this plugin come from who it claims?" The subsequent chapters address related but distinct questions:

  • Chapter 5 (ZIP Extraction Path Traversal) answers: "Even if the plugin is authentic, can the ZIP contents escape the extraction directory?" A signed-but-malicious plugin from a compromised publisher could still contain path traversal entries.

  • Chapter 6 (Plugin Integrity & Version Security) answers: "Can the version identification system be manipulated to serve a different version than expected?" Short SHA collisions and ZIP bombs are integrity failures that operate independently of signing.

Together, these three chapters close the Plugin Supply Chain dependency chain (findings 1, 2, 4, 15, 25, 29) identified in the security assessment. Signing prevents impersonation. Path traversal defense prevents filesystem escape. Version integrity prevents substitution. All three are required --- any one without the others leaves an exploitable gap.
