Chapter 6: Plugin Integrity & Version Security

The first two chapters of Part II addressed authenticity (Chapter 4: Is this plugin from who it claims?) and containment (Chapter 5: Can the plugin escape its directory?). This chapter addresses the third dimension of plugin supply chain security: integrity. Specifically, two vulnerabilities that allow an attacker to manipulate what version of a plugin gets loaded and how much system resources the extraction consumes.

Finding 29 (CWE-328, MEDIUM) identifies that plugin versions use 12-character short git SHAs with a collision space of only 2^48 --- feasible for a targeted attack. Finding 25 (CWE-409, MEDIUM) identifies that ZIP bomb detection occurs only during extraction, with no pre-download size validation. Together, these findings enable two distinct attack patterns: version confusion (tricking the CLI into loading the wrong version of a plugin) and resource exhaustion (consuming all available memory or disk space before the extraction-time limits kick in).

6.1 CWE-328: Short SHA Collision Risk

The Vulnerability

Claude Code's plugin versioning system identifies plugin versions by their git commit SHA. This is a sensible choice --- git commits are immutable, content-addressable, and universally available. The problem is truncation.

The pluginVersioning.ts module truncates the 40-character (160-bit) git SHA to 12 characters (48 bits):

// VULNERABLE: utils/plugins/pluginVersioning.ts
if (gitCommitSha) {
  const shortSha = gitCommitSha.substring(0, 12)
  // ...
  return shortSha
}

if (installPath) {
  const sha = await getGitCommitSha(installPath)
  if (sha) {
    const shortSha = sha.substring(0, 12)
    // ...
    return shortSha
  }
}

A 12-character hex string represents 48 bits of entropy. The birthday paradox tells us that a collision probability of 50% is reached at approximately 2^24 (16.7 million) values. For a targeted attack (finding a specific collision), the expected work is 2^48 SHA-1 computations. At modern GPU speeds (approximately 10 billion SHA-1 hashes per second on a high-end GPU), this takes:

2^48 / 10^10 = 281,474,976,710,656 / 10,000,000,000 ≈ 28,147 seconds ≈ 7.8 hours

Seven and a half hours of GPU time to produce a git commit whose first 12 hex characters match a target. This is well within the budget of a motivated attacker. For comparison, Bitcoin miners perform approximately 2^70 SHA-256 operations per day. Producing a 12-character SHA-1 collision is trivially inexpensive by modern standards.

Attack Scenario: Version Substitution

The attack proceeds as follows:

  1. Attacker identifies a popular plugin awesome-plugin at version sha:a1b2c3d4e5f6 (12 chars).
  2. Attacker creates a malicious fork with a backdoor.
  3. Attacker brute-forces commits until they find one whose SHA starts with a1b2c3d4e5f6.
  4. The malicious commit has the same short SHA as the legitimate version.
  5. If the CLI caches or references plugins by short SHA, the malicious version can be substituted.

The cache path is the critical exposure. Plugin ZIPs are cached in directories keyed by version string. If two versions share the same 12-character prefix, they resolve to the same cache entry. An attacker who can populate the cache first (via a compromised CDN mirror, DNS hijack, or local filesystem access) controls which version is loaded.

The Fix: Full 40-Character SHA

The fix is straightforward: use the full 40-character git SHA instead of truncating to 12 characters. The collision space increases from 2^48 to 2^160 --- firmly in the "heat death of the universe" category for brute-force attacks.

// SECURE PATCH: utils/plugins/pluginVersioning.ts

import { createHash } from 'crypto'

// Use full SHA for version pinning — 12-char has ~2^48 collision space.
if (gitCommitSha) {
  const fullSha =
    gitCommitSha.length >= 40
      ? gitCommitSha.substring(0, 40)
      : gitCommitSha
  if (
    typeof source === 'object' &&
    source.source === 'git-subdir'
  ) {
    const normPath = source.path
      .replace(/\\/g, '/')
      .replace(/^\.\//, '')
      .replace(/\/+$/, '')
    const pathHash = createHash('sha256')
      .update(normPath)
      .digest('hex')
      .substring(0, 8)
    const v = `${fullSha}-${pathHash}`
    logForDebugging(
      `Using git-subdir SHA+path version for ${pluginId}: ${v} (path=${normPath})`,
    )
    return v
  }
  logForDebugging(
    `Using pre-resolved git SHA for ${pluginId}: ${fullSha}`,
  )
  return fullSha
}

if (installPath) {
  const sha = await getGitCommitSha(installPath)
  if (sha) {
    logForDebugging(`Using git SHA for ${pluginId}: ${sha}`)
    return sha
  }
}

Three changes in this patch:

  1. Full SHA usage. gitCommitSha.substring(0, 40) replaces substring(0, 12). The conditional length >= 40 handles edge cases where the input is already shorter than 40 characters (e.g., manually specified versions).

  2. Git-subdir path hash. For monorepo plugins where multiple packages share the same git commit SHA, a SHA-256 hash of the normalized subdirectory path is appended. This ensures that two packages at the same commit but different paths produce different version identifiers. The path hash is truncated to 8 hex characters (32 bits) --- collision resistance is not critical here since the full commit SHA provides the primary identity.

  3. Full SHA in fallback path. When the SHA is read from getGitCommitSha(installPath), it is used in its entirety. git rev-parse HEAD returns the full 40-character SHA by default.

Cache Migration

Existing installations have cache directories keyed by 12-character SHAs. The migration strategy:

  1. New installs use full SHA cache keys immediately.
  2. Existing cache entries remain valid until the plugin is updated.
  3. On update, the old 12-character key directory is removed and a new 40-character key directory is created.
  4. Backward compatibility: if a cache lookup for a full SHA fails, fall back to checking the 12-character prefix. This handles the case where a user downgrades the CLI after installing a plugin with the new version.
/**
 * Resolve a version-keyed cache directory, with backward-compatible
 * fallback to short SHA directories from pre-patch installations.
 */
async function resolveVersionCacheDir(
  baseDir: string,
  version: string,
): Promise<string | null> {
  const fullPath = join(baseDir, version)
  if (await exists(fullPath)) return fullPath

  // Backward compat: check if old 12-char SHA directory exists
  if (version.length === 40) {
    const shortPath = join(baseDir, version.substring(0, 12))
    if (await exists(shortPath)) {
      logForDebugging(
        `[version] Migrating cache from short SHA to full SHA: ${version}`,
      )
      return shortPath
    }
  }

  return null
}

SHA-1 vs. SHA-256 for Version Identity

A natural question: if we are concerned about SHA-1 collision attacks on git SHAs, should we switch to SHA-256 for version identification?

Git itself has been transitioning from SHA-1 to SHA-256 (the sha256 object format in git 2.42+). However, as of 2026, the vast majority of git repositories still use SHA-1. The vulnerability we are fixing is not SHA-1's collision resistance at full length (which requires approximately 2^63 operations for a chosen-prefix collision, as demonstrated by SHAMbles in 2020). The vulnerability is the 12-character truncation that reduces the space to 2^48. Using the full 40-character SHA-1 hash provides 160 bits of collision resistance --- more than sufficient when the attacker does not have the ability to control both sides of the collision (they can only craft their own commit, not modify the legitimate plugin's commit).

For the git-subdir path hash, SHA-256 is used because we are introducing a new hash (not constrained by git's format) and there is no reason not to use the stronger primitive.

6.2 CWE-409: ZIP Bomb Detection Gaps

The Vulnerability

A ZIP bomb is a crafted archive that is small when compressed but expands to an enormous size when decompressed. The classic example is 42.zip --- a 42KB file that expands to 4.5 petabytes through nested ZIP archives. In Claude Code's context, a ZIP bomb targeting the plugin extraction pipeline could:

  • Exhaust available disk space, causing cascading failures across the system.
  • Exhaust available memory during decompression, crashing the CLI process.
  • Saturate CPU during decompression, creating a denial-of-service condition.

The existing defense is in zip.ts's unzipFile() function, which checks the compression ratio during extraction:

// Existing defense (extraction-time): zip.ts unzipFile()
export async function unzipFile(
  zipData: Buffer,
): Promise<Record<string, Uint8Array>> {
  const { unzipSync } = await import('fflate')
  const compressedSize = zipData.length

  const state: ZipValidationState = {
    fileCount: 0,
    // ... ratio checks, file count limits, total size limits
  }
  // Validation happens during extraction
}

The problem: this validation occurs only during extraction. The ZIP has already been downloaded and loaded into memory as a Buffer. For a ZIP bomb that is 50MB compressed and would expand to 50GB, the CLI has already consumed network bandwidth and allocated 50MB of heap memory before any validation occurs.

The Fix: Pre-Download Size Validation

The patch adds a pre-download validation step that checks the Content-Length header before downloading the archive, and a pre-extraction size check before calling fflate:

// SECURE PATCH: utils/dxt/zip.ts

/** Maximum compressed archive size (50MB). Call before download. */
export const MAX_DOWNLOAD_SIZE = 50 * 1024 * 1024

/**
 * Pre-download size validation. Call with Content-Length before fetching.
 */
export function validateArchiveDownloadSize(
  contentLength: number | undefined,
): { valid: boolean; reason?: string } {
  if (contentLength === undefined) return { valid: true }
  if (contentLength > MAX_DOWNLOAD_SIZE) {
    return {
      valid: false,
      reason: `Archive too large: ${Math.round(
        contentLength / 1024 / 1024,
      )}MB (max: ${Math.round(MAX_DOWNLOAD_SIZE / 1024 / 1024)}MB)`,
    }
  }
  if (contentLength < 0) {
    return { valid: false, reason: 'Invalid Content-Length' }
  }
  return { valid: true }
}

export async function unzipFile(
  zipData: Buffer,
): Promise<Record<string, Uint8Array>> {
  // Pre-check buffer size before expensive extraction
  const sizeCheck = validateArchiveDownloadSize(zipData.length)
  if (!sizeCheck.valid) {
    throw new Error(sizeCheck.reason)
  }

  const { unzipSync } = await import('fflate')
  const compressedSize = zipData.length

  const state: ZipValidationState = {
    fileCount: 0,
    // ... existing validation continues
  }
}

Level 1: Content-Length header check. Before downloading, the CLI sends a HEAD request or checks the Content-Length header from the initial GET response. If the compressed size exceeds 50MB, the download is aborted. This prevents network bandwidth waste and memory allocation for obviously oversized archives.

Level 2: Buffer size check. After downloading, but before calling fflate's decompressor, the buffer size is validated. This catches cases where the Content-Length header was missing, incorrect, or chunked transfer encoding was used (where Content-Length is not available).

Level 3: Extraction ratio check (existing). During extraction, the ratio of decompressed size to compressed size is monitored. If it exceeds 50:1, extraction is aborted. This catches ZIP bombs that are within the 50MB compressed limit but expand to gigabytes.

Content-Type Verification

An additional defense not in the original finding but warranted by the threat model: verify that the downloaded content is actually a ZIP archive before attempting extraction.

/**
 * Validate that the response content-type indicates a ZIP archive.
 * Prevents extraction of non-ZIP content that might crash fflate.
 */
export function validateArchiveContentType(
  contentType: string | undefined,
): { valid: boolean; reason?: string } {
  if (!contentType) return { valid: true } // Permissive when absent

  const normalized = contentType.toLowerCase().split(';')[0].trim()
  const VALID_ZIP_TYPES = new Set([
    'application/zip',
    'application/x-zip-compressed',
    'application/octet-stream', // Generic binary — common for GCS
    'binary/octet-stream',
  ])

  if (!VALID_ZIP_TYPES.has(normalized)) {
    return {
      valid: false,
      reason: `Unexpected content-type: ${normalized} (expected ZIP archive)`,
    }
  }
  return { valid: true }
}

This prevents an attacker from serving an HTML page, a JavaScript file, or other non-ZIP content at the plugin download URL. While fflate would fail to parse non-ZIP data, the error message from a decompression library is less informative than a clear content-type mismatch error.

Caller Integration

The validateArchiveDownloadSize function is designed to be called by the marketplace download code before fetching the full archive:

// marketplaceManager.ts — integration point

import {
  validateArchiveDownloadSize,
  validateArchiveContentType,
} from '../dxt/zip.js'

async function downloadPluginArchive(url: string): Promise<Buffer> {
  // HEAD request to check size before downloading
  const headResp = await axios.head(url, { timeout: 5000 })
  const contentLength = headResp.headers['content-length']
    ? parseInt(headResp.headers['content-length'], 10)
    : undefined

  const sizeCheck = validateArchiveDownloadSize(contentLength)
  if (!sizeCheck.valid) {
    throw new PluginError(
      `Plugin archive rejected: ${sizeCheck.reason}`,
    )
  }

  const typeCheck = validateArchiveContentType(
    headResp.headers['content-type'],
  )
  if (!typeCheck.valid) {
    throw new PluginError(
      `Plugin archive rejected: ${typeCheck.reason}`,
    )
  }

  // Proceed with download
  const resp = await axios.get(url, {
    responseType: 'arraybuffer',
    maxContentLength: MAX_DOWNLOAD_SIZE,
    timeout: 30000,
  })

  return Buffer.from(resp.data)
}

The HEAD request adds one round-trip (typically 50-100ms) but prevents downloading archives that will be rejected. The maxContentLength on the GET request provides a belt-and-suspenders defense --- if the server lies about Content-Length in the HEAD response, the GET request will abort after exceeding the limit.

6.3 SHA-256 Full Hash Pinning: Integrity Manifests

Beyond version identification and size validation, a comprehensive plugin integrity system needs content pinning --- the ability to verify that a specific version of a plugin has not been modified since it was published.

The Integrity Manifest

Each plugin version includes an integrity manifest: a JSON file listing every file in the plugin with its SHA-256 hash.

{
  "version": "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2",
  "algorithm": "sha256",
  "generated": "2026-04-12T00:00:00Z",
  "files": {
    "manifest.json": "e3b0c44298fc1c149afb4c8996fb92427ae41e4649b934ca495991b7852b855",
    "src/index.ts": "a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a",
    "src/tools/myTool.ts": "2c26b46b68ffc68ff99b453c1d30413413422d706483bfa0f98a5e886266e7ae"
  },
  "archiveHash": "d7a8fbb307d7809469ca9abcb0082e4f8d5651e46d3cdb762d02d0bf37c9e592"
}

The archiveHash field is the SHA-256 of the entire ZIP archive. This is the hash that the cryptographic signature from Chapter 4 covers. The per-file hashes allow verification of individual files after extraction --- useful for detecting post-extraction tampering.

Implementation

import { createHash } from 'crypto'
import { readFile } from 'fs/promises'
import { join } from 'path'

export interface IntegrityManifest {
  version: string
  algorithm: 'sha256'
  generated: string
  files: Record<string, string>
  archiveHash: string
}

/**
 * Verify the integrity of an extracted plugin directory against
 * its integrity manifest.
 */
export async function verifyPluginIntegrity(
  pluginDir: string,
  manifest: IntegrityManifest,
): Promise<{
  valid: boolean
  violations: Array<{ file: string; expected: string; actual: string }>
}> {
  const violations: Array<{
    file: string
    expected: string
    actual: string
  }> = []

  for (const [relPath, expectedHash] of Object.entries(manifest.files)) {
    const fullPath = join(pluginDir, relPath)
    try {
      const contents = await readFile(fullPath)
      const actualHash = createHash('sha256')
        .update(contents)
        .digest('hex')

      if (actualHash !== expectedHash) {
        violations.push({
          file: relPath,
          expected: expectedHash,
          actual: actualHash,
        })
      }
    } catch {
      violations.push({
        file: relPath,
        expected: expectedHash,
        actual: '<missing>',
      })
    }
  }

  return {
    valid: violations.length === 0,
    violations,
  }
}

The integrity check runs on plugin load, not on every CLI invocation. The first load after installation (or update) verifies all file hashes. Subsequent loads check only if the manifest's generated timestamp is newer than the last verification timestamp stored in the plugin's metadata. This balances security with performance --- a full SHA-256 scan of a 5MB plugin takes approximately 5ms, but running it on every CLI startup for 10 plugins adds 50ms that is unnecessary when the files have not changed.

6.5 Compensating Controls

While the patches in this chapter are being implemented and deployed, the following compensating controls reduce risk:

For CWE-328 (short SHA collision):

  • Plugins are sourced from trusted marketplaces only. An attacker would need to compromise the marketplace or a publisher's account to inject a collision --- at which point they could simply replace the plugin directly without needing a collision.
  • Cache directories are keyed on the full SHA internally even though the version string displayed to the user is truncated. The cache is not directly addressable by external inputs.

For CWE-409 (ZIP bombs):

  • The existing extraction-time ratio check (50:1 maximum) catches most ZIP bombs during extraction. The pre-download check prevents downloading bombs that would waste bandwidth and memory even if caught during extraction.
  • MAX_FILE_SIZE and MAX_TOTAL_SIZE limits cap individual file and aggregate extraction sizes.
  • The validateZipFile() function enforces entry count limits, preventing entry-count bombs (archives with millions of tiny files designed to exhaust filesystem inodes).

6.6 Edge Cases and Corner Cases

Short SHA in Git Subdir Plugins

Monorepo plugins present a special case. Multiple plugins can share the same git commit SHA because they live in the same repository. The original code handled this with the short SHA alone, meaning two plugins at the same commit would have identical version identifiers. The patch adds a path hash:

const v = `${fullSha}-${pathHash}`
// Example: "a1b2c3...40chars...-3f2a7b81"

The path hash is only 8 hex characters (32 bits), which might seem insufficient. But the path hash is not the primary identifier --- it is a disambiguation suffix. Two plugins at the same commit with different paths will have different path hashes. Two plugins at different commits cannot collide regardless of path hash. The combination of 40-char SHA + 8-char path hash provides 192 bits of total identifier space.

Handling Pre-Patch Cache Entries

When a user upgrades their CLI from a pre-patch version, their plugin cache contains directories keyed by 12-character SHAs. The migration must be transparent:

  1. On first plugin use after upgrade, the CLI checks for the full SHA cache directory.
  2. If not found, it falls back to the 12-character prefix.
  3. If the 12-character directory is found, the plugin loads from it (no re-download).
  4. On next plugin update, the old directory is removed and a new full-SHA directory is created.

This ensures zero disruption for existing users while moving the cache to the stronger key format.

Content-Length Header Absent

Not all HTTP servers include a Content-Length header. Cloud storage services (GCS, S3) typically include it, but CDN edge servers and custom download handlers may omit it, especially for dynamically-generated responses or chunked transfer encoding.

When Content-Length is absent, validateArchiveDownloadSize returns { valid: true } --- the download proceeds. The buffer size check after download provides the second line of defense. And axios's maxContentLength option provides a third defense by aborting the download if the response body exceeds the limit, regardless of headers.

Race Condition in Concurrent Plugin Installs

Two concurrent loadPluginFromMarketplaceEntry() calls for the same plugin could race on the cache directory. The first call downloads and extracts. The second call checks the cache, finds it partially populated (extraction in progress), and either fails or loads an incomplete plugin.

The defense is the existing .gcs-sha sentinel file pattern: the sentinel is written only after extraction completes. A concurrent call that finds the cache directory but no sentinel re-downloads. The full-SHA version identifier makes this race harder to trigger because cache keys are longer and more specific, but the sentinel pattern remains the primary concurrency control.

6.9 Relationship to Part III and Beyond

Part II (Chapters 4, 5, and 6) closes the Plugin Supply Chain dependency chain. Part III begins with Credential Storage Encryption (Chapter 7), which addresses the second highest-priority dependency chain.

The connection between Part II and Part III is direct: a compromised plugin (prevented by the defenses in Part II) is one of the primary attack vectors for credential theft (defended in Part III). If an attacker bypasses plugin signing, escapes the extraction directory, and loads a malicious plugin, the first thing that plugin does is read ~/.claude/.credentials.json --- which, as Chapter 7 will reveal, is stored in plaintext on all non-macOS platforms.

The defense ordering matters. Plugin supply chain hardening (Part II) must be deployed before credential encryption (Part III) can be relied upon. An attacker who can load arbitrary code via a compromised plugin can bypass any client-side encryption --- they simply read the credentials after the legitimate code decrypts them. The defenses are complementary, not substitutable: Part II prevents the attacker from running code, Part III limits the damage if they succeed despite Part II.

This layered approach --- prevention before mitigation, authentication before authorization, integrity before confidentiality --- is the organizing principle for the entire remediation roadmap. The seven phases in the Implementation Roadmap (Chapter 3) are sequenced to maximize the security gain from each successive deployment, with each phase building on the protections established by the previous one.
