Chapter 17: WebSocket & Network Security

Chapter 16 addressed how the dangerouslySkipPermissions flag crosses the network boundary to remote servers. This chapter broadens the scope to the entire network attack surface of Claude Code. Three findings from the security audit converge here: WebSocket origin validation (Finding 21, CWE-346), SSRF via DNS rebinding (Finding 17, CWE-918), and CA bundle download without certificate pinning (Finding 18, CWE-295). Together, they represent the network trust model -- how Claude Code establishes, validates, and maintains the integrity of its network connections.

Claude Code makes network connections in three contexts: the API connection to Anthropic's servers (streaming responses, session management), the WebSocket connection for remote sessions and real-time event delivery, and the WebFetch tool for user-directed HTTP requests. Each context has a different trust model, a different attack surface, and a different set of defenses that must be implemented.

17.1 WebSocket Origin Validation

The Missing Origin Check

Finding 21 identifies a medium-severity vulnerability (CVSS 5.5): SessionsWebSocket.ts establishes WebSocket connections with Authorization: Bearer headers but no explicit Origin validation. The isSessionsMessage() type guard accepts any object with a string type field, providing minimal message validation.

The data flow in the audit finding:

Malicious web page -> JavaScript opens WebSocket to
wss://api.anthropic.com/v1/sessions/ws/{id}/subscribe ->
if token is accessible (e.g., via XSS) -> connection succeeds ->
attacker receives session messages

While the audit notes this is low probability (the token is stored in keychain/file, not cookies), the defense should not rely on the absence of other vulnerabilities. If token theft ever becomes possible -- through a future XSS in a web-based interface, through environment variable exposure, or through an MCP server that reads the credential file -- the missing Origin validation becomes a direct exploitation path.

In the standard WebSocket hijacking scenario, the browser sends cookies automatically with the WebSocket handshake. Claude Code does not use cookies for WebSocket authentication -- it uses Authorization: Bearer headers. This means the browser-based attack requires the attacker to already possess the token. However, the Origin header validation provides defense-in-depth against scenarios where token theft happens through other means.

Client-Side Origin Enforcement

The client should set the Origin header explicitly and validate the server's response:

import WebSocket from 'ws'

interface SecureWebSocketOptions {
  url: string
  token: string
  expectedServerIdentity: string
  allowedOrigins: string[]
}

function createSecureWebSocket(
  options: SecureWebSocketOptions
): WebSocket {
  const { url, token, expectedServerIdentity, allowedOrigins } = options

  // Set explicit Origin header
  const origin = 'claude-code-cli'  // Not a web origin -- CLI identifier

  const ws = new WebSocket(url, {
    headers: {
      'Authorization': `Bearer ${token}`,
      'Origin': origin,
      'X-Client-Version': getClientVersion(),
      'X-Session-Id': getSessionId(),
    },
    // TLS options
    rejectUnauthorized: true,
    // Connection timeout
    handshakeTimeout: 10_000,
  })

  // Validate server identity on upgrade response
  ws.on('upgrade', (response: IncomingMessage) => {
    const serverIdentity = response.headers['x-server-identity']

    if (serverIdentity !== expectedServerIdentity) {
      ws.close(4001, 'Server identity mismatch')
      throw new SecurityError(
        `WebSocket server identity mismatch. ` +
        `Expected: ${expectedServerIdentity}, Got: ${serverIdentity}`
      )
    }
  })

  return ws
}

Server-Side Origin Validation

The server must validate the Origin header on every WebSocket upgrade request:

const ALLOWED_ORIGINS = new Set([
  'claude-code-cli',
  'claude-code-vscode',
  'claude-code-jetbrains',
])

function handleWebSocketUpgrade(
  request: IncomingMessage,
  socket: Socket,
  head: Buffer
): void {
  const origin = request.headers['origin'] ?? ''

  // Reject unknown origins
  if (!ALLOWED_ORIGINS.has(origin)) {
    socket.write(
      'HTTP/1.1 403 Forbidden\r\n' +
      `X-Rejection-Reason: Origin "${origin}" not allowed\r\n` +
      '\r\n'
    )
    socket.destroy()

    logSecurityEvent({
      event: 'websocket_origin_rejected',
      origin,
      ip: socket.remoteAddress,
      timestamp: Date.now(),
    })
    return
  }

  // Proceed with upgrade
  wss.handleUpgrade(request, socket, head, (ws) => {
    wss.emit('connection', ws, request)
  })
}

Message Validation Hardening

Beyond origin validation, the isSessionsMessage() type guard should be strengthened from a minimal type check to a full structural validation:

// BEFORE: Minimal check (vulnerable)
function isSessionsMessage(data: unknown): data is SessionsMessage {
  return typeof data === 'object' &&
    data !== null &&
    'type' in data &&
    typeof (data as Record<string, unknown>).type === 'string'
}

// AFTER: Structural validation
import { z } from 'zod'

const SessionsMessageSchema = z.discriminatedUnion('type', [
  z.object({
    type: z.literal('session_created'),
    sessionId: z.string().uuid(),
    createdAt: z.number(),
  }),
  z.object({
    type: z.literal('tool_result'),
    toolUseId: z.string(),
    content: z.array(z.object({
      type: z.enum(['text', 'image', 'document']),
    })),
  }),
  z.object({
    type: z.literal('session_ended'),
    sessionId: z.string().uuid(),
    reason: z.enum(['completed', 'timeout', 'error', 'user_cancel']),
  }),
  z.object({
    type: z.literal('heartbeat'),
    timestamp: z.number(),
  }),
])

function validateSessionsMessage(
  data: unknown
): z.infer<typeof SessionsMessageSchema> | null {
  const result = SessionsMessageSchema.safeParse(data)
  if (!result.success) {
    logSecurityEvent({
      event: 'invalid_ws_message',
      errors: result.error.issues,
      rawData: JSON.stringify(data).slice(0, 200),
    })
    return null
  }
  return result.data
}

The Zod schema ensures that: - Only known message types are accepted - Each message type has the expected fields with correct types - UUIDs are formatted correctly - Enum values are from the allowed set - Unknown properties are stripped

17.2 SSRF via DNS Rebinding

The WebFetch SSRF Vulnerability

Finding 17 (CVSS 5.9) identifies a Server-Side Request Forgery (SSRF) vulnerability in the WebFetch tool. The tool validates URLs at the application level but does not validate the IP address that DNS resolves to before making the connection.

// Current implementation -- VULNERABLE
export function isPermittedRedirect(
  originalUrl: string,
  redirectUrl: string
): boolean {
  const stripWww = (hostname: string) =>
    hostname.replace(/^www\./, '')
  return originalHostWithoutWww === redirectHostWithoutWww
}

This redirect check verifies hostname equivalence but does not check the resolved IP address. The key finding from the audit: "The ssrfGuardedLookup is only used for HTTP hooks, not for the WebFetch tool."

The attack exploits DNS TTL: the attacker's DNS server returns a public IP on the first query (passing validation) and then switches to a private/metadata IP on subsequent queries (exploiting the rebind). Because the WebFetch tool does not re-validate the resolved IP on each connection, the second resolution to 169.254.169.254 is used for the actual HTTP request.

The ssrfGuardedLookup Solution

The fix is to apply the existing ssrfGuardedLookup function -- currently only used for HTTP hooks -- to all WebFetch requests:

import { lookup as dnsLookup, LookupAddress } from 'node:dns'
import { isIP } from 'node:net'

// IP ranges that should never be contacted by WebFetch
const BLOCKED_RANGES: Array<{
  cidr: string
  start: bigint
  end: bigint
  description: string
}> = [
  { cidr: '127.0.0.0/8', start: ipToBigInt('127.0.0.0'),
    end: ipToBigInt('127.255.255.255'), description: 'Loopback' },
  { cidr: '10.0.0.0/8', start: ipToBigInt('10.0.0.0'),
    end: ipToBigInt('10.255.255.255'), description: 'Private (RFC 1918)' },
  { cidr: '172.16.0.0/12', start: ipToBigInt('172.16.0.0'),
    end: ipToBigInt('172.31.255.255'), description: 'Private (RFC 1918)' },
  { cidr: '192.168.0.0/16', start: ipToBigInt('192.168.0.0'),
    end: ipToBigInt('192.168.255.255'), description: 'Private (RFC 1918)' },
  { cidr: '169.254.0.0/16', start: ipToBigInt('169.254.0.0'),
    end: ipToBigInt('169.254.255.255'), description: 'Link-local / Cloud metadata' },
  { cidr: '0.0.0.0/8', start: ipToBigInt('0.0.0.0'),
    end: ipToBigInt('0.255.255.255'), description: 'Current network' },
  { cidr: 'fc00::/7', start: ipv6ToBigInt('fc00::'),
    end: ipv6ToBigInt('fdff:ffff:ffff:ffff:ffff:ffff:ffff:ffff'),
    description: 'IPv6 ULA' },
  { cidr: '::1/128', start: ipv6ToBigInt('::1'),
    end: ipv6ToBigInt('::1'), description: 'IPv6 loopback' },
  { cidr: 'fe80::/10', start: ipv6ToBigInt('fe80::'),
    end: ipv6ToBigInt('febf:ffff:ffff:ffff:ffff:ffff:ffff:ffff'),
    description: 'IPv6 link-local' },
]

function isBlockedIp(ip: string): { blocked: boolean; reason?: string } {
  const ipBigInt = isIPv4(ip) ? ipToBigInt(ip) : ipv6ToBigInt(ip)

  for (const range of BLOCKED_RANGES) {
    if (ipBigInt >= range.start && ipBigInt <= range.end) {
      return {
        blocked: true,
        reason: `IP ${ip} is in blocked range ${range.cidr} (${range.description})`,
      }
    }
  }

  return { blocked: false }
}

DNS Resolution Caching with Pinning

To prevent DNS rebinding, the resolved IP address must be pinned for the duration of the request:

interface PinnedDnsEntry {
  hostname: string
  resolvedIp: string
  resolvedAt: number
  ttl: number
}

class SsrfSafeDnsCache {
  private cache = new Map<string, PinnedDnsEntry>()
  private readonly MIN_TTL_MS = 30_000  // Minimum 30s TTL regardless of DNS

  async resolve(hostname: string): Promise<string> {
    // Check cache first
    const cached = this.cache.get(hostname)
    if (cached && Date.now() - cached.resolvedAt < cached.ttl) {
      return cached.resolvedIp
    }

    // Perform DNS resolution
    const addresses = await dnsResolveAll(hostname)

    if (addresses.length === 0) {
      throw new SsrfError(`DNS resolution failed for ${hostname}`)
    }

    // Validate ALL resolved addresses
    for (const addr of addresses) {
      const check = isBlockedIp(addr.address)
      if (check.blocked) {
        throw new SsrfError(
          `SSRF blocked: ${hostname} resolved to ${addr.address}. ` +
          check.reason
        )
      }
    }

    // Pin the first valid address
    const pinnedIp = addresses[0].address
    const ttl = Math.max(this.MIN_TTL_MS, (addresses[0].ttl ?? 30) * 1000)

    this.cache.set(hostname, {
      hostname,
      resolvedIp: pinnedIp,
      resolvedAt: Date.now(),
      ttl,
    })

    return pinnedIp
  }
}

Integrating SSRF Protection into WebFetch

const dnsCache = new SsrfSafeDnsCache()

async function secureFetch(
  url: string,
  options: RequestInit = {}
): Promise<Response> {
  const parsed = new URL(url)

  // Step 1: Resolve hostname with SSRF check
  const resolvedIp = await dnsCache.resolve(parsed.hostname)

  // Step 2: Create a custom agent that connects to the pinned IP
  const agent = new https.Agent({
    lookup: (hostname, opts, callback) => {
      // Override DNS: always use the pre-validated, pinned IP
      callback(null, resolvedIp, isIPv4(resolvedIp) ? 4 : 6)
    },
    // Verify the TLS certificate against the original hostname
    servername: parsed.hostname,
    rejectUnauthorized: true,
  })

  // Step 3: Make the request with the pinned agent
  const response = await fetch(url, {
    ...options,
    // @ts-expect-error -- Node.js fetch supports agent
    agent,
    redirect: 'manual',  // Handle redirects ourselves
  })

  // Step 4: Validate redirects
  if (response.status >= 300 && response.status < 400) {
    const redirectUrl = response.headers.get('location')
    if (redirectUrl) {
      return handleSecureRedirect(url, redirectUrl, options)
    }
  }

  return response
}

async function handleSecureRedirect(
  originalUrl: string,
  redirectUrl: string,
  options: RequestInit,
  depth: number = 0
): Promise<Response> {
  // Prevent infinite redirects
  if (depth >= 5) {
    throw new SsrfError(`Too many redirects (${depth}) from ${originalUrl}`)
  }

  const redirectParsed = new URL(redirectUrl, originalUrl)

  // Validate redirect destination
  const redirectIp = await dnsCache.resolve(redirectParsed.hostname)
  const check = isBlockedIp(redirectIp)
  if (check.blocked) {
    throw new SsrfError(
      `SSRF blocked: redirect from ${originalUrl} to ${redirectUrl} ` +
      `resolved to blocked IP ${redirectIp}. ${check.reason}`
    )
  }

  // Follow the redirect with the same security checks
  return secureFetch(redirectUrl, options)
}

17.3 CA Bundle Certificate Pinning

The Unpinned CA Download

Finding 18 (CVSS 5.9) identifies that downloadCaBundle() fetches a CA certificate from the API server and concatenates it with the system CA bundle. The downloaded CA is then used to validate all HTTPS connections going through the upstream proxy.

// Current implementation -- VULNERABLE
const resp = await fetch(
  `${baseUrl}/v1/code/upstreamproxy/ca-cert`,
  { signal: AbortSignal.timeout(5000) }
)
const ccrCa = await resp.text()
const systemCa = await readFile(systemCaPath, 'utf8').catch(() => '')
await writeFile(outPath, systemCa + '\n' + ccrCa, 'utf8')

The data flow: ANTHROPIC_BASE_URL -> fetch CA cert -> concatenate with system CA -> write to ~/.ccr/ca-bundle.crt -> used as SSL_CERT_FILE for all subprocesses.

Why This Matters

If an attacker can MITM the initial HTTPS connection to the API server (using a valid certificate for the API domain -- possible via a compromised CA, a corporate proxy, or a state-level attacker), they can provide a rogue CA certificate. Once the rogue CA is added to the bundle, the attacker can MITM all subsequent HTTPS connections from Claude Code and its subprocesses.

Implementing Certificate Pinning

The fix uses public key pinning: the client knows the expected public key hash of the CA certificate before downloading it. Even if an attacker provides a certificate with the correct subject name, it will have a different public key.

import { createHash, X509Certificate } from 'node:crypto'

// Known CA public key hashes (base64-encoded SHA-256 of SubjectPublicKeyInfo)
const PINNED_CA_HASHES: ReadonlySet<string> = new Set([
  // Primary CA
  'sha256/YLh1dUR9y6Kja30RrAn7JKnbQG/uEtLMkBgFF2Fuihg=',
  // Backup CA (for rotation)
  'sha256/sRHdihwgkaib1P1gN7akICObfQ0XY1oqEv8xCZH4Dns=',
])

interface CaPinningResult {
  valid: boolean
  downloadedHash: string
  reason?: string
}

function validateCaCertificate(
  certPem: string,
  pinnedHashes: ReadonlySet<string> = PINNED_CA_HASHES
): CaPinningResult {
  try {
    const cert = new X509Certificate(certPem)

    // Extract SubjectPublicKeyInfo (SPKI) and hash it
    const spki = cert.publicKey.export({
      type: 'spki',
      format: 'der',
    })
    const hash = 'sha256/' +
      createHash('sha256').update(spki).digest('base64')

    if (pinnedHashes.has(hash)) {
      return { valid: true, downloadedHash: hash }
    }

    return {
      valid: false,
      downloadedHash: hash,
      reason: `CA certificate public key hash ${hash} ` +
        'does not match any pinned hash. ' +
        'This may indicate a MITM attack or a CA rotation. ' +
        'If this is expected, update the pinned hashes.',
    }
  } catch (error) {
    return {
      valid: false,
      downloadedHash: 'PARSE_ERROR',
      reason: `Failed to parse CA certificate: ${(error as Error).message}`,
    }
  }
}

Secure CA Download with Pinning

async function downloadCaBundleSecure(
  baseUrl: string,
  outPath: string,
  systemCaPath: string
): Promise<void> {
  // Step 1: Fetch the CA certificate
  const resp = await fetch(
    `${baseUrl}/v1/code/upstreamproxy/ca-cert`,
    {
      signal: AbortSignal.timeout(5000),
      // Use system CA for this initial fetch
      // (this is the bootstrap trust problem)
    }
  )

  if (!resp.ok) {
    throw new Error(`CA download failed: ${resp.status} ${resp.statusText}`)
  }

  const ccrCa = await resp.text()

  // Step 2: Validate the certificate against pinned hashes
  const pinResult = validateCaCertificate(ccrCa)

  if (!pinResult.valid) {
    logSecurityEvent({
      event: 'ca_pin_mismatch',
      downloadedHash: pinResult.downloadedHash,
      reason: pinResult.reason,
      baseUrl,
      timestamp: Date.now(),
    })

    throw new SecurityError(
      'CA certificate pinning validation failed. ' +
      pinResult.reason +
      '\n\nThe downloaded certificate will NOT be used. ' +
      'If you are behind a corporate proxy, contact your IT team.'
    )
  }

  // Step 3: Validate the certificate is actually a CA
  const cert = new X509Certificate(ccrCa)
  if (!cert.ca) {
    throw new SecurityError(
      'Downloaded certificate is not a CA certificate (basicConstraints.cA is false). ' +
      'This may indicate a MITM attack.'
    )
  }

  // Step 4: Check certificate dates
  const now = new Date()
  if (now < new Date(cert.validFrom) || now > new Date(cert.validTo)) {
    throw new SecurityError(
      `CA certificate is not currently valid. ` +
      `Valid from: ${cert.validFrom}, Valid to: ${cert.validTo}`
    )
  }

  // Step 5: Read system CA and concatenate
  const systemCa = await readFile(systemCaPath, 'utf8').catch(() => '')

  // Step 6: Write the validated bundle atomically
  const tmpPath = `${outPath}.tmp.${process.pid}`
  await writeFile(tmpPath, systemCa + '\n' + ccrCa, 'utf8')
  await chmod(tmpPath, 0o644)
  await rename(tmpPath, outPath)  // Atomic rename

  logSecurityEvent({
    event: 'ca_bundle_updated',
    caHash: pinResult.downloadedHash,
    baseUrl,
    timestamp: Date.now(),
  })
}

Certificate Pin Rotation

Pins must be rotatable. If Anthropic rotates their CA, the CLI must be able to accept the new CA without requiring a code update. The solution: include backup pins and a pin update mechanism.

interface PinSet {
  primary: string[]     // Currently active pins
  backup: string[]      // Pre-staged backup pins for rotation
  version: number       // Pin set version
  updatedAt: string     // ISO timestamp of last update
}

async function fetchPinSet(
  baseUrl: string
): Promise<PinSet> {
  // Fetch the pin set over HTTPS (validated by system CA)
  const resp = await fetch(
    `${baseUrl}/v1/code/upstreamproxy/pin-set`,
    {
      signal: AbortSignal.timeout(5000),
      headers: {
        'X-Current-Pin-Version': String(getCurrentPinVersion()),
      },
    }
  )

  const pinSet: PinSet = await resp.json()

  // Verify the pin set itself is signed
  if (!verifyPinSetSignature(pinSet)) {
    throw new SecurityError('Pin set signature verification failed')
  }

  // The pin set must always include at least one primary
  // and one backup pin
  if (pinSet.primary.length === 0 || pinSet.backup.length === 0) {
    throw new SecurityError('Pin set must have primary and backup pins')
  }

  return pinSet
}

The Bootstrap Trust Problem

Certificate pinning has a chicken-and-egg problem: the initial HTTPS connection to download the CA uses the system's default TLS validation. If the system's CA store is compromised (corporate proxy, malicious CA), the initial fetch is already MITM'd, and the pinning check validates against the attacker's certificate.

Defense Layer What It Protects Against What It Does Not Protect Against
TLS (system CA) Network-level eavesdroppers Compromised CA in system store
Certificate pinning Rogue CAs, CA compromise First-connection MITM before pins are cached
Pin set versioning Downgrade attacks (old pins) First-ever connection (no cached pins)
Backup pins CA rotation All pins compromised simultaneously

The practical mitigation: ship initial pins as compile-time constants in the Claude Code binary. The first connection does not need to download pins -- it uses the embedded pins. Subsequent connections can update the pin set through the secure channel established by the initial pinned connection. This is the same approach used by Chrome's certificate pinning (HPKP predecessor) and Certificate Transparency logs.

17.4 TLS Configuration Hardening

Beyond certificate pinning, the TLS configuration itself must be hardened to prevent downgrade attacks and weak cipher usage.

Minimum TLS Version

import { Agent as HttpsAgent } from 'node:https'

function createSecureAgent(): HttpsAgent {
  return new HttpsAgent({
    // Minimum TLS 1.2, prefer TLS 1.3
    minVersion: 'TLSv1.2',
    maxVersion: 'TLSv1.3',

    // Reject connections that don't verify
    rejectUnauthorized: true,

    // Cipher suite ordering (prefer AEAD ciphers)
    ciphers: [
      'TLS_AES_256_GCM_SHA384',
      'TLS_AES_128_GCM_SHA256',
      'TLS_CHACHA20_POLY1305_SHA256',
      'ECDHE-ECDSA-AES256-GCM-SHA384',
      'ECDHE-RSA-AES256-GCM-SHA384',
      'ECDHE-ECDSA-AES128-GCM-SHA256',
      'ECDHE-RSA-AES128-GCM-SHA256',
    ].join(':'),

    // ECDH curves
    ecdhCurve: 'X25519:P-256:P-384',

    // Session tickets (for TLS 1.2 resumption)
    sessionTimeout: 300,
  })
}

Heartbeat and Stale Connection Detection

WebSocket connections can become stale without either side detecting it (half-open connection due to network failure, firewall timeout, or server crash). Without detection, the client continues operating under the assumption that the server is receiving its messages.

class SecureWebSocketConnection {
  private ws: WebSocket
  private heartbeatInterval: ReturnType<typeof setInterval> | null = null
  private lastPongAt: number = Date.now()
  private readonly HEARTBEAT_INTERVAL_MS = 15_000  // 15 seconds
  private readonly PONG_TIMEOUT_MS = 30_000  // 30 seconds

  startHeartbeat(): void {
    this.heartbeatInterval = setInterval(() => {
      // Check if the last pong is too old
      if (Date.now() - this.lastPongAt > this.PONG_TIMEOUT_MS) {
        this.handleStaleConnection()
        return
      }

      // Send ping
      if (this.ws.readyState === WebSocket.OPEN) {
        this.ws.ping()
      }
    }, this.HEARTBEAT_INTERVAL_MS)

    this.ws.on('pong', () => {
      this.lastPongAt = Date.now()
    })
  }

  private handleStaleConnection(): void {
    logSecurityEvent({
      event: 'websocket_stale_connection',
      lastPongAt: this.lastPongAt,
      staleDurationMs: Date.now() - this.lastPongAt,
    })

    // Close and reconnect
    this.ws.terminate()  // Hard close (no close frame)
    this.reconnectWithBackoff()
  }

  private async reconnectWithBackoff(): Promise<void> {
    const maxRetries = 5
    for (let attempt = 0; attempt < maxRetries; attempt++) {
      const delay = Math.min(1000 * Math.pow(2, attempt), 30_000)
      await sleep(delay)

      try {
        await this.connect()
        return
      } catch (error) {
        logSecurityEvent({
          event: 'websocket_reconnect_failed',
          attempt: attempt + 1,
          error: (error as Error).message,
        })
      }
    }

    throw new ConnectionError(
      `WebSocket reconnection failed after ${maxRetries} attempts`
    )
  }
}

Message Size Limits

WebSocket messages should have size limits to prevent memory exhaustion:

const MAX_WS_MESSAGE_SIZE = 10 * 1024 * 1024  // 10 MB

ws.on('message', (data: Buffer) => {
  if (data.length > MAX_WS_MESSAGE_SIZE) {
    logSecurityEvent({
      event: 'websocket_oversized_message',
      size: data.length,
      limit: MAX_WS_MESSAGE_SIZE,
    })
    ws.close(4002, 'Message exceeds size limit')
    return
  }

  // Process normally
  handleMessage(data)
})

Testing SSRF Defenses

SSRF defenses require specific test scenarios:

describe('SSRF protection', () => {
  test('blocks direct metadata IP', async () => {
    await expect(secureFetch('http://169.254.169.254/latest/'))
      .rejects.toThrow('SSRF blocked')
  })

  test('blocks IPv6 mapped IPv4 loopback', async () => {
    await expect(secureFetch('http://[::ffff:127.0.0.1]/'))
      .rejects.toThrow('SSRF blocked')
  })

  test('blocks redirect to internal IP', async () => {
    // Mock server returns 302 to http://10.0.0.1/
    mockServer.onGet('/redirect').reply(302, '', {
      location: 'http://10.0.0.1/admin',
    })
    await expect(secureFetch(mockServer.url + '/redirect'))
      .rejects.toThrow('SSRF blocked')
  })

  test('respects minimum DNS TTL', async () => {
    // First resolution: public IP
    mockDns.resolve('rebind.example.com', '203.0.113.50', { ttl: 0 })
    await secureFetch('https://rebind.example.com/page1')

    // Second resolution: would return private IP
    mockDns.resolve('rebind.example.com', '169.254.169.254', { ttl: 0 })
    // But cache has not expired (minimum 30s TTL)
    // Still uses pinned 203.0.113.50
    const resp = await secureFetch('https://rebind.example.com/page2')
    expect(resp.ok).toBe(true)
  })

  test('validates all DNS responses', async () => {
    // Hostname resolves to both public and private IPs
    mockDns.resolveMulti('dual.example.com', [
      '203.0.113.50',    // Public
      '169.254.169.254', // Metadata
    ])
    await expect(secureFetch('https://dual.example.com/'))
      .rejects.toThrow('SSRF blocked')
  })
})
