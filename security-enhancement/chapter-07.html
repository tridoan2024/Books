Chapter 7: Cross-Platform Secure Storage

Claude Code runs on macOS, Linux, and Windows. On macOS, credentials flow into the system Keychain -- a hardware-backed, kernel-protected credential store that has been hardened over two decades of real-world attacks. On every other platform, credentials land in ~/.claude/.credentials.json as plaintext JSON, protected by nothing more than chmod 0o600. This chapter eliminates that gap.

The vulnerability is not subtle. Finding 7 (CWE-256, CVSS 7.1) and Finding 10 (CWE-922, CVSS 6.5) document it clearly: getSecureStorage() returns plainTextStorage for all non-macOS platforms, with a TODO comment that has been there since the initial implementation. Finding 8 (CWE-312, CVSS 7.1) extends the blast radius to macOS itself -- when the Keychain is unavailable (Docker containers, SSH sessions, CI pipelines), the fallback is that same plaintext file.

We will build a cross-platform storage abstraction that routes credentials to the strongest available backend on each platform: macOS Keychain, Linux libsecret (GNOME Keyring / KDE Wallet), Windows Credential Manager, and an encrypted file fallback for headless environments. The abstraction layer ensures that no calling code ever needs to know which backend is active.

7.1 The Vulnerability: Plaintext on Disk

The current getSecureStorage() dispatcher is seven lines that determine the security posture of every credential Claude Code stores:

// utils/secureStorage/index.ts:9
export function getSecureStorage(): SecureStorage {
  if (process.platform === "darwin") {
    return createFallbackStorage(macOsKeychainStorage, plainTextStorage)
  }
  // TODO: add libsecret support for Linux
  return plainTextStorage
}

The plainTextStorage implementation writes credentials as JSON via writeFileSync and sets chmod 0o600:

// utils/secureStorage/plainTextStorage.ts:57
writeFileSync_DEPRECATED(storagePath, jsonStringify(data), {
  encoding: 'utf8',
  flush: false,
})
chmodSync(storagePath, 0o600)

The data flow is direct: OAuth tokens obtained during authentication are serialized to JSON, written to ~/.claude/.credentials.json, and set to owner-readable permissions. On macOS, the Keychain is tried first and this path is the fallback. On Linux and Windows, this is the only path.

Why chmod 0o600 Is Not Enough

Unix file permissions prevent other users from reading the file. They do not prevent:

Attack Vector Bypasses chmod 0o600? Real-World Scenario
Root access Yes Container escape, privilege escalation, compromised admin
Same-user process Yes Malware, malicious npm postinstall script, trojan in PATH
Disk imaging / backup Yes Cloud VM snapshots, Time Machine, enterprise backup agents
Filesystem mount in container Yes Docker volume mounts, Kubernetes hostPath volumes
Memory dump of reading process Yes Core dumps, /proc/<pid>/mem on Linux
Cloud sync agents Yes Dropbox, OneDrive, iCloud scanning ~/ subdirectories

In containerized environments -- where Claude Code increasingly runs for CI/CD -- the ~/.claude/ directory is often on a shared volume mount. File permissions on mounted volumes may not be enforced by the container runtime. A 0o600 file on a Docker bind mount is readable by any process with access to the host directory.

Impact Assessment

The credentials stored in .credentials.json include:

  • OAuth access tokens: Grant API access to the Claude service
  • OAuth refresh tokens: Can generate new access tokens indefinitely
  • Trusted device tokens: Bypass device enrollment checks
  • Session identifiers: Correlate to active authenticated sessions

An attacker who obtains the refresh token has persistent access to the Claude API under the victim's identity until the token is explicitly revoked server-side. The access token alone provides temporary access but the refresh token is the high-value target -- it is the equivalent of stealing a session cookie with no expiration.

7.2 Architecture: The Storage Abstraction Layer

The remediation replaces the two-path dispatcher (Keychain or plaintext) with a four-path dispatcher behind a uniform interface. Every platform gets a native credential store as the primary backend and an encrypted file as the fallback. Plaintext storage is eliminated entirely.

The SecureStorage interface remains unchanged -- existing code that calls getSecureStorage().read() or getSecureStorage().write() requires zero modifications:

interface SecureStorage {
  read(): Promise<Record<string, unknown> | null>
  write(data: Record<string, unknown>): Promise<void>
  delete(key: string): Promise<void>
  update(
    updater: (data: Record<string, unknown>) => Record<string, unknown>,
  ): Promise<void>
}

The createFallbackStorage wrapper already handles the primary-to-fallback cascade: try the primary backend, log a warning if it fails, fall through to the fallback. The only change is that the fallback is now encryptedFileStorage instead of plainTextStorage.

7.3 Linux: libsecret Integration via D-Bus Secret Service

Linux desktop environments provide the D-Bus Secret Service API (specified by freedesktop.org) for secure credential storage. GNOME Keyring and KDE Wallet both implement this API. The secret-tool CLI provides a portable command-line interface.

Why secret-tool Over FFI

There are two approaches to integrating with libsecret: native FFI bindings via node-ffi-napi or subprocess calls to secret-tool. The tradeoff:

Approach Startup Cost Runtime Cost Dependency Weight Failure Modes
FFI (libsecret.so) High (native build) Low (direct call) Heavy (node-gyp, libsecret-dev) Build failures on Alpine, musl, ARM
CLI (secret-tool) None Medium (process spawn) Zero (uses system binary) Missing binary on headless systems

Claude Code already uses subprocess execution for macOS Keychain (security command). The secret-tool approach maintains consistency and avoids native build dependencies that break in container and CI environments. The credential operations (read, write, delete) happen at most a few times per session -- the ~50ms overhead of process spawning is irrelevant.

Implementation: linuxSecretStorage.ts

// utils/secureStorage/linuxSecretStorage.ts
import { execFileSync } from 'child_process'

const SCHEMA = 'org.claude.credentials'
const ATTRIBUTE_KEY = 'account'
const ATTRIBUTE_VALUE = 'claude-code'
const LABEL = 'Claude Code OAuth Credentials'

function isSecretToolAvailable(): boolean {
  try {
    execFileSync('which', ['secret-tool'], {
      stdio: 'pipe',
      timeout: 5000,
    })
    return true
  } catch {
    return false
  }
}

export const linuxSecretStorage: SecureStorage = {
  async read(): Promise<Record<string, unknown> | null> {
    if (!isSecretToolAvailable()) return null
    try {
      const stdout = execFileSync(
        'secret-tool',
        ['lookup', ATTRIBUTE_KEY, ATTRIBUTE_VALUE],
        { encoding: 'utf8', stdio: ['pipe', 'pipe', 'pipe'], timeout: 10000 },
      )
      if (!stdout.trim()) return null
      return JSON.parse(stdout) as Record<string, unknown>
    } catch {
      return null
    }
  },

  async write(data: Record<string, unknown>): Promise<void> {
    if (!isSecretToolAvailable()) {
      throw new Error('secret-tool not available')
    }
    const json = JSON.stringify(data)
    execFileSync(
      'secret-tool',
      ['store', '--label', LABEL, ATTRIBUTE_KEY, ATTRIBUTE_VALUE],
      { input: json, stdio: ['pipe', 'pipe', 'pipe'], timeout: 10000 },
    )
  },

  async delete(): Promise<void> {
    if (!isSecretToolAvailable()) return
    try {
      execFileSync(
        'secret-tool',
        ['clear', ATTRIBUTE_KEY, ATTRIBUTE_VALUE],
        { stdio: ['pipe', 'pipe', 'pipe'], timeout: 10000 },
      )
    } catch {
      // Item may not exist -- not an error
    }
  },

  async update(
    updater: (data: Record<string, unknown>) => Record<string, unknown>,
  ): Promise<void> {
    const existing = await this.read()
    const updated = updater(existing ?? {})
    await this.write(updated)
  },
}

How D-Bus Secret Service Protects Credentials

When secret-tool store is called, the credential data travels through a D-Bus session to the secret service daemon (gnome-keyring-daemon or kwalletd). The daemon encrypts the data using a master key derived from the user's login password. The encrypted data is stored in ~/.local/share/keyrings/ (GNOME) or ~/.local/share/kwalletd/ (KDE).

The security properties exceed chmod 0o600 significantly:

Property chmod 0o600 D-Bus Secret Service
Encryption at rest No AES-128-CBC (GNOME) or Blowfish (KDE)
Key derivation N/A PBKDF2 from login password
Automatic locking No Locks on screen lock / session timeout
Access control File owner only Per-application ACL (optional)
Backup safety Plaintext in backups Encrypted in backups

Headless Linux: When No Secret Service Exists

On headless servers, Docker containers, and CI runners, there is no D-Bus session and no secret service daemon. isSecretToolAvailable() returns false, and the createFallbackStorage wrapper routes to encryptedFileStorage. This is the expected behavior -- headless environments cannot provide interactive credential storage, so encrypted file storage is the appropriate fallback.

7.4 Windows: Credential Manager via wincred

Windows provides the Credential Manager (wincred) for storing credentials. It is backed by DPAPI (Data Protection API), which derives encryption keys from the user's login credentials and machine-specific secrets.

Implementation: windowsCredStorage.ts

The Windows implementation uses cmdkey.exe for credential operations. This avoids native module dependencies while accessing the same credential store:

// utils/secureStorage/windowsCredStorage.ts
import { execFileSync } from 'child_process'

const TARGET_PREFIX = 'ClaudeCode:'
const TARGET_NAME = `${TARGET_PREFIX}oauth`

export const windowsCredStorage: SecureStorage = {
  async read(): Promise<Record<string, unknown> | null> {
    try {
      // PowerShell provides programmatic access to Credential Manager
      const script = `
        $cred = Get-StoredCredential -Target '${TARGET_NAME}' -ErrorAction SilentlyContinue
        if ($cred) {
          [System.Runtime.InteropServices.Marshal]::PtrToStringAuto(
            [System.Runtime.InteropServices.Marshal]::SecureStringToBSTR($cred.Password)
          )
        }
      `
      const stdout = execFileSync(
        'powershell.exe',
        ['-NoProfile', '-NonInteractive', '-Command', script],
        { encoding: 'utf8', stdio: ['pipe', 'pipe', 'pipe'], timeout: 15000 },
      )
      if (!stdout.trim()) return null
      return JSON.parse(stdout.trim()) as Record<string, unknown>
    } catch {
      return null
    }
  },

  async write(data: Record<string, unknown>): Promise<void> {
    const json = JSON.stringify(data)
    // cmdkey stores credentials in Credential Manager
    execFileSync(
      'cmdkey.exe',
      ['/generic:' + TARGET_NAME, '/user:claude-code', '/pass:' + json],
      { stdio: ['pipe', 'pipe', 'pipe'], timeout: 10000 },
    )
  },

  async delete(): Promise<void> {
    try {
      execFileSync('cmdkey.exe', ['/delete:' + TARGET_NAME], {
        stdio: ['pipe', 'pipe', 'pipe'],
        timeout: 10000,
      })
    } catch {
      // Credential may not exist
    }
  },

  async update(
    updater: (data: Record<string, unknown>) => Record<string, unknown>,
  ): Promise<void> {
    const existing = await this.read()
    const updated = updater(existing ?? {})
    await this.write(updated)
  },
}

DPAPI Protection Properties

Windows Credential Manager credentials are encrypted with DPAPI, which provides:

  • User-scoped encryption: Only the user who stored the credential can decrypt it, even with local admin access (unless the admin resets the user's password)
  • Machine binding: Credentials cannot be decrypted on a different machine (the master key includes a machine-specific component)
  • Transparent to backups: Backed-up credentials remain encrypted; they can only be restored on the same machine under the same user account

The credential size limit for cmdkey is approximately 2,560 bytes. OAuth credential JSON typically fits within this limit, but the implementation should validate size before writing and fall through to encrypted file storage for oversized payloads.

7.5 Encrypted File Fallback: AES-256-GCM

When no platform credential store is available -- headless Linux, Docker containers, CI/CD runners, or any platform where the primary backend fails -- the encrypted file fallback provides defense in depth. It replaces the current plainTextStorage entirely.

Key Derivation

The encryption key is derived from machine-specific data that is available without user interaction:

// utils/secureStorage/encryptedFileStorage.ts
import { createHash, randomBytes, createCipheriv, createDecipheriv } from 'crypto'
import { readFileSync, existsSync } from 'fs'
import { homedir } from 'os'

const ALGORITHM = 'aes-256-gcm'
const KEY_LENGTH = 32 // 256 bits
const IV_LENGTH = 12  // 96 bits for GCM
const SALT_LENGTH = 32
const TAG_LENGTH = 16 // 128-bit auth tag

function getMachineIdentifier(): string {
  // Linux: /etc/machine-id (unique per installation, persists across reboots)
  // macOS: IOPlatformUUID via ioreg
  // Windows: MachineGuid from registry
  // Fallback: hostname + homedir hash
  const candidates = [
    '/etc/machine-id',
    '/var/lib/dbus/machine-id',
  ]
  for (const path of candidates) {
    try {
      const id = readFileSync(path, 'utf8').trim()
      if (id.length >= 16) return id
    } catch {
      continue
    }
  }
  // Fallback: hash of hostname + homedir + uid
  return createHash('sha256')
    .update(`${require('os').hostname()}:${homedir()}:${process.getuid?.() ?? 0}`)
    .digest('hex')
}

function deriveKey(salt: Buffer): Buffer {
  const machineId = getMachineIdentifier()
  const userContext = `claude-code:${process.getuid?.() ?? homedir()}`
  // HKDF-like derivation: HMAC-SHA256(salt, machineId || userContext)
  return createHash('sha256')
    .update(salt)
    .update(machineId)
    .update(userContext)
    .digest()
}

Encryption and Decryption

function encrypt(plaintext: string, key: Buffer): Buffer {
  const iv = randomBytes(IV_LENGTH)
  const cipher = createCipheriv(ALGORITHM, key, iv, { authTagLength: TAG_LENGTH })
  const encrypted = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()])
  const authTag = cipher.getAuthTag()
  // Format: [salt_len(1)][salt][iv][authTag][ciphertext]
  // Salt is stored alongside for key re-derivation on read
  return encrypted
}

function decrypt(bundle: Buffer, key: Buffer, iv: Buffer, authTag: Buffer): string {
  const decipher = createDecipheriv(ALGORITHM, key, iv, { authTagLength: TAG_LENGTH })
  decipher.setAuthTag(authTag)
  return decipher.update(bundle, undefined, 'utf8') + decipher.final('utf8')
}

File Format

The encrypted credential file (.credentials.enc) uses a binary format:

Byte layout of .credentials.enc:
┌──────────┬──────────┬──────────┬──────────┬──────────────────┐
│ Version  │  Salt    │  IV      │ Auth Tag │ Ciphertext       │
│ (1 byte) │ (32 B)  │ (12 B)  │ (16 B)  │ (variable)       │
│ 0x01     │          │          │          │                  │
└──────────┴──────────┴──────────┴──────────┴──────────────────┘

The version byte enables future format changes without breaking existing encrypted files. The salt is stored with the ciphertext because it is needed to re-derive the key on read -- the salt is not secret (it randomizes the key derivation, but the secrecy comes from the machine identifier).

Complete Storage Implementation

export const encryptedFileStorage: SecureStorage = {
  async read(): Promise<Record<string, unknown> | null> {
    const encPath = getEncryptedStoragePath()
    if (!existsSync(encPath)) return null
    try {
      const raw = readFileSync(encPath)
      if (raw.length < 1 + SALT_LENGTH + IV_LENGTH + TAG_LENGTH + 1) return null

      const version = raw[0]
      if (version !== 0x01) {
        throw new Error(`Unknown credential file version: ${version}`)
      }
      let offset = 1
      const salt = raw.subarray(offset, offset + SALT_LENGTH); offset += SALT_LENGTH
      const iv = raw.subarray(offset, offset + IV_LENGTH); offset += IV_LENGTH
      const authTag = raw.subarray(offset, offset + TAG_LENGTH); offset += TAG_LENGTH
      const ciphertext = raw.subarray(offset)

      const key = deriveKey(salt)
      const plaintext = decrypt(ciphertext, key, iv, authTag)
      return JSON.parse(plaintext) as Record<string, unknown>
    } catch {
      return null
    }
  },

  async write(data: Record<string, unknown>): Promise<void> {
    const encPath = getEncryptedStoragePath()
    const dir = dirname(encPath)
    if (!existsSync(dir)) {
      mkdirSync(dir, { recursive: true, mode: 0o700 })
    }

    const plaintext = JSON.stringify(data)
    const salt = randomBytes(SALT_LENGTH)
    const key = deriveKey(salt)
    const iv = randomBytes(IV_LENGTH)
    const cipher = createCipheriv(ALGORITHM, key, iv, { authTagLength: TAG_LENGTH })
    const encrypted = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()])
    const authTag = cipher.getAuthTag()

    const bundle = Buffer.concat([
      Buffer.from([0x01]),  // version
      salt, iv, authTag, encrypted,
    ])

    // Atomic write (see Chapter 8 for the full pattern)
    const tmpPath = encPath + '.tmp.' + process.pid
    const fd = openSync(tmpPath, 'w', 0o600)
    try {
      writeSync(fd, bundle)
      fsyncSync(fd)
    } finally {
      closeSync(fd)
    }
    renameSync(tmpPath, encPath)
  },

  // ... delete() and update() follow the same patterns
}

Security Properties of the Encrypted Fallback

Property plainTextStorage (BEFORE) encryptedFileStorage (AFTER)
At-rest encryption None AES-256-GCM
Authentication None GCM auth tag (tamper detection)
Key source N/A Machine-specific identifier + user context
Backup safety Plaintext in backups Encrypted in backups
Cross-machine portability File readable anywhere File decryptable only on same machine
Root access Full credential access Must know machine-id to derive key

Threat model limitation: An attacker with root access on the same machine can read /etc/machine-id and derive the key. The encrypted fallback is defense-in-depth, not a substitute for a proper credential store. It raises the bar from "read a JSON file" to "understand the key derivation scheme and extract machine-specific inputs." This stops backup exfiltration, casual disk access, and cloud sync leaks -- the most common real-world attack vectors.

7.7 Container and CI/CD Considerations

Containerized environments present unique challenges for credential storage:

  1. No D-Bus session: Container images typically do not include gnome-keyring or any D-Bus secret service
  2. Ephemeral filesystems: Container filesystems may be destroyed between runs
  3. Shared volumes: Mounted directories may have relaxed permissions
  4. No interactive authentication: CI/CD pipelines cannot prompt for passwords

Container Detection

The storage layer should detect container environments and adjust behavior:

function isContainerEnvironment(): boolean {
  // Docker
  if (existsSync('/.dockerenv')) return true
  // Kubernetes
  if (process.env.KUBERNETES_SERVICE_HOST) return true
  // Generic cgroup detection
  try {
    const cgroup = readFileSync('/proc/1/cgroup', 'utf8')
    if (cgroup.includes('docker') || cgroup.includes('kubepods')) return true
  } catch {
    // Not on Linux or no access to /proc
  }
  return false
}

In container environments, the recommended credential injection method is environment variables with short-lived tokens:

if (isContainerEnvironment()) {
  logWarning(
    'Running in container environment. ' +
    'Recommend using CLAUDE_OAUTH_TOKEN env var with short-lived tokens. ' +
    'File-based credential storage in containers is inherently less secure.',
  )
}

Shared Volume Detection

When ~/.claude/ resides on a volume mount (the stat device differs from the home directory's device), the storage layer should warn:

function isOnSharedVolume(path: string): boolean {
  try {
    const pathStat = statSync(path)
    const homeStat = statSync(homedir())
    return pathStat.dev !== homeStat.dev
  } catch {
    return false
  }
}

CI/CD Token Lifetime Management

In CI/CD pipelines, long-lived tokens stored in environment variables create risk -- if the CI runner is compromised, the token remains valid. The storage layer should support short-lived token requests:

interface TokenLifetimeConfig {
  /** Token lifetime in seconds. Default: 86400 (24h). CI recommended: 3600 (1h). */
  lifetimeSeconds: number
  /** Source identifier for audit trail */
  source: 'oauth_flow' | 'env_var' | 'ci_injection'
}

function getTokenLifetime(): number {
  const envLifetime = process.env.CLAUDE_TOKEN_LIFETIME
  if (envLifetime === 'short') return 3600      // 1 hour for CI/CD
  if (envLifetime === 'medium') return 28800     // 8 hours for dev sessions
  return 86400                                     // 24 hours default
}

The CLAUDE_TOKEN_LIFETIME=short environment variable signals that the token should expire quickly. This is documented as the recommended configuration for CI/CD environments in the Security Action Report's remediation guidance for Finding 10. Combined with container detection, the storage layer can automatically suggest short-lived tokens when it detects an ephemeral environment.

WSL (Windows Subsystem for Linux)

WSL presents a unique case: it is a Linux environment but has access to Windows Credential Manager via cmd.exe /c cmdkey. The storage layer should detect WSL and offer the Windows backend as the primary, with the Linux encrypted fallback:

function isWSL(): boolean {
  try {
    const release = readFileSync('/proc/version', 'utf8')
    return release.toLowerCase().includes('microsoft')
  } catch {
    return false
  }
}

// In the dispatcher:
if (process.platform === 'linux' && isWSL()) {
  return createFallbackStorage(windowsCredStorage, encryptedFileStorage)
}

This routes WSL users to the same DPAPI-backed credential store that native Windows users enjoy, avoiding the less-secure encrypted file fallback when a stronger option is available.

7.8 Migration: Plaintext to Encrypted

Existing installations have credentials in ~/.claude/.credentials.json. The migration must be seamless -- users should not need to re-authenticate.

Migration Strategy

graph TD
    START["getSecureStorage().read()"] --> CHECK{"Encrypted file<br/>exists?"}
    CHECK -->|Yes| READ_ENC["Read encrypted file"]
    CHECK -->|No| CHECK_PLAIN{"Plaintext file<br/>exists?"}

    CHECK_PLAIN -->|Yes| MIGRATE["Read plaintext<br/>Write to new backend<br/>Delete plaintext"]
    CHECK_PLAIN -->|No| RETURN_NULL["Return null<br/>(no stored credentials)"]

    MIGRATE --> VERIFY{"Migration<br/>successful?"}
    VERIFY -->|Yes| DELETE_PLAIN["Securely delete<br/>.credentials.json"]
    VERIFY -->|No| KEEP_PLAIN["Keep plaintext<br/>Log warning"]

    READ_ENC --> RETURN["Return credentials"]
    DELETE_PLAIN --> RETURN
    KEEP_PLAIN --> RETURN

Secure Deletion of Plaintext Credentials

After migrating credentials to the new backend, the plaintext file must be destroyed -- not just deleted. A simple unlink() leaves the data on disk until the filesystem overwrites those blocks.

function secureDeleteFile(filePath: string): void {
  try {
    const stat = statSync(filePath)
    // Overwrite with random data before deleting
    const fd = openSync(filePath, 'w')
    try {
      const randomData = randomBytes(stat.size)
      writeSync(fd, randomData)
      fsyncSync(fd)
    } finally {
      closeSync(fd)
    }
    unlinkSync(filePath)
  } catch {
    // Best effort -- if overwrite fails, still try to unlink
    try { unlinkSync(filePath) } catch { /* ignore */ }
  }
}

Caveat: On copy-on-write filesystems (ZFS, APFS, btrfs), overwriting a file does not destroy the original data blocks -- the filesystem allocates new blocks and marks old ones as free. On SSD media, TRIM may defer actual block erasure. Secure deletion is best-effort defense-in-depth, not a guarantee. The primary defense is preventing plaintext storage in the first place.

7.10 Residual Risk

The cross-platform secure storage eliminates the plaintext credential vulnerability on all platforms. However, residual risks remain:

Residual Risk Severity Mitigation
Root attacker on same machine can derive encryption key Medium Encrypted fallback is defense-in-depth; root is game-over in most threat models
Container environments have weaker isolation Medium Document env var token injection as preferred CI/CD path
Copy-on-write filesystems retain plaintext during migration Low Migration is one-time; TRIM eventually clears blocks
secret-tool CLI may not be installed on all Linux distros Low Encrypted file fallback activates automatically
Windows cmdkey credential size limit (~2.5KB) Low Fall through to encrypted file for oversized payloads

The dependency chain impact, as documented in the Security Action Report, is significant: Findings 7, 8, and 10 are all resolved by this implementation. The Credential Storage Chain (Findings 7, 8, 10, 20, 30, 37, 39) has its root cause -- plaintext storage on non-macOS platforms -- eliminated. As discussed in Chapter 8, the atomic write pattern addresses Finding 30. The chain effect means this single architectural change reduces risk across seven related findings.
