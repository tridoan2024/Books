Chapter 13: Process-Level Agent Isolation

Part IV secured the authentication token lifecycle: JWT signatures are verified via JWKS (Chapter 10), token refresh is bounded and source-aware (Chapter 11), and the OAuth/device trust flows are hardened against local attacks (Chapter 12). With authentication solid, Part V turns to the most architecturally significant vulnerability in Claude Code: subagents execute in the same process as the parent agent, sharing memory, file descriptors, and tool access without isolation boundaries.

This chapter addresses Finding V-3: Subagent Execution Without Process-Level Isolation (CWE-269, CVSS 7.8). In the current architecture, when Claude Code spawns a subagent --- whether from a user-defined agent file, a plugin-supplied agent, or a recursive fork --- the subagent runs as a function call within the parent Node.js process. It shares the parent's AppState store, has access to all tools (filtered only by name-based string matching), and can fork additional children recursively. A single malicious plugin agent has full access to credentials, filesystem, network, and shell execution through the parent's process context.

The fix requires process isolation via child_process.fork() with IPC channels, capability-based tool filtering enforced at process boundaries, and memory isolation between parent and child agents.

The Name-Based Filtering Illusion

The tool restriction appears to limit subagent capabilities:

// Agent frontmatter
tools: ['Read', 'Grep', 'Glob']

But this restriction is advisory, not enforced:

  1. Same process memory. The filtered ToolRegistry is a JavaScript array in the same heap. The subagent's LLM conversation is limited to the filtered tools, but the parent's tool implementations are still in memory. A sufficiently sophisticated prompt injection in the subagent's context could, through chain-of-thought manipulation, cause the parent to execute unfiltered tools on the subagent's behalf.

  2. Wildcard access. Many plugin-defined agents specify tools: ['*'], which bypasses filtering entirely. The audit found this pattern in real marketplace plugins.

  3. Agent tool recursion. The AgentTool itself is available to subagents, enabling recursive forking. Each child inherits the parent's tool set (or a superset if wildcard is specified), creating an exponential expansion of capability.

  4. Hooks in parent context. Agent frontmatter can define hooks that execute in the parent's context, not the subagent's context. A malicious hook specification could execute arbitrary code with full parent privileges.

The Recursive Forking Amplification (CWE-674)

Finding V-14 compounds the isolation problem. The current fork depth guard is a single-layer check based on message content:

// forkSubagent.ts — VULNERABLE depth guard
export function isInForkChild(messages: MessageType[]): boolean {
  return messages.some(m => {
    if (m.type !== 'user') return false
    const content = m.message.content
    if (!Array.isArray(content)) return false
    return content.some(
      block =>
        block.type === 'text' &&
        block.text.includes(`<${FORK_BOILERPLATE_TAG}>`),
    )
  })
}

This check only detects whether we are in a fork child, not how deep the fork tree is. A depth-2 fork child passes the same check as a depth-1 child. Without hard depth tracking, the following attack chain is possible:

Parent Agent
├── Subagent A (depth 1) — from malicious plugin
│   ├── Subagent B (depth 2) — recursive fork
│   │   ├── Subagent C (depth 3) — recursive fork
│   │   │   └── ... (continues until OOM)
│   │   └── Subagent D (depth 3)
│   └── Subagent E (depth 2)
└── Subagent F (depth 1) — legitimate

Each subagent consumes memory for its conversation context, LLM state, and tool results. With no depth limit, exponential growth quickly exhausts system resources.

13.2 The Fix: Process-Level Isolation Architecture

The remediation replaces in-process subagent execution with child_process.fork() for plugin-sourced agents, creating a true process boundary between parent and child.

Design Principles

  1. Plugin agents run in child processes. Any agent defined by a plugin (marketplace or local) executes in a forked child process with IPC message passing.

  2. Built-in agents run in-process. Agents defined in .claude/agents/ by the user are trusted (same trust level as the user's own code) and run in-process for performance.

  3. Capability enforcement at process boundary. Tool calls from child processes pass through a ToolProxy in the parent that validates each call against the agent's declared capabilities.

  4. AppState isolation. Child processes receive a serialized read-only snapshot of AppState. Mutations require explicit IPC roundtrips to the parent.

  5. Resource limits. Each child process has CPU, memory, and file descriptor limits enforced by the OS.

Component 1: Process Forking with IPC

// tools/AgentTool/isolatedAgent.ts — NEW FILE
import { fork, ChildProcess } from 'child_process'
import { createHash, randomBytes } from 'crypto'
import { EventEmitter } from 'events'

interface AgentCapabilities {
  filesystem: 'none' | 'read' | 'readwrite'
  network: 'none' | 'allowed'
  shell: 'none' | 'restricted' | 'allowed'
  maxMemoryMB: number
  maxCpuSeconds: number
  maxFileDescriptors: number
  allowedTools: string[]
  deniedPaths: string[]
}

interface IpcToolRequest {
  type: 'tool_request'
  requestId: string
  toolName: string
  toolInput: Record<string, unknown>
  agentId: string
}

interface IpcToolResponse {
  type: 'tool_response'
  requestId: string
  success: boolean
  result?: unknown
  error?: string
}

interface IpcStateRequest {
  type: 'state_request'
  requestId: string
  path: string  // dot-separated path into AppState
}

const MAX_FORK_DEPTH = 3
const MAX_CONCURRENT_AGENTS = 10
const CHILD_STARTUP_TIMEOUT_MS = 10_000
const CHILD_IDLE_TIMEOUT_MS = 300_000  // 5 minutes

/**
 * Spawn an isolated agent in a child process with capability-based restrictions.
 * Communication is via structured IPC messages only — no shared memory.
 */
export class IsolatedAgentRunner extends EventEmitter {
  private child: ChildProcess | null = null
  private capabilities: AgentCapabilities
  private agentId: string
  private forkDepth: number
  private pendingRequests: Map<string, {
    resolve: (value: IpcToolResponse) => void
    timeout: NodeJS.Timeout
  }> = new Map()

  constructor(
    agentConfig: AgentConfig,
    parentForkDepth: number,
  ) {
    super()
    this.agentId = createHash('sha256')
      .update(randomBytes(16))
      .digest('hex')
      .slice(0, 16)
    this.forkDepth = parentForkDepth + 1
    this.capabilities = this.deriveCapabilities(agentConfig)
  }

  /**
   * Derive capability set from agent configuration.
   * Plugin agents get restricted capabilities by default.
   * User-defined agents get broader access (but still process-isolated if from plugin).
   */
  private deriveCapabilities(config: AgentConfig): AgentCapabilities {
    const tools = config.tools ?? []
    const hasWildcard = tools.includes('*')

    return {
      filesystem: this.deriveFilesystemAccess(tools, hasWildcard),
      network: tools.some(t => ['WebFetch', 'WebSearch'].includes(t))
        ? 'allowed' : 'none',
      shell: this.deriveShellAccess(tools, hasWildcard),
      maxMemoryMB: config.maxMemoryMB ?? 512,
      maxCpuSeconds: config.maxCpuSeconds ?? 300,
      maxFileDescriptors: 256,
      allowedTools: hasWildcard ? [] : tools,  // Empty = check denied
      deniedPaths: [
        '~/.claude/.credentials.json',
        '~/.claude/settings.local.json',
        '**/.env',
        '**/*.pem',
        '**/*.key',
      ],
    }
  }

  private deriveFilesystemAccess(
    tools: string[],
    hasWildcard: boolean,
  ): 'none' | 'read' | 'readwrite' {
    if (hasWildcard) return 'readwrite'
    const writeTools = ['Write', 'Edit', 'NotebookEdit']
    const readTools = ['Read', 'Glob', 'Grep']
    if (tools.some(t => writeTools.includes(t))) return 'readwrite'
    if (tools.some(t => readTools.includes(t))) return 'read'
    return 'none'
  }

  private deriveShellAccess(
    tools: string[],
    hasWildcard: boolean,
  ): 'none' | 'restricted' | 'allowed' {
    if (!hasWildcard && !tools.includes('Bash')) return 'none'
    // Even with Bash access, plugin agents get restricted shell
    return 'restricted'
  }

  /**
   * Start the isolated agent process.
   */
  async start(
    directive: string,
    stateSnapshot: SerializedAppState,
  ): Promise<void> {
    if (this.forkDepth > MAX_FORK_DEPTH) {
      throw new Error(
        `Maximum fork depth (${MAX_FORK_DEPTH}) reached. ` +
        `Cannot create nested subagent at depth ${this.forkDepth}.`,
      )
    }

    // Fork child process with restricted environment
    this.child = fork(
      require.resolve('./agentChildProcess.js'),
      [],
      {
        stdio: ['pipe', 'pipe', 'pipe', 'ipc'],
        env: this.buildRestrictedEnv(),
        execArgv: [
          `--max-old-space-size=${this.capabilities.maxMemoryMB}`,
        ],
      },
    )

    // Set up IPC message handling
    this.child.on('message', (msg: IpcToolRequest | IpcStateRequest) => {
      this.handleChildMessage(msg)
    })

    this.child.on('exit', (code, signal) => {
      this.emit('exit', { code, signal, agentId: this.agentId })
      this.cleanup()
    })

    // Send initialization message
    this.child.send({
      type: 'init',
      agentId: this.agentId,
      directive,
      capabilities: this.capabilities,
      stateSnapshot,
      forkDepth: this.forkDepth,
    })

    // Startup timeout
    await this.waitForReady(CHILD_STARTUP_TIMEOUT_MS)
  }

  /**
   * Build a restricted environment for the child process.
   * Strips sensitive variables and adds isolation markers.
   */
  private buildRestrictedEnv(): NodeJS.ProcessEnv {
    const restricted: NodeJS.ProcessEnv = {}

    // Allowlist of safe environment variables
    const allowedEnvVars = [
      'PATH', 'HOME', 'USER', 'SHELL', 'TERM', 'LANG',
      'NODE_ENV', 'TZ', 'TMPDIR',
    ]

    for (const key of allowedEnvVars) {
      if (process.env[key]) {
        restricted[key] = process.env[key]
      }
    }

    // Add isolation markers
    restricted.CLAUDE_AGENT_ISOLATED = '1'
    restricted.CLAUDE_AGENT_ID = this.agentId
    restricted.CLAUDE_FORK_DEPTH = String(this.forkDepth)

    // Explicitly exclude sensitive variables
    // CLAUDE_CODE_OAUTH_TOKEN, ANTHROPIC_API_KEY, etc. are NOT copied

    return restricted
  }
}

Key design decisions:

Environment variable stripping. The child process receives only an allowlist of safe environment variables. All CLAUDE_*, ANTHROPIC_*, and AWS_* variables are excluded. This prevents the child from reading credentials or API keys from the environment --- a significant isolation improvement over the in-process model where process.env was fully shared.

Memory limits via --max-old-space-size. Node.js V8 heap size is capped per child process. The default 512MB is sufficient for most agent tasks while preventing a single child from consuming all available memory.

IPC-only communication. The child process has no direct access to parent memory. All tool calls must be serialized as IPC messages, pass through the ToolProxy, and return as IPC responses. This creates a mechanical enforcement boundary --- the child physically cannot access parent memory because it runs in a separate OS process with a separate address space.

Component 2: Capability-Based Tool Proxy

The ToolProxy sits in the parent process and mediates every tool call from child agents:

// tools/AgentTool/toolProxy.ts — NEW FILE

interface ProxyDecision {
  allowed: boolean
  reason?: string
}

/**
 * ToolProxy enforces capability-based restrictions on tool calls
 * from isolated agent processes. Every tool request from a child
 * process passes through this proxy before reaching the actual
 * tool implementation.
 *
 * This replaces the name-based filtering (which was advisory)
 * with process-boundary enforcement (which is mechanical).
 */
export class ToolProxy {
  private capabilities: AgentCapabilities
  private callCount: number = 0
  private readonly MAX_CALLS_PER_AGENT = 1000

  constructor(capabilities: AgentCapabilities) {
    this.capabilities = capabilities
  }

  /**
   * Evaluate whether a tool call is permitted under the agent's
   * capability set. Returns a decision with reason.
   */
  evaluate(request: IpcToolRequest): ProxyDecision {
    this.callCount++

    // Rate limiting
    if (this.callCount > this.MAX_CALLS_PER_AGENT) {
      return {
        allowed: false,
        reason: `Agent exceeded maximum tool calls (${this.MAX_CALLS_PER_AGENT})`,
      }
    }

    // Tool allowlist check
    if (
      this.capabilities.allowedTools.length > 0 &&
      !this.capabilities.allowedTools.includes(request.toolName)
    ) {
      return {
        allowed: false,
        reason: `Tool '${request.toolName}' not in agent's allowed tools`,
      }
    }

    // Capability-specific checks
    switch (request.toolName) {
      case 'Read':
      case 'Glob':
      case 'Grep':
        return this.evaluateFilesystemRead(request)

      case 'Write':
      case 'Edit':
      case 'NotebookEdit':
        return this.evaluateFilesystemWrite(request)

      case 'Bash':
        return this.evaluateShellExec(request)

      case 'WebFetch':
      case 'WebSearch':
        return this.evaluateNetwork(request)

      case 'AgentTool':
        return this.evaluateNestedAgent(request)

      default:
        return { allowed: true }
    }
  }

  private evaluateFilesystemRead(request: IpcToolRequest): ProxyDecision {
    if (this.capabilities.filesystem === 'none') {
      return {
        allowed: false,
        reason: 'Agent does not have filesystem read permission',
      }
    }

    // Check denied paths
    const path = String(request.toolInput.file_path ?? request.toolInput.path ?? '')
    for (const denied of this.capabilities.deniedPaths) {
      if (matchesGlob(path, denied)) {
        return {
          allowed: false,
          reason: `Path '${path}' matches denied pattern '${denied}'`,
        }
      }
    }

    return { allowed: true }
  }

  private evaluateFilesystemWrite(request: IpcToolRequest): ProxyDecision {
    if (this.capabilities.filesystem !== 'readwrite') {
      return {
        allowed: false,
        reason: 'Agent does not have filesystem write permission',
      }
    }

    const path = String(request.toolInput.file_path ?? '')
    for (const denied of this.capabilities.deniedPaths) {
      if (matchesGlob(path, denied)) {
        return {
          allowed: false,
          reason: `Write to '${path}' blocked by denied pattern '${denied}'`,
        }
      }
    }

    return { allowed: true }
  }

  private evaluateShellExec(request: IpcToolRequest): ProxyDecision {
    if (this.capabilities.shell === 'none') {
      return {
        allowed: false,
        reason: 'Agent does not have shell execution permission',
      }
    }

    const command = String(request.toolInput.command ?? '')

    if (this.capabilities.shell === 'restricted') {
      // Restricted shell: block destructive commands
      const blocked = [
        /rm\s+-rf/,
        /chmod\s+777/,
        /curl.*\|\s*sh/,
        /wget.*\|\s*sh/,
        />\s*\/dev\/sd/,
        /mkfs/,
        /dd\s+if=/,
      ]

      for (const pattern of blocked) {
        if (pattern.test(command)) {
          return {
            allowed: false,
            reason: `Command matches restricted pattern in isolated agent context`,
          }
        }
      }
    }

    return { allowed: true }
  }

  private evaluateNetwork(request: IpcToolRequest): ProxyDecision {
    if (this.capabilities.network === 'none') {
      return {
        allowed: false,
        reason: 'Agent does not have network access permission',
      }
    }

    return { allowed: true }
  }

  private evaluateNestedAgent(request: IpcToolRequest): ProxyDecision {
    // Nested agent calls are always routed through the parent's
    // IsolatedAgentRunner, which enforces MAX_FORK_DEPTH.
    // We permit the request here but it will be depth-checked
    // by the parent before forking.
    return { allowed: true }
  }
}

Component 3: Fork Depth Enforcement

The recursive forking vulnerability (V-14) requires hard depth tracking that cannot be spoofed by message manipulation:

// tools/AgentTool/forkDepth.ts — NEW FILE

/** Maximum allowed fork depth. Prevents exponential process/memory growth. */
export const MAX_FORK_DEPTH = 3

/** Maximum concurrent agent processes across all depths. */
export const MAX_CONCURRENT_AGENTS = 10

/**
 * Global registry of active agent processes.
 * Tracks depth, resource usage, and parent-child relationships.
 */
class AgentRegistry {
  private agents: Map<string, {
    agentId: string
    depth: number
    parentId: string | null
    pid: number
    startedAt: number
    capabilities: AgentCapabilities
  }> = new Map()

  register(
    agentId: string,
    depth: number,
    parentId: string | null,
    pid: number,
    capabilities: AgentCapabilities,
  ): { allowed: true } | { allowed: false; reason: string } {
    // Check depth limit
    if (depth > MAX_FORK_DEPTH) {
      return {
        allowed: false,
        reason: `Fork depth ${depth} exceeds maximum ${MAX_FORK_DEPTH}`,
      }
    }

    // Check concurrent limit
    if (this.agents.size >= MAX_CONCURRENT_AGENTS) {
      return {
        allowed: false,
        reason: `Maximum concurrent agents (${MAX_CONCURRENT_AGENTS}) reached`,
      }
    }

    // Check for circular fork chains
    if (parentId && this.hasAncestor(parentId, agentId)) {
      return {
        allowed: false,
        reason: 'Circular fork chain detected',
      }
    }

    this.agents.set(agentId, {
      agentId,
      depth,
      parentId,
      pid,
      startedAt: Date.now(),
      capabilities,
    })

    return { allowed: true }
  }

  unregister(agentId: string): void {
    this.agents.delete(agentId)
  }

  /**
   * Check if `candidateAncestor` is an ancestor of `agentId`.
   * Prevents circular fork chains where A forks B forks A.
   */
  private hasAncestor(agentId: string, candidateAncestor: string): boolean {
    let current = agentId
    const visited = new Set<string>()

    while (current) {
      if (visited.has(current)) return false  // Cycle guard
      visited.add(current)

      if (current === candidateAncestor) return true
      current = this.agents.get(current)?.parentId ?? ''
    }

    return false
  }

  /**
   * Get a tree visualization of active agents for debugging.
   */
  getTree(): string {
    const roots = Array.from(this.agents.values())
      .filter(a => a.parentId === null)

    const lines: string[] = []
    for (const root of roots) {
      this.printTree(root.agentId, 0, lines)
    }
    return lines.join('\n')
  }

  private printTree(agentId: string, indent: number, lines: string[]): void {
    const agent = this.agents.get(agentId)
    if (!agent) return

    const prefix = '  '.repeat(indent) + (indent > 0 ? '|- ' : '')
    const age = Math.round((Date.now() - agent.startedAt) / 1000)
    lines.push(
      `${prefix}[${agent.agentId.slice(0, 8)}] depth=${agent.depth} ` +
      `pid=${agent.pid} age=${age}s`,
    )

    for (const child of this.agents.values()) {
      if (child.parentId === agentId) {
        this.printTree(child.agentId, indent + 1, lines)
      }
    }
  }
}

export const agentRegistry = new AgentRegistry()

The depth is tracked in the parent process's AgentRegistry, not in the child's message context. This means a malicious child process cannot manipulate its perceived depth by editing its conversation messages --- the depth is recorded by the parent when the child is forked and cannot be changed by the child.

The isolation is mechanical:

  1. Separate address spaces. The child process has its own virtual memory. There is no way to read parent heap memory from the child process (without kernel exploits, which are out of scope).

  2. Serialized IPC only. Messages passed via child.send() are serialized to JSON (or structured clone) and deserialized in the other process. No object references, closures, or buffer pointers cross the boundary.

  3. Stripped environment. The child's process.env contains only the allowlisted variables. CLAUDE_CODE_OAUTH_TOKEN, ANTHROPIC_API_KEY, and all other sensitive variables are absent.

  4. Separate file descriptor table. The child cannot access the parent's open file handles, network sockets, or database connections. The stdio: ['pipe', 'pipe', 'pipe', 'ipc'] configuration gives the child its own stdin/stdout/stderr plus the IPC channel.

Component 5: OS-Level Resource Limits

Beyond Node.js --max-old-space-size, we apply OS-level limits to contain resource consumption:

// tools/AgentTool/resourceLimits.ts — NEW FILE

import { execSync } from 'child_process'

interface ResourceLimits {
  maxMemoryMB: number
  maxCpuSeconds: number
  maxFileDescriptors: number
  maxProcesses: number
}

/**
 * Apply OS-level resource limits to a child process.
 * Uses platform-specific mechanisms:
 * - Linux: cgroups v2 or ulimit
 * - macOS: launchctl limits or ulimit
 */
export function applyResourceLimits(
  pid: number,
  limits: ResourceLimits,
): void {
  if (process.platform === 'linux') {
    applyLinuxLimits(pid, limits)
  } else if (process.platform === 'darwin') {
    applyDarwinLimits(pid, limits)
  }
  // Windows: not yet supported (child_process inherits parent limits)
}

function applyLinuxLimits(pid: number, limits: ResourceLimits): void {
  try {
    // Create a cgroup for this agent process
    const cgroupPath = `/sys/fs/cgroup/claude-agents/${pid}`

    // Memory limit
    execSync(`mkdir -p ${cgroupPath}`)
    execSync(`echo ${limits.maxMemoryMB * 1024 * 1024} > ${cgroupPath}/memory.max`)

    // CPU limit (in microseconds per 100ms period)
    const cpuQuota = Math.min(limits.maxCpuSeconds * 10000, 100000)
    execSync(`echo ${cpuQuota} 100000 > ${cgroupPath}/cpu.max`)

    // Process count limit
    execSync(`echo ${limits.maxProcesses} > ${cgroupPath}/pids.max`)

    // Add the child process to the cgroup
    execSync(`echo ${pid} > ${cgroupPath}/cgroup.procs`)
  } catch {
    // cgroups may not be available (container, unprivileged)
    // Fall back to ulimit-based limits via child process
  }
}

13.3 IPC Protocol Design

The IPC channel between parent and child uses a structured message protocol:

sequenceDiagram
    participant Parent as Parent Process
    participant Proxy as ToolProxy
    participant Child as Child Process (Agent)
    participant LLM as LLM API

    Parent->>Child: init { agentId, directive, capabilities, stateSnapshot }
    Child-->>Parent: ready { agentId }

    loop Agent Conversation
        Child->>LLM: Query with tool definitions
        LLM-->>Child: Tool call response

        Child->>Parent: tool_request { requestId, toolName, toolInput }
        Parent->>Proxy: evaluate(request)

        alt Allowed
            Proxy-->>Parent: { allowed: true }
            Parent->>Parent: Execute tool
            Parent-->>Child: tool_response { requestId, success: true, result }
        else Denied
            Proxy-->>Parent: { allowed: false, reason }
            Parent-->>Child: tool_response { requestId, success: false, error }
        end

        Child->>Child: Feed result to LLM conversation
    end

    Child-->>Parent: complete { agentId, result }
    Parent->>Parent: Cleanup child process

Message Types

// tools/AgentTool/ipcProtocol.ts — NEW FILE

/** Messages from parent to child */
type ParentToChildMessage =
  | { type: 'init'; agentId: string; directive: string;
      capabilities: AgentCapabilities; stateSnapshot: SerializedAppState;
      forkDepth: number }
  | { type: 'tool_response'; requestId: string; success: boolean;
      result?: unknown; error?: string }
  | { type: 'abort'; reason: string }

/** Messages from child to parent */
type ChildToParentMessage =
  | { type: 'ready'; agentId: string }
  | { type: 'tool_request'; requestId: string; toolName: string;
      toolInput: Record<string, unknown>; agentId: string }
  | { type: 'state_request'; requestId: string; path: string }
  | { type: 'complete'; agentId: string; result: string }
  | { type: 'error'; agentId: string; message: string }
  | { type: 'log'; level: 'debug' | 'info' | 'warn'; message: string }

The protocol is deliberately simple: the child sends requests, the parent evaluates and responds. There is no mechanism for the child to execute code in the parent's context, access parent memory, or modify parent state. The IPC channel is the only interface.

13.4 Trust Tiers for Agent Sources

Not all agents need the same level of isolation. The system defines three trust tiers based on agent source:

Trust Tier Source Isolation Level Example
Tier 1: Trusted User's .claude/agents/ In-process User-written agents
Tier 2: Verified Marketplace (signed + reviewed) Process-isolated, broad capabilities Popular community agents
Tier 3: Community Marketplace (signed, not reviewed) Process-isolated, restricted capabilities New/unreviewed agents 
// tools/AgentTool/trustTier.ts — NEW FILE

type TrustTier = 'trusted' | 'verified' | 'community'

function determineAgentTrustTier(agentConfig: AgentConfig): TrustTier {
  // User-defined agents in .claude/agents/ are trusted
  if (agentConfig.source === 'local' &&
      agentConfig.path?.includes('.claude/agents/')) {
    return 'trusted'
  }

  // Marketplace agents with verified badge
  if (agentConfig.source === 'marketplace' &&
      agentConfig.verified === true) {
    return 'verified'
  }

  // Everything else is community tier
  return 'community'
}

function shouldIsolate(tier: TrustTier): boolean {
  return tier !== 'trusted'
}

function getDefaultCapabilities(tier: TrustTier): Partial<AgentCapabilities> {
  switch (tier) {
    case 'trusted':
      return {} // No restrictions (in-process)

    case 'verified':
      return {
        filesystem: 'readwrite',
        network: 'allowed',
        shell: 'restricted',
        maxMemoryMB: 1024,
        maxCpuSeconds: 600,
      }

    case 'community':
      return {
        filesystem: 'read',
        network: 'none',
        shell: 'none',
        maxMemoryMB: 512,
        maxCpuSeconds: 300,
      }
  }
}

13.7 Performance Considerations

Process isolation introduces overhead compared to in-process execution:

Operation In-Process Process-Isolated Overhead
Agent startup ~5ms ~200ms (fork + init) 40x
Tool call (Read) ~1ms ~10ms (IPC roundtrip) 10x
Tool call (Bash) ~50ms ~60ms (IPC + exec) 1.2x
Memory per agent ~50MB (shared heap) ~150MB (separate process) 3x
Maximum concurrent Limited by heap Limited by OS processes Comparable

The overhead is acceptable for plugin agents, which are expected to perform complex, multi-step tasks where the per-call IPC latency (10ms) is negligible compared to LLM inference time (1-5 seconds per turn). The startup cost (200ms) is a one-time cost per agent invocation.

For trusted agents (user-defined in .claude/agents/), in-process execution is preserved for zero overhead. Only plugin-sourced agents pay the isolation cost.

13.8 Migration Path

Phase 1: Deploy AgentRegistry and fork depth enforcement. This is a pure addition that enforces MAX_FORK_DEPTH = 3 and MAX_CONCURRENT_AGENTS = 10 without changing the execution model. It immediately stops recursive fork bombs.

Phase 2: Deploy ToolProxy with logging-only mode. The ToolProxy evaluates every tool call from subagents but only logs denials without blocking them. This collects data on which plugin agents would be affected by capability restrictions.

Phase 3: Enable ToolProxy enforcement for community-tier agents. Community agents (unsigned or unreviewed) have their tool calls enforced. Verified and trusted agents continue with logging-only.

Phase 4: Deploy process isolation for community-tier agents. Community agents now run in forked child processes with full IPC-based tool proxying. Verified agents remain in-process with ToolProxy enforcement.

Phase 5: Deploy process isolation for all plugin agents. Both verified and community agents run in child processes. Only user-defined trusted agents run in-process.

Chapter 14 will extend this isolation model with cryptographic fork depth tracking and resource budget enforcement per agent process tree.

13.9 Key Takeaways

  1. Process boundaries are the only reliable isolation mechanism. In-process "isolation" via name-based filtering is advisory --- it can be bypassed through shared memory, environment variables, and prompt injection. child_process.fork() creates a mechanical boundary enforced by the operating system's virtual memory system.

  2. Capabilities, not names, define access. Replacing string-based tool filtering (tools: ['Read']) with structured capability sets (filesystem: 'read', network: 'none') enables fine-grained access control that covers cross-cutting concerns like path restrictions and rate limiting.

  3. Fork depth must be tracked by the parent, not the child. Storing depth in the child's conversation messages allows message manipulation to bypass the check. The parent's AgentRegistry is authoritative and tamper-resistant.

  4. Trust tiers reduce overhead for trusted agents. Not all agents need process isolation. User-defined agents run in-process for performance. Only plugin-sourced agents (which could be malicious) pay the isolation cost.

  5. Environment stripping is as important as process isolation. A forked child process that inherits the parent's environment variables has access to all secrets. The explicit environment allowlist ensures that credentials never reach the child process.

  6. The ToolProxy is the security perimeter. Every tool call from an isolated agent must pass through the parent's ToolProxy. The proxy is the single point of enforcement for capability restrictions, path denials, rate limiting, and audit logging. Its correctness is the foundation of the isolation model.
