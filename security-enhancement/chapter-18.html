Chapter 18: Debug Log Sanitization

Chapters 16 and 17 hardened the bridge and network layers -- the channels through which Claude Code communicates with remote servers. This chapter shifts focus to what those channels inadvertently carry outward: debug log output. Every debugging statement that includes token material, session identifiers, or organizational metadata creates a data exfiltration surface that persists long after the session ends. Log files get collected by centralized logging infrastructure, shipped to SIEMs, stored in S3 buckets with overly broad access policies, and indexed by full-text search engines. A single token.slice(0, 15) in a debug message can turn an entire logging pipeline into a credential exposure vector.

The audit identified four distinct instances of token prefix logging (V-32, V-41, V-43, V-47), one instance of organizational UUID exposure in URL parameters (V-42), and a systemic absence of structured log redaction across the debug utility layer. This chapter implements comprehensive log sanitization -- not by trying to detect and remove sensitive data after the fact, but by establishing an allowlist architecture where only explicitly approved data fields can appear in log output.

18.1 The Anatomy of Debug Log Exposure

Why Token Prefixes Matter

A common misconception in security engineering is that partial token exposure is harmless. The reasoning goes: if the full token is 128 characters, showing the first 15 characters reveals only 12% of the entropy, leaving the remaining 88% as the security barrier. This reasoning is wrong for three reasons.

First, token prefixes reveal the token type. Claude Code's authentication tokens use the sk-ant-si- prefix, which consumes 10 of those 15 characters. The remaining 5 characters of actual secret material reduce the search space from the full token entropy to a much smaller universe. An attacker who knows 5 characters of a base62-encoded token has reduced the brute-force space from 62^n to 62^(n-5) -- a factor of approximately 916 million.

Second, token prefixes enable correlation attacks. If the same prefix appears in multiple log entries across different systems, an attacker can link sessions, identify users, and map access patterns without ever obtaining the full token. This is particularly damaging in enterprise environments where logs from multiple Claude Code instances aggregate into shared infrastructure.

Third, token prefixes in logs create compliance violations. PCI DSS Requirement 3.4 mandates rendering PANs unreadable anywhere they are stored. SOC 2 CC6.1 requires protection of confidential information in all forms. While these frameworks were written for payment card data and customer information, the principle applies universally: secret material in logs is secret material at rest, subject to the same protection requirements as the original credential.

18.2 CWE-532: Insertion of Sensitive Information into Log File

CWE-532 describes the insertion of sensitive information into log files that are accessible to unauthorized actors. The CWE entry specifically calls out authentication credentials, session tokens, and personally identifiable information as data categories that should never appear in logs.

The Vulnerable Code Path

The primary vulnerability exists in the token refresh scheduling logic within bridge/jwtUtils.ts:

// VULNERABLE: bridge/jwtUtils.ts — scheduleTokenRefresh
function scheduleTokenRefresh(label: string, sessionId: string, token: string): void {
  const expiry = decodeJwtExpiry(token)
  if (!expiry) {
    logForDebugging(
      `[${label}:token] Could not decode JWT expiry for sessionId=${sessionId}, token prefix=${token.slice(0, 15)}…, keeping existing timer`,
    )
    return
  }
  // ... schedule refresh based on expiry
}

And in the token refresh callback:

// VULNERABLE: bridge/jwtUtils.ts — refresh callback
logForDebugging(
  `[${label}:token] Refreshing token for sessionId=${sessionId}: new token prefix=${oauthToken.slice(0, 15)}…`,
)

Both statements use token.slice(0, 15) as a debugging identifier, intended to help engineers distinguish between different tokens during troubleshooting. The intent is understandable -- when debugging token refresh issues, knowing which token is being processed is valuable. But the implementation leaks the token type prefix and the beginning of the secret material.

The Secure Patch: SHA-256 Fingerprinting

The fix replaces token prefix logging with a cryptographic fingerprint that preserves debugging utility without exposing token material:

// SECURE: bridge/jwtUtils.ts — token fingerprint utility
import { createHash } from 'node:crypto'

/**
 * Generate a short, non-reversible fingerprint for token identification.
 * 12 hex chars = 48 bits of entropy, sufficient for log correlation
 * without exposing any token material.
 */
function tokenFingerprint(token: string): string {
  return createHash('sha256').update(token).digest('hex').slice(0, 12)
}

// SECURE: scheduleTokenRefresh
function scheduleTokenRefresh(label: string, sessionId: string, token: string): void {
  const expiry = decodeJwtExpiry(token)
  if (!expiry) {
    const fingerprint = tokenFingerprint(token)
    logForDebugging(
      `[${label}:token] Could not decode JWT expiry for sessionId=${sessionId}, ` +
      `tokenId=${fingerprint}, keeping existing timer`,
    )
    return
  }
  // ... schedule refresh based on expiry
}

This approach provides:

  1. Uniqueness: Different tokens produce different fingerprints with overwhelming probability (birthday bound at ~2^24 for 48-bit hashes).
  2. Non-reversibility: SHA-256 is a one-way function. The fingerprint cannot be used to recover any portion of the original token.
  3. Correlation: The same token always produces the same fingerprint, so engineers can still trace a token's lifecycle through log entries.
  4. Type-blindness: The fingerprint does not reveal whether the token is a JWT, API key, or opaque bearer token.

# Expected: no matches

# Expected: no matches

18.3 CWE-598: Use of GET Request Method With Sensitive Query Strings

CWE-598 addresses the transmission of sensitive information in URL query parameters. While primarily concerned with HTTP GET requests (where URLs appear in browser history, referrer headers, and server access logs), the principle applies equally to WebSocket connection URLs that flow through logging infrastructure.

The Vulnerable Code

// VULNERABLE: remote/SessionsWebSocket.ts
const baseUrl = getOauthConfig().BASE_API_URL.replace('https://', 'wss://')
const url = `${baseUrl}/v1/sessions/ws/${this.sessionId}/subscribe?organization_uuid=${this.orgUuid}`
logForDebugging(`[ws] Connecting to ${url}`)

The organization_uuid parameter in the WebSocket URL serves a legitimate purpose -- the server uses it to route the connection to the correct organization context. But logging the complete URL including this parameter exposes the UUID to any system that processes the log output.

The Secure Patch

// SECURE: remote/SessionsWebSocket.ts
const baseUrl = getOauthConfig().BASE_API_URL.replace('https://', 'wss://')
const url = `${baseUrl}/v1/sessions/ws/${this.sessionId}/subscribe?organization_uuid=${this.orgUuid}`

// Log the connection target without exposing organizational metadata
const redactedUrl = url.replace(
  /organization_uuid=[^&]+/,
  'organization_uuid=<redacted>'
)
logForDebugging(`[ws] Connecting to ${redactedUrl}`)

The actual url variable retains the real orgUuid for the WebSocket connection. Only the log output is redacted. This is a critical distinction: redaction must happen at the logging boundary, not at the data source.

18.4 Structured Log Redaction: The Systemic Fix

Patching individual logging statements is necessary but insufficient. The four findings identified in the audit are the instances that the review caught. In a 500K-line codebase, there are likely additional instances that were not flagged, and every future logForDebugging() call introduces the possibility of new data leaks. The systemic fix is a structured log redaction layer that operates at the logForDebugging() function itself.

The Allowlist Architecture

There are two approaches to log sanitization: denylist and allowlist.

Denylist approach: Define patterns that look like sensitive data (API keys, JWTs, UUIDs) and strip them from log output. This is the regex-based approach.

Allowlist approach: Define the fields that are safe to log (event type, timestamp, session phase, error category) and exclude everything else. This is the structured approach.

The denylist approach is fragile. It requires maintaining regex patterns for every possible token format, and a single missed pattern creates a data leak. The allowlist approach is robust: new data formats are excluded by default, and engineers must explicitly mark fields as safe for logging.

For Claude Code's debug utility, a hybrid approach makes sense: regex-based redaction as an immediate defense layer, with a path toward structured logging as the long-term architecture.

Implementing the Redaction Layer

// SECURE: utils/debug.ts — redaction patterns

/** 
 * Patterns matching known sensitive data formats.
 * Order matters: more specific patterns before general ones.
 * Each pattern is tested against the log message; matches are replaced.
 */
const REDACTION_PATTERNS: ReadonlyArray<{
  pattern: RegExp
  replacement: string
  label: string
}> = [
  // Anthropic API keys: sk-ant-xxx-...
  {
    pattern: /\bsk-ant-[a-z]{2,4}-[A-Za-z0-9_-]{10,}\b/g,
    replacement: '<redacted-api-key>',
    label: 'anthropic-api-key',
  },
  // Generic Bearer tokens
  {
    pattern: /Bearer\s+[A-Za-z0-9_-]{20,}/g,
    replacement: 'Bearer <redacted-token>',
    label: 'bearer-token',
  },
  // JWT format (three base64url segments separated by dots)
  {
    pattern: /\beyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\b/g,
    replacement: '<redacted-jwt>',
    label: 'jwt-token',
  },
  // Datadog client tokens (pub prefix)
  {
    pattern: /\bpub[a-f0-9]{32,}\b/g,
    replacement: '<redacted-dd-token>',
    label: 'datadog-client-token',
  },
  // Generic hex tokens (32+ chars)
  {
    pattern: /\b[a-f0-9]{32,}\b/g,
    replacement: '<redacted-hex-token>',
    label: 'hex-token',
  },
  // Organization UUIDs in URLs
  {
    pattern: /organization_uuid=[0-9a-f-]{36}/g,
    replacement: 'organization_uuid=<redacted>',
    label: 'org-uuid',
  },
] as const

/**
 * Redact sensitive data from a log message.
 * Returns the redacted message and a list of redaction labels applied.
 */
function redactSensitiveData(message: string): {
  redacted: string
  applied: string[]
} {
  let redacted = message
  const applied: string[] = []

  for (const { pattern, replacement, label } of REDACTION_PATTERNS) {
    // Reset regex lastIndex for global patterns
    pattern.lastIndex = 0
    if (pattern.test(redacted)) {
      pattern.lastIndex = 0
      redacted = redacted.replace(pattern, replacement)
      applied.push(label)
    }
  }

  return { redacted, applied }
}

Integrating Redaction into logForDebugging()

// SECURE: utils/debug.ts — enhanced logForDebugging

/**
 * Log a debug message with automatic sensitive data redaction.
 * 
 * Redaction is always on in production. The CLAUDE_CODE_DEBUG_REDACT=false
 * escape hatch is available ONLY for internal debugging by Anthropic engineers
 * and should never be set in user-facing environments.
 */
export function logForDebugging(
  message: string,
  options?: { level?: 'info' | 'warn' | 'error' }
): void {
  if (!isDebugEnabled()) return

  const skipRedaction = process.env.CLAUDE_CODE_DEBUG_REDACT === 'false'

  let output: string
  if (skipRedaction) {
    output = message
  } else {
    const { redacted, applied } = redactSensitiveData(message)
    output = redacted
    if (applied.length > 0) {
      // Append redaction metadata for audit trail
      output += ` [redacted: ${applied.join(', ')}]`
    }
  }

  writeDebugLog(output, options?.level ?? 'info')
}

Preventing ReDoS in Redaction Patterns

A critical concern with regex-based redaction is ReDoS (Regular Expression Denial of Service). If an attacker can craft a log message that triggers catastrophic backtracking in a redaction pattern, they can freeze the debug logging pipeline. This is particularly dangerous because the redaction layer sits in the critical path of every logForDebugging() call -- a ReDoS in the redaction layer would effectively disable all debug logging, potentially masking other attacks in progress.

The patterns above are designed to avoid this:

  1. No nested quantifiers: None of the patterns use (a+)+ or similar constructions that cause exponential backtracking.
  2. Bounded character classes: Each pattern uses specific character classes ([A-Za-z0-9_-], [a-f0-9]) rather than wildcards.
  3. Anchored or bounded matches: The \b word boundary anchors prevent unbounded scanning.

Verification that redaction patterns are ReDoS-safe:

// Test: redaction performance with adversarial input
import { performance } from 'node:perf_hooks'

const adversarialInput = 'a'.repeat(1000) + 'sk-ant-si-' + 'b'.repeat(1000)
const start = performance.now()
redactSensitiveData(adversarialInput)
const elapsed = performance.now() - start

assert(elapsed < 1, `Redaction took ${elapsed}ms, expected < 1ms`)

18.5 Tool Input Sanitization for Telemetry (V-47)

Finding V-47 (CWE-532, CVSS 2.4 INFO) addresses a different logging surface: tool input arguments that flow to telemetry when the OTEL_LOG_TOOL_DETAILS environment variable is set.

The Risk Context

While V-32 and V-41 affect debug logs that remain on disk, V-47 represents a more concerning data flow because tool inputs travel over the network to telemetry endpoints. The telemetry pipeline ships events to both Anthropic's first-party analytics and to Datadog (a third-party observability platform, discussed in Chapter 19). Tool inputs that contain file paths, URLs with authentication tokens, or Bash commands with embedded secrets become externally accessible once they reach the telemetry endpoint.

The severity is rated INFO because the feature requires explicit opt-in (OTEL_LOG_TOOL_DETAILS=1). However, enterprise deployments commonly enable detailed telemetry for operational visibility, making this a practical concern rather than a theoretical one. In a SOC 2 audit, telemetry data that includes file paths with usernames or command arguments with API keys would be flagged as a CC6.1 gap (confidential information protection).

The Vulnerable Code

// VULNERABLE: services/analytics/metadata.ts
export function extractToolInputForTelemetry(
  input: unknown,
): string | undefined {
  if (!isToolDetailsLoggingEnabled()) {
    return undefined
  }
  // Truncates to 512 chars for strings, 4KB total JSON
  // But no redaction of file paths, URLs, or command arguments
  return truncateAndSerialize(input)
}

While this feature is opt-in (requiring OTEL_LOG_TOOL_DETAILS=1), the truncation-without-redaction approach means that when enabled, file paths containing usernames, URLs with authentication parameters, and bash commands with embedded secrets all flow to telemetry endpoints.

The Secure Patch

// SECURE: services/analytics/metadata.ts
export function extractToolInputForTelemetry(
  input: unknown,
): string | undefined {
  if (!isToolDetailsLoggingEnabled()) {
    return undefined
  }

  const serialized = truncateAndSerialize(input)
  if (serialized === undefined) return undefined

  // Apply the same redaction patterns used in debug logging
  const { redacted } = redactSensitiveData(serialized)

  // Additionally, reduce file paths to relative-only
  // /Users/john.doe/projects/app/src/auth.ts -> ./src/auth.ts
  const pathRedacted = redacted.replace(
    /\/(?:Users|home)\/[^/]+\/[^"'\s]*/g,
    (match) => {
      const segments = match.split('/')
      // Keep last 3 path segments for debugging utility
      return './' + segments.slice(-3).join('/')
    }
  )

  return pathRedacted
}

This ensures that even when telemetry detail logging is explicitly enabled, no raw file paths with usernames or embedded credentials reach the telemetry endpoint.

18.6 The Allowlist Approach: Moving Beyond Regex

Regex-based redaction is a necessary first step, but the long-term architecture should move toward structured logging with explicit field declarations. This section presents the design for that migration.

Structured Debug Events

Instead of passing arbitrary strings to logForDebugging(), debug output should use structured event objects where each field is explicitly declared:

// FUTURE: Structured logging interface

interface DebugEvent {
  /** Event category for filtering */
  category: 'auth' | 'ws' | 'mcp' | 'plugin' | 'tool' | 'bridge'
  /** Machine-readable event type */
  event: string
  /** Human-readable context */
  message: string
  /** Structured data fields — each field must be on the allowlist */
  data?: Record<string, DebugFieldValue>
}

type DebugFieldValue = 
  | { type: 'public'; value: string | number | boolean }
  | { type: 'fingerprint'; value: string }  // Will be hashed before logging
  | { type: 'redacted' }                     // Logged as <redacted>

// Example usage:
logDebugEvent({
  category: 'auth',
  event: 'jwt-decode-failed',
  message: 'Could not decode JWT expiry, keeping existing timer',
  data: {
    sessionId: { type: 'public', value: sessionId },
    tokenId: { type: 'fingerprint', value: token },
    label: { type: 'public', value: label },
    rawToken: { type: 'redacted' },
  },
})

The Field Allowlist

Migration Path

The migration from unstructured to structured logging should happen incrementally. Attempting a big-bang migration would introduce regressions across the entire codebase, as every logForDebugging() call site would need to be updated simultaneously. The phased approach allows the team to validate the structured API on high-risk modules first, then expand incrementally.

The critical insight is that Phase 1 (regex redaction) provides immediate protection while the structured migration progresses. This means the codebase is protected from day one, and the structured migration improves the protection quality over time rather than being a prerequisite for safety.

Phase Action Timeline Risk
1 Add regex redaction to logForDebugging() Immediate (V-43 patch) Low -- additive change
2 Remove token.slice(0, 15) from all call sites Immediate (V-32, V-41 patches) Low -- direct replacement
3 Redact org UUID in WebSocket URL logs Immediate (V-42 patch) Low -- localized change
4 Add logDebugEvent() structured API alongside logForDebugging() Sprint 1 Medium -- new API design
5 Migrate high-risk modules (auth, bridge, ws) to structured API Sprint 2 Medium -- behavior changes possible
6 Deprecate logForDebugging() for new code Sprint 3 Low -- policy, not code
7 Migrate remaining modules Sprint 4-6 Low -- mechanical changes
8 Remove logForDebugging() Post-migration Medium -- breaking change

Structured Logging in Practice: Before and After

To illustrate the concrete improvement, consider a real debugging scenario. An engineer is investigating why a JWT token refresh is failing for a specific session:

// BEFORE: Unstructured (easy to write, dangerous)
logForDebugging(
  `[auth:token] Refreshing token for session=${sessionId}: ` +
  `old token prefix=${token.slice(0, 15)}, ` +
  `new token prefix=${newToken.slice(0, 15)}, ` +
  `org=${this.orgUuid}`
)
// Output: [auth:token] Refreshing token for session=sess_abc123: old token prefix=sk-ant-si-XXXXX, ...
// Problem: Token material + org UUID + session ID all in plaintext

// AFTER: Structured (slightly more verbose, fundamentally safe)
logDebugEvent({
  category: 'auth',
  event: 'token-refresh',
  message: 'Token refreshed successfully',
  data: {
    sessionId: { type: 'fingerprint', value: sessionId },
    oldTokenId: { type: 'fingerprint', value: token },
    newTokenId: { type: 'fingerprint', value: newToken },
    orgId: { type: 'fingerprint', value: this.orgUuid },
    refreshReason: { type: 'public', value: 'expiry' },
  },
})
// Output: {"category":"auth","event":"token-refresh","sessionId":"a3f2c8","oldTokenId":"7b91e4",...}
// Benefit: All identifiers are non-reversible hashes, still useful for correlation

18.7 Diagnostic Log Path Security (V-48)

Finding V-48 (CWE-73, CVSS 2.0 INFO) addresses a related concern: the diagnostic log file path is controlled by an environment variable without validation.

// VULNERABLE: utils/diagLogs.ts
function getDiagnosticLogFile(): string | undefined {
  return process.env.CLAUDE_CODE_DIAG_LOG
}

An attacker who controls the environment can set CLAUDE_CODE_DIAG_LOG to a path like /etc/cron.d/backdoor or //attacker.com/share/collect.log, causing debug output -- which may contain sensitive data even after redaction -- to be written to an attacker-controlled location.

The Secure Patch

// SECURE: utils/diagLogs.ts
import { resolve, dirname } from 'node:path'
import { existsSync, statSync } from 'node:fs'

function getDiagnosticLogFile(): string | undefined {
  const logPath = process.env.CLAUDE_CODE_DIAG_LOG
  if (!logPath) return undefined

  const resolved = resolve(logPath)

  // Reject UNC paths and non-local paths
  if (resolved.startsWith('//') || resolved.startsWith('\\\\')) {
    logForDebugging(
      '[diag] Rejected CLAUDE_CODE_DIAG_LOG: UNC/network paths not allowed',
      { level: 'warn' }
    )
    return undefined
  }

  // Verify parent directory exists and is writable
  const parentDir = dirname(resolved)
  if (!existsSync(parentDir)) {
    logForDebugging(
      '[diag] Rejected CLAUDE_CODE_DIAG_LOG: parent directory does not exist',
      { level: 'warn' }
    )
    return undefined
  }

  // Reject symlinks in the path
  try {
    const stat = statSync(parentDir, { throwIfNoEntry: true })
    if (!stat.isDirectory()) {
      return undefined
    }
  } catch {
    return undefined
  }

  return resolved
}

18.10 Dependency Chain Impact

The debug log sanitization patches affect the Data Exfiltration Chain (Finding IDs: 9, 24, 26, 33, 38, 43, 47, 49). By eliminating sensitive data from log output, these patches reduce the blast radius of any future compromise of log collection infrastructure. Even if an attacker gains access to log aggregation systems, the redacted output contains no actionable credential material.

The patches in this chapter should be applied after the bridge and network hardening from Chapters 16-17, as those chapters may modify logging statements that need to comply with the new redaction framework. Apply the systemic fix (V-43, the logForDebugging() redaction layer) first, as it provides defense-in-depth for any individual logging statement that might be missed.

As discussed in Chapter 3, Phase 6 (Data Protection & Privacy) encompasses these debug log fixes alongside the telemetry and memory protection work covered in Chapters 19 and 20. The redaction patterns established here will be reused in Chapter 19's telemetry sanitization implementation.

Summary

This chapter addressed five findings (V-32, V-41, V-42, V-43, V-47) plus the related V-48 diagnostic path vulnerability. The key patches are:

  1. Token prefix removal (V-32, V-41): Replace token.slice(0, 15) with SHA-256 fingerprints in bridge/jwtUtils.ts
  2. URL parameter redaction (V-42): Redact organization_uuid in WebSocket URL logging in remote/SessionsWebSocket.ts
  3. Systemic redaction layer (V-43): Add regex-based sensitive data redaction to logForDebugging() in utils/debug.ts
  4. Telemetry input sanitization (V-47): Add redaction and path normalization to extractToolInputForTelemetry() in services/analytics/metadata.ts
  5. Diagnostic path validation (V-48): Validate CLAUDE_CODE_DIAG_LOG environment variable against path traversal and network paths

The allowlist architecture presented in Section 18.6 provides the long-term path toward log sanitization that does not depend on maintaining a complete inventory of sensitive data patterns -- a fundamentally more robust approach than regex-based denylist matching.
