Chapter 19: Telemetry & Analytics Security

Chapter 18 addressed the debug logging surface -- data that leaks through diagnostic output intended for developers. This chapter examines a more deliberate data flow: the telemetry and analytics pipeline that transmits usage data from every Claude Code installation to Anthropic's infrastructure and to Datadog, a third-party observability platform. The distinction matters. Debug logs are accidental exposure. Telemetry is intentional collection. Both create security and privacy risks, but the remediation strategies differ fundamentally.

The audit identified three distinct vulnerabilities in the telemetry pipeline: a hardcoded Datadog client token that prevents rotation (V-24, CWE-798), an overly broad data collection scope that creates detailed usage profiles (V-26, CWE-200), and the transmission of telemetry data to a third-party service without explicit user consent (V-33, CWE-359). A fourth finding (V-49, CWE-359) revealed that the existing opt-out mechanism fails to gate all network requests, allowing GrowthBook feature flag polling to continue even when users believe they have disabled telemetry.

Together, these findings describe a telemetry system that was designed for operational visibility but lacks the security and privacy controls expected of a tool that handles authentication tokens, processes source code, and operates in enterprise environments subject to regulatory compliance requirements.

19.2 CWE-798: Hardcoded Datadog Client Token (V-24)

The Vulnerability

CWE-798 (Use of Hard-coded Credentials) describes the practice of embedding authentication credentials directly in source code. Finding V-24 (CVSS 5.3, MEDIUM) identified a Datadog client token hardcoded in services/analytics/datadog.ts:

// VULNERABLE: services/analytics/datadog.ts:14
const DATADOG_LOGS_ENDPOINT =
  'https://http-intake.logs.us5.datadoghq.com/api/v2/logs'
const DATADOG_CLIENT_TOKEN =
  'pubbbf48e6d78dae54bceaa4acf463299bf'

The pub* prefix indicates this is a client-side token, which Datadog classifies as write-only -- it can send data to Datadog but cannot read existing data. This limits the direct exploit impact: an attacker who extracts this token can inject fake telemetry into Anthropic's Datadog project, but cannot access collected data.

However, the security implications go beyond the immediate access control:

  1. Token rotation impossible: Rotating this token requires a code change, build, and release. During the time between a compromise and the deployment of a new build, the old token continues accepting injected data.

  2. Telemetry pollution: An attacker can inject arbitrary events into Anthropic's analytics pipeline, corrupting usage metrics, creating false error reports, and degrading the signal-to-noise ratio of operational dashboards.

  3. Infrastructure reconnaissance: The token reveals the Datadog datacenter (us5), the ingestion endpoint, and the API version. This information helps map Anthropic's observability infrastructure.

  4. Supply chain indicator: The token's presence in the source code means it is present in every fork, every CI/CD artifact, and every developer's local checkout. Any compromise of these systems exposes the token.

The Secure Patch

The fix externalizes the token while maintaining backward compatibility:

// SECURE: services/analytics/datadog.ts

/**
 * Datadog configuration.
 * 
 * Token and endpoint are overridable via environment variables to support:
 * - Token rotation without code changes
 * - Enterprise deployments redirecting telemetry to their own Datadog org
 * - Testing with separate Datadog projects
 * 
 * The fallback values preserve existing behavior for users who don't
 * set environment variables.
 */
const DATADOG_LOGS_ENDPOINT: string =
  process.env.DATADOG_LOGS_ENDPOINT ??
  'https://http-intake.logs.us5.datadoghq.com/api/v2/logs'

const DATADOG_CLIENT_TOKEN: string =
  process.env.DATADOG_CLIENT_TOKEN ??
  'pubbbf48e6d78dae54bceaa4acf463299bf'

/**
 * Validate the Datadog token format.
 * Client tokens must start with 'pub' prefix.
 */
function validateDatadogToken(token: string): boolean {
  return /^pub[a-f0-9]{32}$/.test(token)
}

// At initialization:
if (!validateDatadogToken(DATADOG_CLIENT_TOKEN)) {
  logForDebugging(
    '[analytics] Invalid Datadog client token format — telemetry disabled',
    { level: 'warn' }
  )
}

19.3 CWE-200: Broad Telemetry Data Collection (V-26)

The Vulnerability

CWE-200 (Exposure of Sensitive Information to an Unauthorized Actor) describes the disclosure of information to entities not authorized to access it. Finding V-26 (CVSS 5.3, MEDIUM) identified that Claude Code's telemetry collects a broad set of data that, in aggregate, creates detailed usage profiles:

services/analytics/datadog.ts:13-14 — hardcoded endpoint and client token
services/analytics/datadog.ts:19-64 — 64 event types enumerated
services/analytics/firstPartyEventLogger.ts — batches up to 200 events with 10s flush
services/analytics/metadata.ts:60-234 — tool names, MCP server IDs in telemetry

The data flow includes:

Data Field Source Privacy Concern
session_id Generated per session Correlates all actions within a session
model API request Reveals which models the user has access to
subscription_tier Auth context Reveals payment status
user_type Configuration Classifies user (individual, team, enterprise)
platform process.platform OS identification
tool_name Tool execution Reveals specific actions taken
mcp_server_id MCP connections Reveals which MCP servers are installed
error_hash Error handling May correlate with specific code patterns

Individually, none of these fields constitute PII. In aggregate, they create a usage fingerprint that can identify individual users, track their work patterns, and reveal the technologies and workflows they use.

The Secure Patch: Data Minimization

The remediation follows the data minimization principle: collect only what is necessary for the stated purpose (operational monitoring), and reduce the identifiability of what is collected.

// SECURE: services/analytics/metadata.ts — session anonymization

/**
 * Replace session_id with a bucketed hash that preserves
 * aggregate analysis capability without enabling individual tracking.
 * 
 * Hash mod 1000 creates 1000 buckets. This preserves:
 * - Session count estimation
 * - Error rate calculation
 * - Feature usage percentages
 * While preventing:
 * - Individual session tracking
 * - Cross-event session correlation
 * - User identification through session patterns
 */
function anonymizeSessionId(sessionId: string): string {
  const hash = createHash('sha256').update(sessionId).digest()
  const bucket = hash.readUInt32BE(0) % 1000
  return `bucket_${bucket.toString().padStart(4, '0')}`
}

// SECURE: services/analytics/datadog.ts — reduced event metadata

/**
 * Essential operational events only.
 * Removed from DATADOG_ALLOWED_EVENTS:
 * - USER_TYPE (reveals organizational classification)
 * - Individual tool usage events (aggregated instead)
 * - MCP server identifiers (reveals installed extensions)
 */
const DATADOG_ALLOWED_EVENTS_REDUCED: ReadonlySet<string> = new Set([
  // Operational health (keep)
  'session.start',
  'session.end',
  'error.api',
  'error.fatal',
  // Performance monitoring (keep)
  'perf.latency',
  'perf.timeout',
  // Feature adoption (keep, aggregated)
  'feature.used',
  // Authentication health (keep, no user details)
  'auth.failure',
  'auth.refresh_failure',
])

// Remove USER_TYPE from the env field in Datadog events
function buildDatadogEnv(): string {
  // Previously: `${platform}-${subscription}-${userType}`
  // Now: just platform for operational monitoring
  return process.platform
}

// SECURE: Telemetry event TTL metadata
interface TelemetryEvent {
  type: string
  timestamp: number
  data: Record<string, unknown>
  /** Maximum retention period in days. Downstream systems 
   *  must honor this TTL for GDPR Article 5(1)(e) compliance. */
  retentionDays: number

function createTelemetryEvent(
  type: string,
  data: Record<string, unknown>
): TelemetryEvent {
  const retentionMap: Record<string, number> = {
    'session.start': 90,
    'session.end': 90,
    'error.api': 30,
    'error.fatal': 30,
    'perf.latency': 14,
    'perf.timeout': 14,

    type,
    timestamp: Date.now(),
    data,
    retentionDays: retentionMap[type] ?? 30,
  }
}

## 19.4 CWE-359: Third-Party Data Sharing Without Consent (V-33, V-49)

### The Vulnerability

CWE-359 (Exposure of Private Personal Information to an Unauthorized Actor) addresses the sharing of user data with third parties without appropriate consent. Two findings address this concern:

**V-33 (CVSS 4.3, MEDIUM)**: Telemetry data is sent to Datadog without an explicit consent UI. Users can opt out by setting environment variables or configuration flags, but there is no first-run consent prompt.

**V-49 (CVSS 1.8, INFO)**: The analytics opt-out mechanism does not gate all network requests. Specifically, GrowthBook feature flag polling continues even when the user has disabled telemetry.

}

The Secure Patch: Comprehensive Telemetry Gate

// SECURE: services/analytics/config.ts

/**
 * Master switch for ALL non-essential network traffic.
 * When true, NO analytics, telemetry, or feature flag requests are made.
 * 
 * This gates:
 * - Datadog event transmission
 * - First-party analytics batching
 * - GrowthBook feature flag polling
 * - Any future telemetry integrations
 */
export function isAllTelemetryNetworkDisabled(): boolean {
  // Explicit env var (highest priority)
  if (process.env.CLAUDE_CODE_DISABLE_ALL_TELEMETRY === '1') {
    return true
  }

  // Privacy level configuration
  if (getPrivacyLevel() === 'no-telemetry') {
    return true
  }

  // CLI configuration
  if (getConfig('telemetry') === 'off') {
    return true
  }

  return false
}

// isAnalyticsDisabled() continues to exist for backward compatibility
// but delegates to the master switch
export function isAnalyticsDisabled(): boolean {
  return isAllTelemetryNetworkDisabled()
}

// SECURE: GrowthBook initialization with telemetry gate
async function initGrowthBook(): Promise<void> {
  // Check the master telemetry switch BEFORE any network request
  if (isAllTelemetryNetworkDisabled()) {
    logForDebugging('[growthbook] Telemetry disabled — using default feature flags')
    return
  }

  await growthbook.loadFeatures()
}

// SECURE: Datadog initialization with telemetry gate
function initDatadog(): void {
  if (isAllTelemetryNetworkDisabled()) {
    logForDebugging('[datadog] Telemetry disabled — Datadog not initialized')
    return
  }

  // ... existing initialization
}

GrowthBook Remote Configuration Hardening (V-38)

Finding V-38 (CWE-829, CVSS 3.5, LOW) revealed that GrowthBook remote configuration controls the analytics pipeline batch settings, including the endpoint URL. A compromised GrowthBook configuration could redirect analytics events to an attacker-controlled endpoint.

// SECURE: Validate GrowthBook batch configuration
function validateBatchConfig(config: BatchConfig): BatchConfig {
  const ANTHROPIC_DOMAINS = new Set([
    'api.anthropic.com',
    'statsig.anthropic.com',
    'events.anthropic.com',
  ])

  // Validate baseUrl against allowlist
  if (config.baseUrl) {
    try {
      const url = new URL(config.baseUrl)
      if (!ANTHROPIC_DOMAINS.has(url.hostname)) {
        logForDebugging(
          `[analytics] Rejected remote baseUrl: ${url.hostname} not in allowlist`,
          { level: 'warn' }
        )
        delete config.baseUrl
      }
    } catch {
      delete config.baseUrl
    }
  }

  // Never allow skipAuth from remote config
  if (config.skipAuth) {
    logForDebugging(
      '[analytics] Rejected remote skipAuth=true — auth is always required',
      { level: 'warn' }
    )
    config.skipAuth = false
  }

  // Bound batch size to prevent DoS
  if (config.maxExportBatchSize !== undefined) {
    config.maxExportBatchSize = Math.min(
      Math.max(config.maxExportBatchSize, 1),
      1000
    )
  }

  // Bound queue size
  if (config.maxQueueSize !== undefined) {
    config.maxQueueSize = Math.min(
      Math.max(config.maxQueueSize, 100),
      10000
    )
  }

  return config
}

19.5 Enterprise Telemetry Configuration

Enterprise deployments have unique telemetry requirements. Some organizations mandate that all telemetry flows through their own infrastructure. Others require complete telemetry suppression for compliance with data sovereignty regulations.

Enterprise Telemetry Modes

Enterprise deployments have unique telemetry requirements. Some organizations mandate that all telemetry flows through their own infrastructure. Others require complete telemetry suppression for compliance with data sovereignty regulations. A particularly common requirement in healthcare and government sectors is "no data leaves our network boundary" -- which the off and internal-only modes address.

Mode Datadog First-Party GrowthBook Use Case
default Enabled Enabled Enabled Individual developers
first-party-only Disabled Enabled Enabled Orgs that prohibit third-party analytics
internal-only Redirected Redirected Disabled Orgs with own observability stack
off Disabled Disabled Disabled Maximum privacy / air-gapped

The internal-only mode deserves special attention. In this mode, the Datadog and first-party analytics endpoints are replaced with customer-specified URLs, allowing telemetry data to flow to the organization's own Splunk, Elasticsearch, or Datadog instance. This satisfies data sovereignty requirements while preserving operational visibility.

// SECURE: Enterprise telemetry configuration
type TelemetryMode = 'default' | 'first-party-only' | 'internal-only' | 'off'

function getTelemetryMode(): TelemetryMode {
  const mode = process.env.CLAUDE_TELEMETRY_MODE ?? getConfig('telemetry_mode')
  if (mode && ['default', 'first-party-only', 'internal-only', 'off'].includes(mode)) {
    return mode as TelemetryMode
  }
  return 'default'
}

function shouldSendToDatadog(): boolean {
  const mode = getTelemetryMode()
  return mode === 'default'
}

function shouldSendFirstParty(): boolean {
  const mode = getTelemetryMode()
  return mode === 'default' || mode === 'first-party-only'
}

function shouldPollGrowthBook(): boolean {
  const mode = getTelemetryMode()
  return mode !== 'off' && mode !== 'internal-only'
}

Internal Redirect Configuration

For the internal-only mode, organizations specify their own telemetry endpoints:

// SECURE: Internal telemetry endpoint configuration
interface InternalTelemetryConfig {
  /** Organization's telemetry ingestion endpoint */
  endpoint: string
  /** Authentication header for the internal endpoint */
  authHeader?: string
  /** TLS certificate verification (should remain true in production) */
  tlsVerify: boolean
}

function getInternalTelemetryConfig(): InternalTelemetryConfig | null {
  const endpoint = process.env.CLAUDE_INTERNAL_TELEMETRY_ENDPOINT
  if (!endpoint) return null

  // Validate the endpoint URL
  try {
    const url = new URL(endpoint)
    if (url.protocol !== 'https:') {
      logForDebugging(
        '[analytics] Internal telemetry endpoint must use HTTPS',
        { level: 'warn' }
      )
      return null
    }
    return {
      endpoint,
      authHeader: process.env.CLAUDE_INTERNAL_TELEMETRY_AUTH,
      tlsVerify: process.env.CLAUDE_INTERNAL_TELEMETRY_TLS_VERIFY !== 'false',
    }
  } catch {
    logForDebugging(
      '[analytics] Invalid internal telemetry endpoint URL',
      { level: 'warn' }
    )
    return null
  }
}

19.9 Dependency Chain Impact

The telemetry patches affect the Data Exfiltration Chain (Finding IDs: 9, 24, 26, 33, 38, 43, 47, 49). By reducing the data that flows through the telemetry pipeline and providing a complete opt-out mechanism, these patches reduce the blast radius of any compromise of the analytics infrastructure.

The GrowthBook remote configuration hardening (V-38) is particularly important because it addresses a cross-chain vulnerability: if an attacker compromises GrowthBook, they could previously redirect analytics events to an attacker-controlled endpoint, effectively turning the telemetry pipeline into a data exfiltration channel. The domain allowlist prevents this.

These patches should be applied after the debug log sanitization from Chapter 18, as the telemetry layer reuses the redaction patterns established there. As discussed in Chapter 3, Phase 6 (Data Protection & Privacy) encompasses both the debug logging and telemetry fixes as a coordinated remediation effort.

Summary

This chapter addressed four telemetry findings (V-24, V-26, V-33, V-49) plus the related GrowthBook configuration vulnerability (V-38). The key patches are:

  1. Token externalization (V-24): Move Datadog client token to environment variable with fallback, enabling rotation without code changes
  2. Data minimization (V-26): Reduce allowed events from 64 to essential operational metrics, bucket session IDs, remove USER_TYPE and MCP server identifiers
  3. Comprehensive opt-out (V-33, V-49): Master telemetry gate that blocks ALL non-essential network traffic including GrowthBook
  4. First-run disclosure: Telemetry notice during initialization with claude --privacy for full details
  5. Remote config hardening (V-38): Domain allowlist for batch endpoints, skipAuth always false, bounded batch sizes

The enterprise telemetry modes provide organizations with granular control over where their usage data flows, supporting compliance with data sovereignty requirements and organizational security policies.
