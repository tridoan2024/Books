Chapter 16: Remote Permission Controls

Part V has so far addressed isolation within the local machine: process-level agent separation (Chapter 13), fork depth and resource governance (Chapter 14), and MCP server sandboxing (Chapter 15). This chapter crosses the network boundary. When Claude Code operates in remote mode -- connecting to a server over HTTP/WebSocket to execute tools on a remote machine -- the permission model faces a fundamentally different threat: the permission bypass flag can be transmitted across the network.

Finding 12 from the security audit -- CWE-862: Missing Authorization (CVSS 6.5) -- identifies the core vulnerability: createDirectConnectSession() accepts a dangerouslySkipPermissions parameter and sends it to the remote server as dangerously_skip_permissions: true in the POST body. The function is at server/createDirectConnectSession.ts:54. A compromised or malicious server URL could be used to create sessions with no permission checks on the remote side.

This chapter implements the controls that prevent permission bypass flags from escaping the local trust boundary, enforces server-side authorization validation, and builds the warning system that ensures users understand the risk of remote permission escalation.

16.1 The Remote Permission Problem

How Remote Sessions Work

Claude Code supports a remote execution mode where the CLI connects to a server that hosts the agent runtime. This enables use cases like:

  • Cloud development environments: The agent runs on a remote server with access to cloud resources
  • Team collaboration: Multiple users connect to a shared agent session
  • CI/CD integration: Build pipelines invoke the agent on build servers
  • Container execution: The agent runs inside a Docker container or Kubernetes pod

The connection flow:

sequenceDiagram
    participant Client as CLI (local)
    participant Server as Remote Server
    participant Agent as Agent Runtime

    Client->>Server: POST /sessions<br/>{cwd, dangerously_skip_permissions: true}
    Server->>Agent: Create session with no permission checks
    Agent->>Agent: All tool calls auto-approved
    Agent->>Server: Tool results
    Server->>Client: Session output

    Note over Agent: Every Bash, Write, Edit<br/>executes WITHOUT user approval

The Vulnerable Code

The audit identified the exact code path:

// server/createDirectConnectSession.ts:54
const response = await fetch(`${serverUrl}/sessions`, {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': `Bearer ${token}`,
  },
  body: jsonStringify({
    cwd,
    ...(dangerouslySkipPermissions && {
      dangerously_skip_permissions: true,
    }),
  }),
})

When dangerouslySkipPermissions is true, the request body includes dangerously_skip_permissions: true. The remote server receives this flag and creates a session where all tool calls bypass the permission system. The flag name -- prefixed with "dangerously" -- signals risk, but it provides no technical enforcement.

Why This Is a Security Boundary Violation

The permission system in Claude Code is the primary defense against tool abuse. It gates every destructive operation: file writes, bash execution, MCP tool calls. When dangerouslySkipPermissions is active, none of these gates exist. The assumption is that the user explicitly chose to bypass permissions and accepts the risk.

Locally, this assumption holds: the user controls the CLI, the flag is passed via command-line argument, and the permissions apply to the user's own machine. Remotely, the assumption breaks:

Concern Local Context Remote Context
Who set the flag? The user, via CLI argument Could be the user, or could be an automation script, a deployment template, or an environment variable
What does it affect? The user's own filesystem A remote server that may host shared resources, production data, or other users' environments
Can it be intercepted? No -- stays in process memory Yes -- transmitted as JSON over HTTPS to a URL that may be misconfigured
Who verifies it? The local permission system The remote server, which may have a different (or absent) authorization model

The fundamental problem: a security-critical flag designed for local trust contexts is being transmitted across a network boundary without additional authorization checks.

Attack Scenarios

Scenario 1: Malicious Server URL

An attacker crafts a server URL that mimics a legitimate Claude Code server. The victim's CI pipeline is configured with CLAUDE_SERVER_URL=https://attacker.example.com and dangerouslySkipPermissions=true. When the pipeline runs, it sends a permissionless session request to the attacker's server. The attacker now has an agent session on the victim's build machine with no permission restrictions.

Scenario 2: URL Injection via Environment Variable

# Legitimate CI configuration
export CLAUDE_SERVER_URL="https://claude-server.internal:8080"
export CLAUDE_SKIP_PERMISSIONS="true"

# Attacker modifies .env or CI variables
export CLAUDE_SERVER_URL="https://attacker.example.com"
# The existing SKIP_PERMISSIONS flag now goes to the attacker

Scenario 3: Shared Server Permission Escalation

In a team environment, one user creates a remote session with dangerously_skip_permissions: true for debugging. Another user connects to the same server and discovers that all sessions are running without permission checks, because the server applied the flag globally rather than per-session.

16.2 Localhost-Only Restriction

The first and most important defense: dangerouslySkipPermissions should only be accepted by servers running on localhost.

Rationale

The original purpose of dangerouslySkipPermissions is local development convenience: the user wants the agent to execute without interactive prompts. This use case does not require network transmission. If the server is on the same machine (localhost), the flag can be communicated through local IPC mechanisms that do not cross a network boundary.

Implementation

import { URL } from 'node:url'
import { isLoopbackAddress } from './networkUtils'

interface CreateSessionOptions {
  serverUrl: string
  cwd: string
  dangerouslySkipPermissions: boolean
  token: string
}

async function createDirectConnectSession(
  options: CreateSessionOptions
): Promise<SessionResponse> {
  const { serverUrl, cwd, dangerouslySkipPermissions, token } = options

  // DEFENSE 1: Localhost-only restriction for permission bypass
  if (dangerouslySkipPermissions) {
    const url = new URL(serverUrl)
    const isLocalhost = await isLoopbackAddress(url.hostname)

    if (!isLocalhost) {
      throw new SecurityError(
        'dangerouslySkipPermissions cannot be used with remote servers. ' +
        'This flag is restricted to localhost connections. ' +
        `Server URL "${serverUrl}" resolves to a non-loopback address.`
      )
    }
  }

  // DEFENSE 2: Never include the raw flag in the request body
  const body: SessionRequest = {
    cwd,
    permissions_mode: dangerouslySkipPermissions
      ? 'skip_local'   // Server knows it was requested locally
      : 'standard',    // Normal permission mode
  }

  const response = await fetch(`${serverUrl}/sessions`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${token}`,
    },
    body: JSON.stringify(body),
  })

  return response.json()
}

Loopback Address Verification

The loopback check must be resistant to DNS tricks:

import { resolve as dnsResolve } from 'node:dns/promises'
import { isIP, isIPv4, isIPv6 } from 'node:net'

async function isLoopbackAddress(hostname: string): Promise<boolean> {
  // Direct IP check
  if (isIP(hostname)) {
    return isLoopbackIP(hostname)
  }

  // Hostname resolution -- check ALL resolved IPs
  try {
    const addresses = await dnsResolve(hostname)
    // ALL resolved addresses must be loopback
    return addresses.length > 0 &&
      addresses.every(addr => isLoopbackIP(addr))
  } catch {
    return false  // DNS failure = not localhost
  }
}

function isLoopbackIP(ip: string): boolean {
  if (isIPv4(ip)) {
    return ip.startsWith('127.')  // 127.0.0.0/8
  }
  if (isIPv6(ip)) {
    return ip === '::1' || ip === '0:0:0:0:0:0:0:1'
  }
  return false
}

The critical detail: ALL resolved addresses must be loopback. A hostname that resolves to both 127.0.0.1 and 10.0.0.5 is not treated as localhost. This prevents DNS rebinding attacks where evil.example.com initially resolves to 127.0.0.1 (passing the check) and later resolves to an attacker's IP.

16.3 Server-Side Authorization Validation

Even when the permission bypass flag is restricted to localhost, the server must independently validate that the requesting client is authorized to create permissionless sessions.

The Server-Side Check

// Server: POST /sessions handler
async function handleCreateSession(
  req: Request,
  authContext: AuthContext
): Promise<Response> {
  const body = await req.json() as SessionRequest

  // Server-side permission bypass authorization
  if (body.permissions_mode === 'skip_local') {
    // Check 1: Request must come from loopback
    const clientIp = getClientIp(req)
    if (!isLoopbackIP(clientIp)) {
      return new Response(
        JSON.stringify({
          error: 'Permission bypass only allowed from localhost',
          code: 'PERMISSION_BYPASS_REMOTE',
        }),
        { status: 403 }
      )
    }

    // Check 2: User must have admin/owner role
    if (!authContext.roles.includes('admin') &&
        !authContext.roles.includes('owner')) {
      return new Response(
        JSON.stringify({
          error: 'Permission bypass requires admin or owner role',
          code: 'PERMISSION_BYPASS_UNAUTHORIZED',
        }),
        { status: 403 }
      )
    }

    // Check 3: Session must be flagged and time-limited
    const session = createSession({
      cwd: body.cwd,
      permissionMode: 'skip',
      skipExpiresAt: Date.now() + 3600_000,  // 1 hour max
      skipRequestedBy: authContext.userId,
      auditLog: true,  // Force audit logging
    })

    // Log the permission bypass for compliance
    logAuditEvent({
      event: 'permission_bypass_session_created',
      userId: authContext.userId,
      sessionId: session.id,
      expiresAt: session.skipExpiresAt,
      sourceIp: clientIp,
    })

    return new Response(JSON.stringify(session), { status: 201 })
  }

  // Standard session creation
  const session = createSession({
    cwd: body.cwd,
    permissionMode: 'standard',
  })

  return new Response(JSON.stringify(session), { status: 201 })
}

16.4 Warning Prompts with Risk Context

When a user attempts to use dangerouslySkipPermissions, the CLI should display a warning that provides specific risk context. The current behavior -- silently sending the flag -- does not inform the user of the consequences.

Non-Interactive Confirmation

In CI/CD environments where there is no TTY, the confirmation relies on an environment variable with an explicit acknowledgment value:

# CI pipeline configuration

The value yes_i_understand is intentionally verbose -- it cannot be set accidentally. A boolean flag like CONFIRM=true could be set by any number of automation tools without the operator understanding its significance.

16.5 Removing the Raw Flag from Network Transmission

The current implementation sends dangerously_skip_permissions: true as a raw boolean in the JSON body. This is problematic because:

  1. Replay attacks: If a request is intercepted (even over HTTPS, via log files or proxy inspection), the flag can be replayed against any server.
  2. Flag confusion: The server receives a boolean with no context about who authorized it, when it was authorized, or for how long it should be valid.
  3. Audit gap: There is no traceable record of the authorization decision.

Replacing the Boolean with a Signed Token

Instead of transmitting a raw boolean, the client generates a time-limited, signed authorization token:

interface PermissionBypassToken {
  action: 'skip_permissions'
  requestedBy: string     // User ID or machine identity
  requestedAt: number     // ISO timestamp
  expiresAt: number       // Maximum lifetime: 1 hour
  serverUrl: string       // Bound to specific server
  nonce: string           // Replay prevention
  signature: string       // HMAC-SHA256 of above fields
}

function createPermissionBypassToken(
  userId: string,
  serverUrl: string,
  lifetimeMs: number = 3600_000
): PermissionBypassToken {
  const requestedAt = Date.now()
  const expiresAt = requestedAt + lifetimeMs
  const nonce = randomBytes(16).toString('hex')

  const payload = JSON.stringify({
    action: 'skip_permissions',
    requestedBy: userId,
    requestedAt,
    expiresAt,
    serverUrl,
    nonce,
  })

  // Sign with the user's local session key
  const signature = createHmac('sha256', getSessionKey())
    .update(payload)
    .digest('hex')

  return {
    action: 'skip_permissions',
    requestedBy: userId,
    requestedAt,
    expiresAt,
    serverUrl,
    nonce,
    signature,
  }
}

Using the Token in Session Creation

async function createDirectConnectSession(
  options: CreateSessionOptions
): Promise<SessionResponse> {
  const { serverUrl, cwd, dangerouslySkipPermissions, token } = options

  const body: Record<string, unknown> = { cwd }

  if (dangerouslySkipPermissions) {
    // Validate localhost restriction
    await validateLocalhostOnly(serverUrl)

    // Generate time-limited, server-bound token
    const bypassToken = createPermissionBypassToken(
      getUserId(),
      serverUrl,
      3600_000  // 1 hour maximum
    )

    body.permission_bypass_token = bypassToken
  }

  const response = await fetch(`${serverUrl}/sessions`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${token}`,
    },
    body: JSON.stringify(body),
  })

  return response.json()
}

Server-Side Token Validation

function validateBypassToken(
  token: PermissionBypassToken,
  expectedServerUrl: string
): { valid: boolean; reason?: string } {
  // Check expiry
  if (Date.now() > token.expiresAt) {
    return { valid: false, reason: 'Token expired' }
  }

  // Check server binding
  if (token.serverUrl !== expectedServerUrl) {
    return {
      valid: false,
      reason: `Token bound to ${token.serverUrl}, not ${expectedServerUrl}`,
    }
  }

  // Check nonce (prevent replay)
  if (isNonceUsed(token.nonce)) {
    return { valid: false, reason: 'Nonce already used (replay detected)' }
  }
  markNonceUsed(token.nonce, token.expiresAt)

  // Verify signature (requires shared secret or public key)
  if (!verifyTokenSignature(token)) {
    return { valid: false, reason: 'Invalid signature' }
  }

  return { valid: true }
}

16.6 Rate Limiting Permission Bypass Requests

Even with all the above controls, an attacker who gains access to the local machine could repeatedly create bypass sessions. Rate limiting provides a backstop:

interface RateLimitConfig {
  maxBypassSessionsPerHour: number
  maxBypassSessionsPerDay: number
  cooldownAfterRejection: number  // milliseconds
}

const DEFAULT_RATE_LIMIT: RateLimitConfig = {
  maxBypassSessionsPerHour: 5,
  maxBypassSessionsPerDay: 20,
  cooldownAfterRejection: 60_000,  // 1 minute cooldown after rejection
}

class BypassRateLimiter {
  private timestamps: number[] = []

  canCreateBypassSession(config: RateLimitConfig = DEFAULT_RATE_LIMIT): {
    allowed: boolean
    reason?: string
    retryAfterMs?: number
  } {
    const now = Date.now()
    const oneHourAgo = now - 3600_000
    const oneDayAgo = now - 86400_000

    // Clean old entries
    this.timestamps = this.timestamps.filter(t => t > oneDayAgo)

    const hourCount = this.timestamps.filter(t => t > oneHourAgo).length
    const dayCount = this.timestamps.length

    if (hourCount >= config.maxBypassSessionsPerHour) {
      const oldestInHour = this.timestamps
        .filter(t => t > oneHourAgo)
        .sort()[0]
      return {
        allowed: false,
        reason: `Hourly limit (${config.maxBypassSessionsPerHour}) reached`,
        retryAfterMs: oldestInHour + 3600_000 - now,
      }
    }

    if (dayCount >= config.maxBypassSessionsPerDay) {
      return {
        allowed: false,
        reason: `Daily limit (${config.maxBypassSessionsPerDay}) reached`,
        retryAfterMs: this.timestamps[0] + 86400_000 - now,
      }
    }

    this.timestamps.push(now)
    return { allowed: true }
  }
}

16.7 Restricting dangerouslySkipPermissions to Non-Production

The strongest control for enterprise environments: block dangerouslySkipPermissions entirely in production.

Environment-Based Restriction

function isDangerouslySkipPermissionsAllowed(): {
  allowed: boolean
  reason?: string
} {
  // Check managed settings (enterprise policy)
  const managedPolicy = getManagedSettings()
  if (managedPolicy?.disablePermissionBypass === true) {
    return {
      allowed: false,
      reason: 'Permission bypass disabled by organization policy',
    }
  }

  // Check environment markers
  const env = process.env.NODE_ENV ?? 'development'
  const isProduction = env === 'production' ||
    process.env.CI === 'true' ||
    process.env.CLAUDE_PRODUCTION === 'true'

  if (isProduction &&
      !process.env.CLAUDE_ALLOW_PRODUCTION_BYPASS) {
    return {
      allowed: false,
      reason: 'Permission bypass is not allowed in production environments. ' +
        'Set CLAUDE_ALLOW_PRODUCTION_BYPASS=true to override (not recommended).',
    }
  }

  return { allowed: true }
}

Enterprise Policy Integration

{
  "managedSettings": {
    "disablePermissionBypass": true,
    "requireMFA": true,
    "auditAllSessions": true,
    "maxSessionDuration": 28800
  }
}

When disablePermissionBypass is set in managed settings (distributed via MDM or configuration management), no user on the machine can create bypass sessions, regardless of command-line arguments or environment variables. This provides organizational control over the most dangerous capability in the system.

Fuzzing the Loopback Check

The loopback address check is a critical security boundary. Edge cases in IP parsing can create bypasses:

Input Expected Risk if Wrong
0x7f000001 Loopback (127.0.0.1 in hex) Attacker bypasses remote check with hex IP
2130706433 Loopback (127.0.0.1 in decimal) Attacker bypasses with decimal IP
0177.0.0.1 Loopback (127.0.0.1 in octal) Attacker bypasses with octal notation
127.0.0.1.evil.com NOT loopback (DNS resolves) Loopback check passes but connects to attacker
[::ffff:127.0.0.1] Loopback (IPv4-mapped IPv6) IPv6 notation bypasses IPv4-only check
127.1 Loopback (short form of 127.0.0.1) Some platforms expand, others reject

The isLoopbackAddress() function must handle all these representations. Using Node.js's net.isIP() for initial classification, then DNS resolution for hostnames, ensures consistent handling:

test('handles exotic IP representations', async () => {
  // These should all be handled without security bypass
  expect(await isLoopbackAddress('0x7f000001')).toBe(false)  // Not a valid IP for net.isIP
  expect(await isLoopbackAddress('2130706433')).toBe(false)   // Not a valid IP for net.isIP
  expect(await isLoopbackAddress('0177.0.0.1')).toBe(false)   // Octal not recognized
  expect(await isLoopbackAddress('127.0.0.1.evil.com')).toBe(false) // DNS resolves to attacker
})

The defense strategy: treat only addresses that pass net.isIP() validation as literal IPs. Everything else goes through DNS resolution, which resolves the actual target. This prevents octal/hex/decimal representation tricks.

16.9 Attack Scenario: CI/CD Pipeline Exploitation

The most realistic attack scenario for remote permission bypass targets CI/CD pipelines. These environments have unique properties that amplify the risk:

  1. Non-interactive: No human is present to read warning prompts or type confirmations
  2. Credential-rich: Build environments contain deployment keys, NPM tokens, cloud credentials
  3. Network-accessible: Build servers are reachable from the corporate network
  4. Script-driven: Configuration is in code (.yml, .toml, .env), not interactive setup

How Each Defense Layer Mitigates This

Layer Effect on CI/CD Attack
Environment check If NODE_ENV=production or CI=true, bypass is blocked unless explicitly overridden
Warning prompt Non-interactive -- falls through to env var check (CLAUDE_CONFIRM_SKIP_PERMISSIONS)
Localhost check Blocks the attack -- attacker.com is not localhost
Rate limit Limits damage if localhost check is somehow bypassed
Signed token Token bound to server URL -- cannot be replayed against different server
Server validation Attacker's server would need to implement the validation protocol

The localhost check is the primary defense for CI/CD attacks. Even if the attacker controls the CLAUDE_SERVER_URL, the client refuses to send permission bypass tokens to non-loopback addresses. The CI pipeline can still use Claude Code with standard permission mode (where each tool call requires explicit allow rules in configuration), but it cannot create permissionless sessions against remote servers.

Backward Compatibility

The transition from raw boolean to signed token requires coordination between client and server:

  1. Phase 1: Server accepts both old format (dangerously_skip_permissions: true) and new format (permission_bypass_token: {...}). Log deprecation warning when old format is used.
  2. Phase 2: CLI update pushed to all clients, generating signed tokens instead of raw booleans.
  3. Phase 3: Server rejects old format. Only signed tokens accepted.

This three-phase approach ensures that no client-server version mismatch causes a service disruption. The deprecation window should be at least 4 weeks, with prominent warnings in the CLI output when the old format is still in use.

As discussed in Chapter 15, the sandbox system prevents MCP servers from exceeding their declared capabilities. This chapter applies similar principles to the remote session boundary: no component should receive more privilege than it needs, privilege escalation must require explicit authorization, and every authorization decision must be auditable.
