Chapter 10: JWT Signature Verification

Part III secured the credential storage layer --- encrypting tokens at rest on all platforms, eliminating TOCTOU races in credential file writes, and protecting conversation history from plaintext exposure. With credentials now stored securely, Part IV turns to the next link in the chain: how those credentials are used at runtime. The authentication token lifecycle --- from issuance through refresh to expiration --- presents a distinct attack surface where vulnerabilities compound across multiple files and trust boundaries.

This chapter addresses the most severe finding in the Auth Token Lifecycle chain: CWE-347 --- JWT Decoded Without Signature Verification (CVSS 7.5). The decodeJwtPayload() function in bridge/jwtUtils.ts performs Base64 decoding of JWT payloads without any cryptographic verification, then uses the unverified exp claim to schedule token refresh timers. A forged token with a far-future expiration can suppress refresh indefinitely, while a near-past expiration can trigger tight refresh loops that degrade service. The fix requires JWKS-based signature verification, a public key cache with automatic rotation, cross-validation of exp claims against server-provided expires_in, and the clampTokenRefreshDelay defense that bounds timer scheduling to safe ranges.

10.1 The Vulnerability: Base64 Decode as "Verification"

JWT (JSON Web Token, RFC 7519) is a three-part structure: header, payload, and signature, each Base64URL-encoded and separated by periods. The signature exists precisely so that recipients can verify the token was issued by a trusted party and has not been tampered with. Skipping signature verification defeats the entire purpose of using signed tokens.

The vulnerable code in bridge/jwtUtils.ts treats JWT decoding as a simple string-splitting operation:

// bridge/jwtUtils.ts — VULNERABLE
export function decodeJwtPayload(token: string): unknown | null {
  const jwt = token.startsWith('sk-ant-si-')
    ? token.slice('sk-ant-si-'.length)
    : token
  const parts = jwt.split('.')
  if (parts.length !== 3 || !parts[1]) return null
  try {
    return jsonParse(Buffer.from(parts[1], 'base64url').toString('utf8'))
  } catch {
    return null
  }
}

export function decodeJwtExpiry(token: string): number | null {
  const payload = decodeJwtPayload(token)
  if (
    payload !== null &&
    typeof payload === 'object' &&
    'exp' in payload &&
    typeof payload.exp === 'number'
  ) {
    return payload.exp
  }
  return null
}

Three things are absent:

  1. No signature verification. The function splits on . and decodes the second segment. It never touches the third segment (the signature). Any party can construct a JWT with arbitrary claims, and this function will accept it.

  2. No issuer validation. The iss claim, which identifies who signed the token, is never checked. A token signed by any key --- or no key at all --- passes through.

  3. No audience validation. The aud claim, which identifies the intended recipient, is ignored. A token intended for a completely different service is accepted.

The Token Prefix Stripping

The sk-ant-si- prefix stripping reveals an implementation detail: Anthropic's session tokens use a proprietary prefix before the standard JWT structure. The code strips this prefix to access the raw JWT, but this stripping happens before any validation --- creating an additional parsing surface where malformed prefixes could lead to unexpected behavior.

Where the Decoded Claims Are Used

The unverified exp claim flows directly into the token refresh scheduler:

// bridge/jwtUtils.ts — schedule() function
function schedule(sessionId: string, token: string): void {
  const expiry = decodeJwtExpiry(token)
  if (!expiry) {
    logForDebugging(
      `[${label}:token] Could not decode JWT expiry for sessionId=${sessionId}, ` +
      `token prefix=${token.slice(0, 15)}..., keeping existing timer`,
    )
    return
  }
  const existing = timers.get(sessionId)
  if (existing) { clearTimeout(existing) }
  const gen = nextGeneration(sessionId)
  const expiryDate = new Date(expiry * 1000).toISOString()
  const delayMs = expiry * 1000 - Date.now() - refreshBufferMs
  if (delayMs <= 0) {
    logForDebugging(`Token for sessionId=${sessionId} expires=${expiryDate}, refreshing immediately`)
    void doRefresh(sessionId, gen)
    return
  }
  logForDebugging(`Scheduled token refresh for sessionId=${sessionId} in ${formatDuration(delayMs)}`)
  const timer = setTimeout(doRefresh, delayMs, sessionId, gen)
  timers.set(sessionId, timer)
}

This creates two attack vectors:

Far-future exp suppresses refresh. A forged token with exp set to year 2099 produces a delayMs of approximately 2.3 trillion milliseconds. The setTimeout call schedules a refresh that will never fire during any realistic session. If the legitimate token has been revoked server-side, the client continues using the stale token until the server rejects it --- but by then, the session state may be corrupted.

Near-past exp triggers tight loops. A token with exp set to one second in the past produces delayMs <= 0, triggering immediate refresh. If the refresh returns another near-expired token (or the same forged token via a MITM), this creates a tight retry loop that consumes CPU and generates excessive API calls.

The Debug Log Leak (CWE-532)

Notice the logging statement: token prefix=${token.slice(0, 15)}. For tokens starting with sk-ant-si- (10 characters), this logs the prefix plus 5 characters of the actual secret. Finding V-32 and V-41 in the audit identify four instances of this pattern across bridge/jwtUtils.ts. Debug logs with token material are a credential exposure vector --- anyone with access to log files gets a head start on brute-forcing the full token.

10.3 The Fix: JWKS-Based Signature Verification

The complete remediation has four components: JWKS verification, public key caching, exp claim cross-validation, and the clampTokenRefreshDelay defense. We implement them in sequence because each builds on the previous.

Component 1: JWKS Public Key Cache

Before we can verify JWT signatures, we need the signing authority's public keys. JSON Web Key Set (JWKS, RFC 7517) is the standard mechanism for distributing public keys. The Anthropic authentication server publishes its signing keys at a JWKS endpoint.

// bridge/jwksCache.ts — NEW FILE
import { createHash } from 'crypto'
import { createPublicKey, KeyObject } from 'crypto'

interface JwksKey {
  kty: string
  kid: string
  use?: string
  n?: string    // RSA modulus
  e?: string    // RSA exponent
  x?: string    // EC x-coordinate
  y?: string    // EC y-coordinate
  crv?: string  // EC curve name
  alg?: string
}

interface JwksResponse {
  keys: JwksKey[]
}

interface CachedKeySet {
  keys: Map<string, KeyObject>
  fetchedAt: number
  expiresAt: number
}

const JWKS_CACHE_DURATION_MS = 60 * 60 * 1000   // 1 hour
const JWKS_MIN_REFRESH_MS = 5 * 60 * 1000       // 5 minutes (rate limit)
const JWKS_FETCH_TIMEOUT_MS = 10_000             // 10 seconds

let cachedKeySet: CachedKeySet | null = null
let lastFetchAttempt = 0

/**
 * Convert a JWK (JSON Web Key) to a Node.js KeyObject for signature verification.
 * Supports RSA (RS256, RS384, RS512) and EC (ES256, ES384, ES512) key types.
 */
function jwkToKeyObject(jwk: JwksKey): KeyObject {
  return createPublicKey({ key: jwk, format: 'jwk' })
}

/**
 * Fetch and cache the JWKS key set from the authentication server.
 * Implements rate limiting to prevent excessive requests during key rotation.
 */
export async function getSigningKey(kid: string): Promise<KeyObject | null> {
  const now = Date.now()

  // Return cached key if available and not expired
  if (cachedKeySet && now < cachedKeySet.expiresAt) {
    return cachedKeySet.keys.get(kid) ?? null
  }

  // Rate limit JWKS fetches
  if (now - lastFetchAttempt < JWKS_MIN_REFRESH_MS) {
    // Return stale cache if available, null otherwise
    return cachedKeySet?.keys.get(kid) ?? null
  }

  lastFetchAttempt = now

  try {
    const controller = new AbortController()
    const timeout = setTimeout(() => controller.abort(), JWKS_FETCH_TIMEOUT_MS)

    const response = await fetch(getJwksUrl(), {
      signal: controller.signal,
      headers: { 'Accept': 'application/json' },
    })
    clearTimeout(timeout)

    if (!response.ok) {
      // Extend stale cache on fetch failure (fail-open for availability)
      if (cachedKeySet) {
        cachedKeySet.expiresAt = now + JWKS_MIN_REFRESH_MS
      }
      return cachedKeySet?.keys.get(kid) ?? null
    }

    const jwks: JwksResponse = await response.json()
    const keys = new Map<string, KeyObject>()

    for (const key of jwks.keys) {
      if (key.kid && (key.use === 'sig' || !key.use)) {
        keys.set(key.kid, jwkToKeyObject(key))
      }
    }

    cachedKeySet = {
      keys,
      fetchedAt: now,
      expiresAt: now + JWKS_CACHE_DURATION_MS,
    }

    return keys.get(kid) ?? null
  } catch {
    // Network failure: extend stale cache
    if (cachedKeySet) {
      cachedKeySet.expiresAt = now + JWKS_MIN_REFRESH_MS
    }
    return cachedKeySet?.keys.get(kid) ?? null
  }
}

Key design decisions in the cache:

Rate limiting. The JWKS_MIN_REFRESH_MS of 5 minutes prevents an attacker from forcing repeated JWKS fetches by presenting tokens with unknown kid values. Without this, an attacker could trigger a JWKS fetch on every token presentation, creating a denial-of-service via upstream load.

Stale cache fallback. When the JWKS endpoint is unreachable, the cache extends its stale keys for JWKS_MIN_REFRESH_MS. This provides availability during transient network failures while still forcing periodic revalidation. The trade-off: during the stale window, revoked keys remain trusted.

Key filtering. Only keys with use: "sig" (or no use field, per RFC 7517 Section 4.2) are cached. Keys marked use: "enc" are for encryption, not signing, and must be excluded from the verification set.

Component 2: JWT Signature Verification

With the key cache in place, we implement actual signature verification:

// bridge/jwtUtils.ts — SECURE VERSION
import { createVerify, createHash } from 'crypto'
import { getSigningKey } from './jwksCache.js'

interface JwtHeader {
  alg: string
  kid?: string
  typ?: string
}

interface VerifiedJwtPayload {
  exp?: number
  iat?: number
  iss?: string
  aud?: string | string[]
  sub?: string
  [key: string]: unknown
}

const EXPECTED_ISSUER = 'https://auth.anthropic.com'
const EXPECTED_AUDIENCE = 'claude-code-cli'

/**
 * Verify a JWT signature using JWKS-sourced public keys.
 * Returns the verified payload or null if verification fails.
 *
 * This replaces the previous decodeJwtPayload() which performed
 * Base64 decode WITHOUT signature verification (CWE-347).
 */
export async function verifyJwt(
  token: string,
): Promise<VerifiedJwtPayload | null> {
  // Strip Anthropic proprietary prefix if present
  const jwt = token.startsWith('sk-ant-si-')
    ? token.slice('sk-ant-si-'.length)
    : token

  const parts = jwt.split('.')
  if (parts.length !== 3 || !parts[0] || !parts[1] || !parts[2]) {
    return null
  }

  const [headerB64, payloadB64, signatureB64] = parts

  // 1. Decode and validate header
  let header: JwtHeader
  try {
    header = JSON.parse(
      Buffer.from(headerB64, 'base64url').toString('utf8'),
    )
  } catch {
    return null
  }

  // Reject 'none' algorithm (CWE-327: Use of Broken Crypto Algorithm)
  if (!header.alg || header.alg.toLowerCase() === 'none') {
    return null
  }

  // Require kid for JWKS lookup
  if (!header.kid) {
    return null
  }

  // 2. Fetch signing key
  const signingKey = await getSigningKey(header.kid)
  if (!signingKey) {
    return null
  }

  // 3. Verify signature
  const signedContent = `${headerB64}.${payloadB64}`
  const signature = Buffer.from(signatureB64, 'base64url')

  const algMap: Record<string, string> = {
    RS256: 'RSA-SHA256',
    RS384: 'RSA-SHA384',
    RS512: 'RSA-SHA512',
    ES256: 'SHA256',
    ES384: 'SHA384',
    ES512: 'SHA512',
  }

  const nodeAlg = algMap[header.alg]
  if (!nodeAlg) {
    return null // Unsupported algorithm
  }

  const verifier = createVerify(nodeAlg)
  verifier.update(signedContent)

  if (!verifier.verify(signingKey, signature)) {
    return null // Signature invalid
  }

  // 4. Decode payload (signature now verified)
  let payload: VerifiedJwtPayload
  try {
    payload = JSON.parse(
      Buffer.from(payloadB64, 'base64url').toString('utf8'),
    )
  } catch {
    return null
  }

  // 5. Validate standard claims
  if (payload.iss && payload.iss !== EXPECTED_ISSUER) {
    return null
  }

  if (payload.aud) {
    const audiences = Array.isArray(payload.aud) ? payload.aud : [payload.aud]
    if (!audiences.includes(EXPECTED_AUDIENCE)) {
      return null
    }
  }

  return payload
}

The alg: 'none' rejection is critical. The JWT none algorithm attack (CVE-2015-9235) allows tokens with no signature to pass verification when the verifier accepts the none algorithm from the token header. By rejecting none before any signature operation, we eliminate this entire class of attack.

Component 3: exp Claim Cross-Validation

Even with signature verification, a legitimately-signed token could carry an unusual exp value due to server bugs or clock skew. We cross-validate the JWT exp against the server-provided expires_in from the OAuth token response:

// bridge/jwtUtils.ts — exp cross-validation

/** Reasonable bounds for token expiry (V-16 fix) */
const MIN_REASONABLE_EXP = 1577836800  // 2020-01-01T00:00:00Z
const MAX_FUTURE_SECONDS = 365 * 24 * 60 * 60  // 1 year

/**
 * Extract and validate the exp claim from a verified JWT payload.
 * Applies reasonable bounds to prevent timer manipulation even with valid signatures.
 */
export function extractVerifiedExpiry(
  payload: VerifiedJwtPayload,
): number | null {
  if (
    typeof payload.exp !== 'number' ||
    !Number.isFinite(payload.exp)
  ) {
    return null
  }

  const maxReasonableExp = Math.floor(Date.now() / 1000) + MAX_FUTURE_SECONDS

  if (payload.exp < MIN_REASONABLE_EXP || payload.exp > maxReasonableExp) {
    return null  // Reject unreasonable exp values
  }

  return payload.exp
}

/**
 * Cross-validate JWT exp against server-provided expires_in.
 * If both are available and diverge by more than 60 seconds,
 * use the shorter (more conservative) value.
 */
export function crossValidateExpiry(
  jwtExp: number,
  serverExpiresIn: number | null,
): number {
  if (serverExpiresIn === null) {
    return jwtExp
  }

  const serverExp = Math.floor(Date.now() / 1000) + serverExpiresIn
  const divergence = Math.abs(jwtExp - serverExp)

  if (divergence > 60) {
    // Significant divergence: use the shorter expiry (conservative)
    return Math.min(jwtExp, serverExp)
  }

  return jwtExp
}

The cross-validation provides defense-in-depth: even if an attacker compromises the signing key and creates a token with a far-future exp, the server's expires_in response (transmitted over a separate channel) provides a second opinion. The 60-second divergence threshold accommodates normal clock skew while catching manipulation.

Component 4: clampTokenRefreshDelay

The final defense layer bounds the timer scheduling regardless of all other validation. This is the "belt and suspenders" approach --- even if signature verification fails open (network error during JWKS fetch), the clamp prevents extreme timer values:

// bridge/jwtUtils.ts — clampTokenRefreshDelay

/** Maximum allowed token lifetime (24 hours) */
const MAX_TOKEN_LIFETIME_MS = 24 * 60 * 60 * 1000

/** Minimum refresh delay to prevent tight loops (10 seconds) */
const MIN_REFRESH_DELAY_MS = 10_000

/**
 * Clamp a raw refresh delay derived from JWT exp claim.
 * This is the last line of defense: even if signature verification
 * fails open and exp validation is bypassed, the clamp prevents
 * both infinite-delay and tight-loop attacks.
 *
 * Bounds: [10 seconds, 24 hours]
 */
function clampTokenRefreshDelay(rawDelayMs: number): number {
  if (rawDelayMs <= 0) return 0  // Immediate refresh
  if (rawDelayMs < MIN_REFRESH_DELAY_MS) return MIN_REFRESH_DELAY_MS
  if (rawDelayMs > MAX_TOKEN_LIFETIME_MS) return MAX_TOKEN_LIFETIME_MS
  return rawDelayMs
}

The 10-second minimum prevents tight refresh loops from consuming excessive API quota. The 24-hour maximum ensures that no token --- forged or legitimate --- can suppress refresh for more than one day. These bounds are deliberately conservative: a legitimate session token rarely needs more than a few hours of lifetime.

10.4 The Hardened Schedule Function

With all four components in place, the schedule() function transforms from a trust-everything consumer of unverified claims into a defense-in-depth pipeline:

// bridge/jwtUtils.ts — HARDENED schedule()

async function schedule(
  sessionId: string,
  token: string,
  serverExpiresIn: number | null = null,
): Promise<void> {
  // Step 1: Verify JWT signature via JWKS
  const payload = await verifyJwt(token)

  if (!payload) {
    // Signature verification failed — use conservative default
    const tokenFingerprint = createHash('sha256')
      .update(token).digest('hex').slice(0, 12)
    logForDebugging(
      `[${label}:token] JWT verification failed for sessionId=${sessionId}, ` +
      `fingerprint=${tokenFingerprint}, scheduling conservative refresh`,
    )
    // Schedule refresh at MIN_REFRESH_DELAY_MS as fail-safe
    const timer = setTimeout(doRefresh, MIN_REFRESH_DELAY_MS, sessionId, nextGeneration(sessionId))
    timers.set(sessionId, timer)
    return
  }

  // Step 2: Extract and validate exp claim
  const jwtExp = extractVerifiedExpiry(payload)
  if (!jwtExp) {
    logForDebugging(
      `[${label}:token] Invalid exp claim for sessionId=${sessionId}, ` +
      `scheduling conservative refresh`,
    )
    const timer = setTimeout(doRefresh, MIN_REFRESH_DELAY_MS, sessionId, nextGeneration(sessionId))
    timers.set(sessionId, timer)
    return
  }

  // Step 3: Cross-validate against server expires_in
  const effectiveExp = crossValidateExpiry(jwtExp, serverExpiresIn)

  // Step 4: Calculate and clamp delay
  const existing = timers.get(sessionId)
  if (existing) { clearTimeout(existing) }

  const gen = nextGeneration(sessionId)
  const rawDelayMs = effectiveExp * 1000 - Date.now() - refreshBufferMs
  const delayMs = clampTokenRefreshDelay(rawDelayMs)

  if (delayMs <= 0) {
    logForDebugging(
      `[${label}:token] Token for sessionId=${sessionId} expired or within buffer, ` +
      `refreshing immediately`,
    )
    void doRefresh(sessionId, gen)
    return
  }

  logForDebugging(
    `[${label}:token] Scheduled refresh for sessionId=${sessionId} ` +
    `in ${formatDuration(delayMs)}`,
  )
  const timer = setTimeout(doRefresh, delayMs, sessionId, gen)
  timers.set(sessionId, timer)
}

Notice the token fingerprint replacement: createHash('sha256').update(token).digest('hex').slice(0, 12) replaces token.slice(0, 15). This eliminates the debug log credential leak (V-32, V-41) while preserving correlation capability --- the same token always produces the same 12-character hex fingerprint.

10.6 Handling Degraded Scenarios

Production systems must handle scenarios where JWKS verification is unavailable. The design makes explicit choices about each degradation mode:

JWKS Endpoint Unreachable

When the network is down or the JWKS endpoint returns an error, the key cache extends stale keys for 5 minutes. This is a deliberate availability trade-off: the system continues operating with potentially outdated keys rather than blocking all token operations.

Security implication: During the stale window, a revoked signing key remains trusted. The 5-minute stale window bounds this risk, and the server-side 401 check provides a secondary revocation mechanism.

Unknown Key ID

When a token presents a kid not found in the cached key set, the system triggers a JWKS refresh (subject to the 5-minute rate limit). If the refresh returns the new key, verification proceeds. If not, the token is rejected.

Security implication: Key rotation at the authentication server is handled gracefully. An attacker cannot force continuous JWKS fetches by presenting tokens with random kid values, because the rate limiter caps fetch frequency.

First-Run (No Cache)

On the first token verification of a session, the JWKS cache is empty. The system must fetch keys synchronously before proceeding. If the fetch fails, the token falls through to the conservative default (refresh in 10 seconds), providing availability at the cost of an extra round-trip.

10.9 Migration Path

Deploying JWKS verification in a production CLI tool requires careful sequencing to avoid breaking existing sessions.

Phase 1: Ship clampTokenRefreshDelay immediately. This is a pure addition that bounds timer scheduling without requiring JWKS infrastructure. It provides immediate protection against the worst attack vectors (infinite delay, tight loops) while the full JWKS implementation is built.

Phase 2: Deploy JWKS cache with fail-open. The initial JWKS deployment uses fail-open semantics: if verification fails (network error, unknown key, timeout), the token falls through to the existing Base64-decode path with clamp protection. This prevents breakage during rollout while collecting metrics on verification success rates.

Phase 3: Tighten to fail-closed. Once metrics confirm that 99%+ of tokens verify successfully, switch to fail-closed: verification failure triggers immediate refresh rather than accepting the unverified token. The conservative 10-second refresh default provides availability while forcing re-authentication.

Phase 4: Remove legacy decode path. Delete decodeJwtPayload() and all call sites that bypass signature verification. This eliminates the temptation to "just decode" in new code paths.

As Chapter 11 will discuss, the clampTokenRefreshDelay defense also enables the token refresh hardening that addresses CWE-613 --- environment variable tokens that never expire. The bounded timer ensures that even tokens without explicit expiry are periodically re-evaluated.

10.10 Key Takeaways

  1. Never trust JWT claims without signature verification. Base64 decoding is not verification. Any party can construct a JWT with arbitrary claims. The signature is the only proof that the issuer created the token with those exact claims.

  2. Defense-in-depth for timer scheduling. Four independent layers (signature verification, claim bounds checking, cross-validation against server data, and timer clamping) ensure that no single failure allows extreme timer values. Each layer catches different failure modes.

  3. Public key management is its own subsystem. JWKS caching requires rate limiting, stale-cache fallback, graceful key rotation handling, and first-run bootstrapping. The key cache is as security-critical as the verification itself.

  4. Debug logs are a credential exposure vector. Replacing token.slice(0, 15) with a SHA-256 fingerprint eliminates credential leakage while preserving the debugging utility of token correlation.

  5. Clamp first, verify later. The clampTokenRefreshDelay defense can ship independently and immediately, providing protection while the more complex JWKS infrastructure is built and tested. Layered deployment reduces rollout risk.
