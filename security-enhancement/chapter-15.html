Chapter 15: MCP Server Sandboxing

Chapter 14 built the resource governance framework for the agent hierarchy -- cryptographic depth tracking, width limits, and per-agent budgets. But those controls govern agents within the Claude Code process tree. A separate and equally dangerous execution domain exists outside that tree: MCP server tools.

MCP (Model Context Protocol) servers are external processes that provide tools to Claude Code. They run with the full privileges of the user who launched them. Finding 6 from the security audit -- CWE-250: Execution with Unnecessary Privileges (CVSS 7.5) -- identifies this as a HIGH severity issue. The finding is blunt: "MCP server tool calls execute within the CLI process's security context with no process-level sandboxing. Approved MCP tools run with the full capabilities of the CLI process."

This chapter implements the sandbox that the audit found missing. We cover seccomp-bpf for Linux, sandbox-exec for macOS, capability-based restrictions per server, and network namespace isolation for untrusted MCP servers.

15.1 The MCP Execution Model

Current Architecture: Trust Everything

When a user installs an MCP server (via .mcp.json or the marketplace), the following trust chain is established:

graph TD
    USER["User installs MCP server"] --> CONFIG["Server registered in .mcp.json"]
    CONFIG --> SPAWN["Claude Code spawns server process"]
    SPAWN --> DISCOVER["Tool discovery: server declares tools"]
    DISCOVER --> CALL["Agent calls MCP tool"]
    CALL --> PERM["Permission check (user prompt or auto-allow)"]
    PERM --> EXEC["Tool executes in server process<br/>with FULL user privileges"]

    EXEC --> FS["Full filesystem access"]
    EXEC --> NET["Full network access"]
    EXEC --> PROC["Process spawning"]
    EXEC --> ENV["Environment variables"]

    style EXEC fill:#fce4ec
    style FS fill:#fce4ec
    style NET fill:#fce4ec
    style PROC fill:#fce4ec
    style ENV fill:#fce4ec

The permission check at the PERM stage asks the user "Allow this tool call?" But that permission is binary -- allow or deny. There is no option to "allow with restricted filesystem" or "allow but block network." Once approved, the tool executes with the same privileges as the Claude Code process itself.

Why This Is Dangerous

The audit finding describes the scenario precisely: "A malicious MCP server registered in a marketplace could define tools that appear benign (e.g., 'format_code') but internally execute arbitrary commands when approved. Once the user approves the tool, it runs with full CLI privileges."

Consider a concrete attack:

  1. Attacker publishes "mcp-code-formatter" to the MCP marketplace
  2. Tool declares itself as readOnlyHint: true with description "Formats code using prettier"
  3. User installs it, trusts the marketplace listing
  4. Agent calls the tool with a code snippet
  5. Instead of formatting, the server reads ~/.ssh/id_rsa and ~/.aws/credentials
  6. Server returns the "formatted" code along with exfiltrated credentials as a side effect
  7. User sees properly formatted code and suspects nothing

The self-reported readOnlyHint: true annotation is meaningless -- the server can do anything regardless of what it declares.

15.2 Sandbox Architecture Overview

The sandbox wraps every MCP server process in an OS-level confinement that restricts what the process can do, regardless of what the server code attempts. The sandbox has four layers:

graph TD
    subgraph "Layer 1: Process Isolation"
        FORK["Separate process<br/>(already exists)"]
    end

    subgraph "Layer 2: Filesystem Sandbox"
        FS["Restrict file access<br/>to declared paths only"]
    end

    subgraph "Layer 3: Syscall Filter"
        SC["seccomp-bpf (Linux)<br/>sandbox-exec (macOS)<br/>Block dangerous syscalls"]
    end

    subgraph "Layer 4: Network Isolation"
        NET["Network namespace (Linux)<br/>Block outbound connections<br/>for untrusted servers"]
    end

    FORK --> FS --> SC --> NET

    style FORK fill:#e8f5e9
    style FS fill:#fff3e0
    style SC fill:#fce4ec
    style NET fill:#e1f5fe

Each layer provides defense even if the other layers fail:

Layer What It Prevents Failure Mode
Process isolation Shared memory access, signal injection Does NOT prevent filesystem/network abuse
Filesystem sandbox Reading secrets, writing backdoors Does NOT prevent network exfiltration
Syscall filter Process spawning, raw socket creation Does NOT prevent allowed-but-abused syscalls
Network isolation Data exfiltration, C2 communication Does NOT prevent local-only attacks

15.3 Capability Declarations

Before implementing the sandbox, we need a way for MCP servers to declare what capabilities they actually need. This declaration serves two purposes: (1) the sandbox knows what to allow, and (2) the user knows what the server requires before installing it.

The Capability Schema

interface McpServerCapabilities {
  filesystem: {
    read: string[]      // Glob patterns for readable paths
    write: string[]     // Glob patterns for writable paths
    execute: string[]   // Glob patterns for executable paths
  }
  network: {
    outbound: NetworkRule[]  // Allowed outbound connections
    dns: boolean             // Whether DNS resolution is needed
  }
  process: {
    spawn: boolean      // Whether child process spawning is needed
    maxChildren: number // Maximum child processes
  }
  environment: {
    read: string[]      // Env vars the server needs to read
    inherit: boolean    // Whether to inherit all env vars
  }
}

interface NetworkRule {
  host: string          // Hostname or IP pattern
  port: number | '*'    // Port number or wildcard
  protocol: 'tcp' | 'udp' | 'tls'
}

Example Capability Declarations

    },

      "dns": false
    },

Capability Verification at Install Time

When a user installs an MCP server, Claude Code presents the capability requirements:

Installing: mcp-code-formatter v1.2.0

Required capabilities:
  Filesystem: Read/Write *.ts, *.js, *.py in workspace
  Network:    None (no outbound connections)
  Process:    May spawn up to 2 child processes
  Env vars:   NODE_ENV, HOME

Accept these capabilities? [y/N]

If a server later attempts to exceed its declared capabilities (reading a file outside its declared paths, connecting to a network host not in its outbound list), the sandbox blocks the operation and logs the violation.

Undeclared Capabilities Default to Denied

The most important security property: capabilities that are not explicitly declared are denied. A server that declares no network.outbound rules cannot make any network connections. A server that declares no filesystem.write patterns cannot write to any files.

function resolveCapabilities(
  declared: Partial<McpServerCapabilities> | undefined
): McpServerCapabilities {
  return {
    filesystem: {
      read: declared?.filesystem?.read ?? [],
      write: declared?.filesystem?.write ?? [],
      execute: declared?.filesystem?.execute ?? [],
    },
    network: {
      outbound: declared?.network?.outbound ?? [],
      dns: declared?.network?.dns ?? false,
    },
    process: {
      spawn: declared?.process?.spawn ?? false,
      maxChildren: declared?.process?.maxChildren ?? 0,
    },
    environment: {
      read: declared?.environment?.read ?? [],
      inherit: declared?.environment?.inherit ?? false,
    },
  }
}

15.4 Linux Sandboxing with seccomp-bpf

On Linux, the sandbox uses seccomp-bpf (Secure Computing with Berkeley Packet Filter) to restrict which system calls the MCP server process can make. seccomp-bpf operates at the kernel level -- no amount of application-level trickery can bypass it.

How seccomp-bpf Works

sequenceDiagram
    participant App as MCP Server Process
    participant Kernel as Linux Kernel
    participant BPF as seccomp-bpf Filter

    App->>Kernel: syscall(open, "/etc/shadow", O_RDONLY)
    Kernel->>BPF: Check syscall against filter
    BPF->>BPF: open() with /etc/shadow?<br/>Path not in allowed list
    BPF-->>Kernel: SECCOMP_RET_ERRNO (EACCES)
    Kernel-->>App: errno = EACCES (Permission denied)

    App->>Kernel: syscall(socket, AF_INET, SOCK_STREAM)
    Kernel->>BPF: Check syscall against filter
    BPF->>BPF: socket(AF_INET)?<br/>Network not in capabilities
    BPF-->>Kernel: SECCOMP_RET_ERRNO (EPERM)
    Kernel-->>App: errno = EPERM (Operation not permitted)

Building the seccomp Profile

The seccomp profile is generated from the server's capability declaration. Each capability maps to a set of allowed syscalls:

interface SeccompProfile {
  defaultAction: 'SCMP_ACT_ERRNO'  // Default: deny
  architectures: string[]
  syscalls: SeccompRule[]
}

interface SeccompRule {
  names: string[]
  action: 'SCMP_ACT_ALLOW' | 'SCMP_ACT_ERRNO' | 'SCMP_ACT_LOG'
  args?: SeccompArg[]
}

function buildSeccompProfile(
  capabilities: McpServerCapabilities
): SeccompProfile {
  const rules: SeccompRule[] = []

  // Always allowed: basic process operations
  rules.push({
    names: [
      'read', 'write', 'close', 'fstat', 'lseek', 'mmap', 'mprotect',
      'munmap', 'brk', 'rt_sigaction', 'rt_sigprocmask', 'ioctl',
      'nanosleep', 'clock_nanosleep', 'getpid', 'getuid', 'getgid',
      'geteuid', 'getegid', 'exit', 'exit_group', 'futex',
      'clock_gettime', 'clock_getres', 'getrandom', 'memfd_create',
      'eventfd2', 'epoll_create1', 'epoll_ctl', 'epoll_wait',
      'pipe2', 'fcntl',
    ],
    action: 'SCMP_ACT_ALLOW',
  })

  // Filesystem: only if declared
  if (capabilities.filesystem.read.length > 0 ||
      capabilities.filesystem.write.length > 0) {
    rules.push({
      names: ['openat', 'stat', 'lstat', 'access', 'readlink',
              'getdents64', 'newfstatat'],
      action: 'SCMP_ACT_ALLOW',
    })
  }

  if (capabilities.filesystem.write.length > 0) {
    rules.push({
      names: ['openat', 'rename', 'renameat2', 'unlink', 'unlinkat',
              'mkdir', 'mkdirat', 'chmod', 'fchmod', 'truncate',
              'ftruncate', 'fsync', 'fdatasync'],
      action: 'SCMP_ACT_ALLOW',
    })
  }

  // Network: only if declared
  if (capabilities.network.outbound.length > 0 ||
      capabilities.network.dns) {
    rules.push({
      names: ['socket', 'connect', 'sendto', 'recvfrom', 'sendmsg',
              'recvmsg', 'bind', 'listen', 'accept4', 'getsockopt',
              'setsockopt', 'getpeername', 'getsockname'],
      action: 'SCMP_ACT_ALLOW',
    })
  }

  // Process spawning: only if declared
  if (capabilities.process.spawn) {
    rules.push({
      names: ['clone', 'clone3', 'execve', 'execveat', 'wait4',
              'waitid'],
      action: 'SCMP_ACT_ALLOW',
    })
  }

  // Dangerous syscalls: always blocked
  rules.push({
    names: [
      'ptrace',           // Process tracing (debug other processes)
      'personality',      // Change execution domain
      'mount', 'umount2', // Filesystem mount manipulation
      'pivot_root',       // Root filesystem manipulation
      'reboot',           // System reboot
      'sethostname',      // Change hostname
      'setdomainname',    // Change domain name
      'kexec_load',       // Load new kernel
      'init_module',      // Load kernel module
      'finit_module',     // Load kernel module from fd
      'delete_module',    // Remove kernel module
      'keyctl',           // Kernel key management
      'add_key',          // Add kernel key
      'request_key',      // Request kernel key
    ],
    action: 'SCMP_ACT_ERRNO',
  })

  return {
    defaultAction: 'SCMP_ACT_ERRNO',
    architectures: ['SCMP_ARCH_X86_64', 'SCMP_ARCH_AARCH64'],
    syscalls: rules,
  }
}

Applying the seccomp Profile

The profile is applied to the MCP server process immediately after fork, before exec:

import { execFileSync } from 'node:child_process'

function spawnSandboxedMcpServer(
  serverConfig: McpServerConfig,
  capabilities: McpServerCapabilities
): ChildProcess {
  const profile = buildSeccompProfile(capabilities)
  const profilePath = writeTempProfile(profile)

  // Use a sandbox wrapper that applies seccomp before exec
  const child = spawn(
    '/usr/bin/bwrap',  // bubblewrap sandbox
    [
      '--ro-bind', '/usr', '/usr',
      '--ro-bind', '/lib', '/lib',
      '--ro-bind', '/lib64', '/lib64',
      '--ro-bind', '/etc/resolv.conf', '/etc/resolv.conf',
      '--dev', '/dev',
      '--proc', '/proc',
      // Workspace access based on capabilities
      ...buildMountArgs(capabilities),
      // seccomp filter
      '--seccomp', '3',
      // The actual server command
      '--', serverConfig.command, ...serverConfig.args,
    ],
    {
      stdio: ['pipe', 'pipe', 'pipe', 'pipe'],  // fd 3 for seccomp
      env: buildSandboxedEnv(capabilities),
    }
  )

  // Write seccomp profile to fd 3
  child.stdio[3]!.write(JSON.stringify(profile))
  child.stdio[3]!.end()

  return child
}

bubblewrap Mount Mapping

The buildMountArgs function translates filesystem capabilities into bubblewrap bind-mount arguments:

function buildMountArgs(
  capabilities: McpServerCapabilities
): string[] {
  const args: string[] = []

  // Read-only mounts for readable paths
  for (const pattern of capabilities.filesystem.read) {
    const resolved = resolveCapabilityPath(pattern)
    args.push('--ro-bind', resolved, resolved)
  }

  // Read-write mounts for writable paths
  for (const pattern of capabilities.filesystem.write) {
    const resolved = resolveCapabilityPath(pattern)
    args.push('--bind', resolved, resolved)
  }

  // Executable mounts
  for (const pattern of capabilities.filesystem.execute) {
    const resolved = resolveCapabilityPath(pattern)
    args.push('--ro-bind', resolved, resolved)
  }

  // Temporary directory (always available)
  args.push('--tmpfs', '/tmp')

  return args
}

15.5 macOS Sandboxing with sandbox-exec

macOS does not support seccomp-bpf. Instead, it provides sandbox-exec (also known as Seatbelt), a mandatory access control framework based on the TrustedBSD subsystem.

sandbox-exec Profile Language

Seatbelt profiles use a Scheme-like language (SBPL -- Sandbox Profile Language):

(version 1)

;; Default: deny everything
(deny default)

;; Allow basic process operations
(allow process-exec)
(allow process-fork)
(allow signal (target self))
(allow sysctl-read)

;; Allow reading specific paths
(allow file-read*
  (subpath "/usr/lib")
  (subpath "/usr/local/lib")
  (subpath "/System/Library")
  (literal "/dev/null")
  (literal "/dev/urandom")
  ;; Workspace paths injected from capabilities
  %%WORKSPACE_READ_RULES%%
)

;; Allow writing specific paths
(allow file-write*
  (subpath "/private/tmp")
  %%WORKSPACE_WRITE_RULES%%
)

;; Network: conditional on capabilities
%%NETWORK_RULES%%

;; Block dangerous operations
(deny file-write*
  (subpath "/System")
  (subpath "/usr")
  (subpath "/Library")
  (regex #"^/Users/[^/]+/\.(ssh|gnupg|aws|azure)")
)

;; Block process inspection
(deny process-info-pidinfo (target others))
(deny process-info-setcontrol (target others))

;; Allow IPC with parent (Claude Code)
(allow mach-lookup
  (global-name "com.apple.system.notification_center")
)

Generating macOS Profiles from Capabilities

function buildSeatbeltProfile(
  capabilities: McpServerCapabilities,
  workspacePath: string
): string {
  let profile = `(version 1)
(deny default)

;; Basic process operations
(allow process-exec)
(allow process-fork)
(allow signal (target self))
(allow sysctl-read)
(allow mach-lookup)
(allow ipc-posix-shm-read-data)
(allow ipc-posix-shm-write-data)

;; System libraries (read-only)
(allow file-read*
  (subpath "/usr/lib")
  (subpath "/usr/local/lib")
  (subpath "/System/Library/Frameworks")
  (subpath "/System/Library/PrivateFrameworks")
  (subpath "/Library/Frameworks")
  (literal "/dev/null")
  (literal "/dev/urandom")
  (literal "/dev/random")
  (literal "/etc/resolv.conf")
)
`

  // Filesystem read access
  for (const pattern of capabilities.filesystem.read) {
    const resolved = resolveCapabilityPath(pattern, workspacePath)
    profile += `(allow file-read* (subpath "${resolved}"))\n`
  }

  // Filesystem write access
  for (const pattern of capabilities.filesystem.write) {
    const resolved = resolveCapabilityPath(pattern, workspacePath)
    profile += `(allow file-write* (subpath "${resolved}"))\n`
  }

  // Always allow tmp
  profile += `(allow file-write* (subpath "/private/tmp"))\n`
  profile += `(allow file-read* (subpath "/private/tmp"))\n`

  // Network access
  if (capabilities.network.outbound.length > 0 ||
      capabilities.network.dns) {
    profile += `\n;; Network access (declared in capabilities)\n`
    profile += `(allow network-outbound)\n`
    profile += `(allow network-inbound)\n`
    profile += `(allow system-socket)\n`
  } else {
    profile += `\n;; No network access (not declared)\n`
    profile += `(deny network-outbound)\n`
    profile += `(deny network-inbound)\n`
  }

  // Always block sensitive paths
  profile += `
;; Sensitive path protection (always blocked)
(deny file-read*
  (regex #"^/Users/[^/]+/\\.ssh")
  (regex #"^/Users/[^/]+/\\.gnupg")
  (regex #"^/Users/[^/]+/\\.aws")
  (regex #"^/Users/[^/]+/\\.azure")
  (regex #"^/Users/[^/]+/\\.credentials")
  (regex #"^/Users/[^/]+/Library/Keychains")
)
(deny file-write*
  (regex #"^/Users/[^/]+/\\.(bashrc|zshrc|profile|bash_profile)")
  (regex #"^/Users/[^/]+/\\.ssh")
  (subpath "/System")
  (subpath "/usr")
)
`

  return profile
}

Launching with sandbox-exec

function spawnSandboxedMcpServerMacOS(
  serverConfig: McpServerConfig,
  capabilities: McpServerCapabilities,
  workspacePath: string
): ChildProcess {
  const profile = buildSeatbeltProfile(capabilities, workspacePath)
  const profilePath = writeTempFile(profile, 'sb')

  const child = spawn(
    '/usr/bin/sandbox-exec',
    [
      '-f', profilePath,
      '--', serverConfig.command, ...serverConfig.args,
    ],
    {
      stdio: ['pipe', 'pipe', 'pipe', 'ipc'],
      env: buildSandboxedEnv(capabilities),
    }
  )

  return child
}

15.6 Network Namespace Isolation

For MCP servers that do not declare network capabilities, we go beyond syscall-level blocking and provide full network namespace isolation on Linux. This ensures that even if a server finds a way to create a socket (through a vulnerability in the seccomp filter or through an allowed helper process), it has no network to connect to.

Implementation with unshare

function spawnNetworkIsolatedServer(
  serverConfig: McpServerConfig,
  capabilities: McpServerCapabilities
): ChildProcess {
  const hasNetwork = capabilities.network.outbound.length > 0

  if (hasNetwork) {
    // Server needs network -- use standard spawn with firewall rules
    return spawnWithFirewallRules(serverConfig, capabilities)
  }

  // No network needed -- full namespace isolation
  return spawn(
    '/usr/bin/unshare',
    [
      '--net',        // New network namespace (only loopback)
      '--map-current-user',  // Map current user into namespace
      '--', serverConfig.command, ...serverConfig.args,
    ],
    {
      stdio: ['pipe', 'pipe', 'pipe', 'ipc'],
      env: buildSandboxedEnv(capabilities),
    }
  )
}

In the isolated network namespace, the server has only a loopback interface. There is no route to any external host. DNS resolution fails. HTTP requests fail. Exfiltration via network is physically impossible.

Selective Network Access with veth Pairs

For servers that need network access to specific hosts, we create a virtual ethernet (veth) pair with iptables rules:

function spawnWithFirewallRules(
  serverConfig: McpServerConfig,
  capabilities: McpServerCapabilities
): ChildProcess {
  const nsName = `mcp-${randomBytes(4).toString('hex')}`

  // Create network namespace with controlled access
  execFileSync('ip', ['netns', 'add', nsName])
  execFileSync('ip', ['link', 'add', `veth-${nsName}`, 'type', 'veth',
    'peer', 'name', `vethp-${nsName}`])
  execFileSync('ip', ['link', 'set', `vethp-${nsName}`, 'netns', nsName])

  // Set up routing within the namespace
  execFileSync('ip', ['netns', 'exec', nsName,
    'ip', 'addr', 'add', '10.200.0.2/24', 'dev', `vethp-${nsName}`])
  execFileSync('ip', ['addr', 'add', '10.200.0.1/24', 'dev', `veth-${nsName}`])

  // Enable NAT for the namespace
  execFileSync('iptables', ['-t', 'nat', '-A', 'POSTROUTING',
    '-s', '10.200.0.0/24', '-j', 'MASQUERADE'])

  // Apply per-host firewall rules
  for (const rule of capabilities.network.outbound) {
    execFileSync('iptables', ['-A', 'FORWARD',
      '-s', '10.200.0.2',
      '-d', resolveHostToIp(rule.host),
      '-p', rule.protocol === 'udp' ? 'udp' : 'tcp',
      '--dport', String(rule.port),
      '-j', 'ACCEPT',
    ])
  }

  // Default: drop all other forwarded traffic
  execFileSync('iptables', ['-A', 'FORWARD',
    '-s', '10.200.0.2', '-j', 'DROP'])

  return spawn(
    'ip', ['netns', 'exec', nsName,
      serverConfig.command, ...serverConfig.args],
    {
      stdio: ['pipe', 'pipe', 'pipe', 'ipc'],
      env: buildSandboxedEnv(capabilities),
    }
  )
}

15.7 Environment Variable Isolation

MCP servers run as child processes and by default inherit the parent's environment variables. This includes sensitive values like API_KEY, DATABASE_URL, AWS_SECRET_ACCESS_KEY, and authentication tokens.

The Environment Leak

// Current behavior: full inheritance
const child = spawn(serverConfig.command, serverConfig.args, {
  env: process.env,  // ALL parent env vars visible to MCP server
})

Every secret in the parent's environment is available to the MCP server. A malicious server can read process.env and exfiltrate every API key, database credential, and cloud token.

Sandboxed Environment

function buildSandboxedEnv(
  capabilities: McpServerCapabilities
): NodeJS.ProcessEnv {
  // Start with a minimal base environment
  const base: Record<string, string> = {
    PATH: '/usr/local/bin:/usr/bin:/bin',
    HOME: process.env.HOME ?? '/tmp',
    LANG: process.env.LANG ?? 'en_US.UTF-8',
    TERM: process.env.TERM ?? 'xterm-256color',
    NODE_ENV: process.env.NODE_ENV ?? 'production',
  }

  // Add only declared environment variables
  if (capabilities.environment.inherit) {
    // Server declared it needs all env vars (flag for review)
    return { ...process.env }
  }

  for (const varName of capabilities.environment.read) {
    const value = process.env[varName]
    if (value !== undefined) {
      base[varName] = value
    }
  }

  return base
}
Environment Policy What Server Sees Risk Level
inherit: true All parent env vars HIGH -- full secret access
inherit: false, read: ["NODE_ENV"] Only NODE_ENV + base LOW -- minimal exposure
inherit: false, read: [] Only base (PATH, HOME, LANG) MINIMAL -- no secret access

Servers that declare inherit: true receive a warning during installation:

This includes any API keys, tokens, and secrets in your environment.

15.8 Sandbox Violation Monitoring

When a sandboxed MCP server attempts a blocked operation, the violation is logged and optionally reported to the user.

Violation Log Structure

interface SandboxViolation {
  timestamp: number
  serverId: string
  serverName: string
  syscall: string           // The blocked syscall
  args: string[]            // Syscall arguments (if available)
  resource: string          // The resource that was blocked
  declaredCapabilities: string[]  // What the server declared
  severity: 'warning' | 'critical'
}

Distinguishing Malicious from Accidental

Not every sandbox violation indicates malicious intent. Many libraries probe for capabilities at startup:

  • Node.js checks /proc/self/status (blocked by filesystem sandbox on Linux)
  • Python checks os.getlogin() which calls utmp reads
  • Ruby checks for fork() availability at require time

The violation monitor uses a classification system:

function classifyViolation(violation: SandboxViolation): 'expected' | 'suspicious' | 'malicious' {
  // Known-benign probes
  const expectedProbes = [
    { syscall: 'openat', resource: '/proc/self/status' },
    { syscall: 'access', resource: '/etc/localtime' },
    { syscall: 'stat', resource: '/etc/nsswitch.conf' },
  ]

  if (expectedProbes.some(p =>
    p.syscall === violation.syscall &&
    violation.resource.includes(p.resource)
  )) {
    return 'expected'
  }

  // Immediately malicious
  const alwaysMalicious = ['ptrace', 'init_module', 'kexec_load',
    'keyctl', 'mount']
  if (alwaysMalicious.includes(violation.syscall)) {
    return 'malicious'
  }

  // Everything else is suspicious
  return 'suspicious'
}

15.9 Trust Tiers for MCP Servers

Not all MCP servers deserve the same level of sandboxing. A first-party server built by Anthropic has a different trust profile than a random package from npm.

Trust Tier Model

Tier Examples Sandbox Level Verification
Built-in File system tools, Bash, Agent No sandbox (runs in-process) Code review, CI/CD
First-party Anthropic-published MCP servers Light sandbox (filesystem only) Signed by Anthropic key
Marketplace verified Verified third-party servers Full sandbox Marketplace review + signing
Community Unverified third-party Maximum sandbox No verification -- user assumes risk
Unknown No source, no marketplace Maximum sandbox + network isolation Blocked by default

Applying Trust Tiers

function getSandboxLevel(
  server: McpServerConfig
): 'none' | 'light' | 'full' | 'maximum' {
  if (server.source === 'builtin') return 'none'

  if (server.signature && verifyAnthropicSignature(server.signature)) {
    return 'light'
  }

  if (server.marketplace && server.marketplaceVerified) {
    return 'full'
  }

  if (server.source === 'local' || server.source === 'npm') {
    return 'maximum'
  }

  return 'maximum'  // Default to maximum restriction
}

function applySandbox(
  server: McpServerConfig,
  capabilities: McpServerCapabilities
): ChildProcess {
  const level = getSandboxLevel(server)

  switch (level) {
    case 'none':
      return spawn(server.command, server.args)

    case 'light':
      // Filesystem restrictions only
      return spawnWithFilesystemSandbox(server, capabilities)

    case 'full':
      // Filesystem + syscall filter
      return spawnFullySandboxed(server, capabilities)

    case 'maximum':
      // Filesystem + syscall filter + network isolation
      return spawnMaxSandboxed(server, capabilities)
  }
}

Migration Strategy

The sandbox cannot be deployed as a hard requirement overnight -- existing MCP servers do not have capability declarations. The migration follows three phases:

  1. Phase 1 (Week 1-4): Deploy monitoring-only sandbox. Log all operations that would be blocked. Publish capability schema specification.
  2. Phase 2 (Week 5-12): Require capability declarations for new marketplace submissions. Existing servers run with a permissive default capability set derived from monitoring data.
  3. Phase 3 (Week 13+): Enable enforcement for all servers. Servers without declarations receive a minimal default capability set (read-only workspace, no network, no process spawning).

As discussed in Chapter 14, the resource budget system governs agents within the Claude Code process tree. This chapter extends that governance to the MCP server boundary. Together, they ensure that no component in the system -- whether an internal subagent or an external MCP server -- can exceed its declared privileges.
