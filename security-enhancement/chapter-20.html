Chapter 20: Memory Protection

Chapters 18 and 19 addressed data that leaks through logging and telemetry -- outbound channels where sensitive information escapes the process boundary. This chapter turns inward, examining what happens to sensitive data while it resides inside the process itself. Specifically: how long do authentication tokens, proxy credentials, and session secrets remain in memory after they are no longer needed, and what can an attacker with memory access do with them?

The audit identified three instances of credential material persisting on the heap after the code's intended use is complete (V-23, CWE-316), a platform-limited heap protection mechanism (V-44, CWE-316), and a cross-platform architectural gap in memory protection (V-45, CWE-316). Together, these findings describe a credential handling architecture where secrets are read into JavaScript strings -- immutable objects that cannot be overwritten and persist until garbage collection -- creating a window during which any process with sufficient access can extract them from memory.

This is not a theoretical concern. Container escape vulnerabilities (CVE-2024-21626, CVE-2023-3676), kernel exploits, and same-user ptrace access all provide paths to reading another process's memory. In Claude Code's CCR (Cloud Container Runtime) deployment, where the upstream proxy handles session tokens for remote connections, the memory exposure window is the entire lifetime of the proxy process.

20.1 JavaScript Memory Model and Security Implications

Why Strings Are Dangerous

JavaScript strings are immutable. Once a string is created, its contents cannot be modified. This is a language-level guarantee enforced by every JavaScript engine (V8, JavaScriptCore, SpiderMonkey, Bun's JSC-based runtime).

// This does NOT work — strings are immutable
let token = 'sk-ant-si-secret-token-value'
token = '0'.repeat(token.length)  // Creates a NEW string
// The original string 'sk-ant-si-secret-token-value' still exists
// somewhere on the heap, unreferenced but not zeroed

When you "overwrite" a string variable in JavaScript, you are actually creating a new string object and updating the variable reference to point to it. The original string remains in memory until the garbage collector reclaims it -- which happens at an unpredictable time determined by the engine's GC heuristics.

The Buffer Alternative

Node.js (and Bun) provide the Buffer class, which wraps a raw memory allocation that can be explicitly zeroed:

// Buffer CAN be securely wiped
const tokenBuf = Buffer.from('sk-ant-si-secret-token-value')
// ... use tokenBuf ...
tokenBuf.fill(0)  // Overwrites the actual memory with zeros
// The secret is gone. No GC timing dependency.

Buffer.fill(0) performs a direct memory write to the underlying ArrayBuffer. This is a synchronous, deterministic operation that does not depend on garbage collection. After fill(0), the memory contains only zeros.

Even after GC reclaims the memory, most allocators do not zero freed pages. The data persists until the memory is reallocated and overwritten by new data -- which may take milliseconds or hours depending on allocation patterns.

20.2 CWE-316: Cleartext Storage of Sensitive Information in Memory (V-23)

The Vulnerability

Finding V-23 (CVSS 5.3, MEDIUM) identified that the upstream proxy reads a session token from disk, uses it as a JavaScript string, then unlinks the file -- but the string representation of the token remains on the heap indefinitely:

// VULNERABLE: upstreamproxy/upstreamproxy.ts
async function readToken(path: string): Promise<string | null> {
  try {
    return await readFile(path, 'utf8')  // Returns a JS string — immutable
  } catch (err) {
    if (isENOENT(err)) return null
    logForDebugging(
      `[upstreamproxy] token read failed: ${err instanceof Error ? err.message : String(err)}`,
      { level: 'warn' },
    )
    return null
  }
}

// In initUpstreamProxy():
const token = await readToken(tokenPath)  // string on heap
// ... pass to relay ...
const relay = await startUpstreamProxyRelay({ wsUrl, sessionId, token })
// ... delete file from disk ...
await unlink(tokenPath).catch(() => {})
// token string STILL on heap, referenced by relay

The token file at /run/ccr/session_token is deleted after reading, which removes the on-disk copy. But the in-memory copy persists for the entire lifetime of the relay connection. The setNonDumpable() call (discussed in Section 20.4) provides some protection against ptrace-based extraction, but only on Linux with the Bun runtime.

The Attack Surface

An attacker who can read the proxy process's memory can extract the session token and:

  1. Impersonate the session: Use the token to create a parallel connection to the bridge, intercepting or injecting messages.
  2. Escalate privileges: If the token grants access beyond the proxy's intended scope, the attacker inherits those permissions.
  3. Persist access: Even after the original session ends, the token may be valid for some time (depending on server-side expiry enforcement).

Attack vectors for memory access include:

Vector Platform Requirement
/proc/pid/mem Linux Same UID or CAP_SYS_PTRACE
ptrace(PTRACE_PEEKDATA) Linux Same UID (unless PR_SET_DUMPABLE=0)
Core dump All Process crash + core dump enabled
Container escape Linux Kernel vulnerability or misconfigured seccomp
Memory forensics All Physical access or VM snapshot

The Secure Patch: Buffer-Based Token Handling

The fix replaces string-based token handling with Buffer-based handling, enabling deterministic memory wiping:

// SECURE: upstreamproxy/upstreamproxy.ts

/**
 * Read token into a Buffer that can be zeroed after use.
 * JS strings are immutable — a string token stays on the heap until GC.
 * Buffer.fill(0) overwrites memory deterministically.
 */
async function readTokenAsBuffer(path: string): Promise<Buffer | null> {
  try {
    const buf = await readFile(path)  // Returns Buffer (no encoding = raw)
    return buf
  } catch (err) {
    if (isENOENT(err)) return null
    logForDebugging(
      `[upstreamproxy] token read failed: ${err instanceof Error ? err.message : String(err)}`,
      { level: 'warn' },
    )
    return null
  }
}

The relay initialization changes to use the Buffer and zero it after constructing the authentication header:

// SECURE: upstreamproxy/relay.ts — Buffer-based auth construction

interface RelayOptions {
  wsUrl: string
  sessionId: string
  token: Buffer  // Changed from string to Buffer
}

async function startUpstreamProxyRelay(opts: RelayOptions): Promise<Relay> {
  // Construct auth material using Buffers
  const sessionIdBuf = Buffer.from(opts.sessionId)
  const colonBuf = Buffer.from(':')

  // Concatenate sessionId:token as a single Buffer
  const rawAuth = Buffer.concat([sessionIdBuf, colonBuf, opts.token])

  // Base64 encode the auth material
  const authHeaderBuf = Buffer.from(
    'Basic ' + rawAuth.toString('base64')
  )

  // CRITICAL: Zero the raw credential components immediately
  rawAuth.fill(0)
  sessionIdBuf.fill(0)
  // Note: opts.token is zeroed by the caller after relay start

  const wsAuthBuf = Buffer.from('Bearer ')
  const wsAuthHeader = Buffer.concat([wsAuthBuf, opts.token])

  // ... establish WebSocket connection using authHeaderBuf ...

  // Expose cleanup for relay stop
  const zeroAuthBuffers = (): void => {
    authHeaderBuf.fill(0)
    wsAuthHeader.fill(0)
    wsAuthBuf.fill(0)
  }

  return {
    // ... relay interface ...
    stop: async () => {
      zeroAuthBuffers()
      // ... close WebSocket ...
    }
  }
}

And in the initialization function:

// SECURE: initUpstreamProxy — zero token after relay start
const tokenBuf = await readTokenAsBuffer(tokenPath)
if (!tokenBuf) {
  throw new Error('Session token not found')
}

try {
  const relay = await startUpstreamProxyRelay({
    wsUrl,
    sessionId,
    token: tokenBuf,
  })
  // Token is now copied into relay's auth headers
  // Zero the original Buffer
  tokenBuf.fill(0)

  // Delete the file from disk
  await unlink(tokenPath).catch(() => {})

  return relay
} catch (err) {
  // Zero token even on error path
  tokenBuf.fill(0)
  throw err
}

Limitations of the Buffer Approach

The Buffer-based approach has important limitations that must be acknowledged. These are not reasons to avoid the approach -- Buffer handling is strictly superior to string handling -- but they define the boundaries of what userspace code can achieve in a garbage-collected runtime.

  1. String copies in V8/JSC internals: When the Buffer's contents are used in string operations (e.g., toString('base64')), the engine may create internal string copies that cannot be zeroed from JavaScript. V8's string deduplication and interning features may keep copies of short strings in the string table indefinitely. This is a fundamental limitation of operating in a managed runtime.

  2. No GC control: Even with Buffers, JavaScript provides no mechanism to force garbage collection of intermediate objects created during the auth construction process. The global.gc() function exists in some runtimes with the --expose-gc flag, but it only suggests collection and does not guarantee immediate deallocation.

  3. JIT compiler optimizations: The JIT compiler may keep copies of values in registers or stack frames that are not accessible to Buffer.fill(0). V8's TurboFan and SparkPlug compilers may inline small string values into machine code, creating copies that persist in the code cache.

  4. OS memory management: The operating system may write heap pages to swap, creating persistent copies on disk. Even with mlock() (which prevents swapping), the kernel may create copies during page migration or compaction. On Linux, setting vm.swappiness=0 and using mlock() via FFI can mitigate this, but neither is foolproof.

  5. Speculative execution: On modern CPUs, speculative execution may load credential data into CPU caches where it can be observed via side-channel attacks (Spectre variants). This is beyond the scope of application-level mitigation.

Despite these limitations, the Buffer approach is strictly superior to string-based token handling because it eliminates the primary persistence vector -- the immutable string on the heap -- and provides deterministic zeroing of the main credential storage. The remaining vectors require kernel-level or hardware-level mitigations.

20.3 Proxy Credentials in Memory (V-31)

Finding V-31 (CWE-522, CVSS 4.4, MEDIUM) identified a related issue in the relay module where proxy authentication credentials are encoded as Base64 Basic Auth and stored in memory:

// VULNERABLE: upstreamproxy/relay.ts:161
const authHeader =
  'Basic ' + Buffer.from(`${opts.sessionId}:${opts.token}`).toString('base64')
const wsAuthHeader = `Bearer ${opts.token}`

Both authHeader and wsAuthHeader are JavaScript strings that persist on the heap for the relay's lifetime. The Buffer-based fix from Section 20.2 addresses this by keeping the auth material in Buffers that are explicitly zeroed on relay stop.

20.4 Cross-Platform Heap Protection: setNonDumpable() (V-44, V-45)

The Current Implementation

Finding V-44 (CWE-316, CVSS 2.5, LOW) identified that the setNonDumpable() function is platform-gated to only work on Linux with the Bun runtime:

// VULNERABLE: upstreamproxy/upstreamproxy.ts:226
function setNonDumpable(): void {
  if (process.platform !== 'linux' || typeof Bun === 'undefined') return
  try {
    const ffi = require('bun:ffi') as typeof import('bun:ffi')
    const lib = ffi.dlopen('libc.so.6', {
      prctl: {
        args: ['i32', 'i64', 'i64', 'i64', 'i64'],
        returns: 'i32',
      },
    })
    const PR_SET_DUMPABLE = 4
    const rc = lib.symbols.prctl(PR_SET_DUMPABLE, 0n, 0n, 0n, 0n)
    if (rc !== 0) {
      logForDebugging('[upstreamproxy] prctl(PR_SET_DUMPABLE, 0) failed', {
        level: 'warn',
      })
    }
  } catch (err) {
    logForDebugging(
      `[upstreamproxy] setNonDumpable failed: ${err instanceof Error ? err.message : String(err)}`,
      { level: 'warn' },
    )
  }
}

This function calls prctl(PR_SET_DUMPABLE, 0) via Bun's FFI, which prevents other processes from using ptrace() to attach to the proxy process and read its memory. This is an effective defense against the most common memory extraction vector on Linux.

However, the function is a complete no-op on:

  • macOS: All macOS users get no heap protection
  • Linux + Node.js: Users running Claude Code under Node.js instead of Bun get no protection
  • Windows: No protection (though the upstream proxy is primarily a Linux/CCR feature)

Finding V-45 (CWE-316, CVSS 3.2, INFO) elevates this to an architectural concern: the upstream proxy's heap protection is a Linux-only feature in a cross-platform tool.

The Secure Patch: Platform-Aware Protection

// SECURE: upstreamproxy/upstreamproxy.ts — cross-platform heap protection

/**
 * Attempt to make the current process non-dumpable.
 * 
 * Linux/Bun: prctl(PR_SET_DUMPABLE, 0) via FFI
 * Linux/Node: prctl via child_process (fallback)
 * macOS: PT_DENY_ATTACH via ptrace() (future)
 * 
 * Returns true if protection was successfully applied.
 */
function setNonDumpable(): boolean {
  if (process.platform === 'linux') {
    return setNonDumpableLinux()
  } else if (process.platform === 'darwin') {
    return setNonDumpableMacOS()
  } else {
    logForDebugging(
      `[upstreamproxy] Heap protection not available on ${process.platform}`,
      { level: 'warn' }
    )
    return false
  }
}

function setNonDumpableLinux(): boolean {
  // Prefer Bun FFI (fast, no subprocess)
  if (typeof Bun !== 'undefined') {
    try {
      const ffi = require('bun:ffi') as typeof import('bun:ffi')
      const lib = ffi.dlopen('libc.so.6', {
        prctl: {
          args: ['i32', 'i64', 'i64', 'i64', 'i64'],
          returns: 'i32',
        },
      })
      const PR_SET_DUMPABLE = 4
      const rc = lib.symbols.prctl(PR_SET_DUMPABLE, 0n, 0n, 0n, 0n)
      if (rc === 0) {
        logForDebugging('[upstreamproxy] PR_SET_DUMPABLE=0 set via Bun FFI')
        return true
      }
    } catch (err) {
      logForDebugging(
        `[upstreamproxy] Bun FFI failed: ${err instanceof Error ? err.message : String(err)}`,
        { level: 'warn' }
      )
    }
  }

  // Fallback: Node.js with node-ffi-napi (if available)
  try {
    const ffi = require('ffi-napi')
    const libc = ffi.Library('libc', {
      prctl: ['int', ['int', 'long', 'long', 'long', 'long']],
    })
    const PR_SET_DUMPABLE = 4
    const rc = libc.prctl(PR_SET_DUMPABLE, 0, 0, 0, 0)
    if (rc === 0) {
      logForDebugging('[upstreamproxy] PR_SET_DUMPABLE=0 set via node-ffi-napi')
      return true
    }
  } catch {
    // ffi-napi not available — log and continue
  }

  // Last resort: shell out to a helper
  try {
    const { execFileSync } = require('node:child_process')
    // Small C program compiled and cached at install time
    execFileSync('./bin/set-nondumpable', { timeout: 1000 })
    logForDebugging('[upstreamproxy] PR_SET_DUMPABLE=0 set via helper binary')
    return true
  } catch {
    logForDebugging(
      '[upstreamproxy] WARNING: Could not set PR_SET_DUMPABLE on Linux',
      { level: 'warn' }
    )
    return false
  }
}

function setNonDumpableMacOS(): boolean {
  // PT_DENY_ATTACH prevents debuggers from attaching to the process.
  // Note: This is a one-way operation — once set, it cannot be undone
  // for the lifetime of the process.
  //
  // macOS implementation requires a native addon or helper binary
  // because ptrace() is not available via standard FFI in most
  // JavaScript runtimes.

  logForDebugging(
    '[upstreamproxy] macOS heap protection: PT_DENY_ATTACH not yet implemented',
    { level: 'warn' }
  )

  // Alternative: Use macOS sandbox-exec to restrict debugging
  // This is a compensating control documented in the security model

  return false
}

The Helper Binary for Linux/Node.js

For environments where FFI is not available, a small C helper program can be compiled at install time:

// bin/set-nondumpable.c
// Compiled at npm install time: cc -o bin/set-nondumpable bin/set-nondumpable.c

#include <sys/prctl.h>
#include <stdio.h>

int main(void) {
    if (prctl(PR_SET_DUMPABLE, 0, 0, 0, 0) != 0) {
        perror("prctl");
        return 1;
    }
    printf("PR_SET_DUMPABLE=0 set successfully\n");
    return 0;
}

20.5 Memory Protection for Credential Handling Paths

Beyond the upstream proxy, several other code paths handle credential material that benefits from Buffer-based management. The goal is to establish a consistent pattern: every code path that touches credential material uses Buffers, and every Buffer is zeroed in a finally block.

Keychain Read/Write

The macOS keychain storage reads credentials as strings from the security command output:

// Current: String-based credential read
const result = execFileNoThrow('security', [
  'find-generic-password', '-a', username, '-w', '-s', serviceName
])
// result.stdout is a string — credential on heap as immutable string

The secure approach wraps the credential in a Buffer as early as possible:

// SECURE: Buffer-based credential read
const result = execFileNoThrow('security', [
  'find-generic-password', '-a', username, '-w', '-s', serviceName
])
if (result.exitCode === 0 && result.stdout) {
  // Convert to Buffer immediately, minimize string lifetime
  const credentialBuf = Buffer.from(result.stdout.trim())
  // result.stdout string will be GC'd eventually
  // But credentialBuf can be explicitly zeroed when done
  try {
    return processCredential(credentialBuf)
  } finally {
    credentialBuf.fill(0)
  }
}

OAuth Token Handling

OAuth tokens received from the API should follow the same pattern:

// SECURE: OAuth token Buffer management
interface SecureTokenHolder {
  /** Get token value as string (creates temporary copy) */
  toString(): string
  /** Zero the underlying Buffer */
  destroy(): void
  /** Check if token has been destroyed */
  isDestroyed: boolean
  /** Token age in milliseconds */
  ageMs: number
}

function createSecureToken(tokenString: string): SecureTokenHolder {
  const buf = Buffer.from(tokenString)
  let destroyed = false
  const createdAt = Date.now()

  return {
    toString() {
      if (destroyed) throw new Error('Token has been destroyed')
      return buf.toString('utf8')
    },
    destroy() {
      buf.fill(0)
      destroyed = true
    },
    get isDestroyed() {
      return destroyed
    },
    get ageMs() {
      return Date.now() - createdAt
    },
  }
}

Environment Variable Tokens

Environment variable tokens present a unique challenge: process.env.* always returns strings, and there is no mechanism in Node.js or Bun to zero the underlying C string storage. The best mitigation is to read the token once, store it in a Buffer, and delete the environment variable:

// SECURE: Minimize env var token lifetime
function extractEnvToken(envVar: string): Buffer | null {
  const value = process.env[envVar]
  if (!value) return null

  // Convert to Buffer immediately
  const buf = Buffer.from(value)

  // Delete the env var to reduce the number of string copies
  // Note: The original string may still exist in V8's string table
  delete process.env[envVar]

  return buf
}

This does not eliminate the env var string from memory (V8 may retain it), but it reduces the number of references and shortens the window of exposure.

20.6 Core Dump Protection

Even with PR_SET_DUMPABLE=0, a process crash can produce a core dump if the system is configured to generate them. Core dumps contain the complete process memory, including any credentials on the heap.

Disabling Core Dumps for the Proxy Process

// SECURE: Disable core dumps via setrlimit
function disableCoreDumps(): boolean {
  if (process.platform !== 'linux') return false

  if (typeof Bun !== 'undefined') {
    try {
      const ffi = require('bun:ffi') as typeof import('bun:ffi')
      const lib = ffi.dlopen('libc.so.6', {
        setrlimit: {
          args: ['i32', 'pointer'],
          returns: 'i32',
        },
      })

      const RLIMIT_CORE = 4
      // struct rlimit { rlim_t rlim_cur; rlim_t rlim_max; }
      const rlimit = new BigInt64Array([0n, 0n])
      const rc = lib.symbols.setrlimit(
        RLIMIT_CORE,
        ffi.ptr(rlimit)
      )

      if (rc === 0) {
        logForDebugging('[upstreamproxy] Core dumps disabled via setrlimit')
        return true
      }
    } catch (err) {
      logForDebugging(
        `[upstreamproxy] Failed to disable core dumps: ${err}`,
        { level: 'warn' }
      )
    }
  }

  return false
}

20.7 Secure Memory Wiping Patterns

The Wipe-After-Use Pattern

Every code path that handles credential material should follow this pattern:

// Pattern: Wipe-after-use for credential Buffers

async function withCredential<T>(
  credentialPath: string,
  operation: (credential: Buffer) => Promise<T>
): Promise<T> {
  const credential = await readFile(credentialPath)

  try {
    return await operation(credential)
  } finally {
    // ALWAYS zero, even if operation throws
    credential.fill(0)
  }
}

// Usage:
const result = await withCredential('/run/ccr/session_token', async (token) => {
  return await startRelay({ token })
})

The Credential Scope Guard

For synchronous operations, a scope guard ensures cleanup:

class CredentialScope {
  private buffers: Buffer[] = []
  private destroyed = false

  track(buf: Buffer): Buffer {
    if (this.destroyed) throw new Error('Scope already destroyed')
    this.buffers.push(buf)
    return buf
  }

  destroy(): void {
    for (const buf of this.buffers) {
      buf.fill(0)
    }
    this.buffers = []
    this.destroyed = true
  }
}

// Usage:
const scope = new CredentialScope()
try {
  const token = scope.track(Buffer.from(rawToken))
  const sessionId = scope.track(Buffer.from(rawSessionId))
  const auth = scope.track(
    Buffer.from(`Basic ${Buffer.concat([sessionId, Buffer.from(':'), token]).toString('base64')}`)
  )
  // ... use auth ...
} finally {
  scope.destroy()
}

# 2. Before wipe: search for canary in process memory
echo "Searching for canary in PID ${PID} (before wipe)..."
sleep 2
if grep -c 'CANARY_SECRET_VALUE' "/proc/${PID}/maps" 2>/dev/null || \
   strings "/proc/${PID}/mem" 2>/dev/null | grep -c 'CANARY_SECRET_VALUE'; then
  echo "FOUND: Canary present in memory (expected before wipe)"
fi

# 3. After wipe: search again
sleep 12
echo "Searching for canary in PID ${PID} (after wipe)..."
if strings "/proc/${PID}/mem" 2>/dev/null | grep -c 'CANARY_SECRET_VALUE'; then
  echo "FAIL: Canary still present after Buffer.fill(0)"
else
  echo "PASS: Canary not found after Buffer.fill(0)"
fi

kill "${PID}" 2>/dev/null

20.10 Dependency Chain Impact

The memory protection patches affect the Bridge/Remote Session Chain (Finding IDs: 12, 17, 18, 21, 22, 23, 28, 31, 42, 44, 45). The proxy token heap exposure (V-23) is a linchpin in this chain: if an attacker can extract the proxy token from memory, they can establish a parallel session to the bridge, effectively bypassing all other bridge security controls.

By converting to Buffer-based token handling and implementing multi-layer memory protection (Buffer.fill(0) + PR_SET_DUMPABLE + RLIMIT_CORE), the exposure window is reduced from the entire relay lifetime to the brief period during which the token is used for authentication construction.

These patches should be applied after the bridge security hardening from Chapters 16-17 and alongside the debug log sanitization from Chapter 18, as the logging statements in the proxy code must comply with the redaction requirements established there. As discussed in Chapter 3, Phase 6 encompasses these memory protection fixes as part of the Data Protection & Privacy remediation effort.

Summary

This chapter addressed three memory protection findings (V-23, V-44, V-45) and the related credential-in-memory finding (V-31). The key patches are:

  1. Buffer-based token handling (V-23): Replace string-based token reading with readTokenAsBuffer() that returns a Buffer capable of deterministic zeroing via Buffer.fill(0)
  2. Auth material management (V-31): Construct relay authentication headers using Buffers, zero intermediate values immediately, zero auth headers on relay stop
  3. Cross-platform heap protection (V-44): Extend setNonDumpable() with fallbacks for Node.js on Linux, document macOS gap, add platform-aware logging
  4. Core dump prevention: Disable core dumps via setrlimit(RLIMIT_CORE, 0) to prevent credential extraction from crash dumps
  5. Credential scope guard: Reusable pattern for tracking and zeroing all Buffer-based credentials within a code scope

The fundamental limitation remains: JavaScript's immutable strings create an unavoidable window of exposure. The Buffer-based approach minimizes this window and provides defense-in-depth through multiple protection layers, but it cannot eliminate the risk entirely in a garbage-collected runtime.
