Chapter 12: OAuth & Device Trust Hardening

Chapters 10 and 11 secured the JWT verification pipeline and the token refresh lifecycle. Tokens are now cryptographically verified via JWKS, bounded by clampTokenRefreshDelay, and tracked through a session-scoped lifecycle manager that eliminates immortal environment variable tokens. This chapter addresses two remaining authentication vulnerabilities that sit at the boundary between the client and the identity provider: the OAuth authorization code flow and the device trust mechanism.

Finding V-36: OAuth Callback Listener on Predictable Localhost Port (CWE-352, CVSS 4.3). The OAuth callback server binds to a fixed port on localhost, making it possible for other local processes to predict when and where the callback will arrive. While the existing PKCE state parameter prevents cross-site request forgery on the OAuth flow itself, the predictable port creates an unnecessary attack surface for local privilege escalation.

Finding V-34: Trusted Device Token Overridable via Environment Variable (CWE-473, CVSS 4.3). The readStoredToken() function in bridge/trustedDevice.ts gives unconditional precedence to CLAUDE_TRUSTED_DEVICE_TOKEN from the environment. This means any process that can set environment variables for the Claude Code process can override the trusted device identity --- bypassing keychain storage entirely.

Finding V-50: PKCE Implementation Verification (Positive Finding). The audit confirmed that the PKCE implementation in services/oauth/crypto.ts uses correct cryptographic primitives: 256-bit random verifiers, SHA-256 S256 challenges, and 256-bit state parameters. This section documents the existing strength and identifies hardening opportunities.

Before addressing specific vulnerabilities, we need to understand the complete OAuth flow as implemented in Claude Code. The flow follows RFC 6749 (OAuth 2.0) with the PKCE extension (RFC 7636):

The flow has three security-critical moments:

  1. Code challenge generation --- must be cryptographically strong to prevent authorization code interception
  2. Callback reception --- must verify state and only accept the expected callback
  3. Token exchange --- must use the original code_verifier to prove possession

PKCE: What the Audit Confirmed

Finding V-50 is a positive finding --- the PKCE implementation is correct:

// services/oauth/crypto.ts — VERIFIED CORRECT
export function generateCodeVerifier(): string {
  return base64URLEncode(randomBytes(32))  // 256-bit entropy
}

export function generateCodeChallenge(verifier: string): string {
  const hash = createHash('sha256')
  hash.update(verifier)
  return base64URLEncode(hash.digest())  // SHA-256 S256 method
}

export function generateState(): string {
  return base64URLEncode(randomBytes(32))  // 256-bit CSRF protection
}

This implementation is compliant with RFC 7636 Section 4.1: the verifier has at least 256 bits of entropy, the challenge uses S256 (not the weaker plain method), and the state parameter provides adequate CSRF protection. These primitives are correctly used --- but the flow around them has weaknesses.

12.2 The Predictable Port Vulnerability (CWE-352)

The Problem

The OAuth callback listener in services/oauth/auth-code-listener.ts binds to a deterministic port on localhost. While the exact port number is configurable, it defaults to a fixed value that is consistent across installations.

// services/oauth/auth-code-listener.ts — VULNERABLE
private handleRedirect(req: IncomingMessage, res: ServerResponse): void {
  const parsedUrl = new URL(
    req.url || '',
    `http://${req.headers.host || 'localhost'}`,
  )
  // ... process callback
}

The vulnerability is subtle: any other process running on the same machine that knows the port can:

  1. Race to bind the port first. If a malicious local process binds the callback port before Claude Code starts its listener, it receives the OAuth callback with the authorization code. The PKCE code_verifier prevents the attacker from exchanging the code (they do not have the verifier), but the authorization code exposure is still an information leak.

  2. Predict callback timing. A local process monitoring port activity can detect exactly when the OAuth flow is in progress, which is useful for timing-based attacks on the token exchange.

  3. Host header injection. The handleRedirect code constructs a URL using req.headers.host, which is client-controlled. While this specific usage does not create an exploitable vulnerability (the URL is parsed locally), it establishes a pattern where attacker-controlled headers influence URL construction.

Why PKCE Mitigates but Does Not Eliminate the Risk

The PKCE extension provides the primary defense: even if an attacker captures the authorization code from the callback, they cannot exchange it for tokens without the code_verifier, which never leaves the Claude Code process memory. This reduces the practical severity from HIGH to LOW.

However, PKCE does not protect against:

  • Authorization code replay against the legitimate client. If the attacker can also inject the captured code back into the legitimate callback (e.g., by racing), the legitimate client exchanges the code successfully, but the attacker now knows which authorization was granted.
  • Local denial of service. By occupying the callback port, the attacker prevents the OAuth flow from completing, forcing the user to retry or use alternative authentication methods.

The Fix: Ephemeral Port Selection

The remediation replaces the fixed port with an OS-assigned ephemeral port:

// services/oauth/auth-code-listener.ts — SECURE VERSION
import { createServer, IncomingMessage, ServerResponse, Server } from 'http'

interface CallbackListenerOptions {
  timeoutMs?: number
  allowedHost?: string
}

const DEFAULT_TIMEOUT_MS = 120_000  // 2 minutes
const ALLOWED_HOSTS = new Set(['localhost', '127.0.0.1', '[::1]'])

export class AuthCodeListener {
  private server: Server | null = null
  private assignedPort: number | null = null

  /**
   * Start the OAuth callback listener on an OS-assigned ephemeral port.
   * Returns the port number for inclusion in the authorization URL.
   */
  async start(options: CallbackListenerOptions = {}): Promise<number> {
    return new Promise((resolve, reject) => {
      this.server = createServer((req, res) => {
        this.handleRedirect(req, res)
      })

      // Bind to port 0: OS assigns an available ephemeral port
      this.server.listen(0, '127.0.0.1', () => {
        const addr = this.server!.address()
        if (typeof addr === 'object' && addr !== null) {
          this.assignedPort = addr.port
          resolve(this.assignedPort)
        } else {
          reject(new Error('Failed to determine assigned port'))
        }
      })

      this.server.on('error', reject)

      // Timeout: close listener if no callback received
      const timeout = options.timeoutMs ?? DEFAULT_TIMEOUT_MS
      setTimeout(() => {
        if (this.server?.listening) {
          this.stop()
          reject(new Error(`OAuth callback timeout after ${timeout}ms`))
        }
      }, timeout)
    })
  }

  /**
   * Handle the OAuth redirect callback.
   * Validates Host header against allowlist before processing.
   */
  private handleRedirect(
    req: IncomingMessage,
    res: ServerResponse,
  ): void {
    // Validate Host header
    const host = req.headers.host
    if (host) {
      const hostname = host.split(':')[0]
      if (!ALLOWED_HOSTS.has(hostname ?? '')) {
        res.writeHead(400, { 'Content-Type': 'text/plain' })
        res.end('Invalid host header')
        return
      }
    }

    // Construct URL using known-good base (never from request headers)
    const parsedUrl = new URL(
      req.url || '',
      `http://127.0.0.1:${this.assignedPort}`,
    )

    // ... process callback with state validation
  }

  /**
   * Stop the listener and release the port.
   */
  stop(): void {
    if (this.server) {
      this.server.close()
      this.server = null
      this.assignedPort = null
    }
  }
}

Key changes:

  1. Port 0 binding. Passing 0 to server.listen() causes the OS to assign a random available ephemeral port (typically in the 49152-65535 range). This eliminates port prediction --- each OAuth flow uses a different port.

  2. Host header validation. Instead of trusting the Host header for URL construction, we validate it against an allowlist (localhost, 127.0.0.1, [::1]). Requests with unexpected Host headers receive a 400 response.

  3. Known-good URL base. The URL is constructed using the known bound address (127.0.0.1:${this.assignedPort}) rather than the client-provided Host header. This eliminates the Host header injection vector entirely.

  4. Explicit timeout. A 2-minute timeout closes the listener if no callback arrives, preventing port squatting on the ephemeral port.

OAuth Redirect URI Registration

Ephemeral ports introduce a challenge: OAuth providers typically require pre-registered redirect URIs. Two patterns solve this:

Pattern 1: Loopback URI exception. RFC 8252 Section 7.3 specifies that OAuth providers SHOULD allow any port in loopback redirect URIs (http://127.0.0.1:*/callback). Most major providers implement this exception. The redirect URI registration uses http://127.0.0.1 without specifying a port, and the provider matches any port.

Pattern 2: Dynamic registration. If the provider does not support the loopback exception, the CLI can use OAuth 2.0 Dynamic Client Registration (RFC 7591) to register a new redirect URI for each flow. This adds a round-trip but ensures compatibility.

12.3 The Device Trust Override Vulnerability (CWE-473)

The Problem

The trusted device mechanism in bridge/trustedDevice.ts establishes persistent identity for the CLI installation. When a device is "trusted," subsequent operations skip certain verification steps. The vulnerability is in the token retrieval:

// bridge/trustedDevice.ts — VULNERABLE
const readStoredToken = memoize((): string | undefined => {
  // Env var takes precedence for testing/canary.
  const envToken = process.env.CLAUDE_TRUSTED_DEVICE_TOKEN
  if (envToken) {
    return envToken
  }
  return getSecureStorage().read()?.trustedDeviceToken
})

The comment says "for testing/canary," but the env var is available in all environments, not gated behind a feature flag. This means:

  1. Any process that can set environment variables for the Claude Code process can impersonate the device identity. On shared systems (CI runners, containers with shared env), one process can set CLAUDE_TRUSTED_DEVICE_TOKEN to impersonate another device's identity.

  2. The env var token bypasses keychain security. The macOS Keychain requires user authentication (password, Touch ID) to release stored secrets. The env var bypass means an attacker who cannot access the Keychain (because they do not have the user's password) can still override the device trust token.

  3. No expiry or validation. The env var token is memoized unconditionally --- it is read once and cached for the process lifetime. Even if the env var is later unset, the memoized value persists.

The Fix: Gated Override with Validation

The remediation gates the env var override behind a feature flag and adds validation for the override when permitted:

// bridge/trustedDevice.ts — SECURE VERSION
import { logForDebugging } from '../utils/debug.js'
import { getSecureStorage } from '../utils/secureStorage/index.js'
import { isFeatureEnabled } from '../services/featureGates.js'

interface DeviceTokenSource {
  token: string
  source: 'keychain' | 'env_var'
  validatedAt: number
}

/**
 * Read the trusted device token with source tracking and validation.
 *
 * Env var override is ONLY available when:
 * 1. The 'env_device_token_override' feature gate is enabled (server-controlled)
 * 2. The env var token passes JWT format validation (if JWT-formatted)
 * 3. The env var token is not expired (if JWT-formatted)
 *
 * This prevents local processes from silently overriding device identity.
 */
function readStoredTokenSecure(): DeviceTokenSource | undefined {
  const envToken = process.env.CLAUDE_TRUSTED_DEVICE_TOKEN

  if (envToken) {
    // Gate check: only allow env override when explicitly enabled
    if (!isFeatureEnabled('env_device_token_override')) {
      logForDebugging(
        '[trusted-device] CLAUDE_TRUSTED_DEVICE_TOKEN env var present but ' +
        'env_device_token_override feature gate is disabled. ' +
        'Using keychain token instead.',
        { level: 'warn' },
      )
      // Fall through to keychain
    } else {
      // Validate JWT-format tokens
      const validationResult = validateDeviceToken(envToken)
      if (!validationResult.valid) {
        logForDebugging(
          `[trusted-device] CLAUDE_TRUSTED_DEVICE_TOKEN env var ` +
          `failed validation: ${validationResult.reason}. ` +
          `Using keychain token instead.`,
          { level: 'warn' },
        )
        // Fall through to keychain
      } else {
        logForDebugging(
          '[trusted-device] Using device token from env var ' +
          '(env_device_token_override gate enabled)',
          { level: 'warn' },
        )
        return {
          token: envToken,
          source: 'env_var',
          validatedAt: Date.now(),
        }
      }
    }
  }

  // Default path: read from secure storage
  const stored = getSecureStorage().read()?.trustedDeviceToken
  if (!stored) return undefined

  return {
    token: stored,
    source: 'keychain',
    validatedAt: Date.now(),
  }
}

/**
 * Validate a device token from the environment variable.
 * - JWT tokens: check format, decode payload, verify not expired
 * - Opaque tokens: accept if non-empty string
 */
function validateDeviceToken(
  token: string,
): { valid: true } | { valid: false; reason: string } {
  if (!token || token.trim().length === 0) {
    return { valid: false, reason: 'empty token' }
  }

  // JWT-format validation
  if (token.startsWith('eyJ')) {
    try {
      const parts = token.split('.')
      if (parts.length !== 3) {
        return { valid: false, reason: 'malformed JWT (expected 3 parts)' }
      }

      const payload = JSON.parse(
        Buffer.from(parts[1]!, 'base64url').toString('utf8'),
      ) as { exp?: number }

      if (payload.exp && payload.exp * 1000 < Date.now()) {
        return { valid: false, reason: 'JWT expired' }
      }
    } catch {
      return { valid: false, reason: 'JWT decode failed' }
    }
  }

  return { valid: true }
}

Key changes:

  1. Feature gate. The env_device_token_override gate is server-controlled (via GrowthBook or equivalent). In production, this gate is disabled. Enterprise deployments that need env var override for their specific use case can request gate enablement.

  2. Expiry validation. JWT-formatted device tokens from the env var are checked for expiry. Expired tokens fall through to the keychain, preventing stale env vars from overriding fresh keychain tokens.

  3. Source tracking. The DeviceTokenSource type records whether the token came from the keychain or the env var, enabling audit trail and source-aware error handling (following the pattern from Chapter 11).

  4. Warning logs. Every env var usage or rejection is logged at warn level, creating a clear audit trail. Security teams can monitor for unexpected env var override attempts.

Removing Memoization

The original code used memoize() to cache the token read, meaning the env var was only read once per process. The secure version reads fresh on each call, enabling:

  • Detection of mid-process environment changes
  • Immediate effect of feature gate changes
  • Fresh expiry checks on JWT-formatted tokens

The performance cost is negligible: reading an env var is a single hash table lookup in the process, and the keychain read is already cached by the secure storage layer.

12.4 PKCE S256 Strengthening

While Finding V-50 confirmed that the PKCE implementation is cryptographically correct, there are hardening opportunities that strengthen the overall OAuth flow.

Verifier Length Validation

RFC 7636 Section 4.1 requires code verifiers to be between 43 and 128 characters. The current implementation generates a 43-character verifier (32 bytes base64url-encoded), which meets the minimum. Adding explicit length validation prevents accidental shortening:

// services/oauth/crypto.ts — HARDENED

const CODE_VERIFIER_MIN_LENGTH = 43
const CODE_VERIFIER_MAX_LENGTH = 128

export function generateCodeVerifier(): string {
  const verifier = base64URLEncode(randomBytes(32))

  // Defense-in-depth: verify the output meets RFC 7636 requirements
  if (
    verifier.length < CODE_VERIFIER_MIN_LENGTH ||
    verifier.length > CODE_VERIFIER_MAX_LENGTH
  ) {
    throw new Error(
      `Generated code verifier length ${verifier.length} outside ` +
      `RFC 7636 range [${CODE_VERIFIER_MIN_LENGTH}, ${CODE_VERIFIER_MAX_LENGTH}]`,
    )
  }

  return verifier
}

/**
 * Validate that the code challenge method is S256, not plain.
 * The 'plain' method transmits the verifier as the challenge,
 * which defeats PKCE's security if the authorization request
 * is intercepted.
 */
export function assertS256Method(method: string): void {
  if (method !== 'S256') {
    throw new Error(
      `PKCE challenge method must be S256, got: ${method}. ` +
      'The "plain" method is insecure and not permitted.',
    )
  }
}

State Parameter Binding

The state parameter prevents CSRF by binding the authorization request to the callback. The current implementation generates a random state and validates it on callback. We strengthen this by binding the state to the session:

// services/oauth/crypto.ts — State binding

/**
 * Generate a state parameter that is bound to the session context.
 * This prevents state reuse across different sessions or machines.
 *
 * State = base64url(random(32) || SHA-256(sessionContext))
 * The random component ensures uniqueness.
 * The session component prevents cross-session replay.
 */
export function generateBoundState(sessionContext: {
  machineId: string
  processId: number
  timestamp: number
}): string {
  const random = randomBytes(32)
  const contextHash = createHash('sha256')
    .update(JSON.stringify(sessionContext))
    .digest()

  // Combine: 32 bytes random + 32 bytes context hash
  const combined = Buffer.concat([random, contextHash])
  return base64URLEncode(combined)
}

/**
 * Validate a state parameter against the expected session context.
 */
export function validateBoundState(
  receivedState: string,
  expectedState: string,
): boolean {
  // Constant-time comparison to prevent timing attacks
  if (receivedState.length !== expectedState.length) return false

  const a = Buffer.from(receivedState)
  const b = Buffer.from(expectedState)

  return timingSafeEqual(a, b)
}

The timingSafeEqual comparison is critical: without it, a timing side-channel could allow an attacker to discover the expected state value byte-by-byte by measuring response times.

    // Should fall through to keychain (expired JWT ignored)
    expect(result?.source).not.toBe('env_var')

    delete process.env.CLAUDE_TRUSTED_DEVICE_TOKEN
  })

  it('accepts valid JWT from env var when gate enabled', () => {
    const validJwt = createValidJwt({ exp: futureTimestamp() })
    process.env.CLAUDE_TRUSTED_DEVICE_TOKEN = validJwt
    mockFeatureGate('env_device_token_override', true)

    const result = readStoredTokenSecure()
    expect(result?.source).toBe('env_var')

    delete process.env.CLAUDE_TRUSTED_DEVICE_TOKEN
  })
})

12.10 Key Takeaways

  1. Ephemeral ports eliminate an entire class of local attacks. Using port 0 with OS-assigned ephemeral ports makes port prediction infeasible. Combined with PKCE, the OAuth callback is protected against both remote CSRF and local port racing.

  2. Environment variable overrides for security-critical values must be gated. The "testing convenience" of CLAUDE_TRUSTED_DEVICE_TOKEN env var becomes a privilege escalation vector in production. Feature gates make the override available when explicitly needed (enterprise testing) and disabled by default.

  3. Host headers are attacker-controlled. Never use req.headers.host to construct security-sensitive URLs. Use the known-good server address (from server.address()) instead.

  4. PKCE is correct but incomplete. Cryptographically sound PKCE protects the authorization code exchange, but does not protect against port-level attacks, timing side-channels in state comparison, or device identity override. Defense-in-depth across multiple layers is required.

  5. Constant-time comparison prevents subtle information leaks. Using timingSafeEqual for state parameter validation eliminates timing side-channels that could allow byte-by-byte state discovery. This is a small code change with significant security impact.

  6. Audit logging is a feature, not overhead. Every env var override attempt, rejected Host header, and feature gate decision is logged. These logs are the security team's first indicator of attack attempts.
