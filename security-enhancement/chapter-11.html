Chapter 11: Token Refresh Hardening

Chapter 10 established JWT signature verification as the foundation for trustworthy token handling. With signatures validated via JWKS public keys and exp claims bounded by clampTokenRefreshDelay, the system can now distinguish legitimate tokens from forgeries. But signature verification alone does not address a critical gap in the token lifecycle: tokens sourced from environment variables bypass the entire refresh pipeline and persist indefinitely.

This chapter addresses CWE-613 --- Insufficient Session Expiration (CVSS 6.5), specifically Finding V-13: environment variable tokens that never expire or refresh. In Claude Code's utils/auth.ts, tokens provided via CLAUDE_CODE_OAUTH_TOKEN receive { refreshToken: null, expiresAt: null }, causing isTokenExpired() to always return false and checkAndRefreshOAuthTokenIfNeeded() to skip refresh entirely. The result: a revoked token continues working client-side until the server rejects it with a 401, at which point the error handling provides no guidance about the env var source.

The fix requires bounded refresh delays with MIN_REFRESH_DELAY_MS and MAX_TOKEN_LIFETIME_MS, token rotation for environment variable overrides, and session-scoped token lifecycle management that tracks token provenance from issuance through expiration.

11.1 The Vulnerability: Immortal Environment Variable Tokens

In production deployments, Claude Code accepts OAuth tokens from three sources: interactive OAuth flow, cached credentials in secure storage, and environment variables. The first two sources include refresh tokens and expiration timestamps. The third source --- environment variables --- includes neither.

The Vulnerable Code Path

// utils/auth.ts — lines 1260-1284 (VULNERABLE)

function getTokenFromEnvironment(): OAuthCredentials | null {
  const envToken = process.env.CLAUDE_CODE_OAUTH_TOKEN
  if (!envToken) return null

  return {
    accessToken: envToken,
    refreshToken: null,    // No refresh mechanism
    expiresAt: null,       // Never expires client-side
  }
}

function isTokenExpired(creds: OAuthCredentials): boolean {
  if (creds.expiresAt === null) return false  // null = immortal
  return Date.now() > creds.expiresAt
}

async function checkAndRefreshOAuthTokenIfNeeded(
  creds: OAuthCredentials,
): Promise<OAuthCredentials> {
  if (!isTokenExpired(creds)) return creds

  if (!creds.refreshToken) {
    // Env var tokens hit this path — no refresh possible
    throw new AuthError('Token expired and no refresh token available')
  }

  return await refreshOAuthToken(creds.refreshToken)
}

The logic chain is clear:

  1. getTokenFromEnvironment() sets expiresAt: null
  2. isTokenExpired() returns false for null expiry --- the token never expires
  3. checkAndRefreshOAuthTokenIfNeeded() sees the token as valid and returns immediately
  4. The token is used until the server returns 401, with no proactive expiry check

Why This Matters

Environment variable tokens are the primary authentication mechanism in three critical deployment contexts:

CI/CD Pipelines. Automated builds set CLAUDE_CODE_OAUTH_TOKEN from a secrets manager (GitHub Actions secrets, AWS Secrets Manager, etc.). If the token is revoked server-side but the CI/CD job is long-running, the job continues sending requests with the revoked token until the 401 triggers failure. In pipelines that batch multiple operations, partial completion with a revoked token can leave artifacts in an inconsistent state.

Containerized Deployments. Docker containers running Claude Code receive tokens via environment variables. Container orchestrators like Kubernetes may restart containers with the same token for weeks or months. If the token is compromised, server-side revocation is the only defense --- but the client has no mechanism to detect revocation proactively.

Developer Workstations. Developers who set CLAUDE_CODE_OAUTH_TOKEN in their shell profile have tokens that persist across sessions indefinitely. If the developer's machine is compromised, the attacker obtains an immortal token that the developer may not think to rotate.

11.2 The Fix: Bounded Token Lifecycle

The remediation has four components: maximum token age for env var tokens, periodic token introspection, improved 401 error handling with source awareness, and session-scoped lifecycle management.

Component 1: Maximum Token Age

The simplest and highest-impact fix: assign an expiresAt to environment variable tokens instead of null. This forces periodic re-evaluation even when no refresh token is available.

// utils/auth.ts — SECURE VERSION

/** Maximum age for env var tokens before re-validation is required */
const ENV_TOKEN_MAX_AGE_MS = 24 * 60 * 60 * 1000  // 24 hours

/** Minimum age — prevents overly aggressive re-validation */
const ENV_TOKEN_MIN_AGE_MS = 60 * 60 * 1000  // 1 hour

/** Introspection interval for env var tokens */
const TOKEN_INTROSPECTION_INTERVAL_MS = 30 * 60 * 1000  // 30 minutes

interface TokenMetadata {
  source: 'oauth_flow' | 'secure_storage' | 'env_var'
  createdAt: number
  lastIntrospection: number | null
  introspectionFailures: number
}

function getTokenFromEnvironment(): (OAuthCredentials & { _meta: TokenMetadata }) | null {
  const envToken = process.env.CLAUDE_CODE_OAUTH_TOKEN
  if (!envToken) return null

  const now = Date.now()

  return {
    accessToken: envToken,
    refreshToken: null,
    expiresAt: now + ENV_TOKEN_MAX_AGE_MS,  // Expires in 24h
    _meta: {
      source: 'env_var',
      createdAt: now,
      lastIntrospection: null,
      introspectionFailures: 0,
    },
  }
}

The 24-hour maximum age is a deliberate trade-off between security and usability:

  • Shorter (1 hour): More secure, but causes frequent interruptions in long CI/CD runs. Developers re-exporting tokens constantly is a usability burden that leads to workarounds (longer-lived tokens from the secrets manager, defeating the purpose).
  • 24 hours: Aligns with common CI/CD job durations. Most pipelines complete within hours, so a 24-hour window covers virtually all legitimate use cases while ensuring daily rotation.
  • Longer (7 days): Reduces friction but creates a week-long window where a revoked token remains active client-side.

Component 2: Token Introspection

For tokens that cannot be refreshed (no refreshToken), we add periodic introspection --- a lightweight server call that checks whether the token is still valid:

// utils/auth.ts — Token introspection

const MAX_INTROSPECTION_FAILURES = 3
const INTROSPECTION_TIMEOUT_MS = 5_000

interface IntrospectionResponse {
  active: boolean
  exp?: number
  scope?: string
}

/**
 * Check whether a token is still valid via the introspection endpoint.
 * Returns true if the token is active, false if revoked or expired.
 * Returns null if the introspection check itself fails (network error, timeout).
 */
async function introspectToken(
  accessToken: string,
): Promise<boolean | null> {
  try {
    const controller = new AbortController()
    const timeout = setTimeout(
      () => controller.abort(),
      INTROSPECTION_TIMEOUT_MS,
    )

    const response = await fetch(getIntrospectionUrl(), {
      method: 'POST',
      signal: controller.signal,
      headers: {
        'Content-Type': 'application/x-www-form-urlencoded',
        'Authorization': `Bearer ${accessToken}`,
      },
      body: new URLSearchParams({ token: accessToken }),
    })

    clearTimeout(timeout)

    if (!response.ok) return null

    const data: IntrospectionResponse = await response.json()
    return data.active
  } catch {
    return null  // Network failure — inconclusive
  }
}

/**
 * Perform periodic introspection for env var tokens.
 * Called from checkAndRefreshOAuthTokenIfNeeded() when the token
 * source is 'env_var' and introspection interval has elapsed.
 */
async function maybeIntrospect(
  creds: OAuthCredentials & { _meta: TokenMetadata },
): Promise<'valid' | 'revoked' | 'inconclusive'> {
  const now = Date.now()
  const timeSinceLastCheck = creds._meta.lastIntrospection
    ? now - creds._meta.lastIntrospection
    : Infinity

  if (timeSinceLastCheck < TOKEN_INTROSPECTION_INTERVAL_MS) {
    return 'valid'  // Too soon to check again
  }

  const result = await introspectToken(creds.accessToken)

  if (result === true) {
    creds._meta.lastIntrospection = now
    creds._meta.introspectionFailures = 0
    return 'valid'
  }

  if (result === false) {
    return 'revoked'
  }

  // Inconclusive — network failure
  creds._meta.introspectionFailures++
  if (creds._meta.introspectionFailures >= MAX_INTROSPECTION_FAILURES) {
    // Too many consecutive failures — treat as suspicious
    return 'revoked'
  }

  return 'inconclusive'
}

The introspection endpoint follows RFC 7662 (OAuth 2.0 Token Introspection). The MAX_INTROSPECTION_FAILURES threshold of 3 prevents a network partition from immediately invalidating a legitimate session while ensuring that persistent connectivity issues (which could indicate a MITM blocking revocation checks) eventually force re-authentication.

Component 3: Source-Aware Error Handling

When a 401 response arrives, the current error handling provides a generic "Token expired" message. With token source metadata, we can provide actionable guidance:

// utils/auth.ts — Source-aware 401 handling

async function handle401Response(
  creds: OAuthCredentials & { _meta?: TokenMetadata },
): Promise<never> {
  const source = creds._meta?.source ?? 'unknown'

  switch (source) {
    case 'env_var':
      throw new AuthError(
        'Your CLAUDE_CODE_OAUTH_TOKEN has been revoked or expired. ' +
        'Please provide a new token via the environment variable.\n' +
        'Tip: For CI/CD, use short-lived tokens (1h max). ' +
        'See: https://docs.anthropic.com/claude-code/auth#ci-cd',
      )

    case 'secure_storage':
      throw new AuthError(
        'Your cached credentials have expired. ' +
        'Run `claude login` to re-authenticate.',
      )

    case 'oauth_flow':
      throw new AuthError(
        'Your session token has been revoked. ' +
        'This may indicate a security event. ' +
        'Run `claude login` to re-authenticate.',
      )

    default:
      throw new AuthError(
        'Authentication failed. Run `claude login` to re-authenticate.',
      )
  }
}

The error message for env_var tokens explicitly recommends short-lived tokens for CI/CD. This is a security nudge: developers who encounter this error learn the correct pattern (short-lived tokens) rather than simply re-exporting the same long-lived token.

Component 4: Session-Scoped Lifecycle Management

The final component integrates all of the above into a unified lifecycle manager that tracks tokens from creation through expiration:

// utils/tokenLifecycle.ts — NEW FILE

import { createHash } from 'crypto'

interface TokenLifecycleEntry {
  fingerprint: string
  source: 'oauth_flow' | 'secure_storage' | 'env_var'
  createdAt: number
  expiresAt: number
  lastUsed: number
  lastIntrospection: number | null
  refreshCount: number
  introspectionFailures: number
}

class TokenLifecycleManager {
  private tokens: Map<string, TokenLifecycleEntry> = new Map()

  /**
   * Register a token in the lifecycle manager.
   * The token is identified by its SHA-256 fingerprint (first 16 hex chars).
   */
  register(
    token: string,
    source: TokenLifecycleEntry['source'],
    expiresAt: number,
  ): string {
    const fingerprint = this.fingerprint(token)

    this.tokens.set(fingerprint, {
      fingerprint,
      source,
      createdAt: Date.now(),
      expiresAt,
      lastUsed: Date.now(),
      lastIntrospection: null,
      refreshCount: 0,
      introspectionFailures: 0,
    })

    return fingerprint
  }

  /**
   * Record that a token was used for an API call.
   */
  markUsed(fingerprint: string): void {
    const entry = this.tokens.get(fingerprint)
    if (entry) {
      entry.lastUsed = Date.now()
    }
  }

  /**
   * Record that a token was refreshed (new token replaces old).
   */
  recordRefresh(
    oldFingerprint: string,
    newToken: string,
    newExpiresAt: number,
  ): string {
    const oldEntry = this.tokens.get(oldFingerprint)
    const newFingerprint = this.fingerprint(newToken)

    this.tokens.set(newFingerprint, {
      fingerprint: newFingerprint,
      source: oldEntry?.source ?? 'oauth_flow',
      createdAt: Date.now(),
      expiresAt: newExpiresAt,
      lastUsed: Date.now(),
      lastIntrospection: null,
      refreshCount: (oldEntry?.refreshCount ?? 0) + 1,
      introspectionFailures: 0,
    })

    // Remove old token entry
    if (oldFingerprint !== newFingerprint) {
      this.tokens.delete(oldFingerprint)
    }

    return newFingerprint
  }

  /**
   * Check if a token needs proactive renewal.
   * Returns the reason for renewal or null if the token is still good.
   */
  needsRenewal(fingerprint: string): string | null {
    const entry = this.tokens.get(fingerprint)
    if (!entry) return 'unknown token'

    const now = Date.now()

    // Hard expiry
    if (now >= entry.expiresAt) {
      return `expired ${Math.round((now - entry.expiresAt) / 1000)}s ago`
    }

    // Approaching expiry (within 10% of lifetime)
    const lifetime = entry.expiresAt - entry.createdAt
    const remaining = entry.expiresAt - now
    if (remaining < lifetime * 0.1) {
      return `${Math.round(remaining / 1000)}s remaining (within 10% threshold)`
    }

    // Too many introspection failures
    if (entry.introspectionFailures >= MAX_INTROSPECTION_FAILURES) {
      return `${entry.introspectionFailures} consecutive introspection failures`
    }

    return null  // Token is healthy
  }

  /**
   * Get lifecycle statistics for debugging.
   * Uses fingerprints — never exposes raw tokens.
   */
  getStats(): Record<string, unknown>[] {
    return Array.from(this.tokens.values()).map(entry => ({
      fingerprint: entry.fingerprint,
      source: entry.source,
      ageMinutes: Math.round((Date.now() - entry.createdAt) / 60_000),
      remainingMinutes: Math.round(
        Math.max(0, entry.expiresAt - Date.now()) / 60_000,
      ),
      refreshCount: entry.refreshCount,
      introspectionFailures: entry.introspectionFailures,
    }))
  }

  private fingerprint(token: string): string {
    return createHash('sha256').update(token).digest('hex').slice(0, 16)
  }
}

export const tokenLifecycle = new TokenLifecycleManager()

11.3 The Hardened Refresh Pipeline

With all four components integrated, the token refresh pipeline becomes provenance-aware and proactively expires all tokens regardless of source:

// utils/auth.ts — HARDENED checkAndRefreshOAuthTokenIfNeeded()

async function checkAndRefreshOAuthTokenIfNeeded(
  creds: OAuthCredentials & { _meta?: TokenMetadata },
): Promise<OAuthCredentials> {
  const source = creds._meta?.source ?? 'unknown'

  // Step 1: Check hard expiry (now applies to env var tokens too)
  if (isTokenExpired(creds)) {
    if (creds.refreshToken) {
      // Standard OAuth refresh
      return await refreshOAuthToken(creds.refreshToken)
    }

    if (source === 'env_var') {
      // Re-read from environment (may have been rotated)
      const fresh = getTokenFromEnvironment()
      if (fresh && fresh.accessToken !== creds.accessToken) {
        return fresh  // Token was rotated in the environment
      }
    }

    // No refresh mechanism and token expired
    await handle401Response(creds)
  }

  // Step 2: Periodic introspection for env var tokens
  if (source === 'env_var' && creds._meta) {
    const status = await maybeIntrospect(creds as OAuthCredentials & { _meta: TokenMetadata })

    if (status === 'revoked') {
      await handle401Response(creds)
    }
    // 'inconclusive' — continue with caution (failure counter incremented)
    // 'valid' — proceed normally
  }

  // Step 3: Proactive renewal check via lifecycle manager
  const fingerprint = tokenLifecycle.register(
    creds.accessToken,
    source as TokenLifecycleEntry['source'],
    creds.expiresAt ?? Date.now() + ENV_TOKEN_MAX_AGE_MS,
  )

  const renewalReason = tokenLifecycle.needsRenewal(fingerprint)
  if (renewalReason && creds.refreshToken) {
    logForDebugging(`Proactive token renewal: ${renewalReason}`)
    return await refreshOAuthToken(creds.refreshToken)
  }

  return creds
}

Token Re-Read on Expiry

Notice the env var re-read in Step 1: when an env var token expires, the system re-reads process.env.CLAUDE_CODE_OAUTH_TOKEN. If the value has changed (e.g., a sidecar process rotated it, or the user re-exported a new token), the fresh token is used. This enables a rotation pattern for CI/CD:

11.4 Bounded Refresh Delays

Chapter 10 introduced clampTokenRefreshDelay with bounds of [10 seconds, 24 hours]. This section expands on how those bounds interact with the token lifecycle for each source type:

Token Source MIN_REFRESH_DELAY MAX_TOKEN_LIFETIME Rationale
OAuth flow (interactive) 10s 24h Server controls expiry via expires_in; clamp is safety net
Secure storage (cached) 10s 24h Same as OAuth flow; refresh token available
Environment variable 10s 24h No refresh token; forces re-read of env var at expiry
Bridge session JWT 10s 24h Cross-validated with clampTokenRefreshDelay (Chapter 10)

The 10-second minimum applies uniformly because the attack vector (tight refresh loop from near-past exp) is source-independent. The 24-hour maximum is also uniform: regardless of what the server claims, the client will not wait more than 24 hours before attempting to refresh or re-validate.

Why Not Per-Source Maximums?

An alternative design uses shorter maximums for env var tokens (e.g., 1 hour) and longer maximums for OAuth tokens (e.g., 7 days). We rejected this because:

  1. Complexity breeds bugs. Per-source timeout logic creates more code paths to test and more opportunities for misconfiguration. A single MAX_TOKEN_LIFETIME_MS is easier to audit.

  2. The server already controls OAuth token lifetime. For OAuth tokens with refresh capability, the server's expires_in drives refresh scheduling. The 24-hour maximum is a safety net, not the normal operating point. Most OAuth tokens refresh within 1-4 hours.

  3. Env var tokens need the same ceiling. The 24-hour ceiling for env var tokens aligns with common secrets rotation policies. Making it shorter penalizes legitimate long-running CI jobs; making it longer undermines the security goal.

11.5 Token Rotation for Environment Variable Overrides

Beyond the env var re-read on expiry, we implement explicit token rotation guidance and detection:

// utils/auth.ts — Token rotation detection

interface RotationState {
  currentFingerprint: string
  previousFingerprints: string[]
  rotationCount: number
  lastRotation: number
}

const rotationState: Map<string, RotationState> = new Map()

/**
 * Detect and record token rotation in environment variables.
 * Called when a fresh env var token differs from the current one.
 */
function recordTokenRotation(
  envName: string,
  oldToken: string,
  newToken: string,
): void {
  const oldFp = createHash('sha256').update(oldToken).digest('hex').slice(0, 16)
  const newFp = createHash('sha256').update(newToken).digest('hex').slice(0, 16)

  const state = rotationState.get(envName) ?? {
    currentFingerprint: oldFp,
    previousFingerprints: [],
    rotationCount: 0,
    lastRotation: 0,
  }

  state.previousFingerprints.push(state.currentFingerprint)
  // Keep last 10 fingerprints for audit trail
  if (state.previousFingerprints.length > 10) {
    state.previousFingerprints.shift()
  }

  state.currentFingerprint = newFp
  state.rotationCount++
  state.lastRotation = Date.now()

  rotationState.set(envName, state)

  logForDebugging(
    `[auth] Token rotation detected for ${envName}: ` +
    `fingerprint ${oldFp} -> ${newFp} ` +
    `(rotation #${state.rotationCount})`,
  )
}

Detecting Stale Tokens

The rotation tracker also enables detection of tokens that have not been rotated when they should have been:

/**
 * Check if an env var token appears stale (has been in use
 * for longer than the recommended maximum without rotation).
 */
function isTokenStale(envName: string): boolean {
  const state = rotationState.get(envName)
  if (!state) return false

  const timeSinceRotation = Date.now() - state.lastRotation
  const STALE_THRESHOLD_MS = 7 * 24 * 60 * 60 * 1000  // 7 days

  return timeSinceRotation > STALE_THRESHOLD_MS
}

When a token is detected as stale, the system emits a warning (not an error) in the debug log. This creates an audit trail for security reviews without blocking legitimate usage.

CI/CD Token Lifecycle Best Practices

The token rotation mechanism enables several deployment patterns that security teams should recommend to their organizations:

GitHub Actions with OIDC. The preferred pattern for GitHub-hosted runners. Instead of storing a long-lived CLAUDE_CODE_OAUTH_TOKEN in GitHub Secrets, configure GitHub Actions OIDC to exchange a short-lived OIDC token for a Claude Code access token on each workflow run. The access token expires with the workflow, and no long-lived secrets are stored.

Self-Hosted Runners with Vault. For self-hosted CI runners, HashiCorp Vault's dynamic secrets engine issues a unique token per job with a configurable TTL (typically 1 hour). The Claude Code CLI uses the token until it expires, then re-reads the environment variable for the next Vault-issued token.

The common thread across all patterns: the token lifetime should match the task lifetime. A CI job that takes 30 minutes needs a 1-hour token, not a 30-day token. The 24-hour maximum in ENV_TOKEN_MAX_AGE_MS provides a safety net, but the correct pattern is to issue tokens with the shortest practical lifetime from the source.

Introspection Security Considerations

The token introspection endpoint itself becomes a potential target. An attacker who can call the introspection endpoint can probe whether arbitrary tokens are valid. RFC 7662 Section 4 addresses this by requiring the introspection endpoint to authenticate the caller --- the introspection request must include a valid token or client credential.

Our implementation sends the token-under-test as both the Bearer credential and the introspection target. This means a revoked token cannot be used to introspect itself (the Bearer authentication fails first). However, it also means we cannot introspect tokens that have already been rejected by the server's authentication layer --- which is the correct behavior, since a token rejected by the server is definitively invalid.

The MAX_INTROSPECTION_FAILURES threshold of 3 deserves security analysis. A man-in-the-middle who can selectively block introspection responses (while allowing API calls to succeed) could prevent the client from detecting server-side revocation. The 3-failure threshold means the MITM must sustain the block for 90 minutes (3 * 30-minute intervals) before the client treats the token as revoked. During this window, the revoked token continues to be used for API calls. This is an acceptable trade-off: the alternative --- treating a single introspection failure as revocation --- would cause false-positive lockouts during transient network issues.

11.7 The isTokenExpired Fix

The most impactful single-line change in this chapter:

// BEFORE (VULNERABLE)
function isTokenExpired(creds: OAuthCredentials): boolean {
  if (creds.expiresAt === null) return false  // null = never expires
  return Date.now() > creds.expiresAt
}

// AFTER (SECURE)
function isTokenExpired(creds: OAuthCredentials): boolean {
  if (creds.expiresAt === null) {
    // Tokens without explicit expiry are treated as expired.
    // This forces re-validation for env var tokens and surfaces
    // bugs in credential creation that fail to set expiresAt.
    return true
  }
  return Date.now() > creds.expiresAt
}

Changing the default from "null means immortal" to "null means expired" is a fundamental shift in the security posture. Under the new semantics:

  • Correctly-created tokens always have expiresAt set, so this change does not affect them.
  • Env var tokens now have expiresAt = now + 24h (from Component 1), so they never reach the null check.
  • Buggy token creation that forgets to set expiresAt now fails safe (token treated as expired) rather than failing dangerous (token treated as immortal).

This is the principle of fail-closed design: when a security-relevant value is missing, assume the restrictive interpretation.

11.10 Deployment Sequence

The changes in this chapter should be deployed in a specific order that minimizes disruption:

Phase 1: Deploy isTokenExpired null-means-expired change. This is the highest-impact single change. Combined with the expiresAt assignment in getTokenFromEnvironment(), it eliminates immortal tokens. Deploy these two changes together.

Phase 2: Deploy token introspection. The introspection endpoint requires server-side support. Coordinate with the authentication team to ensure the /v1/token/validate endpoint is available before enabling client-side introspection. Start with a 60-minute introspection interval and tighten to 30 minutes after confirming acceptable load.

Phase 3: Deploy source-aware error handling. This is purely a UX improvement that helps developers fix authentication issues faster. It can deploy independently of the other phases.

Phase 4: Deploy lifecycle manager. The full TokenLifecycleManager provides the audit trail and proactive renewal features. This is the most complex component and benefits from the stability of Phases 1-3 before deployment.

Chapter 12 will extend this token lifecycle work to the OAuth and device trust layers, addressing the predictable OAuth callback port (CWE-352), the environment variable override for trusted device tokens (CWE-473), and PKCE validation strengthening.

11.11 Key Takeaways

  1. Null means dangerous, not immortal. When a security-relevant timestamp is missing, the fail-closed interpretation (treat as expired) prevents an entire class of "immortal token" vulnerabilities. Design defaults to be restrictive.

  2. Environment variable tokens need the same lifecycle as interactive tokens. The deployment context (CI/CD, containers, developer workstations) does not reduce the security requirements. Env var tokens must expire, rotate, and be introspectable.

  3. Token provenance enables targeted remediation. Tracking where a token came from (OAuth flow, secure storage, env var) allows the system to provide actionable error messages, choose the right renewal mechanism, and build an audit trail.

  4. Introspection is the bridge between client and server revocation. Without introspection, a client has no way to know that a token has been revoked server-side. Periodic introspection closes this gap with configurable aggressiveness.

  5. Rotation detection via env var re-read is a zero-cost feature. Re-reading the environment variable when the current token expires enables external rotation without requiring any integration beyond the secrets manager writing to the environment. The CLI adapts to whatever rotation mechanism the deployment uses.
