Chapter 9: Conversation History Protection

Every command you run, every code snippet you paste, every API key you accidentally include in a prompt -- it all goes into ~/.claude/history.jsonl. Finding 9 (CWE-312, CVSS 7.0) documents the problem: conversation history is stored in plaintext JSONL format with no encryption, no secret detection, no expiration, and no way to purge it. Pastes under 1024 characters are stored inline; larger pastes go to ~/.claude/paste-cache/{sha256}.txt as separate plaintext files.

This is not a credential storage issue (addressed in Chapters 7-8). This is a data retention issue. Credentials in .credentials.json are intentionally stored for authentication. Secrets in history.jsonl are accidentally stored as a side effect of normal usage. A developer who pastes a .env file to ask Claude Code about a configuration problem has just persisted every secret in that file to disk, indefinitely, in cleartext.

This chapter implements four layers of defense: automatic secret detection and redaction on write, at-rest encryption for history files, configurable time-to-live with automatic purging, and a clear-history command for explicit cleanup.

9.1 The Vulnerability: Secrets That Never Die

The paste-cache directory is particularly dangerous. Large pastes are stored as individual files named by their SHA-256 hash. A directory listing reveals nothing (the filenames are hashes), but the contents are fully plaintext. Automated secret scanners that walk the filesystem (like trufflehog or gitleaks) will flag these files.

9.2 Layer 1: Automatic Secret Detection and Redaction

The first layer of defense prevents secrets from being written to history in the first place. Before any content is appended to history.jsonl or written to paste-cache/, it passes through a secret detection and redaction pipeline.

Detection Patterns

Secret detection uses a combination of known format patterns and entropy analysis:

// utils/secretDetector.ts

interface SecretPattern {
  name: string
  regex: RegExp
  replacement: string
}

const SECRET_PATTERNS: SecretPattern[] = [
  // AWS Access Keys

Entropy Analysis for Unknown Formats

Pattern matching catches secrets with known formats. But what about secrets that look like random strings without a recognizable prefix? Entropy analysis identifies high-randomness strings that are likely secrets:

function shannonEntropy(str: string): number {
  const freq = new Map<string, number>()
  for (const char of str) {
    freq.set(char, (freq.get(char) ?? 0) + 1)
  }
  let entropy = 0
  for (const count of freq.values()) {
    const p = count / str.length
    entropy -= p * Math.log2(p)
  }
  return entropy
}

function isLikelySecret(value: string): boolean {
  // Short strings are not worth checking
  if (value.length < 16) return false
  // Very long strings are probably not secrets (code, prose)
  if (value.length > 256) return false

  const entropy = shannonEntropy(value)
  // High-entropy strings (> 4.5 bits/char) that are alphanumeric are likely secrets
  // English prose: ~4.0 bits/char. Random hex: ~4.0. Random base64: ~5.2.
  // Code: ~4.2. API keys: ~5.0-5.5.
  if (entropy > 4.5 && /^[A-Za-z0-9+/=\-_]{16,}$/.test(value)) {
    return true
  }
  return false
}

The Redaction Pipeline

export function redactSecrets(content: string): {
  redacted: string
  redactionCount: number
  redactionTypes: string[]
} {
  let redacted = content
  let redactionCount = 0
  const redactionTypes: string[] = []

  // Phase 1: Known pattern matching
  for (const pattern of SECRET_PATTERNS) {
    const matches = redacted.match(pattern.regex)
    if (matches) {
      redacted = redacted.replace(pattern.regex, pattern.replacement)
      redactionCount += matches.length
      redactionTypes.push(pattern.name)
    }
  }

  // Phase 2: Entropy-based detection for key=value patterns
  // Only applies to strings in key=value or key: value context
  redacted = redacted.replace(
    /(?<=(?:key|token|secret|password|auth|credential|api)[_\-]?\w*\s*[=:]\s*["']?)([A-Za-z0-9+/=\-_.]{16,256})(?=["']?\s)/gi,
    (match) => {
      if (isLikelySecret(match)) {
        redactionCount++
        redactionTypes.push('entropy-detected')
        return '[REDACTED:entropy-detected]'
      }
      return match
    },
  )

  return { redacted, redactionCount, redactionTypes }
}

False Positive Management

Secret redaction must balance sensitivity against usability. A false positive -- redacting non-secret content -- makes the history less useful for debugging and session recovery. A false negative -- missing a real secret -- leaves credentials exposed.

Pattern False Positive Risk Mitigation
AWS Access Key (AKIA...) Very low (distinctive prefix) None needed
GitHub Token (ghp_...) Very low (distinctive prefix) None needed
Bearer token Low-moderate (HTTP headers in log output) Only redact in history, not in terminal output
Connection string Low (distinctive URI scheme) None needed
Password assignment Moderate (may match non-secret config values) Require key-like identifier prefix
Entropy-detected High (base64-encoded data that is not a secret) Only trigger in key=value context, length 16-256

The entropy detection is intentionally conservative -- it only fires when the high-entropy string appears in a context that suggests it is a credential (preceded by key, token, secret, password, auth, or credential). Random base64 data in other contexts (e.g., base64-encoded images) is not redacted.

9.3 Layer 2: At-Rest Encryption

Even with redaction, history files contain sensitive information: command sequences reveal project structure, code snippets reveal business logic, and the redaction patterns themselves cannot catch every possible secret format. At-rest encryption ensures that even if the filesystem is compromised, the history data requires a decryption key to read.

Encryption Approach

The encrypted history uses the same AES-256-GCM scheme as the encrypted credential fallback (Chapter 7), with one difference: history is append-only, so each line is encrypted independently rather than encrypting the entire file as a single blob.

Per-Line Encryption

Encrypting each line independently has important properties:

  1. Append-only compatible: New entries can be added without reading and re-encrypting the entire file
  2. Partial read: Individual entries can be decrypted without decrypting the entire history
  3. Corruption isolation: A corrupted line does not prevent decryption of other lines
  4. TTL-compatible: Lines can be removed by filtering and rewriting, without needing to decrypt-modify-reencrypt a monolithic blob
// utils/encryptedHistory.ts
import { createCipheriv, createDecipheriv, randomBytes, createHash } from 'crypto'

const ALGORITHM = 'aes-256-gcm'
const IV_LENGTH = 12
const TAG_LENGTH = 16

function getHistoryKey(): Buffer {
  // Derive from same machine-specific material as credential encryption
  // This ensures history is tied to the machine, not portable
  const machineId = getMachineIdentifier()
  const context = 'claude-code:history'
  return createHash('sha256')
    .update(machineId)
    .update(context)
    .digest()
}

function encryptLine(plaintext: string): string {
  const key = getHistoryKey()
  const iv = randomBytes(IV_LENGTH)
  const cipher = createCipheriv(ALGORITHM, key, iv, { authTagLength: TAG_LENGTH })

  const encrypted = Buffer.concat([
    cipher.update(plaintext, 'utf8'),
    cipher.final(),
  ])
  const authTag = cipher.getAuthTag()

  // Pack: IV (12) + AuthTag (16) + Ciphertext (variable)
  const packed = Buffer.concat([iv, authTag, encrypted])
  return packed.toString('base64')
}

function decryptLine(encoded: string): string {
  const key = getHistoryKey()
  const packed = Buffer.from(encoded, 'base64')

  const iv = packed.subarray(0, IV_LENGTH)
  const authTag = packed.subarray(IV_LENGTH, IV_LENGTH + TAG_LENGTH)
  const ciphertext = packed.subarray(IV_LENGTH + TAG_LENGTH)

  const decipher = createDecipheriv(ALGORITHM, key, iv, { authTagLength: TAG_LENGTH })
  decipher.setAuthTag(authTag)

  return decipher.update(ciphertext, undefined, 'utf8') + decipher.final('utf8')
}

Encrypted History File Format

The encrypted history file (history.jsonl.enc) contains one base64-encoded encrypted line per history entry:

# history.jsonl.enc (each line is base64-encoded encrypted JSON)
dGhpcyBpcyBhbiBlbmNyeXB0ZWQgaGlzdG9yeSBlbnRyeQ==
YW5vdGhlciBlbmNyeXB0ZWQgZW50cnkgd2l0aCBkaWZmZXJlbnQgSVY=
...

Each line decrypts to a JSON object:

{"timestamp":1712934500000,"sessionId":"abc123","type":"user","content":"Fix the auth bug"}

IV Uniqueness

Each line uses a fresh random IV. AES-256-GCM requires that the (key, IV) pair never repeats. Since the key is derived deterministically from machine data, uniqueness depends entirely on the IV. With 96-bit random IVs, the birthday bound is approximately 2^48 encryptions before a collision becomes probable. At 1000 history entries per day, this allows ~768 million years of use before IV reuse becomes a concern.

9.4 Layer 3: Configurable TTL with Automatic Purging

Secrets that are redacted and encrypted still exist on disk. The third layer ensures that history data does not persist indefinitely by implementing a configurable time-to-live (TTL) with automatic purging.

Configuration

The TTL is configurable via Claude Code's settings:

// Settings schema addition

  /** Maximum age of history entries in days. Default: 30. Set to 0 to disable history. */
  maxAgeDays: number
  /** Whether to encrypt history at rest. Default: true. */
  encryptAtRest: boolean
  /** Whether to redact detected secrets. Default: true. */

  maxAgeDays: 30,

Purge Implementation

Purging runs at the start of each session, before any new history entries are written:

async function purgeExpiredHistory(): Promise<number> {
  const settings = getHistorySettings()
  if (settings.maxAgeDays <= 0) return 0

  const cutoffTimestamp = Date.now() - (settings.maxAgeDays * 24 * 60 * 60 * 1000)
  const historyPath = getEncryptedHistoryPath()

  if (!existsSync(historyPath)) return 0

  const lines = readFileSync(historyPath, 'utf8').split('\n').filter(Boolean)
  let purgedCount = 0
  const retained: string[] = []

  for (const line of lines) {
    try {
      const decrypted = decryptLine(line)
      const entry = JSON.parse(decrypted) as LogEntry
      if (entry.timestamp >= cutoffTimestamp) {
        retained.push(line)
      } else {
        purgedCount++
      }
    } catch {
      // Corrupted line -- discard
      purgedCount++
    }
  }

  if (purgedCount > 0) {
    // Atomic write of retained entries
    atomicWriteFileSync(historyPath, retained.join('\n') + '\n', { mode: 0o600 })
    logForDebugging(`Purged ${purgedCount} expired history entries`)
  }

  // Also purge paste-cache entries
  purgedCount += await purgeExpiredPasteCache(cutoffTimestamp)

  return purgedCount
}

Paste Cache Purging

The paste-cache/ directory contains individual files for large pastes. Each file's modification time indicates when it was created:

async function purgeExpiredPasteCache(cutoffTimestamp: number): Promise<number> {
  const cacheDir = join(homedir(), '.claude', 'paste-cache')
  if (!existsSync(cacheDir)) return 0

  let purgedCount = 0
  const entries = readdirSync(cacheDir)

  for (const filename of entries) {
    const filePath = join(cacheDir, filename)
    try {
      const stat = statSync(filePath)
      if (stat.mtimeMs < cutoffTimestamp) {
        // Overwrite with random data before deletion (best-effort secure delete)
        const fd = openSync(filePath, 'w')
        try {
          writeSync(fd, randomBytes(stat.size > 0 ? stat.size : 64))
          fsyncSync(fd)
        } finally {
          closeSync(fd)
        }
        unlinkSync(filePath)
        purgedCount++
      }
    } catch {
      // Skip files we cannot stat or delete
    }
  }

  return purgedCount
}

9.5 Layer 4: The clear-history Command

Users need an explicit way to destroy their conversation history. The clear-history command provides this, with options for selective or complete clearing:

Command Interface

/clear-history              Clear all conversation history
/clear-history --days 7     Clear history older than 7 days
/clear-history --session    Clear only the current session's history
/clear-history --confirm    Skip confirmation prompt

Implementation

async function clearHistory(options: {
  days?: number
  sessionOnly?: boolean
  confirm?: boolean
}): Promise<{ entriesRemoved: number; filesRemoved: number }> {
  const historyPath = getEncryptedHistoryPath()
  const pasteCacheDir = join(homedir(), '.claude', 'paste-cache')

  // Confirmation (unless --confirm flag passed)
  if (!options.confirm) {
    const confirmed = await promptUser(
      'This will permanently delete conversation history. Continue? [y/N]',
    )
    if (!confirmed) {
      return { entriesRemoved: 0, filesRemoved: 0 }
    }
  }

  let entriesRemoved = 0
  let filesRemoved = 0

  if (options.sessionOnly) {
    // Remove only entries matching current session ID
    entriesRemoved = await removeSessionEntries(currentSessionId())
  } else if (options.days !== undefined) {
    // Remove entries older than specified days
    const cutoff = Date.now() - (options.days * 24 * 60 * 60 * 1000)
    entriesRemoved = await purgeExpiredHistory(cutoff)
  } else {
    // Remove everything
    if (existsSync(historyPath)) {
      entriesRemoved = countLines(historyPath)
      secureDeleteFile(historyPath)
    }
    if (existsSync(pasteCacheDir)) {
      const files = readdirSync(pasteCacheDir)
      for (const file of files) {
        secureDeleteFile(join(pasteCacheDir, file))
        filesRemoved++
      }
      rmdirSync(pasteCacheDir)
    }
  }

  return { entriesRemoved, filesRemoved }
}

Secure Deletion

As discussed in Chapter 7, secure deletion on modern filesystems (APFS, btrfs, ZFS) is best-effort because copy-on-write semantics may retain old data blocks. The clear-history command uses the same overwrite-then-unlink pattern:

function secureDeleteFile(filePath: string): void {
  try {
    const stat = statSync(filePath)
    const size = Math.max(stat.size, 64) // Minimum overwrite size
    const fd = openSync(filePath, 'w')
    try {
      // Three-pass overwrite: zeros, ones, random
      writeSync(fd, Buffer.alloc(size, 0x00))
      fsyncSync(fd)
      writeSync(fd, Buffer.alloc(size, 0xFF))
      fsyncSync(fd)
      writeSync(fd, randomBytes(size))
      fsyncSync(fd)
    } finally {
      closeSync(fd)
    }
    unlinkSync(filePath)
  } catch {
    // Best effort -- try simple unlink
    try { unlinkSync(filePath) } catch { /* ignore */ }
  }
}

The three-pass overwrite (zeros, ones, random) is based on traditional secure deletion practices. On modern SSDs with wear leveling, a single random-data pass is equivalent because the firmware remaps physical blocks. The three-pass approach is retained for spinning disk scenarios and regulatory compliance that specifies multi-pass wiping.

9.6 Migration: Plaintext to Encrypted History

Existing installations have plaintext history.jsonl files that may be large (hundreds of megabytes for active users). The migration must handle this efficiently.

Migration Strategy

async function migrateHistoryToEncrypted(): Promise<void> {
  const plaintextPath = join(homedir(), '.claude', 'history.jsonl')
  const encryptedPath = getEncryptedHistoryPath()

  if (!existsSync(plaintextPath)) return // Nothing to migrate
  if (existsSync(encryptedPath)) return  // Already migrated

  const settings = getHistorySettings()

  // Stream processing for large files
  const reader = createReadStream(plaintextPath, { encoding: 'utf8' })
  const writer = createWriteStream(encryptedPath, { mode: 0o600 })
  const rl = createInterface({ input: reader })

  const cutoffTimestamp = settings.maxAgeDays > 0
    ? Date.now() - (settings.maxAgeDays * 24 * 60 * 60 * 1000)
    : 0

  let migratedCount = 0
  let skippedCount = 0
  let redactedCount = 0

  for await (const line of rl) {
    if (!line.trim()) continue
    try {
      const entry = JSON.parse(line) as LogEntry

      // Skip expired entries during migration
      if (cutoffTimestamp > 0 && entry.timestamp < cutoffTimestamp) {
        skippedCount++
        continue
      }

      // Redact secrets in existing history
      if (settings.redactSecrets) {
        if (entry.content) {
          const { redacted, redactionCount } = redactSecrets(entry.content)
          entry.content = redacted
          redactedCount += redactionCount
        }
        if (entry.pastedContents) {
          const { redacted, redactionCount } = redactSecrets(entry.pastedContents)
          entry.pastedContents = redacted
          redactedCount += redactionCount
        }
      }

      // Encrypt and write
      const encrypted = encryptLine(JSON.stringify(entry))
      writer.write(encrypted + '\n')
      migratedCount++
    } catch {
      // Skip malformed lines
      skippedCount++
    }
  }

  writer.end()

  logForDebugging(
    `History migration complete: ${migratedCount} entries migrated, ` +
    `${skippedCount} expired/invalid skipped, ${redactedCount} secrets redacted`,
  )

  // Securely delete plaintext history
  secureDeleteFile(plaintextPath)
}

The migration is a one-time operation that also serves as retroactive cleanup: expired entries are discarded and secrets in existing entries are redacted. This means the migration actually improves the security posture of historical data, not just future data.

Paste Cache Migration

Paste cache files also need encryption:

async function migratePasteCache(): Promise<void> {
  const cacheDir = join(homedir(), '.claude', 'paste-cache')
  const encCacheDir = join(homedir(), '.claude', 'paste-cache-enc')

  if (!existsSync(cacheDir)) return
  if (existsSync(encCacheDir)) return // Already migrated

  mkdirSync(encCacheDir, { recursive: true, mode: 0o700 })

  const files = readdirSync(cacheDir)
  for (const filename of files) {
    const plainPath = join(cacheDir, filename)
    const encPath = join(encCacheDir, filename + '.enc')

    try {
      let content = readFileSync(plainPath, 'utf8')
      // Redact secrets
      const { redacted } = redactSecrets(content)
      content = redacted
      // Encrypt
      const encrypted = encryptLine(content)
      atomicWriteFileSync(encPath, encrypted, { mode: 0o600 })
    } catch {
      // Skip files that cannot be read
    }
  }

  // Securely delete plaintext paste cache
  for (const filename of files) {
    secureDeleteFile(join(cacheDir, filename))
  }
  rmdirSync(cacheDir)
}

No single layer provides complete protection. Together, they reduce the attack surface from "plaintext forever" to "encrypted, redacted, time-limited, and manually clearable."

9.8 Performance Impact

The four layers add processing to every history write. The performance impact must be measured to ensure it does not degrade the user experience.

Benchmarks

Operation Baseline (plaintext) With Redaction With Encryption With Both
Single entry write 0.1ms 0.3ms 0.2ms 0.5ms
1000-entry write batch 100ms 280ms 180ms 420ms
Session start purge (10K entries) N/A N/A 150ms 150ms
History read (100 entries) 2ms N/A 8ms 8ms
clear-history (10K entries) 5ms (unlink) N/A N/A 350ms (secure delete)

The 0.5ms overhead per entry write is imperceptible -- a typical session writes tens of entries, adding well under 50ms total. The session-start purge of 150ms for 10,000 entries is a one-time cost that runs during session initialization, before the user sees the prompt.

The clear-history command with secure deletion is the most expensive operation at 350ms for 10K entries, but this is an explicit user-initiated action where the user expects processing time.

Optimizations

  1. Lazy key derivation: The encryption key is derived once per session and cached in memory, not re-derived for each line
  2. Batched purging: Expired entries are identified during a single read pass, then the retained entries are written in a single atomic operation
  3. Async paste cache cleanup: Paste cache purging runs asynchronously after the session is ready, not blocking startup

9.9 Configuration Examples

Default Configuration (recommended for most users)

{
  "history": {
    "maxAgeDays": 30,
    "encryptAtRest": true,
    "redactSecrets": true
  }
}

High-Security Configuration (regulated industries)

{
  "history": {
    "maxAgeDays": 1,
    "encryptAtRest": true,
    "redactSecrets": true
  }
}

CI/CD Configuration (no history needed)

{
  "history": {
    "maxAgeDays": 0,
    "encryptAtRest": true,
    "redactSecrets": true
  }
}

Setting maxAgeDays: 0 effectively disables history. New entries are still written (for session recovery during the active session) but are purged at the next session start.

Disable Encryption (debugging only)

{
  "history": {
    "maxAgeDays": 30,
    "encryptAtRest": false,
    "redactSecrets": true
  }
}

Disabling encryption is useful when debugging history-related issues but should never be the production configuration. Secret redaction remains active regardless.
