Chapter 11: Secret Detection & Prevention

Chapters 9 and 10 focused on managing credentials that the agent should have --- OAuth tokens, JWTs, API keys that the agent needs to function. This chapter addresses the inverse problem: preventing the agent from exposing secrets that it encounters during its work. An AI agent that reads source code, processes environment files, executes commands, and generates output has countless opportunities to ingest, transmit, and persist secrets that should never leave the local machine.

The secret exposure surface in AI agent systems is fundamentally different from traditional applications. A web application might leak a database password in an error page. An AI agent leaks secrets through its conversation history, its API requests (which transmit the full context window to the model provider), its telemetry, its output files, and its tool results that become part of the persistent conversation. Every file the agent reads becomes context that is sent to the model provider's API. Every command output that enters the context window crosses the trust boundary between the local machine and the cloud.

This chapter builds the secret detection and prevention architecture that AI agent systems require: regex-based pattern matching, entropy analysis, git hook integration, runtime guardrails, and the fundamental challenge of detecting secrets in natural language context.

The most dangerous exposure point is also the hardest to mitigate: the API payload. Every file the agent reads, every command it executes, every search result it processes enters the context window, which is transmitted to the model provider's API endpoint. If the agent reads a .env file containing DATABASE_PASSWORD=hunter2, that password crosses the network to the model provider's servers.

The secret file deny list (discussed in Chapter 9) prevents the agent from intentionally reading known secret files. But secrets appear in unexpected places: hardcoded in source code, embedded in configuration, returned in command output, pasted by users. The deny list cannot anticipate every location.

11.2 Regex-Based Secret Detection

The foundation of secret detection is pattern matching. Known secret formats have identifiable structures that can be matched with regular expressions.

Production Secret Patterns

import re
from dataclasses import dataclass
from typing import Pattern

@dataclass(frozen=True)
class SecretPattern:
    name: str
    pattern: Pattern[str]
    severity: str
    description: str

    ),

        name="Generic Secret Assignment",

def scan_for_secrets(
    content: str,
    min_severity: str = "LOW"
) -> list[dict[str, str]]:
    """Scan content for known secret patterns."""
    severity_order = {"CRITICAL": 4, "HIGH": 3, "MEDIUM": 2, "LOW": 1}
    min_level = severity_order.get(min_severity, 0)

    findings: list[dict[str, str]] = []
    for sp in SECRET_PATTERNS:
        if severity_order[sp.severity] < min_level:
            continue
        for match in sp.pattern.finditer(content):
            findings.append({
                "pattern": sp.name,
                "severity": sp.severity,
                "match": match.group()[:20] + "..." if len(match.group()) > 20 else match.group(),
                "position": f"offset {match.start()}",
                "description": sp.description,
            })
    return findings

Pattern Effectiveness

Pattern Type Precision Recall Notes
AWS Access Key (AKIA...) Very High (99%) Very High (98%) Fixed prefix, fixed length
GitHub Tokens (ghp_...) Very High (99%) Very High (97%) Fixed prefix format
Private Key Headers Very High (99%) Very High (99%) Distinctive markers
Database URIs High (90%) Medium (75%) Schema prefix is distinctive
Generic password=... Low (30%) Medium (60%) High false positive rate
High-entropy strings Very Low (10%) High (80%) Too many false positives

The precision-recall trade-off is the central challenge. Strict patterns (fixed prefixes like AKIA, ghp_) have excellent precision but only detect specific services. Generic patterns (anything after password=) catch more secrets but also flag legitimate values like password=test in unit test fixtures.

11.3 Entropy-Based Detection

For secrets without distinctive prefixes, entropy analysis provides a complementary detection mechanism. High-entropy strings --- those with a large number of distinct characters in a random-looking distribution --- are more likely to be cryptographic secrets than natural language or structured data.

import math
from collections import Counter

def shannon_entropy(s: str) -> float:
    """Calculate Shannon entropy of a string."""
    if not s:
        return 0.0
    freq = Counter(s)
    length = len(s)
    return -sum(
        (count / length) * math.log2(count / length)
        for count in freq.values()
    )

def is_high_entropy(
    s: str,
    threshold: float = 4.5,
    min_length: int = 20
) -> bool:
    """
    Detect high-entropy strings that may be secrets.

    Shannon entropy thresholds:
    - English text: ~3.5-4.0 bits/char
    - Base64 encoded: ~5.0-5.5 bits/char
    - Hex encoded: ~3.5-4.0 bits/char
    - Random alphanumeric: ~5.7 bits/char
    """
    if len(s) < min_length:
        return False
    return shannon_entropy(s) > threshold

11.4 Git Pre-Commit Hooks

The most impactful place to detect secrets is before they enter version control. Once a secret is committed, it exists in the git history forever (even if the file is later deleted) and is replicated to every clone of the repository.

The Secret-Scan Hook Architecture

sequenceDiagram
    participant Dev as Developer
    participant Git as Git
    participant Hook as Pre-Commit Hook
    participant Scanner as Secret Scanner
    participant Store as Allowlist Store

    Dev->>Git: git commit
    Git->>Hook: PreCommit trigger
    Hook->>Git: git diff --cached --diff-filter=ACMR
    Git->>Hook: Staged file contents
    Hook->>Scanner: Scan staged content
    Scanner->>Scanner: Regex patterns + entropy
    Scanner->>Store: Check findings against allowlist
    Store->>Scanner: Known false positives

    alt Secrets Found
        Scanner->>Hook: Findings list
        Hook->>Dev: BLOCKED — secrets detected<br/>(file:line, pattern, severity)
        Hook->>Git: Exit code 1 (block commit)
    else Clean
        Scanner->>Hook: No findings
        Hook->>Git: Exit code 0 (allow commit)
    end

Implementation

#!/usr/bin/env bash
set -euo pipefail

# .claude/hooks/secret-scan.sh
# Pre-commit hook: scan staged files for secrets

# Read hook input from stdin (Claude Code hook protocol)
INPUT=$(cat)
TOOL=$(echo "${INPUT}" | python3 -c \
  "import sys,json; print(json.load(sys.stdin).get('tool_name',''))" \
  2>/dev/null || echo "")

# Only trigger on git commit
COMMAND=$(echo "${INPUT}" | python3 -c \
  "import sys,json; print(json.load(sys.stdin).get('tool_input',{}).get('command',''))" \
  2>/dev/null || echo "")

if [[ "${TOOL}" != "Bash" ]] || [[ "${COMMAND}" != *"git commit"* ]]; then
  exit 0
fi

# Get staged file contents
STAGED_DIFF=$(git diff --cached --diff-filter=ACMR -U0 2>/dev/null || echo "")

if [[ -z "${STAGED_DIFF}" ]]; then
  exit 0
fi

# Secret patterns (added lines only — lines starting with +)
FINDINGS=""

# AWS Access Keys
if echo "${STAGED_DIFF}" | grep -E '^\+.*AKIA[0-9A-Z]{16}' > /dev/null 2>&1; then
  FINDINGS="${FINDINGS}\n  - AWS Access Key ID detected"
fi

# GitHub tokens
if echo "${STAGED_DIFF}" | grep -E '^\+.*(ghp_|gho_|ghu_|ghs_|github_pat_)[A-Za-z0-9_]{20,}' > /dev/null 2>&1; then
  FINDINGS="${FINDINGS}\n  - GitHub token detected"
fi

# Private keys
if echo "${STAGED_DIFF}" | grep -E '^\+.*-----BEGIN (RSA |EC |DSA |OPENSSH )?PRIVATE KEY-----' > /dev/null 2>&1; then
  FINDINGS="${FINDINGS}\n  - Private key detected"
fi

# Generic secrets
if echo "${STAGED_DIFF}" | grep -iE '^\+.*(password|secret|api_key|access_token)\s*[=:]\s*[^ ]{8,}' > /dev/null 2>&1; then
  FINDINGS="${FINDINGS}\n  - Potential secret in assignment"
fi

# Anthropic/OpenAI keys
if echo "${STAGED_DIFF}" | grep -E '^\+.*sk-ant-[a-zA-Z0-9_-]{20,}' > /dev/null 2>&1; then
  FINDINGS="${FINDINGS}\n  - Anthropic API key detected"
fi

if [[ -n "${FINDINGS}" ]]; then
  REASON="Secret scan blocked commit. Findings:${FINDINGS}"
  echo "{\"hookSpecificOutput\":{\"hookEventName\":\"PreToolUse\",\"permissionDecision\":\"deny\",\"permissionDecisionReason\":\"${REASON}\"}}" >&2
  exit 2
fi

exit 0

Allowlist Management

False positives are the primary operational challenge. A secret scanner that flags test fixtures, example values, and documentation will be disabled by developers who tire of overriding it.

# .secret-scan-allowlist.yaml
# Known false positives — reviewed and approved

allowlist:
  - pattern: "AKIAIOSFODNN7EXAMPLE"
    reason: "AWS documentation example key"
    reviewer: "tdoan"
    date: "2026-03-15"

  - pattern: "ghp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
    reason: "Placeholder in test fixtures"
    reviewer: "tdoan"
    date: "2026-03-15"

  - file: "tests/fixtures/mock_credentials.json"
    reason: "Test fixture with fake credentials"
    reviewer: "tdoan"
    date: "2026-03-15"

The allowlist must be version-controlled and reviewed. Each entry requires a reviewer, a date, and a reason. Allowlist entries should be re-reviewed periodically to catch cases where a "test" credential became a real credential.

11.5 Runtime Secret Guardrails

Git hooks protect against committing secrets. But in AI agent systems, secrets are exposed through channels that git hooks never see: API payloads, conversation history, and telemetry. Runtime guardrails are needed.

Secret Redaction in Conversation History

Claude Code stores conversation history in ~/.claude/history.jsonl as plaintext JSONL. Every message, tool result, and pasted content is recorded. From the audit report (Finding 9, MEDIUM):

"All conversation history including commands, code snippets, and pasted content is stored in plaintext JSONL format. API keys, tokens, passwords, and other secrets pasted during sessions persist on disk indefinitely in cleartext."

The data flow:

User pastes API key into session 
  -> LogEntry created with pastedContents 
  -> writeToFile() appends to history.jsonl in plaintext 
  -> paste-cache/{sha256}.txt stores full content 
  -> persists until manual deletion

Recommended mitigation: Scan-on-write redaction.

import { createHash } from "crypto";

const SECRET_PATTERNS = [
  /AKIA[0-9A-Z]{16}/g,                          // AWS
  /ghp_[A-Za-z0-9_]{36,}/g,                     // GitHub PAT
  /sk-ant-[a-zA-Z0-9_\-]{20,}/g,                // Anthropic
  /sk-[a-zA-Z0-9]{48,}/g,                       // OpenAI
  /-----BEGIN (?:RSA |EC )?PRIVATE KEY-----/g,   // Private keys
];

function redactSecrets(content: string): string {
  let redacted = content;
  for (const pattern of SECRET_PATTERNS) {
    redacted = redacted.replace(pattern, (match) => {
      const hash = createHash("sha256")
        .update(match)
        .digest("hex")
        .slice(0, 8);
      return `[REDACTED:${hash}]`;
    });
  }
  return redacted;
}

// Apply before writing to history
function writeToHistory(entry: LogEntry): void {
  const sanitized = {
    ...entry,
    content: redactSecrets(entry.content),
    pastedContents: entry.pastedContents?.map(redactSecrets),
  };
  appendFileSync(
    historyPath,
    JSON.stringify(sanitized) + "\n"
  );
}

The [REDACTED:hash] format preserves a fingerprint for correlation (same secret always produces the same hash) while removing the actual credential value.

The deny rule Read(./.env) blocks the Read tool but does not block: - cat .env via the Bash tool - grep SECRET .env via the Bash tool - source .env && env via the Bash tool - Grep(pattern="SECRET", path=".") which searches all files including .env

Defense: Cross-tool file access enforcement.

// Centralized file access checker
function isFileAccessBlocked(
  filePath: string, 
  denyPatterns: string[]
): boolean {
  const canonical = realpathSync(filePath);
  return denyPatterns.some(pattern => 
    minimatch(canonical, pattern)
  );
}

// Apply to ALL tools that read files
function preToolCheck(
  toolName: string, 
  toolInput: Record<string, unknown>
): boolean {
  // Extract file paths from any tool's input
  const accessedFiles = extractFilePathsFromInput(toolName, toolInput);

  for (const file of accessedFiles) {
    if (isFileAccessBlocked(file, DENY_PATTERNS)) {
      return false;  // Block this tool call
    }
  }
  return true;
}

function extractFilePathsFromInput(
  toolName: string,
  input: Record<string, unknown>
): string[] {
  switch (toolName) {
    case "Read":
      return [input.path as string];
    case "Bash":
      // Parse command for file arguments
      return extractFilePathsFromCommand(input.command as string);
    case "Grep":
      // The path and any files matching the glob
      return expandGlobToFiles(input.path as string, input.glob as string);
    default:
      return [];
  }
}

11.6 Secret Detection in Agent Telemetry

AI agent systems collect telemetry for debugging, performance monitoring, and usage analytics. Secrets can leak into telemetry through several channels:

Telemetry Field Secret Risk Mitigation
Error messages Exception text may include credentials Redact before collection
Command strings curl -H "Authorization: Bearer ..." Truncate or hash arguments
File paths Path may reveal credential file names Normalize paths
API latency traces Request bodies may include context Never include request body
User-agent strings May include version + config details Standardize format
Session metadata Session ID could correlate to token Use separate session IDs

The security action report for Claude Code specifically identified telemetry as Phase 6 of the remediation plan, recommending:

  1. Make telemetry opt-in with a clear CLI toggle
  2. Exclude all content from telemetry payloads (metadata only)
  3. Redact known secret patterns from error messages before transmission
  4. Document all collected telemetry fields in an accessible privacy notice

Telemetry Redaction Pipeline

from __future__ import annotations
from dataclasses import dataclass, field

@dataclass
class TelemetryEvent:
    event_type: str
    timestamp: float
    session_id: str
    metadata: dict[str, str] = field(default_factory=dict)

    def sanitize(self) -> TelemetryEvent:
        """Remove any potential secrets before transmission."""
        sanitized_meta = {}
        for key, value in self.metadata.items():
            # Redact values that look like secrets
            if _contains_secret(value):
                sanitized_meta[key] = "[REDACTED]"
            # Truncate long values (may contain embedded secrets)
            elif len(value) > 200:
                sanitized_meta[key] = value[:100] + "...[TRUNCATED]"
            else:
                sanitized_meta[key] = value

        return TelemetryEvent(
            event_type=self.event_type,
            timestamp=self.timestamp,
            session_id=self.session_id,
            metadata=sanitized_meta,
        )

def _contains_secret(value: str) -> bool:
    """Check if a string contains known secret patterns."""
    return any(
        pattern.pattern.search(value) 
        for pattern in SECRET_PATTERNS
        if pattern.severity in ("CRITICAL", "HIGH")
    )

11.8 Limitations of Secret Detection

Secret detection is a fundamentally incomplete solution. It is essential as a defense layer but cannot be relied upon as the sole protection. Understanding these limitations is critical for setting appropriate expectations and investing in complementary defenses.

What Detection Cannot Catch

Scenario Why Detection Fails
Encoded secrets (base64, hex, rot13) Pattern does not match encoded form
Split secrets across multiple lines Regex matches single-line patterns
Secrets in binary files Pattern matching operates on text
Novel token formats No pattern exists yet
Secrets shared conversationally ("The password is hunter2") Natural language, no structural pattern
Environment variable values without key context High-entropy string, but no password= prefix
Secrets in image/screenshot content OCR would be required

The False Positive Problem

In production deployments, the false positive rate determines whether the guardrail is used or disabled:

    FP -->|"> 10%"| DISABLED["Developers disable<br/>the scanner"]
    FP -->|"5-10%"| FATIGUE["Approval fatigue<br/>(rubber-stamping)"]
    FP -->|"1-5%"| USABLE["Usable with<br/>allowlist management"]

The key to maintaining a low false positive rate: 1. Use service-specific patterns first (fixed prefixes like AKIA, ghp_) 2. Generic patterns only in key-value context (preceded by password=, secret:, etc.) 3. Entropy analysis only as a secondary signal, never as the sole trigger 4. Maintain a reviewed allowlist for known false positives 5. Differentiate blocking vs. warning --- block CRITICAL, warn MEDIUM

The Cost of False Negatives vs. False Positives

The asymmetry between false negatives and false positives creates a fundamental tuning dilemma:

  • False negative (missed secret): The secret enters version control, API payloads, or conversation history. Cost: potential credential compromise, breach notification, key rotation across all systems.
  • False positive (flagged non-secret): The developer dismisses the alert or adds an allowlist entry. Cost: 30 seconds of developer time plus minor trust erosion in the scanner.

This asymmetry argues for aggressive detection with easy override mechanisms. A scanner that flags 5% false positives but catches 95% of real secrets is more valuable than one with 0.1% false positives but only 60% recall. The key is making the override process painless (one-line allowlist entry with review) so developers do not disable the scanner entirely.

In AI agent systems, the cost asymmetry is even more extreme. A false negative does not just commit a secret to git --- it transmits the secret to the model provider's API, where it may be logged, cached, or processed by multiple systems. The blast radius of a false negative in an AI agent pipeline is larger than in traditional development.

Integration Pattern for AI Agents

#!/usr/bin/env bash
set -euo pipefail

# Pre-commit hook delegating to gitleaks
# .claude/hooks/secret-scan-gitleaks.sh

INPUT=$(cat)
COMMAND=$(echo "${INPUT}" | python3 -c \
  "import sys,json; print(json.load(sys.stdin).get('tool_input',{}).get('command',''))" \
  2>/dev/null || echo "")

if [[ "${COMMAND}" != *"git commit"* ]]; then
  exit 0
fi

# Run gitleaks on staged changes
if command -v gitleaks > /dev/null 2>&1; then
  RESULT=$(gitleaks protect --staged --no-banner 2>&1 || true)
  if echo "${RESULT}" | grep -q "leaks found"; then
    REASON="Gitleaks detected secrets in staged files: ${RESULT}"
    echo "{\"hookSpecificOutput\":{\"hookEventName\":\"PreToolUse\",\"permissionDecision\":\"deny\",\"permissionDecisionReason\":\"${REASON}\"}}" >&2
    exit 2
  fi
fi

exit 0

11.10 Key Takeaways

Secret detection is a necessary but insufficient defense. It catches the most common exposure patterns --- AWS keys with AKIA prefixes, GitHub tokens with ghp_ prefixes, private key headers --- and misses everything novel, encoded, or contextual. The value of secret detection is not in what it catches (which is a subset of all secrets) but in what it prevents from becoming permanent: a secret caught before it enters git history is a secret that does not propagate to every clone, backup, and CI/CD system. A secret caught before it enters the model provider's API is a secret that does not cross your organization's trust boundary.

Three principles for secret detection in AI agent systems:

  1. Scan at every exit point, not just git. Conversation history, API payloads, telemetry, and file writes are all secret exposure vectors. Git pre-commit hooks are necessary but not sufficient. The API payload exposure --- where every piece of context is transmitted to the model provider --- is uniquely dangerous to AI agent systems and has no equivalent in traditional development workflows.

  2. Combine detection methods. Regex patterns catch known formats with high precision. Entropy analysis catches unknown formats with low precision. Context analysis (key-value proximity) improves entropy's precision. Use all three, weighted by confidence. No single method provides adequate coverage alone, but the combination covers the majority of secret formats encountered in production.

  3. Enforce across all tools, not just Read. A deny list that blocks Read(.env) but allows Bash(cat .env) is security theater. Centralize file access control so that every tool that reads files --- Read, Grep, Bash, and any custom tools --- respects the same deny list. The cross-tool enforcement problem is the most commonly overlooked gap in AI agent secret prevention.

Chapter 12 shifts from the credentials and secrets domain to the most critical threat facing AI agents: prompt injection. Where this chapter addressed secrets as data that should not be exposed, Chapter 12 addresses instructions that should not be followed --- the fundamental vulnerability of mixing instructions and data in a single channel.
