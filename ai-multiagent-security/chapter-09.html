Chapter 9: Credential Management for AI Agents

Part II examined the security of single-agent internals --- command execution, permission systems, file system safety, and sandbox isolation. Those chapters addressed threats that arise from what the agent does. Part III shifts to what the agent knows --- the credentials, tokens, and secrets that grant it access to external services. A compromised credential is not a local problem. It is a lateral movement vector that turns a single agent breach into an organization-wide incident.

AI agents authenticate against APIs, cloud services, code repositories, and model providers. Unlike traditional applications where a developer hardcodes a service account credential at deployment time, AI agents acquire credentials dynamically through OAuth flows, inherit them from environment variables, and cache them across sessions. This dynamic lifecycle creates a credential management surface area that most security architectures were not designed to handle.

This chapter dissects the credential lifecycle for AI agents: how credentials are acquired, where they are stored, how they are refreshed, and where the chain fails. We use Claude Code's authentication system as the primary case study, drawing on findings from production security audits that revealed plaintext storage on Linux, TOCTOU race conditions in credential writes, and keychain fallback paths that silently degrade to insecure storage.

9.1 The Agent Credential Landscape

Traditional applications authenticate through a narrow set of patterns: API keys embedded in environment variables, service account JSON files mounted as secrets, or certificate-based mutual TLS. The developer configures these once, and the application uses them for its lifetime.

AI agents break this model in three ways:

Dynamic acquisition. Agents authenticate on behalf of humans through interactive OAuth flows, receiving short-lived access tokens and long-lived refresh tokens. The agent must manage the full token lifecycle --- acquisition, storage, refresh, and revocation --- without human intervention after the initial authorization.

Multi-provider authentication. A single agent session may authenticate against the model provider API (Anthropic, OpenAI), a code hosting platform (GitHub, Azure DevOps), MCP servers with their own authentication, and enterprise SSO systems. Each provider has different token formats, lifetimes, and refresh mechanisms.

Session persistence. Unlike stateless API clients, AI agents maintain sessions across multiple interactions. Credentials must persist between sessions so users do not re-authenticate every time they launch the agent. This persistence creates a storage problem: where do you put credentials that survive process restarts?

9.2 OAuth2 + PKCE for Agent Authentication

The industry standard for interactive agent authentication is OAuth 2.0 with Proof Key for Code Exchange (PKCE). PKCE was originally designed for mobile applications that cannot securely store client secrets, and AI CLI agents share exactly this constraint --- they run on the user's machine where any compiled-in secret can be extracted.

The PKCE Flow for CLI Agents

sequenceDiagram
    participant User as User
    participant CLI as AI Agent CLI
    participant Browser as System Browser
    participant AuthServer as OAuth Provider

    CLI->>CLI: Generate PKCE code_verifier (random 128 bytes)
    CLI->>CLI: Derive code_challenge = SHA-256(code_verifier)
    CLI->>CLI: Generate state parameter (CSRF protection)
    CLI->>CLI: Start localhost callback listener
    CLI->>Browser: Open authorization URL with code_challenge + state
    Browser->>AuthServer: User authenticates + authorizes scopes
    AuthServer->>Browser: Redirect to localhost callback with auth code + state
    Browser->>CLI: Callback delivers auth code
    CLI->>CLI: Verify state parameter matches
    CLI->>AuthServer: Exchange auth code + code_verifier for tokens
    AuthServer->>CLI: access_token + refresh_token
    CLI->>CLI: Store tokens in secure storage

The critical security properties of this flow:

No client secret. The agent never possesses a static client secret. The code_verifier is generated fresh for each authentication attempt and used only once. An intercepted authorization code is useless without the corresponding verifier.

PKCE prevents authorization code interception. Even if an attacker intercepts the redirect URI callback (by binding to the same localhost port before the agent), they cannot exchange the authorization code without the code_verifier that was generated in-memory by the agent.

State parameter prevents CSRF. The state parameter links the authorization request to the callback, preventing an attacker from injecting their own authorization code into the agent's callback.

Real-World Implementation: Claude Code's OAuth Flow

Claude Code implements OAuth2+PKCE in services/oauth/, with a security audit revealing one noteworthy finding:

Finding: OAuth callback listener on predictable localhost port (CWE-352, CVSS 3.7). The callback listener binds to a predictable localhost port. While PKCE's code_verifier prevents authorization code theft even if the port is intercepted, the predictable port creates a narrow race window: a local attacker could bind to the port first and receive the browser redirect. The state parameter and PKCE verifier prevent the attacker from completing the token exchange, but the failed callback creates a denial-of-service condition for the legitimate authentication attempt.

Mitigation pattern: Use ephemeral port binding (port 0) and include the dynamically assigned port in the redirect URI registered with the OAuth provider. This eliminates the predictable port attack entirely but requires the OAuth provider to support dynamic redirect URIs or a range of pre-registered ports.

// Secure pattern: ephemeral port binding
import { createServer } from "net";

function getEphemeralPort(): Promise<number> {
  return new Promise((resolve, reject) => {
    const server = createServer();
    server.listen(0, "127.0.0.1", () => {
      const port = (server.address() as { port: number }).port;
      server.close(() => resolve(port));
    });
    server.on("error", reject);
  });
}

// Use the ephemeral port in the redirect URI
const callbackPort = await getEphemeralPort();
const redirectUri = `http://127.0.0.1:${callbackPort}/callback`;

PKCE Cryptographic Requirements

The PKCE specification (RFC 7636) requires specific cryptographic primitives. Production audit of Claude Code confirmed correct implementation:

Parameter Requirement Claude Code Implementation Status
code_verifier 43-128 char, unreserved charset crypto.randomBytes(32).toString('base64url') Correct
code_challenge BASE64URL(SHA256(verifier)) crypto.createHash('sha256').digest('base64url') Correct
code_challenge_method S256 (not plain) Hardcoded S256 Correct
state Unpredictable, unique per request crypto.randomBytes(16).toString('hex') Correct

The plain challenge method (sending the verifier as the challenge, without hashing) is a documented downgrade attack. Agents must enforce S256 and reject servers that only support plain.

The Audit Findings

A production security audit of Claude Code's credential storage revealed a chain of vulnerabilities that collectively represent the most common real-world attack vector against AI agent credentials:

Finding 7 (HIGH): Plaintext credential storage on non-macOS platforms (CWE-312, CVSS 6.5). getSecureStorage() returns plainTextStorage for all non-macOS platforms. OAuth tokens and credentials are stored as a JSON file at ~/.claude/.credentials.json with chmod 0600 permissions. While chmod 0600 restricts access to the file owner, same-user processes and root can read the credentials freely.

// Actual code pattern from production audit
// utils/secureStorage/index.ts
export function getSecureStorage(): SecureStorage {
  if (process.platform === "darwin") {
    return keychainStorage;
  }
  // TODO: add libsecret support for Linux
  return plainTextStorage;
}

That TODO comment is the credential security posture for every Linux user. The entire Linux credential chain reduces to:

OAuth tokens -> plainTextStorage.update() -> JSON.stringify(data) 
-> writeFileSync("~/.claude/.credentials.json") -> chmod 0o600

Finding 8 (HIGH): Keychain fallback silently degrades to plaintext (CWE-312, CVSS 5.9). On macOS, when the Keychain is unavailable (Docker containers, SSH sessions, CI environments), the storage silently falls back to plainTextStorage. A warning is logged, but the user is not alerted. Credentials that the user believes are protected by the hardware-backed Keychain are actually sitting in a plaintext JSON file.

OAuth token obtained → saveOAuthTokensIfNeeded() → secureStorage.write() 
→ macOS keychain fails → fallbackStorage activates 
→ plainTextStorage.write() → .credentials.json on disk in plaintext

Finding 30 (MEDIUM): TOCTOU race in credential file write (CWE-367, CVSS 4.7). The credential write operation uses writeFileSync followed by chmodSync. Between the write and the permission change, there is a window where the file exists with the default umask permissions (potentially world-readable). On shared systems, another process could read the file during this window.

The Blast Radius

The security action report identified credential storage as a high-priority remediation chain affecting:

  • All Linux users --- no keychain equivalent implemented
  • macOS Docker/SSH users --- keychain unavailable, silent fallback
  • CI/CD pipelines --- headless environments with no keyring daemon
  • Container environments --- volume mounts may expose credential files

Any process running as the same user can read ~/.claude/.credentials.json. Backup software, cloud sync agents, filesystem scanning tools, and malware all have access. In containerized environments where the home directory is mounted as a volume, the attack surface expands to any process in the container ecosystem.

Linux: libsecret Integration

The D-Bus Secret Service specification provides a standard API for credential storage on Linux, implemented by GNOME Keyring and KDE Wallet:

# Python example using libsecret via GObject Introspection
import gi
gi.require_version('Secret', '1')
from gi.repository import Secret

# Define a schema for agent credentials
CREDENTIAL_SCHEMA = Secret.Schema.new(
    "org.aiagent.credentials",
    Secret.SchemaFlags.NONE,
    {
        "account": Secret.SchemaAttributeType.STRING,
        "provider": Secret.SchemaAttributeType.STRING,
    }
)

def store_credential(
    account: str, 
    provider: str, 
    token: str
) -> bool:
    """Store a credential in the system keyring."""
    return Secret.password_store_sync(
        CREDENTIAL_SCHEMA,
        {"account": account, "provider": provider},
        Secret.COLLECTION_DEFAULT,
        f"AI Agent OAuth Token ({provider})",
        token,
        None  # cancellable
    )

def retrieve_credential(
    account: str, 
    provider: str
) -> str | None:
    """Retrieve a credential from the system keyring."""
    return Secret.password_lookup_sync(
        CREDENTIAL_SCHEMA,
        {"account": account, "provider": provider},
        None
    )

For environments where libsecret is unavailable (containers, headless servers), the fallback should use encrypted file storage with a machine-derived key rather than plaintext:

import os
import hashlib
from pathlib import Path
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

def derive_machine_key() -> bytes:
    """Derive an encryption key from machine-specific entropy."""
    entropy_sources = []

    # Machine ID (stable across reboots)
    machine_id_path = Path("/etc/machine-id")
    if machine_id_path.exists():
        entropy_sources.append(machine_id_path.read_bytes())

    # User ID (scopes to current user)
    entropy_sources.append(str(os.getuid()).encode())

    # Hostname
    entropy_sources.append(os.uname().nodename.encode())

    combined = b"".join(entropy_sources)
    return hashlib.pbkdf2_hmac(
        "sha256", combined, b"ai-agent-credential-store", 100_000
    )

def encrypt_credentials(data: bytes, key: bytes) -> bytes:
    """Encrypt credential data using AES-256-GCM."""
    nonce = os.urandom(12)
    aesgcm = AESGCM(key)
    ciphertext = aesgcm.encrypt(nonce, data, None)
    return nonce + ciphertext  # prepend nonce for decryption

Windows: DPAPI Integration

Windows Data Protection API (DPAPI) encrypts data using credentials derived from the user's login password, providing user-scoped encryption without managing keys:

# Windows DPAPI via ctypes
import ctypes
import ctypes.wintypes

class DATA_BLOB(ctypes.Structure):
    _fields_ = [
        ("cbData", ctypes.wintypes.DWORD),
        ("pbData", ctypes.POINTER(ctypes.c_byte)),
    ]

def dpapi_encrypt(data: bytes) -> bytes:
    """Encrypt data using Windows DPAPI (user scope)."""
    input_blob = DATA_BLOB(
        len(data), 
        ctypes.cast(ctypes.create_string_buffer(data), 
                     ctypes.POINTER(ctypes.c_byte))
    )
    output_blob = DATA_BLOB()

    if ctypes.windll.crypt32.CryptProtectData(
        ctypes.byref(input_blob), None, None, None, None, 0,
        ctypes.byref(output_blob)
    ):
        result = ctypes.string_at(output_blob.pbData, output_blob.cbData)
        ctypes.windll.kernel32.LocalFree(output_blob.pbData)
        return result
    raise OSError("DPAPI encryption failed")

Atomic Credential Operations

The TOCTOU race condition in credential file writes requires atomic operations:

import { writeFileSync, renameSync, chmodSync } from "fs";
import { join, dirname } from "path";
import { randomBytes } from "crypto";

function atomicCredentialWrite(
  path: string, 
  data: string
): void {
  const dir = dirname(path);
  const tmpFile = join(dir, `.tmp-${randomBytes(8).toString("hex")}`);

  try {
    // Write to temp file with restrictive permissions from the start
    const fd = openSync(tmpFile, "w", 0o600);
    writeSync(fd, data);
    fsyncSync(fd);   // ensure data hits disk
    closeSync(fd);

    // Atomic rename replaces the target file
    renameSync(tmpFile, path);
  } catch (err) {
    // Clean up temp file on failure
    try { unlinkSync(tmpFile); } catch {}
    throw err;
  }
}

The key insight: renameSync on the same filesystem is atomic on both Linux and macOS. The credential file is never in a partially-written or world-readable state.

9.5 Token Lifecycle Management

Credential storage is only half the problem. The other half is managing the token lifecycle --- ensuring tokens are refreshed before expiry, revoked when compromised, and never persisted longer than necessary.

The Token State Machine

stateDiagram-v2
    [*] --> Acquired: OAuth flow completes
    Acquired --> Active: Token stored securely
    Active --> NearExpiry: expiry - buffer reached
    NearExpiry --> Refreshing: Refresh token exchange
    Refreshing --> Active: New access_token received
    Refreshing --> Expired: Refresh fails
    Active --> Revoked: Server-side revocation
    Revoked --> [*]: Re-authenticate required
    Expired --> [*]: Re-authenticate required
    Active --> Leaked: Credential compromise detected
    Leaked --> Revoked: Immediate revocation

The Immortal Token Problem

A production audit finding reveals a particularly dangerous pattern in how AI agents handle environment variable tokens:

Finding 13 (MEDIUM): Env var tokens treated as immortal (CWE-613, CVSS 5.4). Tokens provided via the CLAUDE_CODE_OAUTH_TOKEN environment variable are assigned expiresAt: null and refreshToken: null. The client treats them as immortal --- isTokenExpired() returns false for null expiry, and checkAndRefreshOAuthTokenIfNeeded() skips refresh for tokens without a refresh token.

// auth.ts:1260-1284 — Actual pattern from audit
// Env var tokens get null expiry and null refresh
const tokenObj = {
  accessToken: process.env.CLAUDE_CODE_OAUTH_TOKEN,
  refreshToken: null,    // No refresh mechanism
  expiresAt: null,       // Treated as never-expiring
};

function isTokenExpired(token: TokenObj): boolean {
  if (token.expiresAt === null) return false;  // Immortal!
  return Date.now() > token.expiresAt;
}

If a token provided via environment variable is later revoked server-side, the agent continues presenting it until it receives a 401 response. There is no periodic introspection check to verify the token is still valid.

Recommended mitigation:

const MAX_TOKEN_AGE_MS = 24 * 60 * 60 * 1000; // 24 hours

function isTokenExpired(token: TokenObj): boolean {
  // Never treat any token as immortal
  if (token.expiresAt === null) {
    // For tokens without explicit expiry, enforce max age
    const acquiredAt = token.acquiredAt ?? 0;
    return Date.now() - acquiredAt > MAX_TOKEN_AGE_MS;
  }
  return Date.now() > token.expiresAt;
}

// Periodic introspection for long-lived tokens
async function validateTokenPeriodically(
  token: TokenObj,
  introspectionEndpoint: string
): Promise<boolean> {
  const response = await fetch(introspectionEndpoint, {
    method: "POST",
    headers: { "Content-Type": "application/x-www-form-urlencoded" },
    body: `token=${token.accessToken}`,
  });
  const result = await response.json();
  return result.active === true;
}

Token Expiry Enforcement Across Agent Types

Different agent deployment patterns require different expiry strategies. The right approach depends on whether a human is available to re-authenticate:

Deployment Re-authentication Available? Recommended Max Token Age Refresh Strategy
Interactive CLI Yes (user present) 4-8 hours Silent refresh; re-auth on failure
CI/CD pipeline No (headless) Job duration + buffer Short-lived scoped token per job
Long-running daemon Maybe (operator on-call) 1 hour with auto-refresh Refresh + alert on failure
Multi-agent worker No (child process) Task duration + 5 min Scoped token from parent; no refresh
Bridge/remote session Yes (user at other end) 24 hours Refresh via bridge protocol

The key insight: token lifetime should match the task duration, not the maximum allowed by the authorization server. A CI/CD job that takes 10 minutes should not receive a 24-hour token, because those 23 hours and 50 minutes of unnecessary validity are pure attack surface.

Refresh Token Security

Refresh tokens are the crown jewels of the credential system. An access token grants temporary access; a refresh token grants the ability to generate new access tokens indefinitely. Refresh tokens require stricter protections:

Property Access Token Refresh Token
Lifetime Minutes to hours Days to months
Storage location Memory preferred, disk if needed Secure storage only
Rotation Replaced on refresh Should rotate with each use
Revocation impact Limited (short-lived) Critical (grants new access tokens)
Exposure in logs Token prefix only (fingerprint) Never log any portion
Transmission Bearer header per request Only to token endpoint

Refresh token rotation is a critical defense: each time a refresh token is used, the authorization server issues a new refresh token and invalidates the old one. If an attacker steals a refresh token, their first use of it triggers a rotation that invalidates the legitimate client's token. When the legitimate client tries to refresh, the failure signals a compromise.

Finding from Claude Code audit (Finding 3, CRITICAL): Subagents share parent's credential store. Subagents execute in the same process as the parent CLI. They share AppState, tool pools, and environment --- including full access to the credential storage. A malicious or compromised subagent can read ~/.claude/.credentials.json, exfiltrate tokens via allowed network tools, and fork child agents to establish persistence.

The Principle of Least Credential

Each agent should receive only the credentials necessary for its task, with the narrowest possible scope:

Agent Role Required Credentials Scoping Strategy
Code reviewer Model API (read), Repo (read-only) Scoped PAT with repo:read only
Test runner Model API (read) No external credentials
Deploy agent Model API (read), Cloud (deploy scope) Short-lived deploy token
MCP bridge Model API (read), MCP server auth Per-server scoped tokens

Implementation pattern: Credential delegation with scoped tokens.

from dataclasses import dataclass
from datetime import datetime, timedelta
from typing import FrozenSet

@dataclass(frozen=True)
class ScopedCredential:
    """A credential scoped to specific capabilities and lifetime."""
    token: str
    scopes: FrozenSet[str]
    expires_at: datetime
    agent_id: str
    parent_agent_id: str

def delegate_credential(
    parent_token: str,
    agent_id: str,
    required_scopes: FrozenSet[str],
    max_lifetime: timedelta = timedelta(hours=1)
) -> ScopedCredential:
    """
    Create a scoped credential for a child agent.

    In practice, this requires the authorization server to support
    token exchange (RFC 8693) or scope restriction on refresh.
    """
    # Request a new token with reduced scope
    scoped_token = exchange_token(
        parent_token,
        requested_scopes=required_scopes,
        audience=f"agent:{agent_id}",
        lifetime=max_lifetime,
    )

    return ScopedCredential(
        token=scoped_token.access_token,
        scopes=required_scopes,
        expires_at=datetime.utcnow() + max_lifetime,
        agent_id=agent_id,
        parent_agent_id="orchestrator",
    )

Environment variable credentials are visible in process listings. On Linux, any process running as the same user can read another process's environment from /proc/<pid>/environ. This means every credential passed as an environment variable is readable by every same-user process for the lifetime of the agent.

Project settings can inject environment variables. As discussed in Chapter 21 of Claude Code's analysis, project-level settings.json files can define environment variables that are applied after the trust dialog. A malicious repository could set LD_PRELOAD, NODE_OPTIONS, or PYTHONSTARTUP to inject code into subprocess execution --- but it could also set credential-like variables to confuse the agent's authentication logic.

Secure Alternatives to Environment Variables

Method Security Complexity Best For
Env vars Low (process-visible, inheritable) Trivial Quick dev, not production
File descriptors Medium (not in /proc/environ) Low CI/CD pipelines
Unix domain sockets High (authenticated, not persisted) Medium Local agent-to-service auth
Mounted secrets (K8s) High (tmpfs, auto-rotation) Medium Container deployments
Vault/HSM integration Very High (audited, rotated) High Enterprise production

File descriptor credential passing eliminates the /proc/environ exposure:

#!/usr/bin/env bash
set -euo pipefail

# Pass credential via file descriptor instead of env var
exec 3< <(vault kv get -field=token secret/ai-agent)
CLAUDE_CODE_OAUTH_TOKEN_FD=3 claude --resume
exec 3<&-  # close FD after agent exits

The credential exists only in the file descriptor, not in the process environment. It is not visible in /proc/<pid>/environ and is not inherited by child processes unless the file descriptor is explicitly passed.

9.9 Key Takeaways

The credential management story for AI agents is a story of platform fragmentation and silent degradation. The best-case scenario --- macOS Keychain with hardware-backed encryption --- protects credentials at a level comparable to native application secrets. The worst-case scenario --- plaintext JSON files on Linux servers, containers, and CI/CD pipelines --- is the default for most deployments.

The production audit findings are clear: credential storage is Phase 2 of the remediation plan, immediately after plugin supply chain hardening, because stored tokens are the primary target for attackers. Every other security mechanism --- permission systems, sandboxes, content trust --- is circumvented if the attacker can steal the agent's credentials and impersonate it directly.

Three principles should guide credential management for any AI agent system:

  1. Never store credentials in plaintext. Use platform credential managers with encrypted fallback. If plaintext is truly the only option, make it loud (user-visible warnings), time-limited (automatic expiry), and monitored (file access auditing).

  2. Enforce token lifetimes. Every token must have a maximum age, regardless of what the authorization server says. Immortal tokens are a vulnerability, not a feature.

  3. Scope credentials to the task. In multi-agent systems, each agent should receive only the credentials it needs, with the narrowest possible scope and shortest possible lifetime. The principle of least privilege applies to credentials as much as to permissions.

Chapter 10 examines the specific case of JWT tokens in agent systems --- how signature verification failures and unbounded refresh delays create exploitable attack chains even when the credential storage is secure.
