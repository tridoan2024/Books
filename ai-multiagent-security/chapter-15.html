Chapter 15: Multi-Agent Architecture Patterns

The shift from single AI agents to multi-agent systems represents the most consequential architectural change in the AI application landscape since the introduction of tool use. A single agent operating in a loop -- read prompt, reason, call tools, return result -- is conceptually simple. Its security properties are analyzable because there is one decision-maker, one context window, one set of permissions. Multi-agent systems shatter this simplicity. Multiple reasoning processes operate simultaneously, communicate through natural language channels, delegate authority across trust boundaries, and aggregate results from potentially compromised peers. Every architectural pattern for organizing these agents introduces distinct security trade-offs that practitioners must understand before they can defend.

This chapter catalogs the four dominant multi-agent architecture patterns -- orchestrator-worker, peer-to-peer, hierarchical, and swarm -- and analyzes the security implications of each. We draw on production implementations from Claude Code's subagent system, LangGraph's multi-agent orchestration, CrewAI's role-based agents, Microsoft AutoGen's conversation patterns, and the pyramid team model used in production coding assistants. The goal is not to rank patterns but to give security architects the vocabulary and threat models needed to evaluate any multi-agent deployment.

15.1 Why Multi-Agent? The Security Motivation

Before examining patterns, we must understand why multi-agent architectures exist -- and why security is paradoxically both a motivation for and a victim of the multi-agent approach.

The Single-Agent Ceiling

A single agent with full authority -- read, write, execute, browse -- is a monolithic security risk. If it is compromised through prompt injection (as detailed in Chapters 12-14), the attacker gains access to every capability the agent possesses. There is no containment. The blast radius is the entire capability set.

Multi-agent systems were conceived, in part, to address this. By splitting capabilities across specialized agents, each with restricted authority, the compromise of any single agent limits the blast radius to that agent's capability set. A read-only code reviewer that is compromised by a malicious file cannot write to the filesystem or execute commands -- it can only produce misleading results. This is the principle of least authority applied to AI systems, and it is a genuine security improvement.

But multi-agent systems also introduce new attack surfaces that do not exist in single-agent architectures:

Attack Surface Single Agent Multi-Agent
Prompt injection One target N targets, each with different resistance
Confused deputy Not applicable Parent acts on compromised subagent's recommendations
Result poisoning Output only Intermediate results influence other agents
Authority amplification Fixed capability set Capability escalation through delegation chains
Consensus manipulation Not applicable Majority vote can be corrupted
Resource exhaustion Linear cost Exponential cost through recursive spawning
Communication channel attacks Not applicable Message injection, replay, interception

The net security effect depends entirely on the architecture pattern chosen and how rigorously its security properties are enforced. A well-designed orchestrator-worker system with strict isolation is more secure than a single omnipotent agent. A poorly designed peer-to-peer system with unrestricted communication may be less secure than either.

15.2 Pattern 1: Orchestrator-Worker

The orchestrator-worker pattern is the most common multi-agent architecture in production systems. A single orchestrator agent receives the user's request, decomposes it into subtasks, dispatches each subtask to a specialized worker agent, and aggregates the results into a unified response.

    O -->|"Task: Verify tests"| W3["Worker: Test Runner<br/>(Read, Bash)"]

    W2 -->|"Result: 1 vulnerability"| O
    W3 -->|"Result: 94% passing"| O

Claude Code implements this pattern through its AgentTool. The parent agent (orchestrator) dispatches subagents (workers) with type-specific tool schemas: the code-reviewer gets Read, Grep, and Glob; the security-reviewer adds restricted Bash; the explorer gets read-only Bash. Each worker operates in an isolated context window with no access to the parent's conversation history.

Security Properties

Centralized control. The orchestrator is the single point of authority. All delegation decisions flow through it, all results return to it, all user-facing output is composed by it. This centralization is a security advantage: there is one place to enforce policy, one place to validate results, one place to audit decisions.

Star topology trust model. Workers trust the orchestrator (they follow its delegation prompts), and the orchestrator must evaluate worker results. Workers do not communicate with each other. This eliminates cross-worker contamination -- a compromised code-reviewer cannot directly influence the security-reviewer's analysis.

Clear authority boundaries. Each worker has a defined capability set enforced through tool schema filtering. The orchestrator assigns capabilities at dispatch time and cannot change them during execution (except through the SendMessage pattern, which we analyze in Chapter 17).

Security Weaknesses

Single point of failure. If the orchestrator is compromised through prompt injection, the entire system is compromised. The orchestrator has full authority and can dispatch workers with any configuration, aggregate results deceptively, and present fabricated output to the user. All the worker-level isolation in the world is irrelevant if the orchestrator is the compromised component.

Aggregation vulnerability. The orchestrator combines results from multiple workers using LLM reasoning, not formal verification. A compromised worker can embed prompt injection payloads in its result that influence the orchestrator's aggregation logic. This is the result aggregation poisoning attack we examine in depth in Chapter 17.

Over-delegation of context. The orchestrator formulates delegation prompts from its full context. A well-intentioned orchestrator may over-share, including sensitive information from the user's request in the delegation prompt. A malicious file that has already injected into the orchestrator's context can cause it to include credentials or secrets in worker delegation prompts.

Real-World Implementation: Claude Code's AgentTool

Claude Code's subagent dispatch in tools/AgentTool/runAgent.ts implements the orchestrator-worker pattern with the following security controls:

// Simplified from Claude Code's subagent dispatch
interface AgentConfig {
  type: "code-reviewer" | "security-reviewer" | "explore" | "general-purpose";
  tools: ToolDefinition[];      // Schema-level filtering
  model: "opus" | "sonnet" | "haiku";
  maxTurns: number;
  systemPrompt: string;         // Role-specific behavioral constraints
  permissionRules: Rule[];      // Layer 3 runtime enforcement
}

function dispatchWorker(config: AgentConfig, task: string): Promise<Result> {
  // Worker gets ONLY the tools in config.tools
  // Worker gets a FRESH context (no parent history)
  // Worker is rate-limited by maxTurns
  const apiRequest = {
    model: config.model,
    tools: config.tools,          // Only these tools exist for the worker
    system: config.systemPrompt,
    messages: [{ role: "user", content: task }],
    max_tokens: 16384,
  };
  return executeAgent(apiRequest, config.permissionRules);
}

The security audit (Finding #3, CVSS 7.8, CWE-269) identified that workers execute in the same OS process as the orchestrator. There is no process-level isolation -- a worker with Bash access that achieves command injection operates with the same filesystem permissions as the orchestrator. The tool schema filtering prevents the worker from asking the API for unauthorized tools, but it does not prevent a compromised Bash command from accessing files or network resources outside the worker's intended scope.

Hardening the Orchestrator-Worker Pattern

Control Implementation What It Defends Against
Tool schema filtering Remove unauthorized tools from API call Workers calling undefined tools
Context isolation Fresh context per worker, no parent history Information leakage across workers
Result size limits Cap worker output at N tokens Context flooding of orchestrator
Process isolation Fork workers into sandboxed child processes OS-level capability escalation
Result validation Cross-reference worker claims against filesystem Fabricated results
Delegation prompt minimization Include only task-relevant context Over-sharing sensitive data
Aggregation hardening Structured output schemas, not free-text Prompt injection through results

15.3 Pattern 2: Peer-to-Peer

In the peer-to-peer pattern, agents communicate directly with each other without a central orchestrator. Each agent has a role, and agents collaborate by passing messages in a conversation graph. LangGraph and Microsoft AutoGen implement variants of this pattern.

    A2 <-->|"Messages"| A3["Agent: Tester<br/>(Read, Bash)"]
    A3 <-->|"Messages"| A1
    A1 <-->|"Messages"| A3

    style A2 fill:#4CAF50,color:#fff
    style A3 fill:#FF9800,color:#fff

Security Properties

No single point of failure. Unlike orchestrator-worker, compromising one agent does not give the attacker control over the entire system. Each agent has its own authority, and there is no centralized aggregation point that a single compromised agent can manipulate.

Distributed trust. Each agent evaluates messages from other agents through its own reasoning. A compromised planner that sends a malicious message to the coder is subject to the coder's own prompt injection resistance. The message must survive two layers of LLM reasoning -- the compromised agent's message construction and the receiving agent's interpretation.

Security Weaknesses

Unbounded communication surface. Every agent can send messages to every other agent. In a system with N agents, there are N(N-1) directed communication channels. Each channel is a potential injection vector. Compared to the orchestrator-worker pattern (N channels to/from the orchestrator), the attack surface grows quadratically.

No authority hierarchy. Without a central orchestrator enforcing policy, authority decisions are distributed. If the coder agent decides to write a file based on the planner's message, there is no higher authority to validate that decision. In the orchestrator-worker pattern, the orchestrator can apply policy before acting on worker results. In peer-to-peer, each agent is its own policy enforcer -- and each might enforce policy differently.

Consensus problems. When agents disagree, there is no clear mechanism for resolution. A compromised agent that disagrees with a legitimate agent creates a deadlock or forces a vote. If the compromised agent can recruit one more agent to its position (through persuasive messaging or further injection), it can achieve majority consensus on an incorrect or malicious action.

Message replay and ordering. In conversation-based peer-to-peer systems, message ordering matters. An agent that can inject messages out of order (or replay previous messages) can manipulate other agents' reasoning. There is no sequence numbering, no message authentication, no replay protection in natural-language conversation channels.

Real-World Vulnerability: AutoGen Conversation Poisoning

Microsoft AutoGen implements a GroupChat pattern where agents take turns speaking in a shared conversation. Each agent sees the full conversation history. This creates a vulnerability where a compromised agent's message permanently contaminates the shared context:

# AutoGen GroupChat (simplified)
class GroupChat:
    def __init__(self, agents: list[Agent]):
        self.agents = agents
        self.messages: list[Message] = []  # Shared conversation history

    def run(self, task: str):
        self.messages.append(Message(role="user", content=task))
        while not self.is_complete():
            speaker = self.select_next_speaker()
            # Speaker sees ALL previous messages -- including 
            # any injection payloads from compromised agents
            response = speaker.generate(self.messages)
            self.messages.append(response)  # Permanently in history

If Agent A is compromised and produces a response containing a prompt injection payload, that payload is permanently added to the shared conversation history. Every subsequent agent that speaks processes the full history, including the payload. The contamination is persistent -- it cannot be removed without restarting the conversation.

This is analogous to stored XSS (CWE-79) in web applications: the injection is stored in shared state and executed every time a new participant loads that state.

When to Use Peer-to-Peer (and When Not To)

Use Case Appropriate? Rationale
Debate/adversarial testing Yes Agents should challenge each other
Code review committee Somewhat Multiple perspectives, but needs a chair
Autonomous task execution No No authority hierarchy creates security chaos
Security-sensitive operations No Cannot enforce least authority without hierarchy

15.4 Pattern 3: Hierarchical

The hierarchical pattern extends orchestrator-worker to multiple levels. A top-level orchestrator delegates to mid-level coordinators, which in turn delegate to leaf-level workers. This models the structure of large organizations -- and their security challenges.

Architecture

    CEO --> PM3["QA Coordinator<br/>(Read, Bash)"]

    PM1 --> W1["API Developer<br/>(Read, Write, Edit)"]
    PM1 --> W2["DB Developer<br/>(Read, Write, Bash)"]

    PM2 --> W4["Style Developer<br/>(Read, Write)"]

    PM3 --> W6["Integration Tester<br/>(Read, Bash)"]

Security Properties

Progressive authority restriction. The hierarchy enables a natural authority gradient: the lead orchestrator has full authority, coordinators have domain-scoped authority, and leaf workers have minimal authority. This models the principle of least authority more naturally than flat orchestrator-worker, where all workers are at the same level.

Blast radius containment by subtree. If a backend coordinator is compromised, the blast radius is limited to the backend subtree (API Developer, DB Developer). The frontend and QA subtrees are unaffected. In a flat orchestrator-worker pattern, a compromised orchestrator affects all workers.

Delegation audit trail. Each level of delegation produces a logged interaction. Tracing a security-relevant action through the hierarchy produces a clear chain: lead orchestrator delegated to backend coordinator, which delegated to DB developer, which executed the command. This audit trail is richer than flat dispatch.

Security Weaknesses

Transitive trust amplification. The lead orchestrator trusts the backend coordinator, and the backend coordinator trusts the DB developer. But the lead orchestrator has no direct relationship with the DB developer -- it trusts the coordinator to have made good delegation decisions. If the coordinator is compromised, it can dispatch malicious workers that the lead orchestrator never directly evaluates.

Deep injection propagation. An injection payload can traverse multiple hierarchy levels, as we analyzed in the Claude Code security book (Chapter 20). A malicious file read by a leaf worker propagates through the worker's result to the coordinator, through the coordinator's result to the lead orchestrator. At each level, the payload is embedded in increasingly legitimate-looking context, making detection progressively harder.

Authority gap magnification. In a flat system, the authority gap between worker and orchestrator is one level. In a hierarchy, the gap between a leaf worker and the lead orchestrator can be three or more levels. The confused deputy attack (Chapter 17) becomes more potent because the leaf worker's recommendation passes through multiple interpretation layers before reaching the entity with full authority.

Coordination overhead as attack surface. Mid-level coordinators add communication channels. A hierarchy with 3 coordinators and 6 workers has 9 vertical channels (3 coordinator-to-lead, 6 worker-to-coordinator). Each is an injection vector. The orchestrator-worker pattern for the same 6 workers has only 6 channels.

Progressive Authority Restriction: The Ideal

The hierarchy's greatest security feature -- progressive authority restriction -- is also its most challenging to implement correctly. The ideal model restricts capabilities at each level:

Level Role Tools Model Max Turns
0 Lead Orchestrator All Opus Unlimited
1 Domain Coordinator Domain tools + Agent Opus/Sonnet 30
2 Leaf Worker Task-specific tools Sonnet/Haiku 15

The critical constraint is that coordinators can only dispatch workers with fewer capabilities than themselves. A backend coordinator with Read, Write, and Bash cannot dispatch a worker with Web access, because the coordinator itself does not have Web access. This prevents authority amplification through delegation -- a property that must be enforced at the dispatch layer, not trusted to the coordinator's reasoning.

Claude Code's security audit (Finding #14, CWE-674) found that recursive subagent forking had a weak depth guard. The forkSubagent.ts implementation at line 311 used a depth counter that could be manipulated in edge cases. The remediation action plan prescribed a hard fork depth counter with a maximum of 3 levels and a maximum concurrent subagent limit -- exactly the controls needed for a secure hierarchical pattern.

15.5 Pattern 4: Swarm

The swarm pattern is the most autonomous and the most dangerous. Agents can spawn other agents dynamically based on the task requirements. There is no fixed topology -- the system self-organizes. The number of agents, their roles, and their communication patterns emerge at runtime.

The critical difference from the hierarchical pattern is that the topology is not predetermined. Agent C decided at runtime to spawn Agent F based on its analysis of the subtask. The system designer did not anticipate Agent F's existence. This dynamic spawning is what makes swarms powerful -- and what makes them extremely difficult to secure.

We dedicate all of Chapter 18 to swarm security. Here, we summarize the pattern's key characteristics:

Dynamic topology. The number of agents and their relationships are determined at runtime. Security analysis at design time can only reason about worst-case scenarios, not specific topologies.

Emergent behavior. The collective behavior of the swarm is not directly programmed. It emerges from individual agent decisions. This makes it difficult to predict, difficult to audit, and difficult to constrain without over-restricting individual agents.

Exponential resource risk. Without hard limits on spawning, a swarm can grow exponentially. A seed agent that spawns 3 workers, each of which spawns 3 more, reaches 40 agents in 4 levels and 121 in 5. At current API costs, this translates to hundreds of dollars per user request.

15.6 The Pyramid Team Model

The pyramid team model is a production-tested variant of the hierarchical pattern designed specifically for AI coding assistants. It was developed to address the coordination challenges of having multiple AI agents work on a single codebase simultaneously. The model draws on military command structure: a lead orchestrator ("general") commands a small number of specialized coordinators ("officers"), each of whom directs leaf workers ("soldiers").

Security Properties Unique to the Pyramid Model

Domain isolation through worktrees. Each coordinator and its workers operate in a separate git worktree. Backend changes cannot conflict with frontend changes at the filesystem level. This prevents a compromised backend worker from modifying frontend code -- the files simply do not exist in its worktree.

Merge-gate review. The lead agent reviews all coordinator outputs before merging them into the main branch. This is a human-in-the-loop checkpoint (or more precisely, a lead-agent-in-the-loop checkpoint) that can detect malicious modifications, inconsistent changes, or introduced vulnerabilities.

Bounded concurrency. The pyramid model enforces a maximum number of concurrent coordinators (typically 3-4) and workers per coordinator (typically 2-3). This prevents the exponential spawning problem of unconstrained swarms. The maximum agent count is bounded by coordinators * workers_per_coordinator, which is typically 9-12.

Role-based authority. Each position in the pyramid has a defined role with specific tool access. Workers have the narrowest access (often just Read, Write, Edit for their domain). Coordinators add delegation capability. The lead adds full authority and review responsibility.

Security Weaknesses Unique to the Pyramid Model

Lead agent as single point of failure. Like all hierarchical systems, the pyramid model concentrates risk at the top. A compromised lead agent can approve malicious merges, dispatch compromised coordinators, and fabricate user-facing output.

Coordinator trust assumption. The lead trusts coordinators to make good delegation decisions within their domain. A compromised backend coordinator could dispatch a worker with instructions to introduce a subtle backdoor -- and the lead's code review might not catch it if the change is technically valid.

Worktree cross-access. As analyzed in the Claude Code security audit (Chapter 19 of the Claude Code security book), git worktrees share the same .git object store. A worker in the backend worktree can run git show frontend-branch:src/components/Login.tsx to read files from the frontend worktree. This cross-worktree read access undermines the domain isolation that worktrees are supposed to provide.

Production Implementation Considerations

Consideration Recommendation Rationale
Max pyramid depth 3 levels (lead, coordinator, worker) Deeper hierarchies amplify confused deputy risk
Max concurrent agents 9-12 total Rate limiting, cost control, audit feasibility
Coordinator capabilities Domain tools + delegation No full Bash -- coordinators coordinate, not execute
Worker capabilities Minimal for task Leaf workers should not delegate further
Merge review Lead reviews all before merge Human/lead checkpoint for all changes
Worktree isolation Separate branch per coordinator Filesystem-level domain isolation
Cross-worktree access Block git show/log of other branches Prevent domain isolation bypass

The Default Recommendation

For most production deployments, the orchestrator-worker pattern with process-level isolation is the recommended starting point. It provides:

  1. Centralized policy enforcement -- one place to apply security rules
  2. Clear trust hierarchy -- workers are less trusted than the orchestrator
  3. Analyzable communication -- star topology with N channels
  4. Mature implementation -- Claude Code, LangGraph, and most production systems use this pattern
  5. Auditable delegation -- one-hop trace from orchestrator to any worker

The hierarchical pattern (and its pyramid variant) is appropriate when domain isolation is needed -- typically in multi-team or multi-domain codebases where different parts of the system have different security requirements.

The peer-to-peer pattern is appropriate only for adversarial testing and debate scenarios where agents should challenge each other's findings.

The swarm pattern should be used with extreme caution and only with the hard resource limits described in Chapter 18.

15.8 Cross-Cutting Security Concerns

Regardless of the pattern chosen, several security concerns apply universally to all multi-agent architectures.

Identity and Attribution

In a multi-agent system, every action (file write, command execution, network request) should be attributable to a specific agent. This requires:

  • Agent identifiers assigned at dispatch time and logged with every tool call
  • Delegation chains recording which agent spawned which
  • Action provenance linking every filesystem change to the agent that made it

Without attribution, post-incident forensics becomes impossible. "Which agent wrote the backdoor?" is unanswerable if agents are not individually identified.

Resource Budgets

Every multi-agent deployment needs hard resource limits:

# Resource budget per agent session
@dataclass
class AgentBudget:
    max_turns: int = 30           # Maximum reasoning iterations
    max_tokens: int = 100_000     # Maximum total token consumption
    max_tool_calls: int = 50      # Maximum tool invocations
    max_wall_time: int = 300      # Maximum seconds of execution
    max_child_agents: int = 3     # Maximum subagent spawns
    max_output_size: int = 10_000 # Maximum characters in result

These limits serve dual purposes: cost control and security. An agent under prompt injection influence that enters an infinite loop (reading files repeatedly to exfiltrate data, spawning recursive subagents, or flooding the orchestrator's context) is stopped by budget exhaustion rather than relying on the compromised agent's own judgment.

Secure Defaults

The most secure multi-agent configuration is the most restrictive one that still accomplishes the task. Secure defaults mean:

  • Workers start with no tools and gain them through explicit configuration
  • Communication channels are closed by default and opened through explicit policy
  • Spawning is disabled by default and enabled only for designated agent types
  • Authority is minimal by default and escalated only with justification

These defaults invert the common pattern of starting with full capability and trying to restrict it. As we learned from decades of operating system security, it is far easier to grant additional permissions than to revoke excessive ones after the fact.

15.9 Key Takeaways

Multi-agent architecture is a security decision, not just an engineering decision. The pattern you choose determines your attack surface, your blast radius model, your audit complexity, and your ability to enforce least authority.

  1. Orchestrator-worker is the secure default. Centralized control, star topology, clear trust hierarchy.
  2. Hierarchies enable progressive authority restriction but amplify confused deputy risk and injection propagation depth.
  3. Peer-to-peer creates quadratic attack surface and should be reserved for adversarial scenarios.
  4. Swarms create exponential risk and require hard resource limits at every level.
  5. The pyramid team model is a production-hardened hierarchical variant with worktree isolation and merge gates.
  6. All patterns require identity attribution, resource budgets, and secure-by-default configuration.
