Chapter 10: JWT Security in Agent Systems

Chapter 9 examined the broad challenge of credential management for AI agents --- OAuth flows, storage mechanisms, and the plaintext problem. This chapter narrows the focus to a specific token format that dominates agent authentication: JSON Web Tokens. JWTs are the lingua franca of modern authentication, and their misuse in AI agent systems creates a distinct class of vulnerabilities that traditional JWT security guidance does not address.

The core problem is deceptively simple: AI agents decode JWTs to read claims (expiry, scopes, subject) but frequently skip signature verification. In a traditional web application, this is a known anti-pattern with well-documented consequences. In an AI agent system, the consequences are amplified by the agent's autonomous behavior --- an agent that trusts an unverified JWT may schedule incorrect refresh timers, maintain revoked sessions indefinitely, or grant itself capabilities based on forged claims.

This chapter dissects every JWT vulnerability relevant to AI agent systems, using Claude Code's bridge authentication as the primary case study. We trace the full attack chain from unverified JWT decode through unbounded refresh delays to session persistence attacks, and we build the defense architecture that production systems require.

10.1 JWT Fundamentals for Agent Systems

A JSON Web Token consists of three base64url-encoded segments separated by dots:

header.payload.signature

graph LR
    subgraph JWT["JWT Structure"]
        H["Header<br/>{alg: RS256, kid: abc123}"]
        P["Payload<br/>{sub: user123, exp: 1712000000,<br/>scope: read write}"]
        S["Signature<br/>RSA-SHA256(header.payload,<br/>server_private_key)"]
    end

    H --> DECODE["Base64url Decode"]
    P --> DECODE
    S --> VERIFY{"Signature<br/>Verification"}

    VERIFY -->|"Valid"| TRUST["Trust Claims"]
    VERIFY -->|"Invalid"| REJECT["Reject Token"]
    VERIFY -->|"Skipped"| DANGER["Trust Unverified Claims<br/>(VULNERABLE)"]

    style DANGER fill:#cc4444,color:#fff
    style TRUST fill:#2d6a2d,color:#fff
    style REJECT fill:#b8860b,color:#fff

The signature is the security mechanism. Without verifying it, the header and payload are just base64-encoded JSON that anyone can create. The JWT specification (RFC 7519) is explicit: "JWS MUST be validated before trusting any claims."

In agent systems, tokens serve multiple purposes beyond simple authentication:

JWT Use Case Claims Used Verification Required?
API authentication sub, scope, aud Yes --- server verifies
Session management exp, iat, jti Yes --- both sides should verify
Refresh scheduling exp Yes, but often skipped client-side
Capability delegation scope, custom claims Yes --- defines agent permissions
Inter-agent auth sub, iss, custom claims Yes --- agent-to-agent trust

The critical insight: even when the server verifies the JWT for API calls, the client also reads JWT claims to make local decisions (when to refresh, what capabilities are available, which session to use). If the client does not verify the signature, those local decisions are based on unverified data.

10.2 The Decode-Only Vulnerability

The Pattern

The most common JWT vulnerability in AI agent systems is decoding the payload without verifying the signature. The pattern looks like this:

// VULNERABLE: Decode without verify
export function decodeJwtPayload(token: string): unknown | null {
  const jwt = token.startsWith("sk-ant-si-")
    ? token.slice("sk-ant-si-".length)
    : token;
  const parts = jwt.split(".");
  if (parts.length !== 3 || !parts[1]) return null;
  try {
    return JSON.parse(
      Buffer.from(parts[1], "base64url").toString("utf8")
    );
  } catch {
    return null;
  }
}

This code splits the JWT on ., takes the second segment (payload), base64url-decodes it, and parses it as JSON. The signature (third segment) is completely ignored. The function is used to extract the exp (expiry) claim for scheduling token refresh timers.

This exact pattern was identified in Claude Code's bridge authentication system as Finding 5 (HIGH, CVSS 7.5, CWE-347: Improper Verification of Cryptographic Signature):

"JWT tokens from bridge sessions are decoded using simple base64url parsing without any signature verification. The decodeJwtPayload() function strips the sk-ant-si- prefix, splits on ., and base64-decodes the payload --- but never verifies the signature in parts[2]. This means any entity that can inject or modify a JWT in transit can alter claims (exp, sub, scope) without detection on the client side."

Why Developers Skip Verification

The pattern is pervasive because client-side JWT verification introduces real complexity:

  1. Key management. Verification requires the server's public key or JWKS endpoint URL. The client must fetch, cache, and rotate these keys.
  2. Algorithm selection. The client must know which algorithms are acceptable (RS256, ES256) and reject dangerous ones (none, symmetric HS256 with an asymmetric key).
  3. Clock skew. Token expiry checks must tolerate reasonable clock differences between client and server.
  4. Library dependencies. JWT verification libraries add dependency surface area and potential vulnerabilities.

The rationalization is: "The server verifies the JWT on every API call. Client-side verification is redundant." This is true for authentication but false for every local decision the client makes based on JWT claims.

10.3 The Unbounded Refresh Delay Attack

The decode-only pattern creates a specific, exploitable attack chain in agent systems: the unbounded refresh delay attack.

Attack Mechanics

sequenceDiagram
    participant Attacker as Attacker (MITM)
    participant Agent as AI Agent
    participant Server as Auth Server

    Agent->>Server: Request session JWT
    Server->>Attacker: Legitimate JWT (exp: +1 hour)
    Attacker->>Attacker: Forge JWT with exp: +10 years
    Attacker->>Agent: Modified JWT (exp: +10 years)
    Agent->>Agent: decodeJwtPayload() — no signature check
    Agent->>Agent: Schedule refresh in ~10 years
    Note over Agent: Token NEVER refreshes
    Note over Agent: Server revokes token (compromised)
    Agent->>Server: API call with revoked token
    Server->>Agent: 401 Unauthorized
    Note over Agent: Agent retries once, then fails
    Note over Agent: User must manually re-authenticate

The attack proceeds:

  1. An attacker in a position to modify traffic (corporate proxy, compromised DNS, man-in-the-middle on the bridge connection) intercepts the JWT returned by the authentication server.
  2. The attacker decodes the JWT, modifies the exp claim to a far-future timestamp, and re-encodes it (signature becomes invalid, but the client does not check).
  3. The agent's decodeJwtExpiry() reads the forged exp claim and schedules the refresh timer for years in the future.
  4. The token is eventually revoked server-side (because it was compromised), but the agent continues using it until the server returns a 401.
  5. The agent has no graceful recovery path --- it retries once, fails, and the user must manually re-authenticate.

The Reverse Attack: Refresh Loop DoS

The same vulnerability enables the opposite attack:

sequenceDiagram
    participant Attacker as Attacker (MITM)
    participant Agent as AI Agent
    participant Server as Auth Server

    Agent->>Server: Request session JWT
    Server->>Attacker: Legitimate JWT (exp: +1 hour)
    Attacker->>Attacker: Forge JWT with exp: +1 second
    Attacker->>Agent: Modified JWT (exp: near-past)
    Agent->>Agent: decodeJwtPayload() — no signature check
    Agent->>Agent: Token appears expired
    Agent->>Server: Immediate refresh request
    Server->>Agent: New JWT
    Agent->>Agent: Decode again — still forged?
    Note over Agent: If MITM persists: infinite refresh loop
    Note over Server: Rate limiting may lock account

A near-past exp claim causes the agent to immediately attempt a refresh. If the MITM is persistent, every new token is also forged with a near-past expiry, creating a tight refresh loop that: - Amplifies load on the authentication server - May trigger rate limiting or account lockout - Degrades agent performance (constant auth overhead) - Generates excessive logging and telemetry

Production Remediation: The Clamp Pattern

The security action report provided a specific patch for this vulnerability --- a delay clamping function that bounds the refresh timer regardless of the JWT's claims:

/** Maximum allowed token lifetime — prevents forged far-future exp. */
const MAX_TOKEN_LIFETIME_MS = 24 * 60 * 60 * 1000; // 24 hours

/** Minimum refresh delay — prevents near-past exp refresh loops. */
const MIN_REFRESH_DELAY_MS = 10_000; // 10 seconds

/**
 * Clamp a raw refresh delay derived from an UNVERIFIED JWT exp claim.
 * Since decodeJwtPayload() does not verify the signature, a forged token
 * could carry an extreme exp value. This bounds the delay to a safe range.
 */
function clampTokenRefreshDelay(rawDelayMs: number): number {
  if (rawDelayMs <= 0) return 0;              // Expired: refresh now
  if (rawDelayMs < MIN_REFRESH_DELAY_MS) {
    return MIN_REFRESH_DELAY_MS;              // Floor: prevent tight loops
  }
  if (rawDelayMs > MAX_TOKEN_LIFETIME_MS) {
    return MAX_TOKEN_LIFETIME_MS;             // Ceiling: prevent suppression
  }
  return rawDelayMs;
}

This is a defense-in-depth patch, not a fix. The underlying vulnerability (decode without verify) remains. The clamp limits the impact of exploitation but does not prevent it. An attacker can still set the refresh delay to anywhere within the 10-second to 24-hour range.

10.4 JWKS-Based Signature Verification

The proper fix is client-side signature verification using JSON Web Key Sets (JWKS).

JWKS Architecture

sequenceDiagram
    participant Agent as AI Agent
    participant JWKS as JWKS Endpoint
    participant Auth as Auth Server

    Agent->>JWKS: Fetch /.well-known/jwks.json
    JWKS->>Agent: { keys: [{ kid: "abc", kty: "RSA", ... }] }
    Agent->>Agent: Cache JWKS (with TTL)

    Auth->>Agent: JWT with header { kid: "abc", alg: "RS256" }
    Agent->>Agent: Look up key by kid in cached JWKS
    Agent->>Agent: Verify signature with public key
    Agent->>Agent: Validate exp, iat, iss, aud claims
    Agent->>Agent: Trust verified claims

    Note over Agent: Key rotation
    Auth->>Agent: JWT with header { kid: "def", alg: "RS256" }
    Agent->>Agent: kid "def" not in cache
    Agent->>JWKS: Re-fetch JWKS (cache miss)
    JWKS->>Agent: { keys: [{ kid: "def", ... }, { kid: "abc", ... }] }
    Agent->>Agent: Verify with new key

Implementation

import { createPublicKey, verify } from "crypto";

interface JWK {
  kid: string;
  kty: string;
  alg: string;
  n: string;    // RSA modulus
  e: string;    // RSA exponent
  use?: string;
}

interface JWKSCache {
  keys: Map<string, JWK>;
  fetchedAt: number;
  ttlMs: number;
}

class JWKSVerifier {
  private cache: JWKSCache | null = null;
  private readonly jwksUrl: string;
  private readonly ttlMs = 3600_000; // 1 hour cache
  private readonly allowedAlgorithms = new Set(["RS256", "ES256"]);

  constructor(jwksUrl: string) {
    this.jwksUrl = jwksUrl;
  }

  async verifyToken(token: string): Promise<JWTPayload> {
    const [headerB64, payloadB64, signatureB64] = token.split(".");
    if (!headerB64 || !payloadB64 || !signatureB64) {
      throw new Error("Malformed JWT: expected 3 segments");
    }

    // Decode header to get kid and alg
    const header = JSON.parse(
      Buffer.from(headerB64, "base64url").toString()
    );

    // Algorithm restriction — block "none" and unexpected algorithms
    if (!this.allowedAlgorithms.has(header.alg)) {
      throw new Error(
        `JWT algorithm ${header.alg} not in allowed set`
      );
    }

    // Fetch key matching kid
    const key = await this.getKey(header.kid);
    if (!key) {
      throw new Error(`No JWKS key found for kid: ${header.kid}`);
    }

    // Verify signature
    const data = `${headerB64}.${payloadB64}`;
    const signature = Buffer.from(signatureB64, "base64url");
    const publicKey = createPublicKey({ key, format: "jwk" });

    const isValid = verify(
      header.alg === "RS256" ? "RSA-SHA256" : "SHA256",
      Buffer.from(data),
      publicKey,
      signature
    );

    if (!isValid) {
      throw new Error("JWT signature verification failed");
    }

    // Parse and validate claims
    const payload = JSON.parse(
      Buffer.from(payloadB64, "base64url").toString()
    );
    this.validateClaims(payload);
    return payload;
  }

  private validateClaims(payload: JWTPayload): void {
    const now = Math.floor(Date.now() / 1000);
    const clockSkew = 30; // 30 second tolerance

    if (payload.exp && payload.exp + clockSkew < now) {
      throw new Error("JWT expired");
    }
    if (payload.nbf && payload.nbf - clockSkew > now) {
      throw new Error("JWT not yet valid");
    }
    if (payload.iat && payload.iat - clockSkew > now) {
      throw new Error("JWT issued in the future");
    }
  }

  private async getKey(kid: string): Promise<JWK | null> {
    // Check cache first
    if (this.cache && Date.now() - this.cache.fetchedAt < this.ttlMs) {
      const cached = this.cache.keys.get(kid);
      if (cached) return cached;
    }

    // Cache miss or expired — re-fetch
    await this.refreshCache();
    return this.cache?.keys.get(kid) ?? null;
  }

  private async refreshCache(): Promise<void> {
    const response = await fetch(this.jwksUrl);
    if (!response.ok) {
      throw new Error(`JWKS fetch failed: ${response.status}`);
    }
    const jwks = await response.json();
    const keys = new Map<string, JWK>();
    for (const key of jwks.keys) {
      keys.set(key.kid, key);
    }
    this.cache = { keys, fetchedAt: Date.now(), ttlMs: this.ttlMs };
  }
}

Critical Verification Rules

Rule Why Consequence of Violation
Never accept alg: "none" Disables signature entirely Any token accepted as valid
Restrict to expected algorithms Prevents algorithm confusion attacks HS256 with RSA public key = forgeable
Match kid to JWKS key Ensures correct key for verification Wrong key = invalid signature accepted
Validate exp with clock skew Accounts for time differences Expired tokens accepted, or valid tokens rejected
Validate iss (issuer) Prevents cross-service token reuse Token from Service A accepted by Service B
Validate aud (audience) Ensures token was meant for this agent Token meant for different service accepted
Cache JWKS with bounded TTL Balances freshness vs. availability Stale keys = revoked keys still accepted

10.5 The Algorithm Confusion Attack

One of the most dangerous JWT attacks exploits the relationship between signing algorithms. It is particularly relevant to agent systems because agents often support multiple authentication providers, each potentially using different signing algorithms.

Background: Symmetric vs. Asymmetric Signing

JWT supports two families of signing algorithms:

  • Asymmetric (RS256, ES256): The server signs with a private key. The client verifies with the corresponding public key. The public key is... public. Anyone can obtain it from the JWKS endpoint. But only the server can sign new tokens.
  • Symmetric (HS256): The same secret is used to both sign and verify. Both parties must possess the shared secret.

The vulnerability arises when a verification library accepts the alg header from the JWT itself to decide which algorithm to use for verification, rather than enforcing the expected algorithm.

The Attack

graph TD
    subgraph Legitimate["Legitimate Flow"]
        L1["Server signs JWT with RS256<br/>(private key)"]
        L2["Agent verifies with RS256<br/>(public key from JWKS)"]
        L1 --> L2
    end

    subgraph Attack["Algorithm Confusion Attack"]
        A1["Attacker gets server's<br/>public key (from JWKS)"]
        A2["Attacker signs JWT with HS256<br/>using public key as HMAC secret"]
        A3["Vulnerable library sees alg: HS256<br/>and verifies with 'public key'<br/>as symmetric secret"]
        A4["Verification succeeds!<br/>Forged token accepted"]
        A1 --> A2 --> A3 --> A4
    end

    style A4 fill:#cc4444,color:#fff
    style L2 fill:#2d6a2d,color:#fff

The attack works because: 1. RS256 uses asymmetric cryptography: private key signs, public key verifies. 2. HS256 uses symmetric cryptography: the same secret signs and verifies. 3. The server's public key is... public. Anyone can obtain it from the JWKS endpoint. 4. If the verification library respects the alg header from the token (instead of enforcing the expected algorithm), an attacker can forge a token signed with HS256 using the public key as the HMAC secret.

Defense

// VULNERABLE: Trust the alg header from the token
const algorithm = jwtHeader.alg; // Attacker controls this!
verify(token, publicKey, { algorithms: [algorithm] });

// SECURE: Enforce expected algorithm, ignore token's alg claim
const EXPECTED_ALGORITHM = "RS256";
verify(token, publicKey, { algorithms: [EXPECTED_ALGORITHM] });

The fix is simple: never trust the alg header from the JWT. The verifying party should know which algorithm the server uses and enforce it, rejecting any token that claims a different algorithm.

For agent systems that authenticate against multiple providers, each with different algorithms, the agent must maintain a mapping of provider to expected algorithm:

const PROVIDER_ALGORITHMS: Record<string, string> = {
  "auth.anthropic.com": "RS256",
  "accounts.google.com": "RS256",
  "login.microsoftonline.com": "RS256",
  "github.com": "RS256",
};

function getExpectedAlgorithm(issuer: string): string {
  const alg = PROVIDER_ALGORITHMS[issuer];
  if (!alg) {
    throw new Error(`Unknown JWT issuer: ${issuer}`);
  }
  return alg;
}

This per-provider mapping ensures that the agent never accepts a token with an unexpected algorithm, even if the agent authenticates against multiple services with different configurations.

10.6 Token Prefix Leakage in Logs

A seemingly minor finding from the Claude Code audit illustrates how JWT security extends beyond cryptographic verification into operational practices:

Finding 41 (LOW, CWE-532: Insertion of Sensitive Information into Log File). Debug logging includes token prefixes:

logForDebugging(
  `[${label}:token] Could not decode JWT expiry ` +
  `for sessionId=${sessionId}, ` +
  `token prefix=${token.slice(0, 15)}...`
);

The token.slice(0, 15) exposes the token type (sk-ant-si- is 10 characters) plus 5 characters of the actual token. In aggregate, across many log entries, partial token exposure aids brute-force recovery.

Remediation: Use cryptographic fingerprints for token correlation.

import { createHash } from "crypto";

function tokenFingerprint(token: string): string {
  return createHash("sha256")
    .update(token)
    .digest("hex")
    .slice(0, 12);
}

logForDebugging(
  `[${label}:token] Could not decode JWT expiry ` +
  `for sessionId=${sessionId}, ` +
  `token fingerprint=${tokenFingerprint(token)}`
);

The SHA-256 fingerprint provides the same correlation utility (same token always produces the same fingerprint) without exposing any credential material. This pattern should be standard for any token logging in AI agent systems.

Token Logging Across the Agent Pipeline

The token prefix leakage problem extends beyond JWT debug logging. AI agents handle tokens at multiple points in their processing pipeline, and each point is a potential logging exposure:

Pipeline Stage What Gets Logged Risk Mitigation
Token acquisition Full token (if debug enabled) CRITICAL Never log full tokens; use fingerprints
Token storage Storage path, write success LOW Acceptable; no credential material
Token refresh Old and new token (if verbose) HIGH Fingerprints for both old and new
API request Authorization header CRITICAL Redact in HTTP client interceptors
Error handling Token in error context MEDIUM Strip tokens from error objects
Telemetry Session metadata MEDIUM Hash session identifiers

The defense pattern is consistent: replace every token value in every log path with its SHA-256 fingerprint. The fingerprint must be computed at the point of logging, not stored alongside the token, to avoid creating an additional credential-adjacent artifact.

10.7 Trusted Device Token Bypass

AI agents that integrate with enterprise environments often use device trust tokens --- long-lived tokens that attest the device is managed and compliant. The security of these tokens has direct implications for multi-agent systems where agents may run on untrusted infrastructure.

The Environment Variable Override

Claude Code's trusted device system reads device trust tokens from the macOS Keychain. However, an environment variable override exists:

function getTrustedDeviceToken(): string | null {
  // Env var takes precedence for testing/canary
  const envToken = process.env.CLAUDE_TRUSTED_DEVICE_TOKEN;
  if (envToken) {
    console.warn(
      "[trusted-device] Using CLAUDE_TRUSTED_DEVICE_TOKEN " +
      "from env var (overrides keychain)"
    );
    return envToken;
  }
  // Fall through to keychain read
  return readFromKeychain("trusted-device-token");
}

The environment variable bypasses the keychain entirely. In production, this is intended for testing and canary deployments. But as discussed in Chapter 9, project-level settings can inject environment variables. A malicious repository with:

{
  "env": {
    "CLAUDE_TRUSTED_DEVICE_TOKEN": "forged-device-token"
  }
}

could override the legitimate device trust token. The security action report recommended adding JWT expiry validation for environment-variable-sourced tokens:

function getTrustedDeviceToken(): string | null {
  const envToken = process.env.CLAUDE_TRUSTED_DEVICE_TOKEN;
  if (envToken) {
    // Validate JWT-format tokens are not expired
    const expiry = decodeJwtExpiry(envToken);
    if (expiry !== null) {
      const now = Math.floor(Date.now() / 1000);
      if (expiry < now) {
        console.warn(
          "[trusted-device] CLAUDE_TRUSTED_DEVICE_TOKEN " +
          "env var contains expired JWT, ignoring"
        );
        return readFromKeychain("trusted-device-token");
      }
    }
    console.warn(
      "[trusted-device] Using CLAUDE_TRUSTED_DEVICE_TOKEN " +
      "from env var (overrides keychain)"
    );
    return envToken;
  }
  return readFromKeychain("trusted-device-token");
}

Note: even this improved version still uses decodeJwtExpiry() without signature verification. The expiry check prevents the most obvious abuse (using an already-expired token) but does not prevent a forged token with a valid expiry. Full JWKS verification of the device trust token would require the JWKS endpoint for the device trust issuer.

10.8 JWT Security in Multi-Agent Token Exchange

When multiple agents cooperate, they need a mechanism to delegate authority. JWT provides this through token exchange (RFC 8693), where a parent agent's token is exchanged for a scoped child token.

The Token Exchange Flow

    participant STS as Security Token Service
    participant Child as Child Agent
    participant API as Protected API

Requirement Why Implementation

The Confused Deputy in Token Exchange

A critical risk in multi-agent token exchange is the confused deputy attack: a child agent uses its scoped token to perform an action that the parent did not intend, but that falls within the token's granted scope.

graph TD
    P["Parent Agent<br/>Full scope: read, write, delete"]
    P -->|"Delegate: scope=write"| C["Child Agent"]
    C -->|"Intended: write test results"| GOOD["Write test-results.json"]
    C -->|"Unintended: write malicious code"| BAD["Write malicious-payload.py"]

    style BAD fill:#cc4444,color:#fff
    style GOOD fill:#2d6a2d,color:#fff

The parent intended the child to write test results, but the write scope also permits writing arbitrary files. The token's scope is correct (the child has write permission), but the intent is violated.

Mitigation: Resource-scoped tokens. Instead of granting write as a broad capability, bind the token to specific resources:

{
  "sub": "child-agent-001",
  "scope": "write",
  "resource": "/test-results/*",
  "aud": "file-api",
  "exp": 1712000000,
  "act": {
    "sub": "parent-agent",
    "delegation_reason": "write test results"
  }
}

10.9 JWT Security Checklist for Agent Systems

The following checklist consolidates the security requirements discussed throughout this chapter into an actionable reference for agent developers and security engineers:

Check Priority Details
Client-side signature verification CRITICAL Verify via JWKS before trusting any claim
Algorithm restriction CRITICAL Enforce expected algorithm, reject none and unexpected
Refresh delay clamping HIGH Bound delays between min (10s) and max (24h)
Token expiry enforcement HIGH Validate exp with clock skew tolerance (30-60s)
iss and aud validation HIGH Ensure token is from expected issuer for expected audience

10.10 Key Takeaways

JWT security in agent systems goes beyond the standard web application guidance. The autonomous nature of AI agents means that JWT claims drive automated decisions --- refresh timing, capability assessment, session management --- without human review. Every unverified claim is a control input that an attacker can manipulate.

The production audit findings paint a clear picture:

  1. Decode-only is the default. In Claude Code's implementation, decodeJwtPayload() performs base64 decoding without any signature verification. This pattern exists because client-side verification adds complexity, and the rationalization that "the server verifies" feels sufficient. It is not.

  2. Unbounded refresh delays are exploitable. Without clamping, a forged exp claim can suppress token refresh indefinitely (far-future expiry) or cause refresh loops (near-past expiry). The clamp pattern --- bounding delays between a minimum and maximum --- is a necessary defense-in-depth measure.

  3. Token logging leaks credentials. Even logging 15 characters of a token prefix exposes the token type and partial credential material. Cryptographic fingerprints provide equivalent debugging utility without exposure.

  4. Multi-agent token exchange requires scope binding. When parent agents delegate to children, the delegated tokens must be scope-reduced, audience-bound, short-lived, and non-delegatable. Without these constraints, a compromised child agent inherits the parent's full authority.

The fundamental principle: treat every JWT claim as attacker-controlled until the signature is verified against a known, trusted key. This applies to all claims, including exp, iss, aud, and custom claims. The signature is the only thing that separates a JWT from a plain JSON object that anyone can create.
