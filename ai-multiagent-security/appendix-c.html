Appendix C: Threat Model Template for AI Agent Systems

This appendix provides a ready-to-use threat modeling template for AI applications, adapted from the STRIDE methodology introduced in Chapter 3. It includes trust boundary diagrams, data flow diagram templates, threat enumeration worksheets, and worked examples. Security architects can use this template directly for threat modeling AI CLI agents, multi-agent orchestrators, RAG pipelines, and autonomous coding assistants.

The template is designed to be completed iteratively. Start with Section 1 (System Description), work through Section 2 (Trust Boundaries), enumerate threats in Section 3 (STRIDE Worksheet), chain them in Section 4 (Attack Chain Analysis), and prioritize mitigations in Section 5 (Remediation Plan). A complete worked example for a multi-agent coding assistant is provided in Section 6.

3.3 Severity Scoring Guide

Use this matrix to convert Likelihood x Impact into a severity rating. Align with your organization's risk framework.

Impact: Low Impact: Medium Impact: High Impact: Critical
Likelihood: High Medium High Critical Critical
Likelihood: Medium Low Medium High Critical
Likelihood: Low Low Low Medium High

Likelihood assessment for AI systems: - High: Attack can be executed with publicly available tools and techniques. No authentication required. Prompt injection via file content is High likelihood because the attacker only needs to place text in a file the agent will read. - Medium: Attack requires specific conditions (MITM position, compromised infrastructure, social engineering). MCP server update attacks are Medium because they require the victim to have installed the server. - Low: Attack requires advanced capabilities (cryptographic collision, zero-day in the LLM provider, physical access). Deliberate SHA collision for plugin version is Low.

Impact assessment for AI systems: - Critical: Full system compromise. Arbitrary code execution with user privileges. Credential theft enabling lateral movement. - High: Significant data exposure or unauthorized modification. Access to source code, configuration, or sensitive files. - Medium: Limited data exposure or degraded functionality. Context poisoning that alters agent behavior without full compromise. - Low: Information leakage of non-sensitive data. Performance degradation without security impact.

4.3 Chain Severity Calculation

Attack chain severity is not the sum or average of individual threat severities. Use this formula:

Chain Severity = max(individual severities) 
                 + escalation_bonus(chain_length)
                 - mitigation_credit(existing_controls)

Where: - Escalation bonus: +1 severity level if chain has 4+ steps (indicates systemic weakness) - Mitigation credit: -1 severity level if at least 2 independent mitigations exist along the chain

In practice: a chain of four Medium-severity threats with no existing mitigations should be rated High, because the chain enables an outcome more severe than any individual link.

5.2 Mitigation Categories for AI Systems

Organize mitigations by defense layer. A robust defense implements controls at multiple layers so that failure of one control does not result in compromise.

Layer 1: Input Validation (Prevent malicious content from entering) - Content boundary markers with unpredictable tokens - MCP tool description scanning for instruction patterns - Configuration schema validation with deny-list enforcement - Package integrity verification (signatures, not just hashes)

Layer 2: Decision Validation (Prevent the LLM from making malicious decisions) - Permission system with deny-first evaluation - AI classifier for auto-mode decisions (with fail-closed default) - Hook-based pre-execution checks - Conservative session memory pattern generalization

Layer 3: Execution Isolation (Limit blast radius of malicious actions) - Process sandboxing for MCP servers and tools - Network isolation for shell commands - Filesystem access restrictions (project directory only) - Resource limits (CPU, memory, file descriptors, fork depth)

Layer 4: Detection and Response (Identify and respond to successful attacks) - Audit logging with tamper-evident storage - Anomaly detection on tool call patterns - Credential rotation on suspected compromise - Session termination on policy violation

Layer 5: Recovery (Restore to known-good state) - Configuration rollback capability - Credential revocation and re-issuance - Memory/RAG store purging - Incident response runbook

Usage Guidelines

For Security Architects

  1. Complete Sections 1-5 during the design phase, before implementation begins
  2. Use the STRIDE prompt questions (Section 3.2) as a systematic enumeration aid -- do not rely on intuition alone
  3. Focus on attack chains (Section 4) for prioritization rather than individual threat severity
  4. Review the worked example (Section 6) before starting your first assessment

For Penetration Testers

  1. Use the attack chain templates (Section 4.2) as test scenarios
  2. Map discovered vulnerabilities back to the threat model using CWE references
  3. Validate that documented mitigations actually function as described
  4. Test the "weakest link" in each documented chain first

For Development Teams

  1. Use the trust boundary diagram (Section 2) as a design constraint -- every data flow crossing a trust boundary needs a security control
  2. Validate new features against the STRIDE prompt questions before merging
  3. When adding MCP servers or subagents, update the component inventory and re-run relevant STRIDE prompts
  4. Use the defense layer model (Section 5.2) to ensure defense-in-depth: no single layer should be the only protection

For Compliance Teams

  1. Map threats to compliance framework controls using Chapter 23's mapping tables
  2. Use the remediation plan (Section 5) as evidence of risk management process
  3. Document residual risk acceptances (Section 5.3) as required by SOC 2 and ISO 27001
  4. Retain completed threat models as audit artifacts with version history
