Chapter 7: File System and Path Security

AI agents interact with the filesystem thousands of times per session. Reading source code, writing generated files, searching directories, editing configurations -- these operations form the backbone of any coding agent's workflow. Each operation accepts a path as input, and that path is the attack surface. A path that resolves to a different file than the security system expects bypasses every access control in the stack.

This chapter examines file system security for AI agents from the attacker's perspective: path traversal attacks that escape allowed directories, symlink attacks that redirect file operations to unintended targets, TOCTOU race conditions that exploit the gap between security checks and actual file access, the canonical path defense and its limitations, and ZIP extraction as a weaponized file system attack. The treatment draws on real vulnerabilities from Claude Code's security audit, where path traversal through symlinks in ZIP extraction was rated HIGH severity (CVSS 7.5, CWE-22) and TOCTOU races in file operations were rated MEDIUM (CVSS 5.0, CWE-367).

7.1 The File Path Attack Surface

In traditional applications, file path vulnerabilities require an attacker to find an input field that reaches a file operation. In AI agents, every file tool accepts paths generated by the AI model -- which is influenced by user prompts, file contents, and external data sources, any of which could contain malicious path values.

7.2 Path Traversal Attacks

Path traversal (CWE-22) exploits relative path components (..) to escape a restricted directory. In AI agents, the restricted directory is typically the project root -- the agent should only read and write files within the user's project.

Classic Traversal Patterns

# Escape project directory to read system files
../../../etc/passwd
../../../etc/shadow
../../../home/user/.ssh/id_rsa
../../../home/user/.aws/credentials

# Escape to read other projects
../../other-project/.env
../../other-project/secrets/api-key.json

# Double encoding (URL-encoded dots)
%2e%2e/%2e%2e/%2e%2e/etc/passwd

# Null byte injection (legacy systems)
../../../etc/passwd%00.txt

# Backslash traversal (Windows)
..\..\..\Windows\System32\config\SAM

Path Normalization as Defense

The primary defense against traversal is path normalization: resolve the path to its canonical absolute form before applying access control rules.

import { resolve, normalize } from 'path';

function validatePath(inputPath: string, allowedRoot: string): string {
  // Step 1: Resolve to absolute path (expands .. and .)
  const absolutePath = resolve(allowedRoot, inputPath);

  // Step 2: Normalize (collapses redundant separators)
  const normalizedPath = normalize(absolutePath);

  // Step 3: Check containment
  const normalizedRoot = normalize(allowedRoot);
  if (!normalizedPath.startsWith(normalizedRoot + '/') && 
      normalizedPath !== normalizedRoot) {
    throw new SecurityError(
      `Path "${inputPath}" resolves to "${normalizedPath}" ` +
      `which is outside allowed root "${normalizedRoot}"`
    );
  }

  return normalizedPath;
}

What resolve() handles: The .. component is resolved by removing the preceding directory component. /project/src/../../etc/passwd becomes /etc/passwd. The containment check then rejects it because /etc/passwd does not start with /project/.

What resolve() does NOT handle: Symlinks. If /project/src/link is a symlink to /etc/, then resolve('/project/src/link/passwd') returns /project/src/link/passwd -- still inside the project directory by string comparison. But the actual file read follows the symlink to /etc/passwd. This is the symlink attack, covered in Section 7.3.

Platform-Specific Traversal Quirks

Platform Quirk Impact
Windows Backslash \ is a path separator ..\..\etc\passwd traverses on Windows
macOS (HFS+) Case-insensitive by default .ENV and .env are the same file
macOS /private/ prefix for /tmp/, /var/, /etc/ /tmp/ is actually /private/tmp/
Linux Case-sensitive .ENV and .env are different files
All POSIX Null bytes in paths Some implementations truncate at null byte
Windows Drive letter prefixes C:\..\D:\secret may cross drives
Windows UNC paths \\server\share\..\..\ can escape network boundaries

The case-sensitivity difference between macOS and Linux is particularly dangerous for deny-list rules. A deny rule for Read(./.env) on macOS also blocks Read(./.ENV) because HFS+ treats them as the same file. On Linux, the same deny rule does NOT block .ENV. An attacker who knows the deployment platform can exploit this discrepancy.

7.3 Symlink Attacks

Symbolic links (symlinks) are filesystem-level redirections: they point to another path that the kernel follows transparently. This transparency is exactly the problem -- the security system sees the symlink path, but the kernel accesses the target path.

The Basic Symlink Attack

sequenceDiagram
    participant ATK as Attacker
    participant FS as File System
    participant AGENT as AI Agent
    participant SEC as Security System

    ATK->>FS: Create symlink:<br/>project/link → /etc/shadow
    AGENT->>SEC: Request: Read("project/link")
    SEC->>SEC: Path check: "project/link"<br/>is inside project → ALLOW
    SEC-->>AGENT: Allowed
    AGENT->>FS: open("project/link")
    FS->>FS: Follow symlink → /etc/shadow
    FS-->>AGENT: Contents of /etc/shadow
    Note over AGENT: Secret file disclosed<br/>despite never requesting<br/>a path outside project

The security system approves the operation because the symlink path is inside the allowed directory. The kernel follows the symlink to the actual target, which is outside the allowed directory. The file contents returned to the agent -- and potentially to the AI model's context -- are from the target, not the symlink.

Symlink Attack Variants

Write-through-symlink: More dangerous than read-through-symlink because it modifies files outside the project:

# Attacker creates: project/config → ~/.ssh/authorized_keys
# Agent writes: Write("project/config", "ssh-rsa AAAA... attacker@evil")
# Result: Attacker's SSH key added to authorized_keys

Symlink-in-parent: The attacker replaces a parent directory with a symlink:

# Original: project/src/components/Button.tsx
# Attack: rm -rf project/src/components && ln -s /etc project/src/components
# Agent writes: Write("project/src/components/passwd", "malicious content")
# Result: Writes to /etc/passwd

Recursive symlinks: A symlink that points to a path containing another symlink:

# project/a → /tmp/staging
# /tmp/staging/b → /etc/
# Agent reads: Read("project/a/b/shadow")
# Follows: project/a → /tmp/staging → /tmp/staging/b → /etc/ → /etc/shadow

Defense: Canonical Path Resolution

The canonical path defense resolves all symlinks before applying access control:

import { realpathSync } from 'fs';
import { resolve, normalize } from 'path';

function validatePathWithSymlinkResolution(
  inputPath: string, 
  allowedRoot: string
): string {
  // Step 1: Resolve to absolute path
  const absolutePath = resolve(allowedRoot, inputPath);

  // Step 2: Resolve ALL symlinks to canonical path
  let canonicalPath: string;
  try {
    canonicalPath = realpathSync(absolutePath);
  } catch (err) {
    if (err.code === 'ENOENT') {
      // File doesn't exist yet (write operation)
      // Resolve parent directory instead
      canonicalPath = resolve(
        realpathSync(dirname(absolutePath)),
        basename(absolutePath)
      );
    } else {
      throw err;
    }
  }

  // Step 3: Resolve symlinks in the root path too
  const canonicalRoot = realpathSync(allowedRoot);

  // Step 4: Containment check against canonical paths
  if (!canonicalPath.startsWith(canonicalRoot + '/') && 
      canonicalPath !== canonicalRoot) {
    throw new SecurityError(
      `Path resolves to "${canonicalPath}" outside root "${canonicalRoot}"`
    );
  }

  return canonicalPath;
}

Critical detail: Both the input path AND the allowed root must be canonicalized. If the allowed root is /project and /project itself is a symlink to /mnt/data/project, the containment check must compare canonical paths: the input's canonical path must start with /mnt/data/project/, not /project/.

7.4 TOCTOU Race Conditions

Time-of-Check to Time-of-Use (TOCTOU, CWE-367) vulnerabilities exploit the gap between when a security check is performed and when the checked resource is actually used. In file operations, this gap allows an attacker to modify the filesystem between the check and the use.

The TOCTOU Window in File Operations

sequenceDiagram
    participant SEC as Security Check
    participant ATK as Attacker (concurrent)
    participant FS as File System

    SEC->>FS: stat("project/config") → regular file
    SEC->>SEC: Path is inside project → ALLOW
    Note over ATK,FS: TOCTOU WINDOW
    ATK->>FS: rm project/config
    ATK->>FS: ln -s /etc/shadow project/config
    SEC->>FS: open("project/config")
    FS->>FS: Follow symlink → /etc/shadow
    Note over SEC: Security check passed<br/>but file changed between<br/>check and open

The window between stat() and open() may be microseconds, but on a multi-core system with a motivated attacker running a tight loop, the race is winnable.

TOCTOU in Claude Code's File Operations

The Claude Code audit identified two TOCTOU vulnerabilities:

Finding 27 (CVSS 5.0): TOCTOU Race Between Read State Check and File Write. The FileWriteTool checks the file's current state (using mtime) before writing. A concurrent process could modify the file between the check and the write, causing the write to silently overwrite concurrent changes. The mtime check catches most cases, but filesystem timestamp granularity (1 second on some systems) can miss rapid concurrent modifications.

Finding 30 (CVSS 4.7): TOCTOU Race in Credential File Write. The plainTextStorage.update() function writes the file then sets permissions. The window between writeFileSync and chmodSync leaves the file with default permissions -- potentially world-readable if umask is 0o000.

Mitigation Strategies

Strategy 1: Open-Then-Check (reversing the order)

Instead of checking the path then opening the file, open the file first, then check properties of the opened file descriptor:

import { openSync, fstatSync, readFileSync } from 'fs';

function secureRead(filePath: string, allowedRoot: string): string {
  // Open the file first — get a file descriptor
  const fd = openSync(filePath, 'r');

  try {
    // Check properties of the OPENED file (not the path)
    const stat = fstatSync(fd);

    // Verify it's a regular file (not a device, socket, etc.)
    if (!stat.isFile()) {
      throw new SecurityError('Not a regular file');
    }

    // Read from the file descriptor (not the path)
    // The fd points to the same inode regardless of path changes
    const content = readFileSync(fd, 'utf-8');
    return content;
  } finally {
    closeSync(fd);
  }
}

This eliminates the TOCTOU window for the read operation: the file descriptor is bound to an inode at open time, and subsequent path manipulation (deleting the file, replacing it with a symlink) does not affect the already-opened descriptor.

Strategy 2: O_NOFOLLOW for Symlink Prevention

The O_NOFOLLOW flag causes open() to fail if the path's final component is a symlink:

import { constants, openSync } from 'fs';

function secureOpen(filePath: string): number {
  return openSync(filePath, constants.O_RDONLY | constants.O_NOFOLLOW);
  // Throws ELOOP if filePath is a symlink
}

Limitation: O_NOFOLLOW only checks the final path component. If an intermediate directory is a symlink (/project/link_to_etc/passwd), O_NOFOLLOW does not detect it. Full symlink protection requires canonicalization of the entire path before opening.

Strategy 3: Atomic Write with Restrictive Permissions

For write operations, the atomic write pattern eliminates the permission TOCTOU:

function atomicSecureWrite(
  filePath: string, 
  content: string, 
  mode: number = 0o600
): void {
  const dir = dirname(filePath);
  const tmpPath = join(dir, `.tmp-${randomBytes(8).toString('hex')}`);

  // Create temp file with correct permissions from the start
  const fd = openSync(tmpPath, 
    constants.O_WRONLY | constants.O_CREAT | constants.O_EXCL, 
    mode
  );

  try {
    writeSync(fd, content, 0, 'utf-8');
    closeSync(fd);
    renameSync(tmpPath, filePath); // Atomic on same filesystem
  } catch (err) {
    closeSync(fd);
    unlinkSync(tmpPath); // Clean up on failure
    throw err;
  }
}

The O_CREAT | O_EXCL combination creates the file exclusively -- it fails if the file already exists, preventing an attacker from pre-creating the temp file as a symlink. The mode parameter sets permissions at creation time, eliminating the write-then-chmod window.

The Deny List Architecture

The deny list is the primary access control for file reads. It uses the permission system's deny rules with glob matching:

{
  "deny": [
    "Read(./.env)",
    "Read(./.env.*)",
    "Read(./credentials.json)",
    "Read(./token.json)",
    "Read(./.claude/settings.local.json)",
    "Read(./secrets/**)"
  ]
}

Default-open stance: Files not in the deny list are readable. This is a deliberate design decision -- developers need to read arbitrary project files. But it means the deny list must be comprehensive. A credential stored at ~/project/creds/prod-db.json is not covered unless explicitly denied.

The sensitive file read problem: AI agents need to read configuration files to understand projects, but configuration files often contain secrets mixed with non-secret settings. The deny list blocks entire files, not specific lines within files. A configuration file that contains both database connection strings (secret) and logging levels (non-secret) must be either entirely allowed or entirely blocked.

Binary Detection

Binary detection prevents the model from receiving raw binary data that could contain steganographic prompt injection, corrupt the conversation format, or consume excessive tokens:

function isBinary(buffer: Buffer): boolean {
  const scanLimit = Math.min(buffer.length, 8192);
  for (let i = 0; i < scanLimit; i++) {
    if (buffer[i] === 0) return true;
  }
  return false;
}

The 8192-byte scan window is a practical tradeoff. A file with null bytes only after 8KB would be misclassified as text, but such files are rare. The false positive rate on text files with embedded null bytes (e.g., some UTF-16 encoded files without BOM) is a known limitation.

7.6 ZIP Extraction as a Weapon

ZIP files deserve special attention because they combine multiple file system attack vectors into a single deliverable package. The Claude Code audit rated symlink-based path traversal in ZIP extraction as HIGH severity (CVSS 7.5, CWE-22).

The Zip Slip Attack

Zip Slip exploits the fact that ZIP archives can contain entries with relative path components:

Archive contents:
  src/index.ts           (normal file)
  src/utils.ts           (normal file)
  ../../../../.bashrc    (path traversal entry)

When extracted naively, the traversal entry writes to ../../../../.bashrc relative to the extraction directory -- potentially overwriting the user's shell configuration.

The defense:

function safeExtract(
  zipEntry: ZipEntry, 
  targetDir: string
): string {
  const fullPath = resolve(targetDir, zipEntry.path);

  // Containment check: resolved path must be inside target directory
  if (!fullPath.startsWith(targetDir + sep) && fullPath !== targetDir) {
    throw new SecurityError(
      `Zip entry "${zipEntry.path}" escapes target directory`
    );
  }

  return fullPath;
}

Symlink Entries in ZIP Archives

The more sophisticated attack uses ZIP entries that create symlinks:

Archive contents:
  config/             (directory)
  config/link         (symlink → /etc/shadow)
  config/link/data    (file — follows the symlink!)

When extracted, config/link becomes a symlink pointing to /etc/shadow. Subsequent writes to config/link/data follow the symlink and write to /etc/shadow.

Claude Code's audit finding (Finding 4, CVSS 7.5):

ZIP extraction validates against '..' path traversal (containsPathTraversal check) but symlink targets within ZIP archives are followed without validating that resolved paths remain within the extraction root directory. A crafted ZIP with symlinks pointing to paths outside the extraction directory (e.g., ~/.ssh/authorized_keys) could write files to arbitrary locations.

The data flow: Malicious ZIP → extract → symlink followed → write outside extraction directory.

The defense:

function safeExtractWithSymlinkProtection(
  zipEntry: ZipEntry,
  targetDir: string
): void {
  const fullPath = resolve(targetDir, zipEntry.path);

  // Check 1: Path traversal
  if (!fullPath.startsWith(targetDir + sep)) {
    throw new SecurityError('Path traversal detected');
  }

  if (zipEntry.isSymlink) {
    // Check 2: Symlink target must resolve inside target directory
    const symlinkTarget = resolve(dirname(fullPath), zipEntry.linkTarget);
    if (!symlinkTarget.startsWith(targetDir + sep)) {
      throw new SecurityError(
        `Symlink target "${zipEntry.linkTarget}" escapes target directory`
      );
    }
  }

  // Check 3: After creating any symlink, verify with realpath
  if (existsSync(fullPath)) {
    const canonicalPath = realpathSync(fullPath);
    if (!canonicalPath.startsWith(realpathSync(targetDir) + sep)) {
      unlinkSync(fullPath); // Remove the dangerous symlink
      throw new SecurityError('Symlink resolved outside target directory');
    }
  }
}

ZIP Bomb Detection

A ZIP bomb uses compression ratios to create archives that expand to enormous sizes:

Archive Size Extracted Size Compression Ratio
42 KB 4.5 PB (Petabytes) 106 billion : 1
10 MB 281 TB 28 million : 1
1 MB 1 GB 1,000 : 1

The 42.zip "zip of doom" is the classic example: 42 kilobytes that expand to 4.5 petabytes through nested compression layers.

Defense layers:

interface ZipExtractionLimits {
  maxTotalSize: number;        // Total extracted size (e.g., 1 GB)
  maxEntrySize: number;        // Single entry size (e.g., 100 MB)
  maxEntryCount: number;       // Total number of entries (e.g., 10,000)
  maxCompressionRatio: number; // Ratio check (e.g., 100:1)
  maxDepth: number;            // Nesting depth for recursive ZIPs (e.g., 2)
}

function checkZipBomb(
  entry: ZipEntry, 
  limits: ZipExtractionLimits,
  cumulativeSize: number
): void {
  // Check individual entry size
  if (entry.uncompressedSize > limits.maxEntrySize) {
    throw new SecurityError(`Entry exceeds size limit: ${entry.path}`);
  }

  // Check cumulative extracted size
  if (cumulativeSize + entry.uncompressedSize > limits.maxTotalSize) {
    throw new SecurityError('Total extraction size exceeds limit');
  }

  // Check compression ratio
  if (entry.compressedSize > 0) {
    const ratio = entry.uncompressedSize / entry.compressedSize;
    if (ratio > limits.maxCompressionRatio) {
      throw new SecurityError(`Suspicious compression ratio: ${ratio}`);
    }
  }
}

Claude Code's audit (Finding 25, MEDIUM) noted that ZIP bomb detection only occurs during initial extraction, not during streaming decompression. A bomb that passes initial ratio checks but expands exponentially during streaming could exhaust disk space.

A write to .git/hooks/pre-commit is particularly insidious: the hook executes on every git commit, which the AI agent itself performs frequently. An attacker who poisons the pre-commit hook through a file write gets code execution every time the agent commits code -- a self-reinforcing loop.

Defense: Maintain a separate deny-write list for high-impact project paths:

const DANGEROUS_WRITE_TARGETS = [
  '.git/hooks/**',        // Git hooks - arbitrary code execution
  '.github/workflows/**', // CI/CD pipelines
  '.gitlab-ci.yml',       // GitLab CI
  'Jenkinsfile',          // Jenkins pipelines
  '.husky/**',            // Husky git hooks
  'Makefile',             // Build system (conditional)
  'Dockerfile',           // Container definition (conditional)
];

function isHighImpactWriteTarget(relativePath: string): boolean {
  return DANGEROUS_WRITE_TARGETS.some(pattern => 
    minimatch(relativePath, pattern)
  );
}

7.8 The Edit Tool: Surgical Modification Risks

The Edit tool modifies specific portions of existing files -- it replaces an old_string with a new_string. This surgical precision creates a unique attack vector: unlike the Write tool (which replaces entire files and is obviously destructive), the Edit tool can make subtle modifications that are difficult to detect.

Subtle Code Injection Through Edits

An AI agent influenced by prompt injection could make edits that appear to be normal code changes but introduce vulnerabilities:

// Benign-looking edit: "updating the authentication check"
// old_string:
if (user.isAuthenticated && user.hasRole('admin')) {

// new_string:  
if (user.isAuthenticated || user.hasRole('admin')) {
  // Changed && to || — now ANY authenticated user is admin

The change is a single character (&& to ||) that fundamentally alters the authorization logic. In a code review, this could easily be missed among dozens of legitimate changes.

Defense considerations:

  1. Diff highlighting in permission prompts: When the Edit tool requires permission, show the exact diff with changed characters highlighted
  2. Semantic analysis for security-sensitive patterns: Flag edits that modify authentication, authorization, or cryptographic operations
  3. Post-edit verification hooks: Run linters and static analysis on modified files to detect introduced vulnerabilities

7.9 Cross-Platform Path Security Considerations

File path security behaves differently across operating systems. AI agents that target multiple platforms must handle each platform's quirks:

Issue macOS Linux Windows
Case sensitivity Case-insensitive (HFS+) Case-sensitive Case-insensitive (NTFS)
Path separator / / \ (also accepts /)
Symlinks require privilege No No Yes (SeCreateSymbolicLinkPrivilege)
Max path length 1024 bytes 4096 bytes 260 chars (or 32,767 with prefix)
Alternate data streams No No Yes (file.txt:stream)
Reserved names None None CON, PRN, AUX, NUL, COM1-9, LPT1-9
Unicode normalization NFD (decomposed) None (bytes) NFC (composed)

The Unicode normalization difference between macOS and Linux deserves special attention. macOS decomposes Unicode characters (NFD), so the file name cafe\u0301 (cafe + combining accent) and caf\u00e9 (precomposed) refer to the same file on macOS but different files on Linux. A deny rule matching one form does not necessarily match the other on cross-platform deployments.

Windows alternate data streams are a particularly dangerous edge case. On NTFS, file.txt:hidden creates a hidden data stream attached to file.txt. A path validation that checks file.txt may not detect that :hidden contains injected content. AI agents running on Windows must strip or reject paths containing : after the drive letter.

7.10 Designing File System Security for AI Agents

The lessons from production systems yield design principles for any AI agent that interacts with the filesystem:

The lessons from production systems yield design principles for any AI agent that interacts with the filesystem:

Principle 1: Canonicalize Before Every Check

Every file path must be resolved to its canonical form (absolute path with all symlinks resolved) before any access control decision. Paths that cannot be canonicalized (broken symlinks for read operations, non-existent parent directories for write operations) should be handled explicitly, not silently passed through.

Principle 2: Use Deny Lists for Sensitive Files, Sandboxing for Everything Else

Deny lists target specific high-value files (credentials, SSH keys, configuration). Sandboxing (Chapter 8) provides the broad boundary (project directory only). Neither is sufficient alone: deny lists can be incomplete, and sandboxes allow all writes within the project directory -- including dangerous targets like .git/hooks/.

Principle 3: Validate ZIP Contents Before Extraction

ZIP extraction must validate every entry against path traversal, symlink targets, file sizes, compression ratios, and entry counts before writing any file to disk. Post-extraction validation (checking files after they have been written) is too late -- the damage (symlink creation, file overwrite) has already occurred.

Principle 4: Use Atomic Operations for Security-Sensitive Writes

Any write operation that involves security-relevant state (credentials, permissions, configuration) must use atomic write patterns: create with restrictive permissions, then rename into place. The write-then-chmod pattern leaves a TOCTOU window that attackers can exploit.

Principle 5: Treat the AI Model as an Untrusted Path Source

The AI model generates paths based on its understanding of the user's request, file contents it has read, and external data it has received. Any of these sources can contain path injection attempts. The path validation pipeline must treat every model-generated path with the same suspicion as user input in a web application -- because that is exactly what it is.

7.11 Key Takeaways

File system security in AI agents centers on one problem: ensuring that the file actually accessed matches the file the security system authorized. Path traversal, symlink attacks, and TOCTOU races each exploit a different gap between authorization and access.

The canonical path defense -- resolving all symlinks and normalizing all path components before access control decisions -- is necessary but not sufficient. TOCTOU races can modify the filesystem between canonicalization and access. ZIP extraction introduces batch file creation where each entry must be individually validated against traversal, symlink escape, and resource exhaustion. Write operations to project-internal files (.git/hooks/, CI/CD configs, build scripts) are as dangerous as writes outside the project.

As discussed in Chapter 6, the permission system controls which file operations are allowed. This chapter showed that even allowed operations can be redirected to unintended targets through path manipulation. The next chapter examines the final defense layer: process-level sandboxing that constrains what file operations a command can actually perform at the kernel level, regardless of what the permission system authorized.
