Chapter 16: VaultAgent Technical Architecture

Engineering the Trust Layer for AI Agent Credentials

This chapter is the engineering blueprint for VaultAgent. Every component described here maps to a system that must be built, deployed, and maintained at scale. We cover the five core subsystems in implementation detail: the Agent SDK, the encrypted vault, the secret scanner, the lifecycle manager, and the audit dashboard. We also address the cross-cutting concerns that determine whether the system works in practice: performance, reliability, platform compatibility, and the security of VaultAgent itself.

The architecture follows two non-negotiable constraints:

  1. Zero-knowledge. VaultAgent's cloud infrastructure never sees plaintext credentials. All encryption and decryption happens on the developer's machine. This is not a nice-to-have — it is the architectural foundation that makes enterprise adoption possible.

  2. Transparent integration. Existing AI coding agents must work with VaultAgent without modification. Developers should not need to change their workflow. The security layer must be invisible during normal operation and visible only when it prevents a problem.

Component 1: Agent SDK Layer

The Agent SDK is the interface between AI coding agents and VaultAgent's security services. It provides three integration methods, ordered from least to most invasive.

Filesystem Hooks (Primary — Zero-Config)

The filesystem hook intercepts file I/O operations on known credential file paths. This requires no changes to any AI agent — VaultAgent watches the filesystem and transparently encrypts/decrypts credential files.

macOS Implementation: Endpoint Security Framework (ESF)

macOS provides the Endpoint Security framework for monitoring filesystem events. VaultAgent registers as an ESF client and subscribes to ES_EVENT_TYPE_NOTIFY_WRITE and ES_EVENT_TYPE_AUTH_OPEN events on monitored paths.

Event flow:
1. Claude Code calls writeFileSync("~/.claude/.credentials.json", data)
2. ESF delivers ES_EVENT_TYPE_NOTIFY_WRITE to VaultAgent
3. VaultAgent reads the written file
4. VaultAgent encrypts the content: encrypt(data, key, nonce)
5. VaultAgent writes encrypted blob back to the same path
6. Latency added: ~5ms (encryption) + ~2ms (write)

Read flow:
1. Claude Code calls readFileSync("~/.claude/.credentials.json")
2. ESF delivers ES_EVENT_TYPE_AUTH_OPEN to VaultAgent
3. VaultAgent decrypts file content to a tmpfs-backed temporary file
4. VaultAgent redirects the read to the decrypted temporary
5. Temporary file is zeroed and deleted after read completes
6. Latency added: ~5ms (decryption) + ~1ms (tmpfs)

ESF requires a system extension (kext-free since macOS 10.15.4) distributed via MDM or user-approved installation. This is the same mechanism used by security products like CrowdStrike Falcon and SentinelOne.

Linux Implementation: eBPF + fanotify

On Linux, VaultAgent uses a combination of fanotify (for filesystem event monitoring) and eBPF (for high-performance path filtering).

fanotify provides:
- FAN_CLOSE_WRITE: notification when a file is written and closed
- FAN_OPEN_PERM: permission event before file open (allows blocking)

eBPF provides:
- High-performance path filtering (avoid processing irrelevant filesystem events)
- Process identification (know which agent is accessing which credential)
- Zero-copy event processing (minimal overhead)

The Linux implementation requires CAP_SYS_ADMIN for fanotify and CAP_BPF for eBPF program loading. VaultAgent runs as a systemd service with these capabilities.

Windows Implementation: Minifilter Driver

On Windows, VaultAgent uses a minifilter driver to intercept file I/O on credential paths. The minifilter is a signed, Microsoft-approved driver (WHQL certified for enterprise deployment).

Key Management

Master key generation:

On first run:
1. Generate 256-bit random master key using libsodium randombytes_buf()
2. Store master key in OS keychain:
   - macOS: security add-generic-password -s "vaultagent-master"
   - Linux: secret-tool store --label "VaultAgent Master Key"
   - Windows: CredWrite() to Windows Credential Manager
3. Derive machine-specific salt from:
   - macOS: IOPlatformSerialNumber (hardware serial)
   - Linux: /etc/machine-id
   - Windows: MachineGuid from registry
4. Salt is stored in ~/.vaultagent/machine.salt (non-secret, prevents 
   key reuse across machines)

Per-file key derivation:

file_key = Argon2id(
  password = master_key,
  salt = machine_salt || file_id,
  time_cost = 3,        // Moderate — runs on every encrypt/decrypt
  memory_cost = 65536,   // 64 MB
  parallelism = 1,
  output_length = 32     // 256-bit key
)

Argon2id is used instead of a simpler KDF (like HKDF) to provide resistance against GPU-based brute force attacks if the encrypted vault files are exfiltrated without the master key. The 64MB memory cost makes GPU attacks impractical while keeping derivation time under 100ms on modern hardware.

Encryption operation:

encrypt(plaintext, file_key):
  nonce = randombytes_buf(24)  // 24-byte nonce for XSalsa20
  ciphertext = crypto_secretbox(plaintext, nonce, file_key)
  return nonce || ciphertext   // Prepend nonce for decryption

Why XSalsa20-Poly1305? - 256-bit key with 192-bit nonce eliminates nonce collision risk (critical for files that are frequently re-encrypted) - Authenticated encryption (Poly1305 MAC) prevents tampering - Constant-time implementation in libsodium prevents timing attacks - Battle-tested: used by NaCl, WireGuard, Signal (for some operations) - Fast: ~1 GB/s on modern hardware, negligible overhead for credential-sized payloads

Vault File Format

Each encrypted credential is stored as a single file in ~/.vaultagent/vault/:

File: ~/.vaultagent/vault/{uuid}.enc
Format:
  Bytes 0-3:    Magic number "VA01" (file format version)
  Bytes 4-7:    KDF parameters (encoded Argon2id config)
  Bytes 8-31:   Nonce (24 bytes)
  Bytes 32-47:  Poly1305 authentication tag (16 bytes)
  Bytes 48-N:   Encrypted payload (variable length)

Total overhead: 48 bytes per credential (negligible)

Metadata Database

A local SQLite database (~/.vaultagent/meta.db) stores credential metadata without storing credential values:

CREATE TABLE credentials (
    id TEXT PRIMARY KEY,           -- UUID
    agent_name TEXT NOT NULL,      -- Which AI agent owns this
    credential_type TEXT NOT NULL, -- oauth_token, api_key, etc.
    provider TEXT,                 -- anthropic, openai, github, etc.
    created_at TIMESTAMP NOT NULL,
    last_accessed_at TIMESTAMP,
    expires_at TIMESTAMP,          -- NULL if no expiry set
    rotation_policy TEXT,          -- JSON: rotation configuration
    vault_file TEXT NOT NULL,      -- Path to .enc file
    status TEXT DEFAULT 'active',  -- active, expired, revoked
    tags TEXT                      -- JSON: user-defined tags
    -- NOTE: No credential values stored here
);

CREATE TABLE access_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    credential_id TEXT NOT NULL,
    timestamp TIMESTAMP NOT NULL,
    action TEXT NOT NULL,          -- read, write, rotate, revoke
    agent_name TEXT,
    agent_pid INTEGER,
    session_id TEXT,
    policy_result TEXT,            -- allow, deny, warn
    FOREIGN KEY (credential_id) REFERENCES credentials(id)
);

CREATE INDEX idx_access_log_credential ON access_log(credential_id, timestamp);
CREATE INDEX idx_access_log_timestamp ON access_log(timestamp);
CREATE INDEX idx_credentials_agent ON credentials(agent_name);
CREATE INDEX idx_credentials_expires ON credentials(expires_at);

SQLite is chosen for the metadata store because: - Zero configuration (no database server to install) - WAL mode provides concurrent read access without blocking - Single-file database simplifies backup and migration - Proven reliability for local applications (used by Firefox, Chrome, iOS) - Row-level locking sufficient for single-machine workload

Three-Stage Detection Pipeline

Stage 1: Fast Pattern Matching (< 1ms per file)

A compiled regex engine (based on Rust's regex crate, exposed via FFI to the Node.js/Python runtime) applies 400+ patterns simultaneously using a single-pass automaton. Each pattern has a unique identifier and confidence score:

Category Patterns Example Pattern Confidence
AWS 12 AKIA[0-9A-Z]{16} 0.95
GitHub 8 gh[pso]_[a-zA-Z0-9]{36,} 0.98
Google/GCP 10 AIza[0-9A-Za-z_-]{35} 0.90
Azure 6 [a-z0-9]{8}-[a-z0-9]{4}-...-[a-z0-9]{12} (with context) 0.70
Generic API keys 20 (api[_-]?key|apikey)["\s:=]+["']?[a-zA-Z0-9]{20,} 0.60
Database URIs 8 (postgres|mysql|mongodb)://[^"'\s]+ 0.85
Private keys 4 -----BEGIN (RSA|EC|DSA) PRIVATE KEY----- 0.99
JWT tokens 3 eyJ[a-zA-Z0-9_-]*\.eyJ[a-zA-Z0-9_-]*\.[a-zA-Z0-9_-]* 0.80
SSH keys 3 ssh-(rsa|ed25519|ecdsa) AAAA[a-zA-Z0-9+/]+ 0.95
Passwords in context 15 password[\s]*[=:]\s*["']?[^\s"']{8,} 0.50
Slack tokens 4 xox[bprs]-[0-9]{10,}-[a-zA-Z0-9-]+ 0.95
Stripe keys 3 [sr]k_(test|live)_[a-zA-Z0-9]{24,} 0.98

Patterns with confidence < 0.70 are passed to Stage 2 for entropy analysis. Patterns with confidence >= 0.70 skip directly to Stage 3 for verification.

Stage 2: Entropy Analysis (< 5ms per candidate)

For candidates from Stage 1 that need additional validation, Stage 2 computes Shannon entropy and contextual scoring:

Shannon entropy of candidate string:
  H = -Σ p(x) * log2(p(x)) for each character class

Scoring:
  - Entropy > 4.5 bits/char: Likely a secret (API keys, tokens)
  - Entropy 3.5-4.5: Possible secret (check context)
  - Entropy < 3.5: Likely not a secret (common words, code)

Contextual scoring modifiers:
  +0.3 if preceded by "key", "token", "secret", "password", "auth"
  +0.2 if in a JSON value position (after ":")
  +0.2 if in an environment variable assignment
  -0.3 if in a code comment explaining format
  -0.5 if matches a known test/example pattern (e.g., "sk-test-...")

Stage 3: Verification (< 100ms per confirmed candidate)

For confirmed high-confidence candidates, Stage 3 performs:

  1. Format validation. Check that the candidate matches the expected format for its type (correct length, character set, checksum if applicable).

  2. Deduplication. Check if this secret has been previously detected and is already in the vault. Avoid duplicate alerts for the same secret appearing in multiple places.

  3. Live verification (optional, opt-in). For certain secret types, attempt a non-destructive API call to verify if the credential is active:

  4. AWS: sts:GetCallerIdentity (read-only, no side effects)
  5. GitHub: GET /user with the token
  6. Slack: auth.test API call

Live verification is disabled by default (privacy concern: VaultAgent should not make network calls with discovered credentials without explicit consent).

  1. Context extraction. Capture surrounding text (sanitized) for the alert context: which agent, which session, what was the user doing when the secret was exposed.

Component 4: Lifecycle Manager

The lifecycle manager enforces credential hygiene: rotation before expiry, maximum lifetime enforcement, and immediate revocation propagation.

Expiry Monitoring

The lifecycle manager maintains a priority queue of credential expiry events, sorted by expiry time:

Priority queue (min-heap by expiry time):
  [credential_id: "cred-001", expires_at: 2027-03-15T14:00:00Z, agent: "claude-code"]
  [credential_id: "cred-002", expires_at: 2027-03-15T15:30:00Z, agent: "cursor"]
  [credential_id: "cred-003", expires_at: 2027-03-16T00:00:00Z, agent: "copilot"]
  ...

Timer fires at: next_expiry - refresh_buffer (default: 10% of token lifetime)

On timer fire:
  1. Dequeue credential
  2. Check rotation_policy for this credential
  3. If auto-rotation configured: execute rotation flow
  4. If manual rotation: generate alert (dashboard + Slack/email)
  5. If past expiry and no rotation: revoke + alert at CRITICAL severity

Token Rotation Flows

OAuth 2.0 refresh token rotation:

1. Retrieve encrypted refresh token from vault
2. Call token endpoint: POST /oauth/token (grant_type=refresh_token)
3. Receive new access_token + refresh_token
4. Encrypt and store new tokens in vault
5. Update expiry in metadata database
6. Update credential file for the agent (transparent)
7. Log rotation event to audit trail
8. Zero old tokens from memory

API key rotation (provider-specific):

For providers with key rotation APIs (AWS, GCP, Stripe):
1. Call provider's key rotation API to generate new key
2. Encrypt and store new key in vault
3. Deactivate old key via provider API
4. Update credential file for the agent
5. Log rotation event

For providers without rotation APIs:
1. Generate alert: "API key for {provider} approaching max age"
2. Provide instructions: "Generate a new key at {provider_dashboard_url}"
3. Wait for user to provide new key via CLI: vaultagent rotate {credential_id}

Revocation Protocol

When a credential is revoked (by admin, by policy, or by detection of compromise):

sequenceDiagram
    participant Admin as Admin / Policy Engine
    participant LM as Lifecycle Manager
    participant Vault as Encrypted Vault
    participant Agents as AI Agent Files
    participant Audit as Audit Engine
    participant Alert as Alert Pipeline

    Admin->>LM: Revoke credential cred-001
    LM->>Vault: Read cred-001 metadata
    Vault-->>LM: {agent: "claude-code", file: "~/.claude/.credentials.json"}
    LM->>Vault: Zero and delete cred-001.enc
    LM->>Agents: Overwrite credential in agent's file
    Note over Agents: Agent sees empty/invalid credential<br/>triggers re-authentication
    LM->>Audit: Log revocation event
    LM->>Alert: Send CRITICAL alert
    Alert-->>Admin: "Credential cred-001 revoked. Affected: claude-code. Reason: manual revocation."

Key property: revocation is immediate and atomic. The credential file is overwritten with an invalid placeholder (not deleted — deletion might cause the agent to error differently than an invalid credential). The agent's next authentication attempt fails, triggering its normal re-authentication flow.

Security of VaultAgent Itself

A credential security platform must be exceptionally secure itself. VaultAgent's security posture:

Client-side security: - The encryption module is open source and audited quarterly by a third-party firm - All cryptographic operations use libsodium (audited, constant-time implementations) - Memory containing plaintext credentials is explicitly zeroed after use (sodium_memzero) - The VaultAgent daemon runs with minimal privileges (only filesystem hooks require elevated permissions) - Automatic updates are signed with Sigstore and verified before installation

Cloud-side security: - Zero-knowledge: cloud never receives plaintext credentials - mTLS for all client-to-cloud communication - SOC 2 Type II certified infrastructure - Penetration tested quarterly - Bug bounty program (HackerOne) - All data encrypted at rest (AES-256-GCM) and in transit (TLS 1.3) - GDPR-compliant data handling (audit logs are personal data)

Technical Risks and Mitigations

Risk Probability Impact Mitigation
OS keychain unavailable in target environment Medium High Graceful degradation to encrypted file with hardware-derived key (TPM/Secure Enclave). Never fall back to plaintext.
Agent vendor changes credential file format High Low Adapter architecture isolates format changes. Community + automated testing detects changes quickly.
Filesystem hooks impact agent performance Medium Medium Benchmark-driven development. Hooks add < 10ms per credential operation. Bypass mode for emergencies.
Encryption key compromised (keychain breach) Low Critical Key rotation protocol. Per-file keys limit blast radius. Automatic re-encryption on key rotation.
Scanner false positives annoy developers Medium Medium Conservative defaults (detect mode). Tunable sensitivity per team. Machine learning on feedback to reduce FP over time.
Competing solution from AI agent vendor Medium High Cross-tool value proposition. Enterprise features (SIEM, compliance, policy) beyond vendor scope. Move faster.

Conclusion

VaultAgent's technical architecture is built on the principle that the best security is invisible security. Developers continue using their AI coding tools exactly as they do today. VaultAgent operates transparently underneath — encrypting credentials, scanning for secrets, rotating tokens, and generating audit trails — without requiring any change in developer behavior.

The zero-knowledge architecture makes enterprise adoption possible. The transparent integration makes developer adoption frictionless. The comprehensive audit trail makes compliance achievable. And the cross-tool management makes VaultAgent more valuable than any single-vendor solution.

The vulnerability data from our audit research is not abstract — it represents real credentials, real developers, and real exposure in production environments.
