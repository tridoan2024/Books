Chapter 11: MCPGuard Technical Architecture

From Concept to System: Building the MCP Security Platform

The previous two chapters established the problem (MCP as the new unsecured package ecosystem) and the product vision (supply chain security for MCP servers). Now we translate that vision into a technical architecture that can scan thousands of MCP servers, compute trust scores in real time, and monitor runtime behavior at scale.

This chapter is the engineering blueprint. Every component described here maps to a concrete system that must be built, deployed, and scaled. We cover the five core subsystems, the data flows between them, the trust score algorithm, and the operational infrastructure required to run MCPGuard as a production security platform.

If you are a technical co-founder reading this to evaluate feasibility: everything described here uses proven technology (static analysis, dynamic sandboxing, anomaly detection) applied to a new domain (MCP server security). The innovation is not in any single component but in the end-to-end integration of these components into a unified trust pipeline for the MCP ecosystem.

System Architecture Overview

MCPGuard is a five-layer security platform. Each layer operates independently but feeds data into a centralized trust score engine. The layers are:

  1. MCP Server Scanner — Static and dynamic analysis of MCP server packages
  2. Trust Score Engine — Multi-signal scoring algorithm that produces a 0-100 trust rating
  3. Verified Registry — Curated, signed registry of analyzed MCP servers
  4. Runtime Monitor — Real-time behavior tracking of deployed MCP servers
  5. Incident Dashboard — Alerting, investigation, and response console

The architecture follows a pipeline pattern: MCP servers enter through the ingestion layer, flow through analysis and scoring, land in the verified registry, and are continuously monitored at runtime. Any anomaly detected at runtime feeds back into the trust score, creating a closed-loop security system.

Layer 1: MCP Server Scanner

The scanner is the foundation of the entire platform. It performs both static analysis (examining source code without execution) and dynamic analysis (running the server in a controlled sandbox and observing its behavior). Every MCP server in the ecosystem must pass through this pipeline before receiving a trust score.

Static Analysis Engine

The static analyzer operates on MCP server source packages and performs four categories of checks:

Abstract Syntax Tree (AST) Analysis. We parse the server's source code into an AST using language-specific parsers (tree-sitter for polyglot support, TypeScript compiler API for TS/JS, Python AST module for Python). The AST analysis detects:

  • Tool description injection patterns (descriptions that contain prompt injection payloads)
  • Dynamic code generation (eval(), new Function(), exec(), subprocess.Popen with shell=True)
  • Filesystem access outside declared scope (reading ~/.ssh/, ~/.aws/credentials, /etc/shadow)
  • Network calls to undeclared endpoints (hardcoded IPs, non-HTTPS URLs, DNS exfiltration patterns)
  • Capability lying (server declares read-only but code contains write operations)

Dataflow Analysis. Beyond individual AST nodes, we trace how data flows through the server. This catches sophisticated attacks where the malicious payload is constructed across multiple functions:

Input parameter → string concatenation → base64 encode → HTTP POST body

We build a taint graph from all user-controllable inputs (tool arguments, environment variables, configuration files) and trace them to sensitive sinks (network calls, filesystem writes, process spawning). Any path from tainted source to sensitive sink without sanitization is flagged.

Dependency Analysis. We resolve the full dependency tree and cross-reference every dependency against known vulnerability databases (NVD, GitHub Advisory Database, Snyk). We also check for:

  • Typosquatting (Levenshtein distance from popular packages)
  • Dependency confusion (private package names that shadow public packages)
  • Maintainer account changes (new maintainer on previously single-owner packages)
  • Suspicious post-install scripts

Pattern Matching. A rules engine applies known-bad patterns from our threat intelligence database. These patterns are updated continuously as new attack techniques emerge. Examples:

Pattern ID Description Severity
MCP-001 Tool description contains hidden system prompt CRITICAL
MCP-002 Server reads OAuth tokens from host filesystem HIGH
MCP-003 Server makes DNS queries with encoded payloads HIGH
MCP-004 Capability manifest does not match code behavior HIGH
MCP-005 Post-install script downloads and executes binary CRITICAL
MCP-006 Server accesses process environment variables MEDIUM
MCP-007 Undeclared network endpoints in code MEDIUM
MCP-008 Dynamic import of modules from remote URLs CRITICAL

Dynamic Analysis Sandbox

Static analysis catches known patterns. Dynamic analysis catches everything else by actually running the server and observing what it does.

Sandbox Infrastructure. Each MCP server runs in an isolated Firecracker microVM with:

  • 256MB RAM, 1 vCPU, 1GB ephemeral disk
  • No network access by default (allowlisted on a per-analysis basis)
  • Read-only root filesystem with writable overlay
  • Syscall filtering via seccomp-bpf (allow-list of ~80 syscalls)
  • 60-second maximum execution time
  • UID namespace isolation (runs as unprivileged user inside VM)

Behavioral Observation. During execution, we capture:

  • All syscalls via eBPF tracing (file opens, network connections, process spawns)
  • All DNS queries (via DNS proxy in the VM network namespace)
  • All HTTP/HTTPS requests (via transparent proxy with TLS interception)
  • Memory allocation patterns (detecting cryptominer behavior)
  • CPU usage profiles (detecting computational abuse)

Test Harness. We drive the MCP server through a comprehensive test suite that exercises every declared tool:

  1. Connect to the server via stdio transport
  2. Call initialize and validate capability negotiation
  3. Invoke each declared tool with valid inputs, edge-case inputs, and adversarial inputs
  4. Observe which resources the server actually accesses versus what it declared
  5. Test tool description stability (descriptions should not change based on input context)

Delta Comparison. For version updates, we diff the behavioral profile against the previous version. Behavioral changes that exceed expected bounds trigger manual review:

  • New network endpoints not present in previous version
  • New filesystem access patterns
  • New process spawning behavior
  • Changes in tool descriptions or capability declarations

Layer 2: Trust Score Engine

Signal Weights (default configuration):

Signal Weight Description
Static Analysis 25% Code quality, pattern matches, dataflow safety
Dynamic Analysis 25% Actual runtime behavior in sandbox
Dependency Health 15% CVE count, dependency freshness, maintainer stability
Publisher Reputation 15% Publishing history, identity verification, response time to issues
Community Signal 5% Download count, GitHub stars, issue/PR activity, user reports
Historical Behavior 10% Behavioral consistency across versions
Capability Attestation 5% Match between declared capabilities and observed behavior

Critical Override Rules. Certain findings override the weighted score entirely:

  • Any CRITICAL static finding → maximum score capped at 20
  • Dynamic analysis detects credential theft → score set to 0, auto-quarantine triggered
  • Publisher identity not verified → maximum score capped at 60
  • Known CVE in direct dependency without patch → score reduced by 30 points

Trust Tiers:

Tier Score Range Badge Meaning
Verified 80-100 Green shield Passed all checks, publisher verified, behavioral history clean
Standard 50-79 Yellow shield Minor issues, unverified publisher, or insufficient history
Caution 20-49 Orange warning Significant issues detected, use at own risk
Blocked 0-19 Red stop Active threat detected, quarantined from registry

Explainability

Every trust score comes with a structured explanation. This is critical for enterprise adoption — security teams need to understand why a server was scored the way it was, not just accept a black-box number.

The explainability report includes:

  • Per-signal breakdown with individual scores
  • Specific findings that reduced the score, with code references
  • Comparison to ecosystem median for servers in the same category
  • Recommendations for the publisher to improve their score
  • Historical trend showing how the score changed across versions

Anti-Gaming Measures

Sophisticated attackers will try to game the trust score. Our defenses:

Temporal analysis. We track behavior across versions. A server that suddenly adds network capabilities in version 2.3.1 after 20 versions of clean behavior gets flagged, even if the individual version passes analysis.

Capability creep detection. We alert on gradual expansion of permissions — the "boiling frog" attack where each version adds one small permission until the server has full access.

Randomized dynamic analysis. The sandbox test harness includes randomized test cases and non-deterministic execution ordering to prevent servers from detecting they are in analysis and behaving differently.

Canary inputs. We include synthetic secrets and credentials in the sandbox environment. Any server that attempts to exfiltrate these canary values is immediately scored 0 and quarantined.

Package Signing with Sigstore

Unlike npm, which took years to implement package signing, MCPGuard uses Sigstore from day one. Every published MCP server package is:

  1. Signed by the publisher using Sigstore's keyless signing (OIDC identity from GitHub, Google, or Microsoft accounts)
  2. Counter-signed by MCPGuard after passing analysis (adding our attestation to the package)
  3. Logged to a transparency log (Rekor-compatible) so that any tampering is publicly detectable

The signature chain means consumers can verify: - Who published the package (identity) - That MCPGuard analyzed and approved it (attestation) - That the package has not been modified since signing (integrity) - The full history of signatures for audit (transparency)

Capability Attestation Protocol

This is MCPGuard's most novel contribution. Each MCP server in the registry includes a capability attestation document — a signed, machine-readable declaration of exactly what the server does:

  "version": "2.1.0",
  "capabilities": {

The attestation is verified at install time and enforced at runtime. If a server attempts to access resources not declared in its attestation, the runtime monitor blocks the access and generates an alert.

Layer 4: Runtime Monitor

Static and dynamic analysis catch threats before deployment. Runtime monitoring catches threats that emerge after deployment — behavioral changes, compromised updates, and zero-day exploitation.

Monitoring Architecture

The runtime monitor operates as a lightweight sidecar or SDK hook that intercepts MCP protocol messages between the AI agent and the MCP server.

Behavioral Baseline Engine

When a monitored MCP server is first deployed, the monitor enters a "learning phase" (configurable, default 7 days) where it records baseline behavior:

  • Average tool invocations per minute
  • Typical result payload sizes
  • Network endpoints accessed
  • Filesystem paths accessed
  • Error rates and patterns
  • Resource consumption (CPU, memory)

After the learning phase, the monitor switches to "enforcement mode" where deviations from the baseline trigger alerts:

Deviation Threshold Response
New network endpoint Any new endpoint Alert + block (configurable)
Result payload 10x larger than baseline > 10x p95 Alert
Tool description changed at runtime Any change CRITICAL alert + auto-block
Filesystem access outside attestation Any violation Block + incident
Error rate spike > 3x baseline for 5 minutes Alert
CPU/memory spike > 5x baseline sustained Alert + throttle

Result Poisoning Detection

One of the most dangerous MCP attack vectors is result poisoning — an MCP server returns results that contain prompt injection payloads designed to manipulate the AI agent. The runtime monitor scans all tool results for:

  • Known prompt injection patterns (instruction override attempts)
  • Hidden Unicode characters used for steganographic injection
  • Base64-encoded payloads in text fields
  • Anomalous result structures that differ from the server's historical patterns
  • Results that reference tools or capabilities not present in the conversation

The detection engine uses a combination of regex pattern matching (fast, low false-positive for known patterns) and a small, fast LLM classifier (catches novel injection attempts at the cost of ~10ms latency per result).

Event Stream Architecture

All monitoring events flow through a Kafka-compatible event stream (we recommend Redpanda for operational simplicity) with the following topic structure:

  • mcpguard.events.tool-calls — Every tool invocation with timing and metadata
  • mcpguard.events.anomalies — Detected behavioral deviations
  • mcpguard.events.blocks — Enforcement actions taken
  • mcpguard.events.attestation-violations — Capability attestation breaches
  • mcpguard.events.result-scans — Result poisoning detection events

Enterprise customers can consume these streams directly for integration with their SIEM (Splunk, Sentinel, Elastic Security) or SOAR platforms.

Layer 5: Incident Dashboard

The incident dashboard is the human interface for security teams. It transforms raw monitoring events into actionable intelligence.

Dashboard Components

Real-Time Event Feed. A live-updating stream of security events across all monitored MCP servers. Filterable by severity, server, event type, and time range. Each event links to the underlying telemetry data for investigation.

Server Health Grid. A bird's-eye view of all MCP servers in the organization's environment. Each server is represented as a tile colored by its current health status (green/yellow/orange/red). Clicking a tile drills into that server's detailed behavioral profile.

Incident Timeline. When an incident is detected, the dashboard automatically constructs a timeline from the event stream:

  1. First anomalous event (with timestamp and context)
  2. Escalation events (if the anomaly persisted or worsened)
  3. Enforcement actions taken (blocks, quarantines)
  4. Affected users and sessions
  5. Recommended remediation steps

Trust Score Trends. Historical charts showing how trust scores for each server have changed over time. This makes it easy to spot the gradual degradation that indicates a supply chain compromise (the "slow burn" attack pattern).

Policy Compliance. For enterprises with defined trust policies (e.g., "only Verified-tier servers in production"), the dashboard shows compliance status with drill-down into violations.

Alert Pipeline

Alerts flow through a configurable pipeline:

  1. Detection — Runtime monitor or scheduled re-scan identifies an issue
  2. Deduplication — Multiple alerts for the same root cause are grouped
  3. Enrichment — Alert is enriched with server metadata, trust score, affected users
  4. Routing — Alert routes to the appropriate channel based on severity and server owner
  5. Escalation — If not acknowledged within SLA, alert escalates to next tier

Integration targets: PagerDuty, OpsGenie, Slack, Microsoft Teams, email, webhook.

Security of the Platform Itself

A security platform must be secure. MCPGuard's own security posture:

  • Zero-trust architecture — Every internal service authenticates via mTLS
  • Secrets in HSM — Signing keys stored in AWS CloudHSM, never in environment variables
  • Immutable audit trail — All administrative actions logged to append-only storage
  • Pen-tested quarterly — Third-party penetration testing of all public-facing surfaces
  • SOC 2 Type II — Compliance from Year 1 (requirement for enterprise sales)
  • Bug bounty program — Launching at public beta to incentivize external security research

Conclusion

MCPGuard's technical architecture is designed around one principle: defense in depth. No single layer is sufficient. Static analysis catches known patterns. Dynamic analysis catches behavioral threats. Runtime monitoring catches post-deployment changes. The trust score engine synthesizes all signals into an actionable decision. And the incident dashboard gives security teams the visibility they need to respond.

The architecture is deliberately modular. We can ship the static scanner and registry (Phase 1) with a small team in four months, then iterate toward runtime monitoring and enterprise features based on customer feedback. Each layer adds value independently while becoming more powerful in combination.

For the MCP ecosystem to achieve enterprise adoption, it needs a security infrastructure layer. MCPGuard is that layer. The next chapter maps this architecture to the market opportunity and go-to-market strategy that turns the technology into a business.
