6.1 System Architecture Overview

AgentShield is a lightweight runtime security layer that sits between AI agents and the operating system. It intercepts, analyzes, and enforces policy on every system call an AI agent makes -- file reads, file writes, process spawns, network connections, and IPC operations -- without requiring changes to the agent's source code.

The architecture has three primary layers:

  1. Sensor Layer -- Kernel-level observation using eBPF (Linux) and Endpoint Security Framework (macOS)
  2. Policy Engine -- User-space decision engine that evaluates observed behavior against security policies
  3. Enforcement Layer -- Blocks, allows, or modifies operations based on policy decisions

6.2 Sensor Layer: eBPF on Linux

Extended Berkeley Packet Filter (eBPF) is the foundation of AgentShield's Linux implementation. eBPF allows us to run sandboxed programs inside the Linux kernel without modifying kernel source code or loading kernel modules. This is the same technology that powers Cilium (Kubernetes networking), Falco (runtime security), and Facebook's production monitoring infrastructure.

Why eBPF Over Alternatives

Approach Latency Safety Root Required Modification to Agent
eBPF (our approach) <1us per probe Kernel-verified, cannot crash Yes (CAP_BPF) None
ptrace (strace-style) 10-100us per syscall User-space, safe No None, but high overhead
LD_PRELOAD injection <1us User-space, bypassable No Requires shared library
Kernel module <1us Unsafe, can crash kernel Yes None
seccomp-bpf only <1us Kernel-verified No (with TSYNC) Must be set by parent

eBPF provides kernel-level visibility with user-space safety. The eBPF verifier -- a static analyzer built into the Linux kernel -- guarantees that our sensor code cannot crash the system, access arbitrary memory, or enter infinite loops. This is not a security claim we make; it is a guarantee enforced by the kernel itself.

Probe Architecture

AgentShield deploys four categories of eBPF probes:

1. Syscall Probes (seccomp-bpf + tracepoints)

We attach to the entry and exit points of security-relevant system calls:

// Simplified eBPF probe for file open operations
SEC("tracepoint/syscalls/sys_enter_openat")
int trace_openat_entry(struct trace_event_raw_sys_enter *ctx) {
    u32 pid = bpf_get_current_pid_tgid() >> 32;

    // Fast-path: skip if PID not in monitored set
    if (!bpf_map_lookup_elem(&monitored_pids, &pid))
        return 0;

    struct event_t *event = bpf_ringbuf_reserve(&events, sizeof(*event), 0);
    if (!event)
        return 0;

    event->pid = pid;
    event->syscall = SYS_openat;
    event->timestamp = bpf_ktime_get_ns();
    bpf_probe_read_user_str(event->path, sizeof(event->path),
                            (const char *)ctx->args[1]);
    event->flags = (int)ctx->args[2];

    bpf_ringbuf_submit(event, 0);
    return 0;
}

The monitored syscalls cover the complete attack surface of AI agents:

Syscall Category Syscalls Monitored Agent Behavior Captured
File I/O openat, read, write, unlinkat, renameat File reads, writes, deletions
Process execve, execveat, clone, fork, kill Shell commands, subagent spawning
Network connect, bind, sendto, recvfrom API calls, data exfiltration
IPC pipe2, socketpair, mmap (shared) Agent-to-agent communication
Metadata fstat, getdents64, readlinkat Directory listing, symlink following

2. LSM (Linux Security Module) Probes

Where available (Linux 5.7+), we attach eBPF programs to LSM hooks for mandatory access control decisions. LSM hooks fire before the kernel performs a security-sensitive operation, giving us the ability to block operations rather than just observe them:

SEC("lsm/file_open")
int BPF_PROG(agent_file_open, struct file *file) {
    u32 pid = bpf_get_current_pid_tgid() >> 32;

    struct agent_identity *agent = bpf_map_lookup_elem(&agent_map, &pid);
    if (!agent)
        return 0;  // Not a monitored agent, allow

    // Extract file path and check against agent's allowed paths
    // Returns -EPERM to deny, 0 to allow
    return evaluate_file_policy(agent, file);
}

3. Network Probes (TC and XDP)

For network-level enforcement, we use Traffic Control (TC) eBPF programs attached to the agent's network namespace:

SEC("tc")
int agent_egress_filter(struct __sk_buff *skb) {
    // Extract destination IP and port
    struct iphdr *ip = (void *)(long)skb->data + sizeof(struct ethhdr);
    struct tcphdr *tcp = (void *)ip + sizeof(struct iphdr);

    u32 pid = skb->mark;  // PID injected by cgroup eBPF
    struct agent_identity *agent = bpf_map_lookup_elem(&agent_map, &pid);
    if (!agent)
        return TC_ACT_OK;

    // Check destination against agent's network allowlist
    struct network_rule key = {
        .agent_type = agent->type,
        .dst_ip = ip->daddr,
        .dst_port = tcp->dest,
    };

    if (!bpf_map_lookup_elem(&network_allowlist, &key))
        return TC_ACT_SHOT;  // Drop packet

    return TC_ACT_OK;
}

4. cgroup Probes (Resource Accounting)

We use cgroup eBPF programs to enforce resource budgets per agent:

  • CPU time limits per tool invocation

  • Network bandwidth quotas

6.3 Sensor Layer: macOS Endpoint Security Framework

macOS does not support eBPF. Apple's kernel does not expose the infrastructure, and the System Integrity Protection (SIP) model prevents loading kernel extensions in modern macOS versions. Instead, macOS provides the Endpoint Security (ES) framework -- a user-space API introduced in macOS 10.15 (Catalina) that provides real-time notification of security-relevant events.

ES Framework Architecture

The Endpoint Security framework runs as a system extension (not a kernel extension), which means:

  • It survives macOS updates without recompilation
  • It does not require disabling SIP
  • It receives events through a Mach port from the kernel
  • It can block operations (AUTH events) or just observe them (NOTIFY events)

Monitored Event Types

AgentShield subscribes to the following ES event types on macOS:

ES Event Equivalent Linux Syscall What It Captures
ES_EVENT_TYPE_AUTH_OPEN openat File open (can block)
ES_EVENT_TYPE_AUTH_EXEC execve Process execution (can block)
ES_EVENT_TYPE_AUTH_SIGNAL kill Signal delivery (can block)
ES_EVENT_TYPE_NOTIFY_WRITE write File write (observe only)
ES_EVENT_TYPE_NOTIFY_UNLINK unlinkat File deletion (observe only)
ES_EVENT_TYPE_NOTIFY_FORK fork Process creation (observe only)
ES_EVENT_TYPE_NOTIFY_EXIT exit_group Process termination (observe only)

Critical limitation: The ES framework's AUTH events (which can block operations) have a 60-second deadline. If AgentShield does not respond within 60 seconds, macOS auto-allows the operation. Our policy engine is designed to respond in under 1 millisecond, but this deadline is an important architectural constraint -- we cannot defer decisions to a remote server for AUTH events.

6.4 The Policy Engine

The policy engine is the brain of AgentShield. It receives events from the sensor layer and makes allow/deny/audit decisions based on configurable policies. The engine runs in user space and is designed for two competing requirements: low latency (decisions in microseconds, not milliseconds) and rich context (understanding which agent, which tool, which session is making the request).

Policy Language

AgentShield policies are written in a declarative YAML format designed for security teams, not kernel developers:

# agentshield-policy.yaml
version: "1.0"
name: "enterprise-ai-agents"

      bash:

              - "${WORKSPACE}/**"           # Project files

            deny:
              - "~/.ssh/**"                 # SSH keys
              - "~/.aws/**"                 # AWS credentials
              - "**/.env"                   # Environment files
              - "/etc/shadow"               # System passwords
          write:
            allow:
              - "${WORKSPACE}/**"
              - "/tmp/claude-*/**"

              - "${WORKSPACE}/.git/hooks/**"  # Git hook injection
              - "**/*.pem"                    # Certificate files

        process_execution:

            - "git"
            - "npm"
            - "node"

Rule Evaluation Performance

Policy evaluation must be fast -- every syscall goes through the engine. We use a multi-tier evaluation strategy:

Tier 1: eBPF-side fast path (kernel space, <1us)

Simple allow/deny decisions are pushed into eBPF maps. The eBPF probe checks the map before forwarding the event to user space:

PID 12345 + syscall openat + path prefix "/home/user/project/" → ALLOW (no event emitted)
PID 12345 + syscall openat + path prefix "/etc/" → FORWARD TO USER SPACE

This eliminates 80-90% of events before they leave the kernel, because most agent activity involves reading and writing files within the project directory.

Tier 2: Policy engine fast path (user space, <50us)

Events that reach user space hit a precompiled rule table. Policies are compiled from YAML into a radix tree (for path matching) and a hash map (for process and network matching) at load time:

Rule lookup: O(1) for exact matches, O(k) for prefix matches where k = path depth
Memory: ~2MB per 10,000 rules

Tier 3: Context-enriched evaluation (user space, <500us)

Complex rules that require context -- parent process chain, cumulative resource usage, behavioral anomaly scores -- go through the full evaluation pipeline. This applies to less than 5% of events.

Anomaly Detection

Beyond static rules, the policy engine maintains behavioral baselines for each agent type. The baseline captures:

Metric Baseline Example (Claude Code) Alert Threshold
Files read per minute 15-40 >200
Files written per minute 5-15 >100
Unique directories accessed 3-8 >30
Shell commands per minute 2-10 >50
Network connections per minute 1-5 >20
Subagent spawn rate 0-2 per task >5 per minute

When an agent exceeds a threshold, the policy engine escalates: first to audit mode (log but allow), then to interactive mode (prompt the user), then to block mode if the anomaly continues.

6.5 The Agent Identity Model

The most novel technical contribution of AgentShield is the agent identity model. Traditional security tools monitor processes by PID. But AI agents are not single processes -- they are process trees. Claude Code spawns bash shells, which spawn git, python, npm, and other tools. Each of those tools may spawn further child processes. Without an identity model, a security tool cannot distinguish between "the developer ran rm -rf node_modules" and "Claude Code's bash tool ran rm -rf /".

Identity Resolution

AgentShield builds an identity chain for every monitored process:

Process: python3 (PID 45678)
  Parent: bash (PID 45670)
    Parent: claude (PID 45650)
      Parent: zsh (PID 12345)
        Parent: Terminal (PID 1000)

Identity Resolution:
  Agent: claude-code
  Tool: BashTool
  Session: sess_abc123
  Operation: test execution (python3 -m pytest)

The identity resolution algorithm:

  1. On fork/clone/execve, record the new PID and its parent PID in the process tree map
  2. Walk the parent chain upward until we find a known agent binary ("claude", "cursor", "copilot-agent")
  3. Extract the agent type and session context from the agent process's environment variables and command-line arguments
  4. Inherit the parent's policy context, with any restrictions applied by the agent's tool-level policies
  5. Cache the identity resolution for the PID's lifetime (invalidated on exit)

Subagent Tracking

The subagent explosion is one of the key security problems identified in our audit research (Chapter 4). When Claude Code spawns a subagent using its AgentTool, the subagent runs as a new instance of the same binary, with its own tool set and permissions. Our security audit of Claude Code's source (finding #3: "Subagent Execution Without Process-Level Isolation," CVSS 7.8) revealed that subagents inherit the parent agent's full permissions with no additional restrictions.

AgentShield solves this with depth-based policy attenuation:

Subagent Depth Default Permissions
Depth 0 (primary agent) Full policy as configured
Depth 1 (first subagent) Read-only file access, no network, no further subagents
Depth 2 (sub-subagent) Read-only file access within ${WORKSPACE}/src only
Depth 3+ Blocked by default (configurable)

Each depth level removes capabilities rather than adding them. This implements the principle of least privilege across the agent hierarchy.

On Linux, we use unshare(CLONE_NEWNET) to create the namespace and veth pairs to connect it to the host network through our filtering proxy. On macOS, we use the Network Extension framework's content filter to achieve equivalent filtering (though without true namespace isolation, which macOS does not support).

DNS Control

DNS is the most commonly exploited side channel for data exfiltration. AgentShield runs a local DNS resolver inside the agent's network namespace that:

  1. Resolves only domains on the allowlist
  2. Returns NXDOMAIN for all other queries
  3. Logs all DNS queries for audit
  4. Blocks DNS-over-HTTPS to prevent resolver bypass

This closes the DNS exfiltration vector entirely -- an agent cannot resolve data.attacker.com to encode stolen data in subdomain labels.

6.7 Resource Budgets

AI agents can consume unbounded resources. A buggy or malicious agent can fill a disk, exhaust memory, or saturate a network connection. Our audit research identified recursive subagent forking without depth limits (finding #14) as a medium-severity vulnerability.

AgentShield enforces resource budgets per agent session:

resource_budgets:
  claude-code:
    per_session:
      cpu_seconds: 3600        # 1 hour of CPU time
      memory_mb: 4096          # 4GB RAM
      disk_write_mb: 1024      # 1GB of disk writes
      network_egress_mb: 100   # 100MB outbound data
      process_count: 50        # Max concurrent processes
      open_files: 500          # Max open file descriptors

    per_tool_invocation:
      cpu_seconds: 60          # 1 minute per tool call
      memory_mb: 1024          # 1GB per tool call
      timeout_seconds: 300     # 5 minute hard timeout

On Linux, budgets are enforced through cgroup v2 controllers. On macOS, we use a combination of setrlimit (for the agent process) and the policy engine's event-based accounting (for cumulative limits).

When a budget is exhausted, the policy engine takes graduated action:

  1. Warning at 80% -- log event, optionally notify user
  2. Throttle at 90% -- rate-limit the agent's operations
  3. Block at 100% -- deny further operations of that type
  4. Kill at 110% (grace period exceeded) -- terminate the agent process

6.9 Why This Architecture Wins

The technical decisions in AgentShield's architecture map directly to competitive advantages:

eBPF-based (not ptrace) 100x lower overhead than strace-style approaches
Kernel-level observation Cannot be bypassed by the agent -- unlike user-space wrappers
Zero-modification deployment Works with any agent immediately, no vendor partnership required
Agent identity model Solves the multi-agent attribution problem no one else addresses
Network namespace isolation True isolation, not just logging -- data cannot leave

Dual-platform (Linux + macOS) Covers 95%+ of developer workstations

Technical Moat

The technical moat is the eBPF expertise. Writing correct, performant, production-grade eBPF programs is hard -- the verifier rejects the vast majority of programs, maps must be carefully sized, and race conditions at kernel speed are subtle. There are perhaps 500 engineers in the world with deep eBPF production experience, and most of them work at Cilium/Isovalent, Meta, Google, or Netflix. Our founding team includes one of them.

The agent identity model is an additional moat. No existing security tool understands that PID 45678 is "a python process spawned by a bash shell spawned by Claude Code's BashTool in session abc123." Building this understanding requires deep knowledge of how AI agents work internally -- knowledge that comes from the security audit research described in Chapter 2.

6.10 Open Engineering Questions

We are honest about what is not yet solved:

  1. Windows support. Windows does not have eBPF or an ES Framework equivalent. ETW (Event Tracing for Windows) provides observation but not enforcement. We will need a minifilter driver, which is expensive to develop and requires Microsoft signing. Windows support is planned for v2 (post-Series A).

  2. Container environments. When AI agents run inside Docker containers (common in CI/CD), our eBPF probes need access to the container's cgroup and PID namespace. This works today on Linux but requires privileged container permissions, which some enterprises restrict.

  3. Remote MCP servers. AgentShield monitors local system calls, but MCP servers accessed over HTTP (Streamable HTTP transport) run on remote machines. We cannot observe their behavior at the kernel level. For remote MCP servers, we rely on network-level monitoring and response content analysis -- a weaker security guarantee.

  4. Policy update latency. When policies are updated from the enterprise console, there is a propagation delay to endpoints. During this window, stale policies apply. We target <30 second propagation, but network conditions can increase this.

These are engineering problems, not fundamental limitations. Each has a clear path to resolution, and each represents a product roadmap milestone that justifies continued investment.

Chapter Summary

AgentShield's technical architecture is built on three insights from our security research:

  1. Kernel-level observation is the only reliable approach. User-space wrappers can be bypassed. eBPF cannot. The agent does not get to choose whether it is monitored.

  2. Agent identity is the missing abstraction. Traditional security tools see processes. AgentShield sees agents, tools, sessions, and subagent hierarchies. This is the difference between "PID 45678 read a file" and "Claude Code's subagent tried to read your SSH keys."

  3. Policy must be declarative and fast. Security teams need to write rules in YAML, not C. And those rules must evaluate in microseconds, not seconds. The two-tier evaluation strategy (eBPF fast path + user-space rich context) delivers both.

The architecture is implementable with a team of four engineers in six months, production-ready in nine. The eBPF and ES Framework code is the hardest part; the policy engine and dashboard are straightforward by comparison.
