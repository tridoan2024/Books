Appendix A: Vulnerability Research That Inspired These Companies

This appendix provides the technical foundation for every claim in this book. Each startup proposal --- AgentShield, MCPGuard, and VaultAgent --- was inspired by specific vulnerabilities discovered during our security source review of production AI coding agents. What follows is a structured catalog linking each vulnerability to the startup it inspired, the technical details of the finding, and the product feature designed to prevent it.

The source data comes from Security Source Review Report SECSR-20260412, a 50-finding audit of a production AI coding agent comprising over 500,000 lines of TypeScript. The audit was conducted using multi-agent security analysis (static scanner, design reviewer, supply chain scanner, patch engineer) and produced findings across 5 severity levels: 2 CRITICAL, 8 HIGH, 23 MEDIUM, 11 LOW, and 6 INFO.

A.1 Methodology

Audit Scope

The audit targeted the complete source code of a production AI coding agent, including:

  • CLI entry point and main orchestrator (4,000+ line core module)
  • 30+ tool implementations (Bash, Read, Write, Edit, Grep, Glob, WebFetch, AgentTool, etc.)
  • Permission system (6 modes, 8 rule sources, 3 rule types)
  • Authentication and credential management (OAuth2 PKCE, keychain integration, JWT handling)
  • Plugin and extension system (marketplace, installation, execution)
  • MCP server integration (connection management, tool execution, result handling)
  • Network infrastructure (bridge sessions, WebSocket, upstream proxy)
  • Telemetry and diagnostics (analytics, error reporting, debug logging)

Analysis Techniques

Technique Tool/Method Coverage
Static analysis Custom pattern matching (9 raw log files generated) Full codebase
Design review Architecture analysis against OWASP, CWE, NIST frameworks Core modules
Supply chain analysis Dependency tree audit, plugin system review All external dependencies
Data flow analysis Credential lifecycle tracing from input to storage to logging Authentication paths
Threat modeling STRIDE applied to each architectural component Entry points, trust boundaries

A.2 Vulnerabilities That Inspired AgentShield

AgentShield addresses runtime security for AI agents --- sandboxing, permission enforcement, and behavioral monitoring. The following vulnerabilities demonstrate why dedicated runtime security is necessary.

Finding: Subagent Execution Without Process-Level Isolation

Field Value
Severity HIGH (CVSS 7.8)
CWE CWE-269: Improper Privilege Management
Location tools/AgentTool/runAgent.ts:248
Startup AgentShield

Technical detail: When an AI agent spawns a subagent (using the AgentTool), the subagent inherits the parent's full process context: environment variables, file system access, network capabilities, and credential access. No process-level isolation (separate PID namespace, filesystem namespace, or network namespace) is applied. A compromised or malicious subagent has identical privileges to the parent agent.

Product mapping: AgentShield's per-agent sandboxing creates isolated execution contexts for subagents. Each subagent receives a capability-scoped policy: limited file system paths, restricted network access, and no access to parent agent credentials. The eBPF sensor layer monitors syscalls per subagent process, enforcing resource budgets and behavioral policies independently.

Finding: Shell Command Injection Risk via Unsanitized Tool Arguments

Field Value
Severity MEDIUM (CVSS 6.5)
CWE CWE-78: OS Command Injection
Location BashTool command construction
Startup AgentShield

Technical detail: The Bash tool's security pipeline checks 100+ injection patterns, but the pattern-matching approach is fundamentally incomplete. Obfuscated commands, encoding tricks (hex-encoded strings, base64 piped to eval), and chained command construction through environment variables can evade static pattern matching. The command classification system (READ-ONLY, WRITE, DESTRUCTIVE, INDIRECT, NETWORK, UNKNOWN) is comprehensive but operates on the command string, not the actual system calls executed.

Product mapping: AgentShield monitors actual syscalls via eBPF, not command strings. Even if a command string evades pattern matching, the resulting syscalls (file open, network connect, process exec) are captured and evaluated against the agent's security policy. This shifts the security boundary from string analysis to system call enforcement.

Finding: dangerouslySkipPermissions Flag Bypasses All Safety Controls

Field Value
Severity MEDIUM (CVSS 6.2)
CWE CWE-862: Missing Authorization
Location Permission system bypass mode
Startup AgentShield

Technical detail: The --dangerously-bypass-permissions flag disables all permission checks. The flag name is intentionally verbose as a friction mechanism, but no runtime check verifies that the environment is actually sandboxed (container, VM, or disposable filesystem). A developer who passes this flag on their workstation gets bypass mode on their production filesystem.

Product mapping: AgentShield provides the external sandboxing that makes bypass mode safe. Even in bypass mode, AgentShield's eBPF policies enforce: no access outside the project directory, no modification of system files, no network connections to internal services, and resource budgets on CPU/memory/disk. The agent can bypass its own permission system; it cannot bypass the OS-level sandbox.

Finding: Recursive Subagent Forking Without Depth Limits

Field Value
Severity MEDIUM (CVSS 5.8)
CWE CWE-674: Uncontrolled Recursion
Location Subagent spawning logic
Startup AgentShield

Technical detail: Agents can spawn subagents, which can spawn further subagents, with no enforced depth limit. A prompt injection that instructs the agent to "spawn a subagent that spawns a subagent" can create an exponential process tree. The maxTurns limit on individual agents does not prevent the total process count from growing.

Product mapping: AgentShield enforces global resource budgets: maximum total subagent processes, maximum depth of agent tree, maximum aggregate memory/CPU across all agent processes. These limits operate at the process tree level, not the individual agent level.

A.3 Vulnerabilities That Inspired MCPGuard

MCPGuard addresses supply chain security for the MCP ecosystem --- server verification, trust scoring, and behavioral monitoring.

Finding: No Cryptographic Signature Verification for Plugins

Field Value
Severity CRITICAL (CVSS 9.1)
CWE CWE-494: Download of Code Without Integrity Check
Location plugins/ and utils/plugins/
Startup MCPGuard

Technical detail: Plugins and MCP servers are downloaded and executed without cryptographic signature verification. No code signing, no hash verification, no certificate chain validation. A man-in-the-middle attacker, a compromised registry, or a malicious package maintainer can substitute arbitrary code that the agent will execute with full privileges.

Product mapping: MCPGuard implements a trust verification pipeline: cryptographic signature validation (package must be signed by a known maintainer key), content hash verification (SHA-256 of package contents must match registry record), and behavioral attestation (runtime behavior must match declared capabilities). Unsigned or unverified packages are flagged and quarantined.

Finding: No Cryptographic Signature Verification for Downloaded Plugins (Duplicate Pattern)

Field Value
Severity CRITICAL (CVSS 8.1)
CWE CWE-494: Download of Code Without Integrity Check
Location utils/plugins/pluginLoader.ts, marketplaceManager.ts
Startup MCPGuard

Technical detail: The plugin loader downloads zip archives from marketplace URLs and extracts them directly. The marketplace manager does not verify package authenticity. Both the download (network transfer) and installation (zip extraction) lack integrity checks. The plugin version tracking uses short git commit hashes that are trivially collision-prone.

Product mapping: MCPGuard's registry provides verified package listings with full-length content hashes, signature chains, and provenance tracking. The scanner component analyzes extracted plugin code before execution, checking for obfuscated payloads, suspicious system calls, and capability mismatches between declared functionality and actual code behavior.

Finding: Symlink-Based Path Traversal Risk in ZIP Extraction

Field Value
Severity HIGH (CVSS 7.5)
CWE CWE-22: Path Traversal
Location utils/plugins/zipCache.ts, utils/dxt/zip.ts
Startup MCPGuard

Technical detail: ZIP files can contain symlinks that point to arbitrary locations on the file system. When a plugin ZIP is extracted, a malicious symlink entry can create a link from the extraction directory to /etc/passwd, ~/.ssh/id_rsa, or any other sensitive file. Subsequent file operations through the "extracted plugin" actually read or write to the symlink target.

Product mapping: MCPGuard's package scanner detects symlinks in ZIP archives before extraction, checks for path traversal sequences (../) in file names, and validates that all extracted paths remain within the expected installation directory. Packages with suspicious ZIP entries are flagged and blocked.

Finding: MCP Server Tools Execute Without Capability Verification

Field Value
Severity HIGH (CVSS 7.0)
CWE CWE-862: Missing Authorization
Location MCP service layer
Startup MCPGuard

Technical detail: When an MCP server declares tools (via the tools/list endpoint), those tool declarations are trusted without verification. A malicious MCP server can declare tools with misleading descriptions (tool description injection), claim capabilities it does not have, or change its tool declarations between listing and invocation. There is no capability attestation protocol to verify that a server's declared tools match its actual behavior.

Product mapping: MCPGuard's capability attestation protocol compares declared tool capabilities against observed runtime behavior. If a server declares a "read-only file search" tool but the tool makes network connections or writes files, the behavior anomaly triggers an alert and the server's trust score is downgraded.

A.4 Vulnerabilities That Inspired VaultAgent

VaultAgent addresses credential security --- encrypted storage, secret scanning, lifecycle management, and audit trails.

Finding: Plaintext Credential Storage in Configuration Files

Field Value
Severity HIGH (CVSS 7.1)
CWE CWE-312: Cleartext Storage of Sensitive Information
Location Credential storage modules
Startup VaultAgent

Technical detail: API tokens and authentication credentials are stored in plaintext JSON configuration files. The files use standard file system permissions (typically 0644 on creation) without additional encryption. On multi-user systems, any local user can read these credentials. Backup software, cloud sync tools, and search indexers may copy these files to unprotected locations.

Product mapping: VaultAgent's encrypted vault replaces plaintext JSON with libsodium-encrypted storage backed by OS keychain integration. Credentials are encrypted at rest with keys derived from the OS keychain (macOS Keychain, Windows Credential Locker, Linux Secret Service). The plaintext credential files are detected, migrated, and securely deleted.

Finding: Plaintext Credential Fallback Storage

Field Value
Severity HIGH (CVSS 7.0)
CWE CWE-522: Insufficiently Protected Credentials
Location Secure storage fallback path
Startup VaultAgent

Technical detail: When the OS keychain is unavailable (headless environments, CI/CD, SSH sessions without desktop), the credential storage system falls back to plaintext file storage. This fallback is silent --- the user is not warned that their credentials are being stored without encryption. The fallback path stores credentials in a JSON file in the user's home directory.

Product mapping: VaultAgent eliminates the plaintext fallback entirely. For headless environments, VaultAgent provides an encrypted file vault using a passphrase-derived key (Argon2id key derivation). The user is always explicitly informed of the storage mode and encryption status. No silent fallback to plaintext.

Finding: Conversation History Stored Without Encryption

Field Value
Severity HIGH (CVSS 6.8)
CWE CWE-316: Cleartext Storage of Sensitive Information in Memory
Location History storage module
Startup VaultAgent

Technical detail: Conversation history --- including any credentials the user shared with the agent (database URLs, API keys, SSH commands with embedded passwords) --- is stored in plaintext JSON. The history files accumulate over time and are not subject to credential scanning or redaction.

Product mapping: VaultAgent's secret scanner monitors conversation history in real-time, detecting 23+ credential patterns (API keys, database URLs, SSH passwords, cloud tokens). Detected credentials are automatically redacted from the stored history and replaced with vault references. The original credential is stored only in the encrypted vault.

Finding: JWT Decoded Without Signature Verification

Field Value
Severity HIGH (CVSS 7.5)
CWE CWE-347: Improper Verification of Cryptographic Signature
Location bridge/jwtUtils.ts:21
Startup VaultAgent

Technical detail: JWT tokens from the authentication bridge are decoded using base64 parsing without cryptographic signature verification. An attacker who can intercept or modify the JWT can inject arbitrary claims (user ID, organization, permissions) that the agent trusts without validation. This is a textbook JWT vulnerability (OWASP JWT Cheat Sheet, #1 common mistake).

Product mapping: VaultAgent's token lifecycle manager validates JWT signatures using the issuer's public key before accepting any claims. Token rotation is enforced on a per-session basis, and expired or revoked tokens are immediately rejected. The audit trail records every token validation event, including failures.

Finding: Token Prefix Logged in Debug Output

Field Value
Severity MEDIUM (CVSS 5.5)
CWE CWE-532: Insertion of Sensitive Information into Log File
Location Debug logging modules
Startup VaultAgent

Technical detail: Debug log output includes token prefixes (first 8-12 characters of authentication tokens). While the full token is not logged, the prefix may be sufficient for correlation attacks (identifying which token is in use) and, in combination with other information leaks, could assist in token reconstruction.

Product mapping: VaultAgent's log scanner detects token-like patterns in debug output and either redacts them completely or replaces them with opaque identifiers that can be resolved only through the audit dashboard with appropriate authorization.

A.5 Cross-Cutting Vulnerabilities

Some findings affect multiple layers and inform features across multiple products:

Finding: TOCTOU Race Conditions (3 instances)

Field Value
Severity MEDIUM (CVSS 5.0-6.0)
CWE CWE-367: Time-of-Check Time-of-Use
Locations Read stat checks, credential file checks, plugin version checks
Startups AgentShield, MCPGuard, VaultAgent

Technical detail: Three separate TOCTOU race conditions exist where a security check (file exists? file permissions? credential valid?) and the subsequent use (read file, use credential, execute plugin) are separated by a time gap. An attacker who can modify the checked resource between the check and the use can bypass the security control.

Product mapping: AgentShield addresses filesystem TOCTOU via atomic open-and-check operations at the syscall level. VaultAgent addresses credential TOCTOU via atomic vault transactions (check + use in a single locked operation). MCPGuard addresses plugin TOCTOU via content-hash-based verification (hash is computed at extraction time and re-verified at execution time).

Finding: WebSocket Missing Origin Validation / SSRF Risks

Field Value
Severity MEDIUM
CWE CWE-346 (Origin Validation), CWE-918 (SSRF)
Locations WebSocket handler, WebFetch tool
Startups AgentShield

Technical detail: The WebSocket connection for remote sessions does not validate the Origin header, potentially allowing cross-site WebSocket hijacking. The WebFetch tool follows redirects and may be susceptible to DNS rebinding attacks for SSRF.

Product mapping: AgentShield's network policy enforcement blocks outbound connections to internal network ranges (10.x, 172.16-31.x, 192.168.x), validates WebSocket origins against an allowlist, and implements DNS rebinding protection through pre-resolution IP address verification.
