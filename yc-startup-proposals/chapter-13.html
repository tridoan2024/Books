Idea

Why did you pick this idea to work on?

We were doing security audits of production AI agent codebases when we discovered something alarming: MCP servers are the new npm packages, but the ecosystem has none of the security infrastructure that took npm a decade to build.

In our most detailed audit — a 500K+ line AI coding agent — we found 50 vulnerabilities organized into 7 dependency chains. The credential storage chain alone contained 8 HIGH-severity findings: plaintext OAuth tokens on disk (CWE-312, CVSS 7.1), credential fallback to unencrypted JSON files (CWE-256, CVSS 7.1), conversation history with pasted secrets stored permanently in cleartext (CWE-312, CVSS 7.0), and environment variable tokens that never expire (CWE-613, CVSS 6.5).

The supply chain was worse. The plugin system had no code signing. Zip extraction had path traversal vulnerabilities. MCP servers loaded into the host process with full access to filesystem, network, and credentials. A single compromised MCP server could steal every OAuth token, API key, and conversation in the developer's environment.

These are not theoretical vulnerabilities. We built proof-of-concept exploits for each one. And this was one agent, from one major vendor, who is generally considered security-conscious. The ecosystem-wide exposure is orders of magnitude larger.

We picked this idea because we are the researchers who found these vulnerabilities, and we know exactly what the security layer needs to look like.

Investor Notes: This answer demonstrates: (1) the idea came from real research, not market analysis, (2) we have deep technical understanding of the vulnerability landscape, (3) specific CVE and CVSS references prove we are credentialed security researchers, not generalists claiming a security opportunity. The data from the actual audit reports (8 HIGH credential findings, 7 dependency chains, 50 total vulnerabilities) provides the concrete evidence YC partners respect.

What's new about what you are making?

Three things:

  1. Protocol-native security. Existing security tools (Snyk, Socket.dev, Wiz) analyze packages and infrastructure. MCPGuard understands MCP at the protocol level — we analyze tool descriptions for injection, validate capability attestations against code behavior, and monitor runtime MCP message flows. No existing tool does this.

  2. Behavioral trust scoring. We do not just check for known vulnerabilities. Our dynamic sandbox runs each MCP server and observes its actual behavior: what files it reads, what network calls it makes, how it responds to adversarial inputs. This catches zero-day threats that static analysis misses.

  3. Ecosystem-scale registry. We are not just a scanner — we are building the verified registry that becomes the authoritative source for MCP server security data. This creates a network effect: every server scanned makes the platform more valuable for every user.

No direct competitor in MCP-specific supply chain security. Adjacent competitors:

  • Socket.dev ($10M ARR): npm/PyPI supply chain analysis. Closest in concept but package-level only. No protocol-level analysis, no runtime monitoring, no trust scoring for AI-specific threats.

  • Pillar Security ($5M ARR): Broad AI security platform. Covers many threat vectors but lacks depth in MCP supply chain analysis.

The opportunity exists because MCP is new enough that incumbents have not prioritized it, and broad enough that a focused startup can own the category.

Investor Notes: YC wants honest competitive analysis. We acknowledge that Snyk could theoretically build this, but we explain why they likely will not prioritize it. The key insight: incumbents are generalists; we are specialists in a rapidly growing niche. This is the classic startup advantage.

What's your moat against these competitors?

Four compounding advantages:

  1. Threat intelligence data. Every MCP server we scan feeds our detection models. By the time a competitor reaches 1,000 servers scanned, we will have analyzed 50,000. This data advantage compounds — our scanners get smarter with every server, detecting new patterns that only emerge at scale.

  2. Publisher ecosystem. Publishers who build their trust score history on MCPGuard cannot transfer that history to a competitor. Their verified identity, behavioral track record, and accumulated trust score are locked into our platform. This is the same lock-in that npm created for package publishers.

  3. Enterprise policy integration. When an enterprise configures "only install Verified-tier MCP servers" as policy, they are referencing MCPGuard's trust tiers. Switching requires re-evaluating every server against a new scoring system and reconfiguring policy across all developer machines.

  4. Specification influence. By contributing capability attestation and signing standards to the MCP specification, we embed our approach into the protocol itself. Competitors must implement our standards, effectively validating our architecture.

Additional Context

Is there anything else you would like us to know?

The MCP ecosystem is at a critical inflection point. The protocol has achieved remarkable adoption — it is now the standard way to extend AI agents with external capabilities. But this adoption has outpaced security infrastructure, creating a window of vulnerability that grows wider every day.

Every new npm-style ecosystem goes through the same cycle: explosive growth, security incident, reactive tooling. npm had left-pad, event-stream, and ua-parser-js before the ecosystem invested seriously in supply chain security. PyPI had its own series of typosquatting attacks. Docker Hub had cryptomining images.

MCP has not had its "event-stream moment" yet. But with 10,000+ servers and growing, it is a matter of when, not if. MCPGuard is building the security infrastructure before the first major breach — not after.

We would rather be one year early than one day late.

Founder Q&A: Tough Questions and Direct Answers

YC interviews are known for pointed, skeptical questions. Here are the most likely challenges and how we would respond.

Q: "Snyk could build this in a weekend."

A: They could build a static scanner in a weekend. They cannot build MCP protocol awareness, behavioral trust scoring, a capability attestation protocol, and a verified registry ecosystem in a weekend. More importantly, Snyk is a $7B company optimizing for net retention on their existing npm/pip/Maven customer base. MCP security is a rounding error in their TAM today. By the time it is not, we will have the threat intelligence database, the publisher ecosystem, and the enterprise reference customers. This is the classic innovator's dilemma: the incumbent's existing customers do not need MCP security yet, so they will not prioritize it.

Q: "What if MCP gets replaced by something else?"

A: Our architecture is protocol-agnostic in the analysis and monitoring layers. The scanner engine, trust score algorithm, behavioral baseline, and incident dashboard work with any structured tool protocol. MCP-specific logic lives only in the parser and transport adapter layers — perhaps 15% of the codebase. If a new protocol emerges, we port in weeks, not months. That said, MCP has Anthropic's backing plus integration with every major AI coding tool. Replacing it would be like replacing HTTP — possible in theory, unlikely in practice once the ecosystem reaches critical mass.

Q: "Your traction is thin. 500 servers scanned is not a business."

A: Correct. 500 servers scanned is not a business — it is a proof that the scanner works and that developers care enough to use it. The business starts with enterprise runtime monitoring, which is why we have 5 design partners evaluating that tier now. Our progression is CLI adoption (free) → enterprise evaluation (design partner) → enterprise contract (paid). We are at step 2. YC funding accelerates us to step 3.

Q: "How do you get to $27M ARR in 3 years? That's aggressive."

A: It is aggressive but grounded in comparable trajectories. Snyk went from $0 to $100M ARR in approximately 5 years. Wiz went from $0 to $100M ARR in 18 months. The AI security market is growing faster than the cloud security market was when those companies started. Our $27M Year 3 target requires 5,000 paying customers at $5,400 average revenue — in a market with 100,000+ organizations using MCP. That is 5% penetration. Conservative.

Q: "What is your biggest risk?"

A: Timing. If the first major MCP breach happens before we have runtime monitoring generally available, we miss the conversion opportunity. Our mitigation: the free CLI scanner is live now. When the breach happens, we are the tool everyone reaches for first — even if the monitoring product is still in beta. Security demand spikes after incidents, and the company that already has mindshare captures the demand.
