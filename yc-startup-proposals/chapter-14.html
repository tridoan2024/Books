Chapter 14: The Problem — AI Agents Store Secrets in Plaintext

The Credential Crisis Hiding in Every Developer's Home Directory

Every AI coding agent on the market today has the same dirty secret: they store credentials insecurely. OAuth tokens in plaintext JSON files. API keys in unencrypted conversation history. Passwords pasted into sessions that persist on disk indefinitely. Tokens in environment variables that never expire or rotate.

This is not speculation. This is what we found when we performed a deep security audit of a production AI coding agent — one of the most widely deployed, from one of the most security-conscious companies in the industry. The audit uncovered 50 vulnerabilities organized into 7 dependency chains. The credential storage chain alone contained 8 HIGH-severity findings, each individually sufficient to compromise every secret a developer has shared with or through the agent.

This chapter presents the specific vulnerabilities we found, explains why they exist, quantifies the enterprise-wide exposure, and makes the case that credential management for AI agents is not a feature request — it is an urgent infrastructure gap that represents a venture-scale opportunity.

What We Found: 8 HIGH-Severity Credential Vulnerabilities

Our audit targeted a production AI coding agent: a 500,000+ line TypeScript/Node.js codebase that runs on developer machines, manages OAuth authentication, stores conversation history, and connects to cloud APIs via bridge servers and WebSocket connections. The agent runs on macOS, Linux, and Windows. Millions of developers use it daily.

Here are the credential storage vulnerabilities we discovered, ordered by CVSS severity score.

Finding 1: Plaintext Credential Storage on Non-macOS Platforms

Severity: HIGH | CVSS: 7.1 | CWE: CWE-256 (Plaintext Storage of a Password)

Location: utils/secureStorage/index.ts:9

The function getSecureStorage() returns different storage backends depending on the operating system. On macOS, it uses the system keychain. On every other platform — Linux, Windows, WSL — it returns plainTextStorage, which writes OAuth tokens and credentials as a JSON file at ~/.claude/.credentials.json with chmod 0600 permissions.

The source code contained a telling comment:

// TODO: add libsecret support for Linux
return plainTextStorage

A TODO comment guarding the credential storage path for every non-macOS user. Every Linux developer, every WSL user, every CI/CD pipeline, every container — all using plaintext credential storage protected by nothing more than file permissions.

Why this matters: chmod 0600 prevents other users on the same system from reading the file. It does not prevent: - Root access (standard in containers, common in cloud instances) - Same-user process access (any malware running as the developer) - Backup exfiltration (Time Machine, cloud sync, corporate backup agents) - Disk imaging (forensic tools, VM snapshots) - Container volume mounts (shared filesystems in Docker/Kubernetes)

Exploitation scenario: A developer runs the AI agent in a Docker container (a common setup for isolated development environments). The container stores OAuth tokens in ~/.claude/.credentials.json inside the container's writable layer. Another process in the same container — or anything with access to the Docker socket — reads the credentials file and exfiltrates the tokens.

Finding 2: Plaintext Credential Fallback Storage

Severity: HIGH | CVSS: 7.1 | CWE: CWE-312 (Cleartext Storage of Sensitive Information)

Location: utils/secureStorage/plainTextStorage.ts:57

Even on macOS where the keychain is the primary storage, a fallback mechanism silently activates when keychain operations fail. This fallback writes credentials to the same plaintext JSON file.

The data flow:

OAuth token obtained
  → saveOAuthTokensIfNeeded()
    → secureStorage.write()
      → macOS keychain write attempt
        → FAILS (Docker container, SSH session, CI runner)
          → fallbackStorage activates silently
            → plainTextStorage.write()
              → .credentials.json on disk in plaintext

The critical issue is the word "silently." The fallback logs a warning at debug level, but the user is never informed that their credentials just fell from keychain-level security to plaintext-on-disk. No confirmation prompt. No visible warning. Just a debug log line that 99.9% of users will never see.

Why this matters: macOS developers who believe their credentials are protected by the system keychain may actually be using plaintext storage without knowing it. Common scenarios that trigger the fallback: - Running in a Docker container (no keychain available) - SSH session without a GUI (keychain requires user interaction) - CI/CD pipeline (headless environment) - Freshly provisioned cloud instance (keychain not configured) - macOS keychain locked after restart (user has not unlocked it)

Finding 3: Conversation History Stored in Plaintext

Severity: HIGH | CVSS: 7.0 | CWE: CWE-312 (Cleartext Storage of Sensitive Information)

Location: history.ts:115

Every conversation with the AI agent is stored in a plaintext JSONL file at ~/.claude/history.jsonl. Content pasted into sessions under 1,024 characters is stored inline in the history entry. Larger pastes are stored in individual plaintext files at ~/.claude/paste-cache/{sha256-hash}.txt.

There is no encryption. There is no TTL. There is no automatic purging. There is no secret detection or redaction.

This means that when a developer pastes an API key into a session — a common action when configuring cloud services, debugging authentication issues, or setting up environment variables — that API key persists on disk indefinitely in cleartext. The full data flow:

Developer pastes API key into session
  → LogEntry created with pastedContents field
    → writeToFile() appends to history.jsonl (plaintext)
    → If paste > 1024 chars: paste-cache/{sha256}.txt (plaintext)
      → File persists until manual deletion
        → Backup software captures file
          → Cloud sync uploads to storage
            → API key now in 3+ locations, all plaintext

Why this matters: Developers routinely share secrets with AI agents: - "Here's my AWS access key, help me configure the SDK" - "This is the database connection string, why am I getting a connection error?" - "My JWT token is [token], decode it and tell me what scopes are missing" - Copy-pasting .env file contents for debugging

Each of these interactions creates a permanent plaintext record. Over time, a developer's history file becomes a comprehensive inventory of every secret they have ever shared with the agent.

Finding 4: Plaintext Credential Storage on Linux

Severity: HIGH | CVSS: 6.5 | CWE: CWE-922 (Insecure Storage of Sensitive Information)

Location: utils/secureStorage/index.ts:16

This is the Linux-specific manifestation of Finding 1, distinguished because Linux is the primary operating system for cloud development, CI/CD pipelines, and containerized workloads — environments where credential security is most critical.

On macOS, the keychain provides hardware-backed credential storage through the Secure Enclave. On Linux, equivalent functionality exists through libsecret (GNOME Keyring, KDE Wallet) and the D-Bus Secret Service API. None of these are implemented. The code simply returns plainTextStorage.

Enterprise exposure: According to the Stack Overflow 2025 Developer Survey, 48% of professional developers use Linux as their primary development OS. For cloud-native development and DevOps, the number is higher — approximately 72% by industry estimates. Every one of these developers using this AI agent stores credentials in plaintext.

Finding 5: Environment Variable Tokens Never Expire

Severity: HIGH (by impact, MEDIUM by CVSS) | CVSS: 6.5 | CWE: CWE-613 (Insufficient Session Expiration)

Location: utils/auth.ts:1260

Tokens provided via the CLAUDE_CODE_OAUTH_TOKEN environment variable are assigned expiresAt: null and refreshToken: null. The client treats them as immortal — they never expire, never refresh, and never rotate.

// Reconstructed from audit findings
{
  accessToken: process.env.CLAUDE_CODE_OAUTH_TOKEN,
  refreshToken: null,    // No refresh mechanism
  expiresAt: null,       // No expiry check
}

The isTokenExpired() function returns false for null expiry. The checkAndRefreshOAuthTokenIfNeeded() function skips refresh for tokens without a refresh token. The result: a leaked environment variable token remains usable from the client's perspective indefinitely, even after server-side revocation, because the client never checks.

Why this matters: CI/CD pipelines are the primary consumers of environment variable tokens. A token leaked from a CI pipeline (through log exposure, configuration drift, or compromised runner) can be used by an attacker until someone manually discovers and revokes it. The client provides no early warning.

Findings 6-8: The Supporting Chain

Beyond the five primary findings above, three additional HIGH-severity credential issues complete the chain:

Finding 6: JWT Tokens Decoded Without Signature Verification (CVSS 7.5, CWE-347)

The bridge client's decodeJwtPayload() function performs base64 decoding of JWT payloads without verifying the signature. An attacker who can intercept the connection (corporate proxy, compromised DNS) can forge JWTs with manipulated expiry claims, preventing token refresh and keeping revoked tokens active indefinitely.

Finding 7: Proxy Credentials in WebSocket Headers (CVSS 5.4, CWE-522)

When connecting through corporate proxies, proxy authentication credentials are sent in WebSocket upgrade headers and encoded as Base64 Basic Auth in memory. These credentials remain on the heap after use without zeroing.

Finding 8: TOCTOU Race in Credential File Write (CVSS 4.7, CWE-367)

The plaintext credential storage writes credentials using a non-atomic write pattern: open file, write content, set permissions. Between the write and chmod, a brief window exists where the file may be readable by other users.

The Systemic Problem: Why Every AI Agent Is Vulnerable

The eight findings above are from one agent. But the underlying problem is systemic — every AI coding agent faces the same credential management challenges, and most solve them the same way (or worse).

Why Agents Handle Credentials Poorly

1. Credential management is not the core product. AI coding agents are built by AI/ML teams optimized for model performance, code generation quality, and developer experience. Secure credential storage is a solved problem in theory (OS keychains, secret managers) but a complex engineering challenge in practice. It falls into the "we'll get to it" category — hence the TODO comment in the source code.

2. Cross-platform complexity. A credential storage solution that works on macOS, Linux, Windows, WSL, Docker, CI/CD runners, and cloud instances requires platform-specific integrations (keychain, libsecret, DPAPI, credential manager) plus fallback paths for environments where none are available. Most teams implement the macOS path (loudest user base) and punt on the rest.

3. The conversation history problem is new. Traditional CLI tools do not store conversation history. AI agents do — because conversations are the core interface. But conversation history is also the most dangerous data surface, because developers routinely share secrets during conversations. Existing secret scanning tools (gitleaks, truffleHog) scan git repositories, not conversation history files.

4. Token lifecycle management adds operational complexity. Short-lived tokens with automatic rotation require server-side coordination, refresh token storage, expiry monitoring, and graceful degradation when refresh fails. Environment variable tokens are simpler — but simpler means insecure, because simplicity comes at the cost of never expiring.

Real-World Attack Chains

Our research identified three high-impact attack chains that combine multiple vulnerabilities:

Chain 1: Backup Exfiltration

Developer authenticates with AI agent
  → OAuth token stored in ~/.agent/.credentials.json (plaintext)
  → Time Machine backs up home directory hourly
  → Backup stored on NAS accessible to IT staff
  → IT staff member (or compromised NAS) reads backup
  → OAuth token extracted from backup
  → Attacker accesses developer's AI API account

Chain 2: Container Escape

Developer runs AI agent in Docker container for isolation
  → Keychain unavailable in container (fallback activates silently)
  → Credentials stored plaintext in container writable layer
  → Docker socket exposed for CI/CD management
  → Malicious CI job reads container filesystem
  → Credentials exfiltrated via container inspection

Chain 3: Conversation History Mining

Developer pastes AWS key into AI agent chat session
  → Secret stored in history.jsonl indefinitely (no TTL, no redaction)
  → Developer leaves company; laptop returned to IT
  → IT re-images laptop but does not securely wipe
  → Next employee receives laptop
  → Previous developer's secrets accessible in hidden directories

Each chain is individually plausible and collectively represents the kind of risk that keeps CISOs awake at night — diffuse, hard to detect, and impossible to remediate with current tools.

The Compliance Time Bomb

The credential storage problem is not just a security risk — it is a compliance violation waiting to be discovered.

Regulatory Frameworks at Risk

SOC 2 Type II. The Trust Services Criteria require that "the entity authorizes, modifies, or removes access to data, software, functions, and other protected information assets based on roles" (CC6.1) and that "confidential information is protected during the processes of storing, using, transmitting, and disposing" (C1.2). Plaintext credential storage on developer machines violates both criteria.

PCI DSS 4.0. Requirement 3.5 mandates that primary account numbers (PANs) and sensitive authentication data are rendered unreadable anywhere they are stored. Developers who paste payment API keys into AI agents create PCI scope on every machine with unencrypted conversation history.

GDPR. Article 32 requires "encryption of personal data" as a technical measure. If AI agents process personal data (common in development and debugging), the plaintext conversation history creates a GDPR violation in every EU-based development environment.

HIPAA. The Security Rule requires encryption of electronic protected health information (ePHI) at rest. Healthcare developers using AI agents to work with ePHI systems create a HIPAA violation every time they paste patient-related data into a session.

NIST 800-53. Control SC-28 (Protection of Information at Rest) requires encryption of sensitive data. Federal contractors using AI agents with plaintext credential storage are out of compliance.

The Audit Scenario

Imagine a compliance auditor asks: "Show me how your developers' AI coding tools store credentials."

The honest answer for most organizations today: "We don't know. Each tool stores credentials in its own format, in hidden directories on developer machines. We have no visibility, no encryption, and no policy enforcement."

This answer fails every framework listed above. And as AI tool adoption grows, auditors are beginning to ask this question.

The Enterprise Blocker

The credential problem is not just creating risk — it is actively blocking enterprise AI adoption.

CISOs Are Saying No

In conversations with enterprise security teams, we hear the same concerns repeatedly:

"We cannot deploy AI coding tools on machines with access to production credentials." This means developers must use AI tools on isolated machines or VMs without access to the systems they need to work on — defeating the purpose of AI-assisted development.

"Our DLP tools flag AI agent configuration files as credential leaks." Data Loss Prevention tools detect plaintext tokens in AI agent directories and generate alerts. Security teams then spend time investigating false-alarm-like findings that are actually real credential exposures, but ones they cannot fix because the agent provides no alternative storage mechanism.

"We need an audit trail for every credential access by every AI tool." Compliance requirements demand that organizations know which credentials are being accessed, by which tools, at what time, for what purpose. AI agents provide none of this visibility.

"We blocked [Agent X] after finding OAuth tokens in plaintext during a pen test." Real incident from a Fortune 500 financial services company. Their penetration test found plaintext OAuth tokens in the AI agent's configuration directory. The agent was banned from all corporate machines pending a fix. That fix has not come — because the agent vendor does not offer encrypted credential storage.

Why This Is a Startup, Not a Feature

A reasonable question: why will AI agent vendors not solve this themselves? The answer is nuanced.

Some will — partially. Major AI tool vendors will eventually implement OS keychain integration across platforms. The macOS path will come first (it always does). Linux libsecret support will follow. This addresses Findings 1, 2, and 4 from our audit — the plaintext storage findings.

But the systemic problems will remain:

  1. Conversation history secret detection requires a specialized scanning engine that understands credential patterns across hundreds of secret types. Building and maintaining this is a full product, not a feature.

  2. Cross-tool credential management cannot be solved by any single vendor. Each vendor can secure their own storage, but the proliferation problem (3,750 credential files per enterprise) requires a layer that sits above individual tools.

  3. Audit trails and compliance reporting require a centralized system that tracks credential access across all AI tools, maps to compliance frameworks, and generates reports. No individual AI tool vendor has the incentive or capability to build this for their competitors' products.

  4. Token lifecycle management (rotation, expiry enforcement, revocation propagation) requires coordination between the agent, the secret storage layer, and the credential provider. This is middleware, not a feature.

  5. Enterprise policy enforcement (which tools can access which credentials, in which environments, under what conditions) requires a policy engine that spans the entire AI tool ecosystem.

The credential management problem for AI agents is the same class of problem that HashiCorp Vault solved for cloud infrastructure: too complex for any single application to solve well, too critical for enterprises to ignore, and too cross-cutting for any single vendor to own.
