Chapter 5: AgentShield --- Runtime Security for AI Agents

AgentShield is runtime security infrastructure for AI coding agents. It sits between the agent process and the operating system kernel, monitoring every system call that agent-initiated tool executions produce, and enforcing per-agent, per-tool security policies with sub-millisecond overhead. It is the security layer that AI agents should have shipped with but did not.

This chapter defines the product: what it does, how it works, why the technical architecture produces a defensible competitive advantage, and how it integrates with the AI coding agents that developers already use. Chapter 6 provides the detailed technical architecture. Chapter 7 covers the market and go-to-market strategy. Chapter 8 contains the complete YC application.

5.1 Product Overview

What AgentShield Does

AgentShield provides three capabilities:

1. Syscall Monitoring. Every system call made by agent-initiated processes --- file opens, network connections, process forks, memory maps --- is captured in real-time. The monitoring is transparent to the agent and adds <100 microseconds of latency per syscall.

2. Policy Enforcement. Security policies define what each agent (and each tool within an agent) is allowed to do at the kernel level. A file-read tool can access the project directory but not ~/.ssh/. A shell command tool can connect to localhost but not external hosts. A sub-agent can read files but not fork additional processes.

3. Audit Trail. Every syscall, every policy decision, and every blocked action is logged to an immutable audit trail. Enterprise compliance teams can answer: "What did the AI agent do on developer X's machine between 2pm and 3pm last Tuesday?"

How It Feels to the Developer

From the developer's perspective, AgentShield is invisible during normal operation:

$ agentshield install
AgentShield v1.0 installed. Default policy: standard-developer.
Monitoring: claude-code, cursor, copilot-agent

$ claude
> Read the file src/main.py and suggest improvements.

[Claude Code reads src/main.py --- ALLOWED by policy]
[Claude Code writes suggested changes --- ALLOWED by policy]

> Deploy this to staging.

[Claude Code runs: kubectl apply -f deploy.yaml --- BLOCKED by policy]
[AgentShield: kubectl commands require explicit approval. Approve? y/n]

The developer types the same commands, uses the same AI agents, and gets the same results --- except that dangerous operations are blocked, sensitive resources are protected, and an audit trail exists for every action.

What AgentShield Is Not

AgentShield is not:

  • A WAF or prompt injection filter. It does not analyze prompt content. It monitors system calls.
  • A replacement for agent permission systems. It is an additional enforcement layer below the agent. Defense in depth.
  • An EDR/XDR product. It does not monitor all processes on the machine. It monitors only agent-initiated processes.
  • A network firewall. It does not inspect packet contents. It controls which network connections agent processes can establish.

The scope is deliberate. AgentShield does one thing --- runtime enforcement for AI agent tool execution --- and does it at the kernel level where it cannot be bypassed by application-layer attacks.

Layer 1: eBPF Sensor Layer (Kernel Space). eBPF programs attached to kernel tracepoints and LSM (Linux Security Module) hooks intercept system calls from agent-initiated processes. The programs are loaded into the kernel at AgentShield startup and execute in-kernel with no context switch overhead. They read policy tables from eBPF maps and make allow/deny decisions in <100 microseconds.

Layer 2: Policy Engine (User Space). The AgentShield daemon runs in user space, managing policy definitions, agent identity tracking, and eBPF map updates. When a new agent starts or a policy changes, the daemon updates the eBPF maps. The policy engine evaluates complex policies that are too expensive for in-kernel execution and caches the results in eBPF maps for fast lookup.

Layer 3: Audit and Dashboard. Every syscall event, policy decision, and blocked action is written to an append-only audit log. The dashboard provides real-time visibility into agent behavior, policy violations, and threat indicators.

Agent Identity Model

The core innovation in AgentShield's architecture is the agent identity model. Traditional process monitoring identifies processes by PID, UID, or binary path. These identifiers are insufficient for AI agents because:

  • A single agent process may execute hundreds of tool calls with different security contexts
  • Sub-agents run as separate processes but belong to the same agent hierarchy
  • MCP servers are independent processes invoked by the agent

AgentShield introduces a four-level identity hierarchy:

Level Identity Example Policy Scope
Agent Which AI coding agent Claude Code, Cursor, Copilot Agent-level defaults
Session Which user session Session started at 14:30, project=/app Session-specific overrides
Tool Which tool is executing BashTool, FileWriteTool, WebFetchTool Tool-specific restrictions
Operation Which specific operation git push origin main Operation-specific approval

The agent identity is established when the agent process starts (via process name, binary hash, or explicit registration). The session identity is established when the agent opens a project directory. The tool identity is established when the agent spawns a subprocess for a tool call. The operation identity is established when the subprocess makes its first syscall.

This identity model enables policies like: - "Claude Code's BashTool can access the project directory but not ~/.ssh/" - "Cursor's file write tool can write to src/ but not to .github/workflows/" - "Sub-agents spawned by Claude Code cannot make outbound network connections" - "MCP servers can only access files within their declared scope"

eBPF: Why This Technology

eBPF (extended Berkeley Packet Filter) is the enabling technology for AgentShield. Here is why it is the right choice:

Alternative Overhead Bypass Resistance Cross-Platform Why Not
ptrace High (context switch per syscall) Low (detachable) Linux only Too slow (10-100x overhead)
seccomp-bpf Low High Linux only Cannot make contextual decisions (no map access pre-6.x)
LD_PRELOAD Low Low (bypassable) Linux/macOS Trivially bypassed by static linking or direct syscalls
macOS Seatbelt Low High macOS only Coarse-grained (per-process, not per-tool)
eBPF Very low (<100us) High Linux (native), macOS (via shim) Best combination of performance, security, and flexibility

eBPF programs execute in the kernel's virtual machine with verified safety guarantees. They cannot be detached by the monitored process. They add minimal overhead because there is no user-kernel context switch --- the program runs in-kernel at the tracepoint. And they can read from eBPF maps, enabling policy decisions that depend on runtime state (agent identity, session context, accumulated behavior).

macOS Support: Endpoint Security Framework

macOS does not support eBPF natively. AgentShield uses the macOS Endpoint Security (ES) framework as the enforcement backend on macOS:

Feature Linux (eBPF) macOS (Endpoint Security)
Syscall monitoring BPF tracepoints ES event subscriptions
File access control LSM hooks AUTH events (ES_EVENT_TYPE_AUTH_OPEN)
Process monitoring sched_process_fork tracepoint ES_EVENT_TYPE_NOTIFY_FORK
Network control cgroup/sock eBPF programs Network Extension framework
Policy enforcement eBPF map lookups ES client response (allow/deny)
Overhead <100 microseconds <500 microseconds

The macOS backend is slightly higher overhead than the Linux eBPF backend, but still well within the sub-millisecond target. The policy definition format is identical across platforms --- developers and security teams write one policy that works on both operating systems.

5.3 Policy Language

Policy Structure

AgentShield policies are YAML files that define what agents, tools, and operations are allowed:

# agentshield-policy.yaml
apiVersion: agentshield.io/v1
kind: AgentPolicy
metadata:
  name: standard-developer
  description: Default policy for AI coding agents on developer workstations

spec:
  agents:
    - name: claude-code
      match:
        binary: "**/claude"
      defaults:
        filesystem:
          read: [project, temp]
          write: [project, temp]
          deny: [ssh, aws, kube, gnupg]
        network:
          allow: [localhost, "*.anthropic.com", "*.github.com"]
          deny: ["*"]  # deny all other network access
        process:
          maxChildren: 10
          maxDepth: 3
          denyFork: false

      tools:
        - name: BashTool
          filesystem:
            read: [project, temp, homebrew]
            write: [project, temp]
          network:
            allow: [localhost]
            deny: ["*"]
          process:
            allowedCommands: ["git", "npm", "python", "ruff", "pytest"]
            deniedCommands: ["curl", "wget", "ssh", "scp"]

        - name: FileWriteTool
          filesystem:
            write: [project]
            deny: ["**/.*", "**/*.env", "**/*.pem"]
          network:
            deny: ["*"]

        - name: SubAgent
          inherit: parent
          restrictions:
            filesystem:
              write: deny-all
            network:
              deny: ["*"]
            process:
              denyFork: true

  paths:
    project: "${AGENT_PROJECT_DIR}"
    temp: ["/tmp", "/private/tmp", "/var/folders"]
    ssh: ["~/.ssh"]
    aws: ["~/.aws"]
    kube: ["~/.kube"]
    gnupg: ["~/.gnupg"]
    homebrew: ["/opt/homebrew", "/usr/local"]

Policy Semantics

The policy language follows three principles:

1. Deny by default. Any access not explicitly allowed is denied. This inverts the current default where everything is allowed.

2. Scope narrowing. Each level in the identity hierarchy can only narrow permissions, never widen them. A tool policy cannot grant permissions the agent policy does not allow. A sub-agent policy cannot grant permissions the parent tool policy does not allow.

3. Explicit over implicit. Every policy decision is traceable to a specific rule in a specific policy file. No hidden defaults, no ambient authority.

Built-In Policy Templates

AgentShield ships with four policy templates covering common use cases:

Template Use Case Filesystem Network Process
minimal Maximum security Project read-only Deny all No sub-processes
standard-developer Daily development Project read/write Localhost + approved domains Limited sub-processes
ci-cd Automated pipelines Project + artifacts Build services only Unrestricted within project
audit-mode Monitoring only All access (logged) All access (logged) All access (logged)

The standard-developer template is the default. It allows normal development workflows while blocking the attack scenarios documented in Chapter 4: credential exfiltration (deny ~/.ssh, ~/.aws), unauthorized network access (deny by default), and uncontrolled sub-agent forking (maxDepth: 3, denyFork for sub-agents).

5.4 Integration Model

Zero-Config Integration

AgentShield does not require changes to AI coding agents. It operates at the OS level, below the agent's abstraction layer:

sequenceDiagram
    participant Dev as Developer
    participant Agent as AI Agent (unchanged)
    participant AS as AgentShield Daemon
    participant Kernel as OS Kernel + eBPF

    Dev->>Agent: "Read src/main.py"
    Agent->>Kernel: open("src/main.py", O_RDONLY)
    Kernel->>Kernel: eBPF program triggers
    Kernel->>Kernel: Check: agent=claude-code, tool=FileReadTool, path=src/main.py
    Kernel->>Kernel: Policy lookup: project dir, read → ALLOW
    Kernel-->>Agent: File descriptor returned
    Agent-->>Dev: File contents displayed

    Note over AS: Audit log: [14:30:01] claude-code/FileReadTool OPEN src/main.py → ALLOW

    Dev->>Agent: "Check my SSH config"
    Agent->>Kernel: open("/Users/dev/.ssh/config", O_RDONLY)
    Kernel->>Kernel: eBPF program triggers
    Kernel->>Kernel: Check: agent=claude-code, tool=FileReadTool, path=~/.ssh/config
    Kernel->>Kernel: Policy lookup: ssh dir, read → DENY
    Kernel-->>Agent: EACCES (Permission denied)
    Agent-->>Dev: "I don't have access to that file."

    Note over AS: Audit log: [14:30:15] claude-code/FileReadTool OPEN ~/.ssh/config → DENY (policy: deny-ssh)

The agent sees a standard EACCES error and reports it naturally. No integration code needed. No agent modification. No API hooks. AgentShield works with Claude Code, Cursor, Copilot, and any future AI agent because it operates at the syscall level, which is the universal interface between all user-space programs and the operating system.

5.6 Competitive Advantage

The Technical Moat

AgentShield's competitive advantage is the combination of three capabilities that are individually hard and collectively unique:

1. eBPF expertise. Building production-grade eBPF programs for security enforcement requires deep kernel knowledge. The eBPF verifier imposes strict constraints on program structure (no unbounded loops, bounded memory access, stack depth limits). Writing correct, performant eBPF programs for syscall monitoring is a specialized skill with a small talent pool.

2. AI agent internals knowledge. Effective policies require understanding how AI agents structure tool calls, how sub-agent delegation works, how MCP servers communicate, and how agent processes interact with the filesystem and network. This knowledge comes from source-level security audits, not from documentation.

3. Cross-platform enforcement. Supporting both eBPF (Linux) and Endpoint Security Framework (macOS) with a unified policy language requires maintaining two enforcement backends with identical security semantics. This is engineering complexity that creates a barrier to entry.

The moat deepens over time. Each new AI agent that AgentShield supports requires understanding that agent's internals. Each new policy template requires knowledge of real-world attack patterns. Each enterprise deployment generates audit data that improves anomaly detection. The feedback loop between deployment, monitoring, and policy refinement is a compounding advantage.

The Network Effect

AgentShield's policy library is a network effect. As more enterprises deploy AgentShield:

  • More agent-specific policies are created and shared
  • More attack patterns are detected and added to default policies
  • The anomaly detection models improve with more training data
  • The community of security engineers contributing policies grows

This is the same dynamic that made Snyk's vulnerability database a competitive advantage. The more users, the better the data, the better the product, the more users.

5.8 Deployment Scenarios

Scenario 1: Individual Developer

A senior engineer at a Series B startup uses Claude Code daily. They work on a codebase that includes AWS Lambda functions, database migration scripts, and Kubernetes manifests. Their machine has AWS credentials, database connection strings, and kubectl access to production.

Without AgentShield: The engineer's AI agent can read ~/.aws/credentials, access the production database, and modify Kubernetes deployments. A prompt injection attack in a dependency's README could exfiltrate production credentials.

With AgentShield: The standard-developer policy allows the agent to read and write project files but denies access to ~/.aws, ~/.kube, and ~/.ssh. Network access is restricted to localhost and approved domains. The engineer installs in 5 minutes:

brew install agentshield
agentshield init --policy standard-developer
# Done. All AI agents on this machine are now monitored and restricted.

The first time the agent attempts to read ~/.aws/credentials (triggered by a task like "help me debug this Lambda function"), the request is blocked. The agent reports "I don't have access to that file" and asks the engineer to paste the relevant configuration instead. The credentials never leave the protected directory.

Scenario 2: Enterprise Engineering Team

A Fortune 500 financial services company has 400 developers using a mix of Claude Code and Cursor. The security team needs to:

  1. Ensure no AI agent can access production credentials
  2. Restrict AI agent network access to approved internal services
  3. Generate audit logs for compliance with SOC 2 and the EU AI Act
  4. Allow developers to continue using AI agents productively

With AgentShield Enterprise: The security team deploys via MDM (Jamf, Intune) and pushes a custom policy that: - Denies access to all credential directories and environment variables matching *_SECRET, *_TOKEN, *_PASSWORD - Allows network access only to internal Git, npm registry, and CI/CD services - Logs all tool executions to the central AgentShield console - Sends high-severity events (blocked credential access, denied network connections) to Splunk

Developers see no change in their daily workflow except that certain sensitive operations are blocked with clear explanations. The security team gets a compliance dashboard showing: "400 developers, 1.2M tool executions this month, 847 policy violations blocked, 0 credential exfiltrations."

Scenario 3: CI/CD Pipeline

A DevOps team runs AI agents in CI/CD pipelines for automated code review, test generation, and documentation updates. The agents run in containerized environments but still need filesystem and network access to perform their tasks.

With AgentShield CI/CD policy: The ci-cd policy template allows filesystem access within the build directory and network access to build services (artifact registries, test databases). It denies access to the CI/CD runner's service account credentials and blocks network access to production environments. The audit log provides a complete record of every AI agent action in every build, enabling the security team to detect supply chain attacks that manipulate AI agents in the build pipeline.

5.9 Key Takeaways

  • AgentShield provides syscall-level monitoring and policy enforcement for AI agent tool execution, operating below the agent's abstraction layer where application-level bypasses cannot reach.
  • The architecture uses eBPF on Linux and Endpoint Security Framework on macOS, achieving <100 microsecond overhead per syscall --- undetectable by users.
  • The agent identity model tracks agents, sessions, tools, and operations, enabling fine-grained policies like "Claude Code's BashTool can access the project directory but not ~/.ssh/."
  • Zero-config integration works with any AI agent without modification. The agent sees standard OS permission errors when policies are violated.
  • Enterprise features include central policy management, compliance dashboards, SIEM integration, and anomaly detection.
  • The competitive moat is the combination of eBPF expertise, AI agent internals knowledge, and cross-platform enforcement --- each individually hard, collectively unique.
  • The product roadmap moves from core enforcement (months 0-6) to enterprise management (months 6-12) to platform and ecosystem (months 12-24).
  • AgentShield addresses every threat identified in Chapter 4 at the kernel level, below the reach of application-layer attacks.
