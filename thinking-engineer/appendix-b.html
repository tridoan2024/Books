Appendix B: Architectural Patterns Cheat Sheet

This appendix collects the twenty architectural patterns discussed throughout this book into a quick-reference format. For each pattern: when to use it, when not to use it, how Claude Code uses it, and the one-sentence principle it embodies.

These patterns are not prescriptions. They are tools. A switch statement is better than a Registry for three items. An if/else is better than a State Machine for two states. The skill is knowing when a pattern's benefits exceed its costs for your specific system, your specific scale, and your specific team.

Structural Patterns

1. Registry
When to Use A growing set of components (tools, plugins, handlers) must be discoverable by multiple consumers, and adding a new component should be a single-file change.
When NOT to Use You have fewer than five components and the set is stable. A simple array or map is clearer.
Claude Code Example The Tool Registry manages 52+ tools. Each tool registers itself with name, schema, and execute function. Adding a tool touches one file. (Ch. 6)
Principle Decouple registration from discovery so producers and consumers evolve independently.

2. Adapter (Provider Abstraction)
When to Use You integrate with multiple external services that serve the same purpose but have different APIs, and you want the application to be agnostic to which backend is active.
When NOT to Use You only have one provider and no realistic plan for a second. The abstraction adds indirection without benefit.
Claude Code Example The API client defines one interface implemented by three adapters: Anthropic Direct, AWS Bedrock, and Google Vertex. The agent loop calls provider.sendMessage() without knowing which cloud handles the request. (Ch. 11)
Principle Make the backend a configuration choice, not an architectural commitment.

3. Cascade (Settings Merge)
When to Use Multiple stakeholders (platform, organization, user, project) need to control the same configuration, with clear precedence rules.
When NOT to Use Single-user tools with one configuration file. Seven layers of settings for a solo project is overengineering.
Claude Code Example Seven configuration layers (defaults, managed policy, enterprise, user, project, local, CLI flags) merge with defined precedence. Managed policy can lock fields. (Ch. 8)
Principle Give every stakeholder a voice, but define who wins when they disagree.

4. Pipeline (Staged Processing)
When to Use A request requires multiple processing steps (validation, authorization, transformation, execution, formatting) that should be independently testable and reorderable.
When NOT to Use Processing is a single step. Wrapping one function in a pipeline framework adds ceremony without value.
Claude Code Example Every tool call passes through six stages: schema validation, permission check, hook execution, security analysis, tool execution, result formatting. Any stage can halt the pipeline. (Ch. 6, 8)
Principle Decompose complex processing into independent stages that each do one thing well.

Behavioral Patterns

5. State Machine
When to Use A component has distinct operational modes with explicit transitions, and you want to make invalid states unrepresentable.
When NOT to Use You have two states (on/off). A boolean is clearer than a state machine.
Claude Code Example The agent loop cycles through Idle, Assembling, Streaming, and Processing states with 10 exit conditions and 7 continuation conditions. Invalid transitions are structurally impossible. (Ch. 10, 14)
Principle Enumerate the valid states and transitions explicitly so bugs are impossible, not just unlikely.

6. Observer (Event System)
When to Use Components need to react to lifecycle events without the event source knowing about the observers. Extensibility without modifying core code.
When NOT to Use You have one observer. A direct function call is simpler than an event bus.
Claude Code Example The hook system defines 27 lifecycle events. Users register shell scripts as observers in settings.json. PreToolUse hooks can block actions. PostToolUse hooks auto-lint files. (Ch. 8)
Principle Decouple "what happened" from "what should happen in response."

7. Strategy (Selectable Algorithms)
When to Use A component's behavior must vary based on a mode or policy, and the modes are known at design time but selected at runtime.
When NOT to Use You have one algorithm. A strategy interface for one implementation is an abstraction tax with no benefit.
Claude Code Example Six permission modes (plan, default, auto, trust, deny, bypass) each implement a different evaluation strategy. The agent loop calls evaluatePermission() without knowing which mode is active. (Ch. 8, 12)
Principle Let the caller choose the behavior without knowing the implementation.

8. Chain of Responsibility (Layered Security)
When to Use Multiple independent checks must evaluate a request, any check can reject it, and the checks should be composable.
When NOT to Use You have one check. A single if statement is clearer than a chain.
Claude Code Example Bash command security uses five layers: pattern blocklist, AST analysis, path analysis, permission rules, user confirmation. Layers are ordered cheapest-first. (Ch. 3, 12)
Principle Defense in depth: multiple independent layers must all be bypassed for an attack to succeed.

9. Circuit Breaker
When to Use Calling an external service that may be slow or down. You want to fail fast after repeated failures rather than waiting for timeouts.
When NOT to Use The external call is to local code or a highly reliable service. The overhead of state tracking is not justified.
Claude Code Example MCP server health monitoring tracks consecutive failures. After three failures, the circuit opens: requests fail immediately instead of waiting for timeout. Recovery probes test periodically. (Ch. 9)
Principle Fail fast when the downstream is broken, and recover automatically when it heals.

10. Fail-Open / Fail-Closed
When to Use Every error handling path in a security-relevant system must make an explicit choice: allow the operation when unsure (fail-open) or block it (fail-closed).
When NOT to Use Non-security contexts where "try again" is the only sensible response.
Claude Code Example Hook errors are fail-open: a broken hook does not paralyze the agent. But exit code 2 is always fail-closed: an intentional block from a hook is never ignored. Permission evaluation defaults to fail-closed: unknown tools require user confirmation. (Ch. 8, 12)
Principle Decide which is worse --- blocking a legitimate action or allowing a dangerous one --- and design accordingly.

Concurrency Patterns

11. Fan-Out / Fan-In
When to Use A task decomposes into independent subtasks that benefit from parallel execution, and the results must be synthesized.
When NOT to Use Subtasks are sequential (each depends on the previous result). Forced parallelism adds complexity without reducing latency.
Claude Code Example Multi-agent orchestration fans out work to subagents: security reviewer, code quality reviewer, performance analyzer. Each runs in parallel with isolated context. Results are aggregated, deduplicated, and ranked. (Ch. 15)
Principle Parallelize independent work, then merge results with an explicit aggregation strategy.

12. Producer-Consumer (Input Buffer)
When to Use The producer generates work items at an unpredictable rate and the consumer processes them at a different rate. You need to prevent data loss without blocking the producer.
When NOT to Use Producer and consumer run at the same rate. A buffer adds latency without benefit.
Claude Code Example During startup, keystrokes are buffered before the REPL is ready. When the UI mounts, buffered input is replayed. The user never notices the 135ms module loading delay. (Ch. 4, 16)
Principle Absorb rate differences between producer and consumer to prevent data loss and blocking.

13. Streaming Pipeline
When to Use Data arrives incrementally and must be processed in real time without waiting for the complete input.
When NOT to Use The complete input is available before processing starts. Batch processing is simpler than streaming.
Claude Code Example The SSE response pipeline processes tokens as they arrive: bytes to SSE events, events to content blocks (text or tool use), text to rendered markdown, tool use fragments to assembled JSON. First-token-to-screen latency is minimized. (Ch. 13)
Principle Process data as it arrives so the user sees progress, not a blank screen.

AI-Specific Patterns

14. Agentic Loop
When to Use Building any AI agent that uses tools. The agent must repeatedly think, act, observe, and decide whether to continue.
When NOT to Use Single-turn inference where the model produces a response and you are done. Adding a loop adds unnecessary complexity.
Claude Code Example The core agent loop: assemble context, call model, process response, execute tools, observe results, check exit conditions, repeat. Ten exit conditions prevent infinite loops. (Ch. 10)
Principle Loop until done, but always define what "done" means before you start looping.

15. Tool-Use Conversation
When to Use The model needs to see the results of its previous actions to decide what to do next. Every agentic system uses this pattern.
When NOT to Use The model does not use tools. Standard prompt-response is simpler.
Claude Code Example The conversation alternates assistant messages (containing tool calls) and user messages (containing tool results). Tool results are keyed to tool call IDs so the model correlates requests with responses. (Ch. 10, 13)
Principle Structure the conversation so the model can build on its own observations.

16. Context Compaction
When to Use The agent loop runs for many turns and the accumulated conversation exceeds the context window limit.
When NOT to Use Sessions are short enough to fit in the context window. Compaction adds latency and loses information.
Claude Code Example At 80% context capacity, the system compacts: preserves the system prompt and recent turns verbatim, summarizes older turns, truncates large tool results. Users can trigger compaction manually with /compact [focus]. (Ch. 8, 10)
Principle Sacrifice old detail to preserve space for new reasoning.

17. VCR Testing (Record/Replay)
When to Use Testing code that calls an LLM API, where responses vary between calls and cost money per request.
When NOT to Use The code under test is deterministic. Standard assertion-based testing is simpler and more reliable.
Claude Code Example API interactions are recorded as cassette files during a test run, then replayed on subsequent runs. Tests become deterministic, fast, and free. Structural matching handles minor prompt changes. (Ch. 19)
Principle Record reality once, then replay it forever --- re-record only when reality intentionally changes.

18. Trust Boundary
When to Use The system processes content from sources with different trust levels and must prevent lower-trust content from hijacking higher-trust operations.
When NOT to Use All content comes from a single trusted source. Trust boundaries add overhead without benefit.
Claude Code Example Five trust levels: system prompt (highest), user messages, tool results (medium), file contents (low), web content (lowest). Content crossing boundaries is tagged, size-limited, and structurally delineated. (Ch. 12)
Principle Make trust levels explicit and enforce boundaries between them.

19. Feature Flags (Compile-Time + Runtime)
When to Use You need controlled evolution: dark launches, gradual rollouts, kill switches, A/B testing, or SKU generation from one codebase.
When NOT to Use You ship one product to one audience with no need for gradual rollout. Flags add branching complexity.
Claude Code Example 80+ compile-time flags control what code exists in the binary (security boundary, dead code elimination). 500+ runtime flags control what code runs in a session (A/B testing, gradual rollout, kill switches). Coded defaults ensure graceful degradation when the flag service is unreachable. (Ch. 10)
Principle Separate what ships from what activates. Compile-time flags gate existence; runtime flags gate behavior.

20. Gradual Migration
When to Use Evolving a production system used by many users. You need to change behavior without a big-bang deployment.
When NOT to Use You have zero users or the change is trivially backward-compatible. Gradual rollout adds monitoring overhead.
Claude Code Example New features roll out at 1%, then 10%, then 50%, then 100% of sessions. Metrics are monitored at each stage. Rollback is a flag flip, not a deployment. No deployment required for rollback. (Ch. 10)
Principle Make every change reversible, and increase exposure only as confidence grows.

No pattern is universally correct. Each solves a specific problem and introduces specific costs. The trade-off sections in the referenced chapters are not caveats --- they are design constraints. Choose the pattern whose costs you can afford and whose benefits match your requirements.
