Chapter 6: Interface Design

The most expensive lines of code in any system are the interfaces between its components. Not because they are hard to write -- interface definitions are often short -- but because they are hard to change. An implementation can be rewritten in a weekend. An interface that ten modules depend on cannot be changed without modifying all ten. The implementation is the house; the interface is the foundation. You can renovate the house. Replacing the foundation means tearing everything down first.

Chapter 5 showed how to decompose a system into manageable pieces. This chapter addresses the harder question: how do those pieces talk to each other? The contracts between components determine how easily the system can evolve, how independently teams can work, and whether adding a new capability takes one file or forty.

The case study is Claude Code's tool interface -- a single contract that 52 tools implement. It is, arguably, the most important design decision in the entire 500K-line codebase. This chapter explains why, and extracts principles you can apply to any system.

Contracts Before Code

The natural instinct is to write the implementation first and extract the interface later. You build the file-reading tool, then the bash-execution tool, then the search tool. When you have three tools, you notice their common shape and factor out an interface.

This is backwards.

When you extract an interface from existing implementations, you get an interface shaped by the accidents of those implementations. The file reader returns strings. The bash executor returns a struct with exit code, stdout, and stderr. The search tool returns a list of matches. Your extracted interface must accommodate all three return types, so it becomes a union type or a generic blob. The interface does not guide the implementations; it merely describes what already exists.

When you design the interface first, every implementation is shaped by the contract. The file reader, bash executor, and search tool all return the same result type because the contract requires it. Differences that seemed essential in a bottom-up extraction turn out to be accidental -- there is no reason the file reader cannot return a structured result with a type field, just like the bash executor.

The Discipline of Pre-Design

Designing the interface first requires answering three questions before writing any implementation:

1. Who is the caller, and what do they need? The interface exists for the caller, not the implementer. If the agent loop needs to dispatch tool calls, the interface should be shaped around dispatching, not around individual tool mechanics. If the permission system needs to check whether a tool is safe, the interface should declare safety properties, not bury them in implementation details.

2. What is the minimum information that must cross the boundary? Every field in the interface is a commitment. Once callers depend on it, removing it is a breaking change. Start with the minimum and add fields only when a concrete use case demands them.

3. What should be impossible to express? A good interface makes illegal states unrepresentable. If a tool cannot be both read-only and destructive, the type system should prevent it. If a tool result must include either data or an error (never both, never neither), a discriminated union enforces this at compile time.

An Example of Contract-First Thinking

Consider designing a tool system. The bottom-up approach starts with one tool:

// Bottom-up: shaped by the first implementation
class FileReadTool {
  async readFile(path: string): Promise<string> { ... }
}

Then you add another:

class BashTool {
  async execute(command: string): Promise<{
    exitCode: number; stdout: string; stderr: string
  }> { ... }
}

Now you need a common interface. The two implementations have different signatures, different return types, and different parameter shapes. The extracted interface is awkward:

// Extracted: awkward union of two different shapes
interface Tool {
  run(input: unknown): Promise<unknown>
}

The contract-first approach starts differently. Before writing any tool, you ask: what does the agent loop need?

// Contract-first: shaped by the caller's needs
interface Tool {
  name: string
  inputSchema: Schema
  call(input: ValidatedInput): AsyncGenerator<Progress, Result>
}

The agent loop needs to know a tool's name (for dispatch), its input schema (for validation), and a way to call it (for execution). Every tool implements this. The file reader does not get to define its own signature. The bash executor does not get to return a custom struct. They both conform to the contract.

Why Interfaces Matter More Than Implementations

An implementation can be wrong and fixed in a day. An interface can be wrong and unfixable for years.

This asymmetry exists because interfaces create coupling. Every module that depends on an interface is coupled to its shape. Changing the shape requires changing every dependent module. In a system where 52 tools implement one interface, changing that interface means modifying 52 tool implementations, plus every consumer of the interface (the registry, the executor, the permission system, the UI renderer, the context compactor, the search system).

Implementations create no external coupling. The bash tool's internal parsing logic can change completely without affecting any other module, as long as it still satisfies the tool interface. This is the fundamental value proposition of interfaces: they allow independent evolution of the pieces on each side.

The Cost of Interface Changes

Claude Code's tool interface has approximately 20 methods and properties. Changing any method's signature affects:

  • 52+ tool implementations that must update their conformance
  • The tool registry that queries the method
  • The executor that calls the method
  • The permission system that checks the method
  • The UI that renders the method's output
  • The compactor that summarizes the method's results
  • The test harness that mocks the method

A single interface change can cascade to 60+ files. This is why Claude Code's tool interface uses fail-closed defaults with a factory function -- new methods are added with default implementations, so existing tools do not need to change:

const DEFAULTS = {
  isReadOnly: () => false,
  isDestructive: () => false,
  isConcurrencySafe: () => false,
  maxResultSizeChars: undefined,
}

function buildTool<I, O>(def: ToolDefinition<I, O>): Tool<I, O> {
  return { ...DEFAULTS, ...def }
}

When a new behavioral property is needed (say, canRunInBackground()), it is added to DEFAULTS with a conservative default (false). No existing tool must change. Only tools that want to opt into the new behavior override the default. This is the practical cost of a 52-implementation interface: every addition must be backward-compatible by construction.

The Power of Narrow Interfaces

A narrow interface is one that exposes the minimum surface area needed by its callers. The narrower the interface, the less coupling, the more freedom for implementations, and the easier it is to test.

What "Narrow" Means

Narrow does not mean "few methods." It means "each method carries the minimum information necessary." Consider two designs for a tool's permission check:

// Wide: exposes the tool's internals to the permission system
interface Tool {
  getPermissionRules(): Rule[]
  getRequiredCapabilities(): Capability[]
  getSandboxProfile(): SandboxConfig
  getFileAccessPatterns(): GlobPattern[]
}

// Narrow: the tool answers a single question
interface Tool {
  checkPermissions(input: ValidatedInput,
                   context: PermissionContext): PermissionResult
}

The wide interface leaks implementation details. The permission system must understand rules, capabilities, sandbox profiles, and file access patterns. If any of these concepts change, the permission system changes too.

The narrow interface hides all of that. The tool receives the input and context, consults its own rules internally, and returns a verdict: allow, deny, or ask. The permission system does not know how the tool makes the decision. It only knows the result.

Claude Code uses the narrow approach. Each tool's checkPermissions() method encapsulates the full permission logic for that tool. The Bash tool checks the parsed command against security rules. The Read tool checks the file path against deny lists. The Edit tool checks whether the file has been read first. Each tool knows its own domain-specific rules. The permission system orchestrates the check without understanding any tool's internals.

The Information Hiding Principle

David Parnas formulated this in 1972, and it remains the most important principle in interface design: each module hides a design decision that is likely to change. The interface exposes only what other modules need to know.

In Claude Code's tool system, the design decisions hidden behind the tool interface include:

Hidden Decision What the Interface Exposes
How the Bash tool parses commands inputSchema: z.object({ command: z.string() })
How the Edit tool finds text to replace call(input): AsyncGenerator<Progress, Result>
How the Read tool handles binary files mapToolResultToAPIBlock(result): ContentBlock
How each tool evaluates permissions checkPermissions(input, ctx): PermissionResult
How tools render in the terminal renderToolUseMessage(input): ReactNode

Every tool can change how it parses, searches, renders, and checks permissions without affecting any other tool or any consumer of the interface. The implementation is free to evolve because the interface is stable.

Designing for the Caller, Not the Implementer

The most common interface design mistake is shaping the interface around the implementer's convenience rather than the caller's needs. The implementer knows their internals and creates methods that expose them. The caller must then map their needs onto the implementer's model.

The Agent Loop as the Primary Caller

Claude Code's tool interface was designed around the agent loop's needs. The agent loop needs to:

  1. Discover tools -- know what tools exist and their schemas
  2. Dispatch calls -- route a tool call to the right implementation
  3. Check permissions -- determine whether a call is allowed
  4. Execute calls -- run the tool and get results
  5. Handle progress -- show the user what is happening
  6. Format results -- convert results to the API's message format
  7. Summarize calls -- compress old tool calls during context compaction

Each need maps to one or two methods on the tool interface:

interface Tool<Input, Output> {
  // Discovery (need 1)
  name: string
  description: string | ((ctx: ToolUseContext) => string)
  inputSchema: z.ZodType<Input>

  // Dispatch (need 2)
  aliases?: string[]

  // Permissions (need 3)
  checkPermissions(input: Input, ctx: PermissionContext): PermissionResult
  isReadOnly(): boolean

  // Execution (need 4)
  call(input: Input, ctx: ToolUseContext): AsyncGenerator<Progress, Output>

  // Progress (need 5)
  renderToolUseProgressMessage(progress: Progress): ReactNode

  // Formatting (need 6)
  mapToolResultToAPIBlock(result: Output): ContentBlock
  renderToolUseMessage(input: Input): ReactNode
  renderToolResultMessage(result: Output): ReactNode

  // Summarization (need 7)
  getToolUseSummary(input: Input, result: Output): string
}

Notice what is absent from this interface. There is no initialize() method -- the agent loop does not need to initialize tools. There is no getState() method -- the agent loop does not need tool-internal state. There is no configure() method -- tools are configured through their constructors, not through the interface. The interface contains exactly what the callers need and nothing more.

Each caller uses 2-4 methods out of the ~20 available. No caller uses the full interface. This is typical of well-designed interfaces -- they serve multiple consumers, each using a different facet.

An alternative design would create separate interfaces for each consumer: Dispatchable, Permissioned, Renderable, Summarizable. Some languages encourage this (Go's small interfaces, Rust's traits). But in a TypeScript codebase with 52 implementations, each tool would need to satisfy 4-6 separate interfaces. The cognitive overhead of understanding which interface provides which method outweighs the purity benefit. One interface with good defaults is more practical than five interfaces with perfect separation.

The Uniform Contract

The most powerful aspect of Claude Code's tool interface is its uniformity. Every tool -- from the simple Glob tool (find files by pattern) to the complex Bash tool (4,400-line parser, security analysis, sandboxing) -- implements the same contract. This uniformity has profound consequences.

What Uniformity Enables

Generic infrastructure. The tool executor does not need a switch statement to handle different tools. It calls tool.call(input, context) on every tool, regardless of what the tool does. The permission system calls tool.checkPermissions(input, context) on every tool. The UI calls tool.renderToolUseMessage(input) on every tool. No special cases, no type checks, no "if this tool, do this" branching.

// Generic execution -- works for any tool, past or future
async function executeTool(tool: Tool, input: unknown, ctx: ToolUseContext) {
  const validated = tool.inputSchema.parse(input)
  const permission = tool.checkPermissions(validated, ctx)
  if (permission === 'denied') return errorResult(permission)

  const generator = tool.call(validated, ctx)
  for await (const progress of generator) {
    renderProgress(tool.renderToolUseProgressMessage(progress))
  }
  return generator.return
}

This function works for 52 tools today and will work for tool 53 without modification. The tool interface is a protocol -- the executor speaks it fluently without knowing the specifics of any tool.

Adding a tool is a self-contained change. When Claude Code adds a new tool, the change touches exactly one directory: the new tool's directory. No registry file to update (the tool registers itself). No executor switch to extend. No permission rules to add (the tool defines its own via checkPermissions). No UI code to modify (the tool provides its own render methods). The uniform interface means every subsystem adapts automatically.

Testing is generic. Test utilities can verify that any tool conforms to the contract without knowing what the tool does:

// Generic conformance test -- applicable to all 52 tools
function testToolConformance(tool: Tool) {
  expect(tool.name).toBeDefined()
  expect(tool.inputSchema).toBeDefined()
  expect(typeof tool.call).toBe('function')
  expect(typeof tool.checkPermissions).toBe('function')
  expect(typeof tool.isReadOnly).toBe('function')
  expect(typeof tool.isConcurrencySafe).toBe('function')
}

What Uniformity Costs

Uniformity has costs, and acknowledging them is honest engineering.

Lowest common denominator risk. The uniform interface must accommodate the simplest tool (Glob: takes a pattern, returns paths) and the most complex (Bash: takes a command, parses it into an AST, runs security analysis, spawns a process, captures output, enforces timeout). The interface must be flexible enough for the complex case without imposing unnecessary burden on the simple case. The factory defaults solve this -- simple tools implement name, inputSchema, and call; everything else uses defaults.

Semantic mismatch. The isReadOnly() method makes sense for filesystem tools but is awkward for web tools. Is WebFetch read-only? It does not modify the local filesystem, but it makes a network request that could have side effects on the remote server. The interface forces a boolean answer to a non-binary question. Claude Code resolves this pragmatically: WebFetch returns true for isReadOnly because the relevant question for the permission system is "does this modify the user's local environment?"

Evolution pressure. Adding a new method to the interface requires every tool to either implement it or accept a default. Over time, the interface accumulates methods that most tools use the default for. Claude Code's tool interface has ~20 methods. A typical tool overrides 5-8 of them. The rest use defaults. This is acceptable -- the defaults handle the common case, and the methods exist because at least one caller needs them.

API Ergonomics

Interface design is not just about what information crosses the boundary. It is about how easy it is for the implementer to get right and how hard it is to get wrong.

The Pit of Success

A good API makes the correct usage the easiest usage. Incorrect usage should require extra effort -- ideally, it should not even compile.

Claude Code's tool factory function embodies this principle:

const ReadTool = buildTool({
  name: 'Read',
  description: 'Read file contents',
  inputSchema: z.object({
    file_path: z.string(),
    offset: z.number().optional(),
    limit: z.number().optional(),
  }),
  isReadOnly: () => true,
  isConcurrencySafe: () => true,
  async *call(input, context) {
    // Implementation
  },
})

The buildTool factory:

  1. Requires only the essential fields. name, inputSchema, and call are mandatory. Everything else has a default.
  2. Sets safe defaults. isReadOnly: false, isConcurrencySafe: false. A tool that forgets to declare itself read-only is treated as mutating -- the permission system checks it more carefully. This is fail-closed: the safe assumption is the default.
  3. Validates at construction time. If the schema is invalid or the name conflicts with another tool, the error occurs when the tool is built, not when it is first used.
  4. Provides type inference. The input type for call is inferred from inputSchema. The implementer does not need to manually declare the input type -- it is derived from the schema definition.

Making Wrong Things Hard

The interface design prevents several classes of errors:

Error: Forgetting to handle permissions. Every tool call passes through checkPermissions before call. The executor enforces this, not the tool. A tool cannot accidentally skip the permission check because the executor calls it externally.

Error: Returning unformatted results. The mapToolResultToAPIBlock method converts tool results to the API format. The executor calls this after call returns. A tool cannot accidentally return raw data to the API because the formatting step is external.

Error: Running unsafe tools in parallel. The executor checks isConcurrencySafe before parallelizing. The default is false. A new tool cannot be accidentally parallelized because it must explicitly opt in.

Error: Allowing a write to an unread file. The Write and Edit tools check readFileState in their checkPermissions method. The agent loop cannot bypass this because the permission check is part of the standard execution pipeline.

Each of these protections works because the interface puts the enforcement in the caller (the executor), not the implementer (the tool). The tool does not need to remember to check permissions, format results, or prevent parallelism. The infrastructure does it.

The Zod + JSON Schema Dual

A particularly elegant ergonomic decision is the dual-schema pattern. Tools define their input schemas using Zod (a TypeScript-native schema library):

inputSchema: z.object({
  command: z.string().describe('The command to execute'),
  timeout: z.number().optional().describe('Timeout in milliseconds'),
})

This one definition serves two consumers:

Consumer Format Needed How
Agent process Runtime validation schema.parse(input)
Model API JSON Schema for generation constraint Auto-converted from Zod

The implementer writes one schema. The system derives both validation and API constraint from it. The auto-conversion is cached per session for performance and stability (the same bytes on every request preserve the prompt cache key). The implementer does not need to know that JSON Schema exists, that it is cached, or that it affects caching economics. The interface hides all of it.

Case Study: 52 Tools, One Contract

Let us trace how the uniform tool interface plays out across the full tool system. Claude Code has tools ranging from trivially simple to extraordinarily complex:

Tool Complexity Lines Key Methods Overridden
Glob Simple ~200 name, schema, call, isReadOnly, isConcurrencySafe
Read Medium ~800 + deduplication, format dispatch, token limits
Edit Complex ~1,200 + staleness check, atomic write, read-before-write
Bash Very complex ~12,000 + AST parser, security analysis, sandboxing
Agent Complex ~600 + subagent spawning, result aggregation

The Bash tool is 60x larger than the Glob tool, yet both implement the same interface. The Bash tool's complexity is entirely internal. From the executor's perspective, BashTool.call(input, ctx) and GlobTool.call(input, ctx) are identical invocations. The 4,400-line parser, the security analyzer, the sandbox configuration -- all invisible to the caller.

This is the payoff of the uniform contract. The system's most complex component (Bash) and its simplest (Glob) participate in the same infrastructure without the infrastructure knowing the difference.

How New Tools Are Added

The process for adding tool number 53 to Claude Code:

  1. Create a directory: src/tools/NewTool/
  2. Define the tool using buildTool():
export const NewTool = buildTool({
  name: 'NewTool',
  description: 'Does something new',
  inputSchema: z.object({ /* fields */ }),
  async *call(input, context) {
    // Implementation
    yield { type: 'progress', message: 'Working...' }
    return { type: 'success', data: result }
  },
})
  1. Register it in the tool list (one line).

That is it. The registry picks it up. The executor dispatches to it. The permission system checks it (using defaults -- it is treated as mutating and non-concurrent until declared otherwise). The UI renders it (using default renderers). The compactor summarizes it (using the default summarizer). The schema is auto-converted and cached. No other file needs modification.

This is the measure of a good interface: how many files must change to add a new implementation? If the answer is "one," the interface is doing its job.

How the Interface Evolved

The tool interface was not born with 20 methods. It started with 4: name, inputSchema, description, call. Every additional method was added when a concrete use case demanded it:

Method Added When Why
checkPermissions Permission system was built Tools needed to define their own permission logic
isReadOnly Auto-mode classifier needed to know which tools are safe Could not classify without this signal
isConcurrencySafe Parallel tool execution was implemented Needed to know which tools could run simultaneously
getToolUseSummary Context compaction needed shorter representations Full tool results wasted context tokens
prompt Some tools needed to inject context into the system prompt The system prompt builder needed tool-specific content
renderToolUseMessage UI needed tool-specific rendering Generic rendering was too verbose for some tools

Each addition followed the same process: a caller needed information that the interface did not provide, a new method was added with a default implementation, and only tools that needed non-default behavior overridden it. The interface grew by accretion, driven by real needs, not by speculation.

Interface Design Principles

1. The Dependency Rule

Interfaces should point in the direction of stability. Stable components should not depend on volatile components. In practice, this means the interface is defined by the more stable side of the boundary.

In Claude Code, the tool interface is defined by the infrastructure (executor, registry, permission system), not by the tools. The infrastructure is stable -- it changes rarely. The tools are volatile -- new tools are added, existing tools are modified. The dependency points from volatile (tools) toward stable (infrastructure). This is correct.

If the tools defined their own interfaces and the infrastructure adapted to each one, every new tool would require infrastructure changes. The system would become harder to evolve, not easier.

2. The Uniformity Principle

Treat different things the same way when possible. Uniformity reduces the cognitive load on everyone who works with the system. The developer adding tool 53 does not need to understand how tools 1-52 work. They need to understand one interface.

The cost of uniformity is semantic mismatch -- some tools fit the interface more naturally than others. The benefit is that every piece of infrastructure (executor, registry, permission system, UI, compactor) works with every tool without special cases. In a system with 52 tools, the benefit overwhelms the cost.

3. The Default Direction Principle

When a property has a safe default and a dangerous override, the default should be the safe option. This is the fail-closed principle applied to API design:

Property Safe Default Override
isReadOnly false (mutating) true (read-only)
isConcurrencySafe false (serialized) true (parallelizable)
isDestructive false (non-destructive) true (destructive)
strict false (flexible schema) true (strict validation)

A tool that forgets to declare itself read-only gets extra permission checks -- annoying but safe. A tool that is falsely declared read-only skips permission checks -- dangerous. The default must be the one that fails safely.

4. The Composition Principle

Design interfaces so that tools compose naturally. In Claude Code, tool composition happens through the conversation: the output of one tool becomes context for the next model response, which may invoke another tool. This implicit composition works because:

  • Output formats are consistent. Every tool returns structured results that the model can parse.
  • Path formats are normalized. A file path returned by Grep is valid input to Read. A path returned by Glob is valid input to Edit. No translation needed.
  • Errors are visible. When a tool fails, the model sees the error and can adapt. Silent failures break the composition chain.

5. The Evolution Principle

Interfaces will change. Design for change by:

  • Using factory functions with defaults (new methods do not break existing implementations)
  • Preferring additive changes (new optional methods) over breaking changes (modified signatures)
  • Documenting the rationale for each method (so future engineers know whether it can be removed)

The Anti-Patterns

The Leaky Abstraction

The interface exposes implementation details that callers become dependent on. When the implementation changes, callers break.

Example: A tool interface that exposes getProcessId() because one caller needs it. Now every implementation must have a process concept, even tools that do not spawn processes. The interface is shaped by one implementation's internals, not by the callers' actual needs.

Fix: If one caller needs implementation-specific information, provide it through a separate, narrower interface -- not through the universal tool interface.

The Kitchen Sink Interface

The interface accumulates every method any caller might ever need. It grows to 50 methods. New implementations are a burden because they must satisfy a massive contract.

Example: renderToolUseMessage, renderToolUseCompactMessage, renderToolUseOneLineMessage, renderToolUseIconMessage, renderToolUseDarkThemeMessage...

Fix: Ask whether each method is used by more than one caller. If a method serves only one caller, it may belong in a separate, caller-specific interface rather than the universal contract.

The Over-Specific Interface

The interface is so specific to current requirements that it cannot accommodate future needs without a breaking change.

Example: execute(command: string): string -- works for bash but cannot accommodate tools that return structured data, images, or streaming results.

Fix: Design the interface for the category of operations, not for specific operations. call(input: Validated): AsyncGenerator<Progress, Result> accommodates bash commands, file reads, web fetches, and anything else that produces progressive output.

The Phantom Abstraction

An interface exists between two components, but only one implementation exists for one side. The interface adds ceremony without providing any of the benefits of abstraction (substitutability, testing isolation, independent evolution).

Fix: Remove the interface. Use the concrete type directly. Add the interface when a second implementation actually appears. The premature interface costs maintenance today with no benefit until the second implementation arrives -- which may never happen.

Key Principles

  1. Design the interface before the implementation. The interface shapes every implementation; extracting it after the fact shapes the interface around implementation accidents.

  2. Design for the caller, not the implementer. The agent loop's needs determine the tool interface, not the bash tool's internals.

  3. Narrow interfaces reduce coupling. Each method should carry the minimum information necessary. Hide implementation decisions behind single-method queries (checkPermissions returns a verdict, not the rules).

  4. Uniformity beats specificity at scale. 52 tools implementing one contract means zero special cases in the infrastructure. The cost (semantic mismatch for edge cases) is overwhelmed by the benefit (generic executor, generic permissions, generic rendering).

  5. Defaults must fail safely. Every boolean property defaults to the restrictive option. A forgotten override causes extra caution, not a security hole.

  6. Adding an implementation should be a one-file change. If adding tool 53 requires modifying the registry, the executor, the permission system, and the UI, the interface is not doing its job.

Think About It

Exercise 1: The Caller Inventory. Pick an interface in your codebase. List every caller. For each caller, list which methods it actually uses. Draw the diagram (as shown in this chapter). If every caller uses all methods, the interface is well-factored. If most callers use 2 out of 20 methods, consider whether the interface should be split.

Exercise 2: The Default Audit. Find every boolean property in your interfaces. What is the default value? Is it the safe option or the convenient option? For each property where the default is the dangerous option (e.g., allowParallelExecution: true), consider whether the default should be inverted.

Exercise 3: The New Implementation Test. Imagine adding a new implementation of your most important interface. How many files must you touch? Write down every file. If the number is greater than 3, the interface is leaking implementation coupling into the infrastructure. Identify which infrastructure components have hard-coded knowledge of existing implementations and refactor them to query the interface instead.

Exercise 4: The Contract-First Rewrite. Take a module you built bottom-up. Imagine you are starting over, but this time you must write the interface first -- before any implementation. What would change? Would the interface be narrower? Would the method signatures be different? Would some methods disappear entirely? This exercise reveals the gap between your current interface (shaped by implementation accidents) and the ideal interface (shaped by caller needs).

Exercise 5: The Evolution Simulation. Take your system's most stable interface. Imagine three new requirements: (a) a new implementation with different performance characteristics, (b) a new caller that needs a property the interface does not currently expose, (c) a requirement to remove a method that is now obsolete. For each requirement, trace the ripple: how many files change? If adding a property requires touching 50 files, you need a factory-with-defaults pattern. If removing a method is impossible because too many callers depend on it, you have a coupling problem to address before it gets worse.
