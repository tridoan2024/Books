Chapter 10: The Feedback Loop

The most powerful concept in engineering is not any algorithm, data structure, or design pattern. It is the feedback loop: the cycle of build-measure-learn that turns guesses into knowledge and prototypes into production systems.

Feedback loops exist at every scale. A developer runs a test and sees it fail -- that is a feedback loop measured in seconds. A team ships a feature and watches adoption metrics -- that is a feedback loop measured in days. A company pivots its strategy after a quarter of market data -- that is a feedback loop measured in months.

The engineer's job is not just to build within these loops but to tighten them. Every reduction in feedback latency -- from minutes to seconds, from days to hours, from months to weeks -- multiplies the team's learning rate. And learning rate, compounded over the lifetime of a project, determines whether a system thrives or stagnates.

This chapter examines feedback loops at three scales, the meta-strategy of tightening them, and why fast tests matter more than comprehensive tests. The case study is Claude Code's agentic loop -- a feedback loop that runs prompt-think-act-observe cycles millions of times per day, refined through continuous measurement into a system with 10 exit conditions and 7 continuation reasons, each tuned by real-world data.

Engineering operates on three nested feedback loops, each with different cycle times, costs, and learning outputs.

The Inner Loop: Edit-Run-Verify

The inner loop is where the developer lives. Edit a file. Run a test. See the result. Adjust. Repeat.

The speed of this loop determines developer productivity more than any other factor. A developer with a 2-second inner loop makes 30 iterations per minute. A developer with a 30-second inner loop makes 2 iterations per minute. Over an 8-hour day, that is the difference between 14,400 feedback cycles and 960. The first developer learns 15x faster than the second, even though both are equally skilled.

This is not an abstract argument. It is the reason why:

  • Hot module replacement exists (sub-second feedback for UI changes)
  • Incremental compilation exists (seconds vs. minutes for build feedback)
  • Watch mode exists in test runners (instant re-run on file save)
  • REPLs exist (millisecond feedback for expression evaluation)

Every tool that tightens the inner loop is a multiplier on the engineer's learning rate. Every tool that widens it -- slow builds, flaky tests, manual deployment steps -- is a tax on every iteration for the lifetime of the project.

The Development Loop: Feature-Test-Deploy

The development loop encompasses the full lifecycle of a feature: implement it, verify it works, ship it to users, monitor the results.

The critical bottleneck in most development loops is the gap between "works on my machine" and "works in production." Every manual step in this gap -- creating a PR, waiting for CI, getting a review, merging, deploying, monitoring -- is friction that slows the loop and discourages small, frequent changes. Friction breeds batch size. When deployment is painful, developers batch their changes into large, risky releases. When deployment is fast and safe, developers ship small, reversible changes.

The engineering principle: optimize for small batch size. Small changes are easier to review, easier to test, easier to roll back, and easier to reason about. The development loop should make small changes cheap and large changes expensive.

The Strategic Loop: Build-Measure-Pivot

The strategic loop is where engineering meets business. You build a capability. You measure whether users want it. You learn and adjust your direction.

Most engineers underestimate the importance of this loop. They optimize their inner loop to iterate quickly on code, but they do not optimize for quickly learning whether the code should exist at all. A feature built in 2 days and validated in 1 week is worth more than a feature built in 1 day and validated in 3 months -- because the faster validation lets you course-correct before you have invested heavily in the wrong direction.

The Nested Structure

These loops are nested, not independent. The inner loop runs inside the development loop, which runs inside the strategic loop. Tightening an inner loop amplifies the outer loops:

If you tighten... The effect is...
Inner loop (seconds) More iterations per feature, higher code quality, faster bug fixes
Development loop (hours) More features shipped per sprint, faster user feedback, smaller batch size
Strategic loop (weeks) Faster market learning, less wasted investment, better product-market fit

The reverse is also true. A slow inner loop (30-second test suite) drags down the development loop (developers avoid running tests, ship more bugs) which drags down the strategic loop (more time spent on bug fixes, less time on new learning).

Why Fast Tests Matter More Than Comprehensive Tests

This is a controversial statement, so let me be precise about what I mean and what I do not mean.

I am not saying comprehensive tests are unnecessary. I am saying that, given a choice between a test suite that takes 2 seconds and covers 70% of cases, and a test suite that takes 2 minutes and covers 90% of cases, the fast suite is more valuable -- because engineers will actually run it.

The Test Speed Paradox

A comprehensive but slow test suite has a perverse effect on development behavior:

  1. Tests take 2 minutes to run.
  2. Developers stop running them after every change (too slow).
  3. Developers batch changes and run tests every 30 minutes.
  4. Bugs introduced at minute 5 are discovered at minute 30.
  5. By minute 30, the developer has written 5 more changes on top of the bug.
  6. Debugging the bug now requires untangling 6 changes instead of 1.

A fast but less comprehensive test suite produces better outcomes:

  1. Tests take 2 seconds to run.
  2. Developers run them after every change (no friction).
  3. Bugs are discovered within seconds of introduction.
  4. The developer fixes the bug immediately, in context.
  5. The fix is trivial because only one change has been made since the last passing state.

The comprehensive suite catches more bugs per run. The fast suite catches bugs sooner. In practice, sooner matters more than more, because bugs caught sooner are exponentially cheaper to fix.

The testing pyramid is traditionally presented as a quality strategy -- more unit tests, fewer integration tests, fewest end-to-end tests. But it is equally valid as a speed strategy:

  • Unit tests (milliseconds): Run on every save. Catch logic errors, boundary conditions, type mismatches. Your primary feedback mechanism.
  • Integration tests (seconds): Run before committing. Catch interaction bugs, API contract violations, configuration errors. Your pre-commit gate.
  • End-to-end tests (minutes): Run in CI, before deploy. Catch system-level bugs, deployment issues, environment differences. Your safety net, not your feedback loop.

The mistake most teams make is inverting this pyramid -- relying on slow end-to-end tests for feedback and skipping fast unit tests. This is like navigating by satellite imagery when you have a compass. The satellite gives you more information, but the compass gives it to you now.

The Practical Implication

When you are building a new component, write tests that run in milliseconds first. Add integration tests when the component's interfaces stabilize. Add end-to-end tests when the component ships. During active development, your feedback comes from the fast tests. The slow tests validate what the fast tests have already told you.

Claude Code applies this principle to its own development. When an engineer makes a change to the agent loop, they run a single focused test that exercises the specific behavior they changed. That test completes in seconds. The full test suite -- thousands of tests, including end-to-end evaluations that run actual model inference -- runs in CI. The engineer gets fast feedback locally and comprehensive validation before merge.

The Agentic Loop as Feedback System

Claude Code's core agent loop -- the prompt-think-act-observe cycle that drives every interaction -- is a feedback loop running at machine speed. Each iteration takes seconds to complete. The model proposes an action, the system executes it, and the result feeds back into the model's next decision. This is the inner loop of an AI agent, and its design determines how quickly the agent converges on a solution.

The Fundamental Cycle

graph LR
    A[User Prompt] --> B["Think:<br/>Model generates response"]
    B --> C{"Tool use<br/>requested?"}
    C -->|Yes| D["Act:<br/>Execute tools"]
    D --> E["Observe:<br/>Collect results"]
    E --> B
    C -->|No| F["Respond:<br/>Return to user"]

This looks identical to the inner loop from the previous section: edit-run-verify. The model edits (proposes an action), the system runs (executes the tool), and the model verifies (observes the result and decides what to do next). The parallel is not accidental. The agentic loop is a feedback loop with the same dynamics as human development, operating at a different speed.

A single user prompt may trigger 1 to 50 iterations of this loop. The user asks "find and fix all TODO comments in the codebase," and the model searches, reads, edits, verifies, reads, edits, verifies, until all TODOs are addressed. Each iteration builds on the results of the previous one. The model's understanding of the problem deepens with each observation.

The Cost of Each Iteration

Every iteration costs tokens. The context window grows with each cycle -- the model's previous responses and the tool results accumulate. By iteration 8, the context contains the original user message plus 7 model responses and 7 sets of tool results. By iteration 20, the context may approach the window limit.

This creates a tension that does not exist in human feedback loops: the feedback medium has a capacity limit. A human developer can iterate indefinitely -- their editor does not get slower with each edit. The model's context window fills up, and eventually the system must either compress (losing information) or stop.

This tension drives several design decisions in the agent loop:

  • Context compression: Aggressive strategies to reduce context size without losing critical information (as discussed in Chapter 8).
  • Turn limits: Hard caps on iteration count to prevent runaway loops.
  • Token budgets: Explicit spending limits that the model can see and self-pace against.
  • Convergence detection: Signals that indicate the model is making progress versus spinning.

Why the Loop Needs 10 Exit Conditions

A naive agent loop has one exit condition: the model stops requesting tools. A production agent loop needs many more, because there are many reasons to stop, and each requires different handling.

Exit Reason Trigger What It Means
completed Model finished naturally Normal success
prompt_too_long Context exceeded limits, all recovery failed Ran out of room
blocking_limit Approaching context ceiling About to run out of room
model_error API error after all retries External failure
aborted_streaming User canceled during model output User changed mind
aborted_tools User canceled during tool execution User changed mind
stop_hook_prevented Quality gate rejected the response Not done yet
hook_stopped Hook explicitly terminated External control
max_turns Turn limit reached Runaway prevention
image_error Unrecoverable image processing failure Bad input

Each exit reason is a different kind of feedback. completed means the loop converged. max_turns means it did not converge fast enough. prompt_too_long means the problem outgrew the available context. stop_hook_prevented means an external quality check found the output insufficient.

These are not error codes -- they are discriminated union variants, each carrying different payload data. The consumer pattern-matches on the reason and handles each case explicitly. A completed result shows the final response. A max_turns result warns the user that the agent may not have finished. An aborted_streaming result shows partial output. The type system ensures every exit path is handled. Add a new exit reason and every consumer must update.

Why the Loop Needs 7 Continuation Reasons

Equally important to knowing when to stop is knowing why to continue. The continuation reason determines what state carries forward into the next iteration:

Continuation Reason What Happened State Impact
next_turn Normal tool-to-model cycle All recovery counters reset
collapse_drain_retry Context compression freed space Preserves collapse state
reactive_compact_retry Emergency compaction after overflow Sets compaction flag
max_output_tokens_escalate Hit 8K limit, retry at 64K Sets limit override
max_output_tokens_recovery Hit 64K limit, inject resume Increments recovery count
stop_hook_blocking Quality gate injected feedback Preserves compaction guards
token_budget_continuation Budget remaining, nudge injected Increments continuation count

This looks like over-engineering until you understand why each reason exists. Every continuation reason represents a distinct state management requirement. When the loop continues because of a normal tool result (next_turn), all recovery counters should reset -- the system is healthy. When the loop continues because a stop hook rejected the output (stop_hook_blocking), the compaction guard must be preserved -- because a previous compaction attempt may have failed, and resetting the guard would create an infinite loop.

The Interaction Trap

The most dangerous aspect of multiple continuation reasons is their interaction. Consider this sequence:

  1. A stop hook injects error messages into the conversation.
  2. The new messages push the context past the compaction threshold.
  3. Compaction fires but fails (context too large even for summarization).
  4. The compaction failure flag is set.
  5. The model responds to the hook errors, triggering the stop hook again.
  6. The stop hook injects more messages.
  7. If the compaction failure flag was reset at step 6, compaction would fire again, fail again, and the loop would repeat forever.

The fix: when continuing due to stop_hook_blocking, preserve the compaction failure flag. Never reset it. This prevents the death spiral.

This kind of interaction between recovery paths is the primary source of infinite loop bugs in agent systems. Every new continuation reason must be analyzed against every existing one for potential cycles. Recording the continuation reason on the state makes this analysis tractable -- you can trace the exact path through the decision tree and verify that no cycle exists.

Error Recovery as Feedback

The agent loop's error recovery is a feedback loop within a feedback loop. When the model's output is truncated because it hit the token limit, the recovery sequence is:

Phase 1 - Silent escalation:
  Default limit: 8K tokens (optimized for GPU utilization)
  Hit limit → retry at 64K tokens
  User never knows it happened

Phase 2 - Multi-turn recovery:
  Hit 64K limit → inject message: "Resume where you left off.
  No apology, no recap. Break remaining work into smaller pieces."
  Up to 3 attempts

Phase 3 - Surface the error:
  All recovery failed → show truncated output, explain what happened

Each phase is a feedback cycle. Phase 1 feeds the observation "output was truncated" back into the system, which adjusts parameters and retries. Phase 2 feeds the observation "output was still truncated" into the conversation itself, asking the model to change its approach. Phase 3 feeds the observation "recovery is not working" to the user, who can make a higher-level decision.

The Error Withholding Pattern

A critical design choice in the agent loop: recoverable errors are withheld from the output stream during streaming, not surfaced immediately. This is counterintuitive -- most systems surface errors immediately -- but it is essential for feedback loop integrity.

The reason is the generator protocol. Once you yield a message to the consumer, it is gone. If the consumer reacts to an error by disconnecting, your subsequent recovery is invisible. By withholding potentially recoverable errors, the loop defers the decision until it has enough information to make it correctly. Either recovery succeeds (and the consumer never saw the error) or recovery fails (and the consumer sees a final, definitive error).

This is a general principle for feedback systems: defer terminal decisions until you have terminal information. An intermediate failure is not a terminal failure unless recovery has been attempted and exhausted.

The Pull-Based Architecture

The agent loop is implemented as an async generator -- a pull-based stream where the consumer drives the pace. This architectural choice is itself a feedback mechanism.

sequenceDiagram
    participant UI as UI Renderer
    participant Loop as Agent Loop
    participant Model as Language Model
    participant Tools as Tool Executor

    UI->>Loop: next()
    Loop->>Model: Stream request
    Model-->>Loop: Token chunk
    Loop-->>UI: yield TextDelta
    Note over UI: Render to screen

    UI->>Loop: next()
    Model-->>Loop: Tool use block
    Loop->>Tools: Execute tool
    Tools-->>Loop: Result
    Loop-->>UI: yield ToolResult
    Note over UI: Render result

    UI->>Loop: next()
    Loop->>Model: Continue with result
    Model-->>Loop: Final text
    Loop-->>UI: yield AssistantMessage
    Loop-->>UI: return { reason: 'completed' }

Three aspects of this design serve the feedback loop:

Backpressure. If the UI is slow to render (complex markdown, syntax highlighting), the generator naturally pauses. The model does not generate faster than the UI can display. This prevents the feedback from becoming invisible -- the user always sees what the agent is doing.

Streaming feedback. The user sees tokens as they are generated, not after the full response is complete. This transforms a 30-second black box into a 30-second window where the user watches the agent think. The user can abort early if the agent is headed in the wrong direction. This is feedback from the user back to the loop -- the abort is a signal that the current approach is wrong.

Typed exit channel. The generator's return value carries the exit reason as a discriminated union. The yield channel carries messages (what happened). The return channel carries the terminal state (why it stopped). These are separate information channels serving separate feedback purposes.

Why Not Callbacks or Event Emitters?

Alternative Feedback Problem
Callbacks No return channel for exit reasons. No backpressure. Consumer cannot signal "slow down."
Event Emitter No backpressure. Events fire regardless of consumer readiness. Lost events = lost feedback.
Observable (RxJS) Heavy dependency for a single iteration pattern. Operator composition is overkill.
Promise No streaming. User sees nothing until the entire response is complete. No intermediate feedback.

The async generator provides backpressure (feedback from consumer to producer), streaming (feedback from producer to consumer), and typed exit (feedback about termination) -- all from the language runtime, with zero dependencies.

Tightening the Loop: A Meta-Strategy

Tightening feedback loops is not a one-time optimization. It is a meta-strategy -- a strategy for making all other strategies more effective. Every time you reduce the cycle time of a feedback loop, you increase the rate at which you learn, and learning rate compounds.

How Claude Code Tightened Its Own Loop

The agent loop as it exists today was not designed in a single iteration. It was shaped by feedback from millions of executions:

  1. The 8K default output limit. Originally, the model was given a high output token limit for every request. This wasted GPU resources -- 99% of responses were under 8K tokens. Measuring actual output distributions led to a design where the default is 8K and the system silently escalates to 64K only when needed. Result: 4-8x better GPU utilization with no user-visible impact.

  2. Streaming tool execution. Originally, tools executed sequentially after the model's response completed. Measuring latency showed that the model often requests 3-5 tools per response. Pipelining tool execution with streaming -- starting tool N while the model generates the request for tool N+1 -- cut total latency by 60-70% for multi-tool responses.

  3. The 10 exit conditions. The original loop had 3 exit conditions: completed, error, and abort. Each new exit condition was added because real usage revealed a case where the existing exits produced wrong behavior. max_turns was added after sessions spiraled to 200+ iterations. prompt_too_long was added after the system wasted API calls on requests guaranteed to fail. Each condition is a lesson learned from production feedback.

  4. The continuation reasons. Originally, the loop had one continuation reason: "tools were called, keep going." Each new reason was added after a bug was discovered where two recovery paths interacted badly. The stop_hook_blocking reason exists because stop hooks and compaction interacted to create infinite loops. Recording the reason made the interaction visible and fixable.

  5. The diminishing returns detector. A token budget continuation originally ran until the budget was exhausted. But some models would enter loops producing near-empty responses -- consuming budget without making progress. Measuring output size per continuation led to a heuristic: if the last two continuations produced less than 500 tokens each, the model is stuck. Stop early to prevent waste.

Each of these optimizations came from the same process: measure real behavior, identify a gap between expected and actual, adjust the design, measure again. The feedback loop that tightens feedback loops.

The Measurement Imperative

You cannot tighten what you do not measure. The agent loop tracks:

  • Token usage per iteration. Reveals efficiency trends and budget consumption patterns.
  • Exit reason distribution. Shows which exit conditions fire most often and which are dead code.
  • Continuation reason traces. Reveals interaction patterns and potential infinite loop risks.
  • Time-to-first-token. Measures the responsiveness of each iteration.
  • Tool execution latency. Identifies tools that are bottlenecks.
  • Recovery success rate. Shows how often error recovery actually works (vs. just delaying the inevitable failure).

Without these measurements, optimizations are guesses. With them, optimizations are evidence-based decisions. The measurement infrastructure is not overhead -- it is the foundation of the feedback system that improves the feedback system.

Immutable Config vs. Mutable State

A subtle but important feedback loop principle: the loop's configuration and its state must be separated. Configuration is what was true when the loop started. State is what changes on every iteration.

Immutable (snapshotted at loop entry):     Mutable (replaced every iteration):
- System prompt                             - Conversation messages
- Tool definitions                          - Turn counter
- Model name                               - Recovery counters
- Feature flags                             - Compaction tracking
- Maximum turns                             - Transition reason

Why does this matter for feedback? Because the feedback loop needs a stable reference point. When something goes wrong on iteration 47, you need to compare the current state against the original configuration. If both live in the same mutable object, you must reconstruct the original from the mutated version -- a process that is error-prone and often impossible.

The pattern: destructure config once at entry, never reassign it. Build a new state object on every iteration (replace, do not mutate). Every iteration declares the complete next state explicitly.

# Replace, don't mutate
state = LoopState(
    messages=[*state.messages, *assistant_msgs, *tool_results],
    turn_count=state.turn_count + 1,
    recovery_count=0,           # Explicit: recovery resets on success
    compaction_attempted=False,  # Explicit: new turn, new chance
    transition=Transition(reason="next_turn"),
)

When you replace the entire state object, every continuation site declares its complete intent. You can read any transition independently without tracing what other code paths might have mutated before it. The transition field is the feedback record -- it tells you why this iteration was started.

Feature flags deserve special attention. In a production system, feature flags can change mid-session. If the loop reads flags on every iteration, behavior can change mid-query -- iteration 1 uses one code path, iteration 5 uses another because a flag was toggled between them. The solution: snapshot all relevant flags at entry. The loop uses the snapshot for its entire lifetime, ensuring consistent behavior and reproducible debugging.

Feedback Loops in System Design

The feedback loop concept extends beyond code to system architecture. Every monitoring system, every alerting rule, every performance dashboard is a feedback loop for the humans operating the system.

Observability as Feedback

As discussed in Chapter 9, you cannot fix what you cannot see. Observability -- metrics, logs, traces -- is the feedback mechanism that connects a running system to the humans responsible for it.

But not all observability is equally valuable. The key question is latency: how quickly does the observation reach the person who can act on it?

Feedback Mechanism Latency Value for Fast Response
Real-time dashboard Seconds Immediate incidents
Alerting rule Minutes Known failure patterns
Log aggregation Minutes-hours Post-incident analysis
Weekly metrics review Days Trend analysis
Quarterly architecture review Months Strategic direction

Each mechanism serves a different timescale. Real-time dashboards are useless for strategic planning. Quarterly reviews are useless for incident response. The complete observability stack covers all timescales.

Deployment as Feedback

Every deployment is a hypothesis: "this change will improve the system." The feedback comes from production behavior after the deployment. Fast feedback requires:

  • Canary deploys: Ship to 1% of traffic first. Measure. If metrics degrade, roll back automatically.
  • Feature flags: Decouple deployment from activation. Ship the code, then enable the feature gradually.
  • Automated rollback: If error rates spike within N minutes of deployment, revert automatically.

Each of these techniques tightens the deployment feedback loop. Without them, the loop is: deploy, wait for user complaints, investigate, roll back manually. With them, the loop is: deploy, measure automatically, roll back automatically if needed. The cycle time drops from hours to minutes.

The Compound Effect

Feedback loops compound. A team with fast inner loops (seconds), fast development loops (hours), and fast strategic loops (weeks) learns exponentially faster than a team with slow loops at any level.

Over a year, the fast team has run: - ~3 million inner loop cycles (vs. ~200,000 for the slow team) - ~2,000 development cycles (vs. ~500) - ~50 strategic cycles (vs. ~12)

The cumulative learning difference is staggering. The fast team has explored more of the solution space, encountered and fixed more bugs, validated more hypotheses, and built more accurate mental models of their system. This is not a marginal advantage -- it is a category difference.

Convergence: Knowing When to Stop

Every feedback loop needs a convergence criterion: a signal that indicates the loop has achieved its goal and should stop. Without one, the loop runs forever.

In the agentic loop, convergence is detected through multiple signals:

Natural completion. The model generates a response without requesting any tools. It has decided it is done. This is the most common exit path.

Diminishing returns. The model is still producing output, but each iteration produces less than the last. After two consecutive iterations of less than 500 tokens, the system concludes the model is stuck and stops.

External validation. Stop hooks run after the model's response, checking whether the output meets quality criteria. If the hook says "not done yet," the loop continues with the hook's feedback. If the hook says "good enough," the loop stops.

Budget exhaustion. The token budget is consumed. The model has done all it can within the allocated resources.

Each signal addresses a different failure of convergence. Natural completion handles the happy path. Diminishing returns handles oscillation. External validation handles quality drift. Budget exhaustion handles runaway complexity.

The convergence design also illustrates a broader principle: compound stopping conditions are more robust than simple ones. A loop that stops only on natural completion will spin when the model oscillates. A loop that stops only on budget exhaustion will waste tokens on non-productive iterations. Multiple independent stopping conditions create a safety net where any one can catch the loop.

Key Principles

  1. Tightening feedback loops is the highest-leverage engineering activity. Every reduction in cycle time multiplies learning rate. Learning rate compounds over the project lifetime. Invest in fast loops before investing in features.

  2. Fast tests beat comprehensive tests. A 2-second test suite that runs after every change catches bugs faster than a 2-minute suite that developers avoid running. Speed determines usage, usage determines value.

  3. Discriminate your exit conditions. A loop with one exit reason produces ambiguous outcomes. A loop with 10 typed exit reasons produces precise, actionable information. Use discriminated unions, not exceptions.

  4. Track continuation reasons to prevent interaction bugs. When recovery paths interact (compaction + stop hooks + token limits), recorded continuation reasons make the interactions visible and debuggable. Without them, infinite loops are inevitable.

  5. Separate immutable config from mutable state. Snapshot configuration at entry, replace state on every iteration. This gives you a stable reference point for debugging and prevents flag-toggling from creating inconsistent behavior.

  6. Defer terminal decisions until you have terminal information. Do not surface errors to consumers until recovery has been attempted. Once you yield an error, you cannot take it back.

  7. Use pull-based streams for feedback-intensive loops. Async generators provide backpressure (consumer controls pace), streaming (producer shares intermediate state), and typed exits (separate channel for termination) -- all without external dependencies.

Think About It

  1. The inner loop audit. Time your inner loop: from saving a file to seeing whether your change worked. How many seconds? Now list every step in that loop. Which step is the slowest? What would it take to cut that step in half? What would the compounding effect be over a year of development?

  2. The test speed tradeoff. You have a test suite with 200 tests. 180 run in under 100ms each. 20 run in 5-10 seconds each (they hit a database). The fast tests take 2 seconds total. The slow tests take 3 minutes total. Design a strategy that gives developers fast feedback while keeping comprehensive coverage. Hint: think about when each group runs, not whether they run.

  3. The convergence problem. You are building an agent that generates and refines a document. The model produces a draft, then revises it, then revises the revision. How do you detect when the revisions are no longer improving the document? What metrics would you track? What is the risk of stopping too early vs. stopping too late?

  4. The feedback loop inventory. For a system you work on, list every feedback loop at all three scales (inner, development, strategic). For each one, estimate its cycle time. Identify the slowest loop at each scale. Now imagine you could halve the cycle time of just one loop at each scale -- which three would you choose, and why?

  5. The state machine exercise. The agentic loop has 10 exit conditions and 7 continuation reasons. Draw the state machine. Now add a new continuation reason: tool_timeout_retry (a tool timed out, retry with a shorter input). Which existing continuation reasons might interact with this new one? What state would you need to preserve to prevent infinite loops?
