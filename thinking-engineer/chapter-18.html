Chapter 18: Prompt Engineering is Problem Engineering

The phrase "prompt engineering" is misleading. It implies the skill is in crafting clever strings -- finding the magic words that make the AI produce good output. This is like saying architecture is about choosing wall paint. The paint matters, but it is not the structure.

The real skill is problem engineering. A well-defined problem produces a good prompt naturally. A vague problem produces a vague prompt no matter how cleverly you phrase it. The best prompt engineers are not wordsmiths -- they are engineers who have mastered the discipline of specification: stating inputs, outputs, constraints, edge cases, and failure modes so precisely that the AI has no room for wrong assumptions.

This chapter examines prompt engineering as a form of problem engineering: why precision matters, how to structure specifications for AI consumption, how system prompts function as architecture documents, how context management is information architecture, and how all of this comes together in Claude Code's prompt pipeline -- a system that assembles 10+ sections into a coherent system prompt before every API call, with priority-based token budgeting that determines what the AI sees and what it does not.

Why Vague Prompts Produce Vague Code

Consider two prompts for the same task:

Prompt A: "Add caching to the API client."

Prompt B: "Add a response cache to ApiClient.sendRequest(). Cache key: ${method}:${url}:${bodyHash}. TTL: 5 minutes. Max entries: 1000, LRU eviction. Cache only GET requests with 200 status. Invalidate on POST/PUT/DELETE to the same URL prefix. Thread-safe. Return type: CachedResponse | FreshResponse (discriminated union so callers know the source). Do not cache responses larger than 100KB. Log cache hits/misses to the existing metrics.requestCache counter."

Prompt A will produce working code. It will also produce code that: - Uses an unbounded cache that grows until it consumes all memory - Caches POST requests, causing stale data bugs - Uses a cache key that does not account for request body variations - Returns cached responses indistinguishably from fresh ones - Is not thread-safe - Has no metrics instrumentation

The AI will make reasonable choices for each of these -- but "reasonable" is not the same as "correct for your system." The AI does not know your memory constraints, your consistency requirements, your observability stack, or your concurrency model. Without those constraints, it fills the gaps with generic defaults.

Prompt B leaves no gaps. Every design decision is explicit. The AI generates exactly one reasonable implementation because the specification admits exactly one interpretation. The engineer spent 10 minutes writing the prompt and saved 2 hours of debugging wrong defaults.

This is not about prompt tricks, template formatting, or magic keywords. It is about the ancient engineering discipline of specification.

The Specification Discipline

A complete specification answers seven questions:

Question What It Prevents
What are the inputs? Wrong data type assumptions, missing validation
What are the outputs? Ambiguous return types, missing error signals
What are the constraints? Unbounded resource usage, missing safety checks
What are the edge cases? Happy-path-only code that fails in production
What are the failure modes? Missing error handling, silent failures
What are the non-goals? Over-engineering, solving the wrong problem
What context exists? Reinventing what already exists, breaking conventions

Each unanswered question is a degree of freedom that the AI fills with an assumption. Each assumption is a potential bug. The relationship is direct: specification precision is inversely proportional to bug count.

Claude Code's development bears this out. The most expensive bugs in the system were not logic errors -- they were missing constraints:

  • The auto-compaction system worked correctly but did not account for cache economics. Missing constraint: "must not invalidate the prompt cache." Cost: 10x increase in per-turn API costs for users who triggered compaction.

  • The tool result budget enforced a per-result token limit but did not account for concurrent tool calls. Missing constraint: "total across concurrent results must not exceed window capacity." Cost: sessions that ran 5 concurrent Read operations could overflow the context window.

  • The session resume feature restored conversation state correctly but did not restore the compact boundary. Missing constraint: "must preserve the compaction watermark across resume." Cost: resumed sessions re-processed messages that had already been summarized.

Every one of these was caught during verification. Every one could have been prevented by a more complete specification. The pattern is consistent: the cost of a missing constraint is always higher than the cost of specifying it.

System Prompts as Architecture Documents

A system prompt is not "instructions for the AI." It is an architecture document. It defines the system's identity, capabilities, behavioral boundaries, and operational context. It is the most important piece of text in the entire system -- more important than any individual source file, because every source file's behavior is filtered through the system prompt.

The Architecture Analogy

Consider a traditional architecture document for a web service:

Identity:     "Order Processing Service"
Capabilities: Process orders, validate inventory, charge payments
Boundaries:   No direct database access (use API gateway)
Context:      Part of the e-commerce platform, deployed to us-east-1
Rules:        All prices in USD, all timestamps in UTC

Now consider a system prompt for an AI agent:

Identity:     "Claude Code, an AI coding assistant"
Capabilities: 52 tools (Read, Write, Bash, Edit, Grep...)
Boundaries:   Permission system, denied files, blocked commands
Context:      Working directory, git status, project rules
Rules:        Communication style, coding standards, verification steps

The structure is identical. Both define what the system is, what it can do, what it cannot do, and what context it operates in. The system prompt is the architecture document for the AI's behavior within the session.

This analogy has practical implications. If you treat the system prompt as "instructions" that you tweak until the AI behaves correctly, you are doing prompt engineering. If you treat it as an architecture document that you design with the same rigor as a system architecture, you are doing problem engineering.

The Stability Gradient

The sections are ordered by stability -- the most stable blocks come first, the most volatile blocks come last. This ordering is not arbitrary. It is driven by prompt cache economics.

The prompt cache stores the byte sequence of the system prompt prefix. A cache hit costs 1/10th of a cache miss. Modifying any byte in the cached prefix invalidates the cache. By placing stable blocks first:

Cache Boundary
    |
    v
[Identity | Tools | Model Instructions]  [Rules | Memory | Skills | Session | MCP | Custom | Plan]
<--------- CACHED (stable) ---------->   <---------- RE-PROCESSED (volatile) --------->

Everything before the cache boundary is byte-identical across turns. The first three blocks -- identity, tool definitions, model instructions -- rarely change within a session. They form the cacheable prefix, potentially saving 15,000+ tokens of re-processing per turn at 1/10th cost.

This is architecture in the truest sense. The ordering decision is driven by a constraint (cache economics), produces a measurable benefit (10x cost reduction on the cached prefix), and requires disciplined maintenance (any change to a stable block invalidates all cached sessions).

Why the Order Matters: A Real Example

Early in Claude Code's development, the MCP server descriptions were placed in block position 3 -- after identity and tools, before model instructions. MCP servers connect and disconnect dynamically. Every time a server reconnected, the byte sequence at position 3 changed, invalidating the cache for blocks 1 and 2 (which were unchanged). This cost roughly 15,000 tokens of re-processing that could have been avoided.

Moving MCP descriptions to position 8 -- after all stable blocks -- meant server reconnections only invalidated the volatile suffix. The stable prefix remained cached. The change saved an estimated 15% of total API costs for sessions with MCP servers.

The lesson: in a system prompt, position is architecture. Moving a section from position 3 to position 8 can change system economics by double digits.

Context Management as Information Architecture

The system prompt is one piece of the context puzzle. The full context -- everything the AI sees when making a decision -- includes the system prompt, the conversation history, tool results, and injected metadata. Managing this context is information architecture: deciding what information is present, where it appears, and how much space it occupies.

The Information Budget

The context window is a fixed resource: 200,000 tokens for current models. This budget must cover:

System Prompt:        ~20,000 tokens (10%)
Conversation History: ~140,000 tokens (70%)  <- variable, compressible
Output Reserve:       ~20,000 tokens (10%)
Tool Results Buffer:  ~20,000 tokens (10%)

Each category competes for space. A system prompt that grows to 40,000 tokens (because someone added a 20K-token knowledge base to CLAUDE.md) cuts the conversation budget in half. Fewer turns before compaction. More frequent LLM summarization calls. Higher costs. Worse user experience.

This is why CLAUDE.md should be concise. Not because brevity is a virtue -- because tokens are a finite resource with real costs. Every token in the system prompt is processed on every turn. A 100-token addition to the system prompt costs 100 tokens x N turns x sessions per day. Over millions of sessions, a verbose system prompt is measurably expensive.

The Priority Hierarchy

When the context fills up, what gets removed? This is the defining question of context management, and the answer reveals the system's priorities:

The hierarchy encodes a bet: the model's ability to reason about the current task (recent messages) is more valuable than its memory of past tasks (old tool results).

The bet pays off in practice. Users rarely need the AI to recall a file it read 30 turns ago verbatim. They frequently need it to remember what they asked 2 turns ago. The priority hierarchy matches actual usage patterns.

The Five Context Injection Patterns

Context enters the AI's view through five distinct patterns, each with different characteristics:

Pattern Where Persistence Cache Impact Best For
System prompt block System prompt parameter Every turn Cached (stable blocks) Identity, tools, rules
User context injection Prepended to user message One turn Not cached Working dir, git status
System reminder Tagged block in user message One turn Not cached Behavioral nudges
Tool result Response to tool_use request Until compacted Not cached File contents, command output
Meta-message System-generated user message Until compacted Not cached Error recovery, budget alerts

Choosing the wrong pattern wastes tokens or degrades performance. Putting per-turn context (working directory) in the system prompt wastes cache -- the directory might change, invalidating the cache. Putting permanent rules in a system reminder wastes tokens -- the reminder is re-sent every turn without caching benefit.

The design rule: match the context lifetime to the injection pattern. Permanent context goes in the system prompt. Per-turn context goes in user injections. Temporary context goes in meta-messages that can be garbage-collected.

Step 3 (prioritize) and Step 5 (order) are where the architecture lives. Prioritization determines what the AI knows. Ordering determines what the AI knows cheaply (cached) versus expensively (re-processed).

Deterministic Assembly

The pipeline is a deterministic function: given the same inputs (source files, session state, feature flags), it produces the same output (byte-identical system prompt). This determinism enables:

  • Snapshot testing. Record the system prompt for a known state. Verify it matches on future runs. Any deviation is a regression.
  • Cache stability analysis. Compare the system prompt across turns. Identify which blocks changed and whether the change was necessary.
  • Cost prediction. Given a session configuration, predict the system prompt size and therefore the per-turn cost.

Determinism requires discipline. Tool definitions must be sorted consistently (not hash-order). Feature flags must be latched at session start (not re-evaluated per turn). Path-scoped rules must be evaluated against a frozen file set (not the live filesystem, which might change during assembly).

Any source of non-determinism in the assembly pipeline produces non-deterministic cache behavior, which produces non-deterministic costs, which makes the system's economics unpredictable. Determinism is not a nice-to-have. It is an economic requirement.

Token Budgeting as Resource Allocation

Each block in the system prompt has a token budget. The budgets are not equal -- they reflect the relative importance of each information source:

Block                    Budget     Justification
----                     ------     -------------
Identity                 3,000      Fixed, essential, never truncated
Tool definitions         15,000     52 tools, schemas required for tool use
Model instructions       1,000      Small, stable
Project rules            3,000      CLAUDE.md + path-scoped rules
Memory                   2,000      Auto-memory from previous sessions
Active skills            5,000      Truncated if over budget
Session context          500        Minimal metadata
MCP descriptions         1,500      Dynamic tool availability
Custom instructions      1,000      User preferences
Plan context             2,000      Current task state

When the total exceeds the system prompt budget (~30K tokens), lower-priority blocks are truncated first. Skills (5K budget) are truncated before memory (2K budget). Memory is truncated before project rules (3K budget). Identity and tools are never truncated.

This is resource allocation. The budgets encode a value judgment: tool definitions are more important than skills. Skills are more important than MCP descriptions. The AI without tool definitions cannot use tools. The AI without MCP descriptions loses access to external tools but retains core functionality.

The judgment call is visible in the numbers. Engineers debated whether skills should get 5K or 10K tokens. At 10K, skills consume a third of the system prompt budget, leaving less room for everything else. At 5K, complex skills are truncated but the overall system prompt stays lean. The 5K budget was chosen because skill truncation degrades gradually (the AI has partial instructions) while system prompt overflow degrades catastrophically (blocks get dropped entirely).

Building Your Own Prompt Architecture

If you are building a system that uses AI as a component, the prompt pipeline design decisions in this chapter apply to you. Here is the minimum viable architecture:

1. Separate Static from Dynamic

Identify which parts of your prompt change between calls and which do not. Static parts go first (for cache stability). Dynamic parts go last.

class PromptAssembler:
    def assemble(self, session: Session) -> SystemPrompt:
        blocks = []

        # Static core (cacheable)
        blocks.append(self.identity_block)           # Never changes
        blocks.append(self.tool_definitions)          # Changes only on deploy
        blocks.append(self.behavioral_rules)          # Changes only on config change

        # Semi-stable (cacheable within a session)
        blocks.append(self.project_rules(session))    # Changes when file context changes
        blocks.append(self.memory(session))            # Changes when memory updates

        # Dynamic (re-processed every call)
        blocks.append(self.session_context(session))   # Changes every turn
        blocks.append(self.active_task(session))        # Changes every turn

        return SystemPrompt(blocks=blocks)

2. Budget Each Block

Assign a token budget to each block. Enforce it by truncation, not by hoping the content is short enough:

BUDGETS = {
    "identity": 3000,
    "tools": 15000,
    "rules": 3000,
    "memory": 2000,
    "context": 500,
    "task": 2000,
}

def apply_budget(block: str, budget: int) -> str:
    tokens = count_tokens(block)
    if tokens <= budget:
        return block
    return truncate_to_tokens(block, budget) + "\n[Truncated]"

3. Place Cache Breakpoints

Put cache control markers at the boundary between static and dynamic blocks:

def add_cache_control(blocks: list[Block]) -> list[Block]:
    # Find the last stable block
    last_stable = max(
        i for i, b in enumerate(blocks) if b.stability == "static"
    )
    # Place cache marker after the last stable block
    blocks[last_stable].cache_control = {"type": "ephemeral"}
    return blocks

4. Make Assembly Deterministic

Sort any collections that feed into the prompt. Latch configuration at session start. Avoid reading from sources that change during assembly:

def tool_definitions(self) -> str:
    # Sort alphabetically for cache stability
    tools = sorted(self.tools, key=lambda t: t.name)
    return "\n".join(t.to_schema() for t in tools)

5. Test the Pipeline

Snapshot test the assembled prompt. When the snapshot changes, verify the change is intentional:

def test_prompt_assembly_is_deterministic():
    session = make_test_session()
    prompt_1 = assembler.assemble(session)
    prompt_2 = assembler.assemble(session)
    assert prompt_1.to_bytes() == prompt_2.to_bytes()

def test_prompt_snapshot():
    session = make_test_session()
    prompt = assembler.assemble(session)
    assert prompt.to_text() == load_snapshot("prompt_baseline.txt")

The Recursive Insight

There is a recursive quality to this chapter's argument. The claim is that prompt engineering is problem engineering -- that the best prompt is a well-defined problem. But this chapter itself is a prompt of sorts. It is defining, for you the reader, the problem of prompt design. And it follows the same discipline it advocates:

  • Inputs: Raw context sources (files, memory, session state)
  • Outputs: A coherent system prompt that produces correct AI behavior
  • Constraints: Token budgets, cache economics, processing costs
  • Edge cases: What happens when a block exceeds its budget? When MCP servers reconnect? When the system prompt itself is too large?
  • Failure modes: Cache invalidation, context overflow, stale instructions
  • Non-goals: Making the AI "creative" or "personality-rich" -- the system prompt is for correctness, not style

The prompt pipeline is not clever. It is engineered. It follows the same principles as any well-designed data pipeline: typed inputs, defined transformations, budgeted resources, deterministic output, and testable behavior.

The engineers who built it did not write "a really good prompt." They defined a really precise problem -- "assemble the context the model needs to behave correctly within economic constraints" -- and then engineered a solution. The prompt is an artifact of the engineering, not the other way around.

The Context Window as a Design Constraint

Every AI system operates within a finite context window. This constraint is analogous to memory constraints in systems programming, bandwidth constraints in networking, or screen real estate in UI design. The best engineers do not fight constraints -- they design with them.

The Graduated Compression Pipeline

When the context fills up, Claude Code does not simply fail or discard everything. It applies a graduated series of compressions, each more aggressive than the last:

Tier Strategy Cost Information Loss
0 Server-side tool result clearing Zero Old tool result content
1 Per-tool result truncation Near-zero Tail of large results
2 History snipping by count Near-zero Oldest messages entirely
3 Microcompact old results Near-zero Old tool result content (preserve metadata)
4 LLM summarization One API call Detailed history becomes summary
5 Reactive compact (error recovery) Two API calls Emergency compression after overflow

A user whose session stays under 30 turns never hits Tier 4. Tiers 0-3 handle their context silently. Only long, intensive sessions trigger the expensive LLM summarization. The architecture ensures the system spends the minimum cost necessary for each session's actual context pressure.

This graduated approach embodies a principle from Chapter 4 (Thinking in Constraints): the constraint breeds the design. A smaller context window would require more aggressive compression earlier. A larger window would allow simpler strategies. The 200K-token window with 20K reserved for output and 20K for the system prompt leaves 160K for conversation -- enough for 30-80 tool calls before compression is needed. The compression tiers are tuned to this specific constraint.

The 83.5% Threshold

Auto-compaction triggers at 83.5% of context capacity. Not 90%. Not 95%. Not 100%.

The number is not arbitrary. The compaction call itself requires tokens -- the model reads the messages being summarized and generates a summary. If the threshold is 95%, there is not enough room for the compaction call. If it is 70%, the system compacts too aggressively, wasting API calls and losing conversational detail unnecessarily.

83.5% was determined empirically: the p99.99 of summarization output is ~17K tokens. With a 20K output reserve and a 13K buffer between the threshold and the hard limit, there is 33K tokens of headroom for the compaction call. This is enough for all but the most extreme cases.

The threshold also has a hysteresis design -- compaction fires at 83.5% but does not re-trigger until context drops below a lower bound after compaction. Without hysteresis, sessions that hover near the threshold would compact repeatedly, wasting API calls on oscillation.

This is problem engineering applied to system design. The "problem" is: when should the system compress context? The "specification" includes inputs (token count), outputs (compression decision), constraints (must leave room for the compaction call), edge cases (oscillation), and failure modes (what if compaction fails three times -- circuit break). The solution follows naturally from the specification.

The Compaction Summary as a Prompt

When Claude Code compacts the conversation, it does not simply delete old messages. It summarizes them using a structured prompt that requests 9 specific sections:

  1. Primary user request and goal
  2. Key technical concepts encountered
  3. Files read or modified (with paths)
  4. Errors encountered and how they were resolved
  5. Problem-solving approaches tried
  6. All user instructions (verbatim where possible)
  7. Pending tasks and open questions
  8. Current state of work
  9. Recommended next step

This summary prompt is itself a specification. It defines the inputs (old messages), the outputs (structured summary), the constraints (must fit in ~5K tokens), and the failure modes it guards against:

  • Task drift -- prevented by Section 1 (primary goal) and Section 9 (next step must align with user's most recent request)
  • Lost instructions -- prevented by Section 6 (preserve all user instructions)
  • Recap waste -- prevented by the structured format that forces action items over narrative
  • Stale context -- prevented by Section 8 (current state) overriding any narrative from older sections

The summary prompt is the most important prompt in the system that users never see. It determines what the model remembers after compaction. A bad summary prompt produces summaries that lose critical context, causing the model to forget what the user asked for or repeat work that was already completed.

Writing this prompt required the same problem engineering discipline as writing any other specification. The engineers identified the failure modes first (what goes wrong after compaction?), then designed the summary structure to prevent each one.

Key Principles

  1. A well-defined problem is the best prompt. Specify inputs, outputs, constraints, edge cases, failure modes, and non-goals. Each unspecified element is a degree of freedom that the AI fills with an assumption -- and each assumption is a potential bug.

  2. Missing constraints are the most expensive specification gaps. Logic errors are caught by tests. Missing constraints are caught by production failures. A 30-second constraint statement saves hours of debugging.

  3. System prompts are architecture documents. They define identity, capabilities, boundaries, and context. Design them with the same rigor as system architecture. Test them with snapshots. Budget them with token limits.

  4. Position in the system prompt is architecture. Stable blocks go first for cache stability. Moving a section from position 3 to position 8 can change system economics by double-digit percentages.

  5. Token budgets are resource allocation. Every token in the system prompt is processed on every turn. Assign explicit budgets. Truncate to enforce them. Audit for waste.

  6. Assembly must be deterministic. Sort collections, latch flags at session start, avoid live-reading from volatile sources. Non-deterministic assembly produces non-deterministic cache behavior produces unpredictable costs.

  7. Match context lifetime to injection pattern. Permanent context goes in the system prompt (cached). Per-turn context goes in user injections (not cached). Temporary context goes in meta-messages (garbage-collected).

  8. Design compression for the constraint. The 200K context window, with reserves, leaves 160K for conversation. The compression tiers are graduated from cheap (string truncation) to expensive (LLM summarization), ensuring minimal cost for each session's actual pressure.

Think About It

  1. The Specification Audit. Take the last prompt you gave to an AI (or the system prompt of your product). Score it against the seven specification questions: inputs, outputs, constraints, edge cases, failure modes, non-goals, context. How many questions are unanswered? For each unanswered question, identify the assumption the AI would make. Is that assumption correct?

  2. The Cache Stability Exercise. If your system uses a system prompt, map each section to a stability level (static, semi-stable, dynamic). Are they ordered by stability? If not, estimate the cache miss cost of the current ordering versus an optimally ordered prompt.

  3. The Token Budget. Measure your system prompt in tokens. What percentage of the context window does it consume? If you had to cut it in half, what would you remove? That prioritization exercise reveals your implicit value hierarchy -- make it explicit.

  4. The Compression Design. Imagine your context window is 10x smaller (20K tokens instead of 200K). How would you redesign your prompt architecture? What would you cut? What would you compress differently? The answers reveal which parts of your current design are essential and which are luxury.

  5. The Summary Prompt. Write a compaction summary prompt for your system. What 5-9 sections would you request? What failure modes would each section prevent? Test it: summarize a 50-turn conversation with your prompt and evaluate whether the model can continue working correctly from the summary alone.
