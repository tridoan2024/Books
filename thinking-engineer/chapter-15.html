Chapter 15: Concurrency and Coordination

Parallel execution is easy. You call Promise.all(), spawn threads, or fork processes. Any junior engineer can make things run at the same time. The hard part -- the part that separates production systems from demos -- is coordination: making parallel work converge into correct results, handling partial failures, and knowing when parallelism helps versus when it makes everything worse.

This chapter is about thinking concurrently. Not the syntax of async/await or the mechanics of mutexes, but the engineering discipline of decomposing work into parallel streams, designing coordination points, and reasoning about the failure modes that concurrency introduces. The patterns are universal: fork-join, pipeline, event-driven, actor model. The traps are also universal: race conditions, deadlocks, the coordination tax that eats the performance gains you thought you were getting.

We will use Claude Code's multi-agent orchestration as the running case study -- a system where the "threads" are independent AI agents, each with its own context window, tool permissions, and failure modes. The coordination challenges are the same ones you face in any concurrent system: how to dispatch work, how to collect results, how to handle the case where one worker fails while others succeed.

15.1 The Concurrency Decision

The first question is not "how do I parallelize this?" but "should I parallelize this at all?"

Parallelism has costs. Every concurrent operation requires coordination overhead: dispatching work, synchronizing results, handling partial failures. If the overhead exceeds the time saved, parallelism makes your system slower, more complex, and harder to debug -- all at once.

The Break-Even Analysis

Consider a task that takes 100ms sequentially. You split it into two parallel subtasks of 50ms each. Sounds like a 2x speedup. But add the real costs:

Cost Time
Dispatch overhead (spawning, context setup) 5ms
Coordination (collecting results, merging) 10ms
Synchronization (waiting for the slower subtask) varies
Error handling (what if one fails?) complexity, not time

Your "50ms parallel" execution actually takes 65ms (50ms work + 15ms overhead), compared to 100ms sequential. A 35% improvement, not 50%. And you have added error handling complexity that did not exist before.

Now consider the case where the two subtasks are not balanced: one takes 20ms and the other takes 80ms. Your parallel execution takes 95ms (80ms + 15ms overhead). You saved 5ms and added a failure mode. This is worse than not parallelizing.

The break-even rule: parallelism helps when the coordination overhead is small relative to the work, and the work is roughly balanced across workers. Unbalanced parallelism is the most common trap -- you pay the full overhead but only save the difference between the longest and second-longest task.

Claude Code's Decision Framework

When Claude Code encounters a task that could benefit from delegation to subagents, it evaluates five thresholds before spawning parallel work:

flowchart TD
    A[New task identified] --> B{Single tool call?}
    B -->|Yes| C[Execute directly]
    B -->|No| D{Independent of current context?}
    D -->|No| E{Would pollute context?}
    D -->|Yes| F{Can parallelize with other work?}
    E -->|No| C
    E -->|Yes| G[Delegate to subagent]
    F -->|Yes| H[Delegate to parallel subagents]
    F -->|No| I{Exceeds 10 tool calls?}
    I -->|Yes| G
    I -->|No| C

The key insight embedded in this tree: delegation is primarily about context management, not capability. The parent agent could theoretically do everything a subagent does. The value of delegation is keeping the parent's working memory clean, restricting the blast radius of errors, and enabling parallelism for independent analyses.

This is a general principle. In any system, the decision to parallelize should be driven by the characteristics of the work, not by the availability of concurrency primitives. Just because you can run things in parallel does not mean you should.

15.2 The Four Fundamental Patterns

Every concurrent system, regardless of implementation technology, uses one or more of four fundamental patterns. Understanding them as thinking tools -- not just as code patterns -- is the key to designing correct concurrent systems.

Fork-Join

Dispatch N independent tasks. Wait for all to complete. Aggregate results.

graph TB
    D["Dispatch"] --> A1["Worker 1"]
    D --> A2["Worker 2"]
    D --> A3["Worker 3"]

    A1 --> J["Join Point"]
    A2 --> J
    A3 --> J

    J --> S["Aggregate Results"]

    style D fill:#e8f4f8,stroke:#2196F3
    style J fill:#fff3e0,stroke:#FF9800
    style S fill:#e8f5e9,stroke:#4CAF50

Fork-join is the workhorse of concurrent programming. It is appropriate when:

  • All tasks are independent (no data flows between workers)
  • All results are needed before proceeding
  • The tasks are roughly balanced in duration

Claude Code example: When reviewing a pull request, Claude Code spawns a code-reviewer agent and a security-reviewer agent in parallel. Each operates in its own context window with its own system prompt. The parent waits for both to complete, then synthesizes a unified review. The two analyses are independent -- neither needs the other's findings to do its work.

The critical design question: What happens at the join point when one worker fails? Three strategies:

Strategy Behavior When to Use
All-or-nothing Cancel remaining workers if any fails Financial transactions, atomic operations
Collect-all Wait for all, report successes and failures Analysis tasks, reviews
Best-effort Return whatever succeeded Non-critical enrichment, telemetry

Claude Code uses collect-all for PR reviews. If the security review times out, the code review results are still valuable. The parent notes the partial failure: "Security review was incomplete -- agent reviewed 2 of 4 modules."

Pipeline

Output from Stage N becomes input for Stage N+1. Each stage transforms or enriches the data.

graph LR
    S1["Stage 1: Investigate"] -->|"File list"| S2["Stage 2: Analyze"]
    S2 -->|"Root cause"| S3["Stage 3: Fix"]
    S3 -->|"Changes"| S4["Stage 4: Verify"]

Pipelines are sequential by definition -- each stage depends on the previous. The "concurrency" comes from two sources:

  1. Pipelining across items: If you have multiple items to process, Stage 1 can work on item N+1 while Stage 2 works on item N.
  2. Internal parallelism: Each stage can internally parallelize its work.

Claude Code example: Bug fixing follows a pipeline: an explore agent investigates the codebase (cheap, fast, read-only), then a debugger agent analyzes the evidence (expensive, Opus-class reasoning), then a general-purpose agent implements the fix. Each stage's output feeds the next. The explore agent is deliberately cheap -- Haiku or Sonnet model, read-only tools. The debugger is expensive -- Opus model, full bash access. This is the "start cheap, escalate if needed" principle applied to a pipeline.

The critical design question: What happens when a pipeline stage produces empty or invalid output? A robust pipeline validates at each stage boundary. If the explore agent finds nothing relevant, the parent agent does not blindly dispatch the debugger with empty input -- it reports the investigation came up empty.

Event-Driven

Components react to events as they arrive, rather than polling for results.

Event-driven concurrency is appropriate when:

  • The timing of work completion is unpredictable
  • Multiple independent event sources produce work
  • You need responsiveness -- the system should react immediately when something happens, not at the next polling interval

Claude Code example: MCP server connections use event-driven notification handlers. When a connected server changes its tool list, it sends a ToolListChangedNotification. The client reacts immediately -- invalidating tool caches, re-fetching the new tool set, and updating the UI. No polling. No wasted cycles checking "has anything changed?"

// Three notification types, each driving cache invalidation
client.on(ToolListChangedNotification, () => {
  fetchToolsForClient.cache.delete(name);
  refreshTools();
});

client.on(PromptListChangedNotification, () => {
  fetchCommandsForClient.cache.delete(name);
  refreshCommands();
});

client.on(ResourceListChangedNotification, () => {
  fetchResourcesForClient.cache.delete(name);
  refreshResources();
});

The event-driven model composes well with fork-join. When parallel workers complete at different times, the join point can be implemented as an event counter: each completion event increments the counter, and when it reaches N, the aggregation runs.

Actor Model

Independent actors with private state communicate through message passing. No shared memory. No locks.

The actor model is the most restrictive concurrency pattern and the most resistant to bugs. Each actor:

  • Has its own state (no shared mutable data)
  • Processes one message at a time (no internal concurrency)
  • Can send messages to other actors (but not access their state)
  • Can create new actors

Claude Code example: Subagents are actors. Each has its own context window (private state), processes one API call at a time, and communicates with the parent through structured messages. The parent cannot reach into a subagent's context -- it can only send delegation prompts and receive results. The isolation is enforced by the architecture: subagents literally operate in separate API conversations.

    style Agent1 fill:#e8f5e9,stroke:#4CAF50
    style Agent2 fill:#fff3e0,stroke:#FF9800

The actor model's constraints -- no shared state, message-only communication -- eliminate entire categories of concurrency bugs. Race conditions cannot exist when actors do not share memory. Deadlocks cannot exist when there are no locks. The trade-off is performance: message passing is slower than shared memory access. For AI agents, where each "message" is an API call taking seconds, the overhead is irrelevant.

Pattern Comparison

Pattern Communication Failure Handling Best For
Fork-join None between workers Join-point decision Independent parallel work
Pipeline Sequential data flow Stage-boundary validation Dependent multi-step work
Event-driven Asynchronous events Per-event error handlers Reactive, timing-unpredictable work
Actor model Message passing only Actor-level isolation Complex state, strong isolation

Most real systems combine patterns. Claude Code's multi-agent orchestration uses actors (subagents with isolated state), fork-join (parallel dispatch with join-point aggregation), and pipelines (sequential investigation-to-fix chains).

15.3 Race Conditions: When Timing is Destiny

A race condition occurs when the correctness of your system depends on the relative timing of concurrent operations. The operation that "wins the race" determines the result, and different executions can produce different results.

Race conditions are the most common and most insidious concurrency bug. They are common because they arise naturally whenever concurrent operations access shared state. They are insidious because they often work correctly in testing -- the race only manifests under specific timing conditions that are hard to reproduce.

The General Pattern

Every race condition follows the same structure:

  1. Two or more operations access shared state
  2. At least one operation modifies the state
  3. The operations are not synchronized
  4. The outcome depends on which operation executes first

A Concrete Example: Concurrent Compaction

Claude Code's context window management system (discussed in Chapter 9 of this book's companion architecture volume) maintains a compaction state tracker:

@dataclass
class AutoCompactTracking:
    last_token_count: int
    consecutive_failures: int
    last_compact_turn: int
    compaction_in_progress: bool  # The race condition guard

The compaction_in_progress flag exists to prevent a specific race condition: if two concurrent API calls both detect high context pressure, they might both trigger compaction simultaneously. Two concurrent compactions would produce two conflicting summaries, corrupting the conversation state.

Without the flag:

Thread A: checks token count → above threshold → starts compaction
Thread B: checks token count → above threshold → starts compaction
Thread A: completes, replaces messages with summary A
Thread B: completes, replaces messages with summary B (overwrites A)
Result: Summary B is based on pre-compaction messages, not on summary A
         Information from summary A is lost

With the flag:

Thread A: checks token count → above threshold → sets flag → starts compaction
Thread B: checks token count → above threshold → flag is set → skips compaction
Thread A: completes, clears flag
Result: Single compaction, consistent state

The MCP Connection Cache Race

A subtler race condition exists in MCP connection management. When a connection closes, all associated caches must be invalidated:

client.onclose = () => {
  fetchToolsForClient.cache.delete(name);
  fetchResourcesForClient.cache.delete(name);
  fetchCommandsForClient.cache.delete(name);
  connectToServer.cache.delete(key);
};

Without this invalidation, a reconnected client would serve stale tools from the previous connection -- tools whose call() closures reference a dead MCP SDK client instance. The call would either hang (waiting for a response from a dead process) or throw with a confusing error about a closed transport.

The race: if a reconnection starts before all caches are invalidated, the new connection might be served the stale cache. The solution is not more locking -- it is ensuring that cache invalidation runs synchronously on connection close, before any reconnection logic can access the cache.

Thinking About Races

The discipline for preventing race conditions is not "add locks everywhere." It is:

  1. Identify all shared mutable state. Draw a diagram of what state exists and which concurrent operations access it.
  2. For each piece of shared state, determine the invariant. What must always be true? (e.g., "at most one compaction runs at a time")
  3. Ensure the invariant is enforced. Use the simplest mechanism that works: a boolean flag, an atomic operation, a queue, or -- as a last resort -- a lock.
  4. Prefer eliminating shared state over synchronizing access. The actor model's power comes from making shared mutable state impossible, not from managing it carefully.

15.4 The Coordination Tax

Every concurrent system pays a coordination tax: the overhead of dispatching work, synchronizing results, and handling the interactions between concurrent operations. This tax is paid in three currencies.

Time Tax

Coordination takes time. Spawning workers, passing messages, waiting at join points -- all of this adds latency that does not exist in sequential execution.

In Claude Code's multi-agent system, each subagent delegation incurs:

Overhead Time
Delegation prompt construction ~5ms
Subagent context initialization ~50ms
System prompt injection ~20ms
Tool schema filtering ~5ms
Result collection and parsing ~10ms
Total coordination overhead ~90ms

This is dwarfed by the subagent's actual execution time (typically 10-60 seconds). But the overhead exists, and it matters at the margins. If you are delegating a task that takes 200ms, the 90ms coordination overhead makes delegation a bad trade.

Complexity Tax

Concurrent code is harder to reason about than sequential code. Every concurrent operation introduces new failure modes: what if the worker hangs? What if it produces a partial result? What if it succeeds but the parent has already moved on?

The complexity compounds when concurrent operations interact. Consider three parallel subagents reviewing different aspects of a PR. Each might flag the same line of code. The parent must deduplicate findings across agents -- a task that does not exist in sequential execution. The parent must handle the case where one agent's recommendation contradicts another's. The parent must decide what to do when one agent finishes in 10 seconds and another takes 2 minutes.

Token Tax

In AI agent systems, there is a third tax: tokens. Each subagent operates in a fresh context window. It must re-read files the parent already read. It must re-establish context that the parent already has. A subagent reviewing auth.ts does not know that the parent already read auth.ts and identified the relevant functions -- it must discover this independently.

Claude Code mitigates this through context stripping -- subagents skip CLAUDE.md, memory entries, skill prompts, and most project context. The parent digests project context and passes only what the subagent needs in the delegation prompt. This saves 500-2,000 tokens per subagent invocation. Over a session with 10 delegations, that is 5,000-20,000 tokens saved.

But the fundamental tax remains: isolated workers duplicate discovery. The trade-off is worth it when the alternatives -- shared context that enables pollution and prompt injection -- are worse. As discussed in Chapter 12 of this book, the defender's asymmetry means that correctness and security constraints often dominate performance considerations.

15.5 When Parallelism Hurts

The most important concurrency skill is knowing when not to parallelize. Three scenarios consistently produce worse outcomes with parallelism than without.

Scenario 1: Sequential Dependencies Disguised as Parallel Tasks

A developer looks at a workflow -- investigate, analyze, fix, test -- and says "let's run investigate and analyze in parallel." The problem: analyze depends on investigate's output. Running them in parallel means the analyzer starts with no information and wastes its early work discovering what the investigator already knows.

Claude Code's delegation decision tree explicitly checks for this: "Independent of current context?" If the answer is no -- if the task needs information that only the current conversation has -- delegation loses more than it gains.

The engineering heuristic: if you must include more than 2 paragraphs of context in the delegation prompt to make the subtask self-contained, the task is probably not independent enough for parallel execution.

Scenario 2: Resource Contention

Parallel tasks that compete for the same resource can actually serialize themselves through contention, producing worse throughput than sequential execution.

Claude Code encounters this with local MCP server spawning. Each stdio MCP server requires spawning a subprocess, which involves process creation, file descriptor allocation, and environment setup. Spawning 20 servers simultaneously overwhelms the OS process table. The solution: batch local server connections at 3 concurrently, while remote HTTP connections (which are cheap) batch at 20.

await Promise.all([
  processBatched(localServers, 3, processServer),    // Subprocess-heavy
  processBatched(remoteServers, 20, processServer),  // Network I/O only
]);

The batching numbers were determined empirically. The general principle: match concurrency to resource constraints, not to task count. Having 100 tasks does not mean you should run 100 in parallel.

Scenario 3: The Thundering Herd

When multiple workers wake up simultaneously in response to the same event, they stampede through the same critical section. Classic examples: cache invalidation causing all workers to regenerate the cache, all reconnection timers firing at once after a network outage.

Claude Code's MCP reconnection uses exponential backoff (1s, 2s, 4s, 8s, 16s, capped at 30s) specifically to prevent thundering herds. If 10 MCP servers disconnect simultaneously, staggered backoff ensures they do not all reconnect at the same time and overwhelm the authentication service.

15.6 The Principle of Least Authority for Delegated Work

When you dispatch work to a concurrent worker, the worker should have exactly the tools and permissions it needs -- no more. This is the principle of least authority (POLA), adapted from security to concurrency.

POLA is not just a security principle. It is a correctness principle. A worker with access to tools it does not need will occasionally use them. A code-review agent with write access will sometimes "helpfully" fix the issues it finds, corrupting the review's objectivity. A research agent with bash access might try to install packages instead of reporting findings.

Claude Code enforces POLA through three layers of defense:

graph TB
    subgraph Layer1["Layer 1: System Prompt"]
        SP["Role definition:<br/>'You are a read-only reviewer.<br/>You will NOT modify code.'"]
    end

    subgraph Layer2["Layer 2: Tool Schema"]
        TS["Tool allowlist:<br/>Only Read, Grep, Glob available.<br/>Write, Bash not in schema."]
    end

    subgraph Layer3["Layer 3: Permission Rules"]
        PR["Runtime enforcement:<br/>Even if tool is somehow called,<br/>permission system blocks it."]
    end

    Layer1 --> Layer2 --> Layer3

    style Layer1 fill:#e8f4f8,stroke:#2196F3
    style Layer2 fill:#e8f5e9,stroke:#4CAF50
    style Layer3 fill:#fff3e0,stroke:#FF9800

Layer 1 (System Prompt) is a soft constraint -- the model might ignore it. But it handles 95% of cases.

Layer 2 (Tool Schema) is a hard constraint at the API level. If the Write tool is not in the schema, the model cannot generate a valid tool-use request for it. The model literally does not know the tool exists.

Layer 3 (Permission Rules) catches anything that slips through Layers 1 and 2. Even if a tool is in the schema (because the agent type needs limited bash access), the permission rules can restrict which specific commands are allowed.

The result is a taxonomy of agent types, each with a different authority profile:

Agent Type Read Write Bash Web Typical Use
explore Yes No Read-only No Fast codebase investigation
code-reviewer Yes No No No Code quality review
security-reviewer Yes No Analysis only No Security audit
debugger Yes No Yes No Root cause analysis
researcher Yes No No Yes Information synthesis
doc-writer Yes Yes (docs only) No No Documentation
general-purpose Yes Yes Yes Yes Full autonomy

The general-purpose agent is the only type that can itself spawn subagents. This enables hierarchical delegation -- but also enables exponential cost growth. Which brings us to the next section.

15.7 Error Propagation Across Boundaries

In sequential code, error propagation is simple: an exception bubbles up the call stack. In concurrent code, errors propagate across boundaries -- from worker to coordinator, from subagent to parent. The boundary crossing makes error handling fundamentally different.

The Five Failure Modes

Every delegated concurrent task can fail in five ways:

Failure Mode Cause Is Result Usable?
Timeout Worker exceeded time/turn limit Partial (what it produced before timeout)
Infrastructure error Network failure, API error No
Resource exhaustion Context window full, memory exhausted Partial (what fit)
Tool error Individual operation failed Depends (usually recoverable)
Wrong answer Worker completed but produced garbage No (but looks like success)

The last failure mode -- "wrong answer" -- is the most dangerous because it is undetectable at the coordination level. The worker reports success. The result looks plausible. But it is wrong. In AI agent systems, this manifests as a subagent confidently reporting findings about the wrong file, or summarizing a function incorrectly.

The only defense against wrong answers is validation at the join point. The parent agent must critically evaluate subagent results, not blindly incorporate them. This is why Claude Code's parent agent acts as a synthesizer, not a pass-through: it reads all results, checks for consistency, and applies its own judgment before presenting to the user.

The Collect-All-Report-All Strategy

When multiple workers run in parallel, the recommended error handling strategy is collect-all, report-all:

  1. Dispatch all workers
  2. Wait for all to complete (success, failure, or timeout)
  3. Collect all results and errors
  4. Synthesize a response that includes successful results and notes failures

This is simpler and more robust than selective cancellation. Cancellation introduces race conditions (the cancellation message might arrive after the worker finishes), and partial results from a "failed" worker might still be valuable.

PR Review Results:
- Code Quality: 3 issues found (completed)
- Security: Review incomplete -- agent timed out after reviewing
  2 of 4 modules. Partial findings: 1 critical vulnerability.
- Test Coverage: 72% (completed)

The user gets maximum information. Successful analyses are presented in full. Failed analyses are transparently reported with whatever partial results exist. The alternative -- silently dropping the failed analysis and presenting incomplete results as complete -- is worse in every way.

15.8 Orchestration Design

Designing a concurrent system is designing its orchestration: who dispatches work, who collects results, who makes decisions about failures and retries. The orchestration design determines whether your concurrent system is manageable or chaotic.

The Coordinator Pattern

Every concurrent system needs a coordinator -- the entity responsible for:

  1. Dispatching work -- deciding what runs in parallel and what runs sequentially
  2. Tracking state -- knowing which workers are running, completed, or failed
  3. Handling failures -- deciding whether to retry, skip, or abort
  4. Aggregating results -- combining worker outputs into a coherent response

In Claude Code, the parent agent is the coordinator. It maintains an agent tracker for each dispatched subagent:

Agent Tracker:
  agent_id: "sr-abc123"
  type: security-reviewer
  status: running | completed | failed
  turns_used: 12 / 25 max
  result: null | ResultMessage
  error: null | ErrorInfo

The tracker enables timeout management: each agent type has a default turn limit, and the dispatch layer enforces wall-clock timeouts as a safety net. An agent still running after 5 minutes is terminated regardless of its turn count.

Depth Limits

When the coordinator can itself be a worker (a general-purpose subagent can spawn its own subagents), you need depth limits. Without them:

Level 0: Parent spawns 3 agents           →  3 agents
Level 1: Each spawns 3 more              →  9 agents  
Level 2: Each spawns 3 more              →  27 agents
Level 3: Each spawns 3 more              →  81 agents
Total: 120 agents, exponential cost

Claude Code enforces a maximum delegation depth of 2-3 levels. The key insight: only general-purpose agents should be allowed to delegate further. Specialist agents (explore, security-reviewer, code-reviewer) focus on their task. Restricting delegation rights is another application of the principle of least authority.

Cost-Aware Orchestration

In AI agent systems, every concurrent operation has a direct financial cost. The orchestrator must track and manage this cost:

Budget Level Enforcement
Per-agent token limit Agent terminated when limit reached
Per-session cost limit New delegations blocked when budget exhausted
Per-model cost limit Expensive models restricted after threshold

The optimization strategy: start cheap, escalate if needed. Try an explore agent (Haiku model, fast, cheap) first. If the result is insufficient, retry with a debugger (Opus model, deep reasoning, expensive). This avoids paying Opus prices for tasks that Haiku can handle. The cost difference is 50x -- a security review on Opus might cost $2.06, while the same task on Haiku costs $0.03.

15.9 The Sync Point: Where Concurrent Meets Sequential

The most critical design decision in any concurrent system is where to place the sync points -- the moments where parallel work converges and sequential logic takes over.

Claude Code's startup pipeline illustrates this perfectly. Three I/O operations start as fire-and-forget async calls:

gantt
    title Startup Timeline (400ms)
    dateFormat X
    axisFormat %Lms

    section Async I/O
    MDM subprocess         :active, mdm, 0, 20
    Keychain read          :active, kc, 0, 30

    section Synchronous
    Entry point            :crit, entry, 0, 2
    Module evaluation      :crit, eval, 2, 137
    CLI parsing            :crit, parse, 137, 140
    preAction rendezvous   :crit, pre, 140, 145

    section Rendezvous
    MDM await (resolved)   :milestone, m1, 140, 140
    Keychain await         :milestone, m2, 140, 140

The sync point is the preAction hook at the 140ms mark. By this point, the MDM subprocess (20ms) and keychain reads (30ms) have had 140ms to complete. The await resolves in <1ms -- the promises are already settled.

The design principle: place sync points as late as possible. Earlier sync points reduce the overlap window. If the rendezvous were at the 2ms mark (before the module import), the prefetches would have had 0ms to complete. At the 140ms mark, they get 140ms -- 7x more than they need. This margin absorbs variance: if the keychain read occasionally takes 80ms instead of 30ms, the sync point still works.

This is a universal pattern called speculative prefetch: start I/O operations whose results you will need later, then do unrelated synchronous work while the I/O completes. When you finally need the results, they are already waiting in resolved promises. The pattern applies to any system with known-upcoming I/O needs.

15.10 Case Study: Claude Code's Multi-Agent Orchestration

Let us trace through a complete multi-agent workflow to see how the patterns from this chapter combine in practice.

A user asks: "Review PR #42 -- check code quality and security."

Phase 1: Decomposition

The parent agent decomposes the request into independent subtasks:

  1. Code quality review (code-reviewer agent, Sonnet model, read-only tools)
  2. Security review (security-reviewer agent, Opus model, read + analysis bash)

These are independent: neither needs the other's findings. Fork-join is the correct pattern.

Phase 2: Dispatch

The parent constructs delegation prompts for each agent. Each prompt contains:

  • Task description: Self-contained, because the subagent has no access to the parent's conversation
  • Relevant context: Files changed in the PR, key observations from the parent's initial scan
  • Output format: Structured table with severity, location, and fix recommendation
  • Priority: What to focus on (security focuses on OWASP Top 10; code quality focuses on logic errors)

Both agents are dispatched in parallel. Each gets a fresh context window, a specialized system prompt, and a restricted tool set.

Phase 3: Parallel Execution

Both agents work simultaneously:

sequenceDiagram
    participant P as Parent Agent
    participant CR as Code Reviewer (Sonnet)
    participant SR as Security Reviewer (Opus)

    P->>CR: Delegate: "Review code quality of PR #42..."
    P->>SR: Delegate: "Audit PR #42 for OWASP vulnerabilities..."

    par Code Review
        CR->>CR: Read changed files (turns 1-3)
        CR->>CR: Analyze patterns (turns 4-8)
        CR->>CR: Format findings (turn 9)
    and Security Review
        SR->>SR: Read changed files (turns 1-4)
        SR->>SR: Check injection vectors (turns 5-10)
        SR->>SR: Check auth bypass (turns 11-15)
        SR->>SR: Format findings (turn 16)
    end

    CR-->>P: "3 issues: 1 HIGH, 2 MEDIUM"
    SR-->>P: "2 findings: 1 CRITICAL, 1 HIGH"

    P->>P: Synthesize unified review

Phase 4: Aggregation

The parent receives both results and performs synthesis -- not just concatenation:

  1. Deduplication: Both agents flagged the same unvalidated input on line 42 of auth.ts. The parent merges the duplicate, keeping the security reviewer's more detailed analysis.
  2. Prioritization: The security reviewer's CRITICAL finding (JWT key without rotation) is promoted above all code quality issues.
  3. Conflict resolution: The code reviewer suggested inlining a validation function for readability. The security reviewer flagged the same function as needing additional checks. The parent reconciles: keep the function, add the security checks.
  4. Summary: A 30-second executive summary followed by the detailed findings.

What Makes This Work

The entire orchestration rests on three design decisions:

  1. Context isolation prevents pollution. The security reviewer's analysis of attack vectors does not clutter the code reviewer's context (or vice versa).
  2. Least authority prevents interference. The code reviewer cannot modify files. The security reviewer cannot install packages. Each does exactly its job.
  3. Structured output enables aggregation. Both agents produce tables with the same schema (severity, location, finding, fix), making deduplication and prioritization mechanical rather than interpretive.

Key Principles

The Concurrency Decision Rule: Parallelism helps when coordination overhead is small relative to the work, and the work is roughly balanced across workers. Unbalanced parallelism wastes the overhead without meaningful speedup.

Isolation Over Synchronization: Prefer designs that eliminate shared state (actors, fresh contexts) over designs that synchronize access to shared state (locks, flags). Isolation makes race conditions structurally impossible.

Collect All, Report All: When parallel workers fail, do not silently drop results. Collect everything -- successes and failures -- and present a transparent report. Partial results with explicit caveats are more valuable than complete-looking results with hidden gaps.

Least Authority for Workers: Give each concurrent worker exactly the tools and permissions it needs. Over-provisioned workers produce unpredictable behavior. Three layers of restriction (prompt, schema, runtime) provide defense in depth.

Sync Points as Late as Possible: The later the synchronization, the more overlap you get between async operations and synchronous work. Place rendezvous points at the latest moment that still provides the data you need.

Depth Limits for Recursive Delegation: When workers can spawn workers, enforce maximum depth. Without limits, delegation trees grow exponentially in both cost and complexity.

Think About It

  1. The Ordering Problem: You have five analysis tasks for a deployment check: dependency audit, secret scan, test suite, lint check, and build verification. Some take 5 seconds, others take 60 seconds. Design the concurrency strategy. Which tasks run in parallel? Are there dependencies? Where are the sync points? What is the expected wall-clock time versus the sequential time?

  2. The Partial Failure Decision: Your system dispatches three parallel workers for a critical analysis. Worker A completes successfully with useful findings. Worker B times out with 60% completion. Worker C fails with an infrastructure error. Design the aggregation strategy. Do you present Worker A's results immediately or wait for B's partial results? How do you communicate the gaps to the user? Would your strategy change if this were a financial transaction instead of an analysis?

  3. The Contention Trap: You are building a system that processes incoming events by spawning a worker for each. Under normal load (10 events/second), each worker takes 100ms. But each worker reads from a shared database, and under high load (100 events/second), database contention causes each worker to take 500ms. Design a system that handles both loads gracefully. What concurrency limit do you set? How do you detect and respond to contention?

  4. The Isolation Cost: In Claude Code's subagent model, each subagent re-reads files that the parent already read, costing extra tokens. Design an alternative that shares file read results between agents without sharing their full contexts. What are the security implications? What if a shared file read was corrupted by a prompt injection -- how would isolation have protected you?

  5. The Coordinator Bottleneck: In a hierarchical delegation with 3 levels and 3 agents per level, the top-level coordinator must manage 3 direct reports, each of which manages 3 more. Design the communication protocol. How does a Level 2 failure propagate to Level 0? Should Level 0 receive intermediate status updates, or only final results? At what point does the coordination overhead exceed the value of parallelism?
