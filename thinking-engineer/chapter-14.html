Chapter 14: State Machines Everywhere

Most bugs are state bugs. Not off-by-one errors, not null pointer dereferences, not syntax mistakes — state bugs. A variable that should be true is false. A connection that should be open is closing. A session that should be active is paused but the UI thinks it is running. Two fields that must change together get updated one at a time, and another thread reads the intermediate state.

State bugs are the hardest to reproduce, the hardest to diagnose, and the hardest to fix, because the system's behavior depends not on what it is doing now but on everything it has done before. The current state is the accumulation of every transition since initialization. When the state is wrong, you must trace backward through every transition to find the one that went astray.

Explicit state machines eliminate entire categories of these bugs. When you model your system as a finite set of states with defined transitions between them, three things happen: illegal states become unrepresentable, invalid transitions become compile-time errors, and the system's behavior becomes a diagram you can stare at on a whiteboard. Claude Code models its streaming pipeline, session lifecycle, and permission resolution as explicit state machines. The bugs they prevent are the bugs you never see — and never have to debug at 2 AM.

The Cost of Implicit State

Before we discuss explicit state machines, consider what happens without them. Implicit state is state that exists in the code but has no formal model — it lives in boolean flags, enum-like strings, and conditional chains that implicitly encode what the system is "doing."

Here is an implicit state model for a streaming connection:

// Implicit state — scattered across variables
let isConnected = false
let isStreaming = false
let hasError = false
let isRetrying = false
let buffer: string[] = []

This looks reasonable. Five booleans, a buffer. But how many states can this represent? Five booleans give 2^5 = 32 possible combinations. How many of those combinations are valid?

  • isConnected=false, isStreaming=true: Streaming without a connection? Invalid.
  • isRetrying=true, isStreaming=true: Retrying and streaming simultaneously? Invalid.
  • hasError=true, isConnected=true, isStreaming=true: Error but still connected and streaming? Maybe valid — depends on the error type.
  • isConnected=true, isStreaming=false, isRetrying=true: Connected but retrying? Invalid.

Of 32 possible states, perhaps 6-8 are valid. The other 24-26 are illegal states that the code does not prevent. Every bug in this system is a path that reaches one of those illegal states. And every if statement that checks these flags is an implicit transition that may or may not maintain the invariants.

Now count the transitions. With 5 booleans, each of which can be set or cleared independently, there are 10 possible mutations per step. With 8 valid states and 10 mutations, you have 80 possible transitions — most of which are invalid but not prevented.

This combinatorial explosion is why implicit state produces bugs. The developer cannot hold 80 transitions in their head. They write code that handles the common paths and hope the uncommon ones never happen.

The Explicit State Machine

An explicit state machine replaces scattered booleans with a single state variable and a defined transition table. Here is the same streaming connection modeled explicitly:

type StreamState =
  | 'Idle'
  | 'Connecting'
  | 'Streaming'
  | 'Error'
  | 'Recovering'
  | 'Done'

type StreamEvent =
  | { type: 'connect' }
  | { type: 'message_start' }
  | { type: 'data'; payload: string }
  | { type: 'disconnect' }
  | { type: 'error'; error: Error }
  | { type: 'retry' }
  | { type: 'complete' }

function transition(state: StreamState, event: StreamEvent): StreamState {
  switch (state) {
    case 'Idle':
      if (event.type === 'connect') return 'Connecting'
      break
    case 'Connecting':
      if (event.type === 'message_start') return 'Streaming'
      if (event.type === 'error') return 'Error'
      break
    case 'Streaming':
      if (event.type === 'data') return 'Streaming' // self-transition
      if (event.type === 'disconnect') return 'Error'
      if (event.type === 'complete') return 'Done'
      break
    case 'Error':
      if (event.type === 'retry') return 'Recovering'
      break
    case 'Recovering':
      if (event.type === 'connect') return 'Connecting'
      if (event.type === 'error') return 'Error'
      break
    case 'Done':
      break // terminal state — no transitions
  }
  throw new InvalidTransitionError(state, event)
}

Count the differences from the implicit model:

  1. 6 states instead of 32. Every state is named and meaningful. There is no combination like "connected but not streaming but retrying."

  2. 13 transitions instead of 80. Every valid transition is listed explicitly. Everything else throws an error.

  3. One variable instead of five. The current state is a single discriminated value. There is no way to have inconsistent flags.

  4. The transition function is the specification. Reading the switch statement tells you exactly what the system can do from any state. No hunting through scattered if chains to reconstruct the state model.

Visualizing the Machine

The transition function can be rendered as a diagram — and it should be. State diagrams are the most effective specification format for stateful systems because they show both the states and the transitions in a single visual:

stateDiagram-v2
    [*] --> Idle
    Idle --> Connecting : connect
    Connecting --> Streaming : message_start
    Connecting --> Error : error
    Streaming --> Streaming : data
    Streaming --> Error : disconnect
    Streaming --> Done : complete
    Error --> Recovering : retry
    Recovering --> Connecting : connect
    Recovering --> Error : error
    Done --> [*]

This diagram is the design. Not a documentation artifact generated after the code was written — the design that precedes the code. When a new requirement arrives ("support pause/resume"), you add states and transitions to the diagram first, then update the transition function.

Making Illegal States Unrepresentable

The most powerful technique in state machine design is ensuring that invalid states cannot exist at all — not that they are checked at runtime, but that the type system prevents them from being constructed.

The Boolean Trap

Consider a session with three properties: whether the user has authenticated, whether the session has a valid token, and whether the session is active. The boolean representation:

interface Session {
  isAuthenticated: boolean
  hasValidToken: boolean
  isActive: boolean
}

This allows { isAuthenticated: false, hasValidToken: true, isActive: true } — an active session with a valid token but unauthenticated? That should never happen. But the type system permits it.

The Discriminated Union Solution

Replace the booleans with a discriminated union that only contains valid combinations:

type Session =
  | { state: 'anonymous' }
  | { state: 'authenticating'; challenge: Challenge }
  | { state: 'active'; token: Token; user: User }
  | { state: 'expired'; lastToken: Token; user: User }
  | { state: 'terminated'; reason: string }

Now the token field only exists when the session is active. The user field only exists when the session is active or expired. The challenge field only exists during authenticating. There is no combination of fields that represents an illegal state because each state variant declares exactly which fields exist.

This is what "making illegal states unrepresentable" means in practice. It is not a runtime check ("assert that if isAuthenticated is false then hasValidToken is also false"). It is a compile-time guarantee: the type Session cannot hold an illegal combination.

Claude Code's Session State

Claude Code's session lifecycle (as discussed in Chapter 6's source material) uses this pattern. The session is not a bag of booleans (isCreating, isActive, isPaused, isShuttingDown). It is a discriminated state with explicit transitions:

stateDiagram-v2
    [*] --> Creating : claude invoked

    Creating --> Initializing : UUID generated, transcript opened
    Initializing --> TrustCheck : Config loaded, auth resolved

    TrustCheck --> Active : Directory trusted
    TrustCheck --> Restricted : Trust declined

    Active --> Active : User prompts, tool calls, responses
    Restricted --> Restricted : Limited functionality

    Active --> Resuming : --resume invoked
    Resuming --> Active : Transcript replayed

    Active --> Switching : switchSession() called
    Switching --> Active : New session + project dir

    Active --> Compacting : Context window full
    Compacting --> Active : Conversation summarized

    Active --> ShuttingDown : User exits
    Active --> Crashed : Unexpected termination

    ShuttingDown --> Ended : Cleanup complete
    Crashed --> Ended : No cleanup

    Ended --> Resuming : claude --resume
    Ended --> [*] : No resume

    Restricted --> ShuttingDown : User exits

Each state carries specific data. The Active state has a conversation history, a cost accumulator, and a transcript path. The Resuming state has the session ID being resumed and the transcript being replayed. The Crashed state has no cleanup data — that is the point; cleanup did not happen.

The transition from Active to Switching uses the Atomic Switch Pattern — a single function that updates both sessionId and sessionProjectDir together, with no separate setters exposed. This prevents the invariant violation where one field is updated but the other is not.

State Transition Diagrams as Design Tools

State diagrams are not just documentation. They are design tools that reveal problems before code is written.

Finding Missing Transitions

Draw the state diagram for your system. Then ask for every state: "What happens if [unexpected event] occurs while in this state?" The diagram makes missing transitions visible.

Example: In the streaming state machine, what happens if a disconnect event occurs during the Recovering state? If the diagram does not show this transition, the code probably does not handle it either. Adding the transition to the diagram (Recovering → Error on disconnect) makes the code fix obvious.

Finding Unreachable States

A state with no incoming transitions (except from the initial state) is either the initial state or a dead state that can never be reached. A state with no outgoing transitions is a terminal state — which may be intentional (Done) or a design bug (the system gets stuck).

Walk the diagram from the initial state. Every state should be reachable through some sequence of events. Every non-terminal state should have at least one outgoing transition. Violations indicate either a design error or an unnecessary state that should be removed.

Finding Missing States

The most valuable insight from state diagrams: discovering states that the system implicitly enters but has not formally defined.

In Claude Code's session lifecycle, the Compacting state was not in the original design. Sessions went from Active to Active when compaction happened — it was treated as an operation within the active state. But compaction temporarily changes the session's behavior: new messages cannot be added while compaction is in progress, the model sees a different conversation history (the summary), and certain operations (like session resume) must wait for compaction to complete.

Making Compacting an explicit state with explicit transitions (Active → Compacting on context pressure, Compacting → Active when summarization completes) made these constraints visible and enforceable. Without the explicit state, the code used a boolean flag (isCompacting) that created the same scattered-boolean problems described earlier.

Event Sourcing and State Reconstruction

An event-sourced system stores the sequence of events that caused state transitions, rather than the current state itself. The current state is reconstructed by replaying the event sequence. This pattern has a natural relationship with state machines: the events are the transition triggers, and replaying them walks the state machine from its initial state to the current state.

The JSONL Transcript as Event Log

Claude Code's session transcript is an event log. Every conversation message, tool call, tool result, and state change is recorded as a JSONL entry with a timestamp:

{"type":"session_start","sessionId":"abc-123","timestamp":1712956800000,"cwd":"/project"}
{"type":"message","role":"user","content":"Fix the login bug","timestamp":1712956801000}
{"type":"tool_use","name":"Read","input":{"path":"auth.ts"},"timestamp":1712956802000}
{"type":"tool_result","toolUseId":"tu_01","output":"...","timestamp":1712956803000}
{"type":"message","role":"assistant","content":"Found the issue...","timestamp":1712956810000}
{"type":"session_end","timestamp":1712957000000,"totalCost":0.42,"reason":"user_exit"}

This event log enables session resume. When the user runs claude --resume, the system reads the transcript line by line, reconstructs the conversation history, recomputes accumulated metrics (cost, token counts), and continues from where it left off.

The reconstruction is a state machine replay:

function reconstructSession(transcript: TranscriptEntry[]): SessionState {
  let state: SessionState = initialState()

  for (const entry of transcript) {
    state = applyEvent(state, entry)
  }

  return state
}

function applyEvent(state: SessionState, entry: TranscriptEntry): SessionState {
  switch (entry.type) {
    case 'session_start':
      return { ...state, sessionId: entry.sessionId, cwd: entry.cwd }
    case 'message':
      return {
        ...state,
        messages: [...state.messages, entry],
        messageCount: state.messageCount + 1,
      }
    case 'tool_use':
      return {
        ...state,
        pendingToolCalls: [...state.pendingToolCalls, entry],
      }
    case 'tool_result':
      return {
        ...state,
        pendingToolCalls: state.pendingToolCalls.filter(
          t => t.id !== entry.toolUseId
        ),
        toolResults: [...state.toolResults, entry],
      }
    case 'session_end':
      return { ...state, totalCost: entry.totalCost, ended: true }
  }
}

Why Event Sourcing Over State Snapshots

The alternative to event sourcing is state snapshots — periodically saving the current state to disk. Claude Code's designers chose event sourcing (the JSONL transcript) for three reasons:

Crash safety. Each JSONL entry is an atomic append — if the process crashes mid-write, at most one line is corrupted. All previous entries survive. A state snapshot that corrupts mid-write can lose the entire session.

Auditability. The event log answers "what happened" — not just "what is the current state" but "how did we get here." When debugging a session, the transcript shows every tool call, every response, every state change in chronological order. A state snapshot shows only the end result.

Cheap writes. Appending a single line to a file is O(1) regardless of file size. Writing a full state snapshot is O(n) in the state size, which grows throughout the session.

The tradeoff: reconstruction is O(n) in the event count. Resuming a long session (thousands of events) takes measurable time. Claude Code accepts this tradeoff because resume is infrequent (once per session at most) while writes are constant (every message, every tool call).

The Dual Write Pattern

In practice, Claude Code uses a hybrid approach. The transcript is the source of truth (event sourcing), but the in-memory state is the working copy (state snapshot). Writes go to both:

Event occurs
  ├── Update in-memory state (fast, used for all operations)
  └── Append to transcript file (durable, used for recovery)

This dual write means the in-memory state can drift from the transcript if a write fails. The recovery strategy is to trust the transcript: if the process crashes and restarts, the in-memory state is rebuilt from the transcript, not from a cached snapshot.

Coupled State: The Atomic Switch Pattern

The most dangerous state bugs occur when two fields must change together but can be observed in an intermediate state where one has changed and the other has not.

The Problem

Claude Code's session has two fields that are semantically coupled: sessionId (which session this is) and sessionProjectDir (which project directory this session belongs to). These fields determine where the transcript file is stored:

~/.claude/projects/{hash(sessionProjectDir)}/sessions/{sessionId}.jsonl

If sessionId changes but sessionProjectDir does not, the system looks for the transcript in the wrong directory. If sessionProjectDir changes but sessionId does not, it stores new entries in the wrong project's session list.

With separate setters, this race is trivial to introduce:

// DANGEROUS: Non-atomic update
setSessionId(newId)
// <-- Other code reads sessionId here
//     but sessionProjectDir still points to old directory
//     → reads wrong transcript → corrupt state
setSessionProjectDir(newDir)

The Solution

Expose a single function that updates both fields. Do not expose individual setters:

function switchSession(
  sessionId: SessionId,
  projectDir: string | null = null,
): void {
  // 1. Clean up outgoing session
  STATE.planSlugCache.delete(STATE.sessionId)

  // 2. Atomically update both fields
  STATE.sessionId = sessionId
  STATE.sessionProjectDir = projectDir

  // 3. Notify listeners
  sessionSwitched.emit(sessionId)
}

There is no setSessionId(). There is no setSessionProjectDir(). The only way to change either field is through switchSession(). This is not a convention documented in a style guide. It is a structural constraint: the setter functions do not exist, so they cannot be called.

Generalizing the Pattern

The Atomic Switch Pattern applies whenever you have coupled state — fields that must maintain a mutual invariant:

Coupled Fields Invariant Atomic Function
sessionId + projectDir Point to same session switchSession()
userId + permissions Permissions belong to user switchUser()
host + port Form a valid endpoint setEndpoint(host, port)
minValue + maxValue min <= max setRange(min, max)
width + height Maintain aspect ratio resize(w, h)

The implementation pattern is always the same:

  1. Identify the invariant between the fields.
  2. Create a single function that updates all fields.
  3. Remove individual setters (or make them private).
  4. Emit a signal so observers react to the change as a unit.

Guard Transitions, Not States

A common mistake with state machines is putting validation logic in the wrong place. Engineers check "am I in state X?" before performing an action. The correct approach is to guard the transition, not the state.

Wrong: Guarding the State

function processMessage(msg: Message) {
  if (state !== 'Active') {
    throw new Error('Cannot process messages when not active')
  }
  // process the message
}

This check is scattered everywhere that messages are processed. Every call site must remember to check the state. Missing one check means processing a message in an invalid state.

Right: Guarding the Transition

function transition(current: State, event: Event): State {
  const allowed = TRANSITION_TABLE[current]
  const next = allowed?.[event.type]

  if (!next) {
    throw new InvalidTransitionError(current, event)
  }

  return next
}

The transition function is the single point of control. It does not matter who calls it or from where — invalid transitions are rejected at the gate. There is no way to reach state Processing from state Idle without going through the transition function, which enforces the valid transition path (Idle → Active → Processing).

This centralization has a second benefit: logging. Every transition can be logged in one place:

function transition(current: State, event: Event): State {
  const next = TRANSITION_TABLE[current]?.[event.type]

  if (!next) {
    log.warn('invalid_transition', { current, event })
    return current // graceful degradation
  }

  log.info('state_transition', { from: current, to: next, event: event.type })
  return next
}

This log is invaluable for debugging. When a system is in an unexpected state, the transition log shows exactly how it got there — every event that triggered every transition, in order.

Graceful Degradation in State Machines

Production systems must decide what to do when an invalid transition is attempted. Two strategies:

Strict: Throw on Invalid Transitions

if (!next) {
  throw new InvalidTransitionError(current, event)
}

Use strict mode during development and testing. Invalid transitions are bugs — they should fail loudly so they are found and fixed. A state machine that silently accepts invalid transitions provides no guarantees.

Lenient: Ignore Invalid Transitions

if (!next) {
  log.warn('unknown_transition', { current, event })
  return current // stay in current state
}

Use lenient mode in production for forward compatibility. Claude Code's streaming state machine uses lenient mode because the API server may introduce new event types in future versions. A strict state machine would crash on new_event_type; a lenient one ignores it and continues working.

The choice depends on the source of invalid transitions:

Source Strategy Reasoning
Internal code bug Strict (throw) Bugs should be caught, not hidden
External protocol evolution Lenient (ignore) New events should not crash old clients
User input Lenient (reject with message) Users should not crash the system
Race conditions Lenient (log and continue) Races are transient; crashing makes them permanent

Hybrid: Strict Internally, Lenient Externally

The best approach is a hybrid: strict validation for internally generated events (where invalid transitions are definitely bugs) and lenient validation for externally generated events (where invalid transitions may be protocol evolution or network artifacts).

Claude Code's streaming pipeline applies this: if the internal code attempts an invalid transition (e.g., emitting a text_delta event while processing a tool-use block), it throws. If the external SSE stream delivers an unknown event type, it logs and ignores.

Hierarchical State Machines

Simple state machines have flat states. But real systems have states within states — an Active session contains sub-states like Idle, Processing, WaitingForTool. Hierarchical state machines (also called statecharts) model this nesting.

The Nesting Problem

Consider Claude Code's active session. Within the Active state, the system cycles through a sub-machine:

stateDiagram-v2
    state Active {
        [*] --> WaitingForInput
        WaitingForInput --> SendingToAPI : user submits prompt
        SendingToAPI --> Streaming : first token arrives
        Streaming --> ProcessingTools : tool_use detected
        ProcessingTools --> SendingToAPI : tool results ready
        Streaming --> WaitingForInput : response complete
        ProcessingTools --> WaitingForInput : response complete
    }

    state Streaming {
        [*] --> InTextBlock
        InTextBlock --> InTextBlock : text_delta
        InTextBlock --> BetweenBlocks : content_block_stop
        BetweenBlocks --> InToolBlock : content_block_start(tool_use)
        BetweenBlocks --> InTextBlock : content_block_start(text)
        BetweenBlocks --> InThinkingBlock : content_block_start(thinking)
        InToolBlock --> InToolBlock : input_json_delta
        InToolBlock --> BetweenBlocks : content_block_stop
        InThinkingBlock --> InThinkingBlock : thinking_delta
        InThinkingBlock --> BetweenBlocks : content_block_stop
    }

The Streaming state itself contains a sub-machine with its own states (InTextBlock, InToolBlock, InThinkingBlock, BetweenBlocks). Events like Disconnect at the outer level apply regardless of which inner state the streaming sub-machine is in — the entire Streaming state transitions to Error, taking the sub-machine with it.

Benefits of Hierarchy

Shared transitions. The Active → ShuttingDown transition applies regardless of the inner state. Without hierarchy, you would need separate transitions: WaitingForInput → ShuttingDown, SendingToAPI → ShuttingDown, Streaming → ShuttingDown, ProcessingTools → ShuttingDown. Four transitions encoding the same logic.

Encapsulation. The streaming sub-machine's internal states (InTextBlock, InToolBlock) are invisible to the outer machine. The outer machine knows only that the session is Streaming — the details of which content block type is currently active are encapsulated within the sub-machine.

Manageable complexity. A flat state machine with all states at one level might have 12+ states and 50+ transitions. A hierarchical machine with 3 levels of 4 states each has the same expressiveness but is far easier to understand because each level has only 4 states to reason about.

State Machines in Shutdown Sequences

Shutdown is where state machines prove their worth most dramatically. A system that shuts down correctly from any state is a system that never loses data, never leaves zombie processes, and never corrupts shared resources.

The Shutdown State Machine

Claude Code's graceful shutdown is an ordered sequence of operations, each dependent on the previous:

stateDiagram-v2
    [*] --> StopInput : shutdown signal received
    StopInput --> AbortRequests : input disabled
    AbortRequests --> FlushTelemetry : in-flight requests cancelled
    FlushTelemetry --> RunCleanups : telemetry flushed
    RunCleanups --> WriteEndMarker : cleanup handlers complete
    WriteEndMarker --> Deregister : session_end written
    Deregister --> RestoreTerminal : active_sessions updated
    RestoreTerminal --> [*] : terminal restored

Each state has a clear precondition (the previous state completed) and a clear action. The ordering is not arbitrary:

  1. StopInput before AbortRequests. If you abort requests before stopping input, the user could start a new request during shutdown, which would then be aborted, creating a confusing experience.

  2. AbortRequests before FlushTelemetry. In-flight requests might generate telemetry events. Aborting them first ensures the telemetry flush captures their abort status.

  3. RunCleanups before WriteEndMarker. Cleanup handlers (stopping language servers, killing subagents, disconnecting MCP servers) might update the cost counter. The end marker must record the final cost.

  4. WriteEndMarker before Deregister. The end marker in the transcript must be written before the session is deregistered. If deregistration happens first, another process might see "no active session" and start a new one, while the old session is still writing its end marker.

Error Isolation in Shutdown

Each cleanup step is wrapped in a try/catch:

for (const cleanup of registeredCleanups) {
  try {
    await cleanup()
  } catch (err) {
    logError('Cleanup handler failed', err)
    // Continue — other cleanups must still run
  }
}

A failed cleanup step transitions to the next step, not to an error state. This is a deliberate violation of the "fail fast" principle — during shutdown, the goal is to complete as many cleanup steps as possible, even if some fail. A language server that fails to stop should not prevent the transcript from being written.

The Transition Table as Documentation

A transition table is the most compact and precise documentation of a stateful system. It is more complete than prose (which tends to omit edge cases) and more precise than diagrams (which tend to omit events).

Example: Streaming State Machine

Current State Event Next State Side Effect
Idle message_start MessageActive Record TTFT
MessageActive content_block_start(text) InTextBlock Initialize text buffer
MessageActive content_block_start(tool_use) InToolUseBlock Initialize JSON buffer, record tool name
MessageActive content_block_start(thinking) InThinkingBlock Initialize thinking buffer
MessageActive message_delta MessageComplete Record stop_reason, merge usage
InTextBlock text_delta InTextBlock Append to buffer, yield to renderer
InTextBlock content_block_stop MessageActive Finalize text block
InToolUseBlock input_json_delta InToolUseBlock Append to JSON buffer
InToolUseBlock content_block_stop MessageActive Parse JSON, create tool request
InThinkingBlock thinking_delta InThinkingBlock Append to thinking buffer
InThinkingBlock content_block_stop MessageActive Finalize thinking block
MessageComplete message_stop Done Release resources
Any timeout Error Start stall detection
Any network_error Error Record partial state for recovery
Error retry_allowed Recovering Initialize retry with backoff

This table has 15 rows. It completely specifies the streaming pipeline's behavior. Any event-state combination not in the table is an invalid transition. A developer reading this table can answer any question about "what happens when X occurs during Y" in seconds.

Compare this to the hundreds of lines of if/else code that implement the same logic. The table is both the specification and the test oracle — generate tests that exercise every row, and you have complete coverage of the state machine.

When Not to Use State Machines

State machines are powerful but not universal. Three cases where they are the wrong tool:

1. When State Is Continuous

A progress bar that fills from 0% to 100% is not a state machine — it is a continuous value. Modeling it as discrete states (0-25%, 25-50%, 50-75%, 75-100%) adds artificial boundaries. Use a numeric variable with bounds checking.

2. When Transitions Are Unstructured

A free-form text editor does not have meaningful states. The user can type any character at any position in any order. There is no useful transition table because every "state" (the current document content) can transition to any other "state" (the document with one character changed). Use data structures, not state machines.

3. When the State Space Is Too Large

A chess game has approximately 10^44 legal states. Modeling this as an explicit state machine is absurd. Use rules and constraints (legal move generation) rather than enumerated states.

The rule of thumb: use state machines when you have fewer than ~20 states and the transitions between them carry important semantics. Beyond 20 states, consider hierarchical state machines. Beyond 100 states, consider a different modeling approach.

Testing State Machines

State machines are among the easiest code to test because the specification (the transition table) directly maps to test cases.

Transition Coverage

For every row in the transition table, write a test:

test('Idle + message_start → MessageActive', () => {
  const next = transition('Idle', { type: 'message_start' })
  expect(next).toBe('MessageActive')
})

test('InTextBlock + text_delta → InTextBlock', () => {
  const next = transition('InTextBlock', { type: 'text_delta', text: 'hello' })
  expect(next).toBe('InTextBlock')
})

This gives you one test per valid transition. For a 15-row table, that is 15 tests — comprehensive coverage of the state machine's behavior.

Invalid Transition Coverage

For every state, test at least one invalid event:

test('Idle + text_delta → throws', () => {
  expect(() => transition('Idle', { type: 'text_delta', text: 'x' }))
    .toThrow(InvalidTransitionError)
})

test('Done + any event → throws', () => {
  expect(() => transition('Done', { type: 'message_start' }))
    .toThrow(InvalidTransitionError)
})

Sequence Tests

Beyond individual transitions, test sequences that exercise meaningful paths through the machine:

test('complete happy path: Idle → Streaming → Done', () => {
  let state: StreamState = 'Idle'
  state = transition(state, { type: 'message_start' }) // → MessageActive
  state = transition(state, { type: 'content_block_start', blockType: 'text' }) // → InTextBlock
  state = transition(state, { type: 'text_delta', text: 'Hello' }) // → InTextBlock
  state = transition(state, { type: 'content_block_stop' }) // → MessageActive
  state = transition(state, { type: 'message_delta', stopReason: 'end_turn' }) // → MessageComplete
  state = transition(state, { type: 'message_stop' }) // → Done
  expect(state).toBe('Done')
})

Sequence tests verify that the machine's states compose correctly — that the end state of one transition is a valid start state for the next.

Key Principles

  1. Most bugs are state bugs. When behavior depends on accumulated history, scattered boolean flags create an exponential space of possible states. Most combinations are invalid. Bugs are paths that reach invalid combinations.

  2. Make illegal states unrepresentable. Use discriminated unions instead of boolean flags. If a field only makes sense in certain states, it should only exist in those states.

  3. The transition function is the specification. A single function that maps (current state, event) to next state is both the implementation and the documentation. If you cannot write the transition table, you do not understand the system.

  4. Guard transitions, not states. Put validation in the transition function, not scattered across call sites. One gate, not many.

  5. Coupled state requires atomic transitions. When two fields must change together, expose a single function that changes both. Remove individual setters.

  6. Strict internally, lenient externally. Throw on invalid transitions from internal code (they are bugs). Ignore or log invalid transitions from external protocols (they may be forward-compatible events).

  7. Event sourcing pairs naturally with state machines. Store the events (transitions), derive the state (by replay). Crash safety, auditability, and cheap writes — all from one design decision.

Think About It

  1. Boolean audit. Find a class or module in your codebase with three or more boolean flags that interact. How many total state combinations do the flags create? How many are actually valid? Could you replace the flags with a discriminated union that only allows valid combinations?

  2. Draw the diagram. Pick a stateful component you work with (a connection pool, a request handler, a workflow engine). Draw its state diagram on paper. Did you discover states or transitions you had not considered? Did you find states that are unreachable?

  3. The shutdown test. Your system is in the middle of processing (any state except idle or terminated). The process receives SIGTERM. Walk through your shutdown sequence. Is it ordered? Does each step depend on the previous? What happens if step 3 of 6 fails — do steps 4-6 still run?

  4. Atomic coupling. Find two fields in your codebase that must always change together (they maintain a mutual invariant). Is there a single function that updates both, or can they be updated independently? If they can be updated independently, what happens when another thread reads between the two updates?

  5. Transition table exercise. Write the complete transition table for a traffic light controller (green, yellow, red, with a pedestrian crossing request button). How many states? How many transitions? What happens if the pedestrian presses the button during yellow? Is there a state for "flashing red" (power failure mode), and if so, how does the system enter and leave it?
