Chapter 13: Data Flow Architecture

Every system is a data transformation pipeline. Inputs arrive, get processed through a series of stages, and emerge as outputs. This sounds obvious. It is not. Most engineers design systems around components — classes, modules, services — and then figure out how data moves between them. Data flow architecture inverts this: design the data transformations first, and the component boundaries reveal themselves.

This inversion is not academic. When you follow the data through a system, you discover natural seam lines that no amount of class diagrams will show you. You find stages that can run in parallel because they touch different data. You find bottlenecks where data accumulates faster than it drains. You find failure modes that only appear when data takes an unexpected path.

Claude Code's message pipeline — the path from user keystroke to rendered terminal output — is a case study in data flow architecture. A single user prompt triggers system prompt assembly (10+ sections concatenated in stability order), API streaming (Server-Sent Events parsed into typed content blocks), tool dispatch (parallel execution of read-only operations, serialized execution of mutations), and incremental rendering (markdown parsed and formatted token by token as they arrive). Each stage transforms data for the next. The architecture is the data flow.

Follow the Data

The first discipline of data flow architecture is literal: trace the path of a single datum through the entire system. Not the happy path. Not the error path. Every path.

Consider a user typing "Fix the login bug" in Claude Code. That string travels through:

Count the transformations. A five-word string becomes a structured content block, merged with context injections into a user message, appended to a conversation array, combined with a dynamically assembled system prompt, serialized into an HTTP request, streamed back as dozens of SSE events, parsed into typed content blocks, and either rendered to a terminal or dispatched to a tool executor whose output feeds back into the conversation for the next cycle.

This is not unusual. Most production systems have similarly deep data transformation chains. The discipline is mapping them. Engineers who do not map data flow end up debugging blind — they know the input was right and the output was wrong, but they cannot identify which transformation corrupted the data.

The Data Audit

Before designing anything, audit the data. Answer four questions about every datum in the system:

  1. Where does it enter? Every datum has an origin. User input, API response, file read, environment variable, clock. Know the entry points.

  2. What transforms it? Each stage that touches the data can corrupt it. Encoding changes, truncation, serialization, deserialization, validation, normalization. Each is a potential failure point.

  3. Where does it rest? Data at rest — in memory, on disk, in a cache — has different durability and access characteristics than data in flight. Know the resting points and their guarantees.

  4. Where does it exit? Terminal output, API response, file write, log entry, telemetry event. Every exit point is a contract with a consumer.

In Claude Code's message pipeline, a tool result datum enters from the tool executor, gets wrapped in a tool_result content block with a correlation ID linking it to the original tool_use request, gets merged into a user-role message (because the API requires alternating roles), gets appended to the conversation history, and eventually gets either sent to the API on the next turn or compacted into a summary when context runs low. That is five transformations and two resting points (conversation array and JSONL transcript) for a single tool result.

The Pipeline Pattern

A pipeline is a sequence of stages where each stage's output is the next stage's input. The pattern is ancient — Unix pipes, ETL workflows, signal processing chains. It endures because it maps to how data naturally flows through systems: raw input gets progressively refined into useful output.

Stage Independence

The power of pipelines comes from stage independence. Each stage knows only two things: what data it receives and what data it produces. It does not know what stage came before it or what stage comes after. This independence enables three capabilities:

Testing in isolation. You can test the system prompt assembler by feeding it mock inputs and checking its output, without running the HTTP client or the terminal renderer. Claude Code's prompt pipeline is tested with snapshot tests — given these inputs (conversation state, rules, skills), assert the assembled system prompt matches the expected output byte for byte.

Replacement without propagation. If you change how the SSE parser works, no other stage needs to change, as long as the output type remains the same. Claude Code replaced its markdown renderer without touching the streaming state machine, because the interface between them — a stream of text deltas — remained stable.

Parallel execution. Independent stages that process different data can run concurrently. While the streaming pipeline renders text to the terminal, the tool accumulator silently collects JSON fragments. They share a state machine but process different event types along different paths.

Typed Stages

In production, pipeline stages must have explicit types. Not just "data in, data out," but specific types that the compiler checks:

// Each stage is a typed transformation
type PromptAssembler = (
  conversation: Message[],
  systemBlocks: SystemBlock[],
  userContext: UserContext
) => APIRequestParams

type StreamProcessor = (
  rawStream: AsyncIterable<RawSSEEvent>
) => AsyncGenerator<ProcessedEvent>

type ToolDispatcher = (
  toolCalls: ToolUseBlock[]
) => Promise<ToolResult[]>

When a stage's output type does not match the next stage's input type, you have a design problem. Either you need a transformation step between them (an adapter), or your stage boundaries are in the wrong place. Type mismatches at stage boundaries are the compiler telling you that your pipeline design has a seam in the wrong location.

Streaming vs. Batch

Every data flow faces a fundamental choice: process data as it arrives (streaming) or collect it first and process it all at once (batch). The choice is not binary — most real systems mix both modes at different stages.

The Batch Model

Batch processing collects all input before producing any output. The non-streaming API call is the canonical example: send the full prompt, wait for the full response, process the result.

Input complete → Process all → Output complete
     |              |              |
  Known size    Full context    Single delivery

Batch is simpler. You have the complete input, so you can make globally optimal decisions. A batch JSON parser has the full string; it parses once, in O(n), and produces a complete result. A batch system prompt assembler has all blocks; it can sort them optimally and compute the total size before sending anything.

The Streaming Model

Streaming processes data incrementally as it arrives. The streaming API returns Server-Sent Events token by token. Each token must be processed without knowledge of future tokens.

Input chunk₁ → Process → Output chunk₁
Input chunk₂ → Process → Output chunk₂
   ...          ...          ...
Input chunkₙ → Process → Output chunkₙ

Streaming is harder but delivers lower latency. The user sees the first word of the response within 500ms, rather than waiting 10 seconds for the complete response. For a CLI tool where responsiveness determines the user experience, this latency advantage is decisive.

The Hybrid: Batch Boundaries in a Streaming Pipeline

Claude Code's streaming pipeline is streaming at the token level but batch at the block level. Text deltas stream to the renderer immediately — every token appears as the model generates it. But tool-use deltas accumulate in a buffer until the entire JSON input is received, then get parsed and dispatched as a batch.

graph TB
    subgraph "Streaming Path (text)"
        TD1["text_delta: 'Let me '"] --> R1["Render immediately"]
        TD2["text_delta: 'check '"] --> R2["Render immediately"]
        TD3["text_delta: 'that.'"] --> R3["Render immediately"]
    end

    subgraph "Batch Path (tool use)"
        JD1["json_delta: '{\"file_'"] --> BUF["Buffer"]
        JD2["json_delta: 'path\":\"'"] --> BUF
        JD3["json_delta: 'src/main.ts\"}'"] --> BUF
        BUF --> PARSE["Parse complete JSON"]
        PARSE --> EXEC["Dispatch tool"]
    end

This hybrid exists because text and tool-use data have different requirements. Text can be rendered incrementally — displaying half a sentence is useful (the user reads along). But half a JSON object is useless and cannot be parsed. The data's nature dictates the processing mode.

The principle generalizes: use streaming when partial data is useful, batch when partial data is meaningless. Log entries can be streamed (each line is independent). SQL transactions must be batched (a partial transaction is worse than no transaction). Image data can be streamed for progressive display. Cryptographic signatures must be batched (you need the complete message to verify).

Choosing the Processing Mode

Criterion Streaming Batch
Latency requirement Low (interactive) Tolerant (background)
Partial data value Useful Useless or dangerous
Memory constraint Tight (can't hold all data) Relaxed
Processing complexity Simple per-item logic Complex cross-item logic
Error recovery Per-item retry Full restart
Ordering guarantee Natural (arrival order) Requires explicit sort

Backpressure: The Hidden Architecture

When a producer generates data faster than a consumer can process it, something must give. That "something" is backpressure — the mechanism by which a slow consumer signals a fast producer to slow down. Backpressure is invisible in working systems and catastrophic in broken ones.

The Problem Concrete

Claude Code's streaming pipeline has an explicit backpressure scenario. The language model generates tokens at roughly 100 tokens per second. The terminal renderer must parse markdown, apply syntax highlighting, and write to stdout. On a slow terminal — an SSH session over a satellite link, a terminal with complex ligature rendering, a screen reader processing output — rendering takes longer than token generation.

Without backpressure, the pipeline buffers tokens in memory. A 64K-token response generates roughly 16,000 delta events. If the renderer processes 1,000 per second and the model produces 3,000 per second, the buffer grows by 2,000 events per second. Over a 30-second generation, 60,000 events accumulate in memory. The process eventually runs out of memory or the user sees a frozen terminal followed by a flood of text.

Pull vs. Push

Two fundamental approaches to flow control:

Push-based: The producer pushes data to the consumer. The consumer must process it or buffer it. Flow control requires explicit signals — the consumer tells the producer "pause" and "resume." This is the observer pattern, event emitters, and callback-based architectures.

Pull-based: The consumer pulls data from the producer when it is ready. The producer blocks until the consumer pulls. Flow control is implicit — the producer simply cannot produce faster than the consumer pulls.

Claude Code's streaming pipeline uses the pull-based approach via async generators:

async function* processStream(
  rawStream: AsyncIterable<RawSSEEvent>
): AsyncGenerator<ProcessedEvent> {
  for await (const raw of rawStream) {
    const processed = processEvent(raw)
    yield processed  // Pauses until consumer pulls
  }
}

The yield statement is the backpressure mechanism. When the consumer (the terminal renderer) has not pulled the next event, the generator pauses at yield. This pause propagates through the async iterable chain to the HTTP response stream, which signals TCP flow control to the server. The model's token generation is not affected (it continues into a server-side buffer), but the byte delivery to the client slows down, keeping the client's memory bounded.

Batching Under Pressure

Pure pull-based backpressure has a visual problem: when the renderer is slow, tokens arrive in bursts instead of smoothly. The user sees nothing for 100ms, then a chunk of text, then nothing again. This stuttering is distracting.

The solution is frame-rate batching — accumulate text deltas during a frame budget (16ms for 60fps) and render them as a single chunk:

// Batch deltas into 16ms frames for smooth display
if (elapsed > 16) {
  yield { type: 'batched_text_delta', text: pendingText }
  pendingText = ''
  lastYieldTime = performance.now()
}

This trades individual token latency (each token arrives up to 16ms late) for visual smoothness (the user sees steady text flow). The 16ms budget is not arbitrary — it matches the display refresh cycle. Humans cannot perceive latency below 16ms, so the delay is invisible while the batching eliminates stutter.

Backpressure as Architecture

Backpressure is not an optimization you add later. It is a fundamental architectural property that must be designed from the start. A pipeline without backpressure is a pipeline with an implicit unbounded buffer — and unbounded buffers always fill up eventually.

The design checklist for every pipeline stage:

  1. What is my input rate? The maximum rate at which the upstream stage produces data.
  2. What is my processing rate? The rate at which I can transform and emit data.
  3. What happens when input rate exceeds processing rate? Buffer (bounded), drop, slow the producer, or error.
  4. Who controls the flow? The producer, the consumer, or an external coordinator.

System Prompt Assembly: A Pipeline Case Study

Claude Code's system prompt assembly is one of the most architecturally significant data pipelines in the system. Before every API call, the system assembles a prompt from 10+ sections, each drawn from a different source. The design of this pipeline determines prompt cache hit rates, context window utilization, and — ultimately — the quality of the model's responses.

The Stability Gradient

The system prompt blocks are ordered by stability — how frequently they change:

graph LR
    subgraph "Stable (rarely change)"
        B1["Identity Block"]
        B2["Tool Definitions (52 tools)"]
        B3["Model-Specific Instructions"]
    end

    subgraph "Semi-stable (change across sessions)"
        B4["Project Rules (.claude/rules/)"]
        B5["Memory (CLAUDE.md, auto-memory)"]
    end

    subgraph "Dynamic (change between turns)"
        B6["Active Skills"]
        B7["Session Context (cwd, git status)"]
        B8["MCP Server Descriptions"]
    end

    subgraph "Volatile (change every turn)"
        B9["Custom Instructions"]
        B10["Plan Context"]
    end

    B1 --> B2 --> B3 --> B4 --> B5 --> B6 --> B7 --> B8 --> B9 --> B10

    B10 --> CACHE["Cache Control Marker"]

This ordering is not about logical grouping. It is about cache economics. The prompt cache matches on byte-identical prefixes. Everything before the first changed byte is cached. Everything after is re-processed. By placing the most stable blocks first, the maximum prefix is cacheable.

A concrete example: the identity block and tool definitions are roughly 15,000 tokens. If these are stable across turns, the cache saves 15,000 tokens of input processing on every API call. At $3 per million input tokens, a session with 50 API calls saves $2.25 from this single optimization. Multiply by millions of sessions and the economics are decisive.

The design constraint this creates: no block can depend on a block after it in the ordering. If the identity block referenced the current active skill, it would change every time a skill was invoked, breaking the cache for all subsequent blocks. Dependencies must flow forward (later blocks can reference earlier ones), never backward.

Deterministic Assembly

The assembly pipeline is a pure function: given the same inputs, it produces the same output byte for byte. This determinism enables three things:

  1. Snapshot testing. Record the assembled prompt for a set of inputs, store it as a test fixture, and assert future assemblies match. Any drift indicates a bug or an intentional change that needs review.

  2. Cache stability analysis. Compare the assembled prompts from consecutive turns. If only the last two blocks differ, the cache prefix covers blocks 1-8. If an early block changed unexpectedly, investigate why.

  3. Debugging model behavior. When the model produces unexpected output, dump the assembled prompt. The prompt is what the model saw. If the prompt is wrong, the output is a symptom, not the problem.

Determinism requires discipline. Tool definitions must be sorted by name (not hash-order, which varies between runs). Feature flags must be latched at session start (not re-evaluated per turn, which could change mid-session). MCP tool schemas must be placed after core tools (so adding an MCP server does not shift core tool bytes).

The Rendering Pipeline: Data Flow to the User's Eyes

The final stage of the data flow pipeline transforms structured data into pixels on a terminal. This is not a trivial serialization step — it is a complex incremental parser that must handle markdown formatting, syntax highlighting, code blocks, and ANSI escape codes, all while tokens arrive one at a time.

Incremental Markdown Parsing

Markdown is not designed for incremental parsing. A ** token could be the start of bold text or the end of bold text, depending on what comes later. A ` could be the start of an inline code span or a literal backtick. The renderer must make provisional decisions and revise them as more tokens arrive.

The state the renderer maintains:

- Am I inside a code block? (``` ... ```)
- Am I inside an inline code span? (` ... `)
- Am I inside bold? (** ... **)
- Am I inside italic? (* ... *)
- Am I inside a heading? (# ...)
- What indentation level am I at?
- Is the current line a list item?

Each text delta updates this state. Most updates are simple (append text to the current context). Some require retrospective correction (a * that looked like italic turns out to be a bullet point at the start of a new line).

The rendering pipeline handles this by separating parsing from rendering:

Text delta → Incremental parser → Parse tree update → Renderer → ANSI output → Terminal

The parser maintains a mutable parse tree. Each delta extends the tree (append a text node, open a formatting span, close a code block). The renderer walks the updated portions of the tree and produces ANSI escape sequences for the terminal. Only the changed portions are re-rendered — the renderer does not reprocess the entire output on every delta.

This incremental approach is what makes streaming feel instant. The user sees each word appear with correct formatting as the model generates it. A batch approach (wait for the complete response, then render) would be simpler but would destroy the responsiveness that makes a CLI agent feel alive.

Data Flow Reveals Component Boundaries

One of the most powerful consequences of data flow thinking: the natural component boundaries in a system align with the transformation boundaries in the data flow.

In Claude Code's message pipeline, the natural components are:

Component Input Output Boundary
REPL Keystrokes User prompt string Human-machine interface
Context injector Prompt string + env state Enriched user message Context assembly
System prompt assembler Rules, skills, memory, tools System prompt blocks Static → dynamic
API client Request params SSE event stream Network boundary
Stream state machine Raw SSE events Typed content blocks Protocol parsing
Text renderer Text deltas ANSI terminal output Data → presentation
Tool dispatcher Tool-use blocks Tool results Computation boundary
Conversation manager New messages Updated history State management

Each component exists because the data transformation at that point is fundamentally different from the transformations before and after. The context injector combines data from multiple sources (working directory, git status, user preferences) into a single message — that merging operation defines the component. The stream state machine parses a byte-level protocol into typed events — that parsing operation defines the component.

When engineers struggle with "where should I put this code?", the data flow answer is: put it at the stage where the data transformation happens. If you are adding a feature that transforms tool results before they enter the conversation, it belongs in the conversation manager. If you are adding a feature that modifies the system prompt based on the current file, it belongs in the system prompt assembler.

Anti-Pattern: Cross-Cutting Data Access

The worst violation of data flow architecture is when a component reaches across stages to access data it should not know about. A renderer that queries the conversation history to decide how to format text. A tool dispatcher that modifies the system prompt. An API client that reads user preferences directly.

These cross-cutting accesses create invisible dependencies. When you change the conversation history format, the renderer breaks. When you refactor the system prompt assembly, the tool dispatcher produces different results. The data flow diagram shows clean pipeline stages; the actual code is a web of hidden connections.

The fix is strict interface enforcement: each stage receives data only from its input and produces data only through its output. If a stage needs additional data, it must arrive as an explicit input, not as a side-channel read from shared state.

Error Propagation in Pipelines

Errors in a pipeline can originate at any stage. The question is not whether errors will happen but how they propagate. Three strategies:

Strategy 1: Fail Fast

The error halts the pipeline immediately. No downstream stages execute. The error propagates to the caller.

Use when: The error makes downstream processing meaningless. If the API client cannot connect, there is no stream to parse, no tool to dispatch, no text to render. Fail fast.

Strategy 2: Error as Data

The error becomes a datum in the pipeline. Downstream stages process it as a special case of their normal input.

Use when: The error is recoverable at a later stage. In Claude Code, a malformed SSE event becomes an Error state in the streaming state machine. The state machine does not crash — it logs the violation, stays in its current state, and waits for the next valid event. The error is absorbed rather than propagated.

Strategy 3: Parallel Error Channel

Errors flow through a separate channel from normal data. This is the Result<T, E> pattern — every stage returns either a success value or an error, and the pipeline branches on which it is.

Use when: Error handling logic is complex and should not pollute the normal data path. Claude Code's streaming pipeline uses this for partial response recovery: when a disconnect occurs mid-stream, the error channel carries information about what was received (which complete content blocks exist, whether the JSON buffer is parseable), while the normal channel carries the successfully-received data.

Recovery at Pipeline Boundaries

The most effective recovery happens at pipeline boundaries — the points where data changes form. If the API client fails (network boundary), retry at the network level. If the JSON parser fails (protocol boundary), retry parsing with error-tolerant mode. If the renderer fails (presentation boundary), fall back to plain text.

Recovery at non-boundary points is usually wrong. Retrying a single token in the middle of a stream does not make sense. Retrying a single block in the system prompt assembly creates an inconsistent prompt. Recovery is a stage-level operation, not a datum-level operation.

Monitoring Data Flow

You cannot optimize what you cannot measure. For data flow architectures, the critical metrics are:

Throughput

How many data units per second pass through each stage. In Claude Code's streaming pipeline, the key throughput metrics are:

  • Time to first token (TTFT): Latency from API request to first message_start event. This measures network latency plus model initialization time.
  • Token rate: Tokens per second through the text rendering pipeline. This is the user-perceived speed.
  • Tool dispatch latency: Time from content_block_stop (tool JSON complete) to tool execution start.

Queue Depth

How much data is waiting between stages. A growing queue indicates backpressure failure — the upstream stage is producing faster than the downstream stage consumes.

In Claude Code, the text delta buffer is the primary queue. The batching processor accumulates deltas during each 16ms frame. If the buffer grows beyond a frame's worth of text, the renderer is falling behind.

Error Rate Per Stage

Which stage produces the most errors reveals which transformation is the most fragile. In a typical API streaming session, the SSE parser has the highest error potential (network issues), while the system prompt assembler has the lowest (it operates on local data with no I/O).

Key Principles

  1. Follow the data. Trace every datum from entry to exit. The data flow diagram is the architecture diagram.

  2. Design stages, then components. The data transformations define the natural component boundaries. Do not force data into pre-conceived component shapes.

  3. Use streaming when partial data is useful, batch when it is not. Text renders incrementally. JSON parses in batch. Match the processing mode to the data's nature.

  4. Backpressure is architectural. A pipeline without explicit flow control has an implicit unbounded buffer. Unbounded buffers always fill.

  5. Order by stability for caching. In any assembled output (prompts, configurations, documents), place the most stable content first. This maximizes cache prefix length.

  6. Keep stages independent. Each stage knows only its input type and output type. No cross-cutting data access. No reaching around stages to read shared state.

  7. Recovery happens at boundaries. Retry at the stage level, not the datum level. Network errors retry at the network boundary. Parse errors retry at the protocol boundary.

Think About It

  1. Map a data flow you own. Pick a feature in your current system. Trace a single user action from input to final output. How many transformations does the data undergo? Where are the resting points? Where could data be corrupted? Did you find any cross-cutting accesses that violate stage independence?

  2. Batch-streaming boundary. You are building a system that receives a stream of financial transactions. Each transaction must be validated against the user's current balance (which requires querying a database). Where do you place the batch boundary? What are the tradeoffs of validating each transaction individually (streaming) versus collecting a batch and validating the set?

  3. Backpressure audit. Examine a producer-consumer relationship in your codebase. What happens when the consumer is 10x slower than the producer? Is there explicit flow control? What is the maximum memory consumed by the intermediate buffer? What happens when that maximum is exceeded — does the system degrade gracefully or crash?

  4. Cache stability analysis. Take a configuration or prompt that is assembled from multiple sources and sent repeatedly. Are the sources ordered by stability? Could you reorder them to improve caching? What is the cost of a cache miss, and how often does it happen?

  5. Error channel design. You have a 5-stage pipeline where stage 3 occasionally produces invalid output. The current behavior is to crash the pipeline. Design an alternative: should the error become data (skip the bad item), trigger a retry (re-run stage 3), or flow through a parallel error channel? What information does each downstream stage need about the error to make correct decisions?
