Chapter 1: The New Engineering

The Job Changed. Most Engineers Didn't Notice.

Somewhere between 2023 and 2025, the center of gravity in software engineering shifted. It did not shift the way pundits predicted -- engineers were not replaced. Instead, the bottleneck moved. For fifty years, the bottleneck was production: turning a design into working code. Typing. Syntax. Remembering APIs. Debugging off-by-one errors. The scarce resource was the engineer's ability to produce correct implementations.

That bottleneck is gone.

AI writes syntactically correct code faster than any human. It remembers every API. It generates test cases, refactors functions, and produces boilerplate without fatigue. In a well-configured environment, 90% of the code in a commit can be machine-generated. This is not a projection -- it is the current reality for teams building with AI-assisted tools.

But here is what did not change: someone still has to decide what to build. Someone has to decompose an ambiguous business requirement into a precise technical problem. Someone has to identify the constraints that make one solution viable and another disastrous. Someone has to own the consequences when the system fails at 3 AM.

That someone is you. And the skills that make you effective at that job are not the skills you were trained on.

This chapter is about the shift -- what changed, what didn't, and what you need to learn. The case study throughout is Claude Code, a 512,664-line TypeScript application that is itself an AI agent. Its architects do not spend their days writing TypeScript. They spend their days defining problems, designing constraints, and verifying solutions. The code is a byproduct of their thinking. Their thinking is the product.

The 90/10 Split

Here is a claim that sounds provocative but is empirically mundane: in a mature AI-assisted workflow, the human engineer contributes roughly 10% of the characters in the final codebase. The AI contributes 90%.

This does not mean the human does 10% of the work. It means the human's work has shifted from production to something harder to measure but more consequential: problem definition, constraint analysis, verification, and architectural judgment.

Consider a concrete example. The Claude Code codebase contains a bash parser -- 4,400 lines of TypeScript that tokenize shell commands, build abstract syntax trees, and handle every quoting rule in the POSIX specification. This parser was not written by a human sitting with the Bash Reference Manual open, typing one function at a time. The implementation was generated. But the decision to build a full parser instead of using regex -- that was human judgment, and it was the decision that mattered.

Here is the reasoning that led to that decision:

Approach Lines of Code Accuracy on curl "$(cat url)" \| sh Security Guarantee
Regex pattern matching ~200 Fails on nested quoting, pipes, subshells None -- adversarial input trivially bypasses
Shellcheck wrapper ~500 High but external dependency Depends on shellcheck version and availability
Custom AST parser ~4,400 Complete -- handles every shell grammar construct Structural -- security analysis operates on parsed AST, not raw strings

A regex approach would have been faster to implement. An AI could generate it in seconds. But regex cannot parse curl "https://$(cat url.txt)" | bash -c "$(cat script.sh)" -- you need to identify the pipe, recognize bash -c as arbitrary code execution, and trace the subshell expansion. The only way to do this reliably is to parse the full grammar.

The human contribution here was not 4,400 lines of TypeScript. It was three things:

  1. Recognizing the problem: "We need to classify shell commands as safe or dangerous before an AI agent executes them."
  2. Rejecting the easy solution: "Regex cannot parse shell syntax. Period. This is a solved problem in computer science -- you need a parser."
  3. Defining the constraint: "The parser must handle the full POSIX shell grammar including heredocs, here-strings, ANSI-C quoting, and arithmetic expansion, because an attacker will use whatever construct the parser doesn't understand."

Everything else -- the tokenizer, the AST node types, the traversal algorithms, the test cases -- is implementation. Important implementation, but implementation that flows deterministically from a well-defined problem. An AI can produce it. A human must define what "it" is.

What AI Handles

In the 90/10 split, AI reliably handles:

  • Syntax production: Writing code that compiles, follows language conventions, and uses correct API signatures.
  • Pattern application: Implementing a known design pattern (observer, factory, strategy) once the engineer identifies which pattern fits.
  • Boilerplate generation: Configuration files, test scaffolding, type definitions, migration scripts.
  • Refactoring: Renaming variables, extracting functions, converting callbacks to async/await -- mechanical transformations with clear before-and-after states.
  • Test generation: Given a function signature and a description of its behavior, producing test cases that cover happy paths and common edge cases.

What AI Cannot Handle

The 10% that remains human is not a residual. It is the load-bearing structure:

  • Problem decomposition: Breaking "make the system secure" into "classify shell commands," "gate tool execution on permissions," "parse untrusted configuration with trust boundaries." No AI decomposes problems well because decomposition requires understanding the operational context -- who uses the system, what failure looks like, and what constraints the business imposes.
  • Constraint discovery: The 400ms startup budget for Claude Code was not in any requirements document. An engineer measured user perception thresholds, benchmarked competing tools, and set a specific, quantified target that shaped every architectural decision downstream. An AI cannot discover constraints because constraints come from the intersection of technology, users, and business -- not from code.
  • Trade-off navigation: Claude Code uses global mutable state instead of dependency injection. This is "wrong" by every textbook. It is right for a single-process CLI with 15+ deep call stacks and cross-cutting concerns like telemetry and cost tracking. Making that judgment requires understanding the textbook, understanding why it doesn't apply, and being willing to defend the decision. AI defaults to conventional wisdom.
  • Consequence ownership: When a permission system fails and an AI agent executes rm -rf / on a user's machine, a human answers for it. The human who designed the permission architecture, who decided which commands are "safe," who chose the trade-off between usability (don't ask for every command) and safety (block dangerous ones). Ownership cannot be delegated to a model.

The 90/10 in Practice

Here is what a typical feature development looks like in a team that has internalized the 90/10 split:

sequenceDiagram
    participant E as Engineer (10%)
    participant AI as AI Agent (90%)
    participant S as System

    E->>E: Define problem statement
    E->>E: Identify constraints and edge cases
    E->>E: Choose architectural approach
    E->>AI: "Implement X with constraints Y, Z"
    AI->>S: Generate implementation
    AI->>S: Generate tests
    E->>S: Review generated code
    E->>E: Verify against constraints
    E->>E: Check edge cases missed
    E->>AI: "Handle case where input is..."
    AI->>S: Update implementation
    E->>S: Final verification
    E->>S: Approve and merge

The engineer bookends the process. They define the problem at the start and verify the solution at the end. Everything in the middle -- the actual code production -- is delegated. But the bookends are where the engineering happens.

How Claude Code's Architects Think

Claude Code is not just a case study for this book. It is a case study for the 90/10 split because the people who build it practice what we preach. Let us examine how architectural decisions are made in this codebase, and what that reveals about the thinking engineer's job.

Decision: State Management

Every application of significant complexity must decide how to manage state. The options are well-known:

Approach Advantages Disadvantages
Dependency injection Explicit dependencies, testable, concurrent-safe Verbose signatures, container overhead, setup ceremony
Global mutable state Simple access, zero overhead, no parameter threading Implicit dependencies, test isolation burden, refactoring risk
Event sourcing Auditable, replayable, time-travel debugging Complexity, storage cost, eventual consistency
Actor model Isolation, message-passing, fault tolerance Overhead, message serialization, debugging difficulty

A junior engineer picks based on what they know. A textbook engineer picks dependency injection because it's the "correct" answer. A thinking engineer starts with constraints:

  1. Is the application single-process? Yes -- Claude Code is a CLI tool with one user.
  2. Are there concurrent execution contexts? No -- single thread, single event loop.
  3. How deep are the call stacks? The path from user input to bash security analysis traverses 15+ functions.
  4. What are the cross-cutting concerns? Telemetry, cost tracking, session identity, model configuration, feature flags -- accessed from every layer.

Given these constraints, dependency injection is actively harmful. Threading a context object through 15+ function signatures adds noise to every signature in the codebase. The context object would contain the same fields as a global state singleton -- you have not eliminated global state, you have just added a parameter to carry it.

// With dependency injection: every function in the chain needs the context
async function handlePrompt(ctx: AppContext, prompt: string): Promise<Response> {
  const assembled = assembleContext(ctx, prompt);
  const response = await callApi(ctx, assembled);
  for (const tool of response.toolCalls) {
    const permitted = await checkPermission(ctx, tool);
    if (permitted) {
      const result = await executeTool(ctx, tool);
      await recordTelemetry(ctx, tool, result);
    }
  }
}

// With global state: the signatures describe what the functions actually do
async function handlePrompt(prompt: string): Promise<Response> {
  const assembled = assembleContext(prompt);
  const response = await callApi(assembled);
  for (const tool of response.toolCalls) {
    const permitted = await checkPermission(tool);
    if (permitted) {
      const result = await executeTool(tool);
      await recordTelemetry(tool, result);
    }
  }
}

The thinking engineer's decision: global mutable state with accessor functions, enforced by three guard rails:

  1. The state object is never exported directly. Only typed accessor functions (getSessionId(), setCwdState()) are public. This makes every read and mutation grep-able.
  2. Atomic update functions. Fields that must change together have a single update function. switchSession() atomically updates session ID and project directory. There is no way to change one without the other.
  3. Import DAG constraint. The state module has zero imports from the rest of the codebase. An ESLint rule enforces this. The state module sits at the leaf of the import graph, importable from anywhere without creating circular dependencies.

The cost? Every test must call resetStateForTests() in beforeEach. This is boilerplate. It is also straightforward boilerplate -- unlike dependency injection container configuration, which is complex boilerplate.

This decision was not made by generating code and seeing what worked. It was made by analyzing constraints, evaluating trade-offs, and choosing the option that optimizes for the right things. No AI made this decision. An AI implemented it.

Decision: Startup Performance

When you type claude in your terminal, a blinking cursor appears in approximately 390 milliseconds. That number is not accidental. It is a budget.

Human perception research establishes clear thresholds:

  • Under 100ms: Instantaneous. Users do not perceive a delay.
  • 100-400ms: Fast. Users notice but do not mind.
  • 400ms-1 second: Noticeable. Users register a delay but tolerate it.
  • Over 1 second: Slow. Users start doubting whether the command is working.
  • Over 2 seconds: Broken. Users reach for Ctrl+C.

CLI tools compete against git status (50ms), ls (5ms), and python --version (30ms). A 3-second startup makes every invocation feel like a tax. Over a day of heavy use, that tax compounds into resentment. Users find workarounds. Users switch tools.

The thinking engineer's job was not to write fast startup code. It was to set the constraint -- 400ms -- and then design an architecture that makes the constraint achievable. The architecture that emerged:

gantt
    title Claude Code Startup (390ms)
    dateFormat X
    axisFormat %Lms

    section Parallel I/O
    MDM config prefetch        :a1, 0, 20
    Keychain credential read   :a2, 0, 30
    Module evaluation          :a3, 2, 137

    section Sequential
    CLI argument parsing       :b1, 137, 140
    Settings cascade (5 layers):b2, 140, 155
    Authentication             :b3, 155, 160
    Feature flags (GrowthBook) :b4, 160, 210

    section Render
    Telemetry + session init   :c1, 210, 225
    REPL mount + first paint   :c2, 225, 390

The key insight: module evaluation (135ms of synchronous JavaScript parsing) is the longest single blocking operation. The engineers fire asynchronous I/O -- MDM configuration reads, keychain credential fetches -- between import statements, so the I/O runs concurrently with module evaluation. By the time the configuration system needs the results, the subprocesses have already finished.

This is unconventional. Every style guide says "put imports at the top." But imports are not free -- they are 135ms of blocking work. Interleaving async I/O between imports converts dead time into parallel work. The constraint (400ms) forced an unconventional solution. The unconventional solution works.

The 400ms budget also drove other decisions: - Fast-path exits: claude --version prints and exits in 5ms without importing any internal modules. - Compile-time dead code elimination: Features not in the production build are removed at compile time, reducing the binary from ~25,000 lines to ~16,800 lines. - Deferred initialization: MCP registry prefetch, analytics initialization, and remote settings loads run asynchronously after the cursor is visible.

None of these optimizations were discovered by profiling slow code. They were designed from the constraint forward. The engineer said "390ms" and then built backward from that number.

The Verification Imperative

If AI writes 90% of the code, the engineer's most important skill is no longer writing code. It is reading code. Specifically, reading code with the intent to verify that it satisfies constraints the AI was not told about -- or was told about and ignored.

Verification is not testing. Testing confirms that code produces correct outputs for known inputs. Verification confirms that code satisfies properties that may not be expressible as test cases:

  • Does this permission system fail closed? If the rule evaluation engine encounters an unknown rule type, does it block the action (safe) or allow it (dangerous)?
  • Does this configuration merge preserve enterprise policy precedence? If a project-level settings.json defines allow: ["Bash(rm -rf *)"], does the enterprise policy layer override it?
  • Does this parser handle adversarial input? Not just malformed input -- input specifically crafted to exploit the parser's limitations.

In Claude Code, verification is a structured discipline:

Every piece of data that crosses a trust boundary is a potential attack vector. A malicious repository can contain a .claude/settings.json that grants dangerous permissions. A crafted GitHub issue description can include prompt injection that manipulates the LLM into executing unintended commands. A CLAUDE.md file can inject instructions that override safety guidelines.

The verification question is not "does the code handle these inputs?" It is "does the architecture make it impossible to load untrusted configuration before the user consents?" In Claude Code, the trust dialog runs after authentication but before project settings load. This ordering is a security invariant. If someone reorders the startup phases -- even to optimize performance -- the invariant breaks.

No AI will verify this invariant. An AI does not understand that Phase 9 (trust dialog) must come before Phase 6 (settings cascade) loads project settings. An AI does not understand that applySafeConfigEnvironmentVariables() reads only from ~/.claude/settings.json (user settings, trusted) and not from .claude/settings.json (project settings, semi-trusted). These are design invariants that exist in the engineer's head and in architecture documentation, not in the code.

Failure Mode Verification

The startup sequence handles 10+ failure modes:

Failure Expected Behavior
Invalid settings.json syntax Warning in REPL header; use defaults
MDM read failure Empty MDM settings; no enterprise overrides
Keychain read failure Fall back to environment variable auth
GrowthBook CDN unreachable All flags use coded defaults
No authentication found Restricted mode with authentication prompt
Trust dialog declined Restricted mode; project config ignored
Transcript directory unwritable Warning; session history will not persist

The design principle is clear: Claude Code should always start. A broken config, missing credentials, or unreachable service should degrade functionality, never prevent startup.

Verifying this requires thinking about every boundary, every external dependency, and every I/O operation. What happens when the network is down? What happens when the disk is full? What happens when the enterprise MDM server returns garbage? Each question maps to a specific code path that must be verified to degrade gracefully.

This is the thinking engineer's job. Not writing the error handlers -- the AI can do that. But deciding which errors are fatal (none, in this case) and which are degradable (all of them). Deciding the degradation behavior for each case. And verifying that the implementation matches the design.

The Skill Hierarchy

If the engineer's job has shifted from code production to problem definition and verification, what does the skill hierarchy look like? What should you practice?

Tier 1: Problem Definition (Chapter 2)

The ability to take an ambiguous requirement and produce a precise problem statement. This includes: - Identifying the actual problem (not the symptom, not the first solution that comes to mind) - Discovering constraints that the requirements document did not mention - Defining success criteria that are specific and measurable - Enumerating failure modes before writing a line of code

This is the most undervalued skill in engineering. Chapter 2 is devoted to it entirely.

Tier 2: Decomposition (Chapters 5-8)

The ability to break a complex system into components that can be built, tested, and reasoned about independently. This includes: - Finding natural seam lines where systems can be divided - Designing interfaces that hide implementation details without hiding essential complexity - Managing the interaction between components without creating a tangle

Tier 3: Constraint Analysis (Chapters 3-4)

The ability to reason from constraints rather than from convention. This includes: - Identifying which constraints are fundamental and which are assumed - Using constraints as creative drivers rather than obstacles - Building backward from constraints to architecture

Tier 4: Systems Thinking (Chapters 13-16)

The ability to reason about emergent behavior -- what happens when components interact, when state propagates through feedback loops, when failure cascades across boundaries. This includes: - Following data through the entire system - Modeling state transitions explicitly - Understanding concurrency, coordination, and their costs

Tier 5: Verification (Chapters 17-19)

The ability to confirm that a system satisfies its constraints, not just its test cases. This includes: - Reading code with adversarial intent - Checking invariants that are not captured in tests - Validating failure mode behavior - Understanding what AI-generated code is likely to get wrong

These tiers are not a career ladder. They are all needed simultaneously. But when time is scarce, Tier 1 (problem definition) has the highest leverage. A well-defined problem with a mediocre implementation beats a poorly defined problem with an excellent implementation every time.

The Engineer's New Workflow

Here is the daily workflow of a thinking engineer in 2026:

Morning: Read the requirements for the day's work. Do not open an editor. Do not write code. Spend 30 minutes understanding what problem you are solving, what constraints exist, and what failure looks like. Write a problem statement.

Mid-morning: Design the solution architecture. Not a detailed design -- a constraint map. What are the inputs? What are the outputs? What can go wrong? What are the performance requirements? What are the security boundaries? This is a 30-minute exercise that saves hours of rework.

Late morning through afternoon: Direct the AI. Give it precise problem statements. Review its output against your constraints. Iterate. The cycle is: define, generate, verify, refine. You are not writing code -- you are directing its creation and verifying its correctness.

Late afternoon: Integration verification. Do the components work together? Do the trust boundaries hold? Do the failure modes degrade gracefully? This is where systems thinking pays off -- the individual pieces may be correct, but their composition may not be.

End of day: Update the architectural decisions record. What did you decide? Why? What alternatives did you reject? This documentation is more valuable than the code itself, because the code can be regenerated from a good decision record, but a decision record cannot be reconstructed from code.

This workflow sounds slow. It is not. The total time from problem statement to merged code is shorter than the old workflow because the production step -- the actual coding -- takes minutes instead of hours. The thinking time is the same as it always was. It is just no longer hidden behind typing.

What This Book Teaches

This book is not about Claude Code. Claude Code is the case study -- a 512,664-line codebase that illustrates every principle with concrete, real-world examples. But the principles are universal.

Chapter 2 teaches problem definition -- the most undervalued engineering skill. Chapters 3-4 teach constraint analysis and first principles reasoning. Chapters 5-8 teach decomposition and interface design. Chapters 9-12 teach patterns of thought: designing for failure, building feedback loops, engineering abstractions, and security as structured problem solving. Chapters 13-16 teach systems thinking: data flow, state machines, concurrency, and performance as design. Chapters 17-20 teach the AI-native engineering workflow: human-AI partnership, prompt engineering as problem engineering, verification, and what endures.

Every chapter follows the same structure: principle, concrete example from Claude Code, generalization to your work, and exercises that force you to practice.

The goal is not to make you better at using AI tools. The goal is to make you better at thinking. The tools will change. The thinking endures.

Key Principles

  1. The bottleneck has moved. Production is cheap. Problem definition, constraint analysis, and verification are the scarce skills.

  2. The 90/10 split is real. AI writes most of the code. You define what it should write and verify that it did so correctly.

  3. Constraints drive architecture. Claude Code's 400ms startup budget, single-process model, and security requirements shaped every design decision. Start with constraints, not with code.

  4. Verification is the new writing. Reading code with adversarial intent -- checking invariants, failure modes, and trust boundaries -- is the engineer's primary daily activity.

  5. The thinking is the product. Code is a byproduct of architectural decisions. The decisions are what matter. Document them. Defend them. Iterate on them.

Think About It

  1. Audit your last week of work. What percentage of your time was spent writing code versus defining problems, analyzing constraints, and verifying solutions? If you spent more than 50% writing code, identify one task where better upfront problem definition would have reduced total time.

  2. The regex trap. You need to validate email addresses in a web application. A junior engineer suggests a regex. A senior engineer says "use a library." A thinking engineer asks a different question entirely. What is that question, and how does it change the solution? (Hint: what problem are you actually solving?)

  3. Constraint discovery exercise. Take any system you work on daily. List five constraints that are not documented anywhere -- performance budgets, security assumptions, backwards compatibility requirements, user expectations. For each one, ask: if this constraint were violated, what would break?

  4. The trust boundary audit. Draw a trust boundary diagram for your application. Where does untrusted data enter the system? What prevents that data from being treated as trusted instructions? If you cannot draw this diagram, that is a finding.

  5. Decision archaeology. Find a design decision in your codebase that seems "wrong" by textbook standards (global state, large files, no abstraction layer, duplicated code). Investigate the constraints that led to it. Was it actually the right decision given those constraints? Write a one-paragraph defense of the decision, or a one-paragraph argument for changing it now that constraints have evolved.
