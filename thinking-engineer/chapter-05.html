Chapter 5: System Decomposition

Every complex system is a collection of simpler systems that someone decided to group together. The skill of system decomposition is deciding where the groups are. Get the boundaries right and each piece is small enough to understand, test, and change independently. Get them wrong and you spend your career fighting accidental coupling -- changes in one subsystem cascade unpredictably into others, every bug requires understanding the whole, and new engineers take months to become productive.

AI does not help with decomposition. You can ask a model to "break this into modules" and it will produce something plausible-looking that misses every real constraint: performance budgets, team boundaries, deployment units, security domains. Decomposition requires understanding the forces acting on a system -- the technical constraints, the organizational realities, the operational requirements -- and finding the cut lines that respect all of them simultaneously.

This chapter teaches the thinking process behind decomposition. The case study is Claude Code -- a 500K-line production AI CLI agent -- but the principles apply to any system too large for one person to hold in their head.

Why Decomposition Is Hard

Decomposition looks easy in retrospect. After the fact, every well-designed system's module boundaries seem obvious. "Of course you separate the query engine from the tool system. Of course the UI renderer is its own pillar." But before the boundaries exist, you face a continuous design space with no obvious cut lines.

The difficulty comes from three sources:

Competing forces. Every decomposition decision is a trade-off between multiple concerns. Separating the permission system from the tool executor improves testability but adds a communication boundary. Keeping them together reduces latency but creates a monolith that is hard to reason about. There is no decomposition that optimizes for all concerns simultaneously.

Hidden dependencies. The most damaging coupling is the kind you do not see until you try to change something. Two modules that share no code but both depend on the same global state are coupled. Two modules that communicate through a shared database are coupled. Two modules that must be deployed together are coupled. Decomposition must account for dependencies that do not appear in the import graph.

Future uncertainty. You are decomposing based on today's requirements, but the system will evolve. A boundary that makes sense today may be wrong in six months when a new feature needs to cross it. The best decompositions are robust to change -- they put boundaries where they are unlikely to need modification, not where they happen to be convenient right now.

These forces mean that decomposition is not a mechanical process. You cannot follow a recipe. You must think about the system's constraints, its likely evolution, and the forces acting on each potential boundary.

Top-Down vs. Bottom-Up

There are two fundamental approaches to decomposition, and experienced engineers use both -- often on the same system.

Top-Down: Divide and Conquer

Start with the whole system. Identify its primary responsibilities. Assign each responsibility to a subsystem. Repeat recursively until each subsystem is small enough to implement.

Top-down decomposition works when you understand the domain well enough to name the responsibilities. If you are building a web server, you know it needs request parsing, routing, handler dispatch, and response formatting. These responsibilities are well-established. The domain tells you where to cut.

The failure mode of top-down decomposition is premature abstraction. You divide the system into elegant subsystems that match your mental model of the domain, but your mental model is wrong. The real complexity lives at a boundary you did not anticipate, and your decomposition puts it in the worst possible place -- split across two subsystems that must coordinate tightly.

Bottom-Up: Compose from Parts

Start with the smallest useful pieces. Build utilities, then combine them into larger components, then combine those into subsystems. The structure emerges from the composition.

Bottom-up decomposition works when you do not understand the domain well enough to name the responsibilities upfront. You build what you know, see how the pieces interact, and let the architecture emerge from real constraints rather than imagined ones.

The failure mode of bottom-up decomposition is architecture drift. Without a guiding vision, each piece makes locally optimal decisions that produce globally incoherent structure. You end up with utilities that overlap, services that duplicate logic, and no clear layering.

The Pragmatic Approach

The best engineers use top-down for the first decomposition and bottom-up for refinement. Start with a rough top-down sketch -- three to five major subsystems, named by responsibility. Then build bottom-up within each subsystem, letting the internal structure emerge from implementation. Periodically step back and check whether the top-down boundaries still make sense given what you have learned.

Claude Code's Three Pillars architecture (Query Engine, Tool System, UI Renderer) was a top-down decision. The internal structure of the tool system -- the registry pattern, the execution pipeline, the permission cascade -- emerged bottom-up as the team discovered what each tool needed.

Finding Natural Seam Lines

A seam line is a place where a system can be divided with minimal coupling across the boundary. Natural seam lines exist where the system already has low coupling. Artificial seam lines require effort to maintain -- you must enforce the boundary through discipline, conventions, or technical constraints.

The Five Tests for Seam Lines

Before cutting a system at a proposed boundary, apply these five tests:

1. The Data Flow Test. Trace the primary data flows through the system. Natural seam lines run parallel to data flows, not perpendicular to them. If your proposed boundary cuts across a hot data path, every request pays the crossing cost.

In Claude Code, the boundary between the Query Engine and the Tool System is natural because data flows through them in sequence: user message enters the Query Engine, which calls the API, which returns tool requests, which cross to the Tool System for execution, which returns results back to the Query Engine. The data flow crosses the boundary twice per tool call, at well-defined points with well-defined contracts. Contrast this with a hypothetical boundary that split "text processing" from "JSON processing" -- data flows would cross that boundary dozens of times per request, because text and JSON are interleaved throughout the pipeline.

2. The Change Frequency Test. Components that change together should live together. Components that change independently should live apart. Look at your version history. Which files are always modified in the same commit? Those are tightly coupled regardless of what the module boundaries say.

Claude Code's UI Renderer changes when the terminal rendering needs work -- new components, layout changes, input handling. The Tool System changes when tools are added or modified. These two areas rarely change in the same commit. The boundary between them is natural because their change frequencies are independent.

3. The Team Boundary Test. Conway's Law states that system structure mirrors communication structure. If different teams own different subsystems, the boundaries between subsystems will reflect the boundaries between teams. This is not a bug -- it is a pragmatic recognition that coordination across team boundaries is expensive. Decompose along team lines when possible.

4. The Failure Domain Test. A failure domain is the set of components that fail together. When the API is unreachable, the Query Engine cannot function -- but the Tool System and UI Renderer can still display cached results, show error messages, and accept user input. Putting the API communication in its own subsystem means its failure does not drag down the entire system.

5. The "Could This Be a Separate Service?" Test. Imagine deploying your proposed subsystem independently -- as a separate process, a microservice, or a library. If the exercise is easy to imagine, the boundary is natural. If the exercise immediately raises questions about shared state, shared data, and tight coordination, the boundary is artificial.

Claude Code's Tool System could, in principle, be a separate service. It receives tool requests, executes them, and returns results. It does not need to know about the API, the UI, or the conversation history. The boundary is clean enough that you can imagine it running in a separate process. The Query Engine, by contrast, could not easily be separated from the context manager -- they share too much state about the conversation.

A Practical Hierarchy

When analyzing a system for decomposition, examine potential seam lines in this order:

Priority Seam Type Example
1 Trust boundary Untrusted input vs. trusted internals
2 I/O boundary Network calls vs. pure computation
3 Data domain User data vs. system configuration
4 Rate of change Stable core vs. frequently updated features
5 Technology boundary TypeScript vs. native code

Trust boundaries are the most important because they carry security implications. A misplaced trust boundary is a vulnerability. I/O boundaries are next because they determine testability -- pure computation can be tested without mocking, I/O cannot.

When to Split and When to Keep Together

Not every potential boundary should be realized. Splitting has costs: communication overhead, interface maintenance, deployment coordination, debugging difficulty. Sometimes the right answer is to keep things together.

Split When:

Independent deployment. If two components need different release cadences, split them. The tool that ships weekly should not wait for the UI that ships quarterly.

Independent scaling. If one component needs 10x more resources than another, split them so you can scale independently. In Claude Code, the Bash tool's process spawning is resource-intensive, but it runs on the user's machine, so scaling is not a concern. In a server-side agent, it would be.

Independent testing. If testing one component requires standing up another, they are too coupled. Split them so each can be tested in isolation.

Different trust levels. Code that handles untrusted input should be separated from code that operates on trusted data. The boundary between them is where validation happens.

Keep Together When:

Shared state is essential. If two components must read and write the same mutable state in real time, separating them introduces synchronization complexity that outweighs the separation benefit.

Claude Code's global state singleton (250+ fields, imported by 50+ files) is a deliberate decision to keep state together rather than distributing it across subsystems. The alternative -- passing state through dependency injection or message passing -- would add thousands of lines of plumbing to a system where every component needs to know the current model, permission mode, and session identity. The pragmatic choice: one state module with zero internal imports, accessible from everywhere.

The boundary would be crossed on every operation. If every request crosses a proposed boundary, the overhead of the crossing (serialization, validation, network) dominates the benefit of the separation.

The components share a lifecycle. If two components must start together, stop together, and recover together, separating them adds coordination complexity without independence benefit.

The Razor: Coupling vs. Cohesion

Every decomposition decision reduces to one question: does this boundary increase cohesion within the pieces more than it increases coupling between them?

Cohesion is the degree to which elements within a module belong together. High cohesion means every function, type, and constant in the module serves the same purpose. Low cohesion means the module is a grab bag of unrelated functionality.

Coupling is the degree to which modules depend on each other. Low coupling means modules can change independently. High coupling means a change in one module cascades to others.

The ideal decomposition maximizes cohesion within modules and minimizes coupling between them. In practice, you cannot optimize both simultaneously -- increasing cohesion (putting related things together) sometimes increases coupling (the related things need data from elsewhere). The art is finding the sweet spot.

Claude Code's decision to keep the permission system inside the tool pillar illustrates this trade-off. Extracting permissions into a separate pillar would increase the tool system's cohesion (it would contain only execution logic). But it would dramatically increase coupling: the permission system needs tool schemas, tool metadata, and tool-specific context. Every tool call would cross the new boundary twice (once for permission check, once for execution). The coupling cost exceeds the cohesion benefit.

The Complexity Budget

Think of your system as having a fixed complexity budget. Every boundary you add spends some of that budget on interface definition, contract maintenance, and cross-boundary debugging. Every boundary you omit spends budget on larger, harder-to-understand modules.

The art is balancing these costs. A system with too many boundaries is over-engineered -- every change requires updating interfaces, contracts, and tests across multiple modules. A system with too few boundaries is a monolith -- every change requires understanding the whole.

A practical rule of thumb: the number of major subsystems should be between 3 and 7. This maps to the cognitive limit of working memory. You should be able to draw the system's architecture on a whiteboard in under a minute, with each box representing a subsystem you can describe in one sentence.

Case Study: Claude Code's Three Pillars

Claude Code is a 500K-line TypeScript application that decomposes into three primary subsystems -- the Three Pillars. This decomposition was a top-down decision driven by the fundamental question: what does an AI CLI agent do?

The answer: it thinks (calls an LLM), it acts (executes tools), and it communicates (renders output). Three verbs, three pillars.

Why These Three and Not Four or Five

A natural question: why not separate the Permission System from the Tool System? Why not make the Context Manager its own pillar?

The Permission System stays with the Tool System because permissions are meaningless without tools. Every permission rule references a tool name (Bash(git diff *), Read(./.env)). Every permission check receives tool-specific context. Separating them would require the Permission System to import tool definitions, creating a circular dependency. They share a data domain -- tool metadata -- and changing one almost always requires considering the other.

The Context Manager stays with the Query Engine because context management is inextricable from query construction. The context window budget determines what goes into the API call. The compaction decision depends on the current token usage, which depends on the current system prompt, which depends on the registered tools. Pulling the Context Manager out would require it to query the Query Engine for state it already has.

The API Client stays with the Query Engine because it exists to serve the agent loop. The API client's design -- beta header latching, prompt cache management, retry strategies -- exists entirely because the agent loop needs stable, cached, resilient model communication. Without the agent loop, the API client has no reason to exist.

The Decomposition Forces in Action

Look at how the five tests apply to this decomposition:

Data Flow Test. The primary data flow is linear: user input enters the Query Engine, the Query Engine calls the API, the API returns tool requests, tool requests cross to the Tool System, the Tool System returns results, results go back to the Query Engine, and the Query Engine sends the final response to the UI Renderer. The data flow crosses each boundary at defined points with defined types. The boundaries run parallel to the flow, not perpendicular.

Change Frequency Test. The Tool System changes most frequently -- new tools are added, existing tools are modified, permission rules evolve. The Query Engine changes when the API protocol changes, context management algorithms improve, or new caching strategies are needed. The UI Renderer changes when the terminal rendering needs work. These three change frequencies are largely independent. A new Bash tool security rule does not require a Query Engine change. A new context compaction tier does not require a UI change.

Failure Domain Test. When the API is down, the Query Engine cannot function, but the Tool System can still validate inputs and the UI can still accept user input and display cached content. When a tool crashes, the Query Engine catches the error, formats it as a tool result, and continues. When the UI renderer throws (a React rendering exception, for instance), the other two pillars are unaffected -- the conversation state and tool execution pipeline remain intact. Each pillar fails independently.

Independent Service Test. The Tool System could plausibly be a separate process that receives tool requests over a socket and returns results. The interface is narrow enough. The Query Engine could be a separate service that communicates with the API and dispatches tool requests. The UI Renderer could be a separate process that receives rendering instructions. In practice, they run in one process for simplicity, but the boundaries are clean enough that separation is architecturally feasible.

How the Pillars Communicate

The three pillars communicate through narrow, well-defined interfaces:

From To Interface Data
Query Engine Tool System tool_use block Tool name + JSON input
Tool System Query Engine tool_result block Execution result + metadata
Query Engine UI Renderer Streaming message events Text, tool progress, errors
UI Renderer Query Engine User input Text message
Tool System UI Renderer Permission dialogs Tool name, arguments, context

Five interfaces connecting three pillars. Each interface carries one type of data in one direction. The Query Engine never reaches into the Tool System's internals to check tool state. The Tool System never reads the conversation history directly. The UI Renderer never calls the API. Each pillar operates on its own data and communicates through messages.

This is the hallmark of good decomposition: the interfaces are narrow and the data flow is unidirectional where possible.

Beneath the three pillars lies a shared infrastructure layer that every pillar depends on: global state (250+ fields), the hook engine (27 lifecycle events), session management (JSONL persistence), and telemetry (OpenTelemetry instrumentation).

The infrastructure layer has a critical property: it imports nothing from the pillars. The global state module has zero imports from the rest of the codebase. The hook engine processes events without knowing which pillar generated them. This one-way dependency is enforced by a custom ESLint rule (bootstrap-isolation) that prevents the state module from importing anything that might transitively pull in pillar code.

Why does this matter? If the state module imported from the Tool System (to access tool definitions, say), and the Tool System imported from the state module (to read the current permission mode), you have a circular dependency. Now the state module cannot initialize without the Tool System, which cannot initialize without the state module. By keeping the infrastructure layer at the leaf of the import graph, every pillar can import it safely without creating cycles.

The Module Dependency Graph

The pillars decompose further into a six-layer dependency hierarchy:

Layer Contains Imports From
L0: Foundation Global state, types, constants Nothing internal
L1: Utilities Bash parser, permission evaluator, hook engine L0
L2: Services API client, MCP client, analytics L0, L1
L3: Tools Tool registry, all tool implementations L0, L1, L2
L4: Orchestration Agent loop, context assembler L0-L3
L5: UI REPL, components, layout engine L0-L4

Each layer imports only from layers below it. This is not enforced by the language -- TypeScript does not have layer-level visibility -- but it is enforced by convention and the import linting rule. Violations exist (resolved through lazy require() calls that break cycles at runtime), but they are tracked and justified.

The layer hierarchy is the decomposition within the decomposition. The Three Pillars answer "what are the major subsystems?" The layers answer "what order do they initialize, and what depends on what?"

Breaking the Layers: Lazy Loading

No layer hierarchy survives contact with reality perfectly. Circular dependencies will appear. The question is not how to prevent them entirely -- it is how to manage them when they occur.

Claude Code uses lazy require() to break cycles at runtime without breaking them at build time:

const getTeammateUtils = () =>
  require('./utils/teammate.js') as typeof import('./utils/teammate.js')

Instead of a top-level import (which executes at module load time and forces the dependency to be resolved before any code runs), the module is loaded on first call. This breaks the cycle because the dependent module does not need to be resolved during initialization. The as typeof import(...) cast preserves full type safety at the TypeScript level while deferring the actual module load to runtime.

This pattern is not a hack -- it is a deliberate choice. Alternatives like dependency injection containers would add runtime complexity and performance overhead. Event systems would add indirection that obscures the code flow. Lazy loading solves the problem simply: the module is loaded when needed, not when imported. The cycle exists in the code but does not exist at initialization time.

The key discipline: every lazy require() is documented with a comment explaining which cycle it breaks and why. Without this documentation, future engineers cannot distinguish intentional cycle-breaking from accidental lazy loading.

Decomposition Anti-Patterns

The Premature Split

You split a component before understanding its internal structure. The boundary turns out to cut through the densest part of the coupling graph. Now every change requires modifying both sides of the boundary and updating the interface between them.

Symptom: Most commits touch files on both sides of a module boundary.

Fix: Merge the components back together. Re-split only when you understand the real coupling structure. The cost of an unnecessary merge is one afternoon. The cost of maintaining a bad boundary is permanent.

The God Module

One module accumulates responsibilities because no one wants to decide where new features belong. It grows to thousands of lines with dozens of exports. New engineers import from it because "everything is there." The module becomes a dependency of everything.

Symptom: One module appears in 50+ import statements across the codebase.

Claude Code's global state module deliberately accepts this role -- it is imported by 50+ files. But it earns that position by having zero internal imports. It is a leaf in the import graph, not a hub. A god module that both imports and exports widely is the anti-pattern; a foundation module that only exports is a deliberate architectural choice.

The Distributed Monolith

You split the system into services, but they all depend on the same database, deploy together, and fail together. You have the operational overhead of a distributed system with none of the benefits.

Symptom: You cannot deploy one service without deploying all of them. An outage in one service takes down all of them.

Fix: If the components share state, lifecycle, and failure domains, they are one system. Make them one process. Distribute only when you need independent scaling, deployment, or failure isolation.

The Abstraction Inversion

You create an abstract interface between two modules, but the abstraction does not match the real boundary. Callers must work around the abstraction to get the behavior they need, and implementations must jump through hoops to satisfy a contract that does not fit their natural structure.

Symptom: Extensive use of "escape hatches" -- methods like getUnderlying(), raw(), or asSpecificType() that bypass the abstraction.

Fix: The abstraction is in the wrong place. Remove it and let the concrete types flow until you find the real boundary.

Decomposition as Decision

Every decomposition is a decision with long-lasting consequences. Like all architectural decisions, it should be documented with its rationale, considered alternatives, and trade-offs. When you decompose a system, write down:

  1. What you split -- the components and their responsibilities.
  2. Why you split there -- which of the five tests (data flow, change frequency, team boundary, failure domain, independent service) motivated the boundary.
  3. What you considered and rejected -- alternative decompositions and why they lost.
  4. What would change your mind -- the conditions under which you would re-merge or re-split.

This record serves your future self and your team. When someone asks "why is the permission system inside the tool system?" there is a document that explains the reasoning. When requirements change and the boundary no longer makes sense, there is a record of the original rationale to evaluate against the new reality.

Key Principles

  1. Decomposition is not a mechanical process. It requires understanding the forces acting on the system: data flow, change frequency, team boundaries, failure domains, and trust levels.

  2. Natural seam lines run parallel to data flows, not perpendicular. Boundaries that cut across hot data paths create communication overhead on every request.

  3. Split what changes independently. Keep together what changes together. Version history tells you where the real coupling is, regardless of what the module boundaries claim.

  4. The infrastructure layer must import nothing from the layers above it. One-way dependencies prevent circular imports and enable safe initialization ordering.

  5. Three to seven major subsystems. Matches the cognitive limit of working memory. If you cannot draw the architecture on a whiteboard in under a minute, you have too many pieces.

  6. Every boundary spends complexity budget. Too many boundaries over-engineer the system. Too few create a monolith. The art is finding the balance.

Think About It

Exercise 1: The Boundary Audit. Take a system you work on. Draw its current module boundaries on a whiteboard. Now look at the last 50 commits. For each commit, mark which modules were changed. If most commits touch multiple modules, your boundaries do not match your change patterns. Where would you re-draw them?

Exercise 2: The Merge Thought Experiment. Pick two modules in your system that communicate heavily. Imagine merging them into one. What would you gain? (Simpler communication, fewer interfaces, less ceremony.) What would you lose? (Independent testing, separate ownership, clear responsibility.) If the gains outweigh the losses, you should probably merge them.

Exercise 3: The Service Extraction Test. Pick a subsystem in your monolith. Imagine extracting it as a standalone service with an RPC interface. List every piece of shared state it currently accesses. That list is the coupling you would need to eliminate. If the list is short (2-3 items), extraction is feasible. If it is long (10+ items), the boundary is not natural.

Exercise 4: The Layer Violation Hunt. Map your codebase's import graph. Find every import that goes "upward" -- from a lower layer to a higher one. Each such import is a potential circular dependency waiting to happen. For each violation, determine whether it should be eliminated (by moving code to a lower layer), inverted (by introducing a callback or interface), or accepted (by using lazy loading to break the cycle at runtime).

Exercise 5: The Three-Pillar Exercise. Take any application you have built or worked on. Decompose it into exactly three pillars, each described in one sentence. If you cannot find three, the system may be too simple for this exercise. If you find more than three, decide which responsibilities should merge. The constraint of exactly three forces you to find the highest-level decomposition -- the one that explains the system to a new engineer in thirty seconds.
