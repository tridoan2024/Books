Chapter 7: The Architecture of Decisions

Every production system is a fossil record of decisions. The code you ship is the sum of thousands of choices — some deliberate, some accidental, some brilliant, some desperate. The difference between a system that ages gracefully and one that collapses under its own weight is not the quality of individual decisions, but the process by which decisions are made, recorded, and revisited.

This chapter is about that process. We will examine Architecture Decision Records (ADRs) as thinking tools, not bureaucratic artifacts. We will build trade-off matrices that force rigor on decisions that intuition alone cannot resolve. We will distinguish reversible decisions from irreversible ones and calibrate our decision-making process accordingly. And we will study one of the most instructive decisions in Claude Code's architecture: the choice to use global mutable state instead of dependency injection — a decision that violates every textbook recommendation and is exactly right.

7.1 Decisions Are the Architecture

Junior engineers think architecture is about boxes and arrows. Senior engineers know architecture is about decisions. The boxes and arrows are consequences.

When someone asks "what's the architecture?", they are really asking three questions:

  1. What decisions were made? Global state or DI? Monolith or microservices? REST or gRPC?
  2. Why were those decisions made? What constraints existed? What trade-offs were accepted?
  3. Are those decisions still valid? Have the constraints changed? Should we revisit?

A system with clear architectural documentation answers all three. A system without it can only answer the first — and only by reading the code, which tells you what but never why.

The Cost of Lost Context

Every engineer has experienced this: you open a file, see a pattern that looks wrong, and "fix" it. Three days later, tests fail in production because the "wrong" pattern was load-bearing. The original developer had a reason for it, but that reason existed only in their head, and they left the company two years ago.

This is the cost of undocumented decisions. Not the cost of the decision itself — the decision might have been excellent — but the cost of losing the reasoning. Without the reasoning, every future engineer must either:

  • Reverse-engineer the intent from the code (expensive, error-prone)
  • Ask someone who was there (impossible after turnover)
  • Assume it was arbitrary and change it (dangerous)

Architecture Decision Records exist to prevent this. They are not bureaucracy. They are engineering memory.

7.2 ADRs as Thinking Tools

Michael Nygard's lightweight ADR format has four sections. Each one forces a specific kind of thinking:

# ADR-0042: Use Global Mutable State for Application State

## Status
Accepted

## Context
[What forces are at play? What constraints exist?]

## Decision
[What did we decide?]

## Consequences
[What are the trade-offs? What becomes easier? What becomes harder?]

Why This Format Works

The format is valuable not because of what it captures, but because of what it forces you to articulate before you write code.

Context forces constraint discovery. Writing the Context section requires you to enumerate the forces shaping the decision. Most engineers skip this step. They jump from "we have a problem" to "here's my solution" without mapping the constraint space. The Context section is where you discover that the real constraint is not technical but organizational, or that the constraint you assumed was fixed is actually flexible.

Decision forces commitment. Vague decisions produce vague architectures. "We'll use some kind of caching" is not a decision. "We will use a session-scoped in-memory cache with LRU eviction and a 500ms debounce on invalidation" is a decision. The Decision section forces you to be specific enough that another engineer could implement it without asking questions.

Consequences forces honesty. Every decision has costs. The Consequences section forces you to enumerate them. This is where you write "Test isolation will require a manual reset function in beforeEach" instead of pretending global state has no downsides. Honesty in the Consequences section is what separates architectural documentation from marketing.

When to Write an ADR

Not every decision needs an ADR. The heuristic: write an ADR when the decision is hard to reverse or when reasonable engineers would disagree.

Decision ADR? Why
Use TypeScript for a new TypeScript project No No reasonable alternative exists in context
Use global state vs. dependency injection Yes Reasonable engineers disagree strongly
Name a variable userId vs user_id No Trivially reversible
Use a monolithic binary vs. CLI + daemon Yes Structural, expensive to reverse
Choose between two logging libraries Maybe Depends on how deeply integrated
Cache API headers for prompt cache stability Yes Non-obvious, has financial implications

The threshold is roughly: if you would need to explain your decision in a code review comment of more than two sentences, it deserves an ADR.

7.3 The Trade-Off Matrix

Some decisions resist intuition. When you are choosing between three database engines, four caching strategies, or two fundamentally different architectural patterns, the number of factors exceeds what you can hold in your head. This is where the trade-off matrix earns its place.

Structure

A trade-off matrix is a table where rows are options and columns are evaluation criteria, each weighted by importance:

Criterion Weight Option A Option B Option C
Startup speed 5 4 (20) 2 (10) 3 (15)
Test isolation 3 2 (6) 5 (15) 3 (9)
Code simplicity 4 5 (20) 2 (8) 3 (12)
Refactoring ease 2 2 (4) 5 (10) 4 (8)
Total 50 43 44

Scores are 1-5 (5 = best). The weighted score is in parentheses. The total tells you which option wins across all criteria.

Why the Matrix Works

The matrix does three things that gut-feel decision-making cannot:

  1. Surfaces hidden criteria. Building the column list forces you to articulate all the things you care about, not just the loudest one. Engineers naturally anchor on whichever criterion they thought of first. The matrix corrects for this.

  2. Makes weights explicit. Two engineers might agree that "test isolation" matters but disagree on how much. Making weights explicit turns implicit disagreements into explicit ones that can be resolved.

  3. Separates scoring from weighting. You might score Option B highest on test isolation (5/5) but still reject it because test isolation has low weight relative to startup speed. The matrix keeps these two judgments separate.

When the Matrix Lies

The matrix is a tool for structured thinking, not a decision algorithm. It can lie in three ways:

Criteria are not independent. If "startup speed" and "binary size" are both columns, and they correlate strongly (smaller binary = faster startup), you are double-counting the same underlying factor. Fix: identify correlated criteria and merge them or reduce one's weight.

Scores are fabricated precision. Is Option A really a 4 on startup speed, or could it be a 3? The difference between 3 and 4 at weight 5 is 5 points — enough to swing the total. Fix: use only three values (1, 3, 5) instead of five. Less precision, but the rankings are more robust.

The matrix cannot capture non-linear effects. Option B might score well on every criterion but have a fatal flaw that the matrix averages away. A database that is fast, cheap, and well-documented but loses data under network partitions gets a reasonable total score despite being unusable. Fix: add "deal-breaker" criteria that are pass/fail, not scored.

Use the matrix to structure your thinking. Then use your judgment to make the decision.

7.4 Reversible vs. Irreversible Decisions

Jeff Bezos calls them one-way doors and two-way doors. The concept is simple: some decisions can be undone cheaply, others cannot.

One-Way Doors (Irreversible)

These decisions are expensive or impossible to reverse once made:

  • API contract published to external clients. Once third parties build against your API, removing or changing a field breaks them. You can add, but you cannot subtract.
  • Data format committed to storage. Once you write billions of records in format A, migrating to format B is a multi-month project with risk of data loss.
  • Architectural topology. Switching from monolith to microservices (or vice versa) after two years of development is a rewrite, not a refactor.
  • The serialization format of session persistence. Claude Code chose JSONL for session files. Once millions of sessions exist on disk, changing the format requires a migration path that supports both old and new formats indefinitely.

One-way doors deserve maximum deliberation. ADRs, trade-off matrices, prototype implementations, team reviews. The cost of getting it wrong is measured in months, not hours.

Two-Way Doors (Reversible)

These decisions can be undone cheaply:

  • Which linter to use. Switching from ESLint to Biome requires updating config files and running the new linter. A day of work, not a month.
  • Default values. Changing a timeout from 2 seconds to 5 seconds is a one-line change with a deploy.
  • Internal function signatures. Renaming parameters, reordering arguments, splitting functions — these are refactors, not rewrites.
  • Runtime feature flags. Claude Code's GrowthBook integration lets behavior change without redeployment. A runtime flag is, by definition, a two-way door.

Two-way doors deserve speed, not deliberation. Make the decision with 70% of the information you wish you had, ship it, and adjust based on feedback.

The Meta-Decision

The most important decision is deciding which kind of decision you are making. Engineers over-deliberate two-way doors (spending a week choosing between two equivalent libraries) and under-deliberate one-way doors (committing to a database schema in an afternoon).

A useful rule of thumb: if you can reverse the decision in less time than you would spend deliberating it, just decide. If reversing takes longer than deciding would have, slow down and use the full toolbox — ADRs, matrices, prototypes, reviews.

7.5 Decision Fatigue and the Power of Defaults

Herbert Simon's concept of "satisficing" — choosing an option that is good enough rather than optimal — is the antidote to decision fatigue. In engineering, satisficing manifests as defaults.

Why Defaults Matter

Every configurable system is a collection of decisions deferred to the user. Each configuration option says: "I couldn't decide, so you decide." Too many options and the user is paralyzed. Too few and the system is inflexible.

Claude Code's configuration cascade (Chapter 5 covered this in detail for the architecture book) has seven layers of configuration. But the critical design insight is not the layers — it is the defaults. A fresh installation with zero configuration works correctly. The model defaults to Sonnet. The permission mode defaults to "ask for writes." Auto-compaction is enabled. The context window is 200K tokens.

These defaults are not arbitrary. Each one is a decision made by the engineering team on behalf of all users who will never touch a config file. Most users never will. The defaults are the architecture for 90% of users.

The Default as a Decision Record

Every default should be justified:

Setting Default Justification
Model Sonnet Best cost/quality balance for typical development tasks
Permission mode Default (ask for writes) New users should see what the agent does before trusting it
Auto-compaction Enabled Prevents context overflow; no sane reason to disable
Startup flag fetch timeout 2 seconds p99 network latency with margin; fail-open on timeout
Max output tokens 8,000 (with escalation) p99 actual output is ~5K; saves 4-8x GPU reservation

Look at the last row. The default of 8,000 max output tokens seems wrong — the model can produce 32,000. But the engineering team analyzed the output distribution: p99 is 4,911 tokens. Setting the default to 32,000 wastes 6.5x GPU capacity globally. Setting it to 8,000 with automatic escalation to 64,000 when needed serves 99%+ of requests efficiently and handles the tail with one retry per 100 requests. The default encodes a sophisticated engineering decision that most users will never see.

Decision Fatigue in API Design

Tool design for AI agents is particularly susceptible to decision fatigue — not for the user, but for the LLM. Claude Code has 35+ tools. Each tool call is a decision the model makes. If each tool has ten parameters, the model faces a combinatorial explosion of possibilities.

The antidote: tools with good defaults. The BashTool requires only command. The optional timeout, description, and run_in_background parameters have sensible defaults. The model makes one decision (what command to run) instead of four. The principle of least surprise (Chapter 6 of the outline) applies here: a tool that does the obvious thing with minimal parameters reduces the decision load on both the model and the user.

7.6 Case Study: Global State vs. Dependency Injection

This is the most instructive decision in Claude Code's architecture because it violates conventional wisdom and is exactly right. Understanding why it is right teaches more about architectural decision-making than any textbook.

The Decision

Claude Code uses a global mutable singleton for application state: a single object with 250+ fields, accessed through approximately 130 typed accessor functions. Not dependency injection. Not a service container. Not event sourcing.

Every senior engineer reading this just flinched. Global mutable state is the first thing you learn to avoid. It makes testing hard. It creates implicit dependencies. It resists refactoring. The entire dependency injection ecosystem exists to solve the problems that global state creates.

And yet, for this system, global state is the correct choice.

The Constraints That Change Everything

Three constraints specific to Claude Code's domain make DI the wrong choice:

Constraint 1: Single process, single thread. A CLI agent runs as one process with one user. There is no concurrent mutation. The primary argument for DI — isolating dependencies to manage concurrency — does not apply. There is no race condition to prevent because there is only one execution context.

Constraint 2: Deep call stacks. The path from a user prompt to tool execution to permission evaluation to bash security analysis traverses 15+ function calls. With DI, every function in that chain needs a context parameter:

// With DI: context parameter in every signature
function handlePrompt(ctx: AppContext, prompt: string): Promise<Response> {
  const assembled = assembleContext(ctx, prompt);
  const response = await callApi(ctx, assembled);
  for (const tool of response.toolCalls) {
    const result = await executeTool(ctx, tool);
  }
}

// With global state: clean signatures
function handlePrompt(prompt: string): Promise<Response> {
  const assembled = assembleContext(prompt);
  const response = await callApi(assembled);
  for (const tool of response.toolCalls) {
    const result = await executeTool(tool);
  }
}

Across hundreds of functions, the ctx parameter becomes noise. It appears in every signature but most functions only read one or two fields. The signal-to-noise ratio of the code degrades measurably.

Constraint 3: Cross-cutting concerns. Telemetry, cost tracking, session identity, model usage, and feature flags are accessed from every architectural layer. In a DI framework, these become "singleton-scoped" services — which is global state with an abstraction layer on top. The abstraction buys you nothing in a single-process application. It is complexity without benefit.

The Trade-Offs Accepted

The engineering team did not pretend global state has no costs. They enumerated them and designed mitigations:

Test isolation. Every test must start with a clean state. The solution: a resetStateForTests() function that overwrites every field with fresh defaults, called in beforeEach. This is boilerplate, but it is straightforward boilerplate.

Implicit dependencies. When a function calls getSessionId(), the dependency on global state is invisible in the function signature. The mitigation: accessor functions are grep-able. getSessionId() finds every consumer. setSessionId() finds every mutation point.

Refactoring difficulty. Removing a state field requires finding all accessor calls. The mitigation: the accessor pattern (not exporting the raw state object) means field renames require changing one accessor, not 50+ direct property accesses.

The Guard Rails

Global state without discipline is a disaster. Three patterns prevent it:

  1. No direct export of the state object. Only accessor functions are exported. STATE.sessionId = "oops" cannot appear in arbitrary files.

  2. Atomic update functions. Fields that must change together have a single update function. switchSession() atomically updates sessionId, sessionProjectDir, and emits a signal. There is no separate setSessionId().

  3. Import DAG leaf constraint. The state module has zero imports from the rest of the codebase. An ESLint rule enforces this. The state module can be imported by any module without creating circular dependencies.

The Decision Through the ADR Lens

Let us write the ADR for this decision:

# ADR-001: Global Mutable State for Application State

## Status
Accepted

## Context
Claude Code is a single-process, single-user CLI agent. Call stacks
reach 15+ levels from prompt to tool execution. Cross-cutting concerns
(telemetry, cost tracking, session state, feature flags) are accessed
from every layer. The team considered dependency injection, service
locators, and event sourcing.

## Decision
Use a global mutable singleton accessed through ~130 typed accessor
functions. No direct export of the state object. Atomic update
functions for fields that must change together. ESLint rule enforcing
zero imports in the state module.

## Consequences
- POSITIVE: Clean function signatures (no ctx threading)
- POSITIVE: No abstraction overhead for cross-cutting concerns
- POSITIVE: Simple mental model (one state, one source of truth)
- NEGATIVE: Test isolation requires manual resetStateForTests()
- NEGATIVE: Implicit dependencies (invisible in function signatures)
- NEGATIVE: Cannot easily switch to multi-process without rewrite
- MITIGATED: Accessor pattern makes dependencies grep-able
- MITIGATED: Import DAG constraint prevents circular dependencies

What This Decision Teaches

The decision teaches three principles:

Principle 1: Constraints determine correctness. DI is not universally "better" than global state. It is better under specific constraints (concurrent processes, large teams, multiple implementations). Change the constraints (single process, single user, deep call stacks) and the calculus inverts. The textbook answer is wrong when the textbook's assumptions do not match your reality.

Principle 2: Accept trade-offs explicitly. The team did not choose global state because they did not know about DI. They chose it after evaluating the alternatives and accepting the costs. The costs are documented. The mitigations are implemented. This is deliberate engineering, not negligence.

Principle 3: Guard rails make dangerous patterns safe. Global state is dangerous in general. Global state with accessor functions, atomic updates, ESLint enforcement, and test-reset discipline is safe in this specific context. The pattern is not "use global state." The pattern is "use global state with these five guard rails."

7.7 The Decision Cascade

Individual decisions do not exist in isolation. They form a cascade where each decision constrains or enables subsequent ones.

graph TD
    A["Single-process CLI agent"] -->|enables| B["Global mutable state"]
    A -->|requires| C["400ms startup budget"]
    A -->|justifies| D["Monolithic binary"]

    B -->|simplifies| E["Deep call stacks"]
    B -->|requires| F["Test reset discipline"]
    B -->|enables| G["Cache latching"]

    C -->|drives| H["Parallel I/O in bootstrap"]
    C -->|drives| I["Compile-time flag elimination"]

    D -->|enables| J["Shared types, no schema drift"]
    D -->|combined with| I

    G -->|driven by| K["Prompt cache economics"]

    style A fill:#e94560,stroke:#1a1a2e,color:#fff
    style K fill:#e94560,stroke:#1a1a2e,color:#fff

The root decision — "this is a single-process CLI agent" — cascades through the entire architecture. It enables global state (no concurrency concerns), requires fast startup (CLI users expect responsiveness), and justifies a monolith (one user, one binary). Global state enables cache latching (simple boolean fields in a singleton). The startup budget drives compile-time flags (smaller binary = faster load). Cache economics shape context compaction strategy (preserve the cached prefix, compact the middle).

This cascade is what coherent architecture looks like. Not a collection of independent "best practices" applied in isolation, but a web of decisions that reinforce each other because they all derive from the same root constraints.

Identifying Root Decisions

When analyzing any system, look for the root decisions — the ones from which everything else follows. In Claude Code:

  • "Single-process CLI" is a root decision. Everything about state management, startup, and deployment follows from it.
  • "Global state" is a derived decision. It follows from the root, enabled by the single-process constraint.
  • "Cache latching" is a leaf decision. It follows from global state and cache economics.

Changing a leaf decision is cheap. Changing a root decision is a rewrite. Know which is which before you start.

7.8 Making Decisions Under Uncertainty

Most real decisions happen with incomplete information. You do not know the future traffic pattern. You do not know which feature will be most popular. You do not know whether the third-party API will change its rate limits.

The 70% Rule

Make the decision when you have 70% of the information you wish you had. At 50%, you are guessing. At 90%, you have wasted time gathering information that will not change the outcome. The 70% threshold is the sweet spot where you have enough data to make a defensible choice without analysis paralysis.

Reversibility as a Decision Accelerator

The 70% rule has a corollary: lower the threshold for reversible decisions. If you can undo it in an afternoon, decide at 50%. If undoing it takes six months, wait until 85%.

Claude Code's dual feature flag system embodies this principle:

  • Runtime flags (GrowthBook): Reversible in seconds. No deployment needed. Decide fast, adjust based on data.
  • Compile-time flags: Reversible only with a new release. Decide carefully, because rolling back requires a deploy cycle.

The system design itself encodes the reversibility of each decision type.

Documenting Uncertainty

The most valuable thing you can add to an ADR is an explicit statement of what you did not know:

## Unknowns at Decision Time
- We do not know if the model output distribution will change with
  future model versions. The 8K default assumes p99 < 5K tokens.
  If future models produce longer output, the escalation will fire
  more frequently, adding latency.
- We do not know if cache economics will change. The 7x cost
  difference between cache hit and miss drives cache latching.
  If pricing changes, this optimization may become unnecessary.

These unknowns are the most useful part of the ADR two years later. When the model does produce longer output and the escalation fires on 10% of requests instead of 1%, the unknown statement tells the future engineer exactly which assumption changed and what to revisit.

Key Principles

1. Architecture is decisions, not diagrams. The boxes and arrows are consequences of decisions. Document the decisions, and the diagrams draw themselves.

2. ADRs are thinking tools, not compliance artifacts. The value is in writing them (forcing clarity), not in reading them (though that helps too).

3. Use trade-off matrices when intuition fails. When the decision space is too large for gut feel, structure it. Then override the matrix with judgment if it misses something important.

4. Calibrate deliberation to reversibility. One-way doors deserve ADRs, matrices, and reviews. Two-way doors deserve a quick decision and a willingness to course-correct.

5. Constraints determine correctness. The "right" pattern depends on the constraints. Global state is wrong in general and right for a single-process CLI. Know your constraints before reaching for conventions.

6. Document what you don't know. The most valuable line in an ADR is the one that says "we assumed X, and if X changes, revisit this decision."

7. Decisions cascade. Root decisions constrain derived decisions. Know which decisions are root (expensive to change) and which are leaf (cheap to change).

Think About It

Exercise 1: Identify the Root Decision Take a system you work on. List ten architectural decisions. For each, trace it back: does it derive from another decision on the list? Which decisions are roots (nothing else forces them) and which are derived? What would change if you reversed a root decision?

Exercise 2: Write the ADR for a "Wrong" Decision Find a decision in your codebase that violates conventional wisdom (a large file that "should" be split, a pattern that "should" be different, a dependency that "should" be abstracted). Write an ADR for it. Can you articulate why it is right in context? If you cannot, it might actually be wrong — and now you have the framework to fix it.

Exercise 3: The Reversibility Audit List five decisions you made in the last month. For each, estimate the time to reverse it (hours, days, weeks, months). For each, estimate the time you spent deliberating. Did you spend proportionally more time on the harder-to-reverse decisions? If not, recalibrate.

Exercise 4: Build a Trade-Off Matrix Choose a decision you are currently facing (library choice, API design, infrastructure selection). Build a trade-off matrix with at least five criteria. Weight the criteria. Score the options. Does the matrix agree with your intuition? If not, examine why — did you weight a criterion incorrectly, or is your intuition wrong?

Exercise 5: The Decision Cascade Draw the decision cascade for your system, following the format in Section 7.7. Start with the root decisions (deployment model, language, single/multi-tenant) and trace how they constrain everything downstream. Find one derived decision that conflicts with its root — a place where the architecture is internally inconsistent. What would it take to resolve the inconsistency?
