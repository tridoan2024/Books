Chapter 16: Performance as Design

Performance is not optimization. Optimization is what you do after the system exists -- profiling hotspots, tightening loops, adding caches. Performance is what you do before the system exists -- choosing architectures that make fast execution structurally possible.

The distinction matters because architecture determines the performance ceiling. Optimization only gets you closer to it. A system with a fundamentally sequential startup path cannot be optimized below the sum of its sequential steps. A system designed with parallel I/O from the start has a ceiling set by the slowest single operation, not the sum of all operations. No amount of micro-optimization can close the gap between those two ceilings.

This chapter teaches the thinking discipline behind performance-as-design: how to identify the critical path before writing code, how to apply Amdahl's Law to system design decisions, how to build performance budgets that constrain architecture, and how to measure before -- and instead of -- guessing. We use Claude Code's 400ms startup as the case study: a budget that shaped every design decision from module loading to I/O scheduling to process spawning.

16.1 Architecture Determines the Ceiling

Consider two architectures for the same system -- a CLI tool that needs to read configuration, authenticate, and render a UI.

Architecture A: Sequential

Read config (15ms) → Authenticate (65ms) → Load modules (135ms) → Render UI (165ms)
Total: 380ms

Architecture B: Parallel I/O with Deferred Loading

Start I/O: config (15ms) + auth (65ms)     ← fire-and-forget
Start synchronous: load modules (135ms)      ← overlap with I/O
Sync point: collect I/O results (0ms)        ← already resolved
Render UI (165ms)
Total: 300ms

Architecture A's ceiling is 380ms. No optimization can make it faster without changing the architecture. You could shave 5ms off config reading, 10ms off module loading -- but the sequential dependency chain is the fundamental constraint.

Architecture B's ceiling is 300ms (135ms module load + 165ms UI render, with I/O hidden behind the module load). The 65ms authentication cost is invisible -- it completes during the 135ms of module evaluation. The architecture made performance possible. Optimization would address the remaining 300ms.

The difference between these architectures is not cleverness. It is the decision to think about timing relationships before writing code. Which operations have data dependencies? Which are truly independent? Where can I/O overlap with computation?

The Critical Path

The critical path is the longest sequential chain through your system's dependency graph. It is your absolute performance floor -- no amount of parallelism can reduce execution time below it.

Identifying the critical path is the first step in performance-as-design. Once you know it, every subsequent decision is informed by a simple question: "Does this add to the critical path, or can it run in parallel?"

16.2 Measurement Before Optimization

The single most important performance discipline is measurement before optimization. Not because measurement is novel advice -- everyone knows it -- but because the urge to optimize without measuring is extraordinarily strong, and the results of unmeasured optimization are consistently wrong.

Why Intuition Fails

Engineers' performance intuitions are wrong roughly 80% of the time. We overestimate the cost of things we can see (function calls, object allocations) and underestimate the cost of things we cannot see (cache misses, context switches, module evaluation). We optimize the code we just wrote -- because it is fresh in our minds -- not the code that actually dominates execution time.

Consider Claude Code's startup. An engineer might look at the 16-step init() function and think "that must be the bottleneck -- 16 steps!" In reality, the critical init steps (Steps 1-3, 9-11, 15) take a combined 25ms. Module evaluation (a single import() call) takes 135ms. The REPL first paint (framework overhead) takes 165ms. Those two operations -- neither of which looks "complex" -- account for 77% of startup time.

Without measurement, an engineer might spend a week optimizing init() and save 5ms. With measurement, they know the optimization targets are module evaluation (tree-shaking, deferred imports) and REPL rendering (unavoidable framework cost, target for future replacement).

The Measurement Architecture

Claude Code's startup profiler is deliberately minimal -- it adds microseconds per checkpoint, not milliseconds:

const checkpoints: Array<{
  name: string;
  time: number;       // performance.now() relative to process start
  delta: number;      // time since previous checkpoint
  memory?: NodeJS.MemoryUsage;
}> = [];

export function profileCheckpoint(name: string): void {
  const now = performance.now();
  const delta = checkpoints.length > 0
    ? now - checkpoints[checkpoints.length - 1].time
    : now;
  checkpoints.push({ name, time: now, delta });
}

Two details matter:

  1. performance.now() over Date.now(). Sub-millisecond resolution versus millisecond resolution. When you are measuring a 3ms CLI parse phase, millisecond resolution gives you "3ms" -- useless for detecting regressions. Sub-millisecond resolution gives you "3.142ms" -- useful.

  2. Delta between checkpoints, not just absolute time. The delta tells you the cost of each phase independently. When a 2ms phase regresses to 12ms, the delta column catches it immediately.

Checkpoint Placement Strategy

Checkpoints are placed at decision boundaries -- the moments where the execution path might diverge:

cli_entry                    →  Before any routing decision
cli_before_main_import       →  Before the 135ms import
cli_after_main_import        →  After — measures eval cost
main_tsx_entry               →  First line of main module
run_before_parse             →  Before argv parsing
run_after_parse              →  After — measures parse cost
action_after_hooks           →  preAction hook complete
main_after_run               →  REPL mounted, cursor visible

The naming convention -- component_event -- makes checkpoints greppable across versions. When investigating a regression, you diff the checkpoint output: "The delta between cli_before_main_import and cli_after_main_import increased by 40ms in version 2.3 -- the import graph grew."

The Profiling Report

With detailed profiling enabled, each checkpoint captures RSS and heap usage alongside timing:

[+  0.000ms] (+  0.000ms) cli_entry              | RSS: 42.1MB, Heap: 12.3MB
[+  2.340ms] (+  2.340ms) cli_before_main_import | RSS: 42.8MB, Heap: 12.5MB
[+137.892ms] (+135.552ms) cli_after_main_import  | RSS: 98.4MB, Heap: 45.2MB
[+389.221ms] (+251.329ms) main_after_run         | RSS: 112.7MB, Heap: 58.6MB

This data answers specific questions:

  • "Is the import graph growing?" -- Watch cli_after_main_import delta across releases.
  • "Is there a memory leak in startup?" -- Compare RSS at cli_entry across versions.
  • "Which phase regressed?" -- Compare the delta column across commits.

The lesson is general: instrument your critical path permanently, not just during debugging. Profiling checkpoints cost microseconds and prevent weeks of regression investigation.

16.3 The Performance Budget

A performance budget is a constraint that shapes architecture the way a financial budget shapes spending. You have a fixed amount of time (or memory, or tokens), and every feature must justify its withdrawal from the budget.

Claude Code's 400ms Startup Budget

The budget allocation:

pie title Startup Time Budget (390ms)
    "Module Evaluation" : 135
    "REPL First Paint" : 165
    "Settings + Auth" : 20
    "Feature Flags" : 50
    "Session + Telemetry" : 15
    "Entry + Parsing" : 5
Phase Budget Bottleneck Optimization Lever
Entry + parsing 5ms JS parse of entry file Keep entry minimal
Module evaluation 135ms Transitive import graph Tree-shaking, deferred imports
Settings + Auth 20ms File I/O (5 files) + keychain Prefetch, parallel reads
Feature flags 50ms Network (CDN fetch) Timeout + cached fallback
Session + telemetry 15ms Directory creation, UUID Fast-path for existing dirs
REPL first paint 165ms Layout engine (Yoga/WASM) Framework cost (unavoidable)

The budget enforces discipline in four ways.

First, it prevents death by a thousand cuts. Without a budget, each team adds "just 10ms" of initialization. After 20 teams, startup is 200ms slower. With a budget, each 10ms must be justified: where does it come from? What other phase gives up its allocation?

Second, it forces design decisions. When the feature flags phase was designed, the team had to choose: synchronous fetch (blocking until CDN responds) or async with timeout (proceed with defaults if CDN is slow). The budget made the decision obvious: 50ms timeout with cached fallback. A synchronous fetch could take 2,000ms on a slow network, blowing the entire budget.

Third, it identifies what cannot be optimized. Two phases dominate: module evaluation (135ms) and REPL first paint (165ms). Together they are 77% of the budget. Module evaluation is constrained by JavaScript's single-threaded parser -- you cannot make it parse faster without changing the runtime. REPL first paint is constrained by the Ink/Yoga layout engine. These are framework costs. The budget makes it explicit: 77% of startup time is outside our direct control.

Fourth, it defines what stays off the critical path. Operations deliberately excluded from startup because they would blow the budget:

Operation Cost Why Excluded
MCP server startup 200-500ms each Started lazily on first MCP tool call
Git repository indexing 50-500ms Deferred to first query
Full schema validation ~10ms Only critical fields validated at startup
LSP server connection 500ms-2s Connected when first needed

The principle: if it can wait until the user's first interaction, defer it. The startup path is reserved for operations that must complete before the cursor can blink.

16.4 Amdahl's Law Applied to System Design

Amdahl's Law states that the speedup from parallelizing a computation is limited by the fraction that must remain sequential. If 50% of your work is inherently sequential, perfect parallelization of the other 50% gives you at most a 2x speedup -- regardless of how many cores you throw at it.

Most engineers learn Amdahl's Law in a theoretical context and then forget it. That is a mistake. It is the most powerful tool for reasoning about whether a performance optimization is worth pursuing.

The Formula in Practice

Speedup = 1 / (S + P/N)

Where:
  S = fraction of work that is sequential
  P = fraction of work that can be parallelized (S + P = 1)
  N = number of parallel workers

Apply this to Claude Code's startup:

  • Sequential work: Module evaluation (135ms) + CLI parse (3ms) + Settings (15ms) + REPL (165ms) = 318ms
  • Parallelizable work: MDM read (20ms) + Keychain reads (60ms) + API preconnect (150ms) = 230ms
  • Total sequential time: 548ms
  • S = 318/548 = 0.58
  • P = 230/548 = 0.42

Maximum speedup with infinite parallelism: 1 / 0.58 = 1.72x

Actual speedup with current parallelism: 548ms → 390ms = 1.41x

Current efficiency: 1.41 / 1.72 = 82% of theoretical maximum.

This tells the team something precise: they are getting 82% of the available parallelism benefit. Investing more engineering effort in parallelizing startup I/O has diminishing returns. The remaining gains are in reducing the sequential work (135ms module eval, 165ms REPL) -- which requires architectural changes, not optimization.

Amdahl's Law for Multi-Agent Systems

The same law applies to Claude Code's multi-agent orchestration. When a parent dispatches two parallel subagents:

  • Sequential work: Delegation prompt construction + result aggregation = ~200ms
  • Parallel work: Code review (30s) + Security review (45s) = 75s
  • S = 200ms / 75.2s = 0.003
  • Maximum speedup: 1 / 0.003 = 333x (with infinite agents)
  • Actual speedup: 75s → 45s = 1.67x (with 2 agents)

The sequential fraction is tiny (0.3%), so parallelism helps enormously. But with only 2 agents, you get 1.67x -- far below the theoretical maximum. Adding a third parallel agent (e.g., test coverage analysis at 20s) would give:

  • Sequential: 75s → 45s → 45s (still bounded by the 45s security review)
  • The third agent adds no wall-clock improvement because it finishes before the slowest agent

This is the practical Amdahl's insight: parallelism is bounded by the slowest parallel task, not by the number of workers. Adding more workers helps only if the work can be subdivided into roughly equal chunks.

16.5 Fast-Path Exits: Paying Only for What You Use

A fast-path exit is an early return that avoids expensive initialization when it is not needed. It is one of the highest-leverage performance patterns because it eliminates work entirely rather than making it faster.

Claude Code's entry point is a router, not an initializer. It reads just enough of process.argv to determine which execution path to take:

Invocation What Loads Time
claude --version Nothing ~5ms
claude mcp serve MCP server module only ~80ms
claude -p "prompt" Phases 0-12 (no REPL) ~225ms
claude (interactive) Full 13-phase pipeline ~390ms

The --version path is the extreme case: it prints a version string and exits in 5ms. No configuration, no authentication, no module loading. In a CI/CD pipeline running claude --version as a health check across 50 containers, the difference between 5ms and 390ms is 19.25 seconds per deployment cycle.

The Cost of a Misplaced Import

Fast-path exits require discipline at the entry point. A single misplaced import can destroy the fast path:

// DON'T DO THIS: adds ~135ms to every invocation
import { logger } from './utils/logger.js';

async function main() {
  if (args[0] === '--version') {
    console.log(VERSION);  // Now takes 140ms instead of 5ms
    return;
  }
}

That import transitively pulls in the logging framework, which depends on configuration, which depends on settings file I/O. The 5ms --version path becomes 140ms. The rule is strict: top-level imports in the entry point are limited to language built-ins and build constants. Everything else is a dynamic import() behind a conditional.

This is a performance-as-design decision, not an optimization. It constrains how the entry point is written. It forces any new feature that adds to the entry point to justify its import. The constraint breeds better design: features that could be top-level imports are instead lazy-loaded, which also improves memory usage for paths that never need them.

The Non-Interactive Fast Path

When invoked with claude -p "prompt", the tool skips two expensive phases:

  1. Trust Dialog (Phase 9) -- Skipped because non-interactive mode trusts implicitly
  2. REPL Launch (Phase 13) -- Replaced with a single query loop, saving 165ms

The 165ms savings from skipping the REPL makes claude -p suitable for scripting. The import graph for non-interactive mode is roughly 40% smaller because the entire Ink rendering framework, Yoga layout engine, and React component tree are never loaded.

The design principle: separate expensive initialization from the execution paths that do not need it. This is not "lazy loading" in the general sense -- it is architectural separation of concerns where the concern is "what does this execution path actually require?"

16.6 The Prefetch-Rendezvous Pattern

The most architecturally significant performance pattern in Claude Code's startup is prefetch-rendezvous: start I/O operations early, do unrelated work while they complete, then collect results at the latest possible moment.

The Pattern

// 1. Module-level promise holder
let prefetchPromise: Promise<Result> | null = null;

// 2. Fire function (called early in the pipeline)
export function startPrefetch(): void {
  prefetchPromise = doExpensiveIO();
}

// 3. Retrieve function (called late, with fallback)
export function getPrefetchedResult(): Promise<Result> {
  return prefetchPromise ?? doExpensiveIO();
}

Three properties make this pattern safe:

Idempotent fallback. If the prefetch was never started (different platform, different code path), the retrieve function falls back to a direct call. The caller never needs to know whether the result was prefetched.

Promise-based coordination. No callbacks, no events, no shared mutable state. The prefetch stores a promise; the consumer awaits it. If the promise is already resolved, the await completes synchronously.

Failure isolation. Each prefetch catches its own errors and returns a safe default. A failed keychain read does not crash the MDM read or the module evaluator.

The Timing Diagram

Time 0ms:    Start MDM + keychain subprocesses (fire-and-forget)
Time 2ms:    Start module import (135ms of synchronous JavaScript parsing)
Time ~20ms:  MDM subprocess completes (result stored in promise)
Time ~30ms:  Keychain subprocess completes (result stored in promise)
Time 137ms:  Module import completes
Time 140ms:  CLI parsing completes
Time 140ms:  preAction hook fires → await prefetch results
             → MDM promise: already resolved (settled 120ms ago) → <1ms
             → Keychain promise: already resolved (settled 110ms ago) → <1ms

The overlap is 135ms of module evaluation during which three I/O operations complete. Without the overlap, these operations would add 65ms to the sequential critical path. With the overlap, they add approximately 0ms.

Where to Place the Rendezvous

The rendezvous point should be:

  1. After as much unrelated work as possible (maximizing overlap)
  2. Before any code that depends on the prefetched result (maintaining correctness)
  3. At a natural synchronization point (reducing architectural complexity)

Claude Code uses Commander.js's preAction hook -- the moment between CLI argument parsing and command execution. This is a natural boundary in the program's lifecycle. It gives the prefetches 140ms of overlap (far more than the 30ms they need) while ensuring results are available before any command logic runs.

The general rule: the best rendezvous point is the last natural boundary before the data is needed. Not "somewhere in the middle" -- at the last possible moment. This maximizes the chance that the async work is already complete when you await it.

16.7 Cache Hierarchies and Economics

Caching is the most powerful performance tool and the most dangerous. Every cache is a bet: "this value will be requested again before it changes." When the bet pays off, you save the cost of recomputation. When it does not, you serve stale data and introduce a correctness bug.

The Cache Hierarchy in AI Agent Systems

Claude Code operates a multi-level cache hierarchy, each level with different characteristics:

Level What Hit Cost Miss Cost Invalidation
In-memory memoization Function results 0ms Full recomputation Manual or TTL
Prompt cache (API-side) System prompt + early messages 1/10th input cost Full input cost Byte-level: any change invalidates
File system Settings, credentials ~1ms read ~30ms subprocess File modification time
MCP connection cache Server connections Reuse existing Full handshake (30s timeout) On transport close
Auth token cache OAuth tokens File read Full OAuth flow (seconds) 15-minute TTL

Cache Economics: The 10x Rule

Claude Code's prompt cache deserves special attention because it illustrates the economics of caching at scale. The API-side prompt cache stores the byte sequence of the system prompt and early conversation messages. A cache hit costs 1/10th of a cache miss.

This 10x ratio drives profound design decisions:

  1. Context compression must be cache-aware. Every compression strategy must answer: "Does this bust the prompt cache?" Modifying any byte in the cached region invalidates the cache and costs 10x more on every subsequent API call. The entire cache-aware microcompact tier in Claude Code's context management exists because modifying local message bytes would invalidate a cache that cost 50-70K tokens to create.

  2. Stability is worth paying for. The system prompt is assembled in a specific order with stable content first and volatile content last. The cache anchors on the stable prefix. This means system prompt sections are ordered by volatility, not by logical grouping -- a design decision that is worse for readability but dramatically better for cache hit rates.

  3. MCP tool loading interacts with caching. Non-deferred MCP tools disable global prompt caching because they vary per user. By deferring MCP tools to name-only references (loaded on demand), the system preserves the 90% cost reduction from cached prefills. This is why Claude Code spent significant engineering effort on deferred tool loading -- not for startup speed, but for per-request cache economics.

The Memoization Hierarchy

Claude Code uses three memoization layers at different granularities:

Layer Key Invalidation Example
Connection name-${jsonStringify(config)} On transport close MCP server connections
Tool/Resource fetch Server name (LRU, max 20) On close or notification MCP tool discovery
Auth cache Server name (file, 15-min TTL) TTL expiry OAuth tokens

The MCP connection memoization prevents duplicate connections to the same server. Without it, two tool calls in rapid succession would each try to establish a new connection. The memoization key includes the full serialized config so that a config change forces a new connection.

The LRU cache for tool fetches caps at 20 entries because Claude Code sessions typically connect to fewer than 20 MCP servers. The cap prevents unbounded memory growth in edge cases (a test script that connects and disconnects hundreds of times).

When Caches Become Liabilities

Caches become liabilities when:

  1. Invalidation is incorrect. Serving stale data is worse than serving no data. Claude Code invalidates all MCP caches on connection close specifically to prevent stale tool closures that reference dead processes.

  2. Cache thundering herd. When a cache expires and all consumers simultaneously try to repopulate it. Claude Code's init() function uses memoization (not caching) specifically because memoization collapses concurrent calls into a single execution -- multiple callers awaiting init() share the same promise.

  3. Cache hides the real cost. When a cache masks a 500ms operation, you stop optimizing the operation. Then the cache fails in production and everything is slow. The performance budget should account for cache miss costs, not just cache hit costs.

16.8 Deferred Work: Loading Only What You Need

Deferred loading is the principle that no module, connection, or resource should be initialized until it is actually needed. It is the inverse of eager initialization, and it interacts with performance budgets by keeping costs off the startup critical path.

The Three Flavors

// Flavor 1: Awaited import — result needed before proceeding
const main = await import('./main.js');

// Flavor 2: Fire-and-forget — side effect, no result needed
void import('./analytics.js').then(m => m.initialize());

// Flavor 3: Conditional — only loaded for specific features
if (isRemoteSession()) {
  const proxy = await import('./proxy.js');
}

Each flavor has different performance characteristics:

Flavor Blocks Execution? When to Use
Awaited Yes Module's exports are needed immediately
Fire-and-forget No Side effects that can run in the background
Conditional Only when condition is true Features not needed on every execution path

The Import Budget

On a modern machine, module evaluation costs are roughly proportional to code volume:

Module Category Typical Size Eval Time
Utility module (pure functions) 200-500 lines <1ms
Service module (class + deps) 1,000-3,000 lines 2-5ms
UI framework (React/Ink) 5,000-10,000 lines 15-30ms
Full transitive graph ~16,800 lines ~135ms

The 135ms for the full import graph is the floor -- JavaScript's single-threaded parser cannot go faster. The optimization is ensuring that fast paths (--version, MCP serve, bridge mode) never pay this cost.

What Gets Deferred in Claude Code

Operation Eager Cost Deferred Strategy
MCP server startup 200-500ms each Started on first MCP tool invocation
Git repository indexing 50-500ms Deferred to first file query
Full schema validation ~10ms Only critical fields validated at startup
LSP server connection 500ms-2s Connected when first language feature needed
Analytics initialization ~50ms Fire-and-forget during init pipeline

Each deferral has the same justification: the operation's cost exceeds its value at startup time. An MCP server that might never be used should not cost 300ms on every startup. A git index needed only when the user asks about files should not delay the cursor from appearing.

The design discipline: question every operation on the startup path. Does the user need this before they can type their first character? If not, defer it.

16.9 Graceful Degradation Under Performance Constraints

Performance-as-design includes designing what happens when performance targets cannot be met. Network timeouts, slow filesystems, overloaded CPUs -- production systems encounter conditions that make the performance budget unreachable. The design question is: what degrades, and how?

The Timeout Hierarchy

Every network operation in Claude Code's startup has an explicit timeout:

Operation Timeout Degradation
Feature flags (GrowthBook CDN) 2,000ms Use coded defaults
MCP registry prefetch 3,000ms No autocomplete for MCP servers
Remote managed settings 5,000ms Use cached/local settings
API preconnect None (best-effort) First API call does its own connect

The timeouts are aggressive. GrowthBook gets 2 seconds -- enough for a CDN hit, not enough for a retry on network issues. The philosophy: network unreliability should never block a local tool. If the CDN is slow, use defaults and fetch again in the background.

The Failure Cascade Design

Each startup phase has a designed failure mode:

Phase Failure Degradation
MDM read Subprocess fails Empty MDM settings; no enterprise overrides
Keychain read Permission denied Falls back to environment variable auth
Settings cascade Malformed JSON Warning in header; uses defaults
Authentication No credentials Restricted mode; prompts user
Feature flags CDN unreachable All flags use coded defaults
Trust dialog User declines Restricted mode; project config ignored
Telemetry Provider init fails No-op providers; silent
REPL launch Terminal not interactive Falls back to basic I/O mode

The design principle: Claude Code should always start. A broken config, missing credentials, or unreachable service degrades functionality but never prevents startup. The only fatal failure is a missing core dependency during module evaluation -- and even that produces a clear error message rather than a cryptic stack trace.

This is performance-as-design applied to failure: the architecture is designed so that slow or failed components do not block the critical path. Each component has a fallback that is fast (using defaults is faster than fetching settings) and safe (degraded is better than broken).

16.10 Input Buffering: Perceived Performance

Performance is not just wall-clock time. It is perceived performance -- how fast the system feels. A 400ms startup with no input loss feels faster than a 300ms startup that drops the first two characters the user typed.

The Problem

Between starting the main module import and the REPL mounting, there is a 300ms window where the terminal accepts input but nothing is listening. Users who start typing immediately lose their keystrokes.

The Solution

Claude Code captures terminal input during the load window and replays it when the REPL mounts:

export function startCapturingEarlyInput(): void {
  const buffer: Buffer[] = [];

  process.stdin.setRawMode?.(true);
  process.stdin.resume();

  const onData = (chunk: Buffer) => buffer.push(chunk);
  process.stdin.on('data', onData);

  earlyInputReplay = () => {
    process.stdin.removeListener('data', onData);
    return Buffer.concat(buffer);
  };
}

When the REPL mounts, it calls earlyInputReplay() and injects the buffered keystrokes into the input field. The user sees their text appear as if the tool was ready the instant they pressed Enter.

The setRawMode(true) call is load-bearing. Without it, the terminal line-buffers input and will not deliver characters until the user presses Enter. Raw mode delivers each keystroke immediately, which is what the REPL expects.

Edge cases handled:

Input During Load Behavior
Regular text Buffered, replayed into input field
Ctrl+C Buffered as \x03, causes graceful exit on replay
Escape sequences (arrows) Buffered as multi-byte sequences, replayed correctly
Paste (large text) Buffered entirely, replayed as single event
No input Empty buffer, replay is a no-op

The Lesson

Any tool that takes more than 50ms to start should buffer user input during initialization. Losing the user's first keystrokes creates a perception of unreliability that no amount of actual performance improvement can fix. A system that is 10% slower but never drops input feels faster than one that is 10% faster but occasionally loses characters.

16.11 Performance Anti-Patterns

Knowing what not to do is as valuable as knowing what to do. These anti-patterns recur in every system where performance matters.

Anti-Pattern 1: The Monolithic Init

function init() {
  readConfig();         // 15ms
  authenticate();       // 65ms
  loadModules();        // 135ms
  connectDatabase();    // 200ms
  startMCPServers();    // 500ms
  renderUI();           // 165ms
}
// Total: 1,080ms — every invocation pays full price

The fix: decompose into phases with explicit dependencies. Operations that do not depend on each other run in parallel. Operations that are not needed on every code path are deferred.

Anti-Pattern 2: Premature Abstraction for Performance

Building a caching layer before measuring whether the underlying operation is a bottleneck. Building a thread pool before knowing whether parallelism helps. Adding a queue before understanding the throughput requirements.

The fix: measure first. Know the current numbers. Calculate the theoretical improvement. Then decide whether the engineering investment is justified.

Anti-Pattern 3: Optimizing the Wrong Layer

Spending time optimizing function-level micro-benchmarks while the architectural bottleneck is a synchronous network call. Shaving nanoseconds off a hash function while the database query takes 50ms.

The fix: profile the system end-to-end. Identify where time is actually spent. Optimize the largest contributors first. Claude Code's profiling data shows that 77% of startup time is in two phases (module eval + REPL paint). Optimizing anything else has at most a 23% ceiling on improvement.

Anti-Pattern 4: Ignoring Cache Invalidation

Adding a cache makes the system faster. Forgetting to invalidate the cache makes the system wrong. "Wrong" is worse than "slow." Claude Code invalidates all MCP caches on connection close, not because it is convenient, but because serving stale tool references that point to dead processes produces confusing errors that are nearly impossible to debug.

Anti-Pattern 5: The Invisible Tax

Adding "just 10ms" of startup work. Ten features later, startup is 100ms slower and no single change is responsible. The fix: a performance budget with explicit accounting. Every addition must declare its cost and justify its allocation.

16.12 Case Study: The 400ms Budget in Practice

Let us trace how the 400ms performance budget shaped a specific design decision: where to load feature flags.

The Problem

Claude Code uses GrowthBook for feature flags. Feature flags control which features are enabled, what models are available, and how aggressive context compression should be. They need to be loaded before the first API call -- otherwise the system makes decisions without knowing the configuration.

The Constraint

The CDN fetch for feature flags takes 50ms on a cache hit, 200ms on a cache miss, and can timeout at 2,000ms on a slow network. The 400ms budget cannot accommodate a 200ms+ synchronous fetch.

The Design Decision

Feature flags are loaded with a 2,000ms timeout and a cached fallback:

  1. If the CDN responds within the startup window: use fresh flags.
  2. If the CDN is slow or unreachable: use cached flags from the last successful fetch.
  3. If no cache exists (first run): use coded defaults compiled into the binary.

The implications ripple through the architecture:

  • Every feature flag must have a sensible coded default, because the first run has no cache.
  • Feature flags that change behavior dramatically (like enabling a new model) must degrade gracefully when the default is used.
  • The cache is not just a performance optimization -- it is a correctness mechanism for offline operation.

Why Not Fire-and-Forget?

An alternative design: start the CDN fetch as fire-and-forget and use defaults until it resolves. This would eliminate the feature flag cost from the startup budget entirely.

The problem: feature flags influence settings cascade resolution, which influences tool availability, which influences the system prompt. If flags arrive mid-session, the system prompt changes, which invalidates the prompt cache, which costs 10x on the next API call. The performance savings at startup are offset by a performance cost on the first interaction.

The budget forced a disciplined analysis. The team calculated: 50ms for feature flags (CDN cache hit) saves 10x on every subsequent API call by keeping the prompt cache stable. That 50ms investment pays for itself after 2 API calls. The budget analysis said: spend the 50ms.

Key Principles

Architecture Before Optimization: The architecture determines the performance ceiling. Optimization gets you closer to it but cannot exceed it. Design the ceiling high -- think about critical paths, parallel opportunities, and data dependencies before writing code.

Measure Before Acting: Engineers' performance intuitions are wrong 80% of the time. Profile the actual system. Identify where time is actually spent. Optimize the largest contributors first.

Budget Milliseconds Explicitly: A performance budget forces discipline. Every feature must declare its cost and justify its allocation. Without a budget, death by a thousand 10ms additions is inevitable.

Amdahl's Law is Your Planning Tool: Calculate the sequential fraction before parallelizing. If 60% of your work is sequential, perfect parallelism of the rest gives at most 2.5x speedup. Know the ceiling before investing in parallelism.

Fast-Path Exits Eliminate Work Entirely: The fastest code is code that never runs. Design entry points as routers that skip expensive initialization for simple operations.

Prefetch-Rendezvous Hides I/O: Start async operations as early as possible. Do unrelated synchronous work during the wait. Rendezvous at the latest natural boundary. The overlap window turns sequential I/O into parallel I/O for free.

Design Degradation, Not Just Performance: Every network operation needs a timeout. Every timeout needs a fallback. Every fallback needs a coded default. The system should always start, even when the world is slow.

Cache Economics Drive Architecture: When a cache hit is 10x cheaper than a miss, architectural decisions about what to cache and how to invalidate become first-class design concerns, not afterthoughts.

Think About It

  1. The Budget Exercise: You are building a web application with a target time-to-interactive of 2 seconds. The current architecture: load HTML (200ms), parse CSS (100ms), download JS bundle (800ms), parse JS (300ms), hydrate React (400ms), fetch initial data (500ms). Total: 2,300ms. You are 300ms over budget. Using the principles from this chapter, design a strategy to meet the budget. Which operations can overlap? Which can be deferred? Which need fast-path exits? What is the critical path after your changes?

  2. The Amdahl's Calculation: Your CI/CD pipeline runs 5 stages: lint (10s), unit tests (60s), integration tests (120s), build (30s), deploy (20s). Currently all sequential: 240s total. You can parallelize lint + unit tests + build (they are independent). Integration tests depend on build. Deploy depends on integration tests. Calculate the theoretical maximum speedup. Calculate the actual speedup with 3 parallel workers. Where is the bottleneck? Would adding more workers help?

  3. The Cache Invalidation Design: You are building a system where users configure their preferences, and a downstream service caches these preferences for 5 minutes to avoid database reads. A user changes their preferences and immediately tests the change. They see the old preferences. Design a cache invalidation strategy that handles this case without eliminating the performance benefit of caching. Consider: cache-aside, write-through, and event-driven invalidation. Which is best for this scenario and why?

  4. The Prefetch Decision: Your application makes three API calls during initialization: user profile (50ms), feature flags (100ms), and notification count (30ms). Only user profile is needed before the first render. Feature flags affect the UI layout. Notification count is displayed in a badge. Design the prefetch and rendezvous strategy. When does each call start? When is each result awaited? What is the critical path of your design versus a sequential design?

  5. The Framework Tax: Your team chose a UI framework that adds 200ms of render time to every page load. This is 50% of your 400ms budget. The framework provides excellent developer experience and the team is productive with it. A lighter framework would save 150ms but require rewriting 60% of the application. Using the performance budget framework from this chapter, how do you evaluate this trade-off? What data would you need to make the decision? At what point does the framework tax become unacceptable?
