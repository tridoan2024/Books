Chapter 9: Design for Failure

Optimists build features. Engineers build failure modes.

Ask a junior engineer what their system does and they will describe the happy path: the user submits a request, the service processes it, the database stores it, the response returns. Ask a senior engineer the same question and they will tell you what happens when the database is down, the network partitions, the disk fills up, the upstream service returns garbage, and the user submits the same request fourteen times in two seconds.

The difference between these two descriptions is the difference between a prototype and a production system. A prototype demonstrates that something can work. A production system demonstrates that something keeps working when everything around it is trying to make it stop.

This chapter is about the discipline of failure-first thinking: designing every component to answer the question "What happens when I fail?" before answering "What do I do when I succeed?" We will examine graceful degradation, circuit breakers, retry strategies, timeout hierarchies, and the blast radius concept. The running case study is Claude Code's MCP server lifecycle -- a subsystem that manages connections to five or ten external servers simultaneously, any of which can crash, hang, or disappear at any moment, without ever taking the agent down with them.

The Failure-First Mindset

Most engineering education is success-oriented. Textbooks teach you how to build things that work. Courses grade you on correct output. Code reviews focus on whether the logic is right. But production systems spend most of their operational lifetime dealing with failure -- partial failure, transient failure, cascading failure, silent failure.

The failure-first mindset inverts the design process. Before writing the happy path, you write the failure inventory:

Question Why It Matters
What are my dependencies? Each one is a failure source
What happens when each dependency fails? Determines blast radius
How will I detect the failure? Silent failure is worse than loud failure
How will I recover? Manual vs. automatic recovery
How long can I tolerate the failure? Determines timeout strategy
What do my users see during the failure? Determines degradation strategy

This is not pessimism. It is realism applied to distributed systems. Network calls fail. Processes crash. Disks fill up. Memory leaks. Certificates expire. DNS flakes. These are not exceptional events -- they are the baseline operating conditions of any system that runs long enough.

The Optimism Tax

Every component built without failure handling accumulates what I call the optimism tax: the cost you pay later when reality contradicts your assumptions. The tax compounds. A service that assumes its database is always available requires an emergency patch at 3 AM when the database goes down. That patch, written under pressure, introduces a new bug that manifests when the database comes back up with stale connections. That bug requires another emergency patch. Each iteration costs more than the last, because each one is built on the shaky foundation of the previous one.

The alternative is to pay the failure-handling cost upfront, when you are calm, rested, and thinking clearly. Design the retry logic before you need it. Build the circuit breaker before the cascade happens. Write the graceful degradation path before users are screaming.

Claude Code's architects understood this. The MCP server lifecycle manager -- the subsystem that connects the agent to external tool servers -- was designed failure-first. Every state in the connection state machine has an explicit failure transition. Every failure transition has a recovery strategy. Every recovery strategy has a fallback when recovery fails. The result: when an MCP server crashes (and they crash), the agent continues operating with reduced capability rather than dying alongside it.

The Blast Radius Concept

When something fails, the first question is not "how do I fix it?" The first question is "how far does the damage spread?"

The blast radius of a failure is the set of functionality affected when a component goes down. A well-designed system has small blast radii -- each failure affects only its immediate neighborhood. A poorly designed system has large blast radii -- one failure cascades through the entire system.

Isolation as Architecture

The primary technique for controlling blast radius is isolation: ensuring that components cannot infect each other with their failures.

Claude Code achieves this through independent connection management for each MCP server. Each server gets its own:

  • Process (for stdio servers) or TCP connection (for HTTP servers)
  • State machine instance tracking connection health
  • Reconnection timer with independent backoff
  • Health monitoring with independent ping intervals
  • Tool registry entries that can be added or removed independently

When the memory server crashes, the memory tools disappear from the agent's tool list. The database connector, the CI/CD bridge, the API gateway -- all continue operating normally. The agent tells the model "the memory tool is currently unavailable" and the model adapts its strategy. It does not tell the model "everything is broken."

This isolation comes at a cost. Independent state machines mean more code, more memory, more complexity in the lifecycle manager. A shared connection pool would be simpler. But simplicity in the implementation would buy complexity in the failure modes -- a single shared pool means a single shared failure.

The Principle: Independent Failure Domains

Every external dependency should be its own failure domain. When you design a system that talks to five services, you should be able to draw five independent circles around them. A failure inside any one circle should not escape to the others.

This applies recursively. Within a single service connection, the initialization handshake, the health monitoring, and the tool dispatch are separate failure domains. A failed health check should trigger reconnection, not crash the tool dispatcher. A failed tool call should return an error to the model, not corrupt the health monitor's state.

Graceful Degradation

When a component fails and cannot be immediately recovered, the system has two choices: stop entirely or continue with reduced capability. Graceful degradation is the engineering discipline of choosing the second option and doing it well.

The Degradation Hierarchy

Not all components are equally important. A production system should classify its dependencies by criticality and define explicit behavior for each level:

Category Example Behavior When Down
Enhancement Memory server, analytics Continue normally, note reduced context
Functional Database connector, API gateway Continue with warning, some tasks impossible
Critical Authentication provider Warn user, block protected operations
Fatal Language model API Cannot proceed, exit with clear error

The key insight: in Claude Code, no MCP server is fatal. The agent can always continue without any individual MCP server. The model API is the only true fatal dependency. This design choice reflects a principle: the system should degrade gracefully all the way down to its irreducible core, and nothing external should be part of that core.

Dynamic Tool Registry

Claude Code implements graceful degradation through a dynamic tool registry. When an MCP server disconnects, its tools are removed from the model's tool list. When it reconnects, its tools are re-added. The model sees different tool lists on different turns -- not because the system is broken, but because the system is honestly reporting what is currently available.

sequenceDiagram

    Agent->>Registry: Re-add memory tools
    Agent->>Registry: Get available tools
    Registry-->>Agent: [search_memory, save_fact, query_db, list_tables]
    Agent->>Model: System prompt + 4 tools
    Note over Model: Memory tools available again

This approach is superior to returning errors for unavailable tools. If the model sees search_memory in its tool list, it may try to call it and get an error. If the tool is simply absent, the model never tries. The model's behavior naturally adapts to available capabilities without needing special error-handling logic.

The Error Message as Interface

When degradation does produce an error (for example, a tool call arrives while the server is reconnecting and the wait times out), the error message itself is a design artifact:

Tool 'search_memory' is currently unavailable (memory server disconnected). 
You can continue without memory context, or suggest the user restart the 
memory server.

This message is crafted for the model, not the user. It tells the model three things: what happened, what it can still do, and what it cannot do. The model uses this information to adjust its approach -- perhaps retrieving information from the codebase instead of from memory, or informing the user that results may be incomplete.

Compare this with a typical error message:

Error: ECONNREFUSED 127.0.0.1:8886

This tells the model nothing actionable. It does not know what capability was lost, what alternatives exist, or what to tell the user. The quality of your degradation experience is directly proportional to the quality of your error messages.

Retry Strategies

When a transient failure occurs, the first instinct is to try again. This instinct is correct -- most network errors, rate limits, and service hiccups are transient. But naive retry logic causes more problems than it solves.

The Thundering Herd

Consider a service that goes down for 10 seconds. During those 10 seconds, 100 clients accumulate failed requests. When the service comes back, all 100 clients retry simultaneously. The sudden spike of 100 concurrent requests overwhelms the just-recovered service, which goes down again. The cycle repeats until someone manually intervenes.

This is the thundering herd problem, and it is the most common retry-related failure in distributed systems. The solution has two parts: exponential backoff and jitter.

Exponential Backoff with Jitter

Attempt 1:  base_delay * 2^0 + jitter  =  1s   + rand(0, 500ms)
Attempt 2:  base_delay * 2^1 + jitter  =  2s   + rand(0, 500ms)
Attempt 3:  base_delay * 2^2 + jitter  =  4s   + rand(0, 500ms)
Attempt 4:  base_delay * 2^3 + jitter  =  8s   + rand(0, 500ms)
Attempt 5:  base_delay * 2^4 + jitter  =  16s  + rand(0, 500ms)
Attempt 6+: capped at max_delay        =  30s  + rand(0, 500ms)

Exponential backoff ensures that each failed attempt waits longer than the last, reducing pressure on the recovering service. Jitter ensures that clients that failed at the same time do not retry at the same time, distributing the retry load over a wider window.

The parameters matter:

Parameter Claude Code MCP Default Rationale
Base delay 1 second Short enough for quick recovery from transient failures
Max delay 30 seconds Long enough to avoid hammering a struggling server
Max attempts 10 ~3 minutes of total retry time before giving up
Jitter range 0-500ms Decorrelates concurrent reconnection attempts

These are not arbitrary. A 1-second base delay means that a server that crashed and restarted in 2 seconds is reconnected within 3 seconds. A 30-second max delay means that a server experiencing sustained issues is not pounded with connection attempts. Ten total attempts over approximately 3 minutes gives the server ample time to recover before the client gives up.

The Retry-After Contract

Sometimes the server knows better than the client how long to wait. HTTP APIs communicate this through the Retry-After header on 429 (rate limited) and 529 (overloaded) responses. A well-behaved client always respects this header, overriding its own calculated backoff:

function calculateRetryDelay(attempt: number, retryAfterHeader?: string): number {
  // Server's instruction always wins
  if (retryAfterHeader) {
    const seconds = parseInt(retryAfterHeader, 10)
    if (!isNaN(seconds)) return seconds * 1000
  }

  // Client-side exponential backoff with proportional jitter
  const baseDelay = Math.min(500 * Math.pow(2, attempt - 1), 32000)
  const jitter = Math.random() * 0.25 * baseDelay
  return baseDelay + jitter
}

The server's instruction "always wins" is not a guideline -- it is a contract. The server set that delay because it knows its own recovery timeline. Ignoring it is like a patient telling their surgeon "I'll decide when the anesthesia kicks in."

Error Classification

Not all errors deserve the same retry strategy. A production retry engine classifies errors before deciding how to handle them:

Error Type Status Code Strategy
Rate limited 429 Respect Retry-After, exponential backoff
Overloaded 529 Exponential backoff, consider fallback after 3 consecutive
Auth expired 401/403 Refresh credentials, retry once
Context overflow 400 (prompt too long) Reduce parameters, retry
Stale connection ECONNRESET Reconnect, retry
Client error 400 (other) Do not retry -- fix the request
User abort Signal.aborted Do not retry -- user canceled

The classification is a priority-ordered ladder, not a flat switch. Some errors match multiple categories. A 429 during a rate-limited period with expired credentials is both a rate limit and an auth error. The first matching handler wins, which means the order of the ladder encodes your recovery priorities.

Circuit Breakers

Retry logic handles individual request failures. Circuit breakers handle systemic failures -- when the entire service is down and retrying individual requests is wasteful.

The Three States

stateDiagram-v2
    [*] --> Closed
    Closed --> Open : Failure threshold exceeded<br/>(5 failures in 60s)
    Closed --> Closed : Success resets counter
    Open --> HalfOpen : Cooldown expires (30s)
    Open --> Open : All requests rejected instantly
    HalfOpen --> Closed : Probe succeeds
    HalfOpen --> Open : Probe fails, restart cooldown

Closed is the normal state. Requests flow through. Failures are counted in a sliding window. When failures exceed a threshold (e.g., 5 in 60 seconds), the breaker trips to Open.

Open is the protective state. All requests fail immediately without contacting the service. This protects both the client (no wasted time waiting for failures) and the server (no additional load while recovering). A cooldown timer runs.

Half-Open is the probe state. When the cooldown expires, one request is allowed through as a probe. If it succeeds, the breaker closes. If it fails, the breaker re-opens.

Why Circuit Breakers Matter

Without a circuit breaker, during a provider outage, every tool call triggers a retry sequence -- potentially 10 attempts with exponential backoff. Multiply by every concurrent agent sharing that provider. A single user's session could generate hundreds of failed API calls per minute. The circuit breaker reduces this to one probe every 30 seconds.

The sliding window (filtering timestamps older than the window size) is a critical implementation detail. Without it, ancient failures that happened minutes ago would keep the circuit open. Only recent, sustained failures should trigger the breaker.

Per-Dependency Breakers

In a multi-dependency architecture, each dependency gets its own circuit breaker. When the memory server trips, the database connector continues operating normally. When the API provider trips, the agent can fall back to an alternative provider. Independent breakers prevent one dependency's problems from affecting unrelated functionality.

This connects back to the blast radius concept. Independent circuit breakers are an enforcement mechanism for independent failure domains. They make the isolation concrete rather than theoretical.

Timeout Hierarchies

Every network call needs a timeout. The question is: what timeout?

The Problem with Single Timeouts

A single global timeout (say, 30 seconds) applied to all operations is wrong in both directions. It is too long for a health check ping (which should complete in milliseconds) and too short for a complex model inference call (which may legitimately take 60 seconds during extended thinking).

Hierarchical Timeouts

A production system uses a hierarchy of timeouts, each tuned to its specific operation:

Operation Timeout Rationale
Health check ping 5 seconds Network round-trip should be <100ms
MCP server initialization 30 seconds Server may download dependencies at startup
API request (streaming) 90 seconds idle Model may think for 30-60s between tokens
Graceful shutdown 5 seconds + 3 seconds Give server time to flush, then force-kill
Session-end hooks 1.5 seconds User is waiting to exit
Background async hooks 15 seconds Non-critical, should not block indefinitely

Each timeout reflects an understanding of the operation it guards. The 30-second initialization timeout for MCP servers exists because some servers do substantial work at startup -- loading databases, compiling schemas, downloading packages via npx. A server that does not respond within 30 seconds is almost certainly hung, not just slow.

The 90-second streaming idle watchdog is tuned to model inference characteristics. During extended thinking, the model may go 30-60 seconds between visible output tokens. The watchdog must be set above this expected gap to avoid false positives, but not so high that a truly dead connection hangs forever.

The Graduated Shutdown

Shutdown is where timeout hierarchies are most visible. Claude Code's MCP server disconnect follows a graduated approach:

1. Close stdin pipe          → signals graceful shutdown
2. Wait 5 seconds            → grace period for cleanup
3. Send SIGTERM              → polite termination
4. Wait 3 seconds            → grace period for signal handling
5. Send SIGKILL              → forced termination
6. Collect exit status       → prevent zombie processes
7. Close stdout/stderr pipes → release file descriptors

Each step is more forceful than the last. Well-behaved servers shut down at step 1 when they detect stdin closing. Most servers respond to SIGTERM at step 3. Only misbehaving servers that ignore both signals reach SIGKILL at step 5. The graduated approach balances patience (giving servers time to flush buffers and close connections) with determination (ensuring cleanup completes in bounded time).

The Connection State Machine

All of these concepts -- blast radius, degradation, retries, circuit breakers, timeouts -- come together in the connection state machine. Claude Code models each MCP server connection as a finite state machine with six states:

stateDiagram-v2
    [*] --> Disconnected
    Disconnected --> Connecting: connect()
    Connecting --> Negotiating: transport established
    Connecting --> Error: transport failure
    Negotiating --> Ready: handshake complete
    Negotiating --> Error: handshake timeout (30s)
    Ready --> Error: 3 missed pings / process exit
    Ready --> Disconnecting: session ends
    Error --> Connecting: backoff timer fires
    Error --> Disconnected: max retries exceeded
    Disconnecting --> Disconnected: cleanup complete

Why a State Machine?

Explicit state machines eliminate entire categories of bugs. Without a state machine, connection management is a tangle of boolean flags: isConnected, isReconnecting, hasTimedOut, isShuttingDown. These flags interact in unexpected ways. Can you be connected and reconnecting? Connected and shutting down? The state space grows exponentially with each flag.

With a state machine, every state is explicit and every transition is documented. The system is in exactly one state at any time. Illegal transitions (e.g., going from Disconnected directly to Ready) are structurally impossible. The state machine makes the system's behavior legible -- you can look at the diagram and immediately understand every possible lifecycle path.

The Key Invariant

Tool calls are only accepted in the Ready state. If a tool call arrives in any other state:

  • Connecting / Negotiating: Queue the call. Execute when Ready is reached.
  • Error: Queue the call. Execute if reconnection succeeds, fail if max retries exceeded.
  • Disconnecting / Disconnected: Reject immediately.

Queuing during transient states is a design choice that prioritizes user experience. If the user invokes a memory tool while the memory server is reconnecting (a 1-2 second window), the call should wait for reconnection rather than immediately failing with a confusing error.

State Recovery After Reconnection

When reconnection succeeds, the client does not simply resume. The server may have restarted with different capabilities -- perhaps a newer version was deployed during the outage. The recovery sequence:

  1. Re-initialize. Full handshake runs again.
  2. Re-fetch tool list. Tools may have changed.
  3. Drain queued calls. Execute any calls that were waiting.
  4. Notify the agent. Update the tool registry with refreshed tools.

Step 2 is critical. If the old server supported search_memory and the new server does not, pending calls to search_memory must be rejected with an informative error, not silently dropped.

What Cannot Be Recovered

Reconnection restores the connection, not the server's state. If the MCP server maintained in-memory data before crashing -- caches, session variables, intermediate results -- that data is gone. The agent must not assume state continuity across reconnections.

This has an architectural implication for MCP server design: servers that need state across restarts must persist it to disk or a database. In-memory-only state is state that you are willing to lose. Design accordingly.

Defense in Depth for Cleanup

When the agent process crashes without going through graceful shutdown, the MCP server processes become orphans -- running processes with no parent to manage them. Claude Code prevents orphan accumulation through three independent mechanisms:

  1. Process group management. MCP servers spawn in the same process group as the agent. When the agent terminates, the OS can kill the entire group.

  2. PID file tracking. The agent writes spawned server PIDs to a file. On next startup, it checks for and terminates orphans from previous sessions.

  3. Server-side timeout. Well-designed servers detect when their parent dies (stdin closes, pings stop) and self-terminate.

Any one of these can fail, and the system still cleans up. Process groups may not work across all operating systems. The PID file may be corrupted. The server may not implement self-termination. But the probability of all three failing simultaneously is negligible.

This is defense in depth applied to resource management. The same principle applies to any cleanup operation: never rely on a single mechanism. Use two or three independent mechanisms that each cover the same failure. The redundancy cost is trivial compared to the operational cost of leaked resources accumulating over time.

The Fail-Open vs. Fail-Closed Decision

Every failure handler must make a fundamental choice: fail open (continue operating) or fail closed (stop and report).

Fail open means the system continues, possibly with degraded functionality. This is appropriate for interactive tools where losing some capability is annoying but losing the entire session is unacceptable. When an MCP server dies, Claude Code fails open -- the agent continues without that server's tools.

Fail closed means the system stops and reports the failure. This is appropriate for security-critical decisions where an incorrect default could cause harm. When Claude Code's permission classifier cannot determine whether a command is safe, it fails closed -- the command is denied.

The decision depends on the consequences of being wrong:

Scenario Wrong "open" consequence Wrong "closed" consequence Correct default
MCP server down Reduced capability Session terminates Open
Permission check fails Unsafe command executes Safe command blocked Closed
Health check fails Stale connection used Connection reestablished Closed
Cost tracker errors Overspend Work interrupted Open

There is no universal answer. Each failure point in your system requires its own analysis. The framework is: ask "what is the cost of being wrong in each direction?" and default to the direction where being wrong costs less.

As discussed in Chapter 8, Claude Code's permission system fails closed when the auto-mode classifier is unavailable. The cost of wrongly allowing a dangerous command far exceeds the cost of wrongly blocking a safe one. But the MCP lifecycle fails open because the cost of losing the entire session far exceeds the cost of losing one server's tools.

Designing for Observability

You cannot fix what you cannot see. Every failure-handling mechanism must produce observable signals -- metrics, logs, state transitions -- that allow operators to understand what happened and why.

Claude Code's MCP lifecycle manager logs every state transition with structured data:

{
  "timestamp": "2026-04-12T10:15:30Z",
  "level": "info",
  "event": "mcp.connection.ready",
  "server": "copilot-mem",
  "transport": "stdio",
  "negotiation_ms": 1247,
  "tools_count": 12,
  "capabilities": ["tools", "resources"]
}

Every reconnection attempt, every health check failure, every state transition is logged. When someone reports "the memory tool stopped working," the diagnostic data is already there. Retroactive debugging without observability requires reproducing the failure, which in distributed systems may be impossible.

The diagnostic commands (/mcp status, /mcp restart, /mcp logs) expose this observability to users. Users should not need to read log files to understand the health of their system. The system should tell them.

Key Principles

  1. Failure-first design. Before writing the happy path, inventory your dependencies and define what happens when each one fails. The optimism tax compounds -- pay the failure-handling cost upfront.

  2. Minimize blast radius. Each dependency should be its own failure domain. A failure in one should not cascade to others. Independent state machines, independent circuit breakers, independent retry timers.

  3. Degrade gracefully. When a component fails, continue operating with reduced capability. Remove unavailable tools from the model's options rather than returning errors for tools that cannot execute.

  4. Retry with discipline. Exponential backoff prevents hammering. Jitter prevents thundering herds. Server-provided delays override client calculations. Error classification determines whether to retry at all.

  5. Use state machines for lifecycle management. Explicit states and transitions make system behavior legible, prevent illegal state combinations, and provide natural integration points for monitoring and recovery.

  6. Defense in depth for cleanup. Never rely on a single cleanup mechanism. Use two or three independent mechanisms -- any one can fail, and the system still recovers.

  7. Choose fail-open or fail-closed based on consequences. There is no universal default. Analyze the cost of being wrong in each direction and choose the direction where wrong costs less.

Think About It

  1. The hidden dependency. Your system connects to a database, a cache, and a message queue. You have failure handling for each. But the database, cache, and message queue all depend on DNS. What is the blast radius when DNS fails? How would you design your system to limit it?

  2. The retry paradox. You have a service with a 99.9% success rate. You add retry logic that retries failed requests once. What is the new effective success rate? Now consider: if 1,000 clients all retry at the same time, what happens to the service? At what point do retries make the problem worse instead of better?

  3. The graceful degradation audit. Take any system you work on. List every external dependency. For each one, answer: what happens right now if it becomes unavailable? Is the degradation graceful (reduced functionality) or catastrophic (system crash)? What is one change you could make to improve the worst degradation path?

  4. The timeout design exercise. You are building a CLI tool that calls three APIs in sequence: an authentication service (fast, <100ms), a data service (moderate, 1-5 seconds), and a report generator (slow, 10-60 seconds). Design a timeout hierarchy for this pipeline. What happens when the second API times out -- do you skip it and try the third, or abort the entire pipeline? What factors determine your answer?

  5. The state machine test. Draw the state machine for a WebSocket connection to a chat server. Include states for connecting, authenticated, reconnecting, and disconnected. Now add a state for "connection degraded" (messages can be received but not sent). What transitions lead to this state? What transitions leave it? How does this state affect the user experience?
