Chapter 10: MCP — Wiring the Loop to the World

Level: S (Standard) · ~4,000 words · Levels served: L2, L3, L4

10.1 The Connector Problem

A loop that only operates on local files lives in a sandbox. Production work happens across systems: GitHub for code, Linear for tickets, Slack for communication, databases for data, CI/CD for deployment, monitoring for observability. Without connectors to these systems, the loop produces suggestions. With connectors, it produces outcomes.

The difference:

  • Without connectors: "I recommend creating a PR with these changes." (Human must act.)
  • With connectors: "I created PR #342, CI is green, I've tagged the reviewer, and I posted the summary to Slack." (Done.)

Model Context Protocol (MCP) is the standard interface for building these connectors. Announced by Anthropic in late 2024 and adopted broadly through 2025-2026, MCP provides a uniform way for AI systems to discover, connect to, and interact with external tools and data sources.

10.2 MCP Architecture

MCP follows a client-server architecture:


┌─────────────────────┐         ┌─────────────────────┐
│   AI Application    │         │    MCP Server        │
│   (MCP Client)      │◀───────▶│    (Connector)       │
│                     │  JSON   │                      │
│  - Claude Code      │  RPC    │  - GitHub server     │
│  - Custom loop      │  over   │  - Database server   │
│  - Any harness      │  stdio/ │  - Slack server      │
│                     │  HTTP   │  - Custom server     │
└─────────────────────┘         └─────────────────────┘

The MCP server exposes:

  • Tools: Actions the model can take (create PR, send message, query database)
  • Resources: Data the model can read (file contents, database schemas, API docs)
  • Prompts: Pre-built prompt templates for common operations

The MCP client (your loop harness) connects to one or more servers, discovers their capabilities, and presents them to the model as available tools.

10.3 Why MCP Matters for Loops

MCP matters for three reasons specific to loop engineering:

Reason 1: Standardized discovery

Before MCP, every integration was custom: bespoke code to call GitHub's API, different code to call Slack's API, different code for each database. With MCP, the loop discovers available tools dynamically. Add a new MCP server, and the loop can immediately use its tools without code changes.


# Without MCP: hardcoded integrations
def create_pr(title, body, branch):
    response = requests.post(
        f"https://api.github.com/repos/{repo}/pulls",
        headers={"Authorization": f"token {token}"},
        json={"title": title, "body": body, "head": branch, "base": "main"}
    )
    return response.json()

# With MCP: tools discovered from server
# The loop just calls whatever tools are available
tools = mcp_client.list_tools()  # Discovers create_pr, list_prs, etc.
result = mcp_client.call_tool("create_pull_request", {
    "title": title, "body": body, "branch": branch
})

Reason 2: Code execution

MCP servers can provide sandboxed code execution — a critical capability for loops that need to test their own output. The loop generates code, the MCP server executes it in isolation, and the result comes back as a tool response.


{
  "tool": "execute_code",
  "arguments": {
    "language": "python",
    "code": "import pytest; result = pytest.main(['tests/', '-x'])",
    "timeout_seconds": 30,
    "sandbox": true
  }
}

Reason 3: Authentication delegation

MCP servers handle authentication to external services. The loop doesn't need credentials in its context — it just calls tools, and the server handles OAuth flows, API keys, and token refresh behind the scenes. This is a security win: credentials never enter the model's context where they could be leaked via prompt injection.

10.4 MCP Server Anatomy

An MCP server is a process that implements the MCP protocol. It can be written in any language that supports JSON-RPC communication. Here's the structure:


import { Server } from "@modelcontextprotocol/sdk/server";

const server = new Server({
  name: "github-connector",
  version: "1.0.0",
});

// Register tools
server.setRequestHandler("tools/list", async () => ({
  tools: [
    {
      name: "create_pull_request",
      description: "Create a new pull request. Use after pushing changes to a feature branch.",
      inputSchema: {
        type: "object",
        properties: {
          title: { type: "string", description: "PR title (max 72 chars)" },
          body: { type: "string", description: "PR description in markdown" },
          branch: { type: "string", description: "Source branch name" },
          base: { type: "string", default: "main", description: "Target branch" },
        },
        required: ["title", "body", "branch"],
      },
    },
    // ... more tools
  ],
}));

// Handle tool calls
server.setRequestHandler("tools/call", async (request) => {
  if (request.params.name === "create_pull_request") {
    const { title, body, branch, base } = request.params.arguments;
    const pr = await github.createPR({ title, body, head: branch, base });
    return { content: [{ type: "text", text: `PR #${pr.number} created: ${pr.url}` }] };
  }
});

10.5 Building Custom MCP Servers

When production needs exceed available community servers, you build custom ones. The pattern is straightforward:

  1. Identify the integration: What system does the loop need to interact with?
  2. Define the tools: What actions should be available? (Start minimal — 3-5 tools.)
  3. Design for the model: Write descriptions that tell the model when and how to use each tool.
  4. Handle errors gracefully: Return actionable error messages, not stack traces.
  5. Add authentication: Handle credentials server-side, never expose them in tool responses.

Common custom servers:

Server Tools Loop use case
Internal wiki search, read_page, update_page Research loops that need company knowledge
Deployment deploy, rollback, health_check Operations loops that ship to staging/prod
Monitoring query_metrics, get_alerts, acknowledge Incident response loops
Database query, describe_table, explain_plan Data analysis loops
CI/CD trigger_build, get_status, read_logs Build-fix loops

10.6 MCP in Fleet Architecture

In a fleet loop, different agents may need different MCP servers:


fleet_mcp_config:
  orchestrator:
    servers: [github, linear, slack]  # Coordination tools
  
  code_agent:
    servers: [filesystem, code_execution, tests]  # Implementation tools
  
  review_agent:
    servers: [filesystem, github]  # Read code, post comments
  
  deploy_agent:
    servers: [github, deployment, monitoring]  # Ship and watch

Each agent sees only the tools relevant to its role. This is the principle of least privilege applied to tool access — the code agent can't accidentally send Slack messages, and the review agent can't accidentally deploy.

10.7 Security Considerations

MCP servers are a supply chain risk. A malicious or compromised MCP server can:

  • Return misleading tool results (poisoning the loop's context)
  • Exfiltrate data from tool arguments (the model passes sensitive info to tools)
  • Execute unauthorized actions (if the server has broader permissions than intended)
  • Inject prompts via tool results (response content that manipulates the model)

Mitigations:

1. Vet servers carefully. Use official or well-maintained community servers. For custom servers, review the code.

2. Scope permissions tightly. The GitHub server should have read-only access unless the loop explicitly needs to create PRs. The database server should only have SELECT permissions unless mutations are required.

3. Audit tool calls. Log every tool call and its result. Flag unexpected patterns (tools called at unusual times, unusual argument patterns, sensitive data in arguments).

4. Validate tool results. Don't trust tool results blindly. If a tool returns code, validate it before execution. If it returns URLs, verify they point where expected.

10.8 MCP vs. Direct API Integration

When should you use MCP vs. writing direct API calls in your harness?

Factor MCP Direct Integration
Standardization Uniform interface for all services Custom code per service
Discovery Dynamic tool discovery Static, hardcoded
Reusability Same server works across loops Each loop reimplements
Latency Additional RPC hop Direct API call
Debugging Standardized tracing Custom logging
Complexity Server setup + protocol overhead Simple HTTP calls

Use MCP when: You have multiple loops that need the same integrations, you want dynamic tool discovery, or you're building a platform that others will extend.

Use direct integration when: You have a single loop with a single integration, latency is critical, or the integration is too simple to warrant the MCP overhead.

For most production loops, the MCP overhead is negligible and the standardization benefits are significant. Default to MCP unless you have a specific reason not to.

10.9 The Connector Transforms the Loop

Adding connectors fundamentally changes what a loop can do:

Without connectors (L2-L3):

  • Read local files, write local files
  • Run local commands
  • Produce artifacts for human delivery

With connectors (L3-L4):

  • Create PRs, merge code, deploy
  • Update tickets, notify teams
  • Query production systems
  • Monitor health post-deployment
  • Close the loop end-to-end without human delivery

The connector is what promotes a loop from "helpful assistant that produces suggestions" to "autonomous system that ships outcomes." It's the difference between generating a fix and deploying a fix.
