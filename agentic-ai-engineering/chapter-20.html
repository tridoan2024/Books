Chapter 20: The Hierarchy of Oracles

Level: A (Anchor) · ~6,000 words · Levels served: L3, L4, L5

20.1 The Oracle Is Everything

The oracle determines whether a loop's output is good. Without an oracle, a loop is blind generation — producing output with no way to know if it meets the goal. With a bad oracle, a loop converges on the wrong answer. With a good oracle, a loop reliably ships verified work.

Choosing the right oracle is the second most important decision in loop design (after goal specification). Get the oracle right, and the loop self-corrects to quality. Get it wrong, and the loop either rejects good output (false negatives — wasting budget on unnecessary retries) or accepts bad output (false positives — shipping defective work).

20.2 The Hierarchy

Oracles are arranged in a hierarchy from cheapest to most expensive, from most reliable to most subjective:


Level 1: Deterministic Checks     ($0.000/eval)   100% precision
Level 2: Property-Based Tests     ($0.001/eval)   High precision
Level 3: Rubric Scoring           ($0.01/eval)    Medium precision
Level 4: Model Judge              ($0.10/eval)    Variable precision
Level 5: Human Review             ($10-100/eval)  Gold standard

The rule: use the cheapest oracle that still discriminates. Don't use a model judge if tests can verify correctness. Don't use a human if a model judge provides sufficient quality discrimination.

20.3 Level 1: Deterministic Checks

The cheapest and most reliable oracle: a program that produces a binary pass/fail with zero ambiguity.

Examples:

  • Test suites: pytest tests/ -x exits 0 (all pass) or non-zero (failure)
  • Type checkers: pyright src/ reports zero errors
  • Linters: ruff check src/ produces no warnings
  • Schema validation: Output matches a JSON schema
  • Compilation: Code compiles without errors
  • Format checks: Output matches required structure

Characteristics:

  • Cost: Near zero (CPU only, no model inference)
  • Speed: Milliseconds to seconds
  • Precision: 100% — if the check passes, the property holds
  • Recall: Variable — only checks what it's designed to check. A passing test suite doesn't guarantee correctness; it guarantees the specific properties tested.

When to use:

Always use deterministic checks as the first layer of your oracle. They're essentially free, instantaneous, and perfectly reliable. The question is whether they're SUFFICIENT — do they catch enough issues that you don't need a more expensive layer?


class DeterministicOracle:
    def __init__(self, checks: list[Check]):
        self.checks = checks
    
    def evaluate(self, workspace: Path) -> OracleResult:
        failures = []
        for check in self.checks:
            result = check.run(workspace)
            if not result.passed:
                failures.append(result)
        
        return OracleResult(
            passed=len(failures) == 0,
            failures=failures,
            confidence=1.0,  # Deterministic = perfect confidence
            cost=0.0,
        )

The gap problem:

Deterministic checks can only verify properties you've explicitly encoded. They can't check:

  • Whether the code is correct (only whether specific test cases pass)
  • Whether the approach is sensible (only whether it compiles)
  • Whether the output is good (only whether it matches a schema)

This gap is where higher-level oracles come in.

20.4 Level 2: Property-Based Tests

A step above specific test cases: property-based tests verify that invariants hold across a wide range of inputs, without specifying exact expected outputs.


from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_sort_is_sorted(xs):
    result = my_sort(xs)
    assert all(result[i] <= result[i+1] for i in range(len(result)-1))

@given(st.lists(st.integers()))
def test_sort_preserves_elements(xs):
    result = my_sort(xs)
    assert sorted(result) == sorted(xs)  # Same multiset

@given(st.text(), st.text())
def test_search_results_contain_query(query, document):
    results = search(query, document)
    for r in results:
        assert query.lower() in r.text.lower()

Characteristics:

  • Cost: Low (CPU for generation + execution, typically hundreds of test cases)
  • Speed: Seconds to minutes (depending on the number of examples)
  • Precision: Very high — if a property violation is found, it's real
  • Recall: Higher than specific tests (explores edge cases automatically)

When to use:

When you can express the correctness criteria as universal properties rather than specific input-output pairs. Property-based testing excels at finding edge cases that handwritten tests miss.

20.5 Level 3: Rubric Scoring

When correctness can't be expressed as a binary property, rubrics provide structured evaluation criteria. A rubric defines dimensions of quality, levels within each dimension, and scoring thresholds.


rubric = {
    "dimensions": [
        {
            "name": "factual_accuracy",
            "weight": 0.4,
            "levels": {
                5: "All claims are verifiable and correctly cited",
                3: "Most claims are accurate, minor unsourced statements",
                1: "Contains factual errors or unverifiable claims",
            }
        },
        {
            "name": "completeness",
            "weight": 0.3,
            "levels": {
                5: "Covers all required topics with sufficient depth",
                3: "Covers most topics, some gaps",
                1: "Major topics missing",
            }
        },
        {
            "name": "actionability",
            "weight": 0.3,
            "levels": {
                5: "Every recommendation has specific next steps",
                3: "Some recommendations are vague",
                1: "Recommendations are too general to act on",
            }
        }
    ],
    "passing_score": 3.5
}

Characteristics:

  • Cost: Low to medium (evaluating against a rubric can be done by a model or a human)
  • Speed: Varies (model: seconds; human: minutes to hours)
  • Precision: Medium — depends on rubric clarity and evaluator consistency
  • Recall: Good for the dimensions specified, blind to unspecified dimensions

When to use:

For tasks where quality is multi-dimensional and not reducible to a binary pass/fail. Documentation, code review findings, research summaries, reports — outputs where "good" is a spectrum, not a threshold.

20.6 Level 4: Model Judge

A separate model evaluates the output. The judge has a different context than the maker (critical for independence) and is prompted specifically for evaluation.


async def model_judge(output: str, goal: str, criteria: str) -> JudgeResult:
    prompt = f"""You are evaluating an AI system's output against specific criteria.
    
    Goal: {goal}
    
    Criteria for success:
    {criteria}
    
    Output to evaluate:
    {output}
    
    Evaluate each criterion. For each:
    - State whether it's met (PASS/FAIL)
    - Provide a one-sentence justification
    - If FAIL, state specifically what's wrong
    
    Final verdict: PASS if all criteria met, FAIL otherwise.
    """
    
    result = await judge_model.generate(prompt, schema=JudgeSchema)
    return result

Characteristics:

  • Cost: Medium ($0.01-$0.50 per evaluation, depending on model and output length)
  • Speed: 2-30 seconds
  • Precision: Variable (70-95% agreement with human judgment, depending on task clarity)
  • Recall: Good for detecting quality issues, but subject to its own biases

The independence requirement:

The judge MUST NOT share the maker's context. If the judge sees the maker's reasoning, it will be biased toward agreement — it already "understands" what the maker intended, filling in gaps with the maker's intent rather than evaluating what's actually on the page.


# BAD: Judge shares maker's context
judge_context = maker_conversation + [{"role": "user", "content": "Now evaluate your output"}]

# GOOD: Judge only sees the output and criteria
judge_context = [{"role": "user", "content": f"Evaluate this output: {output}\nCriteria: {criteria}"}]

Model diversity:

Using the same model as both maker and judge introduces correlated biases. If Claude writes the code, Claude might also overlook the same issues when reviewing it. Using a different model (or the same model with a very different prompt emphasizing skepticism) reduces this correlation.

20.7 Level 5: Human Review

The most expensive and highest-quality oracle: a human expert evaluates the output.

When human review is necessary:

  • The task involves subjective judgment that no automated oracle can capture
  • The stakes are high enough that automated verification alone is insufficient
  • The loop is in its early days and you're still developing trust in automated oracles
  • The output will be presented to customers or stakeholders

Making human review efficient:

Don't ask the human to review everything. Use the lower-level oracles as a filter:


Output generated
    ↓
Level 1: Deterministic checks (fast, free)
    ↓ (only if passes)
Level 4: Model judge (fast, cheap)
    ↓ (only if ambiguous or high-stakes)
Level 5: Human review (slow, expensive)

The human only sees output that has already passed automated checks. This reduces their review burden dramatically — they're catching subtle issues, not obvious ones.

20.8 Composite Oracles

Production loops rarely use a single oracle level. They compose multiple levels into a pipeline:


class CompositeOracle:
    def __init__(self):
        self.levels = [
            DeterministicOracle(checks=[tests, types, lint]),
            PropertyOracle(properties=[sort_invariant, search_contract]),
            ModelJudge(criteria=security_review_rubric),
        ]
    
    async def evaluate(self, output: str) -> OracleResult:
        for level in self.levels:
            result = await level.evaluate(output)
            if not result.passed:
                return result  # Fail fast at cheapest level
        
        return OracleResult(passed=True, confidence=0.95)

The pipeline fails fast: if deterministic checks catch the issue, the model judge is never invoked. This minimizes cost while maximizing coverage.

20.9 Oracle Cost vs. Loop Cost

The oracle's cost must be small relative to the generation cost. If verification costs more than generation, you've built an expensive review process with extra steps.

The ratio rule: oracle cost should be <20% of generation cost per iteration.


Generation: 5K output tokens × $15/M = $0.075
Oracle budget: $0.075 × 0.20 = $0.015

At $0.015/eval, you can afford:
- All deterministic checks (free)
- Property tests (negligible)
- One model judge call (Haiku: $0.01)
- NOT: Human review ($50+)
- NOT: Multiple Opus judge calls ($0.30+)

When the oracle is too expensive, you have three options:

  1. Use a cheaper oracle (lower in the hierarchy)
  2. Sample (don't verify every output, verify a random subset)
  3. Amortize (batch outputs and verify in bulk)

20.10 Actionable Feedback from Oracles

A good oracle doesn't just say pass/fail. It says what's wrong and how to fix it. This feedback is what enables convergence — without it, the loop retries blindly.

Feedback quality hierarchy:


Worst:  "FAIL"
Bad:    "FAIL: Output doesn't meet criteria"
OK:     "FAIL: Section 3 is incomplete"
Good:   "FAIL: Section 3 is missing the performance comparison table (required by criterion 4)"
Best:   "FAIL: Section 3 is missing the performance comparison table. The data for this table
         is available in benchmarks/results.json. Include columns: operation, p50, p99, comparison."

Each level of feedback quality translates directly to convergence speed. The "Best" feedback tells the model exactly what to do next — the fix is almost trivial. The "Worst" feedback tells the model nothing — it must explore to find what's wrong.

20.11 Building Your Oracle Strategy

For any new loop, build the oracle bottom-up:

  1. Start with deterministic checks. What can you verify with tests, types, schema validation, format checks? These are free and reliable. Enumerate everything checkable.
  1. Identify the gap. What aspects of quality do the deterministic checks NOT cover? These are your "judgment gaps" — things that require evaluation beyond pass/fail.
  1. Fill the gap minimally. Can a rubric + model judge cover the judgment gaps? Usually yes. Design the rubric to capture the specific quality dimensions your deterministic checks miss.
  1. Human review only for calibration. Use human review to calibrate your model judge. Compare judge verdicts with human verdicts periodically. If they diverge, fix the judge (better rubric, better prompt, different model).
  1. Iterate. As you observe the loop's failures, add deterministic checks for newly-discovered failure modes. Push work down the hierarchy — every issue that can be caught deterministically should be.
