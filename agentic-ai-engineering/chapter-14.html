Chapter 14: Triggers and Automations — The Heartbeat

Level: S (Standard) · ~4,000 words · Levels served: L3, L4, L5

14.1 The Automation Rule

If you start the loop by hand, the human is still in the loop — they've just moved from "reviewer" to "initiator." The loop runs when they remember. It doesn't run when they forget. Their attention remains the bottleneck, just at a different stage.

The automation rule: a loop that requires human initiation is not fully automated. The trigger — the mechanism that starts the loop — is as important as the loop itself. Without automation, you have a powerful tool. With automation, you have a system.

14.2 Trigger Types

Schedule Triggers

The simplest automation: run the loop at fixed intervals.


# Cron-based schedule triggers
every_morning:
  cron: "57 8 * * 1-5"  # Weekdays at ~9am
  loop: "security_review"
  
every_hour:
  cron: "7 * * * *"     # Hourly (off :00 to avoid thundering herd)
  loop: "pr_scan"

nightly:
  cron: "23 2 * * *"    # 2:23am daily
  loop: "dependency_audit"

Best for: Monitoring loops, periodic scans, daily maintenance, scheduled checks.

Event Triggers

The loop starts when something happens in an external system.


# Event-based triggers
pr_opened:
  event: "github.pull_request.opened"
  loop: "code_review"
  args: { pr_number: "{{ event.number }}" }

ticket_ready:
  event: "linear.issue.status_changed"
  condition: "event.to_state == 'ready_for_dev'"
  loop: "implementation"
  args: { issue_id: "{{ event.id }}" }

deploy_completed:
  event: "github.deployment.completed"
  loop: "post_deploy_verification"

Best for: Reactive loops that respond to changes, CI/CD integration, workflow automation.

Threshold Triggers

The loop starts when a metric crosses a boundary.


error_spike:
  metric: "error_rate_5m"
  condition: "> 0.01"  # 1% error rate
  loop: "incident_diagnosis"
  cooldown: "15m"      # Don't re-trigger for 15 minutes

cost_alert:
  metric: "daily_token_spend"
  condition: "> 50.00"  # $50/day
  loop: "cost_investigation"
  cooldown: "4h"

Best for: Anomaly detection, SLA monitoring, resource management.

Webhook Triggers

External systems call your automation endpoint directly.


@app.post("/hooks/trigger")
async def webhook_trigger(payload: WebhookPayload):
    if payload.event == "review_requested":
        await start_loop("security_review", args=payload.data)
    elif payload.event == "build_failed":
        await start_loop("build_diagnosis", args=payload.data)

Best for: Integration with systems that support outbound webhooks (GitHub, Slack, CI tools).

Chained Triggers

One loop's completion triggers another loop.


pipeline:
  - loop: "code_review"
    on_success: "merge_check"
  - loop: "merge_check"
    on_success: "deploy"
  - loop: "deploy"
    on_success: "post_deploy_verify"
    on_failure: "rollback"

Best for: Multi-stage pipelines, approval workflows, dependent operations.

14.3 Idempotency

A trigger may fire more than once. Network retries, duplicate webhooks, overlapping schedules — all produce repeated invocations. Every loop started by a trigger must be idempotent: running it twice with the same input must produce the same outcome without harmful side effects.

Idempotency patterns:

1. Check-before-act: Before the loop starts work, verify that the work hasn't already been done.


async def security_review_loop(pr_number: int):
    # Check if we already reviewed this PR version
    existing_review = await get_existing_review(pr_number)
    if existing_review and existing_review.commit == await get_head_commit(pr_number):
        return  # Already reviewed this version, skip
    
    # Proceed with review...

2. Deduplication keys: Track which triggers have been processed using a unique key.


class TriggerDeduplicator:
    def __init__(self):
        self.processed = set()
    
    async def should_process(self, trigger_id: str) -> bool:
        if trigger_id in self.processed:
            return False
        self.processed.add(trigger_id)
        return True

3. Last-write-wins: For loops that produce artifacts (comments, files, reports), overwrite previous output rather than appending. Running twice produces one result, not two.

14.4 Re-Entrancy

What happens when a trigger fires while the loop is already running? Three strategies:

Queue: Buffer the new trigger and run it after the current invocation completes. Simple, ensures no concurrent execution, but creates latency.

Skip: Discard the new trigger if the loop is already running. Appropriate when the current run will handle the new event as part of its normal operation.

Replace: Cancel the current run and start fresh with the new trigger. Appropriate when the new event invalidates the current run's work (e.g., new commits pushed while reviewing old commits).


class LoopScheduler:
    def __init__(self, strategy: str = "queue"):
        self.strategy = strategy
        self.running: dict[str, asyncio.Task] = {}
        self.queue: dict[str, list] = {}
    
    async def trigger(self, loop_name: str, args: dict):
        if loop_name in self.running:
            if self.strategy == "queue":
                self.queue.setdefault(loop_name, []).append(args)
            elif self.strategy == "skip":
                return  # Discard
            elif self.strategy == "replace":
                self.running[loop_name].cancel()
                self.running[loop_name] = asyncio.create_task(
                    self.run_loop(loop_name, args)
                )
        else:
            self.running[loop_name] = asyncio.create_task(
                self.run_loop(loop_name, args)
            )

14.5 Cooldown and Rate Limiting

Triggers can fire too frequently. A threshold trigger on error rate might fire every second during an outage. An event trigger on file changes might fire on every save during active development. Without rate limiting, the loop consumes unbounded resources.

Cooldown: After the loop runs, ignore new triggers for a specified period.

Rate limiting: Maximum N invocations per time window.

Debouncing: Wait until triggers stop arriving for a specified period before running. Appropriate for file-change triggers where multiple changes happen in rapid succession.


class DebouncedTrigger:
    def __init__(self, delay_seconds: float = 5.0):
        self.delay = delay_seconds
        self.pending: asyncio.Task | None = None
    
    async def fire(self, args: dict):
        if self.pending:
            self.pending.cancel()
        self.pending = asyncio.create_task(self._delayed_run(args))
    
    async def _delayed_run(self, args: dict):
        await asyncio.sleep(self.delay)
        await self.run_loop(args)

14.6 Trigger Observability

Every trigger invocation should be logged with:

  • When it fired
  • What event caused it
  • Whether it was processed, skipped, or queued
  • The loop's outcome (success, failure, budget exhausted)
  • Duration and cost

This data answers critical operational questions:

  • Are triggers firing too often? (Adjust cooldowns or thresholds)
  • Are loops failing frequently? (Investigate the failure pattern)
  • Is the cost within budget? (Adjust trigger frequency or loop scope)
  • Are there dead triggers? (Triggers that fire but never produce useful work)

14.7 Production Trigger Architecture

A production automation system typically looks like:


┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   Sources    │     │   Router     │     │   Executor   │
│              │────▶│              │────▶│              │
│ - Cron       │     │ - Dedup      │     │ - Start loop │
│ - Webhooks   │     │ - Rate limit │     │ - Monitor    │
│ - Events     │     │ - Route      │     │ - Report     │
│ - Thresholds │     │ - Queue      │     │ - Cleanup    │
└──────────────┘     └──────────────┘     └──────────────┘

The router is the critical piece — it prevents duplicate processing, enforces rate limits, routes events to the appropriate loop, and manages the queue of pending work.

14.8 Designing Your Trigger Strategy

Start with these questions:

  1. What events matter? List the events that should trigger loop execution.
  2. How quickly must you respond? Determines whether you need event triggers (immediate) or schedule triggers (periodic).
  3. What's the maximum cost per day? Determines rate limits and cooldowns.
  4. What happens if you miss an event? Determines whether you need guaranteed delivery or can tolerate occasional skips.
  5. What happens if you process the same event twice? Determines your idempotency requirements.

For most teams starting with loop automation:

  • Week 1: One schedule trigger (daily security scan or weekly dependency audit)
  • Week 2: One event trigger (PR-opened review loop)
  • Month 2: Add threshold triggers (error rate, cost alerts)
  • Month 3: Add chained triggers (review → merge → deploy pipeline)

Build the automation incrementally. Each new trigger is a commitment to maintaining and monitoring an autonomous system. Don't add triggers faster than you can observe their behavior.
