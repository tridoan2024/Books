Chapter 13: Choosing Your Primitive

Level: B (Brief) · ~2,800 words · Levels served: L2, L3, L4

13.1 The Primitive Zoo

When building a loop, you have six primitives available at every decision point:

  1. Prompt: Instructions to the model in natural language
  2. Code: Deterministic logic in your harness
  3. Tool: A function the model can call
  4. MCP Server: An external service exposing tools and resources
  5. Skill: Reusable project knowledge loaded into context
  6. Subagent: A separate model execution with its own context

Each has a different cost profile, context footprint, reliability characteristic, and appropriate use case. The most common mistake in loop engineering is using the wrong primitive for the job — typically, using a model call where code would suffice, or using a subagent where a tool would work.

13.2 The Decision Table

When you need... Use Not
Deterministic transformation Code Prompt (non-deterministic)
Reasoning about ambiguous input Prompt Code (can't handle ambiguity)
Interaction with external system Tool/MCP Prompt (can't act on world)
Stable project knowledge Skill Prompt (rediscovered each run)
Independent evaluation Subagent Prompt (shares maker's context)
Parallel execution on different data Subagent Sequential prompts (slow)
Simple format conversion Code Tool (overhead not justified)
Complex multi-step operation Tool (composite) Multiple simple tools (coordination burden on model)
Knowledge that changes per project Skill Hardcoded prompt (not portable)

13.3 Cost and Context Profile

Each primitive carries a context cost (tokens consumed) and an execution cost (compute/time):

Primitive Context Cost Execution Cost Latency
Code 0 tokens CPU only <1ms
Prompt N tokens (instruction) Inference 1-30s
Tool (schema) ~800-1500 tokens per tool Varies Tool-dependent
MCP Server ~1000 tokens per tool exposed RPC + execution 100ms-10s
Skill 2K-15K tokens loaded 0 (just context) 0 (pre-loaded)
Subagent Full context per agent Full inference 10-120s

The total cost of a loop is the sum of its primitives across all iterations. Choosing cheaper primitives where they're sufficient has a multiplicative effect:


Loop cost = Σ (primitive_cost × iterations)

Using code vs. prompt for a parse step:
  Prompt: 500 tokens × 10 iterations = 5,000 tokens
  Code: 0 tokens × 10 iterations = 0 tokens
  Savings: 5,000 tokens per loop run

13.4 When to Use Code

Use code — not the model — for anything deterministic:

  • Parsing structured output: JSON/YAML parsing, regex extraction, schema validation
  • File operations: Reading, writing, copying, moving files
  • Data transformation: Sorting, filtering, mapping, formatting
  • Conditional logic: If-then routing based on clear criteria
  • Accumulation: Counting, summing, tracking state across iterations
  • Validation: Type checking, schema conformance, format verification

The rule: if the operation has no ambiguity — if a competent programmer could write it as a pure function — it should be code, not a model call.


# BAD: Using the model to parse test output
result = model.generate("Extract the test counts from this output: " + test_output)

# GOOD: Using code to parse test output
import re
match = re.search(r"(\d+) passed, (\d+) failed", test_output)
passed, failed = int(match.group(1)), int(match.group(2))

13.5 When to Use a Prompt

Use a prompt — an in-context instruction to the model — for:

  • Reasoning about ambiguous situations: What approach should we take? What's wrong here?
  • Generating novel content: Code, text, plans, explanations
  • Making judgment calls: Is this good enough? Should we continue or stop?
  • Synthesizing information: Combining multiple sources into a coherent understanding

13.6 When to Use a Tool

Use a tool when the model needs to interact with something outside its context:

  • External systems: Files, databases, APIs, services
  • Verification: Running tests, type checkers, linters
  • Information gathering: Searching code, reading documentation, querying data

Prefer fewer, well-designed tools over many narrow ones. The model's ability to choose correctly degrades with the number of options. A tool set of 5-10 well-designed tools is easier for the model to navigate than 50 narrowly-scoped ones.

13.7 When to Use an MCP Server

Use an MCP server instead of a direct tool when:

  • Multiple loops need the same integration: The server is shared infrastructure
  • Authentication is complex: OAuth flows, token refresh, credential management
  • The integration is maintained separately: Updates to the external service don't require updating every loop
  • You want dynamic discovery: Loops should be able to find new capabilities without code changes

Don't use an MCP server when:

  • The integration is trivial (a single HTTP call)
  • Latency is critical (the RPC hop adds ~50-100ms)
  • Only one loop will ever use it

13.8 When to Use a Skill

Use a skill (loaded context document) when:

  • The knowledge is stable: It doesn't change between runs
  • The knowledge is needed every run: The cold-start tax is real
  • The knowledge is non-derivable: Can't be easily discovered from the code itself
  • The knowledge shapes behavior: Rules, preferences, conventions that affect output quality

Don't use a skill when:

  • The information changes frequently (it'll be stale)
  • The information is easily derivable (reading a config file is cheaper)
  • The information is rarely needed (progressive disclosure, load on demand)

13.9 When to Use a Subagent

Use a subagent — a separate model execution with its own context — when:

  • Context isolation is needed: The maker and checker must not share context
  • Parallel execution provides speedup: Multiple independent tasks can run simultaneously
  • The task exceeds one context window: Too much information for a single model to hold
  • Specialization helps: Different tasks benefit from different prompts/tools/models
  • Independence improves quality: Multiple perspectives catch more issues

Don't use a subagent when:

  • A tool call would suffice (subagents are expensive for simple operations)
  • The tasks are sequential and dependent (parallelism provides no benefit)
  • The context is small enough for one model (splitting adds coordination overhead)
  • Communication overhead between agents exceeds the benefit

13.10 The Composition Checklist

When designing a loop, for each step ask:

  1. Is this deterministic? → Code
  2. Does this need reasoning? → Prompt (stay in current context)
  3. Does this need external interaction? → Tool or MCP
  4. Does this need project knowledge? → Skill
  5. Does this need independence from the current context? → Subagent
  6. Is this shared across multiple loops? → MCP server

If multiple answers apply, prefer the cheaper option. Code > Tool > Prompt > Subagent, in ascending order of cost.

13.11 Anti-Patterns

Using a subagent for a tool call: "Spawn an agent to check if the file exists." A filesystem tool does this for zero inference cost.

Using a prompt for a parse: "Tell me what JSON key has value X." A jq command or dict lookup is instant and deterministic.

Using a tool for a code operation: Calling a "sort" tool when sorted() in the harness code is free.

Using a skill for volatile information: Loading today's metrics into a skill file that's stale by tomorrow.

Using code for ambiguous decisions: Writing complex heuristics when the model could reason about the decision naturally.

The right primitive is the one that solves the problem at the lowest cost with the highest reliability. When in doubt, start with code and escalate to model calls only when deterministic solutions are insufficient.
