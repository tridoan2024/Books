Chapter 22: Evals as Loop Infrastructure

Level: S (Standard) · ~4,000 words · Levels served: L3, L4

22.1 Evals Are Not Tests

Tests verify specific input-output pairs. Evals verify that a system handles a class of inputs correctly. Tests are binary (pass/fail for one case). Evals are statistical (success rate across many cases).

For loops, evals serve a different purpose than unit tests:

  • Tests are the oracle (Chapter 20) — they verify individual loop outputs within a run
  • Evals measure the loop itself — how reliably does the entire system produce good outcomes across many runs?

Tests:  "Does this specific output meet this specific criterion?"  → Oracle
Evals:  "How often does this loop produce outputs that meet criteria?" → Loop health metric

22.2 Attempts-to-Pass: The Core Metric

The single most important metric for loop health: how many iterations does it take to produce a passing result?


@dataclass
class LoopEvalResult:
    task_id: str
    passed: bool
    iterations_used: int
    tokens_consumed: int
    time_elapsed: float
    
    @property
    def attempts_to_pass(self) -> int | None:
        return self.iterations_used if self.passed else None

Why attempts-to-pass matters:

  • 1 attempt = excellent. The loop gets it right first try. Oracle confirms immediately. Minimal cost.
  • 2-3 attempts = good. The loop needed correction but converged quickly. Acceptable cost.
  • 4-5 attempts = concerning. The loop is struggling. Either the task is hard, the oracle feedback is poor, or the model capability is insufficient.
  • >5 attempts or failure = broken. The loop can't handle this task type. Requires redesign.

Tracking over time:


class LoopHealthDashboard:
    def __init__(self):
        self.results: list[LoopEvalResult] = []
    
    def add_result(self, result: LoopEvalResult):
        self.results.append(result)
    
    @property
    def pass_rate(self) -> float:
        return sum(1 for r in self.results if r.passed) / len(self.results)
    
    @property
    def avg_attempts(self) -> float:
        passed = [r for r in self.results if r.passed]
        return sum(r.iterations_used for r in passed) / len(passed)
    
    @property
    def cost_per_success(self) -> float:
        passed = [r for r in self.results if r.passed]
        return sum(r.tokens_consumed for r in passed) / len(passed)

22.3 Building an Eval Suite

An eval suite is a collection of representative tasks with known-good solutions (or at least known-good criteria):


eval_suite = [
    EvalCase(
        id="fix_null_pointer",
        description="Fix a NullPointerException in UserService.getProfile()",
        setup=setup_broken_code,       # Set up the workspace with the bug
        oracle=lambda ws: run_tests(ws, "test_user_profile"),  # Deterministic check
        max_budget=Budget(iterations=5, tokens=200_000),
    ),
    EvalCase(
        id="add_validation",
        description="Add email validation to the registration endpoint",
        setup=setup_registration_code,
        oracle=lambda ws: (
            run_tests(ws, "test_registration") and
            check_validation_exists(ws, "email")
        ),
        max_budget=Budget(iterations=5, tokens=200_000),
    ),
    # ... 20-50 representative cases
]

Eval case design principles:

1. Representative: Cases should match the distribution of real tasks the loop will handle. If 60% of real tasks are bug fixes, 60% of eval cases should be bug fixes.

2. Diverse: Cover different difficulty levels, different file types, different patterns. Don't build 50 cases that are all trivial — include cases at the edge of the loop's capability.

3. Deterministic setup: Each case must be reproducible. The same setup always produces the same starting state. No flaky evals.

4. Independent: Cases don't depend on each other. Any subset can be run in any order.

22.4 Eval-Driven Loop Development

Build the loop BY building the eval suite:

Phase 1: Define what success looks like

Write eval cases for the tasks you want the loop to handle. Don't build the loop yet.

Phase 2: Run baseline

Run the eval suite against the simplest possible loop (model + basic tools, no iteration). Record the pass rate and attempts-to-pass. This is your baseline.

Phase 3: Improve iteratively

Make one change to the loop (add a tool, improve the oracle, add skills, change the prompt). Rerun the eval suite. Compare with baseline. Keep changes that improve metrics; revert changes that don't.

Phase 4: Regression checking

Every time you modify the loop, run the full eval suite. No change ships if it regresses pass rate or increases average attempts-to-pass.


# The eval-driven development cycle
$ run-eval --baseline     # Establish baseline metrics
$ # Make changes to the loop
$ run-eval --compare baseline  # Compare with baseline
# Output:
# Pass rate: 78% → 84% (+6%)  ✓
# Avg attempts: 3.2 → 2.8 (-0.4)  ✓
# Cost/success: $0.45 → $0.38 (-16%)  ✓
# Regressions: 0 cases newly failing  ✓

22.5 Eval Dimensions

A comprehensive eval suite measures multiple dimensions:

Capability

Can the loop handle this task at all? (Binary: pass/fail)

Efficiency

How many attempts does it need? (Lower is better)

Cost

How many tokens does it consume? (Lower is better)

Robustness

Does it handle variations of the same task consistently? (Test with perturbations)

Safety

Does it avoid harmful actions? (Test with adversarial inputs that might trigger dangerous operations)

22.6 Regression Suites

Some eval cases exist specifically to prevent regressions — tasks the loop used to fail on that were fixed. These form a regression suite:


regression_cases = [
    # Bug: loop used to delete test files when fixing bugs
    EvalCase(
        id="regression_no_delete_tests",
        description="Fix bug without modifying test files",
        oracle=lambda ws: tests_unchanged(ws) and bug_is_fixed(ws),
    ),
    # Bug: loop used to infinite-loop on circular import errors
    EvalCase(
        id="regression_circular_import",
        description="Handle circular import without infinite loop",
        oracle=lambda ws: loop_terminated_within_budget(ws),
    ),
]

Every bug found in production should become a regression case. The eval suite grows over time, encoding the loop's history of failures and their fixes.

22.7 Eval Infrastructure

Running evals requires infrastructure:


class EvalRunner:
    def __init__(self, loop: Loop, suite: list[EvalCase]):
        self.loop = loop
        self.suite = suite
    
    async def run_all(self, parallelism: int = 4) -> EvalReport:
        results = []
        for batch in chunk(self.suite, parallelism):
            batch_results = await asyncio.gather(*[
                self.run_case(case) for case in batch
            ])
            results.extend(batch_results)
        
        return EvalReport(results=results)
    
    async def run_case(self, case: EvalCase) -> LoopEvalResult:
        # Create isolated workspace
        workspace = create_temp_workspace()
        case.setup(workspace)
        
        # Run the loop
        start = time.time()
        result = await self.loop.run(
            workspace=workspace,
            goal=case.description,
            budget=case.max_budget,
        )
        
        # Evaluate
        passed = case.oracle(workspace)
        
        return LoopEvalResult(
            task_id=case.id,
            passed=passed,
            iterations_used=result.iterations,
            tokens_consumed=result.tokens,
            time_elapsed=time.time() - start,
        )

22.8 The Eval-Oracle Relationship

Evals and oracles are related but distinct:

  • The oracle runs inside the loop, on every iteration, to tell the loop whether its current output is good enough
  • The eval runs outside the loop, across many runs, to tell YOU whether the loop is good enough

Sometimes the eval oracle and the loop oracle are the same (both run tests). Sometimes they differ (the loop oracle is a model judge for speed, but the eval uses human annotation for accuracy).

When they differ, you must periodically calibrate: does the loop oracle agree with the eval oracle? If they diverge (loop oracle says PASS but eval says FAIL), the loop is shipping bad output with false confidence.

22.9 Continuous Evaluation

Don't run evals only during development. Run them continuously:

  • On every loop change: Run full suite before deploying loop modifications
  • Weekly on production: Sample 10% of real tasks and evaluate manually (or with a gold-standard oracle) to detect drift
  • On model updates: When the underlying model updates, run full suite immediately. Model behavior changes can degrade loops that were tuned to previous behavior

eval_schedule:
  on_change: "full suite (blocking — must pass before deploy)"
  weekly: "10% random sample with human annotation"
  on_model_update: "full suite within 24 hours of model release"
  monthly: "adversarial suite (edge cases + security)"

22.10 From Eval Results to Loop Improvements

Eval results tell you WHERE the loop is weak. The improvement process:

  1. Identify failing patterns: Which eval cases consistently fail? What do they have in common?
  2. Diagnose root cause: Is it the oracle (not detecting success)? The model (not capable enough)? The tools (missing capability)? The context (insufficient information)?
  3. Targeted fix: Address the specific root cause for the failing pattern
  4. Verify improvement: Rerun the failing cases. Did the fix help without regressing other cases?

Example: 8/50 eval cases fail. All 8 involve multi-file changes. Diagnosis: the model loses track of changes across files when context gets long. Fix: add a running "changes made" summary to context. Verify: 6/8 now pass, 0 regressions.
