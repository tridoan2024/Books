Chapter 11: Skills — Reusable Project Knowledge

Level: S (Standard) · ~4,000 words · Levels served: L2, L3, L4, L5

11.1 The Cold-Start Tax

Every time a loop starts without project context, it pays a cold-start tax: tokens spent discovering what the project is, how it's structured, what the rules are, and how to verify work. This tax is paid on every single run.

For a typical code loop:

  • ~2K tokens to understand the tech stack
  • ~3K tokens to find relevant files
  • ~1K tokens to learn the testing approach
  • ~2K tokens to understand coding conventions
  • Total: ~8K tokens × cost per token × runs per day

At 50 runs per day, that's 400K tokens of repeated discovery — roughly $1.20/day in pure waste. Over a month, $36. Over a year, $432. For one loop. Multiply by the number of loops in your fleet.

Skills eliminate this tax. A skill file is project knowledge encoded once, loaded on demand, and reused across every run.

11.2 What a Skill Is

A skill is a document that teaches an agent everything it needs to know about a specific project, domain, or task — without requiring the agent to discover that knowledge from scratch.

A skill is NOT:

  • A prompt template (though it may contain prompt fragments)
  • A tool definition (though it may reference tools)
  • A full conversation history
  • A codebase summary

A skill IS:

  • Curated project knowledge, organized for agent consumption
  • Stable across runs (updated when the project changes, not when the loop runs)
  • Loaded into context on demand (not always present)
  • Designed for the model as the primary reader

11.3 SKILL.md Anatomy

The standard skill file format:


# [Project Name] — [Skill Purpose]

## Vision
One paragraph: what this project does and why it matters.

## Architecture
How the system is structured. Key components and their relationships.
Include a Mermaid diagram for complex architectures.

## Key Conventions
- Language/framework specifics
- Naming conventions
- File organization patterns
- Import ordering rules

## Rules (Must Follow)
Constraints the agent must never violate. These are hard rules, not suggestions.
- [ ] Never modify files in /migrations/ after they're applied
- [ ] All API endpoints require authentication
- [ ] Error responses use RFC 7807 format
- [ ] No direct database access from controllers

## Rules (Should Follow)
Strong preferences that may be overridden with justification.
- Prefer composition over inheritance
- Keep functions under 30 lines
- Use structured logging, not print statements

## Anti-Patterns (Never Do)
Things the agent must actively avoid. Often learned from past mistakes.
- Never use SELECT * in production queries
- Never store secrets in environment variables committed to git
- Never modify the ORM models without a migration

## Build & Verify
How to verify work is correct. This feeds directly into the loop's oracle.

Run tests

pytest tests/ -x --tb=short

Type check

pyright src/

Lint

ruff check src/ --fix

Build

docker build -t app .



## Common Tasks
Brief guides for tasks the loop handles frequently.

### Adding a new API endpoint
1. Define schema in schemas/
2. Implement handler in routes/
3. Add integration test in tests/integration/
4. Update OpenAPI spec

### Fixing a failing test
1. Read the test to understand intent
2. Read the error to understand the failure
3. Fix the source code, not the test (unless the test is wrong)
4. Run the specific test, then the full suite

11.4 Progressive Disclosure

Not every run needs all project knowledge. A bug fix loop doesn't need the deployment architecture. A documentation loop doesn't need the testing strategy. Loading everything into every context wastes tokens on irrelevant information.

Progressive disclosure loads skills in layers:

Layer 0 — Always loaded (~2K tokens):

  • Project name and purpose
  • Tech stack (language, framework, key deps)
  • Build and test commands

Layer 1 — Loaded for code tasks (~5K tokens):

  • Architecture overview
  • Coding conventions
  • File organization
  • Key rules

Layer 2 — Loaded on demand (~variable):

  • Domain-specific knowledge (auth patterns, data model, API design)
  • Common task guides
  • Anti-patterns and lessons learned

class SkillLoader:
    def load_for_task(self, task_type: str) -> str:
        context = self.load_layer_0()  # Always
        
        if task_type in ("code", "fix", "refactor", "test"):
            context += self.load_layer_1()
        
        if task_type == "auth":
            context += self.load_domain_skill("authentication")
        elif task_type == "api":
            context += self.load_domain_skill("api_design")
        
        return context

11.5 Skill Composition

Large projects have multiple skills that compose:


project_skill.md          — Overall project context (Layer 0-1)
├── auth_skill.md         — Authentication domain knowledge
├── api_skill.md          — API design patterns and conventions
├── testing_skill.md      — Testing strategy and patterns
├── deployment_skill.md   — Deployment process and constraints
└── data_skill.md         — Data model and migration patterns

The loop loads the base skill plus domain-specific skills based on the task. A fleet orchestrator might load only the base skill (to plan) while delegating domain-specific work to specialists who load the relevant domain skill.

11.6 Skill Versioning

Skills change as projects evolve. A skill file that says "we use Jest for testing" when the project migrated to Vitest last month will cause the loop to use the wrong test runner.

Version management approaches:

1. Git-tracked skills: Skills live in the repository alongside the code. When the code changes, the skill is updated in the same PR. This ensures skills and code stay synchronized.

2. Auto-generated skills: A script reads the project structure and generates baseline skills automatically. Human-curated additions are maintained separately and merged with the auto-generated base.


# Auto-generate skill base from project structure
skill-gen --project . --output .claude/skills/project_skill.md

# Output includes:
# - Detected tech stack (from package.json, requirements.txt, etc.)
# - File structure overview
# - Build commands (from Makefile, package.json scripts, etc.)
# - Test commands (detected from config files)

3. Skill-per-branch: For projects with long-lived branches that diverge significantly, maintain branch-specific skill overrides.

11.7 Skill Quality Metrics

How do you know if a skill is good? Two metrics:

1. First-attempt success rate: How often does the loop succeed without needing to re-discover information that should be in the skill? If the loop frequently reads files to learn things the skill should have told it, the skill is incomplete.

2. Token efficiency: Compare total tokens consumed with and without the skill. A good skill reduces total loop token consumption by 30-60% despite adding tokens to the initial context.

Common skill quality issues:

Symptom Cause Fix
Loop asks "what testing framework?" Missing from skill Add Build & Verify section
Loop uses wrong file paths Stale architecture section Update with current structure
Loop violates project conventions Missing from Rules section Add discovered conventions
Loop recreates existing patterns No Common Tasks section Add task guides for frequent work
Loop reads too many files in discovery Skills too vague Add specific file paths and patterns

11.8 Skills for Different Loop Types

Different loops benefit from different skill emphases:

Coding loop skills emphasize:

  • Architecture and file structure
  • Testing commands and patterns
  • Coding conventions and anti-patterns
  • Dependency management

Research loop skills emphasize:

  • Domain expertise boundaries
  • Trusted sources and how to access them
  • Quality criteria for findings
  • Output format requirements

Operations loop skills emphasize:

  • System topology and dependencies
  • Runbook procedures
  • Escalation paths
  • SLA thresholds

Content loop skills emphasize:

  • Voice and tone guidelines
  • Audience definition
  • Structure templates
  • Quality rubrics

11.9 The Skill Lifecycle

Skills aren't write-once artifacts. They evolve:

1. Bootstrap: Auto-generate from project structure. Covers basics: stack, commands, file layout.

2. Curate: Human adds domain knowledge, rules, anti-patterns, and task guides. This is where the real value lives — things the auto-generator can't know.

3. Iterate: As the loop runs and encounters issues, update the skill. Every time the loop fails because of missing context, that context belongs in the skill.

4. Prune: Remove stale information. Skills that grow without pruning become noise. If a section hasn't been relevant in months, consider removing it.

5. Split: When a skill exceeds ~10K tokens, split it into composable sub-skills with progressive disclosure.

11.10 Skills vs. CLAUDE.md

In the Claude Code ecosystem, CLAUDE.md serves a similar purpose to skills — project instructions loaded into context. The distinction:

  • CLAUDE.md: Global project instructions. Always loaded. Covers everything.
  • Skills: Composable, domain-specific knowledge modules. Loaded on demand.

For simple projects, CLAUDE.md is sufficient. For complex projects with multiple domains, skills provide finer-grained control over what context is loaded when.

The evolution: start with CLAUDE.md for overall project context. When CLAUDE.md exceeds 15K tokens or when different tasks need different knowledge, split into skills.
