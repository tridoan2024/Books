Chapter 6: LLMs as Unreliable Reasoning Engines

Level: S (Standard) · ~4,000 words · Levels served: L3, L4, L5

6.1 The Reliability Illusion

Large language models feel reliable on any single call. Ask Claude to write a function, and it produces something correct 90-95% of the time. Ask it to explain a concept, and the explanation is sound 95%+ of the time. The per-step accuracy is impressive enough that most practitioners trust it implicitly.

This trust breaks down over sequences. A loop doesn't make one call — it makes five, ten, fifty. Each call introduces a small probability of error. Those probabilities compound multiplicatively, not additively. And the result is catastrophic failure rates that the per-step accuracy completely masks.

6.2 The Compounding Math

The fundamental equation of loop reliability:


P(all steps correct) = P(step correct) ^ number_of_steps

This is the product rule of independent probabilities. If each step has accuracy p, then a sequence of n steps has accuracy p^n.

The numbers are sobering:

Per-Step Accuracy 5 Steps 10 Steps 20 Steps 50 Steps
99% 95.1% 90.4% 81.8% 60.5%
95% 77.4% 59.9% 35.8% 7.7%
90% 59.0% 34.9% 12.2% 0.5%
85% 44.4% 19.7% 3.9% 0.03%

At 95% per-step accuracy — which is genuinely excellent for any individual LLM call — a 20-step sequence fails two-thirds of the time. A 50-step sequence fails 92% of the time.

This isn't a criticism of LLMs. It's mathematics. The same math applies to any system with independent failure modes: network packets, manufacturing tolerances, sequential test execution. The difference is that those domains have decades of engineering practice around error correction. LLM-based systems are only now developing theirs.

6.3 Why Steps Aren't Independent

The situation is actually worse than the naive calculation suggests, because steps in an LLM loop are not independent. Errors correlate and cascade:

Correlated failures

If a model misunderstands the project architecture on step 1 (discovery), every subsequent step builds on that misunderstanding. Steps 2-20 don't each have an independent 5% failure chance — they have a 5% chance of failure given that step 1 was correct. If step 1 was wrong, steps 2-20 may all be wrong with much higher probability.

Error amplification

A small error in step 3 can produce a larger error in step 7. The model makes an off-by-one error in an array index. Later, it uses that index in a calculation. Still later, it uses that calculation in a condition. The original off-by-one becomes a logic error that's much harder to detect and fix.

Confidence drift

Models don't distinguish between things they know and things they believe. If a model hallucinates a fact in step 5 and that fact enters the context, the model will treat it as ground truth in all subsequent steps. The hallucination doesn't get weaker with repetition — it gets stronger, because now it has the reinforcement of appearing in the conversation history.

6.4 The Decomposition Consequence

The compounding math has a direct engineering consequence: loop length must be inversely proportional to per-step unreliability.

If your model achieves 95% per-step accuracy, you can run approximately 5-7 steps before cumulative reliability drops below 75%. Beyond that, you need verification checkpoints.

If your model achieves 99% per-step accuracy (only achievable on narrow, well-specified tasks with clear success criteria), you can run 10-15 steps safely.

This creates the decomposition imperative: complex goals must be broken into sub-goals, each achievable in a short sequence, with verification between sub-goals. The verification step resets the error accumulation.


Without verification:
  Step 1 → Step 2 → Step 3 → ... → Step 20
  Cumulative reliability: 0.95^20 = 35.8%

With verification every 5 steps:
  [Step 1 → ... → Step 5] → VERIFY → [Step 6 → ... → Step 10] → VERIFY → ...
  Per-segment reliability: 0.95^5 = 77.4%
  4 segments × 77.4% × detection correction = much higher overall

The verification step serves two functions:

  1. Error detection: Catch failures before they propagate
  2. Context reset: If the verification step feeds clean state into the next segment, you reset the error accumulation

6.5 Error Categories in LLM Reasoning

Not all errors are equal. Understanding the error taxonomy helps you build targeted verification:

Factual errors (hallucination)

The model states something that isn't true. "This function is defined in utils.py" when it's actually in helpers.py. "The API requires authentication" when it doesn't.

Detection: Ground-truth comparison. Check the claim against reality (read the file, test the API, verify the assertion).

Logic errors

The model reasons incorrectly. "Since A implies B, and we have B, therefore A." (Affirming the consequent.) "The function handles null because it checks for empty string." (Null ≠ empty string.)

Detection: Property testing. Check logical invariants that the output must satisfy regardless of the specific content.

Omission errors

The model forgets to handle a case. Edge cases, error paths, race conditions, boundary values — things that require actively thinking about what's not there.

Detection: Coverage analysis. Checklist validation against known requirements.

Drift errors

The model gradually moves away from the original intent. Each step is locally reasonable, but the overall direction diverges from the goal. The model rewrites a function for "clarity" and subtly changes its semantics.

Detection: Goal-level verification. Compare the output against the original specification, not just against the previous step.

Sycophancy errors

The model agrees with implied preferences in the prompt rather than stating the truth. If the context suggests a certain approach is preferred, the model will validate that approach even if it's flawed.

Detection: Adversarial checker. A separate agent, prompted to find flaws, without the context that created the bias.

6.6 The Verification Dividend

Here's the good news: verification per step doesn't need to match generation accuracy. Even imperfect verification dramatically improves cumulative reliability.


def loop_with_verification(
    per_step_accuracy: float,
    error_detection_rate: float,
    correction_accuracy: float,
    steps: int
) -> float:
    """
    Model: after each step, an oracle catches errors with probability
    detection_rate. Caught errors are corrected with probability
    correction_accuracy.
    """
    effective_accuracy = (
        per_step_accuracy +
        (1 - per_step_accuracy) * error_detection_rate * correction_accuracy
    )
    return effective_accuracy ** steps

With 95% per-step accuracy, 80% error detection, and 90% correction accuracy:

  • Effective per-step: 95% + 5% × 80% × 90% = 98.6%
  • Over 20 steps: 98.6%^20 = 75.5% (vs. 35.8% without verification)

With 95% per-step accuracy, 95% error detection, and 95% correction:

  • Effective per-step: 95% + 5% × 95% × 95% = 99.5%
  • Over 20 steps: 99.5%^20 = 90.5%

Imperfect verification still provides a dramatic improvement. You don't need a perfect oracle. You need a good-enough oracle that catches most errors and provides actionable feedback for correction.

6.7 Practical Implications for Loop Design

The reliability math drives five concrete design principles:

Principle 1: Short steps with frequent verification

Don't plan a 20-step sequence and run it end-to-end. Plan 4 segments of 5 steps, with verification between segments. The cumulative reliability per segment is much higher than end-to-end.

Principle 2: Decompose until steps are verifiable

If you can't verify the output of a step, you can't detect errors at that step. Decompose until each step produces something checkable. "Improve the codebase" is not verifiable. "Make this specific test pass" is.

Principle 3: Invest in oracle quality proportional to sequence length

Short loops (3-5 steps) can tolerate weak oracles. Long loops (15+ steps) need strong oracles at each checkpoint, or error accumulation will destroy reliability regardless of model quality.

Principle 4: Use independent verification

The agent that produced the output is the worst judge of that output. It shares the context, including any misconceptions, that produced the error in the first place. Independent verification — a separate model, a separate context, or a deterministic check — catches errors the producer is blind to.

Principle 5: Budget for iteration, not just execution

A 20-step task at 95% per-step accuracy will fail 64% of the time without verification. With verification and correction, it will succeed ~90% of the time — but only if the loop has budget for the correction iterations. Budget 2-3x the minimum tokens needed for a single pass.

6.8 The Model Quality Investment

Given these realities, where should you invest in model quality?

The high-leverage investment: Improve per-step accuracy from 90% to 95%. This changes 20-step reliability from 12.2% to 35.8% — still bad, but it reduces the correction burden dramatically.

The diminishing-returns investment: Improve per-step accuracy from 97% to 99%. Over 20 steps, this improves from 54.4% to 81.8%. Meaningful, but expensive in model cost. The same improvement could often be achieved cheaper by improving the oracle.

The practical approach: Use the best model you can afford at the per-step level, then invest heavily in verification. A 95%-accurate model with a 90%-detection oracle outperforms a 99%-accurate model with no oracle for any sequence longer than 10 steps.

6.9 Why This Makes Loops Necessary, Not Optional

The compounding failure math seems like an argument against loops. "If LLMs fail over sequences, don't run sequences."

The opposite is true. The compounding math is an argument for loops — specifically, for loops with verification. Without a loop, you have a single-pass generation with no error correction. The output quality is exactly the model's one-shot accuracy. For simple tasks, that's fine. For complex tasks requiring multiple decisions, the math guarantees failure.

Only a loop — with verification, correction, and iteration — can achieve reliable outcomes on multi-step tasks. The loop doesn't eliminate unreliability. It contains it. Each verification step bounds the error, and each correction step reduces it. The result is a system that reliably produces correct output despite being built on an unreliable foundation.

This is not a new engineering pattern. Error-correcting codes, TCP/IP, and RAID arrays all achieve reliability from unreliable components through redundancy and verification. Loop engineering is the LLM-native version of the same principle: reliable systems from unreliable parts, through structured verification and iteration.
