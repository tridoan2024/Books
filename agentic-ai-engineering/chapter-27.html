Chapter 27: Token Economics of Loops

Level: A (Anchor) · ~5,800 words · Levels served: L3, L4, L5

27.1 Cost Kills Loops Before Bugs Do

Most loops that get abandoned aren't abandoned because they don't work. They're abandoned because they're too expensive. A loop that costs $5 per run and runs 50 times a day costs $250/day — $7,500/month. If the value it produces is less than that, it dies regardless of how clever it is.

Token economics is the discipline of understanding where those tokens go and reducing the spend without reducing the quality. It's not optimization for optimization's sake — it's the difference between a loop that runs in production and one that stays a demo.

27.2 Where Tokens Go: The Anatomy of Loop Cost

A single-agent loop running a code fix task typically consumes 50K-200K tokens. Here's where they go:


Token budget breakdown (typical 150K token code-fix loop):

Input tokens (things the model reads):
├── System prompt + skills:      8,000  (5%)
├── Tool schemas (active):       5,000  (3%)
├── Conversation history:       25,000  (17%)
├── Tool results (file reads):  40,000  (27%)
├── Oracle feedback:             5,000  (3%)
└── Re-reading own output:      12,000  (8%)
    Subtotal input:             95,000  (63%)

Output tokens (things the model writes):
├── Reasoning / thinking:       20,000  (13%)
├── Tool calls:                  5,000  (3%)
├── Code generation:            15,000  (10%)
├── Plan updates:                3,000  (2%)
└── Final output:                2,000  (1%)
    Subtotal output:            45,000  (30%)

Overhead:
├── Failed iterations (wasted):  7,000  (5%)
└── Retried tool calls:          3,000  (2%)
    Subtotal overhead:          10,000  (7%)

TOTAL:                         150,000  (100%)

Key insight: input dominates.

63% of tokens are input — things the model reads. This is where cost reduction has the most leverage. Reducing what the model reads (through context engineering, tool result summarization, and history pruning) has 2x the impact of reducing what the model writes.

The retry tax:

Every failed iteration isn't just "one more attempt." It adds:

  • The oracle feedback tokens (what went wrong)
  • The plan update tokens (what to try next)
  • All accumulated context from previous iterations
  • The new attempt's generation tokens

By iteration 5, the context has grown by 30-50K tokens beyond what iteration 1 required. Each retry is MORE expensive than the last because context accumulates.

└── Coordination overhead:       10,000
    Subtotal:                    95,000

├── Verification:                15,000
└── Report generation:           10,000
    Subtotal:                   105,000

Specialist B (data flow):        95,000
Specialist C (API surface):     110,000

Communication overhead:
├── Delegation messages:          5,000

At $3/M input + $15/M output (Claude Sonnet pricing), that's roughly:

  • Input (~400K): $1.20
  • Output (~230K): $3.45
  • Total per fleet run: ~$4.65

If this runs on every PR (50/day): $232/day = $6,975/month.

27.4 The Cost-Per-Verified-Outcome Metric

Raw token cost is misleading. The metric that matters is cost per verified outcome — how much you spend to produce one result that passes the oracle.


Cost per verified outcome = Total tokens spent / Number of successful outputs

If a loop succeeds 80% of the time at 150K tokens per run:

  • Average cost per success: 150K / 0.80 = 187.5K tokens
  • The 20% failures add cost without producing value

If you improve success rate to 95%:

  • Average cost per success: 150K / 0.95 = 158K tokens
  • Better success rate directly reduces cost per outcome

This is why oracle quality matters economically: a better oracle improves success rate, which reduces cost per verified outcome, which makes the loop sustainable.

27.5 The Weekly-Millions Reality

Scheduled loops add up fast:

Loop Frequency Tokens/Run Daily Monthly
PR security review 50/day 200K 10M 300M
Nightly dependency audit 1/day 500K 500K 15M
Hourly PR re-scan 24/day 100K 2.4M 72M
Daily code quality check 1/day 300K 300K 9M
Total 13.2M 396M

At $3/M input + $15/M output (assume 60/40 split): roughly $3,960/month in API costs alone.

This is real. Teams running production loop fleets spend thousands per month on API costs. The question isn't "can we afford any loops?" — it's "which loops produce enough value to justify their cost, and how do we make the rest cheaper?"

27.6 The Token Cost Breakdown by Phase

Different loop phases have different cost profiles:

Phase Token Cost Value Produced Optimization Opportunity
Discovery High (reading files, searching) Context for reasoning Just-in-time retrieval
Planning Low (reasoning) Direction for execution Minimal — necessary thinking
Execution Medium (tool calls + generation) The actual output Better first-attempt accuracy
Verification Low-Medium (oracle evaluation) Quality assurance Cheaper oracles, tiered checking
Iteration High (retry overhead) Error correction Better feedback, faster convergence

The highest-leverage optimization: Reduce iteration count. Every iteration avoided saves the full cost of one discovery + planning + execution + verification cycle. Improving first-attempt success rate from 60% to 80% eliminates 33% of iterations.

27.7 Model Cost Tiers

Not every step requires the same model. Cost engineering uses the right model for each step:

Model Tier Cost (approx) Capability Use For
Haiku $0.25/M in, $1.25/M out Fast, shallow reasoning Classification, formatting, simple extraction
Sonnet $3/M in, $15/M out Strong reasoning Implementation, analysis, most specialist work
Opus $15/M in, $75/M out Deep reasoning Planning, synthesis, complex judgment

A naive loop uses Opus for everything: expensive. A cost-engineered loop cascades:


# Cost-engineered model selection
def select_model(step_type: str) -> str:
    if step_type in ("format", "extract", "classify", "summarize"):
        return "haiku"
    elif step_type in ("implement", "review", "analyze", "test"):
        return "sonnet"
    elif step_type in ("plan", "synthesize", "resolve_conflict", "architecture"):
        return "opus"
    return "sonnet"  # Default

The savings are dramatic. If 30% of steps can use Haiku (12x cheaper than Sonnet) and only 10% need Opus (5x more expensive), the weighted average cost drops significantly.

27.8 Input Token Reduction Strategies

Since input tokens are 63% of total cost, reducing them has the most impact:

Strategy 1: Aggressive context pruning

Remove tool results older than 2 iterations. Summarize conversation history. Keep only the current state + last iteration in full detail.

Savings: 30-50% of input tokens in multi-iteration loops.

Strategy 2: Programmatic pre-processing

Use code (not the model) to extract relevant portions of files before loading them into context. Don't feed a 3000-line file when only lines 40-65 matter.

Savings: 60-80% of file-reading tokens.

Strategy 3: Tool Search instead of pre-loading schemas

Load only the tool schemas the model actually uses (3-5 tools) instead of all available tools (30-50).

Savings: 40-50K tokens per loop that would have been wasted on unused tool definitions.

Strategy 4: Skill-based cold start

Load project knowledge from skills instead of discovering it each run through file reads and searches.

Savings: 20-40K tokens per run that would have been spent on repeated discovery.

27.9 Output Token Reduction Strategies

Strategy 1: Constrained generation

Use structured output (JSON schemas) to prevent the model from generating verbose explanations when all you need is a data structure.

Strategy 2: Extended thinking budgets

Claude's extended thinking feature lets you set a budget for reasoning tokens. For simple steps, limit thinking to 1K tokens. For complex steps, allow 10K.


# Budget thinking tokens per step type
thinking_budgets = {
    "simple_edit": 1024,
    "code_review": 4096,
    "architecture_decision": 16384,
}

Strategy 3: Batch processing

Instead of one model call per item, batch multiple items into a single call. One call to review 5 findings is cheaper than 5 separate calls.

27.10 The Kill Decision

Sometimes the most cost-effective action is to kill a loop that isn't converging:


class CostAwareStopController:
    def __init__(self, max_cost_per_outcome: float):
        self.max_cost = max_cost_per_outcome
        self.tokens_spent = 0
        self.best_score = 0.0
    
    def should_kill(self, current_score: float) -> bool:
        cost_so_far = self.tokens_spent * self.cost_per_token
        
        # If we've spent more than the max without reaching threshold
        if cost_so_far > self.max_cost and current_score < self.success_threshold:
            return True
        
        # If the trend suggests we won't converge within budget
        if self.projected_cost_to_converge() > self.max_cost * 2:
            return True
        
        return False

Killing a failing loop early saves the remaining budget for a different approach — or for escalation to a human who can solve it in 5 minutes.

If the monthly cost exceeds the monthly value — don't run the loop. Invest the budget in a different approach.
