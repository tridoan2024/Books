Chapter 5: When Not to Build a Loop

Level: S (Standard) · ~4,000 words · Levels served: All

5.1 The Automation Trap

Every new capability creates a temptation to apply it everywhere. Loops are powerful. They ship verified work without human gates. Therefore — the reasoning goes — every task should be a loop.

This reasoning is wrong. Loops carry costs that simple workflows don't: token burn on iteration, oracle maintenance, failure mode complexity, and the cognitive overhead of debugging autonomous systems. A loop that costs $3 to produce what a human could produce in 30 seconds isn't engineering — it's performance art.

Before building a loop, pass the task through three gates. If it fails any one, don't build a loop. Build a simpler system instead.

5.2 Gate 1: Verifiability

The question: Can you write a machine-checkable oracle for this task's output?

If you can't verify the output automatically, you can't close the loop. Without an oracle, the loop degenerates into generation-without-verification — which is just a single prompt with extra steps and extra cost.

Tasks that pass Gate 1:

  • Code generation: Tests verify correctness. Type checkers verify safety. Linters verify style.
  • Data transformation: Schema validation. Input/output pair comparison. Row counts and checksums.
  • Structured content: Format validation. Required-field checks. Cross-reference consistency.
  • Classification: Ground-truth labels exist for evaluation.

Tasks that fail Gate 1:

  • Creative writing with no rubric: "Write something beautiful" has no oracle. (But "Write a paragraph that scores 8+ on these five criteria" does — so reframe before rejecting.)
  • Strategic decisions: "Should we enter the European market?" cannot be mechanically verified.
  • Taste judgments: "Is this logo good?" depends on subjective evaluation that doesn't reduce to computable criteria.
  • Novel research: "Discover something new about protein folding" has no oracle because you don't know the answer yet.

The reframe test: Before concluding a task is unverifiable, ask: "Could I write a rubric?" Many seemingly unverifiable tasks become verifiable once you define explicit criteria. "Write good documentation" fails Gate 1. "Write documentation that covers all public API methods, includes at least one example per method, and passes the readability formula at grade 8" passes.

If you can't write the rubric and you can't reframe the task into something with a rubric — don't build a loop. Use a single-pass model call with human review.

5.3 Gate 2: Unit Economics

The question: Is the cost of loop operation (tokens + oracle + infrastructure) less than the cost of human operation for the same task?

A loop that costs more than a human is a net loss. This sounds obvious, but it's surprisingly easy to build expensive loops for cheap tasks.

The math:


Loop cost per task = (avg_iterations × tokens_per_iteration × cost_per_token)
                   + oracle_cost_per_verification
                   + infrastructure_overhead

Human cost per task = hourly_rate × time_in_hours

Build a loop when: loop_cost_per_task × volume < human_cost_per_task × volume + loop_build_cost

Where the math kills loops:

Low-volume tasks: If a task happens once a week, the build cost of the loop may never amortize. A 2-hour loop build that saves 5 minutes per run needs 24 runs to break even. At once-per-week, that's 6 months.

Fast human tasks: If a human can do the task in under a minute (quick review, simple classification, obvious fix), the loop's iteration overhead likely exceeds the human cost. Don't automate tasks that are already fast.

Tasks that rarely fail: If the model gets it right on the first pass 98% of the time, the verification and iteration machinery exists for 2% of cases. The infrastructure cost of maintaining the oracle for those 2% may exceed the cost of human review for the 2%.

Where the math favors loops:

High-volume tasks: Processing 500 PRs per day for security review. At 10 minutes human review each, that's 83 hours of human time daily. A loop at $0.50 per PR costs $250/day vs. $6,000+/day in human cost.

Human-slow tasks: Tasks where human review takes 30+ minutes each but loop verification takes seconds. Deep code review, comprehensive test generation, multi-source research synthesis.

Consistency-critical tasks: Tasks where human fatigue introduces errors. The 400th PR reviewed at 4pm on Friday gets less attention than the first PR on Monday morning. Loops don't get tired.

5.4 Gate 3: Blast Radius

The question: If the loop produces wrong output and ships it, what's the worst-case damage?

Loops can fail. Oracles can miss. The question isn't whether failure is possible — it's whether failure is survivable.

Low blast radius (loop-friendly):

  • Generating a draft that a human will review before publishing
  • Creating a PR that requires human approval before merging
  • Producing an internal report that informs but doesn't trigger action
  • Running analysis on a copy of data, not production data

High blast radius (loop-hostile):

  • Sending emails to customers
  • Deploying to production
  • Modifying financial records
  • Deleting data
  • Publishing content publicly
  • Making irreversible infrastructure changes

The mitigation spectrum:

High blast radius doesn't automatically disqualify a loop. It means the loop needs stronger safeguards:

Blast Radius Mitigation Loop Example
None No mitigation needed Generate an internal summary
Low Automated oracle sufficient Fix a failing test on a feature branch
Medium Oracle + dry-run + human approval before final action Generate a PR with changes
High Oracle + approval gate + canary + rollback plan Deploy a configuration change
Critical Don't loop. Human in the loop. Always. Delete customer data

5.5 The Workflow Alternative

When a task fails one or more gates, the answer isn't always "just use a human." There's a middle ground: deterministic workflows with an LLM step.

A workflow is a fixed pipeline where each step is predetermined by the developer. An LLM fills one or more slots in the pipeline, but the LLM doesn't decide what happens next — the pipeline does.


Workflow (deterministic):
  Step 1: Fetch data from API
  Step 2: Call LLM to transform data
  Step 3: Validate output schema
  Step 4: Store in database

Loop (adaptive):
  Step 1: LLM decides what data to fetch
  Step 2: LLM fetches and transforms
  Step 3: LLM evaluates its own output
  Step 4: LLM decides whether to retry or proceed

Workflows are cheaper (no iteration), simpler (no oracle needed beyond schema validation), and more predictable (fixed paths are debuggable). They sacrifice adaptability — the system can't recover from novel failures — but for many tasks, adaptability isn't needed.

The decision rule: If the task has a known path from input to output and the only uncertainty is "can the LLM fill this slot correctly?" — build a workflow, not a loop. Use a loop only when the path itself is uncertain or when iteration is needed to reach quality.

5.6 The Hybrid Pattern

Many production systems combine workflows and loops:


Workflow level:
  1. Trigger: PR opened
  2. Fetch diff (deterministic)
  3. LOOP: Review diff for issues (iterate until confident)
  4. Post review comment (deterministic)
  5. LOOP: If author replies, re-evaluate (iterate until resolved)
  6. Cast vote (deterministic)

The workflow provides the skeleton — the fixed sequence of what happens. The loops fill in the adaptive parts — where the system needs to reason, iterate, and verify. This hybrid gives you the predictability of workflows with the quality of loops, at the cost of complexity.

5.7 The Decision Matrix

Pull it all together into a quick-reference matrix:

Verifiable? Economical? Low blast? Build
Yes Yes Yes Full loop — autonomous, iterate until done
Yes Yes No Loop + approval gate — loop produces, human ships
Yes No Yes Workflow with retry — fixed path, one retry on failure
Yes No No Workflow + human review — LLM slot, human gate
No Yes Yes Single pass + human eval — generate once, human checks
No Yes No Human only — don't automate
No No * Human only — don't automate

5.8 Antipatterns

Common mistakes that violate these gates:

The Gold-Plated Loop: Building a full fleet with specialists, memory, and cross-run learning for a task that happens three times a month. The infrastructure cost exceeds the value for years.

The Unverifiable Loop: "Generate marketing copy that resonates with our audience." There's no oracle. The loop iterates blindly, producing variants but never converging on quality. The human still reviews everything. You've built an expensive random-content generator.

The High-Stakes YOLO: Running an autonomous loop that posts to social media, sends emails, or modifies production infrastructure without a human gate. When it fails — and it will — the damage is immediate and public.

The Premature Fleet: Splitting a task across five specialist agents when a single agent with a good skill file would handle it in one context window. Fleets add communication overhead, coordination complexity, and cost. Use them only when a single agent demonstrably can't handle the task.

The Infinite Oracle: Building a verification system that costs more than the generation it verifies. If your oracle is a full manual test run by a QA team, the loop hasn't automated anything — it's just added a generation step before the existing human process.

5.9 The Meta-Rule

When in doubt, start with the simplest thing that could work:

  1. Single model call with human review
  2. Model call with automated validation (schema, type, format)
  3. Model call with retry on validation failure
  4. Loop with oracle and budget
  5. Fleet with specialists and orchestration

Escalate only when the simpler approach demonstrably fails. Each escalation adds cost, complexity, and failure modes. The right level is the lowest level that meets the task's actual requirements.
