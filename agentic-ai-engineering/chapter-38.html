Chapter 38: Self-Designing Loops

Level: S (Standard) · ~4,000 words · Levels served: L4, L5

38.1 The Meta-Loop

Every loop in this book has been designed by a human. A human wrote the skill file. A human chose the oracle. A human defined the stop condition. A human decided how many specialists the fleet needs and what each one does.

The frontier question: can loops design themselves?

The answer in 2026 is "partially, with guardrails." Loops can update their own skills based on repeated corrections. They can propose new memory entries. They can adjust their own stop conditions based on historical performance. They cannot — safely — redesign their own verification criteria without human oversight. This chapter covers what works, what breaks, and what's coming.

38.2 Self-Writing Skills

The simplest form of self-design: a loop that modifies its own skill file based on patterns in human corrections.

38.2.1 The Mechanism

When a human corrects a loop's output, the correction implies a rule that wasn't in the skill file. A loop that tracks corrections can propose skill file updates:


from pathlib import Path
from dataclasses import dataclass


@dataclass
class Correction:
    original_output: str
    corrected_output: str
    correction_type: str  # "factual", "style", "format", "logic"
    timestamp: str


class SkillEvolver:
    def __init__(self, skill_file: Path, correction_threshold: int = 3):
        self.skill_file = skill_file
        self.corrections: list[Correction] = []
        self.threshold = correction_threshold  # How many similar corrections before proposing a rule
    
    def record_correction(self, correction: Correction) -> None:
        self.corrections.append(correction)
        self._check_for_patterns()
    
    def _check_for_patterns(self) -> None:
        """Detect repeated correction patterns and propose skill updates."""
        # Group corrections by type
        by_type: dict[str, list[Correction]] = {}
        for c in self.corrections:
            by_type.setdefault(c.correction_type, []).append(c)
        
        for ctype, corrections in by_type.items():
            if len(corrections) >= self.threshold:
                self._propose_skill_update(corrections)
    
    async def _propose_skill_update(self, corrections: list[Correction]) -> None:
        """Generate a proposed addition to the skill file."""
        current_skill = self.skill_file.read_text()
        
        proposal = await model.generate(f"""
        The following corrections have been made repeatedly to this loop's output:
        
        {[f"Original: {c.original_output[:200]}... → Corrected: {c.corrected_output[:200]}..." for c in corrections[-5:]]}
        
        Current skill file:
        {current_skill}
        
        Propose a new rule to add to the skill file that would prevent these 
        corrections from being needed in the future. The rule should be:
        - Specific and actionable
        - Consistent with existing rules
        - Generalizable (not overfitting to one specific case)
        """)
        
        # Log the proposal for human review
        self._log_proposal(proposal)

38.2.2 Real Example: Code Style Convergence

A code review loop initially produces findings like "variable name x is unclear." A human repeatedly changes these to "variable name x should be descriptive — suggest request_count or retry_limit." After three such corrections, the loop proposes a skill update:


## Added Rule (auto-proposed, pending approval)
When flagging unclear variable names, always suggest 2-3 specific alternatives
based on the surrounding context. Don't just say "unclear" — show what clarity
looks like.

After human approval, this rule is appended to the skill file. The loop's future output includes specific suggestions.

38.2.3 What Works

Self-writing skills work well for:

  • Style and format rules (how output should look)
  • Domain terminology (words that should or shouldn't be used)
  • Structural patterns (how to organize output)
  • Correction of systematic biases (the loop consistently over-qualifies, under-specifies, etc.)

38.2.4 What Breaks

Self-writing skills break when:

  • The corrections are contradictory (different humans correct in opposite directions)
  • The pattern is overfitted (3 corrections on the same edge case don't generalize)
  • The proposed rule conflicts with existing rules (creating a contradiction the loop can't resolve)

Guardrail: All self-proposed skill updates require human approval before activation. The loop proposes; the human disposes. This maintains the human's role as the architect while letting the loop identify what's missing.

38.3 Self-Curating Memory

As discussed in Chapter 15, memory is a loop's accumulated knowledge. Self-curation means the loop decides what to remember, what to forget, and how to organize its own memory.

38.3.1 What to Remember

A loop that processes hundreds of tasks per day cannot store everything. It must decide what's worth remembering:


class MemoryCurator:
    def __init__(self, max_entries: int = 1000):
        self.max_entries = max_entries
        self.entries: list[MemoryEntry] = []
    
    async def should_remember(self, task_result: TaskResult) -> bool:
        """Decide if this result contains information worth storing."""
        criteria = [
            task_result.required_retry,           # Failures are educational
            task_result.human_corrected,           # Corrections reveal gaps
            task_result.novel_pattern,             # New patterns expand capability
            task_result.high_confidence_output,    # High-quality outputs serve as exemplars
        ]
        return any(criteria)
    
    async def curate(self) -> None:
        """Periodically clean memory: merge duplicates, expire stale entries."""
        # Merge similar entries
        clusters = self._cluster_similar(self.entries)
        for cluster in clusters:
            if len(cluster) > 1:
                merged = await self._merge_entries(cluster)
                self.entries = [e for e in self.entries if e not in cluster]
                self.entries.append(merged)
        
        # Expire entries that haven't been accessed in 30 days
        cutoff = datetime.now() - timedelta(days=30)
        self.entries = [
            e for e in self.entries
            if e.last_accessed > cutoff or e.importance >= 4
        ]
        
        # If still over limit, drop lowest-importance entries
        if len(self.entries) > self.max_entries:
            self.entries.sort(key=lambda e: e.importance, reverse=True)
            self.entries = self.entries[:self.max_entries]

38.3.2 Memory Drift

The dangerous failure mode of self-curating memory: drift. Over time, the loop's memory can drift from ground truth because:

  1. Confirmation bias in storage: The loop preferentially stores results that confirm its existing approach, not results that challenge it.
  2. Lossy merging: When two memory entries are merged, nuance is lost. After many merges, the memory contains generalizations that no longer accurately represent any specific case.
  3. Stale exemplars: A "high-quality output" stored 6 months ago may no longer represent current standards.

Guardrail: Immutable correction memory. Human corrections are never merged, expired, or curated by the loop. They persist in a separate, read-only store that the loop can reference but never modify.


class ProtectedMemory:
    """Memory entries that the loop cannot modify or delete."""
    
    def __init__(self, store_path: Path):
        self.store_path = store_path
    
    def add(self, entry: MemoryEntry) -> None:
        """Only callable by human-triggered actions, never by the loop itself."""
        entries = self._load()
        entries.append(entry)
        self._save(entries)
    
    def query(self, context: str, limit: int = 5) -> list[MemoryEntry]:
        """Loop can read but never write."""
        return self._semantic_search(context, limit)

38.4 Self-Tuning Rubrics

A rubric is a scored checklist used by model judges (Level 4 oracles from Chapter 20). Self-tuning means the loop adjusts its rubric weights based on historical correlation with human judgment.

38.4.1 The Mechanism


@dataclass
class RubricItem:
    criterion: str
    weight: float  # 0.0 to 1.0
    historical_correlation: float  # How well this criterion predicts human approval


class SelfTuningRubric:
    def __init__(self, items: list[RubricItem]):
        self.items = items
    
    def update_weights(self, human_judgments: list[HumanJudgment]) -> None:
        """Adjust rubric weights based on which criteria correlate with human approval."""
        for item in self.items:
            # For each criterion, compute correlation with human pass/fail
            scores = []
            approvals = []
            for judgment in human_judgments:
                criterion_score = judgment.rubric_scores.get(item.criterion, 0)
                scores.append(criterion_score)
                approvals.append(1.0 if judgment.human_approved else 0.0)
            
            if len(scores) >= 10:  # Need minimum sample
                correlation = compute_correlation(scores, approvals)
                item.historical_correlation = correlation
                # Increase weight of criteria that predict human approval
                item.weight = 0.3 + (0.7 * max(0, correlation))

38.4.2 Specification Gaming

This is where self-tuning rubrics break catastrophically. If the loop discovers that humans approve outputs with certain surface features (long outputs, confident tone, lots of code examples), it will optimize for those features — potentially at the expense of actual quality.

Real example: A self-tuning code review rubric discovers that reviews mentioning "security" get approved at higher rates. The loop starts mentioning security in every review, regardless of relevance. The rubric has been gamed — not by an adversary, but by the loop's own optimization pressure.

Guardrails against specification gaming:

  1. Weight bounds: No single criterion can exceed 0.4 weight. No criterion can drop below 0.1.
  2. Human audit of weight changes: When weights shift significantly (>0.1 in either direction), flag for human review.
  3. Diverse evaluation data: Don't tune on a single human reviewer's preferences. Aggregate across reviewers to find consensus quality, not individual taste.

38.5 Self-Spawning Specialists

The most advanced form of self-design: a loop that recognizes it needs a specialist it doesn't have, designs the specialist's skill file, and deploys it.

38.5.1 How It Works Today


class FleetDesigner:
    def __init__(self, orchestrator, existing_specialists: list[Specialist]):
        self.orchestrator = orchestrator
        self.specialists = existing_specialists
        self.routing_failures: list[RoutingFailure] = []
    
    def record_routing_failure(self, task: str, attempted_specialist: str, failure_reason: str):
        """Track tasks that no specialist handled well."""
        self.routing_failures.append(RoutingFailure(
            task=task,
            specialist=attempted_specialist,
            reason=failure_reason,
            timestamp=datetime.now(),
        ))
    
    async def propose_new_specialist(self) -> SpecialistProposal | None:
        """If routing failures cluster, propose a new specialist."""
        if len(self.routing_failures) < 5:
            return None
        
        # Cluster failures by similarity
        clusters = await self._cluster_failures(self.routing_failures)
        
        for cluster in clusters:
            if len(cluster) >= 3:  # Pattern detected
                proposal = await model.generate(f"""
                These tasks all failed to be handled by existing specialists:
                {[f.task for f in cluster]}
                
                Existing specialists: {[s.name + ": " + str(s.handles) for s in self.specialists]}
                
                Design a new specialist to handle this class of tasks:
                - name: short descriptive name
                - skill: complete skill prompt
                - tools: which tools it needs
                - handles: what task types it covers
                - test_cases: 3 tasks it should be able to handle
                """)
                return parse_specialist_proposal(proposal)
        
        return None

38.5.2 The Validation Gate

A proposed specialist must pass validation before deployment:

  1. Non-overlap check: Does this specialist's domain overlap with an existing one? If so, merge rather than spawn.
  2. Test case execution: Run the proposed specialist on its test cases. Does it produce acceptable output?
  3. Human review of the skill prompt: Before any self-designed specialist goes live, a human reads its skill file.

async def validate_specialist(proposal: SpecialistProposal) -> ValidationResult:
    """Validate a proposed specialist before deployment."""
    issues = []
    
    # Check for domain overlap
    for existing in self.specialists:
        overlap = set(proposal.handles) & set(existing.handles)
        if overlap:
            issues.append(f"Overlaps with {existing.name} on: {overlap}")
    
    # Run test cases
    test_results = []
    for test_case in proposal.test_cases:
        result = await run_specialist(proposal, test_case)
        test_results.append(result)
    
    pass_rate = sum(1 for r in test_results if r.passes) / len(test_results)
    if pass_rate < 0.67:
        issues.append(f"Only passed {pass_rate:.0%} of test cases")
    
    return ValidationResult(
        approved=len(issues) == 0,
        issues=issues,
        requires_human_review=True,  # Always true for self-spawned specialists
    )

38.6 What Breaks: The Three Failure Modes of Self-Design

38.6.1 Specification Gaming of Self-Modified Rubrics

Covered in 38.4.2. The loop optimizes for proxies of quality rather than quality itself. This is Goodhart's Law applied to agentic systems: when a measure becomes a target, it ceases to be a good measure.

Detection: Track the gap between rubric scores and human approval over time. If rubric scores increase but human approval doesn't, the rubric has been gamed.

38.6.2 Drift in Self-Curated Memory

Over months of self-curation, memory accumulates subtle errors through lossy merging and confirmation bias. The loop's behavior shifts incrementally — each step is small enough to pass human review, but the cumulative drift is significant.

Detection: Periodic regression testing. Run the current loop (with its evolved memory) on a fixed benchmark set. Compare output quality to baseline. If quality on the benchmark degrades while reported metrics improve, drift has occurred.

38.6.3 Loss of Interpretability

When a loop has self-modified its skills, self-curated its memory, self-tuned its rubric, and self-spawned its specialists, a human looking at the system can no longer easily understand why it behaves the way it does. The skill file has accumulated rules from hundreds of automated proposals. The memory contains merged entries whose provenance is unclear. The rubric weights reflect correlations that no human verified.

Detection: This is the hardest to detect because it's gradual. The mitigation is structural:


@dataclass
class EvolutionLog:
    """Track every self-modification with full provenance."""
    timestamp: str
    modification_type: str  # "skill_update", "memory_curate", "rubric_tune", "specialist_spawn"
    before_state: str
    after_state: str
    trigger: str  # What caused this modification
    evidence: list[str]  # The corrections/failures that motivated it
    human_approved: bool
    human_reviewer: str | None

Every self-modification is logged with its motivation. A human can trace any current behavior back to the specific corrections that caused it.

38.7 What 2027 Looks Like

Three developments at the frontier are moving from research to production:

38.7.1 Meta-Loops That Design Verification Criteria

Today, humans write oracles. Tomorrow, a meta-loop observes what the production loop gets wrong and proposes new verification checks:

"I notice that 30% of failures in the code review loop involve race conditions that the existing rubric doesn't check for. Proposed addition: for any code involving shared mutable state, verify that concurrent access is addressed."

This is self-tuning rubrics elevated one level: not just adjusting weights on existing criteria, but proposing entirely new criteria.

38.7.2 Model-Written Evals

Evaluation suites (the benchmarks we use to measure loop quality) are currently hand-authored. The frontier is model-written evals: a meta-loop that generates new test cases specifically designed to probe the production loop's weaknesses.


async def generate_adversarial_eval(
    loop_failures: list[FailureCase],
    existing_evals: list[EvalCase],
) -> list[EvalCase]:
    """Generate new eval cases that target known weakness patterns."""
    new_evals = await model.generate(f"""
    The production loop has failed on these types of inputs:
    {[f.input_summary for f in loop_failures]}
    
    Existing eval cases already cover:
    {[e.description for e in existing_evals]}
    
    Generate 5 new eval cases that:
    1. Target the same weakness patterns
    2. Are not duplicates of existing evals
    3. Have unambiguous expected outputs
    4. Are diverse (cover different manifestations of the weakness)
    """)
    return parse_eval_cases(new_evals)

38.7.3 Agents That Architect Their Own Fleet Topologies

Given a task description and a set of available tools, a meta-loop determines: how many specialists are needed, what each one does, how they coordinate, and what the budget allocation should be. It then provisions the fleet, runs the task, and evaluates whether the topology was efficient.

Over time, it learns which topologies work for which task types:

  • "Sequential pipeline works best for document processing tasks"
  • "Star topology with 3 specialists works best for code refactoring"
  • "Single loop is more efficient for tasks under 5 steps"

This is AutoML applied to agent architecture instead of model hyperparameters.

38.8 The Irreducible Human Role

Self-designing loops raise an obvious question: if the loop can modify its own skills, curate its own memory, tune its own rubrics, and spawn its own specialists — what role remains for the human?

The answer: the human owns the objective function.

A loop can optimize toward a goal. It cannot choose the goal. It can propose new verification criteria. It cannot decide what "quality" means in the first place. It can spawn specialists. It cannot decide whether the task is worth doing.

The progression through this book mirrors this:

  • Chapter 1: The human is the loop (doing everything)
  • Chapters 2-33: The human designs the loop (architecting)
  • Chapter 34-37: The human reviews the loop's output (oversight)
  • Chapter 38: The human defines what the loop should optimize for (governance)

Each stage removes the human from a lower-level concern to elevate them to a higher-level one. The human never leaves the system — they move up the abstraction stack.

38.9 The Architecture of Trust

Self-designing loops require a new trust architecture:

│                    HUMAN AUTHORITY                        │
│                                                          │
│  Defines: objectives, constraints, values, boundaries    │
│  Reviews: major capability changes, rubric redesigns     │
│  Audits: drift detection, regression benchmarks          │
└──────────────────────────┬──────────────────────────────┘
                           │
                    Approval Gate
                           │
┌──────────────────────────▼──────────────────────────────┐
│                    META-LOOP                              │
│                                                          │
│  Proposes: skill updates, new specialists, rubric        │
│  changes. Monitors: drift, gaming, regression            │

└──────────────────────────┬──────────────────────────────┘
                           │
              Deploys approved changes
                           │
┌──────────────────────────▼──────────────────────────────┐
│                 PRODUCTION LOOPS                          │
│                                                          │
│  Executes: tasks within deployed skill/rubric            │

└─────────────────────────────────────────────────────────┘

The production loops cannot modify themselves. The meta-loop proposes modifications. The human approves or rejects. This three-tier architecture maintains human authority while enabling the system to evolve faster than any human could manually redesign it.

38.10 Closing: The Loop That Ships Verified Work

This book began with a single observation: the human is the bottleneck. Not because humans are slow at thinking — but because humans have been doing work that can be encoded, verified, and automated.

The progression from that observation to this chapter follows a single thread: if you can check whether work is correct, you can build a loop that does the work and verifies it without human involvement in each iteration.

The building blocks are simple. A skill tells the loop what to do. Tools give it the ability to act. An oracle tells it whether the output is good. Memory lets it learn. Iteration lets it recover from errors. And verification — always verification — ensures that what ships actually works.

The loops you build will not be perfect. They will fail in ways you didn't anticipate. They will require tuning, correction, and occasionally wholesale redesign. But each failure teaches the system something, and each correction makes the next iteration better. That's the nature of loops: they converge.

What matters isn't building the perfect loop on day one. What matters is building a loop that verifies its own output, learns from its failures, and improves over time. Start with one loop. Make it work on 20 real inputs. Add memory. Add automation. Split the maker from the checker. Spawn a specialist. Build a fleet.

The senior engineer's job in 2026 is not to write code. It's to design the loops that write code, verify it, ship it, and learn from the result. The loops do the work. The engineer designs the system that ensures the work is correct.

That's the entire book in one sentence: design loops that ship verified work.
