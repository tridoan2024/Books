Chapter 37: Your First 90 Days — From One Loop to a Fleet

Level: S (Standard) · ~4,000 words · Levels served: L3, L4, L5

37.1 The Staged Build Plan

You don't build a fleet on day one. You build one loop, prove it works, then add capabilities in a sequence where each stage's success validates the foundation for the next. This chapter provides that sequence — the order practitioners should actually follow, the common failure at each stage, and the "ready to advance" criteria.

Every team that has successfully deployed an agentic fleet followed this progression — whether they planned to or not. Teams that tried to skip stages (building a full fleet before proving one loop works reliably) universally regretted it. The fleet amplifies whatever the individual loop does — including its bugs. A fleet of unreliable loops is an unreliable fleet that fails in coordinated, hard-to-debug ways.

The six stages map to the building blocks from earlier chapters:

Stage Days What You Add Key Chapter Reference
1 1-7 First closed loop Skill + Tools + Oracle (Ch. 14, 20)
2 8-21 Memory and iteration Memory (Ch. 15) + Loop control (Ch. 14)
3 22-45 Automation triggers Scheduling + Event handling (Ch. 16)
4 45-60 Maker-checker split Oracle hierarchy (Ch. 20)
5 60-75 First specialist Fleet topology (Ch. 25)
6 75-90 Full fleet with orchestrator Coordination + Cost (Ch. 25, 28)

37.2 Days 1-7: Your First Closed Loop

Goal: One task, fully automated from input to verified output, with a human reviewing after the fact — not during.

What to build

Pick the simplest valuable task in your workflow. Not the hardest. Not the most interesting. The simplest one that currently consumes human time with predictable, verifiable steps. The selection criteria:

  1. Repetitive: It happens at least weekly.
  2. Deterministic success criteria: You can describe what "correct output" looks like without ambiguity.
  3. Low stakes: If the loop produces wrong output, the consequence is inconvenience, not catastrophe.
  4. Bounded scope: The task takes a human 5-30 minutes, not hours.

Good first loops:

  • Run linting on new PRs and post structured findings as comments
  • Generate a changelog from commits since the last release tag
  • Triage new GitHub issues by adding labels based on content analysis
  • Convert API response schemas into TypeScript interfaces
  • Summarize a meeting transcript into formatted action items with owners

Bad first loops (too complex for week 1):

  • Full code review with actionable fix suggestions
  • Customer support resolution
  • Security vulnerability remediation
  • Multi-step data pipeline debugging

The minimum viable implementation


from dataclasses import dataclass
from pathlib import Path

SKILL = """

changelog grouped by: Features, Fixes, Breaking Changes, Internal.

Rules:
- Omit commits with prefix "chore:", "ci:", "deps:", or "style:"
- Group by conventional commit prefix: feat: → Features, fix: → Fixes
- Write each entry as a user-facing sentence describing the impact
- If a commit references a GitHub issue (#NNN), include the link
- Breaking changes MUST be called out even if not using breaking: prefix
  (look for removed endpoints, changed return types, renamed config keys)
- Sort entries within each section by impact (user-visible first)
"""

# Day 3-4: Wire the tools
TOOLS = ["git_log", "git_diff", "file_read", "file_write"]

# Day 5-7: Define the oracle and close the loop
ORACLE = """
Verify the changelog against these criteria (all must pass):
1. COVERAGE: Every non-excluded commit appears in exactly one section
2. ACCURACY: No commit appears in multiple sections
3. GRAMMAR: Each entry is grammatically correct, starts with a verb
4. BREAKING: Any commit that removes/renames a public API is in Breaking Changes
5. LINKS: Every issue reference (#NNN) is properly linked
6. FORMAT: Output is valid markdown with correct heading levels
"""

Common failure: Over-engineering

The week-1 failure is building infrastructure before proving value. You don't need a message queue, a database, a retry framework, a monitoring dashboard, or a microservice architecture. You need a script that runs, produces output, and has a way to check if the output is correct. Everything else can be added later — but only after you've proven the core loop works.


# WRONG: Enterprise architecture on day 3
class ChangelogPipeline:
    def __init__(self, queue: RedisQueue, db: PostgresDB, monitor: Datadog,
                 retry: ExponentialBackoff, cache: RedisCache):
        ...

# RIGHT: Script that works
async def generate_changelog(since_tag: str) -> str:
    commits = subprocess.check_output(
        ["git", "log", "--oneline", f"{since_tag}..HEAD"]
    ).decode()
    
    result = await model.generate(SKILL + "\n\nCommits:\n" + commits)
    
    # Simple verification
    verification = await model.generate(ORACLE + "\n\nChangelog:\n" + result)
    if "FAIL" in verification:
        # One retry with feedback
        result = await model.generate(
            SKILL + f"\n\nPrevious attempt failed verification: {verification}"
            f"\n\nCommits:\n{commits}\n\nProduce a corrected changelog."
        )
    
    return result

Ready to advance when

  • The loop produces correct output on 80%+ of real inputs (not cherry-picked demos)
  • You've run it at least 20 times on diverse real inputs
  • You understand its failure modes: what inputs cause wrong output, and why
  • The oracle actually catches errors (test it by feeding in known-bad output)
  • Total cost per execution is predictable and acceptable

Budget for this stage: $5-20 total for week 1 experimentation. If you're spending more, you're over-engineering.

37.3 Days 8-21: Add Memory and Iteration

Goal: The loop remembers past executions and uses that memory to improve. It iterates on its own output rather than producing a one-shot answer.

What to add

Two capabilities that compound together:

  1. Execution memory: The loop stores what it did, what worked, what failed, and what humans corrected. This memory is consulted on future runs to avoid repeating mistakes.
  1. Multi-pass iteration: Instead of generate-once-verify-once, the loop generates, verifies, and revises until the oracle passes or the retry budget is exhausted.

from pathlib import Path
import json
from datetime import datetime


class LoopMemory:
    """Simple file-based memory for loop learning."""
    
    def __init__(self, memory_path: Path):
        self.path = memory_path
        self.path.mkdir(parents=True, exist_ok=True)
    
    def record_execution(
        self,
        input_summary: str,
        output: str,
        passed_oracle: bool,
        human_correction: str | None = None,
    ) -> None:
        """Store execution result for future reference."""
        entry = {
            "input": input_summary,
            "output": output[:500],  # Truncate for token efficiency
            "passed": passed_oracle,
            "correction": human_correction,
            "timestamp": datetime.now().isoformat(),
        }
        log_file = self.path / "executions.jsonl"
        with log_file.open("a") as f:
            f.write(json.dumps(entry) + "\n")
    
    def get_relevant_lessons(self, current_input: str, limit: int = 3) -> list[dict]:
        """Retrieve past corrections relevant to the current task."""
        log_file = self.path / "executions.jsonl"
        if not log_file.exists():
            return []
        
        # Return recent corrections (in production, use embedding similarity)
        entries = [json.loads(line) for line in log_file.read_text().splitlines()]
        corrections = [e for e in entries if e.get("correction")]
        return corrections[-limit:]

Multi-pass iteration with memory


async def iterate_with_memory(
    task: str,
    skill: str,
    oracle_criteria: str,
    memory: LoopMemory,
    max_iterations: int = 3,
) -> tuple[str, bool]:
    """Generate, verify, and revise until oracle passes or budget exhausted."""
    
    # Retrieve relevant past lessons
    lessons = memory.get_relevant_lessons(task)
    lesson_context = ""
    if lessons:
        lesson_context = "\n\nLessons from past executions (avoid these mistakes):\n"
        for lesson in lessons:
            lesson_context += (
                f"- Input similar to: {lesson['input'][:100]}...\n"
                f"  Correction needed: {lesson['correction']}\n"
            )
    
    # First generation attempt
    result = await model.generate(skill + lesson_context + "\n\nTask:\n" + task)
    
    for iteration in range(max_iterations):
        # Verify against oracle
        verification = await model.generate(
            f"Evaluate this output against criteria. Be strict.\n\n"
            f"Criteria:\n{oracle_criteria}\n\n"
            f"Output to evaluate:\n{result}\n\n"
            f"For each criterion, state PASS or FAIL with one-line explanation."
        )
        
        # Parse pass/fail
        all_pass = "FAIL" not in verification
        
        if all_pass:
            memory.record_execution(task[:200], result, passed_oracle=True)
            return result, True
        
        # Revise based on oracle feedback
        result = await model.generate(
            f"{skill}{lesson_context}\n\nTask:\n{task}\n\n"
            f"Previous attempt:\n{result}\n\n"
            f"Oracle feedback (fix all FAIL items):\n{verification}\n\n"
            f"Produce a corrected version."
        )
    
    # Budget exhausted — return best effort
    memory.record_execution(task[:200], result, passed_oracle=False)
    return result, False

Common failure: Memory without curation

The day 8-21 failure is storing everything and retrieving nothing useful. Memory becomes a junk drawer of irrelevant past executions that consume context tokens without improving output quality. Every past correction gets injected regardless of whether it's relevant to the current task.

Fix: Memory must be selective. Only store corrections that represent repeatable patterns — the same type of error appearing across multiple executions. Discard one-off corrections that were caused by unusual inputs. And never inject more than 3-5 lessons into context — beyond that, you're spending tokens on diminishing returns.

Ready to advance when

  • The loop's success rate has measurably improved since adding memory (track the number: was 80%, now 90%)
  • Iteration catches and fixes at least 30% of first-pass failures (the oracle rejection → fix → pass cycle works)
  • Memory retrieval is selective and relevant (not stuffing all history into context)
  • You have at least 10 stored corrections that represent genuine repeatable patterns
  • The cost of iteration (2-3x the single-pass cost) is justified by the quality improvement

Budget: $20-50/month at this stage.

37.4 Days 22-45: Add Automation (Triggers)

Goal: The loop runs without you starting it. It activates on events — a new PR, a new issue, a schedule, a webhook — and delivers results to the right place.

What to add

Three components:

  1. Event triggers: What causes the loop to run (webhook, cron, file change, message)
  2. Filtering: Not every event should trigger execution (only certain PRs, only certain issue labels)
  3. Delivery: Loop output reaches humans or systems that need it (comment on PR, send Slack message, write file)

from dataclasses import dataclass
from enum import Enum


class TriggerType(Enum):
    WEBHOOK = "webhook"        # GitHub/GitLab/ADO push events
    CRON = "cron"              # Time-based schedule
    FILE_CHANGE = "file_watch" # Filesystem events
    MESSAGE = "message"        # Slack/Teams/email


@dataclass
class TriggerConfig:
    type: TriggerType
    filter_expression: str  # Which events actually trigger execution
    rate_limit_per_hour: int
    cooldown_seconds: int   # Minimum gap between executions
    delivery: dict          # Where to send output


# Example configurations
CHANGELOG_ON_RELEASE = TriggerConfig(
    type=TriggerType.WEBHOOK,
    filter_expression="event.action == 'published' and event.release is not None",
    rate_limit_per_hour=5,
    cooldown_seconds=60,
    delivery={"type": "github_release_body", "repo": "org/app"},
)

PR_LINT_ON_OPEN = TriggerConfig(
    type=TriggerType.WEBHOOK,
    filter_expression=(
        "event.action in ('opened', 'synchronize') and "
        "event.pull_request.draft == False and "
        "'skip-lint' not in [l.name for l in event.pull_request.labels]"
    ),
    rate_limit_per_hour=20,
    cooldown_seconds=30,
    delivery={"type": "github_pr_comment", "deduplicate": True},
)

ISSUE_TRIAGE_PERIODIC = TriggerConfig(
    type=TriggerType.CRON,
    filter_expression="*/15 * * * *",  # Every 15 minutes
    rate_limit_per_hour=4,
    cooldown_seconds=900,
    delivery={"type": "github_labels", "also_comment": True},
)

The delivery problem

The most common Day 22-45 mistake: the loop runs correctly but nobody sees the output. An automated loop without delivery is a tree falling in an empty forest. Every trigger configuration must specify delivery:


async def deliver_result(
    result: str,
    config: dict,
    trigger_context: dict,
) -> None:
    """Route loop output to the appropriate destination."""
    match config["type"]:
        case "github_pr_comment":
            # Check for existing comment to update (avoid spam)
            if config.get("deduplicate"):
                existing = await github.find_bot_comment(
                    repo=trigger_context["repo"],
                    pr=trigger_context["pr_number"],
                    marker="<!-- loop-output -->",
                )
                if existing:
                    await github.update_comment(existing.id, result)
                    return
            await github.create_pr_comment(
                repo=trigger_context["repo"],
                pr=trigger_context["pr_number"],
                body=f"<!-- loop-output -->\n{result}",
            )
        case "slack":
            await slack.post(channel=config["channel"], text=result)
        case "file":
            Path(config["path"]).write_text(result)
        case "github_labels":
            await github.add_labels(
                repo=trigger_context["repo"],
                issue=trigger_context["issue_number"],
                labels=parse_labels(result),
            )

Common failure: Alert fatigue

The day 22-45 failure is triggering too often or on irrelevant events. The loop fires on every PR including dependency bumps, documentation fixes, and automated Renovate updates. Recipients learn to ignore its output within a week. The loop becomes noise.

Fix: Aggressive filtering. The filter expression should exclude at least 30% of events. If the loop triggers on every single event and produces useful output every time, your filter isn't discriminating enough — you'll eventually hit a case where it triggers on something irrelevant and nobody notices because they've stopped reading.

Also: implement deduplication. If the loop has already commented on a PR and the PR is updated, update the existing comment rather than posting a new one. A PR with 15 bot comments is worse than one with zero.

Ready to advance when

  • The loop runs autonomously for a full week with zero manual intervention
  • False trigger rate is below 10% (90%+ of executions produce output that someone reads and finds useful)
  • Delivery is working reliably (output reaches its destination)
  • You've handled at least one edge case where the trigger fired inappropriately
  • Rate limiting is working (a burst of events doesn't cause a burst of API charges)

Budget: $50-150/month. Automation increases execution frequency dramatically.

37.5 Days 45-60: First Maker-Checker Split

Goal: Separate generation from verification into distinct model calls with different roles. The maker produces; the checker validates. Neither trusts the other.

What to add

This is the architectural upgrade from "one model doing everything" to "adversarial verification." As discussed in Chapter 20, a model judging its own output suffers from confirmation bias — it tends to approve what it generated. Splitting into separate calls with different prompts creates genuine tension:


async def maker_checker(
    task: str,
    maker_skill: str,
    checker_rubric: str,
    max_rounds: int = 3,
) -> tuple[str, float, int]:
    """Generate with maker, verify with checker. Returns (output, score, rounds)."""
    
    feedback_history = []
    
    for round_num in range(1, max_rounds + 1):
        # MAKER: generate output (creative, allowed to be bold)
        maker_context = maker_skill + f"\n\nTask: {task}"
        if feedback_history:
            maker_context += "\n\nPrevious checker feedback (address all issues):\n"
            maker_context += "\n".join(f"- Round {i+1}: {fb}" for i, fb in enumerate(feedback_history))
        
        output = await model.generate(maker_context, temperature=0.7)
        
        # CHECKER: independent evaluation (skeptical, no access to maker's reasoning)
        checker_prompt = f"""You are an independent quality checker. You did NOT produce this output.
        Evaluate it critically against the rubric below. Be strict — it's better to reject
        marginally acceptable work than to let problems through.
        
        RUBRIC:
        {checker_rubric}
        
        OUTPUT TO CHECK:
        {output}
        
        For each rubric item, score 0-10 and explain. Then give an overall score 0.0-1.0.
        If overall score < 0.85, list specific issues the maker must fix.
        """
        
        check_result = await model.generate(checker_prompt, temperature=0.0)
        score = extract_score(check_result)
        
        if score >= 0.85:
            return output, score, round_num
        
        # Record feedback for next maker attempt
        issues = extract_issues(check_result)
        feedback_history.append(issues)
    
    # Return best effort after max rounds
    return output, score, max_rounds

Why the split works

A single model asked to "generate and verify your own output" exhibits a measurable confirmation bias: it approves its own output at 15-25% higher rates than an independent checker would. The split eliminates this by creating genuine adversarial pressure. The checker has no investment in the maker's output — its only job is to find problems.

Architecture Self-Approval Bias Cost Typical Quality Gain
Single model (generate + self-verify) 15-25% over-approval 1x Baseline
Maker-checker (same model, different prompts) 5-10% over-approval 2x +15-25% quality
Maker-checker (different models) ~0% bias 2-3x +20-35% quality
Maker-checker (model + deterministic) 0% bias on checked criteria 1.1x Best ROI for checkable criteria

Common failure: Checker is too lenient (or too strict)

Two failure modes at this stage:

Too lenient: The checker passes everything because its rubric criteria are vague. "Is this good?" is not a discriminating criterion. Fix: write rubric items as specific, binary checks. "Does every code example include error handling?" is checkable. "Is the code quality high?" is not.

Too strict: The checker rejects everything, forcing 3 rounds every time and still returning sub-threshold output. This usually means the maker's skill prompt is misaligned with the checker's rubric — they're optimizing for different things. Fix: ensure the maker's skill explicitly addresses every criterion the checker evaluates.

Ready to advance when

  • The checker catches real errors that would have shipped without it (quantify: how many per week?)
  • Checker rejection rate is between 15-35% on first pass (below 15% = rubber-stamping, above 35% = maker needs help)
  • The maker's first-pass quality has improved because it anticipates checker feedback (measure this over time)
  • You can articulate specifically what the checker catches that deterministic checks don't

Budget: $100-300/month. The checker approximately doubles model cost per execution.

37.6 Days 60-75: First Specialist (Two-Agent Fleet)

Goal: Split one generalist loop into two specialists with non-overlapping domains. Add routing that sends tasks to the right specialist.

What to add


@dataclass
class Specialist:
    name: str
    skill: str            # What this specialist knows and does
    tools: list[str]      # Tools available to this specialist
    handles: list[str]    # Task categories it's responsible for
    oracle: str           # Verification criteria specific to this specialist's domain


CODE_REVIEWER = Specialist(
    name="code_reviewer",
    skill="You are an expert code reviewer. You find bugs, security issues...",
    tools=["read_file", "search_code", "run_tests", "check_types"],
    handles=["code_review", "bug_detection", "security_scan", "test_coverage"],
    oracle="Review identifies at least one actionable finding OR explicitly states code is clean...",
)

DOC_WRITER = Specialist(
    name="doc_writer",
    skill="You write technical documentation from source code...",
    tools=["read_file", "write_file", "search_code"],
    handles=["api_docs", "readme_update", "architecture_docs", "changelog"],
    oracle="Documentation accurately reflects current code, all code examples are syntactically valid...",
)


async def route_task(task: str, specialists: list[Specialist]) -> Specialist:
    """Determine which specialist handles this task."""
    routing = await model.generate(
        f"Task: {task}\n\n"
        f"Specialists:\n" +
        "\n".join(f"- {s.name}: handles {s.handles}" for s in specialists) +
        f"\n\nWhich specialist should handle this? Return only the name.",
        temperature=0.0,
    )
    name = routing.strip().lower()
    return next(s for s in specialists if s.name == name)

The coordination requirement

Two specialists need shared state. When the code reviewer finds a bug and the documentation writer needs to update docs to reflect the fix, they need a communication channel. This doesn't need to be complex — a shared context dictionary is sufficient for a two-agent fleet:


@dataclass
class SharedState:
    """Shared context between specialists within a single task execution."""
    project_path: str
    current_branch: str
    files_modified: list[str] = None
    decisions: list[str] = None
    findings: list[str] = None
    
    def __post_init__(self):
        self.files_modified = self.files_modified or []
        self.decisions = self.decisions or []
        self.findings = self.findings or []
    
    def record(self, specialist: str, action: str, detail: str) -> None:
        self.decisions.append(f"[{specialist}] {action}: {detail}")


async def fleet_execute(task: str, state: SharedState) -> str:
    """Route task to specialist and execute with shared state."""
    specialist = await route_task(task, [CODE_REVIEWER, DOC_WRITER])
    
    result = await run_specialist_loop(
        specialist=specialist,
        task=task,
        context=state,
    )
    
    # Update shared state with this execution's results
    state.record(specialist.name, "completed", result.summary)
    state.files_modified.extend(result.files_changed)
    
    return result.output

Common failure: Overlapping specialists

If both specialists can handle the same task type, routing becomes a coin flip and outputs are inconsistent depending on which specialist is chosen. The same task produces different quality depending on routing.

Fix: Specialists must have strictly non-overlapping domains. If you find yourself giving both specialists the same tool or the same task category, you haven't split the responsibilities cleanly. The test: can you draw a Venn diagram of their domains with zero overlap? If not, refactor the split.

Ready to advance when

  • Routing accuracy is 90%+ (measure by human-reviewing routing decisions)
  • Each specialist performs measurably better on its domain than a single generalist loop did
  • The shared state mechanism works: specialist B can see and use specialist A's findings
  • You've handled the handoff case: a task that starts with one specialist and needs the other to finish

Budget: $200-500/month.

37.7 Days 75-90: Full Fleet with Orchestrator

Goal: An orchestrator that decomposes complex tasks, assigns sub-tasks to specialists, manages dependencies, handles failures, and assembles the final output.

What to add

The orchestrator is not a specialist — it's the coordinator. It doesn't do the work; it plans the work, assigns it, and integrates the results. Its skill is decomposition and assembly, not domain expertise:


class Orchestrator:
    def __init__(self, specialists: list[Specialist], budget: float):
        self.specialists = specialists
        self.budget = budget
        self.spent = 0.0
    
    async def execute_task(self, task: str) -> str:
        """Full orchestration: decompose, assign, execute, assemble."""
        # Phase 1: Decompose into sub-tasks
        sub_tasks = await self.decompose(task)
        
        # Phase 2: Execute with dependency ordering
        results = {}
        while pending := [t for t in sub_tasks if t.id not in results]:
            # Find tasks whose dependencies are all satisfied
            ready = [
                t for t in pending
                if all(dep_id in results for dep_id in t.depends_on)
            ]
            
            if not ready:
                # All pending tasks are blocked — deadlock
                raise OrchestrationError(
                    f"Deadlock: {len(pending)} tasks blocked, none ready"
                )
            
            # Execute ready tasks (could parallelize if independent)
            for sub_task in ready:
                if self.spent >= self.budget:
                    raise BudgetExhausted(f"Spent ${self.spent:.2f} of ${self.budget:.2f}")
                
                # Provide results of dependencies as context
                dep_context = {
                    dep_id: results[dep_id].summary 
                    for dep_id in sub_task.depends_on
                }
                
                result = await self.execute_subtask(sub_task, dep_context)
                results[sub_task.id] = result
                self.spent += result.cost
        
        # Phase 3: Assemble final output from sub-task results
        return await self.assemble(task, results)
    
    async def decompose(self, task: str) -> list[SubTask]:
        """Break complex task into specialist-assignable sub-tasks."""
        plan = await model.generate(f"""
        Decompose this task for these specialists:
        {[(s.name, s.handles) for s in self.specialists]}
        
        Task: {task}
        
        For each sub-task specify: id, description, assigned_specialist, depends_on (list of ids).
        Order so dependencies come before dependents.
        Minimize sub-tasks — combine where possible. Max 6 sub-tasks.
        """)
        return parse_subtask_plan(plan)
    
    async def assemble(self, original_task: str, results: dict) -> str:
        """Combine sub-task results into a coherent final output."""
        return await model.generate(f"""
        Original task: {original_task}
        
        Sub-task results:
        {json.dumps({k: v.output for k, v in results.items()}, indent=2)}
        
        Assemble these into a single coherent output that fully addresses 
        the original task. Resolve any contradictions between sub-tasks.
        Remove redundancy. Ensure consistent terminology.
        """)

Budget management at fleet scale

At fleet scale, cost control becomes critical. Without it, a complex task can burn through $50 of API calls before you realize it:


@dataclass
class FleetBudget:
    total: float                    # Total $ allowed for this task
    per_subtask_default: float      # Default cap per sub-task
    orchestrator_reserve: float     # Reserved for planning + assembly
    retry_reserve: float            # Reserved for failed sub-task retries
    
    @classmethod
    def from_total(cls, total: float, num_subtasks: int = 4) -> "FleetBudget":
        orchestrator = total * 0.15  # 15% for orchestrator overhead
        retry = total * 0.20         # 20% for retries
        available = total - orchestrator - retry
        per_task = available / num_subtasks
        return cls(
            total=total,
            per_subtask_default=per_task,
            orchestrator_reserve=orchestrator,
            retry_reserve=retry,
        )

Common failure: Orchestrator overhead exceeds value

If the orchestrator spends more tokens planning and coordinating than the specialists spend executing, the fleet is less efficient than a single loop handling the whole task. This happens when tasks aren't complex enough to warrant decomposition.

Rule of thumb: Don't orchestrate tasks that complete in fewer than 3 specialist calls. A task that one specialist can handle in one iteration doesn't benefit from decomposition — the orchestrator's planning step adds cost without adding capability. Reserve fleet orchestration for tasks that genuinely require multiple domains, multiple steps with dependencies, or parallel execution.

Ready to declare victory when

  • The fleet handles end-to-end tasks that no single specialist could handle alone
  • Orchestrator overhead is less than 25% of total fleet cost
  • You have monitoring showing: task completion rate, average cost, failure rate by specialist, routing accuracy
  • A human can review the audit trail and understand what the fleet did and why
  • The fleet has handled at least one failure gracefully (specialist failed, orchestrator re-routed or retried)

Budget: $500-2000/month depending on execution frequency and task complexity.

37.8 The Advancement Criteria Summary

Stage Advance When Do NOT Advance If
1→2 80%+ success, understand failure modes Oracle doesn't discriminate (passes everything)
2→3 Memory measurably improves outcomes Still debugging core loop logic
3→4 Runs unattended for a week, <10% false triggers Output delivery isn't reliable
4→5 Checker catches real errors (15-35% first-pass rejection) Checker rubber-stamps or rejects everything
5→6 Specialists outperform generalist in their domains Routing accuracy below 90%
Fleet Handles multi-domain tasks end-to-end Orchestrator overhead exceeds 25%

The most common meta-failure: Advancing before the current stage is solid. A fleet built on a loop that doesn't verify correctly is a fleet that ships defective work at scale. Each stage must be genuinely working on real inputs — not "working in the demo" but "working on 50 diverse inputs without human intervention."

37.9 The 90-Day Cost Curve


Week 1:   $0.50/day   (manual testing, 2-3 runs)
Week 3:   $2/day      (iteration adds model calls, 5-10 runs)
Week 5:   $5/day      (automated triggers, 15-30 runs)
Week 8:   $10/day     (maker-checker doubles cost per run)
Week 10:  $15/day     (two specialists, routing overhead)
Week 12:  $30-60/day  (full fleet with orchestrator)

At $60/day ($1,800/month), a well-designed fleet should replace 20-40 hours of human work per week. The economics work when the automated work would cost $4,000-8,000/month in human time (at $50-100/hour for senior engineers). If your loop automates work that takes 5 minutes per week, it's not worth a fleet.

Start with the task that consumes the most human time with the most predictable, verifiable steps. Build the fleet around that anchor task. Expand only when the foundation is proven solid.
