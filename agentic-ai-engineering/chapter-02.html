Chapter 2: Levels of Agency — The Autonomy Ladder

Level: B (Brief) · ~2,800 words · Navigation device for the entire book

2.1 Six Levels of Autonomy

Not all agents are created equal, and not all loops require the same level of autonomy. The Autonomy Ladder provides a shared vocabulary for describing how much control a system exercises over its own actions — and therefore how much verification infrastructure it requires.

Each level represents a qualitative jump in what the system decides on its own, what can go wrong without human intervention, and what verification machinery you need to trust it.


L5 │ Self-Designing Fleet    │ Designs own loops, spawns specialists, curates memory
L4 │ Autonomous Fleet        │ Orchestrator + specialists, cross-agent coordination
L3 │ Autonomous Single Agent │ Plans, executes, verifies, iterates — no human gate
L2 │ Guided Agent            │ Executes a human-designed plan, asks when stuck
L1 │ Tool-Augmented Model    │ Responds to prompts, calls tools when asked
L0 │ Autocomplete            │ Predicts next token, no tool use, no agency

L0: Autocomplete

The model predicts the next token based on context. No tools, no actions, no state, no iteration. This is GPT-3 in 2020 or any model running in a pure chat interface without function calling.

What can go wrong: Hallucination. Inaccurate information. Nothing external changes.

Verification needed: Human reads the output. That's it.

Book chapters that serve L0: None. This book starts at L1.

L1: Tool-Augmented Model

The model can call external tools — search the web, read files, query databases, execute code — but only when explicitly directed by a human prompt. Each interaction is a single turn: human asks, model responds (possibly using tools), human evaluates.

This is the standard AI assistant experience in 2024-2025: ChatGPT with plugins, Claude with tool use, Copilot with @workspace queries.

What can go wrong: Tool misuse, incorrect tool arguments, acting on hallucinated information from tool results.

Verification needed: Human reviews each response before acting on it.

Book chapters that serve L1: Chapters 9 (Tool Design), 10 (MCP).

L2: Guided Agent

The model executes a multi-step plan that a human designed. It follows the plan sequentially, uses tools as specified, and escalates when it encounters ambiguity or failure. The human defines the path; the model walks it.

Examples: a CI/CD pipeline where the model performs code review at a specified step, a data processing workflow where the model transforms data according to a schema, a testing workflow where the model runs a defined test plan.

What can go wrong: Misinterpretation of plan steps, failure to escalate when stuck, silent deviation from the plan.

Verification needed: Checkpoints at each step. Human spot-checks rather than reviews every output.

Book chapters that serve L2: Chapters 14 (Triggers), 16 (Planning), 17 (Execution and State).

L3: Autonomous Single Agent

The model plans its own approach, executes, verifies its own output against criteria, and iterates until done — all without human intervention. This is a single-agent loop: discover → plan → execute → verify → iterate.

Examples: Claude Code fixing a bug (reads the error, investigates, writes a fix, runs tests, iterates until tests pass), a research agent that searches, synthesizes, verifies claims, and stops when confidence is sufficient.

What can go wrong: Infinite loops, budget exhaustion, goal misinterpretation, reward hacking (gaming its own verification), silent scope drift.

Verification needed: Budget ceilings, stop conditions, oracle quality, post-hoc audit of results.

Book chapters that serve L3: Part III (Building the Loop), Part IV (Verification), Part VI (Economics).

L4: Autonomous Fleet

An orchestrator agent decomposes a goal into sub-tasks and delegates them to specialist agents. Each specialist is itself an L3 loop. The orchestrator coordinates, aggregates results, handles cross-agent dependencies, and makes strategic decisions about resource allocation.

Examples: Claude Code's workflow system (orchestrator fans out review agents, synthesis agents, verification agents), a security audit fleet (scanner agents, exploit-verification agents, report-synthesis agents), a content production pipeline (research agents, writing agents, editing agents, fact-checking agents).

What can go wrong: Everything from L3, plus: coordination failures, context contamination between agents, cascading errors, resource starvation (one specialist consumes the entire budget), deadlock.

Verification needed: All L3 requirements, plus: inter-agent consistency checks, resource allocation monitoring, topology-level health metrics.

Book chapters that serve L4: Part V (Fleets), Chapter 25 (Coordination), Chapter 29 (Observability).

L5: Self-Designing Fleet

The system designs its own loops, decides what specialists to spawn, writes its own skills, curates its own memory, tunes its own rubrics, and evolves its own verification criteria. The human defines the meta-goal and constraints; the system designs the architecture to achieve it.

Examples: An agent that, given "improve test coverage for this repository," designs its own workflow (analyze coverage → identify gaps → prioritize by risk → spawn per-module agents → verify each agent's tests → merge), writes the specialist prompts, runs the fleet, evaluates outcomes, and refines its approach for next time.

What can go wrong: Everything from L4, plus: specification gaming (optimizing for the metric rather than the intent), loss of human interpretability, emergent objectives misaligned with human intent, inability to audit the system's reasoning about its own design.

Verification needed: All L4 requirements, plus: meta-level audits (is the system's design of its own loops sound?), human-interpretable explanations of design decisions, periodic human review of evolved verification criteria.

Book chapters that serve L5: Chapter 38 (Self-Designing Loops).

2.2 The Ladder as Navigation Device

Every chapter in this book states which levels it serves. This isn't decoration — it's a practical guide for where to focus your reading:

  • Building your first loop (L2→L3)? Focus on Parts II and III.
  • Already have loops, need them cheaper and more reliable (L3)? Focus on Parts IV and VI.
  • Scaling to multi-agent (L3→L4)? Focus on Part V.
  • Everything's working but security keeps you up at night (L4)? Focus on Part VII.
  • Pushing toward self-improvement (L4→L5)? Focus on Chapter 38, but be honest about whether your L3/L4 fundamentals are solid first.

The ladder also provides a planning framework. Before building a system, ask: what level does this task actually require? The most common mistake in agentic AI is over-engineering — building an L4 fleet for an L2 problem. A guided agent with clear checkpoints is cheaper, more reliable, and easier to debug than an autonomous fleet for most tasks.

2.3 What Agentic AI Isn't — Honest Debunking

The term "agentic" has been diluted by marketing until it means almost anything an AI system does autonomously. Let's be precise about what doesn't count:

Not agentic: A chatbot that uses tools. If a human initiates every action and reviews every response before anything happens in the world, there's no loop. There's a tool-augmented conversation. Useful, but not agentic.

Not agentic: A pipeline with an LLM step. If you have a deterministic pipeline — fetch data → format → call LLM → parse output → store — that's an LLM-in-the-loop pipeline, not an agent. The LLM doesn't decide what to do next. It fills a slot in a human-designed sequence. (This is fine. Most production LLM uses are exactly this, and they work well.)

Not agentic: A single retry. If your system calls an LLM and retries on malformed output, that's error handling, not agency. Agency implies the system adapts its approach based on feedback, not just re-rolls the dice.

Not agentic: Agentic framing on non-agentic systems. Many "AI agent" products are thin wrappers around API calls with hardcoded fallback logic. They appear autonomous because the user doesn't see the pipeline. They aren't — the behavior is entirely predetermined by the developer.

Actually agentic: A system that observes a result, evaluates it against criteria, and makes a non-trivial decision about what to do next — where "non-trivial" means the next action wasn't predetermined by the developer. The system exercises judgment, even if that judgment is constrained by guardrails.

2.4 The Cost Multiplier

Each level up the autonomy ladder multiplies cost in three dimensions:

Level Typical Token Cost Verification Overhead Failure Blast Radius
L0 1x (one prompt) 0 (human reads) None (no action)
L1 2-5x (tools) Low (human checks) Low (one action)
L2 10-50x (multi-step) Medium (checkpoints) Medium (plan scope)
L3 50-200x (iterate) High (oracle per step) High (autonomous scope)
L4 500K-2M tokens/run Very high (multi-agent) Very high (fleet scope)
L5 Unbounded Requires meta-verification Unbounded

This table is why Chapter 5 (When Not to Build a Loop) exists. Not every problem benefits from climbing the ladder. The right level is the lowest level that meets the task's actual requirements — never higher.

2.5 Climbing the Ladder Safely

The safe way to increase autonomy is incremental and evidence-based:

  1. Start at L2: Build a guided workflow with human-designed steps and checkpoints. Measure reliability.
  2. Graduate to L3: Once reliability at L2 exceeds 95%, remove the human gate and add automated verification. Measure cost and reliability.
  3. Graduate to L4: Once a single L3 loop handles its task reliably, add specialists only where the single agent demonstrably struggles (context overflow, conflicting tool sets, tasks that benefit from independence).
  4. Never jump to L5 without extensive L4 experience. Self-designing systems are research, not production, for most teams in 2026.

The criteria for each graduation:

  • L2→L3: Your oracle catches >95% of errors the human would have caught, and the cost of oracle operation is <20% of the cost of human review.
  • L3→L4: A single agent's context window is demonstrably insufficient, or task independence would provide >3x speedup with maintained quality.
  • L4→L5: You have >6 months of L4 fleet operation data, your verification infrastructure is mature, and the meta-goal is stable enough that self-modification won't drift.
