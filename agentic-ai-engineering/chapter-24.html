Chapter 24: From Loop to Fleet

Level: A (Anchor) · ~5,800 words · Levels served: L4, L5

24.1 When One Loop Isn't Enough

A single-agent loop hits three ceilings:

Context ceiling. The task requires more information than fits in one context window. A full-codebase security audit needs to read hundreds of files. A single agent can't hold them all. It forgets file A by the time it finishes reading file Z.

Capability ceiling. The task requires diverse expertise that conflicts within a single prompt. A code-writing agent needs to be creative and bold. A security-reviewing agent needs to be skeptical and conservative. One agent can't be both effectively.

Time ceiling. The task has multiple independent sub-tasks that could run in parallel. A single agent processes them serially — reviewing five modules sequentially takes 5x longer than five specialists running simultaneously.

When you hit any of these ceilings, it's time for a fleet.

24.2 What a Fleet Is

A fleet is a collection of loops coordinated by a lead agent:


                    ┌──────────────┐
                    │     Lead     │
                    │ (Orchestrator)│
                    └──────┬───────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
     ┌────────▼───┐  ┌────▼────┐  ┌───▼────────┐
     │ Specialist │  │Specialist│  │ Specialist  │
     │   Agent A  │  │ Agent B  │  │  Agent C   │
     └────────────┘  └─────────┘  └────────────┘

Each specialist is itself a loop — it discovers, plans, executes, verifies, and iterates within its own scope. The lead coordinates: decomposing the goal, assigning work, aggregating results, and making strategic decisions.

24.3 The Real Reason for Subagents: Context Isolation

The most common justification for fleets is parallelism — running things faster. But parallelism is the secondary benefit. The primary benefit is context isolation.

When a single agent holds too much information, its reasoning degrades. The "lost in the middle" problem (Chapter 7) means that information buried in a 150K-token context gets less attention than it deserves. By splitting work across specialists, each specialist reasons over a small, focused context — and reasons about it well.


Single agent (150K context, degraded attention):
  [Project overview + File A + File B + File C + ... + File Z + Current task]
  
  Quality: Medium (attention spread thin)

Fleet (3 specialists, 30K context each):
  Agent A: [Project overview + Files A-H + Review task]    Quality: High
  Agent B: [Project overview + Files I-P + Review task]    Quality: High
  Agent C: [Project overview + Files Q-Z + Review task]    Quality: High

Each specialist has a small enough context to reason well. The lead synthesizes their findings — a much simpler task than doing all the detailed analysis itself.

24.4 Fleet Composition

The Lead Agent

The lead (orchestrator) has three responsibilities:

  1. Decompose: Break the goal into sub-tasks that can be assigned to specialists
  2. Coordinate: Manage dependencies, handle conflicts, aggregate results
  3. Decide: Make strategic choices the specialists can't make (because they lack cross-cutting context)

The lead uses a more capable model (typically Opus) because its job requires broad reasoning about the entire task — not detailed execution on any single sub-task.


lead = Agent(
    model="claude-opus-4-6",
    tools=["plan", "delegate", "aggregate", "search_code"],
    system="""You are the lead of a specialist fleet. Your job:
    1. Decompose the goal into independent sub-tasks
    2. Assign each sub-task to a specialist with clear scope
    3. Aggregate results into a coherent whole
    4. Resolve conflicts between specialists
    Do NOT do detailed implementation work yourself. Delegate."""
)

Specialist Agents

Specialists have narrow scope, specific tools, and focused prompts:


code_specialist = Agent(
    model="claude-sonnet-4-6",
    tools=["read_file", "write_file", "run_tests", "search_code"],
    system="You implement code changes. Your scope is limited to the files assigned to you."
)

review_specialist = Agent(
    model="claude-opus-4-6",
    tools=["read_file", "search_code"],
    system="You review code for bugs and security issues. You cannot modify files."
)

test_specialist = Agent(
    model="claude-sonnet-4-6",
    tools=["read_file", "write_file", "run_tests"],
    system="You write and fix tests. You only modify files in the tests/ directory."
)

Specialist Design Principles:

  1. Minimal scope: Each specialist handles one type of work. Narrow scope = better performance.
  2. Own tools: Each specialist has only the tools relevant to its work. Code writers can write; reviewers can only read.
  3. Own model: Use the cheapest model that handles the specialist's task well. Code review might need Opus. Code formatting needs only Haiku.
  4. Independent verification: Each specialist verifies its own work before reporting to the lead.

24.5 When a Fleet Is Strictly Worse

Fleets aren't always better. They carry overhead that single agents don't:

Communication overhead: Every message between the lead and specialists costs tokens. A fleet with 5 specialists and 3 rounds of communication uses ~15 extra inference calls just for coordination.

Context duplication: Every specialist needs basic project context. If you have 5 specialists, you load the project overview 5 times — paying the token cost 5x.

Coordination complexity: Dependencies between specialists require the lead to sequence work correctly. A single agent handles dependencies implicitly (it remembers what it just did).

Merge conflicts: When multiple specialists modify related code, their changes may conflict. Resolution adds complexity and cost.

Don't use a fleet when:

  • The task fits in one context window
  • The task has many sequential dependencies (specialist B can't start until A finishes)
  • The task is simple enough that splitting introduces more overhead than it saves
  • Context switching cost between specialists exceeds the benefit of specialization

The break-even point:

A fleet becomes worthwhile when: fleet_quality × parallelism_speedup > single_agent_quality + coordination_overhead

Rule of thumb: if a single agent can handle the task in under 5 iterations with good quality, don't fleet it. If it needs 10+ iterations or the context fills up, fleet it.

24.6 The Delegation Prompt

The most important artifact in fleet orchestration is the delegation prompt — what the lead tells each specialist. A good delegation prompt contains:


## Task
[Specific sub-task this specialist should accomplish]

## Scope
[Which files/functions/areas this specialist is responsible for]

## Context
[Relevant project information — minimal, focused]

## Constraints
[What the specialist must NOT do]

## Success Criteria
[How the specialist knows it's done]

## Report Format
[How results should be structured for aggregation]

Anti-patterns in delegation:

Too vague: "Review the code and find issues." The specialist doesn't know which code, what to look for, or what counts as an issue.

Too detailed: Step-by-step instructions that micromanage the specialist. You hired a specialist — let it use judgment.

No scope boundary: "Look at the whole codebase." Without boundaries, the specialist duplicates work with other specialists.

No output format: The lead receives unstructured text from each specialist and must manually parse it. Specify the format upfront.

24.7 Result Aggregation

The lead receives results from all specialists and must combine them into a coherent whole. This is harder than it sounds:

Challenges:

  • Contradictions: Specialist A says "this code is fine." Specialist B says "this code has a bug." Who's right?
  • Duplicates: Two specialists flag the same issue with different descriptions
  • Prioritization: 30 findings from 5 specialists. Which matter most?
  • Synthesis: Findings from different specialists may interact in ways no individual specialist sees

Aggregation patterns:


async def aggregate_results(lead: Agent, specialist_results: list[Result]) -> FinalResult:
    # Remove duplicates
    deduped = deduplicate_findings(specialist_results)
    
    # Resolve contradictions
    for contradiction in find_contradictions(deduped):
        resolution = await lead.resolve(contradiction)
        deduped = apply_resolution(deduped, resolution)
    
    # Prioritize
    prioritized = await lead.prioritize(deduped)
    
    # Synthesize cross-cutting insights
    synthesis = await lead.synthesize(prioritized)
    
    return FinalResult(findings=prioritized, synthesis=synthesis)

24.8 The N-Agent Sweet Spot

How many specialists is the right number? The answer depends on the task, but there's a sweet spot:

Agents Overhead Benefit Net Value
1 None Baseline quality Baseline
2-3 Low Specialization + independence Often optimal
4-6 Medium Full coverage of complex tasks Good for large scope
7-10 High Diminishing returns on specialization Rarely justified
10+ Very high Coordination dominates Almost never worth it

The overhead is super-linear: doubling agents more than doubles coordination cost (each agent potentially interacts with every other). Start with the minimum number of specialists needed to cover the task's dimensions, and add more only when you have evidence that coverage is insufficient.

24.9 Fleet Lifecycle


PLAN ──→ DELEGATE ──→ EXECUTE ──→ COLLECT ──→ AGGREGATE ──→ VERIFY ──→ DELIVER
  │                      │                         │              │
  │                      │ (parallel)              │              │
  └── Lead decomposes    └── Specialists work      └── Lead       └── Final 
      into sub-tasks         independently             synthesizes     oracle

The lead's timeline:

  1. Plan: Understand the goal, decompose into sub-tasks, decide specialist assignments
  2. Delegate: Send clear instructions to each specialist
  3. Wait (or work): While specialists run, the lead can do its own analysis or prepare for aggregation
  4. Collect: Receive results from all specialists
  5. Aggregate: Combine, deduplicate, resolve contradictions
  6. Verify: Run the final oracle on the aggregated result
  7. Deliver: Present the verified output

24.10 Fleet vs. Pipeline

Two patterns for multi-agent work:

Fleet (parallel): All specialists work simultaneously on different aspects of the same goal. Results are aggregated by the lead.

Pipeline (sequential): Each agent processes the output of the previous agent. Research agent → Writing agent → Editing agent → Formatting agent.

Pattern When to use Advantage
Fleet Independent sub-tasks, coverage is the goal Faster (parallel)
Pipeline Dependent stages, quality-through-iteration Each stage refines

Many real systems combine both: a fleet of researchers runs in parallel, their results feed into a sequential pipeline of synthesis → writing → review.
