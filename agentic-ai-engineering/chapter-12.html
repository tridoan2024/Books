Chapter 12: Memory and Between-Run Consolidation

Level: A (Anchor) · ~6,000 words · Levels served: L3, L4, L5

12.1 The Goldfish Problem

A model without memory wakes up every session as a stranger. It doesn't know what was tried yesterday, what failed last week, what the user corrected, or what patterns recur. Every run starts from scratch — rediscovering the project, re-making past mistakes, re-learning preferences the user already taught it.

This is the goldfish problem. The model's context window is a working memory that lasts exactly one session. When the session ends, everything learned is gone.

For single-use interactions, this doesn't matter. For loops that run daily — reviewing PRs, maintaining code quality, managing infrastructure — it's catastrophic. A loop that can't learn from its own history is doomed to repeat its mistakes indefinitely.

Memory is the system that solves this: capturing what was learned in each run and making it available to future runs.

12.2 The Four Types of Memory

Memory in agentic systems mirrors the taxonomy from cognitive science:

Working Memory

What's currently in the context window. Fast to access, limited in capacity, gone when the session ends. This is what the model is actively reasoning about.

  • Capacity: The context window (128K-1M tokens, depending on model)
  • Persistence: One session only
  • Cost to access: Zero (already loaded)
  • Use: Current-step reasoning, in-progress work

Episodic Memory

Records of specific past events — what happened, when, and what the outcome was. "Last Tuesday, the auth loop failed because it tried to modify a read-only config file." Episodic memories are timestamped, specific, and tied to particular runs.

  • Capacity: Unbounded (stored externally)
  • Persistence: Days to weeks
  • Cost to access: Retrieval overhead (search + load)
  • Use: Avoiding repeated mistakes, learning from past failures

Semantic Memory

Accumulated knowledge — facts, relationships, and patterns that have been abstracted from multiple episodes. "This project uses UTC internally and converts to local time only at the display layer." Semantic memories are timeless truths (until invalidated), not tied to specific events.

  • Capacity: Unbounded
  • Persistence: Months to permanent
  • Cost to access: Retrieval overhead
  • Use: Project understanding, domain knowledge, stable facts

Procedural Memory

Learned workflows and skills — how to do things. "When tests fail with a database error, check if the migration has been applied before investigating the code." Procedural memories are if-then rules or step sequences that have been validated through experience.

  • Capacity: Unbounded
  • Persistence: Permanent (until workflow changes)
  • Cost to access: Loaded with skills
  • Use: Task execution, automatic recovery from known failure modes

12.3 Memory Storage Mechanisms

Memory must be stored somewhere the model can access across sessions. The options, from simplest to most sophisticated:

File-Based Memory

The simplest and most robust approach. Memory lives in markdown or JSON files in a known location. The model reads and writes these files directly.


.claude/memory/
├── MEMORY.md           # Index of all memories
├── episodes/
│   ├── 2026-07-15.md   # What happened on this date
│   └── 2026-07-16.md
├── facts/
│   ├── project_arch.md # Semantic: architecture facts
│   └── conventions.md  # Semantic: coding conventions
├── procedures/
│   ├── fix_db_errors.md    # Procedural: how to handle DB failures
│   └── deploy_process.md   # Procedural: deployment steps
└── feedback/
    ├── user_prefs.md   # User corrections and preferences
    └── false_positives.md  # Things to stop flagging

Advantages: Simple, transparent, version-controllable, human-readable, no infrastructure needed.

Disadvantages: No semantic search (must read files sequentially), can grow large, no automatic relevance ranking.

Structured Database Memory

Memory stored in a database (SQLite, PostgreSQL) with metadata for search and retrieval.


CREATE TABLE memories (
    id TEXT PRIMARY KEY,
    type TEXT,          -- episodic, semantic, procedural
    content TEXT,
    created_at TIMESTAMP,
    last_accessed TIMESTAMP,
    access_count INTEGER,
    importance INTEGER, -- 1-5
    project_path TEXT,
    embedding BLOB      -- for semantic search
);

Advantages: Semantic search via embeddings, structured queries, automatic relevance ranking, metadata tracking.

Disadvantages: Infrastructure overhead, less transparent, harder for humans to browse.

Hybrid (File + Search)

The most practical approach for production: memories stored as files (human-readable, version-controlled) with a search index built on top (fast retrieval, relevance ranking).


class MemorySystem:
    def __init__(self, memory_dir: Path):
        self.dir = memory_dir
        self.index = SearchIndex(memory_dir)
    
    def save(self, memory: Memory) -> None:
        file_path = self.dir / memory.type / f"{memory.key}.md"
        file_path.write_text(memory.to_markdown())
        self.index.update(memory)
    
    def search(self, query: str, limit: int = 5) -> list[Memory]:
        return self.index.search(query, limit)
    
    def get_relevant(self, current_task: str) -> list[Memory]:
        """Return memories relevant to the current task."""
        return self.search(current_task, limit=10)

12.4 The Memory Lifecycle

Memory isn't just storage. It's a lifecycle: capture → store → consolidate → recall → forget.

Capture

Deciding what to remember. Not everything is worth storing. The capture criteria:

  • Novel: Information the loop didn't know before this run
  • Useful: Information likely to help in future runs
  • Non-derivable: Can't be easily rediscovered from the code or git history
  • Stable: Won't become stale within a few runs

What NOT to capture:

  • Current git state (derivable from git log)
  • File contents (read from the filesystem)
  • Debugging solutions (the fix is in the code)
  • Ephemeral task details (not useful next run)

Store

Writing the memory to persistent storage with appropriate metadata: type, timestamp, importance, project association, relationships to other memories.

Consolidate

The critical step that distinguishes a memory system from a log file. Consolidation is the process of:

  1. Deduplicating: Multiple episodes that teach the same lesson are merged into one semantic memory
  2. Resolving contradictions: When two memories conflict, the more recent and better-evidenced one wins
  3. Surfacing patterns: When the same issue recurs across multiple episodes, create a procedural memory for handling it
  4. Updating importance: Memories that are frequently accessed increase in importance; rarely-accessed memories decrease

Anthropic calls this process "dreaming" — a background consolidation that runs between sessions, curating accumulated memories into useful knowledge.


class MemoryConsolidator:
    def consolidate(self, memories: list[Memory]) -> list[Memory]:
        # Find duplicate episodes
        duplicates = self.find_duplicates(memories)
        for group in duplicates:
            merged = self.merge_into_semantic(group)
            self.replace(group, merged)
        
        # Detect recurring patterns
        patterns = self.detect_patterns(memories)
        for pattern in patterns:
            if pattern.frequency >= 3:
                proc = self.create_procedural(pattern)
                self.store(proc)
        
        # Resolve contradictions
        contradictions = self.find_contradictions(memories)
        for pair in contradictions:
            winner = self.resolve(pair)  # More recent, better evidenced
            self.archive(pair.loser)
        
        # Decay unused memories
        stale = [m for m in memories if m.days_since_access > 90]
        for memory in stale:
            memory.importance -= 1
            if memory.importance <= 0:
                self.archive(memory)

Recall

Loading relevant memories into context at the start of a run. Not all memories are relevant to every task — recall must be selective:


def prepare_context_with_memory(task: str, memory_system: MemorySystem) -> str:
    # Always load: user preferences, critical project facts
    always = memory_system.get_by_type("preference") + \
             memory_system.get_by_importance(min_importance=5)
    
    # Task-relevant: search for memories related to current work
    relevant = memory_system.search(task, limit=10)
    
    # Recent episodes: what happened in the last few runs
    recent = memory_system.get_recent_episodes(days=7, limit=5)
    
    # Compose into context
    return format_memories(always + relevant + recent)

Forget

Not all memories should persist forever. Forgetting is a feature:

  • Stale facts: "The API uses version 2" when it's been upgraded to version 3
  • Superseded procedures: "Deploy with Jenkins" when the team moved to GitHub Actions
  • Resolved episodes: "Bug X exists" when bug X was fixed
  • Low-value memories: Memories that are never recalled, never relevant

Forgetting prevents memory bloat — a growing pile of irrelevant memories that consume context tokens without providing value. Active pruning keeps the memory system lean and relevant.

12.5 Cross-Run Learning Patterns

Pattern 1: Error Memory

Every time a loop fails, record the error and the resolution. Next time the same error pattern appears, apply the known resolution directly.


# Error Memory: Database connection timeout

## Pattern
Error message: "psycopg2.OperationalError: connection timed out"
Context: occurs after deploy, when new instances start

## Resolution
1. Check if the connection pool is exhausted (SELECT count(*) FROM pg_stat_activity)
2. If yes, restart the connection pool (kill idle connections)
3. If no, check if the migration lock is held (pg_locks table)

## History
- 2026-07-10: Occurred after deploy. Root cause: migration lock.
- 2026-07-15: Occurred after deploy. Root cause: pool exhaustion from health checks.

Pattern 2: User Preference Learning

When a user corrects the loop ("don't do X", "always do Y"), record the preference. Apply it in all future runs without the user needing to repeat themselves.


# Preference: Code Review Style

## Rules learned from user corrections
- Never flag single-letter variables in loops (i, j, k are fine)
- Don't suggest type annotations for test helper functions
- Always flag any function over 50 lines, regardless of complexity
- Prefer "not X" over "X is False" in Python conditionals

## Source
- 2026-07-05: User said "stop flagging loop variables"
- 2026-07-08: User said "test helpers don't need types, they change too fast"
- 2026-07-12: User said "I want to know about long functions always"

Pattern 3: Project Evolution Tracking

As the project changes across runs, memory tracks the evolution — what changed, why, and what the implications are.


# Evolution: Auth System

## Timeline
- 2026-06-01: Session-based auth (express-session + Redis)
- 2026-06-15: Added JWT for API clients (dual auth: session + JWT)
- 2026-07-01: Migrating fully to JWT (session deprecated, will be removed)
- 2026-07-20: Sessions removed. Pure JWT now.

## Implications
- Old code referencing req.session is deprecated
- Token refresh is now handled client-side
- Auth middleware checks JWT only (no more cookie parsing)

12.6 Memory and Loop Quality

Memory directly improves loop quality in measurable ways:

Memory Type Quality Improvement Mechanism
Error memory Fewer iterations on known problems Skip diagnosis, go straight to fix
User preferences Fewer corrections needed Match user expectations on first pass
Procedural memory Faster task completion Known-good procedures, no exploration
Semantic memory Better decisions Richer context for reasoning
Episode memory Avoid repeated mistakes Don't try approaches that failed before

The compound effect: a loop with well-maintained memory converges faster (fewer iterations), produces higher-quality output (matches preferences and avoids known pitfalls), and costs less (less wasted exploration) with every passing week.

12.7 Memory Anti-Patterns

The Hoarder

Saving everything. Every tool result, every reasoning step, every intermediate state. Memory bloats until retrieval returns noise instead of signal. Fix: Strict capture criteria. If it's derivable, don't store it.

The Amnesia Loop

Never consolidating. Episodes accumulate without being synthesized into semantic or procedural memory. The system "remembers" individual events but never learns patterns. Fix: Schedule consolidation after every N runs.

The Stale Oracle

Memories that were true once but aren't anymore. "Use pytest-asyncio for async tests" when the project migrated to anyio. The loop follows outdated procedures and fails. Fix: Verify memories against reality before acting on them. Timestamp and review regularly.

The Overfitted Memory

Procedural memories that are too specific. "When test_auth_expiry fails, add 1 to the timeout value" — a memorized fix for a symptom, not the underlying cause. Fix: Capture the root cause, not the specific workaround.

12.8 Implementation: The File-Based Memory Tool

The simplest production-ready memory implementation:


from pathlib import Path
from datetime import datetime
import frontmatter

class FileMemory:
    def __init__(self, base_dir: Path):
        self.base_dir = base_dir
        self.base_dir.mkdir(parents=True, exist_ok=True)
    
    def save(self, key: str, content: str, memory_type: str, 
             importance: int = 3) -> Path:
        file_path = self.base_dir / f"{key}.md"
        doc = frontmatter.Post(
            content=content,
            name=key,
            type=memory_type,
            importance=importance,
            created=datetime.now().isoformat(),
            last_accessed=datetime.now().isoformat(),
        )
        file_path.write_text(frontmatter.dumps(doc))
        self._update_index(key, doc.metadata)
        return file_path
    
    def recall(self, query: str, limit: int = 5) -> list[str]:
        """Simple keyword search across memory files."""
        results = []
        for file_path in self.base_dir.glob("*.md"):
            content = file_path.read_text()
            if self._matches(query, content):
                results.append(content)
                self._touch(file_path)  # Update last_accessed
        return sorted(results, key=self._relevance_score)[:limit]
    
    def forget(self, key: str) -> None:
        file_path = self.base_dir / f"{key}.md"
        archive_path = self.base_dir / "archive" / f"{key}.md"
        file_path.rename(archive_path)
        self._update_index(key, remove=True)

Simple. File-based. Human-readable. Version-controllable. No database infrastructure required. For most loops, this is sufficient.
