Chapter 18: The Stop Problem

Level: A (Anchor) · ~5,500 words · Levels served: L3, L4, L5

18.1 The Most Under-Taught Topic

Every loop engineering tutorial teaches you how to start a loop. Almost none teach you how to stop one. This asymmetry is dangerous because a loop that can't stop is worse than a loop that never starts — it burns money, produces garbage, and blocks the system from doing useful work.

The stop problem is: given a loop that's running, how do you know when to terminate it? The answer isn't always "when the goal is met." Sometimes the answer is "when progress has stalled," "when the budget is exhausted," "when the approach is provably wrong," or "when continuing would make things worse."

18.2 The Five Termination Conditions

A well-designed loop can terminate for exactly five reasons:

1. Success

The oracle confirms that the goal is met. This is the happy path — the loop produced verified output.


if oracle.evaluate(output) >= goal.threshold:
    return TerminationReason.SUCCESS

2. Budget Exhaustion

The loop has consumed its allocated resources without achieving the goal. More resources won't help — either the problem is too hard for this loop, or the approach is wrong.


if budget.tokens_spent >= budget.max_tokens:
    return TerminationReason.BUDGET_EXHAUSTED
if budget.iterations >= budget.max_iterations:
    return TerminationReason.BUDGET_EXHAUSTED
if budget.wall_clock >= budget.max_time:
    return TerminationReason.BUDGET_EXHAUSTED

3. No Progress

The loop is running but not improving. The last N iterations produced output at the same quality level — the loop has plateaued.


def detect_no_progress(scores: list[float], window: int = 3) -> bool:
    if len(scores) < window:
        return False
    recent = scores[-window:]
    return max(recent) - min(recent) < 0.05  # Less than 5% variance

4. Oscillation

The loop is undoing and redoing the same changes — modifying a file, then reverting, then re-modifying. This is a sign that the loop has conflicting constraints it can't resolve.


def detect_oscillation(actions: list[Action], window: int = 6) -> bool:
    if len(actions) < window:
        return False
    # Check if actions repeat in a cycle
    half = window // 2
    first_half = actions[-window:-half]
    second_half = actions[-half:]
    return actions_equivalent(first_half, second_half)

5. External Signal

Something outside the loop triggered termination: a human interrupt, a dependency failure, a context change that invalidates the current work.


if interrupt_signal.is_set():
    return TerminationReason.HUMAN_INTERRUPT
if dependency_changed_since(loop_start):
    return TerminationReason.CONTEXT_STALE

18.3 Oscillation: The Silent Killer

Oscillation is the most insidious termination condition because it looks like activity. The loop is doing things — editing files, running tests, producing output — but it's not making progress. It's going in circles.

Common oscillation patterns:

The flip-flop: The model adds code to fix one test, which breaks another test, so it reverts, which re-breaks the first test.


Iteration 1: Add null check → test_null passes, test_valid fails
Iteration 2: Remove null check → test_valid passes, test_null fails
Iteration 3: Add null check → test_null passes, test_valid fails
(repeats forever)

The style war: The model reformats code, then "fixes" the formatting because it looks wrong, then reformats again.

The scope creep cycle: The model expands scope to fix an issue, then contracts scope because it's too complex, then expands again.

Detecting oscillation:


class OscillationDetector:
    def __init__(self, window: int = 4, similarity_threshold: float = 0.8):
        self.history: list[str] = []  # Sequence of file states or actions
        self.window = window
        self.threshold = similarity_threshold
    
    def record(self, state: str):
        self.history.append(state)
    
    def is_oscillating(self) -> bool:
        if len(self.history) < self.window:
            return False
        
        # Check if current state is similar to state N iterations ago
        for lookback in range(2, self.window):
            if len(self.history) > lookback:
                current = self.history[-1]
                past = self.history[-(lookback + 1)]
                if self.similarity(current, past) > self.threshold:
                    return True
        return False
    
    def similarity(self, a: str, b: str) -> float:
        # Simple: exact match or hash comparison
        # Better: diff-based similarity ratio
        return SequenceMatcher(None, a, b).ratio()

Breaking oscillation:

When oscillation is detected, the loop should not simply retry. It should:

  1. Diagnose: Why is the loop oscillating? What conflicting constraints exist?
  2. Escalate: Report the conflict to the orchestrator or human
  3. Reframe: Attempt a fundamentally different approach, not a variation of the same one

18.4 Deadlock in Fleet Loops

In multi-agent systems, deadlock is a termination condition unique to fleets: Agent A waits for Agent B's output, while Agent B waits for Agent A's output. Neither can proceed.


Agent A: "I need the API schema from Agent B before I can write tests"
Agent B: "I need the test structure from Agent A before I can design the API"
→ Deadlock: neither can proceed

Detection:


class DeadlockDetector:
    def __init__(self, timeout: float = 60.0):
        self.agent_states: dict[str, AgentState] = {}
        self.timeout = timeout
    
    def check(self) -> bool:
        # Find agents that haven't progressed
        stuck = [
            agent_id for agent_id, state in self.agent_states.items()
            if state.time_since_last_progress() > self.timeout
        ]
        
        if len(stuck) < 2:
            return False
        
        # Check for circular dependencies
        for agent_id in stuck:
            if self.has_circular_dependency(agent_id, stuck):
                return True
        return False

Resolution:

  • Break the cycle: The orchestrator provides a default value for one of the dependencies, breaking the circular wait
  • Reorder: Restructure the dependency graph so work can proceed serially
  • Timeout: The first agent to timeout produces a best-effort output, unblocking the other

18.5 Graceful Degradation

Not every termination needs to produce a perfect result. When a loop terminates due to budget or no-progress, it should still produce the best output it achieved — not nothing.


class GracefulLoop:
    def __init__(self):
        self.best_output: str | None = None
        self.best_score: float = 0.0
    
    async def run(self, goal: Goal, budget: Budget) -> Result:
        for iteration in range(budget.max_iterations):
            output = await self.execute_step()
            score = await self.verify(output)
            
            # Track best result seen so far
            if score > self.best_score:
                self.best_output = output
                self.best_score = score
            
            if score >= goal.threshold:
                return Result(status="success", output=output, score=score)
            
            if self.should_stop(budget, iteration):
                return Result(
                    status="partial",
                    output=self.best_output,
                    score=self.best_score,
                    reason=self.stop_reason
                )
        
        return Result(
            status="budget_exhausted",
            output=self.best_output,
            score=self.best_score
        )

The key: always return the best output achieved, even on non-success termination. A 70%-quality result is more valuable than no result. The human or downstream system can decide whether to use it.

18.6 Budget Design

Budget isn't just "how much can I spend." It's a termination signal and a convergence indicator.

Setting the right budget:

Too tight: The loop terminates before it can converge. Tasks that would succeed given one more iteration fail consistently. Symptom: high rate of budget-exhausted terminations with scores just below the threshold.

Too loose: The loop wastes money on problems it can't solve. A hard problem consumes the entire budget without converging. Symptom: expensive runs that terminate at budget with low scores.

Right-sized: The loop succeeds within budget 80-90% of the time, with 10-20% escalating to human review. The budget is sufficient for typical tasks and constrains atypical ones.

Budget by task type:

Task Type Typical Budget Reasoning
Simple bug fix 3 iterations, 100K tokens Usually converges in 1-2 iterations
Feature implementation 7 iterations, 500K tokens More exploration and testing needed
Research synthesis 5 iterations, 300K tokens Converges once sources are found
Code review 2 iterations, 200K tokens Usually right on first pass, one retry
Security audit 10 iterations, 1M tokens Needs thoroughness, multiple passes

Dynamic budget adjustment:


class AdaptiveBudget:
    def __init__(self, base_budget: Budget, history: list[LoopResult]):
        self.base = base_budget
        self.history = history
    
    def for_task(self, task: Task) -> Budget:
        # Find similar past tasks
        similar = [r for r in self.history if r.task_type == task.type]
        
        if not similar:
            return self.base  # No history, use default
        
        # Set budget at the 80th percentile of past successful runs
        successful = [r for r in similar if r.status == "success"]
        if successful:
            p80_iterations = percentile([r.iterations for r in successful], 80)
            p80_tokens = percentile([r.tokens_used for r in successful], 80)
            return Budget(
                max_iterations=int(p80_iterations * 1.2),  # 20% headroom
                max_tokens=int(p80_tokens * 1.2),
            )
        
        return self.base

18.7 The Hand-Off Decision

When a loop terminates without success, the escalation path determines what happens next. The hand-off should include everything the next handler (human or different loop) needs:


# Escalation Report

## Task
Fix the authentication race condition

## Status
Terminated: NO_PROGRESS after 5 iterations

## Best result achieved
Score: 6/10 (threshold: 8/10)
3 of 5 tests passing. 2 remain: test_concurrent_login, test_session_race

## What was tried
1. Mutex lock — correct but 3x latency (failed performance constraint)
2. Optimistic locking — partial success, handles simple case but not concurrent writes
3. Event sourcing approach — too complex, abandoned after exceeding scope

## What I believe the issue is
The race window is between token validation (auth.py:42) and session creation (auth.py:67).
Both operations need to be atomic, but the database doesn't support multi-table transactions
with the current ORM configuration.

## Recommended next steps
- Consider database-level locking (SELECT FOR UPDATE)
- Or restructure to single-table operation (merge token and session)
- Human judgment needed on which approach aligns with architecture goals

18.8 Stop Condition Anti-Patterns

No stop condition at all: The loop runs until context fills or the session crashes. This is the most dangerous anti-pattern — it guarantees either wasted money or corrupted state.

Only success stops: The loop terminates on success but has no other termination condition. If the goal is unreachable, the loop runs forever.

Arbitrary iteration limit: "Stop after 10 iterations" without considering whether the task type typically needs 3 or 30. Some tasks fail at 10 that would succeed at 12. Other tasks thrash for 10 iterations that should have stopped at 3.

No oscillation detection: The loop flip-flops between two states indefinitely, consuming budget without progress. Each iteration "looks like" work because the model is actively making changes — but the changes cancel each other out.

Ignoring no-progress: The model confidently tries variations of the same approach, scoring the same each time. Without no-progress detection, it'll consume the entire budget before stopping.

18.9 Implementing Stop Logic


class StopController:
    def __init__(self, config: StopConfig):
        self.config = config
        self.scores: list[float] = []
        self.states: list[str] = []
        self.start_time = time.time()
        self.tokens_used = 0
    
    def record_iteration(self, score: float, state: str, tokens: int):
        self.scores.append(score)
        self.states.append(state)
        self.tokens_used += tokens
    
    def should_stop(self) -> tuple[bool, str | None]:
        # Success
        if self.scores and self.scores[-1] >= self.config.success_threshold:
            return True, "success"
        
        # Budget
        if len(self.scores) >= self.config.max_iterations:
            return True, "max_iterations"
        if self.tokens_used >= self.config.max_tokens:
            return True, "max_tokens"
        if time.time() - self.start_time >= self.config.max_time:
            return True, "timeout"
        
        # No progress
        if len(self.scores) >= self.config.progress_window:
            recent = self.scores[-self.config.progress_window:]
            if max(recent) - min(recent) < self.config.progress_epsilon:
                return True, "no_progress"
        
        # Oscillation
        if len(self.states) >= 4:
            if self.states[-1] == self.states[-3] and self.states[-2] == self.states[-4]:
                return True, "oscillation"
        
        return False, None

This is the minimum viable stop controller. Production systems add: score trend analysis (if scores are decreasing, stop early), approach diversity checking (if the same approach has been tried 3 times, stop), and external signal handling (interrupts, dependency changes).
