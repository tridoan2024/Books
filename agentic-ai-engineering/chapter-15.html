Chapter 15: Goal Specification

Level: A (Anchor) · ~5,800 words · Levels served: L3, L4, L5

15.1 The Highest-Leverage Skill

If you could invest in exactly one skill to improve your loops, invest in goal specification. Everything downstream — oracle design, stop conditions, cost management, fleet coordination — depends on the quality of the goal. A precise goal enables a precise oracle. A vague goal forces a vague oracle, which produces unreliable verification, which produces unreliable loops.

Goal specification is the art of turning human intent ("make it work," "fix the bug," "write good documentation") into machine-checkable acceptance criteria that an oracle can evaluate without human judgment.

This is harder than it sounds. Humans communicate intent through implication, shared context, and unstated standards. Machines evaluate criteria through explicit checks against formal specifications. The gap between these two modes is where loops fail.

15.2 The Spectrum of Goal Precision

Goals exist on a precision spectrum:


Vague ───────────────────────────────────────────────── Precise

"Make it better"   "Fix the auth"   "Make test X pass"   "test_auth_expired
                                                          returns 401 with
                                                          RFC 7807 body when
                                                          token.exp < now()"

The further right your goal, the more reliable your loop. Each position on the spectrum has different implications:

Precision Level Oracle Type Iterations Needed Cost Predictability
Vague Human judgment Unpredictable Unpredictable
Directional Rubric (model judge) 3-10 Medium
Specific Property tests 2-5 High
Exact Deterministic check 1-3 Very high

15.3 Turning Intent into Criteria

The conversion process has three steps:

Step 1: Identify the observable outcome

Ask: "What is true when this is done that isn't true now?" The answer must be something observable — not a feeling, not a preference, but a measurable state change.

  • Bad: "The code should be cleaner" (not observable)
  • Good: "All functions are under 30 lines, no function has more than 3 parameters, cyclomatic complexity is below 10 for every function" (measurable)

Step 2: Make it machine-checkable

Ask: "Could I write a program that checks this without calling a human?" If yes, you have a goal. If no, you need to decompose further or accept that a model judge will be needed.


# Machine-checkable goal: all tests pass
def goal_met() -> bool:
    result = subprocess.run(["pytest", "tests/", "-x"], capture_output=True)
    return result.returncode == 0

# Machine-checkable goal: complexity thresholds
def goal_met() -> bool:
    report = run_complexity_analysis("src/")
    return all(f.complexity < 10 for f in report.functions)

# NOT machine-checkable (requires judgment): "code is readable"
# Needs decomposition into checkable sub-goals

Step 3: Specify failure modes

Ask: "What does unacceptable look like?" Defining failure is often easier than defining success, and it constrains the solution space.

  • "The response must not contain a stack trace" (failure: exposing internals)
  • "The function must handle null input without throwing" (failure: unhandled exception)
  • "The documentation must cover all public methods" (failure: undocumented method)

15.4 Goal Structures

Binary Goals

The simplest form: pass/fail. Either the criteria is met or it isn't.


goal:
  type: binary
  criteria: "All tests in tests/auth/ pass"
  check: "pytest tests/auth/ -x && echo PASS || echo FAIL"

Best for: Bug fixes, test-related tasks, compilation, linting.

Threshold Goals

The output must meet a minimum quality level on a quantitative scale.


goal:
  type: threshold
  criteria: "Documentation coverage exceeds 90%"
  check: "doc-coverage src/ --format json | jq '.coverage'"
  threshold: 0.90

Best for: Quality metrics, performance targets, coverage goals.

Convergent Goals

The loop runs until no new issues are found — convergence indicates completeness.


goal:
  type: convergent
  criteria: "No new security findings in two consecutive passes"
  check: "Run security scan, compare findings with previous run"
  convergence_threshold: 2  # Consecutive clean passes

Best for: Discovery tasks (finding bugs, security issues, documentation gaps).

Comparative Goals

The output must be better than a baseline by some measurable amount.


goal:
  type: comparative
  criteria: "Response time is 30% faster than baseline"
  baseline: "benchmarks/baseline.json"
  check: "Run benchmarks, compare with baseline"
  improvement_threshold: 0.30

Best for: Optimization tasks, refactoring, performance improvements.

Composite Goals

Multiple criteria that must ALL be satisfied.


goal:
  type: composite
  criteria:
    - type: binary
      check: "All tests pass"
    - type: binary
      check: "Type checker reports zero errors"
    - type: threshold
      check: "Coverage > 80%"
      threshold: 0.80
    - type: binary
      check: "No lint warnings"
  all_required: true

Best for: Complex tasks with multiple quality dimensions.

15.5 Acceptance Criteria as Executable Artifacts

The most powerful form of goal specification: acceptance criteria that are themselves executable programs. The goal isn't described — it's embodied in code that can run.

Test-as-goal:


# The goal IS the test. If this passes, the task is done.
def test_expired_token_returns_401():
    token = create_token(expires_at=datetime.now() - timedelta(hours=1))
    response = client.get("/api/protected", headers={"Authorization": f"Bearer {token}"})
    assert response.status_code == 401
    assert response.json()["type"] == "https://errors.example.com/expired-token"
    assert "token has expired" in response.json()["detail"].lower()

The loop's job is to make this test pass. The test IS the oracle. No ambiguity about what "done" means.

Contract-as-goal:


# Property-based contract: must hold for ALL valid inputs
from hypothesis import given, strategies as st

@given(st.text(), st.text())
def test_search_contract(query: str, document: str):
    """Search must: return results that contain the query,
    never return results that don't contain the query,
    return results in relevance order."""
    results = search(query, document)
    for result in results:
        assert query.lower() in result.text.lower()
    for i in range(len(results) - 1):
        assert results[i].score >= results[i+1].score

Schema-as-goal:


{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "required": ["title", "body", "author", "published_at"],
  "properties": {
    "title": { "type": "string", "minLength": 10, "maxLength": 100 },
    "body": { "type": "string", "minLength": 500 },
    "author": { "type": "string" },
    "published_at": { "type": "string", "format": "date-time" }
  },
  "additionalProperties": false
}

15.6 Rubrics as Specifications

When deterministic checks aren't possible (creative tasks, reasoning tasks, quality assessments), rubrics bridge the gap. A rubric is a structured scoring guide that enables consistent evaluation — by a model judge or a human.

Anatomy of a good rubric:


rubric:
  name: "Code Review Quality"
  dimensions:
    - name: "Correctness"
      weight: 0.4
      levels:
        5: "Identifies all actual bugs with correct explanations"
        4: "Identifies most bugs, no false positives"
        3: "Identifies some bugs, minor false positives"
        2: "Misses major bugs or has significant false positives"
        1: "Fails to identify obvious issues"
    
    - name: "Actionability"
      weight: 0.3
      levels:
        5: "Every finding has a specific fix with file:line reference"
        4: "Most findings have specific fixes"
        3: "Findings describe the problem but not the fix"
        2: "Findings are vague, hard to act on"
        1: "Findings don't map to actionable changes"
    
    - name: "Severity Assessment"
      weight: 0.3
      levels:
        5: "Severity ratings match actual risk accurately"
        4: "Mostly accurate severity, occasional over/under-rating"
        3: "Severity is roughly directional"
        2: "Severity ratings seem arbitrary"
        1: "Critical issues rated low, trivial issues rated high"
  
  passing_score: 3.5  # Weighted average must exceed this

Using rubrics in loops:

The rubric is provided to a judge agent (separate from the maker agent). The judge scores the output against each dimension. If the weighted average exceeds the threshold, the loop considers the goal met.


async def rubric_evaluation(output: str, rubric: Rubric) -> float:
    judge_prompt = f"""
    Evaluate this output against the rubric below.
    Score each dimension 1-5 with a one-sentence justification.
    
    Output to evaluate:
    {output}
    
    Rubric:
    {rubric.to_text()}
    """
    scores = await judge_model.generate(judge_prompt, schema=RubricScores)
    return rubric.weighted_average(scores)

15.7 The Goal Decomposition Pattern

Complex goals that can't be directly machine-checked can often be decomposed into sub-goals that can:


High-level goal (not directly checkable):
  "Write comprehensive documentation for the auth module"

Decomposed into checkable sub-goals:
  1. All public functions have docstrings (ast check)
  2. Every function's docstring includes: description, params, returns, raises (format check)
  3. At least one usage example per function (pattern check)
  4. All cross-references resolve to existing functions (link check)
  5. Readability score > grade 10 on Flesch-Kincaid (metric check)
  6. No function is undocumented (coverage check)

Each sub-goal is independently checkable. The composite goal is met when all sub-goals pass. The decomposition transforms an uncheckable goal into a set of checkable ones.

15.8 Goal Anti-Patterns

The Moving Goal

A goal that changes as the loop works. "Make the code better" → the model makes one change → "but also handle this case" → the model handles it → "and also..." This creates an infinite loop because the target is never stable.

Fix: Define the complete goal before the loop starts. If new requirements emerge, stop the current loop, update the goal, and restart.

The Proxy Goal

Optimizing a measurable proxy rather than the actual intent. "Increase test coverage to 95%" when the actual goal is "ensure correctness." The loop writes trivial tests that increase coverage without testing meaningful behavior.

Fix: Include quality constraints alongside quantity metrics. "Coverage > 95% AND all tests verify at least one assertion about business logic."

The Unfalsifiable Goal

A goal that's defined in terms the oracle can't evaluate. "The code should be elegant." "The documentation should be clear." These feel like goals, but no oracle can determine when they're met.

Fix: Operationalize. "Elegant" → "no function exceeds 20 lines, names describe intent, no nested conditionals deeper than 2." "Clear" → "readability grade 8, no jargon without definition, every concept has an example."

The Implicit Goal

A goal that exists only in the human's mind. The loop is told "fix the bug" but the human also expects the fix to maintain backward compatibility, follow the existing code style, not change the public API, and include a test. These unstated expectations lead to technically-correct-but-unacceptable output.

Fix: Explicit composite goals that include ALL expectations, not just the primary one.

15.9 From Goal to Loop Contract

The goal specification feeds directly into the Loop Contract:


# Human intent: "Fix the login bug"
# ↓ Specification process
# ↓

loop_contract:
  goal:
    primary: "test_login_with_expired_session passes"
    constraints:
      - "All existing tests continue to pass (no regression)"
      - "Public API of auth module unchanged"
      - "Changes limited to src/auth/ directory"
    
  oracle:
    primary: "pytest tests/test_login.py::test_login_with_expired_session"
    constraints:
      - "pytest tests/ -x (full regression)"
      - "git diff --stat | grep -v 'src/auth/' should be empty"
      - "python -c 'import auth; help(auth)' matches baseline"
    
  budget:
    max_iterations: 5
    max_tokens: 300_000
    
  stop_condition:
    success: "All oracle checks pass"
    failure: "Budget exhausted OR 3 consecutive iterations with no progress"
    
  escalation_path:
    on_failure: "Create GitHub issue with diagnosis, @ team lead"

The precision of the goal determines the precision of everything else. A vague goal produces a vague contract. A precise goal produces a precise, enforceable contract.

15.10 Practicing Goal Specification

Like any skill, goal specification improves with practice. Here's a training exercise:

Take any task you'd give to an AI assistant. Write it as you normally would. Then rewrite it with:

  1. Observable outcome (what's true when done?)
  2. Machine-checkable criteria (what program verifies this?)
  3. Explicit constraints (what must NOT change?)
  4. Failure definition (what's unacceptable?)

Before: "Update the README"

After: "README.md includes: project description (>50 words), installation instructions that work when followed literally (verified by running them in a clean Docker container), API documentation for all exported functions (verified by comparing with grep -r 'export function'), and zero broken links (verified by linkchecker)."

The second version takes longer to write. It runs autonomously and reliably. The first version requires human review every single time.
