Chapter 16: Planning and Replanning

Level: S (Standard) · ~4,000 words · Levels served: L3, L4

16.1 The Plan as Durable Artifact

In a loop, the plan isn't just a thought the model has and then forgets. It's a durable artifact — a document that persists across iterations, gets updated as reality changes, and provides continuity when context is compacted or the loop is handed off.

A plan in memory is fragile. A plan in a file is persistent. A plan in a task list is actionable.


# Plan: Fix authentication race condition

## Status: In Progress (iteration 3/5)

## Steps
- [x] 1. Reproduce the bug (test_concurrent_login)
- [x] 2. Identify root cause (token validation not atomic)
- [ ] 3. Implement fix (optimistic locking with retry)  ← CURRENT
- [ ] 4. Verify fix (all auth tests pass)
- [ ] 5. Regression check (full test suite)

## Decisions Made
- Using optimistic locking over mutex (performance req)
- Retry limit: 3 attempts before failure

## Failed Approaches
- Mutex lock: worked but 3x latency regression (iteration 1)

This plan survives compaction. If the context is summarized, the plan file remains intact and readable. If a new agent takes over (handoff), it can read the plan and continue from the current step.

16.2 Plan Depth

How detailed should a plan be? The answer depends on the task's uncertainty:

Low uncertainty tasks (plan deeply):

The path from start to finish is clear. Each step is well-defined. The plan can specify exact files, exact changes, exact verifications.


## Steps
1. Edit src/auth.py:42 — add expiry check before validation
2. Edit tests/test_auth.py — add test_expired_token test case
3. Run pytest tests/test_auth.py -x
4. If pass → run full suite
5. If fail → read error, fix, goto 3

High uncertainty tasks (plan shallowly):

The path isn't clear yet. Early steps will reveal information that changes later steps. Plan only the next 2-3 steps, and replan after each.


## Steps
1. Investigate: what's causing the performance regression?
2. Based on findings, identify the top 3 bottlenecks
3. [REPLAN after step 2 — approach depends on what we find]

The planning depth rule: Plan only as far as you can see clearly. Don't plan step 10 when steps 4-6 might invalidate your assumptions about what step 10 should be.

16.3 Decomposition Depth

A plan step should be achievable in a bounded number of model calls (ideally 1-3). If a step requires more than 5 calls to complete, it should be decomposed into sub-steps.

Too coarse:


Step 3: Implement the entire authentication system

This is a project, not a step. It'll take dozens of iterations and the plan provides no guidance on how to proceed.

Too fine:


Step 3a: Open file auth.py
Step 3b: Navigate to line 42
Step 3c: Type "if token.expired:"
Step 3d: Press enter
Step 3e: Type "    return Response(401)"

This is micro-management. The model is perfectly capable of writing code without keystroke-level instructions.

Right granularity:


Step 3: Add token expiry check in auth.py before the existing validation logic.
         Expired tokens should return 401 with an RFC 7807 error body.

One clear objective. The model knows what to do. It can do it in 1-2 calls.

16.4 Replanning as Progress vs. Thrash

Replanning — revising the plan based on new information — is a healthy part of loop execution. But replanning can also be a symptom of thrashing: the model keeps changing its approach without making progress.

Healthy replanning (progress):

  • Triggered by new information ("tests revealed the bug is in a different file than expected")
  • The new plan builds on what was learned
  • Each replan moves closer to the goal
  • Replans decrease in scope (narrowing down)

Unhealthy replanning (thrash):

  • Triggered by failure without diagnosis ("that didn't work, let's try something else")
  • The new plan ignores what was learned
  • Each replan is equally far from the goal
  • Replans maintain or increase in scope (flailing)

Detecting thrash:


def is_thrashing(plan_history: list[Plan]) -> bool:
    if len(plan_history) < 3:
        return False
    
    # Plans keep changing but completion doesn't advance
    completion_rates = [p.percent_complete for p in plan_history[-3:]]
    if max(completion_rates) - min(completion_rates) < 5:
        return True  # No progress across 3 replans
    
    # Plans are oscillating (approach A → B → A)
    if plan_history[-1].approach == plan_history[-3].approach:
        return True  # Went back to an earlier approach
    
    return False

When thrashing is detected, the loop should stop and escalate. More iterations won't help — the problem requires a fundamentally different approach or human insight.

16.5 Plan-as-Memory

The plan is also a memory device. It records:

  • What was tried (preventing re-attempts of failed approaches)
  • What was decided (preventing decision reversal)
  • What was learned (preserving discoveries across iterations)

When context is compacted, the plan survives because it's a file. When a new agent inherits the work, the plan provides continuity. The plan is the loop's external memory for its current task.

16.6 Todo State as Memory

A lightweight alternative to a full plan file: a todo list that tracks step status.


# Claude Code's task system as plan state
tasks = [
    {"id": 1, "subject": "Reproduce bug", "status": "completed"},
    {"id": 2, "subject": "Identify root cause", "status": "completed"},
    {"id": 3, "subject": "Implement fix", "status": "in_progress"},
    {"id": 4, "subject": "Verify fix", "status": "pending"},
    {"id": 5, "subject": "Regression check", "status": "pending"},
]

The todo list is simpler than a full plan but serves the same purpose: durable state that persists across iterations and context boundaries. The model marks tasks complete as it progresses, providing clear visibility into where it is.

16.7 The Plan Update Protocol

When the plan needs updating (new information, failed step, changed requirements), follow a protocol:

  1. State what changed: "Step 3 failed because X"
  2. State what you learned: "This tells us Y"
  3. Update the plan: Modify the remaining steps based on the new information
  4. Record the failed approach: Add it to the "Failed Approaches" section so it's not retried

## Update (iteration 3)
### What changed
Step 3 (mutex approach) completed but verification revealed 3x latency.

### What we learned
- Synchronization overhead is unacceptable for the hot path
- Need a non-blocking approach
- The race window is ~5ms based on the test timing

### Revised steps
- [x] 3. ~~Implement mutex lock~~ REVERTED (latency regression)
- [ ] 3. Implement optimistic locking with retry ← NEW APPROACH
- [ ] 4. Verify fix (all auth tests pass, latency < baseline * 1.1)
- [ ] 5. Regression check

### Failed approaches (do not retry)
- Mutex lock: correct but 3x latency. Unacceptable for p99 < 50ms requirement.

16.8 Planning in Fleet Loops

In a fleet (Chapter 24), the orchestrator creates the plan and delegates steps to specialists. This creates a coordination challenge: the plan must be visible to all agents, and updates by any agent must propagate.

Centralized planning:

The orchestrator owns the plan. Specialists report results. The orchestrator updates the plan and assigns next steps.


Orchestrator: [Owns plan file]
    ├── Specialist A: "Execute step 3, report result"
    ├── Specialist B: "Execute step 4, report result"
    └── Orchestrator: [Updates plan based on results, assigns next steps]

Decentralized planning:

Each specialist has its own sub-plan for its domain. The orchestrator manages dependencies between sub-plans but doesn't micro-manage within them.


Orchestrator: [High-level plan: milestones and dependencies]
    ├── Specialist A: [Own plan for steps 3-5]
    ├── Specialist B: [Own plan for steps 6-8]
    └── Orchestrator: [Wait for A, then unblock C]

Centralized planning is simpler but creates a bottleneck (everything flows through the orchestrator). Decentralized planning is more efficient but requires clear interfaces between specialists' domains.

16.9 When Not to Plan

Not every task needs a plan. The overhead of planning (creating the artifact, maintaining it, checking against it) is wasted on simple tasks:

  • Single-step fixes with clear resolution
  • Tasks completable in one model call
  • Exploratory tasks where the goal is to learn, not to produce

The planning threshold: if the task requires more than 3 steps or has meaningful uncertainty about the approach, plan. If it's straightforward and achievable in 1-2 steps, just do it.
