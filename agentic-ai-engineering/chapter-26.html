Chapter 26: Human In / On / Out of the Loop

Level: S (Standard) · ~4,000 words · Levels served: L2, L3, L4

26.1 Three Positions for Humans

The human's relationship to an autonomous loop can take three positions:

In the loop: The human is a required step in every iteration. The loop cannot proceed without human approval at each stage. This is L2 — guided agent.

On the loop: The human monitors and intervenes when necessary, but the loop runs independently by default. The human is notified of results and can override or redirect. This is L3-L4 — autonomous with oversight.

Out of the loop: The human sets the goal and constraints, then the loop runs to completion without any human involvement. The human sees only the final result. This is L4-L5 — fully autonomous.


In the Loop:    Human → Agent → Human → Agent → Human → Ship
On the Loop:    Agent → Agent → Agent → [Human notified] → Ship
Out of the Loop: Agent → Agent → Agent → Agent → Ship → [Human sees result]

Each position has different trust requirements, different failure modes, and different escalation designs.

26.2 Designing Escalation

Escalation is the mechanism by which a loop that's out of its depth transitions from "out of the loop" to "on the loop" or "in the loop." Good escalation design means the human is only bothered when their judgment is genuinely needed.

Escalation triggers:

Trigger Action Example
Budget exhausted Notify human with diagnosis "Couldn't fix after 5 attempts. Here's what I tried."
Confidence below threshold Request human verification "I think this is right but I'm only 60% sure."
Irreversible action Request approval "Ready to deploy. Approve?"
Novel situation Request guidance "This pattern doesn't match anything I've seen."
Conflicting constraints Request priority decision "Can't satisfy both X and Y. Which matters more?"
Safety concern Block and notify "This action might delete data. Pausing for review."

Escalation quality:

Bad escalation: "I'm stuck. Help."

Good escalation: "I've identified the bug (race condition in auth.py:42-67). I've tried two approaches: (1) mutex — correct but too slow, (2) optimistic locking — handles simple case but fails under high concurrency. I need guidance on whether the performance constraint can be relaxed, or whether a fundamentally different architecture is needed."

Good escalation gives the human everything they need to make a decision: what happened, what was tried, what the options are, and what tradeoffs each option carries.

26.3 Approval Surfaces

When the loop needs human approval, how does it ask? The approval surface determines friction:

Low-friction (notifications):

  • Slack message with approve/reject buttons
  • GitHub PR review request
  • Email with action links
  • Mobile push notification with quick actions

Medium-friction (review required):

  • Dashboard showing loop state and pending decisions
  • Diff view requiring explicit sign-off
  • Form with structured questions the human must answer

High-friction (session required):

  • Interactive session where the human reviews and discusses with the loop
  • Meeting/call to resolve complex decisions
  • Document review and sign-off

Match friction to stakes: Don't require a meeting to approve a routine deployment. Don't use a Slack button to approve deletion of production data.

26.4 Notification Design

The loop's notifications to humans should follow the "what, so what, now what" pattern:


## [Loop Name] — Action Required

**What happened:** Security review of PR #342 found 2 CRITICAL findings.

**So what:** These findings indicate potential SQL injection in the user search endpoint
and an authentication bypass in the admin panel.

**Now what:** 
- [ ] Review findings at [link]
- [ ] Approve blocking the PR (recommended)
- [ ] Override and allow merge (explain reasoning)

Deadline: PR will auto-block in 2 hours if no response.

Notification anti-patterns:

Alert fatigue: Too many notifications. The human stops reading them. Critical findings get lost in the noise. Fix: Only notify for genuinely new or high-severity situations. Batch low-severity findings into a daily digest.

Insufficient context: "Loop failed. Please investigate." The human has to dig through logs to understand what happened. Fix: Include diagnosis, attempted solutions, and next steps in the notification.

No action available: The notification tells the human something happened but provides no way to respond. Fix: Every notification that requires action must include the action mechanism (button, link, reply format).

26.5 Trust Calibration

How much autonomy to grant depends on trust — and trust is earned through demonstrated reliability:

The trust equation:


Trust = (Consistency × Competence × Track Record) / Stakes
  • Consistency: Does the loop produce similar-quality results across runs?
  • Competence: Does the loop handle the task type well?
  • Track Record: How many successful runs without human correction?
  • Stakes: What's the cost of a mistake?

The trust ladder:


Level 0: Human reviews every output before action
Level 1: Loop acts, human spot-checks 50% of outputs
Level 2: Loop acts, human reviews failures and escalations only
Level 3: Loop acts, human reviews weekly aggregate metrics
Level 4: Loop acts, human audits monthly

Climbing the ladder:

  • 10 consecutive successful runs → Level 0 → Level 1
  • 50 runs with <5% human corrections → Level 1 → Level 2
  • 200 runs with <2% critical issues → Level 2 → Level 3

Descending the ladder:

  • Any critical failure → drop two levels immediately
  • 3 non-critical failures in a week → drop one level
  • Human correction rate exceeds 10% → drop one level

26.6 The Approval Gate Pattern

For actions that are irreversible or high-stakes, the loop pauses and waits for explicit human approval:


class ApprovalGate:
    def __init__(self, channel: NotificationChannel, timeout: float = 3600):
        self.channel = channel
        self.timeout = timeout
    
    async def request_approval(self, action: Action, context: str) -> bool:
        notification = self.channel.send(
            title=f"Approval needed: {action.description}",
            body=context,
            actions=["Approve", "Reject", "Defer"],
        )
        
        try:
            response = await asyncio.wait_for(
                notification.wait_for_response(),
                timeout=self.timeout,
            )
            return response == "Approve"
        except asyncio.TimeoutError:
            # Default action on timeout depends on stakes
            return self.default_on_timeout(action)
    
    def default_on_timeout(self, action: Action) -> bool:
        # High stakes: default deny
        # Low stakes: default approve
        return action.reversible and action.blast_radius == "low"

When to gate:

Action Gate? Reasoning
Edit code on feature branch No Reversible, contained
Create a PR No Human reviews the PR itself
Merge a PR Yes Affects main branch
Deploy to staging No (usually) Low blast radius
Deploy to production Yes High blast radius
Send customer email Yes Irreversible, external
Delete data Yes Irreversible
Post public comment Yes Visible to others

26.7 Webhook Patterns for Notifications

Production notification implementations:


# Slack notification with approval buttons
async def slack_approval(finding: Finding) -> bool:
    response = await slack.post_message(
        channel="#security-approvals",
        blocks=[
            {"type": "header", "text": f"Security Finding: {finding.title}"},
            {"type": "section", "text": finding.summary},
            {"type": "actions", "elements": [
                {"type": "button", "text": "Approve", "action_id": "approve", "style": "primary"},
                {"type": "button", "text": "Reject", "action_id": "reject", "style": "danger"},
            ]}
        ]
    )
    return await wait_for_button_click(response.ts)

# GitHub PR as approval mechanism
async def pr_approval(changes: Changes) -> bool:
    pr = await github.create_pr(
        title=f"[Auto] {changes.summary}",
        body=changes.full_description,
        branch=changes.branch,
    )
    # The PR itself is the approval surface
    # Merge = approve, Close = reject
    return await wait_for_pr_resolution(pr.number)

26.8 Criteria for Climbing the Ladder

Practical checklist for granting more autonomy:

From in-the-loop to on-the-loop (L2→L3):

  • [ ] Oracle catches >95% of issues that human review catches
  • [ ] Zero critical failures in the last 30 runs
  • [ ] Human corrections are <5% of total outputs
  • [ ] The loop's escalations are well-formed and actionable
  • [ ] Rollback mechanism is tested and works

From on-the-loop to out-of-the-loop (L3→L4):

  • [ ] 6+ months of on-the-loop operation without critical issues
  • [ ] Cost per output is well-understood and stable
  • [ ] The loop handles edge cases and novel situations gracefully
  • [ ] Alert fatigue isn't a problem (notifications are rare and meaningful)
  • [ ] A human audits results periodically and finds no systematic issues

26.9 Maintaining Control at Scale

As you run more loops with less oversight, control must come from infrastructure rather than attention:

  1. Aggregate dashboards: See the health of all loops at a glance
  2. Anomaly detection: Alert when any loop's behavior changes significantly
  3. Periodic audits: Sample outputs from each loop monthly for human review
  4. Kill switches: Ability to stop any loop instantly from the dashboard
  5. Budget ceilings: Hard limits that can't be overridden without human authorization

The goal isn't to watch every loop constantly. It's to have confidence that if something goes wrong, you'll know quickly and can respond effectively.
