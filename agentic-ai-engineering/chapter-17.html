Chapter 17: Execution and State — Worktrees, Sandboxes, Checkpoints

Level: S (Standard) · ~4,000 words · Levels served: L3, L4

17.1 The Isolation Imperative

When a loop executes, it modifies state: files change, databases get written, APIs get called. Without isolation, these modifications are permanent and immediate. A mistake in iteration 3 corrupts the state that iteration 4 needs. Two parallel agents editing the same file produce garbage. A failed loop leaves the workspace in an inconsistent state that the developer must clean up manually.

Isolation solves this: give each execution a contained environment where it can work freely, verify its output, and only commit changes to the real world when verification passes.

17.2 Git Worktrees for Code Loops

The most common isolation mechanism for code-modifying loops is the git worktree — a second checkout of the same repository on a separate branch, in a separate directory.


# Create an isolated workspace
git worktree add .claude/worktrees/fix-auth -b fix/auth-race

# Agent works in the isolated directory
# All changes happen on the fix/auth-race branch
# The main workspace is untouched

# On success: merge back
git merge fix/auth-race

# On failure: delete and try again
git worktree remove .claude/worktrees/fix-auth
git branch -D fix/auth-race

Why worktrees, not branches alone?

A branch switch changes the working directory in-place. If two agents need to work simultaneously (fleet loop), they can't both switch branches in the same directory. Worktrees give each agent its own directory with its own branch — true parallel execution without file conflicts.

The worktree lifecycle:


CREATE ──→ WORK ──→ VERIFY ──→ MERGE or DISCARD
  │          │         │           │
  │          │         │           └─ Success: merge to main
  │          │         │              Failure: rm worktree
  │          │         │
  │          │         └─ Run tests, check goals
  │          │
  │          └─ Agent edits, creates, deletes files
  │
  └─ Fresh branch from origin/main

Cost of worktrees:

  • Setup: ~200-500ms (git operations)
  • Disk: full copy of working tree (can be significant for large repos)
  • Merge complexity: potential conflicts when merging back
  • Cleanup: must be explicitly removed or they accumulate

Use worktrees when: Multiple agents edit code in parallel, or a single agent needs to safely experiment without corrupting the main workspace.

Don't use when: A single agent works sequentially on one file at a time. The overhead isn't justified — just work directly and revert on failure.

17.3 Sandboxes for Execution

Code execution carries risk. A loop that can run arbitrary commands might accidentally:

  • Delete important files (rm -rf /)
  • Consume all disk space (infinite loop writing to disk)
  • Exhaust memory (memory leak in generated code)
  • Make unwanted network calls
  • Modify system configuration

Sandboxes contain these risks by limiting what the execution can access:

Container-based sandbox:


import docker

def execute_in_sandbox(code: str, timeout: int = 30) -> str:
    client = docker.from_env()
    container = client.containers.run(
        "python:3.12-slim",
        command=["python", "-c", code],
        mem_limit="512m",
        cpu_period=100000,
        cpu_quota=50000,  # 50% of one CPU
        network_disabled=True,  # No network access
        read_only=True,  # Can't modify filesystem
        detach=True,
        timeout=timeout,
    )
    container.wait(timeout=timeout)
    output = container.logs().decode()
    container.remove()
    return output

Filesystem sandbox:


import tempfile
from pathlib import Path

class FilesystemSandbox:
    def __init__(self):
        self.root = Path(tempfile.mkdtemp(prefix="loop-sandbox-"))
    
    def write(self, relative_path: str, content: str):
        full_path = self.root / relative_path
        assert full_path.resolve().is_relative_to(self.root)  # Prevent path traversal
        full_path.parent.mkdir(parents=True, exist_ok=True)
        full_path.write_text(content)
    
    def commit_to_real(self, real_root: Path):
        """Copy verified changes from sandbox to real filesystem."""
        for file in self.root.rglob("*"):
            if file.is_file():
                dest = real_root / file.relative_to(self.root)
                dest.parent.mkdir(parents=True, exist_ok=True)
                shutil.copy2(file, dest)
    
    def cleanup(self):
        shutil.rmtree(self.root)

17.4 Checkpoints and Resumability

A loop that crashes at iteration 7 of 10 shouldn't restart from iteration 1. Checkpoints save the loop's state at regular intervals so it can resume from the last good state.

What to checkpoint:


@dataclass
class LoopCheckpoint:
    iteration: int
    plan_state: dict          # Which steps completed
    modified_files: list[str]  # Files changed since start
    discoveries: list[str]     # Facts learned during the loop
    budget_spent: float        # Tokens/cost consumed so far
    last_verification: dict    # Results of last oracle check
    timestamp: str

When to checkpoint:

  • After every successful iteration (the loop made verified progress)
  • Before any risky operation (destructive action, expensive API call)
  • At natural milestones (sub-task completed, phase transition)
  • When context is about to be compacted (preserve state before lossy operation)

Resuming from a checkpoint:


async def resume_loop(checkpoint_path: Path) -> Result:
    checkpoint = load_checkpoint(checkpoint_path)
    
    # Verify checkpoint is still valid
    if not verify_workspace_matches_checkpoint(checkpoint):
        raise StaleCheckpointError("Workspace changed since checkpoint")
    
    # Restore state
    plan = load_plan(checkpoint.plan_state)
    budget = Budget(remaining=checkpoint.budget_remaining)
    
    # Continue from last iteration
    for iteration in range(checkpoint.iteration, max_iterations):
        result = await execute_step(plan.current_step)
        verification = await verify(result)
        
        if verification.passed:
            plan.advance()
            save_checkpoint(create_checkpoint(iteration, plan, budget))
        
        if plan.complete:
            return Result(success=True)
    
    return Result(success=False, reason="budget_exhausted")

17.5 Rollback Strategies

When a loop fails — tests break, the output is wrong, the approach doesn't work — you need to undo its changes and return to a known-good state.

Git-based rollback (code loops):


# Option 1: Reset the worktree (if using worktrees)
git worktree remove .claude/worktrees/failed-attempt
git branch -D failed-attempt

# Option 2: Revert to a checkpoint commit
git reset --hard checkpoint-commit-sha

# Option 3: Selective revert (undo specific changes)
git checkout main -- src/auth.py  # Restore one file from main

Filesystem rollback (general):


class TransactionalFilesystem:
    def __init__(self, root: Path):
        self.root = root
        self.originals: dict[Path, str | None] = {}  # path → original content (None = didn't exist)
    
    def write(self, path: Path, content: str):
        if path not in self.originals:
            self.originals[path] = path.read_text() if path.exists() else None
        path.write_text(content)
    
    def rollback(self):
        for path, original in self.originals.items():
            if original is None:
                path.unlink(missing_ok=True)  # File was created — delete it
            else:
                path.write_text(original)     # File was modified — restore
        self.originals.clear()
    
    def commit(self):
        self.originals.clear()  # Discard rollback info — changes are permanent

17.6 State Management Patterns

Pattern 1: Immutable iterations

Each iteration produces a new state directory. On success, the latest state becomes the "current" state. On failure, it's discarded.


states/
├── iteration_001/  # Initial state
├── iteration_002/  # After step 1
├── iteration_003/  # After step 2 (current)
└── iteration_004/  # In progress (may be discarded)

Pattern 2: Write-ahead log

Before any modification, record what's about to change. On crash, replay the log to determine what happened and what needs to be undone.


class WriteAheadLog:
    def __init__(self, log_path: Path):
        self.log_path = log_path
    
    def record(self, operation: str, target: str, before: str, after: str):
        entry = {"op": operation, "target": target, "before": before, "after": after}
        with self.log_path.open("a") as f:
            f.write(json.dumps(entry) + "\n")
    
    def undo_last(self):
        entries = self.log_path.read_text().strip().split("\n")
        if entries:
            last = json.loads(entries[-1])
            Path(last["target"]).write_text(last["before"])

Pattern 3: Branch-per-attempt

Each iteration works on its own branch. Only verified branches get merged to the main working branch.


main ──────────────────────────────────────────→
       \         \         \
        attempt-1  attempt-2  attempt-3
        (failed)   (failed)   (merged ✓)

17.7 Parallel Execution Safety

In a fleet loop, multiple agents may execute simultaneously. Safety requires:

  1. No shared mutable state: Each agent has its own worktree, own files, own sandbox
  2. Coordination through the orchestrator: Agents don't communicate directly — they report to the lead
  3. Merge strategy defined in advance: When parallel work needs to combine, the merge rules are explicit

async def parallel_execution(tasks: list[Task], orchestrator: Agent):
    # Create isolated workspace per agent
    worktrees = [create_worktree(f"agent-{i}") for i in range(len(tasks))]
    
    # Execute in parallel
    results = await asyncio.gather(*[
        execute_in_worktree(task, worktree)
        for task, worktree in zip(tasks, worktrees)
    ])
    
    # Merge verified results
    for result, worktree in zip(results, worktrees):
        if result.verified:
            merge_worktree(worktree)
        else:
            discard_worktree(worktree)

17.8 The Execution Checklist

Before a loop iteration executes:

  • [ ] Workspace is in a known-good state (checkpoint verified)
  • [ ] Changes are isolated (worktree, sandbox, or transaction)
  • [ ] Rollback mechanism is in place
  • [ ] Budget limits are enforced (timeout, resource caps)
  • [ ] Irreversible actions require approval

After execution:

  • [ ] Verification run against the goal
  • [ ] If passed: commit changes, advance plan
  • [ ] If failed: rollback, record failure, update plan
  • [ ] Checkpoint saved
