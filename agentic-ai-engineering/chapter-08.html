Chapter 8: Context Engineering II — Compaction, Editing, and Handoff

Level: S (Standard) · ~4,000 words · Levels served: L3, L4, L5

8.1 When the Window Fills

Every loop eventually faces a choice: stop, or continue with degraded context. A loop that runs 20 iterations on a complex task will fill its context window — regardless of how aggressively you manage it. The question isn't whether you'll hit the limit. It's what you do when you get there.

Three strategies exist, and production loops use all three:

  1. Compaction: Lossy compression of the existing context
  2. Context editing: Surgical removal of specific elements
  3. Handoff: Transferring state to a fresh context (new session or new agent)

Each has tradeoffs. Each is appropriate in different situations. Understanding when to use which is a core loop engineering skill.

8.2 Compaction as Lossy Checkpoint

Compaction takes a long conversation — hundreds of messages, tool results, reasoning chains — and compresses it into a summary that preserves the essential state while discarding the details. It's lossy by design: you lose the specifics of how you got here, but retain where "here" is.

What compaction preserves:

  • Current goal and progress toward it
  • Decisions made and their rationale
  • Key facts discovered during the loop
  • The current plan and what's been completed
  • Active errors or blockers

What compaction discards:

  • The full text of tool outputs (replaced by summaries)
  • Reasoning chains that led to abandoned approaches
  • Superseded plans and old state
  • The specific sequence of actions (replaced by outcome descriptions)

# Compaction summary (what a compacted context looks like)

## Goal
Fix the authentication race condition in auth_middleware.py

## Progress
- Identified root cause: token validation and session creation aren't atomic
- Attempted fix 1: mutex lock — worked but caused 3x latency regression
- Attempted fix 2: optimistic locking with retry — in progress

## Current state
- Branch: fix/auth-race-condition
- Modified files: auth_middleware.py (lines 42-67), tests/test_auth.py
- Test status: 44/47 passing. Failures: test_concurrent_login, test_session_race, test_token_refresh

## Key decisions
- Using optimistic locking over pessimistic (performance requirement)
- Added retry limit of 3 to prevent infinite retry loops
- Keeping backward compatibility with existing session format

## Next step
Complete the retry logic in auth_middleware.py:58, then run the failing tests

This summary is ~200 tokens. The full history it replaces might be 100K tokens. The compression ratio is 500:1, and the essential state is preserved.

The compaction risk

Compaction is lossy. You lose:

  • Nuance: The subtle reasoning about why approach A was abandoned might matter if approach B fails the same way
  • Evidence: The specific tool output that revealed a fact is gone; only the fact remains
  • Recovery paths: If the summary is wrong or incomplete, there's no way back to the original context

The mitigation: write compaction summaries before discarding the original. Store the full conversation externally (a log file, a database) so it can be re-read if the compacted context proves insufficient. Compaction should be "lossy in memory, lossless on disk."

8.3 Structured Handoff Notes

When a loop reaches context capacity and needs to continue in a fresh session, it performs a handoff: transferring accumulated state from the old context to the new one. A handoff note is a structured document that enables a fresh agent to continue work without re-discovering everything the previous agent learned.

A good handoff note contains:


# Handoff: [Task Name]

## Context
What the task is and why it matters. One paragraph.

## Completed work
What has been done so far. Specific files modified, tests passing/failing, decisions made.

## Current state
The exact situation the new agent inherits. File paths, line numbers, test results.

## Active plan
What the previous agent intended to do next. The receiving agent may revise.

## Known issues
Problems discovered but not yet resolved. Gotchas, constraints, edge cases.

## Critical constraints
Things the new agent must NOT do. Approaches already tried and failed.

The handoff quality problem

A handoff note is only as good as the agent that writes it. If the previous agent misunderstands its own state — or if its context is so degraded that it can't accurately summarize — the handoff note will be wrong, and the new agent will start from a misleading position.

Mitigations:

  1. Write handoff notes early: Don't wait until context is full. Write the handoff note while the agent's context is still fresh, and update it incrementally.
  2. Ground in artifacts: Reference specific files, line numbers, and test results rather than relying on the agent's memory of what it did.
  3. Verify post-handoff: The receiving agent's first action should be to verify the handoff note against reality (read the files, run the tests, check the state).

8.4 Designing Loops That Outlive Their Context

A well-designed loop doesn't panic when context fills. It's designed from the start to handle context overflow gracefully:

Pattern 1: The milestone loop

Break the work into milestones. At each milestone, write a checkpoint (compaction + handoff note) and optionally start a fresh context. Each milestone is achievable within a single context fill.


Milestone 1: Reproduce the bug [fits in one context]
  → Checkpoint: "Bug reproduced. Root cause is X. See test_file.py:23"

Milestone 2: Implement the fix [fresh context, starts from checkpoint]
  → Checkpoint: "Fix implemented in file.py:40-55. 3 tests still failing."

Milestone 3: Fix regressions [fresh context, starts from checkpoint]
  → Checkpoint: "All tests pass. Ready for review."

Pattern 2: The rolling window

Keep only the last N iterations in full context. Everything older is compacted into a running summary. The summary grows slowly; the detail window stays fixed.


Context structure:
  [System prompt + skills]           ~10K tokens (fixed)
  [Running summary of all history]   ~2K tokens (grows slowly)
  [Last 3 iterations in full]        ~30K tokens (fixed window)
  [Current iteration]                ~10K tokens (variable)

Pattern 3: The external state pattern

The loop's true state lives outside the context — in files, databases, or structured documents. The context contains only what's needed for the current step, loaded from external state on demand.


# External state pattern
state_file = Path("loop_state.json")

def load_context_for_step(step: int) -> str:
    state = json.loads(state_file.read_text())
    return f"""
    Goal: {state['goal']}
    Current step: {step}
    Completed steps: {state['completed']}
    Current state: {state['current_state']}
    Relevant context: {state.get(f'step_{step}_context', '')}
    """

def save_state_after_step(step: int, result: dict):
    state = json.loads(state_file.read_text())
    state['completed'].append(step)
    state['current_state'] = result['new_state']
    state_file.write_text(json.dumps(state, indent=2))

This pattern is the most robust for long-running loops. The context window is a working memory — a scratch pad for the current step — while the persistent state lives in durable storage.

8.5 Automatic Tool-Result Clearing

The single biggest source of context bloat in production loops is accumulated tool results. A file read returns 3K tokens. A search returns 5K tokens. A command output returns 2K tokens. After ten iterations with three tool calls each, you have 100K tokens of tool results — most of which are irrelevant to the current iteration.

The solution is automatic clearing: tool results are removed or summarized after they've been processed.


class ToolResultManager:
    def __init__(self, max_age_iterations: int = 2, max_size_tokens: int = 2000):
        self.max_age = max_age_iterations
        self.max_size = max_size_tokens
    
    def process_result(self, result: str, current_iteration: int) -> str:
        if len(result) > self.max_size:
            return self.summarize(result)
        return result
    
    def prune_old_results(self, messages: list, current_iteration: int) -> list:
        return [
            msg for msg in messages
            if msg.type != "tool_result" 
            or (current_iteration - msg.iteration) <= self.max_age
        ]

Claude Code implements this aggressively: tool results are available for the current iteration and the next, then they're cleared. If the model needs the information again, it re-reads the file or re-runs the tool. The re-read costs a few hundred tokens; keeping stale results costs thousands of tokens of noise in every subsequent iteration.

8.6 When to Compact vs. When to Handoff

Situation Strategy Rationale
Context 70% full, loop converging Compact in place Don't disrupt a working loop
Context 90% full, loop converging Compact aggressively Buy enough room to finish
Context full, loop stuck Handoff to fresh context The current context may be part of the problem
Context full, task has natural milestones Handoff at milestone Clean break, clear state
Multiple agents need to coordinate External state + minimal context Each agent loads only what it needs

The wrong choice: letting context fill to 100% without action. At capacity, the system must either truncate (losing information unpredictably) or fail (stopping the loop). Neither is acceptable. Context management should be proactive, not reactive.

8.7 The Compaction-Quality Tradeoff

Compaction introduces a fundamental tradeoff: you gain context space at the cost of information fidelity. How much to compact — and when — depends on the task:

High-fidelity tasks (code, data): Compact reasoning and history, but preserve exact file paths, line numbers, test results, and error messages verbatim. A summary that says "some tests failed" is useless; one that says "test_auth.py:test_expired_token fails with AssertionError at line 23" is actionable.

Low-fidelity tasks (research, writing): Can compact more aggressively. A summary of sources and key findings is often sufficient; the exact text of each source isn't needed in context (it can be re-retrieved if needed).

State-heavy tasks (multi-step transformations): The current state is critical; the history of how you got there is less important. Compact the journey, preserve the destination.

8.8 Designing for Compaction from the Start

The best compaction happens when the loop is designed for it from the beginning. Practices that make compaction effective:

  1. Maintain a running state document: Update it each iteration with the current situation. This becomes the compaction target — instead of summarizing a huge history, you already have a concise state description.
  1. Separate ephemeral from durable information: Tool results, reasoning chains, and intermediate states are ephemeral. Decisions, facts, and plan updates are durable. Store durable information in a structured format that survives compaction.
  1. Write checkpoints at natural boundaries: When a sub-task completes, when a decision is made, when a significant fact is discovered. Each checkpoint is a potential compaction point.
  1. Use external storage for large artifacts: File contents, command outputs, and search results should be stored externally and referenced by path, not embedded in context. This makes compaction trivial — you just drop the reference and re-read if needed.
