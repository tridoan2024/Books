Chapter 7: Context Engineering I — The Window Is a Budget

Level: A (Anchor) · ~6,000 words · Levels served: L2, L3, L4, L5

7.1 Context as the Scarce Resource

In 2024, the bottleneck was model capability — the model couldn't reason well enough. In 2026, the bottleneck has shifted. Models are capable enough for most tasks. The bottleneck is now context — getting the right information into the model's window at the right time.

A context window is a budget. Every token in that window has a cost (literal dollars) and an opportunity cost (displaces potentially more useful information). The engineering discipline of context management is about maximizing the signal-to-noise ratio within a fixed budget.

The numbers make this concrete:

  • A 200K-token context window costs $0.60 to fill at $3/M input tokens
  • Every unnecessary token is money spent on noise
  • Attention quality degrades with context length — information at position 100K gets less attention than information at position 1K
  • A loop that runs 10 iterations with a poorly-managed context spends $6 on noise that degrades quality with each iteration

Context engineering isn't optimization for the sake of optimization. It's a prerequisite for loop reliability. A model reasoning over noisy, irrelevant context makes worse decisions at every step. Those worse decisions compound across iterations (Chapter 6). The result: expensive loops that produce poor output.

7.2 The Smallest High-Signal Set Principle

The goal of context engineering is to present the model with the smallest set of information that enables correct reasoning about the current step. Not the maximum information. Not "everything that might be relevant." The minimum sufficient signal.

This principle has three components:

Smallest

Less context is better than more, all else being equal. Every additional token:

  • Increases cost
  • Dilutes attention
  • Introduces potential noise that could mislead reasoning
  • Competes with truly relevant information for the model's limited attention budget

High-Signal

The information that IS in context must be genuinely useful for the current decision. Test: if you removed this piece of context, would the model's output quality degrade? If yes, it earns its place. If no, it's noise.

Set

Context is a collection, and the collection matters. Individual pieces of information may be low-value in isolation but essential when combined with others. The auth.py file alone doesn't explain the bug — but auth.py + the failing test + the error message together make the fix obvious.

7.3 Context Rot

Context doesn't stay fresh. In a loop, the window accumulates the history of every previous iteration: old plans that were superseded, tool outputs that are no longer relevant, error messages from bugs already fixed, reasoning about approaches already abandoned.

This is context rot — the progressive contamination of the window with stale information that was once relevant but now only adds noise.


Iteration 1: [goal + discovery + plan + execution + failure]
Iteration 2: [goal + discovery + plan + execution + failure + OLD failure from iter 1]
Iteration 3: [goal + discovery + plan + OLD plan from iter 1 + OLD plan from iter 2 + ...]
...
Iteration 8: [90% stale context, 10% current information]

By iteration 8, the model is reasoning primarily over irrelevant history. Its decisions degrade not because the model got dumber, but because the signal-to-noise ratio in its context collapsed.

Symptoms of context rot:

  • The model references information from earlier iterations that's no longer current
  • The model "forgets" recent corrections because they're buried under old context
  • The model's output quality degrades monotonically with iteration count
  • Token usage per iteration grows without corresponding increase in output quality

Solutions to context rot:

  1. Aggressive pruning: Remove tool outputs, old plans, and resolved errors after each iteration
  2. Summarization: Replace verbose history with a compact summary of what was learned
  3. Sliding window: Only keep the last N iterations in full detail
  4. Structured state: Maintain a small "current state" document that's updated each iteration, replacing the full history with the current situation

7.4 Attention Decay

Even within a single context window, not all positions are equal. Models exhibit attention decay — information early and late in the context gets more attention than information in the middle. This is the "lost in the middle" phenomenon documented extensively in research.

The practical consequence: where you place information in the context matters as much as what information you include.


High attention ──────────────────────────────── High attention
[System prompt]  [Middle content]  [Recent content + user message]
     ↑               ↑                    ↑
 Well-attended    Under-attended        Well-attended

Placement strategy for loops:

Information Optimal Position Why
Loop Contract (goal, oracle, budget) System prompt (start) Always visible, never buried
Current state / what's been tried Just before the current step Most recent = most attended
Skills / project knowledge Early system context Stable, foundational
Tool results from current step End of context (most recent) Needs immediate attention
History of past iterations Middle (if kept) or removed Least important for current step

7.5 Just-In-Time Retrieval

The alternative to pre-loading context is just-in-time retrieval: loading information only when the model needs it, at the moment it needs it.

Pre-loaded context (RAG-style):


[System prompt + 50K tokens of potentially-relevant documentation]
→ Model reasons over everything, mostly ignoring 80% of it
→ Cost: high. Quality: moderate. The relevant 20% competes with the irrelevant 80%.

Just-in-time retrieval (agentic search):


[System prompt + goal + current step]
→ Model decides what information it needs
→ Model calls search/read tools to retrieve ONLY that information
→ Model reasons over a small, highly-relevant context
→ Cost: lower (fewer input tokens). Quality: higher (pure signal).

The tradeoff: just-in-time retrieval requires an extra inference step (deciding what to search for) and tool-call latency. But for complex tasks where the relevant information depends on what the model discovers during execution, just-in-time retrieval dramatically outperforms pre-loaded context.

When to pre-load vs. retrieve just-in-time:

Pre-load (RAG) Just-in-time (Agentic Search)
Relevant set is small and known in advance Relevant set depends on what the model discovers
Information is stable across iterations Information changes with each step
Task is simple enough that more context doesn't confuse Task is complex enough that irrelevant context hurts
Latency-sensitive (no time for extra retrieval step) Quality-sensitive (worth the retrieval latency)

7.6 The Context Budget Allocation

Think of your context window as a budget with line items. For a 200K-token window:


context_budget:
  system_prompt_and_skills: 5K-15K       # Stable, loaded once
  current_goal_and_contract: 1K-2K       # Always present
  current_state_summary: 2K-5K           # Updated each iteration
  tool_results_current_step: 10K-50K     # Variable, pruned aggressively
  working_history: 10K-30K               # Last 2-3 iterations
  reserved_for_model_output: 10K-30K     # Generation budget
  
  # What does NOT get budget:
  full_conversation_history: 0           # Compacted or pruned
  large_file_contents: 0                 # Read on demand
  irrelevant_tool_results: 0            # Pruned immediately

The exact allocation depends on your task. Code-heavy tasks need more room for file contents. Research tasks need more room for source material. The principle is constant: allocate deliberately, not by default accumulation.

7.7 Agentic Search vs. Pre-Loaded RAG

Traditional RAG (Retrieval Augmented Generation) retrieves documents before the model sees the query. The retrieval system decides what's relevant based on embedding similarity. This works well for simple Q&A but fails for complex agentic tasks because:

  1. The query isn't known in advance. In a loop, what the model needs at step 7 depends on what it discovered at step 6. No pre-retrieval system can predict this.
  1. Relevance is task-dependent. The same document may be crucial for one step and irrelevant for the next. Pre-loading it wastes budget on irrelevant turns.
  1. The model is a better judge of relevance. Given a goal and current state, the model can reason about what information would help. A vector-similarity search cannot.

Agentic search inverts the RAG pattern: the model decides what to search for, retrieves it on demand, and discards it when it's no longer needed.


# Traditional RAG: retrieve before reasoning
docs = retriever.search(user_query, top_k=20)  # 20K tokens pre-loaded
response = model.generate(system_prompt + docs + user_query)

# Agentic search: reason about what to retrieve
for step in loop:
    needed = model.decide_what_to_search(current_state, goal)
    docs = retriever.search(needed, top_k=3)    # 3K tokens, precisely targeted
    action = model.reason_and_act(current_state + docs + goal)
    current_state = update_state(action)

The agentic approach uses fewer tokens per step (3K vs. 20K) with higher relevance (model-directed vs. similarity-guessed). Over a 10-iteration loop, this saves 170K tokens of noise.

7.8 The Tool-Result Problem

Tools produce output. Sometimes a lot of output. A file read returns the entire file. A search returns multiple results. A command execution returns stdout and stderr. This output enters the context and stays there unless actively managed.

The tool-result problem: in a 10-iteration loop where each iteration calls 3 tools that each return 5K tokens, the accumulated tool results consume 150K tokens — three-quarters of a 200K window — most of which is irrelevant to the current iteration.

Solutions:

1. Immediate summarization: After each tool call, the harness (not the model) summarizes the result to its essential content. A 5K file read becomes a 500-token summary of the relevant portions.

2. Expiring results: Tool results from more than 2 iterations ago are automatically removed from context. If the model needs them again, it can re-call the tool.

3. Selective inclusion: The harness analyzes tool results and only includes portions relevant to the current step. A grep that returns 50 matches only shows the 5 most relevant in context.

4. External storage: Large tool results are saved to a file and only a reference is kept in context. The model can read the file if it needs the full content.


# Claude Code's approach: tool results cleared after use
class ContextManager:
    def after_tool_call(self, tool_name: str, result: str) -> str:
        if len(result) > 2000:
            summary = self.summarize(result, current_goal)
            self.store_full_result(tool_name, result)  # Accessible via read
            return summary
        return result
    
    def between_iterations(self, context: list) -> list:
        # Remove tool results older than 2 iterations
        return [msg for msg in context 
                if msg.age < 2 or msg.type != "tool_result"]

7.9 Context Engineering in Practice

A well-engineered loop manages context actively at four moments:

Before the loop starts:

  • Load skills (project knowledge, rules, constraints)
  • Set the goal and Loop Contract in the system prompt
  • Initialize the current-state document

Before each iteration:

  • Update the current-state summary with results from the last iteration
  • Prune stale tool results and old history
  • Verify the context budget isn't exceeded

After each tool call:

  • Summarize long results
  • Discard clearly irrelevant portions
  • Update the current-state if the tool revealed something important

When the context approaches capacity:

  • Trigger compaction (Chapter 8)
  • Remove the oldest history first
  • Preserve: goal, current state, last iteration's results, skills
  • Discard: old tool results, superseded plans, resolved errors

7.10 Measuring Context Quality

How do you know your context engineering is working? Three metrics:

Token efficiency: Verified outcomes per dollar spent on input tokens. If context engineering is working, this number increases over time because you're spending fewer tokens on noise.

Iteration count: Average iterations to convergence. If context engineering is working, the model needs fewer iterations because it's reasoning over better information at each step.

Context utilization: What percentage of context tokens are actively referenced in the model's reasoning? This is harder to measure but can be approximated by tracking which context elements appear in the model's output or tool-selection decisions.

The goal isn't to minimize context — it's to maximize the ratio of useful context to total context. Sometimes that means loading more (when additional context genuinely helps). Usually it means loading less (when the default accumulation creates noise).
