Chapter 9: Tool Design at Scale

Level: A (Anchor) · ~6,000 words · Levels served: L2, L3, L4, L5

9.1 Tools Are the Loop's Hands

A model without tools can only think. A model with tools can act. The quality of those tools — their design, ergonomics, error messages, and composition — determines whether the loop can effectively interact with the world or flails blindly at it.

Tool design is the most underinvested area of loop engineering. Most practitioners grab whatever tools their framework provides and move on. But the difference between well-designed tools and poorly-designed tools is the difference between a loop that converges in 3 iterations and one that thrashes for 15.

9.2 The Three Audiences for a Tool

Every tool has three audiences, and it must serve all three:

Audience 1: The Model (Primary)

The model sees the tool's name, description, parameter schema, and (eventually) its error messages. This is the model's only way to understand what the tool does, when to use it, and what went wrong.

A tool that's opaque to the model is useless regardless of how powerful it is. If the model can't figure out when to call it or what arguments to pass, the tool might as well not exist.

Audience 2: The Harness Developer

The developer implements the tool, maintains it, and debugs failures. The tool should be easy to implement correctly, easy to test, and easy to extend.

Audience 3: The Human Reviewer

A human will eventually audit the loop's behavior — reviewing what tools were called, with what arguments, and what they returned. The tool's inputs and outputs should be interpretable by a human reading a trace log.

9.3 The Tool Description Is the API

For the model, the tool description IS the documentation. There's no other source of truth. The model won't read your README. It won't look at your source code. It makes every decision about whether and how to use the tool based solely on what appears in the tool's schema.

Bad tool description:


{
  "name": "exec",
  "description": "Execute a command",
  "parameters": {
    "cmd": {"type": "string"}
  }
}

Problems: What kind of command? What environment? What are the constraints? When should this be used vs. alternatives? What's the expected output format?

Good tool description:


{
  "name": "run_tests",
  "description": "Execute the project's test suite and return results. Use after making code changes to verify they don't break existing functionality. Returns structured output with pass/fail counts and failure details. For running a single test file, pass the file path. For the full suite, omit the path parameter.",
  "parameters": {
    "test_path": {
      "type": "string",
      "description": "Path to specific test file or directory. Omit to run full suite."
    },
    "verbose": {
      "type": "boolean",
      "description": "Include full stdout/stderr for failed tests. Default false."
    }
  }
}

The good description tells the model:

  • When to use it (after making code changes)
  • Why to use it (verify changes don't break things)
  • What it returns (structured pass/fail with failure details)
  • How to use it for different needs (single file vs. full suite)

9.4 Errors as Teaching Signal

When a tool call fails, the error message is the model's only feedback about what went wrong. A good error message teaches the model how to succeed on the next attempt. A bad error message forces the model to guess.

Bad error:


Error: Command failed with exit code 1

The model learns nothing. It might retry with the same arguments. It might try a completely different approach. It's guessing.

Good error:


Error: File 'src/auth.py' not found. 
Available files matching 'auth': src/authentication.py, src/middleware/auth_handler.py, tests/test_auth.py.
Did you mean one of these?

The model learns: the file doesn't exist, here are the actual options, pick one. The next tool call will almost certainly succeed.

The error design principle:

Every error message should answer three questions:

  1. What failed? — The specific operation that didn't work
  2. Why? — The reason for the failure
  3. What to try instead? — A concrete suggestion for the next attempt

class ToolError:
    def __init__(self, what: str, why: str, suggestion: str):
        self.message = f"Error: {what}. Reason: {why}. Try: {suggestion}"

# Examples:
ToolError(
    what="Cannot write to 'config.json'",
    why="File is read-only (permissions: 444)",
    suggestion="Use 'chmod 644 config.json' first, or write to a different location"
)

ToolError(
    what="Test execution timed out after 30s",
    why="Test 'test_large_dataset' appears to have an infinite loop",
    suggestion="Check the loop condition in test_large_dataset at line 45"
)

9.5 The Tool Search Tool Pattern

A production system might have 50+ tools available. Loading all their schemas into context costs ~55K tokens upfront — a quarter of a 200K window spent before the model does any work. Most of those tools won't be used in any given loop iteration.

The Tool Search Tool pattern solves this: instead of loading all tool schemas upfront, provide a single meta-tool that lets the model search for and load tool schemas on demand.


{
  "name": "tool_search",
  "description": "Search for available tools by capability. Returns tool names and descriptions matching your query. Use this to discover what tools are available before calling them. After finding the right tool, its full schema will be loaded automatically.",
  "parameters": {
    "query": {
      "type": "string",
      "description": "Natural language description of what you want to do. E.g., 'read a file', 'run tests', 'search code for a pattern'"
    }
  }
}

The economics:

  • Without Tool Search: 58 tools × ~950 tokens/schema = ~55K tokens loaded upfront in every message
  • With Tool Search: 1 tool schema (200 tokens) + loaded schemas for tools actually used (~3-5 tools × 950 = ~4.5K tokens)
  • Savings: ~50K tokens per message × many messages per loop = massive cost reduction

This is the exact pattern Claude Code uses. With 52+ registered tools, loading all schemas would consume 25% of context. Instead, tool schemas are loaded on demand — the model asks for what it needs, and only relevant schemas enter context.

Implementing Tool Search effectively:


class ToolRegistry:
    def __init__(self):
        self.tools: dict[str, ToolDefinition] = {}
        self.embeddings: dict[str, list[float]] = {}  # For semantic search
    
    def search(self, query: str, top_k: int = 5) -> list[ToolSummary]:
        """Return brief descriptions of matching tools without full schemas."""
        matches = self.semantic_search(query, top_k)
        return [ToolSummary(name=t.name, description=t.brief) for t in matches]
    
    def load_schema(self, tool_name: str) -> ToolDefinition:
        """Load full schema for a specific tool into the active tool set."""
        return self.tools[tool_name]

9.6 Programmatic Tool Calling

In a standard agent loop, the model decides which tool to call and the harness executes it. But some operations are better orchestrated in code — the harness calls tools programmatically, keeping intermediate results out of the model's context.

When to use programmatic tool calling:

  1. Data pipeline steps: Fetch from API → transform → validate → store. The model doesn't need to see every intermediate result.
  2. Batch operations: Apply the same operation to 100 items. The model decides the operation once; code executes it 100 times.
  3. Multi-tool compositions: Read file → parse → extract section → return to model. The model sees only the final extracted section, not the full file.

# Programmatic tool calling — orchestrate in code, show model only final result
async def get_relevant_code_context(file_path: str, function_name: str) -> str:
    """Called by harness, not by model. Composes multiple tools programmatically."""
    
    # Step 1: Read the file (tool call, not shown to model)
    full_file = await tools.read_file(file_path)
    
    # Step 2: Parse to AST and find the function (code, not a tool)
    tree = ast.parse(full_file)
    func_node = find_function(tree, function_name)
    
    # Step 3: Extract the function and its dependencies (code)
    func_code = ast.get_source_segment(full_file, func_node)
    deps = find_dependencies(tree, func_node)
    
    # Step 4: Return compact, relevant context to the model
    return f"Function {function_name}:\n{func_code}\n\nDependencies:\n{deps}"

The model sees a clean, focused context instead of a raw file dump. The harness did the work of locating and extracting relevant information. The model's context budget is spent on reasoning, not parsing.

The context savings are dramatic:

Approach Tokens in context Quality
Model reads full file (3000 lines) ~12K Low (buried in noise)
Model reads file + grep for function ~8K Medium
Programmatic extraction ~1.5K High (pure signal)

9.7 Tool Use Examples

Models learn tool-use patterns from examples even more than from descriptions. A tool with three examples of correct usage will be used correctly more often than a tool with a paragraph of description but no examples.


{
  "name": "search_code",
  "description": "Search for patterns in the codebase using ripgrep syntax.",
  "examples": [
    {
      "scenario": "Find all uses of a function",
      "call": {"pattern": "authenticate_user\\(", "file_type": "py"},
      "result_summary": "Returns file:line matches"
    },
    {
      "scenario": "Find a specific error message",
      "call": {"pattern": "\"Invalid token\"", "include_context": 3},
      "result_summary": "Returns matches with 3 lines of surrounding context"
    },
    {
      "scenario": "Find TODO comments in test files",
      "call": {"pattern": "TODO|FIXME", "path": "tests/"},
      "result_summary": "Returns all TODO/FIXME comments in test directory"
    }
  ]
}

The examples show the model:

  • What scenarios the tool is appropriate for
  • How to format arguments for each scenario
  • What kind of result to expect

This is more effective than detailed documentation because models learn from patterns, not from specifications. The examples ARE the specification, in a format the model naturally processes.

9.8 Tool Ergonomics for Loops

Tools designed for single-use (a human triggers one tool call) have different requirements than tools designed for loops (an agent calls them repeatedly across iterations). Loop-optimized tools need:

9.8.1 Idempotency

A tool called twice with the same arguments should produce the same result without side effects. In a loop, the model may retry a tool call after an error, or re-execute a plan from a checkpoint. Idempotent tools are safe to retry.

9.8.2 Incremental output

A tool that returns its full output every call forces the model to diff against the previous call mentally. A tool that returns only what changed since the last call is loop-friendly.


# Loop-unfriendly: returns entire test suite output every time
def run_tests() -> str:
    return subprocess.run(["pytest"], capture_output=True).stdout

# Loop-friendly: returns only what changed
def run_tests(previous_results: dict = None) -> str:
    results = parse_test_results(subprocess.run(["pytest"], capture_output=True))
    if previous_results:
        return format_delta(previous_results, results)
    return format_results(results)

9.8.3 Composability

Tools should be small and composable rather than large and monolithic. A tool that "reads a file, finds a function, and edits it" is hard to use in different contexts. Three tools — "read file," "find function," "edit range" — compose to handle any scenario.

9.8.4 Bounded output

A tool that can return unbounded output (e.g., grep with no result limit) is dangerous in a loop context. Always cap output size, paginate results, or summarize when output exceeds a threshold.

9.9 The Cost of Tool Schemas

Every tool schema in the active set consumes context tokens on every model call. For a loop running 10 iterations, a 1K-token tool schema that's never used costs 10K tokens across the loop — roughly $0.03 at typical pricing. Multiply by 30 unused tools, and you're paying $0.90 per loop in wasted schema overhead.

This is why Tool Search matters at scale. It's also why tool sets should be dynamic — load tools relevant to the current step, unload tools that won't be needed.


class DynamicToolSet:
    def __init__(self):
        self.always_available = ["read_file", "write_file", "search_code"]
        self.loaded_on_demand = {}
    
    def for_step(self, step_type: str) -> list[str]:
        """Return the tool set appropriate for this step type."""
        if step_type == "testing":
            return self.always_available + ["run_tests", "run_single_test"]
        elif step_type == "research":
            return self.always_available + ["web_search", "web_fetch"]
        elif step_type == "deployment":
            return self.always_available + ["deploy", "rollback", "health_check"]
        return self.always_available

9.10 Tool Design Checklist

Before adding a tool to a loop, verify:

  • [ ] Name is action-verb: run_tests not tests, read_file not file_content
  • [ ] Description states when to use: Not just what it does, but when it's the right choice
  • [ ] Parameters have descriptions: Every parameter explains its purpose and constraints
  • [ ] Errors are actionable: Every error message suggests what to try next
  • [ ] Output is bounded: Maximum output size is enforced
  • [ ] Idempotent by default: Safe to call twice with same arguments
  • [ ] Examples included: At least 2-3 usage examples in the schema
  • [ ] Cost is proportional: The tool's output size is proportional to its information value

Tools that fail this checklist will work — but they'll work poorly. The model will misuse them, misinterpret their output, and waste iterations on avoidable errors. In a loop, these small inefficiencies compound into significant cost and reliability problems.
