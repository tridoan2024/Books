Chapter 4: The Harness Is the Product

Level: S (Standard) · ~4,000 words · Why scaffold quality dominates model quality

4.1 The Same Model, Wildly Different Outcomes

In March 2025, Anthropic released Claude 3.5 Sonnet. Within weeks, three different products shipped it as their backbone:

  • Product A wrapped Sonnet in a simple chat interface with file reading. Users reported ~40% task completion on SWE-bench-style problems.
  • Product B built a loop: read → plan → edit → test → fix. Same model. Same problems. Task completion jumped to ~65%.
  • Product C added skills (project context loaded on demand), worktrees (parallel editing without conflict), and a maker-checker split. Same model. Task completion hit ~78%.

The model didn't change. The weights were identical. What changed was the harness — the code that wraps the model, manages its context, selects its tools, verifies its output, and decides what happens next.

This isn't a hypothetical. It's the documented history of SWE-bench, where identical base models score dramatically differently depending on the scaffold:

System Base Model SWE-bench Score Key Harness Feature
Raw prompt Claude 3.5 Sonnet 19% None — single pass
Agentless Claude 3.5 Sonnet 27% Localization + patch generation
SWE-agent Claude 3.5 Sonnet 33% Interactive shell + error feedback
Devin Claude 3.5 Sonnet* 42% Full loop + test + plan + retry
Claude Code Claude 3.5 Sonnet 49% Loop + skills + tools + memory

(*Devin's exact model mix is proprietary; the point is the harness delta, not the specific model.)

The spread from 19% to 49% — a 2.5x improvement — comes entirely from the harness. No model upgrade provides that kind of lift. This is the central insight of this chapter: if you're choosing between investing in a better model and investing in a better harness, invest in the harness. The returns are larger and more predictable.

4.2 What a Harness Owes the Model

A model inside a harness is like an employee inside an organization. The employee brings skill and judgment. The organization provides structure, tools, information, and feedback. A brilliant employee in a dysfunctional organization produces mediocre work. A competent employee in a well-run organization produces excellent work.

Here's what the harness owes the model:

4.2.1 The Right Context at the Right Time

The model can only reason about what's in its context window. A harness that dumps an entire codebase into context overwhelms the model with noise. A harness that provides too little context forces the model to guess. The optimal harness provides:

  • Relevant context: only what matters for the current step
  • Structured context: organized so the model can parse it quickly
  • Fresh context: updated as the loop progresses, not stale from the start
  • Sized context: within the model's effective attention range

The "smallest high-signal set" principle (Chapter 7) governs this. Every token in context should earn its place. If removing it would degrade performance, it stays. If removing it wouldn't matter, it's noise.

4.2.2 Clear Affordances

The model needs to know what it can do. A harness with thirty tools but no description of when to use each one produces a model that flails between tools randomly. A harness with clear, well-documented affordances produces a model that selects the right tool for each situation.

Good tool affordances include:

  • A name that describes the action (not tool_7, but run_tests)
  • A description that states when to use it (not "executes code", but "run the test suite to verify your changes compile and pass")
  • Parameters with types and constraints
  • Error messages that guide recovery

4.2.3 Actionable Feedback

When the model's output is wrong, the harness must tell it why in terms the model can act on. "Test failed" is feedback. "Test test_auth_expired_token failed: expected status 401, got 200. The response body indicates the token expiry check is not being reached — see auth.py:42" is actionable feedback.

The quality of feedback determines convergence speed. Vague feedback → random walk → slow convergence → high cost. Precise feedback → targeted fix → fast convergence → low cost.

4.2.4 Protection from Irreversible Mistakes

The model will, inevitably, attempt actions that shouldn't be taken. Delete production data. Force-push to main. Send an email to a customer. The harness must prevent these actions, not rely on the model to avoid them.

Protection mechanisms:

  • Permission scoping: The model literally cannot call tools that would cause irreversible harm
  • Approval gates: Destructive actions require human confirmation
  • Sandboxing: Execution happens in an isolated environment where mistakes can't propagate
  • Dry-run mode: The model can see what an action would do without actually doing it

4.3 The Harness Quality Hierarchy

Not all harnesses are created equal. Here's a hierarchy from worst to best, with the marginal improvement at each level:

Level 1: Prompt + Model (Baseline)

The model receives a prompt and responds. No tools, no iteration, no verification. This is the floor.

Level 2: Prompt + Tools

The model can call tools (read files, search, execute code). It responds to a single prompt, using tools as needed, and produces one output. The human evaluates.

Marginal improvement over Level 1: the model can ground its responses in real data rather than relying on training knowledge.

Level 3: Prompt + Tools + Error Recovery

When a tool call fails or produces unexpected results, the harness feeds the error back and lets the model retry. This is a minimal loop — one iteration of execute → verify → iterate.

Marginal improvement over Level 2: the model can recover from tool-use errors without human intervention.

Level 4: Prompt + Tools + Iteration Loop

The harness implements a full loop: the model plans, executes, verifies against criteria, and iterates until criteria are met or budget is exhausted.

Marginal improvement over Level 3: the model can achieve complex goals that require multiple steps and self-correction.

Level 5: Prompt + Tools + Iteration + Skills + Memory

The harness loads project-specific knowledge (skills) so the model starts warm. It records what worked and what didn't (memory) so future runs benefit from past experience.

Marginal improvement over Level 4: the model doesn't repeat past mistakes and doesn't spend budget rediscovering context.

Level 6: Full Harness (Iteration + Skills + Memory + Subagents + Automation)

The harness orchestrates multiple models, each with its own tools and scope. It runs automatically on triggers. It learns and evolves across runs.

Marginal improvement over Level 5: the system handles problems too complex for a single context, parallelizes work, and provides independent verification.

4.4 Model Choice Is a Harness Decision

The conventional wisdom is to pick the "best" model and build around it. Loop engineering inverts this: the harness determines which model is cost-effective at which step.

Consider a fleet loop for code review:

Step Task Model Needed Why
Discovery Read files, find relevant code Haiku Simple retrieval, doesn't need reasoning
Planning Identify what to review, in what order Sonnet Moderate reasoning about priority
Review Find bugs, security issues, logic errors Opus Deep reasoning, catches subtle issues
Verification Check if the review findings are real Sonnet Confirm/deny claims against code
Summarization Write the final report Haiku Formatting, no reasoning needed

A naive approach uses Opus for everything — expensive. A smart harness cascades: cheap models for cheap steps, expensive models only where they provide unique value. The harness makes the model choice, dynamically, per step.

This is why "which model should I use?" is the wrong question. The right question is: "what does each step of my loop actually require, and what's the cheapest model that provides it?"

4.5 The Scaffold Advantage Is Compounding

Better prompts produce a linear improvement: each prompt improvement helps one task by a fixed amount. Better harnesses produce a compounding improvement: each harness improvement helps every subsequent run of every loop that uses it.

Consider these harness improvements and their compound effect:

  • Add test-running to the loop → every code task now self-verifies (saves ~30% of human review time per task)
  • Add skills → every run starts warm (saves ~15% of tokens per run)
  • Add memory → recurring patterns get handled automatically (saves ~10% of iteration cycles)
  • Add maker-checker split → quality issues caught before shipping (reduces post-ship bugs by ~40%)

Individually, each is modest. Together, over hundreds of runs, they transform the system from "AI assistant that helps a little" to "autonomous system that ships verified work."

4.6 Why Teams Underinvest in the Harness

Despite the evidence, most teams spend 90% of their effort on prompts and 10% on the harness. Three reasons:

1. Prompts are immediately gratifying. You change a prompt, rerun, and see the result in seconds. Harness improvements require building infrastructure, and the payoff only shows up over many runs.

2. Prompts feel like "AI work." Harnesses feel like "plumbing." Engineers want to work on the interesting part (the AI) and neglect the mundane part (the scaffold). But the mundane part is where the value compounds.

3. Model providers incentivize prompt thinking. The industry's marketing focuses on model capabilities, not scaffold capabilities. "Try our new model — it's smarter!" is a simpler sales pitch than "build a better loop around our model."

The antidote is measurement. Track your loops' cost-per-verified-outcome over time. When you invest in the harness, that number goes down reliably. When you invest in prompts, it goes down sporadically. The data makes the case.

4.7 What the Harness Is Not

The harness is not:

  • A framework. Frameworks (LangChain, CrewAI, AutoGen) provide primitives for building harnesses. The harness is your specific implementation for your specific loops. The framework is the toolbox. The harness is the house.
  • A prompt library. Prompts are components of the harness. The harness includes prompts, but also tools, verification logic, state management, error recovery, and orchestration.
  • The model itself. The harness wraps the model. The model is replaceable. If you switch from Sonnet to Opus (or vice versa), the harness should still work — it just works differently because the model's capabilities changed.
  • Deterministic automation. A traditional automation (CI/CD pipeline, cron job, ETL pipeline) follows a fixed path. A harness adapts: the model's reasoning determines the path through the harness, within the constraints the harness defines.

The harness is the environment in which the model operates. It provides structure, resources, feedback, and boundaries. The model provides reasoning, creativity, and judgment within those boundaries. The quality of the outcome is a product of both — but the harness has more variance and more upside.

4.8 Building Your Harness Incrementally

You don't build a Level 6 harness on day one. You build incrementally, adding capability as you encounter limitations:

Week 1: Basic loop — model + tools + run-tests-on-output. This alone gives you 80% of the value.

Week 2: Add skills — load project context so the model stops asking "what testing framework do you use?" every run.

Week 3: Add memory — record what worked and what didn't across runs so the model stops repeating the same mistakes.

Week 4: Add maker-checker — a separate verification agent that evaluates the main agent's output with fresh context.

Month 2: Add automation — trigger loops on events (PR opened, ticket moved, schedule) so humans don't have to remember to start them.

Month 3: Add fleet orchestration — multiple specialists, coordinated by a lead, for tasks too complex for a single agent.

Each step is independently valuable. Each step builds on the previous one. The harness grows with your confidence and your understanding of where the bottlenecks are.

4.9 The Meta-Insight

The harness is the product because the harness is what you ship. Users don't interact with the model — they interact with the system. The system's reliability, speed, cost, and correctness are all harness properties, not model properties.

When a user says "this AI is good," they mean the harness is good. When they say "this AI is unreliable," they mean the harness doesn't verify output adequately. When they say "this AI is too expensive," they mean the harness doesn't control cost effectively.

Model capability is necessary but not sufficient. Harness quality is what transforms model capability into user value. This is why the rest of this book focuses on harness engineering — the specific techniques for building loops that verify, iterate, and ship without human gates.
