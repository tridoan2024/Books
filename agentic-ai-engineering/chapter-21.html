Chapter 21: Maker-Checker — The Grader Must Not Share the Maker's Context

Level: A (Anchor) · ~5,800 words · Levels served: L3, L4, L5

21.1 The Generous Self-Reviewer

Ask a model to write code, then ask the same model in the same context to review that code. What happens? It approves. Almost always. The model that produced the output understands the intent behind it — it fills in gaps with what it meant to write rather than what it actually wrote. It evaluates the idea, not the implementation.

This is the generous self-reviewer problem. It exists because:

  1. Shared context contains the reasoning. The model's planning, the failed attempts, the design decisions — all live in the context window. When reviewing, the model reads its own thought process alongside the output. It judges the thought, not the artifact.
  1. Sycophantic agreement. Models have a documented tendency to agree with content they've generated. The output is "their work" in the conversational frame, and they're biased toward approving their own work.
  1. Intent-completion. If the output has a subtle gap — a missing edge case, an ambiguous variable name — the model "sees" the correct interpretation because it remembers what it intended. A fresh reviewer without that context would flag the ambiguity.

The data is clear: self-review catches 30-50% fewer real issues than independent review. Anthropic's internal testing shows that separating maker and checker contexts improves task success by roughly 10 percentage points.

21.2 The Context Isolation Principle

The fix is architectural: the checker must operate in a separate context from the maker. It sees only the output and the evaluation criteria. It does NOT see:

  • The maker's reasoning or planning
  • Previous failed attempts
  • The conversation history that led to the output
  • The maker's intent or goals beyond what the spec states

# WRONG: Self-review in shared context
maker_messages = [
    {"role": "user", "content": "Write a function that validates email addresses"},
    {"role": "assistant", "content": "I'll use a regex approach because... [reasoning]"},
    {"role": "assistant", "content": "[generated code]"},
    {"role": "user", "content": "Now review your code for correctness"},
    # The model sees its own reasoning. It will approve.
]

# RIGHT: Independent checker with isolated context
checker_messages = [
    {"role": "user", "content": """Review this code for correctness.
    
    Specification: The function should validate email addresses according to RFC 5322.
    It should return True for valid emails and False for invalid ones.
    
    Code to review:
    ```python
    [generated code — NO reasoning, NO history, just the artifact]
    ```
    
    Check specifically:
    1. Does it handle edge cases (empty string, None, Unicode)?
    2. Does the regex match RFC 5322?
    3. Are there inputs that would pass but shouldn't?
    """}
]

21.3 Designing the Checker Agent

A well-designed checker agent has:

Skeptical framing

The checker is prompted to find problems, not to confirm quality. Its default assumption should be that the output has issues — its job is to identify them.


You are a code reviewer. Your job is to find bugs, security issues, 
and correctness problems. Assume the code has at least one issue.
If you cannot find any issues, you must explain why you believe 
the code is correct despite your inability to find problems.
Default to flagging uncertain cases rather than approving them.

Structured evaluation

The checker evaluates against specific criteria, not a general "is this good?" question. Structured evaluation prevents the model from glossing over dimensions.


checker_schema = {
    "type": "object",
    "required": ["criteria_evaluation", "overall_verdict"],
    "properties": {
        "criteria_evaluation": {
            "type": "array",
            "items": {
                "type": "object",
                "required": ["criterion", "passed", "evidence"],
                "properties": {
                    "criterion": {"type": "string"},
                    "passed": {"type": "boolean"},
                    "evidence": {"type": "string"},
                }
            }
        },
        "overall_verdict": {"enum": ["PASS", "FAIL", "NEEDS_REVISION"]},
        "issues_found": {"type": "array", "items": {"type": "string"}},
    }
}

Access to ground truth

The checker should be able to verify claims by accessing the actual codebase, documentation, or specifications — not just evaluating the output in isolation.


checker_tools = [
    "read_file",        # Verify code references exist
    "run_tests",        # Verify claimed behavior
    "search_code",      # Check consistency with rest of codebase
    "check_types",      # Verify type correctness
]
# Note: checker does NOT have write_file or edit_file
# It can verify but not modify

21.4 The Outcomes Pattern

Anthropic's "Outcomes" system demonstrates the power of maker-checker separation at scale. The architecture:

  1. Maker agent produces output toward a goal
  2. Grader agent evaluates the output against a rubric (separate context)
  3. If grading fails: The grading feedback is sent back to the maker for revision
  4. Iterate until the grader approves or budget exhausts

The measured improvement: +10 percentage points on task success compared to self-evaluation loops. This is a significant lift from a purely architectural change — same model, same prompts, same tools. The difference is context isolation.


async def outcomes_loop(goal: str, rubric: Rubric, budget: Budget) -> Result:
    maker_context = [{"role": "user", "content": f"Achieve this goal: {goal}"}]
    
    for iteration in range(budget.max_iterations):
        # Maker produces output
        output = await maker_model.generate(maker_context)
        
        # Grader evaluates in SEPARATE context
        grader_context = [{"role": "user", "content": f"""
            Evaluate this output against the rubric.
            
            Goal: {goal}
            Rubric: {rubric.to_text()}
            Output: {output}
            
            Score each dimension. If any dimension scores below threshold,
            provide specific feedback for improvement.
        """}]
        
        grade = await grader_model.generate(grader_context, schema=GradeSchema)
        
        if grade.passes_threshold(rubric.min_score):
            return Result(success=True, output=output)
        
        # Feed grading feedback to maker (NOT the grader's full context)
        maker_context.append({"role": "user", "content": f"""
            Your output was evaluated and scored {grade.score}/{rubric.max_score}.
            Issues found: {grade.feedback}
            Please revise to address these issues.
        """})
    
    return Result(success=False, best_output=output, best_score=grade.score)

21.5 Model Diversity for Checking

Using the same model as both maker and checker reduces (but doesn't eliminate) the benefit of context isolation. The models share training data, biases, and blind spots. If Claude misses a bug when writing, Claude might also miss it when reviewing — even in a separate context.

Diversity strategies:

1. Same model, different temperature/prompt:

Minimal diversity. The checker uses a more skeptical prompt and lower temperature. Cheapest option, provides some independence.

2. Same model family, different size:

Moderate diversity. Use Opus for checking and Sonnet for making (or vice versa). Different capability profiles may catch different issues.

3. Different model families:

Maximum diversity. If Claude writes, GPT-4 checks (or vice versa). Different training data, different biases, genuinely independent perspectives.

4. Multiple checkers (panel):

Highest confidence. Three independent checkers vote. Majority rules. An issue flagged by 2/3 checkers is almost certainly real; an issue flagged by 1/3 may be a false positive.


async def panel_check(output: str, criteria: str, panel_size: int = 3) -> PanelResult:
    checks = await asyncio.gather(*[
        independent_checker(output, criteria, model=model)
        for model in select_diverse_models(panel_size)
    ])
    
    # Majority vote on each issue
    all_issues = collect_issues(checks)
    confirmed = [issue for issue in all_issues if issue.votes >= panel_size // 2 + 1]
    
    return PanelResult(
        passed=len(confirmed) == 0,
        confirmed_issues=confirmed,
        unanimous_issues=[i for i in confirmed if i.votes == panel_size],
    )

21.6 Adversarial Checking

Beyond neutral evaluation, adversarial checkers are prompted specifically to REFUTE the output. Their goal isn't balanced assessment — it's finding fault.


Your task is to REFUTE this claim/code/output. 
Assume it is wrong and search for the proof.
If after thorough investigation you cannot refute it,
state what you checked and why you believe it survives scrutiny.

If you find it IS wrong, explain exactly what's wrong and provide evidence.
Default to "refuted" if uncertain — it is better to flag a potential issue 
than to miss a real one.

Adversarial checking has higher false-positive rates but dramatically lower false-negative rates. It catches subtle issues that neutral evaluation misses — at the cost of sometimes flagging things that are actually fine.

When to use adversarial vs. neutral checking:

Context Checker Style Reasoning
Low stakes, high volume Neutral False positives waste budget on unnecessary retries
High stakes, low volume Adversarial False negatives are more expensive than false positives
Security review Adversarial Missing a vulnerability > flagging a non-issue
Code correctness Neutral Most code is correct; focus on finding real bugs
Research claims Adversarial Hallucinated claims are common and harmful

21.7 Self-Correction Through Checking Feedback

The checker doesn't just verdict pass/fail — it provides specific feedback that guides the maker's next attempt. The quality of this feedback determines convergence speed:

Feedback that enables convergence:


FAIL: The function doesn't handle the case where input is None.
Line 12: `if len(input) > 0` will throw TypeError when input is None.
Suggestion: Add `if input is None: return []` before line 12.

Feedback that doesn't help:


FAIL: The function has a bug.

The maker receives the checker's feedback (not the checker's full context or reasoning) and revises accordingly. This creates a productive feedback loop:


Maker produces → Checker evaluates → Feedback → Maker revises → Checker re-evaluates → ...

Each cycle should narrow the gap between output and goal. If the gap isn't narrowing across cycles (same issues re-flagged, or new issues appearing as fast as old ones are fixed), the loop should stop — the approach is wrong, not just the execution.

21.8 The Cost of Checking

Every check costs tokens. For a model judge, that's typically 500-2000 output tokens per evaluation. In a 5-iteration loop, that's 2,500-10,000 tokens just for checking — roughly 10-20% of total loop cost.

Reducing check cost:

1. Tiered checking: Run cheap checks first (deterministic), expensive checks only if cheap ones pass.

2. Focused checking: Don't re-evaluate the entire output on each iteration. Only check the dimensions that previously failed.

3. Threshold checking: If the output barely fails (score 7.8/8.0), provide focused feedback on the gap. If it badly fails (score 3/8), provide broad feedback.

4. Skip checking on final iteration: If budget is exhausted, take the best result seen rather than spending remaining budget on one more evaluation that can't lead to improvement.

21.9 When Self-Review Is Acceptable

Context isolation isn't always necessary. Self-review is acceptable when:

  • The oracle is deterministic: Running tests doesn't require context isolation. The tests pass or fail regardless of who runs them.
  • The check is mechanical: Type checking, linting, schema validation — these don't benefit from independence.
  • The task is simple enough that the generous-reviewer bias doesn't matter (single-step tasks with clear success criteria).

The maker-checker separation is specifically for judgment-based evaluation: is this code correct? Is this explanation clear? Is this review thorough? These questions require independent assessment. Mechanical questions (does it compile? does it match the schema?) do not.

21.10 Implementation Patterns

The subagent pattern:


# Maker runs as the main agent
# Checker spawns as a subagent with isolated context
async def make_and_check(goal: str) -> str:
    output = await maker_agent.produce(goal)
    
    check = await spawn_subagent(
        prompt=f"Evaluate this against: {goal}\n\nOutput: {output}",
        tools=["read_file", "run_tests"],  # Read-only tools
        model="claude-opus-4-6",
    )
    
    if check.verdict == "PASS":
        return output
    else:
        return await maker_agent.revise(output, check.feedback)

The dual-model pattern:


# Two model instances, never sharing context
maker = ModelClient(model="claude-sonnet-4-6", system="You are a code writer...")
checker = ModelClient(model="claude-opus-4-6", system="You are a skeptical reviewer...")

# They communicate only through artifacts (the output) and structured feedback

The fresh-context pattern:


# Same model, but checker gets a completely fresh conversation
maker_output = await model.generate(full_conversation_history)

# New conversation for checker — no history from the maker
checker_result = await model.generate([
    {"role": "user", "content": f"Review this: {maker_output}\nCriteria: {criteria}"}
])
