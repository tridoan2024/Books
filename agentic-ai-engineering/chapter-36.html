Chapter 36: Case Study — The Operations Loop

Level: S (Standard) · ~4,000 words · Levels served: L3, L4, L5

36.1 Operations Loops Are Different

Coding loops modify files. Research loops produce documents. Operations loops change the state of running systems. This makes them the highest-stakes category: a bug in a coding loop produces bad code that tests catch; a bug in an operations loop can take down production, leak data, or lock out legitimate users.

The risk profile inverts the usual agentic assumption. In coding, we default to "try it and verify." In operations, we default to "verify first, then try — and have a rollback plan." The oracle doesn't just check whether the action succeeded; it must confirm that the action didn't cause collateral damage.

This chapter covers three operations loops — security triage, support resolution, and browser automation — that collectively demonstrate the full range of operational challenges. They share a common structure: detect a condition, assess its severity, determine the correct action, execute with safety bounds, and verify the system reached the desired state without side effects.

36.2 The Security Triage Loop

A new vulnerability is reported. The clock starts. The security triage loop must: assess impact, identify affected systems, produce a remediation plan, and optionally begin automated remediation — all before a human finishes reading the advisory.

36.2.1 The Loop Structure


graph TD
    A[Vulnerability Report Ingested] --> B[Parse & Classify]
    B --> C[Identify Affected Systems]
    C --> D[Assess Impact]
    D --> E{Severity?}
    E -->|Critical/High| F[Produce Remediation Plan]
    E -->|Medium/Low| G[Queue for Next Sprint]
    F --> H[Verify Plan Feasibility]
    H -->|Plan is executable| I[Execute or Escalate]
    H -->|Plan has gaps| C
    I --> J[Verify Remediation]
    J -->|System patched| K[Close & Document]
    J -->|Verification failed| F

The loop has two distinct phases: assessment (B through E) is safe — it reads state without changing it. Remediation (F through J) is dangerous — it modifies running systems. The escalation boundary sits between D and F: assessment is always autonomous; remediation may require human approval depending on blast radius.

36.2.2 Stage 1: Parse and Classify

The loop ingests vulnerability reports from multiple sources — CVE feeds, vendor advisories (Microsoft Patch Tuesday, GitHub Security Advisories), internal security scanners (Snyk, Dependabot, Trivy), bug bounty submissions. Each source has a different format, urgency level, and signal quality:


from dataclasses import dataclass
from enum import Enum


class VulnSource(Enum):
    CVE_FEED = "cve_feed"           # Structured, delayed, comprehensive
    VENDOR_ADVISORY = "vendor"       # Structured, timely, authoritative
    SCANNER = "scanner"              # Automated, may have false positives
    BUG_BOUNTY = "bug_bounty"        # Unstructured, immediate, may be duplicates
    INTERNAL_AUDIT = "internal"      # High-confidence, specific to our systems


@dataclass
class NormalizedVulnerability:
    cve_id: str | None
    title: str
    description: str
    cvss_score: float | None
    cvss_vector: str | None
    affected_packages: list[str]
    affected_versions: list[str]
    fix_available: bool
    fix_version: str | None
    exploit_available: bool
    exploit_in_wild: bool
    source: VulnSource
    raw_report: str
    ingested_at: str


async def parse_vulnerability(raw_input: str, source: VulnSource) -> NormalizedVulnerability:
    """Normalize vulnerability reports from any source into structured format."""
    extraction_prompt = f"""
    Extract structured vulnerability data from this {source.value} report.
    If a field is not present in the report, use None — do not hallucinate values.
    
    {raw_input}
    
    Extract: CVE ID, title, description, CVSS score and vector, 
    affected packages with version ranges, whether a fix exists and its version,
    whether exploits exist publicly or are being actively used in the wild.
    """
    parsed = await model.generate(
        extraction_prompt, 
        response_format=NormalizedVulnerability,
    )
    return parsed

The parser must handle ambiguity without hallucinating. A bug bounty report that says "I found an XSS in your login page" doesn't have a CVE ID, a CVSS score, or a clear affected package. The parser should extract what's there and leave the rest as None — filling in "probably CVSS 6.1" is a judgment call that belongs in the assessment stage, not the parsing stage.

36.2.3 Stage 2: Identify Affected Systems

This is where the loop earns its value. A human triaging manually must check each system's dependency manifest against the affected package and version range — a process that takes 30-60 minutes for a moderate-sized organization. The loop does it in seconds by querying the asset inventory:


@dataclass
class AffectedSystem:
    system_name: str
    system_id: str
    dependency_name: str
    dependency_version: str
    dependency_depth: str  # "direct" or "transitive"
    internet_facing: bool
    handles_pii: bool
    environment: str  # "production", "staging", "development"


async def find_affected_systems(
    vuln: NormalizedVulnerability,
    inventory: AssetInventory,
) -> list[AffectedSystem]:
    """Cross-reference vulnerability against infrastructure inventory."""
    affected = []
    
    for system in await inventory.list_production_systems():
        # Check direct dependencies (highest risk)
        deps = await inventory.get_dependencies(system.id, depth="direct")
        for dep in deps:
            if dep.name in vuln.affected_packages:
                if version_in_range(dep.version, vuln.affected_versions):
                    affected.append(AffectedSystem(
                        system_name=system.name,
                        system_id=system.id,
                        dependency_name=dep.name,
                        dependency_version=dep.version,
                        dependency_depth="direct",
                        internet_facing=system.is_public,
                        handles_pii=system.data_classification == "pii",
                        environment=system.environment,
                    ))
        
        # Check transitive dependencies (lower risk, higher volume)
        transitive = await inventory.get_dependencies(system.id, depth="transitive")
        for dep in transitive:
            if dep.name in vuln.affected_packages:
                if version_in_range(dep.version, vuln.affected_versions):
                    affected.append(AffectedSystem(
                        system_name=system.name,
                        system_id=system.id,
                        dependency_name=dep.name,
                        dependency_version=dep.version,
                        dependency_depth="transitive",
                        internet_facing=system.is_public,
                        handles_pii=system.data_classification == "pii",
                        environment=system.environment,
                    ))
    
    # Sort by risk: internet-facing + PII first
    affected.sort(
        key=lambda a: (not a.internet_facing, not a.handles_pii, a.dependency_depth != "direct"),
    )
    return affected

36.2.4 Stage 3: Assess Impact

Impact assessment combines the vulnerability severity with the exposure of affected systems. This produces an actionable severity that accounts for context — a Critical CVE in a development-only tool is less urgent than a High CVE in an internet-facing production service processing PII:

CVSS Score Internet-Facing Direct Dep Handles PII Effective Impact
9.0+ Yes Yes Yes CRITICAL — immediate, all hands
9.0+ Yes Yes No CRITICAL — immediate
9.0+ No Yes Yes HIGH — 24h SLA
7.0-8.9 Yes Yes Any HIGH — 24h SLA
7.0-8.9 No Yes No MEDIUM — sprint queue
5.0-6.9 Any Any No LOW — backlog
Any Any Transitive No Reduce by one level

36.2.5 The Oracle: Verification of Remediation

The security loop's oracle is a scanner re-run. After remediation is applied (package upgrade, configuration change, WAF rule), the loop runs the same scanner that detected the vulnerability — or a targeted check that specifically tests for the vulnerable condition:


async def verify_remediation(
    system: AffectedSystem,
    vuln: NormalizedVulnerability,
    action_taken: str,
) -> tuple[bool, str]:
    """Re-scan after remediation to confirm vulnerability is resolved."""
    # First: verify the dependency version actually changed
    current_deps = await inventory.get_dependencies(system.system_id, depth="direct")
    target_dep = next(
        (d for d in current_deps if d.name == system.dependency_name), 
        None,
    )
    
    if target_dep is None:
        return True, "Dependency removed entirely"
    
    if version_in_range(target_dep.version, vuln.affected_versions):
        return False, f"Dependency still at vulnerable version {target_dep.version}"
    
    # Second: run targeted vulnerability scan
    scan_result = await scanner.targeted_scan(
        target=system.system_id,
        checks=[vuln.cve_id] if vuln.cve_id else [vuln.title],
    )
    
    if scan_result.findings:
        return False, f"Scanner still reports vulnerability: {scan_result.findings[0]}"
    
    return True, f"Verified: {system.dependency_name} upgraded to {target_dep.version}"

If verification fails, the loop cycles back to remediation planning. Perhaps the upgrade broke something and was automatically rolled back by the deployment pipeline, or the fix version doesn't actually resolve the issue (rare but it happens with incomplete patches).

36.3 The Support Resolution Loop

Customer support is a different operational domain: the "system" being fixed is a human's experience, and the primary oracle is harder to define. You can check whether a technical issue is resolved (API returns 200 again), but you can't algorithmically verify customer satisfaction.

36.3.1 The Escalation Design

The critical design choice in a support loop is where autonomous resolution ends and human involvement begins. This boundary must be conservative — the cost of a bad autonomous response (frustrated customer, escalated complaint, lost trust) far exceeds the cost of involving a human unnecessarily.


AUTONOMOUS_RESOLUTION = [
    "known_bug_workaround",      # Issue is documented, workaround exists
    "configuration_help",         # User needs help with settings
    "feature_explanation",        # User doesn't understand how something works
    "billing_simple",            # Balance inquiry, receipt request
    "password_reset",            # Standard self-service flow
]

HUMAN_REQUIRED = [
    "data_loss_reported",        # Never autonomous — too risky
    "security_breach",           # Legal/compliance implications
    "billing_dispute",           # Financial decisions need human judgment
    "emotional_distress",        # Empathy-first response needed
    "unknown_bug",              # Novel issue, no playbook
    "legal_compliance",          # Regulatory requirements
    "enterprise_critical",       # High-value customer, SLA at risk
]

DIAGNOSE_FIRST = [
    "performance_complaint",     # Might be their config, might be our bug
    "integration_failure",       # Could be their side, could be ours
    "intermittent_error",        # Need to reproduce before deciding
]

36.3.2 The Diagnosis Phase

For tickets in the DIAGNOSE_FIRST category, the loop investigates before deciding whether to resolve autonomously or escalate:


@dataclass
class Diagnosis:
    root_cause: str
    confidence: float
    evidence: list[str]
    resolution_path: str  # "autonomous", "escalate_l2", "escalate_engineering"
    suggested_response: str | None


async def diagnose_issue(ticket: SupportTicket) -> Diagnosis:
    """Investigate the customer's issue using all available data."""
    # Search knowledge base for matching symptoms
    kb_matches = await knowledge_base.search(
        query=ticket.customer_message,
        filters={"product": ticket.product_area},
        limit=5,
    )
    
    # Check system health for this customer
    health = await monitoring.get_customer_health(
        customer_id=ticket.customer_id,
        window_minutes=60,
    )
    
    # Check for active incidents affecting this product area
    incidents = await incident_tracker.active(product_area=ticket.product_area)
    
    # Check recent changes that might have caused regression
    recent_deploys = await changelog.recent(
        product=ticket.product_area,
        hours=24,
    )
    
    # Synthesize diagnosis
    diagnosis = await model.generate(f"""
    Customer reported issue: {ticket.customer_message}
    
    Knowledge base matches: {format_kb_matches(kb_matches)}
    Customer system health: {health.summary}
    Active incidents: {[i.title for i in incidents]}
    Recent deployments: {[d.summary for d in recent_deploys]}
    
    Diagnose the root cause. Determine whether this can be resolved autonomously
    (known issue with documented fix) or requires escalation (unknown issue,
    requires engineering investigation, or customer needs human attention).
    
    Be conservative: if confidence in diagnosis is below 0.7, escalate.
    """,
    response_format=Diagnosis)
    
    return diagnosis

36.3.3 The Resolution Oracle

The support loop has a two-phase oracle. First, a technical check (did the underlying issue resolve?). Second, a quality check (is the response actually helpful?).


async def verify_resolution(ticket: SupportTicket, response: str) -> tuple[bool, str]:
    """Verify both technical resolution and response quality."""
    
    # Phase 1: Technical verification (if applicable)
    if ticket.has_technical_indicator:
        system_ok = await monitoring.check_health(
            customer_id=ticket.customer_id,
            check=ticket.technical_indicator,
        )
        if not system_ok:
            return False, "Technical issue persists despite response"
    
    # Phase 2: Response quality (model judge)
    quality = await model.judge(f"""
    Customer message: {ticket.customer_message}
    Proposed response: {response}
    
    Evaluate:
    1. Does the response directly address the customer's issue? (not generic)
    2. Is the information accurate based on our documentation?
    3. Is the tone appropriate (professional, empathetic if needed)?
    4. Does it include clear next steps for the customer?
    5. Would a senior support engineer approve this response?
    
    Score 0.0-1.0 with reasoning.
    """)
    
    if quality.score < 0.80:
        return False, f"Response quality {quality.score}: {quality.reasoning}"
    
    return True, "Technical issue resolved and response quality acceptable"

The honest engineering truth: support loops have weaker oracles than coding loops. A model judging its own response quality is inherently circular (as discussed in Chapter 20 on model judges). The mitigation is conservative thresholds and a short leash — if there's any doubt, escalate to a human. The cost of bothering a human support agent ($2-5 per ticket) is lower than the cost of a bad autonomous response that generates a complaint ($50-500 in customer lifetime value impact).

36.4 The Browser Automation Loop

Some systems have no API. The only interface is a web UI — an internal admin panel built in 2015, a third-party SaaS tool, a government portal, a legacy application that nobody wants to add API endpoints to. For these, the operations loop must drive a browser.

36.4.1 The Browser as a Tool Interface

Browser automation (via Playwright, Puppeteer, or similar frameworks) gives the loop a set of primitives that mirror how a human interacts with a web page:


from dataclasses import dataclass


@dataclass
class PageState:
    url: str
    title: str
    html_content: str
    visible_text: str
    interactive_elements: list[dict]  # buttons, inputs, links with their selectors


class BrowserTools:
    async def navigate(self, url: str) -> PageState: ...
    async def click(self, selector: str) -> PageState: ...
    async def fill(self, selector: str, value: str) -> PageState: ...
    async def select_option(self, selector: str, value: str) -> PageState: ...
    async def screenshot(self) -> bytes: ...
    async def get_text(self, selector: str) -> str: ...
    async def wait_for(self, selector: str, timeout_ms: int = 5000) -> bool: ...
    async def get_page_content(self) -> str: ...
    async def wait_for_network_idle(self, timeout_ms: int = 3000) -> None: ...

The model receives page state (a structured representation of the DOM, or a screenshot for visually-complex pages) and emits browser actions. This is the same read-plan-act-verify pattern from coding loops, but the "file" being edited is a web page and the "test" is a DOM or visual assertion.

36.4.2 The Login-Navigate-Extract-Act-Verify Pattern

Nearly every browser automation loop follows a five-step pattern. This pattern is so consistent that it serves as a template:


async def browser_operation(
    task: str,
    target_url: str,
    credentials: dict,
    success_criteria: str,
    max_retries: int = 2,
) -> dict:
    """Execute a browser-based operation with the standard 5-phase pattern."""
    browser = await launch_browser(headless=True)
    
    try:
        # Phase 1: Authenticate
        await browser.navigate(f"{target_url}/login")
        await browser.fill("[name='username']", credentials["username"])
        await browser.fill("[name='password']", credentials["password"])
        await browser.click("[type='submit']")
        await browser.wait_for(".authenticated-indicator", timeout_ms=10000)
        
        # Phase 2: Navigate to target
        page_state = await browser.get_page_content()
        nav_steps = await model.plan_navigation(task, page_state)
        for step in nav_steps:
            await execute_browser_action(browser, step)
            await browser.wait_for_network_idle()
        
        # Phase 3: Extract current state
        current_state = await browser.get_page_content()
        extracted_data = await model.extract_relevant_info(task, current_state)
        
        # Phase 4: Execute the action
        action_plan = await model.plan_action(task, current_state, extracted_data)
        for action in action_plan:
            await execute_browser_action(browser, action)
            await browser.wait_for_network_idle()
        
        # Phase 5: Verify success
        final_state = await browser.get_page_content()
        verification = await verify_browser_action(
            browser, final_state, success_criteria,
        )
        
        if not verification.passed:
            # Retry: maybe a timing issue or state changed
            return await retry_from_phase(browser, task, verification.failure_point)
        
        return {"success": True, "data": extracted_data, "final_state": final_state}
        
    finally:
        await browser.close()

36.4.3 Handling Dynamic UIs

Modern web applications are hostile to automation. They're built for humans, not bots. The challenges are systematic:

Asynchronous loading: Elements appear at unpredictable times as JavaScript fetches data from APIs. The model must wait for stability before reading state. Acting on a half-loaded page produces incorrect understanding of what's available.


async def wait_for_stable_state(browser: BrowserTools, max_wait_ms: int = 5000) -> PageState:
    """Wait until the page stops changing, then return state."""
    previous_content = ""
    stable_count = 0
    
    for _ in range(max_wait_ms // 200):
        await asyncio.sleep(0.2)
        current = await browser.get_page_content()
        if current == previous_content:
            stable_count += 1
            if stable_count >= 3:  # Stable for 600ms
                return await browser.get_full_state()
        else:
            stable_count = 0
            previous_content = current
    
    # Timeout — return current state even if still loading
    return await browser.get_full_state()

Session expiry: Mid-operation, the session expires and the page redirects to login. The loop must detect this condition and re-authenticate without losing the operation context:


async def ensure_authenticated(browser: BrowserTools, credentials: dict) -> bool:
    """Detect and handle session expiry transparently."""
    current_url = await browser.get_current_url()
    page_content = await browser.get_page_content()
    
    # Common session expiry indicators
    is_login_page = (
        "/login" in current_url or 
        "/sign-in" in current_url or
        "session expired" in page_content.lower() or
        "please log in" in page_content.lower()
    )
    
    if is_login_page:
        await browser.fill("[name='username']", credentials["username"])
        await browser.fill("[name='password']", credentials["password"])
        await browser.click("[type='submit']")
        await browser.wait_for(".authenticated-indicator", timeout_ms=10000)
        return True  # Re-authenticated
    
    return False  # Was still authenticated

Confirmation dialogs and modals: The UI pops up "Are you sure?" dialogs, cookie consent banners, or notification permission requests. The loop must handle these without losing its place in the workflow.

36.4.4 Visual vs. DOM Oracles

Browser automation loops have two verification strategies:

DOM assertions (preferred when possible): Check the HTML structure for expected elements, text content, or attribute values. Fast, cheap, reliable:


async def verify_via_dom(browser: BrowserTools, criteria: dict) -> bool:
    """Verify success by checking DOM state."""
    for check in criteria.get("dom_checks", []):
        element_text = await browser.get_text(check["selector"])
        if check["expected"] not in element_text:
            return False
    return True

Visual assertions (when DOM doesn't expose the relevant state): Use a screenshot and a model judge. Expensive, slower, less reliable — but necessary for canvas elements, complex data visualizations, or PDF viewers embedded in iframes:


async def verify_via_vision(browser: BrowserTools, criteria: str) -> bool:
    """Verify success using screenshot and model vision."""
    screenshot = await browser.screenshot()
    
    result = await model.judge_image(
        image=screenshot,
        criteria=criteria,
    )
    
    return result.score >= 0.85

Rule: Use DOM assertions for everything they can check. Reserve visual assertions for genuinely visual success criteria (layout correctness, chart data accuracy, visual diff between expected and actual).

36.5 Shared Patterns Across Operations Loops

36.5.1 The Escalation Boundary

Every operations loop must define where autonomous action ends and human action begins. The universal criteria:


REQUIRE_HUMAN_APPROVAL = [
    "Action is irreversible (data deletion, production deployment, user account termination)",
    "Action affects more than {MAX_BLAST_RADIUS} systems simultaneously",
    "Confidence in diagnosis is below 0.7",
    "Previous automated attempt for this same issue failed",
    "Action has regulatory or compliance implications",
    "Action involves financial transactions above threshold",
    "Customer has explicitly requested human contact",
]

The guiding principle: if you can't verify the action's correctness before it takes effect, don't do it autonomously. Coding loops can be highly autonomous because tests verify before deployment. Operations loops dealing with irreversible actions must be more conservative.

36.5.2 Audit Trails

Operations loops must log every action, decision, and observation. This isn't just good engineering — it's the mechanism by which humans maintain oversight of autonomous systems and organizations maintain compliance:


@dataclass
class AuditEntry:
    timestamp: str
    loop_id: str
    iteration: int
    phase: str           # "assess", "plan", "execute", "verify"
    action_type: str     # What was done
    target: str          # What system/entity was affected
    input_state: str     # State before action
    decision: str        # What the loop decided
    rationale: str       # Why (model's reasoning)
    output_state: str    # State after action
    confidence: float    # How certain the loop was
    human_approved: bool # Whether a human signed off

Every entry answers: what happened, why, to what, when, and who approved it. An auditor reviewing the trail six months later should be able to reconstruct the full decision chain without needing to re-run anything.

36.5.3 Blast Radius Limiting

Operations loops must constrain how much damage a single run can cause, regardless of how confident the loop is in its actions:


class BlastRadiusGuard:
    """Prevent operations loops from affecting too many systems in one run."""
    
    def __init__(
        self,
        max_systems: int = 5,
        max_changes: int = 10,
        max_affected_users: int = 100,
    ):
        self.max_systems = max_systems
        self.max_changes = max_changes
        self.max_affected_users = max_affected_users
        self.systems_touched: set[str] = set()
        self.changes_made: int = 0
        self.users_affected: int = 0
    
    def check_and_record(self, system_id: str, affected_users: int = 0) -> bool:
        """Returns False and halts if action would exceed blast radius."""
        self.systems_touched.add(system_id)
        self.changes_made += 1
        self.users_affected += affected_users
        
        if len(self.systems_touched) > self.max_systems:
            return False
        if self.changes_made > self.max_changes:
            return False
        if self.users_affected > self.max_affected_users:
            return False
        return True

A security triage loop that patches 50 systems simultaneously without this guard can turn a vulnerability response into an outage. The guard forces sequential, verified remediation — patch one system, verify it works, move to the next. Slower, but safe.

36.6 When Operations Loops Fail

Three failure modes unique to operations (not present in coding or research loops):

Cascading actions. The loop takes an action that triggers a secondary condition, which the loop then also tries to fix, causing a third condition. Example: loop patches a service → patch breaks a health check → load balancer removes the instance → loop detects missing instance → loop tries to re-provision → new instance has old vulnerable code → loop tries to patch again. Mitigation: limit cascading depth. After the first action, wait and verify before taking any secondary actions. Never let the loop chase its own tail.

Oracle inversion. The loop's verification check becomes unreliable or inverted. Example: the security scanner used for verification has a false negative — it reports "clean" when the vulnerability still exists (perhaps the scanner's signature database is outdated). The loop closes the ticket. The vulnerability remains. Mitigation: use multiple verification methods. Don't trust a single scanner. Cross-check with at least one alternative signal (dependency version check, behavioral test, manual spot-check on a sample).

Timing sensitivity. Operations loops interact with systems that have their own timing: DNS propagation (up to 48 hours), certificate renewal (minutes to hours), container scheduling (seconds to minutes), database replication lag (milliseconds to seconds). The loop verifies too early, sees the old state, and incorrectly concludes the action failed — then takes corrective action that conflicts with the still-propagating original action. Mitigation: implement wait-before-verify with system-appropriate delays. DNS changes get 5-minute delays. Container restarts get 30-second delays. Database writes get sub-second delays.


VERIFICATION_DELAYS = {
    "dns_change": 300,         # 5 minutes
    "certificate_renewal": 120, # 2 minutes
    "container_restart": 30,    # 30 seconds
    "config_reload": 10,        # 10 seconds
    "database_write": 1,        # 1 second
}

async def verify_with_appropriate_delay(action_type: str, verify_fn) -> bool:
    delay = VERIFICATION_DELAYS.get(action_type, 5)
    await asyncio.sleep(delay)
    return await verify_fn()
