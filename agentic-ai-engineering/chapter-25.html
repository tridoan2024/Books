Chapter 25: Topologies, Shared State, and Coordination

Level: S (Standard) · ~4,000 words · Levels served: L4, L5

25.1 Fleet Topologies

How agents connect determines how they communicate, what overhead they incur, and what failure modes they face. Four topologies cover the practical design space:

Hierarchy (Star)

One lead, multiple specialists. All communication flows through the lead. Specialists never talk to each other directly.


        Lead
       / | \
      /  |  \
     A   B   C

Advantages: Simple coordination, no inter-specialist conflicts, lead has full visibility.

Disadvantages: Lead becomes bottleneck, no direct specialist collaboration, lead must understand all domains.

Best for: Most fleet tasks. Start here unless you have a specific reason not to.

Pipeline (Chain)

Each agent processes the output of the previous one. Work flows in one direction.


A → B → C → D

Advantages: Clear data flow, each stage refines the previous, natural quality escalation.

Disadvantages: Latency (sequential), one failure blocks the entire pipeline, no parallelism.

Best for: Multi-stage processing — research → write → edit → format.

Mesh (Full Connection)

Every agent can communicate with every other. No central coordinator.


A ←→ B
↕     ↕
C ←→ D

Advantages: Maximum flexibility, agents collaborate directly on cross-cutting concerns.

Disadvantages: Combinatorial communication overhead (N² connections), hard to debug, consensus problems.

Best for: Rarely. Only when agents have genuine peer-to-peer collaboration needs. Usually, hierarchy with selective peer channels is better.

Blackboard

Agents don't communicate directly. They read from and write to a shared state (the "blackboard"). Each agent processes whatever is relevant to its specialty.


     ┌───────────┐
     │ Blackboard │
     └───┬───┬───┘
         │   │
    ┌────┘   └────┐
    │    │    │    │
    A    B    C    D

Advantages: Fully decoupled agents, easy to add/remove specialists, no coordination protocol needed.

Disadvantages: Race conditions on shared state, no guaranteed ordering, eventual consistency only.

Best for: Continuous monitoring loops where multiple agents process events independently.

25.2 Shared State Mechanisms

Agents need to share information. The mechanism determines latency, consistency, and complexity:

File-based shared state

The simplest mechanism: agents read and write files in a shared directory.


# Agent writes its findings
Path("shared/findings/agent_a.json").write_text(json.dumps(findings))

# Lead reads all findings
all_findings = []
for f in Path("shared/findings/").glob("*.json"):
    all_findings.extend(json.loads(f.read_text()))

Pros: Simple, no infrastructure, human-readable, survives crashes.

Cons: No atomic updates, potential read-write races, no notification mechanism.

Structured message passing

Agents communicate through a message queue or structured protocol.


class AgentMailbox:
    def __init__(self, agent_id: str):
        self.inbox: asyncio.Queue = asyncio.Queue()
        self.agent_id = agent_id
    
    async def send(self, to: str, message: Message):
        target_mailbox = registry.get_mailbox(to)
        await target_mailbox.inbox.put(message)
    
    async def receive(self, timeout: float = 30.0) -> Message:
        return await asyncio.wait_for(self.inbox.get(), timeout)

Pros: Ordered, reliable delivery, supports async notification.

Cons: Infrastructure overhead, message schema design required.

Event log (append-only)

All agents append to a shared event log. Anyone can read the full history.


class EventLog:
    def __init__(self, path: Path):
        self.path = path
    
    def append(self, agent_id: str, event_type: str, data: dict):
        entry = {"ts": time.time(), "agent": agent_id, "type": event_type, "data": data}
        with self.path.open("a") as f:
            f.write(json.dumps(entry) + "\n")
    
    def read_since(self, timestamp: float) -> list[dict]:
        events = []
        for line in self.path.read_text().splitlines():
            event = json.loads(line)
            if event["ts"] > timestamp:
                events.append(event)
        return events

Pros: Full audit trail, no race conditions (append-only), easy replay.

Cons: Growing size, requires periodic cleanup, read performance degrades.

25.3 Coordination Protocols

Work assignment

The lead assigns work to specialists. Two patterns:

Push: Lead decides what each specialist should do and sends assignments.


await specialist_a.assign(task="Review auth module", scope=["src/auth/"])
await specialist_b.assign(task="Review data module", scope=["src/data/"])

Pull: Specialists request work from a shared queue.


# Specialist loop
while True:
    task = await work_queue.get()
    result = await self.execute(task)
    await results_queue.put(result)

Push is simpler for small fleets. Pull scales better for large, dynamic workloads.

Result collection

How the lead gathers specialist outputs:

Barrier: Wait for all specialists to complete before proceeding.


results = await asyncio.gather(*[spec.run() for spec in specialists])
# All done — proceed to aggregation

Streaming: Process results as they arrive.


async for result in as_completed([spec.run() for spec in specialists]):
    await process_intermediate(result)
# Each result is processed immediately when available

Timeout with partial: Wait up to a deadline, then proceed with whatever results arrived.


done, pending = await asyncio.wait(
    [spec.run() for spec in specialists],
    timeout=120.0
)
for task in pending:
    task.cancel()
results = [task.result() for task in done]

Dependency management

When specialist B depends on specialist A's output:


class DependencyGraph:
    def __init__(self):
        self.deps: dict[str, list[str]] = {}  # task → [dependencies]
        self.completed: set[str] = set()
    
    def can_start(self, task_id: str) -> bool:
        return all(dep in self.completed for dep in self.deps.get(task_id, []))
    
    def mark_complete(self, task_id: str):
        self.completed.add(task_id)
    
    def get_ready_tasks(self) -> list[str]:
        return [t for t in self.deps if self.can_start(t) and t not in self.completed]

25.4 Preventing Conflicts

When multiple agents modify shared resources (code, data, configuration), conflicts are inevitable without explicit prevention:

Ownership locks

Each resource is owned by at most one agent at a time.


class ResourceLock:
    def __init__(self):
        self.owners: dict[str, str] = {}  # resource → agent_id
    
    def acquire(self, resource: str, agent_id: str) -> bool:
        if resource in self.owners:
            return False
        self.owners[resource] = agent_id
        return True
    
    def release(self, resource: str, agent_id: str):
        if self.owners.get(resource) == agent_id:
            del self.owners[resource]

Scope partitioning

Divide resources so each agent operates on a non-overlapping subset.


# Partition codebase by directory
partitions = {
    "agent_a": ["src/auth/", "src/middleware/"],
    "agent_b": ["src/data/", "src/models/"],
    "agent_c": ["src/api/", "src/routes/"],
}
# Each agent can only modify files in its partition

Merge strategy

Allow conflicts but resolve them systematically after execution.


# Each agent works in its own worktree
# After all agents complete:
for agent_branch in completed_branches:
    try:
        merge(agent_branch, into="integration")
    except MergeConflict as e:
        resolution = await lead.resolve_conflict(e)
        apply_resolution(resolution)

25.5 Per-Agent Tracing

In a fleet, debugging requires knowing which agent did what, when, and why. Per-agent tracing provides this visibility:


@dataclass
class AgentTrace:
    agent_id: str
    model: str
    started_at: float
    ended_at: float | None
    iterations: int
    tokens_consumed: int
    tools_called: list[ToolCall]
    findings: list[str]
    status: str  # "completed", "failed", "timeout"
    
class FleetTrace:
    def __init__(self):
        self.agents: dict[str, AgentTrace] = {}
        self.communications: list[Communication] = []
    
    def summary(self) -> str:
        return f"""
Fleet execution summary:
  Agents: {len(self.agents)}
  Total tokens: {sum(a.tokens_consumed for a in self.agents.values())}
  Total time: {self.wall_clock_time}s
  Failures: {sum(1 for a in self.agents.values() if a.status == 'failed')}
"""

Every tool call, every message between agents, every decision is logged with its agent ID and timestamp. When something goes wrong, you can reconstruct exactly what happened and which agent was responsible.

25.6 Handling Specialist Failures

When one specialist in a fleet fails, the fleet must continue. Strategies:

Retry: Re-run the failed specialist with the same scope.

Redistribute: Give the failed specialist's work to another specialist.

Degrade: Continue without that specialist's contribution, noting the gap.

Escalate: Stop the fleet and ask for human guidance.


async def handle_specialist_failure(
    failed_agent: str, 
    task: Task, 
    fleet: Fleet
) -> str:
    if task.retry_count < 2:
        return "retry"
    
    available = fleet.get_idle_specialists()
    if available:
        return "redistribute"
    
    if task.is_optional:
        return "degrade"
    
    return "escalate"

25.7 Communication Cost Budget

Communication between agents isn't free — every message is tokens. Budget communication explicitly:

Fleet Size Rounds Messages/Round Tokens/Message Total Comm Cost
3 agents 2 6 1,000 12,000 tokens
5 agents 3 15 1,000 45,000 tokens
10 agents 3 30 1,000 90,000 tokens

For a 5-agent fleet with 3 communication rounds, you're spending 45K tokens purely on coordination — before any actual work happens. This is why minimizing communication rounds matters. Design the delegation to be clear enough that specialists rarely need to ask clarifying questions.
