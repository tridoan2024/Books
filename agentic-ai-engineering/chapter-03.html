Chapter 3: Anatomy of a Loop

Level: A (Anchor) · ~6,000 words · The book's recurring formalism — every chapter references this

3.1 The Five Stages

Every productive loop — whether a single agent fixing a bug or a fleet auditing a codebase — passes through five stages. The stages may execute in seconds or hours. They may be explicit or implicit. But skip any one of them and the loop either can't start, can't improve, or can't stop.


┌──────────────────────────────────────────────────────┐
│                                                      │
│   ┌──────────┐    ┌──────┐    ┌─────────┐          │
│   │ DISCOVER │───▶│ PLAN │───▶│ EXECUTE │          │
│   └──────────┘    └──────┘    └────┬────┘          │
│                                     │               │
│                                     ▼               │
│   ┌─────────┐                 ┌──────────┐         │
│   │ ITERATE │◀────────────────│  VERIFY  │         │
│   └────┬────┘   (if failed)   └────┬─────┘         │
│        │                            │               │
│        └───────────▶ DISCOVER       │ (if passed)   │
│                    (next cycle)     ▼               │
│                                   STOP              │
└──────────────────────────────────────────────────────┘

Stage 1: Discover

The loop gathers the information it needs to act. This is not passive — the agent actively searches for, retrieves, and synthesizes context relevant to its goal. Discovery answers: "What do I need to know before I can plan?"

In a coding loop: read the error message, find the relevant source files, understand the call chain, identify the test that's failing.

In a research loop: search for sources, identify conflicting claims, find the most authoritative references.

In a security loop: enumerate the attack surface, read the code under review, pull related vulnerability patterns.

Discovery is where most loops fail silently. An agent that plans without adequate discovery is planning in the dark. The output may look confident. It will be wrong.

Key engineering decision: How much discovery is enough? Too little produces bad plans. Too much fills the context window with noise and burns budget on irrelevant information. The answer varies by task, but a good heuristic: discover until you can articulate, in concrete terms, what you're going to do. If the plan would be vague, discovery is insufficient.

Stage 2: Plan

Given what the agent discovered, it produces a plan — a sequence of concrete steps that, if executed correctly, will achieve the goal. The plan is a durable artifact. It lives in the context, in a file, or in a task list. It can be inspected, critiqued, and revised.

In a coding loop: "I'll modify auth.py line 42 to validate the token expiry, add a test case for expired tokens, and run the test suite."

In a content loop: "I'll write sections on X, Y, Z. Each section needs an example and a cross-reference to chapter N."

In a fleet loop: "I'll spawn three specialists — one for each subsystem — have them investigate independently, then synthesize their findings."

The plan is not the prompt. A prompt is what you say to the model. A plan is the model's commitment to itself about what it will do. The plan provides continuity across iterations — if the first attempt fails, the plan tells the next iteration what was tried and what to try differently.

Plans decay. A plan made with incomplete information becomes stale as execution reveals reality. This is why replanning (Chapter 16) exists as a first-class capability. The plan is a living document, not a contract.

Stage 3: Execute

The agent carries out the plan's current step. This is where tools get called, code gets written, files get modified, APIs get hit. Execution is the only stage that changes the world.

Execution must be reversible or isolated. If execution can't be undone (sending an email, deleting a database record), the loop needs an approval gate before the execute step. If execution is reversible (editing a file, writing to a branch), the loop can execute freely and roll back if verification fails.

Execution produces artifacts. Code, text, data, API responses. These artifacts are what the verification stage evaluates. If execution doesn't produce something checkable, the loop has no way to improve.

Stage 4: Verify

The oracle evaluates the execution's output against the goal's acceptance criteria. Verification answers: "Is this done correctly?"

This is the most important stage. Without verification, the loop is just generation — producing output without knowing whether it's good. Verification is what transforms a generation system into a quality system.

Verification can be:

  • Deterministic: Run tests, type-check, lint, parse. Binary pass/fail.
  • Heuristic: Apply a rubric, check against property-based tests, validate structural constraints.
  • Model-based: Use a separate LLM as a judge, with a different context and different incentives than the executor.
  • Human: Escalate to a person for cases the automated oracle can't handle.

The oracle hierarchy (Chapter 20) formalizes the choice. The rule of thumb: use the cheapest oracle that can still discriminate good output from bad.

Stage 5: Iterate

If verification fails, the loop doesn't stop — it feeds the failure information back into a new cycle. The failure signal (test error, rubric score, judge critique) becomes input to the next discovery or planning step.

Good iteration is targeted: "Test X failed because of Y. Modify Z to fix it."

Bad iteration is blind: "That didn't work. Try again."

The quality of the iteration signal determines how many cycles the loop needs to converge. A precise error message from a test suite sends the loop straight to the fix. A vague "the output wasn't good enough" sends it on a random walk through solution space.

Iteration is where cost lives. Each cycle costs tokens, time, and money. The faster the loop converges, the cheaper the result. This is why oracle quality matters so much — a good oracle doesn't just verify, it provides actionable feedback that accelerates convergence.

3.2 The Six Building Blocks

The five stages describe what a loop does. The six building blocks describe what a loop is made of — the infrastructure components that make the stages possible.

Block 1: Automations (The Heartbeat)

An automation is what starts the loop without a human clicking a button. If you start the loop by hand every time, the human is still in the loop — they're just in a different position (trigger rather than reviewer).

Types of automations:


schedule:    "Every weekday at 9am, scan for new PRs"
event:       "When a PR is opened, run the security review loop"
threshold:   "When error rate exceeds 1%, run the diagnosis loop"
webhook:     "When Linear ticket moves to 'ready', start implementation"
chained:     "When loop A completes, start loop B with A's output"
completion:  "Run until all items in the queue are processed"

The rule: if you have to remember to start it, it's not automated enough. A loop's automation is its heartbeat — the thing that keeps it alive without human attention.

Block 2: Worktrees (Isolation)

When multiple agents — or multiple iterations of the same agent — need to modify shared state (files, branches, databases), they collide. Agent A edits line 42 while Agent B edits line 43. Without isolation, the result is corruption.

Worktrees provide isolation: each agent (or each iteration) gets its own copy of the relevant state. In code: a git worktree on a fresh branch. In data: a transaction or a snapshot. In infrastructure: a sandbox environment.


# Claude Code's worktree pattern
git worktree add .claude/worktrees/agent-1 -b agent-1-fix
git worktree add .claude/worktrees/agent-2 -b agent-2-fix

# Agents work in isolation
# Results merge back only after verification

Worktrees are expensive (disk, setup time, merge complexity). Use them only when agents would actually collide. A single-agent loop modifying one file at a time doesn't need isolation. A fleet of five agents all editing the same codebase does.

Block 3: Skills (Reusable Knowledge)

A skill is project-specific knowledge that the loop needs every time it runs. Instead of explaining the project from scratch on every iteration, you encode the knowledge once and load it into context on demand.

A good skill file includes:

  • Vision: What this project does and why
  • Architecture: How the system is structured
  • Rules: Constraints the agent must respect
  • Build/test commands: How to verify output
  • Anti-patterns: Things the agent must never do

# SKILL.md — Example for a web application

## Architecture
- Frontend: React 18, TypeScript strict, Zustand state
- Backend: FastAPI, PostgreSQL 15, Redis cache
- Tests: pytest + Playwright E2E

## Rules
- Never modify migration files after they've been applied
- All API endpoints require authentication middleware
- Error responses must use RFC 7807 format

## Build & Verify
- `npm run build` must pass with zero warnings
- `pytest tests/ -x` must pass before any PR
- `npx playwright test` for UI changes

Without skills, the loop starts cold every run — spending tokens rediscovering what the project is, how it's structured, and what the rules are. With skills, the loop starts warm and spends its budget on the actual work.

Block 4: Connectors (Integration)

A loop that only sees files is limited. Connectors wire the loop into the real tools and systems that production work requires.

Connector What it enables
GitHub/ADO Open PRs, read diffs, post comments, watch CI
Slack/Teams Escalate findings, notify humans, receive commands
Linear/Jira Read tickets, update status, create subtasks
Database Read schema, query data, validate migrations
CI/CD Trigger builds, read test results, gate deployments
Monitoring Read metrics, detect anomalies, correlate with changes

The connector transforms the loop from "here's a suggestion" to "I did the thing, verified it, and updated all the relevant systems." This is the difference between L2 and L3 on the autonomy ladder.

MCP (Model Context Protocol) is the standard connector interface in 2026. Chapter 10 covers it in depth.

Block 5: Subagents (Specialization)

A subagent is a separate execution context with its own prompt, tools, model, and scope. Subagents exist for two reasons:

Reason 1: Context isolation. The maker and the checker should not share context. An agent that wrote code will be generous when reviewing it — it already "knows" what the code is supposed to do, so it fills in gaps with its own intent rather than evaluating what's actually on the page. A separate checker agent, given only the code and the spec, provides an independent evaluation.

Reason 2: Specialization. Different tasks benefit from different configurations. A code-writing agent needs access to the filesystem and test runner. A security-review agent needs access to vulnerability databases and OWASP references. A documentation agent needs access to the API spec and style guide. Mixing all these tools into one context makes each task worse.


# Conceptual fleet structure
orchestrator = Agent(
    model="opus",
    tools=["plan", "delegate", "aggregate"],
    role="Decompose the goal and coordinate specialists"
)

code_agent = Agent(
    model="sonnet",
    tools=["read_file", "write_file", "run_tests", "search_code"],
    role="Implement changes according to the plan"
)

review_agent = Agent(
    model="opus",
    tools=["read_file", "search_code"],
    role="Review changes for correctness and security"
)

Block 6: Memory (Cross-Run Continuity)

A loop that forgets everything between runs is doomed to repeat its mistakes. Memory is what lets a loop learn across invocations — remembering what worked, what failed, what patterns recur, and what the human corrected.

Memory lives at multiple timescales:

  • Working memory: The current context window. Lost on compaction or session end.
  • Episodic memory: Records of specific past events. "Last run, the test failed because of a timezone issue."
  • Semantic memory: Accumulated knowledge. "This codebase uses UTC internally and converts to local time at the display layer."
  • Procedural memory: Learned workflows. "When tests fail with a database error, check if the migration has been applied first."

Memory can be stored in files (markdown notes, JSON logs), databases (structured recall), or model context (loaded from skill files). Chapter 12 covers the full memory architecture.

The critical insight: memory is not just storage. It's consolidation — the process of deduplicating, resolving contradictions, surfacing recurring patterns, and forgetting what's no longer relevant. Anthropic calls this "dreaming" — a background process that curates accumulated memory into useful knowledge.

3.3 The Loop Contract

The Loop Contract is this book's central formalism. Every loop you build must answer these five questions. A loop missing any answer is broken in a specific, predictable way.


loop_contract:
  goal:
    description: "What constitutes done, in machine-checkable terms"
    failure_mode_if_missing: "The loop has no target. It runs but produces nothing useful."
    
  oracle:
    description: "How the loop knows the goal is met"
    failure_mode_if_missing: "The loop cannot verify its own output. It runs once and ships garbage."
    
  budget:
    description: "Maximum resources (tokens, time, dollars, retries) before escalation"
    failure_mode_if_missing: "The loop runs forever, burning money on a problem it can't solve."
    
  stop_condition:
    description: "Precise criteria for termination — success, failure, or indeterminate"
    failure_mode_if_missing: "The loop oscillates, thrashes, or hangs. It never converges."
    
  escalation_path:
    description: "What happens when the loop exhausts budget or detects it cannot succeed"
    failure_mode_if_missing: "The loop fails silently. No one knows. The task is dropped."

Goal

The goal must be machine-checkable. "Make the code better" is not a goal — it's a vibe. "All tests pass, type checker reports zero errors, and the linter produces no warnings" is a goal. The precision of the goal determines the precision of the oracle, which determines the reliability of the loop.

The goal specification skill (Chapter 15) is the single highest-leverage skill in loop engineering. Everything downstream depends on it.

Goals can be:

  • Binary: All tests pass (yes/no)
  • Threshold: Rubric score exceeds 8/10
  • Convergent: No new issues found in two consecutive passes
  • Comparative: Output is better than baseline by metric X

Oracle

The oracle is the mechanism that evaluates the output against the goal. Chapter 20 builds the full oracle hierarchy. Here's the preview:


Cheapest ─────────────────────────────────────────── Most expensive
│ Deterministic │ Property │ Rubric  │ Model   │ Human  │
│ (tests/lint)  │  tests   │ grading │  judge  │ review │
│    $0.00      │  $0.001  │ $0.01   │ $0.10   │ $50    │

The rule: use the cheapest oracle that still discriminates. If tests can tell you the code works, don't use a model judge. If a model judge can tell you the prose is good, don't use a human editor.

Budget

Every loop needs a ceiling. Without one, a loop encountering a hard problem will spend your entire monthly API budget in an afternoon. Budget can be expressed as:

  • Tokens: Maximum 500K tokens per run
  • Time: Maximum 10 minutes wall-clock
  • Money: Maximum $5 per task
  • Retries: Maximum 5 iteration cycles
  • Composite: The first limit hit wins

budget = LoopBudget(
    max_tokens=500_000,
    max_time_seconds=600,
    max_cost_usd=5.00,
    max_iterations=5,
)

Budget isn't just a cost control. It's a convergence signal. If a loop hasn't solved the problem within its budget, either the problem is harder than expected (escalate to human) or the loop is thrashing (stop, diagnose, redesign). Either way, more budget won't help.

Stop Condition

The stop condition tells the loop when to terminate. It's distinct from the oracle (which evaluates quality) because the loop can also stop for reasons other than success:

  • Success: Oracle says the output meets the goal. Ship it.
  • Budget exhausted: The loop has spent its allocation. Escalate.
  • Oscillation detected: The loop is making changes, undoing them, and remaking them. It's stuck.
  • No progress: The last N iterations produced no improvement. The approach is wrong.
  • External signal: A human interrupted, a dependency changed, the context became stale.

def should_stop(state: LoopState) -> StopReason | None:
    if state.oracle_passed:
        return StopReason.SUCCESS
    if state.iterations >= state.budget.max_iterations:
        return StopReason.BUDGET_EXHAUSTED
    if state.last_n_scores_identical(n=3):
        return StopReason.NO_PROGRESS
    if state.detected_oscillation():
        return StopReason.OSCILLATION
    return None  # Continue

Chapter 18 (The Stop Problem) covers this in depth, because getting termination wrong is the most common failure mode in production loops.

Escalation Path

When the loop can't solve the problem, what happens? The answer should never be "nothing." An escalation path ensures that failed loops don't disappear silently.

Escalation options:

  • Notify human: Post to Slack, create a ticket, send an email
  • Reduce scope: Attempt a simpler version of the goal
  • Change approach: Switch to a different strategy (different model, different tools, different decomposition)
  • Park and document: Save the current state, log what was tried, and wait for human guidance

The escalation path is the loop's safety valve. Without it, a loop that encounters a hard problem either burns money forever or fails silently. With it, the loop degrades gracefully.

3.4 ReAct as the Primitive Loop

The Loop Contract formalizes what ReAct (Reason + Act) introduced informally in 2022. ReAct's pattern — Think, Act, Observe, Think — maps directly to our five stages:

ReAct Loop Stage What happens
Think Discover + Plan The model reasons about what it knows and what to do
Act Execute The model calls a tool or performs an action
Observe Verify The model reads the result of the action
Think (next) Iterate The model reasons about what to do differently

ReAct is the primitive loop — the simplest possible implementation. Every more sophisticated pattern (reflection, tree-of-thought, self-consistency, multi-agent debate) is a loop built on top of this primitive. Understanding ReAct as a loop (not as a "prompting technique") is the conceptual key to everything that follows.


# ReAct as the primitive loop — explicit five-stage decomposition
def react_loop(goal: str, tools: list, max_iterations: int = 10) -> Result:
    context = discover(goal)  # Stage 1: Gather initial context
    
    for i in range(max_iterations):
        plan = think(context, goal)              # Stage 2: Plan next action
        action_result = act(plan, tools)         # Stage 3: Execute
        verification = observe(action_result)    # Stage 4: Verify
        
        if verification.goal_met:
            return Result(success=True, output=action_result)
        
        context = iterate(context, verification) # Stage 5: Feed back
    
    return Result(success=False, reason="budget_exhausted")

3.5 Filling the Contract Part by Part

The rest of this book fills in each element of the Loop Contract with increasing precision:

  • Part III (Building the Loop) teaches you to specify goals and stop conditions
  • Part IV (Verification) teaches you to build oracles
  • Part V (Fleets) teaches you to design escalation paths for multi-agent systems
  • Part VI (Economics) teaches you to set and enforce budgets
  • Part VII (Hardening) teaches you to make all five elements robust against adversarial conditions

By the time you finish the book, you'll be able to write a complete Loop Contract for any task — and more importantly, you'll know what breaks when each element is weak.

3.6 A Complete Example: The Bug-Fix Loop

Let's see the full anatomy in action. Here's a bug-fix loop, annotated with stages and contract elements:


loop_contract:
  goal: "The failing test test_user_login_expired_token passes, and no existing tests regress"
  oracle: "pytest tests/ -x exits 0"
  budget: {max_iterations: 5, max_tokens: 200_000, max_time: 300s}
  stop_condition: "All tests pass OR budget exhausted OR oscillation detected"
  escalation_path: "Create GitHub issue with diagnosis, tag team lead"

The loop execution:


DISCOVER: Read the failing test. Read the error message. Find the source file.
           Read related code. Understand the expected behavior.
           
PLAN:     "The test expects a 401 response when token is expired, but the code
           doesn't check token expiry. I'll add an expiry check in auth.py
           at line 42, before the existing validation."

EXECUTE:  Edit auth.py:42. Add: if token.expired: return Response(401)

VERIFY:   Run pytest tests/ -x
           Result: 2 tests fail — the new test passes but test_valid_token broke

ITERATE:  "My fix broke test_valid_token. The issue is that I'm checking expired
           before checking validity. I need to restructure: check validity first,
           then check expiry."

DISCOVER: Read test_valid_token to understand what it expects.

PLAN:     "Restructure: validate format → check expiry → check signature"

EXECUTE:  Rewrite auth.py:40-50 with the new order.

VERIFY:   Run pytest tests/ -x
           Result: All 47 tests pass ✓

STOP:     Oracle passed. Ship it.

Two iterations. Under budget. The loop verified its own work, caught its own regression, fixed the regression, and confirmed success — all without a human reviewing any intermediate step.

This is what loop engineering produces: verified outcomes at machine speed. The rest of this book teaches you to build loops that work this reliably across every domain, at every scale.
