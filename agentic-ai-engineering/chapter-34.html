Chapter 34: Case Study — The Coding Loop

Level: A (Anchor) · ~5,500 words · Levels served: L3, L4, L5

34.1 Why Coding Is the Canonical Loop

Code is the ideal domain for agentic loops because it offers oracles at every level of the hierarchy discussed in Chapter 20. You can type-check code (Level 1). You can run tests (Level 2). You can lint for style and complexity (Level 1). You can run the program and observe behavior (Level 2). You can even ask a model to review the code against requirements (Level 4). No other creative domain offers this density of verifiable checkpoints.

This density matters because it makes the feedback signal tight. A coding loop doesn't need to wait for user feedback or human judgment. It can write code, check if that code compiles, passes type checks, passes lints, and passes tests — all within seconds. Each checkpoint either passes or fails, and each failure produces a specific error message that the model can read and act on. This is the tightest possible feedback loop: act, observe concrete failure, correct, verify.

Compare this to writing prose, where verification requires judgment, or design, where verification requires human perception. Code is unique in offering machine-checkable quality at multiple levels simultaneously. This is why every major AI lab has shipped a coding agent before shipping agents in other domains — the oracle infrastructure already exists. It's called a build system.

This chapter tears down three production coding loops — Claude Code, Cursor, and Devin — to show how the same underlying architecture manifests across different harness designs. The key insight: these tools differ at the harness layer, not the model layer. They all use frontier models. They diverge in how they load context, plan work, execute edits, verify results, and handle failures.

34.2 Claude Code: The Reference Implementation

Claude Code is the most transparent of the three systems because its architecture is documented and its skill-loading mechanism is visible to users. It operates as a terminal-native agent with a read-plan-edit-verify loop. Understanding its architecture means understanding the template for all coding loops.

34.2.1 Skill Loading: CLAUDE.md

The loop begins before the first user message. When Claude Code starts, it reads a hierarchy of instruction files:


~/.claude/CLAUDE.md              # Global user preferences
./CLAUDE.md                      # Project-level instructions
./.claude/rules/*.md             # Domain-specific rules

These files are injected into the system prompt — they become the agent's "muscle memory." A well-written CLAUDE.md transforms the loop from a generic coding assistant into a project-specific specialist. Consider the difference between hiring a contractor who knows nothing about your codebase versus one who has read your contributing guide, understands your stack, and knows your testing conventions.


# CLAUDE.md for a FastAPI microservice

## Stack
- Python 3.12, FastAPI 0.115, SQLAlchemy 2.0, Alembic
- Tests: pytest + httpx TestClient
- Linter: ruff check --fix && ruff format
- Type checker: pyright --strict

## Conventions
- All endpoints return Pydantic models, never raw dicts
- Database access only through repository pattern
- Every new endpoint gets a test in tests/integration/
- Migrations: alembic revision --autogenerate -m "description"

## Before committing
- Run: pytest tests/ -x --tb=short
- Run: ruff check . && pyright
- Verify no secrets in staged files

This is a skill file. It tells the loop what tools to use (ruff, pyright, pytest), what patterns to follow (repository pattern, Pydantic models), and what the verification step looks like (run tests, lint, type-check). Without it, the loop still works — but it works generically, like a developer who just joined the team and hasn't read the contributing guide.

The skill file's power is cumulative. Teams that invest thirty minutes writing a comprehensive CLAUDE.md see immediate improvements in loop output because the model no longer has to guess at conventions. It knows. And when it knows, it gets things right on the first iteration more often — reducing total loop iterations and cost.

34.2.2 Planning: The Task System

When a user presents a complex request, the loop decomposes it into tasks. This isn't always explicit — for simple requests ("fix the typo on line 42"), planning is skipped entirely. The model recognizes that the task is atomic and proceeds directly to execution. For multi-step work ("add user authentication with JWT tokens"), the loop creates an internal task list:


# Internal representation of Claude Code's planning phase
tasks = [
    Task(id="1", subject="Add pyjwt dependency", status="pending"),
    Task(id="2", subject="Create auth utilities module", status="pending",
         blocked_by=["1"]),
    Task(id="3", subject="Add login endpoint", status="pending",
         blocked_by=["2"]),
    Task(id="4", subject="Add auth middleware", status="pending",
         blocked_by=["2"]),
    Task(id="5", subject="Add tests for auth flow", status="pending",
         blocked_by=["3", "4"]),
    Task(id="6", subject="Run full test suite", status="pending",
         blocked_by=["5"]),
]

The dependency graph prevents the loop from attempting work that depends on incomplete prerequisites. This is the same principle as a build system's DAG — topological ordering ensures coherent execution. You can't test the auth middleware before writing it. You can't write it before the auth utilities module exists. The planning phase encodes this ordering.

A critical subtlety: the plan is not fixed. If task 3 fails verification (the login endpoint doesn't work), the model may revise the plan — splitting task 3 into sub-tasks, or adding a new prerequisite task it didn't anticipate. Plans are hypotheses about the work structure. Execution validates or revises them.

34.2.3 Editing: Tool Calls

Claude Code edits files through structured tool calls, not raw text generation. This is a critical architectural choice. The model never generates an entire file and hopes it's correct. Instead, it issues precise edit operations:


# The model emits tool calls, not raw file content
Edit(
    file_path="/src/auth/utils.py",
    old_string="def verify_token(token: str) -> dict:",
    new_string="def verify_token(token: str) -> TokenPayload:",
)

The edit tool performs an exact string match and replacement. If old_string doesn't exist in the file (because the model hallucinated the current state), the tool errors — the loop gets immediate feedback that its mental model of the file is wrong.

This error signal is crucial. It forces the model to re-read the file before attempting another edit. The loop self-corrects:


Model generates edit → Tool says "old_string not found" → 
Model reads file → Model sees actual content → 
Model generates correct edit → Success

The alternative — generating entire files from scratch — is fragile at scale. A 500-line file regenerated from memory will contain subtle differences: extra blank lines, slightly different import ordering, comments that were in the original but aren't in the model's recollection. String-match editing forces precision. The model must identify exactly what to change and leave everything else untouched.

This has a secondary benefit for human review: the diff of a string-match edit shows exactly what changed. A full file regeneration produces a massive diff where the actual semantic change is buried in formatting noise.

34.2.4 Verification: Run Tests After Each Edit

The verification step is where the coding loop earns its keep. After each meaningful edit, the loop runs the oracle:


# Simplified verification flow
async def verify_edit(self, edit_result: EditResult) -> VerifyResult:
    # Level 1: Does it parse?
    syntax_ok = await self.run("python -c 'import ast; ast.parse(open(f).read())'")
    if not syntax_ok:
        return VerifyResult(passed=False, error="Syntax error", level=1)
    
    # Level 1: Does it type-check?
    types_ok = await self.run("pyright --outputjson " + edit_result.file)
    if not types_ok:
        return VerifyResult(passed=False, error=types_ok.stderr, level=1)
    
    # Level 2: Do related tests pass?
    tests_ok = await self.run(f"pytest tests/ -k '{related_test}' -x")
    if not tests_ok:
        return VerifyResult(passed=False, error=tests_ok.stdout, level=2)
    
    return VerifyResult(passed=True)

The verification cascade runs cheapest checks first. A syntax error is caught in milliseconds, avoiding the cost of running the type checker. A type error is caught in under a second, avoiding the cost of running the test suite. This cascading strategy minimizes the wall-clock time to detect failures — which matters because faster failure detection means faster iteration.

When verification fails, the loop doesn't ask the user what to do. It reads the error, diagnoses the cause, and attempts a fix. This is the core feedback loop:


Edit → Verify → Fail → Read Error → Diagnose → Fix → Verify → Pass

The model's ability to read error messages and act on them is what makes this work. A Python traceback contains the file, line number, error type, and often a suggestion. A type checker error specifies exactly which types are incompatible. A test failure shows the expected versus actual values. These are dense information signals that tell the model exactly what went wrong and (often) how to fix it.

34.2.5 Failure Handling: Read Error, Fix, Retry

The failure-handling strategy follows a deterministic escalation:

  1. Parse the error output. Extract the file, line number, and error message.
  2. Read the offending code. Don't guess — look at what's actually there.
  3. Hypothesize a fix. Based on the error type and code context.
  4. Apply the fix. Issue another edit tool call.
  5. Verify again. Same oracle, same threshold.
  6. If still failing after N attempts: Surface the error to the user with context about what was tried.

The retry budget is typically 3-5 attempts for any single verification failure. Beyond that, the loop recognizes it's stuck and escalates. This bounded retry prevents infinite loops where the model keeps trying the same wrong approach. After 3 failures, the model's approach is likely fundamentally wrong — not just a minor error that one more attempt will fix.

A sophisticated implementation tracks the nature of each failure to prevent circular fixes:


class FailureTracker:
    def __init__(self):
        self.failures: list[str] = []
    
    def record(self, error: str) -> None:
        self.failures.append(error)
    
    def is_circular(self) -> bool:
        """Detect if we're oscillating between two states."""
        if len(self.failures) < 3:
            return False
        # Check if the last error matches one we've seen before
        return self.failures[-1] in self.failures[:-1]

34.2.6 Summarization and Stopping

The loop stops when all tasks are complete and all verifications pass. It then produces a summary — what was changed, what was tested, what the user should know. This summary is the "receipt" that allows human oversight without human participation in every iteration.

The stopping condition has a secondary trigger: when the model determines it cannot make further progress. This happens when the task requires information the model doesn't have (credentials, design decisions, business requirements) or when the verification failure is in code the model doesn't have permission to modify.

34.3 Cursor: Inline Completions Plus Agent Mode

Cursor operates in two modes that represent different points on the loop spectrum. Understanding both illuminates what "closing the loop" actually adds beyond simple completion.

34.3.1 Tab Completion Mode (No Loop)

In completion mode, Cursor is a single-pass system. The model sees your cursor position, recent edits, and open files. It generates a completion. You accept or reject. There's no iteration, no verification, no retry. The human is the oracle.

This isn't a loop — it's a tool. The human provides all feedback. But it's instructive because it shows the baseline: model generates, human verifies, human acts on the result. The throughput is limited by human reading speed and judgment speed. You cannot scale this by making the model faster — the bottleneck is the human in the middle.

Tab completion works well for predictable code: boilerplate, pattern continuation, API usage that follows documentation. It fails for novel logic, complex interactions, or anything where "correct" requires running the code to check.

34.3.2 Agent Mode (Full Loop)

Cursor's agent mode activates the full loop architecture. When you issue a command like "Add error handling to all database operations in this file," the agent:

  1. Reads context: Current file, imported modules, project structure, open terminal output.
  2. Plans: Identifies all database operations needing error handling.
  3. Edits: Applies changes using diff-based tool calls.
  4. Verifies: Runs linting (if configured), checks for type errors via LSP.
  5. Iterates: If verification fails, reads errors and retries.

The key architectural difference from Claude Code: Cursor's agent operates within an IDE context. It has access to the language server (LSP) — meaning it gets real-time type information, go-to-definition, and find-references for free. Claude Code gets this through explicit tool calls; Cursor gets it through the IDE integration layer.

This gives Cursor a structural advantage for certain operations. When the model needs to know "what calls this function?" — Cursor's agent can query the LSP's find-references in milliseconds. Claude Code's agent must grep through files or use an explicit LSP tool call that requires spinning up a language server.

The tradeoff: Cursor's agent is bound to the IDE. It can't easily run shell commands in arbitrary directories, manage git branches, or interact with external services. Its world is the codebase as the IDE sees it.

The implication for practitioners: choosing between these tools is a harness decision, not a model decision. Pick the harness that matches your workflow. If you live in the editor and do focused refactoring, Cursor's harness gives you tighter integration. If you do cross-cutting work that spans files, commands, and systems, Claude Code's harness gives you broader reach.

34.4 Devin: Browser-Based Persistent Environment

Devin takes a fundamentally different approach to the harness: it runs in a persistent cloud environment with a browser, terminal, and code editor — all as tools the model can interact with.

34.4.1 The Persistent Environment

Unlike Claude Code (which operates in the user's local terminal) or Cursor (which operates in the user's IDE), Devin operates in its own sandboxed environment. This means:

  • It can install dependencies without affecting the user's machine.
  • It can run long-lived processes (servers, build watchers).
  • It can open a browser and interact with web UIs.
  • Its state persists across model calls — no need to re-establish context.

The persistent environment eliminates a class of problems that Claude Code faces: environmental setup. When Claude Code needs to run tests, it depends on the user's machine having the right Python version, the right dependencies installed, the right environment variables set. Devin controls its own environment entirely — it can install exactly what it needs without permission prompts or conflicts.

34.4.2 The Multi-Modal Loop

Devin's loop incorporates visual verification — a capability that extends the oracle hierarchy beyond what pure terminal-based agents can achieve:


# Devin's verification can include visual checks
async def verify_frontend_change(self) -> bool:
    # Start the dev server
    await self.terminal.run("npm run dev")
    
    # Open browser, navigate to the page
    await self.browser.navigate("http://localhost:3000/dashboard")
    
    # Wait for content to load
    await self.browser.wait_for_stable()
    
    # Screenshot and verify
    screenshot = await self.browser.screenshot()
    
    # Ask model: "Does this match the design spec?"
    judgment = await self.model.judge(
        image=screenshot,
        criteria="Dashboard shows user stats in a 2x2 grid layout with "
                 "each card showing a metric label, current value, and trend arrow"
    )
    
    return judgment.passes

This is a Level 4 oracle (model judge) applied to visual output — something neither Claude Code nor Cursor can do natively. The tradeoff: visual oracles are expensive ($0.01-0.05 per judgment with image input) and less reliable than deterministic checks. A visual oracle might say "looks right" when a specific CSS class is wrong. A DOM assertion checking for that class would catch it instantly.

34.4.3 The Autonomy Spectrum

Devin is designed for higher autonomy than Claude Code or Cursor. It can work on a task for hours without human input. This requires stronger stopping conditions and budget guardrails:

System Typical Autonomy Verification Model Human Touchpoint
Cursor (tab) None Human is oracle Every completion
Cursor (agent) Minutes Lint + tests After each command
Claude Code Minutes to hour Tests + type checks After task completion
Devin Hours Multi-modal + tests After full ticket

Higher autonomy demands better oracles. If a loop runs for two hours and the oracle is weak, it can drift far from the goal before anyone notices. Devin mitigates this with periodic checkpoints — snapshots of progress that a human can review asynchronously without blocking the loop's execution.

The risk profile inverts with autonomy level: low-autonomy systems fail small (one bad completion), high-autonomy systems fail big (hours of wasted work in the wrong direction). The higher the autonomy, the more critical the oracle becomes.

34.5 Annotated Trace: A Real Bug-Fix Loop

Let's trace a complete bug-fix loop from start to finish. The scenario: a test is failing because a function returns None when it should return an empty list. This is a common real-world bug — the function has an implicit return on a code path the developer didn't consider.

The trigger: a failing CI check.


FAILED tests/test_search.py::test_search_no_results
    assert search_documents("nonexistent") == []
    AssertionError: assert None == []

Iteration 1: Read the error, understand the assertion.

The loop first reads the test file to understand what behavior is expected:


Step 1: Read tests/test_search.py:45
        → Finds: assert search_documents("nonexistent") == []
        → Understanding: function should return empty list for no results

Iteration 2: Locate and read the source.


Step 2: Read src/search.py (find the search_documents function)

The model reads src/search.py and finds:


def search_documents(query: str) -> list[Document] | None:
    results = db.execute(
        "SELECT * FROM documents WHERE content LIKE %s",
        (f"%{query}%",)
    )
    if results:
        return [Document(**row) for row in results]
    # BUG: implicit return None when no results

Iteration 3: Hypothesize and fix.

The model identifies the bug: the function returns None implicitly when no results are found. The fix is to return an empty list. The model also notes the type annotation includes | None which should be updated, but fixes the functional bug first (smallest verifiable edit):


Edit(
    file_path="src/search.py",
    old_string="""    if results:
        return [Document(**row) for row in results]""",
    new_string="""    if results:
        return [Document(**row) for row in results]
    return []""",
)

Iteration 4: Verify the specific failing test.


Run: pytest tests/test_search.py::test_search_no_results -x
Result: PASSED

The targeted test passes. But the loop doesn't stop here — it checks for regressions.

Iteration 5: Check for regressions in the test file.


Run: pytest tests/test_search.py -x
Result: All 12 tests PASSED

No regressions within the same test module. The fix didn't break anything.

Iteration 6: Run the type checker.


Run: pyright src/search.py
Result: 1 error — return type annotation includes `None` but function never returns None

The type checker catches something the tests didn't: the type annotation is now wrong. The function never returns None anymore, but the annotation claims it can. This is a secondary issue that a human might have missed — or might have left as tech debt. The loop catches it because the oracle cascade includes type checking.

Iteration 7: Fix the type annotation.


Edit(
    file_path="src/search.py",
    old_string="def search_documents(query: str) -> list[Document] | None:",
    new_string="def search_documents(query: str) -> list[Document]:",
)

Iteration 8: Verify the type fix.


Run: pyright src/search.py
Result: 0 errors

Iteration 9: Check if the type change broke callers.

The type annotation change means any caller that was handling None returns may now have unreachable code. The loop checks:


Run: pyright src/ --outputjson | grep "search_documents"
Result: 0 errors (callers that checked for None just have unnecessary guards)

Iteration 10: Full verification.


Run: pytest tests/ -x --tb=short
Result: 147 tests PASSED
Run: ruff check src/
Result: 0 errors

Loop complete. Total iterations: 10. Human involvement: 0 during execution. Time: approximately 55 seconds. Cost: approximately $0.04 in API calls.

The trace reveals the loop's rhythm: read-hypothesize-fix-verify-expand. Each verification step either confirms progress or reveals additional work. The type checker finding the stale annotation is the loop being more thorough than most developers — who would have fixed the test, confirmed it passes, and moved on. The oracle cascade ensures comprehensive quality, not just "does it pass the one failing test."

34.6 The Harness Layer Hypothesis

All three systems — Claude Code, Cursor, Devin — use the same class of model (frontier LLMs, often literally the same model). Their capabilities diverge entirely because of the harness:

Harness Component Claude Code Cursor Devin
Context loading CLAUDE.md files Open tabs + LSP Full codebase index
Edit mechanism String-match replace Diff apply File write
Verification tools Bash (any CLI) LSP + terminal Terminal + browser
State persistence Conversation only Workspace files Persistent VM
Planning visibility Task list (explicit) Internal (hidden) Planner (visible)
Environment control User's machine User's IDE Sandboxed cloud
Concurrency Sequential Sequential Parallel (multiple terminals)
Session duration Minutes to hours Minutes Hours to days

This table demonstrates the central thesis: the model is a commodity; the harness is the product. Two teams using the same model will get radically different outcomes based on how they design the read-plan-edit-verify loop around it.

This has profound implications for practitioners building their own loops. You don't need a better model — you need a better harness. The marginal value of improving your skill file, adding a new verification check, or building a better retry strategy exceeds the marginal value of switching from one frontier model to another.

34.7 What Makes a Coding Loop Reliable

After examining three implementations, common patterns emerge — principles that hold regardless of which model or harness you use.

34.7.1 Always Read Before Editing

Every reliable coding loop reads the current file state before modifying it. Editing from memory (the model's recollection of what the file contains) fails frequently because:

  • The file may have been modified by a previous edit in the same loop.
  • The model's training data may contain an outdated version of the file.
  • Another process (or another agent in a fleet) may have modified the file concurrently.
  • The model may confuse two similar files in the same codebase.

Rule: Never edit blind. Always read, then edit. This rule costs one extra tool call per edit (the read), but it prevents entire classes of failures that would each cost 2-5 iterations to recover from.

34.7.2 Small, Verifiable Edits

The most reliable loops make the smallest edit that can be independently verified. A 200-line function rewrite is hard to verify incrementally. A 3-line fix followed by a test run is trivially verifiable. If the test fails, you know exactly which 3 lines caused it.


# Anti-pattern: Large edit, then verify everything at once
rewrite_entire_module()
run_all_tests()  # If this fails, where's the bug? Could be anywhere in 200 lines.

# Pattern: Small edits, verify each one
fix_return_type()
verify("pyright src/module.py")  # Passes? Continue.
add_missing_error_handling()
verify("pytest tests/test_module.py -x")  # Passes? Continue.
update_docstring()
verify("ruff check src/module.py")  # Passes? Continue.

Small edits also have a cost benefit: when an edit fails verification, you only revert and retry a small change. With large edits, a failure means replanning the entire approach.

34.7.3 Deterministic Oracles First

Always run the cheapest oracle first. A syntax error caught by the parser in 0.01 seconds saves a model inference call that would have failed anyway. A type error caught by pyright in 0.2 seconds saves a test run that would fail on an import error:


ORACLE_CASCADE = [
    ("syntax", "python -m py_compile {file}"),      # 10ms, free
    ("lint", "ruff check {file}"),                   # 50ms, free
    ("types", "pyright {file}"),                     # 200ms, free
    ("unit_tests", "pytest {test_file} -x"),         # 1-5s, free
    ("integration", "pytest tests/integration/ -x"),  # 5-30s, free
    ("model_review", model.judge(code, criteria)),   # 2-5s, $0.01-0.05
]

Each level in the cascade is a filter. If 60% of errors are caught by syntax + lint (the cheapest checks), then 60% of your verification cost is effectively zero. The expensive checks only run on code that already passes the cheap checks.

34.7.4 Bounded Retry with Escalation

The loop must have a maximum retry count per verification failure. Without it, a loop can spin indefinitely on an issue it cannot solve:


MAX_RETRIES = 3

for attempt in range(MAX_RETRIES):
    result = await edit_and_verify()
    if result.passed:
        break
    if attempt == MAX_RETRIES - 1:
        # Escalate: surface to user with full context
        raise LoopStuck(
            message="Failed to resolve after 3 attempts",
            error=result.error,
            attempts=[a.summary for a in attempts],
        )

The choice of 3 retries isn't arbitrary. Empirically, if the model can't fix an issue in 3 attempts, the fourth attempt is unlikely to succeed either — the model is either missing information (needs human input) or approaching the problem incorrectly (needs a different strategy, not another iteration of the same strategy).

34.7.5 Context Window Management

Long coding sessions accumulate context: file reads, edit results, error traces, test output. Without management, the context window fills and the model loses access to early information — including the original task description. Strategies:

  1. Summarize and discard: After a task completes, replace the full trace with a one-line summary: "Task 1 complete: added pyjwt dependency and created auth/utils.py."
  2. Sliding window: Keep only the last N interactions in full detail. Older interactions become summaries.
  3. Hierarchical context: Full detail for current task, summaries for completed tasks, one-liners for tasks completed more than 5 iterations ago.

The best implementation combines all three: summarize completed work, keep a sliding window of recent details, and maintain a hierarchical structure that the model can expand on demand (by re-reading files if it needs details about earlier work).

34.8 Building Your Own Coding Loop

For practitioners building a custom coding loop (perhaps for a proprietary codebase with unusual requirements, or to integrate coding into a larger multi-domain workflow), here's the minimal viable implementation:


from dataclasses import dataclass
from pathlib import Path
import subprocess
import asyncio


@dataclass
class LoopConfig:
    skill_file: Path
    verify_commands: list[str]
    max_retries: int = 3
    max_iterations: int = 50


@dataclass
class VerifyResult:
    passed: bool
    output: str


class CodingLoop:
    def __init__(self, config: LoopConfig, model_client):
        self.config = config
        self.model = model_client
        self.history: list[dict] = []
        self.iteration = 0
    
    async def run(self, task: str) -> str:
        """Execute the full coding loop for a given task."""
        # Load skill context
        skills = self.config.skill_file.read_text()
        self.history.append({"role": "system", "content": skills})
        self.history.append({"role": "user", "content": task})
        
        while self.iteration < self.config.max_iterations:
            self.iteration += 1
            
            # Get model's next action
            response = await self.model.generate(self.history)
            self.history.append({"role": "assistant", "content": response})
            
            # Parse tool calls from response
            tool_calls = self.parse_tool_calls(response)
            
            if not tool_calls:
                # Model produced a final answer, no more actions needed
                return response
            
            # Execute tool calls
            for call in tool_calls:
                result = await self.execute_tool(call)
                self.history.append({"role": "tool", "content": result})
            
            # After edits, run verification
            if any(c.name == "edit" for c in tool_calls):
                verify_result = await self.verify()
                if not verify_result.passed:
                    self.history.append({
                        "role": "tool",
                        "content": f"Verification failed:\n{verify_result.output}"
                    })
        
        return "Loop budget exhausted without completion."
    
    async def verify(self) -> VerifyResult:
        """Run all verification commands in sequence."""
        for cmd in self.config.verify_commands:
            proc = await asyncio.create_subprocess_shell(

                stderr=asyncio.subprocess.PIPE,

  • File read/write tools with conflict detection (check if file changed since last read)
  • Git integration (branch, commit, diff — so the loop can save progress)
  • Context window management (summarization when history exceeds a token threshold)

34.9 The Key Insight

The coding loop is not a new idea. It's make with an AI in the loop. It's CI/CD with the model as the developer. It's TDD with the model writing both the code and responding to test failures.

What's new is that the model is good enough to close the loop without a human at every iteration. The harness — skills, tools, oracles, retry logic — was always the hard part. We had test suites for decades. We had linters for decades. We had type checkers for decades. What we lacked was an agent capable of reading the failures these tools produce and generating correct fixes in response. As of 2026, we have that agent.

The practitioner's job has shifted from "write code" to "design the loop that writes code." This is the same shift that happened when CI/CD moved from "run tests manually" to "design the pipeline that runs tests automatically." The skill isn't in running the tests — it's in designing which tests to run, in what order, with what thresholds, with what retry strategy, with what escalation path.

The practitioners who thrive in this new paradigm are not the fastest typists or the most encyclopedic memorizers of API signatures. They are the ones who design the best loops — the tightest feedback cycles, the most discriminating oracles, the most efficient harnesses. They are, as the opening quote of Chapter 1 stated, loop designers.
