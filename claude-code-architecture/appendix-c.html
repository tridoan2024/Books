Appendix C: Design Pattern Catalog

How to Use This Catalog

This appendix collects every design pattern used in the AI CLI agent architecture discussed in this book. Each pattern includes its intent, when to use it, a structural diagram, a concrete example from the architecture, and the trade-offs involved.

The patterns are organized into four categories: Structural (how components are composed), Behavioral (how components interact), Concurrency (how parallel work is managed), and AI-Specific (patterns unique to AI agent systems that have no counterpart in traditional software engineering).

For each pattern, the "Example from Claude Code" section references the chapter where the pattern is discussed in depth. This catalog is a lookup table --- use it when you encounter a design problem and need to identify the right pattern, or when reading the codebase and want to understand the pattern you are looking at.

Structural Patterns

Structural patterns define how components are organized, composed, and connected. They determine the static architecture of the system.

Registry

Intent: Centralize discovery and access to a collection of self-registering components, decoupling producers from consumers.

When to Use: You have a growing set of components (tools, plugins, providers) that must be discoverable by multiple consumers, and you want adding a new component to be a single-file change.

Structure:

graph TB
    subgraph Producers["Self-Registering Producers"]
        P1["Component A"]
        P2["Component B"]
        P3["Component C"]
        P4["Component N..."]
    end

    REG["Registry<br/>- register(component)<br/>- getAll(): Component[]<br/>- getByName(name): Component"]

    subgraph Consumers["Discovery Consumers"]
        C1["Consumer X"]
        C2["Consumer Y"]
        C3["Consumer Z"]
    end

    P1 -->|register| REG
    P2 -->|register| REG
    P3 -->|register| REG
    P4 -->|register| REG

    REG -->|query| C1
    REG -->|query| C2
    REG -->|query| C3

Example from Claude Code: The Tool Registry (Chapter 13) manages 35+ built-in tools and an unlimited number of MCP tools. Each tool registers itself with the registry by providing a name, schema, and execution function. The agent loop queries the registry for tool schemas (sent to the API), the permission system queries it for tool metadata (used in rule matching), and the UI queries it for display information. Adding a new tool means creating one file with a registration call --- no other files change.

// Tool registration: self-contained in each tool file
const readTool: Tool = {
  name: "Read",
  schema: z.object({ file_path: z.string(), offset: z.number().optional() }),
  async execute(input) {
    const content = await fs.readFile(input.file_path, "utf-8");
    return { type: "text", text: content };
  },
  userFacingName: "Read File",
};
toolRegistry.register(readTool);

// Consumer: agent loop queries the registry
const tools = toolRegistry.getAll();
const schemas = tools.map(t => t.toApiSchema());

Trade-offs:

Advantage Cost
Adding/removing components is a single-file change Registry is a global coordination point --- a bug here affects all consumers
Consumers are decoupled from producers Registration order may matter (and is implicit, not explicit)
Supports dynamic registration (MCP tools discovered at runtime) Testing requires either mocking the registry or resetting it between tests
Schema generation is centralized The registry becomes a large file in big systems

Adapter (Provider Abstraction)

Intent: Present a uniform interface to multiple external systems that have different APIs, allowing the application to switch between them without changing calling code.

When to Use: You integrate with multiple external services that serve the same purpose (API providers, cloud platforms, storage backends) but have different SDKs and protocols.

Structure:

graph TB
    APP["Application Code<br/>(calls unified interface)"]

    IFACE["Provider Interface<br/>- sendMessage()<br/>- streamResponse()<br/>- getCapabilities()"]

    subgraph Adapters["Concrete Adapters"]
        A1["Anthropic Adapter<br/>(Direct API)"]
        A2["Bedrock Adapter<br/>(AWS SDK)"]
        A3["Vertex Adapter<br/>(GCP SDK)"]
    end

    APP --> IFACE
    IFACE --> A1
    IFACE --> A2
    IFACE --> A3

Example from Claude Code: The API Client (Chapter 10) defines a provider interface with methods for sending messages, streaming responses, and querying model capabilities. Three adapters implement this interface: one for the Anthropic API (direct HTTP), one for AWS Bedrock (AWS SDK with SigV4 authentication), and one for Google Vertex AI (GCP SDK with OAuth). The agent loop calls provider.sendMessage() without knowing which cloud the request reaches.

The adapters handle provider-specific concerns: Bedrock requires region-specific endpoints and IAM credential resolution, Vertex requires project ID and location, and the direct API requires an API key. The unified interface hides all of this behind a single method signature.

// The interface all providers implement
interface ApiProvider {
  sendMessage(messages: Message[], tools: ToolSchema[]): AsyncGenerator<StreamEvent>;
  getModelCapabilities(modelId: string): ModelCapabilities;
  getMaxOutputTokens(modelId: string): number;
}

// Consumer code is provider-agnostic
const provider = resolveProvider(config);  // returns Anthropic, Bedrock, or Vertex
for await (const event of provider.sendMessage(messages, tools)) {
  handleStreamEvent(event);
}

Trade-offs:

Advantage Cost
Provider switching requires zero application code changes The unified interface is limited to the intersection of all providers' capabilities
Testing can use a mock provider without cloud credentials Provider-specific features (Bedrock's custom model endpoints) require escape hatches
New providers are additive changes Each adapter must be kept in sync with its provider's SDK updates independently
Enterprise customers choose their cloud provider Adapter layer adds indirection that makes debugging network issues harder

Cascade (Settings Merge)

Intent: Resolve a configuration value by checking multiple sources in priority order, where higher-priority sources override lower-priority ones, with special rules for certain source types.

When to Use: Multiple stakeholders (platform, organization, user, project, invocation) need to control the same configuration, with clear precedence rules and the ability to lock certain values.

Structure:

graph LR
    subgraph Sources["Priority: Low to High"]
        S1["Defaults"]
        S2["Managed Policy"]
        S3["User Settings"]
        S4["Project Settings"]
        S5["Local Settings"]
        S6["Environment Vars"]
        S7["CLI Arguments"]
    end

    MERGE["Cascade Resolver<br/>- For each field:<br/>  check sources high to low<br/>  first non-null wins<br/>- Policy fields: locked"]

    RESULT["Resolved<br/>Configuration"]

    S1 --> MERGE
    S2 --> MERGE
    S3 --> MERGE
    S4 --> MERGE
    S5 --> MERGE
    S6 --> MERGE
    S7 --> MERGE
    MERGE --> RESULT

Example from Claude Code: The 7-layer configuration cascade (Chapter 5) resolves every setting by checking sources from highest priority (CLI arguments) to lowest (built-in defaults). The first non-null value wins. But managed/MDM settings can lock fields, preventing any higher-priority source from overriding them --- an enterprise security policy that disables certain tools cannot be overridden by a developer's local settings.

The merge semantics vary by field type: scalar values use last-writer-wins, arrays are concatenated (permission rules from all sources combine), and objects are deep-merged with higher-priority keys overriding lower-priority keys.

// Simplified cascade resolution
function resolveConfig(): ResolvedConfig {
  const layers = [
    loadDefaults(),           // Layer 1
    loadManagedSettings(),    // Layer 2 (can lock fields)
    loadUserSettings(),       // Layer 3
    loadProjectSettings(),    // Layer 4
    loadLocalSettings(),      // Layer 5
    loadEnvVars(),            // Layer 6
    loadCliArgs(),            // Layer 7
  ];
  return deepMerge(layers, { respectLocks: true });
}

Trade-offs:

Advantage Cost
Each stakeholder has a clear, non-overlapping configuration surface Debugging "why is this setting this value?" requires checking 7 sources
Policy enforcement is architecturally guaranteed Merge semantics for complex types (arrays, nested objects) are non-obvious
Adding a new source layer is a localized change Performance: cascade resolution on every config read is wasteful (mitigated by resolving once at startup and caching)
Defaults ensure the system always works 7 layers is conceptually heavy for new team members

Pipeline (Tool Execution)

Intent: Process a request through a sequence of stages, where each stage transforms, validates, or enriches the request before passing it to the next stage.

When to Use: A request requires multiple processing steps (validation, authorization, transformation, execution, formatting) that should be independently testable and reorderable.

Structure:

graph LR
    INPUT["Tool Call<br/>(from model)"] --> V["Stage 1:<br/>Schema<br/>Validation"]
    V --> P["Stage 2:<br/>Permission<br/>Check"]
    P --> H["Stage 3:<br/>Hook<br/>Execution"]
    H --> S["Stage 4:<br/>Security<br/>Analysis"]
    S --> E["Stage 5:<br/>Tool<br/>Execution"]
    E --> F["Stage 6:<br/>Result<br/>Formatting"]
    F --> OUTPUT["Tool Result<br/>(to model)"]

    V -.->|reject| ERR1["Validation Error"]
    P -.->|deny| ERR2["Permission Denied"]
    H -.->|block| ERR3["Hook Block"]
    S -.->|block| ERR4["Security Block"]

Example from Claude Code: The tool execution pipeline (Chapter 13) processes every tool call through six stages: (1) schema validation (Zod) rejects malformed inputs, (2) permission evaluation checks the 8-source rule cascade, (3) PreToolUse hooks run user-defined checks, (4) security analysis runs the bash parser for shell commands, (5) execution runs the tool's implementation, and (6) result formatting converts raw output into the format expected by the API. Any stage can halt the pipeline with an error, and each stage is independently testable.

The pipeline also handles the Bash tool's 13-phase startup sequence (Chapter 4), the message assembly pipeline (Chapter 8), and the streaming event processing pipeline (Chapter 11). The pattern recurs at multiple scales throughout the architecture.

Trade-offs:

Advantage Cost
Each stage is independently testable and replaceable Pipeline ordering is implicit --- reordering stages can break security invariants
New stages (logging, metrics, caching) can be inserted without modifying existing stages Error handling must account for failure at any stage, increasing complexity
Clear separation of concerns: validation does not know about security Latency is the sum of all stages (mitigated by fast-path exits for cached permissions)
Debugging can target individual stages Stage interfaces must be stable --- changing the data passed between stages affects all downstream stages

Behavioral Patterns

Behavioral patterns define how components communicate, react to events, and make decisions at runtime.

State Machine (Agent Loop, MCP Lifecycle, Streaming)

Intent: Model a component's behavior as a finite set of states with explicit transitions, making the valid state space enumerable and invalid states unrepresentable.

When to Use: A component has distinct operational modes (running, waiting, error), and the valid transitions between modes must be enforced. Especially valuable when the component's behavior differs significantly between states.

Structure:

stateDiagram-v2
    [*] --> Idle
    Idle --> Assembling: user_prompt
    Assembling --> Streaming: api_call
    Streaming --> Processing: tool_use_event
    Processing --> Assembling: tool_result
    Streaming --> Idle: end_turn
    Streaming --> Error: api_error
    Processing --> Error: tool_error
    Error --> Idle: recovery
    Idle --> [*]: exit

Example from Claude Code: Three subsystems use explicit state machines:

Agent Loop (Chapter 7): The agentic loop cycles through Idle, Assembling (building the prompt), Streaming (receiving tokens), and Processing (executing tool calls). The loop has 10 exit conditions (user abort, max turns, end_turn, error, interrupt, tool_error, context_limit, stop_sequence, cost_limit, guardrail) and 7 continuation conditions (tool result, follow-up needed, partial completion, user input, retry needed, checkpoint saved, context compacted). Each state transition is explicit, and invalid transitions (e.g., Processing directly to Idle without returning a tool result) are structurally impossible.

MCP Server Lifecycle (Chapter 22): Each MCP server connection progresses through Disconnected, Connecting, Negotiating (capability exchange), Connected, and Failed states. Reconnection attempts only trigger from Failed state, preventing duplicate connection attempts.

Streaming Pipeline (Chapter 11): The SSE parser transitions through WaitingForEvent, ReadingType, ReadingData, and Processing states as it parses the server-sent event stream. The state machine ensures that partial data is never processed as a complete event.

Trade-offs:

Advantage Cost
Invalid states are unrepresentable --- eliminates an entire class of bugs State explosion: adding a new state requires defining transitions to/from all existing states
Behavior is predictable --- given a state and an event, the next state is deterministic State machines are harder to extend than free-form logic (by design --- this is a feature)
Debugging is straightforward: log the state transitions Complex logic may require hierarchical state machines, adding implementation complexity
Visual documentation (state diagrams) is automatically accurate States must be identified upfront; discovering a missing state late requires significant rework

Observer (Hooks System)

Intent: Allow components to react to lifecycle events without the event source knowing about the observers, enabling extensibility without modifying core code.

When to Use: You need extensibility points where user-defined or plugin-defined code runs in response to system events, and the set of observers is not known at compile time.

Structure:

    subgraph "Event Sources"
        SRC1["Tool Execution"]
        SRC2["Session Lifecycle"]
        SRC3["User Input"]
    end

    BUS["Event Dispatcher<br/>- on(event, handler)<br/>- emit(event, data)<br/>- 27 lifecycle events"]

    subgraph "Observers (Hooks)"
        H1["block-destructive.sh<br/>(PreToolUse)"]
        H2["secret-scan.sh<br/>(PreToolUse)"]
        H3["auto-lint.sh<br/>(PostToolUse)"]
        H4["notify.sh<br/>(Notification)"]
    end

    SRC1 -->|emit| BUS
    SRC2 -->|emit| BUS
    SRC3 -->|emit| BUS

    BUS -->|dispatch| H1
    BUS -->|dispatch| H2
    BUS -->|dispatch| H3
    BUS -->|dispatch| H4

Example from Claude Code: The hook system (Chapter 29) defines 27 lifecycle events across 5 event categories. Users register shell scripts as observers for specific events in settings.json. When the event fires, the dispatcher runs all registered hooks, passing event data as JSON on stdin. PreToolUse hooks can block actions (exit code 2), PostToolUse hooks run after completion, and Notification hooks deliver alerts. The core system has no knowledge of what hooks are registered --- it only knows how to emit events and interpret exit codes.

The hook protocol uses a structured JSON output format on stderr for blocking decisions:

{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Blocked: destructive command detected"
  }
}

Trade-offs:

Advantage Cost
Users extend behavior without modifying agent source code Debugging requires tracing which hooks fired and what they returned
Hooks are isolated processes --- a crashing hook does not crash the agent Hook execution adds latency to every observed event (mitigated by timeouts)
New events can be added without modifying existing hooks Hook ordering is implicit --- hooks for the same event run in registration order
Shell-based hooks work in any language The JSON stdin/stdout/stderr protocol adds implementation overhead for hook authors

Strategy (Permission Modes)

Intent: Define a family of interchangeable algorithms, encapsulated in separate objects, allowing the algorithm to vary independently from the code that uses it.

When to Use: A component's behavior must vary based on a mode or policy selection, and the modes are known at design time but selected at runtime.

Structure:

graph TB
    EVAL["Permission Evaluator<br/>evaluate(tool, args)"]

    subgraph Strategies["Permission Mode Strategies"]
        S1["Plan Mode<br/>(always ask)"]
        S2["Default Mode<br/>(rule-based)"]
        S3["Auto Mode<br/>(AI classifier)"]
        S4["Trust Mode<br/>(always allow)"]
        S5["Deny Mode<br/>(always deny)"]
        S6["Bypass Mode<br/>(SDK internal)"]
    end

    EVAL --> S1
    EVAL --> S2
    EVAL --> S3
    EVAL --> S4
    EVAL --> S5
    EVAL --> S6

Example from Claude Code: The permission system (Chapter 18) supports 6 modes, each implementing a different evaluation strategy. Plan mode prompts for every action (maximum safety). Default mode evaluates the 8-source rule cascade, checking deny rules first, then ask rules, then allow rules. Auto mode runs a fast AI classifier that analyzes the tool name, arguments, and conversation context to determine risk level. Trust mode skips evaluation entirely for maximum speed. Bypass mode is used internally by the SDK for pre-authorized operations.

The agent loop calls evaluatePermission(tool, args) and gets back allow/deny/ask --- it does not know which strategy made the decision. Mode switching is a runtime configuration change, meaning the same codebase supports workflows ranging from fully autonomous (trust mode) to fully supervised (plan mode).

Trade-offs:

Advantage Cost
Adding a new mode requires one new strategy, no changes to the evaluator All strategies must conform to the same interface, limiting mode-specific capabilities
Mode switching is a runtime configuration change Testing requires exercising each strategy independently and in combination
The agent loop is decoupled from permission logic The strategy selection logic (which mode is active?) adds a layer of indirection
Users choose their safety/speed trade-off More modes means more documentation and more confusion for new users

Chain of Responsibility (Security Layers)

Intent: Pass a request through a chain of handlers, where each handler either processes the request or passes it to the next handler, enabling layered security checks.

When to Use: Multiple independent checks must evaluate a request, any check can reject it, and the checks should be composable and independently deployable.

Structure:

graph LR
    REQ["Bash Command"] --> L1["Layer 1:<br/>Pattern<br/>Blocklist"]
    L1 -->|pass| L2["Layer 2:<br/>AST<br/>Analysis"]
    L2 -->|pass| L3["Layer 3:<br/>Path<br/>Analysis"]
    L3 -->|pass| L4["Layer 4:<br/>Permission<br/>Rules"]
    L4 -->|pass| L5["Layer 5:<br/>User<br/>Confirmation"]
    L5 -->|allow| EXEC["Execute"]

    L1 -.->|block| DENY["Denied"]
    L2 -.->|block| DENY
    L3 -.->|block| DENY
    L4 -.->|block| DENY
    L5 -.->|deny| DENY

Example from Claude Code: Bash command security (Chapters 15, 19) uses defense-in-depth with five layers. The first layer is a fast pattern blocklist that catches obvious threats (rm -rf /, DROP TABLE, curl | bash) using string matching --- cheap and fast. The second layer parses the command into an AST and analyzes the structure for dangerous patterns that string matching misses (command substitution, process substitution, heredoc injection). The third layer extracts file paths from the AST and checks them against sensitive locations. The fourth layer evaluates the command against permission rules from the configuration cascade. The fifth layer presents uncertain cases to the user for confirmation.

Layers are ordered by cost: cheap pattern matching first, expensive AST parsing second, human-in-the-loop last. If the first layer blocks a command, the parser never runs. This ordering is critical for performance --- the pattern blocklist handles 80% of dangerous commands in microseconds.

Trade-offs:

Advantage Cost
Defense-in-depth: multiple independent layers must all be bypassed Latency is the sum of all layers (mitigated by fast-path rejection at early layers)
Each layer can be tested, deployed, and updated independently A gap between layers (something that no layer checks) is a security vulnerability
Fail-open vs fail-closed is configurable per layer Debugging requires understanding which layer rejected and why
New layers can be added without modifying existing ones Layer ordering is a security-critical decision --- wrong ordering degrades both performance and security

Concurrency Patterns

Concurrency patterns manage parallel execution, synchronization, and resource sharing.

Fan-Out/Fan-In (Subagent Orchestration)

Intent: Distribute a task across multiple parallel workers, then collect and aggregate their results into a single response.

When to Use: A task can be decomposed into independent subtasks that benefit from parallel execution, and the results must be synthesized.

Structure:

graph TB
    TASK["Complex Task<br/>(e.g., multi-file review)"]

    subgraph "Fan-Out"
        TASK --> W1["Subagent 1<br/>(security review)"]
        TASK --> W2["Subagent 2<br/>(code quality)"]
        TASK --> W3["Subagent 3<br/>(performance)"]
    end

    subgraph "Fan-In"
        W1 --> AGG["Result Aggregator<br/>- Merge findings<br/>- Deduplicate<br/>- Rank by severity"]
        W2 --> AGG
        W3 --> AGG
    end

    AGG --> RESULT["Unified Review<br/>Report"]

Example from Claude Code: The Multi-Agent system (Chapters 24-25) fans out work to subagents with restricted capabilities. A code review might spawn a security reviewer (Opus model, Bash access for running security scanners), a code quality reviewer (Sonnet model, read-only access), and a performance analyzer (Sonnet model, profiling access) in parallel. Each subagent returns findings in a structured format. The orchestrator fans in: deduplicating overlapping findings, normalizing severity levels, and producing a unified report.

Each subagent runs in an isolated context --- its own conversation history, its own token budget, its own tool restrictions. The isolation prevents one subagent's context from polluting another's reasoning. Subagent failures are contained: if the security reviewer hits a rate limit, the code quality reviewer continues working.

// Simplified fan-out/fan-in orchestration
const subtasks = [
  spawnAgent("security-reviewer", { files, tools: ["Read", "Grep", "Bash"] }),
  spawnAgent("code-reviewer",     { files, tools: ["Read", "Grep"] }),
  spawnAgent("perf-analyzer",     { files, tools: ["Read", "Grep", "Bash"] }),
];

const results = await Promise.allSettled(subtasks);
const findings = aggregateFindings(results.filter(r => r.status === "fulfilled"));

Trade-offs:

Advantage Cost
Wall-clock time reduction: N parallel subagents approach 1/N latency API cost scales linearly with the number of subagents
Each subagent has a focused context, improving reasoning quality Result aggregation is non-trivial: deduplication, conflict resolution, severity normalization
Subagent failures are isolated --- one failure does not abort all work Coordinating cancellation when the user aborts mid-fan-out requires careful lifecycle management
Different models for different subtasks optimizes cost/quality Rate limits may throttle parallel requests (mitigated by staggered launches)

Pipeline (Streaming)

Intent: Process a continuous stream of data through a sequence of transformation stages, where each stage operates on individual items as they arrive.

When to Use: Data arrives incrementally (tokens from an API, bytes from a network connection) and must be processed in real-time without waiting for the complete input.

Structure:

graph LR
    SRC["SSE Stream<br/>(API response)"] --> P1["Stage 1:<br/>SSE Parser<br/>(bytes to events)"]
    P1 --> P2["Stage 2:<br/>Event Router<br/>(text vs tool_use)"]
    P2 --> P3a["Stage 3a:<br/>Token Buffer<br/>(text accumulation)"]
    P2 --> P3b["Stage 3b:<br/>Tool Call<br/>Assembler"]
    P3a --> P4["Stage 4:<br/>Markdown<br/>Renderer"]
    P3b --> P5["Stage 5:<br/>Tool Dispatch"]
    P4 --> UI["Terminal<br/>Display"]
    P5 --> UI

Example from Claude Code: The streaming pipeline (Chapter 11) processes the API response token-by-token. SSE bytes arrive from the network, are parsed into events, routed by type (text content deltas vs. tool use blocks), accumulated (text tokens are buffered for markdown rendering; tool use JSON is assembled incrementally from partial fragments), rendered (streaming markdown updates the terminal display as tokens arrive), and dispatched (complete tool calls enter the execution pipeline). Each stage operates independently, and backpressure propagates upstream when the terminal cannot render fast enough.

The key design challenge is partial data: a tool use block arrives as a series of JSON fragments across multiple SSE events. The assembler stage must buffer fragments, detect completion, parse the assembled JSON, and validate it against the tool schema --- all without blocking the text token rendering that may be interleaved with tool use events.

Trade-offs:

Advantage Cost
First-token-to-screen latency is minimized (no waiting for complete response) Error handling is complex: a parse error at stage 1 must propagate cleanly through all downstream stages
Memory usage is bounded (only buffering current stage data, not entire response) Debugging requires correlating state across multiple stages simultaneously
Natural decomposition into testable stages Backpressure management adds complexity (what happens when the renderer falls behind?)
Interleaved text and tool use are handled naturally by the router stage Reassembling fragmented data (partial JSON) requires careful state management

Producer-Consumer (Input Buffer)

Intent: Decouple the production of work items from their consumption, using a buffer to absorb rate differences between producer and consumer.

When to Use: The producer generates work items at an unpredictable rate (user typing, API responses) and the consumer processes them at a different rate, and you need to prevent data loss without blocking the producer.

Structure:

graph LR
    PROD["Producer<br/>(user keystrokes,<br/>paste events)"] --> BUF["Input Buffer<br/>(queue with<br/>size limit)"]
    BUF --> CONS["Consumer<br/>(input processor,<br/>tab completion)"]

Example from Claude Code: The input processing system (Chapter 28) uses a buffer between keystroke capture and input processing. During the 135ms module loading phase at startup, the user may already start typing. The early input capture system hooks process.stdin immediately and buffers keystrokes in a queue. When the REPL mounts and the input processor is ready, it replays the buffer into the input field. The user never notices the delay --- their typing appears instantaneously when the UI renders.

The same pattern applies during normal operation: when the user types faster than the tab completion engine can respond, keystrokes queue in the buffer. When the user pastes a large block of text, the entire paste enters the buffer at once and is processed incrementally. This prevents dropped keystrokes and ensures that paste events are handled atomically.

Trade-offs:

Advantage Cost
Producer never blocks waiting for consumer Unbounded buffers can consume unbounded memory (mitigated by buffer size limits)
Rate differences are absorbed without data loss Buffer adds latency between production and consumption
Clean separation enables independent testing Shutdown requires draining the buffer, adding complexity to the graceful shutdown path
Startup typing is preserved seamlessly Buffer overflow policy (drop oldest? drop newest? block?) must be decided explicitly

AI-Specific Patterns

These patterns have no counterpart in traditional software engineering. They emerge from the unique properties of AI agent systems: non-deterministic execution, natural language interfaces, token-limited context, and the need to test systems whose outputs vary between runs.

Agentic Loop

Intent: Repeatedly cycle through prompt assembly, model inference, action execution, and observation until the task is complete or an exit condition is met.

When to Use: Building any AI agent that uses tools. This is the fundamental pattern of agentic AI systems --- the equivalent of the event loop in GUI programming or the request-response cycle in web servers.

Structure:

graph TB
    START["User Goal"] --> ASSEMBLE["Assemble Prompt<br/>(system + history +<br/>tool results)"]
    ASSEMBLE --> INFER["Model Inference<br/>(streaming response)"]
    INFER --> DECIDE{Response Type?}
    DECIDE -->|text only| CHECK{"Exit<br/>Condition?"}
    DECIDE -->|tool use| EXEC["Execute Tool(s)"]
    EXEC --> OBSERVE["Observe Result<br/>(add to history)"]
    OBSERVE --> ASSEMBLE
    CHECK -->|exit| DONE["Return Result"]
    CHECK -->|continue| ASSEMBLE

Example from Claude Code: The agent loop (Chapter 7) implements this pattern with 10 exit conditions (end_turn, max_turns, user_abort, error, interrupt, tool_error, context_limit, stop_sequence, cost_limit, guardrail) and 7 continuation conditions (tool_result, follow_up, partial_completion, user_input, retry_needed, checkpoint_saved, context_compacted). The loop is not a simple while loop --- it is a state machine (see State Machine pattern above) with explicit transitions and invariants.

The critical design decision: the loop does not assume convergence. An AI agent can loop forever if the model repeatedly generates tool calls without making progress. The exit conditions are safety valves, not optimistic assumptions. Max turns prevents infinite loops. Cost limits prevent runaway spending. Context limits trigger compaction before the window overflows. Cycle detection identifies repeated tool calls with identical arguments.

// Simplified agentic loop structure
while (true) {
  const messages = assembleContext(conversation, tools);
  const response = await streamModelResponse(messages);

  for (const block of response.contentBlocks) {
    if (block.type === "text") {
      renderText(block.text);
    } else if (block.type === "tool_use") {
      const result = await executeToolWithPermissions(block);
      conversation.addToolResult(block.id, result);
    }
  }

  const exitReason = checkExitConditions(response, conversation);
  if (exitReason) return { result: response, reason: exitReason };
}

Trade-offs:

Advantage Cost
Enables autonomous multi-step task completion Non-deterministic: the same goal may take 2 turns or 20
Natural decomposition of complex tasks into tool calls Cost scales with turn count, which is hard to predict
Model decides what tools to use and in what order The loop can "spin" without progress if the model is confused
Recoverable: errors in one turn can be corrected in the next Each turn adds to conversation history, consuming context window

Tool-Use Conversation

Intent: Structure the conversation between the application and the model as an alternating sequence of assistant messages (containing tool calls) and user messages (containing tool results), enabling the model to build on previous observations.

When to Use: The model needs to see the results of its previous actions to decide what to do next. This is how LLMs interact with external systems --- the conversation format is the integration protocol.

Structure:

sequenceDiagram
    participant App as Application
    participant Model as LLM
    participant Tool as Tool System

    App->>Model: System + User prompt
    Model->>App: "I'll read the file" + tool_use(Read, {path})
    App->>Tool: Execute Read
    Tool->>App: File contents
    App->>Model: tool_result(contents)
    Model->>App: "I see a bug on line 42" + tool_use(Edit, {fix})
    App->>Tool: Execute Edit
    Tool->>App: Edit result
    App->>Model: tool_result(success)
    Model->>App: "Fixed. Here's what I changed."

Example from Claude Code: The message architecture (Chapter 8) maintains the conversation in the Anthropic API's message format: system (assembled once per turn), user (human messages and tool results), and assistant (model text and tool calls). Tool results are injected as user role messages with tool_result content blocks, keyed to the tool_use_id from the assistant's message. This structure enables the model to correlate results with requests and build up understanding across multiple tool calls.

The protocol has a strict constraint: tool_result messages must immediately follow the assistant message containing the corresponding tool_use. This means tool execution order must match the order of tool calls in the assistant's message. When the model makes multiple tool calls in a single response, all must be executed and their results returned before the next inference call.

Trade-offs:

Advantage Cost
Model has full context of previous actions and observations Conversation grows monotonically, consuming more tokens (and cost) per turn
Supports multi-step reasoning: model can build on earlier findings Older context is eventually compacted, losing detail from early turns
Standard API format enables provider switching The alternating user/assistant structure is rigid --- side information must be injected as user messages
Tool result correlation via IDs prevents confusion when multiple tools are called Multiple tool calls per turn must all complete before the next inference, preventing partial-result reasoning

Context Compaction

Intent: Reduce the size of the conversation history when it approaches the context window limit, preserving the most important information while discarding or summarizing less critical content.

When to Use: The agent loop runs for many turns, and the accumulated conversation exceeds the model's context window. Without compaction, the session must end.

Structure:

graph TB
    CONV["Full Conversation<br/>(approaching token limit)"]

    CONV --> ANALYZE["Analyze Turns<br/>- Recency (newer = higher priority)<br/>- Relevance (tool results with active code)<br/>- Size (large outputs = summarizable)"]

    ANALYZE --> COMPACT["Compact<br/>- Summarize old turns<br/>- Truncate large tool results<br/>- Preserve recent N turns verbatim<br/>- Keep system prompt intact"]

    COMPACT --> RESULT["Compacted Conversation<br/>(within token budget)"]

    RESULT --> VERIFY["Verify<br/>- System prompt intact?<br/>- Recent context preserved?<br/>- Coherent conversation flow?"]

Example from Claude Code: Context window management (Chapter 9) triggers automatic compaction when the conversation reaches 80% of the model's context limit. The algorithm preserves the system prompt (always), the most recent 5 turns (always), and selectively summarizes or truncates older turns. Large tool results (full file contents, lengthy command output) are prime candidates for summarization --- a 500-line file read can be summarized as "Read config.ts (500 lines): Express server configuration with middleware setup, route definitions, and error handling."

The compaction is performed by the model itself --- a separate inference call with instructions to summarize the old conversation while preserving key decisions, file paths mentioned, and any errors encountered. The user can also trigger compaction manually with /compact [focus], providing a focus keyword that biases the compaction to preserve information related to that topic.

// Compaction trigger check
function shouldCompact(conversation: Message[], modelLimit: number): boolean {
  const currentTokens = countTokens(conversation);
  return currentTokens > modelLimit * 0.8;
}

// Compaction preserves structure
function compact(conversation: Message[]): Message[] {
  const systemPrompt = conversation[0];        // Always preserved
  const recentTurns = conversation.slice(-10);  // Recent context preserved
  const oldTurns = conversation.slice(1, -10);  // Candidates for summarization

  const summary = await summarize(oldTurns);
  return [systemPrompt, summary, ...recentTurns];
}

Trade-offs:

Advantage Cost
Enables arbitrarily long sessions without hitting context limits Compaction loses information --- the agent may "forget" earlier findings
Automatic trigger prevents mid-conversation context limit errors The compaction inference call adds latency and cost
User-directed focus preserves domain-relevant context Compaction quality depends on the model's summarization ability
Preserves recent context at full fidelity where it matters most The agent cannot refer back to exact code from compacted turns

VCR Testing (Record/Replay)

Intent: Record the inputs and outputs of non-deterministic external calls (API requests to LLMs), then replay the recordings during tests to make test execution deterministic, fast, and free of API costs.

When to Use: Testing code that calls an LLM API, where the response varies between calls and costs money per request.

Structure:

graph TB
    subgraph "Recording Mode (CI nightly / manual)"
        TEST1["Test Case"] --> CODE1["Application Code"]
        CODE1 --> API1["Real API Call"]
        API1 --> REC["VCR Recorder<br/>(save request + response)"]
        REC --> TAPE["Cassette File<br/>(JSON)"]
    end

    subgraph "Playback Mode (every test run)"
        TEST2["Test Case"] --> CODE2["Application Code"]
        CODE2 --> VCR["VCR Interceptor<br/>(match request then replay)"]
        VCR --> TAPE
        VCR --> CODE2
    end

Example from Claude Code: The testing infrastructure (Chapter 31) uses VCR-style recording to make AI agent tests deterministic. When recording, actual API calls are made and the request/response pairs are saved as "cassette" files in a fixtures directory. During normal test runs, the VCR interceptor matches outgoing requests to recorded requests and returns the recorded response. Tests run in milliseconds without API calls, and results are reproducible.

The challenge unique to AI agent testing: the request body includes the full conversation, which changes as the codebase evolves (different file contents produce different tool results, which produce different prompts). Cassette matching must be fuzzy --- matching on the structural shape of the request (same tool schemas, same message count, same role sequence) rather than exact byte equality. When a cassette mismatch is detected, the test framework reports it clearly so engineers know to re-record.

// VCR test setup
describe("agent handles file not found", () => {
  it("suggests alternative files", async () => {
    // In playback mode: uses recorded API response
    // In record mode: makes real API call and saves response
    const agent = createAgent({ vcr: "cassettes/file-not-found.json" });

    const result = await agent.run("Read the file config.yaml");

    expect(result.toolCalls).toContainEqual(
      expect.objectContaining({ name: "Read" })
    );
    expect(result.text).toContain("did not find");
  });
});

Trade-offs:

Advantage Cost
Tests are deterministic, fast, and free of API costs Cassettes become stale: code changes may cause request mismatches
Tests verify actual model behavior (recorded from real calls) Recording requires real API calls (cost, latency, rate limits)
No mock maintenance --- the cassette is the mock Fuzzy matching can mask real changes in request format
CI runs are reproducible and independent of API availability Cassette files can be large (full API responses) and must be version-controlled

Trust Boundary

Intent: Define explicit boundaries between content of different trust levels, enforcing that untrusted content cannot influence trusted execution paths without explicit validation.

When to Use: The system processes content from sources with different trust levels (user input, file contents, web content, model output) and must prevent lower-trust content from hijacking higher-trust operations.

Structure:

graph TB
    subgraph "Trusted Zone"
        SYS["System Prompt<br/>(HIGHEST TRUST)"]
        USER["User Messages<br/>(HIGH TRUST)"]
        RULES["Permission Rules<br/>(HIGH TRUST)"]
    end

    BOUNDARY["Trust Boundary<br/>- Sanitization<br/>- Role tagging<br/>- Length limits<br/>- Structural markers"]

    subgraph "Untrusted Zone"
        FILE["File Contents"]
        WEB["Web Fetch Results"]
        MCP_R["MCP Tool Results"]
        CMD["Command Output"]
    end

    FILE --> BOUNDARY
    WEB --> BOUNDARY
    MCP_R --> BOUNDARY
    CMD --> BOUNDARY
    BOUNDARY --> USER

    SYS -.->|"system-reminder<br/>boundaries"| BOUNDARY

Example from Claude Code: The content trust architecture (Chapter 20) defines five trust levels: system prompt (highest), user messages, tool results (medium), file contents (low), and web content (lowest). Content crossing from a lower trust level to a higher one passes through a boundary that applies: length limits (preventing context flooding), role tagging (tool results are marked with tool_result role, not user role), and structural boundaries (<system-reminder> tags that delineate trusted instruction sections from untrusted data sections within the same message).

Entry Point Trust Level Boundary Enforcement
User keyboard input Trusted (principal) None needed
File contents (Read tool) Low trust system-reminder marking, size limits
Web fetch results Lowest trust HTML-to-markdown conversion, system-reminder marking, aggressive size limits
MCP tool results Low trust Size limits, system-reminder marking, namespace isolation
Command stdout/stderr Medium trust Size limits, encoding sanitization
Git history Low trust Read-only access, size limits

The key insight from Chapter 20: trust boundaries in AI systems are advisory, not enforced by hardware. Unlike OS-level privilege separation, the LLM processes all trust levels in the same context window. The boundary reduces the probability of injection success but cannot eliminate it --- which is why the architecture uses defense-in-depth (Chain of Responsibility pattern) in addition to trust boundaries.

Trade-offs:

Advantage Cost
Makes trust levels explicit in the architecture Boundaries are advisory (LLMs have no hardware-enforced privilege separation)
Enables layered defense: each boundary is a defense layer Sanitization and tagging add token overhead to every piece of untrusted content
Facilitates security auditing: every trust boundary is a reviewable checkpoint False sense of security: boundaries reduce but do not eliminate injection risk
Standard markers (system-reminder) enable model training against injection Aggressive sanitization can strip legitimate content that resembles injection

Pattern Selection Guide

When designing a new component or solving a design problem in an AI agent system, use this table to identify candidate patterns:

Design Problem Candidate Patterns Chapter Reference
Many similar components need discovery Registry Ch. 13
Multiple backends for the same capability Adapter Ch. 10
Settings from multiple stakeholders Cascade Ch. 5
Request processing with multiple stages Pipeline Ch. 13
Component with distinct operational modes State Machine Ch. 7
User-extensible behavior without source changes Observer Ch. 29
Selectable algorithm families Strategy Ch. 18
Multiple independent security checks Chain of Responsibility Ch. 19
Parallelizable subtasks Fan-Out/Fan-In Ch. 24-25
Incremental data processing Pipeline (Streaming) Ch. 11
Rate-mismatched producer and consumer Producer-Consumer Ch. 28
Autonomous multi-step task execution Agentic Loop Ch. 7
Model needs to see previous action results Tool-Use Conversation Ch. 8
Conversation exceeds context window Context Compaction Ch. 9
Deterministic testing of LLM-backed code VCR Testing Ch. 31
Content from different trust levels Trust Boundary Ch. 20

No pattern is universally correct. Each solves a specific problem and introduces specific costs. The trade-off sections in this catalog are not caveats --- they are design constraints. Choose the pattern whose costs you can afford and whose benefits match your requirements.

A switch statement is better than a Registry for 3 tools. An if/else is better than a State Machine for 2 states. A single configuration file is better than a 7-layer Cascade for a solo project. The patterns in this catalog earned their complexity through the scale and requirements of a production AI CLI agent with 500,000 lines of code serving millions of users. Your system may not need all of them --- and that is the correct architectural decision.

As discussed throughout this book, the architectural skill is not knowing patterns --- it is knowing when the costs of a pattern exceed its benefits for your specific system, your specific scale, and your specific team.
