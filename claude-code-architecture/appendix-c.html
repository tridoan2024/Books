Appendix C: Design Pattern Catalog

This appendix catalogs every significant design pattern used in the AI CLI agent architecture, organized by category. For each pattern: what it is, when to use it, how it appears in Claude Code, and the trade-offs involved.

Structural Patterns

Registry Pattern

Intent: Centralize registration and lookup of components that share a common interface.

Where used: Tool Registry (52+ tools), Slash Command Registry (70+ commands), Hook Registry (27 events), Agent Type Registry (8 types).

Structure:

graph LR
    R[Registry] --> T1[Bash Tool]
    R --> T2[Read Tool]
    R --> T3[Edit Tool]
    R --> T4[MCP Tools...]
    C[Caller] --> R

How it works: At startup, each tool registers itself with a name, schema (Zod), description, and handler function. The agent loop looks up tools by name and dispatches through the registry. MCP tools register dynamically when servers connect.

When to use: When you have 10+ components sharing an interface and need runtime lookup by name. Below 10 components, a simple switch statement is clearer.

Trade-offs: | Pro | Con | |-----|-----| | Easy to add new tools without modifying dispatch logic | Indirection makes debugging harder (which handler runs?) | | Dynamic registration enables MCP extensibility | Registry initialization ordering can be subtle | | Single point for schema validation | Over-abstraction risk for small tool sets |

Adapter Pattern (Provider Abstraction)

Intent: Present a uniform interface over multiple implementations with different protocols.

Where used: API Client (Anthropic, AWS Bedrock, Google Vertex), MCP Transports (stdio, SSE, HTTP).

Structure:

graph TB
    AL[Agent Loop] --> AC[API Client Interface]
    AC --> A1[Anthropic Adapter]
    AC --> A2[Bedrock Adapter]
    AC --> A3[Vertex Adapter]
    A1 --> E1[Anthropic API]
    A2 --> E2[AWS Bedrock]
    A3 --> E3[Google Vertex]

How it works: The agent loop calls a single sendMessage() method. The API client resolves which provider to use based on credentials and configuration, then delegates to the appropriate adapter. Each adapter handles provider-specific authentication (API key, SigV4, OAuth), endpoints, and response format differences.

When to use: When you support 2+ external services with different protocols but the same semantic operation. Not needed for a single provider — add it when the second provider arrives.

Trade-offs: | Pro | Con | |-----|-----| | Swap providers without changing agent logic | Adapter layer adds complexity | | Enterprise customers choose their cloud provider | Lowest-common-denominator API surface | | Isolates authentication complexity | Provider-specific features harder to expose |

Cascade Pattern (Configuration)

Intent: Merge values from multiple sources in priority order, where higher-priority sources override lower ones.

Where used: Settings (7 layers), Permission Rules (8 sources), System Prompt Assembly (10+ sections).

Structure:

graph TB
    CLI["CLI Arguments (highest)"] --> M[Merged Config]
    ENV[Environment Variables] --> M
    LOCAL[Local Settings] --> M
    PROJECT[Project Settings] --> M
    USER[User Settings] --> M
    MANAGED[Managed/MDM] --> M
    DEFAULT["Built-in Defaults (lowest)"] --> M

How it works: Each layer is loaded independently. The merge algorithm walks the priority chain top-to-bottom. For scalar values, the first defined value wins. For arrays, layers can append or replace. For objects, deep merge is applied. The result is a single resolved configuration object.

When to use: When configuration comes from multiple stakeholders (developer, team, organization, platform) and you need deterministic conflict resolution.

Trade-offs: | Pro | Con | |-----|-----| | Each stakeholder controls their layer | Debugging "where did this value come from?" is hard | | Higher authority always wins (security) | Merge semantics can be surprising (arrays vs objects) | | Defaults ensure the system always works | 7 layers is a lot to reason about |

Pipeline Pattern (Tool Execution)

Intent: Process an item through a sequence of stages, where each stage can transform, validate, or reject the item.

Where used: Tool Execution (validate → permission → hook → execute → format), Bash Security (parse → classify → pattern → permission → sandbox), Startup (13 phases).

Structure:

graph LR
    I[Tool Call] --> V[Validate Schema]
    V --> P[Check Permission]
    P --> H[Run PreToolUse Hook]
    H --> E[Execute Tool]
    E --> F[Format Result]
    F --> R[Inject into Conversation]

How it works: Each stage receives the current state and either passes it forward (possibly transformed), rejects it (permission denied, validation failed), or handles an error. Stages are independent — you can add, remove, or reorder them without changing the others.

When to use: When processing involves distinct, ordered steps with clear contracts between them. Especially when some steps can short-circuit (reject) the pipeline.

Behavioral Patterns

State Machine Pattern

Intent: Model a component with discrete states and well-defined transitions between them.

Where used: Agent Loop (idle → processing → tool_use → waiting → complete), MCP Connection (disconnected → connecting → negotiating → ready → error), Streaming (waiting → receiving → tool_block → complete).

Agent Loop State Machine:

stateDiagram-v2
    [*] --> Idle
    Idle --> Processing: User message
    Processing --> ToolUse: Model requests tool
    ToolUse --> Processing: Tool result received
    Processing --> Waiting: Model needs user input
    Waiting --> Processing: User responds
    Processing --> Complete: End turn signal
    Complete --> Idle: Ready for next turn
    Processing --> Error: API/tool failure
    Error --> Processing: Retry
    Error --> Complete: Max retries exceeded

When to use: When a component has 3+ distinct behavioral modes and the valid transitions between them are not obvious. A state machine makes illegal transitions impossible.

Trade-offs: | Pro | Con | |-----|-----| | Illegal state transitions are impossible | More code than a simple if/else chain | | Easy to add new states without breaking existing ones | State explosion risk with many dimensions | | Self-documenting via the state diagram | Requires upfront design of all states |

Observer Pattern (Hooks)

Intent: Allow components to react to events without coupling the event source to the event handler.

Where used: Hook Engine (27 lifecycle events), File Watcher (FileChanged), MCP events (McpConnect, McpDisconnect).

Structure:

graph TB
    E[Event Source: Agent Loop] -->|"PreToolUse"| H[Hook Engine]
    H --> H1[block-destructive.sh]
    H --> H2[secret-scan.sh]
    H --> H3[custom-hook.sh]
    H1 -->|"exit 0/2"| H
    H2 -->|"exit 0/2"| H
    H3 -->|"exit 0/2"| H
    H -->|"allow/block"| E

How it works: The agent loop emits events at specific lifecycle points. The hook engine checks which hooks are registered for that event, runs them in priority order, and aggregates their decisions. Blocking hooks (exit code 2) can prevent the operation.

When to use: When external code needs to react to or gate internal operations. Hooks are the primary extensibility mechanism for operations that are not tool calls.

Strategy Pattern (Permission Modes)

Intent: Define a family of algorithms, encapsulate each one, and make them interchangeable.

Where used: Permission Modes (6 modes: default, auto, plan, bypass, deny-all, custom).

How it works: Each permission mode implements the same interface — given a tool name and input, return allow/deny/ask. The active mode is selected at session start and can be changed mid-session. The auto mode uses an AI classifier as its strategy; the default mode uses static rules.

When to use: When you have 3+ algorithms for the same operation and the choice between them is a runtime decision.

Chain of Responsibility (Security Layers)

Intent: Pass a request through a chain of handlers, where each handler either processes it or passes it to the next.

Where used: Bash Security (5 layers: parse → AST analysis → pattern matching → permission rules → sandbox).

Structure:

graph LR
    CMD[Bash Command] --> L1[Parse to AST]
    L1 -->|"parse error"| BLOCK[Block]
    L1 --> L2[Classify Intent]
    L2 --> L3[Match Patterns]
    L3 -->|"dangerous match"| BLOCK
    L3 --> L4[Check Permissions]
    L4 -->|"denied"| BLOCK
    L4 --> L5[Apply Sandbox]
    L5 --> EXEC[Execute]

How it works: Each security layer examines the command independently. Any layer can block execution. If all layers pass, the command executes in a sandbox. The defense-in-depth philosophy means no single layer needs to be perfect — the combination of all five layers provides strong security.

When to use: When security depends on multiple independent checks and you want any single check to be able to reject the request.

Concurrency Patterns

Fan-Out/Fan-In (Subagents)

Intent: Dispatch work to multiple parallel workers and collect their results.

Where used: Parallel subagent execution (e.g., security review + code review simultaneously), batch worktree operations.

graph TB
    P[Parent Agent] -->|"spawn"| A1[Security Reviewer]
    P -->|"spawn"| A2[Code Reviewer]
    P -->|"spawn"| A3[Doc Writer]
    A1 -->|"result"| P
    A2 -->|"result"| P
    A3 -->|"result"| P

When to use: When you have independent subtasks that can run in parallel. The speedup is limited by the slowest worker (Amdahl's law applies).

Trade-offs: | Pro | Con | |-----|-----| | N agents = ~Nx speedup for independent tasks | Token cost multiplied by N | | Each agent gets a fresh, focused context | Results need synthesis (parent agent work) | | Failures isolated to individual agents | Rate limiting may throttle parallel requests |

Producer-Consumer (Input Buffer)

Intent: Decouple the rate of input production from the rate of input consumption.

Where used: Early Input Capture (keystroke buffering during startup), Streaming Pipeline (API tokens to UI rendering).

How it works: During the 135ms module loading phase, the user may start typing. The early input capture system hooks process.stdin and buffers keystrokes. When the REPL mounts, it replays the buffer into the input field. The user never notices the delay.

AI-Specific Patterns

Agentic Loop Pattern

Intent: Enable an AI model to iteratively plan and execute actions until a goal is achieved.

This is THE core pattern of the entire architecture. Unlike request-response (one question, one answer), the agentic loop allows the model to take multiple actions, observe results, and adjust its approach.

graph TB
    A[Receive User Message] --> B[Assemble Context]
    B --> C[Call LLM API]
    C --> D{Response Type?}
    D -->|"Text Only"| E[Render to User]
    D -->|"Tool Call"| F[Execute Tool]
    F --> G[Inject Result into Context]
    G --> C
    D -->|"End Turn"| E
    E --> H[Wait for Next Message]
    H --> A

Key design decisions: 1. Exit conditions must be explicit — 10 defined exit reasons prevent infinite loops 2. Token budgets per turn — prevents runaway cost 3. Observation injection — tool results become new context for the next iteration 4. Error recovery — failed tools do not crash the loop; the model sees the error and adapts

Tool-Use Conversation Pattern

Intent: Represent tool calls and results as messages in the conversation, enabling the model to reason about tool outputs.

How it works: When the model decides to call a tool, it emits a tool_use content block. The agent executes the tool and injects a tool_result message. The model sees this result in its next turn and can decide whether to call more tools or respond to the user.

User:      "What files are in src/?"
Assistant: [tool_use: Glob(pattern="src/*")]
Tool:      [tool_result: "src/main.ts, src/config.ts, src/tools/..."]
Assistant: "The src/ directory contains main.ts, config.ts, and a tools/ directory..."

This pattern is fundamental to how LLMs interact with external systems — the conversation format IS the integration protocol.

Context Compaction Pattern

Intent: Compress conversation history to fit within a finite context window without losing essential information.

When to trigger: When context usage exceeds a threshold (default: 80%).

Strategies: 1. Summarization — Ask the LLM to summarize older conversation turns 2. Truncation — Remove oldest messages first (preserving system prompt) 3. Selective removal — Drop tool results that are no longer relevant 4. Priority preservation — Always keep: system prompt, recent messages, active tool results

VCR Testing Pattern

Intent: Make non-deterministic AI interactions deterministic for testing by recording and replaying API responses.

How it works: 1. Record mode: Run the test normally, capture every API request and response to a "cassette" file 2. Replay mode: Run the test using recorded responses instead of calling the real API 3. Auto mode: Use recordings if available, record new interactions if not

When to use: For integration tests that need to verify end-to-end behavior but cannot afford the cost and non-determinism of live API calls.

Trust Boundary Pattern

Intent: Explicitly mark where untrusted data enters the system and apply appropriate sanitization at each boundary.

Boundaries in Claude Code:

Entry Point Trust Level Sanitization
User input Trusted (principal) None needed
File contents Untrusted System-reminder marking
Web fetch results Untrusted HTML-to-markdown, system-reminder marking
MCP tool results Untrusted Size limits, system-reminder marking
Git history Semi-trusted Read-only
Environment variables Semi-trusted Allowlist in CI

The pattern: Every entry point for external data is wrapped in a trust boundary that marks the content's provenance. The LLM is instructed (via system prompt) to treat marked content differently from direct instructions.

Pattern Selection Guide

When designing a new component for an AI CLI agent, use this decision tree:

If you need to... Use this pattern
Register 10+ similar components Registry
Support multiple backends for one operation Adapter
Merge config from multiple sources Cascade
Process data through ordered stages Pipeline
Model distinct behavioral modes State Machine
Let external code react to internal events Observer (Hooks)
Choose between algorithms at runtime Strategy
Apply multiple independent security checks Chain of Responsibility
Parallelize independent subtasks Fan-Out/Fan-In
Buffer async input for sync consumption Producer-Consumer
Let an AI model take iterative actions Agentic Loop
Integrate LLM with external tools Tool-Use Conversation
Manage growing conversation history Context Compaction
Test non-deterministic AI interactions VCR Recording
Mark untrusted data entry points Trust Boundary

Each pattern has a cost. Use the simplest pattern that solves your problem. A switch statement is better than a Registry for 3 tools. An if/else is better than a State Machine for 2 states. The patterns in this catalog earned their complexity through the scale and requirements of a production AI CLI agent.
