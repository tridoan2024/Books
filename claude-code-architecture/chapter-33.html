Chapter 33: Enterprise Architecture

A developer running an AI coding agent on their personal laptop faces one set of problems: "Does it work? Is it fast? Does it produce good code?" An enterprise deploying the same agent to 500 engineers faces an entirely different set: "Can a junior developer accidentally delete the production database? Can the agent exfiltrate proprietary source code? Can we prove to auditors that the agent never accessed patient health records? Can we control spending when 500 people each run $5/day in API calls?"

Enterprise requirements do not change what the agent does. They change what the agent is allowed to do, what data can flow through it, who can configure it, and what records must be kept. This chapter covers the architectural patterns that make an AI agent enterprise-ready: managed device settings, policy enforcement hierarchies, telemetry and privacy controls, audit logging, and the deployment pattern that lets central IT define guardrails while giving individual teams and developers the flexibility they need.

33.1 The Enterprise Requirements Stack

Enterprise adoption of AI coding agents requires satisfying four stakeholders, each with different concerns:

Stakeholder Primary concern Key question
Security team Control What can the agent do? What tools are allowed?
Privacy/Legal Data flow What data leaves the organization? Where does it go?
Compliance Audit trail Can we prove what happened? Who authorized it?
Finance Cost What are we spending? Can we set limits?

These concerns are not optional features you add after launch. They are architectural constraints that shape the system design from the start. An agent that was not designed for enterprise deployment cannot be retrofitted -- the settings hierarchy, the audit trail, and the privacy controls must be baked into the architecture.

The Trust Hierarchy

Enterprise deployment introduces a trust hierarchy that does not exist for individual users:

    SESSION["Session Overrides<br/>Runtime adjustments<br/>Ephemeral"]

    MDM --> ORG --> TEAM --> USER --> SESSION

The critical property: stricter always wins. If the organization policy denies a tool, no team setting, user preference, or session override can re-enable it. If the MDM profile enforces a specific model, no lower-level setting can override it. This is not a merge -- it is a cascade with precedence.

33.2 MDM (Mobile Device Management) Settings

On managed macOS and Windows devices, organizations push configuration profiles through MDM systems (Jamf, Intune, Workspace ONE). These profiles are cryptographically signed and cannot be modified by the end user.

Configuration Profile Architecture

An MDM configuration profile for an AI agent defines:

{
  "com.example.ai-agent": {
    "allowedModels": ["claude-sonnet-4-6", "claude-haiku-3.5"],
    "deniedModels": ["claude-opus-4"],
    "permissionMode": "plan",
    "maxSessionCostUsd": 5.00,
    "telemetryLevel": "standard",
    "mcpServerAllowlist": ["github", "jira", "internal-kb"],
    "mcpServerDenylist": ["*"],
    "customApiEndpoint": "https://ai-proxy.corp.example.com/v1",
    "settingsHmacKey": "base64:abc123..."
  }
}

HMAC Verification

MDM settings must be tamper-proof. A developer who installs a modified agent binary or edits a config file should not be able to bypass organizational policies. HMAC (Hash-based Message Authentication Code) verification ensures integrity:

sequenceDiagram
    participant MDM as MDM Server
    participant Device as Managed Device
    participant Agent as AI Agent

    MDM->>Device: Push profile + HMAC signature
    Note over Device: Profile stored in system preferences

    Agent->>Device: Read profile
    Device-->>Agent: Profile + HMAC
    Agent->>Agent: Compute HMAC of profile body
    Agent->>Agent: Compare computed vs received HMAC

    alt HMAC matches
        Agent->>Agent: Apply settings as highest priority
    else HMAC mismatch
        Agent->>Agent: Reject settings, use safe defaults
        Agent->>Agent: Log tampering alert
    end

The HMAC key is embedded in the agent binary at build time for the enterprise distribution. A developer building from source cannot produce a valid HMAC signature, which means they cannot create a modified binary that accepts tampered profiles. This is security through the build pipeline, not through code obscurity.

Settings Hierarchy with MDM

The complete settings resolution for an enterprise deployment:

flowchart TD
    MDM["MDM Profile<br/>(highest priority)"] --> MERGE
    ORG["Organization Settings<br/>(remote endpoint)"] --> MERGE
    PROJECT[".claude/settings.json<br/>(committed to repo)"] --> MERGE
    USER["~/.claude/settings.json<br/>(user home)"] --> MERGE
    LOCAL[".claude/settings.local.json<br/>(gitignored)"] --> MERGE
    SESSION["Runtime overrides<br/>(CLI flags)"] --> MERGE

    MERGE["Merge Engine"] --> RESULT["Effective Settings"]

    MERGE -.-> |"For each key:<br/>use most restrictive value"| RESULT

    style MDM fill:#ff6b6b,stroke:#c92a2a,color:#fff
    style RESULT fill:#51cf66,stroke:#2b8a3e,color:#000

The merge semantics differ by field type:

Field type Merge rule Example
Allowlist Intersection (most restrictive) allowedModels: MDM allows [A,B,C], org allows [B,C,D] -> effective [B,C]
Denylist Union (most restrictive) deniedTools: MDM denies [X], org denies [Y] -> effective [X,Y]
Mode enum Most restrictive wins MDM: "plan", user: "auto" -> effective "plan"
Numeric limit Minimum wins MDM: $5 max, user: $10 max -> effective $5
Boolean (safety) true wins MDM: telemetry=true, user: telemetry=false -> effective true
String (endpoint) Highest priority wins MDM: "proxy.corp.com" overrides all

The asymmetry is intentional. Safety-related fields use the most restrictive interpretation. Preference fields (like which model to default to) use highest-priority-wins. An administrator can force a model restriction but should not force a color scheme.

33.3 Managed Policies

Organizations need to control agent behavior beyond what MDM profiles offer. Managed policies provide a remote configuration endpoint that the agent checks periodically.

Policy Architecture

graph LR
    PS["Policy Server<br/>Central IT manages"]
    PS -->|HTTPS + HMAC| A1["Agent (Alice)"]
    PS -->|HTTPS + HMAC| A2["Agent (Bob)"]
    PS -->|HTTPS + HMAC| A3["Agent (Carol)"]

    PS -.->|"Sync every 5min"| A1
    PS -.->|"Sync every 5min"| A2
    PS -.->|"Sync every 5min"| A3

    style PS fill:#ffd43b,stroke:#e67700

The agent fetches the policy from a well-known URL (configurable via MDM) at startup and periodically during the session. The policy is signed with the same HMAC mechanism as MDM profiles.

Policy Capabilities

Model allowlists. Restrict which models can be used. An organization might allow Sonnet for daily use but restrict Opus to specific teams that need it (and can afford it).

{
  "models": {
    "allowed": ["claude-sonnet-4-6", "claude-haiku-3.5"],
    "default": "claude-sonnet-4-6",
    "opus_requires_approval": true
  }
}

Tool restrictions. Disable specific tools or tool categories. An organization processing classified data might disable all MCP tools to prevent data from flowing to external servers. A team working on a production codebase might disable the Bash tool's rm and DROP commands.

{
  "tools": {
    "disabled": ["WebFetch", "WebSearch"],
    "bash_blocked_patterns": [
      "rm -rf *",
      "DROP TABLE *",
      "curl * | sh",
      "chmod 777 *"
    ]
  }
}

Permission mode enforcement. Force a specific permission mode across the organization. "Plan" mode (which requires approval before executing any tool) is common in regulated industries where every action must be auditable.

{
  "permissions": {
    "enforced_mode": "plan",
    "allow_auto_mode": false,
    "require_approval_for": ["Edit", "Write", "Bash"]
  }
}

Telemetry controls. Define what data is collected and where it goes. Privacy levels range from "disabled" (no telemetry at all) to "full" (complete session transcripts sent to the corporate telemetry endpoint).

{
  "telemetry": {
    "level": "standard",
    "endpoint": "https://telemetry.corp.example.com/v1/events",
    "include_prompts": false,
    "include_responses": false,
    "include_tool_inputs": true,
    "include_tool_outputs": false
  }
}

Policy Sync and Offline Behavior

The agent caches the last-known policy locally. If the policy server is unreachable, the agent uses the cached policy with a staleness warning. If no cached policy exists (first run, cache cleared), the agent falls back to the most restrictive defaults:

Condition Behavior
Policy server reachable Fetch, verify HMAC, apply
Server unreachable, cache fresh (<1h) Use cached policy
Server unreachable, cache stale (1-24h) Use cached policy + warn user
Server unreachable, cache expired (>24h) Apply restrictive defaults, warn user
No cache, no server Apply restrictive defaults, block Opus

This graduated degradation prevents both security bypass (using no policy) and denial of service (blocking all work when the policy server has a hiccup).

The Proxy Pattern

Many enterprises route all API traffic through a corporate proxy. This serves three purposes:

  1. Audit. The proxy logs every API request and response, creating a complete audit trail independent of the agent's own logging.
  2. Filtering. The proxy can redact sensitive data from requests before they reach the AI provider. Source code that contains customer PII can have the PII stripped at the proxy level.
  3. Cost control. The proxy enforces rate limits and spending caps at the organizational level, preventing runaway costs from any individual session.

The agent's architecture must accommodate proxying: it reads ANTHROPIC_BASE_URL (or equivalent) from the environment, and all API calls flow through that endpoint. The proxy is transparent to the agent's code -- it sees a standard API endpoint and does not know or care that a proxy sits in between.

33.5 Audit and Compliance

Regulated industries (healthcare, finance, government) require audit trails that prove what the agent did, who authorized it, and what data it accessed. The audit architecture provides three levels of audit data.

Level 1: Permission Decision Log

Every permission evaluation is logged:

{
  "timestamp": "2026-04-12T14:23:45Z",
  "session_id": "sess_a1b2c3",
  "user": "alice@corp.example.com",
  "tool": "Bash",
  "input_summary": "git push origin main",
  "decision": "allow",
  "matched_rule": "Bash(git push *)",
  "rule_source": "project_settings",
  "evaluation_time_ms": 2
}

This log answers: "Who did what, and why was it allowed?" For denied actions, it captures what was attempted and which rule blocked it. For allowed actions, it captures which rule permitted it. This is the minimum viable audit trail.

Level 2: Session Transcript

The full conversation transcript, including user prompts, model responses, tool inputs, and tool outputs. As discussed in Chapter 32, transcripts are the most valuable debugging artifact. For compliance, they serve as a complete record of the agent's activities.

Transcript storage must respect privacy policies. If the telemetry configuration says include_prompts: false, the transcript stores message metadata (timestamp, role, token count) but not the content itself. This creates a "skeleton transcript" that shows the structure of the session without revealing the data.

Level 3: Data Access Log

Every file read, every search result, every MCP resource access is logged with the file path, access type, and timestamp:

{
  "timestamp": "2026-04-12T14:23:46Z",
  "session_id": "sess_a1b2c3",
  "action": "file_read",
  "path": "/repo/src/patient_records.py",
  "bytes_read": 4567,
  "classification": "sensitive",
  "tool": "Read"
}

File classification ("sensitive", "normal", "public") can be driven by path patterns defined in the organization policy:

{
  "data_classification": {
    "sensitive_patterns": [
      "**/patient*", "**/medical*", "**/phi/*",
      "**/*.pem", "**/*.key", "**/.env*"
    ],
    "public_patterns": [
      "**/README*", "**/LICENSE*", "**/docs/**"
    ]
  }
}

When the agent reads a file matching a sensitive pattern, the access is logged at a higher audit level and may trigger additional approval requirements.

Cost Attribution

For organizations where AI costs are charged back to teams or projects, cost attribution requires tagging every API request with organizational metadata:

{
  "x-org-id": "corp-example",
  "x-team": "platform-engineering",
  "x-project": "api-gateway",
  "x-user": "alice@corp.example.com",
  "x-cost-center": "CC-4200"
}

The billing system aggregates these tags to produce per-team and per-project cost reports. This is typically implemented at the proxy level (the proxy adds the tags based on the authenticated user) rather than in the agent itself.

33.6 Privacy Architecture

AI agents process source code, which may contain proprietary algorithms, customer data, API keys, or personally identifiable information. The privacy architecture controls what data flows to the AI provider and what stays local.

Privacy Levels

Level What is sent to AI provider Use case
Full Everything (prompts, code, tool results) Default, maximum capability
Standard Prompts and code, no telemetry metadata Most enterprises
Strict Prompts only, tool results summarized Sensitive industries
Local only Nothing sent externally Air-gapped environments

At "strict" level, tool results are summarized locally before being sent to the model. Instead of sending the full 500-line file content, the agent sends "Read file src/auth.py: 500 lines, Python, contains 12 functions." The model can still reason about the file structure but never sees the actual code. This significantly reduces capability but satisfies the privacy requirement.

At "local only" level, the agent uses a locally-hosted model (if available) or operates in a degraded mode with only deterministic tools (search, read, format) and no AI-powered reasoning. This is for classified environments where no data can leave the network.

Data Flow Controls

The privacy filter is a middleware component that intercepts every outbound data flow. It applies the configured privacy level and strips or summarizes data accordingly. The filter is the single enforcement point -- no data reaches an external endpoint without passing through it.

Prompt Sanitization

Even at the "full" privacy level, certain content should never reach the AI provider. The sanitization pipeline runs before the privacy filter:

  1. Secret detection. Scan outbound content for patterns matching API keys (sk-, AKIA, ghp_), private keys (BEGIN RSA PRIVATE KEY), and connection strings. Replace with [REDACTED_SECRET].

  2. PII detection. For organizations that configure PII rules, scan for social security numbers, credit card numbers, email addresses, and phone numbers matching configured patterns. Replace with [REDACTED_PII].

  3. Classification-based filtering. If the data access log classified a file as "sensitive" and the privacy level is "strict" or lower, replace the file content with a structural summary.

The sanitization pipeline is configurable per organization. A healthcare company might add HIPAA-specific patterns (medical record numbers, patient names from a known list). A financial company might add PCI DSS patterns (16-digit card numbers, CVVs). The agent ships with a sensible default pattern set, and organizations extend it via their managed policy.

MCP Data Flow Controls

MCP servers present a unique privacy challenge. When the agent calls an MCP tool, it sends data to an external process that may itself make network calls. A local MCP server (stdio transport) keeps data on the machine. A remote MCP server (HTTP/SSE transport) sends data over the network.

The privacy architecture applies controls per MCP server:

MCP server scope Data flow control
Local (user-configured, stdio) Trust: same as local tools
Project (team-configured, stdio) Prompt on first use, approve per session
Remote (HTTP/SSE) Subject to privacy filter, allowlisted URLs only
Enterprise (organization-managed) Bypass local controls, use org policy

Remote MCP servers are the highest risk. The privacy filter intercepts tool call arguments before they reach the MCP client, applying the same sanitization pipeline used for API calls. If the privacy level is "strict", tool arguments containing file content are summarized before being sent to the MCP server.

33.7 Compliance Framework Integration

Different industries have different compliance requirements. Rather than building compliance logic directly into the agent, the architecture provides hooks that compliance frameworks can use.

The Compliance Hook Pattern

flowchart TD
    ACTION["Agent action<br/>(tool call, file access)"] --> PRE["PreToolUse Hook"]
    PRE --> COMP["Compliance Check"]
    COMP -->|"Approved"| EXEC["Execute action"]
    COMP -->|"Blocked"| DENY["Deny with reason"]
    COMP -->|"Requires approval"| QUEUE["Queue for approval"]

    EXEC --> POST["PostToolUse Hook"]
    POST --> AUDIT["Audit Log Entry"]

    style COMP fill:#ffd43b,stroke:#e67700
    style DENY fill:#ff6b6b,stroke:#c92a2a,color:#fff
    style AUDIT fill:#51cf66,stroke:#2b8a3e

The compliance check is implemented as a PreToolUse hook (as described in Chapter 29). The hook receives the tool name and input, evaluates them against compliance rules, and returns allow (exit 0), deny (exit 2), or requires-approval (exit with a specific code that triggers the approval workflow).

This hook-based approach means the agent's core code does not know or care about HIPAA, SOC 2, or FedRAMP. The compliance logic lives in external scripts that organizations deploy alongside the agent. The architecture provides the extension point; the organization provides the compliance logic.

Common Compliance Patterns

Framework Key requirement Agent architecture support
SOC 2 Audit trail of all data access Level 3 data access log
HIPAA No PHI in logs, access controls PII sanitization, privacy filter
FedRAMP Approved cloud services only API endpoint enforcement via MDM
GDPR Data minimization, right to erasure Privacy levels, session data deletion
PCI DSS Cardholder data protection Secret detection, sanitization pipeline

Each framework maps onto existing architectural components. SOC 2 needs the data access log that already exists. HIPAA needs the PII sanitization that already exists. FedRAMP needs the MDM-enforced API endpoint. The architecture is framework-agnostic; the configuration is framework-specific.

Session Data Retention and Deletion

For GDPR compliance, the agent must support data deletion. Session transcripts, audit logs, and cached data must be deletable on demand. The architecture provides:

  • Per-user data isolation. Each user's data is stored in a separate directory tree, making deletion straightforward.
  • Configurable retention. Session transcripts expire after a configurable period (default: 30 days for enterprise, unlimited for personal use).
  • Deletion API. A command (/clear-data --user alice@corp.example.com) deletes all session data, transcripts, and cached tokens for a specific user.

The retention policy is set in the managed policy. When a session transcript exceeds the retention period, the cleanup process deletes it automatically. The audit log entry for the session (Level 1: permission decisions only) may be retained longer per compliance requirements, even after the full transcript is deleted.

33.8 Key Takeaways

  1. Enterprise requirements are architectural constraints, not features. Design the settings hierarchy, audit trail, and privacy controls from the start. Retrofitting is prohibitively expensive.

  2. Stricter always wins. The merge semantics for enterprise settings must guarantee that a higher-authority policy cannot be overridden by a lower-level setting. Allowlists intersect, denylists union, numeric limits take the minimum.

  3. HMAC verification prevents tampering. MDM profiles and managed policies must be cryptographically verified. A developer who can edit a config file should not be able to bypass organizational controls.

  4. Graduated degradation for policy sync. When the policy server is unreachable, use cached policies with staleness warnings rather than blocking all work or falling back to no policy.

  5. Three audit levels serve different compliance needs: permission decisions (minimum), session transcripts (standard), and data access logs (regulated industries). Each level adds storage and privacy overhead.

  6. Privacy levels are a spectrum. From "full" (maximum capability) to "local only" (maximum privacy), with "standard" and "strict" as intermediate points. The architecture must support all levels without code changes -- they are configuration, not features.

  7. The proxy pattern is your friend. Routing API traffic through a corporate proxy provides audit, filtering, and cost control without modifying the agent. Design the agent to respect configurable API endpoints from the start.

  8. Cost attribution requires metadata tagging. Every API request must carry organizational metadata (team, project, user, cost center) for billing aggregation. This is best implemented at the proxy level.
