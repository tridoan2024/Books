Chapter 6: Session Lifecycle

What Is a Session?

A session is the unit of continuity in a CLI agent. It begins when the user types claude and ends when they exit. Between those moments, the session accumulates state: conversation messages, tool results, file edits, cost tracking, and permission decisions. When the user types claude --resume, a previous session's state is reconstructed. When the process crashes, session data survives in append-only transcript files.

This chapter examines the architecture of session management in Claude Code: how sessions are created, how their state is persisted, how they survive crashes, how they resume, and how they shut down. We'll pay particular attention to the Atomic Switch Pattern -- a coordination mechanism that prevents a class of bugs where session identity and session data directory can drift apart.

Session Creation

Session creation happens in Phase 11 of the startup pipeline (Chapter 4). The critical data produced:

function initializeSession(): void {
  state.sessionId = generateSessionId();  // UUID v4
  state.sessionStartTime = Date.now();

  // Derive transcript path from project identity
  const transcriptDir = path.join(
    os.homedir(), '.claude', 'projects',
    hashProjectPath(state.projectRoot),
    'sessions'
  );
  ensureDirSync(transcriptDir);
  state.transcriptPath = path.join(
    transcriptDir, `${state.sessionId}.jsonl`
  );

  // Register in active sessions registry
  registerActiveSession(state.sessionId, {
    pid: process.pid,
    cwd: state.cwd,
    startTime: state.sessionStartTime,
  });
}

Three architectural decisions stand out:

UUID v4 for Session Identity

The session ID is a UUID v4 -- 128 bits of randomness. No timestamp component, no sequential counter. This means:

  • Two sessions started simultaneously will never collide (collision probability: 2^-122).
  • Session IDs don't leak timing information (useful for telemetry anonymization).
  • Sessions can't be ordered by ID alone (the transcript file's modification time provides ordering).

The alternative -- timestamp-based IDs like 2026-04-12T14:30:00-session-1 -- would be human-readable but create collision risk when sessions start within the same second. UUID v4 trades readability for uniqueness guarantees.

Project-Scoped Transcript Directory

Transcripts are stored under a project-specific directory:

~/.claude/projects/{hash(projectRoot)}/sessions/{sessionId}.jsonl

The hashProjectPath() function hashes the absolute path to produce a stable, filesystem-safe directory name. This scoping means:

  • Each project has its own session history. claude --resume only shows sessions from the current project.
  • Changing your working directory doesn't contaminate other projects' session lists.
  • The hash prevents filesystem issues from long paths or special characters.

The hash is a SHA-256 of the normalized, NFC-encoded project root path, truncated to 16 hex characters. This gives 2^64 unique directories -- sufficient to avoid collisions across a developer's entire career of projects.

Active Session Registry

The registerActiveSession() call writes to ~/.claude/active_sessions.json:

{
  "sessions": {
    "a1b2c3d4-...": {
      "pid": 12345,
      "cwd": "/Users/dev/myproject",
      "startTime": 1712956800000
    },
    "e5f6g7h8-...": {
      "pid": 12346,
      "cwd": "/Users/dev/another-project",
      "startTime": 1712956803000
    }
  }
}

This registry enables three features: 1. Concurrent session detection. When a new session starts, it checks for existing sessions in the same project. Multiple sessions in the same project can cause file conflicts. 2. Bridge/remote-control discovery. The claude remote-control command uses this registry to find running sessions to connect to. 3. Stale session cleanup. On startup, sessions whose PIDs no longer exist are pruned from the registry.

Why Global State Over DI for Sessions

The argument from Chapter 3 applies directly to session state. Consider how many layers need to access sessionId:

  • The API client (to correlate requests)
  • Telemetry events (to group by session)
  • The transcript writer (to name the file)
  • The permission system (to log decisions)
  • The cost tracker (to attribute spending)
  • The hook system (to pass session context)
  • The bridge/remote-control (to identify the session)
  • The resume system (to match session IDs)

Threading sessionId through 8+ subsystems via constructor parameters would require a SessionContext object passed everywhere. In a single-process CLI with one session at a time, this is ceremony without benefit. The global accessor getSessionId() is simpler, greppable, and sufficient.

The trade-off materializes in testing: every test must call resetStateForTests() to clean up session state. But as Chapter 3 describes, that pattern works -- Claude Code has thousands of tests using it.

JSONL Transcript Persistence

Every conversation message, tool call, tool result, and state change is recorded in a JSONL (JSON Lines) transcript file. JSONL was chosen over alternatives for three architectural reasons:

Why JSONL?

graph LR
    subgraph "Write Pattern"
        A[Message 1] --> F[Append to file]
        B[Tool Call] --> F
        C[Tool Result] --> F
        D[State Change] --> F
    end

    subgraph "transcript.jsonl"
        L1["{'type':'message','role':'user','content':'Fix auth.ts'}\n"]
        L2["{'type':'tool_use','name':'Read','input':{'path':'auth.ts'}}\n"]
        L3["{'type':'tool_result','output':'...'}\n"]
        L4["{'type':'message','role':'assistant','content':'Found the bug...'}\n"]
    end

    F --> L1
    F --> L2
    F --> L3
    F --> L4

1. Crash safety. Each entry is an independent JSON object followed by a newline. An append of {...}\n is atomic on most filesystems for reasonable message sizes (under the filesystem's block size, typically 4KB). If the process crashes mid-write, at most one partial line is corrupted -- all previous entries are intact. Compare this to a single JSON file ([{...}, {...}]) where a crash mid-write can corrupt the entire array.

2. Streaming writes. The transcript writer never needs to read the existing file. Each entry is appended:

function appendToTranscript(entry: TranscriptEntry): void {
  const line = JSON.stringify(entry) + '\n';
  fs.appendFileSync(state.transcriptPath, line, 'utf-8');
}

No read-modify-write cycle. No file locking. The appendFileSync call is the entire persistence operation. This is O(1) per entry regardless of transcript size.

3. Replay-friendly. Resuming a session means reading the transcript line by line and reconstructing the conversation:

function loadTranscript(path: string): TranscriptEntry[] {
  const content = fs.readFileSync(path, 'utf-8');
  return content
    .split('\n')
    .filter(line => line.trim().length > 0)
    .map(line => {
      try {
        return JSON.parse(line);
      } catch {
        return null;  // Skip corrupted lines
      }
    })
    .filter(Boolean);
}

Corrupted lines (from crashes) are silently skipped. The transcript degrades gracefully -- a crash during a tool result write means the result is lost, but all previous messages survive.

Transcript Entry Types

Each JSONL entry is a discriminated union:

type TranscriptEntry =
  | { type: 'session_start'; sessionId: string; timestamp: number; cwd: string }
  | { type: 'message'; role: 'user' | 'assistant'; content: string; timestamp: number }
  | { type: 'tool_use'; id: string; name: string; input: unknown; timestamp: number }
  | { type: 'tool_result'; toolUseId: string; output: string; isError: boolean; timestamp: number }
  | { type: 'state_change'; field: string; oldValue: unknown; newValue: unknown; timestamp: number }
  | { type: 'session_end'; timestamp: number; totalCost: number; reason: string }

Every entry carries a timestamp. This enables: - Duration computation. Time between tool_use and tool_result is the tool's execution time. - Idle detection. Long gaps between entries indicate the user was away. - Replay pacing. A debugger could replay the session in real-time using timestamps.

Comparison with Alternatives

Format Crash Safety Write Performance Resume Cost Space Efficiency
JSONL (chosen) Excellent (line-level) O(1) append O(n) read + parse Moderate
Single JSON file Poor (whole-file corrupt) O(n) rewrite O(n) read + parse Good
SQLite Excellent (WAL mode) O(1) insert O(1) query Excellent
Binary protobuf Excellent (length-prefixed) O(1) append O(n) read Best

JSONL wins on simplicity. SQLite would give better query performance (e.g., "find all sessions where I used the Edit tool") but adds a native dependency and 15ms to startup. Binary protobuf would be more space-efficient but unreadable without tools. JSONL files are human-readable, debuggable with cat and jq, and require zero dependencies.

Project Directory Anchoring

A resumed session must operate in the same project context as the original session. The session_start transcript entry records the original cwd:

// At session start
appendToTranscript({
  type: 'session_start',
  sessionId: state.sessionId,
  timestamp: Date.now(),
  cwd: state.projectRoot,
});

When resuming:

function resumeSession(sessionId: string): void {
  const transcript = loadTranscript(sessionId);
  const startEntry = transcript.find(e => e.type === 'session_start');

  if (startEntry) {
    // Anchor to original project directory
    switchSession(
      sessionId as SessionId,
      startEntry.cwd  // Original project directory
    );
  }
}

The switchSession() call is the Atomic Switch Pattern (detailed below) -- it updates both sessionId and sessionProjectDir together, preventing them from drifting apart.

Session Listing and Selection

When --resume is called without a specific session ID, the system lists recent sessions:

function listRecentSessions(projectDir: string): SessionSummary[] {
  const sessionsDir = path.join(
    os.homedir(), '.claude', 'projects',
    hashProjectPath(projectDir),
    'sessions'
  );

  return fs.readdirSync(sessionsDir)
    .filter(f => f.endsWith('.jsonl'))
    .map(f => {
      const transcript = loadTranscript(path.join(sessionsDir, f));
      const start = transcript.find(e => e.type === 'session_start');
      const end = transcript.find(e => e.type === 'session_end');
      const firstMessage = transcript.find(
        e => e.type === 'message' && e.role === 'user'
      );

      return {
        sessionId: f.replace('.jsonl', ''),
        startTime: start?.timestamp,
        endTime: end?.timestamp,
        preview: firstMessage?.content.slice(0, 80),
        messageCount: transcript.filter(e => e.type === 'message').length,
      };
    })
    .sort((a, b) => (b.startTime ?? 0) - (a.startTime ?? 0));
}

Sessions are sorted by start time (most recent first) and displayed with a preview of the first user message. This gives the user enough context to identify which session they want to resume.

The Atomic Switch Pattern

The switchSession() function is one of the most important coordination mechanisms in the codebase. It solves a bug class where two related pieces of state can drift apart:

export function switchSession(
  sessionId: SessionId,
  projectDir: string | null = null,
): void {
  // 1. Clean up outgoing session
  STATE.planSlugCache.delete(STATE.sessionId);

  // 2. Atomically update both fields
  STATE.sessionId = sessionId;
  STATE.sessionProjectDir = projectDir;

  // 3. Notify listeners
  sessionSwitched.emit(sessionId);
}

Why Atomic?

sessionId and sessionProjectDir are semantically coupled. The session ID determines which transcript file to read; the project directory determines where to look for that file. If they're updated separately, a race condition exists:

// BAD: Non-atomic update
setSessionId(newId);          // sessionId = "abc-123"
// <-- Another module reads sessionId here
//     but sessionProjectDir still points to the OLD directory
//     → looks for abc-123.jsonl in the wrong place → crash
setSessionProjectDir(newDir); // sessionProjectDir = "/new/dir"

With switchSession(), both fields update in a single function call. There's no intermediate state where one is new and the other is old. The comment in the source (referencing internal bug CC-34) says these fields "cannot drift out of sync."

No Separate Setters

There is no setSessionId() or setSessionProjectDir() exposed from the state module. The only way to change either field is through switchSession(). This is enforced by API design, not runtime checks -- the accessor functions simply don't exist.

This is a pattern worth generalizing: when two fields must always change together, expose a single function that changes both. Don't rely on documentation or code review to enforce the invariant. Make the invariant structurally impossible to violate.

Signal Notification

The sessionSwitched.emit(sessionId) call notifies listeners that the session changed. Consumers include:

Listener Reaction
Concurrent sessions manager Updates PID file with new session ID
Transcript writer Opens new transcript file
Telemetry Flushes old session events, starts new correlation
MCP connections Re-announces session identity to servers
REPL header Updates session display

The signal pattern (Chapter 3) decouples the state module from its consumers. bootstrap/state.ts doesn't import any of these modules -- it just emits a signal, and interested parties subscribe.

Crash Recovery

When the process terminates unexpectedly (SIGKILL, out-of-memory, power failure), what survives?

What Survives

Data Survival Mechanism
Conversation history JSONL transcript (all completed writes)
File edits made by tools Already written to disk

The JSONL format's crash resilience means resume after a crash works almost identically to resume after a graceful exit. The only difference: the transcript might be missing the last in-flight entry, and there's no session_end marker. The resume system detects this:

function isSessionCrashed(transcript: TranscriptEntry[]): boolean {
  const hasEnd = transcript.some(e => e.type === 'session_end');
  return !hasEnd;
}

A session without a session_end entry either crashed or is still running. The system checks the active session registry to distinguish: if the PID is still alive, the session is active; if the PID is dead, it crashed.

Graceful Shutdown

When the user exits normally, a cleanup sequence runs in a specific order:

async function gracefulShutdown(reason: string): Promise<void> {
  // 1. Signal the REPL to stop accepting input
  state.shuttingDown = true;

  // 2. Abort any in-flight API requests
  abortActiveRequests();

  // 3. Flush telemetry buffers
  await flushTelemetry();

  // 4. Run registered cleanup handlers
  for (const cleanup of registeredCleanups) {
    try {
      await cleanup();
    } catch (err) {
      // Log but don't throw -- other cleanups must still run
      logError('Cleanup handler failed', err);
    }
  }

  // 5. Write session end marker to transcript
  appendToTranscript({
    type: 'session_end',
    timestamp: Date.now(),
    totalCost: state.totalCostUSD,
    reason,
  });

  // 6. Deregister from active sessions
  deregisterActiveSession(state.sessionId);

  // 7. Restore terminal state
  process.stdin.setRawMode?.(false);
  process.stdout.write('\n');
}

Cleanup Ordering

The ordering is intentional:

  1. Stop input first. Prevents new operations from starting during shutdown.
  2. Abort API requests. In-flight requests would waste money and time. The abort signal is checked by the streaming handler.
  3. Flush telemetry. Telemetry buffers may contain unbatched events. Flushing ensures the session's final metrics are recorded.
  4. Registered cleanups. Subsystems register cleanup functions during init():
// During init()
registerCleanup(shutdownLspServerManager);  // Stop language servers
registerCleanup(cleanupSessionTeams);        // Kill tmux teammates
registerCleanup(closeMcpConnections);        // Disconnect MCP servers
  1. Transcript end marker. Must happen after all other work -- the session_end entry records the final cost, which accumulates during cleanup (telemetry flush might trigger final cost calculations).
  2. Deregister session. Removes the entry from active_sessions.json so other processes know this session is done.
  3. Terminal restore. Raw mode must be turned off so the user's shell works normally after exit.

Error Isolation in Cleanup

Each cleanup handler is wrapped in a try/catch. A failed LSP shutdown must not prevent MCP disconnection or transcript persistence. The handlers run sequentially (not in parallel) to avoid resource contention -- stopping a language server and killing tmux sessions simultaneously could interfere with each other.

This lineage enables: - Cost attribution. The parent session's cost includes all child sessions. - Telemetry correlation. Session State Diagram

The complete lifecycle of a session, including all states and transitions:

stateDiagram-v2
    [*] --> Creating: claude invoked

    Creating --> Initializing: UUID generated, transcript opened
    Initializing --> TrustCheck: Config loaded, auth resolved

    TrustCheck --> Active: Directory trusted
    TrustCheck --> Restricted: Trust declined

    Active --> Active: User prompts, tool calls, responses
    Restricted --> Restricted: Limited functionality

    Active --> Resuming: /resume or --resume
    Resuming --> Active: Transcript replayed

    Active --> Switching: switchSession() called
    Switching --> Active: New session ID + project dir

    Active --> Compacting: Context window full
    Compacting --> Active: Conversation summarized

    Active --> ShuttingDown: User exits
    Active --> Crashed: Unexpected termination

    ShuttingDown --> Ended: Cleanup complete
    Crashed --> Ended: No cleanup

    Ended --> Resuming: claude --resume
    Ended --> [*]: No resume

    Restricted --> ShuttingDown: User exits

Notable transitions:

  • Active -> Switching. The switchSession() call (Atomic Switch Pattern) transitions to a different session without restarting the process. This happens during --resume within a running session.
  • Active -> Compacting. When the context window approaches capacity, the compaction system summarizes the conversation. The session continues with a compressed history.
  • Crashed -> Ended. A crashed session has no session_end marker. It's implicitly ended when the PID is no longer alive.
  • Ended -> Resuming. Any ended session can be resumed, whether it ended gracefully or crashed.

Data Retention

JSONL transcript files are not automatically deleted. They accumulate over time. The expected lifecycle:

Age Size (typical) Action
< 1 day 50-500 KB Active use, may be resumed
1-7 days - Available for resume if needed
7-30 days - Rarely resumed, but valuable for audit
> 30 days - Candidate for cleanup (manual or automated)

A heavy user might generate 1-5 MB of transcripts per day. After a month, that's 30-150 MB -- noticeable but not problematic. There's no built-in garbage collection; users who want to clean up can delete old .jsonl files directly.

Architectural Lessons

1. Use Branded Types for Identity

SessionId is a branded type -- string & { __sessionId: true }. This means you can't accidentally pass a regular string where a session ID is expected. TypeScript catches the error at compile time:

// This compiles
const id: SessionId = generateSessionId();

// This doesn't compile
const id: SessionId = "some-random-string";  // Type error

Branded types cost nothing at runtime (they compile to plain strings) but prevent a class of bugs where identifiers get mixed up. When your system has session IDs, agent IDs, message IDs, and tool-use IDs all represented as strings, branding prevents passing the wrong one.

2. Append-Only Logs for Crash Resilience

JSONL's append-only nature means the transcript is a commit log. Every write extends the log; no write modifies or deletes previous entries. This matches the reality of conversation: messages happen in sequence and can't be un-said. The format matches the domain.

For any persistent state that grows monotonically (logs, event streams, conversation history), append-only formats are the simplest way to achieve crash resilience. The trade-off is query performance -- finding a specific message requires scanning the entire file. For session transcripts (typically hundreds to thousands of entries), this is acceptable.

3. Atomic State Transitions for Coupled Fields

The Atomic Switch Pattern (switchSession()) prevents drift between sessionId and sessionProjectDir. The principle generalizes: when two or more fields are semantically coupled, enforce atomic updates by exposing a single mutation function and no individual setters.

This is a design-time decision, not a runtime enforcement. There's no lock, no transaction, no CAS operation. The protection comes from the API surface: if the only way to change the fields is through a function that changes both, they can't drift.

4. Signal-Based Decoupling for Lifecycle Events

The sessionSwitched signal allows consumers to react to session changes without the state module importing them. This is particularly important for bootstrap/state.ts, which must remain a leaf in the import DAG (Chapter 3). Signals provide the indirection that decouples the emitter from all listeners.

5. Graceful Shutdown Is Ordered Cleanup

The shutdown sequence matters. Stop input before aborting requests. Abort requests before flushing telemetry. Flush telemetry before writing the end marker. Write the end marker before deregistering. Each step depends on the previous step's completion.

Error isolation (try/catch per handler) ensures that a failure in one cleanup step doesn't cascade. The principle: never let a cleanup error prevent other cleanups from running.

6. Design for Resume from Day One

Session resume isn't a feature you bolt on later. The transcript format, the project-scoped storage, the session registry -- these are all decisions made at the architecture level that enable resume as a first-class capability.

If you're building a CLI agent and think "we'll add resume later," you'll discover that your state isn't serializable, your conversation history isn't persisted in a resumable format, and your session identity doesn't survive process restarts. Design for resume from the start, even if you ship it later.
