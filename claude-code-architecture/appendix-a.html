Appendix A: Architecture Decision Record Template

Why ADRs Matter for AI Agent Development

Architecture decisions are the most expensive knowledge to lose. A team can recover from a lost config file in minutes, a deleted database in hours, even a corrupted codebase in days. But lost architectural context --- the reasons behind design choices --- takes months to reconstruct, if it can be reconstructed at all.

Architecture Decision Records (ADRs) solve this by capturing decisions as immutable documents. Each ADR records what was decided, why, what alternatives were considered, and what consequences were accepted. The format originated in Michael Nygard's 2011 blog post and has since become standard practice in systems engineering. But ADRs are especially critical for AI agent development, where the design space is new, the trade-offs are unintuitive, and decisions that seem obvious today will be questioned by every new team member tomorrow.

Consider the decisions discussed throughout this book. Why global state over dependency injection? Why a full shell parser instead of regex? Why JSON-RPC for MCP instead of REST? Each of these has a multi-paragraph justification involving constraints, trade-offs, and rejected alternatives. Without ADRs, that justification lives in the heads of the original authors --- and leaves when they do.

AI agent systems face three properties that make ADRs particularly valuable:

Novel design space. There is no Design Patterns book for AI agents. When you choose between streaming architectures, tool dispatch strategies, or permission models, you are often the first team to make that specific trade-off in that specific context. Future engineers will not find your reasoning in a textbook. The ADR is the textbook.

Rapid evolution. AI capabilities change faster than any other software domain. A decision that was correct for GPT-4-class models may be wrong for next-generation models. ADRs let future engineers understand which constraints shaped the decision, so they know when to revisit it.

Safety-critical consequences. An AI agent that executes shell commands, modifies filesystems, and accesses APIs has a larger blast radius than a typical application. Architectural decisions about security boundaries, permission models, and trust levels carry higher stakes. The reasoning behind these decisions must survive personnel changes.

The ADR Template

Every ADR follows a consistent structure. Consistency matters: when an engineer reads their fifteenth ADR, the format should be invisible, letting the content speak.

The Format

# ADR-NNN: Title (Decision Statement in Imperative Mood)

## Status

[Proposed | Accepted | Deprecated | Superseded by ADR-NNN]

## Date

YYYY-MM-DD

## Context

What is the issue that motivates this decision? What forces are at play?
Include technical constraints, business requirements, team capabilities,
timeline pressures, and any prior decisions that constrain this one.

## Decision

State the decision as a complete sentence in active voice:
"We will use X for Y because Z."

## Consequences

### Positive
- What becomes easier, faster, or safer?
- What capabilities does this enable?

### Negative
- What becomes harder or impossible?
- What technical debt does this introduce?
- What maintenance burden does this create?

### Neutral
- What changes that is neither clearly good nor bad?
- What teams or workflows are affected?

## Alternatives Considered

### Alternative 1: [Name]
- Description of the approach
- Why it was rejected (be specific: "Too slow for X", not "Not ideal")

### Alternative 2: [Name]
- Description of the approach
- Why it was rejected

## References

- Links to relevant discussions, prototypes, benchmarks, or prior art

Field-by-Field Guidance

Title. Use imperative mood: "Use X Over Y" not "We decided to use X." The title should be a complete, searchable decision statement. Bad: "State Management." Good: "Use Global State Over Dependency Injection."

Status. Start at Proposed. Move to Accepted after team review. Never delete --- move to Deprecated or Superseded with a pointer to the replacement ADR.

Context. This is the most important section. A decision without context is just an assertion. Include: - The technical problem being solved - The constraints that limit the solution space (performance, compatibility, team size, timeline) - Any prior decisions that create path dependency - The scale at which the system operates (a decision that works for 10 tools may not work for 100)

Decision. One paragraph. Start with "We will..." followed by the decision, followed by the primary justification. Everything else goes in Context and Consequences.

Consequences. Separate positive, negative, and neutral. Be honest about the negatives --- an ADR that lists only positive consequences is propaganda, not documentation. Future engineers need to know what problems this decision creates so they can plan around them.

Alternatives Considered. The most undervalued section. When a future engineer asks "why didn't we just use X?", this section answers them without a meeting. For each alternative, explain specifically why it was rejected. "Didn't fit our needs" is not a reason. "Added 200ms to startup time because it requires dynamic module loading" is a reason.

Five Example ADRs from AI CLI Agent Architecture

The following ADRs correspond to decisions discussed in Chapters 3, 15, 27, 21, and 34 of this book. Each demonstrates the template applied to a real architectural decision.

ADR-001: Use Global State Over Dependency Injection

Status: Accepted

Date: 2024-02-15

Context:

The AI CLI agent requires shared state across its entire call stack: model configuration, session identity, telemetry counters, cost tracking, feature flags, permission caches, and more. The call stack from user prompt to tool execution traverses 15+ function calls across 8 architectural layers. Every layer needs access to some subset of shared state.

The team has 3 engineers. The application is a single-process CLI tool serving one user at a time. There is no concurrent mutation. The codebase is TypeScript, where dependency injection frameworks (InversifyJS, tsyringe) add significant complexity and bundle size.

Decision:

We will use a global mutable singleton for application state, accessed through typed accessor functions (getters and setters), because the application is single-process, single-user, and the call stack is too deep for parameter threading.

Consequences:

Positive: - Clean function signatures across 500+ functions --- no ctx parameter threading - Zero framework overhead --- no DI container, no lifetime management, no circular dependency resolution - Cross-cutting concerns (telemetry, cost tracking, feature flags) are accessible from any architectural layer without ceremony - New state fields require adding one getter and one setter, not modifying 15 function signatures

Negative: - Test isolation requires an explicit resetStateForTests() function called in every test's beforeEach - Implicit dependencies --- a function's dependency on state is not visible in its signature - Refactoring requires grep-based discovery of all accessor call sites - Cannot run multiple agent instances in the same process (no per-instance state)

Neutral: - Accessor functions serve as a grep-friendly indirection layer, partially mitigating the implicit dependency cost - The single-process constraint eliminates the concurrency argument for DI, but may need revisiting if the agent ever moves to a server architecture

Alternatives Considered:

Dependency Injection (InversifyJS / tsyringe): Would add type-safe constructor injection and testability. Rejected because: (1) every function in the 15-layer call stack would need a context parameter or would need to be a class method on an injected service, (2) the application is single-process with no concurrent state mutation, eliminating the primary benefit of DI, (3) DI containers add 50-100ms to startup, conflicting with the 400ms startup budget.

React-style Context (passed through component tree): The UI layer uses React/Ink, making React Context a natural fit for UI state. Rejected for non-UI state because tool execution, API calls, and permission checks do not flow through the React component tree. Two state systems (React Context for UI, something else for everything else) adds complexity.

Event Sourcing / Redux-style Store: Every state change is an event, enabling replay and debugging. Rejected because the overhead of action creators, reducers, and middleware is disproportionate for a CLI tool where state changes are infrequent and non-concurrent. The debugging benefit does not justify the development velocity cost.

References: - Chapter 3: Design Principles & Trade-offs (detailed analysis) - Michael Nygard on singleton state in CLI tools (2019)

ADR-002: Use Full Shell Parser Over Regex for Bash Security

Status: Accepted

Date: 2024-03-20

Context:

The Bash tool executes shell commands on the user's machine with the user's permissions. Malicious or confused prompts can cause the agent to run destructive commands (rm -rf /, curl | bash, credential exfiltration). The security system must analyze commands before execution to detect dangerous patterns.

The initial implementation used regex patterns to match dangerous commands. Within the first month, 14 distinct bypass techniques were discovered: command substitution ($(rm -rf /)), process substitution (<(malicious_command)), quoted splitting (r''m -rf /), hex escaping (\x72\x6d -rf /), heredoc injection, brace expansion, and more. Each bypass required a new regex, and each new regex introduced edge cases.

The fundamental problem: shell syntax is not a regular language. It cannot be fully parsed by regular expressions. Any regex-based approach will have an infinite supply of bypasses.

Decision:

We will implement a full shell parser that produces an abstract syntax tree (AST) from bash commands, then analyze the AST for dangerous patterns, because regex-based security analysis is fundamentally insufficient for shell syntax.

Consequences:

Positive: - Handles all bash syntax: pipes, subshells, command substitution, process substitution, heredocs, brace expansion, quoting, escaping - Security analysis operates on semantic structure (AST nodes), not textual patterns --- immune to syntactic obfuscation - The parser is also used for non-security purposes: path extraction, command classification, environment variable detection - New security rules are AST node matchers, not fragile regexes

Negative: - 4,400 lines of parser code --- the single largest module in the codebase - Parser bugs are security bugs (a command that parses incorrectly might bypass security checks) - Maintenance burden: bash syntax is complex and poorly specified in edge cases - Startup cost: the parser must be loaded even for non-Bash tool calls (mitigated by deferred loading)

Neutral: - The parser does not execute bash --- it only analyzes syntax. Actual execution uses the system shell. This means the parser must be kept in sync with bash's behavior but does not need to implement execution semantics

Alternatives Considered:

Regex Pattern Matching: Simple to implement, easy to understand. Rejected because 14 bypasses were found in the first month, and the theoretical basis is unsound --- shell syntax is not a regular language. Every new regex is a patch, not a fix.

External Shell Analysis Tool (ShellCheck): ShellCheck is a mature shell linter. Rejected because: (1) it analyzes for correctness, not security --- it would need significant modification to detect destructive patterns, (2) it is a Haskell binary, adding a runtime dependency that conflicts with the single-binary deployment model, (3) round-trip latency to an external process adds ~50ms per command analysis.

Sandbox Execution (Docker/nsjail): Run every command in a container, preventing any destructive action. Rejected because: (1) the agent needs to modify the user's actual filesystem and run real builds, (2) container startup adds 500ms+ per command, (3) not all users have Docker installed, (4) filesystem mounting and network configuration create their own security surface.

Allowlist-Only Execution: Only permit a predefined set of commands. Rejected because an AI agent must be able to run arbitrary build commands, test commands, and development tools. An allowlist would break the core use case.

References: - Chapter 15: The Bash Tool --- A Case Study in Complexity - Chapter 19: Bash Security Architecture

ADR-003: Use React/Ink for Terminal UI Over Raw ANSI

Status: Accepted

Date: 2024-01-28

Context:

The AI CLI agent must render streaming markdown, tool execution progress, permission prompts, multi-line code blocks with syntax highlighting, and interactive elements (tab completion, command palette) in a terminal. The UI must update in real-time as tokens arrive from the streaming API, handle terminal resize events, and degrade gracefully when the terminal does not support advanced features.

Traditional CLI tools use raw ANSI escape sequences or libraries like chalk + readline. These work for simple output but become unmanageable for complex, stateful, real-time UIs. The state management problem --- tracking what is on screen, what needs to be redrawn, and how partial updates interact --- is fundamentally the same problem that React solves for browser UIs.

Decision:

We will use React with the Ink renderer for terminal UI, because the component model, state management, and reconciliation algorithm solve terminal rendering problems that are intractable with raw ANSI sequences.

Consequences:

Positive: - Component model enables composition: <ToolResult> contains <CodeBlock> contains <SyntaxHighlighter>, each managing its own state - React's reconciliation algorithm handles partial re-renders --- only changed regions of the terminal are redrawn - Hooks (useState, useEffect, useMemo) provide familiar state management patterns for streaming data - Third-party Ink components (spinners, tables, select inputs) accelerate UI development - The team's existing React expertise transfers directly

Negative: - Bundle size: React + Ink add ~150KB to the production bundle - Rendering latency: the React reconciliation pass adds ~2ms per frame compared to direct ANSI writes - Terminal abstraction leak: some terminal behaviors (cursor positioning, alternate screen buffer) require escaping the Ink abstraction with raw ANSI - Dependency on Ink's maintenance: if Ink is abandoned, the terminal renderer becomes a maintenance burden

Neutral: - React's virtual DOM model is overkill for simple text output, but the agent's UI is not simple text output --- it is a stateful, streaming, interactive interface - Developers must understand both React patterns and terminal escape codes for advanced features

Alternatives Considered:

Raw ANSI + chalk + readline: Maximum control, minimum dependencies. Rejected because managing stateful re-renders of streaming markdown with inline code blocks, progress bars, and permission prompts requires reimplementing a reconciliation algorithm. That is what React is.

Blessed / blessed-contrib: Full-featured terminal UI library with widgets. Rejected because: (1) effectively unmaintained since 2019, (2) widget-based model is less composable than React's component model, (3) no streaming-first architecture.

Bubbletea (Go) / Ratatui (Rust): Excellent terminal UI frameworks in other languages. Rejected because the codebase is TypeScript. Cross-language FFI for the UI layer introduces complexity disproportionate to the benefit.

References: - Chapter 27: Terminal UI Architecture - Ink documentation: https://github.com/vadimdemedes/ink

ADR-004: Use JSON-RPC Over REST for MCP Protocol

Status: Accepted

Date: 2024-06-10

Context:

The Model Context Protocol (MCP) enables the AI agent to communicate with external tool servers. The protocol needs to support: bidirectional communication (server can send notifications to client), capability negotiation at connection time, multiple concurrent requests on a single connection, and stateful sessions with initialization and shutdown phases.

The protocol must be simple enough for individual developers to implement MCP servers in any language, yet structured enough to support complex interactions like progress reporting, cancellation, and resource subscriptions.

Decision:

We will use JSON-RPC 2.0 as the wire protocol for MCP, transported over stdio (for local servers) and HTTP with Server-Sent Events (for remote servers), because JSON-RPC provides the request-response and notification semantics the protocol requires without the overhead of a full REST API design.

Consequences:

Positive: - JSON-RPC's built-in notification type (no id field) maps directly to MCP's notification semantics (progress updates, log messages) without protocol extensions - Request/response correlation via numeric id enables multiplexed concurrent requests on a single connection - The protocol is transport-agnostic --- the same JSON-RPC messages work over stdio, HTTP, and WebSocket - JSON-RPC is a well-specified standard (3 pages), making server implementation trivial in any language with a JSON parser - Error codes are standardized, reducing ambiguity in error handling

Negative: - No built-in discoverability (unlike REST with HATEOAS or OpenAPI) --- tool schemas must be exchanged during capability negotiation - No built-in streaming for large responses (mitigated by SSE transport for remote servers) - JSON-RPC's batch request feature adds parsing complexity for minimal benefit (MCP does not use batching) - Developers familiar with REST must learn JSON-RPC conventions (method naming, error code ranges)

Neutral: - JSON-RPC is less widely known than REST, but more widely known than gRPC or Cap'n Proto, balancing familiarity with capability

Alternatives Considered:

REST (HTTP + JSON): The default choice for web APIs. Rejected because: (1) REST is fundamentally request-response, making server-initiated notifications awkward (requires long polling or WebSocket upgrade), (2) REST's resource-oriented model does not map cleanly to tool invocation semantics (is a tool call a POST to /tools/{name}/invoke? A POST to /invoke with a body?), (3) HTTP overhead (headers, status codes, content negotiation) is disproportionate for stdio-transported local server communication.

gRPC: Bidirectional streaming, strong typing via protobuf, code generation. Rejected because: (1) protobuf compilation step raises the barrier for individual developers building MCP servers, (2) gRPC's HTTP/2 requirement complicates stdio transport, (3) the protocol's simplicity goal conflicts with gRPC's infrastructure requirements.

WebSocket (raw): Full-duplex communication with minimal overhead. Rejected as the sole transport because: (1) WebSocket requires an HTTP upgrade handshake, which is awkward over stdio, (2) raw WebSocket has no built-in request/response correlation --- we would need to build it, which is what JSON-RPC already provides. WebSocket is used as a transport for JSON-RPC in some MCP implementations.

Custom Binary Protocol: Maximum performance, minimum overhead. Rejected because the ecosystem value of MCP depends on ease of server implementation. A custom binary protocol requires each language to implement a parser. JSON is universally supported.

References: - Chapter 21: MCP Protocol Architecture - JSON-RPC 2.0 Specification: https://www.jsonrpc.org/specification - MCP Specification: https://modelcontextprotocol.io

ADR-005: Use Compile-Time Feature Flags via Bun Bundler

Status: Accepted

Date: 2024-04-05

Context:

The AI CLI agent ships as both a standalone product and an embedded SDK. These two builds share 95% of their code but differ in: entry point, available tools (the SDK exposes a subset), UI components (the SDK has no terminal UI), default permissions, and analytics behavior. Additionally, internal feature flags gate work-in-progress features, A/B tests, and gradual rollouts.

Runtime feature flags (read from config or environment at startup) are the standard approach. However, in a CLI tool with a 400ms startup budget and a 25MB bundle, runtime flags have costs: dead code for disabled features is still in the bundle, the flag evaluation logic runs on every code path, and conditional branches reduce JavaScript engine optimization opportunities.

Decision:

We will use the Bun bundler's compile-time define/replace feature to implement feature flags as build-time constants, because this enables dead code elimination, zero-cost flag evaluation, and build-variant-specific bundles.

Consequences:

Positive: - Dead code elimination: code behind a false flag is removed from the bundle entirely, reducing bundle size by 15-20% for the SDK build - Zero-cost evaluation: if (IS_SDK_BUILD) compiles to if (false) and is eliminated by the minifier --- no runtime check - Build variant isolation: the standalone and SDK builds are fully independent artifacts with no shared runtime state - Feature flag changes require a rebuild, not a redeployment --- appropriate for a CLI tool where "deployment" is a new version download

Negative: - Cannot change flags without rebuilding --- no runtime toggle for gradual rollouts (mitigated by using runtime flags for rollout-sensitive features) - Build matrix grows: each flag combination is a separate build. With N flags, there are 2^N possible builds (mitigated by limiting compile-time flags to build variants, not individual features) - Debugging requires knowing which build variant is running, since the source code contains branches that may not exist in the running binary - Bun-specific: the define/replace feature ties the build system to Bun

Neutral: - The compile-time/runtime split creates two categories of flags that developers must understand: compile-time (build variant, immutable) and runtime (feature rollout, mutable)

Alternatives Considered:

Runtime Feature Flags (LaunchDarkly / environment variables): Toggle features without rebuilding. Rejected for build-variant flags because: (1) dead code for disabled features remains in the bundle, adding 3-5MB to the SDK build, (2) startup must fetch or evaluate flag state, adding 10-50ms, (3) the standalone/SDK split is not a gradual rollout --- it is a permanent build variant. Runtime flags are still used for features that need gradual rollout.

Preprocessor Directives (C-style #ifdef): The traditional approach for build variants. Rejected because TypeScript has no preprocessor, and adding one (via babel plugin or custom transform) introduces non-standard syntax that breaks IDE support, linting, and type checking.

Separate Codebases (fork): Maintain two codebases for standalone and SDK. Rejected because 95% code sharing makes this a maintenance nightmare. Bug fixes must be applied twice, and the codebases will diverge over time.

References: - Chapter 34: The Architecture of Evolution - Bun bundler documentation: https://bun.sh/docs/bundler

Using ADRs in Your Own AI Agent Project

Getting Started

Start with ADR-001 the day you make your first architectural decision. Do not retroactively document all decisions at once --- that produces shallow, after-the-fact rationalizations. Instead, document decisions as they happen, when the context is fresh and the alternatives are still in working memory.

Naming and Numbering

Use sequential numbers with zero-padding: ADR-001, ADR-002, and so on. Store them in a docs/decisions/ directory. Never reuse numbers --- a deprecated ADR stays at its number, and the superseding ADR gets the next number.

docs/
  decisions/
    ADR-001-global-state-over-di.md
    ADR-002-shell-parser-over-regex.md
    ADR-003-react-ink-terminal-ui.md
    ...

When to Write an ADR

Write an ADR when:

  • The decision affects more than one module or subsystem
  • The decision is difficult to reverse (choosing a database, a protocol, a UI framework)
  • The team debated the decision for more than 30 minutes
  • A future engineer is likely to ask "why didn't we just...?"
  • The decision has security implications

Do not write an ADR for:

  • Variable naming conventions (put those in coding standards)
  • Library version choices (put those in dependency management)
  • Decisions that are trivially reversible (formatting rules, lint config)

Reviewing and Updating

ADRs are immutable in their core content. If a decision is revisited, write a new ADR with Status "Supersedes ADR-NNN" and update the original's status to "Superseded by ADR-NNN." This preserves the historical record --- you can always trace the evolution of a decision through the chain of superseding ADRs.

Review the ADR index quarterly. If the codebase has diverged from a decision (it happens), either write a new ADR documenting the actual current approach, or fix the code to match the decision. The worst state is a codebase that contradicts its own documented decisions without explanation.

ADRs as Onboarding

The ADR directory is the single best onboarding document for new engineers. A developer who reads 20 ADRs understands not just what the system does, but why it does it that way and what other approaches were considered. This context takes months to acquire through code reading alone.

For AI agent projects specifically, ADRs serve double duty: they document the architecture for human engineers, and they provide context for the AI agent itself. An agent that can read its own ADRs can make better decisions about code changes, because it understands the reasoning behind the existing architecture. As discussed in Chapter 8, system prompt assembly can include relevant ADRs when the agent is working in areas affected by documented decisions.

Template Files

The template from this appendix is available as a standalone markdown file. Copy it into your project:

mkdir -p docs/decisions
cp template/adr-template.md docs/decisions/ADR-000-template.md

Then for each new decision:

cp docs/decisions/ADR-000-template.md docs/decisions/ADR-NNN-short-title.md

Fill in the sections. Commit it alongside the code that implements the decision. The ADR and the code should land in the same pull request --- this makes the decision's context reviewable at the same time as the implementation.
