Chapter 27: Terminal UI Architecture

Every terminal application eventually faces a fundamental design question: how do you build a rich, interactive interface inside a medium that only understands sequential streams of characters? The browser answered this decades ago with HTML, CSS, and a layout engine. Native applications have toolkit frameworks like Cocoa, GTK, and Qt. Terminal applications, historically, have had two options: raw ANSI escape sequences (fast, brittle, impossible to maintain) or curses-style libraries (stable, but locked into a cell-grid paradigm from the 1970s). Neither is adequate for an AI CLI agent that needs to render streaming markdown, manage virtual scroll through conversations spanning thousands of lines, display overlapping panels, and maintain 30fps responsiveness while an LLM generates tokens at full speed.

This chapter examines the architectural decisions behind building a modern terminal UI for an AI agent. We will cover why a declarative component model like React/Ink beats imperative alternatives, how the component hierarchy organizes a complex interactive application, how streaming content gets parsed and rendered incrementally, how the rendering pipeline transforms application state into terminal output, how state management scales to 80+ behavioral concerns, and how responsive design adapts to terminal dimensions. The patterns here apply to any interactive CLI application, but the constraints of an AI agent -- real-time streaming, long-running sessions, multi-panel layouts -- push them to their limits.

27.1 Why React/Ink for a Terminal Application

The choice of React as the UI framework for a terminal application surprises most engineers. React is a browser technology. Terminals are not browsers. But the choice is not about React's DOM rendering -- it is about React's component model, and that model solves problems that terminal UI developers have struggled with for decades.

The Three Candidates

When designing a terminal UI for an AI agent, three architectural approaches compete:

graph LR
    A[Terminal UI Approaches] --> B[Raw ANSI]
    A --> C[Curses/blessed]
    A --> D[Declarative/React-Ink]
    B --> B1[Direct escape sequences]
    B --> B2[Manual state tracking]
    C --> C1[Cell-grid abstraction]
    C --> C2[Widget toolkit]
    D --> D1[Component model]
    D --> D2[Virtual DOM + Layout engine]
Approach Strengths Weaknesses
Raw ANSI Zero overhead, full control No abstraction, manual cursor math, impossible to compose
Curses/blessed Stable APIs, widget library Imperative paradigm, cell-by-cell updates, no layout engine
React/Ink Declarative, composable, layout engine, differential rendering Larger dependency tree, React learning curve, custom fork needed

Raw ANSI works for simple tools -- a progress bar, a colored log line. But an AI agent's UI has dozens of independently updating regions: the message list, the streaming response, tool execution spinners, the input area, the status bar, the typeahead overlay, the permission prompt. Managing the cursor position and redraw regions for all of these imperatively is a combinatorial nightmare.

Curses-style libraries (blessed, neo-blessed) provide widgets and event handling but operate on a cell-grid model. Every character occupies exactly one cell. There is no concept of flexbox layout, percentage-based widths, or nested overflow clipping. Building a responsive two-panel layout where the sidebar takes 35% of the terminal width requires manual arithmetic on every resize event. Worse, the imperative update model means every state change requires explicit widget.setContent() calls -- there is no reconciliation, no differential updates, no declarative description of "what should be on screen."

React/Ink solves both problems. The component model gives you composition: build a <MessageList>, a <PromptInput>, a <StatusBar>, and assemble them into a screen. The virtual DOM gives you differential rendering: describe the desired state, and the framework computes the minimum terminal writes needed. The Yoga layout engine gives you flexbox: declare flexGrow={1} on the message area and it consumes all available space after fixed-height components claim their rows.

The Declarative Advantage

The core argument for a declarative UI in a terminal is the same as in a browser: when state changes are frequent and interleaved, describing what the screen should look like is simpler and less error-prone than describing how to transform the current screen into the next state.

Consider a streaming response. Tokens arrive every 10-20ms. Each token appends to the current message. The message list may need to scroll. A tool call might start mid-stream, requiring a spinner. The input area must remain responsive. In an imperative model, each of these events requires explicit code to update exactly the right screen region without corrupting adjacent content. In a declarative model, you update the state (append token to buffer), and the framework figures out what changed on screen.

// Imperative: you manage every screen region manually
function onToken(token: string) {
  buffer += token;
  const lines = wrapText(buffer, termWidth);
  const visibleLines = lines.slice(-viewportHeight);
  moveCursor(0, messageAreaTop);
  for (const line of visibleLines) {
    clearLine();
    writeLine(line);
  }
  // Don't forget to restore the input area...
  moveCursor(0, inputAreaTop);
  redrawInput();
  // And the status bar...
  moveCursor(0, statusBarTop);
  redrawStatus();
}

// Declarative: you update state, framework handles rendering
function onToken(token: string) {
  setStreamBuffer(prev => prev + token);
  // React re-renders only the changed components
}

The declarative version is not just shorter -- it is correct by construction. The imperative version has a bug if any component's position changes (resize, new tool result expands, sidebar toggles). The declarative version handles all of that through the layout engine.

The Cost

The React/Ink approach is not free. The dependency tree is larger. Startup time includes React initialization and Yoga WASM loading. A custom Ink fork is needed for production-quality terminal rendering, because upstream Ink does not handle adaptive render throttling, ANSI-aware text measurement, or deep overflow clipping.

For simple CLI tools, this cost is not justified. For an AI agent that runs sessions lasting hours with conversations spanning thousands of rendered lines, the investment pays for itself in the first week of development.

27.2 Component Hierarchy

The component hierarchy of an AI CLI agent's terminal UI is deliberately flat. Deep nesting costs layout performance -- every intermediate <Box> node creates a Yoga layout calculation. The hierarchy looks like this:

graph TD
    App[App] --> REPL[REPL Screen]
    REPL --> ML[MessageList]
    REPL --> PI[PromptInput]
    REPL --> PP[PermissionPrompt]
    REPL --> SP[SidePanel]

    REPL --> SL[StatusLine]

Three design decisions shape this hierarchy:

The REPL is a god component. It owns nearly all application state and passes it down via props. In web development, this is an anti-pattern. In terminal UIs, it is often the correct choice. Terminal applications have fundamentally different constraints: no CSS cascade, no event bubbling, no browser layout engine handling reflows. The REPL needs to know the terminal dimensions, scroll position, streaming state, permission mode, and input state simultaneously to make rendering decisions. Centralizing this state eliminates coordination overhead.

The hierarchy is two levels deep for most paths. REPL contains MessageList contains message components. REPL contains PromptInput contains its sub-components. No intermediate "layout containers" or "wrapper components" exist. Each intermediate component would add a Yoga node, a reconciliation step, and a potential reflow. For a UI rendering at 30fps, these costs add up.

Composition happens through hooks, not components. The REPL component calls 80+ custom hooks, each managing one behavioral concern. This is the inverse of the typical React advice to "break components into smaller components." In terminal UIs, break behavior into smaller hooks and keep the component that composes them as a single unit. The hooks are individually testable without a terminal. The component is the assembly point.

The Render Function

After thousands of lines of hooks and state management, the REPL's render function is structurally simple -- a vertical flex column:

return (
  <Box flexDirection="column" height={terminalHeight}>
    {/* Main content area */}
    <Box flexGrow={1} flexDirection="row">
      <Box flexGrow={1} flexDirection="column">
        <MessageList
          messages={messages}
          visibleRange={scroll.visibleRange}
          streamingMessage={isStreaming ? streamBuffer : null}
          activeTools={activeTools}
        />
      </Box>
      {sidePanelVisible && (
        <Box width={Math.floor(terminalWidth * 0.35)} borderStyle="single">
          <SidePanel content={sidePanelContent} />
        </Box>
      )}
    </Box>

    {backgroundTasks.length > 0 && <BackgroundTaskBar tasks={backgroundTasks} />}

    {mode === 'permission' && (
      <PermissionPrompt request={permissionRequest} />
    )}

    <StatusLine mode={mode} model={session.model} tokens={tokens} cost={cost} />
    <PromptInput value={inputValue} cursor={cursorPosition} />
    {typeahead.visible && <TypeaheadOverlay results={typeahead.results} />}
  </Box>
);

The layout uses Ink's flexbox model. The message list gets flexGrow={1}, consuming all vertical space after fixed-height components (status line, input area, task bar) claim their rows. The side panel, when visible, takes 35% of terminal width. Components that appear conditionally (permission prompt, background task bar, typeahead overlay) are rendered only when their state is active, avoiding layout computation when not needed.

27.3 State Management Architecture

An AI agent's terminal UI manages more state than most web applications. The streaming response, scroll position, input buffer, permission prompts, tool execution tracking, background tasks, typeahead suggestions, terminal dimensions, vim mode, search state -- all of these interact with each other across dozens of event handlers.

The 80+ Hooks Pattern

Rather than a centralized state management library like Redux or Zustand, the state is decomposed into 80+ custom React hooks, each owning one behavioral concern:

Category Count Examples
Input handling 12 useTextInput, useKeyBindings, useHistorySearch, usePasteDetection, useVimMode
Scroll management 6 useVirtualScroll, useScrollSearch, useMessageAnchors
Typeahead & completion 8 useTypeahead, useTabCompletion, useSlashCommandSuggestion, useFileSuggestion
Streaming & messages 10 useStreamingResponse, useStreamBuffer, useMessageFormatting, useToolTracking
Session & lifecycle 15 useSession, useSessionPersistence, useSessionForking, useIdleDetection
Layout & rendering 10 useTerminalLayout, useTerminalSize, useResponsiveLayout, useTheme
Integration & side effects 19+ useMemory, usePermissions, useNotifications, useHookExecution, useMCPServers

Why this many? Testability and composability.

Each hook can be tested in isolation. useVirtualScroll needs a message array and viewport height -- no terminal, no React DOM, no API connection. usePasteDetection needs keystroke timestamps -- feed it synthetic events and assert on detection thresholds. Small hooks mean small test surfaces.

Composability matters because not every screen mode needs every hook. The compact mode during /compact uses a subset. The permission prompt overlay uses only keyboard and layout hooks. Granular hooks let each mode pick exactly what it needs.

Why Not Zustand or Redux?

External state management adds latency that terminal rendering cannot afford. At 30fps with 33ms per frame, the rendering pipeline from state change to terminal output must complete within budget. Direct useState with careful update batching is faster than dispatching through an external store, and -- critically -- easier to debug when frames drop.

The exception is global state that genuinely needs to be shared across component boundaries without prop drilling. Theme configuration, session metadata, and feature flags are candidates for a lightweight store. But the majority of UI state (scroll position, input buffer, streaming buffer) is local to the REPL component and should stay there.

Ref-Based State for High-Frequency Updates

Values that change every frame -- spinner positions, stream buffer text, animation counters -- use useRef instead of useState. The difference is critical: useState triggers React reconciliation on every update. useRef mutates silently. A single useState counter increments on a fixed tick (e.g., 100ms) to trigger the actual re-render, which reads all the refs:

// Anti-pattern: useState for every spinner frame
const [spinnerFrame, setSpinnerFrame] = useState(0);
useEffect(() => {
  const id = setInterval(() => setSpinnerFrame(f => (f + 1) % 10), 100);
  return () => clearInterval(id);
}, []);
// This triggers a full React reconciliation every 100ms

// Better: ref + periodic render tick
const spinnerFrameRef = useRef(0);
const [, forceRender] = useState(0);
useEffect(() => {
  const id = setInterval(() => {
    spinnerFrameRef.current = (spinnerFrameRef.current + 1) % 10;
    forceRender(n => n + 1); // Batch with other ref updates
  }, 100);
  return () => clearInterval(id);
}, []);

This pattern collapses multiple high-frequency state changes into a single render tick, keeping the reconciliation budget under control.

27.4 Streaming Markdown Rendering

Streaming markdown is the defining rendering challenge of an AI agent's UI. Tokens arrive one at a time from the API -- a few characters every 10-20ms. The UI must render each token as it arrives, showing the user a progressively building response. But markdown is not designed for incremental parsing.

The Fundamental Problem

Markdown requires lookahead. Consider these partial streams:

Stream so far: "Here is some `code"
Is this inline code or a stray backtick? You need the closing ` to know.

Stream so far: "```python\ndef hello"
Is this a fenced code block? You need the closing ``` to confirm.

Stream so far: "**bold text"
Is this bold? You need the closing ** to know.

If you parse greedily -- treating every opening delimiter as the start of a formatted block -- you will render half the response as code or bold text until the closing delimiter arrives. If you parse conservatively -- waiting for closing delimiters before formatting -- the response looks like plain text with scattered punctuation until blocks complete.

The Solution: Incremental Parsing with Rollback

The architecture uses a two-phase approach:

sequenceDiagram
    participant API as API Stream
    participant Buffer as Stream Buffer
    participant Parser as Incremental Parser
    participant Render as Renderer
    participant Terminal as Terminal Output

    API->>Buffer: token chunk
    Buffer->>Parser: accumulated text
    Parser->>Parser: Parse with optimistic formatting
    Parser->>Parser: Detect unclosed delimiters
    Parser->>Parser: Rollback unclosed to plain text
    Parser->>Render: Styled spans + cursor
    Render->>Terminal: ANSI-styled output

Phase 1: Optimistic parse. The parser processes the accumulated buffer as if it were complete markdown. Opening delimiters start formatted blocks. The parser tracks which blocks are "open" (started but not closed).

Phase 2: Rollback. Open blocks at the end of the buffer are treated as plain text in the rendered output. The parser remembers their positions so that when the next chunk arrives, it can re-parse from the last known-good boundary.

interface ParseState {
  buffer: string;
  lastGoodBoundary: number; // Position of last fully-closed block
  openBlocks: OpenBlock[];  // Stack of unclosed formatting
}

function parseIncremental(state: ParseState, newChunk: string): StyledSpan[] {
  state.buffer += newChunk;

  // Re-parse from last known-good boundary
  const toParse = state.buffer.slice(state.lastGoodBoundary);
  const result = parseMarkdown(toParse);

  // Identify unclosed blocks
  const unclosed = result.blocks.filter(b => !b.closed);

  // Render closed blocks with formatting, unclosed as plain text
  const spans: StyledSpan[] = [];
  for (const block of result.blocks) {
    if (block.closed) {
      spans.push(...renderFormattedBlock(block));
      state.lastGoodBoundary += block.rawLength;
    } else {
      spans.push({ text: block.rawText, style: 'plain' });
    }
  }

  // Append the blinking cursor
  spans.push({ text: '\u258B', style: 'cursor' });

  return spans;
}

The lastGoodBoundary is the key optimization. When a new chunk arrives, the parser does not re-parse the entire conversation -- only the text from the last fully-closed block forward. For a response that is 90% complete, this means re-parsing only the trailing partial paragraph, not the 5,000 words before it.

Fenced Code Block Handling

Fenced code blocks (triple backticks) deserve special treatment because they are the most common "long-running open block" in AI agent output. The agent frequently generates multi-line code, and the user needs to see syntax highlighting as the code streams.

The solution: treat an opening ``` as the start of a code block immediately. Apply syntax highlighting to content as it arrives. Show a visual indicator (dimmed bottom border) that the block is still open. When the closing ``` arrives, finalize the block and update the border to solid.

function renderStreamingCodeBlock(block: OpenCodeBlock, width: number): Box {
  return (
    <Box flexDirection="column" borderStyle={block.closed ? "single" : "single"}>
      <Box>
        <Text dimColor>{block.language || 'code'}</Text>
      </Box>
      <Box>
        <Text>{highlightSyntax(block.content, block.language)}</Text>
      </Box>
      {!block.closed && (
        <Box>
          <Text dimColor>{'...'}</Text>  {/* Streaming indicator */}
        </Box>
      )}
    </Box>
  );
}

This gives the user immediate visual feedback that code is being generated, with proper highlighting, without waiting for the block to complete.

27.5 The Rendering Pipeline

The full rendering pipeline transforms API tokens into terminal output through five stages:

graph LR
    A[API Token] --> B[Message State]
    B --> C[React Component Tree]
    C --> D[Virtual DOM / Yoga Layout]
    D --> E[Character Grid]
    E --> F[Terminal Output]

    style A fill:#e1f5fe
    style B fill:#f3e5f5
    style C fill:#fff3e0
    style D fill:#e8f5e9
    style E fill:#fce4ec
    style F fill:#f5f5f5

Stage 1: API Token to Message State. Tokens arrive via SSE. The stream buffer accumulates them, debouncing at 16ms intervals to batch multiple tokens into a single state update. This prevents render thrashing -- 50-100 tokens per second would otherwise trigger 50-100 re-renders.

Stage 2: Message State to React Component Tree. State changes trigger React reconciliation. The MessageList component receives the updated messages array. Virtual scrolling (Section 27.6) filters to only the visible range. Each visible message maps to its component type: UserMessage, AssistantMessage, SystemMessage.

Stage 3: React Component Tree to Virtual DOM / Yoga Layout. React's reconciler creates or updates virtual DOM nodes. The Ink fork maps these to Yoga layout nodes. Yoga computes flexbox positions for every element -- widths, heights, offsets relative to parent. This happens in a single calculateLayout() call, typically completing in under 2ms.

Stage 4: Virtual DOM to Character Grid. The renderer traverses the laid-out tree, writing text content at computed positions into a two-dimensional character array. ANSI escape sequences for colors, bold, and underline are applied through composable transform functions. Overflow clipping masks content that extends beyond its container. Borders are drawn as Unicode box-drawing characters.

Stage 5: Character Grid to Terminal Output. The character grid is serialized to a string. A differential renderer compares with the previous frame's output. If identical, no write occurs. If different, ANSI erase-lines commands clear the previous output and the new content is written. A throttle (32ms leading+trailing) ensures no more than 30 terminal writes per second.

The Performance Budget

At 30fps, each frame has ~33ms:

Phase Typical Duration Notes
React reconciliation < 1ms Minimal with memoization
Yoga layout < 2ms Fast even for hundreds of nodes
Tree-to-grid rendering 1-5ms Scales with visible content
Grid serialization 2-10ms Scales with terminal dimensions
Terminal write 1-5ms Depends on diff size
Total 5-23ms Under 33ms budget

The bottleneck is grid serialization for large terminals. A 200-column by 50-row terminal produces 10,000 characters per frame. Each character must be tokenized for ANSI awareness. This is where the rendering budget gets tight on older hardware.

27.6 Virtual Scrolling

A Claude Code conversation can reach 10,000+ rendered lines over a session. Rendering all of them every frame would blow the performance budget. Virtual scrolling solves this by rendering only the lines visible in the viewport, plus a small buffer for smooth scrolling.

Core Data Structure

interface ScrollState {
  offset: number;         // Lines scrolled from top
  totalLines: number;     // Total rendered lines across all messages
  viewportHeight: number; // Visible rows in terminal
}

// Derived values
const visibleStart = offset;
const visibleEnd = Math.min(offset + viewportHeight, totalLines);
const maxOffset = Math.max(0, totalLines - viewportHeight);
const isAtBottom = offset >= maxOffset;

The Auto-Scroll Contract

Auto-scroll is the behavior users expect but never think about:

  1. Starts ON. New content snaps the viewport to the bottom.
  2. Any upward scroll disables it. Even one line up.
  3. Scrolling to the exact bottom re-enables it. offset >= maxOffset.
  4. Explicit "go to bottom" shortcut forces it on. Cmd+End or G in vim mode.

The critical edge case: when streaming content arrives while the user is scrolled up, totalLines increases but offset stays fixed. A subtle indicator shows "N new lines below." Only when they scroll down far enough does auto-scroll re-engage.

Viewport-Sliced Rendering

The performance win comes from skipping layout computation for off-screen messages:

function computeVisibleMessages(
  messages: Message[],
  visibleRange: { start: number; end: number },
): RenderedMessage[] {
  const result: RenderedMessage[] = [];
  let lineAccumulator = 0;

  for (const msg of messages) {
    const msgEnd = lineAccumulator + msg.renderedHeight;

    // Skip messages entirely above viewport
    if (msgEnd <= visibleRange.start) {
      lineAccumulator = msgEnd;
      continue;
    }

    // Stop once we pass below viewport
    if (lineAccumulator >= visibleRange.end) break;

    // Partially visible: slice the rendered lines
    const sliceStart = Math.max(0, visibleRange.start - lineAccumulator);
    const sliceEnd = Math.min(msg.renderedHeight, visibleRange.end - lineAccumulator);

    result.push({
      ...renderMessage(msg),
      lines: renderMessage(msg).lines.slice(sliceStart, sliceEnd),
    });

    lineAccumulator = msgEnd;
  }

  return result;
}

A message that renders to 500 lines of markdown but is only partially visible (lines 490-500 in the viewport) produces only 10 line objects for the layout engine. Without slicing, every frame would compute layout for all 500 lines and discard 490.

Pre-Computing Heights

Virtual scrolling requires knowing each message's rendered height before rendering it. This is a chicken-and-egg problem: you need the height to decide visibility, but you need to render to know the height.

The solution is a two-pass approach. When a message arrives or the terminal resizes, a lightweight estimator computes approximate heights based on content type and terminal width. The estimation is imprecise -- it does not account for complex table layouts or Unicode wide characters -- but the viewport buffer (rendering a few extra lines above and below) absorbs small mismatches.

27.7 Responsive Terminal Design

Terminals range from 40 columns (a narrow split pane) to 300+ columns (an ultra-wide monitor). The UI must adapt gracefully across this range without requiring user configuration.

Breakpoint Architecture

Rather than continuous scaling, the UI defines discrete breakpoints:

type LayoutMode = 'narrow' | 'normal' | 'wide';

function computeLayoutMode(columns: number): LayoutMode {
  if (columns < 60) return 'narrow';
  if (columns < 120) return 'normal';
  return 'wide';
}
Mode Columns Adaptations
Narrow (< 60) 40-59 No side panel, compact status line, truncated tool names, no borders on code blocks
Normal (60-119) 60-119 Full layout, optional side panel, standard status line
Wide (120+) 120+ Side panel default visible, expanded tool output, line numbers in code blocks

Resize Handling

Terminal resize events (SIGWINCH) trigger a re-layout. The resize handler debounces at 100ms to avoid layout thrashing during continuous resize (dragging a terminal edge):

function useTerminalSize() {
  const [size, setSize] = useState({
    columns: process.stdout.columns,
    rows: process.stdout.rows,
  });

  useEffect(() => {
    let timer: NodeJS.Timeout;
    const handler = () => {
      clearTimeout(timer);
      timer = setTimeout(() => {
        setSize({
          columns: process.stdout.columns,
          rows: process.stdout.rows,
        });
      }, 100);
    };
    process.stdout.on('resize', handler);
    return () => {
      process.stdout.off('resize', handler);
      clearTimeout(timer);
    };
  }, []);

  return size;
}

On resize, message heights are invalidated and re-estimated. The virtual scroll offset is adjusted to keep the same content visible (or as close as possible if the new terminal is too narrow to display the same amount of content).

27.8 The Static/Dynamic Rendering Split

Terminal rendering has a unique challenge that browser rendering does not: the "page" is rewritten every frame. In a browser, old content stays on screen and new content appends below. In a terminal UI framework, the entire visible area is cleared and redrawn 30 times per second.

This creates a problem for completed content. A tool result that finished rendering 30 seconds ago gets re-rendered every frame, consuming layout budget for content that will never change. The <Static> component pattern solves this by splitting rendering into two channels:

graph TD
    subgraph "Dynamic Channel (redrawn every frame)"
        DC[Current streaming message]
        DC2[Active tool spinners]
        DC3[Input area + status line]
    end

    subgraph "Static Channel (rendered once, pushed up)"
        SC[Completed messages]
        SC2[Finished tool results]
        SC3[System messages]
    end

    DC --> Terminal[Terminal Output]
    SC --> Terminal

Static content is rendered once and written permanently above the dynamic area. It scrolls up as new content arrives. It never re-renders.

Dynamic content is the live, changing portion of the UI. The streaming response, active spinners, the input area. This gets redrawn every frame.

The boundary between static and dynamic shifts as the conversation progresses. When a streaming response completes, it moves from the dynamic channel to the static channel. When a tool finishes executing, its result moves to static. This keeps the per-frame rendering cost proportional to the amount of actively-changing content, not the conversation length.

Implementation Pattern

function MessageDisplay({ messages, streamingMessage }) {
  // Completed messages render in Static (once, permanently)
  const completedMessages = messages.filter(m => m.status === 'complete');

  // Active messages render in the dynamic area (every frame)
  const activeMessages = messages.filter(m => m.status === 'streaming');

  return (
    <>
      <Static items={completedMessages}>
        {(msg) => <CompletedMessage key={msg.id} message={msg} />}
      </Static>

      {activeMessages.map(msg => (
        <StreamingMessage key={msg.id} message={msg} />
      ))}

      {streamingMessage && (
        <StreamingMessage message={streamingMessage} />
      )}
    </>
  );
}

The <Static> component tracks which items it has already rendered and only processes new additions. Old items are never re-rendered, never re-laid-out, never re-measured. This is what makes a terminal UI viable for conversations that span thousands of messages.

27.9 The Component Model: Reusable UI Pieces

Building a terminal UI from reusable components requires patterns adapted for the terminal's constraints.

Message Components

Each message role has its own component with a consistent interface:

interface MessageProps {
  content: ContentBlock[];
  width: number;
  collapsed?: boolean;
}

// UserMessage: simple text with a role indicator
// AssistantMessage: markdown rendering, code highlighting, tool blocks
// SystemMessage: dimmed text, often single-line
// ErrorMessage: red-highlighted with recovery actions
// ToolResultMessage: collapsible output with truncation

The width prop is critical. Every message component must know the available width for word wrapping. This flows from the terminal dimensions, through the layout engine, down to each component. Without explicit width, components cannot compute their rendered height, which breaks virtual scrolling.

Tool Execution Components

Tool executions are the most complex visual elements:

Phase 1 (running):    spinner Reading src/auth.ts...  3.2s
Phase 2 (complete):   checkmark Read src/auth.ts (142 lines, 3.2s)
Phase 3 (expanded):   [full file content, syntax-highlighted]

The three phases are distinct rendering states managed by a single ToolUseBlock component. The transition from phase 1 to phase 2 is driven by a tool completion event. Phase 3 is user-triggered (clicking or pressing Enter on a collapsed result).

The spinner animation cycles through Braille-pattern characters (['braille1', 'braille2', ...]) at 100ms intervals. Running tools are tracked by a dedicated useToolTracking hook that manages the spinner state and elapsed time display. When the tool completes, the spinner is replaced with a status icon and the elapsed time freezes.

The StatusLine Component

The status line at the bottom of the screen provides persistent context:

mode | model | tokens used | cost | context % | git branch

This single-row component updates frequently but cheaply -- it is a simple horizontal flex layout with text content. The status line reads from multiple hooks (session state, cost tracking, git integration) but renders a single <Box> with <Text> children. Because it is always visible and frequently updated, it is kept in the dynamic rendering channel, never promoted to static.

27.11 Performance Optimization Patterns

Five optimization patterns keep the UI responsive during heavy streaming:

1. Memoized message rendering. Each message is memoized by ID and terminal width. A message rendered in the previous frame returns its cached output instantly. Only new or resized messages trigger re-rendering.

2. Stream debouncing. Instead of re-rendering on every token (50-100/sec), the stream buffer batches tokens into 60fps render cycles (16ms). Multiple tokens arriving within one cycle produce a single state update.

3. Virtual scrolling. Only messages within the visible viewport (plus buffer) are laid out. A conversation with 500 messages but a 40-row viewport lays out ~45 rows of content.

4. Ref-based high-frequency state. Spinner positions, stream buffer text, and animation counters use useRef to avoid triggering reconciliation. A periodic tick reads all refs and triggers a single render.

5. Lazy tool result expansion. Tool results longer than 20 lines render as a collapsed summary. Expanding triggers a one-time full render that is then cached. Most tool results are never expanded.

These optimizations compose. During streaming, the per-frame cost is: reconcile only the changed message (memoization), lay out only the visible viewport (virtual scroll), batch tokens (debouncing), skip spinner state updates from reconciliation (refs), and keep completed tool results collapsed (lazy expansion). The result is sub-16ms frame times even on modest hardware.

27.12 Design Lessons

Building a terminal UI for an AI CLI agent teaches several lessons that transfer to any complex interactive system:

Centralize state when coordination dominates. If most state updates require knowing other state (scroll position depends on message count, which depends on streaming status, which depends on permission mode), centralizing in one component eliminates prop drilling and subscription patterns. The cost is a large file. The benefit is that every state transition is visible in one place.

Decompose behavior, not components. The 80+ hooks are the decomposition. Each is testable, reusable, and single-purpose. The component composes them. Terminal UIs cannot afford the layout overhead of deep component trees.

Optimize the hot path, tolerate the cold path. Streaming renders happen 60 times per second -- they must be fast. Initial conversation load happens once -- it can be slower. Message height computation happens on arrival -- it can be approximate. Optimize aggressively for the hot path, be relaxed about everything else.

The static/dynamic split is essential for long-running sessions. Without it, rendering cost grows linearly with conversation length. With it, cost is proportional to active content. This is the single most important optimization for an AI agent UI.

Declarative rendering eliminates a class of bugs. Every time you add a new UI element that updates independently (a new spinner, a new status indicator, a new overlay), the imperative approach requires updating every other element's redraw logic. The declarative approach just renders the new element -- the framework handles the composition. This is why React/Ink is worth the dependency cost.
