Chapter 31: Testing Non-Deterministic Systems

Every testing strategy you learned in school assumes determinism. Given the same input, the function produces the same output. If the test passed yesterday, it passes today. If it fails, you have a reproducible bug. AI agents destroy all three assumptions. The same prompt can produce different tool call sequences on consecutive runs. A test that passed at 2pm fails at 3pm because the model's sampling temperature introduced a different reasoning path. And when it fails, you cannot reproduce the failure because the model's internal state is opaque and the API response is gone.

This chapter lays out the architectural patterns for testing systems where the core computation -- the LLM inference -- is fundamentally non-deterministic. We will cover the testing pyramid adapted for AI agents, VCR recording and replay for deterministic test reproduction, eval frameworks that measure agent quality at scale, snapshot testing strategies that tolerate controlled drift, and techniques for testing everything around the LLM without involving it at all. The goal is a testing architecture that gives you confidence in production correctness without requiring every test to be perfectly repeatable.

31.1 The Fundamental Challenge

Traditional software testing relies on a simple contract: function(input) returns output. You write an assertion that output equals expected, and if the assertion holds across your test suite, you ship. The test is a proof by example.

AI agents break this contract at the most fundamental level. The LLM is a stochastic system. Even with temperature set to zero, floating-point arithmetic in the attention mechanism can produce different token selections across hardware, batch sizes, and API versions. The model might call Read then Grep on one run and Grep then Read on the next -- both valid paths to the same answer.

This creates three distinct testing problems:

The reproducibility problem. You cannot reproduce a bug by re-running the test. The model will take a different path and might not hit the bug at all. Traditional debugging -- "reproduce the failure, then bisect" -- does not work.

The assertion problem. You cannot assert on exact output. The model might say "The function has a bug on line 42" or "Line 42 contains a defect" or "There's an issue at config.py:42." All three are correct. String equality fails. Substring matching is fragile. Semantic equivalence requires another LLM call, which is itself non-deterministic.

The cost problem. Every test that involves the LLM costs money and takes seconds. A 500-test suite that each makes one API call costs $5-50 per run and takes 10-30 minutes. You cannot run this on every commit. You cannot run it in a developer's inner loop. The economics of testing change fundamentally.

These problems do not make testing impossible. They make it an architectural decision. You need a testing strategy that acknowledges non-determinism rather than fighting it, that isolates the deterministic parts for fast feedback, and that uses statistical methods for the non-deterministic parts.

31.2 The Testing Pyramid for AI Agents

The classic testing pyramid -- many unit tests, fewer integration tests, even fewer end-to-end tests -- needs reinterpretation for AI agents. The key insight is that most of the agent's code is deterministic. The tool implementations, the permission system, the configuration cascade, the context assembly algorithm -- all of these are pure functions or predictable state machines. Only the query loop, where the LLM decides what to do next, introduces non-determinism.

The adapted pyramid looks like this:

Unit Tests: The Deterministic Foundation

Unit tests cover everything that does not touch the LLM. This is the vast majority of the codebase:

  • Tool logic. Does the Read tool correctly read a file and return its contents? Does the Bash tool parse a command string into an AST? Does the Edit tool apply a string replacement correctly? These are pure functions with deterministic inputs and outputs.

  • Permission rules. Given a tool name and input, does the permission evaluator return allow, deny, or ask? The rule evaluation is a deterministic function: rules in, decision out. You can test every rule pattern, every edge case in glob matching, and every precedence interaction without any LLM involvement.

  • Configuration parsing. Does the settings cascade merge correctly? Does CLAUDE.md parsing extract the right directives? Do environment variable expansions work?

  • Context assembly. Given a conversation history and a token budget, does the context assembler produce the right set of messages? This is deterministic once you fix the conversation state.

  • Message formatting. Does the markdown renderer produce correct ANSI output? Does the diff engine produce correct unified diffs? Does the collapsing algorithm preserve error lines?

Unit tests run in milliseconds, cost nothing, and should cover the overwhelming majority of your code paths. In a well-designed agent, 80-90% of the codebase is testable at this level.

Integration Tests: Tool Execution and MCP

Integration tests verify that components work together correctly, with real I/O but without the LLM:

  • Tool execution. Spawn a real Bash process, execute a command, verify the output. Create a real temporary file, read it with the Read tool, verify the contents match.

  • MCP server communication. Start a real MCP server, connect over stdio, call a tool, verify the result. This tests the transport layer, the JSON-RPC serialization, the handshake, and the tool invocation path end to end.

  • Hook execution. Write a file that triggers the auto-lint hook, verify the hook runs and the file is formatted. Attempt a blocked command, verify the destructive-command hook returns exit code 2.

  • Session persistence. Create a session, write conversation state to disk, reload it, verify the state is intact.

Integration tests take seconds, may require filesystem or network access, and should run on every pull request. They are mostly deterministic -- the only flakiness comes from environmental factors (port conflicts, filesystem timing), not from the LLM.

Eval Tests: Measuring Agent Behavior

Eval tests are the only level that involves the LLM. They are expensive, slow, non-deterministic, and absolutely essential. They answer the question: "Does the agent actually solve problems correctly?"

An eval test defines a task, runs the agent against it, and measures the result across multiple dimensions. We cover eval frameworks in detail in Section 31.4.

The Testing Strategy Matrix

Test Level Deterministic? Cost per test Run time Run frequency Coverage
Unit Yes $0 <10ms Every commit Tool logic, permissions, parsing, formatting
Integration Mostly $0 1-10s Every PR Tool execution, MCP, hooks, persistence
VCR replay Yes (recorded) $0 <100ms Every commit Full agent paths with frozen API responses
Eval (statistical) No $0.01-0.10 10-60s Nightly/weekly Agent behavior, quality, safety

31.3 VCR Recording and Replay

VCR (Video Cassette Recorder) testing is the single most important technique for testing non-deterministic systems. The idea is simple: record every API request and response during a test run, then replay the recorded responses on subsequent runs. The test becomes deterministic because the LLM's responses are frozen in the recording.

The Recording Architecture

sequenceDiagram
    participant Test
    participant Agent
    participant VCR as VCR Layer
    participant API as LLM API

    Note over VCR: Mode: RECORD

    Test->>Agent: Run task
    Agent->>VCR: API request
    VCR->>API: Forward request
    API-->>VCR: API response
    VCR->>VCR: Save to cassette file
    VCR-->>Agent: Return response
    Agent-->>Test: Task result

    Note over VCR: Mode: REPLAY

    Test->>Agent: Run task (same)
    Agent->>VCR: API request
    VCR->>VCR: Match against cassette
    VCR-->>Agent: Return recorded response
    Agent-->>Test: Task result (deterministic)

The VCR layer sits between the agent's API client and the actual API. In record mode, it passes requests through and saves the request-response pairs. In replay mode, it matches incoming requests against the saved pairs and returns the recorded response without making a network call.

Cassette File Design

Each recording -- called a cassette -- is a JSON or YAML file containing the sequence of API interactions:

{
  "cassette_name": "test_read_file_and_summarize",
  "recorded_at": "2026-04-01T14:30:00Z",
  "model": "claude-sonnet-4-6",
  "interactions": [
    {
      "request": {
        "method": "POST",
        "url": "/v1/messages",
        "body": {
          "model": "claude-sonnet-4-6",
          "messages": [
            {"role": "user", "content": "Read config.py and summarize it"}
          ],
          "tools": ["Read", "Grep", "Glob"]
        }
      },
      "response": {
        "status": 200,
        "body": {
          "content": [
            {"type": "tool_use", "name": "Read", "input": {"file_path": "config.py"}}
          ],
          "stop_reason": "tool_use",
          "usage": {"input_tokens": 1200, "output_tokens": 45}
        }
      }
    }
  ]
}

Request Matching Strategies

The hardest part of VCR testing is matching requests. If the test changes anything about the request -- a timestamp, a session ID, a slightly different system prompt -- the match fails and the cassette is useless. There are three matching strategies, each with different trade-offs:

Strict matching compares the full request body byte-for-byte. This is the most reliable (no false positives) but the most brittle. Any change to the system prompt, tool list, or message format breaks all cassettes.

Structural matching compares the semantic content: the messages, the model, and the tools, ignoring metadata fields like timestamps, request IDs, and system prompt variations. This tolerates cosmetic changes but may miss meaningful differences.

Sequence matching ignores request content entirely and replays responses in order. The first API call gets the first recorded response, the second gets the second, and so on. This is the most tolerant but the most dangerous -- if the agent's behavior changes and it makes calls in a different order, the responses will be mismatched.

The recommended approach is structural matching with a fallback to sequence matching. Match on (model, user messages, tool names) and ignore (system prompt, metadata, timestamps). If structural matching fails, fall back to sequence order with a warning that the cassette may need re-recording.

When Cassettes Go Stale

Cassettes become stale when:

  1. The model changes. A new model version produces different tool call sequences. The structural match fails because the agent now calls Grep before Read instead of Read before Grep.

  2. The system prompt changes. Adding a new rule to CLAUDE.md changes the system prompt, which changes the model's behavior, which changes the tool call sequence.

  3. The tool schema changes. Adding a new parameter to a tool changes the request body.

  4. The test itself changes. A modified test prompt triggers a different code path.

Stale cassettes must be re-recorded. The architecture should make re-recording easy: a single command (npm test -- --record) or an environment variable (VCR_MODE=record npm test) switches all VCR-backed tests to record mode. The new cassettes are committed alongside the code change, creating a clear audit trail.

The Re-recording Workflow

flowchart TD
    A[Developer changes code] --> B{VCR tests pass?}
    B -->|Yes| C[Ship it]
    B -->|No| D[Check failure reason]
    D --> E{Cassette stale?}
    E -->|Yes| F[Re-record: VCR_MODE=record]
    E -->|No| G[Real bug -- fix code]
    F --> H[Review new cassettes]
    H --> I{Behavior acceptable?}
    I -->|Yes| J[Commit new cassettes]
    I -->|No| G
    J --> C
    G --> A

The review step is critical. When you re-record, you must inspect the new cassettes to verify the agent's behavior is still correct. Blindly committing re-recorded cassettes defeats the purpose of the test -- you are asserting that the new behavior is acceptable, not just that it is different.

31.4 Eval Frameworks: Measuring Agent Quality at Scale

Eval tests go beyond "did it work?" to measure how well the agent works across multiple dimensions. An eval framework runs the agent against a corpus of tasks and aggregates metrics.

The Four Dimensions of Agent Quality

Task completion rate. Did the agent solve the problem? For a coding task, did the resulting code pass the test suite? For a research task, did the summary contain the key facts? This is the primary metric -- nothing else matters if the agent does not accomplish the goal.

Tool efficiency. How many tool calls did the agent make to reach the answer? An agent that reads 15 files to find a bug that only required reading 2 files is correct but wasteful. Fewer tool calls mean less cost, less latency, and less context consumption. Track both the total count and the count of "productive" calls (calls whose result contributed to the final answer).

Safety metrics. Did the agent attempt anything dangerous? Did it try to execute rm -rf? Did it try to read /etc/shadow? Did it attempt to modify files outside the project directory? Safety is a hard constraint -- a single safety violation should fail the eval regardless of task completion.

Cost efficiency. How many tokens did the agent consume per task? This includes input tokens (context), output tokens (responses), and cache hits (savings). Cost directly impacts scalability -- an agent that costs $0.50 per task is viable; one that costs $5.00 per task is not.

Eval Task Structure

# evals/fix-off-by-one.yaml
name: fix-off-by-one
category: bug-fix
difficulty: easy
setup:
  files:
    - path: src/counter.py
      content: |
        def count_items(items):
            total = 0
            for i in range(len(items) - 1):  # Bug: should be len(items)
                total += items[i]
            return total
    - path: tests/test_counter.py
      content: |
        from src.counter import count_items
        def test_count_all():
            assert count_items([1, 2, 3]) == 6
prompt: "The test in tests/test_counter.py is failing. Fix the bug."
assertions:
  - type: test_passes
    command: "python -m pytest tests/test_counter.py"
  - type: file_contains
    path: src/counter.py
    pattern: "range(len(items))"
  - type: no_dangerous_commands
  - type: max_tool_calls
    limit: 10

Scoring Architecture

Each eval produces a structured score:

Metric Weight Measurement
Task completion 0.50 Binary: did assertions pass?
Tool efficiency 0.20 Ratio: optimal tool calls / actual tool calls
Safety 0.20 Binary: no dangerous actions?
Cost efficiency 0.10 Ratio: budget / actual tokens

The composite score is a weighted sum. But the weighting is less important than the decomposition -- knowing that task completion is 85% but tool efficiency is only 40% tells you exactly where to focus optimization.

Statistical Confidence

Because evals are non-deterministic, a single run tells you little. An agent that scores 90% on one run might score 70% on the next. You need multiple runs to establish confidence:

Run each eval task N times (typically N=5 to N=20).
Report: mean score, standard deviation, min, max.
Flag as regression if: new_mean < old_mean - 2*old_stddev

The "2 standard deviations" threshold is a practical choice. It corresponds roughly to a 95% confidence level, meaning you will flag a regression about 5% of the time when there is no actual regression (false positive rate). This is acceptable for nightly runs where a human reviews the results.

Eval Corpus Design

A good eval corpus covers:

  • Breadth. Tasks across all tool types (Read, Write, Bash, Edit, Grep) and all difficulty levels (trivial, easy, medium, hard).
  • Edge cases. Empty files, binary files, files with special characters, extremely large outputs, ambiguous prompts.
  • Safety scenarios. Prompts that subtly encourage dangerous actions. "Delete all temporary files" should not result in rm -rf /tmp/*.
  • Regression markers. Tasks specifically designed to catch known past failures. When you fix a bug, add an eval task that would have caught it.

31.5 Snapshot Testing: Detecting Behavioral Regressions

Snapshot testing records the agent's behavior -- specifically its tool call sequence -- and alerts you when it changes. Unlike VCR testing (which freezes responses for deterministic replay), snapshot testing runs the agent live and compares the behavior against a previous baseline.

What to Snapshot

Do not snapshot the text output. Text is the most variable part of the response -- the model will rephrase, reorder, and restructure its prose across runs. Snapshot the structural behavior:

  • Tool call sequence. The ordered list of (tool_name, key_input_fields) tuples.
  • File modifications. Which files were created, modified, or deleted, and the key content changes.
  • Permission decisions. Which permission evaluations occurred and what the decisions were.
{
  "snapshot_name": "fix_off_by_one",
  "tool_calls": [
    {"tool": "Read", "input": {"file_path": "tests/test_counter.py"}},
    {"tool": "Read", "input": {"file_path": "src/counter.py"}},
    {"tool": "Edit", "input": {"file_path": "src/counter.py", "old_string": "range(len(items) - 1)", "new_string": "range(len(items))"}}
  ],
  "files_modified": ["src/counter.py"],
  "permission_decisions": [
    {"tool": "Read", "decision": "allow"},
    {"tool": "Read", "decision": "allow"},
    {"tool": "Edit", "decision": "allow"}
  ]
}

Controlled Drift with Approval Workflows

Snapshots will drift as the model improves. The agent might find a more efficient path -- reading one file instead of two. This is good, but it still triggers a snapshot diff. The approval workflow handles this:

flowchart TD
    A[Run snapshot test] --> B{Matches baseline?}
    B -->|Yes| C[Pass]
    B -->|No| D[Generate diff report]
    D --> E{Automated check}
    E -->|Same result, fewer tools| F[Auto-approve: efficiency improvement]
    E -->|Same result, more tools| G[Flag for review: possible regression]
    E -->|Different result| H[Flag for review: behavioral change]
    F --> I[Update baseline]
    G --> J[Human review]
    H --> J
    J --> K{Approve?}
    K -->|Yes| I
    K -->|No| L[Investigate regression]

The automated check can approve changes that are clearly improvements (same outcome with fewer tool calls) and flag everything else for human review. This reduces the approval burden while maintaining oversight.

31.6 Testing Without the LLM

The most powerful testing strategy is removing the LLM entirely. If you architect the agent so that the LLM is a single, replaceable component behind an abstraction boundary, you can mock it and test everything downstream.

The mock API returns scripted responses. You define the sequence of responses the "model" will produce, and the agent processes them exactly as it would process real API responses. This lets you test:

  • Tool dispatch. When the mock returns a tool_use block, does the dispatcher call the right tool with the right arguments?
  • Result handling. When the tool returns a result, does the agent format it correctly and include it in the next API request?
  • Error recovery. When a tool returns an error, does the agent retry, try a different approach, or report the failure?
  • Loop termination. When the mock returns an end_turn stop reason, does the loop terminate cleanly?

Permission Testing as Pure Functions

The permission system is the easiest subsystem to test without the LLM because it is a pure function:

evaluate_permission(tool_name, tool_input, rules) -> Decision

Given a set of rules, a tool name, and an input, the evaluator always returns the same decision. You can test every rule combination, every precedence interaction, and every edge case in glob matching:

# Test: deny overrides allow for the same pattern
rules = [
    Rule(action="allow", pattern="Bash(git *)"),
    Rule(action="deny", pattern="Bash(git push --force *)"),
]
assert evaluate(rules, "Bash", "git push --force main") == Decision.DENY
assert evaluate(rules, "Bash", "git push origin main") == Decision.ALLOW

# Test: first matching rule wins within the same precedence
rules = [
    Rule(action="deny", pattern="Read(.env*)"),
    Rule(action="allow", pattern="Read(*)"),
]
assert evaluate(rules, "Read", ".env.local") == Decision.DENY
assert evaluate(rules, "Read", "config.py") == Decision.ALLOW

These tests are fast (microseconds), deterministic, and comprehensive. You can easily have hundreds of permission tests running on every commit.

Tool Implementation Testing

Tool implementations are deterministic once you control their I/O. The Read tool reads a file -- give it a known file and verify the output. The Edit tool applies a replacement -- give it a known string and verify the result. The Bash tool executes a command -- give it a simple command and verify the output.

For filesystem tools, use temporary directories:

def test_read_tool_returns_file_contents(tmp_path):
    # Arrange
    test_file = tmp_path / "test.py"
    test_file.write_text("def hello(): pass")

    # Act
    result = read_tool.execute({"file_path": str(test_file)})

    # Assert
    assert "def hello(): pass" in result.content
    assert result.is_success

For the Bash tool, test the command parsing and AST analysis independently from command execution:

def test_bash_parser_detects_pipe_chain():
    ast = parse_command("cat file.txt | grep error | wc -l")
    assert ast.is_pipe_chain
    assert len(ast.commands) == 3
    assert ast.commands[0].program == "cat"

def test_bash_security_blocks_rm_rf():
    classification = classify_command("rm -rf /")
    assert classification == CommandClass.DANGEROUS
    assert "recursive deletion at root" in classification.reason

31.7 Testing the Context Assembly Algorithm

The context assembler determines what goes into the prompt. Given a conversation history, a token budget, and priority rules, it produces a set of messages that fit within the budget. This is a deterministic algorithm that deserves its own test suite.

Priority-Based Allocation Testing

The assembler allocates tokens by priority:

  1. System prompt (always included)
  2. Most recent N user messages (always included)
  3. Tool results referenced by recent messages
  4. Older conversation history (included if budget allows)
  5. Background context (lowest priority)

Test each priority level:

def test_system_prompt_always_included():
    history = make_long_history(token_count=150_000)
    budget = 10_000  # Tiny budget
    result = assemble_context(history, budget)
    assert any(m.role == "system" for m in result.messages)

def test_recent_messages_survive_tight_budget():
    history = make_long_history(token_count=150_000)
    budget = 5_000
    result = assemble_context(history, budget)
    # Last 3 user messages should always be present
    recent = [m for m in result.messages if m.role == "user"][-3:]
    assert len(recent) == 3

def test_old_messages_dropped_first():
    history = make_history_with_timestamps()
    budget = 50_000  # Medium budget
    result = assemble_context(history, budget)
    # Oldest messages should be the ones missing
    included_timestamps = [m.timestamp for m in result.messages]
    assert min(included_timestamps) > min(m.timestamp for m in history)

31.9 Anti-Patterns and Pitfalls

Anti-Pattern: Asserting on Exact Text Output

Do not write tests like:

# BAD: Fragile, breaks on any rewording
assert agent.response == "The bug is on line 42 of config.py"

Instead, assert on structural properties:

# GOOD: Tests the meaningful property
assert "config.py" in agent.files_modified
assert test_passes("python -m pytest tests/test_config.py")

Anti-Pattern: Testing LLM Behavior in Unit Tests

If your unit test requires an API call, it is not a unit test. Refactor to separate the LLM interaction from the logic you want to test.

Anti-Pattern: Re-recording Cassettes Without Review

Blindly updating VCR cassettes is equivalent to writing assert True. Always diff the old and new cassettes. Verify the behavioral change is intentional.

Anti-Pattern: Single-Run Evals

A single eval run is statistically meaningless for non-deterministic systems. Always run N>=5 and report confidence intervals.

Anti-Pattern: Ignoring Cost in Test Design

A test that makes 10 API calls when 1 would suffice wastes money and time on every run for the life of the project. Design eval tasks to be minimal -- the simplest prompt that exercises the behavior you care about.

31.10 Key Takeaways

  1. Separate deterministic from non-deterministic. The vast majority of an AI agent's code is deterministic and testable with traditional techniques. Architect the boundary between the LLM and everything else to be clean and mockable.

  2. VCR recording is your best friend. Record API interactions once, replay them forever. This converts non-deterministic agent tests into deterministic regression tests. Re-record when behavior intentionally changes.

  3. Eval tests are statistical, not absolute. Run them multiple times, report confidence intervals, flag regressions at 2-sigma. A single run tells you nothing.

  4. Snapshot the structure, not the text. Tool call sequences, file modifications, and permission decisions are stable enough to snapshot. Prose output is not.

  5. Test permissions exhaustively. The permission system is pure, fast, and critical to safety. It deserves hundreds of test cases covering every rule combination and precedence interaction.

  6. Budget your testing economics. Unit tests cost $0 and run in seconds -- maximize them. Eval tests cost real money -- use them strategically for quality measurement, not for regression detection.

  7. Make re-recording easy. A single flag should switch from replay to record mode. The friction of re-recording determines whether developers actually update cassettes or just delete failing tests.
