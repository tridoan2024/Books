Chapter 7: The Core Agent Loop

In Chapters 4-6, we examined bootstrap, configuration, and session lifecycle — everything that happens before the agent starts thinking. Now we reach the architectural heart of any AI CLI agent: the loop that turns a language model into an agent.

This chapter is about one pattern: prompt-think-act-observe. Every AI agent ever built implements some variant of this cycle. The difference between a toy demo and a production system lies in how you handle the edges: when does the loop stop? What happens when it fails? How do you prevent it from running forever? How does the model know it is making progress?

We will design a production agent loop from first principles, examining the architectural decisions that separate a chatbot from an agent. By the end of this chapter, you will have a complete mental model of the agent loop — its invariants, its exit conditions, its error recovery paths, and the data flow that connects each iteration to the next.

The Fundamental Pattern: Prompt-Think-Act-Observe

Every AI agent follows the same cycle:

graph TD
    A[User Prompt] --> B[Think: Call the Model]
    B --> C{Tool Use?}
    C -->|Yes| D[Act: Execute Tools]
    D --> E[Observe: Collect Results]
    E --> B
    C -->|No| F[Respond to User]
    F --> G[Wait for Next Prompt]
    G --> A

This looks simple. A chatbot also calls a model and returns a response. The difference is the inner loop — the path from "Think" through "Act" and "Observe" back to "Think." A chatbot has no inner loop. It calls the model once per user message and returns. An agent calls the model, sees that the model wants to use a tool, executes the tool, feeds the result back, and lets the model decide what to do next. This inner loop may run once or fifty times before the model decides it has finished.

The inner loop is what makes an agent an agent. It is also what makes agents dangerous, expensive, and difficult to debug. Every iteration costs tokens. Every tool execution has side effects. Every continuation decision is a bet that the model will converge rather than spiral.

Why Not Just a Chatbot?

A chatbot's architecture is a single function call:

response = call_model(system_prompt + conversation_history + user_message)
return response

This works when the model's output is the final answer. But the moment you need the model to interact with the environment — read a file, search the web, execute a command, edit code — the single-call architecture breaks down. The model needs to see the result of its action before deciding what to do next.

Consider a user asking: "Find all Python files with SQL injection vulnerabilities and fix them." The model cannot do this in one shot. It needs to:

  1. Search for Python files (tool call)
  2. Read each file (tool calls)
  3. Analyze for SQL injection patterns (reasoning)
  4. Edit the vulnerable files (tool calls)
  5. Verify the fixes (tool calls)

Each step depends on the output of the previous step. The model cannot know which files to read until it has searched. It cannot know what to fix until it has read. The agent loop is the mechanism that lets the model chain these dependent steps together.

The Chatbot-to-Agent Spectrum

Not all loops are equal. Systems exist on a spectrum from pure chatbot to fully autonomous agent:

System Type Inner Loop? Tool Use? Convergence? Example
Chatbot No No N/A ChatGPT (basic)
Tool-augmented chatbot Single pass Yes, one round N/A ChatGPT with plugins (1 tool call)
Simple agent Yes, bounded Yes, multi-round Turn limit Basic ReAct loop
Production agent Yes, managed Yes, concurrent Multi-signal Claude Code, Cursor

The jump from "tool-augmented chatbot" to "simple agent" is the introduction of the inner loop. The jump from "simple agent" to "production agent" is the introduction of convergence detection, error recovery, token budget management, and all the other machinery we will design in this chapter.

Designing the Loop: An Async Generator

The first architectural decision: what is the loop's interface?

Why Not a Simple While Loop?

The naive implementation looks like this:

async def agent_loop(messages: list[Message]) -> list[Message]:
    while True:
        response = await call_model(messages)
        messages.append(response)

        tool_calls = extract_tool_use(response)
        if not tool_calls:
            return messages

        results = await execute_tools(tool_calls)
        messages.extend(results)

This has three problems that matter at production scale:

No streaming. The consumer waits for the entire model response before seeing anything. In a CLI where responses can be thousands of tokens, the user stares at a blank screen for 10-30 seconds.

No backpressure. The loop runs as fast as the model generates. If the UI renderer is slow — rendering markdown, executing syntax highlighting, writing to disk — messages pile up in memory.

No exit reason communication. The function returns messages, but the caller cannot distinguish "completed normally" from "hit a token limit" from "user aborted." All exit paths collapse into the same return type.

The Pull-Based Stream Solution

The architectural solution is to make the agent loop a pull-based stream — an async generator that yields messages one at a time, driven by the consumer's pace.

sequenceDiagram
    participant Consumer as UI / SDK Consumer
    participant Loop as Agent Loop (Generator)
    participant Model as LLM API
    participant Tools as Tool Executor

    Consumer->>Loop: next()
    Loop->>Model: stream request
    Model-->>Loop: token chunk
    Loop-->>Consumer: yield StreamEvent
    Consumer->>Loop: next()
    Model-->>Loop: tool_use block
    Loop->>Tools: execute tool
    Tools-->>Loop: result
    Loop-->>Consumer: yield ToolResult
    Consumer->>Loop: next()
    Loop->>Model: stream request (with tool result)
    Model-->>Loop: final text
    Loop-->>Consumer: yield AssistantMessage
    Loop-->>Consumer: return Terminal(completed)

Three things to notice about this design:

First, the consumer drives the pace. Each next() call pulls one message through the pipeline. If the UI renderer is slow, the generator naturally pauses. Backpressure is free — no explicit flow control needed.

Second, the yield channel carries messages (what happened) and the return channel carries the terminal reason (why it stopped). These are separate channels with separate types. The consumer processes messages as they arrive and only checks the terminal reason when the generator is done.

Third, the generator can yield different message types: stream events (partial tokens), assistant messages (complete responses), tool results, and status updates. The consumer pattern-matches on the message type and routes each to the appropriate handler.

Why Async Generators Over Alternatives

Alternative Problem
Callbacks No return channel for exit reasons. Cleanup requires manual tracking. Callback hell for multi-step flows.
EventEmitter No backpressure. Emitter fires regardless of consumer readiness. Memory grows unbounded during slow rendering.
Observable (RxJS) Heavy dependency. Adds 50KB+ for sugar over generators. Operator composition is overkill for a single iteration pattern.
Channel (Go-style) Not native to most runtimes. Requires a CSP library. Adds conceptual overhead.

The async generator gets backpressure, composable cleanup via .return() and .throw(), and a separate return channel for exit reasons — all from the language runtime, zero dependencies.

Loop State: Immutable Config vs. Mutable State

The second architectural decision: how do you track state across iterations?

The Separation Principle

Every agent loop has two categories of data:

  1. Configuration — what was true when the loop started. The system prompt, the tool definitions, the model to use, the maximum turn count. This never changes within a single agent invocation.

  2. Iteration state — what changes on every loop cycle. The conversation messages, the turn counter, the recovery attempt count, whether compaction has been tried.

Mixing these in a single object creates two problems:

  • Debugging difficulty. When something goes wrong on iteration 47, you need to compare current state against the original request. If both live in the same object, you must reconstruct the original from the mutated version.

  • Refactoring resistance. If you later want to extract the loop body into a pure function — (state, event, config) -> state — mixed state and config blocks this extraction.

The pattern: destructure config once at entry, never reassign it. Create a separate state type that is replaced (not mutated) on every iteration.

┌─────────────────────────────┐
│       QueryConfig           │
│  (immutable, snapshotted    │
│   at loop entry)            │
│                             │
│  - system prompt            │
│  - tool definitions         │
│  - model name               │
│  - feature flags            │
│  - max turns                │
└─────────────────────────────┘

┌─────────────────────────────┐
│       LoopState             │
│  (replaced every iteration) │
│                             │
│  - messages[]               │
│  - turn count               │
│  - recovery counters        │
│  - compaction tracking      │
│  - transition reason        │
└─────────────────────────────┘

Replace, Don't Mutate

A critical sub-pattern: on every continuation, build a new state object rather than mutating the existing one.

# BAD: mutation hides which fields changed
state.messages.extend(tool_results)
state.turn_count += 1
state.recovery_count = 0  # Did we mean to reset this? Hard to tell.

# GOOD: replacement declares the complete next state
state = LoopState(
    messages=[*state.messages, *assistant_msgs, *tool_results],
    turn_count=state.turn_count + 1,
    recovery_count=0,  # Explicit: recovery resets on successful tool turn
    compaction_attempted=False,  # Explicit: new turn, new chance
    transition=Transition(reason="next_turn"),
)

When you replace the entire state object, every continuation site declares the complete next state. You can read any transition independently without tracing what other code paths might have mutated before it. The transition field records why this iteration was started — invaluable for debugging and testing.

Snapshot Feature Flags at Entry

Feature flags deserve special attention. In a production system, feature flags can change at any time — a remote flag server pushes an update, and suddenly a feature is enabled or disabled.

If the agent loop reads flags on every iteration, behavior can change mid-query. Iteration 1 might use streaming tool execution because the flag is on; iteration 5 might not because the flag was turned off between iterations. This creates inconsistencies that are nearly impossible to reproduce or debug.

The solution: snapshot all relevant feature flags into the config object at loop entry. The loop uses the snapshot for its entire lifetime. Even if the flag server pushes an update mid-query, the current loop runs consistently.

This pattern applies to any external state that could change asynchronously: feature flags, configuration files, environment variables, API capabilities. Snapshot at entry, use the snapshot throughout.

The Five-Phase Iteration

Each pass through the loop follows five phases. Understanding this structure is essential to reasoning about the loop's behavior.

flowchart TD
    START([Iteration Start]) --> P1[Phase 1: Context Preparation]
    P1 --> P2[Phase 2: Model Call]
    P2 --> P3{Phase 3: Post-Response Decision}
    P3 -->|No tools, no errors| DONE([Return Terminal])
    P3 -->|Recoverable error| P1
    P3 -->|Tool use detected| P4[Phase 4: Tool Execution]
    P4 --> P5{Phase 5: Continue Decision}
    P5 -->|Max turns reached| DONE
    P5 -->|User aborted| DONE
    P5 -->|Hook blocked| DONE
    P5 -->|Continue| START

Phase 1: Context Preparation

Before calling the model, the loop must ensure the message context fits within the model's context window. This is a chain of increasingly aggressive compression strategies, cheapest first:

1. Tool result budget enforcement → Truncate oversized individual tool results
2. History snipping            → Remove oldest messages by count
3. Microcompact                → Replace old tool content with markers
4. Context collapse            → Summarize old conversation segments
5. Auto-compact                → Full LLM-based summarization
6. Token warning check         → Abort if still over limit

The ordering is deliberate. Each strategy is cheaper and faster than the next. The pipeline only advances when the previous tier cannot reduce context enough. The system never sends a prompt that exceeds the model's context window — if all compression strategies fail and the context still exceeds the limit, the loop exits with a prompt_too_long terminal reason rather than wasting an API call that will definitely fail.

Chapter 9 covers context management in depth. For the agent loop's purposes, what matters is that Phase 1 is a precondition enforcer: after it runs, the context is guaranteed to fit.

Phase 2: Model Call (Streaming)

The core of Phase 2 is a streaming iteration over the model's response. Four things happen simultaneously during the stream:

Yield messages to the consumer. Each token chunk, each content block, each tool use detection streams to the UI for real-time rendering.

Collect the full response. The complete assistant messages accumulate for use in Phases 3-5.

Detect tool use blocks. Tool calls are detected during streaming, not after. This enables pipelining.

Feed the streaming tool executor. This is the key performance optimization. While the model generates content block N+1, the tool from content block N is already executing. For a response that invokes three tools, this can cut total latency by 60-70% compared to sequential execution:

gantt
    title Sequential vs Pipelined Tool Execution
    dateFormat X
    axisFormat %s

    section Sequential
    Model generates response    :s1, 0, 4
    Execute Tool 1              :s2, after s1, 2
    Execute Tool 2              :s3, after s2, 2
    Execute Tool 3              :s4, after s3, 2

    section Pipelined
    Model generates response    :p1, 0, 4
    Execute Tool 1              :p2, 1, 2
    Execute Tool 2              :p3, 2, 2
    Execute Tool 3              :p4, 3, 2

The sequential approach takes 10 time units. The pipelined approach takes 5. The savings grow with the number of tools in a single response.

Not all tools can pipeline safely. Read-only tools (file reads, searches, web fetches) are concurrency-safe — they can execute in parallel. Mutation tools (bash commands, file edits, file writes) are not — they may have implicit dependency chains. The executor classifies each tool and only pipelines concurrency-safe tools.

Phase 3: Post-Response Decision

After the model's response completes, the loop must decide what to do next. This is where most of the complexity lives, because multiple recovery and continuation paths can trigger:

flowchart TD
    STREAM_DONE([Model Response Complete]) --> A{Tool use in response?}
    A -->|Yes| TOOLS[Go to Phase 4: Tool Execution]
    A -->|No| B{Prompt too long error?}
    B -->|Yes| C{Already tried reactive compact?}
    C -->|No| D[Compact and retry]
    C -->|Yes| E([Exit: prompt_too_long])
    B -->|No| F{Output token limit hit?}
    F -->|Yes| G{First time hitting limit?}
    G -->|Yes| H[Escalate token limit and retry]
    G -->|No| I{Recovery attempts < 3?}
    I -->|Yes| J[Inject resume message and continue]
    I -->|No| K[Surface truncation error]
    F -->|No| L{Stop hooks pass?}
    L -->|Blocked| M[Inject hook errors and continue]
    L -->|Prevented| N([Exit: stop_hook_prevented])
    L -->|Pass| O{Token budget remaining?}
    O -->|Yes, not diminishing| P[Inject nudge and continue]
    O -->|No or diminishing| Q([Exit: completed])

    D --> RETRY([Retry from Phase 1])
    H --> RETRY
    J --> RETRY
    M --> RETRY

This decision tree is the most architecturally significant diagram in the agent loop. Each branch represents a distinct recovery or continuation path, and each path has its own state management requirements.

Phase 4: Tool Execution

If tool use was detected during streaming (Phase 2), the loop now collects all tool results. Two paths exist:

  • Streaming execution enabled: The streaming tool executor already started tools during Phase 2. Now it drains any remaining results from tools still in progress.
  • Sequential fallback: Tools start and complete one at a time. Simpler, slower, but useful as a fallback when the streaming executor is disabled via feature flag.

Tool results become user messages in the conversation — this is the API's protocol for feeding tool output back to the model. The model sees its own tool calls and their results, giving it the information it needs to decide what to do next.

Phase 5: Continue Decision

After tools execute, the loop must decide whether to continue. Three immediate exit conditions:

  1. Max turns reached. A configurable limit (typically 200 for interactive sessions, lower for subagents) prevents infinite loops.
  2. User aborted. Ctrl+C or an abort signal was received during tool execution.
  3. Hook blocked. A post-tool-execution hook returned a blocking error.

If none of these trigger, the loop builds the next state and continues from Phase 1. The state construction is the feedback mechanism: messages = [...previous, ...assistant_response, ...tool_results]. The model's response and the tool results become part of the conversation history for the next iteration.

Convergence Detection: The 10 Exit Reasons

The agent loop must know when to stop. This is harder than it sounds. The model does not explicitly say "I am done." Instead, the loop infers completion from multiple signals.

A production agent loop has at least 10 distinct exit reasons:

Exit Reason Trigger User Experience
completed Model finished naturally (no tool calls, no errors) Normal response displayed
prompt_too_long Context exceeded limits, all recovery failed Error message, suggest /clear
blocking_limit Approaching context ceiling, cannot proceed Warning, suggest /compact
image_error Unrecoverable image processing failure Error message
model_error API error after all retries exhausted Error with retry suggestion
aborted_streaming User cancelled during model output Partial response shown
aborted_tools User cancelled during tool execution Partial results shown
stop_hook_prevented Post-turn hook blocked continuation Hook's error message shown
hook_stopped Hook explicitly terminated the session Hook's message shown
max_turns Turn limit reached Warning with turn count

Why Discriminated Unions, Not Exceptions

Each exit reason should be a variant of a discriminated union (tagged enum), not an exception:

type Terminal =
  | { reason: 'completed' }
  | { reason: 'prompt_too_long' }
  | { reason: 'max_turns'; turnCount: number }
  | { reason: 'model_error'; error: unknown }
  | { reason: 'aborted_streaming' }
  // ... 5 more

Three benefits over exceptions:

  1. Exhaustiveness checking. The compiler ensures every exit reason is handled. Add a new reason and every switch statement that does not handle it produces a type error.

  2. Testing precision. Tests assert on terminal.reason === 'max_turns' rather than catching exceptions and parsing error messages.

  3. No stack unwinding. Exceptions unwind the call stack, destroying local state. A terminal return preserves the generator's cleanup path — command lifecycle notifications, metric recording, and transcript persistence all run normally.

The Distinction: Stop vs. Error

Not every exit is an error. completed, max_turns, and stop_hook_prevented are normal terminations — the loop did its job and stopped for a well-defined reason. model_error and prompt_too_long are failures — something went wrong and recovery was not possible.

The UI treatment differs: normal terminations are silent or informational, while failures show error messages with recovery suggestions. Keeping these in the same union type with different variants — rather than separate success/failure return types — simplifies the consumer's control flow. One switch handles all cases.

The 7 Continuation Reasons

Equally important to knowing when to stop is knowing why to continue. The loop continues for seven distinct reasons, each with its own state management:

Continuation Reason Trigger State Impact
next_turn Normal tool-to-model cycle Recovery counters reset to zero
collapse_drain_retry Context collapse freed space, retry Preserves collapse state
reactive_compact_retry Compacted after prompt-too-long Sets compaction_attempted = true
max_output_tokens_escalate 8K limit hit, retry at 64K Sets override, does NOT increment recovery count
max_output_tokens_recovery 64K limit hit, resume message injected Increments recovery count (1..3)
stop_hook_blocking Hook injected error messages Preserves compaction guards
token_budget_continuation Budget remaining, nudge injected Increments continuation count

Why Track Continuation Reasons?

Recording the continuation reason on the state serves three purposes:

1. Prevents state interference. Each recovery path has specific fields it must preserve and specific fields it must reset. The next_turn path resets all recovery counters — because tools executed successfully, there is nothing to recover from. The stop_hook_blocking path preserves the compaction guard — because a previous compaction attempt may have failed, and resetting the guard would create an infinite loop.

2. Enables debugging. When a session enters an unexpected loop (compacting on every turn, or retrying indefinitely), the continuation reason trace shows exactly which paths triggered and in what order.

3. Supports testing. Tests can assert state.transition.reason === 'max_output_tokens_escalate' without inspecting the actual messages or counting API calls.

The Interaction Trap

The most dangerous aspect of continuation reasons is their interaction. Consider this scenario:

  1. Model response triggers a stop hook with blocking errors.
  2. Stop hook injects error messages. Loop continues with stop_hook_blocking.
  3. The new messages push context past the compaction threshold.
  4. Compaction fires but fails (context is too large even for summarization).
  5. The compaction failure flag is set.
  6. The model responds to the hook errors, triggering the stop hook again.
  7. Stop hook injects more errors. Loop continues with stop_hook_blocking.
  8. If the compaction flag was reset at step 7, compaction would fire again at step 3, fail again, and the loop would repeat forever.

The fix: when continuing due to stop_hook_blocking, preserve the compaction failure flag. Do not reset it. This prevents the death spiral.

This kind of interaction between recovery paths is the primary source of infinite loop bugs in agent systems. Every new continuation reason must be analyzed against every existing one for potential cycles. The transition reason field makes this analysis tractable — you can trace the exact path through the state machine.

Error Recovery Within the Loop

Production agent loops encounter three categories of errors, each requiring different recovery strategies:

Category 1: Recoverable API Errors

The most common recoverable error is output token limit exhaustion — the model's response was cut off because it exceeded the configured maximum. The recovery strategy is a three-phase escalation:

Phase 1: Silent escalation. The default output limit is intentionally low (e.g., 8K tokens) to optimize GPU slot reservations. When the model hits this limit, the loop silently retries with a higher limit (e.g., 64K). No user-visible message. No partial output shown. The user never knows it happened.

Phase 2: Multi-turn recovery. If the model hits even the escalated limit, inject a recovery message: "Resume directly where you left off. No apology, no recap. Break remaining work into smaller pieces." This instruction prevents the model from wasting tokens on meta-commentary about being cut off. Up to 3 recovery attempts are allowed.

Phase 3: Surface the error. If all recovery attempts fail, show the user the truncated response and explain what happened.

The key architectural insight: withhold recoverable errors from the output stream. If the loop yields an error message to the consumer during streaming, the consumer might disconnect (an SDK client terminates on errors). When the loop subsequently recovers, nobody is listening. The solution is to detect potentially recoverable errors during streaming, suppress them, attempt recovery, and only surface them if recovery fails.

Category 2: Context Overflow

When the model returns a prompt-too-long error, the conversation has exceeded the context window. The recovery path:

  1. Parse the error to extract the exact token overshoot.
  2. Compact the conversation (remove oldest messages, summarize).
  3. Retry the request with the compacted context.

This is a last-resort compaction — it fires only after the pre-request compaction pipeline (Phase 1) has already tried and failed. The retry is allowed once per query. If compaction fails or the compacted context still exceeds the limit, the loop exits with prompt_too_long.

Category 3: Transient Failures

Network timeouts, rate limits (429), server overload (529), and stale connections. These are handled by the retry engine (covered in Chapter 10's API client design), not by the agent loop directly. The loop sees either a successful response or a final error after retries are exhausted.

The separation matters: the retry engine handles transient failures at the HTTP level. The agent loop handles semantic failures at the conversation level. Mixing these creates confusion about which layer is responsible for recovery.

The Error Withholding Pattern

Error withholding deserves its own discussion because it is counterintuitive. Most systems surface errors immediately. The agent loop does the opposite for recoverable errors:

During Streaming:
┌─────────────────────────────────────────┐
│ Error detected                          │
│   ├── Is it recoverable?                │
│   │   ├── Yes: withhold from consumer   │
│   │   │       (but save for recovery)   │
│   │   └── No: yield to consumer         │
│   └── Continue streaming                │
└─────────────────────────────────────────┘

After Streaming:
┌─────────────────────────────────────────┐
│ Withheld errors exist?                  │
│   ├── Attempt recovery                  │
│   │   ├── Success: continue loop        │
│   │   │   (consumer never saw the error)│
│   │   └── Failure: yield withheld error │
│   │       (consumer sees it now)        │
│   └── No errors: proceed normally       │
└─────────────────────────────────────────┘

This pattern is necessary because of the generator protocol. Once you yield a message, it is in the consumer's hands. You cannot take it back. If the consumer reacts to an error by disconnecting, your subsequent recovery is invisible. By withholding, you defer the decision until you have enough information to make it correctly.

The "Agentic Turn" Concept

A key concept for understanding the agent loop is the agentic turn: one user message may trigger many loop iterations.

User types: "Find and fix all TODO comments in src/"

  Iteration 1: Model calls Grep to find TODO comments
  Iteration 2: Model calls Read on file1.py
  Iteration 3: Model calls Edit on file1.py
  Iteration 4: Model calls Read on file2.py
  Iteration 5: Model calls Edit on file2.py
  Iteration 6: Model calls Read on file3.py
  Iteration 7: Model calls Edit on file3.py
  Iteration 8: Model responds with summary of changes

Total: 8 iterations, 1 user message

The distinction between "user turn" and "agent turn" matters for:

Token accounting. The context window grows across all 8 iterations. By iteration 8, the window contains the original user message plus 7 model responses and 7 tool results. Context management must track tokens across the entire agentic turn, not just per-iteration.

Cost tracking. Each iteration incurs an API call. The user types one sentence, but the system makes 8 API calls. Cost tracking should show the total cost of the agentic turn, not just the last iteration.

Abort handling. If the user presses Ctrl+C during iteration 5, the loop must handle a mid-turn abort. Some tool results are already in the conversation. Some edits have already been applied to disk. The abort handler must decide: roll back the edits? Leave them in place? Show partial results?

Subagent delegation. An agentic turn may spawn subagents that run their own loops. The parent's turn counter includes subagent iterations, but the subagent's budget is separate from the parent's continuation budget.

Token Budget Management Per Turn

An agentic turn can consume significant tokens. Without budget management, a user who asks "refactor everything" could trigger hundreds of iterations, consuming millions of tokens.

Two independent budget systems control spending:

Client-Side Continuation Budget

The user sets a token budget explicitly: "refactor this module +500k". The budget engine tracks total tokens consumed across all iterations of the agentic turn and makes a binary decision after each iteration: continue or stop.

Three stopping conditions, evaluated in order:

  1. Under 90% and making progress — continue. Inject a nudge message: "You've used X% of your budget. Keep working."
  2. Diminishing returns — stop early. After 3+ continuations, if the last two produced less than 500 tokens each, the model is stuck in a loop. Stop to prevent waste.
  3. At or above 90% — stop naturally. The 10% headroom gives the model space for a coherent closing response.

A critical guard: subagents do not inherit the parent's budget. A subagent spawned by the parent should complete its delegated task and return, not auto-continue under the parent's budget.

Server-Side Task Budget

The client-side budget decides whether to continue. But the model does not know about it — the model generates a full response, and the client decides afterward. The model cannot self-pace.

The task budget solves this by passing the total budget and remaining balance to the API. The model sees how much budget is left and can plan accordingly — producing shorter responses when budget is low rather than being cut off mid-thought.

Feature Client-Side Budget Server-Side Task Budget
Who decides The agent loop The model itself
Model awareness None Full (sees total + remaining)
Mechanism Auto-continue with nudge Model self-paces
Works after compaction Yes (tracks total) Yes (remaining recalculated)

They work in concert. The client decides whether to run another iteration. The model, given the task budget, decides how to allocate its response within the available tokens.

Loop Invariants

A loop invariant is a condition that must be true at the start and end of every iteration. Documenting invariants prevents bugs where one iteration's exit state violates another iteration's entry assumptions.

Invariant 1: Messages Are Valid API Input

At every iteration start, the messages array must be a valid sequence for the API: - Starts with a user message (or is empty, for the first turn) - Every tool_use block in an assistant message has a matching tool_result in the subsequent user message - No orphaned tool_result blocks without preceding tool_use blocks

If the stream is interrupted mid-generation, orphaned tool_use blocks would break this invariant. The safety net: a function that scans assistant messages for tool_use blocks without matching results and generates synthetic error results for each. This runs on every error path — abort, network failure, model error — to maintain the invariant.

Invariant 2: Recovery State Is Scoped to the Current Path

Recovery counters (max_output_tokens_recovery_count, compaction_attempted) must only accumulate within their respective recovery paths. When the loop transitions to a normal next_turn, all recovery counters reset to zero. When transitioning between different recovery paths (e.g., from token recovery to stop hook blocking), each path preserves the other's state to prevent interaction bugs.

Invariant 3: Context Fits the Window

After Phase 1 completes, the message context must fit within the model's context window. If it does not, the loop exits rather than sending a request that will fail. This invariant means Phase 2 can assume the API call will not fail due to context overflow (though it may fail for other reasons).

Invariant 4: Turn Count Increases Monotonically

The turn counter increments on every continuation that advances the conversation (new tool results added). Recovery retries (escalation, compaction) do not increment the turn count because they replay the same logical turn. This means the turn limit counts logical turns, not raw API calls.

Designing for Testability

The agent loop is one of the hardest components to test because it depends on an external API, a tool system, and compaction logic. The key to testability: dependency injection of the hot seams.

Identify the Hot Seams

The agent loop has four dependencies that tests need to control:

  1. The model call — what the API returns
  2. Compaction — how and when context is compressed
  3. Microcompaction — the cheap pre-request compression
  4. UUID generation — for deterministic message IDs in tests

Inject Only What You Must

type AgentLoopDeps = {
    callModel: typeof streamModelResponse
    compact: typeof autoCompactIfNeeded
    microcompact: typeof microcompactMessages
    uuid: () => string
}

Using typeof realFunction for the type signature keeps mock signatures in sync with real implementations automatically. If the real function gains a parameter, tests that do not provide it fail at compile time.

The scope is intentionally narrow — four dependencies, not twenty. Start with the minimum viable injection surface and expand only when tests prove it necessary. Over-injection creates a maintenance burden where every new feature requires updating the injection interface.

The Default Fallback Pattern

function agentLoop(params: LoopParams): AsyncGenerator<Message, Terminal> {
    const deps = params.deps ?? productionDeps()
    // ... use deps.callModel, deps.compact, etc.
}

Production code passes no deps — it gets the real implementations. Test code passes mock deps directly. No framework, no container, no decorator. This is explicit dependency injection at its simplest.

Design Lessons

Building the core agent loop for a production CLI agent teaches eight principles:

1. Use pull-based streams for agent loops. Async generators give you backpressure, composable cleanup, and a return channel for exit reasons — all from the language runtime. The consumer controls the pace, not the producer.

2. Separate immutable config from mutable state. Destructure config once at entry, never reassign. Build a new state object on every continuation. This makes every transition self-documenting and independently readable.

3. Use discriminated unions for exit and continuation reasons. 10 exit reasons and 7 continuation reasons as discriminated unions replace magic strings, exception types, and numeric codes. Tests assert on reason fields, not message content or stack traces.

4. Pipeline tool execution with streaming. Starting tools while the model is still generating is the highest-impact performance optimization in the agent loop. It requires concurrent-safe classification and sibling error cascading, but the latency savings of 60-70% justify the complexity.

5. Withhold recoverable errors from the output stream. Do not expose partial failures to consumers. Suppress during streaming, attempt recovery, and surface only when recovery fails. This prevents the bug where SDK consumers disconnect before recovery completes.

6. Document state field interactions across recovery paths. When one recovery path interacts with another (compaction + stop hooks), the interaction can create infinite loops. The transition reason field and explicit state preservation rules make these interactions debuggable.

7. Enforce loop invariants explicitly. Valid API message sequences, scoped recovery state, context window compliance, and monotonic turn counts. Each invariant prevents a class of bugs that would otherwise manifest as mysterious API errors or infinite loops.

8. Optimize for the common case, handle the tail correctly. The 8K default output limit covers 99% of responses at 4-8x better GPU utilization. The escalation to 64K handles the 1% that need more. The 3-attempt recovery handles the 0.01% that need even more. Do not over-provision the default — save resources for the system, recover gracefully when needed.
