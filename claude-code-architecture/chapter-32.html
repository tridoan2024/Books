Chapter 32: Observability Architecture

Traditional software is a deterministic machine. When it breaks, you read the logs, reproduce the bug, and fix the code. AI agents are probabilistic systems wrapped in deterministic infrastructure. When an agent produces a wrong answer, you cannot simply "reproduce" the bug -- the model might take a different path on the next run. When an agent is slow, the bottleneck might be the model's inference time (which you cannot control), the context assembly (which you can), or an MCP server that is silently degrading. When costs spike, you need to know whether it is because the model is generating verbose responses, the context window is ballooning, or a tool is returning oversized results.

Observability for AI agents is not a nice-to-have. It is the difference between operating a system and guessing at one. This chapter covers the observability architecture: structured logging with category-based filtering, OpenTelemetry integration for distributed tracing, cost tracking at multiple granularities, performance profiling from startup through individual tool calls, and production debugging techniques that let you reconstruct what happened after the fact.

32.1 Why Observability Matters More for AI Agents

Every argument for observability in traditional software applies double for AI agents. Four properties of AI agents make observability architecturally essential rather than merely useful:

Non-determinism. The same input produces different outputs. You cannot reproduce a bug by re-running the prompt. The only way to understand what happened is to have recorded it as it happened. Without observability, bugs are anecdotes. With it, they are data.

Expense. Every API call costs money. A misconfigured tool that triggers a 50-turn loop before hitting the max-turn limit can cost $10 in a single session. Without cost tracking, you discover this when the monthly bill arrives. With per-session cost tracking, you catch it in real time.

Latency. A typical agent turn takes 5-30 seconds. Users tolerate this because the output is valuable, but their tolerance has limits. Without latency breakdown, you know the turn was slow but not why. Was it the model? The tool execution? The context assembly? The MCP server? Performance profiling decomposes the latency into actionable components.

Opacity. The model's reasoning is hidden. You see the tool calls it made and the final response it produced, but not why it chose that path. Observability provides proxies for understanding: which tools it considered, how much context it consumed, what information it had available at each decision point.

32.2 Structured Logging Architecture

The logging system must serve two audiences: humans debugging in real time and machines processing logs for analytics. These audiences have conflicting requirements. Humans want readable messages with context. Machines want structured fields they can query. The solution is structured logging with human-readable rendering.

Log Levels and Categories

Log levels define severity. Categories define subsystem. Together, they form a two-dimensional filter space:

Level Semantic meaning Typical volume
ERROR Operation failed, user impact ~1-5 per session
WARN Recoverable issue, potential problem ~10-50 per session
INFO Significant operation completed ~50-200 per session
DEBUG Detailed operation internals ~500-5000 per session
TRACE Everything: payloads, bytes, tokens ~10,000+ per session
Category What it covers
api HTTP requests, responses, headers, token counts
query Query loop iterations, state transitions, exit reasons
tools Tool invocations, inputs, outputs, durations
permissions Rule evaluations, decisions, matched rules
compaction Context compression decisions, strategies, token savings
mcp MCP protocol messages, server status, tool routing
hooks Hook execution, exit codes, durations
settings Configuration loading, merging, validation
session Session creation, persistence, recovery
startup Bootstrap phases, timing checkpoints

Filter Configuration

The filter syntax combines levels and categories:

# Everything at WARN or above
AGENT_LOG_LEVEL=warn

# API subsystem at DEBUG, MCP at TRACE, everything else at WARN
AGENT_LOG_FILTER="api=debug,mcp=trace,*=warn"

# Just tool invocations at debug level
AGENT_LOG_FILTER="tools=debug,*=error"

The filter evaluation is a lookup with fallback:

For each log event (category, level):
  1. Check if category has an explicit level override
  2. If yes, compare event level against override
  3. If no, compare event level against default level
  4. Emit if event level <= threshold

This is intentionally simple. Complex filter expressions (AND/OR/NOT) add cognitive overhead without proportional benefit. The two-dimensional space of (category, level) is expressive enough for practical debugging: "show me everything the API layer is doing" or "show me errors from any subsystem."

Log Sinks

A log sink is a destination for log events. The architecture supports multiple simultaneous sinks:

graph LR
    E["Log Event"] --> F["Filter Engine"]
    F --> S1["File Sink<br/>~/.agent/logs/session.log"]
    F --> S2["Stdout Sink<br/>Human-readable format"]
    F --> S3["OTLP Sink<br/>OpenTelemetry collector"]

    style F fill:#ffd43b,stroke:#e67700

File sink. Writes JSON-structured events to a session-specific log file. This is the primary sink for post-hoc debugging. The file name includes the session ID so multiple concurrent sessions do not interleave.

Stdout sink. Writes human-readable formatted events to stderr (not stdout, which is reserved for agent output). This is the primary sink for real-time debugging during development.

OTLP sink. Ships events to an OpenTelemetry collector for aggregation, dashboarding, and alerting. This is the primary sink for production monitoring.

Each sink can have its own filter configuration. Production might route *=warn to the OTLP sink but *=debug to the file sink, capturing detailed diagnostics locally while keeping the central collector focused on actionable events.

Sensitive Field Redaction

Logs must never contain secrets. The logging pipeline applies automatic redaction before any sink receives the event:

  • API keys are truncated: sk-ant-...3f2a (first 7 chars + last 4)
  • OAuth tokens are replaced: [REDACTED_TOKEN]
  • File contents are truncated to the first N characters with a length indicator
  • User input is logged at DEBUG level only (never at INFO or above)

The redaction layer sits between the filter engine and the sinks. This ensures that even if a developer accidentally logs a full API key at DEBUG level, it is redacted before reaching any sink.

32.3 OpenTelemetry Integration

OpenTelemetry (OTel) provides a vendor-neutral standard for traces, metrics, and logs. For AI agents, traces are the most valuable primitive because they let you decompose a complex operation (an agent turn) into its constituent parts (API call, tool execution, context assembly).

Trace Architecture for AI Agents

A trace represents a complete agent turn. It contains spans, each representing a discrete operation:

gantt
    title Agent Turn Trace
    dateFormat X
    axisFormat %s

    section Context
    Assemble context     :c1, 0, 200
    Estimate tokens      :c2, 200, 50

    section API
    API request          :a1, 250, 3000
    Stream response      :a2, 3250, 2000

    section Tools
    Read file            :t1, 5250, 100
    Grep codebase        :t2, 5350, 800
    Edit file            :t3, 6150, 150

    section Post
    Permission check     :p1, 5250, 20
    Hook execution       :h1, 6300, 300
    Format output        :f1, 6600, 100

Each span carries attributes that are specific to AI agent operations:

API spans include: model name, input token count, output token count, cache read tokens, cache write tokens, stop reason, request ID, latency, and cost.

Tool spans include: tool name, input (redacted), output length, exit code (for Bash), duration, and whether the result was truncated.

Context assembly spans include: total tokens assembled, number of messages included, number pruned, system prompt size, and tool result sizes.

Span Hierarchy

trace: agent_turn_7
  |-- span: context_assembly (200ms)
  |   |-- span: token_estimation (50ms)
  |   |-- span: message_selection (80ms)
  |   |-- span: system_prompt_build (70ms)
  |
  |-- span: api_request (5000ms)
  |   |-- span: streaming_response (4800ms)
  |
  |-- span: tool_execution_batch
      |-- span: permission_check (10ms)
      |-- span: Read_config_py (100ms)
      |-- span: permission_check (10ms)
      |-- span: Grep_error_pattern (800ms)
      |-- span: permission_check (10ms)
      |-- span: Edit_config_py (150ms)
      |-- span: hook_auto_lint (300ms)

The hierarchy makes latency attribution straightforward. If a turn takes 8 seconds, the trace immediately shows that 5 seconds were the API call (model inference), 1.4 seconds were tool execution, 200ms were context assembly, and the rest was overhead. You know exactly where to optimize.

Metrics

Traces show individual operations. Metrics show aggregates over time. The key metrics for AI agents:

Metric Type Unit Purpose
agent.turns.total Counter turns Total agent turns executed
agent.turns.duration Histogram ms Turn latency distribution
agent.api.tokens.input Counter tokens Total input tokens consumed
agent.api.tokens.output Counter tokens Total output tokens generated
agent.api.tokens.cached Counter tokens Tokens served from cache
agent.api.cost Counter USD Cumulative API cost
agent.api.errors Counter errors API errors by type
agent.tools.invocations Counter calls Tool calls by tool name
agent.tools.duration Histogram ms Tool execution latency
agent.context.usage Gauge ratio Context window fill ratio
agent.compaction.events Counter events Compaction triggers
agent.mcp.health Gauge enum MCP server health status

Instrumenting Without Overwhelming

A naive instrumentation approach creates a span for every function call. For an AI agent processing thousands of tokens per second, this generates millions of spans that overwhelm the collector and provide no useful signal.

The instrumentation strategy should follow the 80/20 rule:

  • Always instrument: API calls, tool executions, permission decisions, compaction events. These are the operations that matter for debugging and cost tracking.
  • Instrument at DEBUG level: Context assembly steps, message selection, token estimation. Useful for deep debugging but not needed in production.
  • Never instrument: Token-by-token streaming, individual character processing, render loop iterations. These are too granular to be useful and too voluminous to collect.

32.4 Cost Tracking Architecture

Cost tracking is not optional for AI agents. Unlike traditional software where infrastructure costs are amortized across millions of requests, AI agent costs scale linearly with usage -- every API call has a direct, measurable cost. A cost tracking architecture needs to operate at three levels of granularity.

Per-Request Cost

Every API request has a deterministic cost based on token counts and model pricing:

cost = (input_tokens * input_price_per_token)
     + (output_tokens * output_price_per_token)
     - (cached_tokens * cache_discount)

The pricing model is a lookup table indexed by model name:

Model Input (per 1M tokens) Output (per 1M tokens) Cache read discount
claude-opus-4 $15.00 $75.00 90%
claude-sonnet-4 $3.00 $15.00 90%
claude-haiku-3.5 $0.80 $4.00 90%

The cost calculator must be updated whenever pricing changes, which happens at the provider level, not the agent level. Store the pricing table in configuration, not in code, so it can be updated without a new release.

Per-Session Cost

Aggregate per-request costs into session totals:

Session #a1b2c3:
  Model: claude-sonnet-4-6
  Turns: 14
  Input tokens:  156,000 (89,000 cached)
  Output tokens:  28,000
  Tool calls: 23
  Duration: 12m 34s
  Cost: $0.87
    API:   $0.84
    Cache: -$0.24 (savings from caching)
    Net:   $0.63

Session cost tracking serves two purposes: real-time budget enforcement and post-hoc analysis. Budget enforcement lets you set a per-session cost limit (e.g., $5.00) and warn or stop the agent when it approaches the limit. Post-hoc analysis identifies expensive sessions for optimization.

Per-Organization Cost

For enterprise deployments, costs must be attributed to teams, projects, and users:

graph TB
    ORG["Organization: $4,200/month"]
    ORG --> T1["Team: Platform<br/>$1,800/month"]
    ORG --> T2["Team: Frontend<br/>$1,200/month"]

    T1 --> P1["Project: API<br/>$900"]
    T1 --> P2["Project: Infra<br/>$900"]

    T2 --> P3["Project: Web<br/>$800"]
    T2 --> P4["Project: Mobile<br/>$400"]

    P1 --> U1["alice: $450"]

    style T1 fill:#ffd43b,stroke:#e67700

Cost attribution requires metadata tagging on every API request: organization ID, team, project, and user. The billing system aggregates these tags. The architecture decision is where to tag: at the API client level (simplest), at the session level (most flexible), or at the organizational proxy level (most centralized).

Budget Enforcement

Budget enforcement operates at three thresholds:

Threshold Action
70% of budget Warning message in session
90% of budget Suggest compaction or session wrap-up
100% of budget Block further API calls, require override

The enforcement mechanism is a middleware in the API client that checks the running total before each request. The check is cheap (a comparison against a counter) and non-blocking for requests below the threshold.

32.5 Performance Profiling

Performance profiling for AI agents differs from traditional profiling because the dominant cost is usually network I/O (API calls), not CPU. The profiling architecture must capture both wall-clock time and resource consumption across the agent's lifecycle.

Startup Profiling

As discussed in Chapter 4, the startup sequence has a strict time budget. Profiling startup means placing timing checkpoints at phase boundaries:

Phase                    Duration   Cumulative
----                     --------   ----------
Module loading           120ms      120ms
Configuration cascade     85ms      205ms
Authentication           150ms      355ms
Tool registration         45ms      400ms
MCP server startup       820ms     1220ms
Context loading          310ms     1530ms
UI initialization        125ms     1655ms

The profile immediately reveals that MCP server startup dominates. This suggests architectural changes: lazy MCP initialization (start servers on first use rather than at startup) or parallel server startup (start all servers concurrently rather than sequentially).

Per-Turn Profiling

Each agent turn decomposes into phases:

pie title Turn Latency Breakdown (typical)
    "Model inference" : 65
    "Tool execution" : 20
    "Context assembly" : 8
    "Streaming overhead" : 4
    "Permission checks" : 2
    "Hook execution" : 1

Model inference typically dominates at 60-70% of turn time. This is the one component you cannot optimize directly -- it depends on the model, the prompt size, and the output length. But you can reduce it indirectly:

  • Smaller context means faster inference (fewer tokens to process)
  • Cache hits mean faster response (cached prefixes skip computation)
  • Shorter responses mean faster streaming (fewer output tokens)

Tool execution is the second largest component. Slow tools (large file reads, complex grep patterns, slow MCP servers) directly impact turn time. The profiler identifies which tools are slow and by how much.

Tool Execution Latency

Track per-tool latency as a histogram to identify outliers:

Tool P50 P90 P99 Max Count
Read 12ms 45ms 200ms 1.2s 450
Grep 80ms 350ms 1.5s 8.2s 120
Bash 150ms 800ms 3.5s 30s 85
Edit 8ms 25ms 80ms 300ms 65
MCP:search 200ms 600ms 2.1s 5.0s 30

The P99 column reveals the tail latency -- the cases that feel slow to users. If Grep's P99 is 1.5 seconds, 1 in 100 grep calls takes over 1.5 seconds. If the agent makes 10 grep calls per session, one session in 10 will have a noticeably slow grep.

Context Assembly Profiling

Context assembly has a hidden cost: it runs on every turn, and its cost grows as the conversation gets longer. Profile it separately:

Context assembly for turn 14:
  Message count: 42
  Total message tokens: 156,000
  Token estimation: 12ms
  Priority sorting: 3ms
  Message selection: 45ms (iterated 42 messages)
  System prompt build: 8ms
  Tool result inclusion: 22ms
  Cache prefix check: 5ms
  Total: 95ms

At 95ms for turn 14, assembly time is negligible. But conversations that reach 200+ messages can push this to 500ms+ as the message selection algorithm iterates more candidates. The profiler helps you decide when to implement more aggressive compaction or switch to indexed message selection.

32.6 Debugging Production Issues

When something goes wrong in production, you need to reconstruct what happened. The three primary debugging tools are transcript replay, session inspection, and VCR-based reproduction.

Transcript Replay

Every agent session produces a transcript -- a chronological record of messages, tool calls, and results. The transcript is the most valuable debugging artifact:

[
  {"turn": 1, "role": "user", "content": "Fix the login bug"},
  {"turn": 1, "role": "assistant", "content": "I'll investigate the login code.", "tool_calls": [
    {"name": "Read", "input": {"file_path": "src/auth/login.py"}}
  ]},
  {"turn": 1, "role": "tool", "name": "Read", "output": "def login(username, password):\n    ..."},
  {"turn": 2, "role": "assistant", "content": "Found the issue. The password comparison...", "tool_calls": [
    {"name": "Edit", "input": {"file_path": "src/auth/login.py", "old_string": "==", "new_string": "verify_hash"}}
  ]},
  {"turn": 2, "role": "tool", "name": "Edit", "output": "Edit applied successfully"}
]

Transcript replay lets you step through the conversation turn by turn, seeing exactly what the model received as context and what it decided to do. This is invaluable for diagnosing:

  • Wrong tool choice. The model called Edit when it should have called Read first. The transcript shows what context the model had when it made the decision.
  • Missing context. The model gave a wrong answer because a critical file was not in context. The transcript shows which files were included and which were pruned by compaction.
  • Tool errors. A tool returned an error that the model misinterpreted. The transcript shows the exact error message and the model's response to it.

Session State Inspection

Beyond the transcript, the session state captures the internal state at any point:

  • Context window composition. Which messages are in context, their token counts, and which were pruned.
  • Permission cache. Which rules were evaluated and what decisions were cached.
  • MCP server status. Which servers are connected, their health status, and recent tool calls.
  • Cost accumulator. Running total of tokens and cost.

Session state inspection is typically available through a debug command (/debug-session) that dumps the current state without modifying it.

VCR-Based Reproduction

As covered in Chapter 31, VCR recordings capture the exact API interactions. If a production session produces unexpected behavior and you have the transcript, you can create a VCR cassette from the transcript and replay it locally. This gives you a deterministic reproduction of the production behavior -- the holy grail of debugging non-deterministic systems.

The workflow:

flowchart LR
    A["Production incident"] --> B["Extract transcript"]
    B --> C["Convert to VCR cassette"]
    C --> D["Replay locally"]
    D --> E["Debug with full tooling"]
    E --> F["Fix and add test"]

32.7 Analytics Pipeline

Raw observability data is useful for debugging individual sessions. Analytics transforms it into insights about system behavior over time.

Key Dashboards

Cost dashboard. Daily/weekly/monthly cost trends broken down by model, team, and project. Anomaly detection for unexpected cost spikes.

Latency dashboard. P50/P90/P99 turn latency over time. Breakdown by phase (model, tools, assembly). Correlation with context size.

Quality dashboard. Task completion rate from eval runs. Tool efficiency trends. Safety violation count (should always be zero).

Usage dashboard. Sessions per day, turns per session, tools per turn. Most-used tools. Most-common user intents.

Anomaly Detection

Set alerts on:

Metric Alert condition Likely cause
Session cost >3x median Tool loop, verbose model, large context
Turn latency P99 >2x baseline Slow MCP server, model degradation
Error rate >5% of turns API outage, broken tool, bad config
Compaction rate >3 per session Context growing too fast, inefficient tool use
Safety violations >0 Permission gap, new attack vector

32.9 Key Takeaways

  1. Observability is not optional for AI agents. Non-determinism, expense, latency, and opacity make it architecturally essential. You cannot operate what you cannot observe.

  2. Two-dimensional log filtering (category + level) gives developers precise control. "Show me API calls at debug level, everything else at warn" is the most common debugging pattern.

  3. Trace every turn as a span tree. API call, tool executions, permission checks, and context assembly should all be child spans of the agent turn. This makes latency attribution trivial.

  4. Track cost at three granularities. Per-request for accuracy, per-session for budgets, per-organization for billing. Cost tracking is not an afterthought -- it belongs in the API client layer from day one.

  5. Profile startup separately. The startup budget is typically 400ms-2s. MCP server initialization is usually the bottleneck. Profile it, optimize it, monitor it.

  6. Transcripts are your most valuable artifact. They enable post-hoc debugging of non-deterministic systems. Store them. Index them. Make them easy to replay.

  7. Redact before logging. API keys, tokens, and user input must never reach any log sink. Apply redaction as a pipeline stage, not as a per-call responsibility.

  8. Set anomaly alerts on cost and error rate. A cost spike is usually a bug (tool loop, context explosion). An error spike is usually an outage (API, MCP server). Both need immediate attention.

As discussed in Chapter 31, VCR recordings can convert production transcripts into deterministic test cases. Together, testing and observability form a closed loop: observability detects problems, transcripts enable reproduction, VCR recordings create regression tests, and the test suite prevents recurrence.
