Chapter 5: Configuration Cascade

The Problem of Multiple Stakeholders

A solo developer's CLI tool needs one configuration file. A team's CLI tool needs two -- shared and personal. An enterprise CLI tool needs seven. Each stakeholder has a legitimate claim over the tool's behavior, and their claims conflict:

  • The platform sets sane defaults so the tool works out of the box.
  • The organization enforces security policies that no one can override.
  • The enterprise admin configures device-level settings via MDM.
  • The user sets personal preferences in their home directory.
  • The team commits shared conventions to the project repository.
  • The developer tweaks settings locally without polluting the team config.
  • The invocation overrides everything for a single run.

Claude Code resolves these competing claims with a 7-layer configuration cascade. This chapter examines the architecture of that cascade: why seven layers, how they merge, what happens when they conflict, and how schema validation catches errors without blocking startup.

The Seven Layers

The cascade processes settings from lowest priority to highest. Each successive layer can override, extend, or constrain the previous layers:

But there's a twist: Layer 6 (Managed/MDM) is not simply "overridden by everything above it." Enterprise policy settings operate on a first-source-wins model within their own sub-layers and can lock fields that no other layer can override. The cascade is really two systems: a standard priority override for developer-facing settings, and a policy enforcement layer that sits outside the priority chain.

Why Seven Layers?

Each layer exists because a real stakeholder needs it. Let's examine each layer's justification:

Layer 1: Built-in Defaults. Without defaults, every fresh installation would fail on first run. Defaults encode the product team's opinion about reasonable behavior: Sonnet as the default model, auto-compaction enabled, 200K context window. These defaults change across versions -- which is why the migration system (discussed later) exists.

Layer 2: Managed/MDM Settings. Enterprises need to enforce policy. An organization that restricts model usage to Sonnet (for cost control) or disables --dangerously-skip-permissions (for security) needs a layer that individual developers cannot circumvent. This layer is special: it can lock fields, making them immune to override by higher-priority layers.

Layer 3: User Settings. A developer who works across multiple projects wants consistent preferences -- their preferred model, their global permission rules, their key bindings. User settings are the "home base" configuration.

Layer 4: Project Settings. A team wants consistent behavior for all contributors. Permission rules that allow git commands, hooks that run linters on save, MCP server configurations for the project's development environment -- these belong in version-controlled settings that everyone shares.

Layer 5: Local Settings. A developer wants to override team settings without modifying the shared file. The most common use case: settings.local.json with "allow": ["Bash(*)"] to permit all bash commands locally, while the team's settings.json restricts commands for safety. This file is .gitignored.

Layer 6: Environment Variables. CI/CD pipelines, Docker containers, and ephemeral environments need to configure the tool without writing files. Environment variables are the standard mechanism for runtime-scoped configuration.

Layer 7: CLI Arguments. A single invocation might need different settings: claude --model opus for a complex task, claude --permission-mode plan for a reviewed workflow. CLI flags are the highest-priority file-based override.

Merge Semantics: The Hard Part

If configuration were just "higher layer wins," the cascade would be trivial. The complexity comes from how different field types merge across layers.

The Three Merge Strategies

graph LR
    subgraph "Scalar: Override"
        S1["User: model = sonnet"] --> S2["Project: model = opus"]
        S2 --> SR["Result: model = opus"]
    end

    subgraph "Array: Concatenate"
        A1["User: allow = [git *]"] --> A2["Project: allow = [npm test]"]
        A2 --> AR["Result: allow = [git *, npm test]"]
    end

    subgraph "Object: Deep Merge"
        O1["User: hooks = {Pre: [lint]}"] --> O2["Project: hooks = {Post: [test]}"]
        O2 --> OR["Result: hooks = {Pre: [lint], Post: [test]}"]
    end

The merge algorithm applies different strategies based on the field's semantic meaning:

Field Type Strategy Rationale
Scalars (model, effortLevel) Override (higher layer wins) Only one model can be active
Permission arrays (allow, deny) Concatenate (all layers combine) Permissions are additive -- each layer can grant or restrict
Hook definitions Merge by event key A project hook for PreToolUse and a user hook for PostToolUse should both fire
Environment variables (env) Extend (higher layer wins on collision) Combine env vars from all layers, with local taking precedence on conflicts
MCP servers Append (no deduplication) Each layer can add servers; removal requires editing the layer that added it
Tool config / features Extend (higher layer wins on collision) Feature flags and tool config merge like env vars

The Merge Algorithm

function mergeSettings(base: Settings, override: Settings): Settings {
  const result = { ...base };

  for (const [key, value] of Object.entries(override)) {
    if (key === 'permissions') {
      // Permissions: concatenate allow and deny arrays
      result.permissions = {
        allow: [
          ...(base.permissions?.allow ?? []),
          ...(override.permissions?.allow ?? []),
        ],
        deny: [
          ...(base.permissions?.deny ?? []),
          ...(override.permissions?.deny ?? []),
        ],
      };
    } else if (key === 'hooks') {
      // Hooks: merge by event name, concatenating hook arrays
      result.hooks = mergeHooks(base.hooks, override.hooks);
    } else if (isObject(value) && isObject(base[key])) {
      // Objects: recursive deep merge
      result[key] = mergeSettings(base[key], value);
    } else {
      // Scalars: override
      result[key] = value;
    }
  }

  return result;
}

Why Permissions Concatenate Instead of Override

This is the most important design decision in the merge system. Consider a team with this project settings:

{
  "permissions": {
    "allow": ["Bash(git *)", "Bash(npm test)"],
    "deny": ["Bash(rm -rf *)"]
  }
}

A developer adds local settings:

{
  "permissions": {
    "allow": ["Bash(docker *)"]
  }
}

If permissions overrode: The result would be allow: ["Bash(docker *)"] -- the team's git and npm test permissions would vanish. The developer would suddenly lose access to commands the team intentionally allowed.

With concatenation: The result is allow: ["Bash(git *)", "Bash(npm test)", "Bash(docker *)"] -- the developer adds their Docker permission without affecting the team's rules.

This is why the deny array also concatenates. A user's global deny rules (e.g., "never read .env files") should combine with the team's deny rules, not replace them. Neither party should be able to accidentally remove the other's safety rules.

Array Order Matters

For permission arrays, order determines evaluation priority. The permission system evaluates rules in a deny-first scan:

  1. Scan the deny array from first to last. First match denies.
  2. Scan the allow array from first to last. First match allows.
  3. No match falls through to the default behavior (usually "ask the user").

When merging user settings into project settings, user permissions are prepended:

// User permissions go first (lower priority)
const combinedDeny = [...user.permissions.deny, ...project.permissions.deny];

This means project-level deny rules appear later in the array and are evaluated later. But because deny-first scanning stops at the first match, the first matching deny rule wins. If both user and project have deny rules for the same pattern, the user's rule matches first. If only the project has a deny rule, it still matches.

In practice, this ordering means: project deny rules can add restrictions but can't remove user-level restrictions. And user deny rules can't be circumvented by project allow rules. The system is strictly additive for safety.

The Resolution Algorithm Step by Step

Here's the complete resolution flow, from raw files to final settings:

Three control flow branches deserve attention:

Trust gating (Phases 9-10 in Chapter 4). Project settings and local settings are only loaded if the directory is trusted. An untrusted repository's .claude/settings.json could contain malicious permission rules, dangerous hooks, or environment variable injections. The trust dialog (Chapter 4, Phase 9) determines whether these files are loaded.

Policy field locking. Enterprise managed settings can declare fields as "locked." Even if a CLI flag explicitly sets --model opus, if the organization has locked the model to Sonnet, the final resolution reverts the model to Sonnet. This happens after all other merging -- it's the last step before validation, ensuring no layer can circumvent policy.

Non-blocking validation. The final merged settings are validated against the schema. Invalid values produce warnings, not errors. The tool starts with potentially problematic settings because a partially correct configuration is vastly better than a tool that refuses to launch.

Schema Validation: Catching Errors Without Blocking Startup

The validation system performs 12 checks across 5 categories:

Validation Categories

Category Checks Severity
Permission syntax Empty patterns, unbalanced parentheses, invalid tool names Warning
Model validity Unknown model identifiers Warning
Effort level Unrecognized effort strings Warning
Context tokens Zero value, exceeds 2M ceiling Warning
Hook definitions Unknown event names, empty commands, zero timeouts, invalid types Warning

Every check produces a warning, never an error. The philosophy is captured in a single principle: Claude Code should always start, even with a broken config.

Consider the developer experience of the alternative. You're debugging a production incident at 2 AM. You open your terminal, type claude, and get:

Error: Invalid settings.json at line 47: unknown hook event "PreToolUseFailure"
Claude Code cannot start. Fix your configuration and try again.

That hook event was added in a newer version. Your coworker committed it to the shared settings. Now your older installation can't start. The bug isn't in your code -- it's in a coworker's config change you don't control.

With non-blocking validation:

Warning: Unknown hook event "PreToolUseFailure" in .claude/settings.json (line 47)
         This hook will be ignored. Update Claude Code for full hook support.

claude >  _

You can work. The unknown hook is silently ignored. The warning tells you what happened and how to fix it. No one is blocked.

Forward Compatibility

Non-blocking validation enables forward compatibility: a settings file written for version N+1 works in version N. Unknown model names, unknown hook events, unknown feature flags -- all produce warnings and are skipped. This is the same principle HTTP uses with unknown headers: ignore what you don't understand.

This design decision has a cost: silently ignoring misspelled settings. A developer who writes "effortLevle": "high" (typo) won't see an error -- the field is unknown and skipped, and the default effort level applies. To mitigate this, the validator also checks for common misspellings and near-matches:

if (!KNOWN_KEYS.includes(key)) {
  const closest = findClosestMatch(key, KNOWN_KEYS);
  if (closest && levenshtein(key, closest) <= 2) {
    warnings.push({
      code: 'possible_typo',
      message: `Unknown key "${key}" — did you mean "${closest}"?`,
    });
  }
}

Environment Variable Precedence

Environment variables provide the highest-priority file-less override. Claude Code reads variables with two prefix patterns:

Standard Variables

Variable Overrides Example
ANTHROPIC_API_KEY Authentication credentials sk-ant-...
ANTHROPIC_AUTH_TOKEN OAuth token (highest auth priority) Bearer token
ANTHROPIC_BEDROCK_BASE_URL Enables Bedrock provider https://...
CLAUDE_CODE_USE_BEDROCK Enables Bedrock mode 1
CLAUDE_CODE_USE_VERTEX Enables Vertex AI mode 1

Settings-Derived Environment Variables

The configuration cascade itself can inject environment variables via the env field:

{
  "env": {
    "NODE_ENV": "development",
    "LOG_LEVEL": "debug",
    "CUSTOM_API_URL": "https://internal.example.com"
  }
}

These are applied during init() Step 2 (applySafeConfigEnvironmentVariables()), with a critical security restriction: only user settings (~/.claude/settings.json) can set environment variables during startup. Project settings are excluded from this step because they execute before the trust dialog.

After trust is established, project-level environment variables are applied in a second pass. This two-pass approach prevents an untrusted project from injecting LD_PRELOAD or NODE_OPTIONS before the user has a chance to review the project.

Variable Resolution Order

When the same variable appears in multiple sources:

1. Process environment (set by shell/CI) — highest
2. CLI --env flag
3. Local settings (.claude/settings.local.json → env)
4. Project settings (.claude/settings.json → env)
5. User settings (~/.claude/settings.json → env) — lowest

Process-level environment variables always win. This ensures that export ANTHROPIC_API_KEY=... in your shell profile or CI pipeline takes precedence over any file-based configuration.

Managed Settings: The Enterprise Layer

Enterprise deployments add a layer that operates differently from all others. Managed settings don't just "win" in the priority cascade -- they can lock fields and constrain values.

Sources Within the Managed Layer

The managed layer itself has four sub-sources, resolved with a first-source-wins policy:

    R -->|absent| M

    style NONE fill:#e2e3e5,stroke:#383d41

Remote managed settings are fetched from an Anthropic endpoint during startup (non-blocking, fail-open). If the fetch succeeds, these settings take precedence over all other managed sources.

MDM settings are read via platform-specific mechanisms: plutil on macOS (reading from /Library/Managed Preferences/), reg query on Windows (reading from HKLM\SOFTWARE\Policies\ClaudeCode). These are configured by IT administrators through their MDM platform (Jamf, Intune, etc.).

File-based managed settings are read from managed-settings.json and a .d/ drop-in directory for modular overrides.

User registry settings (Windows only) are read from HKCU, providing user-scoped managed settings that don't require admin access.

Field Locking

The most powerful enterprise feature is field locking. When a managed policy locks a field, no other layer can override it:

{
  "permissionMode": "default",
  "allowManagedHooksOnly": true,
  "allowManagedPermissionRulesOnly": true,
  "allowManagedMcpServersOnly": true,
  "disableAllHooks": false,
  "allowedModels": ["claude-sonnet-4-6"],
  "maxBudget": 10.00
}

When allowManagedHooksOnly is true, user-defined hooks from ~/.claude/settings.json, .claude/settings.json, and .claude/settings.local.json are blocked. Only hooks from managed settings can run. This gives security teams confidence that no developer can install a hook that exfiltrates code or bypasses controls.

When allowedModels is set, the model picker only shows listed models. A developer who sets --model opus in a Sonnet-only organization sees:

Warning: Model "opus" is not allowed by your organization's policy.
         Using "claude-sonnet-4-6" instead.

MDM Prefetch Integration

As discussed in Chapter 4, MDM settings are prefetched during startup Phase 1 -- a subprocess (plutil on macOS) starts before module evaluation begins. By the time the settings cascade runs, the MDM data has been sitting in a resolved promise for 135+ milliseconds.

The prefetch pattern for MDM:

// Phase 1: Fire subprocess
let mdmPromise: Promise<Record<string, unknown>> | null = null;
export function startMdmRawRead(): void {
  if (process.platform === 'darwin') {
    mdmPromise = readMacOSPlist();
  }
}

// Phase 6: Retrieve result (already resolved)
export async function getMdmRawData(): Promise<Record<string, unknown>> {
  return mdmPromise ?? Promise.resolve({});
}

The ?? fallback ensures correctness on platforms without MDM support. Linux and non-managed macOS installations get an empty object -- no MDM constraints.

Configuration for Different Stakeholders

A practical way to understand the cascade is through use cases. Each stakeholder interacts with a different layer:

The Solo Developer

Configures ~/.claude/settings.json (Layer 3) for global preferences and .claude/settings.local.json (Layer 5) for project-specific overrides:

// ~/.claude/settings.json
{
  "model": "opus",
  "effortLevel": "high",
  "permissions": {
    "allow": ["Bash(git *)", "Bash(npm *)"]
  }
}

// .claude/settings.local.json (gitignored)
{
  "permissions": {
    "allow": ["Bash(*)"]  // Permissive locally
  }
}

Result: all bash commands are allowed (local overrides), the model is Opus (user setting), and effort is high.

The Team Lead

Configures .claude/settings.json (Layer 4) and commits it to the repository:

{
  "permissions": {
    "allow": ["Bash(git *)", "Bash(npm test)", "Bash(ruff *)"],
    "deny": ["Bash(rm -rf *)", "Read(./.env)"]
  },
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit",
      "type": "command",
      "command": "./.claude/hooks/auto-lint.sh",
      "timeout": 5000
    }]
  }
}

Every team member gets consistent permissions and hooks. Individual developers can add to these via their local settings, but can't remove the team's deny rules.

The Enterprise Admin

Configures managed settings via MDM:

<!-- macOS: com.anthropic.claude-code.plist -->
<dict>
  <key>permissionMode</key>

The CI Pipeline

Uses environment variables (Layer 6) and CLI flags (Layer 7):

  --model sonnet \
  --permission-mode bypass \
  --output-format json

No settings files needed. Everything is specified per-invocation. This is the cleanest integration path for automated workflows.

Hot-Reload: Watching for Changes

The settings engine watches for file changes and reloads without restarting:

function watchSettingsFile(
  filePath: string,
  callback: (event: SettingsChanged) => void
): void {
  const DEBOUNCE_MS = 500;
  let debounceTimer: NodeJS.Timer | null = null;
  let lastContent: string = '';

  fs.watch(filePath, () => {
    if (debounceTimer) clearTimeout(debounceTimer);
    debounceTimer = setTimeout(() => {
      const newContent = fs.readFileSync(filePath, 'utf-8');
      if (newContent === lastContent) return;

      const oldSettings = parseSettings(lastContent);
      const newSettings = parseSettings(newContent);
      const changedKeys = diffSettings(oldSettings, newSettings);

      lastContent = newContent;
      callback({ path: filePath, changedKeys, timestamp: new Date() });
    }, DEBOUNCE_MS);
  });
}

Why 500ms Debounce?

Text editors don't save files atomically. A typical vim :w or VS Code save produces 2-4 filesystem events:

1. File truncated (size → 0)
2. File written (partial content)
3. File written (full content)
4. File metadata updated (timestamp)

Without debouncing, the watcher would trigger on event 1 (empty file!), parse an empty settings object, and apply defaults -- then trigger again on event 3 with the actual content. The 500ms debounce waits for the save sequence to complete before reading.

Selective Reaction

The diff engine identifies exactly which keys changed:

interface SettingsDiff {
  key: string;
  type: 'added' | 'removed' | 'modified';
  oldValue?: unknown;
  newValue?: unknown;
}

Consumers subscribe to specific categories of changes:

Changed Key Reaction
model Update model selection in bootstrap state
permissions.* Clear permission cache, re-evaluate pending rules
hooks.* Reload hook registry
env.* Clear credential caches, re-apply env vars
mcpServers.* Signal MCP connection manager to reconcile
effortLevel Update query engine effort parameter

Not every change requires action. A change to effortLevel updates a single field. A change to env requires clearing all credential caches (API keys, AWS, GCP credentials might be affected) and re-applying environment variables. The diff granularity enables proportional responses.

Two Settings Systems: The Coexistence Problem

Claude Code has two separate configuration systems that coexist:

System Format Audience Merge Strategy
Project Settings JSON Teams (committed to git) Custom field-specific merge
Layered Config JSON + TOML + env vars Users (personal) Standard priority cascade

This dual system exists for historical and practical reasons:

History. The project started with JSON project settings. The layered config (supporting TOML and multi-format) was added later for richer personal configuration.

Different merge needs. Project settings use custom merge logic where permissions concatenate, hooks merge by event key, and env vars extend. The layered config uses a standard "higher priority wins" cascade. Combining them would require implementing both merge strategies in one system.

Different audiences. Project settings are for things committed to git -- team conventions that affect all contributors. The layered config is for personal preferences that cross project boundaries.

The resolution order between the two systems: project settings (from the JSON cascade) are merged with the layered config during the final resolution. Project settings take precedence for fields they define; the layered config fills gaps.

Architectural Patterns and Trade-offs

Pattern: Additive-Only Security Merge

Permissions use concatenation (not override) to ensure that no layer can accidentally remove another layer's safety rules. This is the additive-only security pattern: security rules can be added by any layer, but can only be removed by editing the layer that added them.

Trade-off: a developer can't use local settings to exempt themselves from a team deny rule. If the team denies Bash(rm -rf *), the developer can't re-allow it locally. This is by design -- but it means the local settings file isn't a true "override." It's an "extension."

Pattern: Trust-Gated Loading

Project settings are only loaded after the trust dialog (Chapter 4, Phase 9). This prevents prompt injection via CLAUDE.md and permission escalation via settings.json from untrusted repositories.

Trade-off: on first run in a new directory, the user sees a trust dialog before any project-specific behavior activates. This adds friction to the onboarding experience but prevents a class of supply-chain attacks where a cloned repository configures the tool to do harmful things.

Pattern: Policy Enforcement as Post-Processing

Enterprise policy doesn't participate in the merge cascade. Instead, locked fields are enforced as a post-processing step after all other merging is complete. This design keeps the merge algorithm simple (it doesn't need to know about locked fields) and makes policy enforcement auditable (you can log exactly which fields were reverted and why).

Trade-off: a developer who sets --model opus won't see an error at parse time. They'll see a warning after resolution that their model choice was overridden. This is a slightly worse developer experience than an immediate parse error, but it avoids entangling policy logic with CLI parsing.

Pattern: Non-Blocking Validation

All validation produces warnings, never errors. The tool starts with whatever configuration it has, even if some values are invalid.

Trade-off: silent failures. A misspelled field name is silently ignored. The near-match detection (levenshtein distance <= 2) catches common typos, but unusual misspellings slip through. The mitigation is the REPL header warning -- developers see a yellow warning banner when their config has issues.

Key Takeaways

  1. Layer by stakeholder, not by abstraction. Each of the seven layers exists because a real person or system needs to control the tool's behavior. If you can't name the stakeholder, you don't need the layer.

  2. Merge semantics must vary by field type. Permissions concatenate (additive security), hooks merge by event key (composable behavior), scalars override (last writer wins). Getting merge semantics wrong creates the subtlest configuration bugs.

  3. Enterprise policy is not just "highest priority." It's a separate enforcement mechanism that can lock fields, constrain values, and operate outside the normal cascade. This distinction matters for compliance.

  4. Trust-gate untrusted configuration. Project settings from an untrusted repository should not be loaded until the user explicitly trusts the directory. This prevents prompt injection and permission escalation.

  5. Validate non-blocking. A broken config should degrade functionality, not prevent startup. Warnings in the REPL header are sufficient -- errors at startup are hostile.

  6. Two-pass environment variable application. Apply user settings env vars before the trust dialog (safe), then project settings env vars after trust is established (potentially unsafe). This two-pass approach prevents environment injection from untrusted projects.

  7. Watch with debounce. File watchers fire multiple events per save. Debounce at 500ms and diff before/after to emit meaningful change events.
