Chapter 12: Multi-Provider Architecture

In Chapters 10 and 11, we designed the API client and the streaming pipeline -- the machinery that communicates with a model provider and processes the response. But those chapters assumed a single provider. Real deployments face a harder problem: the same AI CLI agent must work with the Anthropic API, AWS Bedrock, Google Vertex AI, and potentially custom enterprise endpoints, each with different authentication mechanisms, endpoint formats, capability sets, and pricing models.

This chapter examines the multi-provider architecture: how to resolve credentials without hardcoding provider assumptions, how to route requests to the correct endpoint, how to detect and adapt to provider-specific model capabilities, how to build fallback chains for resilience, and how to normalize costs across providers with different pricing structures. The goal is an agent that "just works" regardless of which cloud a customer uses, while giving each deployment the control it needs.

The Provider Landscape

Before designing the abstraction, understand what you are abstracting over. The three major providers for Anthropic models differ in nearly every dimension:

Dimension Anthropic 1P AWS Bedrock Google Vertex AI
Auth mechanism API key (header) AWS SigV4 (request signing) Google OAuth / service account
Endpoint format api.anthropic.com/v1/messages bedrock-runtime.{region}.amazonaws.com {region}-aiplatform.googleapis.com
Model ID format claude-opus-4-6 anthropic.claude-opus-4-6-v1:0 claude-opus-4-6@20260301
Beta header placement HTTP headers Request body (anthropic_beta field) HTTP headers
countTokens support Native CountTokensCommand Filtered betas
Streaming transport SSE over HTTP AWS EventStream SSE over HTTP
Regional endpoints Global (+ EU) Per AWS region Per GCP region
Billing Anthropic account AWS consolidated billing GCP project billing
Data residency US (default) Region-specific Region-specific
VPC support No VPC endpoints VPC Service Controls

Nine dimensions of difference. Some are trivial (model ID formatting). Others are fundamental (authentication mechanism, streaming transport). The provider abstraction must hide all of these behind the common interface from Chapter 10 while preserving access to provider-specific features that enterprise deployments require.

Each chain is a priority-ordered sequence. The client tries each source in order, using the first one that succeeds. The design principle: never ask the user for credentials if the environment already provides them.

Provider Selection

Before credential resolution, the system must determine which provider to use. This is itself a resolution chain:

1. ANTHROPIC_PROVIDER env var ('bedrock', 'vertex', 'custom')
2. Config file provider setting
3. Heuristic: if AWS_REGION is set and Bedrock model prefix detected -> bedrock
4. Heuristic: if GOOGLE_CLOUD_PROJECT is set -> vertex
5. Default: anthropic (first-party)

Heuristic detection (steps 3-4) is a convenience for deployments that do not explicitly configure the provider. If a developer is running on an EC2 instance with AWS credentials already available, the system can infer Bedrock intent without explicit configuration. The heuristics must be conservative -- false positives (incorrectly selecting a provider) are worse than requiring explicit configuration.

Credential Refresh

Credentials expire. OAuth tokens have TTLs. AWS temporary credentials from STS have session limits. GCP service account tokens rotate. The API client must handle transparent credential refresh without interrupting the user's session.

The factory function pattern from Chapter 10 supports this naturally:

class CredentialManager {
  private cachedCredentials: Credentials | null = null
  private expiresAt: number = 0

  async getCredentials(): Promise<Credentials> {
    if (this.cachedCredentials && Date.now() < this.expiresAt - 60_000) {
      return this.cachedCredentials  // Still valid (with 60s buffer)
    }

    // Resolution chain
    this.cachedCredentials = await this.resolveCredentials()
    this.expiresAt = this.cachedCredentials.expiresAt ?? Infinity
    return this.cachedCredentials
  }

  invalidate(): void {
    this.cachedCredentials = null
    this.expiresAt = 0
  }
}

The 60-second buffer before expiration prevents the race condition where credentials expire between the check and the API call. When the retry engine encounters a 401 (auth error), it calls invalidate() and the next getCredentials() resolves fresh credentials.

AWS SigV4 Signing

AWS Bedrock does not use API keys. Every request is signed with AWS Signature Version 4, which involves:

  1. Create a canonical request string (method, path, query, headers, body hash)
  2. Create a string to sign (algorithm, timestamp, scope, canonical request hash)
  3. Derive a signing key from the secret key + date + region + service
  4. Sign the string with HMAC-SHA256

This is handled by the AWS SDK, but the architectural implication is significant: the request body must be finalized before the signature is computed. You cannot add headers or modify the body after signing. This constrains where in the request pipeline provider-specific transformations can occur -- they must happen before the signing step.

GCP Service Account Authentication

Google Vertex AI uses OAuth 2.0 bearer tokens. Service accounts authenticate with a JWT grant:

  1. Load the service account key file (JSON with private key)
  2. Construct a JWT claiming the appropriate scope
  3. Sign the JWT with the private key
  4. Exchange the signed JWT for an access token at Google's OAuth endpoint
  5. Use the access token as a Bearer header

The access token has a 1-hour TTL. The credential manager handles refresh automatically.

Endpoint Routing

Model ID Translation

The same model has different identifiers across providers:

function translateModelId(model: string, provider: Provider): string {
  const baseModel = normalizeModelName(model)  // 'claude-opus-4-6'

  switch (provider) {
    case 'anthropic':
      return baseModel  // 'claude-opus-4-6'
    case 'bedrock':
      return `anthropic.${baseModel}-v1:0`  // 'anthropic.claude-opus-4-6-v1:0'
    case 'vertex':
      return `${baseModel}@20260301`  // 'claude-opus-4-6@20260301'
    case 'custom':
      return baseModel  // Pass through
  }
}

The agent's internal model references use the canonical Anthropic names. Translation happens at the adapter layer, invisible to the rest of the system. This means the configuration system, the UI, the cost tracker, and the agent loop all work with claude-opus-4-6 -- only the HTTP request contains the provider-specific format.

Region Selection

Cloud providers offer regional endpoints for data residency and latency:

function resolveEndpoint(provider: Provider, config: ProviderConfig): string {
  switch (provider) {
    case 'anthropic':
      return 'https://api.anthropic.com'
    case 'bedrock':
      const region = config.region ?? process.env.AWS_REGION ?? 'us-east-1'
      return `https://bedrock-runtime.${region}.amazonaws.com`
    case 'vertex':
      const location = config.location ?? process.env.GOOGLE_CLOUD_LOCATION ?? 'us-central1'
      return `https://${location}-aiplatform.googleapis.com`
    case 'custom':
      return config.baseURL  // Fully specified by the user
  }
}

Region selection is the first place where enterprise requirements diverge from developer convenience. A developer wants the lowest-latency endpoint (usually the one closest to them). An enterprise wants the endpoint that satisfies their data residency policy (which may be on the other side of the planet). The configuration must support both explicit region specification and automatic detection.

Capability Detection

The system queries capabilities through the provider abstraction:

interface ModelCapabilities {
  supportsTools: boolean
  supportsThinking: boolean
  supportsAdaptiveThinking: boolean
  supportsVision: boolean
  supportsPDFs: boolean
  supportsPromptCaching: boolean
  supportsFastMode: boolean
  supportsMaxEffort: boolean
  maxContextWindow: number
  maxOutputTokens: number
}

function getCapabilities(model: string, provider: Provider): ModelCapabilities {
  const base = BASE_CAPABILITIES[normalizeModelName(model)]
  const overrides = PROVIDER_OVERRIDES[provider]?.[normalizeModelName(model)]

  return { ...base, ...overrides }
}

The base capabilities represent the model's full feature set. Provider overrides narrow it -- Bedrock does not support adaptive thinking, so the override sets supportsAdaptiveThinking: false for Bedrock regardless of the base model.

Graceful Degradation

When a capability is unavailable on the active provider, the system must degrade gracefully rather than crash:

function resolveThinkingConfig(
  model: string, 
  provider: Provider,
  userConfig: ThinkingConfig,
): ThinkingConfig | undefined {
  const caps = getCapabilities(model, provider)

  if (!caps.supportsThinking) return undefined  // No thinking at all

  if (userConfig.type === 'adaptive' && !caps.supportsAdaptiveThinking) {
    // Downgrade adaptive to budget-based
    return { type: 'enabled', budgetTokens: getDefaultThinkingBudget(model) }
  }

  return userConfig
}

The user configured adaptive thinking. Bedrock does not support it. Instead of failing, the system silently downgrades to budget-based thinking. The agent continues to work -- slightly differently than on the first-party API, but functionally correct.

This pattern applies to every capability: fast mode, max effort, extended context windows. Each has a degradation path that preserves functionality at reduced capability.

Fallback Chains

Why Fallback Matters

A single provider outage should not halt your agent. Fallback chains define an ordered list of alternatives when the primary provider is unavailable:

Primary: Bedrock (us-east-1) -- corporate mandate
  |
  +-- Failure (circuit breaker trips)
  |
  v
Fallback 1: Bedrock (us-west-2) -- different region
  |
  +-- Failure (also overloaded)
  |
  v
Fallback 2: Anthropic 1P -- escape hatch
  |
  +-- Success

Designing the Fallback Chain

The fallback chain is an ordered list of provider configurations with conditions:

interface FallbackEntry {
  provider: Provider
  config: ProviderConfig
  condition?: FallbackCondition  // When to use this fallback
}

type FallbackCondition = 
  | { type: 'on_error', codes: number[] }  // Specific HTTP status codes
  | { type: 'on_timeout', thresholdMs: number }
  | { type: 'on_circuit_open' }
  | { type: 'always' }  // Use as unconditional fallback

const FALLBACK_CHAIN: FallbackEntry[] = [
  {
    provider: 'bedrock',
    config: { region: 'us-east-1' },
  },
  {
    provider: 'bedrock',
    config: { region: 'us-west-2' },
    condition: { type: 'on_error', codes: [529, 503] },
  },
  {
    provider: 'anthropic',
    config: {},
    condition: { type: 'on_circuit_open' },
  },
]

Fallback Execution

The fallback chain integrates with the retry engine from Chapter 10. When the retry engine exhausts its attempts on the primary provider, it signals a FallbackTriggeredError. The agent loop catches this and advances to the next entry in the chain:

async function* executeWithFallback(
  params: MessageParams,
  chain: FallbackEntry[],
): AsyncGenerator<StreamEvent> {
  for (const entry of chain) {
    try {
      const client = await createClient(entry.provider, entry.config)
      yield* withRetry(
        () => client.createMessageStream(params),
        { maxRetries: 3 },
      )
      return  // Success
    } catch (error) {
      if (isLastEntry(entry, chain)) throw error  // No more fallbacks
      if (!matchesCondition(error, entry.condition)) throw error
      // Continue to next fallback
      log.warn('provider_fallback', {
        from: entry.provider,
        error: error.message,
      })
    }
  }
}

Model Fallback vs Provider Fallback

Provider fallback (same model, different provider) is distinct from model fallback (different model, same or different provider). Both are important:

Scenario Strategy Example
Provider outage Same model, different provider Opus on Bedrock -> Opus on 1P
Model overloaded Smaller model, same provider Opus on 1P -> Sonnet on 1P
Combined failure Smaller model, different provider Opus on Bedrock -> Sonnet on 1P

The fallback chain can encode all three strategies:

Opus (Bedrock us-east-1)
  -> Opus (Bedrock us-west-2)     // Provider fallback
  -> Opus (Anthropic 1P)          // Provider fallback
  -> Sonnet (Bedrock us-east-1)   // Model fallback
  -> Sonnet (Anthropic 1P)        // Combined fallback

Each step down is a tradeoff: reduced capability (model fallback) or different compliance posture (provider fallback). The user should be informed when a fallback activates so they can make an informed decision about continuing.

The Adapter Pattern in Detail

Adapter Interface

Each provider implements the same interface through an adapter class:

abstract class BaseProviderAdapter implements ModelProvider {
  abstract createMessage(params: MessageParams): Promise<MessageResponse>
  abstract createMessageStream(params: MessageParams): AsyncIterable<StreamEvent>
  abstract countTokens(params: CountTokensParams): Promise<TokenCount>

  // Shared logic
  getModelCapabilities(model: string): ModelCapabilities {
    const base = BASE_CAPABILITIES[normalizeModelName(model)]
    const overrides = this.getProviderOverrides(model)
    return { ...base, ...overrides }
  }

  protected abstract getProviderOverrides(model: string): Partial<ModelCapabilities>
  protected abstract transformRequest(params: MessageParams): ProviderRequest
  protected abstract transformResponse(raw: ProviderResponse): MessageResponse
}

The Bedrock Adapter

Bedrock's key architectural difference: beta headers go in the request body, not HTTP headers. This requires a request transformation:

class BedrockAdapter extends BaseProviderAdapter {
  protected transformRequest(params: MessageParams): BedrockRequest {
    const { betaHeaders, ...rest } = params

    return {
      ...this.translateModelId(rest),
      // Betas move from HTTP headers to body
      anthropic_beta: betaHeaders,
      // Bedrock-specific fields
      anthropic_version: '2023-06-01',
    }
  }

  protected getProviderOverrides(model: string): Partial<ModelCapabilities> {
    return {
      supportsAdaptiveThinking: false,
      supportsFastMode: false,
      supportsMaxEffort: false,
    }
  }
}

The Vertex Adapter

Vertex's key difference: filtered betas for countTokens calls. Some beta features are not supported by Vertex's token counting endpoint, so including their beta headers causes errors:

class VertexAdapter extends BaseProviderAdapter {
  private readonly FILTERED_COUNT_BETAS = new Set([
    'structured-outputs-2025-12-15',
    'fast-mode-2026-02-01',
  ])

  async countTokens(params: CountTokensParams): Promise<TokenCount> {
    // Filter incompatible betas
    const filteredBetas = params.betaHeaders.filter(
      b => !this.FILTERED_COUNT_BETAS.has(b)
    )

    return super.countTokens({
      ...params,
      betaHeaders: filteredBetas,
    })
  }

  protected getProviderOverrides(model: string): Partial<ModelCapabilities> {
    return {
      supportsAdaptiveThinking: false,
      supportsFastMode: false,
    }
  }
}

The Custom Endpoint Adapter

Custom endpoints (Azure AI Foundry, enterprise proxies, local inference servers) use the first-party protocol with a different base URL:

class CustomEndpointAdapter extends BaseProviderAdapter {
  constructor(private config: { baseURL: string; auth: AuthConfig }) {
    super()
  }

  protected transformRequest(params: MessageParams): MessageParams {
    // Strip experimental betas that proxies may not support
    return {
      ...params,
      betaHeaders: params.betaHeaders.filter(
        b => !EXPERIMENTAL_BETAS.has(b)
      ),
    }
  }

  protected getProviderOverrides(): Partial<ModelCapabilities> {
    // Conservative: assume minimum capabilities
    return {
      supportsAdaptiveThinking: false,
      supportsFastMode: false,
      supportsMaxEffort: false,
    }
  }
}

Custom endpoints get conservative capability defaults. Since the system does not know what the proxy supports, it assumes the minimum. Users can override these through configuration.

Streaming Transport Differences

The Hidden Complexity

While the provider abstraction unifies the request/response format, streaming transport differs across providers in ways that affect the pipeline from Chapter 11:

Anthropic 1P and Vertex use standard Server-Sent Events over HTTP. The streaming pipeline from Chapter 11 works directly.

AWS Bedrock uses AWS EventStream, a binary framing protocol. Each event is a binary frame with headers and a payload. The adapter must translate EventStream frames into the same SSE-like event objects that the rest of the pipeline expects:

class BedrockStreamAdapter {
  async *adaptStream(
    bedrockStream: AsyncIterable<BedrockEventFrame>,
  ): AsyncIterable<StreamEvent> {
    for await (const frame of bedrockStream) {
      const payload = JSON.parse(
        new TextDecoder().decode(frame.body)
      )
      // Translate Bedrock event format to standard format
      yield this.translateEvent(payload)
    }
  }

  private translateEvent(payload: BedrockPayload): StreamEvent {
    // Bedrock wraps events in a different envelope
    // but the inner content matches the standard format
    return payload.data as StreamEvent
  }
}

The translation layer sits between the HTTP transport and the state machine from Chapter 11. The state machine does not know which provider produced the events -- it processes them identically.

Error Format Normalization

Error responses also differ across providers:

Provider Error Format HTTP Status
Anthropic 1P {"type":"error","error":{"type":"overloaded","message":"..."}} 529
Bedrock {"message":"...","type":"ThrottlingException"} 429
Vertex {"error":{"code":429,"message":"...","status":"RESOURCE_EXHAUSTED"}} 429

The adapter normalizes these into a common error type before the retry engine processes them:

interface NormalizedError {
  type: 'rate_limited' | 'overloaded' | 'auth' | 'context_overflow' | 'server' | 'client'
  retryable: boolean
  retryAfterMs?: number
  originalStatus: number
  message: string
}

This normalization ensures the retry engine from Chapter 10 applies the same classification ladder regardless of provider. A Bedrock ThrottlingException and an Anthropic overloaded error both map to the same retry strategy.

Provider-Specific Beta Handling

Beta features interact differently with each provider. This is one of the most error-prone areas of multi-provider support because the differences are subtle and the consequences are costly (cache invalidation, API errors, silent feature degradation).

Beta Placement Rules

function formatBetas(
  betas: string[], 
  provider: Provider,
): { headers: Record<string, string>; body: Record<string, unknown> } {
  switch (provider) {
    case 'anthropic':
      return {
        headers: { 'anthropic-beta': betas.join(',') },
        body: {},
      }
    case 'bedrock':
      // Bedrock puts betas in the request body
      return {
        headers: {},
        body: { anthropic_beta: betas },
      }
    case 'vertex':
      return {
        headers: { 'anthropic-beta': betas.join(',') },
        body: {},
      }
    case 'custom':
      // Strip experimental betas that proxies may reject
      const safeBetas = betas.filter(b => !EXPERIMENTAL_BETAS.has(b))
      return {
        headers: { 'anthropic-beta': safeBetas.join(',') },
        body: {},
      }
  }
}

The custom endpoint adapter strips experimental betas because enterprise proxies may validate the request schema strictly and reject unknown beta strings. This is a conservative default that prevents 400 errors at the cost of disabling experimental features behind proxies.

Provider-Agnostic Testing

The Mock Provider

Testing the agent should not require real API calls. A mock provider implements the same interface and returns deterministic responses:

class MockProvider implements ModelProvider {
  private responses: MessageResponse[] = []
  private callLog: MessageParams[] = []

  enqueueResponse(response: MessageResponse): void {
    this.responses.push(response)
  }

  async createMessage(params: MessageParams): Promise<MessageResponse> {
    this.callLog.push(params)
    const response = this.responses.shift()
    if (!response) throw new Error('No mock response available')
    return response
  }

  async *createMessageStream(params: MessageParams): AsyncIterable<StreamEvent> {
    const response = await this.createMessage(params)
    yield* convertToStreamEvents(response)
  }

  getCallLog(): MessageParams[] { return this.callLog }
}

The mock provider records all calls and plays back queued responses. This enables testing the entire agent pipeline -- context management, tool execution, permission checks -- without network calls.

VCR (Record/Replay) Testing

For integration tests that need realistic model responses, record real API calls and replay them:

Record mode:
  Agent -> RecordingProvider -> Real Provider -> API
           |
           +-> Save request/response to fixture file

Replay mode:
  Agent -> ReplayProvider -> Fixture file (no network)

The recording provider wraps a real provider, intercepting and saving each request-response pair. The replay provider loads fixtures and returns matching responses. This pattern works identically across all providers because the recording happens at the abstract interface level, not the HTTP level.

Design Lessons

Building a multi-provider architecture for a production AI CLI agent, these architectural principles emerge:

1. Abstract at the right level. The provider interface should be at the message semantics level (send a message, count tokens, get capabilities), not the HTTP level (make a POST, set headers). HTTP-level abstraction leaks provider details that the rest of the system should not see.

2. Translate model IDs at the adapter boundary. The internal system uses canonical names (claude-opus-4-6). Translation to provider-specific formats (anthropic.claude-opus-4-6-v1:0) happens inside the adapter. This prevents provider-specific naming from leaking into configuration, UI, cost tracking, and logging.

3. Degrade gracefully when capabilities differ. Adaptive thinking on the first-party API becomes budget thinking on Bedrock. Fast mode becomes standard mode on Vertex. Every capability has a degradation path that preserves functionality at reduced capability. Crashing because a provider does not support an optional feature is a design failure.

4. Separate provider fallback from model fallback. Same model on a different provider is a reliability strategy. Different model on the same provider is a capability tradeoff. Both belong in the fallback chain, but they are different decisions with different implications.

5. Design credential resolution as a chain, not a switch. Each provider has 3-5 credential sources. Try them in priority order, use the first success. Never prompt the user for credentials if the environment provides them. Always support credential refresh for long-running sessions.

6. Make provider overrides explicit. A PROVIDER_OVERRIDES map that narrows capabilities per provider is easier to maintain than conditional logic scattered across the codebase. When Bedrock adds adaptive thinking support, you update one map entry, not twenty if statements.

7. Use the same interface for testing and production. A mock provider and a VCR recorder that implement the same ModelProvider interface enable testing the entire agent pipeline without network calls. The test does not know -- and does not need to know -- that it is not talking to a real API.

We examine the registry pattern, the dispatch mechanism, the execution pipeline, and the design patterns that make a tool system extensible without becoming chaotic.
