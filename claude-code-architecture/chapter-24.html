Chapter 24: Subagent Design Philosophy

A single AI agent, no matter how capable, eventually hits a wall. The context window fills up. The task requires expertise the current prompt does not emphasize. A security review and a code refactor need to happen simultaneously. The solution is delegation -- spawning subagents that operate in their own context windows, with their own system prompts, their own tool permissions, and their own constraints.

But delegation is not free. Every subagent costs tokens. Every message passing boundary introduces latency. Every isolated context window means duplicated understanding. The design challenge is not "can we spawn subagents?" but "when should we, and how do we constrain them so they help more than they hurt?"

This chapter lays out the architectural philosophy behind subagent design in AI CLI agents. We will cover the delegation decision framework, the principle of least authority applied to AI agents, a taxonomy of agent types with their tool access levels, model selection strategies, context isolation mechanics, and how to define custom agent types. As we discussed in Chapter 23 (Designing MCP Integrations), external tool surfaces expand the agent's capabilities -- subagents are the architectural mechanism for managing that expanded surface safely.

24.1 When to Delegate vs. When to Do It Yourself

The first design question is not how to delegate, but whether to delegate at all. Every delegation has overhead: the parent agent must formulate a prompt, the subagent must bootstrap its context, results must be passed back, and the parent must interpret them. For simple tasks, this overhead exceeds the cost of just doing the work directly.

The Complexity Threshold

Delegation makes sense when the task crosses one or more of these thresholds:

Threshold Example Why Delegate
Context pollution Security audit generates 2,000 tokens of findings Those findings bloat the parent's context for all subsequent turns
Expertise mismatch Parent is mid-refactor, needs a security opinion The parent's system prompt is optimized for refactoring, not OWASP analysis
Parallelism opportunity Code review AND security review of same PR Two independent analyses that can run concurrently
Tool restriction Read-only codebase exploration A subagent with no write tools cannot accidentally modify files
Blast radius containment Speculative fix that might break things A subagent in a worktree cannot corrupt the main workspace
Turn budget Investigation that might take 30+ tool calls A subagent has its own turn limit, protecting the parent's budget

The anti-patterns are equally important. Do not delegate when:

  • The task is a single tool call (read a file, run a grep). The overhead of spawning a subagent exceeds the cost of just doing it.
  • The result needs to be deeply integrated into the current conversation. Subagent results are injected as a single message -- if the parent needs to iterate on the result, the back-and-forth is expensive.
  • The task requires understanding the full conversation history. Subagents get fresh context windows. They do not see the parent's conversation history unless the parent explicitly includes relevant context in the delegation prompt.

The Decision Tree

The delegation decision follows a structured path:

flowchart TD
    A[New task identified] --> B{Single tool call?}
    B -->|Yes| C[Execute directly]
    B -->|No| D{Independent of current context?}
    D -->|No| E{Would pollute context?}
    D -->|Yes| F{Can parallelize with other tasks?}
    E -->|No| C
    E -->|Yes| G[Delegate to subagent]
    F -->|Yes| H[Delegate to parallel subagents]
    F -->|No| I{Requires restricted tool set?}
    I -->|Yes| G
    I -->|No| J{Exceeds 10 tool calls?}
    J -->|Yes| G
    J -->|No| C

The key insight: delegation is primarily about context management, not capability. A parent agent with all tools could theoretically do everything a subagent does. The value of delegation is keeping the parent's context clean, restricting the blast radius, and enabling parallelism.

24.2 The Principle of Least Authority for AI Agents

In traditional software security, the principle of least privilege states that a process should only have the permissions it needs to accomplish its task. Applied to AI agents, this becomes the principle of least authority: a subagent should only have access to the tools, files, and actions required for its specific mission.

This is not just a security principle -- it is a correctness principle. An agent with access to tools it does not need will occasionally use them. A code-review agent with write access will sometimes "helpfully" fix the issues it finds, corrupting the review's objectivity. A research agent with bash access might try to install packages instead of reporting what it learned. Restricting tools constrains behavior as effectively as system prompt instructions, and more reliably.

Three Layers of Authority Restriction

    style Layer3 fill:#fff3e0,stroke:#FF9800

Layer 1: System Prompt. The subagent's system prompt explicitly states what it can and cannot do. This is a soft constraint -- the model might ignore it -- but it handles 95% of cases. A code-review agent told "You will NOT modify code -- only report findings" almost never attempts writes.

Layer 2: Tool Schema. The subagent only receives tool definitions for the tools it is authorized to use. If the Write tool is not in the schema, the model cannot generate a valid tool-use request for it. This is a hard constraint at the API level -- the model literally does not know the tool exists.

Layer 3: Permission Rules. Even if a tool is in the schema (because the agent type needs limited bash access, for example), the permission system can further restrict what commands are allowed. A security-review agent might have bash access for running grep and find, but the permission rules block destructive commands.

The defense-in-depth approach means that no single layer's failure results in an unauthorized action. If the system prompt fails to constrain behavior, the tool schema catches it. If the tool schema is too permissive, the permission rules enforce boundaries.

Not all subagents are equal. Different tasks require different capability profiles. The agent type taxonomy defines a set of predefined agent configurations, each optimized for a specific class of work.

Detailed Agent Profiles

Each agent type is defined by four dimensions: tools, model, system prompt, and constraints.

general-purpose

The unrestricted agent. Has access to all tools, can perform multi-step tasks, and operates with the same capabilities as the parent agent. Use this when you need a subagent to complete a complex task autonomously -- implementing a feature, fixing a bug end-to-end, or performing a multi-file refactoring.

Dimension Value
Tools All available (Read, Write, Bash, Grep, Glob, Web, Agent)
Model Configurable (defaults to parent's model)
Max turns 30
Context Fresh, isolated
Typical use "Implement the pagination feature in the API module"

The general-purpose agent is the only type that can itself spawn subagents. This enables hierarchical delegation -- a general-purpose agent might spawn an explore agent to investigate the codebase, then a doc-writer agent to document what it built.

explore

The read-only scout. Optimized for fast codebase exploration -- finding files, reading code, answering questions about architecture. Cannot modify anything. This is the most commonly spawned agent type because investigation is the most common subtask.

Dimension Value
Tools Read, Grep, Glob, Bash (read-only commands only)
Model Sonnet or Haiku (speed over depth)
Max turns 15
Context Fresh, isolated
Typical use "Find all files that import the AuthService class"

The "read-only Bash" restriction means the explore agent can run commands like wc -l, find, ls, and cat, but the permission layer blocks any command that writes to the filesystem, starts processes, or modifies state.

plan

The architect. Used for high-level planning that requires understanding the full system but should not touch any code. Given the same read-only tools as explore, but paired with a more capable model (Opus) and a system prompt that emphasizes architectural thinking.

Dimension Value
Tools Read, Grep, Glob
Model Opus (deep reasoning for architecture decisions)
Max turns 20
Context Fresh, isolated
Typical use "Design the migration strategy for moving from REST to GraphQL"

The distinction between explore and plan is model selection and prompt framing. Explore agents are fast and cheap -- they answer factual questions about the codebase. Plan agents are slow and expensive -- they reason about trade-offs, dependencies, and multi-step strategies.

security-reviewer

The auditor with teeth. Has read access plus limited bash for running security scanners, checking file permissions, and inspecting configurations. Paired with Opus because security analysis requires deep reasoning about attack vectors, trust boundaries, and edge cases.

Dimension Value
Tools Read, Grep, Glob, Bash (restricted to analysis commands)
Model Opus (critical analysis requires strongest reasoning)
Max turns 25
Context Fresh, isolated
Typical use "Audit the authentication module for OWASP Top 10 vulnerabilities"

The bash restriction for security-reviewers allows commands like grep -r "password" ., openssl s_client, pip audit, and npm audit, but blocks any command that would modify files or install packages. The security reviewer observes -- it does not remediate.

code-reviewer

The quality inspector. Reads code and reports findings. Explicitly cannot write code -- this prevents the common failure mode where a review agent "helpfully" applies its suggestions, conflating review with implementation.

Dimension Value
Tools Read, Grep, Glob
Model Sonnet (balanced cost/quality for code analysis)
Max turns 15
Context Fresh, isolated
Typical use "Review the changes in this PR for bugs and logic errors"

The code-reviewer's system prompt includes explicit output format instructions: findings must include severity (critical/high/medium/low), file path with line number, description, and suggested fix. This structured output makes it easy for the parent agent to aggregate and present findings.

debugger

The detective. Has full investigative powers -- can read code, run tests, check logs, reproduce issues, and execute diagnostic commands. Paired with Opus because root-cause analysis requires the kind of multi-step reasoning that weaker models often shortcut.

Dimension Value
Tools Read, Grep, Glob, Bash (full access for investigation)
Model Opus (multi-step causal reasoning)
Max turns 30
Context Fresh, isolated
Typical use "Investigate why the payment webhook handler is returning 500 errors"

Debugger agents often consume more turns than other agent types because debugging is inherently iterative: form hypothesis, gather evidence, refine hypothesis, repeat. The 30-turn limit gives them enough room to work while preventing runaway investigations.

researcher

The librarian. Has read access to the codebase plus web search and web fetch for looking up documentation, comparing alternatives, and finding recent information. Cannot modify code or run commands.

Dimension Value
Tools Read, Grep, Glob, WebSearch, WebFetch
Model Sonnet (balanced for synthesis tasks)
Max turns 20
Context Fresh, isolated
Typical use "Research the latest approaches to rate limiting in distributed systems"

The researcher agent is unique in having web access without bash access. This is a deliberate security decision -- web content is untrusted, and an agent that can both fetch web content and execute shell commands creates a prompt injection vector. By separating web access from execution, the researcher can safely consume untrusted content without risking command injection.

doc-writer

The technical writer. Has read access for understanding code plus write access for creating documentation files. Cannot run commands -- documentation should be derivable from reading the code, not from executing it.

Dimension Value
Tools Read, Grep, Glob, Write
Model Sonnet (good prose generation at reasonable cost)
Max turns 20
Context Fresh, isolated
Typical use "Write API documentation for the /users endpoint"

The doc-writer's write access is typically further restricted by permission rules to only allow writing to documentation directories (docs/, *.md files). This prevents a doc-writer from accidentally modifying source code.

plan Yes No No No No Opus 20 Architecture planning
security-reviewer Yes No Analysis No No Opus 25 Security audit

24.4 Model Selection Per Agent Type

Model selection is not a one-size-fits-all decision. Different agent types have different reasoning requirements, latency tolerances, and cost profiles. The selection strategy follows a simple principle: use the strongest model for tasks where errors have the highest consequences, and the fastest model for tasks where speed matters more than depth.

The Model Tiers

graph LR
    subgraph Tier1["Tier 1: Opus — Deep Reasoning"]
        T1A["Security review"]
        T1B["Architecture planning"]
        T1C["Root cause debugging"]
    end

    subgraph Tier2["Tier 2: Sonnet — Balanced"]
        T2A["Code review"]
        T2B["Research synthesis"]
        T2C["Documentation"]
        T2D["General-purpose tasks"]
    end

    subgraph Tier3["Tier 3: Haiku — Speed"]
        T3A["Simple exploration"]
        T3B["File search"]
        T3C["Command execution"]
    end

    style Tier1 fill:#fff3e0,stroke:#FF9800
    style Tier2 fill:#e8f4f8,stroke:#2196F3
    style Tier3 fill:#e8f5e9,stroke:#4CAF50

Opus is reserved for tasks where missing something is costly. A security reviewer that fails to find an SQL injection vulnerability has a real-world impact. A debugger that identifies a red herring instead of the root cause wastes the engineer's time. A plan agent that proposes a flawed architecture creates expensive rework. These tasks justify the higher cost and latency of the strongest model.

Sonnet is the default for balanced tasks. Code review, research, documentation, and general-purpose work all benefit from a capable model but do not require the deepest reasoning. Sonnet provides a good quality-to-cost ratio for these tasks, typically running 3-5x faster than Opus at roughly one-fifth the cost.

Haiku is the speed tier. When the task is simple -- find a file, count lines, check if a function exists -- the quality difference between Haiku and Sonnet is negligible, but the latency difference is significant. Explore agents that answer factual codebase questions are ideal Haiku candidates.

Cost Implications

Model selection directly affects the cost of delegation. Consider a security review that requires 25 turns with an average of 1,500 input tokens and 800 output tokens per turn:

Model Input Cost/1M Output Cost/1M 25-Turn Cost
Opus $15.00 $75.00 $2.06
Sonnet $3.00 $15.00 $0.41
Haiku $0.25 $1.25 $0.03

The difference is 50x between Opus and Haiku. This is why model selection matters -- using Opus for every subagent in a session with 10 delegations could cost $20+, while a mixed strategy that reserves Opus for the two critical tasks and uses Sonnet/Haiku for the rest might cost $3.

Dynamic Model Override

The agent type defines a default model, but the delegation interface should support runtime overrides. When the parent agent determines that a particular code review is unusually complex -- say, reviewing a cryptographic implementation -- it can override the code-reviewer's default Sonnet with Opus for that specific invocation.

Delegation config:
  agent_type: code-reviewer
  model_override: opus        # Override default Sonnet for this task
  prompt: "Review the AES-GCM implementation in crypto/encrypt.ts.
           Pay special attention to IV reuse and padding oracle
           vulnerabilities."

The override mechanism respects a hierarchy: explicit override > agent type default > system default. This gives the parent agent (or the user) fine-grained control without requiring a new agent type for every model variant.

24.5 Context Isolation: Why Subagents Get Fresh Windows

The most important architectural decision in subagent design is context isolation. Every subagent operates in a fresh context window -- it does not share the parent's conversation history, accumulated tool results, or evolving understanding of the task.

This is counterintuitive. Would it not be more efficient to share context so the subagent does not have to re-discover information the parent already knows? In theory, yes. In practice, shared context creates three serious problems.

Problem 1: Context Pollution

The parent agent's context window is a carefully curated conversation. It contains the user's original request, the evolving plan, tool results from investigation, and the agent's own reasoning chain. Injecting a subagent's 25-turn security review directly into this conversation would add thousands of tokens of findings, evidence, and intermediate reasoning that the parent does not need.

Fresh context means the subagent's work stays in the subagent's window. Only the final result -- a structured summary of findings -- flows back to the parent. This keeps the parent's context clean and focused.

Problem 2: Conflicting System Prompts

Different agent types need different system prompts. A code-reviewer needs instructions about output format, severity ratings, and what to ignore. A debugger needs instructions about hypothesis formation and evidence gathering. A researcher needs instructions about source citation and synthesis.

If subagents shared the parent's context, they would inherit the parent's system prompt -- which is optimized for general-purpose work, not for the subagent's specialized role. Fresh context allows each subagent to receive a tailored system prompt without conflicting instructions.

Problem 3: Prompt Injection Blast Radius

Consider a scenario where an explore agent reads a file that contains adversarial content -- a comment designed to manipulate the agent's behavior. In a shared-context model, this injected content would now exist in the parent's conversation and could influence all subsequent actions. In an isolated-context model, the injected content is confined to the subagent's window. When the subagent returns its result, the parent receives a summary, not the raw file content containing the injection.

graph TB
    subgraph SharedContext["Shared Context (Dangerous)"]
        P1["Parent context"] --> S1["Subagent reads<br/>malicious file"]
        S1 --> P1
        P1 --> A1["Injected content now<br/>in parent's context"]
        A1 --> A2["All future actions<br/>potentially influenced"]
    end

    subgraph IsolatedContext["Isolated Context (Safe)"]
        P2["Parent context"] -->|"Task prompt"| S2["Subagent reads<br/>malicious file"]
        S2 -->|"Summary result"| P2
        P2 --> A3["Parent context<br/>uncontaminated"]
    end

    style SharedContext fill:#ffebee,stroke:#E91E63
    style IsolatedContext fill:#e8f5e9,stroke:#4CAF50

Context isolation is the primary defense against lateral prompt injection in multi-agent systems. The subagent might be compromised by malicious content, but its influence is limited to the single result message it returns to the parent. The parent can evaluate that result with its own judgment, potentially catching manipulated outputs.

The Cost of Isolation

The trade-off is real. Context isolation means:

  • Duplicated discovery. The subagent must re-read files the parent already read. If the parent read 5 files during investigation and then delegates to a debugger, the debugger will re-read some of those same files.
  • Lost nuance. The parent may have context from the user's conversation ("the bug started after we upgraded React") that it must explicitly pass to the subagent in the delegation prompt. Implicit context is lost.
  • Higher token cost. Each subagent starts from zero, paying for its own context window.

The architecture accepts these costs because the benefits -- clean context, tailored prompts, injection containment -- are worth more in production than the efficiency gains of sharing.

24.6 The Delegation Decision Framework

When the parent agent encounters a task that crosses the complexity threshold, it needs a systematic way to choose the right agent type. The delegation decision framework combines the task characteristics with the agent taxonomy to select the optimal configuration.

Decision Dimensions

  1. Task nature: Investigation, analysis, creation, or execution?
  2. Tool requirements: Which tools does the task need?
  3. Quality requirements: How costly is an error?
  4. Latency requirements: How fast does the user need results?
  5. Parallelism: Can this run alongside other tasks?

The Routing Table

Task Nature Needs Write? Needs Bash? Needs Web? Error Cost Agent Type
Find code/patterns No Maybe No Low explore
Architecture analysis No No No High plan
Security review No Yes (analysis) No Very High security-reviewer
Code quality review No No No Medium code-reviewer
Bug investigation No Yes No High debugger
Topic research No No Yes Medium researcher
Write documentation Yes (docs only) No No Low doc-writer
Implement feature Yes Yes Maybe Medium general-purpose
Fix bug end-to-end Yes Yes No Medium general-purpose

Parallel Delegation Opportunities

Certain task combinations are natural candidates for parallel execution. The parent identifies these opportunities and dispatches multiple subagents simultaneously:

Scenario Parallel Agents Sync Point
PR review code-reviewer + security-reviewer Both results before presenting
Feature implementation explore (investigate) + plan (design) Both results before coding
Bug triage debugger (reproduce) + explore (find related) Merge findings
Documentation update explore (map changes) + doc-writer (draft) Sequential -- explore first

The last row illustrates an important distinction: some "parallel" tasks actually have dependencies. The doc-writer needs the explore agent's findings before it can write accurate documentation. The framework must distinguish between truly independent tasks (fan-out) and dependent tasks (pipeline). We will explore these orchestration patterns in detail in Chapter 25.

24.7 Custom Agent Definitions

The predefined agent types cover common patterns, but production systems need extensibility. Custom agent definitions allow teams to create new agent types tailored to their specific workflows -- a database-migration agent, a test-generator agent, a compliance-checker agent.

The Agent Definition Format

Custom agents are defined in markdown files with YAML frontmatter. This format is human-readable, version-controllable, and requires no build step. The agent definition file specifies the four dimensions of an agent type:

---
name: database-reviewer
description: >
  Reviews database migrations and schema changes for correctness,
  performance impact, and backward compatibility. Use when user asks
  about migrations, schema reviews, or database changes.
tools:
  - Read
  - Grep
  - Glob
  - Bash
model: opus
effort: high
memory: project
maxTurns: 25
---

You are a database review specialist. When analyzing migrations:

1. Check for irreversible operations (DROP COLUMN, DROP TABLE)
2. Verify indexes support expected query patterns
3. Check for lock contention on large tables
4. Validate data type changes are backward-compatible
5. Ensure rollback migrations exist and are correct

Report findings as:
**[SEVERITY]** migration_file:line — Description

Severity levels:
- CRITICAL: Data loss, extended downtime, irreversible without backup
- HIGH: Performance degradation, lock contention on production tables
- MEDIUM: Missing indexes, suboptimal data types
- LOW: Naming conventions, documentation

How Custom Agents Load

The discovery mechanism scans a well-known directory for agent definition files:

.claude/agents/
├── security-reviewer.md      # Built-in, can be overridden
├── code-reviewer.md          # Built-in, can be overridden
├── debugger.md               # Built-in, can be overridden
├── researcher.md             # Built-in, can be overridden
├── doc-writer.md             # Built-in, can be overridden
├── database-reviewer.md      # Custom agent
├── test-generator.md         # Custom agent
└── compliance-checker.md     # Custom agent

At startup, the agent loader reads all .md files in this directory, parses the YAML frontmatter, validates the configuration (are the tools valid? is the model valid? is maxTurns within bounds?), and registers each agent type with the system prompt registry. Custom agents override built-in agents if they share the same name -- this allows teams to customize the default security-reviewer's behavior without modifying the system.

Agent Description and Auto-Selection

The description field in the frontmatter serves a dual purpose. It documents what the agent does for humans, and it tells the parent agent when to select this agent type. When the parent encounters a task, it evaluates the task description against each agent's description to find the best match.

This is why the description field matters. A vague description like "Reviews database stuff" will match unreliably. A specific description with trigger phrases -- "Reviews database migrations and schema changes for correctness, performance impact, and backward compatibility. Use when user asks about migrations, schema reviews, or database changes" -- gives the parent agent clear signal about when to delegate to this type.

Validation Rules

Custom agent definitions must pass validation before registration:

Field Constraint
name Unique, alphanumeric + hyphens, max 50 chars
tools Must be subset of available tools
model Must be a recognized model identifier
maxTurns 1-100, defaults to 20
effort low, medium, high, or max
memory user, project, or local

Invalid definitions produce warnings at startup rather than errors -- a malformed custom agent should not prevent the system from starting.

24.8 Subagent Context Stripping

A critical optimization in the subagent architecture is what the subagent does NOT receive. The parent agent's context is rich -- it includes project instructions from CLAUDE.md, memory entries, git state, active files, and accumulated skill prompts. Subagents skip most of this.

What Subagents Skip

Context Component Included? Rationale
CLAUDE.md instructions No Parent already applied these when formulating the task
Memory entries No Subagent operates on specific task, not project-wide knowledge
Git context Minimal Branch name only, not full status
Active files No Subagent reads what it needs
Skill prompts No Skills are invoked by the user, not by subagents
Environment info Yes Needed for bash commands, path resolution
Working directory Yes Needed for file operations
Agent system prompt Yes The agent type's specialized instructions

This stripping saves 500-2,000 tokens per subagent invocation. Over a session with 10 delegations, that is 5,000-20,000 tokens saved -- a meaningful reduction in both cost and latency.

The design rationale is that the parent agent acts as a filter. It reads CLAUDE.md, applies project rules, understands the user's preferences, and then translates all of that into a specific, well-scoped task description for the subagent. The subagent does not need to re-derive the project context from raw instructions -- it receives the already-digested version in the delegation prompt.

24.9 The Subagent Lifecycle

Every subagent follows a predictable lifecycle from creation to result delivery.

sequenceDiagram
    participant P as Parent Agent
    participant D as Dispatch Layer
    participant S as Subagent
    participant API as LLM API

    P->>D: Delegate(type, prompt, config)
    D->>D: Resolve agent type
    D->>D: Build system prompt
    D->>D: Filter tool schema
    D->>S: Create subagent context

    loop Agent Loop (up to maxTurns)
        S->>API: API call with subagent prompt
        API-->>S: Response (text/tool-use)
        alt Tool use requested
            S->>S: Execute tool
            S->>S: Append result
        else End turn
            S->>S: Check completion
        end
    end

    S-->>D: Final result message
    D-->>P: Inject result into parent context

Phase 1: Dispatch

The parent agent calls the delegation interface with three parameters: agent type, task prompt, and optional configuration overrides. The dispatch layer resolves the agent type to its configuration, builds the appropriate system prompt, and filters the tool schema to include only authorized tools.

Phase 2: Execution

The subagent runs its own agentic loop -- the same prompt-think-act-observe cycle we covered in Chapter 7, but with its own context window. Each turn, the subagent decides whether to use a tool or produce a final response. The loop continues until the subagent produces a non-tool response, hits the turn limit, or encounters a fatal error.

Phase 3: Result Delivery

The subagent's final response is extracted and passed back to the parent agent. The parent receives this as a single message in its own conversation -- it does not see the subagent's intermediate reasoning, tool calls, or errors. This is by design: the parent cares about the answer, not the process.

24.10 Design Patterns and Anti-Patterns

Pattern: The Specialist Team

When reviewing a PR, spawn a code-reviewer and a security-reviewer in parallel. Each operates in its own context with its own system prompt. The parent collects both results and synthesizes a unified review.

Why it works: Each specialist focuses on its domain without being distracted by the other's concerns. The parallel execution cuts wall-clock time roughly in half.

Pattern: The Investigation Cascade

For complex bugs, spawn an explore agent first to gather information, then pass the findings to a debugger agent for root cause analysis.

Why it works: The explore agent is cheap (Haiku/Sonnet, read-only) and fast. It gathers the raw data. The debugger agent is expensive (Opus, full bash access) but starts with already-collected evidence instead of spending its early turns reading files.

Anti-Pattern: The Overpowered Agent

Spawning a general-purpose agent for every delegation because "it can do everything."

Why it fails: The general-purpose agent has no constraints. It will follow whatever path seems most interesting, which may not be the most useful. It might start fixing bugs during a review, or refactoring code during an investigation. Constrained agents produce more focused results.

Anti-Pattern: The Chatty Delegation

Including the entire conversation history in the delegation prompt because "the subagent needs context."

Why it fails: Most of the conversation history is irrelevant to the specific subtask. Including it wastes tokens, dilutes the task description, and may cause the subagent to pursue tangents mentioned earlier in the conversation. The delegation prompt should contain exactly the context the subagent needs -- no more.

Anti-Pattern: Recursive Delegation Without Limits

A general-purpose subagent spawning its own subagents, which spawn their own subagents.

Why it fails: Each level of recursion multiplies cost and latency. A three-level delegation tree with 3 agents per level creates 13 agents (1 + 3 + 9). Without depth limits, the system can spiral into an exponential cost explosion. The architecture should enforce a maximum delegation depth, typically 2-3 levels.

24.11 Key Takeaways

  1. Delegate for context management, not just capability. The primary value of subagents is keeping the parent's context clean, not accessing tools the parent lacks.

  2. Apply least authority aggressively. Three layers -- system prompt, tool schema, permission rules -- provide defense-in-depth. A code-reviewer with no write tools is more trustworthy than one told "please don't write."

  3. Match the model to the stakes. Opus for security, debugging, and planning where errors are costly. Sonnet for balanced work. Haiku for simple exploration where speed matters.

  4. Isolate contexts to contain damage. Fresh context windows prevent context pollution, enable specialized system prompts, and limit prompt injection blast radius. The token cost of isolation is worth the safety and clarity it provides.

  5. Define agent types as data, not code. Markdown files with YAML frontmatter make agent types versionable, shareable, and customizable without code changes.

  6. Strip subagent context aggressively. Subagents do not need CLAUDE.md, memory, or skill prompts. The parent digests project context and passes only what the subagent needs in the task prompt.

  7. Enforce delegation depth limits. Recursive delegation without bounds leads to exponential cost. Cap the depth and log when limits are hit.

  8. Use the delegation decision tree before spawning. Not every multi-step task needs a subagent. Single tool calls, tasks that need deep conversation context, and simple operations are cheaper to do directly.

In the next chapter, we will explore how these subagents communicate with their parents and with each other -- the message passing, result aggregation, and orchestration patterns that turn a collection of independent agents into a coordinated system.
