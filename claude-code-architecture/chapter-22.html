Chapter 22: MCP Server Lifecycle

Chapter 21 covered the MCP protocol itself -- the wire format, transport layers, and capability negotiation that enable AI agents to communicate with external servers. But a protocol specification tells you what messages look like. It does not tell you how to find servers, start them, keep them alive, recover when they crash, or clean them up when the session ends. That is lifecycle management, and it is where most of the operational complexity lives.

A production AI agent may connect to five or ten MCP servers simultaneously: a memory server, a database connector, an API gateway, a file system extension, a CI/CD bridge. Each server has its own startup sequence, its own failure modes, its own reconnection semantics. The lifecycle manager must handle all of them uniformly while gracefully degrading when any one of them fails. An MCP server going down should never take the agent down with it.

This chapter covers the full operational lifecycle: how servers are discovered from multiple configuration sources, how connections are established and maintained, how failures are detected and recovered, and how resources are cleaned up on disconnect.

22.1 Server Discovery

Before connecting to an MCP server, the agent must know it exists. Server definitions come from four sources, arranged in a precedence hierarchy:

The Four Discovery Sources

graph TD
    A[Enterprise Policy<br/>Managed Settings] --> E[Merged Configuration]
    B[User Settings<br/>~/.claude/settings.json] --> E
    C[Project Config<br/>.mcp.json] --> E
    D[Environment Variable<br/>MCP_SERVERS] --> E
    E --> F[MCP Connection Manager]

    style A fill:#742a2a,color:#fff
    style B fill:#2b6cb0,color:#fff
    style C fill:#276749,color:#fff
    style D fill:#744210,color:#fff
    style E fill:#4a5568,color:#fff
    style F fill:#2d3748,color:#fff

1. Project configuration (.mcp.json). The highest-priority, most common source. A JSON file in the project root that declares MCP servers needed for this specific codebase:

{
  "mcpServers": {
    "copilot-mem": {
      "command": "npx",
      "args": ["-y", "@anthropic/copilot-mem-server"],
      "env": {
        "MEM_DB_PATH": "/Users/dev/.copilot_home/memory.db"
      }
    },
    "postgres": {
      "command": "mcp-postgres",
      "args": ["--host", "localhost", "--port", "5432"],
      "env": {
        "PGPASSWORD": "${DB_PASSWORD}"
      }
    }
  }
}

Project configs are checked into version control (minus any credential references). When a teammate clones the repo, they get the same MCP server definitions. This is the primary mechanism for project-specific tooling.

2. User settings (~/.claude/settings.json). MCP servers that a user wants available across all projects. A memory server is the canonical example -- you want persistent knowledge regardless of which project you are working in:

{
  "mcpServers": {
    "global-memory": {
      "command": "npx",
      "args": ["-y", "copilot-mem-server"],
      "env": {}
    }
  }
}

User settings have lower precedence than project config. If both define a server with the same name, the project config wins. This lets projects override user defaults when needed.

3. Enterprise policy (managed settings). In enterprise deployments, IT administrators can define MCP servers that must be available (or must be blocked) across the organization. Managed settings can enforce:

  • Required servers that every user must connect to (audit logging, compliance tools)
  • Blocked servers that no user may connect to (unapproved third-party tools)
  • Pinned versions for approved servers

Managed settings have the highest enforcement priority for blocking, but the lowest for addition -- they add servers to the pool, and project/user configs can override their parameters.

4. Environment variables (MCP_SERVERS). An escape hatch for CI/CD pipelines and containerized environments where file-based configuration is impractical. The variable contains a JSON string with the same format as .mcp.json:

export MCP_SERVERS='{"ci-tools":{"command":"mcp-ci","args":["--mode","headless"]}}'

Environment variable definitions have the lowest precedence -- they are overridden by all file-based sources.

Configuration Merge Semantics

When the same server name appears in multiple sources, the merge follows these rules:

Conflict Resolution
Same name, different command Project config wins
Same name, different args Project config wins
Same name, different env Deep merge (project overrides per-key)
Server in project + blocked by policy Policy wins (server is blocked)
Server in user settings, not in project Server is available
Server in env var, also in project Project config wins

The deep merge for environment variables is important. A user setting might define MEM_DB_PATH, while the project config adds MEM_LOG_LEVEL. Both should be present when the server starts.

Validation at Discovery Time

Each server definition is validated before any connection attempt:

  1. Command exists. The specified command (e.g., npx, mcp-postgres) must be resolvable in PATH. If not, the server is marked as "unavailable" with a clear error message.
  2. URL is well-formed (for HTTP-based servers). The URL must parse correctly and use HTTPS in production.
  3. Environment variables resolve. References like ${DB_PASSWORD} must resolve to non-empty values. Missing variables produce a warning, not an error -- the server might still function without them.
  4. No circular dependencies. While rare, it is theoretically possible for MCP server A to depend on MCP server B and vice versa. The discovery system detects and rejects circular definitions.

22.2 Connection Management

Once a server definition is validated, the connection manager establishes a connection through a multi-step process.

Connection Establishment for stdio Servers

sequenceDiagram
    participant CM as Connection Manager
    participant OS as Operating System
    participant SP as Server Process

    CM->>OS: spawn(command, args, env)
    OS->>SP: Start process
    OS->>CM: Process handle (PID, stdin, stdout, stderr)

    CM->>SP: stdin: initialize(clientInfo, capabilities)

    alt Success
        SP->>CM: stdout: result(serverInfo, capabilities)
        CM->>SP: stdin: notifications/initialized
        CM->>CM: State -> Ready
    else Timeout (30s)
        CM->>CM: State -> Error("Initialize timeout")
        CM->>OS: kill(PID)
    else Parse Error
        CM->>CM: State -> Error("Invalid response")
        CM->>OS: kill(PID)
    end

The 30-second initialization timeout is generous because some MCP servers do substantial work at startup -- loading databases, compiling schemas, downloading dependencies (when invoked via npx). A server that does not respond to initialize within 30 seconds is almost certainly hung or misconfigured.

Connection Establishment for HTTP Servers

HTTP-based connections follow the same protocol handshake but with different transport mechanics:

  1. DNS resolution and TLS handshake. For remote servers, the connection manager resolves the hostname, establishes a TLS connection, and verifies the certificate chain.
  2. Authentication. If the server requires authentication, the client includes credentials in the HTTP headers (Bearer token, OAuth2 access token, or custom auth scheme).
  3. Initialize request. Sent as an HTTP POST to the server's MCP endpoint.
  4. SSE channel (if using SSE transport). The client opens a persistent SSE connection for server-to-client messages.

Health Monitoring

After establishing a connection, the lifecycle manager monitors server health through two mechanisms:

Periodic pings. The client sends a ping request every 30 seconds. The server must respond with a pong result. If three consecutive pings go unanswered (90 seconds of silence), the server is considered unresponsive and the connection enters the error state.

// Client -> Server
{"jsonrpc": "2.0", "id": "ping-1", "method": "ping"}

// Server -> Client
{"jsonrpc": "2.0", "id": "ping-1", "result": {}}

Process monitoring (stdio only). The connection manager monitors the server process for unexpected termination. If the process exits with a non-zero exit code, the connection immediately enters the error state with the exit code as context.

    A -->|"Process exit"| C[Terminated]
    A -->|"Parse error"| D[Protocol Error]
    B -->|"Ping response"| A
    B -->|"Timeout"| E[Disconnected]
    C --> E
    D --> E
    E -->|"Reconnect"| F[Connecting]

The health monitoring overhead is minimal -- one small JSON round-trip every 30 seconds per server. For an agent connected to five MCP servers, that is 10 messages per minute total. The latency of health checks (typically <5ms for stdio, <50ms for HTTP) is negligible compared to the seconds-long LLM inference cycles.

22.3 The Connection State Machine

Every MCP connection is modeled as a finite state machine with six states. This state machine is the core abstraction that the rest of the lifecycle manager operates on.

stateDiagram-v2
    [*] --> Disconnected
    Disconnected --> Connecting: connect()
    Connecting --> Negotiating: transport established
    Connecting --> Error: transport failure
    Negotiating --> Ready: initialize handshake complete
    Negotiating --> Error: handshake failure / timeout
    Ready --> Error: health check failure / process exit
    Ready --> Disconnecting: disconnect()
    Error --> Connecting: reconnect (after backoff)
    Error --> Disconnected: max retries exceeded
    Disconnecting --> Disconnected: cleanup complete

State Definitions

State Meaning Tool Calls Accepted?
Disconnected No connection exists. Initial and terminal state. No
Connecting Transport is being established (process spawning, TCP handshake). No
Negotiating Transport is up, initialize handshake in progress. No
Ready Fully operational. Tools, resources, and prompts are available. Yes
Error Connection failed or server became unresponsive. May reconnect. No (queued for retry)
Disconnecting Graceful shutdown in progress. Waiting for cleanup. No (rejected immediately)

The key invariant: tool calls are only accepted in the Ready state. If a tool call arrives while the connection is in any other state, the behavior depends on the state:

  • Connecting / Negotiating: Queue the call. It will execute when the connection reaches Ready.
  • Error: Queue the call. It will execute if reconnection succeeds, or fail if max retries are exceeded.
  • Disconnecting / Disconnected: Reject immediately with an error.

Queuing during transient states provides a better user experience than immediate rejection. If the user invokes a memory tool while the memory server is reconnecting (a ~1-2 second window), the call should wait for reconnection rather than failing.

State Transition Events

Each transition is triggered by a specific event:

Disconnected -> Connecting:     Agent session starts, or manual reconnect
Connecting -> Negotiating:      Process spawned / TCP connected successfully
Connecting -> Error:            Process spawn failed, TCP connect refused
Negotiating -> Ready:           initialize response received, capabilities parsed
Negotiating -> Error:           Initialize timeout (30s), malformed response
Ready -> Error:                 3 missed pings, process exit, protocol error
Ready -> Disconnecting:         Agent session ends, user removes server
Error -> Connecting:            Reconnection timer fires (exponential backoff)
Error -> Disconnected:          Max reconnection attempts exhausted (default: 10)
Disconnecting -> Disconnected:  Cleanup complete (process terminated, resources freed)

22.4 Reconnection Strategy

Server failures are inevitable. The MCP server might crash due to a bug, the operating system might kill it for consuming too much memory, or a network partition might sever the HTTP connection. The reconnection strategy determines how quickly and reliably the agent recovers.

Exponential Backoff with Jitter

The reconnection timer uses exponential backoff with randomized jitter to prevent thundering-herd problems (multiple agents reconnecting to a shared server simultaneously):

Attempt 1:  base_delay * 2^0 + jitter  =  1s   + rand(0, 500ms)
Attempt 2:  base_delay * 2^1 + jitter  =  2s   + rand(0, 500ms)
Attempt 3:  base_delay * 2^2 + jitter  =  4s   + rand(0, 500ms)
Attempt 4:  base_delay * 2^3 + jitter  =  8s   + rand(0, 500ms)
Attempt 5:  base_delay * 2^4 + jitter  =  16s  + rand(0, 500ms)
Attempt 6+: capped at max_delay        =  30s  + rand(0, 500ms)
Parameter Default Rationale
Base delay 1 second Short enough for quick recovery from transient failures
Max delay 30 seconds Long enough to avoid hammering a struggling server
Max attempts 10 ~3 minutes of total retry time before giving up
Jitter range 0-500ms Decorrelates concurrent reconnection attempts

State Recovery After Reconnection

When a reconnection succeeds, the client must re-establish the session state. This involves:

  1. Re-initialize. The full handshake runs again. The server may have restarted with different capabilities -- perhaps a newer version was deployed during the outage.
  2. Re-fetch tool list. Tools may have changed. The client must update its tool registry.
  3. Drain queued calls. Any tool calls that were queued during the error state are now executed in order.
  4. Notify the agent. The agent's tool registry is updated with the refreshed tool list. If tools were removed (the server dropped a capability), pending tool calls for those tools are rejected.
sequenceDiagram
    participant Agent as Agent
    participant CM as Connection Manager
    participant Server as MCP Server (restarted)

    Note over CM: Error state, attempt reconnection
    CM->>Server: Spawn new process
    CM->>Server: initialize(...)
    Server->>CM: result(capabilities)
    CM->>Server: notifications/initialized

    CM->>Server: tools/list
    Server->>CM: result([tool1, tool2])

    CM->>Agent: Update tool registry

    Note over CM: Drain queued calls
    CM->>Server: tools/call(queued_call_1)
    Server->>CM: result(...)
    CM->>Agent: Deliver queued result 1

What Cannot Be Recovered

Reconnection restores the connection, not the server's internal state. If the MCP server maintained in-memory state (caches, session data, intermediate computation results) before crashing, that state is lost. The agent must not assume state continuity across reconnections.

This has architectural implications for MCP server design: servers that need state across restarts should persist it to disk or a database, not rely on in-memory storage. The protocol makes no guarantees about server-side state preservation.

22.5 Graceful Degradation

When an MCP server becomes unavailable, the agent must continue operating with reduced capability rather than failing entirely. Graceful degradation is the set of behaviors that ensure one server's failure does not cascade into a session-wide outage.

Tool Call Failure Handling

When a tool call targets an unavailable MCP server, the flow is:

flowchart TD
    A[LLM requests tool call] --> B{Server in Ready state?}
    B -->|Yes| C[Execute tool call normally]
    B -->|No| D{Server reconnecting?}
    D -->|Yes| E[Queue call, wait up to 10s]
    D -->|No, permanently down| F[Return graceful error to LLM]
    E --> G{Reconnected in time?}
    G -->|Yes| C
    G -->|No| F
    F --> H[LLM sees error, adapts strategy]
    H --> I[Agent continues with other tools]

    style C fill:#276749,color:#fff
    style F fill:#c05621,color:#fff
    style I fill:#2b6cb0,color:#fff

The error returned to the LLM is informative but not technical:

Tool 'search_memory' is currently unavailable (memory server disconnected). 
You can continue without memory context, or suggest the user restart the 
memory server.

This message is crafted for the LLM, not the user. It tells the model what happened and what its options are. The LLM can then either work around the missing tool (proceeding without memory context) or inform the user that the memory server needs attention.

Partial Capability Operation

When running with multiple MCP servers, the agent maintains a capability matrix:

Server          Status      Tools Available
-----------     --------    ----------------------------------
copilot-mem     Ready       search_memory, save_fact, ...
postgres        Error       (none - reconnecting)
github          Ready       create_issue, list_prs, ...

The tool registry dynamically reflects which tools are currently available. Tools from disconnected servers are removed from the LLM's tool list (or marked as unavailable in tool descriptions). This prevents the LLM from repeatedly attempting calls to a dead server.

When the server reconnects, its tools are re-added to the registry. The LLM automatically regains access to those tools on the next conversation turn, because the system prompt's tool list is regenerated on each turn.

Degradation Hierarchy

Not all MCP servers are equally critical. The degradation hierarchy defines the agent's behavior based on which servers are down:

Server Category Example Agent Behavior When Down
Enhancement Memory, analytics Continue normally, note reduced recall
Functional Database, API gateway Continue with warning, some tasks impossible
Critical Auth provider (if required) Warn user, some operations blocked

The categorization is implicit -- the agent does not have explicit "critical" flags on servers. Instead, the criticality emerges from the tools: if the only tool that can read the database is on a dead server, database queries are impossible. The LLM reasons about this naturally when it sees the tool error.

22.6 Resource Management

MCP servers consume system resources: operating system processes, file descriptors, memory, network connections. The lifecycle manager is responsible for cleaning these up, both during normal operation and during abnormal termination.

Process Cleanup on Disconnect

For stdio-based servers, disconnect involves terminating the server process:

1. Close stdin pipe          (signals the server to shut down gracefully)
2. Wait 5 seconds            (grace period for cleanup)
3. Send SIGTERM              (polite termination request)
4. Wait 3 seconds            (grace period for signal handling)
5. Send SIGKILL              (forced termination if still alive)
6. Collect exit status       (prevent zombie processes)
7. Close stdout/stderr pipes (release file descriptors)

The graduated approach (close stdin, then SIGTERM, then SIGKILL) gives well-behaved servers a chance to flush buffers, close database connections, and release locks. Misbehaving servers that ignore signals are eventually force-killed.

Orphan Prevention

A critical concern: what happens if the agent process crashes without going through graceful shutdown? The MCP server processes become orphans -- running processes with no parent to manage them.

Three mechanisms prevent orphan accumulation:

Process group management. The agent spawns MCP servers in the same process group. When the agent terminates (even abnormally), the operating system can kill the entire process group.

PID file tracking. The agent writes the PIDs of all spawned MCP server processes to a file (e.g., ~/.claude/mcp-pids.json). On next startup, the agent checks this file and terminates any orphaned processes from previous sessions.

Server-side timeout. Well-designed MCP servers detect when their parent process has died (stdin is closed, no pings arrive) and self-terminate after a timeout. This is a defense-in-depth measure that works even if the agent's cleanup mechanisms fail.

flowchart TD
    A[Agent starts] --> B{PID file exists?}
    B -->|Yes| C[Read PID file]
    C --> D{Any PIDs still running?}
    D -->|Yes| E[Terminate orphans]
    D -->|No| F[Continue startup]
    E --> F
    B -->|No| F
    F --> G[Start MCP servers]
    G --> H[Write PIDs to PID file]

    style E fill:#c53030,color:#fff
    style F fill:#276749,color:#fff

File Descriptor Management

Each stdio MCP server consumes three file descriptors: stdin, stdout, stderr. With five concurrent MCP servers, that is 15 file descriptors. On systems with low file descriptor limits (some Linux distributions default to 1024), this can become a constraint when combined with the agent's own file operations, network connections, and subagent processes.

The lifecycle manager tracks file descriptor usage and warns when approaching the system limit. In extreme cases, it can refuse to start additional MCP servers to protect the agent's core operations.

22.7 Hot Reload

Users should be able to add or remove MCP servers without restarting the agent. Hot reload enables this by watching configuration files for changes and dynamically updating the connection pool.

The Hot Reload Flow

sequenceDiagram
    participant User as User
    participant Agent as Agent
    participant CM as Connection Manager
    participant New as New MCP Server

    User->>User: Edit .mcp.json (add new server)
    Agent->>Agent: File watcher detects change
    Agent->>CM: Reload configuration
    CM->>CM: Diff old config vs new config

    Note over CM: New server detected
    CM->>New: Spawn process
    CM->>New: initialize(...)
    New->>CM: result(capabilities)
    CM->>New: notifications/initialized
    CM->>Agent: Register new tools

    Agent->>Agent: Next LLM turn sees new tools

Configuration Diffing

The reload process computes a diff between the old and new configurations:

Change Type Action
New server added Connect to new server, register its tools
Existing server removed Disconnect from server, unregister its tools
Server config changed (same name) Disconnect old, connect new (full restart)
Server config unchanged No action

Server config changes (e.g., changing arguments or environment variables) require a full reconnect because there is no protocol mechanism to update a running server's configuration. The server must be stopped and restarted with the new parameters.

Tool Registry Consistency

During hot reload, there is a brief window where the tool registry is inconsistent -- the old server's tools have been removed but the new server's tools have not yet been registered. If the LLM attempts a tool call during this window, the call fails.

The mitigation is to overlap: register the new server's tools before unregistering the old server's tools. For servers being restarted (config change), this means connecting to the new instance before disconnecting the old one:

1. Start new server process
2. Complete initialization handshake
3. Fetch new tool list
4. Register new tools in registry
5. Disconnect old server
6. Unregister old tools (if names differ)

If the new and old servers provide the same tool names (which they should, since the server name is unchanged), step 6 is a no-op -- the new registration simply overwrites the old one.

22.8 Authentication for Remote MCP Servers

Local MCP servers (stdio) inherit authentication from process ownership -- if the agent can spawn the process, it can communicate with it. Remote MCP servers over HTTP require explicit authentication.

OAuth 2.0 Flow

MCP supports OAuth 2.0 for remote server authentication. The flow integrates with the agent's existing auth infrastructure:

sequenceDiagram
    participant User as User
    participant Agent as Agent
    participant Auth as Auth Server
    participant MCP as Remote MCP Server

    Agent->>MCP: initialize (no token)
    MCP->>Agent: 401 Unauthorized (auth URL)

    Agent->>User: "MCP server requires auth. Opening browser..."
    Agent->>Auth: Redirect to authorization endpoint
    User->>Auth: Login + consent
    Auth->>Agent: Authorization code (via callback)
    Agent->>Auth: Exchange code for tokens
    Auth->>Agent: Access token + refresh token

    Agent->>MCP: initialize (with Bearer token)
    MCP->>Agent: result(capabilities)

    Note over Agent,MCP: Token refresh loop
    Agent->>Agent: Token expires in 5 min
    Agent->>Auth: Refresh token exchange
    Auth->>Agent: New access token

Token Management

The agent manages three token lifecycle concerns:

Storage. Access tokens and refresh tokens are stored in the OS keychain (macOS Keychain, Linux Secret Service, Windows Credential Manager) -- never in plain-text configuration files. The agent's credential store maps (server_url, user_id) to (access_token, refresh_token, expiry).

Refresh. Before a token expires, the agent proactively refreshes it. The refresh happens in the background, 5 minutes before expiry, so that tool calls never fail due to an expired token.

Revocation. When a user disconnects from a remote MCP server (removes it from configuration), the agent revokes the tokens if the auth server supports revocation. This prevents stale tokens from lingering in the credential store.

API Key Authentication

For simpler remote servers that use API keys instead of OAuth, the key is provided through environment variables in the server configuration:

{
  "remote-api": {
    "url": "https://mcp.example.com/v1",
    "headers": {
      "Authorization": "Bearer ${MCP_API_KEY}"
    }
  }
}

The ${MCP_API_KEY} reference is resolved from the user's environment at connection time. The key never appears in the configuration file, logs, or protocol messages.

22.9 Monitoring and Observability

In production deployments, operators need visibility into MCP server health, performance, and resource consumption.

Diagnostic Commands

The agent provides diagnostic commands for MCP troubleshooting:

/mcp status              Show all servers: name, state, tool count, uptime
/mcp restart <name>      Restart a specific server
/mcp logs <name>         Show recent stderr output from a server
/mcp ping <name>         Manual ping to check server responsiveness

These commands are essential for debugging. When a user reports "the memory tool stopped working," the first step is /mcp status to see if the memory server is in an error state.

Design Principles

Several principles run through the lifecycle architecture:

Fail open, not closed. When an MCP server fails, the agent continues operating. It loses some capabilities but does not stop. This is the opposite of fail-closed (where any failure halts the system). For an interactive tool that engineers use all day, fail-open is the correct default -- losing memory search is annoying; losing the entire session is unacceptable.

Separate server lifecycles from session lifecycles. MCP servers can come and go without restarting the agent session. Hot reload, reconnection, and graceful degradation all serve this principle. The user's conversation, context, and work-in-progress are never disrupted by MCP server lifecycle events.

Monitor everything, expose diagnostics. Every state transition, every health check, every reconnection attempt is logged and metered. When something goes wrong (and it will), the diagnostic data is already there. Retroactive debugging of production issues is orders of magnitude harder without observability.

Defense in depth for cleanup. Orphan prevention uses three independent mechanisms (process groups, PID files, server-side timeouts). Any one of them can fail, and the system still cleans up. This is not over-engineering -- orphaned processes consuming memory and CPU are a real operational problem that accumulates over time.

Graceful shutdown is as important as startup. A clean shutdown -- draining in-flight tool calls, closing connections, terminating processes, collecting exit statuses -- prevents resource leaks and ensures the next startup is clean. Too many systems invest heavily in startup and treat shutdown as an afterthought.
