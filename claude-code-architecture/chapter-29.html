Chapter 29: Hook Architecture

Every production AI agent needs guardrails. The LLM generates tool calls, the tool system executes them, but between intention and action there must be a point where external logic can observe, gate, or modify what happens. This is the hook system: an event-driven architecture that lets shell scripts, HTTP endpoints, prompts, and callback functions participate in every phase of the agent's lifecycle.

This chapter examines how to design a hook system for an AI CLI agent. We will cover the event taxonomy (27 lifecycle events organized into 10 categories), the five hook types, the execution model that determines when hooks block and when they run asynchronously, the exit code protocol that keeps the hook interface simple enough for a bash one-liner yet powerful enough for enterprise policy enforcement, and the advanced capabilities that transform hooks from passive observers into active participants in the agent's execution flow.

The hook system in a production agent like Claude Code spans approximately 3,000 lines of core implementation. It is not a large system. Its power comes not from complexity but from three design decisions: hooks are subprocess-isolated (they cannot crash the agent), hook output is structured JSON (enabling rich communication), and hooks compose through a priority-ordered pipeline (enabling layered policy). Understanding these decisions is the foundation for building your own hook architecture.

29.1 Why Hooks?

Before examining the architecture, consider the problem hooks solve. An AI agent executes tool calls generated by an LLM. The LLM is probabilistic -- it sometimes generates dangerous commands (rm -rf /), sometimes exposes secrets in committed files, sometimes calls tools that violate organizational policy. The agent needs a mechanism to:

  1. Block dangerous actions before they execute
  2. Modify tool arguments to enforce policy (add --dry-run, redirect paths)
  3. Log every action for audit trails
  4. Notify humans when interesting things happen
  5. Inject context that the LLM would not otherwise have
  6. React to external events (file changes, CI results)

You could hardcode these behaviors. But hardcoding means every new policy requires a code change, a release, and a deployment. Hooks externalize these behaviors into user-authored scripts that the agent executes at defined lifecycle points. The organization adds a "no force push" policy by dropping a shell script into a hooks directory, not by forking the agent.

Hooks vs. Middleware vs. Plugins

Three architectures compete for this role:

Architecture Execution Model Isolation Language Flexibility
Middleware In-process chain, function calls None (shared memory) Single language (agent's language)
Plugins In-process modules, API callbacks Partial (module boundary) Limited (FFI or shared runtime)
Hooks Subprocess, stdin/stdout/exit code Full (process boundary) Any language

Middleware is fastest but couples hooks to the agent's language and runtime. A crash in a middleware function crashes the agent. Plugins offer more isolation but still share the process -- a memory leak in a plugin leaks into the agent.

Hooks use subprocess isolation. Each hook runs as an independent process. It communicates through stdin (receives JSON context), stdout (returns structured output), stderr (provides feedback), and exit codes (signals allow/block). A segfaulting hook kills the subprocess, not the agent. A hanging hook is killed by timeout, not by waiting forever. And hooks can be written in any language -- Bash, Python, Go, Rust -- because the interface is the universal process boundary.

The cost is ~50ms per hook invocation (process spawn overhead). This is acceptable because hooks fire at tool-call boundaries, which already involve LLM API round trips measured in seconds. Adding 50ms to a 2-second API call is a 2.5% slowdown.

The "Can Block" Decision

Only seven events support blocking (exit code 2 stops the action):

  • PreToolUse: Block a tool call before execution
  • UserPromptSubmit: Block or rewrite a user prompt
  • PreApiCall: Block an API request
  • PreCompaction: Prevent context compaction
  • SubagentStop: Reject subagent output
  • Stop: Prevent the agent from completing its turn
  • PostToolUse (partial): Can modify MCP tool output but not block

The blocking events are exclusively "Pre" events or quality gates. "Post" events cannot block because the action has already happened -- blocking after the fact would create inconsistent state.

Event Data Schemas

Each event provides specific context to hooks via stdin JSON. Here are the schemas for the most commonly hooked events:

PreToolUse:

{
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": {
    "command": "git push origin main"
  },
  "session_id": "sess-abc123",
  "working_directory": "/project"
}

PostToolUse:

{
  "hook_event_name": "PostToolUse",
  "tool_name": "Write",
  "tool_input": {
    "file_path": "/project/src/config.py",
    "content": "..."
  },
  "tool_output": "File written successfully",
  "exit_code": 0,
  "duration_ms": 45,
  "session_id": "sess-abc123"
}

SessionStart:

{
  "hook_event_name": "SessionStart",
  "session_id": "sess-abc123",
  "working_directory": "/project",
  "model": "claude-opus-4",
  "permission_mode": "auto"
}

The schemas are intentionally flat. No nested objects beyond tool_input/tool_output. This makes them parseable in Bash with simple jq commands -- the most common hook implementation language.

29.3 The Five Hook Types

Hooks are not limited to shell scripts. The system supports five types, each suited to different use cases:

graph LR
    subgraph "Hook Types"
        CMD[command]
        HTTP[http]
        PROMPT[prompt]
        AGENT[agent]
        CB[callback]
    end

    CMD --> |"Shell script via subprocess"| OS[OS Process]
    HTTP --> |"HTTP POST to endpoint"| API[HTTP Server]
    PROMPT --> |"Inject text into LLM context"| LLM[LLM]
    AGENT --> |"Spawn subagent to evaluate"| Sub[Subagent]
    CB --> |"In-process function call"| Runtime[Agent Runtime]

Type 1: Command Hooks

The workhorse. A shell command executed as a subprocess:

{
  "type": "command",
  "command": "./.claude/hooks/block-destructive.sh",
  "timeout": 5000,
  "statusMessage": "Checking safety..."
}

The command receives event context on stdin, returns structured output on stdout, and signals allow/block via exit code. Any executable works -- Bash, Python, compiled binaries.

When to use: Most hooks. Security gates, linting, notifications, audit logging.

Type 2: HTTP Hooks

Posts the event context to an HTTP endpoint:

{
  "type": "http",
  "url": "https://policy.internal.company.com/agent-check",
  "timeout": 10000,
  "headers": {
    "Authorization": "Bearer ${POLICY_TOKEN}"
  }
}

The endpoint receives a POST with the event JSON as the body. The response body is parsed as hook output (same schema as command hook stdout). HTTP status 200 = allow, 403 = block, other = non-blocking error.

When to use: Centralized policy enforcement, compliance systems, external audit services.

Type 3: Prompt Hooks

Injects text into the LLM's context. No subprocess, no HTTP call -- the hook's "command" is treated as text to inject:

{
  "type": "prompt",
  "prompt": "Remember: all database queries must use parameterized statements. Never use string concatenation for SQL.",
  "events": ["PreToolUse"]
}

Prompt hooks cannot block. They influence behavior by adding instructions that the LLM follows.

When to use: Soft guardrails, style guidelines, domain-specific instructions that should apply to every tool call.

Type 4: Agent Hooks

Spawns a subagent to evaluate the event. The subagent has access to tools and can make multiple LLM calls to reach a decision:

{
  "type": "agent",
  "model": "sonnet",
  "prompt": "Review this tool call for security issues. If you find any, explain why and recommend blocking.",
  "maxTurns": 5,
  "timeout": 30000
}

The subagent receives the event context and the prompt. Its final response is parsed for an allow/block decision. This is the most powerful hook type -- and the most expensive (an LLM call per hook invocation).

When to use: Complex security review that requires reasoning, not just pattern matching. Code review gates. Multi-step validation.

Type 5: Callback Hooks

In-process function calls for internal use:

{
  type: "callback",
  handler: (event: HookEvent) => {
    // In-process logic
    return { decision: "allow" };
  }
}

Callback hooks bypass subprocess isolation. They exist for internal agent modules that need to participate in the hook pipeline (the permission system, for example, registers callback hooks to check rule-based permissions). They are not available to users.

When to use: Internal agent modules only. Never for user-authored hooks.

Comparison

Type Latency Isolation Language Can Block Cost
command ~50ms (spawn) Full (subprocess) Any Yes Minimal
http ~100-500ms (network) Full (network) Any (server-side) Yes Network I/O
prompt ~0ms (text inject) None N/A No Tokens
agent ~2-10s (LLM call) Full (subagent) N/A Yes LLM tokens
callback ~0ms (function call) None Agent's language Yes Minimal

29.4 The Execution Model

Sequential Within an Event

When multiple hooks are registered for the same event, they execute sequentially in priority order:

sequenceDiagram
    participant Engine as Hook Engine
    participant H1 as Hook A (managed)
    participant H2 as Hook B (project)
    participant H3 as Hook C (user)

    Engine->>H1: Execute (priority 1)
    H1-->>Engine: exit 0 (allow)
    Engine->>H2: Execute (priority 2)
    H2-->>Engine: exit 0 (allow) + updatedInput
    Engine->>H3: Execute (priority 3, sees H2's modified input)
    H3-->>Engine: exit 0 (allow)
    Engine->>Engine: Proceed with final input

Each hook sees the cumulative result of all previous hooks' modifications. If Hook B returns updatedInput, Hook C receives the modified input, not the original. This creates a pipeline where hooks compose:

Original input
  -> Hook A: validates, allows
    -> Hook B: rewrites command, allows
      -> Hook C: sees rewritten command, allows
        -> Tool executes with final input

Short-Circuit on Block

If any hook exits with code 2 (block), the pipeline stops immediately. Later hooks do not execute:

sequenceDiagram
    participant Engine as Hook Engine
    participant H1 as Hook A
    participant H2 as Hook B
    participant H3 as Hook C

    Engine->>H1: Execute
    H1-->>Engine: exit 0 (allow)
    Engine->>H2: Execute
    H2-->>Engine: exit 2 (BLOCK) + reason on stderr
    Note over Engine,H3: Hook C never executes
    Engine->>Engine: Block action, report reason to LLM

The block reason (from stderr) is reported to the LLM as feedback, allowing it to adjust its approach. For example, if a hook blocks rm -rf /tmp/data, the LLM receives "Blocked: recursive deletion of /tmp/data is prohibited" and can try a safer alternative.

Priority Ordering

Hook sources are merged by priority, highest first:

Priority (highest first):
  1. Policy hooks (enterprise MDM)
  2. Managed hooks (organization-provisioned)
  3. User hooks (~/.claude/settings.json)
  4. Project hooks (.claude/settings.json)
  5. Local hooks (.claude/settings.local.json)
  6. Plugin hooks (third-party extensions)
  7. Built-in hooks (agent internals)

Policy hooks always execute first and can block anything. A user hook cannot override a policy hook's block decision. This ordering is the trust hierarchy: enterprise policy > organization management > individual user > project configuration > local overrides > plugins > defaults.

The hasHookForEvent Guard

Before constructing the event context (which involves serializing tool inputs to JSON), the engine checks if any hooks are registered for the current event:

function hasHookForEvent(event: string): boolean {
  return hookRegistry.some(hook =>
    hook.events.includes(event) || hook.events.includes('*')
  );
}

// In the tool execution pipeline:
if (hasHookForEvent('PreToolUse')) {
  const context = buildToolContext(tool, input); // Expensive: serialization
  const result = await executeHooks('PreToolUse', context);
  if (result.blocked) return blockResult(result.reason);
  if (result.updatedInput) input = result.updatedInput;
}

This guard is critical for performance. When no hooks are registered (the common case for most events), the engine skips context construction, JSON serialization, and the entire hook pipeline. The cost of 27 lifecycle events with no registered hooks is 27 boolean checks -- essentially zero.

29.5 The Exit Code Protocol

The hook interface is defined by three channels and one exit code:

Channel Direction Purpose
stdin Engine -> Hook Event context as JSON
stdout Hook -> Engine Structured output (optional)
stderr Hook -> Engine Human-readable feedback (on block)
Exit code Hook -> Engine Decision signal

Exit code semantics:

Code Meaning Effect
0 Allow / success Action proceeds. Stdout parsed for advanced output.
2 Block Action is prevented. Stderr reported to LLM as feedback.
Other Non-blocking error Hook failure logged. Action proceeds (fail-open).

Why Fail-Open?

The default for hook errors (exit codes other than 0 or 2) is fail-open: the action proceeds as if the hook did not exist. This is the correct default for two reasons:

  1. Availability over safety for most hooks. A broken telemetry hook should not paralyze the agent. A crashing audit logger should not block tool execution.

  2. Explicit blocking requires explicit intent. Exit code 2 is a deliberate signal that the hook author has decided this action must be blocked. All other exit codes -- including crashes, timeouts, and unexpected errors -- are not deliberate block decisions and should not be treated as such.

For environments that need fail-closed behavior, the hook script implements it with a trap:

#!/usr/bin/env bash
set -euo pipefail

# Fail-closed: any error blocks the action
trap 'echo "Hook error: safety check failed" >&2; exit 2' ERR

# ... validation logic ...
exit 0

The Structured Output Protocol

Hooks that need to do more than allow/block return structured JSON on stdout:

{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow",
    "updatedInput": { "command": "git push --no-verify" },
    "additionalContext": "All pushes require --no-verify in this environment"
  }
}

The hookSpecificOutput wrapper is intentional. It allows the engine to distinguish between hook output (structured JSON) and incidental stdout (debug prints, accidental echo statements). Only JSON with the hookSpecificOutput key is parsed as hook communication. Everything else is logged and ignored.

29.6 Advanced Hook Capabilities

The basic allow/block mechanism handles 80% of hook use cases. The remaining 20% requires capabilities that let hooks actively participate in the execution flow.

Input Modification: updatedInput

A PreToolUse hook can return updatedInput to rewrite tool arguments before execution:

sequenceDiagram
    participant LLM
    participant Engine
    participant Hook
    participant Tool

    LLM->>Engine: Bash("git push origin main")
    Engine->>Hook: PreToolUse context
    Hook-->>Engine: updatedInput: {"command": "git push origin main --no-verify"}
    Engine->>Tool: Bash("git push origin main --no-verify")
    Tool-->>Engine: Result
    Engine-->>LLM: Result (LLM does not know about the rewrite)

The merge is shallow: only specified fields are overridden, other fields remain unchanged. The merged input is validated against the tool's schema -- if the hook produces invalid input, the original is used and a warning is logged. This prevents hooks from corrupting tool calls.

Security constraint: updatedInput does not bypass permission rules. Even if a hook allows and rewrites a command, the rewritten command is still checked against deny rules in settings.json. A hook cannot use updatedInput to smuggle rm -rf / past a deny rule.

Output Modification: updatedMCPToolOutput

A PostToolUse hook can modify the output of MCP tool calls before the LLM sees them:

// Hook returns:
{
  "hookSpecificOutput": {
    "hookEventName": "PostToolUse",
    "updatedMCPToolOutput": {
      "content": [{ "type": "text", "text": "[REDACTED: 3 rows contained PII]" }]
    }
  }
}

This is restricted to MCP tools. Built-in tool outputs (Bash exit code, file read content) are consumed by the agent's internal logic -- modifying them would break consistency checks. MCP tool outputs go directly to the LLM with no internal interpretation, making them safe targets for transformation.

Auto-Submit: initialUserMessage

A SessionStart hook can inject the first user message, enabling fully automated sessions:

#!/usr/bin/env bash
set -euo pipefail

if [[ -n "${CI:-}" ]]; then
  echo '{"hookSpecificOutput":{"hookEventName":"SessionStart","initialUserMessage":"Run tests and fix failures"}}'
fi
exit 0

This is the foundation of headless/CI mode. No separate "headless API" is needed -- the same hook system that handles interactive guardrails also handles automated task injection.

File Watching: watchPaths

A SessionStart hook can register filesystem watchers that fire FileChanged events:

echo '{"hookSpecificOutput":{"hookEventName":"SessionStart","watchPaths":["src/","tests/","config.yaml"]}}'

The engine sets up fs.watch listeners with 300ms debounce (to coalesce editor save cycles) and fires FileChanged events when modifications are detected. FileChanged hooks can then react -- re-running linters, invalidating caches, or notifying the agent of stale assumptions.

Context Injection: additionalContext

Multiple hook types support additionalContext -- a string injected into the conversation as a system message:

BRANCH=$(git branch --show-current)
LAST_COMMIT=$(git log -1 --oneline)
echo "{\"hookSpecificOutput\":{\"hookEventName\":\"SessionStart\",\"additionalContext\":\"Branch: ${BRANCH}\nLast commit: ${LAST_COMMIT}\"}}"

SessionStart context injection is the most powerful form: the injected text becomes part of the system prompt for the entire session. PostToolUse context injection adds information after a tool runs, steering subsequent LLM reasoning.

Async Execution: async and asyncRewake

Hooks that need seconds or minutes to complete (security scanners, large test suites) can run asynchronously:

{
  "type": "command",
  "command": "./.claude/hooks/security-scan.sh",
  "asyncRewake": true,
  "timeout": 60000
}

With asyncRewake: true, the hook runs in the background while the agent continues. If the hook exits with code 2 (block) after the agent has moved on, the engine injects a notification into the conversation: "Security scan found vulnerability in dependency X." The agent can then react.

With plain async: true, the hook runs in the background with no wake-up -- pure fire-and-forget for telemetry, logging, and notification delivery.

Once-Only Hooks: once

Some hooks should fire exactly once per session -- an authentication check, a license verification, an environment setup:

{
  "type": "command",
  "command": "./.claude/hooks/check-auth.sh",
  "once": true
}

After successful execution (exit 0), the hook is marked as "fired" and skipped on subsequent events. Crucially, a failed hook (non-zero, non-2 exit) is NOT marked as fired -- it retries on the next event trigger. Only success satisfies the "once" constraint.

Conditional Execution: if Patterns

The if field provides fine-grained filtering using the same pattern syntax as the permission system:

{
  "if": "Bash(git push *)",
  "hooks": [{
    "type": "command",
    "command": "./.claude/hooks/pre-push-check.sh"
  }]
}

This hook fires only for Bash tool calls where the command starts with git push. It does not fire for Bash(npm install) or Write(src/main.py).

The if pattern composes with the matcher field:

Filter Level Matches Against Cost
matcher Group Tool name only String comparison (~0.001ms)
if Individual hook Tool name + arguments Glob compilation + matching (~0.1ms)

The two-stage filtering is a performance optimization. The cheap matcher check eliminates non-matching tool types before the more expensive if evaluation parses arguments and compiles patterns.

29.7 Hook Composition Patterns

The advanced capabilities compose. Here are the architecturally significant patterns:

Pattern 1: Progressive Security Gate

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "./.claude/hooks/quick-check.sh",
            "if": "Bash(curl *)",
            "timeout": 2000
          },
          {
            "type": "command",
            "command": "./.claude/hooks/deep-scan.sh",
            "if": "Bash(curl *)",
            "asyncRewake": true,
            "timeout": 30000
          }
        ]
      }
    ]
  }
}

The first hook runs synchronously (2s timeout), catching obvious issues. The second runs asynchronously (30s timeout), performing deep analysis. If the deep scan finds a problem after the agent has continued, it wakes the agent with a notification.

Pattern 2: Auto-Setup Pipeline

A SessionStart hook combining all capabilities:

#!/usr/bin/env bash
set -euo pipefail

BRANCH=$(git branch --show-current)
TASK=$(cat .claude/current-task.md 2>/dev/null || echo "")

jq -n \
  --arg ctx "Branch: ${BRANCH}" \
  --arg msg "${TASK}" \
  '{
    "hookSpecificOutput": {
      "hookEventName": "SessionStart",
      "additionalContext": $ctx,
      "initialUserMessage": (if $msg != "" then $msg else null end),
      "watchPaths": ["package.json", "pyproject.toml", ".env.local"]
    }
  }'

One hook: injects context, optionally auto-submits a task, and registers file watchers.

Pattern 3: Lint-on-Save

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [{
          "type": "command",
          "command": "ruff check --fix $FILE && ruff format $FILE",
          "if": "Write(*.py)"
        }]
      }
    ]
  }
}

Every time the agent writes or edits a Python file, the linter runs automatically. The agent never sees unlinted code in its output.

Composition Matrix

Capability Composes With Restriction
updatedInput if, once, matcher PreToolUse only
updatedMCPToolOutput if, once PostToolUse + MCP tools only
initialUserMessage watchPaths, additionalContext SessionStart only
watchPaths initialUserMessage, additionalContext SessionStart only

29.8 Hook Execution Flow

The complete execution flow for a PreToolUse event:

graph TD
    Start[Tool call generated by LLM] --> Guard{Any hooks registered for PreToolUse?}
    Guard -->|No| Execute[Execute tool with original input]
    Guard -->|Yes| Build[Build event context JSON]
    Build --> ForEach[For each hook in priority order]

    ForEach --> CheckIf{if pattern matches?}
    CheckIf -->|No| Skip[Skip hook]
    Skip --> Next[Next hook]

    CheckIf -->|Yes| CheckOnce{once: already fired?}
    CheckOnce -->|Yes| Skip

    CheckOnce -->|No| BuildEnv[Build environment vars]
    BuildEnv --> Spawn[Spawn subprocess with timeout]
    Spawn --> Wait{Wait for exit}

    Wait -->|Exit 0| ParseStdout[Parse stdout for JSON]
    ParseStdout --> HasUpdated{Has updatedInput?}
    HasUpdated -->|Yes| Validate{Schema validation passes?}
    Validate -->|Yes| Merge[Merge into current input]
    Validate -->|No| LogWarn[Log warning, keep original]
    HasUpdated -->|No| MarkOnce[Mark once if applicable]
    Merge --> MarkOnce
    LogWarn --> MarkOnce
    MarkOnce --> Next

    Wait -->|Exit 2| Block[BLOCK: stop pipeline]
    Block --> Report[Report stderr to LLM]

    Wait -->|Other exit| LogError[Log error, continue]
    LogError --> Next

    Wait -->|Timeout| Kill[Kill subprocess]
    Kill --> LogTimeout[Log timeout, continue]
    LogTimeout --> Next

    Next --> MoreHooks{More hooks?}
    MoreHooks -->|Yes| ForEach
    MoreHooks -->|No| Execute2[Execute tool with final input]

29.9 Designing Safe and Powerful Hooks

The hook system's design walks a line between power and safety. Here are the key architectural decisions and their rationales:

Decision 1: Subprocess Isolation

Every hook runs as an independent process. This adds 50ms of overhead but provides:

  • Crash isolation. A segfaulting hook kills the subprocess, not the agent.
  • Language independence. Hooks in Bash, Python, Go, or any executable.
  • Security boundary. Hooks cannot read agent memory, modify state, or access API keys.

Decision 2: JSON Protocol

Stdin/stdout communication uses JSON, not environment variables. JSON was chosen because:

  • Environment variables have platform-dependent size limits (32KB on many Linux systems). A large tool input could exceed this.
  • Structured output (updatedInput, asyncRewake) cannot be expressed as exit codes.
  • JSON is parseable in every language without shell-quoting concerns.

Decision 3: Fail-Open Default

Hook errors default to allowing the action. This prioritizes availability over security for the common case. The reasoning:

  • Most hooks are informational (logging, telemetry, notifications). A broken informational hook should not stop work.
  • Security hooks that need fail-closed behavior implement it explicitly with a trap that exits 2 on any error.
  • The distinction between "hook crashed" and "hook decided to block" must be clear. Only exit code 2 is a deliberate block decision.

Decision 4: Priority Ordering

Enterprise policy hooks override project hooks, which override user hooks. This is the organizational trust hierarchy. Without it, a user could disable a compliance hook by registering their own hook with the same name. The priority ordering makes this impossible.

Decision 5: Shallow Merge for updatedInput

Deep merge would introduce ambiguity. If the original input has { "env": { "PATH": "/usr/bin" } } and a hook returns { "env": { "EVIL": "1" } }, deep merge preserves both variables. Shallow merge replaces the entire env object, forcing the hook to be explicit about everything it permits.

Decision 6: Schema Validation on Merge

Hook-produced updatedInput is validated against the tool's schema. Invalid modifications are silently discarded. This prevents hooks from corrupting tool calls through typos or version mismatches.

The critical insight: if patterns and once flags reduce total overhead by preventing unnecessary process spawns. A well-configured hook with if: "Bash(git *)" and once: true incurs near-zero cost for the vast majority of tool calls. The same hook without these optimizations would spawn a process on every Bash invocation for the entire session.

29.11 Building Your Own Hook System: Implementation Checklist

Phase 1: Minimal Viable Hooks

  1. Two events: PreToolUse and PostToolUse. These cover 90% of use cases.
  2. One hook type: command (subprocess). Add others later.
  3. The exit code protocol: 0 = allow, 2 = block, other = fail-open.
  4. Sequential execution within an event. Priority ordering can wait.
  5. The hasHookForEvent guard. Zero cost when no hooks are registered.
  6. Timeout enforcement. Kill hooks that exceed their timeout.

Phase 2: Advanced Capabilities

  1. updatedInput for argument rewriting. Add schema validation.
  2. Priority ordering from multiple sources (user, project, managed).
  3. The if pattern filter for argument-level matching.
  4. once: true for one-shot hooks.
  5. additionalContext for LLM context injection.
  6. The matcher field for cheap tool-name filtering.

Phase 3: Full System

  1. HTTP hook type for centralized policy.
  2. Agent hook type for LLM-powered evaluation.
  3. Async hooks with background execution and rewake.
  4. SessionStart capabilities: initialUserMessage, watchPaths.
  5. updatedMCPToolOutput for MCP tool output transformation.
  6. Plugin hook loading with hot-reload.
  7. All 27 events. Add events as the agent's lifecycle gains complexity.

Each phase is independently valuable. Phase 1 gives you security guardrails in a few hundred lines. Phase 2 adds the power features that make hooks an extensibility platform. Phase 3 completes the enterprise feature set.

29.12 Key Takeaways

Hooks are the automation and guardrail system. They sit between the LLM's intentions and the tool system's actions. Every production AI agent needs this layer.

Subprocess isolation is worth 50ms. The safety properties (crash isolation, language independence, security boundary) are worth the process spawn overhead at tool-call boundaries.

Exit codes are the simplest viable protocol. 0 = allow, 2 = block. Everything else is fail-open. This is simple enough for a bash one-liner and powerful enough for enterprise policy enforcement.

27 events is not over-engineering. Each event fires at a specific lifecycle point with specific semantics. The hasHookForEvent guard ensures that unused events have zero cost. The events are the API surface that hooks program against -- getting them right means hooks can do what they need without hacks.

Advanced capabilities compose through the JSON output protocol. A single hook response can contain updatedInput, additionalContext, and a permission decision. The engine processes each field independently. The protocol was designed to be extensible from the start -- new capabilities are new fields, not new communication channels.

The trust hierarchy is non-negotiable. Enterprise policy hooks must override everything else. Without priority ordering, the hook system cannot serve organizations with compliance requirements.
