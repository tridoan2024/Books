Chapter 10: API Client Design

In Chapter 9, we examined context window management -- how the system decides what content reaches the model within its token budget. But the context assembly pipeline produces a payload that still needs to reach the model. That last mile -- serializing messages, routing to the correct provider, handling failures, tracking costs, and processing the streaming response -- is the job of the API client.

The API client sits at the most consequential boundary in the entire system: the interface between your agent and the model that powers it. Every architectural decision here affects latency, cost, reliability, and correctness. Get the retry logic wrong and your users see cryptic errors during transient outages. Get the streaming wrong and your first-token latency balloons from 200ms to 30s. Get the provider abstraction wrong and you lock your enterprise customers out of their preferred cloud.

This chapter examines the design principles behind a production API client for AI CLI agents: the provider abstraction layer, streaming architecture, retry strategies, circuit breakers, rate limiting, cost tracking, and the header management patterns that make prompt caching economically viable.

Why a Provider Abstraction Layer

An AI CLI agent that talks to a single API endpoint is a prototype. A production agent needs to support multiple model providers -- not because abstraction is inherently virtuous, but because enterprise deployment realities demand it.

The business case is straightforward:

  • AWS-heavy organizations mandate that all API calls route through their cloud. They use Amazon Bedrock, which fronts the same models through AWS's infrastructure with SigV4 authentication, VPC endpoints, and consolidated billing.
  • GCP-heavy organizations have the same requirement but with Google Vertex AI. Service accounts, project-scoped billing, regional endpoints.
  • Regulated industries need data residency guarantees. The first-party API endpoint may route through regions that violate compliance requirements. Cloud-specific endpoints give control over data geography.
  • Startups and individual developers want the simplest path: a direct API key to the model provider's endpoint.

Without a provider abstraction, you build four separate API clients. With one, you build a single client and four thin adapters.

The Adapter Pattern

The provider abstraction follows the classic adapter pattern: a common interface with provider-specific implementations. The interface surface is deliberately narrow:

interface ModelProvider {
  createMessage(params: MessageParams): Promise<MessageResponse>
  createMessageStream(params: MessageParams): AsyncIterable<StreamEvent>
  countTokens(params: CountTokensParams): Promise<TokenCount>
  getModelCapabilities(modelId: string): ModelCapabilities
}

Four methods. That is the entire contract. Every provider-specific concern -- authentication, endpoint routing, header formatting, request body differences -- lives inside the adapter implementation. The rest of the system (the agent loop, the context manager, the tool executor) works against this interface and never knows which provider is active.

This narrowness is deliberate. Every method you add to the interface is a method every adapter must implement. A wide interface turns provider additions from a one-day task into a one-week task. The four methods above cover the three operations the agent actually needs: send a message (streaming or not), count tokens, and check what a model can do.

The Factory Function

Client instantiation happens through a factory function, not a constructor:

async function createModelClient(): Promise<ModelProvider> {
  const provider = resolveProvider()  // env vars, config, CLI flags

  switch (provider) {
    case 'bedrock':
      return new BedrockAdapter({
        region: resolveAWSRegion(),
        credentials: await resolveAWSCredentials(),
      })
    case 'vertex':
      return new VertexAdapter({
        project: resolveGCPProject(),
        location: resolveGCPLocation(),
        credentials: await resolveServiceAccount(),
      })
    case 'custom':
      return new CustomEndpointAdapter({
        baseURL: resolveCustomEndpoint(),
        auth: resolveCustomAuth(),
      })
    default:
      return new AnthropicAdapter({
        apiKey: resolveAPIKey(),
      })
  }
}

The factory is a function, not a class, because client creation may need to be repeated. When credentials expire mid-session (OAuth tokens, temporary AWS credentials), the retry engine discards the old client and calls the factory again. A class with a constructor implies one-time initialization. A factory function communicates "this can happen again."

The factory is also the single point where credential resolution happens. Credentials flow from environment variables, config files, and cloud metadata services through a resolution chain. Centralizing this in the factory means credential bugs have exactly one place to look.

Streaming Architecture

Why Streaming Is Non-Negotiable

A non-streaming API call for a complex response takes 20-40 seconds. The user stares at a blank terminal for the entire duration. A streaming call returns the first token in 200-500ms and renders incrementally. Same total time, but the perceived experience is fundamentally different.

The math is simple. If response generation takes 30 seconds:

Mode Time to first visible output User perception
Non-streaming 30s "Is it frozen?"
Streaming ~300ms "It's working, I can read along"

Streaming is not an optimization. It is a user experience requirement for any interactive AI tool. The technical cost is significant -- parsing Server-Sent Events, managing partial state, handling mid-stream disconnections -- but the alternative (a 30-second blank screen) is unacceptable.

Server-Sent Events Processing

The standard transport for streaming model responses is Server-Sent Events (SSE), a simple protocol layered over HTTP chunked transfer encoding. The server sends a continuous stream of text-based events:

event: message_start
data: {"type":"message_start","message":{"id":"msg_01...","model":"claude-opus-4-6",...}}

event: content_block_start
data: {"type":"content_block_start","index":0,"content_block":{"type":"text","text":""}}

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"Here"}}

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":" is"}}

Each event has a type and a JSON data payload. The client reads the stream line by line, parses events, and dispatches them to handlers. The key architectural decision is how to structure the event processing pipeline.

Raw Stream vs SDK Wrapper

Most model provider SDKs offer a convenience wrapper that accumulates stream events into a high-level message object. This wrapper is convenient for simple applications but can introduce performance problems in production agents.

The specific issue is incremental JSON parsing. When the model generates a tool call, the tool's input arrives as a sequence of input_json_delta events, each containing a few characters of the JSON argument. A convenience wrapper may attempt to parse the partial JSON on every delta to provide incremental access to the tool input. This is O(n^2) -- each parse re-scans the accumulated string from the beginning. For a tool call with 10KB of JSON input (common for file edits), this means thousands of redundant parses.

The production-grade alternative: accumulate raw strings during deltas, parse once at content_block_stop. Linear time, no wasted CPU.

SDK Wrapper approach:
  Delta 1: parse("{")           = 1 char scanned
  Delta 2: parse("{\"f")        = 3 chars scanned
  Delta 3: parse("{\"fi")       = 4 chars scanned
  ...
  Delta N: parse("{\"file\":...") = N chars scanned
  Total: O(N^2) parsing work

Raw accumulation approach:
  Delta 1-N: append to string buffer
  Block stop: parse once         = N chars scanned
  Total: O(N) parsing work

This is a general principle for streaming systems: defer parsing until you have the complete unit. Incremental parsing is useful when you need to act on partial data (rendering text tokens to the screen). It is wasteful when the partial data has no actionable use (partial JSON for a tool call).

The Stream Idle Watchdog

HTTP keep-alive connections can enter a state where the TCP connection is alive but no data flows. The server may have crashed, a network middlebox may be buffering, or a load balancer may have silently dropped the connection. The HTTP library's request timeout only covers the initial connection handshake, not the streaming body.

A production streaming client needs a watchdog timer:

Stream starts
  |
  v
[Reset timer on every event]
  |
  +-- Event received --> Reset 90s timer
  |
  +-- 45s with no event --> Emit warning
  |
  +-- 90s with no event --> Abort stream, trigger retry

The timer resets on every incoming event. If 90 seconds pass with no events, the stream is considered dead and the client triggers a retry. A 45-second warning (halfway) gives observability into streams that are slow but not dead.

The specific timeout values reflect the characteristics of model inference. During extended thinking, the model may go 30-60 seconds between visible output events (thinking tokens may not be streamed). The 90-second timeout is set above this expected gap to avoid false positives.

Retry Logic

Exponential Backoff with Jitter

Every networked system needs retry logic. The question is not whether to retry, but how.

The standard pattern is exponential backoff with jitter:

Attempt 1: fail -> wait  500ms + random(0, 125ms)
Attempt 2: fail -> wait 1000ms + random(0, 250ms)
Attempt 3: fail -> wait 2000ms + random(0, 500ms)
Attempt 4: fail -> wait 4000ms + random(0, 1000ms)
...
Attempt N: fail -> wait min(base * 2^N, 32000ms) + jitter

The exponential growth prevents hammering a recovering server. The jitter prevents thundering herd -- without it, all clients that failed at the same time would retry at the same time, creating synchronized spikes that overwhelm the server again.

The jitter should be proportional to the delay (typically 25% of the base delay), not a fixed value. A fixed 100ms jitter on a 32-second delay provides negligible distribution. A proportional 25% jitter (8 seconds of spread on a 32-second delay) actually distributes the retry load.

Retry-After Header Respect

The server knows its own load better than the client. When the API returns a 429 Too Many Requests or 529 Overloaded with a Retry-After header, that header should take absolute precedence over the client's calculated backoff:

function calculateRetryDelay(attempt: number, retryAfterHeader?: string): number {
  // Server's instruction always wins
  if (retryAfterHeader) {
    const seconds = parseInt(retryAfterHeader, 10)
    if (!isNaN(seconds)) return seconds * 1000
  }

  // Client-side exponential backoff with 25% jitter
  const baseDelay = Math.min(500 * Math.pow(2, attempt - 1), 32000)
  const jitter = Math.random() * 0.25 * baseDelay
  return baseDelay + jitter
}

The Error Classification Ladder

Not all errors deserve the same retry strategy. A production retry engine classifies errors and applies targeted recovery:

Error Type Status Code Recovery Strategy
Rate limited 429 Respect Retry-After, exponential backoff
Overloaded 529 Exponential backoff, consider model fallback after 3 consecutive
Auth expired 401/403 Refresh credentials, get new client from factory, retry once
Context overflow 400 (prompt too long) Reduce max_tokens, retry
Stale connection ECONNRESET, EPIPE Discard client, reconnect, retry
Stream interrupted Mid-stream disconnect Fall back to non-streaming request
Server error 500 Exponential backoff, limited retries
Client error 400 (other) Do not retry -- fix the request
User abort Signal.aborted Do not retry -- user canceled

The classification must be a priority-ordered ladder, not a flat switch. Some errors match multiple categories (a 429 during fast mode is both a rate limit and a fast-mode concern). The first matching handler wins.

The Retry Engine as AsyncGenerator

A key architectural insight: the retry engine should be an async generator, not a function that returns a Promise. During backoff, the engine yields status messages ("Retrying in 8 seconds...") that the UI renders in real-time:

async function* withRetry<T>(
  operation: (client: ModelProvider) => Promise<T>,
  options: RetryOptions,
): AsyncGenerator<RetryStatus, T> {
  for (let attempt = 1; attempt <= options.maxRetries + 1; attempt++) {
    try {
      return await operation(await getClient())
    } catch (error) {
      const delay = classifyAndDelay(error, attempt)
      if (delay === null) throw error  // Non-retryable

      yield { type: 'retrying', attempt, delay, error }
      await sleep(delay)
    }
  }
  throw new MaxRetriesExceededError()
}

Compare this with a traditional async function withRetry(): Promise<T>. The traditional version blocks the caller for the entire backoff duration. The generator version lets the caller render progress, check for user cancellation, or perform other work between attempts. This is the same generator-as-protocol pattern discussed in Chapter 7's agent loop -- the caller drives the pace, the producer yields when ready.

Model Fallback on Persistent Failure

After N consecutive failures (typically 3) on the primary model, the retry engine should trigger a model fallback rather than continuing to hammer an overloaded endpoint:

Attempt 1 (Opus): 529 -> backoff
Attempt 2 (Opus): 529 -> backoff
Attempt 3 (Opus): 529 -> FALLBACK TRIGGER
Attempt 4 (Sonnet): success

The fallback is a separate concern from the retry. The retry engine signals the fallback via a typed error (FallbackTriggeredError), and the agent loop catches it and switches models. This separation means the retry engine does not need to know about model selection -- it just says "I give up on this model" and lets a higher layer decide what happens next.

Persistent Retry for CI/CD

Interactive sessions have a 32-second maximum backoff because users do not tolerate longer waits. CI/CD and unattended sessions have different constraints: they can tolerate minutes of waiting but must not silently fail.

const INTERACTIVE_CONFIG = {
  maxBackoffMs: 32_000,    // 32 seconds
  maxRetries: 10,
  heartbeatMs: 0,          // No heartbeat needed
}

const UNATTENDED_CONFIG = {
  maxBackoffMs: 300_000,   // 5 minutes
  maxRetries: Infinity,    // Retry until hard cap
  hardCapMs: 21_600_000,   // 6 hours
  heartbeatMs: 30_000,     // 30s heartbeat to prevent idle-kill
}

The 30-second heartbeat writes a status message to stdout, preventing CI runners from killing the process for inactivity. The 6-hour hard cap prevents infinite loops in truly broken scenarios.

Circuit Breaker Pattern

The retry engine handles individual request failures. The circuit breaker handles systemic failures -- when the entire provider is unavailable and retrying individual requests is wasteful.

stateDiagram-v2
    [*] --> Closed

    Closed --> Open : Failure threshold exceeded<br/>(e.g., 5 failures in 60s)
    Closed --> Closed : Request succeeds<br/>Reset failure counter

    Open --> HalfOpen : Cooldown timer expires<br/>(e.g., 30 seconds)
    Open --> Open : All requests rejected<br/>immediately (no API call)

    HalfOpen --> Closed : Probe request succeeds<br/>Reset counters
    HalfOpen --> Open : Probe request fails<br/>Restart cooldown

The three states:

  • Closed (normal): Requests flow through. Failures are counted. When failures exceed a threshold (e.g., 5 in 60 seconds), transition to Open.
  • Open (circuit tripped): All requests fail immediately without contacting the API. A cooldown timer runs. When it expires, transition to Half-Open.
  • Half-Open (probe): A single request is allowed through as a probe. If it succeeds, transition to Closed. If it fails, transition back to Open.

The circuit breaker prevents cascade failures. Without it, during a provider outage, every tool call triggers a retry sequence (potentially 10 attempts with exponential backoff), multiplied by every concurrent agent. A single user's session could generate hundreds of failed API calls per minute. The circuit breaker cuts this to one probe every 30 seconds.

Implementing the Circuit Breaker

A practical implementation stores failure timestamps in a sliding window:

class CircuitBreaker {
  private state: 'closed' | 'open' | 'half-open' = 'closed'
  private failures: number[] = []  // timestamps
  private lastOpenedAt: number = 0

  private readonly failureThreshold = 5
  private readonly windowMs = 60_000      // 1 minute window
  private readonly cooldownMs = 30_000    // 30 second cooldown

  canExecute(): boolean {
    if (this.state === 'closed') return true
    if (this.state === 'open') {
      if (Date.now() - this.lastOpenedAt > this.cooldownMs) {
        this.state = 'half-open'
        return true  // Allow one probe
      }
      return false
    }
    return false  // half-open, probe already in flight
  }

  recordSuccess(): void {
    this.state = 'closed'
    this.failures = []
  }

  recordFailure(): void {
    const now = Date.now()
    this.failures.push(now)
    // Trim to window
    this.failures = this.failures.filter(t => now - t < this.windowMs)

    if (this.failures.length >= this.failureThreshold) {
      this.state = 'open'
      this.lastOpenedAt = now
    }
  }
}

The sliding window (filter timestamps older than 60 seconds) prevents ancient failures from keeping the circuit open. Only recent, sustained failures trigger the breaker.

Per-Provider Circuit Breakers

In a multi-provider architecture, each provider gets its own circuit breaker. When Bedrock trips, the system can fall back to Vertex or the first-party API. This requires the fallback chain (covered in Chapter 12) to be circuit-breaker-aware:

Request arrives
  |
  v
Bedrock circuit breaker: OPEN
  |-> Skip Bedrock, try next provider
  v
Vertex circuit breaker: CLOSED
  |-> Send request to Vertex
  v
Success -> return result

Rate Limiting

Client-Side Throttling

The API enforces rate limits server-side, but waiting for a 429 response to throttle is wasteful -- you have already consumed network round-trip time. Client-side throttling prevents requests from being sent when you know they will be rejected.

The simplest effective approach is a token bucket:

class TokenBucket {
  private tokens: number
  private lastRefill: number

  constructor(
    private readonly capacity: number,    // Max burst
    private readonly refillRate: number,  // Tokens per second
  ) {
    this.tokens = capacity
    this.lastRefill = Date.now()
  }

  async acquire(): Promise<void> {
    this.refill()
    if (this.tokens >= 1) {
      this.tokens -= 1
      return
    }
    // Wait until a token is available
    const waitMs = ((1 - this.tokens) / this.refillRate) * 1000
    await sleep(waitMs)
    this.refill()
    this.tokens -= 1
  }

  private refill(): void {
    const now = Date.now()
    const elapsed = (now - this.lastRefill) / 1000
    this.tokens = Math.min(this.capacity, this.tokens + elapsed * this.refillRate)
    this.lastRefill = now
  }
}

Shared Rate Windows

When multiple agent instances share an API key (common in multi-agent architectures), they share a rate limit window. Staggering agent launches by a few seconds prevents all agents from hitting the rate limit simultaneously during startup, when each agent makes its first request.

This is a coordination problem without a coordination mechanism -- the agents do not communicate about rate limits. The practical solution is launch staggering plus per-agent jitter:

Agent 1: launch at T+0s
Agent 2: launch at T+3s
Agent 3: launch at T+6s
Agent 4: launch at T+9s

Each agent adds random(0, 1s) jitter to its first request.

Cap the number of concurrent agents to stay within the shared rate limit. If your API key allows 60 requests/minute and each agent makes ~1 request every 4 seconds, you can safely run ~4 agents.

Cost Tracking

Per-Request Token Counting

Every API response includes usage data: input tokens, output tokens, cache read tokens, and cache write tokens. A production client must track these cumulatively across the session to enable budget enforcement and cost visibility.

interface TokenUsage {
  inputTokens: number
  outputTokens: number
  cacheReadTokens: number
  cacheWriteTokens: number
}

interface SessionCostTracker {
  totalUsage: TokenUsage
  totalCostUSD: number
  requestCount: number

  recordUsage(usage: TokenUsage, model: string, isFastMode: boolean): void
  getRemainingBudget(): number | null
}

A subtlety in streaming responses: the API provides cumulative usage totals in the message_delta event, not deltas. The input_tokens field in a delta event may be 0 (not "zero additional tokens" but "this field is not populated in this event"). The client must handle this by using a "take the non-zero value" merge strategy:

function mergeUsage(current: TokenUsage, update: Partial<TokenUsage>): TokenUsage {
  return {
    inputTokens: (update.inputTokens ?? 0) > 0 
      ? update.inputTokens! : current.inputTokens,
    outputTokens: update.outputTokens ?? current.outputTokens,
    cacheReadTokens: update.cacheReadTokens ?? current.cacheReadTokens,
    cacheWriteTokens: update.cacheWriteTokens ?? current.cacheWriteTokens,
  }
}

Session Budget Enforcement

The agent loop can set a token budget for a session or task. The cost tracker enforces it:

function checkBudget(tracker: SessionCostTracker, budget: TokenBudget): BudgetStatus {
  if (budget.type === 'tokens') {
    const used = tracker.totalUsage.inputTokens + tracker.totalUsage.outputTokens
    const remaining = budget.total - used
    return remaining > 0 ? { ok: true, remaining } : { ok: false, overage: -remaining }
  }
  if (budget.type === 'dollars') {
    const remaining = budget.total - tracker.totalCostUSD
    return remaining > 0 ? { ok: true, remaining } : { ok: false, overage: -remaining }
  }
}

Budget enforcement is informational for the model (via a task_budget parameter that tells the model how much budget remains, so it can self-pace its output) and hard for the client (the agent loop stops when the budget is exhausted).

Header Management and Cache Key Engineering

Beta Headers as Cache Keys

Model APIs use beta headers to enable experimental features. These headers seem like simple string flags, but they have a profound architectural impact: beta headers are part of the server-side cache key. The prompt cache stores processed prompt content keyed by the combination of model, system prompt, tools, and beta headers. Changing any component invalidates the cache.

The cost implication: a typical session has 50-70K tokens of cached system prompt. A cache miss re-processes all of those tokens at full price. A cache hit processes them at 1/10th the price. Toggling a single beta header mid-session can cost $0.75-$1.05 (at Opus pricing) for the cache miss alone.

The Latch Pattern

The solution is the latch pattern: once a beta header is sent in a session, it keeps being sent for every subsequent request, even if the feature that triggered it is no longer active.

Turn 1: fast mode OFF  -> headers: [effort, caching]
Turn 2: fast mode ON   -> headers: [effort, caching, fast-mode]  // Added
Turn 3: fast mode OFF  -> headers: [effort, caching, fast-mode]  // LATCHED
Turn 4: fast mode OFF  -> headers: [effort, caching, fast-mode]  // Still latched

The latch persists for the session lifetime and is cleared only when the conversation context resets (e.g., /clear or /compact), because those operations invalidate the cache regardless.

Separating Cache Key from Behavior

The latch pattern creates a subtle design requirement: you need to separate the cache key (which headers are present) from the behavior (which features are active). For fast mode:

  • The fast-mode beta header is latched (once sent, always sent) -- this keeps the cache key stable.
  • The speed: 'fast' parameter is dynamic (suppressed during cooldown) -- this controls actual behavior.

By keeping the header stable and varying the parameter, the system can toggle fast mode on and off without invalidating the cache. This separation applies to any feature controlled by both a header and a parameter.

Provider-Specific Header Handling

Not all providers handle headers the same way:

Concern Anthropic 1P AWS Bedrock Google Vertex
Beta headers HTTP headers Request body HTTP headers
countTokens betas All sent All sent Filtered subset
Auth mechanism API key header SigV4 signature OAuth bearer token
Model ID format claude-opus-4-6 anthropic.claude-opus-4-6-v1 claude-opus-4-6@latest

The provider abstraction layer handles these differences so the rest of the API client remains provider-agnostic. Only two places need provider awareness: the client factory (authentication) and the header formatter (header vs. body placement).

Request Parameter Assembly

Before the request is sent, the client assembles parameters from multiple sources:

  1. Messages and tools from the context manager
  2. System prompt with cache control markers
  3. Model and effort from session configuration
  4. Beta headers with latch application
  5. Task budget with remaining token count
  6. Provider-specific formatting (body vs. header placement)

This assembly is wrapped in a closure that can be re-evaluated on each retry attempt. The retry engine may change the model (after fallback), the fast mode state (after cooldown), or the effort level. A static parameter object would carry stale values across retries. The closure ensures every attempt gets fresh parameters while the expensive context preparation runs once.

Design Lessons

Building a production API client for an AI CLI agent, these architectural principles emerge:

1. Abstract providers at the narrowest possible layer. The provider interface should be 3-5 methods. Everything else -- retry logic, streaming, cost tracking, header management -- works against this interface. A wide abstraction makes adding providers expensive.

2. Make retries observable. An async generator retry engine yields progress while sleeping. The UI shows real-time retry status without blocking the rendering loop. A traditional Promise<T> retry hides 32 seconds of backoff behind a silent wait.

3. Separate the cache key from behavior. Beta headers (cache key) and feature parameters (behavior) should be independently controllable. The latch pattern keeps headers stable while parameters vary, preventing expensive cache invalidation.

4. Classify errors before retrying. Not all errors are equal. Rate limits need server-directed backoff. Auth errors need credential refresh. Context overflows need parameter adjustment. A flat retry loop with exponential backoff handles none of these correctly.

5. Use circuit breakers for systemic failures. Individual retry handles individual request failure. Circuit breakers handle provider outages. Without a breaker, N concurrent agents each retrying M times creates N*M requests against an already-overloaded endpoint.

6. Track costs as first-class data. Token usage and cost should flow through the system as structured data, not be computed as an afterthought. Budget enforcement, cost display, and provider cost comparison all depend on accurate, real-time cost tracking.

7. Design for credential rotation. Client factories should support being called multiple times per session. OAuth tokens expire, temporary credentials rotate, and long-running CLI sessions outlast all of them.
