Chapter 30: Skills & Custom Workflows

The hook system from Chapter 29 provides guardrails -- gates that observe, block, or modify individual actions. But guardrails alone do not make an agent useful for diverse workflows. A security engineer needs the agent to perform OWASP-referenced audits. A team lead needs it to generate PR summaries with risk assessments. A DevOps engineer needs it to validate deployment readiness across 10 checks. Each of these is a multi-step workflow with domain-specific instructions that the base LLM does not have.

Skills are the answer. A skill is a markdown file with YAML frontmatter that teaches the LLM how to perform a specific task. Skills are the primary mechanism through which an AI CLI agent learns new workflows without code changes. They are the user-facing extensibility layer: where hooks let you automate what happens around tool calls, skills let you define what the agent does in the first place.

This chapter examines the skill system architecture: how skills are authored, loaded, triggered, resolved, and executed. We will cover the YAML frontmatter schema that configures each skill's behavior, the five-source loading pipeline with priority-based shadowing, the dynamic context injection mechanism that lets skills pre-load relevant data, the auto-activation system that triggers skills based on file patterns, and the design decisions that separate skills from agents, hooks, and plugins.

30.1 What Skills Are

A skill is a directory containing a SKILL.md file. The file has two parts: YAML frontmatter (configuration) and a markdown body (instructions). When invoked, the system parses the frontmatter, resolves the body (substituting arguments and executing embedded commands), and delivers the result to the LLM as context for its next response.

Here is a minimal skill:

---
name: code-review
description: Reviews code for bugs, security, performance. Use when user
  says "review", "check my code", "code review", "find bugs".
argument-hint: [file-or-directory]
allowed-tools: Read, Grep, Glob, Bash
---

# Code Review

When invoked, perform a thorough code review of the specified target:

1. Read all files in the target
2. Check for security issues (injection, auth bypass, secrets)
3. Check for logic errors and edge cases
4. Check for performance issues
5. Check for readability and maintainability

Output format:
| Severity | Location | Finding | Fix |

The frontmatter configures how the skill is triggered and what it can do. The body is what the LLM should do when the skill is active. The body is written in the same voice as a system prompt -- imperative instructions that the LLM follows.

Skills vs. System Prompt

Why not put all workflow instructions in the system prompt? Three reasons:

  1. Token budget. A system prompt with 15 workflow descriptions would consume thousands of tokens on every API call, even when only one workflow is active. Skills inject instructions only when invoked.

  2. Maintainability. Fifteen workflows in one file is unmaintainable. Fifteen skills in separate directories, each with their own tests and references, is manageable.

  3. Extensibility. Users and teams can add skills without modifying the agent's core prompts. A new deploy-check skill is a new directory, not a pull request to the system prompt.

30.2 Skill Anatomy: The YAML Frontmatter

The frontmatter is a restricted subset of YAML -- key-value pairs and simple lists, parsed without a YAML library. This restriction is deliberate: a full YAML parser would accept anchors, multi-document streams, and flow sequences that confuse skill authors and produce unhelpful error messages.

The Complete Schema

---
# Identity
name: code-review                    # Slash command name (/code-review)
description: Reviews code...         # Trigger phrases + autocomplete text
argument-hint: [file-or-directory]   # Shown in / menu

# Execution
allowed-tools: Read, Grep, Glob     # Tools that skip permission prompts
model: opus                          # Override model for this skill
effort: high                         # Override reasoning depth

# Context
context: inline                      # inline (inject into conversation) or fork (subagent)
agent: code-reviewer                 # Which subagent type for context: fork

# Activation
paths:                               # Auto-activate for matching file globs
  - "src/**/*.ts"
  - "lib/**/*.py"

# Visibility
user-invocable: true                 # Visible in / menu?
disable-model-invocation: false      # Prevent LLM from auto-triggering?
---

Field Reference

Field Type Default Purpose
name string directory name The /command name
description string "" Trigger phrases for auto-detection + autocomplete hint
argument-hint string none Placeholder shown in the / menu (e.g., [issue-number])
allowed-tools string list all Tools that skip permission prompts during this skill
model string session default Override the LLM model: opus, sonnet, haiku
effort string session default Override reasoning depth: low, medium, high, max
context string "inline" inline injects into conversation; fork spawns a subagent
agent string "general-purpose" Subagent type when context is fork

disable-model-invocation bool false Whether the LLM can auto-trigger it

Additional advanced fields exist for specialized use cases:

Field Type Purpose
memory string Memory scope: user, project, local
max-turns number Limit subagent turns for context: fork
isolation string "worktree" for git-isolated execution
timeout number Skill execution timeout in seconds
references string list Additional files loaded into context
output-format string Expected output format hint (table, diff, json)
requires string list System commands that must exist (validated at load)

The Frontmatter Parser

The parser is approximately 100 lines. It uses line-by-line scanning with two boolean flags to track multi-line list sections:

function parseFrontmatter(text: string): Frontmatter {
  const fm: Frontmatter = { paths: [] };
  let currentList: string | null = null;

  for (const rawLine of text.split('\n')) {
    const line = rawLine.trim();
    if (!line || line.startsWith('#')) continue;

    // Multi-line list items
    if (line.startsWith('- ') && currentList) {
      const value = stripQuotes(line.slice(2).trim());
      if (currentList === 'paths') fm.paths.push(value);
      if (currentList === 'allowed-tools') {
        fm.allowedTools = fm.allowedTools ?? [];
        fm.allowedTools.push(value);
      }
      continue;
    }

    // Key-value pair
    currentList = null;
    const colonIdx = line.indexOf(':');
    if (colonIdx === -1) continue;

    const key = line.slice(0, colonIdx).trim().toLowerCase();
    const rawValue = line.slice(colonIdx + 1).trim();

    switch (key) {
      case 'name': fm.name = stripQuotes(rawValue); break;
      case 'description': fm.description = stripQuotes(rawValue); break;
      case 'paths':
        if (!rawValue) currentList = 'paths';
        else fm.paths = parseInlineArray(rawValue);
        break;
      case 'allowed-tools':
        if (!rawValue) currentList = 'allowed-tools';
        else fm.allowedTools = rawValue.split(',').map(s => s.trim());
        break;
      // ... remaining fields
    }
  }
  return fm;
}

Four list formats are supported:

Format Example
Inline comma-separated allowed-tools: Read, Grep, Bash
Inline bracket paths: ["*.rs", "*.toml"]
Multi-line paths:\n - "*.rs"\n - "*.toml"
Empty key + list items paths: followed by - lines

Validation produces warnings, not errors. A skill with a missing name field loads with the directory name as fallback. A skill with context: fork but no agent field uses the general-purpose agent. The philosophy: load the skill, warn about issues, provide sensible defaults. Strict validation that blocks loading would make the system fragile for user-authored content.

The Shadowing Mechanism

When two skills share the same name, the higher-priority source wins. A project skill named code-review shadows a user skill named code-review. This is enforced by a seenNames map during loading:

function loadSkillRegistry(projectRoot: string): SkillRegistry {
  const skills: Skill[] = [];
  const seenNames = new Map<string, string>(); // name -> source

  // Priority 1: Project
  loadFromDirectory(path.join(projectRoot, '.claude', 'skills'), 'project', skills, seenNames);

  // Priority 2: User
  loadFromDirectory(path.join(os.homedir(), '.config', 'claude', 'skills'), 'user', skills, seenNames);

  // Priority 3-5: Managed, Plugin, Bundled
  // ...

  return { skills, injectCache: new Map() };
}

When a duplicate name is encountered, it is logged at info level and skipped:

Skipping user skill 'code-review' — shadowed by project:code-review

This makes the priority ordering visible in logs. Users can always find out why their skill is not loading.

Why Five Sources?

Each source serves a different audience:

  • Project skills are git-committed. Every team member gets the same workflows.
  • User skills are personal. Your research workflow might differ from your colleague's.
  • Managed skills come from organizational policy. When security mandates OWASP checks on every review, they push a managed skill.
  • Plugin skills come from third-party extensions. The marketplace enables community-built workflows.
  • Bundled skills ship with the agent. Core workflows like /verify, /simplify, /loop work out of the box.

30.4 Dynamic Context Injection

This is the skill system's most powerful feature. Skill authors can embed shell commands inside their skill body. When the skill is invoked, the commands execute and their output replaces the command directive in the prompt text.

The Syntax

The injection syntax is !`command` -- an exclamation point followed by a backtick-delimited command:

---
name: pr-summary
description: Summarize a pull request.
argument-hint: [pr-number]
---

# PR Summary

## Context
- PR diff: !`gh pr diff $ARGUMENTS`
- Changed files: !`gh pr diff $ARGUMENTS --name-only`
- PR details: !`gh pr view $ARGUMENTS --json title,body,author,labels`

## Instructions
Analyze the PR and produce:
1. A 2-3 sentence summary
2. A changes table
3. Risk assessment
4. Review checklist

When a user runs /pr-summary 42, two things happen:

  1. Argument substitution: $ARGUMENTS is replaced with 42 throughout the body.
  2. Injection resolution: Each !`...` directive is replaced with the command's stdout.

The result is a fully-materialized prompt containing the PR diff, file list, and metadata -- before the LLM starts thinking. This eliminates an entire round of tool calls.

The Resolution Pipeline

sequenceDiagram
    participant User
    participant Skill as Skill Resolver
    participant Shell as Shell Subprocess
    participant Cache as Inject Cache
    participant LLM

    User->>Skill: /pr-summary 42
    Skill->>Skill: Replace $ARGUMENTS with "42"
    Skill->>Cache: Check "gh pr diff 42" cached?
    Cache-->>Skill: Miss
    Skill->>Shell: sh -c "gh pr diff 42" (5s timeout)
    Shell-->>Skill: diff output
    Skill->>Cache: Store result
    Skill->>Cache: Check "gh pr diff 42 --name-only" cached?
    Cache-->>Skill: Miss
    Skill->>Shell: sh -c "gh pr diff 42 --name-only" (5s timeout)
    Shell-->>Skill: file list
    Skill->>Cache: Store result
    Skill->>LLM: Materialized prompt with diff + file list + PR details

Four Outcomes

Each injection command produces one of four deterministic results:

Outcome Output Example
Success Trimmed stdout The actual diff
Non-zero exit (command failed: gh pr diff 999) PR does not exist
Timeout (5s) (command timed out after 5s) Network hung
Spawn error (command error: ENOENT) gh not installed

The critical design choice is sentinel strings instead of errors. When a command fails, the LLM receives the full skill prompt with a visible failure marker. The LLM can adapt -- if it sees (command failed: gh pr diff 999), it tells the user "PR 999 doesn't exist" rather than the skill silently failing.

The Inject Cache

Identical commands within a session execute at most once. The cache key is a hash of (command, working_directory):

class InjectCache {
  private entries = new Map<string, string>();

  private key(command: string, cwd: string): string {
    return createHash('sha256').update(command + '|' + cwd).digest('hex');
  }

  get(command: string, cwd: string): string | undefined {
    return this.entries.get(this.key(command, cwd));
  }

  set(command: string, cwd: string, output: string): void {
    this.entries.set(this.key(command, cwd), output);
  }
}

The pipe separator prevents key collisions between ("a", "b|c") and ("a|b", "c"). The cache lives for the session lifetime -- no TTL. Repeated invocations of the same skill with the same arguments return instantly.

Security Implications

Dynamic injection executes shell commands on the user's machine. This is intentional -- the power comes from accessing the user's git state, CLI tools, and filesystem. Three mitigations limit the blast radius:

  1. 5-second timeout per command. No injection can hang the session.
  2. Source priority. Managed skills override plugin skills. You control what runs.
  3. MCP skills cannot use injection. Skills registered by MCP servers (external code) are blocked from the !`command` syntax. Only file-based skills (on the user's filesystem) can inject.

30.5 Auto-Activation: Path-Scoped Skills

Not all skills are invoked by slash command. Some should activate automatically when the user works with specific file types. The paths frontmatter field enables this:

---
name: api-conventions
description: API design conventions for this project.
paths:
  - "src/api/**"
  - "**/routes/**"
  - "**/endpoints/**"
user-invocable: false
disable-model-invocation: false
---

# API Conventions

When working with API files:
- Use RESTful naming: plural nouns for collections
- Return consistent error objects: { error: string, code: number }
- Validate request bodies with Zod schemas

This skill has user-invocable: false -- it does not appear in the / menu. It activates automatically when the user reads or edits files matching the glob patterns.

The Matching Algorithm

When the agent processes a user message, it checks which files are in the active context (recently read, edited, or mentioned). Auto-activating skills are matched against these paths:

function findAutoActivatingSkills(
  registry: SkillRegistry,
  activePaths: string[],
): Skill[] {
  return registry.skills.filter(skill => {
    if (skill.disableModelInvocation) return false;
    if (skill.pathTriggers.length === 0) return false;
    return activePaths.some(filePath =>
      skill.pathTriggers.some(pattern => globMatch(pattern, filePath))
    );
  });
}

Auto-activated skills inject their body into the system prompt, alongside any explicitly invoked skill. The LLM sees the instructions and follows them without the user needing to type a slash command.

Auto-Activation vs. Auto-Invocation

Behavior Description Control Field
Auto-activation Skill body injected into system prompt when matching files are in context paths field
Auto-invocation LLM decides to "run" the skill based on conversation context disable-model-invocation

A skill with paths: ["src/api/**"] and disable-model-invocation: false will both auto-activate (instructions appear when API files are active) and be auto-invocable (the LLM can trigger the full workflow). Setting disable-model-invocation: true allows auto-activation but prevents auto-invocation -- the instructions are available but the LLM cannot trigger the skill independently.

The Always-On Skill Pattern

A special case of auto-activation is the "always-on" skill -- a skill that shapes every interaction without explicit invocation. An auto-router skill that decodes user intent and routes to appropriate workflows is an example:

---
name: auto-router
description: Automatic intent detection and workflow routing.
user-invocable: false
disable-model-invocation: false
---

# Auto-Router

On every user prompt, silently:
1. Decode intent (action + target + depth)
2. Match to the best workflow
3. Execute the full workflow
4. Deliver the final result

Never ask "would you like me to..." — just execute.

This skill has no paths field -- it activates on every message because the LLM sees it in the system prompt listing and follows its instructions. The user-invocable: false flag hides it from the / menu because users do not invoke it directly.

30.6 Skill Composition: Skills + Agents

Skills define workflows. Agents provide specialized expertise. The two systems compose through the context: fork mechanism.

Inline vs. Fork Execution

graph LR
    subgraph "Inline (context: inline)"
        A1[User types /code-review] --> B1[Skill body injected into conversation]
        B1 --> C1[LLM follows instructions in main context]
        C1 --> D1[Result appears in conversation]
    end

    subgraph "Fork (context: fork)"
        A2[User types /security-audit] --> B2[Subagent spawned]
        B2 --> C2[Subagent gets skill body + model override]
        C2 --> D2[Subagent works independently]
        D2 --> E2[Result returned to main conversation]
    end

Inline execution injects the skill body into the current conversation. The main LLM follows the instructions in the same context as the ongoing dialogue. This is fast (no new API call) but consumes the main context window.

Fork execution spawns a subagent with the skill body as its prompt. The subagent can use a different model (e.g., Opus for complex security analysis), has its own context window, and runs independently. The result is returned to the main conversation when complete.

When to Fork

Use When Inline Fork
Quick, simple workflow Yes No
Needs context from conversation Yes No
Complex, multi-step analysis No Yes
Needs different model (Opus for security) No Yes
Long-running (might background) No Yes
Needs isolated context (worktree) No Yes

The agent field selects the subagent type (as defined in .claude/agents/security-reviewer.md). The model and effort fields override the subagent's default settings. The max-turns field limits how many LLM turns the subagent can take. The isolation: worktree field runs the subagent in a git worktree, preventing its file edits from affecting the main working tree.

30.7 The Skill vs. Agent Decision Framework

Skills and agents serve different purposes and the distinction matters for system design:

graph TD

    Q1 -->|Yes| Q2{Triggered by /command?}
    Q2 -->|Yes| Skill[Create a Skill]
    Q2 -->|No| AutoSkill[Skill with paths: auto-activation]

    Q1 -->|No| Q3{Requires judgment?}
    Q3 -->|Yes| Agent[Create an Agent]
    Q3 -->|No| Q4{Needs model override?}
    Q4 -->|Yes| Agent

Criterion Skill Agent
When to use Repeatable workflow with known steps Specialized expertise requiring judgment
Authored as Markdown file with frontmatter Markdown file with system prompt

The practical distinction: skills describe what to do (instructions for the LLM). Agents describe who to be (a persona with specialized knowledge). A skill says "perform these 5 steps." An agent says "you are a security expert -- evaluate this code."

Skills can invoke agents through context: fork. Agents cannot invoke skills directly. This creates a clean dependency direction: skills are the user-facing entry point, and agents are the backend specialists that skills can delegate to.

30.8 Designing Skills That Trigger Reliably

The description field is the key to reliable triggering. It serves two purposes:

  1. LLM auto-detection: The LLM reads the description and decides whether to activate the skill based on the user's prompt.
  2. Autocomplete: The description appears next to the skill name in the / menu.

Writing Good Descriptions

A good description lists every trigger phrase explicitly:

# Bad: vague, misses common phrases
description: Reviews code quality.

# Good: explicit trigger phrases
description: Reviews code for bugs, security, performance.
  Use when user says "review", "check my code",
  "code review", "find bugs", "audit this file",
  "look at this code", "is this good".

The LLM matches user prompts against descriptions. If the user says "look at this code" but the description only mentions "review code," the skill may not activate. Listing explicit trigger phrases eliminates this failure mode.

The disable-model-invocation Guard

Skills with side effects should not auto-trigger:

# /loop: starts recurring tasks -- should not auto-trigger
disable-model-invocation: true

# /remember: writes to persistent memory -- should not auto-trigger
disable-model-invocation: true

# /batch: spawns parallel agents -- should not auto-trigger
disable-model-invocation: true

Without this guard, a user saying "remember to check the tests" might trigger the /remember skill to write to persistent memory, when they simply wanted the agent to keep something in mind for the current conversation.

30.9 Token Budget Management

Skills consume context window tokens. A skill with dynamic injections can expand to thousands of lines. The system enforces a budget to prevent skills from monopolizing the context window:

function shouldTruncateSkill(
  resolvedBody: string,
  contextBudget: number,
  usedTokens: number,
): { truncate: boolean; maxChars: number } {
  const estimated = estimateTokens(resolvedBody);
  const available = contextBudget - usedTokens;
  const skillBudget = Math.floor(available * 0.3); // 30% cap

  if (estimated <= skillBudget) {
    return { truncate: false, maxChars: resolvedBody.length };
  }

  const charsPerToken = resolvedBody.includes('```') ? 3.5 : 4.0;
  return { truncate: true, maxChars: Math.floor(skillBudget * charsPerToken) };
}

The 30% cap is consistent with the file mention budget from Chapter 28. It prevents a /pr-summary on a large PR from consuming the entire context window, leaving no room for the LLM to reason.

When truncation is needed, the system truncates from the end of the resolved body and appends a (truncated -- showing first N characters) marker. The LLM knows it is working with partial data and can request more if needed.

30.10 System Prompt Integration

Skills are advertised to the LLM through the system prompt. The skill registry generates an XML listing of available skills:

<available_skills>
<skill>
  <name>code-review</name>
  <description>Reviews code for bugs, security, performance.</description>
  <location>project</location>
  <argument-hint>[file-or-directory]</argument-hint>
  <allowed-tools>Read, Grep, Glob, Bash</allowed-tools>
</skill>
<skill>
  <name>fix-issue</name>
  <description>Fix a GitHub issue by number.</description>
  <location>project</location>
  <context>fork</context>
  <argument-hint>[issue-number]</argument-hint>
</skill>
</available_skills>

The XML format was chosen because LLMs reliably parse angle-bracket structures. Each entry includes enough information for the LLM to decide when to suggest a skill: name, description (trigger phrases), source location, context mode, and argument hint.

Only user-invocable skills appear in this listing. Skills with user-invocable: false (auto-activating skills) are not listed -- they inject their content directly when path patterns match.

30.12 Building Your Own Skill System: Phased Implementation

Phase 1: Minimal Viable Skills

  1. File-based loading from one directory. Parse SKILL.md with key-value frontmatter.
  2. Slash command dispatch. Parse /name args, look up skill, inject body into conversation.
  3. $ARGUMENTS substitution. Simple string replacement.
  4. Three bundled skills: verify, simplify, and one domain-specific skill.

This gives you a working skill system in a few hundred lines. Users can immediately create custom workflows by dropping SKILL.md files into a directory.

Phase 2: Multi-Source and Injection

  1. Two-directory loading (project + user) with shadowing.
  2. Dynamic context injection (!`command`). Add the inject cache.
  3. Auto-activation via paths globs.
  4. Token estimation to prevent skills from consuming the entire context.

This adds the power features. Dynamic injection is the biggest force multiplier -- it turns static instructions into context-aware workflows.

Phase 3: Advanced Features

  1. Fork mode for skills that spawn subagents.
  2. MCP skill registration for dynamic skills from external servers.
  3. Managed skills from organization policy.
  4. Plugin skills from the marketplace.
  5. Skill metrics and auto-improvement with heuristic analysis.

Each phase is independently shippable. Ship Phase 1 in your first release, gather user feedback, and add Phases 2-3 as the system matures.

30.13 Key Takeaways

Skills are the user-facing extensibility layer. Hooks automate what happens around actions. Skills define what the agent does in the first place. Together, they make the agent extensible without code changes.

The loading pipeline's priority ordering is the trust foundation. Project skills override user skills. Managed skills override plugin skills. Get this wrong and users lose confidence that their project's workflows work consistently.

Dynamic injection is the most powerful feature. The !`command` syntax turns static prompts into dynamic, context-aware instructions. The 5-second timeout, sentinel strings for failures, and the inject cache are the safety nets. Implement this feature carefully.

The frontmatter parser deliberately avoids a YAML dependency. The restricted subset (key-value pairs and simple lists) covers everything skill authors need. A full YAML parser would add complexity, confusing error messages, and 50KB of compiled library for features nobody uses.

auto-activation transforms skills from tools to standards. A path-scoped skill that activates whenever API files are touched becomes a living style guide that the LLM follows automatically. This is how team conventions scale without manual enforcement.

The skill vs. agent distinction is about instructions vs. expertise. Skills say "do these steps." Agents say "be this expert." Skills can delegate to agents through context: fork. This creates a clean architecture: skills are the user-facing entry points, agents are the backend specialists.

Token budget management is non-negotiable. Without the 30% cap, a single /pr-summary on a large PR would leave no room for the LLM to think. Skills that expand dynamically must be checked against the context budget before injection.

The skill system, combined with the hook architecture from Chapter 29, the command router from Chapter 28, and the terminal UI from Chapter 27, completes the extensibility story for an AI CLI agent. The agent ships with a powerful engine. Skills and hooks let every user, team, and organization customize what that engine does without forking the code.
