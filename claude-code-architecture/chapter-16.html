Chapter 16: Tool Extensibility via MCP

A closed tool set is a ceiling on an agent's usefulness. The built-in tools — file read, file write, grep, glob, bash — cover the core operations of a software engineer. But software engineering does not happen in a vacuum. Engineers query databases, interact with cloud APIs, manage CI/CD pipelines, search documentation, control browsers, and interface with dozens of domain-specific tools. No agent team can build and maintain tools for every possible integration.

The Model Context Protocol (MCP) solves this problem by defining a standard interface through which external servers expose tools, resources, and prompts to an AI agent at runtime. Instead of building a database query tool into the agent, you run an MCP server that wraps your database client. Instead of building a Jira integration, you run an MCP server that wraps the Jira API. The agent discovers these tools at startup, presents them to the model alongside its built-in tools, and invokes them through the same pipeline that handles built-in tool calls.

This chapter examines the architectural decisions that make tool extensibility work in production: dynamic registration, namespace isolation, capability annotations, result handling, security boundaries, and the design principles for MCP tools that are safe, discoverable, and composable.

16.1 The Extensibility Problem

Before examining the solution, let us understand the problem clearly. An AI CLI agent with a fixed tool set faces four constraints:

Integration scope. Every new integration (database client, cloud API, project management tool) requires the agent team to build, test, and maintain a dedicated tool. With hundreds of potential integrations and frequent API changes, this approach does not scale.

Deployment coupling. Built-in tools ship with the agent. Adding a new tool means releasing a new agent version. Users who need a custom integration must wait for the agent team to prioritize it — or fork the agent and maintain their own version.

Domain specificity. Different users need different tools. A data scientist needs tools for notebooks and data pipelines. A DevOps engineer needs tools for Kubernetes and Terraform. A security researcher needs tools for vulnerability scanners. Building all of these into a single agent bloats the binary and the model's tool context for every user.

Organizational control. Enterprise users need to provision agent capabilities through their existing infrastructure — corporate identity providers, policy management systems, approved vendor lists. A fixed tool set cannot accommodate this governance model.

MCP addresses all four constraints by moving tool implementation outside the agent. The agent provides the runtime (transport, discovery, execution, security), and external servers provide the tools.

16.2 Protocol Architecture

MCP defines a client-server architecture where the AI agent is the client and tool providers are servers. Communication follows a JSON-RPC 2.0 protocol over multiple transport types:

    subgraph "AI CLI Agent (MCP Client)"
        MC[MCP Client Manager]
        TD[Tool Discovery]
        TE[Tool Execution]
        PS[Permission System]
    end

    subgraph "Transport Layer"
        T1[stdio: Local processes]
        T2[HTTP: Remote servers]
        T3[WebSocket: Real-time]
        T4[In-process: Embedded]
    end

    subgraph "MCP Servers"
        S1["Database Server<br/>(PostgreSQL, SQLite)"]
        S2["Cloud API Server<br/>(AWS, Azure, GCP)"]
        S3["Browser Automation<br/>(Playwright)"]
        S4["Custom Internal Tools"]
    end

    MC --> T1 & T2 & T3 & T4
    T1 --> S1
    T2 --> S2
    T3 --> S3
    T4 --> S4
    TD --> MC
    TE --> MC
    PS --> TE

The Handshake

When a client connects to a server, they exchange capability declarations:

Client → Server: initialize
  {
    clientInfo: { name: "agent-name", version: "1.0" },
    capabilities: { roots: {}, elicitation: {} }
  }

Server → Client: initialize response
  {
    serverInfo: { name: "db-server", version: "2.0" },
    capabilities: { tools: {}, resources: {} },
    instructions: "This server provides PostgreSQL query tools..."
  }

The capability exchange tells each side what the other supports. A client that declares elicitation capability can receive user input requests from the server. A server that declares tools capability can provide tool definitions. This negotiation prevents runtime failures from unsupported operations.

Transport Types

The protocol supports multiple transports because MCP servers run in fundamentally different environments:

Transport Protocol Use Case Connection Model
stdio stdin/stdout pipes Local processes (Python scripts, Node modules) One process per server
Streamable HTTP HTTP POST/GET Remote API servers Stateless or session-based
WebSocket WS/WSS Real-time bidirectional servers Persistent connection
In-process Function calls Embedded servers (same process) Zero-copy message passing

stdio is the most common transport for local tools. The agent spawns a child process and communicates over stdin/stdout. This is simple, universal, and requires no network configuration. The limitation is that stdio servers are process-per-server — each server is a separate child process with its own memory footprint.

Streamable HTTP is the current standard for remote servers. The client sends tool call requests as HTTP POST requests and receives responses. Long-running operations can use Server-Sent Events (SSE) for streaming results. This transport supports standard HTTP infrastructure — load balancers, authentication proxies, CDNs.

WebSocket provides persistent bidirectional communication for servers that need to push updates to the client. This is useful for monitoring tools, real-time collaboration servers, and tools that maintain long-lived sessions.

In-process transport eliminates serialization overhead for servers that run inside the agent process. Instead of JSON-RPC over pipes, messages are passed as JavaScript objects via queueMicrotask(). This saves approximately 325MB of memory per server (the cost of spawning a separate Node/Bun process) and eliminates serialization latency.

The queueMicrotask() call in in-process transports is architecturally significant. Without it, a synchronous request-response cycle would overflow the call stack — the client sends a request, the server synchronously processes it and sends a response, the client synchronously processes the response and sends another request, and so on. The microtask boundary breaks this chain by deferring message delivery to the next microtask checkpoint.

16.3 Dynamic Tool Registration

MCP tools are not known at compile time. They are discovered at runtime through the server's tools/list endpoint and can change during a session through notification events.

Discovery at Startup

During connection establishment, the client queries each server for its available tools:

Client → Server: tools/list
Server → Client:
  {
    tools: [
      {
        name: "query",
        description: "Execute a SQL query against the database",
        inputSchema: { type: "object", properties: { sql: { type: "string" } } },
        annotations: { readOnlyHint: false, destructiveHint: true }
      },
      {
        name: "list_tables",
        description: "List all tables in the database",
        inputSchema: { type: "object", properties: {} },
        annotations: { readOnlyHint: true }
      }
    ]
  }

Each tool definition includes: - name: The tool's identifier within the server namespace - description: Human-readable text explaining what the tool does (capped at 2,048 characters) - inputSchema: JSON Schema defining the tool's parameters - annotations: Capability hints that inform the permission system

The client converts each MCP tool into its internal tool format, wrapping the MCP-specific invocation logic in the same interface that built-in tools implement. From the model's perspective, MCP tools are indistinguishable from built-in tools except for their namespaced names.

Notification-Driven Updates

Servers can modify their tool set mid-session by sending a tools/listChanged notification. The client invalidates its tool cache, re-fetches the tool list, and updates the model's available tools. This enables dynamic tool sets — a server that discovers new database tables can expose query tools for each table as they appear.

Three notification types drive different cache invalidations:

Notification Cache Cleared What Changes
ToolListChanged Tool definitions Tools available to the model
ResourceListChanged Resource definitions + skills Files and data the server provides
PromptListChanged Prompt templates + skills Pre-built prompt templates

Deferred Loading

Not every MCP tool needs to be in the model's active context. A server with 200 tools would consume a significant portion of the model's context window just with tool descriptions. Deferred loading solves this through a search hint mechanism:

{
  "name": "complex_analysis_tool",
  "description": "Performs detailed statistical analysis...",
  "_meta": {
    "anthropic/searchHint": "statistics, regression, correlation, p-value"
  }
}

Tools with searchHint metadata are not loaded into the model's context by default. Instead, their names and search hints are stored in a lightweight index. When the user's prompt or conversation context matches the search hints (keyword matching), the full tool definition is loaded. This preserves prompt cache efficiency — non-deferred MCP tools disable global prompt caching because they vary per user.

The inverse mechanism — anthropic/alwaysLoad: true — forces a tool into the model's context regardless of relevance scoring. Use this sparingly for tools that the model should always know about, like authentication or session management tools.

16.4 Namespace Isolation

When tools come from multiple servers, name collisions are inevitable. Two servers might both expose a tool called query. Without namespacing, the agent cannot distinguish between them.

The Naming Convention

MCP tools use a three-part namespaced name:

mcp__<server_name>__<tool_name>

The double-underscore delimiter separates the three segments: the mcp prefix, the server name, and the tool name. Both server and tool names are normalized to match [a-zA-Z0-9_-]{1,64} — non-alphanumeric characters are replaced with underscores.

Examples: - mcp__postgres__query — The "query" tool from the "postgres" server - mcp__github__create_pr — The "create_pr" tool from the "github" server - mcp__browser__navigate — The "navigate" tool from the "browser" server

Permission Rule Integration

The namespace convention integrates directly with the permission system. Rules can target individual tools or entire servers:

Rule Matches
mcp__postgres__query Only the query tool from the postgres server
mcp__postgres All tools from the postgres server
mcp__postgres__* All tools from the postgres server (explicit wildcard)

Server-level rules are particularly useful for enterprise policy. An admin can deny all tools from an untrusted server with a single rule: deny: ["mcp__untrusted_server"].

Known Limitation: Double-Underscore Ambiguity

The naming scheme has a known limitation: if a server name contains __, parsing becomes ambiguous. mcp__my__server__tool could mean server "my" with tool "server__tool" or server "my__server" with tool "tool". The parser splits on the first two __ boundaries, choosing the first interpretation. This is rarely a problem in practice because server names typically do not contain double underscores, but it is a design constraint that MCP server authors should be aware of.

16.5 Capability Annotations

MCP tools carry annotations that inform the agent's security and scheduling systems about the tool's behavior. These annotations are hints, not guarantees — the server declares them, and the agent uses them to make better decisions.

graph TD
    ANN[Tool Annotations] --> RO[readOnlyHint]
    ANN --> DEST[destructiveHint]
    ANN --> OW[openWorldHint]
    ANN --> IDEM[idempotentHint]

    RO -->|true| RO_EFF["Auto-allow in permissive modes<br/>Safe to parallelize"]
    RO -->|false/absent| RO_DEF["Require permission check<br/>Serialize with other writes"]

    DEST -->|true| DEST_EFF["Always require explicit approval<br/>Never auto-allow"]
    DEST -->|false/absent| DEST_DEF["Normal permission flow"]

    OW -->|true| OW_EFF["Tool accesses external systems<br/>Results may contain untrusted data"]
    OW -->|false/absent| OW_DEF["Tool operates locally<br/>Results are trusted"]

    IDEM -->|true| IDEM_EFF["Safe to retry on failure<br/>Duplicate calls are harmless"]
    IDEM -->|false/absent| IDEM_DEF["Retry with caution"]

readOnlyHint

When true, the tool does not modify any state. The agent can auto-allow it in permissive modes (similar to built-in Read tools) and execute it concurrently with other read-only tools. The query engine uses this hint to parallelize MCP tool calls — two read-only MCP tools can run simultaneously, but a destructive MCP tool serializes with everything else.

destructiveHint

When true, the tool can cause irreversible changes. The agent requires explicit user approval regardless of permission mode. Even in bypass mode, destructive MCP tools trigger a confirmation prompt. This is the MCP equivalent of the bypass-immune safety checks described in Chapter 9.

openWorldHint

When true, the tool accesses systems outside the agent's control — external APIs, databases, cloud services. This hint tells the agent that the tool's results may contain untrusted data (from the perspective of prompt injection defense) and that the tool's effects may be visible to external observers.

idempotentHint

When true, calling the tool multiple times with the same arguments produces the same result. The agent can safely retry failed calls without risk of duplicate side effects. This is important for error recovery — if a tool call times out, the agent can retry it if the tool is idempotent, but should report the failure to the user if it is not.

The Trust Boundary

Annotations are self-reported by the server. A malicious server could declare readOnlyHint: true on a tool that actually deletes data, bypassing the permission system's protection for write operations. This is why annotations are treated as hints, not guarantees. Defense in depth — the same principle that protects the Bash tool — applies here:

  1. Annotations influence permission decisions but do not override deny rules
  2. MCP tools from project-scoped configurations require explicit user approval before connection
  3. Enterprise policy can deny entire servers regardless of their self-reported capabilities
  4. The auto-mode classifier evaluates MCP tool calls in conversation context, independent of annotations

16.6 Result Handling

MCP tool results cross a trust boundary — they come from an external server that may return malicious content (prompt injection), oversized content (context exhaustion), or binary content (images, PDFs) that needs special handling.

Size Limits

MCP tool output is capped at a configurable token limit (default 25,000 tokens). The enforcement uses the same two-tier approach as built-in Read tools:

  1. Heuristic estimate: A rough token count (bytes / 4) determines if the output is likely within limits. If the estimate is under 50% of the cap, the output passes without tokenizer API call.
  2. Precise count: If the heuristic is inconclusive, the actual tokenizer computes an exact count.

For text content, truncation preserves the beginning of the output (unlike Bash output, which preserves the end). The rationale is different: Bash command output has its summary at the end (test results, build status), while MCP tool output typically has the most relevant information at the beginning (query results, API responses).

For array content (multiple content blocks), truncation removes trailing blocks until the total is within limits. Image blocks are compressed before removal is attempted.

Timeout Management

MCP tool calls have a two-tier timeout:

Timeout Default Purpose
Connection timeout 30 seconds Establishing the transport connection
Tool call timeout 10 minutes (configurable, can be much longer) Executing the tool and receiving the result

The tool call timeout is deliberately permissive because MCP servers can perform long-running operations — training models, processing large datasets, running extensive test suites. The timeout is a safety net against stuck operations, not a bound on expected execution time.

Timeouts are implemented through combined abort signals that merge the per-tool timeout with the parent abort signal (user pressing Ctrl+C). Whichever fires first wins, ensuring that tool calls are terminated promptly regardless of which signal triggers.

Binary Content

MCP servers can return binary content — images, PDFs, audio files. The agent detects binary responses by content type and persists them to a tool-results directory on disk rather than injecting them directly into the conversation. The file path is returned as the tool result, allowing the model to use built-in tools (Read for images and PDFs) to examine the content.

This indirection serves two purposes: it prevents binary blobs from consuming conversation context, and it applies the agent's existing content-specific handling (image compression, PDF page extraction) to MCP-sourced content.

16.7 Security Boundaries

MCP servers are external code running on the user's machine or on remote servers. The security boundary between the agent and an MCP server must be clearly defined and enforced.

What MCP Servers CAN Do

  • Expose tools with arbitrary input schemas and behavior
  • Return arbitrary text and binary content as tool results
  • Request user input through the elicitation mechanism
  • Provide instructions that are injected into the agent's system prompt
  • Notify the agent of tool, resource, and prompt changes
  • Access the file system (stdio servers run as child processes with user privileges)
  • Access the network (unless restricted by sandbox or firewall)

What MCP Servers CANNOT Do

  • Bypass the agent's permission system — MCP tool calls go through the same permission pipeline as built-in tools
  • Override deny rules from enterprise policy — deny rules take absolute precedence regardless of the tool source
  • Read the agent's conversation history — the server only receives the specific tool call arguments, not the full conversation
  • Modify the agent's configuration — the server cannot change permission rules, settings, or other server configurations
  • Execute arbitrary code in the agent process — the transport layer is a message-passing boundary, not a code execution boundary
  • Auto-connect without user approval (project-scoped servers) — servers defined in repository configuration require explicit user consent

The Project Server Approval Gate

Servers defined in a project's configuration file (.mcp.json committed to a repository) are untrusted by default. A malicious repository could include MCP server configurations that connect to attacker-controlled servers, enabling data exfiltration or prompt injection.

The approval gate requires explicit user action before connecting to project-scoped servers:

graph TD
    A[Project .mcp.json<br/>defines MCP server] --> B{User approval status?}
    B -->|Approved| C[Connect to server]
    B -->|Rejected| D[Skip server]
    B -->|Pending| E[Show placeholder tool]
    E --> F[User invokes placeholder]
    F --> G[Approval dialog]
    G -->|Approve| C
    G -->|Reject| D

A critical security detail: the approval check reads from user, local, flag, and policy settings but NOT from project settings. This prevents a repository from approving its own MCP servers — the approval must come from a source the repository cannot control.

SSRF Protection

Remote MCP servers (HTTP, WebSocket) are validated against SSRF attacks before connection. The validation blocks private IP ranges and cloud metadata endpoints:

Blocked Range Reason
10.0.0.0/8 Private network
172.16.0.0/12 Private network
192.168.0.0/16 Private network
169.254.0.0/16 Link-local / cloud metadata
fc00::/7 IPv6 unique local
fe80::/10 IPv6 link-local

SSRF validation runs at connection time, not at configuration time. This prevents DNS rebinding attacks where a hostname resolves to a safe IP during configuration but resolves to a private IP during connection.

HTTPS is required for all non-localhost remote connections. HTTP connections to non-localhost URLs are rejected to prevent credential interception on untrusted networks.

16.8 Permission Integration

MCP tool permissions integrate with the existing permission system through the same pipeline that handles built-in tools. From the permission system's perspective, an MCP tool is just another tool with a namespaced name.

Permission Evaluation

When the model invokes mcp__postgres__query, the permission pipeline evaluates:

  1. Deny rules: Is mcp__postgres__query or mcp__postgres in the deny list?
  2. Ask rules: Is there an ask rule for this tool or server?
  3. Tool annotations: Is the tool marked readOnlyHint: true (auto-allow in permissive modes)?
  4. Allow rules: Is there an allow rule for this tool or server?
  5. Mode default: What does the current permission mode say about unrecognized tools?

The evaluation follows the same deny-first, allow-second ordering as built-in tools. Enterprise deny rules override all other considerations. Server-level rules apply to all tools from that server.

Auto-Mode Classifier Integration

In auto mode, MCP tool calls that are not resolved by rules enter the AI classifier. The classifier receives the tool name, description, arguments, and conversation context. It evaluates whether the tool call is consistent with the user's intent.

MCP tools present a unique challenge for the classifier: it cannot inspect the tool's implementation. For a built-in Bash command, the classifier can analyze the command structure. For an MCP tool, it can only evaluate the tool's declared description and the arguments. This makes the destructiveHint and openWorldHint annotations important — they provide the classifier with information it cannot determine independently.

Rule Suggestions

When the permission system prompts the user to approve an MCP tool call, it suggests permission rules at two granularity levels:

  • Tool-level: allow: ["mcp__postgres__query"] — approve only this specific tool
  • Server-level: allow: ["mcp__postgres"] — approve all tools from this server

The suggestion defaults to tool-level (more restrictive). The user can upgrade to server-level if they trust the entire server. This follows the principle of least privilege — start with the narrowest permission and broaden only when requested.

16.9 Connection Lifecycle Management

MCP servers have complex lifecycles: they must be started, connected, health-checked, reconnected on failure, and cleanly shut down. Managing this lifecycle reliably is one of the hardest engineering challenges in MCP integration.

Startup Sequencing

MCP server connections are batched at startup with different concurrency limits for local and remote servers:

Server Type Concurrency Rationale
Local (stdio) 3 Each spawns a child process — resource contention at higher concurrency
Remote (HTTP/WS) 20 Network connections parallelize well

This tuning prevents the "thundering herd" problem where spawning 20 local MCP servers simultaneously overwhelms the system's process table and file descriptors.

Reconnection with Backoff

Remote servers disconnect due to network issues, server restarts, session expiry, and load balancer rotations. The reconnection strategy uses exponential backoff:

Attempt 1: Wait 1 second
Attempt 2: Wait 2 seconds
Attempt 3: Wait 4 seconds
Attempt 4: Wait 8 seconds
Attempt 5: Wait 16 seconds (capped at 30 seconds)
After 5 failures: Transition to Failed state

Local servers (stdio) do not reconnect. If the child process dies, restarting it requires re-initialization that the client cannot guarantee is idempotent. Instead, local server failures are reported to the user, who can restart the server manually or fix the underlying issue.

Graceful Shutdown

Stdio server cleanup uses signal escalation:

  1. SIGINT (100ms timeout) — polite "please stop"
  2. SIGTERM (400ms timeout) — standard termination
  3. SIGKILL — force kill (cannot be caught)

Between signals, the system polls with kill(pid, 0) every 50ms to detect if the server has already exited. A 600ms absolute timeout ensures cleanup never blocks indefinitely.

Cache Invalidation

When a server disconnects, all associated caches are invalidated — tool definitions, resource definitions, prompt templates, and the connection itself. This prevents stale tool objects (whose call() closures reference a dead client) from persisting across reconnections.

16.10 Designing MCP Tools

For engineers building MCP servers, the design of individual tools significantly affects how well they integrate with AI agents. Here are the principles that emerge from production MCP deployments:

Be Specific in Descriptions

The model selects tools based on their descriptions. A description of "Manages database operations" tells the model nothing about what the tool actually does. A description of "Executes a read-only SQL SELECT query against the PostgreSQL database and returns results as a JSON array of row objects" tells the model exactly when and how to use the tool.

Keep descriptions under 2,048 characters. Longer descriptions are truncated, potentially losing critical information about constraints, error cases, or expected input format.

Use Annotations Honestly

Declaring readOnlyHint: true on a tool that modifies state creates a security vulnerability — the permission system may auto-allow the tool based on this annotation. Declaring destructiveHint: true on a read-only tool creates unnecessary friction — the user will be prompted for approval on every call.

Accurate annotations make the agent more useful and more secure. Inaccurate annotations make it worse at both.

Return Structured Data

Tools that return structured data (JSON objects with typed fields) are more useful to the model than tools that return free-form text. The model can extract specific fields, compare values, and compose results with other tools. A tool that returns "Found 42 matching records in table 'users'" is less useful than one that returns {"count": 42, "table": "users", "query_time_ms": 15}.

Handle Errors Explicitly

When a tool call fails, return a structured error with a clear error code and message. The model uses error information to decide whether to retry (transient error), try a different approach (permanent error), or report to the user (configuration error).

Do not return errors as successful results with error text in the output. The model may not recognize the text as an error and may attempt to use the "result" in subsequent operations.

Keep Tools Focused

A tool that does one thing well is more useful than a tool that does many things poorly. If your server provides database access, separate "execute query" from "list tables" from "describe table schema." The model can compose focused tools into complex workflows. It cannot decompose a monolithic tool into the specific operation it needs.

16.11 Design Lessons

MCP extensibility transforms an AI CLI agent from a product into a platform. The architectural decisions examined in this chapter enable that transformation:

1. Protocol over plugin. MCP uses a network protocol (JSON-RPC) rather than a plugin API (shared libraries, dynamic loading). This means servers can be written in any language, run in any process, and deploy on any machine. The cost is serialization overhead. The benefit is universal compatibility and process isolation.

2. Namespace everything. The mcp__server__tool naming convention prevents collisions and enables per-server permission rules. Any extensibility mechanism that does not namespace its identifiers will eventually have collision problems at scale.

3. Treat annotations as hints, not guarantees. Self-reported capabilities from external servers cannot be trusted unconditionally. Use them to optimize decisions (auto-allow read-only tools, prompt for destructive tools) but maintain defense in depth (deny rules still override annotations, the classifier still evaluates in context).

4. Gate untrusted sources. Project-scoped MCP servers require explicit user approval because the project is a lower trust level than the user. This is the same principle that drives the permission system's deny-first evaluation: higher trust levels override lower trust levels, never the reverse.

5. Handle lifecycle explicitly. Connection, disconnection, reconnection, and shutdown are not edge cases — they are the normal operating conditions of a distributed system. Build retry logic, cache invalidation, and graceful degradation into the core architecture, not as afterthoughts.

6. Batch state updates. When 20 servers connect in rapid succession, 20 individual state updates cause 20 React renders. Batching updates to a 16ms window (one frame at 60fps) reduces this to one or two renders. Any system that processes concurrent events should batch its state updates.
