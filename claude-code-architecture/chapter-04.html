Chapter 4: Startup Architecture

Why 13 Phases, Not 1 Big init()

Every CLI tool faces a tension: do everything at startup so the first interaction is fast, or defer everything until needed so startup is fast. Claude Code resolves this by doing neither. Its startup is a 13-phase pipeline that completes in roughly 400 milliseconds -- each phase engineered to run the minimum work required at that moment, overlap I/O with computation wherever possible, and exit early when the full pipeline isn't needed.

The number 13 isn't sacred. It's the natural result of decomposing "get from binary invocation to blinking cursor" into steps that have real dependency ordering. You can't parse CLI flags before reading process.argv. You can't merge settings before reading the settings files. You can't show the trust dialog before knowing which directory the user is in. Each phase exists because it depends on something the previous phase produced -- or because it produces something a later phase needs.

This chapter dissects the architecture of that pipeline. We'll examine why the phases are ordered the way they are, how parallel I/O shaves 65ms off every startup, why fast-path exits exist for trivial operations, and how a 400ms budget constrains every design decision.

The key insight: phases that have no data dependency on each other overlap in time. The MDM subprocess (Phase 1), keychain subprocess (Phase 2), and module evaluation (Phase 4) all run concurrently. The rendezvous point -- Phase 5.5's preAction hook -- is where the async results are collected. This overlap is the single largest optimization in the entire startup path.

Fast-Path Exits: Paying Only for What You Use

Not every invocation needs the full pipeline. The entry point (cli.js) checks for fast-path exits before importing any heavy modules:

Invocation What Loads Approximate Time
claude --version Nothing -- prints and exits ~5ms
claude mcp serve MCP server module only ~80ms
claude bridge / claude rc Bridge module only ~90ms
claude --tmux --worktree Tmux + worktree module ~60ms
claude (interactive) Full 13-phase pipeline ~390ms
claude -p "prompt" Phases 0-12 (no REPL) ~225ms

The architectural decision: the entry point is a router, not an initializer. It reads just enough of process.argv to determine which path to take, then imports only the modules needed for that path.

This pattern has a concrete implementation cost: the entry point cannot use any framework features. No configuration, no logging, no telemetry. It's raw process.argv parsing and conditional import() statements. Any module imported before the routing decision delays every invocation -- including the 5ms --version path.

The Cost of a Misplaced Import

Consider what happens if you add an innocent import at the top of cli.js:

// DON'T DO THIS: adds ~135ms to every invocation
import { logger } from './utils/logger.js';

async function main() {
  if (args[0] === '--version') {
    console.log(VERSION);  // This now takes 140ms instead of 5ms
    return;
  }
  // ...
}

That single import transitively pulls in the logging framework, which depends on configuration, which depends on settings file I/O. Suddenly claude --version takes 140ms. In a CI/CD pipeline running claude --version as a health check across 50 containers, that's 7 seconds of wasted time per deployment.

The discipline is strict: top-level imports in the entry point are limited to Node.js built-ins and build constants. Everything else is a dynamic import() behind a conditional.

Parallel I/O During Startup

The most architecturally significant optimization is overlapping I/O with synchronous computation. Three operations start as fire-and-forget async calls before the heavy module import:

The pattern is called speculative prefetch: start I/O operations whose results you'll need later, then do unrelated synchronous work while the I/O completes. When you finally need the results, they're already waiting in resolved promises.

The Prefetch-Rendezvous Pattern

The implementation follows a consistent shape across all three prefetched operations:

// 1. Module-level promise holder
let prefetchPromise: Promise<Result> | null = null;

// 2. Fire function (called early)
export function startPrefetch(): void {
  prefetchPromise = doExpensiveIO();
}

// 3. Retrieve function (called late, with fallback)
export function getPrefetchedResult(): Promise<Result> {
  return prefetchPromise ?? doExpensiveIO();
}

Three properties make this pattern safe:

Idempotent fallback. If the prefetch was never started (different platform, different code path), the retrieve function falls back to a synchronous call. The caller never needs to know whether the result was prefetched.

Promise-based coordination. No callbacks, no events, no shared mutable state. The prefetch stores a promise; the consumer awaits it. If the promise is already resolved, the await completes synchronously (within the same microtask).

Failure isolation. Each prefetch catches its own errors and returns a safe default (empty object, null). A failed keychain read doesn't crash the MDM read or the module evaluator.

What Gets Prefetched and Why

Operation Subprocess Time Savings
MDM settings (macOS) plutil -convert json ~20ms 20ms (overlaps with 135ms eval)
MDM settings (Windows) reg query ~25ms 25ms (overlaps with 135ms eval)
OAuth keychain security find-generic-password ~30ms 30ms per read
API key keychain security find-generic-password ~30ms 30ms per read
API preconnect TCP + TLS handshake ~150ms 100-200ms on first API call

Total savings: ~65ms from keychain prefetch alone, plus the MDM read is completely hidden behind module evaluation. The API preconnect is fired during init() and completes during the REPL launch phase, saving 100-200ms on the user's first prompt.

Deferred Imports: Loading Only What You Need

Beyond the entry-point routing, Claude Code uses dynamic imports throughout the init() pipeline to avoid loading modules that may not be needed:

// Phase 6.5, Step 4: Analytics loaded only when init runs
void Promise.all([
  import('./services/analytics/firstPartyEventLogger.js'),
  import('./services/analytics/growthbook.js'),
]).then(([fp, gb]) => {
  fp.initialize1PEventLogging();
  gb.onGrowthBookRefresh(() => {
    void fp.reinitialize1PEventLoggingIfConfigChanged();
  });
});

This is fire-and-forget (the void prefix). Analytics module evaluation happens in parallel with the remaining init steps. If the import takes 50ms, it overlaps with Steps 5-16 of init().

The deferred import pattern appears in three flavors:

Pattern When to Use Example
await import() Result needed before proceeding import('./main.js') in cli.js
void import().then() Fire-and-forget side effect Analytics initialization
Conditional import() Feature-gated code if (isRemoteSession()) await import('./proxy.js')

The cost model is straightforward: a dynamic import() in a bundled application resolves to a function call that evaluates the module's code. In an unbundled application, it also involves filesystem I/O. Bundlers like Bun can partially evaluate the module at build time, but the runtime cost is still proportional to the module's top-level code.

The Import Budget

On a modern MacBook, module evaluation costs approximately:

Module Category Typical Size Eval Time
Utility module (pure functions) 200-500 lines <1ms
Service module (class + deps) 1,000-3,000 lines 2-5ms
UI framework (React/Ink) 5,000-10,000 lines 15-30ms
Full transitive graph (main.tsx) ~16,800 lines ~135ms

The 135ms budget for the full import graph is the floor -- you can't make JavaScript parse faster without changing the runtime. The optimization is ensuring that --version, MCP serve, and other fast paths never pay this cost.

The 400ms Startup Budget

Claude Code's engineers work with an explicit performance budget. Here's the allocation and what constrains each phase:

Entry + parsing 5ms JS parse of cli.js Keep entry minimal

Two phases dominate: module evaluation (135ms) and REPL first paint (165ms). Together they account for 77% of startup time. Module evaluation is constrained by JavaScript's single-threaded parser. REPL first paint is constrained by the Ink rendering framework's layout engine (Yoga, a C++ flexbox implementation compiled to WASM).

What Doesn't Fit in 400ms

Some operations are deliberately excluded from the startup path because they would blow the budget:

  • MCP server startup: Spawning MCP server subprocesses takes 200-500ms each. These are started lazily when the first MCP tool is invoked.
  • Git repository indexing: Walking the repository tree for file context takes 50-500ms depending on repo size. Deferred to first query.
  • Full schema validation: Validating all settings against the Zod schema takes ~10ms. Only critical fields are validated at startup; full validation runs lazily.
  • LSP server connection: Language server startup takes 500ms-2s. Connected when first needed.

The principle: if it can wait until the user's first interaction, defer it. The startup path is reserved for operations that must complete before the cursor can blink.

Early Input Capture: Buffering During Module Load

Between starting the main module import and the REPL mounting, there's a 300ms window where the terminal is technically accepting input but no component is listening. Users who start typing immediately would lose their keystrokes.

The early input capture system solves this:

// Called before import('./main.js')
export function startCapturingEarlyInput(): void {
  const buffer: Buffer[] = [];

  process.stdin.setRawMode?.(true);
  process.stdin.resume();

  const onData = (chunk: Buffer) => {
    buffer.push(chunk);
  };

  process.stdin.on('data', onData);

  // Export the replay function
  earlyInputReplay = () => {
    process.stdin.removeListener('data', onData);
    return Buffer.concat(buffer);
  };
}

When the REPL mounts, it calls earlyInputReplay() to get the buffered keystrokes and injects them into the input field as if the user had just typed them. The buffer is consumed once -- replay clears it and detaches the listener.

This is a small detail that has outsized impact on perceived quality. Without it, fast typists would lose their first few characters every time they launch claude. With it, the tool feels like it was ready the instant they pressed Enter.

Edge Cases in Early Input

The capture system handles several non-obvious cases:

Input During Load Behavior
Regular text Buffered, replayed into input field
Ctrl+C Buffered as \x03, causes graceful exit on replay
Escape sequences (arrow keys) Buffered as multi-byte sequences, replayed correctly
Paste (large text) Buffered entirely, replayed as single input event
No input Empty buffer, replay is a no-op

The setRawMode(true) call is critical -- without it, the terminal line-buffers input and won't deliver characters until the user presses Enter. Raw mode delivers each keystroke immediately, which is what the REPL expects.

Startup Profiling Architecture

The startup profiler is intentionally minimal -- it adds microseconds per checkpoint, not milliseconds. But its design enables powerful analysis:

const checkpoints: Array<{
  name: string;
  time: number;       // performance.now() relative to process start
  delta: number;      // time since previous checkpoint
  memory?: NodeJS.MemoryUsage;
}> = [];

export function profileCheckpoint(name: string): void {
  const now = performance.now();
  const delta = checkpoints.length > 0 
    ? now - checkpoints[checkpoints.length - 1].time 
    : now;

  const entry: typeof checkpoints[0] = { name, time: now, delta };

  if (process.env.CLAUDE_DETAILED_PROFILING) {
    entry.memory = process.memoryUsage();
  }

  checkpoints.push(entry);
}

The profiler uses performance.now() (sub-millisecond resolution) rather than Date.now() (millisecond resolution). The delta between consecutive checkpoints is computed inline, so the report shows both absolute time and per-phase cost.

Checkpoint Placement Strategy

Checkpoints are placed at decision boundaries -- the moments where the startup path might diverge:

cli_entry                          →  Before any routing decision
cli_before_main_import             →  Before the 135ms import
cli_after_main_import              →  After -- measures eval cost
main_tsx_entry                     →  First line of main module
main_tsx_imports_loaded            →  All side-effect imports done
run_main_options_built             →  Commander options constructed
run_before_parse                   →  Before argv parsing
run_after_parse                    →  After -- measures parse cost
action_after_hooks                 →  preAction hook complete
main_after_run                     →  REPL mounted, cursor visible

The naming convention -- component_event -- makes checkpoints greppable. cli_* checkpoints are in the entry point, main_* in the main module, run_* in the command action, action_* in hooks.

The preAction Rendezvous

Commander.js provides a hook('preAction') mechanism that fires between parsing and command execution. Claude Code uses this as the rendezvous point for all async startup work:

program.hook('preAction', async (thisCommand) => {
  // Collect async results started 135ms ago
  await Promise.all([
    ensureMdmSettingsLoaded(),
    ensureKeychainPrefetchCompleted(),
  ]);

  // Run the memoized init pipeline
  await init();

  // Handle late-bound options
  processPluginDir(thisCommand);

  // Run version migrations
  runMigrations();

  // Non-blocking: start network fetches
  void loadRemoteManagedSettings();
  void loadPolicyLimits();
});

The Promise.all call is the rendezvous. By this point, the MDM subprocess and keychain reads have had 135+ milliseconds to complete. The await typically resolves in <1ms -- the promises are already settled.

The init() call is memoized. It runs once and caches the result. If the preAction hook fires multiple times (e.g., for subcommands), init() returns immediately on subsequent calls. This is important because Commander.js fires preAction for every command and subcommand in the chain.

Why Rendezvous Here, Not Earlier?

The preAction hook is the latest possible rendezvous point that's still before any command execution. Placing it here maximizes the overlap window:

Time 0ms:    Start MDM + keychain subprocesses
Time 2ms:    Start module import (135ms of synchronous work)
Time 137ms:  Module import complete
Time 140ms:  CLI parsing complete
Time 140ms:  preAction fires → await prefetch results (resolved in <1ms)

If the rendezvous were at Time 2ms (before the import), the prefetches would have had 0ms to complete. If it were at Time 137ms (before parsing), we'd lose the 3ms of parsing overlap. The preAction hook gives the maximum possible overlap: 140ms for operations that take 20-30ms.

The init() Pipeline: 16 Steps in Dependency Order

The init() function is the heaviest single phase. It runs 16 initialization steps, carefully ordered by their dependencies:

Step Operation Blocking? Depends On
1 Enable configs Yes Settings cascade
2 Apply safe env vars + CA certs Yes User settings only (security boundary)
3 Register signal handlers Yes None
4 Initialize analytics No (fire-and-forget) None
5 Populate OAuth account info No (fire-and-forget) Keychain prefetch
6 IDE detection No (fire-and-forget) None
7 Repository detection No (fire-and-forget) CWD
8 Remote settings promises No (fire-and-forget) Auth token
9 Record first start time Yes (fast) None
10 Configure mTLS Yes CA certs from Step 2
11 Configure HTTP agents Yes mTLS from Step 10
12 API preconnect No (fire-and-forget) HTTP agents from Step 11
13 Upstream proxy (remote only) Conditional HTTP agents
14 Windows shell setup Conditional None
15 Register cleanup handlers Yes (fast) None
16 Scratchpad directory Conditional Feature flag

The critical path (Steps 1-3, 9-11, 15) takes approximately 25ms. Steps 4-8 are fire-and-forget -- they start async work that completes in the background. Step 12 (API preconnect) is the most impactful fire-and-forget: it initiates the TCP + TLS handshake to the API server while the remaining startup proceeds, saving 100-200ms on the first API call.

The Security Boundary in Step 2

Step 2 (applySafeConfigEnvironmentVariables()) reads environment variables exclusively from ~/.claude/settings.json -- the user's own settings file. It deliberately excludes project settings (.claude/settings.json). This is a security boundary: an untrusted repository could contain a project settings file that injects malicious environment variables (e.g., LD_PRELOAD, NODE_OPTIONS, PATH manipulation). By restricting env var application to user settings, the init pipeline prevents project-level environment injection before the trust dialog.

Memoization Guarantees

The init() function is wrapped in a memoize() call:

export const init = memoize(async (): Promise<void> => {
  // ... 16 steps
});

Memoization guarantees: 1. The function body runs exactly once, regardless of how many callers await init(). 2. If two callers await init() concurrently, both receive the same promise. 3. If the function throws, subsequent calls rethrow the cached error -- they don't retry.

Property 3 is a design choice: startup errors are fatal. There's no recovery path for "mTLS configuration failed" -- the application can't function without it. Caching the error (rather than retrying) ensures consistent behavior and prevents infinite retry loops.

Startup Failure Modes

The pipeline is designed for resilience. Every phase has a failure mode that degrades gracefully:

Phase Failure Behavior
MDM read Subprocess fails Empty MDM settings; no enterprise overrides
Keychain read Permission denied Falls back to environment variable auth
Module evaluation Missing dependency Fatal -- Node.js throws, process exits
Settings cascade Malformed JSON Warning in REPL header; uses defaults
Authentication No credentials found Restricted mode; prompts user
Feature flags GrowthBook unreachable All flags use coded defaults
Trust dialog User declines Restricted mode; project config ignored
Telemetry Provider initialization fails No-op providers; silent
Session init Transcript directory unwritable Warning; session history won't persist
MCP registry Network timeout No autocomplete for MCP servers
REPL launch Terminal not interactive Falls back to basic I/O mode

The design principle: Claude Code should always start. A broken config, missing credentials, or unreachable service degrades functionality but never prevents startup. The only fatal failure is a missing core dependency during module evaluation -- and even that produces a clear error message rather than a cryptic stack trace.

Network Operations and Timeouts

Every network operation in the startup path has an explicit timeout:

Operation Timeout Failure Behavior
GrowthBook feature flags 2,000ms Use coded defaults
MCP registry prefetch 3,000ms No registry autocomplete
Remote managed settings 5,000ms Use cached/local settings
API preconnect None (best-effort) First API call does its own connect

The timeouts are aggressive. GrowthBook gets 2 seconds -- enough for a CDN hit, not enough to retry on network issues. The philosophy: network unreliability should never block a local tool. If the CDN is slow, use defaults and fetch again in the background.

Architectural Lessons

Building a multi-phase startup pipeline teaches several principles that apply beyond CLI agents:

1. Decompose by dependency, not by category. The phases aren't "I/O phase, parsing phase, config phase." They're ordered by what depends on what. MDM reads happen first not because they're I/O, but because their results are needed 135ms later and the subprocess needs time to run.

2. Fast paths are a product requirement, not an optimization. claude --version at 5ms vs. 400ms is the difference between "usable in CI health checks" and "not." Design fast paths from day one -- retrofitting them into a monolithic init() is painful.

3. The prefetch-rendezvous pattern turns sequential I/O into parallel I/O. Start async work as early as possible. Do unrelated synchronous work. Rendezvous at the latest possible moment. This is the highest-leverage optimization in any startup path with multiple I/O operations.

4. Memoize expensive initialization. When multiple code paths might trigger init(), memoization ensures it runs once. This is cheaper and safer than tracking "has init been called?" with a boolean flag.

5. Budget milliseconds explicitly. When you have a 400ms budget, track where every millisecond goes. Profile checkpoints at decision boundaries give you the data to make informed trade-offs ("Can we add a 10ms validation step? Where does it come from?").

6. Deferred imports are the cheapest optimization. Moving an import behind a conditional costs zero runtime for paths that don't take the branch. The discipline is in the code review: every new top-level import in the entry point should be questioned.

7. Capture input during load. Any CLI tool that takes more than 50ms to start should buffer terminal input during initialization. Losing the user's first keystrokes creates a perception of unreliability that no amount of performance optimization elsewhere can fix.
