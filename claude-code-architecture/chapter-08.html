Chapter 8: Message Architecture

In Chapter 7, we designed the core agent loop — the prompt-think-act-observe cycle that turns a language model into an agent. But we left a critical question unanswered: what flows through that loop? The answer is messages — structured, typed data objects that form the conversation between user, model, tools, and system.

This chapter examines the message architecture: the conversation as a data structure, the roles and semantics of each message type, how the system prompt is assembled from 10+ injected sections, and the patterns for injecting context without breaking conversation flow. Understanding message architecture is essential for anyone designing an AI agent, because every architectural decision about the agent loop ultimately manifests as a message in the conversation.

The Conversation as a Data Structure

At the most basic level, a conversation is an ordered list of typed messages. Every message has a role, content, and metadata. The model sees this list on every API call and generates the next message in the sequence.

        A1 --> U2[User Message 2<br/>tool_result]
        U2 --> A2[Assistant Message 2]
        A2 --> U3[User Message 3<br/>tool_result]
        U3 --> A3[Assistant Message 3]
    end

This looks like a chat transcript. It is not. The conversation is a protocol — a structured sequence that the API validates and the model interprets. Violating the protocol (wrong ordering, missing tool results, orphaned tool calls) produces API errors or degraded model behavior.

The Ordering Contract

The API enforces a strict alternation rule:

  1. The conversation starts with a user message.
  2. Messages alternate between user and assistant roles.
  3. Every tool_use block in an assistant message must have a corresponding tool_result block in the immediately following user message.

This means tool results are always user messages, even though they are generated by the tool system, not by the human user. The human user's actual input and the tool system's output share the same role. The model must distinguish them by content type, not by role.

Why Order Matters

The model treats the conversation as a sequence — not a set, not a graph. Reordering messages changes the model's interpretation:

Order A (correct):
  User: "Read config.py"
  Assistant: [tool_use: Read config.py]
  User: [tool_result: contents of config.py]
  Assistant: "The config file contains..."

Order B (broken):
  User: "Read config.py"
  User: [tool_result: contents of config.py]  ← orphaned result
  Assistant: [tool_use: Read config.py]        ← tool call after result
  Assistant: "The config file contains..."

Order B violates the protocol and would be rejected by the API. But even if the API accepted it, the model would be confused — seeing a tool result before the tool call that produced it. Message ordering is not just a protocol requirement; it is how the model reconstructs the causal chain of events.

Message Roles: Semantics and Boundaries

Four roles participate in the conversation:

system — The Invisible Director

The system prompt is special. It is not part of the conversation history — it is a separate parameter that sets the model's behavior, identity, and constraints. The model cannot reference it, cannot modify it, and (in production) cannot distinguish it from the API infrastructure.

┌──────────────────────────────────────────────┐
│                 API Call                       │
│                                               │
│  system: [system prompt blocks]               │ ← Separate parameter
│                                               │
│  messages: [                                  │ ← Conversation history
│    { role: "user", content: "..." },          │
│    { role: "assistant", content: "..." },     │
│    ...                                        │
│  ]                                            │
└──────────────────────────────────────────────┘

The system prompt is where you embed the agent's identity, its available tools, its behavioral rules, and its knowledge of the current session context. It is the single most important piece of text in the entire system. We will examine its assembly in detail below.

user — The Human and the System's Shared Voice

The user role serves double duty:

  1. Human input — what the user actually typed.
  2. Tool results — output from tool execution, wrapped in tool_result content blocks.
  3. System injections — metadata, context, and instructions injected by the system between turns.

This overloading is an API design constraint, not an architectural choice. The API requires alternating roles, and tool results must follow assistant messages. Since the assistant just spoke, the next message must be user — even if it is a tool result generated by the system.

The implication for agent architects: you must design a content structure that lets the model distinguish human input from tool results from system injections, all within the same role.

assistant — The Model's Voice

Assistant messages contain the model's response, which can include:

  • Text blocks — natural language output.
  • Thinking blocks — the model's internal reasoning (when extended thinking is enabled). Visible in the API response but not rendered to the user by default.
  • Tool use blocks — structured requests to execute tools, with the tool name and JSON input.
  • Redacted thinking — encrypted reasoning blocks that the client cannot read but must preserve for the API's stateful protocol.

A single assistant message can contain multiple content blocks of different types. The model might think, then call two tools, then output text — all in one message:

{
  "role": "assistant",
  "content": [
    { "type": "thinking", "thinking": "Let me check both files..." },
    { "type": "tool_use", "name": "Read", "input": { "path": "config.py" } },
    { "type": "tool_use", "name": "Read", "input": { "path": "settings.py" } },
    { "type": "text", "text": "Reading both configuration files..." }
  ]
}

tool_result — Feedback From the Environment

Tool results are content blocks within user messages that carry the output of tool execution:

{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "toolu_abc123",
      "content": "file contents here...",
      "is_error": false
    }
  ]
}

The tool_use_id links the result back to the specific tool call that produced it. This link is how the model correlates "I asked to read config.py" with "here are the contents of config.py." Without this link, the model would have to infer the correlation from context, which is unreliable when multiple tools execute concurrently.

Why Tool Results Are Separate Messages

A common question from agent architects: why not embed tool results in the assistant message that requested them? The model called the tool; why not put the result right next to the call?

// Hypothetical embedded approach (NOT how the API works):
{
  "role": "assistant",
  "content": [
    { "type": "tool_use", "name": "Read", "input": { "path": "config.py" } },
    { "type": "tool_result", "content": "file contents..." }  ← embedded
  ]
}

Three reasons this does not work:

1. The model generates the tool call. The tool generates the result. The assistant message is generated by the model. The tool result is generated by the environment. They come from different sources at different times. Embedding one in the other would require mutating the assistant message after it is generated — breaking the immutability that enables prompt caching.

2. Prompt caching requires byte-stable prefixes. As discussed in Chapter 10, the prompt cache matches on exact byte sequences. If the assistant message is generated, cached, and then a tool result is appended, the byte sequence changes, the cache misses, and you pay 10x more. Keeping tool results in a separate user message means the assistant message's bytes are stable — it enters the cache once and stays there.

3. Multiple tool calls produce multiple results. When the model calls three tools, there are three tool_use blocks in the assistant message and three tool_result blocks in the next user message. The user message collects all results at once, maintaining the alternating-roles protocol. Embedding would require interleaving results within the assistant message, which would change the message structure on every tool count.

System Prompt Assembly: The Prompt Pipeline

The system prompt is not a static string. It is assembled dynamically before each API call from 10 or more sections, each serving a distinct purpose. This assembly is the prompt pipeline — the most architecturally significant component of the message system.

Why Dynamic Assembly?

A static system prompt would be simpler. But consider what the system prompt must communicate:

  • The model's identity and behavioral rules
  • Available tools and their schemas
  • User-configured rules (from .claude/rules/)
  • Currently active skills
  • Session context (project name, working directory)
  • Memory from previous sessions
  • Active plan or task context
  • MCP server instructions
  • Custom hooks and their constraints
  • File contents mentioned by the user

Some of these are known at boot time (identity, tool schemas). Others change between turns (active skills, memory, file contents). A few change within a turn (MCP tool availability after reconnection). Dynamic assembly is necessary because the context the model needs is not fixed — it evolves with the session.

The 10+ Sections

The system prompt is assembled as an array of blocks, each block being a section of text or structured data. Here is the typical assembly order and purpose:

Blocks 1-3 (Static core): These rarely change within a session. The identity block sets the model's persona and rules. Tool definitions encode the schemas of all available tools. Model-specific instructions adapt behavior to the current model's capabilities (e.g., thinking mode for Opus). Because these blocks are stable, they form the cacheable prefix — the bytes that the prompt cache can reuse across turns.

Blocks 4-5 (Project context): These change when the user switches projects or when memory is updated. Project rules are path-scoped coding standards from .claude/rules/. Memory includes the CLAUDE.md project brain and auto-memory from previous sessions. These are semi-stable — they change rarely within a session but differ across sessions.

Blocks 6-8 (Session-dynamic): These change between turns. Active skills load when the user invokes a slash command. Session context updates when the working directory changes. MCP server descriptions update when servers connect or disconnect.

Blocks 9-10 (Turn-dynamic): These can change on every turn. Custom instructions from hooks or user preferences. Active plan context showing what the agent is working toward.

The Cache-Stability Trade-off

The system prompt ordering is not arbitrary. It follows a stability gradient: the most stable blocks come first, the most volatile blocks come last.

                     Cache Boundary
    ┌─────────────────┐ │ ┌──────────────────────┐
    │  Stable Core    │ │ │  Dynamic Context       │
    │  (Identity,     │ │ │  (Skills, MCP,         │
    │   Tools,        │ │ │   Plan, Custom)        │
    │   Model Rules)  │ │ │                        │
    └─────────────────┘ │ └──────────────────────┘
    ◄── CACHED ─────────►◄── RE-PROCESSED ────────►

Everything before the cache boundary is byte-identical across turns. The prompt cache stores these tokens and reuses them. Everything after the boundary is re-processed on every API call. By placing stable blocks first, the cacheable prefix is as large as possible, minimizing per-turn cost.

A single byte change in any block before the cache boundary invalidates the entire cache. This is why certain design decisions in the prompt pipeline exist purely for cache stability:

  • Tool definitions are sorted deterministically (not hash-order) so the byte sequence is stable.
  • Feature flags that affect the system prompt are latched at session start (not re-read per turn).
  • MCP tool schemas are placed after core tool schemas, so adding/removing an MCP server does not shift the core tools' byte positions.

Block Assembly as a Pipeline

The prompt assembly is a pipeline of transformations:

Raw Sources          →  Block Generators    →  Assembly     →  Cache Marking

CLAUDE.md            →  parseProjectRules() →  ┐              
rules/*.md           →  loadPathRules()     →  ├→ blocks[]  → addCacheControl()
skills/*/SKILL.md    →  loadActiveSkills()  →  ┤              
memory files         →  loadMemory()        →  ┤              
session state        →  buildContext()       →  ┘

Each block generator reads from its source, applies any transformations (truncation, prioritization, deduplication), and produces a text block. The assembly step concatenates blocks in the correct order. The cache marking step places cache_control markers at the appropriate positions.

This pipeline is deterministic — given the same inputs, it produces the same output. This is critical for testing (snapshot tests can compare system prompts) and for cache stability (the same session state produces the same byte sequence).

Context Injection Patterns

The system prompt is one injection point. But context also enters the conversation through messages — tool results, user context blocks, and system reminders. Each pattern has distinct characteristics.

Pattern 1: System Prompt Injection

Context placed in the system prompt is visible to the model on every turn. It does not consume conversation message slots. It is cached efficiently.

Use for: Identity, behavioral rules, tool definitions, project-wide rules, session context that does not change between turns.

Trade-off: System prompt space is finite. Every byte in the system prompt is processed on every API call (even if cached, it occupies context window space). Adding a 10K-token knowledge base to the system prompt means every turn costs 10K tokens of context window.

Pattern 2: User Context Injection

Context prepended to the user's message, before the model sees it. This is the pattern for per-turn context that the model should treat as background information:

{
  "role": "user",
  "content": [
    { "type": "text", "text": "[Current directory: /src/api]\n[Git branch: feat/auth]" },
    { "type": "text", "text": "Fix the login bug" }
  ]
}

Use for: Working directory, git status, recently modified files, active plan reminders.

Trade-off: The model sees this context as part of the user's message. If the injection is poorly formatted, the model may confuse injected context with user instructions.

Pattern 3: System Reminders

System reminders are injected into the conversation at specific points — typically after the last user message or before the model's turn. They use a special format to distinguish them from user content:

{
  "role": "user",
  "content": [
    {
      "type": "text",
      "text": "<system-reminder>\nRemember: Always run tests before committing.\n</system-reminder>"
    }
  ]
}

Use for: Behavioral nudges, safety reminders, instructions that should apply to the current turn but are not permanent enough for the system prompt.

Trade-off: System reminders occupy conversation message space. They grow the context on every turn they are injected. Unlike system prompt blocks, they are not cached — they are re-sent as part of the conversation history.

Pattern 4: Tool Result Injection

Context returned as the output of a tool call. The model requested a file read; the tool returns the file contents.

Use for: File contents, search results, command output, database query results.

Trade-off: Tool results are typically the largest messages in the conversation. A single file read can be 10K tokens. These are prime candidates for compaction — the context management system (Chapter 9) specifically targets old tool results for removal.

Pattern 5: Meta-Message Injection

System-generated user messages that are not tool results and not human input. Recovery messages ("Resume where you left off"), budget nudges ("You've used 45% of your budget"), and hook feedback ("The stop hook found issues: ...").

# A meta-message is marked as system-generated
meta_message = UserMessage(
    content="Output token limit hit. Resume directly — no recap.",
    is_meta=True,  # Marks as system-generated, not human
)

Use for: Error recovery instructions, budget management, hook-injected feedback.

Trade-off: The is_meta flag is critical. During compaction, meta-messages are candidates for removal — they served their purpose in the turn they were injected and are unlikely to be relevant later. Without the flag, the compaction system would preserve them as if they were human input, wasting context space.

Choosing the Right Pattern

Context Type Pattern Reason
Agent identity and rules System prompt Stable, cached, always visible
Tool schemas System prompt Stable, required for tool use
Project coding rules System prompt (path-scoped) Semi-stable, applies to all turns
Working directory User context injection Changes between turns
File contents (requested) Tool result Large, model-requested, compactable
Recovery instructions Meta-message Temporary, removable after use
Safety reminders System reminder Per-turn nudge, not permanent
Skill instructions System prompt (dynamic) Session-scoped, loaded on demand

The Compact Boundary

Step 1 is subtle but important. After compaction (Chapter 9), the conversation has a compact boundary — a marker that says "everything before this point was summarized." The prompt pipeline only sends messages after the boundary. The summary itself is a message at the boundary position.

Full Conversation:
[msg1, msg2, msg3, BOUNDARY/SUMMARY, msg4, msg5, msg6]
                         ↑
                   Compact boundary

Sent to API:
[SUMMARY, msg4, msg5, msg6]

This means the model sees the summary (which covers msg1-msg3) followed by the recent messages (msg4-msg6). The model does not see the original msg1-msg3 — they have been replaced by the summary. This is the fundamental trade-off of compaction: detail loss for space savings.

Message Normalization

Before messages reach the API, they pass through a normalization step that handles API quirks:

  • Tool result pairing repair. If a tool_use block has no matching tool_result (due to an interrupted stream), a synthetic error result is generated.
  • Image/document size limits. Large images are downscaled or removed to fit provider-specific limits.
  • Thinking block handling. Thinking blocks are included or excluded depending on the model's capabilities and the API provider.
  • Content block deduplication. If streaming produced duplicate content blocks (a known edge case with some providers), they are deduplicated.

Normalization is a defensive layer — it ensures the API request is valid regardless of what happened during the session. Sessions that were interrupted, resumed, or involved unusual tool execution patterns can produce malformed message sequences. Normalization repairs them.

Message Metadata: Beyond Content

Messages carry metadata that is not visible to the model but is essential for the agent system:

Timestamps

Every message has a creation timestamp. This enables: - Time-based compaction — clearing old tool results after 60 minutes of idle time. - Token estimation anchoring — correlating API usage data with specific messages. - Session timeline reconstruction — debugging what happened when.

Message IDs

Every message has a unique ID. Tool results reference the ID of the tool call that produced them. This enables: - Tool result correlation — matching results to calls across concurrent execution. - Compaction correctness — ensuring tool call/result pairs are not split during message removal. - Streaming deduplication — detecting when the stream yields the same content block twice.

The is_meta Flag

As discussed above, meta-messages are system-generated messages that are not human input and not tool results. The is_meta flag tells the compaction system these messages are disposable after their immediate use: - Recovery messages ("Resume where you left off") - Budget nudges ("You've used X% of your budget") - Hook feedback messages - Compaction summaries

API Error Fields

When the model's response is truncated (output token limit) or the API returns an error, the error is recorded on the message: - apiError: 'max_output_tokens' — the response was cut off. - apiError: 'prompt_too_long' — the context exceeded the limit.

These fields are used by the error withholding pattern from Chapter 7 to identify recoverable errors without parsing error message strings.

Message Ordering Guarantees

The ordering of messages is not just a protocol requirement — it is how the model understands causality, tracks state, and makes decisions. Three ordering guarantees must be maintained:

Guarantee 1: Strict Role Alternation

user → assistant → user → assistant → ...

Every violation produces an API error. The alternation requirement means: - Multiple consecutive user messages must be merged into one. - Multiple consecutive assistant messages (from streaming) share the same logical position. - System injections between turns must be folded into the preceding or following user message.

Guarantee 2: Tool Call/Result Adjacency

Every tool_use in an assistant message has a tool_result in the immediately next user message. Not two messages later. Not in a different conversation branch. Immediately next.

This adjacency guarantee means tool results cannot be reordered, delayed, or batched across turns. If the model calls three tools, all three results must appear in the next user message. The agent loop enforces this by collecting all tool results before constructing the next user message.

Guarantee 3: Causal Order Within a Turn

Within a single user message, content blocks appear in causal order: 1. Tool results (from the previous assistant turn's tool calls) 2. System reminders (injected context for the current turn) 3. Human input (what the user actually typed)

This ordering ensures the model processes tool results before human instructions, and system reminders before user text. Reversing the order could cause the model to respond to the human input without considering the tool results.

The Message Lifecycle

A message goes through several stages from creation to eventual removal:

stateDiagram-v2
    [*] --> Created: User types / Model generates / Tool executes
    Created --> Yielded: Generator yields to consumer
    Yielded --> Rendered: UI renders to terminal
    Yielded --> Persisted: Written to transcript
    Yielded --> InContext: Part of next API call
    InContext --> Compacted: Too old / Context pressure
    Compacted --> Summarized: Replaced by summary
    Summarized --> [*]
    InContext --> Archived: Session ends
    Archived --> [*]

Created: A message is born — the user typed something, the model generated a response, or a tool produced output.

Yielded: The generator yields the message to the consumer (the UI layer or SDK client).

Rendered: The UI renders the message to the terminal. This happens concurrently with other lifecycle stages.

Persisted: The message is appended to the JSONL transcript file on disk. This enables session resume.

InContext: The message is part of the conversation sent to the API on subsequent turns. This is where it consumes context window space.

Compacted: The context management system decides this message is too old or the context is too full. The message is either removed or replaced by a summary.

Archived: When the session ends, all messages are in the transcript. The in-memory conversation is discarded.

The key insight: a message can be in multiple stages simultaneously. It is rendered, persisted, and in-context at the same time. It is only removed from context (compacted) — it is never removed from the transcript. The transcript is the authoritative record; the in-context conversation is a window into that record.

Design Lessons

Building the message architecture for a production AI agent teaches seven principles:

1. Treat the conversation as a protocol, not a transcript. Messages are structured data with ordering constraints, type semantics, and correlation links. Violating the protocol produces API errors. Understanding the protocol is prerequisite to everything else in agent design.

2. Separate the system prompt from the conversation. The system prompt is a separate assembly pipeline with its own caching semantics, ordering constraints, and injection patterns. It is not "just the first message."

3. Order system prompt blocks by stability. Most stable blocks first (identity, tool schemas), most volatile blocks last (skills, plan context). This maximizes the cacheable prefix and minimizes per-turn cost.

4. Use tool_result messages for environment feedback, not embedded blocks. Separate messages maintain the alternating-role protocol, enable prompt caching of the assistant message, and handle any number of concurrent tool calls cleanly.

5. Mark system-generated messages. The is_meta flag distinguishes recovery messages, budget nudges, and hook feedback from human input. Compaction uses this flag to identify disposable messages. Without it, the system preserves temporary messages as if they were human instructions.

6. Maintain three ordering guarantees. Strict role alternation, tool call/result adjacency, and causal order within turns. Each guarantee prevents a class of bugs — API errors, correlation failures, and context confusion respectively.

7. Build the prompt pipeline as a deterministic function. Given the same inputs (conversation state, system prompt sources, feature flags), the pipeline produces the same API request. Determinism enables snapshot testing, cache stability analysis, and debugging of "why did the model see X on this turn?"
