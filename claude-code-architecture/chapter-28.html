Chapter 28: Input Processing & Command Routing

The most important interaction in an AI CLI agent happens before the LLM is ever involved: the user types something. That input might be a natural language prompt, a slash command, a file mention, or a partial word that needs completion. The input system must classify, parse, route, and in some cases transform the input before it reaches the agent loop. This chapter examines the architecture of that pipeline -- from raw keystrokes to dispatched actions.

As discussed in Chapter 27, the REPL screen centralizes state management and delegates behavior to custom hooks. The input system is where this delegation pattern is most visible: 12 hooks manage different aspects of input handling, from basic text editing to paste detection to vim mode. The command routing layer sits above these hooks, dispatching parsed input to the appropriate handler -- be it a slash command, a file mention resolver, or the agent loop itself.

28.1 The Input Pipeline

Every keystroke flows through a five-stage pipeline before it produces visible effects:

graph LR
    A[Raw Keypress] --> B[Key Event Parser]
    B --> C[Mode Router]
    C --> D[Input Buffer]
    D --> E[Command Classifier]
    E --> F[Dispatch]

    style A fill:#e1f5fe
    style F fill:#e8f5e9

Stage 1: Raw Keypress. The terminal sends raw bytes. Standard characters are single bytes. Special keys (arrows, function keys, escape sequences) are multi-byte sequences. Bracketed paste mode wraps pasted content in escape sequence delimiters.

Stage 2: Key Event Parser. Raw bytes are parsed into typed key events: { key: 'a', ctrl: false, shift: false } or { key: 'up', ctrl: false } or { key: 'v', ctrl: true }. This stage handles the complexity of terminal escape sequences -- the same logical key can produce different byte sequences across terminals (xterm vs iTerm vs Windows Terminal).

Stage 3: Mode Router. The current input mode determines how the key event is processed. In normal mode, characters insert into the buffer. In vim normal mode, characters are interpreted as commands. In permission mode, only y/n/a are accepted. In search mode, characters filter the history.

Stage 4: Input Buffer. The text buffer manages the string content and cursor position. Insert, delete, word-jump, line-kill, and other editing operations modify the buffer. The buffer is a simple string with an integer cursor position -- no gap buffer or rope data structure is needed because input lines rarely exceed a few hundred characters.

Stage 5: Command Classifier. When the user presses Enter (or the equivalent submit action), the classifier examines the buffer content and routes it:

type InputClassification =
  | { type: 'slash_command'; name: string; args: string }
  | { type: 'natural_language'; text: string; mentions: FileMention[] }
  | { type: 'empty' }
  | { type: 'multiline_continuation' };

function classifyInput(buffer: string): InputClassification {
  const trimmed = buffer.trim();

  if (!trimmed) return { type: 'empty' };

  if (trimmed.startsWith('/')) {
    const spaceIndex = trimmed.indexOf(' ');
    if (spaceIndex === -1) {
      return { type: 'slash_command', name: trimmed.slice(1), args: '' };
    }
    return {
      type: 'slash_command',
      name: trimmed.slice(1, spaceIndex),
      args: trimmed.slice(spaceIndex + 1).trim(),
    };
  }

  const mentions = extractFileMentions(trimmed);
  return { type: 'natural_language', text: trimmed, mentions };
}

The classifier is deliberately simple. It makes a binary decision based on the first character: slash means command, everything else is natural language. There is no ambiguity, no heuristic parsing, no LLM involvement. This simplicity is a design choice -- the user always knows whether they are issuing a command or talking to the agent.

28.2 Slash Command Architecture

Slash commands are the primary structured interaction mechanism. They bypass the LLM entirely for system operations (/clear, /compact, /config) and load specialized workflows for agent operations (/fix-issue, /code-review, /research).

The Command Registry

All commands live in a central registry. Each command is a registration record:

interface CommandRegistration {
  name: string;
  aliases: string[];
  description: string;
  category: CommandCategory;
  argumentHint?: string;
  handler: CommandHandler;
  source: 'builtin' | 'skill' | 'plugin';
  hidden?: boolean;
}

type CommandCategory =
  | 'navigation'    // /clear, /compact, /rewind
  | 'session'       // /config, /model, /effort
  | 'workflow'      // /code-review, /fix-issue, /research
  | 'git'           // /commit, /diff, /pr-summary
  | 'system'        // /help, /stats, /doctor
  | 'debug';        // /context, /export, /tokens

type CommandHandler = (args: string, context: CommandContext) => Promise<CommandResult>;

A production AI agent registers 70+ commands. They break down by source:

Source Count Examples
Built-in ~30 /clear, /compact, /help, /model, /effort, /commit, /diff, /stats
Skills ~15-40 /code-review, /fix-issue, /research, /security-audit, /deploy-check
Plugins Variable Depends on installed plugins

Registration

Commands register at startup during the loading phase. Built-in commands register from a static list. Skill-based commands register from the skill registry (as described in Chapter 30). Plugin commands register when plugins load.

class CommandRegistry {
  private commands = new Map<string, CommandRegistration>();
  private aliasMap = new Map<string, string>(); // alias -> canonical name

  register(registration: CommandRegistration): void {
    this.commands.set(registration.name, registration);
    for (const alias of registration.aliases) {
      this.aliasMap.set(alias, registration.name);
    }
  }

  lookup(name: string): CommandRegistration | undefined {
    // Exact match first
    const direct = this.commands.get(name);
    if (direct) return direct;

    // Alias match
    const canonical = this.aliasMap.get(name);
    if (canonical) return this.commands.get(canonical);

    // Case-insensitive fallback
    const lower = name.toLowerCase();
    for (const [key, reg] of this.commands) {
      if (key.toLowerCase() === lower) return reg;
    }

    return undefined;
  }

  listVisible(): CommandRegistration[] {
    return [...this.commands.values()]
      .filter(cmd => !cmd.hidden)
      .sort((a, b) => a.name.localeCompare(b.name));
  }
}

The three-tier lookup (exact, alias, case-insensitive) handles the most common user errors without ambiguity. Aliases provide shortcuts: /cc for /compact, /cr for /code-review. The case-insensitive fallback catches /Clear and /HELP.

Parsing and Execution

The parsing step is minimal by design -- split on the first space:

/fix-issue 42        -> name: "fix-issue",  args: "42"
/research MCP tools  -> name: "research",   args: "MCP tools"
/clear               -> name: "clear",      args: ""
/model sonnet        -> name: "model",      args: "sonnet"

No flag parsing, no quoted arguments, no option-value pairs. The handler receives the raw argument string and parses it however it needs. This avoids the complexity of a universal argument parser (like yargs or commander) and lets each command define its own argument format.

The execution flow:

sequenceDiagram
    participant User
    participant Classifier as Input Classifier
    participant Registry as Command Registry
    participant Handler as Command Handler
    participant Agent as Agent Loop

    User->>Classifier: /fix-issue 42
    Classifier->>Registry: lookup("fix-issue")
    Registry-->>Classifier: CommandRegistration
    Classifier->>Handler: handler("42", context)

    alt Built-in command
        Handler-->>User: Direct result (no LLM)
    else Skill command (inline)
        Handler->>Agent: Inject resolved skill body
        Agent-->>User: LLM response
    else Skill command (fork)
        Handler->>Agent: Spawn subagent with skill
        Agent-->>User: Subagent result
    end

Built-in commands execute synchronously and return a result directly to the REPL. Skill commands resolve their body (argument substitution, dynamic injection as described in Chapter 30) and either inject it into the current conversation or spawn a subagent.

Command Categories and the Help System

The category field serves the help system. /help groups commands by category, showing a structured overview:

Navigation:  /clear  /compact  /rewind  /context
Session:     /config  /model  /effort  /fast
Workflow:    /code-review  /fix-issue  /research  /deploy-check
Git:         /commit  /diff  /pr-summary  /git-cleanup
System:      /help  /stats  /doctor  /export

Hidden commands (hidden: true) are excluded from help output but remain accessible by name. These are typically debug commands (/tokens, /dump-context, /raw-prompt) that clutter the help display without benefiting most users.

28.3 File Mentions: The @-Syntax

File mentions are the second structured input mechanism. When a user types @file.txt, the system resolves the path and injects the file's content into the message context. This lets users reference specific files without the LLM needing to call a read tool.

Syntax

The @-syntax supports four patterns:

Pattern Resolves To Example
@file.txt File content @src/auth.ts injects auth.ts content
@directory/ Directory listing @src/ injects file listing of src/
@*.py Glob match @tests/*.py injects all matching files
@http://... URL content @https://docs.example.com/api fetches and injects

Resolution Pipeline

File mention resolution happens after the input classifier identifies natural language input:

interface FileMention {
  raw: string;           // The @... text as typed
  resolved: ResolvedMention;
  startIndex: number;    // Position in input string
  endIndex: number;
}

type ResolvedMention =
  | { type: 'file'; path: string; content: string; lineCount: number }
  | { type: 'directory'; path: string; entries: string[] }
  | { type: 'glob'; pattern: string; files: ResolvedFile[] }
  | { type: 'url'; url: string; content: string }
  | { type: 'error'; message: string };

function extractFileMentions(input: string): FileMention[] {
  const mentions: FileMention[] = [];
  const regex = /@(\S+)/g;
  let match;

  while ((match = regex.exec(input)) !== null) {
    const raw = match[1];
    const resolved = resolveMention(raw);
    mentions.push({
      raw: '@' + raw,
      resolved,
      startIndex: match.index,
      endIndex: match.index + match[0].length,
    });
  }

  return mentions;
}

function resolveMention(raw: string): ResolvedMention {
  // URL detection
  if (raw.startsWith('http://') || raw.startsWith('https://')) {
    return resolveUrl(raw);
  }

  // Glob detection
  if (raw.includes('*') || raw.includes('?')) {
    return resolveGlob(raw);
  }

  // Path resolution
  const resolved = path.resolve(raw);

  if (!fs.existsSync(resolved)) {
    return { type: 'error', message: `File not found: ${raw}` };
  }

  const stat = fs.statSync(resolved);

  if (stat.isDirectory()) {
    const entries = fs.readdirSync(resolved);
    return { type: 'directory', path: resolved, entries };
  }

  // File size guard
  if (stat.size > 1_000_000) { // 1MB limit
    return { type: 'error', message: `File too large: ${raw} (${stat.size} bytes)` };
  }

  const content = fs.readFileSync(resolved, 'utf-8');
  return {
    type: 'file',
    path: resolved,
    content,
    lineCount: content.split('\n').length,
  };
}

Context Injection

Resolved file mentions are injected into the message sent to the LLM. The injection format wraps file content in XML-like tags that the LLM can reference:

User message: "Review @src/auth.ts for security issues"

Injected as:
"Review src/auth.ts for security issues

<file_content path="src/auth.ts">
[file content here]
</file_content>"

The LLM sees both the user's natural language and the file content in a single message. This is more efficient than the LLM issuing a separate Read tool call -- it saves a round trip in the agent loop.

Token Budget Awareness

File mentions consume context window tokens. The resolution pipeline estimates token count and warns when injected content would exceed a configurable threshold (typically 30% of the remaining context budget, consistent with the skill injection budget described in Chapter 30):

function estimateTokens(content: string): number {
  return Math.ceil(content.length / 3.5); // Conservative estimate for code
}

function checkMentionBudget(
  mentions: FileMention[],
  remainingTokens: number,
): { allowed: FileMention[]; truncated: FileMention[]; warning?: string } {
  const budget = Math.floor(remainingTokens * 0.3);
  let used = 0;
  const allowed: FileMention[] = [];
  const truncated: FileMention[] = [];

  for (const mention of mentions) {
    if (mention.resolved.type === 'file') {
      const estimate = estimateTokens(mention.resolved.content);
      if (used + estimate > budget) {
        truncated.push(mention);
      } else {
        used += estimate;
        allowed.push(mention);
      }
    } else {
      allowed.push(mention);
    }
  }

  const warning = truncated.length > 0
    ? `${truncated.length} file(s) truncated to fit context budget`
    : undefined;

  return { allowed, truncated, warning };
}

Context Detection

The coordinator inspects the text before the cursor to determine which completer to invoke:

function detectCompletionContext(
  input: string,
  cursorPosition: number,
): CompletionContext {
  const beforeCursor = input.slice(0, cursorPosition);
  const currentWord = extractCurrentWord(beforeCursor);

  if (currentWord.startsWith('/')) {
    return { type: 'command', partial: currentWord.slice(1) };
  }

  if (currentWord.startsWith('@')) {
    return { type: 'file', partial: currentWord.slice(1) };
  }

  // No structured completion context
  return { type: 'none' };
}

function extractCurrentWord(text: string): string {
  const match = text.match(/(\S+)$/);
  return match ? match[1] : '';
}

Command Completion

Command completion operates on the static list of registered commands. Matching uses prefix filtering with fuzzy fallback:

function completeCommand(
  partial: string,
  commands: CommandRegistration[],
): CompletionResult[] {
  const query = partial.toLowerCase();

  // Phase 1: Prefix matches (highest priority)
  const prefixMatches = commands
    .filter(cmd => cmd.name.toLowerCase().startsWith(query))
    .map(cmd => ({
      text: '/' + cmd.name,
      description: cmd.description,
      score: 100 + (cmd.name.length === query.length ? 50 : 0),
    }));

  // Phase 2: Fuzzy matches (only if few prefix matches)
  let fuzzyMatches: CompletionResult[] = [];
  if (prefixMatches.length < 5) {
    fuzzyMatches = commands
      .filter(cmd => !cmd.name.toLowerCase().startsWith(query))
      .filter(cmd => fuzzyMatch(query, cmd.name))
      .map(cmd => ({
        text: '/' + cmd.name,
        description: cmd.description,
        score: fuzzyScore(query, cmd.name),
      }));
  }

  return [...prefixMatches, ...fuzzyMatches]
    .sort((a, b) => b.score - a.score)
    .slice(0, 10);
}

The exact-match bonus (score +50) ensures that typing /commit exactly selects /commit over /commit-all. The fuzzy fallback handles typos: /cmmit still finds /commit.

File Path Completion

File completion is asynchronous because it hits the filesystem. The completer maintains a directory cache with lazy expansion:

class FileCompleter {
  private cache = new Map<string, DirectoryEntry[]>();
  private cacheTTL = 30_000; // 30 seconds

  async complete(partial: string, cwd: string): Promise<CompletionResult[]> {
    const dir = path.dirname(path.resolve(cwd, partial));
    const base = path.basename(partial);

    let entries = this.getCached(dir);
    if (!entries) {
      entries = await this.scanDirectory(dir);
      this.setCache(dir, entries);
    }

    return entries
      .filter(e => e.name.toLowerCase().startsWith(base.toLowerCase()))
      .sort((a, b) => {
        // Directories first, then alphabetical
        if (a.isDirectory !== b.isDirectory) return a.isDirectory ? -1 : 1;
        return a.name.localeCompare(b.name);
      })
      .slice(0, 50)
      .map(e => ({
        text: '@' + path.join(path.dirname(partial), e.name) + (e.isDirectory ? '/' : ''),
        description: e.isDirectory ? 'directory' : formatSize(e.size),
        score: 0,
      }));
  }
}

The 30-second cache TTL means files created in another terminal tab appear in completion within 30 seconds. The cache is also invalidated on directory change.

Tab vs. Typeahead

Tab completion and typeahead are related but distinct:

Feature Tab Completion Typeahead
Trigger Tab keypress Every character input
Presentation Replaces current word Shows dropdown overlay
Cycling Tab cycles through matches Arrow keys navigate
Dismiss Escape or type past Escape or type past
Use case Quick known-target completion Discovery and browsing

Both use the same completers but differ in trigger and presentation. Tab is faster for experienced users who know what they want. Typeahead is better for discovery -- browsing available commands or files.

28.5 Vim Mode

Vim mode adds modal editing to the CLI agent's input area. This is not a curiosity feature -- engineers who use vim keybindings are measurably faster at text editing, and an AI agent is primarily a text editing interface.

Modal Architecture

Vim mode introduces three input modes layered on top of the existing mode system (Chapter 27, Section 27.7):

stateDiagram-v2
    [*] --> Insert: Vim disabled or initial state
    Insert --> Normal: Escape
    Normal --> Insert: i, a, o, A, I, O
    Normal --> Visual: v, V
    Visual --> Normal: Escape
    Normal --> Command: :
    Command --> Normal: Enter or Escape
Mode Input Behavior
Insert Characters insert at cursor (standard behavior)
Normal Characters are interpreted as vim commands: h/j/k/l movement, w/b word jump, d/c/y edit operators, / search
Visual Characters extend selection; operators apply to selection
Command : prefix for ex-commands (:w, :q, :set)

Key Binding Architecture

The key binding system uses a trie (prefix tree) for multi-key command recognition:

interface KeyBinding {
  keys: string[];       // e.g., ['d', 'w'] for "delete word"
  action: VimAction;
  mode: VimMode;
  description: string;
}

class KeyBindingTrie {
  private root = new TrieNode();

  register(binding: KeyBinding): void {
    let node = this.root;
    for (const key of binding.keys) {
      if (!node.children.has(key)) {
        node.children.set(key, new TrieNode());
      }
      node = node.children.get(key)!;
    }
    node.action = binding.action;
  }

  match(keys: string[]): TrieMatchResult {
    let node = this.root;
    for (const key of keys) {
      const child = node.children.get(key);
      if (!child) return { type: 'no_match' };
      node = child;
    }
    if (node.action) return { type: 'complete', action: node.action };
    if (node.children.size > 0) return { type: 'partial' };
    return { type: 'no_match' };
  }
}

The trie handles vim's multi-key commands naturally. d alone is a partial match (waiting for a motion). dw is a complete match (delete word). dx is no match (undefined command). The input handler accumulates keys until the trie returns either a complete match (execute) or no match (discard accumulated keys).

Count Prefix

Vim commands support numeric prefixes: 3dw means "delete 3 words." The count parser extracts the prefix before trie matching:

function parseVimInput(keys: string[]): { count: number; command: string[] } {
  let i = 0;
  let countStr = '';

  // Extract leading digits (but not '0' as first character -- that's line start)
  while (i < keys.length && keys[i] >= '1' && keys[i] <= '9') {
    countStr += keys[i];
    i++;
  }
  while (i < keys.length && keys[i] >= '0' && keys[i] <= '9') {
    countStr += keys[i];
    i++;
  }

  return {
    count: countStr ? parseInt(countStr, 10) : 1,
    command: keys.slice(i),
  };
}

The 0 special case is important: in vim, 0 alone means "go to line start," not "repeat 0 times." Only digits 1-9 can start a count prefix.

Integration with the Input Buffer

Vim actions translate to buffer operations. The buffer interface is mode-agnostic:

interface BufferOperations {
  insert(text: string, position: number): void;
  delete(start: number, end: number): string;
  moveCursor(position: number): void;
  getSelection(): { start: number; end: number } | null;
  setSelection(start: number, end: number): void;
  clearSelection(): void;
}

Vim's dw (delete word) translates to: find the next word boundary, call buffer.delete(cursor, wordBoundary). Vim's ci" (change inside quotes) translates to: find enclosing quotes, call buffer.delete(openQuote + 1, closeQuote), switch to insert mode. The buffer does not know about vim -- it provides primitive operations that vim commands compose.

Unknown Command Handling

When a user types an unknown command, the router provides a helpful response rather than a cryptic error:

function handleUnknownCommand(name: string, registry: CommandRegistry): string {
  // Find similar commands using Levenshtein distance
  const similar = registry.listVisible()
    .map(cmd => ({ name: cmd.name, distance: levenshtein(name, cmd.name) }))
    .filter(s => s.distance <= 3)
    .sort((a, b) => a.distance - b.distance)
    .slice(0, 3);

  if (similar.length > 0) {
    return `Unknown command: /${name}. Did you mean: ${similar.map(s => '/' + s.name).join(', ')}?`;
  }

  return `Unknown command: /${name}. Type /help for available commands.`;
}

The Levenshtein threshold of 3 catches common typos (/comit -> /commit, /researh -> /research) without suggesting unrelated commands.

28.7 Multi-line Input

Most AI agent interactions are single-line prompts. But some use cases require multi-line input: pasting code, writing detailed prompts, composing structured requests. The input system supports multi-line through two mechanisms:

Shift+Enter for Explicit Newlines

Shift+Enter inserts a newline character without submitting. The input area expands vertically to accommodate:

function handleKeypress(key: KeyEvent): void {
  if (key.name === 'return' && key.shift) {
    buffer.insert('\n', cursor);
    // Input area height increases
    return;
  }
  if (key.name === 'return' && !key.shift) {
    submit(buffer.value);
    return;
  }
}

Bracketed Paste Detection

When the user pastes multi-line content, the terminal sends it wrapped in bracketed paste escape sequences (\x1b[200~ ... \x1b[201~). The paste detector captures the entire content as a single event rather than processing each character individually:

function usePasteDetection() {
  const pasteBuffer = useRef('');
  const isPasting = useRef(false);

  function handleData(data: string): void {
    if (data.includes('\x1b[200~')) {
      isPasting.current = true;
      pasteBuffer.current = '';
      const start = data.indexOf('\x1b[200~') + 6;
      pasteBuffer.current += data.slice(start);
      return;
    }

    if (isPasting.current) {
      if (data.includes('\x1b[201~')) {
        const end = data.indexOf('\x1b[201~');
        pasteBuffer.current += data.slice(0, end);
        isPasting.current = false;
        // Process complete paste
        handlePaste(pasteBuffer.current);
        return;
      }
      pasteBuffer.current += data;
      return;
    }

    // Normal keystroke handling
    handleKeystroke(data);
  }

  return { handleData };
}

Without bracketed paste detection, a multi-line paste would submit on the first newline character, discarding the rest. The paste detector captures the full content and either inserts it as multi-line input or triggers a paste confirmation dialog for large content.

28.8 Early Input Capture

An AI agent's startup takes time -- loading configuration, connecting to MCP servers, initializing the session. During this period (typically 200-500ms), the user may start typing. Without early input capture, those keystrokes are lost.

The Keystroke Buffer

The early capture system starts listening for keystrokes before the REPL is fully initialized:

class KeystrokeBuffer {
  private buffer: string[] = [];
  private listening = false;

  startCapture(): void {
    this.listening = true;
    process.stdin.setRawMode(true);
    process.stdin.resume();
    process.stdin.on('data', this.onData);
  }

  private onData = (data: Buffer): void => {
    if (this.listening) {
      this.buffer.push(data.toString());
    }
  };

  drain(): string[] {
    this.listening = false;
    process.stdin.off('data', this.onData);
    const captured = [...this.buffer];
    this.buffer = [];
    return captured;
  }
}

When the REPL initializes, it drains the keystroke buffer and replays the captured events through the normal input pipeline. The user's typing appears in the input area as if they had typed it after startup completed.

Timing Considerations

The buffer must start before any async initialization. The startup sequence is:

1. Start keystroke capture     (sync, immediate)
2. Load configuration          (async, 50-100ms)
3. Connect MCP servers         (async, 100-300ms)
4. Initialize REPL             (async, 50-100ms)
5. Drain keystroke buffer      (sync, immediate)
6. Replay captured keystrokes  (sync, immediate)
7. Ready for interaction

Step 1 happens before step 2. This ensures that even keystrokes during the slowest part of initialization (MCP connection) are captured. The replay in step 6 processes the captured data through the fully-initialized input pipeline, including mode routing, vim bindings, and paste detection.

28.9 Input History

The input history system provides command recall (up/down arrows) and reverse search (Ctrl+R), following the behavior that every shell user expects.

Storage

History is stored as a file-backed list with deduplication:

class InputHistory {
  private entries: string[] = [];
  private filePath: string;
  private maxEntries = 1000;

  constructor(sessionDir: string) {
    this.filePath = path.join(sessionDir, 'history.jsonl');
    this.load();
  }

  add(entry: string): void {
    const trimmed = entry.trim();
    if (!trimmed) return;

    // Remove duplicate if it exists
    const idx = this.entries.indexOf(trimmed);
    if (idx !== -1) this.entries.splice(idx, 1);

    // Add to end (most recent)
    this.entries.push(trimmed);

    // Enforce limit
    if (this.entries.length > this.maxEntries) {
      this.entries.shift();
    }

    this.persist();
  }

  search(query: string): string[] {
    return this.entries
      .filter(e => e.toLowerCase().includes(query.toLowerCase()))
      .reverse(); // Most recent first
  }
}

Deduplication ensures that running /commit 50 times does not fill the history with 50 identical entries. The most recent use of a command moves it to the end of the list.

Reverse Search (Ctrl+R)

Reverse search activates a search mode where typed characters filter the history in real time:

function useHistorySearch(history: InputHistory) {
  const [searchTerm, setSearchTerm] = useState('');
  const [results, setResults] = useState<string[]>([]);
  const [selectedIndex, setSelectedIndex] = useState(0);

  useEffect(() => {
    if (searchTerm) {
      const matches = history.search(searchTerm);
      setResults(matches);
      setSelectedIndex(0);
    } else {
      setResults([]);
    }
  }, [searchTerm, history]);

  return {
    searchTerm,
    setSearchTerm,
    results,
    selectedIndex,
    select: () => results[selectedIndex] ?? null,
    cycleUp: () => setSelectedIndex(i => Math.min(i + 1, results.length - 1)),
    cycleDown: () => setSelectedIndex(i => Math.max(i - 1, 0)),
  };
}

The search displays inline in the input area, replacing the normal prompt with (reverse-search)': query_. Pressing Enter selects the highlighted match and returns to normal mode. Pressing Escape cancels the search.

28.10 Design Decisions

Why Not a Full Argument Parser?

Slash commands receive a raw string, not parsed arguments. This is intentional. A full parser (with flags, quoted strings, option-value pairs) would:

  1. Add complexity to every command definition
  2. Require a consistent argument syntax across 70+ commands
  3. Confuse the LLM when it generates slash commands (the LLM reasons about natural language, not flag syntax)
  4. Prevent commands from receiving arbitrary text (like /research What is the latest on MCP security?)

Each command parses its own arguments in the simplest way that works. /model sonnet splits on space. /fix-issue 42 treats the entire arg as an issue number. /research treats the entire arg as a search query. No universal syntax is needed because no two commands have the same argument semantics.

Why @ for File Mentions?

The @ prefix was chosen because: - It is visually distinct from / (commands) and natural text - It mirrors GitHub's @-mention convention - It does not conflict with any common programming syntax in user prompts - Tab completion after @ naturally suggests file paths

Why Not Inline File Resolution by the LLM?

File mentions could be resolved lazily -- leave the @file.txt text in the prompt and let the LLM call a Read tool. Early resolution is preferred because: - It saves an agent loop round trip (no tool call needed) - The user sees immediately if the file does not exist - Token budget estimation is more accurate with content already resolved - The LLM receives the full context in its first turn, enabling better initial analysis

The trade-off: large files consume context tokens even if the LLM would have only read relevant sections. The token budget guard (30% limit) mitigates this by truncating or refusing oversized mentions.
