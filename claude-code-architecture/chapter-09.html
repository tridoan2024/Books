Chapter 9: Context Window Management

In Chapter 8, we designed the message architecture — the typed, ordered conversation that flows through the agent loop. Every message in that conversation consumes tokens. Every token consumes context window space. And the context window is finite.

This is the fundamental constraint of every AI agent: the conversation grows, but the model's memory does not. A 200K-token context window sounds generous until you realize a single large file read consumes 10K tokens, tool results from a dozen operations add another 50K, and the system prompt with tool definitions occupies 20K. Within 15-20 agentic turns, a typical session approaches the window limit.

This chapter covers the architectural response to that constraint: how to allocate tokens across competing needs, how to decide what stays and what goes when space is tight, and how to compress context with minimal information loss. We will design a graduated compression pipeline, examine the compaction algorithm step by step, and establish the memory tiers that determine where information lives.

The Constraint: Finite Window, Growing Conversation

The context window is a hard limit. Exceed it, and the API rejects the request. There is no graceful degradation — you either fit, or you do not.

Three regions compete for space within the window:

System prompt (~20K tokens). The model's identity, tool definitions, project rules, and session context. This is relatively fixed — it changes rarely within a session. But it is non-negotiable: without the system prompt, the model does not know what it is, what tools it has, or what rules to follow.

Conversation history (variable). The messages exchanged between user, model, and tools. This grows with every turn. In an agentic session with many tool calls, it grows fast — each tool result can be thousands of tokens.

Output reserve (~20K tokens). Space reserved for the model's next response. The model needs room to think and respond. If the conversation fills the window completely, the model cannot generate any output.

The arithmetic is simple:

Available for conversation = Context window - System prompt - Output reserve
                           = 200,000 - 20,000 - 20,000
                           = 160,000 tokens

At 160K tokens of conversation space, with tool results averaging 2-5K tokens each, you get 30-80 tool calls before the window fills. In an agentic session that averages 5-10 tool calls per user turn, that is 3-16 user turns. The context window fills faster than most people expect.

Token Budgeting: Allocating a Finite Resource

Token budgeting is the process of deciding how to divide the context window among competing needs. It is a resource allocation problem, and like all resource allocation problems, the design reflects your priorities.

The Budget Hierarchy

Not all tokens are equal. Some are essential (the model cannot function without them), some are important (they significantly improve quality), and some are nice-to-have (they help but are not critical). The budget hierarchy reflects this priority:

        P6["Priority 6: Output Reserve<br/><i>Space for model's response</i><br/>Budget: ~20K tokens (reserved)"]

Priority 1: System prompt core is never compressed. If it does not fit, the session cannot function.

Priority 2: Recent messages are protected from compaction. The model needs the last few exchanges to understand what it is doing right now. Removing the most recent context causes the model to lose track of the current task.

Priority 3: Active tool results from the current agentic turn are important but elastic. If a tool result is 50K tokens (a large file), it can be truncated to 10K. The model sees the beginning and knows the file is large.

Priority 4: Project context (rules, memory, skills) is compressible. If space is tight, skills can be truncated. Memory can be summarized. Rules can be reduced to the most relevant subset.

Priority 5: Historical context — older messages and tool results — is the primary eviction target. When the window fills, old tool results are cleared first, then old messages are summarized. This is where the compression pipeline focuses its effort.

Priority 6: Output reserve is held back from the conversation budget entirely. It is the model's breathing room and must be protected.

Priority-Based Allocation in Practice

When the context approaches the limit, the system does not compress everything equally. It follows the priority hierarchy:

  1. First, clear old tool results (Priority 5). Replace the content of tool results from turns more than N turns ago with [Old tool result cleared]. This is the cheapest compression — no LLM call, no information loss in recent context.

  2. Next, truncate large active tool results (Priority 3). If a single tool result is 50K tokens, truncate it to a configurable budget (e.g., 10K). The model sees the first part and knows more exists.

  3. Then, summarize old messages (Priority 5). Use an LLM to create a summary of the oldest messages and replace them with the summary. This is expensive (an API call) but produces high-quality compression.

  4. Finally, compress project context (Priority 4). Truncate skills, reduce memory, trim rules. This is a last resort — removing project context degrades the model's understanding of the codebase.

The system never compresses Priority 1 (system prompt core) or Priority 2 (recent messages). If these do not fit in the window, the session is in an unrecoverable state and should be cleared.

The Graduated Compression Pipeline

The compression pipeline is the central architectural concept of context management. It implements the priority hierarchy as a sequence of increasingly aggressive strategies, each triggered only when cheaper strategies cannot reduce context enough.

Tier 0: API-Native Context Management

The cheapest possible tier: delegate compression to the API server itself. No local computation, no extra API call. The agent sends directives with the request telling the server to clear old tool results and thinking blocks from the cached context.

When it fires: Always — it is configuration, not a conditional action.

What it does: Tells the server to clear tool result content from messages older than a threshold (e.g., when input exceeds 180K tokens, keep only the 5 most recent tool results). Tells the server to clear thinking blocks from older turns.

Cost: Zero. The server handles it.

Trade-off: Only handles tool results and thinking blocks. Cannot compress conversation text, user messages, or system prompt content.

Tier 1: Tool Result Budget Enforcement

Individual tool results can be enormous. A Read of a large file might return 50K tokens. A Bash command might produce megabytes of output. Without a per-result budget, a single tool call can consume a third of the context window.

When it fires: Before every API call, during context preparation.

What it does: Scans each tool result. If it exceeds the per-tool budget (configurable per tool, default varies), truncates it to the budget. Appends a marker: [Output truncated: showing first N characters of M total].

Cost: Near-zero — string truncation is O(n) with small constant.

Trade-off: The model loses the tail of large tool results. For file reads, this usually means losing the end of the file. For command output, it means losing later log lines. The truncation marker tells the model that more content exists, so it can request the rest if needed.

Tier 2: History Snipping

The simplest form of history management: remove the oldest messages by count or by token budget.

When it fires: Before every API call, after tool result budgeting.

What it does: Counts messages from the oldest end. Removes complete message groups (as defined in Chapter 7 — one assistant response and its tool results) until the total is under a target. Preserves the compact boundary (never removes the summary from a previous compaction).

Cost: Near-zero — counting and slicing arrays.

Trade-off: Removes messages without summarizing them. The model loses all information from the removed turns. This is appropriate only when the removed messages are old enough that a summary would not help (e.g., the first few turns of a long session about a completely different topic).

Tier 3: Microcompact

A targeted compression that replaces old tool result content with lightweight markers while preserving the message structure and metadata.

When it fires: Before every API call, after history snipping.

What it does: For tool results older than a threshold (either by message count or by idle time), replaces the content with [Old tool result content cleared]. The tool call metadata (tool name, input parameters) is preserved — only the result content is cleared.

Two variants exist:

  • Time-based microcompact: Fires when the session has been idle for more than 60 minutes. Since the server-side cache has expired due to inactivity, there is no cache penalty for modifying messages. Clears all but the 5 most recent tool results.

  • Cache-aware microcompact: Uses the API's cache editing mechanism to remove tool results from the cached prefix on the server side, without changing the local message bytes. This preserves the prompt cache while reducing effective context size.

Cost: Zero for time-based (string replacement). Near-zero for cache-aware (API parameters, no extra call).

Trade-off: The model can no longer see the exact output of old tool calls. It knows what tool was called and what inputs were used, but not what the tool returned. For recent analysis, this is a significant loss. For tool calls from 20 turns ago, it rarely matters.

Tier 4: Auto-Compact (Full LLM Summarization)

When cheaper tiers cannot reduce context enough, the system makes a full LLM call to summarize the conversation. This is the most expensive tier but produces the highest-quality compression.

When it fires: After Tiers 0-3, when the token count exceeds 83.5% of the effective context window.

What it does:

  1. Determines which messages to summarize (everything except the most recent N messages, where N is calculated to keep at least 10K tokens of recent context).
  2. Sends the messages to the model with a structured summarization prompt requesting 9 specific sections (primary request, key concepts, files modified, errors fixed, problem-solving approaches, all user messages, pending tasks, current work, optional next step).
  3. Replaces the summarized messages with the summary.
  4. Re-injects critical context: recently read files, active plans, invoked skills, MCP server descriptions.

Cost: One API call for summarization. The summarization model shares the cached prefix with the main conversation, so the cost is primarily output tokens (the summary itself, typically 2-5K tokens).

Trade-off: Information loss is inevitable but structured. The 9-section prompt ensures the summary captures the most important information. Section 6 ("All User Messages") prevents the worst failure mode: forgetting what the user asked for.

Tier 5: Reactive Compact (Error Recovery)

The last resort. Fires only when the API returns a prompt-too-long error — meaning all pre-request tiers failed and the context actually exceeded the window.

When it fires: After an API error, during the agent loop's error recovery phase (Chapter 7's Phase 3).

What it does: Parses the error to extract the exact token overshoot. Removes the minimum number of message groups from the oldest end to close the gap. Summarizes the removed messages. Retries the API call.

Cost: One API call for summarization plus the wasted API call that produced the error.

Trade-off: This is a recovery path — it should rarely fire. If it fires frequently, the pre-request tiers' thresholds need tuning. Each reactive compact wastes one API call (the one that errored), so frequent reactive compaction is expensive.

Why the Ordering Matters

Each tier is cheaper and less destructive than the next:

Tier Cost Information Loss Fires
0: API-native Zero Tool result content Always
1: Result budget Near-zero Tail of large results Always
2: History snip Near-zero Oldest messages entirely When count exceeds threshold
3: Microcompact Near-zero Old tool result content When token count > threshold
4: Auto-compact 1 API call Detailed conversation → summary When at 83.5% capacity
5: Reactive 2 API calls Oldest messages → summary When API returns error

A user who stays within 30 turns never hits Tier 4. Tiers 0-3 handle their context silently. Only long, intensive sessions trigger the expensive LLM summarization. This graduated approach means the system spends the minimum cost necessary for each session's actual context pressure.

The Compaction Algorithm: Step by Step

Tier 4 (auto-compact) is the most architecturally complex tier. Here is the full algorithm:

Step 1: Determine What to Keep

The algorithm must decide where to split the conversation into "summarize" and "keep" segments. Two constraints:

  • Minimum recent context: Keep at least 10K tokens of recent messages. The model needs enough recent context to understand what it is doing.
  • Minimum message count: Keep at least 5 messages with text content. A single massive tool result should not satisfy the token minimum with only one message — the model needs conversational context.
  • Maximum keep size: Do not keep more than 40K tokens. The summary needs room to exist alongside the kept messages.
Full conversation: [M1, M2, M3, M4, M5, M6, M7, M8, M9, M10]
                    ←─── summarize ───→│←── keep ──→│
                                       split point

The split point walks backward from the end of the conversation, accumulating tokens and message counts, until both minimums are met. It then adjusts forward to avoid splitting a tool call/result pair (never separate a tool_use from its tool_result).

Step 2: Build the Summarization Request

The messages to summarize are sent to the model with a structured prompt. The prompt is carefully designed to combat known failure modes:

Failure: Task drift. After compaction, the model resumes a task that was already completed. The prompt counters this with Section 9: "Ensure this next step is DIRECTLY in line with the user's most recent explicit requests."

Failure: Recap waste. The model wastes tokens summarizing "what we did" instead of capturing "what we need to know." The prompt emphasizes action items and pending tasks over narrative history.

Failure: Lost user instructions. The model forgets a user instruction from early in the conversation. Section 6 requires "every user instruction" to be preserved in the summary, preventing this loss.

Step 3: Execute the Summarization

The summarization runs as a forked agent — a subagent that shares the main conversation's cached prefix. This is critical for cost: the summarization call does not re-process the system prompt and early conversation. It reads them from the cache at 1/10th the cost.

The fork is configured with maxTurns: 1 and tool use denied. The summarization agent produces a single response — the summary — and returns. It cannot enter an agentic loop of its own.

Step 4: Post-Compact Rebuilding

Compaction deletes messages, but the model needs context to continue working. The post-compact rebuilding pipeline re-injects critical context:

    COMPACT --> R4[Re-announce MCP tools<br/>Dynamic tool availability]
    COMPACT --> R5[Re-run session hooks<br/>CLAUDE.md and memory]
    COMPACT --> R6[Re-inject agent status<br/>Running background agents]

    R1 --> RESULT[Rebuilt Conversation]
    R2 --> RESULT
    R3 --> RESULT
    R4 --> RESULT
    R5 --> RESULT
    R6 --> RESULT

Each re-injection has its own token budget. The budgets are chosen so that rebuilding itself does not trigger another compaction:

  • File restoration: 50K total, 5K per file, top 5 files by recency
  • Skill restoration: 25K total, 5K per skill, most recently invoked first
  • Plan and agent status: typically small (<2K each)

The total rebuilding budget is ~80K tokens in the worst case — well within the 160K conversation space after a compaction that reduced the conversation to ~40K.

Step 5: Cache Reset

After compaction, caches that reference pre-compaction messages must be invalidated:

  • File content cache — files re-read during rebuilding have fresh content
  • Microcompact state — cleared tool result tracking is reset
  • System prompt cache — CLAUDE.md and memory may have changed
  • Cache break detection — the baseline is reset so the expected cache miss is not flagged as a break

One cache is deliberately not reset: the skill names cache. Skills are ~4K tokens each. If they are already in the cache, re-injecting them would create unnecessary cache writes. Preserving the "already sent" flag saves tokens.

The Threshold System

Four thresholds define the zones of context pressure:

Context Window: 200,000 tokens
  - Output Reserve: 20,000
  = Effective Window: 180,000

  ┌──────────────────────────────────────────────────────────────┐
  │                                                              │
  │   Normal Zone        Warning Zone    Compact    Blocking     │
  │   (< 73.5%)         (73.5-83.5%)    Zone       Limit        │
  │                                     (83.5-     (> 88.5%)    │
  │                                      88.5%)                  │
  │   ●──────────────────●──────────────●─────────●─────────●   │
  │   0                  147K           167K      177K      180K │
  │                                                              │
  └──────────────────────────────────────────────────────────────┘

  Status bar:  🟢 Green        🟡 Yellow      🔴 Red     🔴 Blocked
  Action:      None           None           Auto-      API calls
                                             compact    blocked

The 13K auto-compact buffer is tuned so compaction fires before the blocking limit but not so aggressively that every large tool result triggers it. The gap between auto-compact (83.5%) and blocking (88.5%) gives the compaction call room to complete — the summary itself needs tokens to generate.

The 20K warning buffer provides early user notification. The status bar turns yellow at 73.5%, giving the user time to manually compact (with /compact) before auto-compact fires.

The 3K manual compact buffer is more aggressive than auto-compact because the user explicitly asked for compaction. When you type /compact, the system compacts even if only 3K tokens of headroom remain.

Threshold Design Rationale

Why 83.5% for auto-compact instead of, say, 90% or 95%?

The answer is the compaction cost: the summarization API call itself consumes tokens. The model needs space to read the messages being summarized (they are sent as part of the summarization request). If the threshold is too high (95%), there is not enough room for the summarization call, and the summarization itself fails with a prompt-too-long error.

The 13K buffer was determined empirically: the p99.99 of summarization output is ~17K tokens. With a 20K output reserve and a 13K buffer, there is 33K tokens of headroom for the summarization call. This is enough for all but the most extreme cases.

Memory Tiers: Where Information Lives

Not all context lives in the conversation. The agent system has multiple storage tiers with different characteristics:

Tier 1 (System Prompt) is the model's permanent memory for this session. Information here is always visible. It is cached for efficiency. Adding to the system prompt increases per-turn cost but guarantees the model always has access.

Tier 2 (Conversation History) is the model's working memory. It grows with every turn and is compressed when full. Information here is visible until compacted.

Tier 3 (Persistent Memory) bridges sessions. Auto-memory files, project configuration, and CLAUDE.md imports are loaded into the system prompt at session start. Information here survives session restarts. The compaction summary is also written to persistent memory, so the next session can read what the previous session accomplished.

Tier 4 (Transcript) is the complete record. Every message, every tool result, every system injection — all persisted to a JSONL file on disk. The model cannot see this tier directly, but after compaction, the model can be told "the full transcript is at [path] — use Read to access it." This turns compaction from a lossy operation into a recoverable one.

Tier 5 (External Knowledge) is everything accessible through tools: the filesystem, the web, databases, APIs. The model retrieves information on demand. This tier is unlimited in size but requires a tool call (and therefore a loop iteration) to access.

Tier Interactions

Information flows between tiers:

  • Tier 5 → Tier 2: A tool read brings external knowledge into the conversation.
  • Tier 2 → Tier 4: Compaction archives old messages to the transcript.
  • Tier 2 → Tier 1/3: Compaction summary enters persistent memory and may be loaded into the system prompt.
  • Tier 4 → Tier 2: After compaction, the model can Read the transcript file, bringing archived information back into the conversation.

This last interaction — transcript recovery — is architecturally significant. It means compaction is not truly lossy. The full detail is always available on disk. The model just needs to know where to find it and be motivated to look. The compaction summary includes a reference: "For specific details from before compaction, read the full transcript at: [path]."

Key Design Decisions in the Algorithm

Session memory as a zero-cost compaction path. Before invoking the expensive LLM summarization, the algorithm checks if a session memory summary is available. Session memory is extracted incrementally by a background process during the session — it is pre-computed. Using it for compaction avoids the LLM call entirely. If the pre-computed summary is fresh enough and the post-compact size fits, this path saves 100% of the compaction cost.

Circuit breaker on consecutive failures. If the LLM summarization fails three times consecutively (the summary itself exceeds the window, or the API is unavailable), the circuit breaker trips and blocks further API calls. This prevents the catastrophic scenario discovered in production: sessions that retried compaction thousands of times, wasting 250K API calls per day globally.

Post-compact rebuilding as a separate step. After compaction succeeds, the system re-injects critical context (files, plans, skills). This is a separate step because it must happen regardless of which compaction tier fired. Whether Tier 4 (auto-compact) or Tier 5 (reactive compact) reduced the context, the model needs the same post-compact rebuilding.

Auto-Compaction: Triggering at 80% Context Usage

Auto-compaction is the mechanism that triggers Tier 4 compaction when context usage exceeds a threshold. The design decisions around the trigger are as important as the compaction algorithm itself.

Why Not Compact at 100%?

If you compact only when the window is completely full, you have no room for the compaction call itself. The summarization API call sends the messages being summarized as input — which are the messages that are filling the window. You need headroom.

Additionally, compacting at 100% means the model is already in a degraded state. It is trying to generate a response with barely any output space. The response quality suffers. Compacting earlier (at 80-85%) preserves response quality.

Why Not Compact at 50%?

If you compact too early, you waste an LLM call and lose conversational detail unnecessarily. The model still has room. Let it work.

The sweet spot is around 80-85% — high enough that you have utilized most of the window, low enough that there is room for the compaction call and the model's next response.

The Tracking State

Auto-compaction tracks its own state across turns:

@dataclass
class AutoCompactTracking:
    last_token_count: int           # Token count at last check
    consecutive_failures: int       # Circuit breaker counter
    last_compact_turn: int          # When compaction last fired
    compaction_in_progress: bool    # Prevent concurrent compaction

The consecutive_failures counter is the circuit breaker. The compaction_in_progress flag prevents a subtle race condition: if two concurrent API calls both detect high context pressure, they might both trigger compaction simultaneously, producing two conflicting summaries. The flag serializes compaction.

Cache-Aware Design

Every compression strategy must answer the question: does this bust the prompt cache?

The prompt cache stores the byte sequence of the system prompt and early conversation messages. A cache hit costs 1/10th of a cache miss. Modifying any byte in the cached region invalidates the cache and costs 10x more.

Tier Cache Impact Why
0: API-native Zero Server handles it
1: Result budget Zero Truncation happens before caching
2: History snip Potentially invalidates Removing messages shifts byte positions
3: Microcompact (time-based) Acceptable Only fires when cache is cold (>60 min idle)
3: Microcompact (cache-aware) Zero Uses server-side cache editing API
4: Auto-compact Invalidates, but shares prefix Fork agent shares parent's cached prefix
5: Reactive Invalidates Accepted cost of error recovery

The cache-aware microcompact (Tier 3, cache variant) is the most architecturally interesting case. It does not modify local messages at all. Instead, it sends directives to the server: "delete the content of tool result X from the cached prefix." The server modifies its cache without the client changing any bytes. The cache key stays stable.

This is worth emphasizing: the entire cache-aware microcompact tier exists because modifying a byte in the local message stream would invalidate a cache that cost 50-70K tokens to create. The engineering effort of building a server-side cache editing mechanism is justified by the 10x cost savings on every subsequent API call.

Design Lessons

Building the context window management system for a production AI agent teaches nine principles:

1. Graduate your compression strategies. Cheap operations first (string truncation, server-side directives), expensive operations last (LLM summarization), error-driven recovery as the absolute last resort. Users never pay for more compression than they need.

2. Budget tokens by priority. System prompt and recent messages are non-negotiable. Old tool results are the primary eviction target. Project context is compressible but valuable. The priority hierarchy determines what the model remembers when space is tight.

3. Design compaction around cache economics. A cache-busting compaction can cost more than the context it saves. The 10x difference between cache hits and misses means every compression strategy must answer "does this bust the cache?" before it modifies a byte.

4. Circuit-break runaway compaction. Compaction that fails can trigger more compaction. Without a failure budget, pathological sessions retry thousands of times. Three consecutive failures should disable auto-compaction for the session.

5. Pre-extract summaries in the background. Session memory — incrementally extracted during the session — enables zero-LLM-cost compaction. Background extraction during natural breaks amortizes the cost. When compaction triggers, the summary is already available.

6. Rebuild context after compaction. Compaction deletes messages, but the model needs context to continue — recently read files, active plans, invoked skills. Post-compact rebuilding with strict per-category token budgets (50K for files, 25K for skills) prevents rebuilding from triggering another compaction.

7. Make compaction recoverable, not lossy. Write pre-compaction messages to the transcript. Include a reference in the summary: "Full details at [path]." The model can Read the transcript to recover specific details. Compaction becomes a visibility reduction, not a permanent deletion.

8. Set thresholds with headroom for the compaction call itself. Auto-compact at 83.5%, not 100%. The gap between the trigger and the hard limit gives the summarization call room to execute. Without this headroom, the summarization call itself fails due to context overflow.

9. Separate main-thread from subagent compaction. Module-level caches are shared across forks. A subagent's compaction must not reset the main thread's microcompact state, cache break detection baseline, or system prompt cache. Guard every cleanup function with a thread-identity check.
