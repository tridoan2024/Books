Chapter 26: Worktree Isolation

An AI agent that edits files in your working directory is performing surgery on a live patient. Every half-finished edit, every speculative refactor, every failed experiment leaves debris in the codebase. If the agent makes three changes and the third one fails, you are left with two applied changes and one broken state -- and undoing them means manually reverting files you may not even know were touched.

Git worktrees solve this by giving the agent its own operating room. A worktree is a separate checkout of the same repository, with its own working directory and its own branch, but sharing the same git history. The agent can modify files, run tests, commit changes, and evaluate results -- all without touching the main workspace. If the experiment succeeds, the changes merge back cleanly. If it fails, the worktree is deleted and the main workspace is untouched.

This chapter covers the architecture of worktree isolation for AI agents: why it matters, how the lifecycle works, branch management strategies, the batch operation pattern for parallel multi-file work, rollback mechanics, and a decision framework for when to use worktrees versus direct editing. As we discussed in Chapter 25 (Agent Communication & Orchestration), worktrees are the filesystem isolation primitive that enables safe parallel write operations across multiple subagents.

26.1 Git Worktrees as an Isolation Primitive

A git worktree is a feature of git itself (since git 2.5, released in 2015) that allows multiple working directories to be attached to a single repository. Each worktree has its own index, its own HEAD, and its own checked-out branch -- but all worktrees share the same .git directory and object store.

For AI agent architectures, worktrees provide three properties that no other isolation mechanism offers:

Property 1: Filesystem Isolation Without Repository Duplication

Cloning a repository creates a full copy of the git history. For a large repository, this can be gigabytes of data and take minutes. A worktree, by contrast, creates only a new working directory with checked-out files -- the git history is shared. Creating a worktree in a 10GB repository takes seconds, not minutes.

Property 2: Branch-Level Isolation

Each worktree operates on its own branch. Changes committed in worktree A are on branch A, changes in worktree B are on branch B, and changes in the main workspace are on the main branch. There is no possibility of write conflicts between worktrees because git enforces that no two worktrees can have the same branch checked out simultaneously.

Property 3: Atomic Discard

Deleting a worktree removes its working directory and branch reference in a single operation. There is no cleanup of scattered files, no need to revert individual changes, no risk of missing a modified file. The entire experiment disappears atomically.

These three properties -- cheap creation, branch isolation, atomic discard -- make worktrees the ideal isolation primitive for AI agent work.

26.2 Why File-Level Isolation Matters for AI Agents

AI agents interact with the filesystem differently than human developers. A human developer typically works on one conceptual change at a time, understands the impact of their edits, and can manually recover from mistakes. An AI agent might modify 15 files in rapid succession as part of a refactoring, with each edit dependent on the previous one succeeding.

The Half-Finished Edit Problem

Consider an agent performing a rename refactoring: rename UserService to AccountService across the codebase. The agent finds 12 files that reference UserService and begins editing them in sequence. On file 8, the edit fails -- perhaps the file has an unexpected structure, or the agent's context window fills up and it produces a malformed edit.

Without worktree isolation, the main workspace now has 7 files with the new name and 5 files with the old name. The codebase is in an inconsistent state. The agent cannot roll back its changes because it did not track which files it modified (and even if it did, the original content is not preserved in a recoverable form outside of git).

With worktree isolation, all 7 edits happened in a separate directory. The main workspace is untouched. The user can inspect the worktree to see what the agent accomplished, decide whether to continue manually, or simply delete the worktree and start over.

The Speculative Work Pattern

AI agents excel at exploring possibilities. "What if we refactored this module to use async/await throughout?" "What if we replaced the custom logger with a standard library?" These speculative explorations are valuable but risky -- the agent might invest 20 tool calls into a refactoring that the user ultimately rejects.

Worktrees make speculation cheap. The agent works in an isolated directory, the user reviews the result, and a single decision -- merge or discard -- resolves the experiment. The user never needs to disentangle speculative changes from their actual work.

The Parallel Work Pattern

When multiple subagents need to write files simultaneously (as described in the orchestration patterns of Chapter 25), they cannot all write to the same working directory. Two agents editing the same file will produce conflicts. Even agents editing different files in the same directory can create unexpected interactions -- for example, both might update an index.ts barrel file.

Worktrees give each agent its own directory and branch, eliminating write conflicts entirely. After all agents complete, the parent orchestrator merges their branches, resolving any conflicts in a controlled manner.

26.3 The Worktree Lifecycle

Every worktree follows a five-phase lifecycle: create, work, evaluate, merge-or-discard, and cleanup.

stateDiagram-v2
    [*] --> Create: Agent needs isolation
    Create --> Work: Worktree ready
    Work --> Evaluate: Agent finished
    Evaluate --> Merge: User approves
    Evaluate --> Discard: User rejects
    Merge --> Cleanup: Branch merged
    Discard --> Cleanup: Branch deleted
    Cleanup --> [*]: Directory removed

    Work --> Evaluate: Agent timed out
    Work --> Discard: Agent failed

Phase 1: Create

The system creates a new worktree from the current HEAD with a purpose-specific branch name.

What happens: 1. A new branch is created from the current HEAD (or a specified base). 2. A new directory is created under .claude/worktrees/<name>/. 3. Files are checked out into the new directory. 4. The agent's working directory is set to the worktree.

Design decisions: - Location: Worktrees are created under .claude/worktrees/ rather than a system-level temporary directory. This keeps them visible to the user, version-controlled (the directory is gitignored, but its existence is predictable), and easy to find for debugging. - Branch base: The worktree branches from HEAD by default, giving the agent the same starting state as the main workspace. This is important for consistency -- if the agent reads a file in the worktree, it sees the same content as the main workspace. - Naming: The worktree and branch names include the agent type and a short identifier (e.g., fix-auth-a3b2c1) for traceability.

Phase 2: Work

The agent operates in the worktree exactly as it would in the main workspace. All file operations (read, write, edit) target the worktree directory. Bash commands run with the worktree as the working directory. Git operations apply to the worktree's branch.

The agent can make multiple commits, run tests, and iterate on changes -- all within the worktree. This is identical to how a human developer works on a feature branch.

Phase 3: Evaluate

When the agent finishes (or times out), the system enters the evaluation phase. The user reviews the changes:

  • Git diff shows what the agent changed relative to the base branch.
  • Test results (if the agent ran them) indicate whether the changes are correct.
  • Agent's summary explains what was done and why.

The evaluation phase is where human judgment enters the loop. The agent proposes changes, the human decides whether to accept them. This is a critical safety property -- the worktree pattern ensures that no agent-generated changes affect the user's workspace without explicit approval.

Phase 4: Merge or Discard

Based on the evaluation, the user makes a binary decision:

Merge: The worktree's branch is merged (or rebased) into the original branch. The changes become part of the main codebase. The merge strategy depends on the workflow: - Merge commit preserves the agent's branch history, showing that the changes were made by an agent. - Rebase produces a linear history as if the changes were made directly on the main branch. - Squash combines the agent's potentially many commits into a single commit.

Discard: The worktree's branch and directory are deleted. No changes reach the main codebase. This is the "undo everything" option and is always safe.

Phase 5: Cleanup

After the merge or discard decision, the worktree directory and its branch reference are removed. Git's worktree pruning ensures no stale references remain.

Cleanup checklist:
1. Delete worktree directory: .claude/worktrees/<name>/
2. Delete worktree branch: git branch -D <branch-name>
3. Prune worktree references: git worktree prune
4. Remove from agent tracker: mark delegation as complete

26.4 Branch Management

Branch naming and management are seemingly minor details that become critical in production systems with multiple agents creating worktrees concurrently.

Naming Conventions

Worktree branches follow a predictable naming scheme:

claude/<purpose>/<short-id>

Examples:
  claude/fix-auth/a3b2c1
  claude/refactor-api/d4e5f6
  claude/explore-perf/g7h8i9
  claude/batch-rename/j0k1l2

The three-part structure serves specific purposes: - Prefix (claude/) identifies agent-created branches, making them easy to filter in branch listings. - Purpose describes what the worktree is for, aiding human review. - Short ID ensures uniqueness when multiple agents create worktrees for the same purpose.

Preventing Branch Conflicts

Git worktrees enforce a fundamental constraint: no two worktrees can check out the same branch. This means the branch name must be unique at creation time. The short ID suffix handles this, but the system also validates:

  1. The branch name does not already exist (local or remote).
  2. No other worktree is using this branch.
  3. The branch name conforms to git's naming rules (no spaces, no .., no trailing .lock).

Automatic Cleanup of Stale Branches

Agent-created branches can accumulate if worktrees are not properly cleaned up -- for example, if the process crashes after creating a worktree but before cleanup. A cleanup sweep runs on session start:

Stale branch detection:
1. List all branches matching claude/*
2. For each, check if a corresponding worktree exists
3. If no worktree exists and the branch has no unique commits
   (i.e., it was never used or its changes were merged), delete it
4. If the branch has unmerged commits, log a warning but do not delete

The conservative approach -- only deleting branches with no unique commits -- prevents data loss. If an agent made changes that were never merged, the branch is preserved until the user explicitly deletes it.

26.5 The Batch Operation Pattern

The most powerful application of worktree isolation is the batch operation: a multi-file change where each file (or module) is handled by a separate agent in its own worktree.

The Problem Batch Operations Solve

Consider a large-scale refactoring: updating all API endpoints to use a new error handling pattern. The codebase has 30 endpoint files across 6 modules. A single agent attempting this sequentially would:

  1. Fill its context window after 10-15 files.
  2. Start making inconsistent changes as context degrades.
  3. Leave the codebase in a partially-updated state if it times out.

The Batch Architecture

graph TB
    PARENT["Parent Agent:<br/>Coordinates batch operation"] --> PLAN["Planning Phase:<br/>Identify files, define transformation"]

    PLAN --> W1["Worktree 1<br/>Agent A: endpoints/users.ts"]
    PLAN --> W2["Worktree 2<br/>Agent B: endpoints/orders.ts"]
    PLAN --> W3["Worktree 3<br/>Agent C: endpoints/products.ts"]
    PLAN --> W4["Worktree 4<br/>Agent D: endpoints/auth.ts"]

    W1 --> MERGE["Merge Phase:<br/>Combine all branches"]
    W2 --> MERGE
    W3 --> MERGE
    W4 --> MERGE

    MERGE --> VERIFY["Verification:<br/>Run tests, check types,<br/>validate consistency"]

    VERIFY --> RESULT["Result:<br/>Single commit with all changes<br/>or detailed failure report"]

    style PARENT fill:#e8f4f8,stroke:#2196F3
    style PLAN fill:#e8f5e9,stroke:#4CAF50
    style MERGE fill:#fff3e0,stroke:#FF9800
    style VERIFY fill:#fce4ec,stroke:#E91E63

The batch operation proceeds in four phases:

Phase 1: Planning. The parent agent identifies all files that need modification and defines the transformation to apply. This plan is expressed in a format that each individual agent can follow independently. The plan must be self-contained -- each agent only sees the plan and its assigned file(s), not the other agents' work.

Phase 2: Parallel Execution. Each agent receives its worktree and its file assignment. Agents work in parallel, each applying the transformation to its assigned files. Because each worktree is on a separate branch, there are no write conflicts.

Phase 3: Merge. After all agents complete, the parent merges all worktree branches into a single branch. This is where conflicts can arise -- if two agents both modified a shared file (like a barrel export or a type definition), the merge will conflict. The parent resolves these conflicts, either automatically (for simple cases like barrel exports) or by flagging them for human review.

Phase 4: Verification. The merged branch is checked for consistency: tests pass, types check, the transformation was applied uniformly. If verification fails, the parent can identify which agent's changes are problematic and either retry that agent or flag the issue.

Conflict Prevention Strategies

The most common source of conflicts in batch operations is shared files -- files that multiple agents need to modify because they contain cross-cutting concerns (barrel exports, type definitions, configuration files).

Strategy Approach Trade-off
Exclusion Shared files are excluded from individual agents and updated by the parent after merge Requires the parent to understand the shared file format
Last-writer-wins One designated agent updates shared files; others skip them Simple but may miss necessary changes
Sequential shared phase After parallel phase, a single agent updates all shared files Adds sequential time but avoids conflicts
Conflict resolution agent A dedicated agent resolves merge conflicts after the parallel phase Most flexible but adds complexity

The recommended default is the sequential shared phase: let the parallel agents handle their assigned files without touching shared files, then run a single agent to update all shared files based on the combined results. This avoids conflicts entirely at the cost of a short sequential step after the parallel phase.

26.6 Rollback Patterns

One of the strongest guarantees worktree isolation provides is clean rollback. If an experiment fails, the rollback is complete and atomic -- no leftover files, no partial changes, no corrupted state.

Rollback Granularity

Worktree rollback operates at three levels:

Level 1: Full Discard. Delete the worktree and its branch. All changes are gone. This is the most common rollback -- the experiment failed, the user rejects the changes, or the agent timed out.

Before: main workspace + worktree with 15 modified files
After:  main workspace only, no trace of the experiment

Level 2: Partial Revert. The worktree contains some good changes and some bad ones. The user or agent cherry-picks the good commits and discards the rest.

Before: worktree with commits A, B, C, D (C is bad)
Action: cherry-pick A, B, D onto main branch
After:  main workspace + A, B, D applied; C discarded

Level 3: Commit-Level Undo. Within the worktree, the agent made a commit that broke tests. The agent reverts that specific commit and continues working.

Before: worktree at commit D (tests failing)
Action: git revert D within worktree
After:  worktree at commit E (revert of D), tests passing

Safe Discard Protocol

The discard operation must handle edge cases:

  1. Uncommitted changes. If the worktree has uncommitted modifications, a naive git worktree remove will fail. The system must either force-remove (discarding changes) or warn the user.

  2. Running processes. If the agent launched background processes (tests, servers) in the worktree directory, they must be terminated before the directory can be deleted.

  3. File locks. On some systems, open file handles prevent directory deletion. The cleanup process retries with exponential backoff if the initial deletion fails.

flowchart TD
    A[Discard requested] --> B{Uncommitted changes?}
    B -->|No| D[Delete worktree]
    B -->|Yes| C{User confirmed<br/>force discard?}
    C -->|Yes| D
    C -->|No| E[Warn user,<br/>preserve worktree]
    D --> F{Running processes<br/>in worktree?}
    F -->|Yes| G[Terminate processes]
    F -->|No| H[git worktree remove]
    G --> H
    H --> I{Delete succeeded?}
    I -->|Yes| J[Delete branch<br/>git branch -D]
    I -->|No| K[Retry with backoff]
    K --> I
    J --> L[git worktree prune]
    L --> M[Done]

26.7 When to Use Worktree Isolation vs. Direct Editing

Not every task needs worktree isolation. The overhead of creating and managing worktrees -- branch creation, directory checkout, merge back -- is small but non-zero. For many tasks, direct editing in the main workspace is simpler and faster.

The Decision Framework

flowchart TD
    A[Agent task requires<br/>file modifications] --> B{Speculative?<br/>User might reject changes}
    B -->|Yes| USE["Use worktree"]
    B -->|No| C{Multiple agents<br/>writing simultaneously?}
    C -->|Yes| USE
    C -->|No| D{More than 5<br/>files modified?}
    D -->|Yes| E{Changes are<br/>easily reversible?}
    D -->|No| DIRECT["Edit directly"]
    E -->|No| USE
    E -->|Yes| F{Agent might<br/>time out mid-task?}
    F -->|Yes| USE
    F -->|No| DIRECT

Decision Table

Scenario Worktree? Rationale
Fix a single bug in one file No Simple, easily reversible with git checkout
Rename a variable across 3 files No Small scope, git can revert
Refactor a module (10+ files) Yes Large blast radius, might fail mid-way
Speculative "what if" exploration Yes High probability of discard
Parallel agents writing different features Yes Prevents write conflicts
Batch rename across 30 files Yes Too many files for safe direct editing
Add a new file (test, docs) No No existing files at risk
Upgrade a dependency and fix breaks Maybe Depends on how many files break

The Cost of Worktree Overhead

Worktree creation involves: - Branch creation: ~10ms - Checkout (file copy): 100ms - 5s depending on repo size - Merge back: 100ms - 1s for clean merges - Cleanup: ~50ms

For a large repository (100K+ files), the checkout phase can take several seconds. For small repositories, the overhead is negligible. The heuristic: if the task takes more than 30 seconds of agent time, the worktree overhead is insignificant. If the task is a quick 5-second edit, worktree overhead doubles the wall-clock time.

26.8 Worktree Isolation in Multi-Agent Orchestration

Worktree isolation connects directly to the orchestration patterns from Chapter 25. When the fan-out/fan-in pattern involves write operations, each agent in the fan-out phase operates in its own worktree.

Integration with Orchestration Patterns

Fan-Out/Fan-In with Worktrees:

Parent creates worktree for each agent:
  .claude/worktrees/agent-1/  (branch: claude/fix-module-a/abc123)
  .claude/worktrees/agent-2/  (branch: claude/fix-module-b/def456)
  .claude/worktrees/agent-3/  (branch: claude/fix-module-c/ghi789)

Agents work in parallel (isolated filesystems)

Parent merges all branches:
  git merge claude/fix-module-a/abc123
  git merge claude/fix-module-b/def456
  git merge claude/fix-module-c/ghi789

Verification on merged result

Pipeline with Worktrees:

Stage 1 agent works in worktree-1 (branch: claude/investigate/abc123)
  Commits findings as code comments or a report file

Parent reviews Stage 1 results

Stage 2 agent works in worktree-2, branched FROM worktree-1's branch
  (branch: claude/fix/def456, base: claude/investigate/abc123)
  Inherits Stage 1's changes and adds fixes

Stage 3 agent works in worktree-3, branched FROM worktree-2's branch
  Inherits all prior changes and adds tests

The pipeline variant is particularly elegant: each stage branches from the previous stage's branch, creating a chain of incremental changes. If any stage fails, the chain can be rewound to the last good stage.

Resource Management

Multiple concurrent worktrees consume disk space (one copy of the working tree per worktree) and git lock resources (each worktree operation takes brief locks on the shared .git directory). The architecture enforces limits:

Resource Limit Rationale
Concurrent worktrees 5 Prevents disk exhaustion on large repos
Worktree lifetime 30 minutes Prevents orphaned worktrees from accumulating
Total worktree disk 2x repo size Hard limit prevents runaway disk usage

These limits are configurable but default to conservative values. A 10GB repository with 5 concurrent worktrees uses 50GB of additional disk. On resource-constrained systems, reducing the concurrency limit to 2-3 is advisable.

26.9 Merge Strategies for Agent-Created Branches

When a worktree's changes are accepted, the merge strategy determines how they integrate into the main branch. The choice affects git history readability, conflict handling, and auditability.

Strategy Comparison

Strategy History Shape Audit Trail Conflict Handling Best For
Merge commit Non-linear, branch visible Full: agent's branch preserved Manual at merge time Complex multi-commit changes
Rebase Linear, clean Agent commits appear on main Conflict per commit Simple sequential changes
Squash Linear, single commit Compressed: one commit for all Single conflict point Many small agent commits

Merge commit is the most informative option. The branch history is preserved, showing exactly what the agent did in what order. A git log --graph clearly shows the agent's work as a branch. The downside is a non-linear history that some teams find harder to read.

Rebase produces the cleanest linear history but rewrites the agent's commits onto the tip of the main branch. If conflicts arise, they must be resolved for each commit individually. This is suitable for simple changes where the agent made 1-3 clean commits.

Squash is the pragmatic default for AI agent work. The agent might make 10+ small commits (read file, edit, test, adjust, test again), and preserving all of them adds noise to the history. Squashing produces a single commit that represents the final state, with a commit message that summarizes the entire change.

Recommended Default

For AI agent worktrees, squash merge with a descriptive commit message is the recommended default:

git merge --squash claude/fix-auth/abc123
git commit -m "fix: prevent JWT token reuse after expiry

Applied by AI agent (security-reviewer type, 18 turns).
Changes: src/auth/jwt.ts, src/auth/session.ts, tests/auth.test.ts

Co-Authored-By: Claude <noreply@anthropic.com>"

The commit message attributes the change to the AI agent and lists the affected files, providing both auditability and a clean history.

26.10 Key Takeaways

  1. Worktrees provide filesystem isolation without repository duplication. Creating a worktree is fast (seconds, not minutes) because it shares the git object store with the main repository. This makes worktrees practical for routine agent operations, not just major features.

  2. Three properties make worktrees ideal for AI agents: cheap creation, branch-level isolation, and atomic discard. These properties directly address the half-finished edit problem, speculative work, and parallel write conflicts.

  3. The lifecycle is create-work-evaluate-merge/discard-cleanup. The evaluation phase is where human judgment enters the loop. No agent-generated changes affect the user's workspace without explicit approval.

  4. Branch naming conventions enable management at scale. The claude/<purpose>/<id> convention makes agent-created branches identifiable, filterable, and traceable.

  5. Batch operations are the killer use case. Large-scale refactoring across many files benefits enormously from parallel worktrees: each agent handles its assigned files independently, and the results are merged after verification.

  6. Not every task needs a worktree. Single-file edits, new file creation, and small changes are faster without worktree overhead. Use the decision framework: speculative? parallel writes? large blast radius? If none, edit directly.

  7. Squash merge is the pragmatic default. AI agents make many small commits during their work. Squashing produces a clean single commit that represents the final state, with attribution in the commit message.

  8. Resource limits prevent runaway worktree creation. Cap concurrent worktrees (default: 5), enforce lifetime limits (default: 30 minutes), and monitor disk usage. Stale worktree cleanup runs on session start.

  9. Worktrees integrate naturally with orchestration patterns. Fan-out/fan-in with worktrees enables parallel writes. Pipeline worktrees branch from previous stages, creating incremental change chains. Both patterns benefit from worktree isolation.

  10. Rollback is always an option. The strongest guarantee worktree isolation provides is that any experiment can be completely undone. This freedom to experiment without risk is what makes AI agent work productive rather than anxiety-inducing.

The worktree isolation pattern completes the multi-agent architecture. With the subagent design philosophy from Chapter 24, the orchestration patterns from Chapter 25, and the worktree isolation from this chapter, you have the full toolkit for building multi-agent systems that are safe, scalable, and maintainable.
