Appendix B: Component Dependency Map

Reading This Map

The chapters of this book examine subsystems individually --- the tool system in Part V, the permission system in Part VI, the streaming pipeline in Part IV. But production systems do not run in isolation. Every request flows through multiple subsystems, and understanding the dependencies between them is essential for reasoning about change propagation, failure modes, and performance bottlenecks.

This appendix presents the full component dependency map for an AI CLI agent architecture. It covers all 12 major subsystems, their dependency relationships, the layered architecture that organizes them, a component interaction matrix, critical path analysis, and strategies for preventing the circular dependencies that plague large TypeScript codebases.

The Four-Layer Architecture

The subsystems organize into four layers, each with a strict dependency rule: layers may depend on layers below them, never on layers above. This is the Dependency Rule from Clean Architecture, adapted for an AI agent system.

Layer 1: Infrastructure

Components: Configuration, Session Manager, API Client

Dependency rule: Depends only on standard library and external packages. Never depends on domain or application logic.

The infrastructure layer provides the primitives that every other layer needs: configuration values, persistent session state, and API communication. These components have no knowledge of tools, permissions, or the agent loop. They expose generic interfaces: "read a config value," "persist a transcript entry," "send a message to the model."

This layer changes least frequently. A new configuration source, a new API provider, or a new persistence backend can be added without touching the agent loop or tool system.

Layer 2: Domain

Components: Tool System, Permission System, Security Engine, MCP Runtime

Dependency rule: Depends on Infrastructure. Never depends on Application or UI.

The domain layer contains the core business logic of the AI agent: what tools exist, what permissions govern them, how security analysis works, and how external tool servers are managed. These components define the rules of the system --- what the agent can do, what it is allowed to do, and what is considered dangerous.

The domain layer depends on configuration (to read permission rules, tool settings, security thresholds) and session state (to track tool usage, permission grants). It does not depend on the agent loop --- the tool system does not know when it will be called, only how to execute when it is.

Layer 3: Application

Components: Bootstrap, Agent Loop, Message Assembler, Multi-Agent

Dependency rule: Depends on Domain and Infrastructure. Never depends on UI.

The application layer orchestrates the domain components into workflows. The agent loop calls the message assembler, sends messages through the API client, dispatches tool calls through the tool system, checks permissions through the permission system, and persists state through the session manager. It is the conductor of the orchestra.

The Multi-Agent component sits here because subagent orchestration is an application concern --- it decides when to delegate and how to aggregate results, using domain components for the actual work.

Layer 4: UI

Components: Terminal UI

Dependency rule: Depends on all lower layers. Nothing depends on UI.

The UI layer renders state changes to the terminal and processes user input. It depends on the agent loop (to display progress), the tool system (to render tool results), the permission system (to display permission prompts), and configuration (to read display preferences).

The critical property: removing the UI layer entirely produces a headless agent that still functions. This is not hypothetical --- the SDK build does exactly this, replacing the Terminal UI with a programmatic interface. The layered architecture makes this possible because no lower layer depends on the UI.

Reading the Matrix

Column analysis reveals coupling: Configuration (column 2) is called by 9 of 11 other components. It is the most depended-upon component. Changes to the Configuration API have the widest blast radius.

Row analysis reveals coordination: the Agent Loop (row 4) calls 6 other components. It is the most coordinating component. Bugs in the agent loop can manifest as failures in any downstream component.

Diagonal emptiness confirms: no component calls itself recursively through another component (no circular dependencies at the component level).

Critical Path Analysis

Not all components are on the hot path. Understanding which components execute on every agent turn --- and which execute only during startup or on specific triggers --- is essential for performance optimization.

Always on the hot path (every turn): - Agent Loop --- orchestrates each turn - Message Assembler --- builds the prompt for each API call - API Client --- sends the request and processes the streaming response

On the hot path when tools are invoked (most turns): - Tool System --- dispatches tool calls - Permission System --- evaluates whether the tool call is allowed - Security Engine --- analyzes Bash commands (only for Bash tool invocations) - Terminal UI --- renders tool results and streaming output

Performance implications: Optimizations in the Agent Loop, Message Assembler, and API Client have the highest impact because they execute on every turn. The streaming pipeline (Chapter 11) is particularly critical --- token-by-token processing latency directly affects perceived responsiveness.

Startup only: - Bootstrap --- runs once, then hands off to the agent loop - Configuration --- cascade resolution happens once at startup, then values are cached - Session Manager --- resume check and session creation happen once - MCP Runtime --- server discovery and connection happen once (with reconnection on failure)

Performance implications: These components compete for the 400ms startup budget (Chapter 4). Startup optimization focuses here: parallel I/O for configuration and MCP discovery, deferred imports for large modules, fast-path exits for non-interactive invocations.

The Rare Path: Triggered by Specific Events

  • Multi-Agent --- only when the agent decides to delegate to subagents (Chapter 24)
  • Session Manager (persistence) --- periodically during long sessions, not on every turn
  • MCP Runtime (reconnection) --- only on server failure

Circular Dependency Prevention

Circular dependencies are the silent killer of large TypeScript codebases. When module A imports module B and module B imports module A, the result is undefined behavior at runtime: one module sees an incomplete export object. In a 500,000-line codebase with hundreds of modules, circular dependencies are easy to introduce and hard to detect.

Why AI Agent Systems Are Susceptible

AI agent architectures create natural pressure toward circular dependencies:

  1. The tool-permission cycle. The Tool System needs the Permission System (to check if a tool call is allowed). The Permission System needs the Tool System (to look up tool metadata for rule matching). Without intervention, this becomes a circular import.

  2. The loop-UI cycle. The Agent Loop needs the UI (to display progress). The UI needs the Agent Loop (to know current state). Naive implementation creates a circular dependency.

  3. The config-everything cycle. Every component reads configuration. If the Configuration component imports types from other components (for validation), the cycle closes.

Strategy 1: Interface Segregation at Layer Boundaries

Define interfaces in a shared types module that both layers import. Neither imports the other directly.

graph TB
    subgraph "Shared Types (no logic)"
        TYPES["types/<br/>ToolMetadata, PermissionRule,<br/>ToolResult, PermissionCheck"]
    end

    subgraph "Domain Layer"
        TOOL["Tool System<br/>implements ToolProvider"]
        PERM["Permission System<br/>implements PermissionChecker"]
    end

    TOOL --> TYPES
    PERM --> TYPES

    style TYPES fill:#e2e3e5,stroke:#383d41

The Tool System depends on PermissionChecker (an interface), not on the Permission System (a module). The Permission System depends on ToolMetadata (a type), not on the Tool System. Both modules are independent --- they share types, not implementations.

Strategy 2: Event-Based Decoupling

When two components need to notify each other, use an event bus instead of direct imports.

// The agent loop emits events, the UI subscribes
eventBus.emit('tool:started', { toolName, args });
eventBus.emit('tool:completed', { toolName, result });

// The UI subscribes without importing the agent loop
eventBus.on('tool:started', renderToolProgress);
eventBus.on('tool:completed', renderToolResult);

The Agent Loop and the Terminal UI never import each other. They communicate through a shared event bus that both depend on (a downward dependency to infrastructure).

Strategy 3: Dependency Inversion at the API Client Boundary

The API Client needs to know about tool schemas (to send them to the model). But the Tool System is in a higher layer. Dependency inversion resolves this:

// Infrastructure layer defines the interface
interface ToolSchemaProvider {
  getSchemas(): ToolSchema[];
}

// API Client depends on the interface
class ApiClient {
  constructor(private tools: ToolSchemaProvider) {}
}

// Application layer wires them together
const apiClient = new ApiClient(toolRegistry);

The API Client depends on an abstraction it defines (in its own layer). The Tool System implements that abstraction. The wiring happens in the Application layer, which depends on both. No upward dependency exists.

Strategy 4: Build-Time Cycle Detection

Prevention is better than cure. Run cycle detection as part of the build:

# Using madge for TypeScript cycle detection
npx madge --circular --extensions ts src/

# Or as a pre-commit hook
if npx madge --circular --extensions ts src/ | grep -q "Circular"; then
  echo "Circular dependency detected. Fix before committing."
  exit 1
fi

This catches cycles before they reach the main branch. As discussed in Chapter 34, the build system is architecture enforcement --- if the build rejects circular dependencies, they cannot exist in production.

Strategy 5: Barrel File Discipline

Barrel files (index.ts that re-export everything from a directory) are the most common source of accidental circular dependencies. A barrel file creates an implicit dependency from the barrel to every module in the directory, and from every consumer to every module in the directory.

The rule: barrel files should only exist at layer boundaries, and they should export types and interfaces, not implementations. Internal modules import each other directly, bypassing the barrel.

src/
  tools/
    index.ts          // Barrel: exports ToolSchema, ToolResult types
    registry.ts       // Internal: imports from permission/types directly
    dispatch.ts       // Internal: imports from registry.ts directly
    bash-tool.ts      // Internal: imports from security/parser.ts directly

This keeps the barrel thin and prevents it from becoming a dependency magnet.

Using This Map

For Change Impact Analysis

When modifying a component, trace its outgoing and incoming dependencies in the matrix. Outgoing dependencies tell you what your changes might break. Incoming dependencies tell you who calls your code and might be affected by API changes.

Example: changing the Permission System's rule evaluation order affects the Tool System, the MCP Runtime, the Agent Loop, and the Multi-Agent system (all incoming dependencies). It does not affect the API Client or Session Manager (no dependency relationship).

For Testing Strategy

Components with high fan-in (Configuration, Permission System) need the most comprehensive unit tests, because bugs propagate to the most consumers. Components with high fan-out (Agent Loop, Terminal UI) need integration tests that verify the orchestration of their dependencies works correctly.

For Performance Profiling

Start with the hot path. Profile the Agent Loop, Message Assembler, and API Client first. Then profile Tool System and Permission System for tool-heavy workloads. Do not optimize cold-path components (Bootstrap, MCP discovery) unless startup time exceeds the budget.

For Onboarding

New engineers should read the subsystems in layer order, bottom to top: Configuration first (it has no dependencies --- the simplest to understand in isolation), then Session Manager and API Client, then the Domain layer, then the Application layer, and finally the UI. Each layer builds on the concepts from the layer below.
