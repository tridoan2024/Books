Chapter 34: The Architecture of Evolution

Software that cannot evolve dies. This is true for all systems but acutely true for AI agents, where the underlying models change quarterly, the protocol landscape shifts monthly, and user expectations advance weekly. An AI coding agent that shipped in January and has not evolved by June is already obsolete -- not because the code is wrong, but because the world has moved.

This chapter is about how to evolve a 500,000-line AI agent codebase without breaking everything. We will cover the dual feature flag strategy (compile-time for what exists in the binary, runtime for what behavior activates), backwards compatibility patterns that let you change without breaking, the build system as an architectural primitive, migration patterns for gradual rollout, technical debt management, and the architecture review process that keeps the system coherent as it grows.

The common thread is controlled change. Every pattern in this chapter exists to make change safe, observable, and reversible.

34.1 The Two Feature Flag Systems

Feature flags are the primary mechanism for controlled evolution. But AI agents need two distinct flag systems operating at different phases of the delivery pipeline:

Compile-Time Flags: What Code Exists

Compile-time flags control which code paths are included in the binary. They are evaluated during the build process -- the bundler (Bun, esbuild, webpack) replaces flag checks with true or false constants, and the tree-shaker eliminates dead code.

// In source code:
if (BUILD_FLAGS.ENABLE_EXPERIMENTAL_MCP_V2) {
  // New MCP v2 protocol support
  registerMcpV2Transport();
  registerMcpV2Tools();
}

// After bundling with ENABLE_EXPERIMENTAL_MCP_V2=false:
if (false) {
  // Entire block is tree-shaken — zero bytes in binary
}

This is architecturally significant. Code that does not exist in the binary cannot be activated by accident, cannot be discovered by reverse engineering, and does not contribute to binary size. Compile-time flags serve three purposes:

SKU generation. The same source code produces multiple products. An internal build might include debug tools, experimental features, and verbose logging. An external (public) build strips all of these:

Flag Internal External
ENABLE_DEBUG_TOOLS true false
ENABLE_EXPERIMENTAL_FEATURES true false
ENABLE_TELEMETRY_VERBOSE true false
ENABLE_INTERNAL_MCP_SERVERS true false
INCLUDE_SOURCE_MAPS true false

Dead code elimination. Features that are deprecated but not yet removed can be flagged off at compile time. The code remains in the source for reference and potential reactivation, but it adds zero overhead to the production binary.

Security boundary. Features that should never be accessible to external users -- internal admin tools, debug endpoints, bypass mechanisms -- are compile-time gated. There is no runtime configuration that can enable them because the code literally does not exist in the distributed binary.

Runtime Flags: What Code Runs

Runtime flags control behavior without redeploying. They are evaluated at session start (or on-demand) by querying a flag evaluation service (GrowthBook, LaunchDarkly, or a simple JSON endpoint):

// At session start:
const flags = await featureFlagService.evaluate({
  userId: session.userId,
  orgId: session.orgId,
  version: BUILD_VERSION,
  platform: process.platform,
});

// During execution:
if (flags.get('use_new_context_assembler')) {
  return newContextAssembler.assemble(messages, budget);
} else {
  return legacyContextAssembler.assemble(messages, budget);
}

Runtime flags serve different purposes:

A/B testing. Ship a new context assembly algorithm to 10% of users and measure whether it improves task completion rate. The flag service assigns users to groups; the agent checks the flag and selects the algorithm.

Gradual rollout. Roll out a new permission mode to 1% of sessions, monitor for errors, increase to 10%, monitor, increase to 50%, monitor, go to 100%. If errors spike at any stage, roll back by flipping the flag -- no redeployment needed.

Kill switches. If a feature causes production incidents, disable it immediately by setting the flag to false. The change propagates to all sessions within the flag cache TTL (typically 30-60 seconds).

User segmentation. Enable a feature for enterprise users but not free-tier users. Enable it for macOS but not Windows. Enable it for version 2.5+ but not older versions. The flag service evaluates targeting rules against the session context.

Why You Need Both

Scenario Compile-time Runtime
"Remove debug tools from public build" Yes --
"Roll out new diff algorithm to 10%" -- Yes
"Strip internal-only MCP servers" Yes --
"Kill switch for broken feature" -- Yes
"A/B test new prompt template" -- Yes
"Exclude source maps from release" Yes --
"Enable opus model for enterprise orgs" -- Yes

Compile-time flags control what code exists. Runtime flags control what code runs. Using only compile-time flags means every behavior change requires a new build and deployment. Using only runtime flags means the binary contains all code paths, including security-sensitive ones that should never ship externally. You need both.

Coded Defaults

Runtime flags have a critical design requirement: they must work when the flag service is unreachable. Network failures, DNS issues, and rate limiting can all prevent the flag evaluation call from succeeding. Every flag must have a coded default -- a value baked into the binary that is used when the flag service cannot be reached:

const FLAG_DEFAULTS: Record<string, boolean | string | number> = {
  'use_new_context_assembler': false,  // Default: use legacy
  'max_tool_retries': 3,               // Default: retry 3 times
  'enable_opus_model': true,           // Default: opus available
  'compaction_threshold': 0.80,        // Default: compact at 80%
};

function getFlag<T>(key: string): T {
  try {
    return flagService.getValue(key) as T;
  } catch {
    return FLAG_DEFAULTS[key] as T;
  }
}

The coded default is always the safe, well-tested behavior. New features default to false (disabled). Limits default to conservative values. The flag service overrides these defaults for users in the rollout group. This means a flag service outage degrades gracefully -- users get the proven behavior, not the experimental behavior.

Flag Evaluation Performance

Flag evaluation must be fast. If every getFlag() call makes a network request, tool execution latency will be dominated by flag checks. The standard architecture is:

  1. Fetch flags at session start. One network call, cached for the session duration.
  2. Cache with TTL. For long sessions, refresh the cache every 5 minutes.
  3. Evaluate locally. The cached flag values are a local lookup (microseconds, not milliseconds).
  4. Target in <50ms. Total flag evaluation (cache check + local computation) should be under 50ms even with complex targeting rules.

34.2 Backwards Compatibility

An AI agent has multiple compatibility surfaces: configuration files, tool schemas, MCP protocol messages, session transcripts, and the CLI interface itself. Breaking any of these disrupts users or dependent systems.

Configuration Format Versioning

Settings files evolve over time. New fields are added, old fields are renamed, and occasionally the structure changes. The versioning strategy determines how gracefully this happens:

{
  "version": 3,
  "permissions": {
    "mode": "auto",
    "rules": [...]
  }
}

Additive changes (new fields with defaults) are backwards compatible. A version-2 config works with a version-3 reader because the new fields use defaults:

function migrateSettingsV2ToV3(config: SettingsV2): SettingsV3 {
  return {
    ...config,
    version: 3,
    telemetry: config.telemetry ?? { level: 'standard' },  // New field
    costLimits: config.costLimits ?? { sessionMax: null },  // New field
  };
}

Destructive changes (renamed fields, restructured sections) require migration. The settings loader detects the version and applies the migration chain:

flowchart LR
    V1["Version 1"] --> M12["Migrate 1->2"]
    M12 --> V2["Version 2"]
    V2 --> M23["Migrate 2->3"]
    M23 --> V3["Version 3"]
    V3 --> M34["Migrate 3->4"]
    M34 --> V4["Version 4<br/>(current)"]

Each migration is a pure function: V(n) -> V(n+1). The loader applies all migrations in sequence to reach the current version. Old config files are automatically upgraded on first load. The original file is backed up before migration.

Tool Schema Evolution

Tool schemas define the input and output contract between the model and the tool implementation. The model generates tool inputs based on the schema it was given in the system prompt. If the schema changes, the model might generate inputs that do not match.

The safe evolution pattern is additive only:

  • Add new optional fields (with defaults)
  • Never remove existing fields
  • Never rename fields
  • Never change field types
  • Deprecate fields by adding a new field and documenting that the old one will be removed in version N+2
// Version 1: Original schema
interface ReadToolInput {
  file_path: string;
}

// Version 2: Additive — new optional fields
interface ReadToolInput {
  file_path: string;
  offset?: number;     // NEW: start reading at this line
  limit?: number;      // NEW: read at most this many lines
  encoding?: string;   // NEW: file encoding (default: utf-8)
}

The tool implementation handles missing optional fields with sensible defaults. A model trained on the v1 schema still works with the v2 implementation because the v2 fields are optional.

MCP Protocol Versioning

The MCP protocol carries a version string in the initialize handshake (e.g., "2024-11-05"). Protocol evolution follows the same additive pattern:

  • New methods can be added to the protocol
  • New fields can be added to existing method parameters
  • Existing methods and fields cannot be removed or changed
  • Servers declare capabilities to indicate which optional features they support

When the client encounters a server running an older protocol version, it constrains itself to the capabilities of that version. When a server encounters a client with an older version, it does the same. This bidirectional compatibility negotiation means that clients and servers can be upgraded independently without coordination.

When to Break Compatibility

Sometimes you must break backwards compatibility. The question is when and how:

When: Breaking changes are justified when maintaining compatibility creates a maintenance burden that slows all future development, when the compatibility surface has security implications that cannot be patched incrementally, or when the number of affected users is small enough to handle through migration support.

How: Follow the deprecation timeline:

Version N:   Add new behavior alongside old behavior
             Log deprecation warnings for old behavior
Version N+1: Make new behavior the default
             Old behavior still available via flag
Version N+2: Remove old behavior entirely
             Migration guide published

This gives users two version cycles (typically 2-4 months) to migrate. The deprecation warning is critical -- it makes the upcoming change visible before it becomes disruptive.

34.3 The Build System as Architecture

The build system is not a DevOps concern separate from architecture. For an AI agent, the build system determines what ships, how fast it ships, and how many product variants exist. It is an architectural primitive.

Bundling Architecture

The agent's source code (512K lines across thousands of files) is bundled into a single-file output:

flowchart LR
    SRC["Source Code<br/>512K lines<br/>~2000 files"] --> BUNDLER["Bundler<br/>(Bun/esbuild)"]

    FLAGS["Compile-Time Flags<br/>80+ boolean flags"] --> BUNDLER
    CONSTS["Build Constants<br/>version, date, commit"] --> BUNDLER

    BUNDLER --> TREE["Tree Shaker"]
    TREE --> MIN["Minifier"]
    MIN --> BIN["Single File<br/>~16,800 lines"]

    style BUNDLER fill:#74c0fc,stroke:#1971c2
    style TREE fill:#ffd43b,stroke:#e67700
    style BIN fill:#51cf66,stroke:#2b8a3e

The 32:1 compression ratio (512K to 16.8K lines) comes from three sources:

  1. Tree shaking eliminates unreachable code. Functions that are never called, modules that are never imported, and compile-time-flagged code paths that evaluate to false are all removed.

  2. Dead code from flag evaluation. When BUILD_FLAGS.ENABLE_DEBUG_TOOLS is false, the entire debug tools module and everything it imports is eliminated.

  3. Minification shortens variable names, removes whitespace, and collapses statements. This does not change the logical content but significantly reduces file size.

SKU Generation

The same source code produces multiple products (SKUs) by varying the compile-time flags:

SKU Target Key flags
claude-code Public release Debug=off, Experimental=off, Telemetry=standard
claude-code-internal Anthropic engineers Debug=on, Experimental=on, Telemetry=verbose
claude-code-enterprise Enterprise customers Debug=off, MDM=on, Audit=verbose
claude-code-ci CI/CD pipelines Headless=on, UI=off, Telemetry=json

Each SKU is a separate build with a separate flag configuration. The build system generates all SKUs from a single build.ts script that iterates over the flag combinations:

const SKU_CONFIGS = {
  'claude-code': {
    ENABLE_DEBUG_TOOLS: false,
    ENABLE_EXPERIMENTAL: false,
    ENABLE_MDM: false,
    ENABLE_HEADLESS_ONLY: false,
  },
  'claude-code-internal': {
    ENABLE_DEBUG_TOOLS: true,
    ENABLE_EXPERIMENTAL: true,
    ENABLE_MDM: false,
    ENABLE_HEADLESS_ONLY: false,
  },
  // ...
};

for (const [sku, flags] of Object.entries(SKU_CONFIGS)) {
  await build({
    entrypoint: 'src/main.ts',
    outfile: `dist/${sku}.js`,
    define: Object.fromEntries(
      Object.entries(flags).map(([k, v]) => [`BUILD_FLAGS.${k}`, String(v)])
    ),
    minify: true,
    treeShaking: true,
  });
}

Build-Time Constants

The build process injects constants that are available at runtime but determined at build time:

declare const BUILD_CONSTANTS: {
  VERSION: string;           // "2.5.3"
  BUILD_DATE: string;        // "2026-04-12T00:00:00Z"
  COMMIT_SHA: string;        // "a1b2c3d"
  BUILD_NUMBER: number;      // 4567
  FEATURE_SET: string;       // "public" | "internal" | "enterprise"
  MIN_NODE_VERSION: string;  // "20.0.0"
};

These constants appear in startup logs, error reports, the /doctor command output, and API request headers (for debugging on the server side). They cost zero runtime overhead because they are inlined as string literals by the bundler.

34.4 Migration Patterns

Evolving a production system used by thousands of engineers requires migration patterns that minimize disruption and allow rollback.

Gradual Rollout

The safest migration pattern is gradual rollout controlled by runtime flags:

graph LR
    subgraph "Week 1"
        W1["1% of sessions<br/>New behavior"]
    end
    subgraph "Week 2"
        W2["10% of sessions"]
    end
    subgraph "Week 3"
        W3["50% of sessions"]
    end
    subgraph "Week 4"
        W4["100% of sessions"]
    end

    W1 -->|"Monitor metrics"| W2
    W2 -->|"Monitor metrics"| W3
    W3 -->|"Monitor metrics"| W4

    W1 -.->|"Regression detected"| RB1["Rollback to 0%"]
    W2 -.->|"Regression detected"| RB2["Rollback to 1%"]
    W3 -.->|"Regression detected"| RB3["Rollback to 10%"]

At each stage, monitor: - Error rate (should not increase) - Task completion rate (should not decrease) - Latency P99 (should not increase by >20%) - Cost per session (should not increase by >10%) - User complaints (qualitative signal)

If any metric regresses, roll back to the previous stage by changing the flag percentage. No deployment needed. The rollback is instant (within the flag cache TTL).

Canary Deployment

For infrastructure changes that cannot be feature-flagged (new bundler, new runtime, new dependency versions), canary deployment runs the new version alongside the old:

graph TB
    LB["Load Balancer / Download Server"]
    LB -->|"95% of downloads"| STABLE["Stable: v2.4.8"]
    LB -->|"5% of downloads"| CANARY["Canary: v2.5.0"]

    STABLE --> M1["Metrics: stable baseline"]
    CANARY --> M2["Metrics: canary comparison"]

    M1 --> COMP["Comparison Dashboard"]
    M2 --> COMP

    COMP -->|"Canary healthy"| PROMOTE["Promote canary to stable"]
    COMP -->|"Canary unhealthy"| KILL["Kill canary, investigate"]

Dark Launches

Ship code that is not yet activated. The feature is complete, tested, and deployed, but hidden behind a compile-time flag set to false or a runtime flag at 0%. This lets you:

  1. Merge the code into the main branch (reducing merge conflict risk)
  2. Deploy it to production (verifying it does not break anything by its mere presence)
  3. Activate it later with a flag flip (when you are ready for users to see it)

Dark launches are particularly useful for large features that take weeks to build. Rather than developing on a long-lived feature branch that diverges from main, you merge incrementally behind a flag.

34.5 Technical Debt Management

Every growing codebase accumulates technical debt. The question is not whether you have debt but how you manage it.

The "DO NOT ADD MORE STATE HERE" Pattern

When a module accumulates too much state or responsibility, but a full refactor is not yet justified, add an explicit warning:

// DO NOT ADD MORE STATE HERE.
// This module already tracks 14 pieces of session state.
// The next feature that needs state should go in a new
// SessionExtension module. See ADR-0042 for the plan.
interface SessionState {
  // ... 14 fields ...
}

This pattern serves three purposes:

  1. Prevents further accumulation. New contributors see the warning and create a separate module instead of adding field #15.
  2. Documents the intent. The ADR reference explains why the module is oversized and what the plan is.
  3. Creates a trigger for refactoring. When someone inevitably ignores the warning (or when the warning applies to multiple modules), it signals that the refactoring can no longer be deferred.

When to Pay Down Debt vs. When to Ship

The decision framework:

Pay down debt when... Ship with debt when...
The debt blocks the next three features The debt affects only one area
The debt causes production incidents The debt is cosmetic (naming, structure)
The debt makes onboarding hard The market window is closing
The refactor is well-understood (<2 days) The refactor scope is uncertain (>1 week)
Tests exist to verify the refactor No tests, refactor is risky

Architecture Decision Records

Every significant architectural decision should be documented in an ADR (Architecture Decision Record). The format:

# ADR-0042: Extract Session Extensions from Monolithic State

## Status: Proposed

## Context
SessionState has grown to 14 fields tracking unrelated concerns:
authentication, tool state, conversation history, cost tracking,
and MCP server status. Adding new features requires modifying this
module, creating merge conflicts and increasing coupling.

## Decision
Create a SessionExtension interface that individual subsystems
implement. Each extension owns its own state and lifecycle.
SessionState becomes a container of extensions, not a bag of fields.

## Consequences
- New features add extensions without touching core state
- Extensions can be tested independently
- Migration: existing fields move to extensions over 3 sprints
- Risk: extension loading order may introduce subtle bugs

ADRs serve as the institutional memory of why decisions were made. Without them, future engineers (including your future self) will look at a design choice and wonder "why did they do it this way?" and potentially undo a deliberate decision.

34.6 The Architecture Review Process

As a codebase grows, individual contributors make local decisions that may conflict with the global architecture. The review process maintains coherence.

ADRs for Significant Decisions

Any change that affects the system's architecture -- new subsystems, new external dependencies, new protocols, changes to the data model -- requires an ADR before implementation. The ADR is reviewed by the architecture owner (or a rotating architecture review committee) before the code is written.

The threshold for "requires an ADR" is pragmatic: if the change affects more than three modules, if it introduces a new dependency, or if it changes a public API surface, it needs an ADR. Single-module refactors, bug fixes, and additive features do not.

Design Documents for New Subsystems

Larger changes -- a new tool system, a new protocol implementation, a new deployment model -- require a design document before an ADR. The design document explores alternatives, analyzes trade-offs, and proposes an approach. It is reviewed by the team, revised based on feedback, and then summarized into an ADR that captures the final decision.

Code Review as Architecture Review

Every pull request is an opportunity for architectural review. Reviewers should check not just correctness and style but also:

  • Does this follow existing patterns? If the codebase uses the registry pattern for tools, a new tool should use the same pattern.
  • Does this introduce a new dependency? Every dependency is a liability. Is it actively maintained? Does it have known CVEs? Is there a lighter alternative?
  • Does this increase coupling? A module that imports from five other modules is a coupling risk. Can the dependency be inverted?
  • Does this create a new precedent? If this is the first time the codebase does X, it should be done well because future code will copy it.

34.7 The Evolution Timeline

Architectural evolution follows a predictable pattern. Understanding the stages helps you plan for them:

timeline
    title AI Agent Architecture Evolution
    section Stage 1: Prototype (0-6 months)
        Monolithic architecture : Single-file agent, few tools
        : Global state, no permissions
        : No tests, no observability
    section Stage 2: Product (6-18 months)
        Modular architecture : Tool registry, permission system
        : Configuration cascade, MCP support
        : Unit tests, basic logging
    section Stage 3: Platform (18-36 months)
        Extensible architecture : Plugin system, enterprise settings
        : Multi-provider API, audit logging
        : Eval framework, full observability
    section Stage 4: Ecosystem (36+ months)
        Ecosystem architecture : Third-party tools, marketplace
        : Cross-agent coordination, federation
        : Community contributions, backward compatibility guarantees

Each stage introduces new architectural requirements:

Prototype to Product. The big change is modularity. Global state becomes encapsulated. The monolith splits into subsystems with defined interfaces. Tests appear. The build system becomes meaningful.

Product to Platform. The big change is extensibility. The system must accommodate behaviors the original architects did not anticipate. MCP support, plugin systems, enterprise policies -- all require extension points that are stable, documented, and backwards-compatible.

Platform to Ecosystem. The big change is governance. When third parties build on your architecture, backwards compatibility becomes a hard constraint. Breaking changes have real costs (broken integrations, frustrated developers, community trust). The architecture review process becomes critical.

34.8 Key Takeaways

  1. Two flag systems, not one. Compile-time flags control what code exists in the binary (security boundary, dead code elimination, SKU generation). Runtime flags control what code runs in a session (A/B testing, gradual rollout, kill switches). You need both.

  2. Coded defaults are mandatory. Every runtime flag must have a safe default for when the flag service is unreachable. New features default to off. The flag service enables them; its absence disables them.

  3. Additive-only schema evolution. Add new optional fields with defaults. Never remove, rename, or retype existing fields. This applies to tool schemas, configuration formats, and protocol messages.

  4. Gradual rollout is the safest migration. 1% -> 10% -> 50% -> 100%, monitoring at each stage, with instant rollback via flag change. No deployment required for rollback.

  5. The build system is architecture. SKU generation, tree-shaking, compile-time flag evaluation, and build-time constant injection are all architectural decisions that shape what ships to users.

  6. Document decisions, not just code. ADRs capture why a decision was made, what alternatives were considered, and what consequences are expected. Without them, future engineers will undo deliberate decisions.

  7. The "DO NOT ADD MORE STATE HERE" pattern works. Explicit warnings in code prevent further accumulation of technical debt and create natural trigger points for refactoring.

  8. Plan for the next stage. If you are at the Product stage, design for Platform extensibility. If you are at Platform, design for Ecosystem governance. The cost of retrofitting is always higher than the cost of planning.
