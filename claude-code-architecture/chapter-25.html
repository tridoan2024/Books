Chapter 25: Agent Communication & Orchestration

A subagent that cannot communicate its results is useless. A collection of subagents that cannot be coordinated is chaos. The architecture of multi-agent systems is ultimately an architecture of communication -- how tasks are described, how results flow back, how errors propagate, and how the orchestrating parent synthesizes multiple streams of work into a coherent outcome.

In Chapter 24, we defined the subagent types, their tool access levels, and the isolation guarantees they provide. Now we turn to the mechanics of making them work together. This chapter covers message passing protocols, result aggregation strategies, error handling across agent boundaries, parallel versus sequential execution, orchestration patterns, long-running agent communication, and cost management across the agent tree.

The design challenge is subtle. Unlike microservices that communicate through well-typed RPCs, agents communicate through natural language. The "protocol" is the structure and content of the prompts sent between them. Get the protocol wrong and agents misinterpret tasks, return unusable results, or silently fail. Get it right and you have a system where the parent agent can dispatch a security review, a code quality analysis, and a test generation task in parallel, collect the results, resolve conflicts between them, and present a unified assessment to the user -- all without human intervention.

25.1 The Message Passing Model

Communication between a parent agent and its subagents follows a request-response model with an optional ongoing channel. Understanding the structure of these messages is essential for designing reliable multi-agent workflows.

The Delegation Message

When a parent agent spawns a subagent, it sends a single delegation message. This message contains everything the subagent needs to complete its task:

┌─────────────────────────────────────────────────┐
│ Delegation Message                              │
│                                                 │
│ ┌─────────────────────────────────────────────┐ │
│ │ Task Description                            │ │
│ │ "Review src/auth/ for OWASP Top 10          │ │
│ │  vulnerabilities. Focus on injection,        │ │
│ │  authentication bypass, and secrets          │ │
│ │  exposure."                                  │ │
│ └─────────────────────────────────────────────┘ │
│                                                 │
│ ┌─────────────────────────────────────────────┐ │
│ │ Relevant Context                            │ │
│ │ "The auth module was recently refactored.   │ │
│ │  It now uses JWT with RS256. The key pair   │ │
│ │  is loaded from environment variables."      │ │
│ └─────────────────────────────────────────────┘ │
│                                                 │
│ ┌─────────────────────────────────────────────┐ │
│ │ Output Format Expectation                   │ │
│ │ "Return findings as a table with columns:   │ │
│ │  Severity, CWE, Finding, Location, Fix."     │ │
│ └─────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────┘

The delegation message has three components:

  1. Task description. What the subagent should do. This must be self-contained -- the subagent has no access to the parent's conversation history, so the task description must include all necessary context. A common mistake is writing a delegation like "review the code we discussed" -- the subagent has no idea what was discussed.

  2. Relevant context. Information the parent has already gathered that is relevant to the task. This is a curated subset of the parent's knowledge, not a dump of the full conversation. The parent acts as an editor, selecting only the context the subagent needs.

  3. Output format expectation. How the result should be structured. Without this, subagents produce free-form text that is difficult for the parent to parse and aggregate. Specifying format ("return as a table with columns...") produces structured output that integrates cleanly into the parent's workflow.

The Result Message

The subagent returns a single result message when it completes. This message is the subagent's final response -- the last non-tool-use message in its agentic loop.

┌─────────────────────────────────────────────────┐
│ Result Message                                  │
│                                                 │
│ Agent type: security-reviewer                   │
│ Status: completed                               │
│ Turns used: 18 / 25 max                         │
│ Tokens: 4,200 input / 2,100 output              │
│                                                 │
│ Content:                                        │
│ "## Security Review: src/auth/                  │
│                                                 │
│  | Severity | CWE | Finding | Location | Fix |  │
│  |----------|-----|---------|----------|-----|  │
│  | CRITICAL | 287 | JWT key loaded without      │
│  |          |     | rotation mechanism ...       │
│  ...                                            │
│                                                 │
│  3 critical, 2 high, 1 medium findings."        │
└─────────────────────────────────────────────────┘

The parent receives this result as a message in its own conversation. The metadata (agent type, status, turns, tokens) is available for logging and cost tracking but is not injected into the conversation -- only the content reaches the parent's context.

The SendMessage Pattern

For long-running subagents, the delegation model supports ongoing communication through a SendMessage mechanism. This allows the parent to send additional instructions to a running subagent without spawning a new one.

sequenceDiagram
    participant P as Parent Agent
    participant S as Subagent (running)

    P->>S: Initial delegation
    S->>S: Working... (turns 1-5)
    P->>S: SendMessage("Also check the session middleware")
    S->>S: Incorporates new instruction
    S->>S: Working... (turns 6-15)
    S-->>P: Final result (includes session middleware findings)

The SendMessage pattern is useful when:

  • The parent discovers new information during the subagent's execution that is relevant to the task.
  • The user provides additional input that changes the scope of the delegated work.
  • The parent wants to redirect the subagent's focus based on early findings from a parallel agent.

The architectural constraint is that SendMessage is append-only -- you can add context, but you cannot retract it. Once the subagent has read a message, it has influenced its reasoning, and there is no way to "un-read" it. This is a fundamental limitation of the natural-language communication model.

25.2 Result Aggregation Patterns

When a parent agent spawns multiple subagents, it needs a strategy for combining their results into a coherent response. The aggregation strategy depends on the relationship between the agents' tasks.

Pattern 1: Direct Injection

The simplest case. A single subagent returns a result, and the parent injects it directly into its own response.

graph LR
    P["Parent"] -->|delegate| S["Subagent"]
    S -->|result| P
    P -->|response with<br/>subagent's findings| U["User"]

The parent may lightly edit the result -- adding context, reformatting, or highlighting key points -- but the subagent's output is the primary content. This pattern applies when the delegation covers the entire user request. For example, the user asks for a security review, the parent delegates to a security-reviewer, and the result is the review.

Pattern 2: Parallel Collection and Synthesis

Multiple independent agents work in parallel. The parent collects all results and synthesizes them into a unified response.

graph TB
    P["Parent Agent"] -->|"Code quality?"| CR["Code Reviewer"]
    P -->|"Security issues?"| SR["Security Reviewer"]
    P -->|"Test coverage?"| EX["Explore Agent"]

    CR -->|"3 issues found"| P
    SR -->|"2 vulnerabilities"| P
    EX -->|"67% coverage"| P

    P -->|"Unified PR Review:<br/>3 code issues<br/>2 security findings<br/>67% coverage"| U["User"]

This is the most common multi-agent pattern. The parent dispatches 2-4 agents with independent tasks, waits for all to complete, and then synthesizes. The synthesis step is where the parent adds value beyond simple concatenation:

  • Deduplication. A code-reviewer and security-reviewer might both flag the same unvalidated input. The parent merges duplicate findings.
  • Prioritization. The parent applies a unified severity ordering across findings from different agents.
  • Conflict resolution. A code-reviewer might suggest inlining a function for readability, while a security-reviewer flags the same function for needing additional validation. The parent reconciles the conflicting recommendations.
  • Executive summary. The parent produces a concise summary that a human can read in 30 seconds, followed by the detailed findings.

Pattern 3: Sequential Pipeline

Output from one agent feeds as input to the next. Each agent transforms or enriches the data.

graph LR
    P["Parent"] -->|"Investigate"| A1["Explore Agent"]
    A1 -->|"Found 3 related files"| P
    P -->|"Debug using these files"| A2["Debugger"]
    A2 -->|"Root cause: race condition"| P
    P -->|"Fix the race condition"| A3["General-Purpose"]
    A3 -->|"Fixed, tests pass"| P

In a pipeline, the parent acts as a relay, taking each agent's output and formulating the next agent's input. This is more expensive than parallel execution (wall-clock time is the sum of all agents), but it is necessary when each stage depends on the previous stage's results.

The parent's role between pipeline stages is critical. It does not simply forward the output verbatim. It:

  1. Validates the result. Did the explore agent actually find relevant files, or did it miss the mark?
  2. Extracts the essential information. The debugger does not need the explore agent's full reasoning -- just the file list and key observations.
  3. Reformulates the task. "Debug using these files" is a more useful prompt than "here's what the explore agent said."

Pattern 4: Competitive Evaluation

Multiple agents solve the same problem independently. The parent compares their solutions and selects the best one.

graph TB
    P["Parent Agent"] -->|"Implement pagination"| A1["Agent A<br/>(cursor-based)"]
    P -->|"Implement pagination"| A2["Agent B<br/>(offset-based)"]

    A1 -->|"Cursor implementation"| P
    A2 -->|"Offset implementation"| P

    P -->|"Compare & select<br/>best approach"| U["User"]

This pattern is expensive -- you pay for two full implementations -- but valuable when the design space has multiple viable approaches. The parent can compare the implementations on correctness, performance, complexity, and alignment with existing patterns to select the best option.

In practice, competitive evaluation is rare in CLI agents because the cost is high. It is more commonly used in evaluation pipelines (testing which approach the model handles better) than in production workflows.

Aggregation Comparison Table

Pattern Agents Wall-Clock Time Token Cost Best For
Direct Injection 1 Agent time Low Single-domain tasks
Parallel Collection 2-4 Max(agent times) Medium Multi-aspect analysis
Sequential Pipeline 2-5 Sum(agent times) Medium-High Dependent task chains
Competitive Evaluation 2-3 Max(agent times) High Design decisions

25.3 Error Propagation Across Agent Boundaries

Subagents fail. They hit token limits, encounter API errors, produce malformed output, or simply run out of turns before completing the task. The parent agent must handle these failures gracefully.

Failure Modes

graph TB
    subgraph Failures["Subagent Failure Modes"]
        F1["Timeout<br/>Exceeded maxTurns<br/>without completing"]
        F2["API Error<br/>Rate limit, server error,<br/>connection failure"]
        F3["Context Overflow<br/>Ran out of context<br/>window space"]
        F4["Tool Error<br/>Bash command failed,<br/>file not found"]
        F5["Empty Result<br/>Subagent completed<br/>without meaningful output"]
        F6["Malformed Result<br/>Output doesn't match<br/>expected format"]
    end

    style F1 fill:#fff3e0,stroke:#FF9800
    style F2 fill:#ffebee,stroke:#E91E63
    style F3 fill:#fff3e0,stroke:#FF9800
    style F4 fill:#e8f5e9,stroke:#4CAF50
    style F5 fill:#e8f4f8,stroke:#2196F3
    style F6 fill:#e8f4f8,stroke:#2196F3

Timeout (Turn Limit Exceeded)

The subagent used all its allocated turns without producing a final response. This usually means the task was too complex for the agent type or the turn limit was too low.

Recovery strategy: The dispatch layer captures the subagent's last partial output and returns it to the parent with a status: partial flag. The parent can either present the partial results to the user with a warning ("Security review was incomplete -- the agent examined 3 of 5 modules"), or retry with a higher turn limit or a more capable model.

API Error

A transient failure in the LLM API -- rate limiting, server errors, or network timeouts. These failures are at the infrastructure level, not the task level.

Recovery strategy: The subagent's agentic loop handles retries internally (exponential backoff, as discussed in Chapter 10). If retries are exhausted, the error propagates to the parent. The parent should NOT retry the entire delegation -- the subagent already tried multiple times. Instead, the parent reports the infrastructure failure and suggests the user try again later.

Context Overflow

The subagent's context window filled up before it could complete the task. This happens when the subagent reads too many files or produces too much intermediate reasoning.

Recovery strategy: This is structurally similar to a timeout. The subagent's last output before overflow is captured and returned as a partial result. The parent can split the task into smaller sub-tasks, each with less scope: "Review auth/login.ts" instead of "Review all of auth/".

Tool Error

A specific tool call within the subagent failed -- a file was not found, a bash command returned a non-zero exit code, a web fetch timed out.

Recovery strategy: The subagent should handle individual tool errors within its own loop. A well-designed subagent treats a missing file as information ("the file doesn't exist, so the module may have been moved") rather than a fatal error. Only if tool errors prevent the subagent from making any progress should the error propagate to the parent.

Empty or Malformed Result

The subagent completed successfully but produced output that the parent cannot use -- an empty response, a response that does not match the expected format, or a response that addresses the wrong question.

Recovery strategy: The parent validates the result against the expected format. If validation fails, the parent can retry the delegation with a more explicit format instruction, or fall back to using the malformed result as-is with a warning.

The Error Propagation Protocol

sequenceDiagram
    participant P as Parent Agent
    participant D as Dispatch Layer
    participant S as Subagent

    P->>D: Delegate task
    D->>S: Create and run subagent

    alt Success
        S-->>D: Result (status: completed)
        D-->>P: Result message
        P->>P: Validate and use result
    else Timeout
        S-->>D: Partial result (status: partial)
        D-->>P: Partial result + warning
        P->>P: Decide: use partial or retry
    else API Error
        S-->>D: Error (status: error, reason: api_failure)
        D-->>P: Error message
        P->>P: Report infrastructure failure
    else Context Overflow
        S-->>D: Partial result (status: overflow)
        D-->>P: Partial result + warning
        P->>P: Consider splitting task
    end

The key design principle: errors should never silently disappear. If a subagent fails, the parent must know about it and make an explicit decision about how to proceed. Swallowing errors leads to incomplete results that the user trusts because the parent presented them without caveats.

Error Handling in Parallel Dispatch

When multiple agents run in parallel, error handling becomes more nuanced. Should the parent wait for all agents to complete even if one fails? Should it cancel the remaining agents if a critical one fails?

The recommended strategy is collect all, report all:

  1. Dispatch all agents in parallel.
  2. Wait for all to complete (success, failure, or timeout).
  3. Collect all results and errors.
  4. Synthesize a response that includes successful results and notes any failures.

This is simpler and more robust than selective cancellation. Cancellation introduces race conditions (the cancellation message might arrive after the agent finishes), and partial results from a "failed" agent might still be valuable.

PR Review Results:
- Code Quality: 3 issues found (code-reviewer completed)
- Security: Review incomplete -- agent timed out after reviewing
  2 of 4 modules. Partial findings: 1 critical vulnerability in
  auth/jwt.ts. Consider re-running with focus on remaining modules.
- Test Coverage: 72% (explore agent completed)

25.4 Parallel vs. Sequential Execution

The choice between parallel and sequential execution is one of the most impactful orchestration decisions. It directly affects wall-clock time, token cost, and result quality.

When to Parallelize

Parallel execution is appropriate when tasks are independent -- the output of one does not depend on the input of another.

Parallel Candidates Why Independent
Security review + Code review Different analysis dimensions of same code
Multiple file explorations Each file read is independent
Research + Codebase analysis External sources vs. local code
Test execution + Lint check Different validation tools

The benefit of parallelism is reduced wall-clock time. If a code review takes 30 seconds and a security review takes 45 seconds, sequential execution takes 75 seconds while parallel execution takes 45 seconds.

When to Sequence

Sequential execution is necessary when there are data dependencies between tasks.

Sequential Chain Dependency
Explore → Debug Debugger needs explore's file findings
Investigate → Fix → Test Fix depends on investigation, test depends on fix
Plan → Implement Implementation follows the plan
Review → Revise Revision addresses review findings

Attempting to parallelize dependent tasks is a common mistake. If you dispatch a debugger and an explore agent in parallel, the debugger starts with no codebase context and wastes its early turns re-discovering information the explore agent is simultaneously finding.

Hybrid: Partial Parallelism with Sync Points

Real workflows often mix independent and dependent stages. The hybrid pattern uses sync points to coordinate:

graph TB
    START["Task: Full PR Analysis"] --> PAR1

    subgraph PAR1["Stage 1: Parallel Analysis"]
        CR["Code Review"]
        SR["Security Review"]
        EX["Explore: Map Changes"]
    end

    PAR1 --> SYNC1["Sync Point 1:<br/>Collect all findings"]

    SYNC1 --> PAR2

    subgraph PAR2["Stage 2: Parallel Follow-up"]
        FIX["Fix Critical Issues"]
        DOC["Update Documentation"]
    end

    PAR2 --> SYNC2["Sync Point 2:<br/>Verify fixes"]

    SYNC2 --> FINAL["Final: Synthesize Report"]

    style PAR1 fill:#e8f4f8,stroke:#2196F3
    style PAR2 fill:#e8f5e9,stroke:#4CAF50
    style SYNC1 fill:#fff3e0,stroke:#FF9800
    style SYNC2 fill:#fff3e0,stroke:#FF9800

In this workflow: - Stage 1 runs three agents in parallel (all independent). - Sync Point 1 waits for all three to complete and merges results. - Stage 2 runs two agents in parallel (fixing issues found in Stage 1, updating docs based on Stage 1's change map). - Sync Point 2 waits for both and verifies the fixes pass tests. - The final synthesis produces the unified report.

The sync point is where the parent agent actively works -- it reads all collected results, makes decisions about what to do next, and formulates the next stage's task prompts. This is not passive waiting; it is the orchestration intelligence that turns a collection of independent agents into a coordinated system.

25.5 Context Isolation vs. Context Sharing

As discussed in Chapter 24, subagents operate in isolated context windows by default. But there are scenarios where some form of sharing is valuable. The architecture supports two sharing mechanisms, each with different isolation guarantees.

Full Isolation (Default)

Each subagent gets: - A fresh context window with no conversation history - Its own system prompt (tailored to the agent type) - Its own tool schema (restricted to authorized tools) - No access to the parent's memory or project instructions

This is the safest option. The subagent cannot be influenced by anything in the parent's context except the explicit delegation prompt.

Filesystem Sharing via Worktrees

When a subagent needs to modify files, it can operate in a git worktree -- a separate checkout of the same repository. The worktree provides filesystem isolation (the subagent's changes do not affect the main working directory) while sharing the repository history.

graph TB
    subgraph MainWorkspace["Main Workspace (Parent)"]
        MW["Working directory<br/>/project/"]
        MG["Git branch: main"]
    end

    subgraph Worktree1["Worktree (Agent A)"]
        W1["Working directory<br/>/project/.claude/worktrees/agent-a/"]
        G1["Git branch: agent-a/fix-auth"]
    end

    subgraph Worktree2["Worktree (Agent B)"]
        W2["Working directory<br/>/project/.claude/worktrees/agent-b/"]
        G2["Git branch: agent-b/update-docs"]
    end

    MainWorkspace -.->|"Same repo<br/>different branches"| Worktree1
    MainWorkspace -.->|"Same repo<br/>different branches"| Worktree2

    style MainWorkspace fill:#e8f4f8,stroke:#2196F3
    style Worktree1 fill:#e8f5e9,stroke:#4CAF50
    style Worktree2 fill:#fff3e0,stroke:#FF9800

Worktree sharing is the topic of Chapter 26, but the key point for orchestration is: worktrees provide filesystem isolation without full context isolation. The agents share the same git history, so they can read each other's branches, but they cannot modify each other's working directories.

Comparison

Dimension Full Isolation Worktree Sharing
Context window Fresh, independent Fresh, independent
System prompt Agent-type specific Agent-type specific
Filesystem Shared (same working dir) Isolated (separate worktree)
Git state Shared branch Independent branches
Token cost Higher (re-reads files) Same (still re-reads)
Safety Highest High (changes are isolated)
Use case Read-only analysis Parallel write operations

The choice between isolation modes is driven by a single question: does the subagent need to write files? If yes, use a worktree to prevent write conflicts. If no, full isolation is sufficient and simpler.

25.6 Orchestration Patterns

Production multi-agent systems use recurring orchestration patterns. Each pattern addresses a different workflow shape.

Pattern 1: Fan-Out / Fan-In

Dispatch N agents with independent tasks. Wait for all to complete. Aggregate results.

graph TB
    D["Dispatch"] --> A1["Agent 1<br/>Code Review"]
    D --> A2["Agent 2<br/>Security Review"]
    D --> A3["Agent 3<br/>Performance Review"]
    D --> A4["Agent 4<br/>Test Coverage"]

    A1 --> C["Collect"]
    A2 --> C
    A3 --> C
    A4 --> C

    C --> S["Synthesize<br/>Unified Report"]

    style D fill:#e8f4f8,stroke:#2196F3
    style C fill:#fff3e0,stroke:#FF9800
    style S fill:#e8f5e9,stroke:#4CAF50

Implementation considerations:

  • Dispatch order does not matter. All agents start as close to simultaneously as the runtime allows.
  • Collection requires a barrier. The parent cannot proceed to synthesis until all agents have returned (or timed out).
  • Partial results are acceptable. If one agent fails, the others' results are still valuable. The synthesis step notes which analyses completed and which did not.
  • Cost is predictable. N agents running in parallel cost roughly the same as N agents running sequentially (same total tokens), but wall-clock time is reduced to the slowest agent.

When to use: Any multi-aspect analysis -- PR reviews, deployment readiness checks, architecture evaluations.

Pattern 2: Pipeline

Agent A's output becomes Agent B's input, which becomes Agent C's input. Each agent transforms or enriches the data.

graph LR
    A["Stage 1<br/>Explore<br/>(find relevant code)"] -->|"File list +<br/>key observations"| B["Stage 2<br/>Analyze<br/>(identify issues)"]
    B -->|"Issue list +<br/>root causes"| C["Stage 3<br/>Fix<br/>(implement changes)"]
    C -->|"Changes +<br/>test results"| D["Stage 4<br/>Verify<br/>(run full test suite)"]

    style A fill:#e8f4f8,stroke:#2196F3
    style B fill:#e8f5e9,stroke:#4CAF50
    style C fill:#fff3e0,stroke:#FF9800
    style D fill:#fce4ec,stroke:#E91E63

Implementation considerations:

  • Each stage must produce structured output. The parent extracts specific information from Stage 1's result to formulate Stage 2's prompt. Free-form text makes this extraction unreliable.
  • Failure at any stage halts the pipeline. If Stage 2 finds no issues, there is nothing for Stage 3 to fix. The parent should detect empty pipelines and report accordingly.
  • Stage promotion. Not every stage needs its own subagent. If Stage 2's analysis is simple, the parent can do it directly. Only delegate stages that cross the complexity threshold from section 24.1.
  • Cost grows linearly. Each stage adds its own token cost. A 4-stage pipeline with 20 turns per stage is 80 total turns -- expensive but sometimes necessary.

When to use: Bug fix workflows, refactoring with verification, investigation-to-implementation chains.

Pattern 3: Hierarchical Delegation

A lead agent delegates to specialist agents, who may further delegate to sub-specialists. This creates a tree of agents with the lead at the root.

graph TB
    LEAD["Lead Agent<br/>(General-Purpose)"] --> INVEST["Investigation Team"]
    LEAD --> IMPL["Implementation Team"]

    subgraph INVEST["Investigation"]
        EX1["Explore Agent<br/>(frontend)"]
        EX2["Explore Agent<br/>(backend)"]
        SR["Security Reviewer"]
    end

    subgraph IMPL["Implementation"]
        GP1["Fix Agent<br/>(frontend)"]
        GP2["Fix Agent<br/>(backend)"]
        DW["Doc Writer"]
    end

    LEAD --> VERIFY["Verification"]

    subgraph VERIFY["Verification"]
        TST["Test Runner"]
        LINT["Lint Checker"]
    end

    style LEAD fill:#fff3e0,stroke:#FF9800
    style INVEST fill:#e8f4f8,stroke:#2196F3
    style IMPL fill:#e8f5e9,stroke:#4CAF50
    style VERIFY fill:#fce4ec,stroke:#E91E63

Implementation considerations:

  • Depth limits are essential. Without limits, hierarchical delegation can create deep trees that are expensive and hard to trace. A maximum depth of 2-3 levels is recommended.
  • The lead agent is the bottleneck. It must coordinate all sub-teams, track progress, and handle failures. If the lead's context fills up with coordination overhead, the system degrades.
  • Only general-purpose agents should delegate. Specialist agents (explore, security-reviewer, etc.) should focus on their task, not on spawning sub-agents.
  • Cost grows with the tree. A 3-level tree with 3 agents per level creates 13 agents (1 + 3 + 9). This is the most expensive pattern and should only be used for truly large-scale tasks.

When to use: Complex multi-file features, major refactoring, comprehensive audits across large codebases.

Pattern 4: Competitive / Best-of-N

Multiple agents solve the same problem independently. The parent evaluates and selects the best solution.

graph TB
    P["Parent: 'Implement rate limiting'"] --> A["Agent A<br/>Token bucket approach"]
    P --> B["Agent B<br/>Sliding window approach"]
    P --> C["Agent C<br/>Leaky bucket approach"]

    A --> EVAL["Parent evaluates:<br/>- Correctness<br/>- Performance<br/>- Complexity<br/>- Test coverage"]
    B --> EVAL
    C --> EVAL

    EVAL --> SELECT["Select best<br/>implementation"]

    style P fill:#e8f4f8,stroke:#2196F3
    style EVAL fill:#fff3e0,stroke:#FF9800
    style SELECT fill:#e8f5e9,stroke:#4CAF50

Implementation considerations:

  • Prompt variation drives diversity. If all agents receive identical prompts, they tend to produce similar solutions. Vary the prompt slightly -- suggest different approaches, emphasize different trade-offs -- to get genuinely different solutions.
  • Evaluation criteria must be explicit. The parent needs clear criteria for selecting the best solution. Without criteria, the selection becomes arbitrary.
  • Cost is multiplied. This is the most expensive pattern per task since you pay for N complete implementations. Reserve it for high-stakes design decisions.

When to use: Architecture decisions with multiple viable approaches, critical implementations where correctness is paramount, evaluation/benchmarking.

Pattern Comparison

Pattern Parallelism Stages Typical Agents Cost Complexity
Fan-Out/Fan-In Full 1 2-4 N * single Low
Pipeline None 2-5 1 per stage Sum of stages Medium
Hierarchical Per-level 2-3 levels 5-15 total Tree size High
Competitive Full 1 2-3 N * single Medium

25.7 Orchestration State Management

As orchestration complexity grows, the parent agent needs to track the state of all dispatched agents. This is not just bookkeeping -- it drives decisions about retries, timeouts, and result synthesis.

The Agent Tracker

The dispatch layer maintains a tracker for each active agent:

Agent Tracker State:
┌────────────────────────────────────────────┐
│ agent_id: "sr-abc123"                      │
│ type: security-reviewer                    │
│ status: running | completed | failed       │
│ started_at: 2026-04-12T10:30:00Z           │
│ turns_used: 12 / 25 max                    │
│ tokens_in: 3,200                           │
│ tokens_out: 1,800                          │
│ result: null | ResultMessage               │
│ error: null | ErrorInfo                    │
└────────────────────────────────────────────┘

The tracker enables several critical capabilities:

  1. Progress monitoring. The parent can check how far along each agent is ("security review is on turn 12 of 25") and make decisions about whether to wait or proceed with partial results.

  2. Cost accounting. Token usage per agent flows into the session's cost tracking (covered in Chapter 6). The user can see exactly how much each delegation cost.

  3. Retry decisions. If an agent fails, the tracker provides the context needed to decide whether to retry: how many turns were used, what error occurred, whether the task is idempotent.

  4. Audit trail. The tracker creates a record of all delegations in a session, which is valuable for debugging orchestration issues and optimizing future workflows.

Timeout Management

Each agent type has a default turn limit, but the dispatch layer also enforces wall-clock timeouts. An agent that is still running after 5 minutes (configurable) is terminated regardless of its turn count. This prevents a single stuck agent from blocking an entire orchestration workflow.

The timeout hierarchy:

Timeout Scope Default
Per-turn Single LLM API call 120 seconds
Per-agent Entire subagent lifecycle 300 seconds
Per-orchestration Full multi-agent workflow 600 seconds

These timeouts are additive guards, not replacements for turn limits. A 15-turn explore agent with a 120-second per-turn timeout can theoretically run for 30 minutes (15 turns * 120 seconds), but the per-agent timeout of 300 seconds catches runaway agents much earlier.

25.8 The SendMessage Pattern in Detail

The basic delegation model is fire-and-forget: dispatch, wait, collect. But some workflows need ongoing communication between the parent and a running subagent. The SendMessage pattern enables this.

Use Cases

  1. Scope expansion. The user adds requirements while a subagent is working. The parent sends the new requirements to the running agent rather than restarting.

  2. Cross-agent information sharing. Agent A finishes before Agent B and produces information relevant to B's work. The parent sends A's findings to B via SendMessage.

  3. Priority adjustment. The parent determines that the subagent is investigating a low-priority area and redirects it to a higher-priority one.

  4. Incremental feedback. For very long-running agents, the parent sends periodic check-ins: "Are you making progress? What have you found so far?"

Protocol Design

sequenceDiagram
    participant P as Parent
    participant S as Subagent

    P->>S: Delegate("Review auth module")

    Note over S: Working on auth module...

    P->>S: SendMessage("Agent A found that the JWT library<br/>was upgraded yesterday. Check for<br/>breaking API changes.")

    Note over S: Incorporates new information,<br/>checks JWT library changes

    P->>S: SendMessage("User clarified: focus only on<br/>the login and logout flows, skip<br/>registration.")

    Note over S: Narrows scope to login/logout

    S-->>P: Result("3 findings in login flow,<br/>1 finding in logout flow")

Constraints

  • No response to SendMessage. The subagent does not acknowledge receipt. The message is injected into the subagent's conversation, and the subagent incorporates it as context for its subsequent turns. There is no explicit "got it" reply.
  • Messages are ordered. If the parent sends two messages, they arrive in order. The subagent processes them in the order received.
  • No retraction. Once sent, a message cannot be unsent. If the parent sends incorrect information, it must send a correction as a follow-up message.
  • Rate limiting. Excessive SendMessage calls can disrupt the subagent's focus. Best practice is to limit messages to genuinely new information, not status requests.

25.9 Cost Management Across the Agent Tree

Multi-agent workflows amplify token costs. A single session might spawn 10+ agents, each consuming thousands of tokens. Without cost management, a complex orchestration can easily cost $10-50 in a single workflow.

Every subagent reports its token usage back to the parent when it completes. The session cost tracker aggregates these costs across the entire agent tree, providing the user with a breakdown of where their tokens went.

Cost-Aware Orchestration

The dispatch layer can enforce per-session and per-agent cost budgets:

Budget Level Enforcement
Per-agent token limit Subagent terminated when limit reached
Per-session cost limit New delegations blocked when budget exhausted
Per-model cost limit Expensive models restricted after threshold

When a budget is exhausted, the dispatch layer returns a budget-exceeded error to the parent. The parent can then decide: present partial results, switch to cheaper agents, or inform the user.

Cost Optimization Strategies

  1. Start cheap, escalate if needed. Try an explore agent (Haiku) first. If the result is insufficient, retry with a debugger (Opus). This avoids paying Opus prices for tasks that Haiku can handle.

  2. Share investigation results. If an explore agent gathered codebase context, pass that context to subsequent agents in their delegation prompts. This reduces the number of file reads each agent performs.

  3. Limit turn budgets. Most tasks do not need the full turn allowance. A code review that takes more than 10 turns is probably going in circles. Set tight turn limits and expand only when needed.

  4. Avoid recursive delegation. Each delegation level multiplies context establishment costs. A pipeline of 3 direct delegations from the parent is cheaper than a hierarchical tree where each agent delegates further.

  5. Cache subagent system prompts. The prompt caching strategy from Chapter 9 applies to subagents too. If you spawn multiple agents of the same type, their system prompts share a cache prefix, reducing input costs on subsequent spawns.

25.10 Designing Delegation Prompts

The quality of a subagent's output is directly proportional to the quality of the delegation prompt. A vague prompt produces vague results. A structured prompt with clear scope, context, and format expectations produces focused, useful output.

The Delegation Prompt Template

Effective delegation prompts follow a consistent structure:

## Task
[One sentence describing what to do]

## Scope
[Specific files, modules, or areas to focus on]
[Explicit exclusions if any]

## Context
[Relevant background information the subagent needs]
[Key findings from prior investigation]
[User requirements or constraints]

## Output Format
[Exactly how the result should be structured]
[Examples of expected output format]

## Priority
[What matters most: thoroughness, speed, or specific aspects]

Good vs. Bad Delegation Prompts

Bad: "Review the code."

This gives the subagent no scope (which code?), no context (what has changed?), no format expectation (how should findings be reported?), and no priority (what matters most?).

Good:

## Task
Review the authentication changes in PR #42 for security vulnerabilities.

## Scope
Files changed: src/auth/jwt.ts, src/auth/session.ts, src/middleware/auth.ts
Exclude: test files, documentation changes

## Context
The PR migrates from symmetric HMAC-SHA256 to asymmetric RS256 JWT signing.
The key pair is loaded from AWS Secrets Manager via environment variables.
The existing session store is Redis-based with 24-hour TTL.

## Output Format
Table with columns: Severity (CRITICAL/HIGH/MEDIUM/LOW), CWE ID, Finding, 
File:Line, Remediation.
End with a summary count of findings per severity.

## Priority
Focus on: key management, token validation, session fixation, 
timing attacks.

Context Selection Heuristic

The parent agent must decide what context to include in the delegation prompt. Too little context and the subagent wastes turns re-discovering information. Too much context and the delegation prompt consumes a large share of the subagent's limited context window.

The heuristic: include only context that the subagent cannot efficiently discover on its own.

Include Exclude
User's stated requirements Full conversation history
Key findings from prior agents Raw tool outputs
Specific file paths to focus on General project structure
Technical constraints (language, framework) Coding style preferences
Why the task matters (priority) History of how the task was identified

25.11 Debugging Multi-Agent Workflows

When a multi-agent orchestration produces wrong results, debugging is challenging. The parent's conversation shows delegation prompts and results, but the subagents' intermediate reasoning is not visible. Several architectural provisions make debugging tractable.

Agent Trace Logging

Every subagent's full conversation -- including all tool calls, intermediate reasoning, and the final result -- is logged to the session store. This trace is not injected into the parent's context (that would defeat the purpose of isolation), but it is available for post-hoc analysis.

Session Trace:
  Parent turn 5: Delegated to security-reviewer (agent_id: sr-abc123)
    ├── Turn 1: Read src/auth/jwt.ts (1,200 lines)
    ├── Turn 2: Grep for "verify" in auth/ (15 matches)
    ├── Turn 3: Read src/auth/session.ts (400 lines)
    ├── Turn 4-8: Analysis and reasoning
    ├── Turn 9: Result: 3 findings
    └── Metadata: 18 turns, 8,400 input tokens, 3,200 output tokens
  Parent turn 6: Received security review results

Common Debugging Scenarios

Symptom Likely Cause Diagnostic
Subagent returned empty result Task prompt too vague Check delegation prompt in parent trace
Subagent timed out Task too broad for turn limit Check turn count and last activity
Results contradicted between agents Agents analyzed different code versions Check timestamps and file versions
Parent misinterpreted result Format mismatch Check output format expectation vs. actual output
Unexpected tool calls in subagent Overly permissive tool schema Check agent type's tool allowlist

25.12 Key Takeaways

  1. Delegation prompts are the protocol. Unlike RPC interfaces with schemas, agent-to-agent communication is natural language. The quality of the delegation prompt determines the quality of the result. Invest in structured prompts with task, scope, context, format, and priority.

  2. Three result aggregation patterns cover most cases. Direct injection for single agents, parallel collection for multi-aspect analysis, and sequential pipelines for dependent tasks. Competitive evaluation is a special-purpose fourth option.

  3. Errors must propagate explicitly. Silent failure in subagents leads to incomplete results that users trust incorrectly. The parent must know about every failure and make explicit decisions about recovery.

  4. Parallel where possible, sequential where necessary. Identify data dependencies and parallelize everything that does not have them. Use sync points for hybrid workflows.

  5. Isolation is the default; sharing is opt-in. Full context isolation prevents pollution, enables tailored prompts, and contains prompt injection. Worktree sharing adds filesystem isolation for write operations.

  6. Fan-out/fan-in is the workhorse pattern. Most multi-agent workflows are "analyze from N perspectives, then synthesize." Start here before reaching for more complex patterns.

  7. Cost grows with the agent tree. Track per-agent costs, enforce budgets, and start with cheap agents before escalating to expensive ones. A mixed-model strategy (Haiku for explore, Sonnet for review, Opus for security) can reduce costs by 5-10x compared to using Opus for everything.

  8. SendMessage extends but does not replace delegation. Use it for genuinely new information during long-running tasks, not for status checks or micromanagement.

  9. Log everything for debugging. Subagent traces are essential for diagnosing orchestration failures. Store the full conversation for every agent, even if it is not surfaced to the parent.

  10. Orchestration complexity should be proportional to task complexity. A simple code review does not need a hierarchical delegation tree. Fan-out/fan-in for multi-aspect reviews, pipelines for dependent tasks, and direct delegation for everything else.
