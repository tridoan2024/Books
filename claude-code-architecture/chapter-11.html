Chapter 11: Streaming Pipeline

In Chapter 10, we designed the API client -- the provider abstraction, retry engine, and circuit breakers that get a request to the model and a response back. But "a response" understates what actually arrives: not a single JSON blob, but a continuous stream of Server-Sent Events that must be parsed, classified, accumulated, rendered, and error-handled in real time. The streaming pipeline is the bridge between the raw HTTP byte stream and the structured messages that the agent loop consumes.

Getting streaming right is harder than it looks. The model does not produce clean, well-bounded output. It emits text tokens interleaved with tool-use requests, thinking blocks that may or may not be visible, and usage metadata that arrives in multiple events with merge semantics. The stream can stall, disconnect mid-sentence, or deliver events faster than the terminal can render them. Each of these failure modes requires a different recovery strategy.

This chapter examines the streaming pipeline as a state machine: the event model it processes, the states it transitions through, the tool-use detection that turns passive text streaming into active agent behavior, and the backpressure and recovery mechanisms that keep it running through real-world network conditions.

Why Streaming Changes Everything

The non-streaming API call is conceptually simple: send a request, wait for a response, process the result. The streaming API call inverts the control flow. Instead of the client pulling a complete response, the server pushes a continuous stream of partial results. The client must process these incrementally while the server is still generating.

This inversion creates four architectural concerns that do not exist in non-streaming systems:

  1. Incremental state accumulation. The response arrives in pieces. The client must maintain partial state -- the current content block, the accumulated text, the pending tool-use input -- and assemble the final message from these fragments.

  2. Concurrent rendering. The UI must render partial results while the stream is still active. This creates a producer-consumer relationship between the stream processor and the renderer.

  3. Mid-stream decision points. When the model emits a tool-use block, the agent must decide whether to begin executing the tool immediately (before the rest of the response arrives) or wait for the complete response. This is an architectural choice with latency implications.

  4. Partial failure recovery. The stream can disconnect after delivering 80% of a response. The client must decide: retry from scratch (losing the partial response), or recover what was received and continue from there.

The SSE Event Model

Event Descriptions

message_start -- Emitted once at the beginning of the stream. Contains the message ID, model identifier, and initial usage statistics (input token count). This event marks the time-to-first-token (TTFT) -- the primary latency metric for streaming responses.

content_block_start -- Emitted when the model begins a new content block. The block type determines how subsequent deltas should be accumulated: - text -- Natural language output to render - tool_use -- A tool call with id and name; input JSON arrives via deltas - thinking -- Extended thinking content (reasoning scratchpad) - server_tool_use -- Server-side tool use (web search, code execution)

content_block_delta -- The most frequent event, emitted for every token or small group of tokens. Delta subtypes match block types: - text_delta -- A string fragment of text output - input_json_delta -- A string fragment of JSON for tool-use input - thinking_delta -- A string fragment of thinking content

content_block_stop -- The signal that a content block is complete. For tool-use blocks, this is when the accumulated JSON string should be parsed into structured input. For text blocks, this signals that the text is final.

message_delta -- Contains the stop_reason (why the model stopped generating) and final usage statistics. Stop reasons include: - end_turn -- Model finished naturally - tool_use -- Model wants to use a tool and is yielding control - max_tokens -- Output token limit reached - stop_sequence -- A configured stop sequence was hit

message_stop -- Stream is complete. No more events will arrive.

The Interleaving Pattern

A single model response can contain multiple content blocks of different types, interleaved:

message_start
  content_block_start (thinking)
    thinking_delta ...
  content_block_stop
  content_block_start (text)
    text_delta "Let me "
    text_delta "check "
    text_delta "that file."
  content_block_stop
  content_block_start (tool_use: Read)
    input_json_delta '{"file_'
    input_json_delta 'path":"'
    input_json_delta 'src/main.ts"}'
  content_block_stop
message_delta (stop_reason: tool_use)
message_stop

The pipeline must handle this interleaving correctly: track which block is currently active, accumulate deltas for that block type, finalize on block_stop, and be ready for the next block of a potentially different type.

The Streaming State Machine

The core of the streaming pipeline is a state machine that tracks the current processing state and validates transitions. Illegal transitions indicate either a server bug or a stream corruption.

State Definitions

State Active Block What's Happening
Idle None Stream created, waiting for first event
MessageActive None Between content blocks or before the first block
InTextBlock text Accumulating text deltas, forwarding to renderer
InToolUseBlock tool_use Accumulating JSON deltas into a string buffer
InThinkingBlock thinking Accumulating thinking deltas
MessageComplete None Received message_delta with stop_reason
Done None message_stop received, stream is finished
Error Varies Stream interrupted, entering recovery
Recovery None Falling back to non-streaming or retrying

Transition Validation

The state machine should reject invalid transitions. For example, receiving a text_delta while in InToolUseBlock is a protocol violation. These violations are rare in practice but critical to detect:

function validateTransition(
  currentState: StreamState, 
  event: StreamEvent,
): StreamState {
  const allowed = TRANSITION_TABLE[currentState]
  const nextState = allowed[event.type]

  if (!nextState) {
    // Log the violation for debugging
    logProtocolViolation(currentState, event)
    // Graceful degradation: stay in current state
    return currentState
  }

  return nextState
}

The graceful degradation choice (stay in current state rather than crash) reflects a production reality: the server may introduce new event types in future API versions. A strict state machine that crashes on unknown events would break existing clients. A lenient one that ignores unknown events maintains backward compatibility.

Tool-Use Event Parsing

The most architecturally significant aspect of the streaming pipeline is tool-use detection. When the model emits a content_block_start with type: tool_use, the streaming pipeline transitions from passive text rendering to active agent orchestration.

The Tool-Use Accumulation Pattern

Tool-use input arrives as a sequence of input_json_delta events, each containing a string fragment:

content_block_start: { type: "tool_use", id: "tu_01", name: "Read" }
input_json_delta: '{"file_'
input_json_delta: 'path": '
input_json_delta: '"/src/'
input_json_delta: 'main.ts'
input_json_delta: '"}'
content_block_stop

The pipeline accumulates these fragments into a string buffer. Do not attempt to parse the JSON until content_block_stop. As discussed in Chapter 10, incremental JSON parsing on every delta is O(n^2). Accumulate the string, parse once.

class ToolUseAccumulator {
  private jsonBuffer = ''
  private toolName = ''
  private toolUseId = ''

  startBlock(name: string, id: string): void {
    this.jsonBuffer = ''
    this.toolName = name
    this.toolUseId = id
  }

  appendDelta(jsonFragment: string): void {
    this.jsonBuffer += jsonFragment
  }

  finalizeBlock(): ToolUseRequest {
    const input = JSON.parse(this.jsonBuffer)
    return {
      type: 'tool_use',
      id: this.toolUseId,
      name: this.toolName,
      input,
    }
  }
}

Multiple Tool Calls in One Response

The model can request multiple tool calls in a single response. The stream delivers them sequentially:

content_block_start (tool_use: Read, id: tu_01)
  input_json_delta ...
content_block_stop

content_block_start (tool_use: Read, id: tu_02)
  input_json_delta ...
content_block_stop

content_block_start (tool_use: Bash, id: tu_03)
  input_json_delta ...
content_block_stop

message_delta (stop_reason: tool_use)

The pipeline collects all tool-use blocks and delivers them to the agent loop as a batch. The agent loop then decides which to execute in parallel (read-only tools) and which to serialize (mutating tools), as discussed in Chapter 13's tool execution pipeline.

Early Tool Execution (Speculative Execution)

An advanced optimization: begin executing a tool before the entire response finishes streaming. When the pipeline detects a content_block_stop for a tool-use block, it can immediately dispatch that tool to the executor without waiting for message_stop.

Timeline without early execution:
  [Stream: thinking + text + tool1 + tool2 + message_stop] -> [Execute tool1] -> [Execute tool2]
  |<------- streaming time -------->|<---- execution time ---->|

Timeline with early execution:
  [Stream: thinking + text + tool1]  [tool2 + message_stop]
                              |
                              +-> [Execute tool1 (parallel with stream)]
                                                          |
                                                          +-> [Execute tool2]
  |<---- overlapped time: streaming + execution ------------>|

This optimization is beneficial for read-only tools (Read, Grep, Glob) where execution can safely overlap with continued streaming. It is dangerous for mutating tools (Write, Bash) where the model might reference the result of a previous tool in the same response.

The architectural decision: make early execution opt-in per tool based on the tool's isConcurrencySafe() and isReadOnly() declarations from the tool registry (Chapter 13). Conservative tools wait for the full response; aggressive tools start immediately.

Token-by-Token Processing

The Rendering Pipeline

Text deltas must flow from the stream processor to the terminal renderer with minimal latency. The user should see each word appear as the model generates it, creating the "typewriter" effect that makes streaming feel responsive.

Two pipelines diverge from the state machine:

  1. Text pipeline (green): text deltas flow through a buffer, a markdown renderer (which handles code blocks, headers, lists, and inline formatting incrementally), and finally to the terminal writer.

  2. Tool pipeline (red): tool-use deltas accumulate in a buffer until the block completes, then the parsed tool call flows to the agent loop.

The text pipeline must handle incremental markdown rendering. This is non-trivial because markdown formatting spans multiple tokens:

Delta: "Here is "
Delta: "some `"       <- Code span opens
Delta: "inline"
Delta: " code`"       <- Code span closes
Delta: " and **"      <- Bold opens
Delta: "bold text"
Delta: "**."           <- Bold closes

The markdown renderer maintains open formatting state (am I inside a code span? a bold section? a code block?) and renders each delta in context. When a delta opens a formatting span but does not close it, the renderer must buffer until the closing delimiter arrives.

Partial Line Handling

Terminals render line by line. A text delta that ends mid-line should be written immediately (for the typewriter effect), but the renderer must track that the line is not yet complete for formatting purposes:

class IncrementalRenderer {
  private currentLine = ''
  private inCodeBlock = false
  private inBold = false

  renderDelta(text: string): string {
    let output = ''
    for (const char of text) {
      this.currentLine += char
      if (char === '\n') {
        output += this.formatLine(this.currentLine)
        this.currentLine = ''
      }
    }
    // Flush partial line for immediate display
    if (this.currentLine) {
      output += this.formatPartialLine(this.currentLine)
    }
    return output
  }
}

Backpressure

The Problem

The model generates tokens faster than the terminal can render them. On a slow terminal (SSH over high-latency connection, terminal with complex themes, screen reader integration), the rendering pipeline falls behind the stream processor.

Without backpressure handling, the pipeline buffers events in memory without bound. A 64K-token output response generates ~16,000 delta events. If the renderer can only process 1,000 events per second and the model produces 3,000 per second, the buffer grows by 2,000 events per second. Over a 30-second generation, that is 60,000 buffered events consuming significant memory.

Pull-Based Flow Control

The solution is to make the streaming pipeline pull-based rather than push-based. The async generator pattern naturally provides this:

async function* processStream(
  rawStream: AsyncIterable<RawSSEEvent>,
): AsyncGenerator<ProcessedEvent> {
  for await (const raw of rawStream) {
    const processed = processEvent(raw)
    yield processed  // Pauses here until consumer pulls
  }
}

// Consumer controls the pace
async function renderStream(stream: AsyncGenerator<ProcessedEvent>) {
  for await (const event of stream) {
    await renderToTerminal(event)  // May be slow
    // Generator is paused until we pull the next event
  }
}

When the consumer (renderStream) is slow, the generator (processStream) pauses at each yield. The HTTP stream's TCP flow control propagates the backpressure to the server, which slows down event delivery. This is end-to-end backpressure without explicit buffer management.

Batching Under Pressure

In practice, pure backpressure may cause visible stuttering -- the user sees tokens arrive in bursts rather than smoothly. A better approach is to batch deltas when the renderer falls behind:

async function* batchingProcessor(
  stream: AsyncIterable<StreamEvent>,
): AsyncGenerator<StreamEvent | BatchedTextDelta> {
  let pendingText = ''
  let lastYieldTime = performance.now()

  for await (const event of stream) {
    if (event.type === 'text_delta') {
      pendingText += event.text
      const elapsed = performance.now() - lastYieldTime

      if (elapsed > 16) {  // ~60fps frame budget
        yield { type: 'batched_text_delta', text: pendingText }
        pendingText = ''
        lastYieldTime = performance.now()
      }
    } else {
      // Flush pending text before yielding non-text events
      if (pendingText) {
        yield { type: 'batched_text_delta', text: pendingText }
        pendingText = ''
        lastYieldTime = performance.now()
      }
      yield event
    }
  }

  if (pendingText) {
    yield { type: 'batched_text_delta', text: pendingText }
  }
}

The 16ms frame budget (roughly 60 fps) batches rapid text deltas into chunks that the renderer processes as a single unit. The user sees smooth text flow rather than individual character pops.

Partial Response Recovery

Mid-Stream Disconnection

Networks fail. TCP connections drop. Load balancers time out idle streams. A production streaming pipeline must handle disconnections that occur after partial data has been received.

The disconnection can happen at any point in the state machine:

State When Disconnected What Was Received Recovery Options
Idle Nothing Full retry (same as non-streaming)
InTextBlock Partial text Use partial text, retry for rest
InToolUseBlock Partial JSON Cannot use (invalid JSON), must retry
MessageActive (between blocks) Complete blocks Use completed blocks, may need retry
MessageComplete Everything except message_stop Treat as complete (stop is cosmetic)

Non-Streaming Fallback

When a streaming disconnection occurs and full retry is needed, the client should fall back to a non-streaming request rather than attempting another streaming connection. The rationale: if the streaming infrastructure (SSE parsing, chunked transfer, proxy keep-alive) failed, it may fail again. A non-streaming request uses a different code path and may succeed where streaming did not.

The fallback must account for context overlap. If the streaming request partially succeeded and was counted against the rate limit, the non-streaming retry should not be double-counted. Share failure state between the streaming and non-streaming paths:

async function* sendWithFallback(
  params: MessageParams,
): AsyncGenerator<StreamEvent> {
  try {
    yield* processStreamingResponse(
      await provider.createMessageStream(params)
    )
  } catch (error) {
    if (isStreamDisconnection(error)) {
      // Fall back to non-streaming
      const response = await provider.createMessage(params)
      yield* convertToStreamEvents(response)
    } else {
      throw error
    }
  }
}

Token Limits for Non-Streaming

Non-streaming requests have stricter server-side timeout constraints (typically 10 minutes). This limits the maximum output tokens that can be generated in a single non-streaming call. A production client should cap non-streaming output tokens conservatively:

const MAX_NON_STREAMING_TOKENS = 64_000

function adjustParamsForNonStreaming(params: MessageParams): MessageParams {
  return {
    ...params,
    max_tokens: Math.min(params.max_tokens, MAX_NON_STREAMING_TOKENS),
    stream: false,
  }
}

Usage Tracking — Merge Semantics

The Cumulative Model

The streaming API does not provide per-event token deltas. Instead, usage fields arrive at two points in the stream with cumulative semantics:

  • message_start includes input_tokens (the input token count for the request)
  • message_delta includes output_tokens (the cumulative output token count at end of generation) and may repeat input_tokens as zero

The zero-value problem is subtle. When message_delta reports input_tokens: 0, this does not mean "zero input tokens." It means "this field is not populated in this event." Naive code that always takes the latest value would overwrite the real input token count with zero:

// WRONG: overwrites real values with zero
function updateUsage(current: Usage, delta: Partial<Usage>): Usage {
  return { ...current, ...delta }
}

// CORRECT: only overwrite with non-zero values
function updateUsage(current: Usage, delta: Partial<Usage>): Usage {
  return {
    inputTokens: (delta.inputTokens ?? 0) > 0 
      ? delta.inputTokens! : current.inputTokens,
    outputTokens: delta.outputTokens ?? current.outputTokens,
    cacheReadTokens: delta.cacheReadTokens ?? current.cacheReadTokens,
    cacheWriteTokens: delta.cacheWriteTokens ?? current.cacheWriteTokens,
  }
}

This is a common trap in streaming API consumption. The fix is a "take the non-zero value" merge strategy, and it must be applied consistently across all usage fields.

Extended Thinking Tokens

When extended thinking is enabled, the model generates thinking tokens that count against the output token budget but may not be visible in the stream (depending on whether thinking is redacted). The usage tracking must account for these:

Total output tokens = visible_text_tokens + thinking_tokens + tool_input_tokens

The usage fields in message_delta include all three categories. The cost calculator needs the breakdown to apply different pricing (some providers price thinking tokens differently) and to display accurate metrics to the user.

Thinking Block Handling

Visible vs. Redacted Thinking

Extended thinking creates content blocks that may or may not be visible to the agent:

Visible thinking (type: "thinking") arrives as a normal content block with thinking deltas. The agent can read the model's reasoning, which is useful for debugging and for the context management system (which may need to compress thinking blocks).

Redacted thinking (type: "redacted_thinking") contains an opaque encrypted data blob. The agent cannot read the reasoning, but the blob must be preserved in the conversation history because the API requires it for continuity. The encrypted content counts against the context window, so the size must be tracked even though the content is not accessible.

The streaming pipeline handles both cases:

case 'content_block_start':
  if (block.type === 'thinking') {
    state = 'InThinkingBlock'
    thinkingBuffer = ''
  } else if (block.type === 'redacted_thinking') {
    // No deltas will follow -- the block is complete at start
    accumulateRedactedBlock(block.data)
    // State stays at MessageActive
  }
  break

Redacted thinking blocks are special: they arrive as complete blocks in content_block_start with no subsequent deltas. The state machine does not transition to InThinkingBlock for redacted thinking because there are no deltas to accumulate.

Thinking Block Ordering

The model typically emits thinking blocks before text and tool-use blocks:

message_start
  content_block_start (thinking)
    thinking_delta ...
  content_block_stop
  content_block_start (text)
    text_delta ...
  content_block_stop
message_delta
message_stop

However, the pipeline should not assume this ordering. The state machine accepts any valid transition regardless of block type sequence, making it resilient to future changes in the model's output patterns.

Stall Detection

Beyond hard disconnections, streams can stall -- events arrive, but with unusual gaps. A stall is different from a disconnection: the TCP connection is alive, data is eventually flowing, but something is causing intermittent delays.

Common causes: - Network congestion on a specific path - Server-side GPU scheduling delays during extended thinking - Load balancer buffering - TLS renegotiation

Stall Monitoring

class StallDetector {
  private lastEventTime = performance.now()
  private stallCount = 0
  private totalStallTime = 0

  private readonly stallThresholdMs = 30_000  // 30 seconds

  recordEvent(): void {
    const now = performance.now()
    const gap = now - this.lastEventTime

    if (gap > this.stallThresholdMs) {
      this.stallCount++
      this.totalStallTime += gap
      this.reportStall(gap)
    }

    this.lastEventTime = now
  }

  private reportStall(gapMs: number): void {
    // Telemetry, not termination
    log.warn('stream_stall', {
      gapMs,
      stallCount: this.stallCount,
      totalStallTimeMs: this.totalStallTime,
    })
  }
}

Stalls are logged but do not kill the stream. The data is eventually arriving, and killing a stalled stream discards all accumulated progress. The telemetry helps infrastructure teams identify network paths with high latency variance.

The 30-second threshold accounts for extended thinking pauses. During complex reasoning, the model may go 10-20 seconds between visible output events. The threshold must be set above this expected gap to avoid false positives.

Memory Management

Streaming responses hold native resources (TLS/socket buffers, response body streams) that live outside the garbage collector's reach. A production streaming pipeline must explicitly release these resources on every exit path.

The Resource Cleanup Pattern

async function* processStream(response: Response): AsyncGenerator<StreamEvent> {
  const stream = response.body

  try {
    for await (const event of parseSSE(stream)) {
      yield processEvent(event)
    }
  } finally {
    // Always release native resources
    await stream?.cancel().catch(() => {})
    response.body = null  // Release reference
  }
}

The finally block runs on every exit: normal completion, thrown error, generator .return() (user cancellation), and idle timeout abort. Without explicit cleanup, the Response.body ReadableStream holds native TLS buffers that leak outside the JavaScript heap -- a real memory leak pattern discovered in production Node.js environments.

Resource Lifecycle

Stream created
  |
  +-- Normal completion (message_stop)
  |     --> finally: cancel body, release response
  |
  +-- Error thrown (network, parse)
  |     --> finally: cancel body, release response
  |
  +-- User cancellation (.return())
  |     --> finally: cancel body, release response
  |
  +-- Idle timeout (watchdog fires)
        --> abort signal --> finally: cancel body, release response

All four exit paths converge in the same finally block. This is the advantage of the generator pattern for resource management -- try/finally is enforced by the language runtime, not by the developer remembering to call a cleanup function.

Design Lessons

Building a streaming pipeline for a production AI CLI agent, these architectural principles emerge:

1. Model the stream as a state machine. The event model has implicit sequencing rules (you cannot receive a text_delta before a content_block_start). Making these explicit as state transitions catches protocol violations early and documents the expected event flow for future maintainers.

2. Defer parsing until you have the complete unit. Incremental JSON parsing on every delta is O(n^2). Accumulate strings, parse once at block completion. This principle applies to any streaming system where partial data has no actionable use.

3. Use pull-based flow control for natural backpressure. Async generators pause when the consumer is not pulling. This propagates backpressure through the entire pipeline to the HTTP layer without explicit buffer management. The alternative -- push-based with explicit buffering -- requires manual buffer size limits and overflow strategies.

4. Separate text rendering from tool dispatch. Text deltas and tool-use deltas follow fundamentally different paths: text flows to the renderer in real time, tool-use accumulates silently until complete. A single "process delta" function that handles both will grow into an unmaintainable switch statement. Split them at the state machine.

5. Design every exit path through finally. Streaming responses hold native resources that the garbage collector cannot reach. The generator pattern's try/finally ensures cleanup runs on normal completion, errors, cancellation, and timeouts. Four exit paths, one cleanup block.

6. Distinguish stalls from disconnections. A stall (events arrive slowly) should be logged but tolerated. A disconnection (no events at all) should trigger recovery. The watchdog timeout handles disconnections; the stall detector handles quality monitoring. Different problems, different responses.

7. Batch under pressure, stream when possible. Pure backpressure causes visible stuttering. Batching text deltas into 16ms frame-budget chunks smooths the visual experience while maintaining backpressure semantics for the underlying stream.
