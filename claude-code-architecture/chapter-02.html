Chapter 2: Architecture Overview

The Shape of a Production AI CLI Agent

If Chapter 1 established why the CLI is the right interface for AI agents, this chapter establishes what lives inside one. We will map the full component architecture of a production AI CLI agent, trace the data flow from the moment a user presses a key to the moment rendered output appears on screen, identify the trust boundaries where untrusted data enters the system, and examine the module dependency graph that determines build order and compile-time optimization opportunities.

The specific numbers come from Claude Code -- 52 tools, 27 hook events, 500+ runtime flags, 512K lines of TypeScript -- but the architectural patterns are universal. Any production AI CLI agent will have these same subsystems, whether it implements them in 50K lines or 500K. The difference is not whether you need a tool system, a permission layer, and a context manager -- you do. The difference is how deep each one goes.

By the end of this chapter, you will have a component map that every subsequent chapter hangs on. When Chapter 15 discusses the Bash tool's 4,400-line parser, you will know where it sits in the tool system. When Chapter 18 discusses the permission architecture, you will know which data flows through it and why.

Pillar 1: The Query Engine (Brain)

The Query Engine is the agent loop -- the system that sends messages to an LLM, receives streaming responses, detects tool use requests, executes them, feeds results back, and repeats until the model produces a response with no tool calls.

At its core, this is a while(true) loop. But a production implementation must handle:

  • Streaming: Responses arrive token-by-token over server-sent events. The engine must parse partial JSON tool-use blocks during the stream, not after it completes.
  • Context management: Each turn adds messages to the conversation. The context window has a finite size. The engine must track token usage, decide when to compact (summarize older messages), and manage the budget across system prompt, conversation history, and tool results.
  • Error recovery: API calls fail. Rate limits hit. The model generates malformed tool calls. Context exceeds the window. Each failure mode needs a specific recovery strategy -- retry with backoff, reduce output token limit, compact the context, fall back to a different model.
  • Multi-turn coordination: A single user prompt ("Fix the authentication bug") may require 10+ tool calls across multiple turns. The engine must track turn count, enforce maximums, and detect convergence (when the model is done).

The agent loop architecture is covered in depth in Chapter 7. The key design decision is the loop's interface to its consumers: Claude Code implements it as an async generator that yields each message as it arrives, providing natural backpressure (if the UI is slow, the stream pauses) and a typed return channel for exit reasons.

Pillar 2: The Tool System (Hands)

The Tool System is how the agent acts on the world. It encompasses:

  • Tool Registry: A catalog of available tools with their schemas, descriptions, and capabilities. The registry must support static tools (always available), feature-gated tools (available based on build configuration), and dynamic tools (registered at runtime by MCP servers or plugins).
  • Tool Executor: The engine that dispatches tool calls, manages execution order (sequential vs. parallel vs. streaming pipeline), handles timeouts, and formats results.
  • Permission System: The gatekeeper that evaluates every tool call against a set of rules, modes, and policies to determine whether it should proceed, require user approval, or be blocked.
  • Tool Implementations: The actual tools -- file readers, file writers, shell command executors, search tools, agent spawners, and dozens more.

The tool system is the largest subsystem by code volume, and for good reason. Each tool is a surface area for bugs, security vulnerabilities, and user-facing behavior. The Bash tool alone spans ~12,000 lines across parser, AST, security analysis, and permission evaluation -- because executing shell commands in a user's environment on behalf of an AI model is the highest-risk operation in the system.

Pillar 3: The UI Renderer (Face)

The UI Renderer presents the agent's behavior to the user. In a CLI agent, this means terminal rendering -- but production terminal rendering is far more complex than console.log:

  • Streaming markdown: The agent's response arrives token-by-token. The renderer must parse and format markdown incrementally -- syntax-highlighted code blocks, tables, inline formatting, and headers that appear mid-stream.
  • Permission dialogs: When the tool system requests user approval, the UI must interrupt the stream, present the dialog, capture the response, and resume.
  • Progress indicators: Tool execution can take seconds (running tests, building projects). The UI must show what is happening and allow cancellation.
  • Diff visualization: File edits are presented as diffs with color-coded additions and deletions. This requires computing the diff, formatting it, and rendering it within terminal width constraints.
  • Multi-panel layout: Background tasks, teammate status, status bars, and conversation history may all need to appear simultaneously. This requires a layout engine -- not just sequential output.

Claude Code uses a custom fork of Ink (a React-for-terminals library) with a virtual DOM, Yoga-based flexbox layout, and differential rendering. This is a substantial investment -- roughly 60,000 lines -- but the rendering requirements justify it. Chapter 27 covers the terminal UI architecture.

Data Flow: From Keystroke to Rendered Output

Understanding the data flow is understanding the architecture. Here is the complete path a user prompt takes through the system:

Phase 1: Input Capture

The user types "Fix the bug in auth.ts" and presses Enter. The input handler captures the text, checks for slash commands (it is not one), and creates a user message. If the REPL was displaying a previous response, the input interrupts any in-progress speculation.

Phase 2: Context Assembly

Before the message reaches the API, the context assembler builds the full prompt:

sequenceDiagram
    participant User
    participant Input
    participant Context as Context Assembler
    participant Budget as Token Budget
    participant API as API Client
    participant LLM

    User->>Input: "Fix the bug in auth.ts"
    Input->>Context: new UserMessage
    Context->>Context: Load CLAUDE.md content
    Context->>Context: Assemble tool descriptions (52 tools)
    Context->>Context: Inject memory/plan attachments
    Context->>Context: Build system prompt
    Context->>Budget: Calculate token usage
    Budget-->>Context: Within budget / needs compaction
    Context->>API: Full message array + system prompt
    API->>LLM: Streaming API call (SSE)

The context assembler performs a critical job: it builds the system prompt from project instructions (CLAUDE.md), tool descriptions (one per registered tool), memory attachments, plan context, and system-level instructions. This system prompt alone can be 50,000-70,000 tokens. The token budget tracker ensures the combined system prompt plus conversation history fits within the model's context window.

If the total exceeds the window, the context compactor activates. It has 5 tiers of compression, from cheap (drop old messages) to expensive (LLM-based summarization). The tier selection depends on how far over budget the context is.

Phase 3: API Communication

The API client sends the assembled context to the LLM provider via a streaming API call. The response arrives as server-sent events (SSE), with each event containing either text content or a tool-use block.

The streaming architecture is critical for perceived performance. The first token of the response appears within 500ms-2s of the API call. The user sees text appearing incrementally, even though the full response may take 10-30 seconds to generate.

Phase 4: Tool Detection and Execution

As the stream arrives, the agent loop parses it for tool-use blocks. When it detects one, the tool execution pipeline activates:

sequenceDiagram
    participant Loop as Agent Loop
    participant Exec as Tool Executor
    participant Perm as Permission Engine
    participant Hook as Hook Engine
    participant Tool as Tool Implementation
    participant Loop2 as Agent Loop

    Loop->>Exec: tool_use block detected
    Exec->>Hook: PreToolUse event
    Hook-->>Exec: allow / deny
    Exec->>Perm: evaluate(tool, input)
    Perm-->>Exec: approved / ask user / denied

    alt approved
        Exec->>Tool: execute(input)
        Tool-->>Exec: result
    else ask user
        Exec->>Exec: show permission dialog
        Exec->>Tool: execute(input) [if approved]
        Tool-->>Exec: result
    else denied
        Exec-->>Loop2: denied result
    end

    Exec->>Hook: PostToolUse event
    Exec->>Loop2: tool_result message

The streaming tool execution optimization is architecturally significant. While the model is still generating content block N+1, the tool from block N is already executing. For a response that invokes three tools, this pipelining can reduce total latency by 60-70% compared to sequential execution. The executor classifies tools as concurrent-safe (read operations like file reads, greps, and globs) or exclusive (write operations like file edits and bash commands) and schedules accordingly.

Phase 5: Result Injection and Loop Continuation

The tool result is added to the conversation as a tool_result message. The token budget is updated. If the context now exceeds the window, compaction fires. Then the agent loop sends the updated conversation back to the API, and the cycle repeats.

Phase 6: Terminal Response and Rendering

When the model produces a response with no tool-use blocks, the turn is complete. The output formatter processes the response -- rendering markdown with syntax highlighting, formatting code blocks, computing word wrap for the terminal width -- and the REPL screen displays it.

If the speculation engine is enabled, it may begin a speculative next turn, predicting what the user will say next and pre-computing the response.

The loop from Result Injection back to Context Assembly is what makes this an agent, not a chatbot. The system observes the result of its action and decides what to do next. A single user prompt may traverse this loop 1 time (simple question, no tools needed) or 20+ times (complex task with many file reads, edits, test runs, and corrections).

Trusted Domain

The user and their personal configuration are trusted. The user explicitly chose to run the agent, configured their API keys, and set their permission preferences. User-level settings (~/.claude/settings.json) are loaded without a trust dialog because they are under the user's direct control.

Semi-Trusted Domain

Project-level configuration (.claude/settings.json, CLAUDE.md) is semi-trusted. It was written by a human developer -- possibly the user themselves, possibly a team member, possibly an unknown contributor to an open-source project. The trust dialog mediates this boundary: "Do you trust the files in this folder?"

If the user declines trust, project-level settings, instructions, hooks, and MCP configurations are all ignored. The agent operates in restricted mode with only user-level settings. This prevents a malicious repository from injecting instructions or permissions.

Untrusted Domain

Everything the agent reads from the environment is untrusted: source code files, issue descriptions, web content, MCP server responses, and command output. Any of these can contain prompt injection attempts -- text designed to manipulate the LLM into taking unintended actions.

The architectural defense is layered: 1. Content tagging: Untrusted content is wrapped in system-reminder markers that the LLM is trained to treat as data, not instructions 2. Tool gating: Even if the LLM is manipulated, the permission system blocks dangerous actions 3. Bash security analysis: Shell commands are parsed into ASTs and analyzed for dangerous patterns regardless of what the LLM intended 4. Output sanitization: Tool results are size-limited and format-constrained to prevent exfiltration

Model Domain

The LLM itself is a unique trust domain. It is neither trusted (it might hallucinate dangerous commands) nor untrusted (its responses drive the agent's behavior by design). The architectural approach is to trust the model's judgment for action selection while constraining its execution through the permission and security systems.

Every tool call the model generates passes through the same permission pipeline as if it were entered by an untrusted user. The model's authority comes from the user's trust delegation -- the user has chosen a permission mode that defines how much autonomy the model has.

Layer 0: The Foundation

The foundation layer contains the global state singleton, type definitions, and build constants. The critical property of this layer: it has no imports from the rest of the codebase. bootstrap/state.ts imports only from external packages and TypeScript type-only imports. This is enforced by a custom ESLint rule (bootstrap-isolation).

Why? Because every other module in the system needs to read global state. If the state module imported from, say, utils/permissions.ts, and utils/permissions.ts imported from services/api/claude.ts, then the state module would transitively depend on the API client. Now you cannot initialize state without initializing the API client, which needs authentication, which needs the keychain, which might not be available yet. The import DAG becomes a tangle.

By keeping the state module at the leaf of the import graph, it can be imported from anywhere without creating cycles. This is a deliberate architectural constraint that enables the 50+ files that depend on global state to do so safely.

Layer 1: Pure Utilities

Utilities process inputs and produce outputs without initiating external I/O. The bash parser takes a command string and returns an AST. The permission evaluator takes rules and a tool call and returns a verdict. The hook engine takes an event and a set of registered hooks and runs them.

These are "pure" in the architectural sense -- they depend on Layer 0 for state access but do not initiate API calls, spawn processes, or write to disk. This makes them testable in isolation and safe to import without side effects.

Layer 2: Services

Services are the I/O boundary. The API client talks to LLM providers. The MCP client manages connections to external tool servers. The analytics service sends telemetry. The context compactor makes LLM calls to summarize conversations.

Services import from Layers 0-1. They can also import from each other -- the compactor uses the API client, for example. Circular dependencies at this layer are resolved with the lazy require() pattern discussed in Chapter 3.

Layer 3: Tools

Each tool lives in its own directory with its implementation, schema, tests, and any supporting modules. Tools import from Layers 0-2. The tool registry conditionally includes tools based on compile-time feature flags:

const tools: Tool[] = [
  BashTool,
  FileReadTool,
  // ... always-available tools

  // Feature-gated: only in internal builds
  ...(feature('USER_TYPE') === 'ant'
    ? [require('./tools/REPLTool.js').REPLTool]
    : []),

  // Feature-gated: only when coordinator mode is enabled
  ...(feature('COORDINATOR_MODE')
    ? [require('./tools/TeamCreateTool.js').TeamCreateTool]
    : []),
];

When a feature flag is false at compile time, the require() call and everything it transitively imports are eliminated from the production binary. This is how multiple product SKUs ship from one codebase.

Layers 4-6: Orchestration, UI, and Entry

The orchestration layer wires tools to the agent loop. The UI layer renders everything. The entry point bootstraps the application. These layers import freely from everything below.

Breaking the Rules: Lazy require()

The hierarchy is aspirational. In reality, circular dependencies exist, and the codebase resolves them with a consistent pattern:

const getTeammateUtils = () =>
  require('./utils/teammate.js') as typeof import('./utils/teammate.js');

Instead of a top-level import, the module is loaded on first call. This breaks the cycle because the dependent module does not need to be resolved at import time. The as typeof import(...) cast preserves full type safety at the TypeScript level while deferring the actual module load to runtime.

This pattern is not a hack -- it is a deliberate choice over alternatives like dependency injection containers, which would add complexity and runtime overhead for a problem that lazy loading solves simply.

Reading the Metrics

Fifty-two tools means the tool system needs not just a list, but a registry with: - Schema validation (each tool defines its input schema via Zod) - Permission evaluation (each tool call passes through 6 modes and 8 rule sources) - Feature gating (some tools only exist in certain builds) - Dynamic registration (MCP tools are added at runtime) - Streaming execution (tools can run in parallel with model generation)

Twenty-seven hook lifecycle events means the hook system is not emitter.on('event', callback). It is a 5,000-line state machine that handles: - Pre and post events for tool execution, message submission, and session lifecycle - Blocking hooks (exit code 2 = deny the action) and non-blocking hooks (observe only) - Timeout management (hooks that run too long are killed) - JSON communication (hooks receive structured input on stdin, emit structured output on stderr) - Seven registration sources (user settings, project settings, local settings, managed settings, plugins, skills, and CLI flags)

Five hundred runtime flags means the feature flag system must: - Initialize within 50ms (including a network call to the flag service) - Fall back to coded defaults when the service is unreachable - Support targeting by user attributes (plan type, platform, version, auth method) - Lazy-evaluate per flag (no per-evaluation network call) - Refresh in the background without blocking the main thread

Each metric multiplies the engineering surface area. And the metrics interact: 52 tools multiplied by 6 permission modes multiplied by 27 hook events means thousands of potential execution paths. Testing, observability, and debugging all scale with this combinatorial complexity.

The "Essential Complexity" Argument

A natural question at this point: is 512K lines of TypeScript justified? Could you build the same product in 100K lines?

The answer depends on what "the same product" means. You could build an AI CLI agent in 10K lines that sends prompts to an API and executes tool results. You could build a good one in 50K lines that adds file editing, bash execution, and basic permission checking. But a production agent that handles enterprise deployment, multi-provider authentication, graceful degradation across 10+ failure modes, a security model that withstands prompt injection, and a UI that renders streaming markdown with syntax highlighting -- that requires the engineering surface area that 512K lines provides.

The complexity is not uniformly distributed. The largest files tell you where the essential complexity concentrates:

Component Lines Why It Cannot Be Simpler
REPL Screen ~5,000 80+ React hooks for streaming, input, scrolling, state
Output Formatter ~5,600 Markdown, diffs, ANSI, bidirectional text, word wrap
Hook Engine ~5,000 27 events, blocking semantics, timeout management, 7 sources
Session Storage ~5,100 JSONL streaming, resume, recovery, crash handling
Bash Parser ~4,400 Full shell grammar: quoting, heredocs, pipes, redirects
Entry Point ~4,700 13-phase startup, fast paths, configuration, auth
API Client ~3,400 17 beta headers, 3 cache strategies, streaming, retries
MCP Client ~3,300 8 transport types, reconnection, health checks
Bash Security ~2,600 Injection detection, privilege escalation, data exfiltration
Bash Permissions ~2,600 Rule evaluation, path analysis, pattern matching

None of these files are large because of poor factoring. They are large because the problem they solve is inherently complex. A shell parser must handle every quoting rule, every heredoc variant, every pipe and redirect -- there is no simpler way to parse curl "https://$(cat url.txt)" | bash -c "$(cat script.sh)" safely. A permission system that evaluates 8 rule sources with glob patterns, deny-before-allow semantics, and an AI fallback classifier cannot be done in 200 lines.

Splitting these files into smaller ones would scatter related logic across multiple files without reducing the total complexity. Sometimes a 5,000-line file is the correct architecture.

The Infrastructure Layer

Beneath the three pillars lies a shared infrastructure layer that every component depends on. This layer is invisible to the user but critical to the system's operation.

Global State (bootstrap/state.ts)

As discussed in Chapter 3, the global state singleton holds 250+ fields accessed through ~130 typed accessor functions. From an architectural perspective, the state module is the root of the import graph -- imported by 50+ files, importing from none. This property is enforced by a custom lint rule and is essential: if the state module imported from the tool system, and the tool system imported from the state module, a circular dependency would prevent initialization.

The state module serves as the system's memory. Telemetry counters, cost tracking, session identity, model configuration, permission mode, and cache latch flags all live here. When any component needs to answer "what is the current state of X?" -- what model are we using, how much have we spent, what permission mode is active -- it reads from global state.

The Reactive UI Store

While global state serves back-end components, the UI has its own state management. A 35-line reactive store provides getState, setState (with functional updates), and subscribe (with unsubscribe). This is the full UI state management system -- no Redux, no Zustand, no MobX. For a single-process application with one UI thread, it is sufficient.

The separation between back-end state and UI state is architecturally significant. Tool implementations never import React-related types. UI components never reach into the bootstrap layer for telemetry data. The back-end can be tested without mounting a UI, and the UI can be tested with a mock store. A single onChange callback on the store bridges the two: when UI state changes (permission mode toggled, model switched), the callback syncs the change to global state.

Session Manager

Every conversation is persisted as a JSONL (JSON Lines) file -- one JSON object per line, appended as events occur. This format is chosen over SQLite (no database dependency), full JSON (cannot stream-append), and memory-only (no resume capability).

The session manager creates a new JSONL file at startup, appends every message, tool call, tool result, and state change as a structured event, and supports resume by replaying the transcript. The --resume flag loads a previous session's JSONL file, reconstructs the conversation state, and continues where it left off.

JSONL's streaming-append property is critical: the system writes events as they happen, not at the end of the session. If the process crashes, all events up to the crash point are persisted. Resume after a crash replays those events, losing at most one in-progress tool call.

Hook Engine

The hook system provides 27 lifecycle events that fire at specific points in the agent's execution: before and after tool calls, on session start and stop, before message submission, on notification events, and more. Hooks are shell scripts registered in the configuration cascade.

The hook engine is not a simple event emitter. It handles: - Blocking semantics: A PreToolUse hook that exits with code 2 blocks the tool call. The hook's stderr output is fed back to the LLM as an explanation. - Timeout management: Hooks that exceed their timeout are killed, and the agent continues. - JSON communication: Hooks receive structured input on stdin (the tool name, arguments, and context) and can emit structured output on stderr. - Seven registration sources: User settings, project settings, local settings, flag settings, managed settings, plugins, and skills can all register hooks.

The 27 events cover the full lifecycle: PreToolUse, PostToolUse, PreContentBlock, PostContentBlock, PreApiCall, PostApiCall, SessionStart, SessionStop, UserPromptSubmit, Stop, SubagentStop, TaskCompleted, FileChanged, Notification, and more. Each event type has specific semantics documented in Chapter 29.

Telemetry

OpenTelemetry provides the observability foundation: metrics (cost tracking, latency, token usage), logs (structured event logging), and traces (distributed tracing across subagent sessions). When telemetry is disabled (user opt-out or enterprise policy), the providers are replaced with no-op implementations. This means telemetry callsites throughout the codebase do not need conditional checks -- they always call the provider, and the provider decides whether to record.

MCP Client

The Model Context Protocol client manages connections to external tool servers. MCP is the extensibility protocol -- it allows Claude Code to use tools provided by third-party servers without those tools being compiled into the binary.

The MCP client supports 8 transport types (stdio for local servers, SSE and HTTP for remote servers, WebSocket for real-time connections, and IDE-specific variants) and manages the full connection lifecycle: discovery, initialization, capability negotiation, health checks, reconnection, and graceful shutdown. Chapters 21-23 cover MCP architecture in detail.
