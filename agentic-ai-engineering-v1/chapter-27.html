Chapter 27: Token Economics of Loops

"Cost kills loops before bugs do. A loop that works but cannot justify its expense is a demo, not infrastructure."

The Loop That Ate the Budget

Tomás Reyes is a staff engineer at a healthcare data company processing electronic health records for forty regional hospital systems. His team built a loop that generates structured clinical summaries from unstructured physician notes. The loop reads a note (averaging 1,200 words), identifies diagnoses, medications, procedures, and follow-up instructions, then produces a JSON object conforming to their internal FHIR-adjacent schema. The oracle is a two-level validator: first, a deterministic schema check (JSON structure, required fields, coded values from approved terminology sets), and second, a rubric scorer that evaluates completeness by checking the summary against a term-extraction baseline. Pass rate stabilises at 91% after two weeks of prompt tuning. Physicians in a pilot programme confirm the summaries are clinically accurate and save them roughly seven minutes per note.

Tomás runs the economics for production deployment. The company processes 2,400 physician notes per day across all hospital systems. Each loop run consumes approximately 85,000 tokens. The note itself averages 3,000 tokens. The schema definition with terminology codes adds 4,500 tokens. The system prompt with medical extraction guidance runs 12,000 tokens. The model's reasoning and output generation averages 28,000 tokens. The oracle evaluation pass (re-reading the output against the schema and rubric) consumes 18,000 tokens. The remaining 19,500 tokens account for tool calls, conversation framing, and the retry overhead amortised across all runs: with a 91% first-attempt pass rate, roughly 9% of runs iterate at least once, each retry accumulating the full context of the previous attempt plus oracle feedback.

At Claude Sonnet pricing as of early 2026 — $3 per million input tokens and $15 per million output tokens [VERIFIED: Anthropic published pricing] — Tomás calculates the per-run cost. Input tokens average 57,000 across all iterations (schema, note, system prompt, tool results, oracle evaluation context, plus retry context for the 9% that iterate). Output tokens average 31,000 (model reasoning, generation, oracle grading output, plus retry generation). Per-run cost: ((57,000 × $3) + (31,000 × $15)) / 1,000,000 = $0.171 + $0.465 = $0.64 per run [ESTIMATE: assumes all iterations on Sonnet, no prompt caching, and the amortised retry calculation described above].

At 2,400 runs per day: $1,536 per day. $46,080 per month. $552,960 per year. Tomás's annual budget for the project — including engineering headcount, infrastructure, and API costs — is $200,000. The loop works flawlessly. The engineering is sound. The oracle is validated. It will never reach production at this configuration because the economics do not close. Tomás needs to reduce cost by at least 73% or find budget from elsewhere. The techniques in Chapter 28 will address the reduction. This chapter establishes the analytical framework for understanding where those tokens go and how to reason about the economics of any loop before committing to production deployment.

Defining Cost Per Verified Outcome

Most teams track cost per API call or cost per million tokens. These metrics describe infrastructure consumption but do not answer the question that determines whether a loop should run in production: what does it cost to produce one unit of verified, shippable work?

Cost per verified outcome (CPVO) is defined precisely as the total monetary expenditure across all iterations, retries, verification passes, and coordination overhead, divided by the number of outputs that pass the oracle and ship to consumers.

The distinction between CPVO and naive per-run cost is not pedantic. It changes decisions. A loop that costs $0.64 per run sounds cheap. But if that loop fails 9% of the time, and each failure triggers a retry that costs an additional $0.80 (more expensive than the first attempt because it carries the accumulated context from the failure), and those retries fail 20% of the time triggering a second retry at $0.98, then the actual cost to produce one verified output is substantially higher than $0.64. The failures do not merely reduce throughput — they inflate cost because the retry mechanism charges compounding context penalties.

This metric captures economic realities that raw token cost obscures. If a loop iterates five times before passing the oracle, the CPVO includes all five iterations' cost — not one-fifth of it. If a fleet of four specialists produces one verified synthesis, the CPVO includes all four specialists' token consumption plus the lead agent's coordination work. If a loop exhausts its budget without passing and escalates to a human, the tokens it consumed contributed zero verified outcomes — that expenditure increases the CPVO of the remaining successful runs because the denominator (successful outputs) does not grow while the numerator (total spend) does.

The precise formula:

CPVO = (C_system + C_generation + C_retries + C_oracle + C_coordination) / N_verified

Where C_system is the cost of loading the system prompt, tool schemas, and skill definitions on each model call across all iterations. C_generation is the cost of the model's reasoning and output production. C_retries is the additional context cost from prior failed iterations — oracle feedback, accumulated conversation history, and repeated context loading. C_oracle is the cost of running the verification pass on each iteration's output. C_coordination applies to fleets: the delegation, aggregation, and synthesis cost. N_verified is the number of outputs that pass the oracle and ship.

The relationship between pass rate and CPVO is non-linear and frequently underestimated. Improving pass rate from 80% to 90% does not reduce CPVO by 12.5% (the percentage improvement in pass rate). It reduces it by more, because eliminating a failed iteration eliminates not just that iteration's generation cost but also the growing context cost it would have contributed to subsequent iterations. In a loop where context grows by 12,000 tokens per iteration due to accumulated history and oracle feedback, the fifth iteration processes 48,000 more context tokens than the first iteration — at full input-token cost each time [ESTIMATE: based on typical context accumulation of ~12,000 tokens per iteration including oracle feedback, plan updates, and tool results from the failing attempt]. The most expensive token in a loop is the one in the last retry iteration, because it carries the full weight of every prior failure. This compounding relationship means that the single highest-leverage intervention for reducing CPVO is improving first-attempt pass rate — whether through better prompting, better tool results, or better context engineering. A 10-point pass-rate improvement typically reduces CPVO by 15-25% when compounding effects are included, not the naive 10% that linear thinking suggests [ESTIMATE].

Where Tokens Go: Single-Loop Anatomy

To engineer cost effectively, you must understand the internal token distribution of a typical loop. Without this understanding, cost-reduction efforts target the wrong categories — optimising the 3% when the 27% sits untouched. The following breakdown represents a code-fix loop running on Claude Sonnet that takes an average of 2.3 iterations to pass [ESTIMATE: all proportions are typical values observed across multiple loop implementations; individual loops vary substantially based on task type, tool count, and context engineering maturity]:

The system prompt, tool schemas, and skill definitions constitute approximately 13% of total tokens. These are loaded on every model call within every iteration — a fixed cost that multiplies with iteration count. For a loop with five active tools, this category is roughly 20,000 tokens per call — substantial but manageable. For a loop using MCP with many connected servers, tool schemas alone can reach extraordinary sizes: Anthropic's tool-use research documented a five-server MCP setup (GitHub, Slack, Sentry, Grafana, Splunk) consuming approximately 55K tokens in tool definitions before the conversation even started [VERIFIED] (Anthropic, "Introducing advanced tool use on the Claude Developer Platform"). In the worst measured case, tool definitions consumed 134K tokens [VERIFIED] — more than the entire content budget of many loops. Tool Search (Chapter 9) addresses this by loading only relevant tools on demand, but teams unaware of the problem pay the full schema cost on every call.

Conversation history accounts for approximately 17% of total tokens. This grows monotonically across iterations: each iteration adds its own content (model output, tool calls, tool results) to the history that subsequent iterations must read. By iteration four, the history alone may exceed 40,000 tokens. History is the primary driver of the "each retry is more expensive than the last" phenomenon.

Tool results — file reads, search results, API responses — account for the largest single category at approximately 27% of total tokens. Much of this is waste, which is why it represents the highest-leverage target for cost reduction. An agent reading an entire 3,000-line file to understand a 20-line function pays for 2,980 irrelevant lines. An agent receiving a full CVE database entry (800 tokens) to extract only the severity score (10 tokens) pays for the reporter timeline, the reference list, the workaround description, and the detailed technical analysis that it will not use for its current decision. An agent that searches a codebase and receives twenty results when three are relevant pays for seventeen irrelevant results clogging the context and reducing attention to the three that matter.

The cost-engineering implication is direct: every tool call that returns more content than the model will actually use for its next decision is burning money. The fix is programmatic preprocessing — using code (not the model) to filter, extract, and summarise tool results before they enter the model's context. This technique has zero latency cost (filtering is microseconds versus the model's seconds of processing) and high token savings (60-85% reduction in tool-result tokens for typical file-read operations [ESTIMATE]).

Model reasoning and output generation together account for approximately 26% of total tokens. Unlike input tokens, output tokens cost 5x more per token ($15/M versus $3/M at Sonnet rates [VERIFIED]), making this category the largest dollar-cost contributor despite being a smaller share of total token volume. A loop that generates 30,000 output tokens per run pays $0.45 for those outputs; the same run's 55,000 input tokens cost only $0.165. Optimising output tokens has 2.7x the dollar-per-token-saved leverage of optimising input tokens. This asymmetry means that techniques reducing output (constrained generation, structured output schemas that prevent verbose explanations, extended-thinking budgets that cap reasoning tokens) often deliver more dollar savings than techniques reducing inputs — despite inputs being a larger category by volume.

Oracle evaluation adds approximately 8% of total tokens. The oracle re-reads the output, applies its rubric or checks, and produces a verdict with feedback. This cost exists even on passing iterations — verification is never free. Teams sometimes attempt to eliminate oracle cost by removing verification entirely or making it implicit (the model evaluates its own output within the same context). Both are false economies: removing verification means you cannot distinguish good output from bad output, making CPVO unmeasurable. Self-evaluation in shared context (the generous self-reviewer from Chapter 21) produces systematically inflated pass rates, meaning the loop ships bad output while believing it is good. The oracle's 8% cost buys the quality guarantee that makes the entire loop's output trustworthy. Reducing oracle cost without eliminating the oracle is possible through lighter-weight evaluation strategies: a rubric with three binary checks costs less than a rubric with ten gradient-scored dimensions, and for some tasks a structured-output validator (pure code, zero tokens) suffices as a first-pass oracle with model-based evaluation reserved for cases that pass the structural check.

Failed iteration overhead (wasted tokens in iterations that do not pass) accounts for the remaining approximately 9%. This is the compounding cost that makes pass rate the single highest-leverage economic variable. Each failed iteration adds its own full token expenditure to the run without contributing to the final output. At a 91% pass rate with average 1.1 retries on failing runs, waste is modest — roughly $0.06 per run amortised across all runs. At a 60% pass rate with average 2.5 retries, waste dominates the budget: every verified outcome carries the cost of 1.5 additional failed attempts, each of which is more expensive than a fresh first attempt due to context accumulation. The compounding is vicious: iteration two costs more than iteration one (longer history), iteration three costs more than iteration two, and so forth. A loop that requires four iterations to pass may find that iteration four costs 2.3x what iteration one cost — not because anything changed except the accumulated context from prior failed attempts.

Where Tokens Go: Fleet Anatomy

A fleet multiplies the single-loop pattern by specialist count and adds coordination as a new cost category. Understanding fleet token distribution is essential because the coordination overhead — invisible in single-loop accounting — can dominate the budget for poorly designed fleets. The following model represents a five-specialist security review fleet with a lead on Sonnet, consistent with the architecture described in Chapter 24 [ESTIMATE: all figures derived from the verified fleet architecture; actual costs vary by specialist count, model selection, task complexity, and scope per specialist]:

Component Input tokens Output tokens Cost (USD)
Lead: goal decomposition 18,000 6,000 $0.14
Lead: 5 delegation prompts 12,000 5,000 $0.11
Specialist A (auth review) 48,000 22,000 $0.47
Specialist B (data flow) 42,000 18,000 $0.40
Specialist C (API surface) 52,000 25,000 $0.53
Specialist D (dependencies) 35,000 15,000 $0.33
Specialist E (IaC review) 40,000 18,000 $0.39
Lead: result aggregation 55,000 12,000 $0.35
Oracle evaluation 22,000 8,000 $0.19
Total 324,000 129,000 $2.91

[ESTIMATE: token counts assume each specialist reads 3-5 files within its scope, performs one tool-augmented analysis pass, and produces a structured findings report. Lead aggregation reads all five specialist reports plus project context for cross-specialist synthesis.]

The coordination tax is visible in this breakdown. The lead's total cost across decomposition, delegation, and aggregation is $0.60 — representing 21% of the total fleet cost despite producing no findings directly. This is the price of orchestration. If each specialist averages $0.42 of productive analysis work, coordination adds a 28% surcharge on top [ESTIMATE]. For five specialists, this overhead is acceptable because the quality gain from context isolation (Chapter 24) justifies it. But the ratio degrades with fleet size: a ten-specialist fleet's lead must read twice as many specialist outputs during aggregation (40,000+ tokens of results versus 20,000+), pushing coordination toward 35-40% of total cost while each additional specialist contributes less marginal analytical value.

At 50 PRs per day, this fleet costs $145.50 per day or roughly $4,365 per month [ESTIMATE]. Whether this is justified depends on the alternative cost — a question the break-even analysis below addresses directly.

The Compounding Effect of Scheduled Execution

A run that seems cheap at unit cost becomes a major line item at sustained cadence. Teams consistently underestimate this compounding because they evaluate cost-per-run during development (where they run the loop manually, a few times per day) and do not project forward to production cadence. The psychological error is anchoring on the unit cost ("less than a dollar per run — basically free") without multiplying by the volume that production deployment implies.

The arithmetic for Tomás's clinical summary loop:

Cadence Runs/month Monthly cost Annual cost
Manual testing (10/day) 300 $192 $2,304
Pilot programme (100/day) 3,000 $1,920 $23,040
Single hospital (400/day) 12,000 $7,680 $92,160
Full deployment (2,400/day) 72,000 $46,080 $552,960

[ESTIMATE: all figures use $0.64/run calculated above]

The jump from pilot (affordable) to full deployment (budget-breaking) is a factor of 24 in volume. The loop did not get more expensive per run — the environment scaled, and the unit economics that worked at pilot volume become untenable at production volume. This is the single most common way loops die: they work technically, they pass pilot validation, they impress stakeholders in demos, and they fail economically when deployed at the scale they were designed for. The team discovers that "it works" and "it's affordable at scale" are different claims requiring different evidence.

For fleets, the compounding is even more dramatic because the unit cost per run is higher. A $2.91-per-run fleet that scans every commit across a repository producing 150 commits per day costs $13,138 per month. If the scan is extended to four repositories at similar volume (a natural next step after a successful pilot), the monthly cost reaches $52,552 — the annual loaded cost of a senior engineer, producing work that could alternatively be handled by running the fleet only on PRs (30-50 per day instead of 600 commits) at one-tenth the cost [ESTIMATE]. The cadence decision — per-commit versus per-PR versus nightly — is not a technical choice. It is a budget decision that determines whether the fleet is economically viable.

A useful mental model: any loop that runs more than once per hour should have its annual cost calculated and posted on the team's cost dashboard before reaching production. Any loop that runs more than ten times per hour should require explicit budget approval from whoever manages the API spend. These are not bureaucratic hurdles — they prevent the gradual accumulation of scheduled loops from silently consuming the team's entire infrastructure budget. A team with ten loops running at moderate cadence can easily reach $50,000 per month in aggregate API spend without any individual loop appearing expensive — each loop's owner sees only their $5,000 line item, while the budget owner sees the aggregate. This is the "death by a thousand loops" failure mode that observability (Chapter 29) must surface before it becomes a budget crisis.

Break-Even Against Human Baseline

A loop justifies its production cost when its cost per verified outcome is lower than the human alternative — adjusted for quality, speed, and the human time that remains necessary even with the loop running. This comparison is the fundamental economic test. If the loop costs more than the human it replaces (quality-adjusted), the loop should not run in production regardless of how technically impressive it is. If the loop costs less, the remaining question is whether the absolute cost fits within available budget.

The break-even calculation requires honest accounting on both sides. Teams commonly undercount the human cost (forgetting benefits, overhead, context-switching time, and the opportunity cost of senior engineers doing reviewable work) and undercount the loop cost (forgetting retries, human follow-up on loop failures, and the operational burden of maintaining the loop infrastructure).

The break-even calculation for Tomás's clinical summary loop:

Human cost per summary [ESTIMATE: based on reported physician time savings of 7 minutes per note, valued at a physician's loaded hourly rate; these are estimates because the actual loaded cost of physician time varies by specialty, region, and employment model]:

  • Physician time to write a structured summary manually: 7 minutes average
  • Physician loaded hourly cost (including benefits, overhead, opportunity cost): $250/hour [ESTIMATE]
  • Human cost per summary: 7/60 × $250 = $29.17

Loop cost per verified outcome:

  • Per-run cost: $0.64
  • At 91% pass rate: CPVO = $0.64 / 0.91 = $0.70
  • Plus human review of flagged cases (9% require physician review at 3 min each): 0.09 × (3/60) × $250 = $1.13 amortised across all runs
  • Quality-adjusted CPVO: $0.70 + $1.13 = $1.83

The loop is 15.9x cheaper than manual summarisation [ESTIMATE]. Even at Tomás's full-deployment cost of $552,960/year, the human alternative would cost 2,400 × 365 × $29.17 = $25,554,600/year. The loop is unambiguously worth running at production scale — the problem is not ROI but absolute budget availability. Tomás needs to secure the $552K budget by demonstrating the $25M alternative, or he needs to reduce cost per run through the engineering levers in Chapter 28.

For the security review fleet, the comparison is closer:

Human cost per PR security review [ESTIMATE: assumes a senior security engineer at $85/hour fully loaded; review time based on a medium-complexity PR requiring 25-35 minutes of careful review]:

  • Human time: 30 minutes average
  • Human cost: 0.5 × $85 = $42.50

Fleet cost per verified review: $2.91 (at 88% pass rate, CPVO = $2.91 / 0.88 = $3.31).

The fleet is 12.8x cheaper [ESTIMATE]. But quality adjustment matters: the fleet is not a perfect substitute for a senior security engineer. If 12% of fleet reviews require human follow-up (reviewing the fleet's findings and filling coverage gaps) at 10 minutes each, the adjusted cost is $3.31 + (0.12 × 10/60 × $85) = $3.31 + $1.70 = $5.01 per verified review. Still 8.5x cheaper than pure human review — a robust economic justification for fleet deployment.

The break-even point — where the fleet plus follow-up costs more than a human doing the full review — occurs when human follow-up rate exceeds approximately 88% [ESTIMATE: solving $2.91/pass_rate + follow_up_rate × (10/60) × $85 = $42.50 for follow_up_rate given pass_rate; at this level, the fleet is merely adding a preliminary step before the same human effort]. At that point, the fleet is not saving work — it is adding a preceding step without reducing the human's burden. The fleet ceases to be a labour-saving device and becomes a labour-creating one.

This analysis reveals two paths to economic viability for any loop. Either the loop must be cheap enough that even modest human-time savings justify it (Tomás's case: $0.70 CPVO saving $29.17 of physician time is justified at almost any pass rate). Or the loop must be reliable enough that human follow-up is rare (the security fleet: $3.31 CPVO justified as long as human follow-up stays below 88%). The second path is more fragile because pass-rate degradation — from model updates, codebase changes, or task-distribution shifts — can push follow-up rates above the break-even threshold without any explicit failure event.

A third factor that break-even analyses typically omit: the speed premium. Tomás's loop produces a summary in 45 seconds. A physician takes 7 minutes. For 2,400 daily summaries, the loop saves not just money but 280 hours of physician time per day across all hospitals — time that can be redirected to patient care activities that generate revenue. If each freed physician-minute is worth $4.17 in additional billable care (the same $250/hour rate), and the loop frees 7 minutes per summary, the value of time redirection is $29.17 per summary — equal to the full human cost. The true economic gain is therefore 2x the naive cost comparison suggests, because the physician's freed time has productive alternative uses rather than disappearing.

For batch workloads where latency is irrelevant (Kenji's nightly audit), no speed premium exists and the break-even analysis is purely financial. For interactive workloads (developer tools, clinical decision support), the speed premium can dominate the financial arithmetic. A code-review fleet that costs $3.31 per review but delivers results in 90 seconds versus a 4-hour human turnaround is worth far more than the $42.50 it saves — it unblocks the developer's workflow, preventing the context switch that occurs during a 4-hour wait. Quantifying this unblocking value is difficult, but ignoring it systematically undervalues fast loops in break-even analyses.

The Token Ledger

Production loops need instrumentation that tracks token expenditure by category, enabling targeted cost reduction. The economics.py module provides this ledger alongside the cost-model types:


from __future__ import annotations

import time
from dataclasses import dataclass, field
from enum import StrEnum


class CostCategory(StrEnum):
    SYSTEM_PROMPT = "system_prompt"
    TOOL_SCHEMAS = "tool_schemas"
    CONVERSATION_HISTORY = "conversation_history"
    TOOL_RESULTS = "tool_results"
    ORACLE_EVALUATION = "oracle_evaluation"
    MODEL_REASONING = "model_reasoning"
    GENERATION = "generation"
    COORDINATION = "coordination"
    RETRY_OVERHEAD = "retry_overhead"


# Pricing as of early 2026, at list price [VERIFIED: Anthropic published pricing]
MODEL_RATES: dict[str, dict[str, float]] = {
    "haiku": {"input": 0.80, "output": 4.00},
    "sonnet": {"input": 3.00, "output": 15.00},
    "opus": {"input": 15.00, "output": 75.00},
}


@dataclass
class TokenEntry:
    """A single token-expenditure event tagged by category and model."""

    category: CostCategory
    input_tokens: int
    output_tokens: int
    model: str
    timestamp: float = field(default_factory=time.time)

    @property
    def cost_usd(self) -> float:
        rates = MODEL_RATES.get(self.model, MODEL_RATES["sonnet"])
        return (
            self.input_tokens * rates["input"]
            + self.output_tokens * rates["output"]
        ) / 1_000_000


@dataclass
class TokenLedger:
    """Tracks token spend by category across a loop or fleet run."""

    entries: list[TokenEntry] = field(default_factory=list)

    def record(
        self,
        category: CostCategory,
        input_tokens: int,
        output_tokens: int,
        model: str = "sonnet",
    ) -> None:
        self.entries.append(
            TokenEntry(category, input_tokens, output_tokens, model)
        )

    @property
    def total_cost_usd(self) -> float:
        return sum(e.cost_usd for e in self.entries)

    def cost_by_category(self) -> dict[CostCategory, float]:
        breakdown: dict[CostCategory, float] = {}
        for entry in self.entries:
            breakdown[entry.category] = (
                breakdown.get(entry.category, 0.0) + entry.cost_usd
            )
        return breakdown

    def top_categories(self, n: int = 3) -> list[tuple[CostCategory, float]]:
        return sorted(
            self.cost_by_category().items(), key=lambda x: x[1], reverse=True
        )[:n]


@dataclass
class CostModel:
    """Predicts CPVO for a loop or fleet configuration."""

    base_input_tokens: int
    base_output_tokens: int
    model: str
    avg_iterations: float
    pass_rate: float
    specialist_count: int = 1
    coordination_tokens_per_specialist: int = 5_000

    @property
    def cost_per_attempt(self) -> float:
        rates = MODEL_RATES.get(self.model, MODEL_RATES["sonnet"])
        per_specialist = (
            self.base_input_tokens * rates["input"]
            + self.base_output_tokens * rates["output"]
        ) / 1_000_000
        coordination = (
            self.coordination_tokens_per_specialist
            * self.specialist_count
            * rates["input"]
        ) / 1_000_000 if self.specialist_count > 1 else 0.0
        return per_specialist * self.specialist_count + coordination

    @property
    def cpvo(self) -> float:
        """Cost per verified outcome."""
        return self.cost_per_attempt * (1.0 / self.pass_rate)

    def monthly_cost(self, runs_per_day: int) -> float:
        return self.cpvo * runs_per_day * 30

The Model-Tiered Fleet as Economic Architecture

Chapter 24 described Spiral's architecture: a lead on Haiku, specialists on Opus [VERIFIED]. The economic logic of this design is quantifiable.

If the lead makes eight inference calls per fleet run (decompose goal, formulate five delegation prompts, read results, synthesise) and each averages 10,000 input + 4,000 output tokens, the lead's cost:

  • On Haiku: (80,000 × $0.80 + 32,000 × $4.00) / 1,000,000 = $0.064 + $0.128 = $0.19 per run [ESTIMATE]
  • On Sonnet: (80,000 × $3.00 + 32,000 × $15.00) / 1,000,000 = $0.24 + $0.48 = $0.72 per run [ESTIMATE]
  • On Opus: (80,000 × $15.00 + 32,000 × $75.00) / 1,000,000 = $1.20 + $2.40 = $3.60 per run [ESTIMATE]

The lead on Haiku is 3.8x cheaper than on Sonnet and 18.9x cheaper than on Opus. Since the lead's task is coordination — routing, decomposing, aggregating structured outputs — it does not benefit from the deeper reasoning that justifies Opus pricing. The coordination task needs speed and reliability on classification/routing decisions, not depth.

Conversely, the specialist on Opus producing a complex legal draft or high-quality editorial prose benefits directly from the additional reasoning capability. The quality difference between Opus and Sonnet output on hard generation tasks may mean that Opus passes the oracle on the first attempt while Sonnet requires two attempts — making Opus cheaper per verified outcome despite being 5x more expensive per token.

The generalised principle: allocate model cost where capability differences translate to outcome differences. Routing and formatting can use Haiku. Standard analysis and implementation can use Sonnet. Tasks requiring deep reasoning, creative generation, or complex multi-step synthesis should use Opus — but only those tasks, not the coordination scaffolding around them.

The practical implication for fleet budgeting: the "average model cost per token" metric that many teams use is meaningless for fleets because it conflates cheap coordination tokens (high volume, low value-per-token) with expensive specialist tokens (lower volume, high value-per-token). The useful metric is model cost weighted by value contribution: what percentage of the fleet's total value comes from the lead's coordination versus the specialists' production? If coordination is 15% of total value but costs 40% of total spend, the lead model is over-provisioned. If specialist production is 85% of value and costs 30% of total spend, the specialists may be under-provisioned. This value-weighted analysis drives the model-tiering decisions that separate cost-effective fleets from wasteful ones.

The second economic dimension is retry economics within the cascade. If Opus passes the oracle 94% of the time on the first attempt while Sonnet passes 78% of the time [ESTIMATE], Sonnet requires 1.28 attempts per verified outcome versus Opus's 1.06. At Sonnet's rate, the expected cost per verified outcome for a generation task is $0.42 × 1.28 = $0.54. At Opus's rate: $2.10 × 1.06 = $2.23. Opus is still 4.1x more expensive per verified outcome — but this is far less than the 5x raw token-price differential suggests. For tasks where the pass-rate gap is larger (Opus at 96% versus Sonnet at 65%), the CPVO gap narrows further, and at extreme difficulty levels, Opus can actually become cheaper per verified outcome than Sonnet because Sonnet's retry count drives compound context costs that overwhelm its per-token savings.

What Breaks

The cost model in this chapter assumes three things that drift over time: stable pricing, stable token consumption, and stable pass rates.

Model pricing changes without warning in a production budget. Providers adjust rates, introduce new model versions at different price points, or change the input-to-output cost ratio. A cost model calibrated to early-2026 Sonnet pricing becomes inaccurate the moment pricing shifts. Teams should build cost monitoring that alerts on cost-per-run deviation from rolling averages — this catches both pricing changes (all runs suddenly cost more) and behavioural changes (context growth, retry increase) that affect token consumption.

Token consumption drifts as the environment evolves. Tomás's loop averaged 85,000 tokens when processing notes from forty hospital systems. If the company onboards ten additional systems whose physicians write longer notes (1,800 words versus 1,200 words average), per-run token consumption increases by roughly 15% without any change to the loop itself. Similarly, a code-review fleet's per-run cost grows as the codebase grows, because file reads return more content and more context is needed to understand the code under review.

Pass rates degrade when the input distribution shifts. A loop tuned on typical inputs encounters an atypical period — a complex refactoring sprint, a new coding style from recently-hired engineers, or notes from a specialty the system was not trained on. Pass rate drops from 91% to 74%. CPVO increases by 23% (from $0.70 to $0.86) — not because the loop is broken, but because the input population changed. Cost models must be recalibrated against actual production data at least monthly rather than treated as fixed parameters established during development.

The most insidious economic failure is a loop whose CPVO creeps upward by 3-5% per month — imperceptible in any single month's budget review but compounding to a 50% cost increase over a year. This creep has multiple potential causes: gradual codebase growth increasing per-file token counts, slow model capability degradation on the specific task type (rare but documented for some edge cases), or accumulation of edge-case inputs that require more iterations. Monthly CPVO recalibration against a rolling baseline, with automated alerts when the 30-day CPVO exceeds the 90-day average by more than 15%, catches this drift before it becomes budgetarily significant.

Summary

  • Cost per verified outcome (CPVO) is the headline economic metric: total spend across all iterations and coordination, divided by outputs that pass the oracle and ship.
  • Input tokens dominate volume (~70% of total tokens in a typical loop), but output tokens dominate dollar cost due to 5x higher per-token pricing.
  • Context accumulates across iterations: each retry is more expensive than the last because it reads all prior attempts. Improving first-attempt pass rate is the highest-leverage single cost optimisation.
  • Scheduled loops compound: Tomás's $0.64/run loop costs $552K/year at production volume.
  • Break-even against human baseline requires quality-adjusted comparison: loop CPVO plus human follow-up cost versus pure human cost per task.
  • Model-tiered fleets (cheap lead, expensive specialists) reduce coordination cost by 4-19x without sacrificing output quality.
  • Cost models require monthly recalibration; pricing, consumption, and pass rates all drift with environmental changes.
  • The most common way loops die is not technical failure — it is economics that close at pilot volume but not at production volume.
  • CPVO creep (3-5% per month) compounds silently; automated alerts when 30-day CPVO exceeds 90-day baseline by 15% catch drift early.

The Loop Contract, So Far

This chapter fills the budget field of the Loop Contract. A budget is not merely max_iterations and max_tokens — it is an economic envelope derived from the CPVO threshold at which the loop ceases to justify its existence. The budget field now specifies: "this loop may spend up to $X per verified outcome, operating at Y cadence, within a monthly ceiling of $Z, evaluated against a human-baseline cost of $W per equivalent output." The budget field, combined with Chapter 24's escalation path field, creates a complete economic governance framework: when cost exceeds threshold, the loop either escalates architecturally (fleet) or escalates organisationally (human).
