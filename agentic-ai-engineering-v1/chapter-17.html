Chapter 17: Execution and State — Worktrees, Sandboxes, Checkpoints

State is where loops live. Corrupt the state, and the loop is indistinguishable from one that never ran.

The Corrupted Workspace

Deepa Krishnamurthy's platform team at an e-commerce company ran a fleet of three agents in parallel to accelerate their quarterly dependency upgrade. Each agent handled a different subsystem: payments, inventory, and notifications. All three operated in the same repository checkout because "they edit different directories — they won't collide." This assumption held for the first twelve minutes.

Agent A, handling payments, needed to update a shared utility in lib/http_client.py to support the new version of their HTTP library. Agent B, handling inventory, needed the same utility updated but with a different configuration — a longer timeout for their warehouse API's slower responses. Agent A wrote its version first. Agent B, two seconds later, wrote its version. Agent B's write overwrote Agent A's changes completely without knowing they existed. Agent A's subsequent test run failed because the HTTP client no longer had the connection-pooling configuration it had just added. Agent A "fixed" this by re-writing the file with its configuration. Agent B's tests then failed because the timeout was gone. The cycle repeated four times before the budget ceiling terminated both agents.

The aftermath: three hours of wall-clock time, 2.8 million tokens consumed [ESTIMATE: three agents averaging roughly 200K tokens per iteration over four to five iterations each, at Sonnet pricing approximately $8-12 total], and a workspace in a state that could not be committed. Half the files reflected Agent A's assumptions and half reflected Agent B's. The lib/http_client.py file contained Agent B's last write, which was incompatible with Agent A's completed work in src/payments/. Deepa spent forty minutes manually resolving the mess, ultimately reverting everything and starting over with sequential execution — which completed successfully in twenty-two minutes with no conflicts.

The lesson is not that parallel execution is wrong. Parallel execution, done correctly, is a legitimate and powerful strategy for independent workstreams (Chapter 24, From Loop to Fleet and Chapter 25, Topologies, Shared State, and Coordination). The lesson is that parallel execution without isolation is a concurrency bug waiting for the right moment to manifest. It is the distributed-systems equivalent of writing to a shared variable from two threads without a lock. The outcome is nondeterministic, unreproducible, and guaranteed to be wrong in ways that are expensive to diagnose.

Isolation mechanisms — worktrees, sandboxes, checkpoints — are not optional conveniences for sophisticated teams. They are the infrastructure that makes execution safe (mistakes are contained), resumable (progress survives interruption), and composable (parallel workstreams combine correctly). This chapter provides the concrete mechanics.

Worktrees: Isolation for Code Loops

The most common isolation mechanism for code-modifying loops is the git worktree: a second checkout of the same repository on a separate branch in a separate directory. Each agent (or each attempt by a single agent) works in its own worktree, modifying files freely without affecting the main workspace or other agents' work.

A worktree provides three guarantees. First, write isolation: nothing an agent does in its worktree is visible to any other worktree or to the main checkout until an explicit merge. Agent A's changes to lib/http_client.py exist only in Agent A's worktree directory. Agent B's changes exist only in Agent B's worktree directory. Neither can corrupt the other's state. Second, trivial rollback: discarding a failed attempt means deleting the worktree directory and its branch — a sub-second operation regardless of how many files were modified, requiring no manual cleanup or conflict resolution. Third, safe parallelism: multiple worktrees coexist simultaneously on different branches, each with its own complete file state, with no possibility of write conflicts between them because they occupy different filesystem paths.

The worktree lifecycle follows a four-phase pattern: create, work, verify, merge-or-discard.


"""loopkit/runner.py — extension: worktree lifecycle management."""
from __future__ import annotations

import subprocess
import logging
from dataclasses import dataclass
from pathlib import Path

logger = logging.getLogger(__name__)


@dataclass
class Worktree:
    repo_root: Path
    worktree_path: Path
    branch_name: str

    @classmethod
    def create(cls, repo_root: Path, name: str, base_ref: str = "HEAD") -> "Worktree":
        """Create an isolated worktree branching from base_ref."""
        branch = f"loop/{name}"
        wt_path = repo_root / ".loop-worktrees" / name
        subprocess.run(
            ["git", "worktree", "add", "-b", branch, str(wt_path), base_ref],
            cwd=repo_root, check=True, capture_output=True,
        )
        logger.info("Created worktree at %s on branch %s", wt_path, branch)
        return cls(repo_root=repo_root, worktree_path=wt_path, branch_name=branch)

    def discard(self) -> None:
        """Remove the worktree and delete its branch — total rollback."""
        subprocess.run(
            ["git", "worktree", "remove", "--force", str(self.worktree_path)],
            cwd=self.repo_root, check=True, capture_output=True,
        )
        subprocess.run(
            ["git", "branch", "-D", self.branch_name],
            cwd=self.repo_root, check=True, capture_output=True,
        )
        logger.info("Discarded worktree %s", self.worktree_path)

    def merge_to(self, target_ref: str = "main") -> None:
        """Merge verified work back to target and clean up."""
        subprocess.run(
            ["git", "checkout", target_ref],
            cwd=self.repo_root, check=True, capture_output=True,
        )
        subprocess.run(
            ["git", "merge", "--no-ff", self.branch_name,
             "-m", f"Merge verified loop result: {self.branch_name}"],
            cwd=self.repo_root, check=True, capture_output=True,
        )
        self.discard()
        logger.info("Merged %s into %s", self.branch_name, target_ref)

The cost of worktrees is real but bounded. Each worktree is a full checkout of the working tree — for a repository with 50,000 files, that is 50,000 files on disk, though git shares the object store so only the working-tree files are duplicated, not the full repository history. Setup time is typically 200-500ms for medium-sized repositories on SSD storage [ESTIMATE: based on author's measurements across repositories ranging from 5,000 to 50,000 files]. For a fleet of five agents, you need five worktree checkouts consuming approximately five times the working-tree disk space. This is rarely a problem for modern development machines or CI runners with adequate storage, but it can surprise teams working with very large monorepos where the working tree itself is multiple gigabytes. The worktree lifecycle — create before the agent starts, clean up after the agent finishes or fails — must be managed by the orchestrator, not left to the agents themselves.

The decision of when to use worktrees versus working directly follows a simple rule: use worktrees when agents would collide (modifying overlapping files), when you need trivial rollback (experimenting with approaches that may fail), or when multiple attempts should run in parallel (trying three strategies simultaneously and keeping the best). For a single agent working sequentially on files it owns exclusively — the common case for simple bug fixes — the overhead is not justified. Work directly, use git stash or git reset for rollback, and save the worktree machinery for cases that genuinely need isolation.

Sandboxes: Containment for Execution

Worktrees isolate file-system state between agents. Sandboxes solve a different problem: they contain the damage that executing generated code can do. A loop that writes code and then runs it (to check whether tests pass, to execute a build, to run a data pipeline) must reckon with the possibility that the generated code misbehaves. It might consume unbounded CPU in an infinite loop. It might allocate memory until the system runs out. It might delete files it should not touch. It might make network calls to production systems. It might modify system configuration.

A sandbox constrains four resource axes: filesystem access (what paths can be read and written), network access (what endpoints can be reached), compute resources (CPU time limits, memory caps, process count limits), and system privileges (what syscalls are permitted, what devices are accessible). The appropriate level of constraint depends on the trust level of the code being executed and the consequences of misbehaviour.

For a loop running pytest on code the loop itself generated within a trusted repository: filesystem access should be limited to the repository and its dependencies, network access can be disabled or restricted to localhost, memory should be capped to prevent runaway allocations (512MB-2GB is typical for test suites), and a wall-clock timeout should kill the process if tests hang. These constraints catch accidental misbehaviour — an infinite recursion, a test that inadvertently hits a real API endpoint — without impeding legitimate test execution.

For a loop running user-submitted or internet-sourced code: the sandbox must be maximally restrictive. Read-only filesystem access (the code cannot write persistent state), no network access whatsoever, tight memory limits (256MB), a short CPU timeout (30 seconds), and process isolation that prevents the code from inspecting the host system. Container-based isolation (Docker with appropriate seccomp profiles, or Firecracker microVMs) provides the strongest boundary at the cost of 500ms-2s startup latency.

The engineering trade-off is containment strength versus startup latency and operational complexity. Process-based sandboxes (using ulimit, landlock on Linux, or sandbox-exec on macOS) start instantly and require no additional infrastructure, but provide weaker isolation — a determined adversary can escape them. Container-based sandboxes provide strong isolation but require a container runtime, pre-built images, and add measurable latency to every loop iteration. The choice depends on the threat model: if the code is agent-generated from trusted prompts, process-level restriction suffices. If the code could be adversarial, container isolation is necessary.

A practical middle ground for most loop systems: use a per-iteration timeout (wall-clock limit on the subprocess running tests or builds), a memory limit (set via cgroup or ulimit), and filesystem restriction to the working directory. These three constraints catch the vast majority of accidental misbehaviour from agent-generated code without requiring full container infrastructure. Reserve container isolation for loops that execute code from external sources or that run in multi-tenant environments where one user's loop must not affect another's.

Checkpoints: Resumability After Failure

A loop that crashes at iteration seven of ten should not restart from iteration one. The first six iterations produced verified progress — discoveries made, steps completed, files modified into a known-good state, budget consumed toward a successful outcome. Discarding that progress and re-running from scratch wastes budget on work already done and verified. In Tomás's migration loop from Chapter 16, this waste was caused by compaction destroying the plan. In the general case, any interruption — process crash, timeout, infrastructure failure, manual kill — destroys in-progress state unless that state is explicitly persisted outside the process.

Checkpointing is the mechanism: save the loop's state to durable storage at regular intervals so that a crashed, timed-out, or interrupted loop can resume from the last good state. The cost of checkpointing (a file write and a few hash computations per iteration) is negligible compared to the cost of re-running verified iterations after a failure.

A checkpoint captures five elements of loop state at a specific point in time:


"""loopkit/runner.py — extension: checkpoint save/restore."""
from __future__ import annotations

import hashlib
import json
import time
from dataclasses import dataclass, asdict
from pathlib import Path


@dataclass
class Checkpoint:
    iteration: int
    plan_version: int
    completed_steps: list[str]
    modified_files: dict[str, str]  # relative path -> SHA-256 prefix
    tokens_spent: int
    usd_spent: float
    wall_clock_spent_s: float
    last_score: float | None
    timestamp: float

    def save(self, path: Path) -> None:
        tmp = path.with_suffix(".tmp")
        tmp.write_text(json.dumps(asdict(self), indent=2))
        tmp.rename(path)  # atomic on POSIX

    @classmethod
    def load(cls, path: Path) -> "Checkpoint":
        return cls(**json.loads(path.read_text()))

    def is_valid(self, workspace: Path) -> bool:
        """Verify workspace state matches this checkpoint."""
        for rel_path, expected_hash in self.modified_files.items():
            full_path = workspace / rel_path
            if not full_path.exists():
                return False
            actual = hashlib.sha256(full_path.read_bytes()).hexdigest()[:16]
            if actual != expected_hash:
                return False
        return True

The checkpoint is saved with an atomic write (write to temp, then rename) to prevent corruption if the process is killed mid-write. A partially-written checkpoint file is worse than no checkpoint file because it may contain inconsistent state that causes the resumed loop to make incorrect assumptions about the workspace. The atomic write ensures the checkpoint file is always either the previous valid version or the new valid version, never a partial state.

When to checkpoint: after every iteration that advances the plan (a step marked complete, a score improvement, a new discovery that changes the approach). Checkpointing after every iteration regardless of progress is wasteful if iterations are cheap, but it ensures maximum resumability. Checkpointing only at major milestones saves I/O but risks losing more work on interruption. The recommended default is: checkpoint whenever the loop has done work it would not want to redo. If the iteration produced no lasting value (a failed attempt that will be retried with a different approach), skipping the checkpoint is fine because resuming from the previous checkpoint produces the same outcome as resuming from after the failed attempt.

The resume sequence is: look for a checkpoint file at the expected path. If one exists and is valid (workspace state matches the recorded file hashes), restore state from the checkpoint: set the iteration counter, load the plan version, mark completed steps, and subtract spent budget from the ceiling. If the checkpoint exists but is invalid (files have changed since the checkpoint was written — perhaps a human made manual edits during the loop's downtime), log a warning and start fresh. Attempting to resume from a stale checkpoint produces worse outcomes than restarting because the loop's assumptions about file state no longer hold.

The Shared-Filesystem Coordination Model

In Anthropic's multiagent orchestration, specialists work in parallel on a shared filesystem and contribute to the lead agent's context through persistent events [VERIFIED: Anthropic, "New in Claude Managed Agents"]. Every step is traceable in the console, and events persist so the lead can check back mid-workflow. This model is powerful but requires coordination discipline to prevent the collision scenario from this chapter's opening.

The coordination model has three layers. First, workspace partitioning: assign each specialist a set of paths it owns. Agent A owns src/payments/. Agent B owns src/inventory/. The shared file lib/http_client.py is owned by neither, or designated to a specific agent with others submitting change requests. Enforcement can be soft (prompt instruction: "only modify files in your assigned directory") or hard (filesystem permissions that make other directories read-only for the agent's process).

Second, shared-file protocol: for files that genuinely need modification by multiple agents (configuration files, shared libraries, lock files), designate one agent as the owner and have others communicate needs through the event log rather than writing directly. Agent B needs a longer timeout in the HTTP client? It posts an event: "Request: http_client timeout for warehouse API should be 30s." Agent A (the owner) incorporates the request when it next touches the file, resolving any conflict with its own connection-pooling needs.

Third, merge-time verification: when parallel workstreams combine (worktrees merging to main, or sequential integration of partition results), run the full oracle suite against the merged state. Tests that pass in isolation may fail when combined — Agent A's code calls http_client.pool_size which Agent B's version removed. Integration failures are detectable only at merge time, so merge-time verification is non-optional for parallel work.

Rollback Strategies

When verification fails, the loop must return to a known-good state. The mechanism depends on what was modified and how it was isolated.

For code in a worktree: discard the worktree. This is instantaneous and total — every file modification, every new file, every deletion is undone in a single operation. This is the primary operational advantage of worktrees: rollback costs nothing regardless of the scope of changes.

For code in the main workspace without a worktree: git provides graduated rollback. git reset --hard to the last checkpoint commit undoes everything since that commit. git checkout main -- path/to/file restores a single file from the known-good state. git stash preserves changes for later inspection while restoring the workspace to clean. The common pattern is checkpoint commits: after each verified iteration, commit with a message like [loop] checkpoint: iteration 4, steps 1-3 verified. Rollback means git reset --hard to the appropriate checkpoint commit. These commits can be squashed or rewritten before the loop's work is shared externally.

For non-git state (database changes, API calls, deployed artifacts): rollback requires explicit compensation logic. A migration that ran CREATE TABLE must run DROP TABLE on rollback. A deployment that pushed a new container image must redeploy the previous image. A Slack message that was posted cannot be unsent. This last category — irreversible side effects — is why loops with side effects must verify before acting on the world, not after. The principle from Chapter 3 applies: execution that changes the world irreversibly requires an approval gate before the execute step, not just verification after.

The irreversibility spectrum determines the appropriate isolation strategy. File modifications are fully reversible (git reset). Database schema changes are partially reversible (can be rolled back if migrations are designed to support down operations, but data loss may occur). API calls with external side effects (sending emails, posting to Slack, creating Jira tickets) are irreversible once executed. HTTP POST to a payment processor is irreversible in a legally meaningful sense. The further along this spectrum a loop's execution reaches, the more verification must precede action rather than follow it. A useful heuristic: if you cannot undo it programmatically within your loop's error handler, gate it behind an oracle check before execution.

State Management: The Transactional Pattern

For loops that modify multiple files or multiple systems within a single iteration, the transactional pattern provides atomicity: either all changes from an iteration are committed together, or none of them are. This prevents the intermediate state where three of five files have been modified when the loop crashes, leaving the workspace in a state that is neither the starting state nor the intended end state.

The implementation uses a write-ahead log: before each modification, record the file path, its original content hash, and the intended new content. If the iteration completes and verification passes, apply all changes and clear the log. If the iteration fails or the process crashes, the log allows the next startup to detect incomplete operations and roll them back to the pre-iteration state. This is the same principle that database engines use for crash recovery, applied to filesystem state.

For loops using worktrees, the transactional pattern is built in: the worktree is the transaction boundary. All changes within the worktree are provisional until merge. The merge is the commit. Discarding the worktree is the rollback. This is one reason worktrees are preferred over direct modification for any loop that makes multiple coordinated changes within an iteration.

Making Runs Resumable

A production loop should be designed so that any run can be interrupted at any point and resumed from the last checkpoint without loss of verified progress. This is the resume-first design pattern: the loop's startup sequence always checks for existing state before beginning fresh work.

The startup sequence is: (1) check for a checkpoint file at the known path; (2) if found, validate it against the current workspace state; (3) if valid, restore loop state from checkpoint and continue; (4) if invalid or missing, initialise fresh state and begin from iteration zero. This sequence adds negligible latency (one file read, a few hash computations) and makes the loop robust to the interruptions that production systems routinely experience: process OOM kills, infrastructure rolling restarts, network timeouts that cause the orchestrator to consider the agent dead, and manual cancellations when a human decides the loop is heading in the wrong direction.

The resume-first pattern also enables a useful operational pattern: intentional interruption for course correction. A human observing a loop that is heading toward a poor solution can kill it, modify the plan file (adding a constraint or removing a failed approach), and restart it. The loop resumes from its checkpoint with the human's modification incorporated. This is a lightweight human-in-the-loop intervention that does not require the human to wait for the loop to finish or to restart it from scratch.

Resume-first design also composes well with the trigger system (Chapter 14, Triggers and Automations). A scheduled trigger that fires daily can resume a long-running multi-day task from its checkpoint rather than restarting each day. The loop works for its budget allocation (say, 30 minutes per day), checkpoints its state, and is re-triggered the next day to continue. This pattern enables loops that work on large-scale tasks (repository-wide refactoring, comprehensive documentation generation, multi-hundred-file migrations) without requiring a single uninterrupted session long enough to complete the entire task.

What Breaks

The shared-filesystem coordination model breaks down at its enforcement boundary. A prompt instruction saying "only modify files in src/payments/" is advisory, not enforceable. If the agent's task requires modifying a shared utility to proceed, and the agent's goal says "make the tests pass," the agent will modify the shared utility because that is what makes the tests pass. The prompt boundary is softer than a filesystem permission boundary, and sophisticated tasks routinely require crossing boundaries that seemed clean at design time.

Filesystem-permission enforcement is harder but reduces capability: a read-only filesystem prevents the agent from making necessary modifications to shared code, even when those modifications are legitimate and correct. The fundamental tension is between isolation (safe, predictable, enables parallel work) and flexibility (capable, adapts to reality, solves cross-cutting problems). No single configuration resolves this tension universally; the right balance depends on how tightly coupled the agents' work actually is, which you may not know until they collide.

Checkpoints introduce their own failure mode: the space between the workspace state and the checkpoint state. If the loop modifies three files and then crashes before checkpointing, those modifications exist in the workspace but not in any checkpoint. On restart, the loop sees no checkpoint (or an older checkpoint) and may redo work, producing a second version of the already-modified files — potentially different from the first version, creating subtle inconsistencies. The fix is to checkpoint aggressively (after every modification) or to use worktrees where modifications do not touch the main workspace until verification passes. The worktree pattern eliminates the "partially-modified workspace" problem entirely because the main workspace never sees intermediate state.

Summary

  • Worktrees provide write isolation for parallel agents: each gets its own branch and directory with trivial rollback via deletion and safe merge after verification.
  • Sandboxes contain execution risk across four axes: filesystem, network, compute, and privilege. Constraint level matches the trust level of the executed code.
  • Checkpoints capture loop state (iteration, plan, file hashes, budget, score) for resumability. Atomic writes prevent checkpoint corruption.
  • The shared-filesystem coordination model partitions ownership and uses event logs for cross-partition communication. Merge-time verification catches integration failures.
  • Resume-first design: every loop starts by checking for a valid checkpoint. This makes loops robust to interruption and enables intentional course correction.
  • Rollback strategies vary by state type: worktree discard for code in isolation, git reset for code in the main workspace, compensation logic for irreversible side effects.

The Loop Contract, So Far

This chapter extends the budget field by showing how checkpoints make budget consumption cumulative across restarts rather than resetting on each restart attempt. It also informs the stop condition: a corrupted workspace or invalid checkpoint is itself a termination signal that should trigger escalation rather than silent retry, because the loop's assumptions about state no longer hold.
