Chapter 28: Cost Engineering

"The cheapest token is the one you never send."

The Thousand-Dollar Night

Kenji Watanabe runs a dependency-audit loop for a financial services firm. The loop runs nightly at 2 AM, scanning 340 internal packages across twelve microservices for known CVEs, checking licence compliance against the company's approved-licence list, and flagging outdated dependencies that have fallen more than two major versions behind. It works well: the security team trusts its nightly findings report and has eliminated two categories of manual checklist from their weekly process. The loop averages $85 per night — acceptable for a compliance-critical function.

One Thursday evening, the company's build platform team completes a migration that adds twelve new monorepo packages from an acquired startup. Each package has deep dependency trees averaging 180 transitive dependencies — a consequence of the startup's preference for small, single-purpose npm packages. The loop, designed to read each package-lock.json in its entirety and cross-reference every entry against their CVE database, suddenly has 2,160 additional dependency entries to process.

The system prompt and tool schemas are reloaded for every package-level analysis call. Kenji never added prompt caching because the original 340 packages completed in twenty-two minutes and the cost was acceptable. The CVE database lookup tool returns verbose JSON for each known vulnerability: CVE identifier, description, affected version ranges, CVSS score, reporter information, timeline, references, and workaround notes — averaging 800 tokens per entry when only the identifier, affected versions, and CVSS score are needed for the loop's decision logic. Transitive dependency resolution adds extra iterations per package when the model must trace chains through three or four levels of indirection to determine whether a vulnerable transitive dependency actually affects the top-level package.

The loop runs from 2:00 AM to 5:47 AM. It processes 352 packages (the original 340 plus the 12 new ones, but the new ones each require multiple calls for their deep trees). It makes 1,247 model calls. It consumes 4.2 million tokens. The Friday morning cost report shows $847 for a single night — precisely ten times the normal cost [ESTIMATE: assumes Sonnet pricing at $3/$15 per million input/output with a 65/35 input/output ratio on 4.2M total tokens]. Kenji has until Monday night before the automated schedule runs again and produces another $847 charge. He needs to cut cost by 80% without reducing coverage. This chapter provides the five engineering levers that make that reduction achievable.

The Five Levers: Overview

Cost engineering for agent loops addresses five independent sources of waste. Each lever targets a different mechanism, and their effects are largely additive — pulling all five simultaneously routinely achieves 60-80% total cost reduction without quality degradation [ESTIMATE: based on the arithmetic of combining individual lever savings, which individually range from 20-80% within their target category; the combined effect is less than the product because the categories overlap].

Prompt caching eliminates redundant processing of stable content across iterations. Batch processing amortises fixed overhead (system prompts, tool schemas) across multiple items in a single call. Model cascades ensure each step uses the cheapest model capable of handling it correctly. Context compression reduces the token count of variable content without losing decision-relevant information. Early termination stops loops that are not converging, saving the entire remaining budget for loops that would have exhausted it without passing.

Each lever is independent of the others and can be adopted incrementally. A team can start with caching alone (the simplest to implement) and add other levers as cost pressure demands.

Mapping each lever to the waste it removes shows why they compose rather than compete:

Note the target: every lever is judged against cost per verified outcome, not cost per call. A lever that halves token spend while doubling attempts-to-pass has achieved nothing.

Lever 1: Prompt Caching

When the same content appears at the beginning of consecutive model calls — the system prompt, tool schemas, skill definitions — prompt caching avoids re-processing those tokens on every call. The first call within a caching window processes the full prefix at standard input-token cost. Subsequent calls within the cache time-to-live (5 minutes for Anthropic's implementation as of early 2026 [VERIFIED: Anthropic documentation]) pay only 10% of the input cost for the cached portion.

The savings scale with two factors: the size of the stable prefix, and the number of calls made within the TTL window. For Kenji's loop, the system prompt is 12,000 tokens and the tool schemas add 8,000 tokens — a 20,000-token stable prefix. Over 1,247 calls (assuming calls are spaced closely enough to stay within the 5-minute TTL), without caching those 20,000 tokens are processed at full rate 1,247 times: 24,940,000 input-token equivalents. With caching, they are processed at full rate once and at 10% rate 1,246 times: 20,000 + (1,246 × 2,000) = 2,512,000 input-token equivalents. Savings: 22,428,000 tokens, or approximately 90% of the stable-prefix cost [ESTIMATE].

To maximise cache hits, structure every message with stable content first and variable content last. The system prompt, then tool schemas, then skill definitions, then conversation history (grows per iteration), then the current task. Any change to content before the variable section invalidates the cache for everything after it — so never intersperse variable data with stable definitions.

The TTL constraint matters for slow loops. If one iteration takes six minutes (waiting for a slow external tool, running a long test suite), the next iteration finds the cache expired and pays full price for the prefix again. For loops with slow steps, consider restructuring so the slow step executes asynchronously between model calls rather than within a model call — keeping the inter-call interval under five minutes to maintain cache validity.

Cache-aware architecture has a second, less obvious benefit: it encourages good prompt hygiene. To maximise cache hits, you must clearly separate stable content (which goes first) from variable content (which goes last). This separation is independently good engineering because it means the model encounters its instructions and constraints before the variable task context — improving instruction-following quality. Teams that adopt caching for cost reasons often discover their loop's overall output quality improves slightly, because the prompt restructuring required for cache compatibility also improved the prompt's cognitive ergonomics for the model.

Lever 2: Batch Processing

Kenji's loop processes each package independently, making a separate model call per package. Each call loads the full system prompt and tool schemas. Prompt-level batching groups multiple items into a single model call, paying the system-prompt cost once for the batch rather than once per item.

Without batching: 352 packages × (20,000 token prefix + per-package analysis) = 7,040,000 tokens of repeated prefix cost. With batches of 10: 36 calls × (20,000 token prefix + 10 × per-package data) = 720,000 tokens of prefix cost. Savings on prefix alone: 6,320,000 tokens [ESTIMATE]. Combined with prompt caching within the batch (the prefix is stable across the 36 calls), the savings compound further.

The tradeoff is quality versus cost. A model analysing ten packages simultaneously gives each package less attention than a model focused on one package alone — the same attention-dilution concern from Chapter 7. The design question: at what batch size does quality degrade below acceptable thresholds?

For Kenji's task — scanning lockfile entries against a CVE database, fundamentally a pattern-matching operation with limited reasoning requirements — batches of 10-15 packages maintain accuracy because the task does not require deep cross-item reasoning. Each package's analysis is independent of the others within the batch. For more reasoning-intensive tasks (code review where understanding relationships between functions matters), batch sizes of two to four preserve quality while still providing meaningful prefix amortisation.

Additionally, Anthropic's Batch API provides a 50% cost reduction for requests that can tolerate a 24-hour response window [VERIFIED: Anthropic documentation]. For Kenji's nightly audit — results needed by 9 AM but not within seconds — the Batch API is ideal. The combination of prompt-level batching (items per call) and API-level batching (50% discount) provides compound savings: 90% prefix reduction from caching, further amortisation from prompt-level batching, plus a flat 50% discount from the Batch API on remaining costs.

Lever 3: Model Cascades

Not every step in Kenji's loop requires the same model. Scanning a package and determining "no known CVEs affect this package" is a simple classification task: compare version numbers against a known-vulnerable-versions list. This requires no deep reasoning — Claude Haiku handles it correctly and costs $0.80 per million input tokens versus Sonnet's $3.00 [VERIFIED: Anthropic published pricing]. Only the complex cases — tracing transitive dependency chains to determine whether a vulnerable indirect dependency is actually reachable — require Sonnet's stronger reasoning.

The cascade design for Kenji's loop:

Stage 1 (Haiku): For each package, extract dependency list and compare against CVE database entries. If no matches: report "clean" immediately. If matches found: pass to Stage 2 with the specific matches identified. Expected result: 80% of packages have no CVE matches and terminate here [ESTIMATE: based on typical package vulnerability rates where most packages are current and unaffected].

Stage 2 (Sonnet): For packages with CVE matches, determine severity: is the affected version range actually included in this package's dependency tree? Is the vulnerability exploitable given this package's usage pattern? Produce a structured finding with severity rating.

Stage 3 (Opus, rare): For cases where transitive chains create non-obvious vulnerability paths across multiple packages, or where the licence analysis reveals a conflict requiring legal reasoning about licence compatibility — escalate to Opus for deep multi-factor analysis. Expected rate: 2-3% of packages [ESTIMATE].

The economic impact is dramatic. If 80% of packages use only Haiku ($0.80/M input), 18% use Sonnet ($3.00/M input), and 2% use Opus ($15.00/M input), the weighted average input cost is: (0.80 × $0.80) + (0.18 × $3.00) + (0.02 × $15.00) = $0.64 + $0.54 + $0.30 = $1.48 per million input tokens — roughly half of the all-Sonnet $3.00 rate [ESTIMATE]. The output-token savings are proportionally larger because Haiku's output rate ($4.00/M) versus Sonnet's ($15.00/M) is a 3.75x difference. For a loop where 80% of items terminate at the Haiku tier with minimal output, the weighted output cost drops to approximately $5.30/M versus the all-Sonnet $15.00/M — a 2.8x reduction [ESTIMATE].

The critical implementation detail: the validator that decides whether the cheap model's output is sufficient must be fast, cheap, and deterministic. If the validator itself requires a model call, the cascade adds cost rather than reducing it. For Kenji's use case, the Haiku-tier validator is a simple Python function: "does the response contain any CVE identifiers?" If no, the package is clean and no escalation needed. If yes, the structured CVE data must be analysed by Sonnet. This validator runs in microseconds and costs nothing — the cascade logic is pure code, not model inference.

The verified production example of this pattern is Spiral by Every, where a lead on Haiku manages routing while subagents on Opus handle generation [VERIFIED] (Anthropic, "New in Claude Managed Agents"). The lead-on-cheap-model pattern works because routing decisions — "which specialist handles this?" or "does this package have any CVEs?" — are precisely the kind of fast classification task where cheaper models match more expensive models' accuracy while costing a fraction as much.

Lever 4: Context Compression

Every token in context costs money. Context compression reduces the token count of the variable portions of the prompt without losing the information needed for correct decisions.

Tool result summarisation addresses the largest single cost category (27% of tokens per Chapter 27's analysis). Kenji's CVE lookup returns 800 tokens per vulnerability entry when only four fields matter: CVE ID, affected versions, CVSS score, and a one-line description. A programmatic post-processing step — not a model call, just code — that extracts these four fields reduces each entry to approximately 100 tokens: an 87% reduction per lookup [ESTIMATE]. Across 1,247 calls with an average of 3 lookups each, this saves roughly 2,617,500 tokens [ESTIMATE: 1,247 × 3 × (800-100) = 2,617,500].

Conversation history pruning removes old iterations from the context window, retaining only recent iterations and their feedback. By iteration five of a complex package analysis, the conversation carries iterations one through four in full: approximately 50,000 tokens of historical context that the model must read on every subsequent call. Pruning to the last two iterations reduces this to roughly 20,000 tokens — a 60% reduction in history cost [ESTIMATE]. The model loses access to iterations one through three's specific details, but the feedback from iteration four typically summarises what was learned from earlier iterations.

Selective file loading reads only the portions of files relevant to the current decision. Instead of loading an entire package-lock.json (which for a large monorepo package might span 15,000 tokens), a preprocessing step extracts only the dependency entries with known CVE matches (typically 200-500 tokens). Chapter 9's Tool Search feature applies the same principle to tool schemas: instead of loading all tool definitions upfront (which Anthropic measured at up to 134K tokens before optimisation [VERIFIED] (Anthropic, "Introducing advanced tool use")), Tool Search loads roughly 500 tokens of discovery metadata upfront and fetches only the 3-5 relevant tools (~3,000 tokens) when needed [VERIFIED].

Lever 5: Killing Non-Converging Loops

The most underused cost lever is early termination. A loop that has not improved its oracle score across three consecutive iterations is statistically unlikely to converge within its remaining budget — it is iterating without learning, consuming tokens without approaching a pass verdict.

Kenji's loop encounters this with complex transitive dependency chains. The model attempts to trace a chain, fails (the oracle rejects the incomplete analysis), tries again from a different starting point, fails again, then attempts a third variation that is no better than the first two. Without early termination, it would continue for all seven allowed iterations — consuming 175,000 tokens — before giving up and escalating. With a convergence guard that kills after three flat-or-declining iterations, it escalates at iteration three having consumed only 75,000 tokens [ESTIMATE: 25,000 tokens per iteration × 3 iterations versus × 7 iterations].

The convergence guard from Chapter 18 (The Stop Problem) applies directly:


from dataclasses import dataclass, field


@dataclass
class ConvergenceGuard:
    """Terminates loops that are not making measurable progress."""

    patience: int = 3
    min_improvement: float = 0.05
    scores: list[float] = field(default_factory=list)

    def record_score(self, score: float) -> None:
        self.scores.append(score)

    def should_terminate(self) -> bool:
        if len(self.scores) < self.patience:
            return False
        recent = self.scores[-self.patience:]
        # No meaningful improvement across the patience window
        if max(recent) - min(recent) < self.min_improvement:
            return True
        # Scores are monotonically declining
        if all(recent[i] >= recent[i + 1] for i in range(len(recent) - 1)):
            return True
        return False

For Kenji's loop, roughly 8% of packages trigger complex analysis paths that risk non-convergence. Killing stalled analyses at iteration three saves approximately 100,000 tokens per stalled package. Across 28 stalled packages per night (8% of 352), early termination saves 2,800,000 tokens — roughly $33 at Sonnet rates [ESTIMATE: (2,800,000 × 0.65 × $3 + 2,800,000 × 0.35 × $15) / 1,000,000 = $5.46 + $14.70 = $20.16 on a blended basis; the $33 figure assumes higher output-token ratio for complex analysis steps].

What happens after termination matters as much as the termination decision itself. Three strategies serve different needs: escalate (flag for human review — appropriate when the analysis is critical and human expertise can resolve what the model cannot), skip and log (mark the package as "not analysed: convergence failure" and continue — appropriate for low-severity items where incomplete coverage is acceptable), or escalate to a more capable model (retry with Opus using a fresh context — appropriate when the task is genuinely hard but solvable with more reasoning capability). The choice should be encoded in the loop's configuration, not decided at runtime by the model itself.

Latency Versus Cost

Cost optimisations and latency optimisations are correlated but not identical. Some techniques improve both: caching reduces reprocessing time (fewer tokens to process means faster responses) and compression reduces prompt size (shorter prompts yield lower first-token latency). Others trade latency for cost: cascading through cheap models first adds latency when the cheap model fails and must escalate (two calls instead of one), and API-level batching trades 24-hour latency for 50% cost reduction.

For Kenji's nightly audit, latency is irrelevant — finishing at 3:30 AM versus 4:45 AM makes no difference as long as results are ready by 9 AM. He should apply every lever aggressively, including the Batch API's 50% discount. For an interactive loop responding to a developer's question in real time, the calculus is different: use caching and compression (improve both cost and latency), avoid API-level batching (latency penalty unacceptable), and start with the model most likely to succeed on the first attempt even if it is more expensive (avoiding cascade retry latency).

The general principle: batch workloads can accept all latency penalties in exchange for cost savings. Interactive workloads should optimise for first-attempt success rate and use only latency-neutral cost techniques (caching, compression, Tool Search). The worst mistake is applying batch-workload optimisations to interactive loops: a developer waiting ten seconds for a code suggestion does not care that the cascade saved $0.03 by trying Haiku first and failing before escalating to Sonnet. The developer cares that the response took ten seconds instead of four. Cost engineering must respect the loop's latency contract alongside its budget contract.

Putting It Together: Kenji's Fix

Applying all five levers to Kenji's $847 night run [ESTIMATE: all savings are estimates based on the lever mechanics described above; combined savings assume partial overlap between lever effects]:

  1. Prompt caching: System prompt + tool schemas (20,000 tokens) cached across all 1,247 calls. Saves ~90% of stable-prefix processing: approximately 22.4M token-equivalents of redundant processing eliminated.
  2. Batch processing: Group into batches of 10, reducing call count from 1,247 to ~125. Further reduces prefix repetition. Use Batch API for 50% price reduction on all remaining costs.
  3. Model cascade: Haiku for 80% of packages (clean), Sonnet for 18% (simple CVE matching), Opus for 2% (complex chain analysis). Reduces weighted average model cost by approximately 50%.
  4. Context compression: Summarise CVE tool results (87% per-entry reduction), prune history to last 2 iterations (60% history reduction), selective lockfile loading. Reduces per-call token count by approximately 40%.
  5. Early termination: Kill stalled complex analyses at iteration 3 instead of 7. Saves approximately 2.8M tokens.

Combined estimated new cost: $95-130 per night [ESTIMATE: the levers' effects overlap and do not multiply cleanly; the dominant savings come from the Batch API's 50% flat discount, the cascade's 50% model-cost reduction, and compression's 40% per-call reduction]. Kenji's 80% reduction target is achievable without any change to the loop's core analysis logic or oracle.

What Breaks

Cost engineering introduces its own failure modes that teams must monitor. The most dangerous pattern is an optimisation that changes behaviour without anyone noticing the change.

Aggressive compression that removes information the model needed. A loop previously reading entire files now reads only targeted sections. If the section-selection heuristic misses a relevant code region — perhaps a function defined 200 lines above the flagged vulnerability that establishes the context needed to assess severity — the loop's analysis quality degrades. But the degradation is silent: the oracle still passes (the finding is structurally correct, just missing severity context), and cost metrics improve (fewer tokens consumed). The quality loss surfaces only when a human reviews the output months later and notices that severity assessments have become less nuanced.

Overly aggressive cascading. The cheaper model "passes" the validator because the validator checks structural correctness (valid JSON, required fields present) rather than analytical depth. The finding technically validates but is shallow — missing the transitive dependency path that a more expensive model would have identified. The cascade saves money by terminating at the cheap tier while the expensive tier would have produced a more complete analysis.

The mitigation for both failure modes is the same: treat every cost optimisation as a change that requires regression testing. Run the optimised loop against the same fifty inputs as the unoptimised loop. Compare oracle scores, finding completeness (human-evaluated on a sample), and pass rate. If any quality metric degrades by more than 2 percentage points, the optimisation is too aggressive. The principle: optimise cost until quality moves, then back off one step. Maintain a "cost regression test suite" — a set of inputs where you know the correct output quality level — and run it automatically when cost-optimization parameters change. This is the cost-engineering equivalent of a unit test suite for correctness, and it catches degradation before it reaches production.

Summary

  • Five independent levers reduce loop cost: prompt caching (stable content across calls), batch processing (amortise overhead across items), model cascades (cheapest sufficient model per step), context compression (fewer tokens per call), and early termination (stop non-converging loops).
  • Prompt caching saves up to 90% on stable prefixes when iterations stay within the 5-minute TTL.
  • The Batch API provides 50% cost reduction for non-interactive workloads tolerating 24-hour response windows.
  • Model cascades allocate cost to capability: Haiku for classification/routing, Sonnet for standard analysis, Opus for deep reasoning. Spiral's Haiku-lead / Opus-specialist design is the verified production exemplar.
  • Tool Search reduces tool-schema overhead from 55K+ tokens to roughly 3.5K tokens by loading only relevant tools on demand.
  • Every cost optimisation must be regression-tested against the unoptimised baseline; silent quality degradation is the primary risk of aggressive cost engineering.
  • Combined lever application routinely achieves 60-80% cost reduction without quality loss.
