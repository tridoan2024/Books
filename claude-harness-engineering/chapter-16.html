Chapter 16: Hook System — Intercept and Transform

"Hooks are the points where your code runs inside the harness. Without them, you observe the agent. With them, you govern it."

16.1 Hook Events

The harness fires hooks at eight distinct points in the control loop. Each event represents a moment where external logic can observe, intercept, or modify what the harness does next. Understanding which event fires when — and what data it carries — is the prerequisite for everything else in this chapter.

sequenceDiagram
    participant U as User
    participant H as Harness
    participant M as Claude API
    participant T as Tool Executor
    participant HK as Hook Runner

    U->>H: launch session
    H->>HK: SessionStart
    HK-->>H: stdout context message
    H->>M: first API call
    M-->>H: tool_use block
    H->>HK: PreToolUse (tool_name, tool_input)
    HK-->>H: permissionDecision / updatedInput / defer
    H->>T: execute tool
    T-->>H: result
    H->>HK: PostToolUse (tool_name, tool_input, tool_response)
    HK-->>H: exit 0/1/2
    M-->>H: text-only response (Stop)
    H->>HK: Stop
    H->>HK: PreCompact (before context window summary)
    H->>U: final response

SessionStart

Fires once, immediately after the harness initializes. No tool calls have been made. The system prompt has not been assembled yet.

The stdout of a SessionStart hook is injected into the conversation as context before the first user message. This is the event for environment setup, state recovery, and context priming. Your hook can print a message that the model will read at the start of the session.

PreToolUse

Fires before every tool call, after the permission layer has run its initial evaluation but before execution. The hook receives the tool name and its full input via stdin as JSON.

This is the most powerful event. A PreToolUse hook can:

  • Allow or block the tool call
  • Rewrite the tool input before execution
  • Defer the decision to a later --resume session
  • Satisfy an AskUserQuestion by returning an updatedInput with a pre-filled answer

PostToolUse

Fires after every successful tool call, receiving the tool name, tool input, and the tool's response. The hook cannot modify the response after the fact — the result is already in the conversation history. Its purpose is observation, logging, and side effects (metrics, audit trails, format-on-save rewrites).

A PostToolUse hook firing on Write or Edit can trigger secondary operations — running a formatter, notifying a webhook, updating an index. As of v2.1.90, this event correctly fires for consecutive edits, fixing a regression where format-on-save hooks were skipped when two Edit calls occurred back-to-back.

PostToolUseFailure

Fires when a tool execution fails with an error. Receives the same data as PostToolUse plus the error details. Useful for failure telemetry, retry orchestration, and alerting pipelines that need to know when the agent hits a broken state.

Stop

Fires when the control loop terminates — the model has returned a text-only response with no remaining tool calls. The session is about to end. Use this event for cleanup, state persistence, sending a completion notification, or writing the final session summary.

PreCompact

Fires before the harness performs context window compaction — the process of summarizing a long conversation into a condensed version that fits within the model's context window. The hook's stdout is injected into the compaction summary as preservation instructions. This is the event for state survival across compaction boundaries.

TaskCreated

Fires when the TaskCreate tool creates a new background task (added in v2.1.84). Receives the task ID and initial parameters. Use this for task registry integrations, notification systems, or audit trails that track background work.

PermissionDenied

Fires when the permission layer denies a tool call. Receives the tool name and the denied input. The hook can return {"retry": true} to instruct the harness to present the call to the model as retriable after the hook's logic has run — the mechanism for building human-in-the-loop approval workflows. As discussed in Chapter 4, this is the programmatic equivalent of the /permissions Recent tab's r key.

16.2 Configuration

Hooks are defined in the hooks key of any settings file (global ~/.claude/settings.json, project .claude/settings.json, or managed settings). The structure is a map from event name to an array of matcher objects, each of which contains an array of hook commands.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python3 ./.claude/hooks/bash-validator.py",
            "timeout": 5000,
            "statusMessage": "Validating command..."
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "./.claude/hooks/format-on-save.sh",
            "timeout": 10000,
            "statusMessage": "Formatting saved file..."
          }
        ]
      }
    ]
  }
}

Fields

matcher — A string matched against the tool name. An empty string ("") matches all tools. The matcher is not a glob — it is either an exact tool name, a pipe-separated list of exact names ("Write|Edit"), or empty for all. For MCP tools, the matcher uses the full tool identifier: mcp__servername__toolname.

hooks — An array of hook objects. Multiple hooks can run for the same event and matcher. They execute in order.

type — Currently only "command" is supported. Future hook types (HTTP endpoints, WebAssembly modules) are on the roadmap but not yet shipped.

command — The shell command to run. Executed via the user's default shell. The command runs in the project's working directory. Relative paths in the command are resolved from the project root.

timeout — Maximum milliseconds before the hook is killed. Defaults to 60000 (60 seconds). For hooks in the critical path (PreToolUse), keep timeouts tight — 5000ms is a reasonable upper bound for validation logic. For PostToolUse side effects, you may afford more.

statusMessage — A string shown to the user in the harness UI while the hook runs. This is the user-visible indicator that something is happening. Without it, hooks are invisible — the UI shows nothing while waiting. Set it for any hook that takes more than 100ms.

Multiple Hooks Per Event

When multiple hooks are registered for the same event and matcher, they run in definition order. For PreToolUse, the first hook that returns a blocking exit code (2) stops the chain — subsequent hooks do not run. For PostToolUse, all hooks run regardless of prior results.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "./.claude/hooks/security-check.py",
            "timeout": 5000
          },
          {
            "type": "command",
            "command": "./.claude/hooks/compliance-check.py",
            "timeout": 5000
          }
        ]
      }
    ]
  }
}

16.3 The if Condition

Every hook entry can carry an optional if field that gates whether the hook fires at all. The condition syntax uses the same permission rule DSL described in Chapter 4: tool name, optionally followed by a glob pattern in parentheses.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "if": "Bash(git *)",
        "hooks": [
          {
            "type": "command",
            "command": "./.claude/hooks/git-policy.sh"
          }
        ]
      }
    ]
  }
}

This hook only fires when the Bash tool is called with a command that starts with git. A hook for npm commands, pytest, or arbitrary shell scripts does not trigger it.

Condition Matching in Practice

The if field was added in v2.1.85 and extended in v2.1.89 to handle compound commands and environment variable prefixes. The matching behavior after v2.1.89:

  • Bash(git *) — matches git status, git commit -m "...", git push origin main
  • Bash(git *) — also matches GIT_AUTHOR_NAME="Tri" git commit (env-var prefix stripped before matching)
  • Bash(git *) — also matches cd /some/path && git push (compound command; the git subcommand matches)
  • Write(/src/**) — matches any Write call with an absolute path under /src/
  • Edit(*.py) — matches Edit calls where the file path ends in .py

File Path Matching

For file-touching tools (Read, Write, Edit, Glob), the if condition matches against the absolute file path, which the harness provides as of v2.1.89. This means you can write hook conditions that apply only to specific parts of the project tree:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "if": "Write(/Users/DOANTX26/Documents/2026/src/auth/**)",
        "hooks": [
          {
            "type": "command",
            "command": "python3 ./.claude/hooks/auth-change-alert.py",
            "statusMessage": "Auth module modified — notifying security review..."
          }
        ]
      }
    ]
  }
}

16.4 Exit Codes

The exit code your hook returns is the primary signal to the harness about what to do next. Three values matter:

Exit codeHarness behavior
0Pass-through. The hook ran, everything is fine. For PreToolUse, the tool call proceeds.
1Show stderr to the user, but do not block the tool call. Used for warnings, degraded behavior, hook internal errors. The tool still executes.
2Block the tool call. Stderr content is shown to Claude, not just the user — the model sees the reason for the block and can adjust. PreToolUse only.

Exit code 2 is the blocking signal. When a PreToolUse hook exits 2, the harness returns the hook's stderr to the model as the tool result, instead of executing the tool. The model reads the explanation and decides what to do next — it might try a different command, ask the user for help, or give up on that approach.

This behavior was fixed to work correctly in v2.1.90: previously, a PreToolUse hook that both emitted JSON to stdout and exited 2 might not correctly block the call. After the fix, the combination works as intended — the JSON controls input rewriting, and exit 2 still blocks execution.

Choosing Between Exit 1 and Exit 2

Exit 1 is for the hook's problems, not the agent's. If your hook fails to connect to a logging backend, returns garbage from a regex, or hits an unexpected error — exit 1. The user sees the warning, the tool runs anyway, and the agent is not disrupted.

Exit 2 is for the agent's problem. If the command is dangerous, violates policy, or needs to be rewritten before it runs — exit 2 with a clear explanation on stderr. The model reads that explanation.

# Correct exit code usage
try:
    issues = validate_command(command)
except ValidationError as exc:
    # Hook's problem — warn user, don't block
    print(f"Validator error: {exc}", file=sys.stderr)
    sys.exit(1)

if issues:
    # Agent's problem — block with explanation
    for issue in issues:
        print(f"• {issue}", file=sys.stderr)
    sys.exit(2)

sys.exit(0)

16.5 Hook I/O

Every hook receives a JSON payload on stdin. Depending on the event and what the hook needs to do, it writes JSON or text to stdout, and diagnostic output to stderr.

Stdin Payload

The stdin JSON always includes at minimum:

{
  "tool_name": "Bash",
  "tool_input": {
    "command": "rg --type py 'def main' src/",
    "description": "Find all main functions"
  },
  "session_id": "a1b2c3d4"
}

For file-touching tools as of v2.1.89, tool_input includes file_path as an absolute path:

{
  "tool_name": "Edit",
  "tool_input": {
    "file_path": "/Users/DOANTX26/Documents/2026/src/auth/session.py",
    "old_string": "SESSION_TIMEOUT_MINUTES = 5",
    "new_string": "SESSION_TIMEOUT_MINUTES = 30"
  }
}

For PostToolUse, the payload also includes tool_response — the full text output the tool returned.

Reading stdin in Python:

import json
import sys

data = json.load(sys.stdin)
tool_name = data.get("tool_name", "")
tool_input = data.get("tool_input", {})

Stdout Response — PreToolUse

A PreToolUse hook's stdout is interpreted as a JSON object that can carry three optional fields:

{
  "permissionDecision": "allow" | "deny" | "defer",
  "updatedInput": { ... },
  "userFacingMessage": "Rewrote grep to rg for performance"
}

permissionDecision — Override the permission system's decision. "allow" grants the call without further permission checks. "deny" blocks it. "defer" pauses the call for later resolution (see section 16.6). If omitted, the exit code governs the outcome.

updatedInput — A replacement for the tool's input. The harness substitutes this for the original input before executing the tool. This is the mechanism for command rewriting — transforming grep to rg, rewriting a dangerous glob to a safer form, or injecting required flags. The field must match the tool's input schema exactly.

userFacingMessage — A message shown to the user (not the model) when the hook rewrites the input. Useful for transparency: the user sees "Rewrote grep to rg" in the status bar rather than a mysterious command substitution.

Stdout Response — AskUserQuestion

When Claude calls AskUserQuestion, a PreToolUse hook can satisfy the question automatically — useful for headless sessions where there is no interactive user. The hook returns:

{
  "updatedInput": {
    "question": "Which branch should I target?",
    "answer": "main"
  },
  "permissionDecision": "allow"
}

This was added in v2.1.85. The hook provides the answer, the model receives it as if the user had typed it, and the session continues without blocking.

Large Output Handling

If a hook's stdout exceeds 50,000 characters, the harness saves it to a temporary file and passes the file path plus a preview to the model instead. This prevents oversized hook outputs from consuming context. As of v2.1.89, the harness provides the file path alongside the preview so the model can read the full output if needed. Size your hook outputs accordingly — for large audit payloads, write to your own file and return only a summary on stdout.

16.6 The Defer Decision

The "defer" permission decision is a mechanism for headless sessions. When a PreToolUse hook returns permissionDecision: "defer", the harness pauses at that tool call and does not execute it. The session is serialized to disk in a waiting state. It can be resumed later with:

claude --resume <session-id>

When resumed, the harness fires the PreToolUse hook again. If the hook now returns "allow", the call executes. If it returns "deny", the call is rejected. If it returns "defer" again, the session waits once more.

Use Case: Asynchronous Approval Workflows

The defer mechanism enables a class of approval workflows that the synchronous PermissionDenied hook cannot cover — situations where the approver is offline, in a different time zone, or needs to review in a web UI before responding.

sequenceDiagram
    participant A as Agent (headless)
    participant H as Harness
    participant Q as Approval Queue
    participant R as Reviewer

    A->>H: PreToolUse: kubectl apply -f deploy.yaml
    H->>H: fire PreToolUse hook
    H->>Q: enqueue(session_id, tool_input)
    H-->>A: permissionDecision: "defer"
    Note over A,H: Session paused on disk

    R->>Q: review and approve
    Q->>Q: record decision
    R->>H: claude --resume session_id
    H->>H: fire PreToolUse hook again
    H->>Q: check decision
    Q-->>H: approved
    H-->>A: permissionDecision: "allow"
    A->>A: execute kubectl apply

The implementation of the hook's defer logic:

#!/usr/bin/env python3
"""
PreToolUse hook: defer kubectl apply commands to an approval queue.
"""
from __future__ import annotations

import json
import sys
from pathlib import Path

APPROVAL_DB = Path("/var/lib/claude-approvals/queue.json")


def check_approval(session_id: str, command: str) -> str | None:
    """Return 'approved', 'denied', or None if not yet decided."""
    if not APPROVAL_DB.exists():
        return None
    records = json.loads(APPROVAL_DB.read_text())
    return records.get(f"{session_id}:{command}")


def enqueue(session_id: str, command: str) -> None:
    APPROVAL_DB.parent.mkdir(parents=True, exist_ok=True)
    records = json.loads(APPROVAL_DB.read_text()) if APPROVAL_DB.exists() else {}
    key = f"{session_id}:{command}"
    if key not in records:
        records[key] = "pending"
        APPROVAL_DB.write_text(json.dumps(records, indent=2))


def main() -> None:
    data = json.load(sys.stdin)
    tool_name = data.get("tool_name", "")
    tool_input = data.get("tool_input", {})
    session_id = data.get("session_id", "unknown")

    if tool_name != "Bash":
        sys.exit(0)

    command = tool_input.get("command", "")
    if "kubectl apply" not in command:
        sys.exit(0)

    decision = check_approval(session_id, command)

    if decision == "approved":
        print(json.dumps({"permissionDecision": "allow"}))
        sys.exit(0)

    if decision == "denied":
        print("Deployment denied by reviewer.", file=sys.stderr)
        sys.exit(2)

    # Not yet decided — enqueue and defer
    enqueue(session_id, command)
    print(
        json.dumps({
            "permissionDecision": "defer",
            "userFacingMessage": f"Deployment queued for review. Resume with: claude --resume {session_id}"
        })
    )
    sys.exit(0)


if __name__ == "__main__":
    main()

16.7 PreCompact Hook — Surviving Context Compaction

Context compaction is the process the harness uses to handle long sessions. When the conversation history approaches the model's context limit, the harness produces a compressed summary and continues with that summary as the new conversation baseline. Information not captured in the summary is lost.

For sessions doing complex work — a multi-hour refactor, a long debugging investigation, a book-writing session with accumulated context — compaction without care discards load-bearing state. The PreCompact hook is the mechanism for injecting preservation instructions into the summary.

How It Works

Before compacting, the harness fires the PreCompact hook. The hook's stdout is injected into the compaction prompt as additional instructions. The model, when producing the summary, sees these instructions and treats them as directives about what to preserve verbatim.

The hook receives any currently-available session data on stdin. Its stdout should be a clear, imperative message about what must survive the compaction:

#!/usr/bin/env bash
set -euo pipefail

STATE_DIR="${HOME}/.claude/projects/-Users-DOANTX26-Documents-2026/state"
MAX_STATE_CHARS=4000

# Find most recently modified state file
LATEST_FILE=""
LATEST_MTIME=0

for state_file in "${STATE_DIR}"/*-state.md; do
    [[ -f "${state_file}" ]] || continue
    FILE_MTIME=$(stat -f '%m' "${state_file}" 2>/dev/null || echo "0")
    if [[ "${FILE_MTIME}" -gt "${LATEST_MTIME}" ]]; then
        LATEST_MTIME="${FILE_MTIME}"
        LATEST_FILE="${state_file}"
    fi
done

if [[ -z "${LATEST_FILE}" ]]; then
    # No state file — nothing to preserve
    exit 0
fi

STATE_CONTENT=$(head -c "${MAX_STATE_CHARS}" "${LATEST_FILE}" 2>/dev/null || true)
DOMAIN=$(grep "^domain:" "${LATEST_FILE}" | head -1 | sed 's/^domain: *//')

cat << EOF
CRITICAL — Preserve the following ${DOMAIN} session state verbatim in your summary:

${STATE_CONTENT}

After compaction:
1. Read the state file at ${LATEST_FILE}
2. Verify state freshness before acting
3. Resume from recovered state — do NOT re-investigate
EOF

exit 0

Register it in project settings with a short timeout — the hook must complete before compaction proceeds:

{
  "hooks": {
    "PreCompact": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "./.claude/hooks/pre-compact-checkpoint.sh",
            "timeout": 5000,
            "statusMessage": "Preserving session state..."
          }
        ]
      }
    ]
  }
}

What to Preserve

The PreCompact hook is most valuable when the session has accumulated state that cannot be reconstructed from the codebase alone:

  • Active task lists with completion status
  • Decisions made mid-session ("we decided to skip auth module refactoring")
  • File locations discovered during investigation
  • Partial results from long-running analyses
  • Domain-specific context that took multiple turns to establish

Do not try to preserve everything — the injection has a character limit and the model will truncate or hallucinate if overloaded. Preserve decision points and non-obvious state. Reconstructible facts (file contents, git log, grep results) do not need to survive compaction — the model can retrieve them again.

16.8 SessionStart Hook — Environment Setup and State Recovery

The SessionStart hook fires once at harness launch, before system prompt assembly, before MCP connections, before the first user message. Its stdout is injected into the conversation as the first message the model reads.

This makes it the right place for two things: environment setup (setting env vars, ensuring tools are available) and state recovery (finding the last session's state file and telling the model to read it before starting new work).

Production SessionStart Hook

#!/usr/bin/env bash
set -euo pipefail

# Environment setup — make project tooling available
export PYTHONDONTWRITEBYTECODE=1
export PYTHONUNBUFFERED=1
export PATH="${PATH}:./node_modules/.bin:./venv/bin"

# Verify key tools are present
for tool in python3 rg git; do
    if ! command -v "${tool}" >/dev/null 2>&1; then
        printf "WARNING: %s not found in PATH. Some agent operations may fail.\n" "${tool}"
    fi
done

# Find most recent state file and emit a recovery reminder
STATE_DIR="${HOME}/.claude/projects/-Users-user-Documents-project/state"
LATEST_STATE=""
LATEST_MTIME=0

for state_file in "${STATE_DIR}"/*-state.md; do
    [[ -f "${state_file}" ]] || continue
    FILE_MTIME=$(stat -f '%m' "${state_file}" 2>/dev/null || echo "0")
    if [[ "${FILE_MTIME}" -gt "${LATEST_MTIME}" ]]; then
        LATEST_MTIME="${FILE_MTIME}"
        LATEST_STATE="${state_file}"
    fi
done

if [[ -n "${LATEST_STATE}" ]]; then
    printf "Previous session state found at %s — read it before starting new work." \
        "${LATEST_STATE}"
fi

exit 0

What Makes a Good SessionStart Hook

The hook's stdout becomes the first line of context the model reads. Write it as a direct instruction, not as a log entry for humans:

  • Good: "Previous session state found at /path/to/state.md — read it before starting new work."
  • Bad: "[INFO] 2026-07-28 14:32:11 Session initialized. State file detected."

The model responds to imperative instructions. A log-formatted message may be ignored as ambient noise. A direct instruction is treated as a directive.

Keep the hook fast. SessionStart blocks the session from starting. If your hook takes 10 seconds to complete, users wait 10 seconds before the harness becomes responsive. Cache expensive lookups (API calls, database queries) outside the hook and read from the cache instead.

SessionStart vs CLAUDE.md

There is a meaningful distinction between what belongs in SessionStart and what belongs in CLAUDE.md:

  • CLAUDE.md — Static instructions that apply to every session in this project. Coding standards, tool preferences, project architecture, rules the model should always follow. These are baked into the system prompt.
  • SessionStart hook — Dynamic state that changes between sessions. The location of the last state file, whether a particular service is running, environment-specific warnings. These are injected as conversation context, not system prompt.

Put static rules in CLAUDE.md. Put dynamic recovery information in SessionStart.

16.9 Real Example: bash_command_validator_example.py

This is a production PreToolUse hook that combines two behaviors: blocking dangerous patterns with an explanatory message, and rewriting deprecated commands to their preferred equivalents before they execute.

#!/usr/bin/env python3
"""
PreToolUse hook: validate and rewrite Bash commands.

Behaviors:
  1. Rewrites grep/find to rg/rg-files (faster, respects .gitignore)
  2. Blocks known-dangerous patterns with an explanation for the model

Exit codes:
  0 — command is fine, run it as-is
  2 — command blocked; stderr is shown to the model
"""
from __future__ import annotations

import json
import re
import sys


# Patterns that trigger a rewrite. Each entry: (pattern, replacement_fn, user_message)
_REWRITE_RULES: list[tuple[str, str, str]] = [
    # grep without pipe → rg
    (r"^grep\b(?!.*\|)", "rg", "Rewrote grep → rg (faster, .gitignore-aware)"),
    # find -name → rg --files
    (
        r"^find\s+\S+\s+-name\b",
        None,  # Complex rewrite, handled in code
        "Rewrote find -name → rg --files",
    ),
]

# Patterns that block the command outright. Each entry: (pattern, explanation)
_BLOCK_RULES: list[tuple[str, str]] = [
    (
        r"\brm\s+-rf\s+/\b",
        "Refusing to run 'rm -rf /' — this would destroy the root filesystem.",
    ),
    (
        r"\bcurl\b.*\|\s*(bash|sh)\b",
        "Refusing to pipe curl output to a shell. Download the script first, inspect it, then run it.",
    ),
    (
        r"\bchmod\s+777\b",
        "Refusing chmod 777. Use the minimum permissions required (644 for files, 755 for directories).",
    ),
    (
        r"\bsudo\s+rm\b.*-rf",
        "Refusing elevated recursive delete. Be specific about what to remove.",
    ),
    (
        r">\s*/etc/",
        "Refusing to write to /etc/. System file modification requires explicit human approval.",
    ),
]


def rewrite_grep(command: str) -> str:
    """Replace leading 'grep' with 'rg', preserving flags and arguments."""
    return re.sub(r"^grep\b", "rg", command)


def rewrite_find_name(command: str) -> str:
    """Transform 'find DIR -name PATTERN' to 'rg --files DIR -g PATTERN'."""
    match = re.match(r"find\s+(\S+)\s+-name\s+(\S+)(.*)", command)
    if not match:
        return command
    directory, pattern, rest = match.groups()
    # Strip surrounding quotes from pattern
    pattern = pattern.strip("'\"")
    return f"rg --files {directory} -g '{pattern}'{rest}"


def apply_rewrites(command: str) -> tuple[str, list[str]]:
    """Return rewritten command and list of rewrite messages."""
    messages: list[str] = []

    if re.search(r"^grep\b(?!.*\|)", command):
        command = rewrite_grep(command)
        messages.append("Rewrote grep → rg (faster, .gitignore-aware)")

    if re.search(r"^find\s+\S+\s+-name\b", command):
        command = rewrite_find_name(command)
        messages.append("Rewrote find -name → rg --files")

    return command, messages


def check_blocks(command: str) -> list[str]:
    """Return list of block explanations for patterns that match."""
    return [
        explanation
        for pattern, explanation in _BLOCK_RULES
        if re.search(pattern, command)
    ]


def main() -> None:
    try:
        data = json.load(sys.stdin)
    except json.JSONDecodeError as exc:
        print(f"Hook error: invalid JSON from harness: {exc}", file=sys.stderr)
        sys.exit(1)

    tool_name = data.get("tool_name", "")

    # Only intercept Bash calls
    if tool_name != "Bash":
        sys.exit(0)

    tool_input = data.get("tool_input", {})
    command = tool_input.get("command", "")

    if not command:
        sys.exit(0)

    # Check blocks first — blocking takes priority over rewriting
    block_reasons = check_blocks(command)
    if block_reasons:
        for reason in block_reasons:
            print(f"• {reason}", file=sys.stderr)
        sys.exit(2)

    # Apply rewrites
    rewritten_command, rewrite_messages = apply_rewrites(command)

    if rewritten_command != command:
        updated_input = dict(tool_input)
        updated_input["command"] = rewritten_command
        response = {
            "updatedInput": updated_input,
            "userFacingMessage": "; ".join(rewrite_messages),
        }
        print(json.dumps(response))

    sys.exit(0)


if __name__ == "__main__":
    main()

16.10 Lab: Build a Security Hook That Blocks Dangerous Patterns and Explains Why

This lab builds a production-quality PreToolUse security hook that enforces a threat model around credential handling, network calls, and filesystem modifications. The hook explains every block in terms the model can reason about — not just "denied", but why and what to do instead.

Prerequisites

  • Python 3.10+
  • A project with .claude/settings.json
  • The hook file location: .claude/hooks/security-hook.py

Step 1: Define the Threat Model

Before writing patterns, define what you are protecting against:

  1. Credential exfiltration — commands that read credential files and might pass them to network calls
  2. Uncontrolled network access — curl/wget to arbitrary domains without explicit approval
  3. Irreversible filesystem operations — mass deletes, writes to system paths
  4. Privilege escalation — sudo with file modification or network commands
  5. Shell injection patterns — eval, inline script execution, process substitution abuse

Step 2: Write the Hook

#!/usr/bin/env python3
"""
security-hook.py — PreToolUse security hook.

Enforces the project's threat model for Bash commands.
Every block includes an actionable explanation for the model.
"""
from __future__ import annotations

import json
import re
import sys
from dataclasses import dataclass


@dataclass
class BlockRule:
    pattern: str
    explanation: str
    suggestion: str


# Ordered list — first matching rule wins
SECURITY_RULES: list[BlockRule] = [
    BlockRule(
        pattern=r"\$\(cat\s+.*\.(env|pem|key|crt|token|secret)\b",
        explanation="Detected credential file read inside command substitution.",
        suggestion="Read credential files through the Read tool for auditing, not via shell substitution.",
    ),
    BlockRule(
        pattern=r"\bcurl\b[^|]*-[a-zA-Z]*d\s+@(\.env|.*\.pem|.*\.key|.*\.token)",
        explanation="Detected credential file being posted via curl.",
        suggestion="Do not POST credential files. Use environment variables or a secrets manager.",
    ),
    BlockRule(
        pattern=r"\bcurl\b.*\|\s*(bash|sh|zsh|python|python3)\b",
        explanation="Detected pipe from curl to a shell or interpreter.",
        suggestion="Download the script to a temp file first, inspect it, then execute explicitly.",
    ),
    BlockRule(
        pattern=r"\bwget\b.*-O\s*-\s*\|",
        explanation="Detected pipe from wget to a command.",
        suggestion="Download to a file first, review, then execute.",
    ),
    BlockRule(
        pattern=r"\brm\s+(-[a-zA-Z]*f[a-zA-Z]*|-[a-zA-Z]*r[a-zA-Z]*f|-rf|-fr)\s+/[^t]",
        explanation="Detected recursive force-delete targeting a path outside /tmp.",
        suggestion="Be specific about what to delete. Avoid -rf on paths that contain production data.",
    ),
    BlockRule(
        pattern=r"\beval\s+[\"'`]",
        explanation="Detected eval with a string argument — potential code injection vector.",
        suggestion="Construct and run the command directly. eval with string arguments is rarely necessary.",
    ),
    BlockRule(
        pattern=r"\bsudo\b.*(curl|wget|python|pip|npm|chmod|chown|mv|cp|rm)",
        explanation="Detected sudo combined with a potentially dangerous command.",
        suggestion="Confirm with the user before running elevated network or filesystem operations.",
    ),
    BlockRule(
        pattern=r">\s*/etc/(?!hosts\b)",
        explanation="Detected write redirect to /etc/ (excluding /etc/hosts).",
        suggestion="Writing to /etc/ requires explicit human approval. Use the AskUserQuestion tool.",
    ),
    BlockRule(
        pattern=r"\bchmod\s+[0-9]*7[0-9][0-9]\b",
        explanation="Detected world-writable permission (chmod x7xx or xx7x).",
        suggestion="Use the minimum permissions: 644 for files, 755 for directories.",
    ),
    BlockRule(
        pattern=r"\bbase64\b.*\|\s*(bash|sh)",
        explanation="Detected base64-decoded content piped to a shell.",
        suggestion="Decode to a file, inspect, then execute if safe.",
    ),
]


def find_matching_rule(command: str) -> BlockRule | None:
    for rule in SECURITY_RULES:
        if re.search(rule.pattern, command, re.IGNORECASE):
            return rule
    return None


def format_block_message(rule: BlockRule, command: str) -> str:
    return (
        f"Security policy block:\n"
        f"  Reason: {rule.explanation}\n"
        f"  Suggestion: {rule.suggestion}\n"
        f"  Command: {command[:200]}{'...' if len(command) > 200 else ''}"
    )


def main() -> None:
    try:
        data = json.load(sys.stdin)
    except json.JSONDecodeError as exc:
        print(f"security-hook: malformed stdin JSON: {exc}", file=sys.stderr)
        sys.exit(1)

    tool_name = data.get("tool_name", "")

    if tool_name != "Bash":
        sys.exit(0)

    command = data.get("tool_input", {}).get("command", "")
    if not command:
        sys.exit(0)

    rule = find_matching_rule(command)
    if rule:
        print(format_block_message(rule, command), file=sys.stderr)
        sys.exit(2)

    sys.exit(0)


if __name__ == "__main__":
    main()

Step 4: Extend with an Allowlist

For teams where some commands legitimately match block patterns (a deployment script that uses sudo, a setup script that pipes from curl after verification), add an allowlist:

# Add to security-hook.py

ALLOWLISTED_COMMANDS: list[str] = [
    # Verified safe: Docker official installer (pinned hash checked separately)
    "curl -fsSL https://get.docker.com | sh",
    # Team-internal setup script verified in code review
    "curl https://internal.company.com/setup.sh | bash",
]

def is_allowlisted(command: str) -> bool:
    return any(command.strip() == allowed.strip() for allowed in ALLOWLISTED_COMMANDS)

# In main(), before find_matching_rule:
if is_allowlisted(command):
    sys.exit(0)

Step 5: Enterprise Pattern — Managed Hooks Only

For organizations where the security hook must be non-bypassable, deploy it through managed settings with allowManagedHooksOnly: true:

// Enterprise managed settings
{
  "allowManagedHooksOnly": true,
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "/opt/company/claude-hooks/security-hook.py",
            "timeout": 5000,
            "statusMessage": "Security check..."
          }
        ]
      }
    ]
  }
}

With allowManagedHooksOnly: true, any hook defined in a project's .claude/settings.json is silently ignored. Only the hook at /opt/company/claude-hooks/security-hook.py runs. This prevents a compromised project repository from disabling the hook by overwriting the project settings — a concrete supply-chain defense covered in detail in Chapter 4.

Summary

The hook system is the extension layer that turns a read-only observer into an active participant in every tool call. The eight events — SessionStart, PreToolUse, PostToolUse, PostToolUseFailure, Stop, PreCompact, TaskCreated, and PermissionDenied — cover every meaningful moment in the control loop.

The key operational facts:

  • Exit codes govern behavior. Exit 0 passes through. Exit 1 warns the user without blocking. Exit 2 blocks the call and shows stderr to the model.
  • PreToolUse stdout is interpreted as JSON. Return updatedInput to rewrite the call before execution, permissionDecision to control approval, and userFacingMessage for user-visible explanations.
  • The if condition filters hooks cheaply using the permission rule DSL, so expensive hooks only run on the inputs they care about.
  • defer is the mechanism for async approval workflows. The session pauses on disk and resumes when an external actor provides a decision.
  • PreCompact survives context compaction by injecting preservation instructions before the summary is produced — the escape hatch for sessions with accumulated non-reconstructible state.
  • allowManagedHooksOnly makes hooks non-bypassable at the enterprise level, preventing supply-chain attacks that add malicious hooks via compromised project settings.

The bash_command_validator_example.py and security-hook.py patterns in this chapter are templates. Adapt them to your threat model, add your team's specific block rules, and deploy them through managed settings for the strongest guarantees.
