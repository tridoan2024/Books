Chapter 32: Team-Based Agent Systems

"A single agent can solve a hard problem. A team of agents can solve a class of hard problems simultaneously — if the team is designed with the same care as the code."

32.1 Agent Teams: From Solo to Coordinated

The Agent tool covered in Chapter 11 is a delegation primitive — one agent assigns a task to another. That is powerful, but it is not a team. A team is a standing configuration: a set of agents with defined roles, a coordination protocol, and shared context about the problem domain. The difference is the same as the difference between hiring a freelancer for a task and building an engineering org.

Claude Code exposes team capabilities through CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS. This environment variable activates team mode and sets the default team size:

export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=3
export CLAUDE_CODE_TEAMMATE_COMMAND=~/.local/bin/dcode-tmux-entry

CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=3 tells the harness to maintain a team of three concurrent agent slots in addition to the leader. CLAUDE_CODE_TEAMMATE_COMMAND specifies the binary used to launch each teammate. The default is the Claude Code binary itself; the variable lets you substitute an alternative runner — in production, a tmux-aware wrapper that manages terminal panes for visibility.

The tmux-entry wrapper is important for human-observable teams. Rather than spawning agents as invisible background processes, each teammate occupies its own tmux pane. The lead agent runs in the left half of the terminal; teammates stack vertically in the right half. You can click into any pane, watch the agent work in real time, and intervene if something goes wrong.

The lead dispatches work. The teammates execute. The lead reads results from output files and synthesizes. This is not fundamentally different from the fan-out patterns in Chapter 11 — but team mode makes it a first-class operating mode rather than a one-off pattern you assemble by hand each time.

Teammate Dispatch Mechanics

When the lead agent dispatches to a teammate in tmux team mode, the harness sends the prompt via tmux load-buffer followed by paste-buffer and send-keys Enter. A 2-second sleep between paste and Enter is not optional — it allows the tmux buffer to flush before the keypress lands. Skipping this sleep produces garbled prompt delivery in roughly 30% of cases.

# Inside dcode-tmux-entry — what actually dispatches a task
tmux load-buffer -b agent-prompt - <<< "${PROMPT}"
tmux paste-buffer -b agent-prompt -t "${SESSION}:${PANE}"
sleep 2
tmux send-keys -t "${SESSION}:${PANE}" Enter

The lead does not wait synchronously. It registers an output file path with the teammate and polls it — or uses ScheduleWakeup — to collect results. Chapter 11 covered the polling pattern; in team mode, you will use it constantly.

Stagger on Launch

The second constraint that will burn you if you ignore it: stagger agent launches. Each teammate is a separate Claude Code session, which means a separate API connection. Launching four teammates simultaneously hammers the rate limit and produces 429 errors on the second, third, and fourth agent.

The production rule: launch each teammate with a 3-second delay between launches. For a 4-agent team (lead + 3 teammates) this costs 9 seconds of setup time. That is negligible against most task durations.

// Correct: staggered team launch
for (let i = 0; i < teammates.length; i++) {
  await Agent({
    description: `Launch teammate ${i + 1}`,
    prompt: buildTeammateBootstrap(i, task),
    name: `teammate-${i}`,
  });
  if (i < teammates.length - 1) {
    await sleep(3000); // 3s between launches
  }
}

Running more than four concurrent sessions against a single API key degrades sharply. Context degrades per-agent after approximately 60 minutes of continuous operation — each agent should checkpoint its work and reset after that window. Checkpointing is the agent writing its current findings/state to a file, after which the lead can restart it fresh with the checkpoint as input.

32.2 Custom Agents: Defining the Team Roster

Out-of-the-box agent types — code-reviewer, security-reviewer, debugger, researcher, doc-writer — cover common workflows. For specialized teams, you define custom agents in .claude/agents/. Each file is a Markdown document with YAML frontmatter followed by a system prompt.

The frontmatter fields control the agent's capabilities, cost profile, and context scope:

---
name: code-reviewer
description: Reviews code for quality, bugs, performance, and best practices.
tools: Read, Grep, Glob
model: sonnet
effort: high
memory: project
---

You are a senior software engineer performing a code review.
[system prompt follows...]

Frontmatter Fields Reference

toolsComma-separated list of tools this agent may call. Enforced at the registry level — not just a suggestion.all tools

The Production Agent Roster

A mature project's .claude/agents/ directory looks like a hiring plan:

.claude/agents/
├── code-reviewer.md       # tools: Read, Grep, Glob
├── debugger.md            # tools: Read, Grep, Glob, Bash
├── doc-writer.md          # tools: Read, Grep, Glob, Write
├── researcher.md          # tools: Read, Grep, Glob, WebSearch, WebFetch
└── security-reviewer.md   # tools: Read, Grep, Glob

Notice what is not in most of these tool lists: Bash, Edit, and Write. This is intentional. Tool restrictions are security boundaries enforced at the harness level. A security-reviewer that can only read files genuinely cannot make changes, regardless of how clever its prompting gets. A code-reviewer with Read, Grep, Glob cannot execute shell commands, access the network, or write files — it can only read.

The principle of least privilege applies here with the same force it applies to service accounts and IAM policies. An agent that only needs to read should not have shell access.

Model Pinning

Model selection per agent is one of the most economically significant decisions in team design. A team that uses opus across all agents will spend 10–15× more than a team that uses haiku for high-volume triage work and sonnet for reasoning-intensive steps.

The production model assignment strategy:

haiku  → structured extraction, file scanning, format conversion, triage
sonnet → multi-step analysis, code review, debugging, documentation
opus   → architecture decisions, complex security analysis, contradiction resolution

In the agent definition file, pin the model to the minimum capable for the agent's typical task. Let the caller override upward when a specific task requires it.

---
name: security-reviewer
description: Targeted security vulnerability analysis with OWASP/CWE references.
tools: Read, Grep, Glob
model: sonnet      # sonnet: algorithm confusion and auth logic flaws need reasoning
effort: high
memory: project
---
---
name: changelog-writer
description: Converts git log output to user-facing changelog entries.
tools: Bash        # only needs git log
model: haiku       # haiku: structured text transformation from known input
effort: low
memory: none       # no project context needed
---

The changelog writer uses haiku because the task is fundamentally a template expansion over structured input — git log entries. It doesn't need the reasoning depth of sonnet. The security reviewer uses sonnet because recognizing subtle authentication flaws (JWT algorithm confusion, timing attacks in equality checks) requires real inference, not pattern matching.

Memory Scope

memory: project causes the harness to inject the project's CLAUDE.md into the agent's context before its system prompt. This gives the agent access to project-specific conventions — coding standards, security rules, terminology.

memory: none gives a clean context with only the agent's own system prompt. Use this for agents whose task is generic enough that project conventions would introduce noise rather than signal — the changelog writer doesn't need Python style rules.

When building a team, decide deliberately: which agents need project context to do their job correctly, and which would be better served by a clean slate? A code-reviewer benefits from knowing the project's type-hint requirements. A researcher doing web searches does not.

32.3 Teammate Coordination with SendMessage

The Agent tool creates a fresh session every time. SendMessage continues an existing named session:

export interface SendMessageInput {
  to: string;    // the `name` parameter used when the agent was launched
  message: string;
}

This distinction is fundamental to how teams coordinate over time.

Named Agents as Persistent Collaborators

When you launch an agent with a name, it becomes addressable for the lifetime of the session:

// Launch — agent starts fresh, accumulates context
await Agent({
  description: "Security audit session",
  prompt: `You are a security reviewer for this project.
Repository: /Users/DOANTX26/Documents/2026/myapp
Your task: Review src/auth/ for vulnerabilities.
Start with src/auth/session.py and src/auth/tokens.py.
Return your initial findings.`,
  name: "sec-reviewer",
  subagent_type: "security-reviewer",
  run_in_background: false,
});

// Later: continue the same agent, full context preserved
await SendMessage({
  to: "sec-reviewer",
  message: "Good. Now focus specifically on the JWT validation in tokens.py line 47. Is there an algorithm confusion vector if the client controls the `alg` header?",
});

// Later still: another follow-up
await SendMessage({
  to: "sec-reviewer",
  message: "What's the minimal fix that doesn't require changing the JWT library version?",
});

Each SendMessage call resumes the agent exactly where it left off. The agent's entire conversation history — the files it read, the hypotheses it formed, the findings it recorded — is intact. You are conducting an investigation with a specialist, not issuing independent work orders.

Compare this to spawning a fresh Agent for each question: every call would require re-reading tokens.py, re-establishing context about the JWT library, and re-deriving the vulnerability. The named agent pattern eliminates this overhead for multi-turn investigations.

sequenceDiagram
    participant L as Lead Agent
    participant R as sec-reviewer (named)

    L->>R: Agent(name: "sec-reviewer", prompt: "audit src/auth/")
    Note over R: reads files, forms findings
    R-->>L: initial findings (12 issues found)

    L->>R: SendMessage("focus on tokens.py:47, algorithm confusion?")
    Note over R: has full prior context, no re-reading
    R-->>L: "yes — alg header not validated, CWE-347"

    L->>R: SendMessage("minimal fix without library version change?")
    Note over R: has full prior context + vulnerability details
    R-->>L: "explicitly reject alg: none in validation function"

Choosing Between New Agent and SendMessage

ScenarioUse
Parallel tasks with no shared stateNew Agent calls (fan-out)
Sequential investigation on same subjectNamed agent + SendMessage
Agent accumulated expensive context (many files read)Named agent + SendMessage
Clean isolation requiredNew Agent (no name)
Continuing from a checkpoint after /clearNew Agent with checkpoint in prompt

The named agent pattern is expensive to abandon mid-investigation. Once an agent has read 50 files and formed a nuanced understanding of the vulnerability surface, destroying that session and starting over is wasteful. Use SendMessage to steer, not Agent to restart.

Broadcast vs. Point-to-Point

In a team, the lead often needs to send the same message to all teammates, or route different messages to specific agents. Both patterns emerge naturally from SendMessage's to field:

// Broadcast: same message to all active teammates
const teammates = ["analyst-1", "analyst-2", "analyst-3"];
for (const t of teammates) {
  await SendMessage({
    to: t,
    message: "New data available at /tmp/market-snapshot.json. Revise your analysis.",
  });
}

// Point-to-point: different message to each based on role
await SendMessage({
  to: "scanner",
  message: "Market opened. Begin full scan with dt_fullscan.py.",
});

await SendMessage({
  to: "analyst",
  message: "Scanner output at /tmp/scan-results.json. Run convergence scoring.",
});

await SendMessage({
  to: "executor",
  message: "Standby. Do not execute until analyst returns score >= 7.",
});

The lead is the coordination bus. It routes information, enforces sequencing, and synthesizes results. Teammates do not send messages to each other directly — they write output files that the lead reads and forwards as needed. This star topology is simpler to reason about and debug than a mesh.

32.4 The dcode-team Pattern: Pyramid Hierarchy

The dcode-team system is a production implementation of the team pattern taken to its logical conclusion: a dynamic, reshapable hierarchy where any agent can become a sub-lead with its own team.

Architecture

graph TD
    subgraph "Level 0"
        L[Lead Agent<br/>pane 0]
    end
    subgraph "Level 1"
        A1[Teammate 1]
        A2[Teammate 2]
        A3[Teammate 3]
    end
    subgraph "Level 2 — sub-lead expansion"
        B1[Sub-agent 1a]
        B2[Sub-agent 1b]
        B3[Sub-agent 1c]
    end

    L -->|dispatch| A1
    L -->|dispatch| A2
    L -->|dispatch| A3
    A1 -->|promoted to sub-lead| B1
    A1 -->|promoted to sub-lead| B2
    A1 -->|promoted to sub-lead| B3

The default configuration is flat: one lead, three teammates. The pyramid emerges when a teammate is promoted to sub-lead via /team-promote N [sub_count]. When promoted, the teammate receives a prompt that teaches it to:

  1. Create a tmux sub-session named {parent-session}-sub-N
  2. Split panes and launch a copilot CLI agent in each
  3. Dispatch tasks to sub-agents via tmux load-buffer + send-keys
  4. Collect results from sub-agent output files
  5. Synthesize and return to the parent lead
  6. Clean up the sub-session when done

Sub-lead promotion is the mechanism for scope management. If the lead assigns a "refactor the entire auth module" task to Teammate 1 and that task turns out to be large enough to warrant its own team, the lead promotes Teammate 1 rather than spawning more agents at its own level. This keeps the lead's coordination load bounded.

Safety Limits

Unbounded agent spawning is a real failure mode. The dcode-team system enforces hard limits:

GuardLimitReason
Agents per level10API rate limits per key
Total agents across all levels20Cost + rate limit ceiling
Pyramid depth3Coordination overhead grows with depth

These are not soft recommendations. The harness enforces them and rejects /team-add calls that would exceed them. If you are building your own team system, implement the same guards. An unbounded team will hit rate limits, generate enormous API costs, and produce output that is impossible to synthesize because too many agents ran in parallel.

Copilot CLI as Backend

Each teammate in dcode-team is a copilot CLI session — a Claude Code binary running with --permission-mode auto. This gives every teammate the full 52+ tool surface: Bash, Read, Edit, WebSearch, Agent, and all deferred tools. The lead and teammates are peers at the API level; the hierarchy is a coordination convention, not a capability constraint.

The CLAUDE_CODE_TEAMMATE_COMMAND=~/.local/bin/dcode-tmux-entry environment variable points the harness at the tmux-entry wrapper, which handles:

  • Creating the tmux pane for the new teammate
  • Launching copilot --permission-mode auto inside it
  • Setting the working directory to the project root
  • Writing the teammate's output to the agreed-upon output file path

Dynamic Team Operations

The /team-* directives let you reshape the team at runtime without restarting the session:

/team-add 2          — add 2 more agents to the current level (3s staggered)
/team-remove 2       — remove agent at index 2 and clean up its pane
/team-promote 1 3    — promote agent 1 to sub-lead with 3 sub-agents
/team-tree           — display the full pyramid hierarchy
/team-stop           — recursively destroy all agents and sub-sessions

This dynamic reshaping is operationally valuable. You do not know at task start how large the work is. Starting with a small team and adding agents when scope expands is cheaper than over-provisioning upfront.

32.5 Case Study: The DT Trading 4-Agent Team

The DT (day trading) system is one of the clearest examples of a production multi-agent team because the roles are well-defined, the data flow is explicit, and the stakes make design quality visible immediately.

Team Composition

graph TD
    subgraph "DT Trading Team"
        direction TB
        Lead[Lead Agent<br/>Strategy + Coordination<br/>model: sonnet]
        Scanner[Scanner Agent<br/>Market Data Collection<br/>model: haiku]
        Analyst[Analyst Agent<br/>Convergence Scoring<br/>model: sonnet]
        Executor[Executor Agent<br/>Trade Execution<br/>model: sonnet]
    end

    Lead -->|"scan now, 0DTE SPY"| Scanner
    Scanner -->|"/tmp/scan-results.json"| Lead
    Lead -->|"score these levels"| Analyst
    Analyst -->|"/tmp/convergence.json"| Lead
    Lead -->|"buy 1 contract at 535C if score >= 7"| Executor
    Executor -->|"/tmp/execution-log.json"| Lead

Four agents, four distinct roles:

Lead — The only agent the user talks to directly. It owns strategy decisions (which setups to pursue, when to size up vs. stay flat), coordinates the other three agents, and synthesizes output into decisions. Model: sonnet. It does not execute trades. It does not run data collection. It delegates and decides.

Scanner — Runs dt_fullscan.py and dt_brain.py to collect market data: level 2 quotes, options flow, technical levels, news. It writes structured output to /tmp/scan-results.json. Model: haiku — the task is data collection and format transformation, not reasoning. The scanner does not decide anything.

Analyst — Reads scanner output and runs convergence scoring: checks for alignment across price action, options flow, technical levels, and time of day. Returns a score 1–10 with supporting rationale. Model: sonnet — convergence scoring requires judgment, not just extraction. The analyst does not decide anything.

Executor — Runs dt_executor.py buy/sell when the lead gives a specific, fully-specified order. It reports fill price, confirmation, and position state. Model: sonnet — execution requires reading error messages and retrying intelligently. The executor does not decide anything.

Why This Division Matters

The lead/specialist division is not cosmetic. It addresses a specific failure mode of single-agent trading systems: context contamination.

A single agent running all four roles within one context window accumulates execution details (fill prices, retry attempts, broker error messages) that contaminate its subsequent analysis. After 30 minutes of trading, the agent's context is dominated by execution minutiae rather than market structure. Its analysis degrades.

By isolating each role, each agent's context remains clean and focused. The executor's context is execution logs. The analyst's context is market data and scoring logic. The scanner's context is data collection scripts and their output. The lead's context is strategy, decisions, and the high-level output from each specialist.

Prompt Engineering for the DT Team

Each agent in the team receives a self-contained bootstrap prompt. The lead's prompt is the most complex — it establishes strategy, defines when to call each teammate, and sets the decision framework:

You are the Lead agent for a DT (day trading) paper account on SPY 0DTE options.

## Your team
- Scanner (name: "scanner"): runs market data collection. Call it with: what to scan and when.
- Analyst (name: "analyst"): runs convergence scoring. Call it with: specific setup to evaluate + context from scanner.
- Executor (name: "executor"): executes trades. Call it only with fully-specified orders.

## Decision rules
- Score >= 8: full AM sizing (2 contracts)
- Score 6-7: probe sizing (1 contract)
- Score < 6: no trade
- PM (after 12:00 CDT): max 1 contract regardless of score
- Final 30 minutes: lottery only — no new positions

## Your process
1. On market open: call scanner
2. When scanner returns: call analyst with the setup you want to evaluate
3. When analyst returns score >= 6: call executor with the exact order
4. Monitor position via executor
5. On exit signal: call analyst to re-score, then executor to close

## Output files
- Scanner writes to: /tmp/scan-results.json
- Analyst writes to: /tmp/convergence.json
- Executor writes to: /tmp/execution-log.json

Read these files to collect results after each agent completes.
Never guess — always read the output file.

The scanner receives a simpler prompt because its task is narrow:

You are the Scanner agent for a DT trading team.

Your job: collect market data when the Lead requests a scan.

## Tools available
- Bash: run dt_fullscan.py and dt_brain.py
- Read: read output files

## On each scan request
1. Run: python3 /path/to/dt_fullscan.py --ticker SPY --expiry 0DTE
2. Run: python3 /path/to/dt_brain.py --output /tmp/scan-results.json
3. Write structured output to /tmp/scan-results.json

## Output format
JSON with: levels (support/resistance), flow (puts/calls ratio, unusual activity), 
ta (trend, momentum, vwap), timestamp

Do not make trading decisions. Do not interpret the data beyond formatting it.
The Analyst interprets. You collect.

The last two sentences of the scanner prompt are intentional. Role confusion — an agent that starts interpreting when it should be collecting — is a real failure mode. Explicit role boundaries in the system prompt reduce the probability of it.

Timing and State Management

The DT team operates across a 6.5-hour trading day. Context window management is essential.

Each agent should checkpoint at approximately 60 minutes:

// Lead's checkpoint pattern
async function checkpointAndReset(agentName: string, checkpointPath: string): Promise<void> {
  // Request checkpoint from agent
  await SendMessage({
    to: agentName,
    message: `Write a checkpoint to ${checkpointPath}. Include: all decisions made, current position state, key levels being watched, any patterns you've noted. Be specific — this will be used to resume your session.`,
  });

  // Wait for checkpoint to be written
  await waitForFile(checkpointPath);

  // Resume with fresh context from checkpoint
  const checkpoint = await readFile(checkpointPath);
  await Agent({
    description: `Resume ${agentName}`,
    prompt: buildResumePrompt(agentName, checkpoint),
    name: agentName,  // same name — replaces the old addressable instance
  });
}

Launching a new Agent with the same name replaces the prior named instance. The new agent starts fresh but with the checkpoint as its full prior context — a clean context window containing all the relevant history without the accumulated noise.

The Lead as Safety Interlock

A critical architectural decision in the DT team: the executor never acts without an explicit lead instruction. The analyst never forwards its scores directly to the executor. Every execution order flows through the lead.

This is not an efficiency concern. It is a safety interlock. In a financial context, an autonomous pipeline from analyst output to execution without human-in-the-loop review is a known failure mode. The lead is the decision point, and only the lead issues orders to the executor. The analyst advises. The lead decides. The executor acts.

This pattern generalizes: in any team system where an agent's actions have real-world consequences (code commits, deployments, financial operations), route all consequential actions through a single decision-making agent that is visible to the user. Distribute intelligence. Centralize decisions.

Building Your Own Team: A Design Checklist

The chapter has covered the mechanics. Before you build, answer these questions:

Role definition

  • [ ] What does each agent do that the others do not?
  • [ ] Where are the boundaries? What is explicitly outside each agent's scope?
  • [ ] Is each agent's system prompt explicit about its role boundary?

Tool surface

  • [ ] Does each agent have the minimum tools it needs?
  • [ ] Does any agent have tools it should not have given its role?
  • [ ] Is Write access limited to agents that genuinely need to create files?

Model selection

  • [ ] Which agents perform structured extraction or transformation? (haiku)
  • [ ] Which agents perform multi-step reasoning? (sonnet)
  • [ ] Are there decisions complex enough to warrant opus? (rare)

Coordination topology

  • [ ] Is the lead the single decision point for consequential actions?
  • [ ] Do agents communicate through the lead, or directly?
  • [ ] How does the lead know when a teammate has completed its work?

Context management

  • [ ] When does each agent's context need to be checkpointed and reset?
  • [ ] What is included in the checkpoint?
  • [ ] Is the checkpoint prompt self-contained enough to resume without the original conversation?

Safety limits

  • [ ] Is there a ceiling on concurrent agents?
  • [ ] Is there a ceiling on pyramid depth?
  • [ ] Are launches staggered to avoid rate limit collisions?

A team that fails this checklist will still produce output. But it will produce that output at higher cost, with more coordination failures, and with less predictable behavior than a team designed to these constraints.

Summary

Team-based agent systems are the natural extension of the single-agent patterns from Chapter 11. The mechanics are: CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS activates team mode, custom agents in .claude/agents/ define the roster, tool restrictions enforce role boundaries at the harness level, model pinning aligns cost to capability, and SendMessage makes named agents addressable across multiple turns.

The dcode-team pattern takes these mechanics to production: a dynamic pyramid hierarchy built on tmux panes, copilot CLI as the teammate runtime, safety limits on agent count and pyramid depth, and a 3-second stagger between launches to avoid rate limit collisions.

The DT trading case study illustrates the design principles in a domain where mistakes are visible in account P&L. Specialization keeps each agent's context clean. The lead is the single decision point for consequential actions. Each agent's prompt defines its role boundary explicitly. Context is checkpointed and reset on a 60-minute cadence.

The rule that underlies all of it: distribute intelligence, centralize decisions.
