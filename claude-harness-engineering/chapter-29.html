Chapter 29: Hook, Skill, and Plugin System

"Extensibility is not a feature you bolt on. It is a structure you build from the start — or you rebuild everything later."

29.1 Event System: Lifecycle Events, Tool Events, Custom Events

The hook system is the harness's primary extension surface. Every point in the control loop where external logic might want to observe, intercept, or transform what the harness does is represented as a named event. The harness fires these events; your code listens and responds.

Before you can implement hooks, you need a precise model of the event taxonomy. There are three categories.

Lifecycle Events

Lifecycle events correspond to state transitions in the harness itself — session startup, shutdown, and context management. They do not carry tool-specific data; they carry session state.

SessionStart fires once, immediately after the harness finishes initializing. The system prompt has not been assembled yet. No tools have run. The stdout of any hook registered here is injected into the conversation before the first user message, making this the event for environment priming — loading cached state, checking preconditions, printing a context summary the model will read at session start.

Stop fires when the control loop exits cleanly — the model has returned a text-only response with no pending tool calls. This is the moment for cleanup, state persistence, completion notifications, and cost accounting. A Stop hook that writes the session's tool call count and token cost to a log file is a one-liner that pays for itself in operational visibility.

PreCompact fires before the harness compacts the conversation history. Compaction is the process of summarizing a long conversation into a condensed version that fits within the model's context window; after compaction, the original turn-by-turn history is gone. A PreCompact hook's stdout is injected into the compaction request as preservation instructions. Without this event, any state your agent has built up implicitly in the conversation — current working directory, completed task list, running counters — is silently discarded.

Tool Events

Tool events fire around tool execution. They carry structured data about the specific tool call in progress.

PreToolUse fires after the permission layer has evaluated a tool call but before execution. The hook receives the tool name and full tool input as JSON on stdin. It can allow, block, or rewrite the call. This is the most powerful event and the most latency-sensitive: every tool call passes through every registered PreToolUse hook.

PostToolUse fires after a successful tool execution. The hook receives the tool name, the original input, and the tool's response. The response is already in the conversation history — the hook cannot change it. The purpose of this event is observation and side effects: audit logging, formatting on save, webhook notifications, index updates.

PostToolUseFailure fires when a tool call raises an error during execution. It receives the same data as PostToolUse plus the error details. Use this for failure telemetry, retry orchestration, and alert pipelines that need to know when the agent hits a broken state.

TaskCreated fires when the TaskCreate tool creates a background task. It receives the task ID and initial parameters. Use this for task registry integrations and audit trails.

PermissionDenied fires when the permission layer rejects a tool call before execution. It receives the tool name and denied input. A hook returning {"retry": true} instructs the harness to treat the call as retriable after the hook has run — the mechanism for human-in-the-loop approval workflows.

Custom Events in Your Own Harness

In a harness you control, the event taxonomy is yours to define. The implementation pattern is the same for every event type: a list of registered handlers, a dispatch function that iterates them, and a data envelope describing what happened.

from __future__ import annotations

import asyncio
import json
import subprocess
from dataclasses import dataclass, field
from enum import Enum
from pathlib import Path
from typing import Any


class HarnessEvent(str, Enum):
    SESSION_START = "SessionStart"
    PRE_TOOL_USE = "PreToolUse"
    POST_TOOL_USE = "PostToolUse"
    POST_TOOL_USE_FAILURE = "PostToolUseFailure"
    STOP = "Stop"
    PRE_COMPACT = "PreCompact"
    TASK_CREATED = "TaskCreated"
    PERMISSION_DENIED = "PermissionDenied"
    # Custom events for your harness
    COST_THRESHOLD_EXCEEDED = "CostThresholdExceeded"
    AGENT_SPAWNED = "AgentSpawned"
    AGENT_COMPLETED = "AgentCompleted"


@dataclass
class HookEventPayload:
    event: HarnessEvent
    session_id: str
    tool_name: str | None = None
    tool_input: dict[str, Any] | None = None
    tool_response: Any | None = None
    error: str | None = None
    metadata: dict[str, Any] = field(default_factory=dict)

    def to_json(self) -> str:
        return json.dumps(
            {
                "event": self.event.value,
                "session_id": self.session_id,
                "tool_name": self.tool_name,
                "tool_input": self.tool_input,
                "tool_response": self.tool_response,
                "error": self.error,
                "metadata": self.metadata,
            },
            default=str,
        )

The metadata field carries event-specific data for custom events. For CostThresholdExceeded, it might contain {"current_cost_usd": 4.82, "threshold_usd": 5.00}. For AgentSpawned, it might contain {"subagent_id": "abc123", "parent_task_id": "xyz789"}. The type system is loose here by design — custom events are not standardized, and trying to encode every variant in the enum defeats the purpose of extensibility.

29.2 Hook Execution: Subprocess Spawn, JSON I/O Contract, Exit Code Semantics, Timeout Handling

Understanding the hook execution model precisely is what separates hooks that work reliably in production from hooks that work in development and break under load.

The Execution Model

Every hook is a subprocess. The harness spawns the process, writes the event payload JSON to its stdin, reads stdout and stderr, waits for the process to exit, and interprets the exit code. The subprocess model means:

  • Hooks can be written in any language
  • Hooks have a separate process namespace and cannot directly modify harness state
  • Hook failures are isolated — a segfault in a hook does not crash the harness
  • Hook startup overhead (Python interpreter, module imports) is paid on every call

That last point matters for PreToolUse hooks. Every Bash call goes through every registered PreToolUse hook before executing. A hook that takes 300ms due to Python startup adds 300ms of latency to every shell command the agent runs. For performance-sensitive hooks, compile to a native binary or use a persistent daemon with a socket interface.

The JSON I/O Contract

stdin:  HookEventPayload (JSON)
stdout: HookResponse (JSON, optional)
stderr: Human-readable message (shown to user or Claude based on exit code)

The HookResponse on stdout is parsed only when the harness needs it. For PreToolUse, the harness parses stdout to look for a permissionDecision or updatedInput. For SessionStart, it uses stdout as a context message injected into the conversation. For PostToolUse and Stop, stdout is ignored.

#!/usr/bin/env python3
"""
PreToolUse hook: blocks rm -rf and rewrites dangerous find -delete patterns.
Exit 0 = allow, Exit 1 = warn user (tool still runs), Exit 2 = block (Claude sees stderr).
"""
from __future__ import annotations

import json
import re
import sys


def main() -> None:
    payload = json.load(sys.stdin)
    tool_name = payload.get("tool_name", "")
    tool_input = payload.get("tool_input", {})

    if tool_name != "Bash":
        sys.exit(0)

    command: str = tool_input.get("command", "")

    # Hard block: recursive force-delete of important paths
    if re.search(r"rm\s+-[rf]{1,2}\s+(\/|~|\$HOME|\.\/\.\.)", command):
        print(
            f"Blocked: destructive rm detected in command: {command!r}\n"
            "Use 'trash' CLI or confirm the target path explicitly.",
            file=sys.stderr,
        )
        sys.exit(2)

    # Rewrite: find -delete → safer dry-run first, then confirm
    if "find" in command and "-delete" in command:
        safe_command = command.replace("-delete", "-print")
        response = {
            "updatedInput": {
                **tool_input,
                "command": safe_command,
            }
        }
        print(json.dumps(response))
        print(
            f"Rewrote find -delete to find -print for safety review.\n"
            "Re-run with -delete after confirming the target list.",
            file=sys.stderr,
        )
        sys.exit(1)

    sys.exit(0)


if __name__ == "__main__":
    main()

The rewrite case is the subtlest: the hook emits updatedInput on stdout (exit 1, not 2) so the tool still runs — but with the safer command. The stderr warning is shown to the user. Claude sees the modified command in its tool result and understands what happened.

Exit Code Semantics

Exit codeMeaningWhere stderr appears
0Pass. Tool proceeds normally.Not shown.
1Warning. Tool proceeds, but stderr is shown to the user in the UI.User only.
2Block. Tool does not execute. Stderr shown to Claude as the tool result.Claude reads it, adapts.

Exit code 2 feeds the stderr directly to the model as if the tool had returned an error message. This is important: the model does not know a hook blocked it — it sees what looks like a tool execution error. Write exit-2 stderr as you would write a tool error message that an intelligent assistant should understand and act on.

# Wrong — cryptic, Claude cannot adapt
print("BLOCKED", file=sys.stderr)
sys.exit(2)

# Right — actionable, Claude can retry with a corrected approach
print(
    "Command blocked by security policy: 'npm install' without --save-exact "
    "allows non-deterministic dependency resolution. "
    "Use: npm install --save-exact <package>@<version>",
    file=sys.stderr,
)
sys.exit(2)

Timeout Handling

Every hook registration has a timeout field in milliseconds. The harness kills the subprocess after this interval and treats the kill as exit 1 (warning, tool proceeds).

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python3 ./.claude/hooks/bash-validator.py",
            "timeout": 3000,
            "statusMessage": "Validating command..."
          }
        ]
      }
    ]
  }
}

The default timeout is 60,000ms. That is too long for PreToolUse hooks. A hook that blocks the critical path should have a tight timeout — 3,000–5,000ms — so that a hanging hook does not freeze the entire agent.

For PostToolUse and Stop hooks, longer timeouts are acceptable because they do not block tool execution. A Stop hook that ships metrics to a remote endpoint can afford 30,000ms.

Build your hooks to fail fast rather than wait. Use asyncio.wait_for or subprocess.run(timeout=...) around any network call, and exit 1 rather than hanging.

29.3 Skill Loading: SKILL.md Discovery, Frontmatter Parsing, Conditional Activation

A skill is a named slash command backed by a SKILL.md file. The harness loads skills at session start and again when the user types / — it needs a fresh list of available commands to drive autocomplete. Understanding how loading works tells you exactly how to structure and place your skill files.

Discovery

The harness scans for SKILL.md files along two paths:

  1. ~/.claude/skills/**/SKILL.md — user-level skills, available in every project
  2. .claude/skills/**/SKILL.md — project-level skills, available only in this project

The ** is a glob: any subdirectory depth is valid. A project can organize its skills flat or in subdirectories:

.claude/
└── skills/
    ├── security/
    │   ├── sec-pr/SKILL.md
    │   └── sec-sr/SKILL.md
    ├── deploy/
    │   └── deploy-check/SKILL.md
    └── dt/SKILL.md

The discovery scan runs in lexicographic order within each search path. User-level skills come before project-level skills in the deduplication check. If a user-level skill and a project-level skill have the same name, the user-level skill wins and the project-level one is silently skipped.

Frontmatter Parsing

The YAML frontmatter block is parsed with strict type validation. A malformed frontmatter causes the skill to be skipped, not to raise a fatal error — the harness logs a warning and continues.

import re
import yaml
from dataclasses import dataclass
from pathlib import Path


@dataclass
class SkillFrontmatter:
    name: str
    description: str
    argument_hint: str = ""
    allowed_tools: list[str] | None = None
    model: str | None = None
    effort: str = "medium"
    paths: list[str] | None = None

    def __post_init__(self) -> None:
        if len(self.description) > 250:
            # Truncated in /skills listing — warn at load time
            import warnings
            warnings.warn(
                f"Skill '{self.name}': description exceeds 250 chars "
                f"({len(self.description)} chars). Listing will truncate.",
                stacklevel=2,
            )


def parse_skill_file(skill_path: Path) -> SkillFrontmatter | None:
    """Parse a SKILL.md file and return the frontmatter, or None if invalid."""
    content = skill_path.read_text(encoding="utf-8")
    match = re.match(r"^---\n(.*?)\n---", content, re.DOTALL)
    if not match:
        return None

    try:
        raw = yaml.safe_load(match.group(1))
    except yaml.YAMLError:
        return None

    if not isinstance(raw, dict) or "name" not in raw or "description" not in raw:
        return None

    allowed_tools = raw.get("allowed-tools")
    if isinstance(allowed_tools, str):
        allowed_tools = [t.strip() for t in allowed_tools.split(",")]

    paths = raw.get("paths")
    if isinstance(paths, str):
        paths = [paths]

    return SkillFrontmatter(
        name=raw["name"],
        description=raw["description"],
        argument_hint=raw.get("argument-hint", ""),
        allowed_tools=allowed_tools,
        model=raw.get("model"),
        effort=raw.get("effort", "medium"),
        paths=paths,
    )

The allowed-tools field in YAML uses a hyphen, which is not a valid Python identifier. The parser reads it as raw.get("allowed-tools") and maps it to the allowed_tools attribute.

Conditional Activation via paths

The paths field is the most underused capability in the skill system. It is a list of glob patterns that determine when a skill is visible and offered for autocomplete.

---
name: rust-check
description: Run cargo check, clippy, and test on the current Rust workspace
allowed-tools: Bash
paths:
  - "**/*.rs"
  - "Cargo.toml"
  - "Cargo.lock"
---

When the harness loads skills, it evaluates each skill's paths list against the files present in the current working directory. If none of the globs match any file, the skill is hidden from the /skills listing and excluded from autocomplete. It is still installed — it will reappear if the user switches to a project that has matching files.

The practical consequence: a workspace with twenty skills stays clean. A user in a Python project does not see Rust skills. A user in a frontend project does not see SQL migration skills. The tool surface shrinks to match the context, which reduces cognitive overhead and token cost for the harness's own context assembly.

For skills without a paths field, the skill is always visible. Most general-purpose skills (/sec-pr, /deploy-check, /dt) omit paths because they are context-independent.

The 250-Character Description Limit

The /skills listing card truncates descriptions at 250 characters. This is a UI budget, not a storage limit. A description can be longer in the YAML — but only the first 250 characters appear in the card. The remainder appears only when the user inspects the skill directly.

Structure descriptions for the card: state purpose and invocation vocabulary in the first 200 characters, leave the last 50 for a phrase that trails off gracefully if cut. Never front-load implementation details in a description — the user cannot act on how the skill works from the listing view.

29.4 Plugin Architecture: Manifest Validation, Marketplace Sync, Version Management, Scope Isolation

A plugin packages hooks, skills, commands, agents, executables, and MCP servers into a single distributable unit. Where individual SKILL.md files and hook configurations are easy to manage, a plugin with a full structure and a marketplace distribution mechanism is what makes the extension ecosystem composable.

Manifest Validation at Install Time

The harness validates plugin.json before installing anything. The validation is intentionally strict: a plugin with a malformed manifest fails the install completely, rather than installing partially with unknown behavior.

import json
import re
from pathlib import Path


REQUIRED_FIELDS = {"name", "version", "description", "author"}
SEMVER_RE = re.compile(r"^\d+\.\d+\.\d+$")
NAME_RE = re.compile(r"^[a-z][a-z0-9-]*$")


class PluginManifestError(ValueError):
    pass


def validate_manifest(plugin_dir: Path) -> dict:
    """
    Validate plugin.json and return the parsed manifest.
    Raises PluginManifestError on any validation failure.
    """
    manifest_path = plugin_dir / ".claude-plugin" / "plugin.json"
    if not manifest_path.exists():
        raise PluginManifestError(
            f"Missing .claude-plugin/plugin.json in {plugin_dir}"
        )

    try:
        manifest = json.loads(manifest_path.read_text())
    except json.JSONDecodeError as exc:
        raise PluginManifestError(f"Malformed JSON in plugin.json: {exc}") from exc

    missing = REQUIRED_FIELDS - set(manifest.keys())
    if missing:
        raise PluginManifestError(
            f"plugin.json missing required fields: {', '.join(sorted(missing))}"
        )

    if not NAME_RE.match(manifest["name"]):
        raise PluginManifestError(
            f"plugin name '{manifest['name']}' must be lowercase alphanumeric with hyphens"
        )

    if not SEMVER_RE.match(manifest["version"]):
        raise PluginManifestError(
            f"version '{manifest['version']}' must be semver (MAJOR.MINOR.PATCH)"
        )

    author = manifest.get("author", {})
    if not isinstance(author, dict) or "name" not in author:
        raise PluginManifestError("author must be an object with a 'name' field")

    return manifest

Call validate_manifest before touching any other file in the plugin directory. If validation passes, you have a manifest you can reason about. If it raises, abort and tell the user exactly what is wrong.

Marketplace Sync

Marketplace sync is a two-phase operation: refresh the index, then apply updates to installed plugins.

import hashlib
import subprocess
from dataclasses import dataclass
from datetime import datetime, timezone
from pathlib import Path


@dataclass
class MarketplaceEntry:
    marketplace_id: str
    repo: str                     # e.g. "anthropics/claude-plugins-official"
    install_location: Path
    last_updated: datetime | None = None


def sync_marketplace(entry: MarketplaceEntry) -> bool:
    """
    Pull the latest marketplace index from GitHub.
    Returns True if the index was updated, False if already current.
    """
    clone_cmd = ["git", "-C", str(entry.install_location), "pull", "--ff-only"]
    clone_or_init = (
        clone_cmd
        if entry.install_location.exists()
        else [
            "git",
            "clone",
            f"https://github.com/{entry.repo}.git",
            str(entry.install_location),
        ]
    )

    result = subprocess.run(
        clone_or_init,
        capture_output=True,
        text=True,
        timeout=30,
    )
    if result.returncode != 0:
        raise RuntimeError(
            f"Marketplace sync failed for {entry.marketplace_id}: {result.stderr}"
        )

    entry.last_updated = datetime.now(tz=timezone.utc)
    return "Already up to date." not in result.stdout


def list_available_plugins(entry: MarketplaceEntry) -> list[dict]:
    """Return all plugins with valid manifests in the marketplace."""
    plugins = []
    for plugin_dir in entry.install_location.iterdir():
        if not plugin_dir.is_dir():
            continue
        try:
            manifest = validate_manifest(plugin_dir)
            plugins.append(manifest)
        except PluginManifestError:
            pass  # Skip malformed plugins, do not raise
    return plugins

The git-based sync model means marketplaces are versioned, auditable, and rollback-able. If a plugin update breaks something, git -C <install_location> log shows exactly what changed. This is the same property that makes the harness's own config management reliable.

Version Management

The installed plugin record stores both the declared version and the git commit SHA. Use both:

@dataclass
class InstalledPlugin:
    name: str
    marketplace_id: str
    scope: str          # "user" or "project"
    install_path: Path
    version: str
    installed_at: datetime
    git_commit_sha: str

    @property
    def registry_key(self) -> str:
        return f"{self.name}@{self.marketplace_id}"

    def is_current(self, available_sha: str) -> bool:
        return self.git_commit_sha == available_sha

    def needs_update(self, available_version: str) -> bool:
        """Compare semver strings. Returns True if available_version is newer."""
        installed = tuple(int(x) for x in self.version.split("."))
        available = tuple(int(x) for x in available_version.split("."))
        return available > installed

The needs_update check compares semver tuples. The is_current check compares SHAs. Use needs_update for user-facing "updates available" notifications. Use is_current for integrity verification — a plugin that has been manually edited will have a SHA mismatch even if the declared version is unchanged.

Scope Isolation

User-scope and project-scope plugins are isolated at the filesystem level. A user-scope install lives in ~/.claude/plugins/installed/. A project-scope install lives in .claude/plugins/installed/ within the project. The harness resolves the full plugin list by merging both scopes at session start.

Scope isolation has two consequences. First, a project can override a user-level plugin with a local version — the project-scope install takes precedence when names conflict. This is the mechanism for pinning a specific plugin version in a project without affecting other projects. Second, uninstalling a project-scope plugin does not affect users who have the same plugin installed at user scope, and vice versa.

Enterprise operators can enforce scope using the allowedChannelPlugins setting, which whitelists plugins by name, and strictKnownMarketplaces, which prevents installation from any marketplace not listed in known_marketplaces.json. These settings live in managed settings that override user config.

29.5 MCP Hosting: Implementing an MCP Server Your Harness Can Consume (and Expose)

Chapter 19 covered MCP consumption — connecting your harness to external MCP servers. This section covers the other direction: implementing an MCP server that your harness exposes as a tool surface, and implementing an MCP server that your harness itself can consume.

Implementing a stdio MCP Server in Node.js

The MCP SDK for Node.js is the reference implementation. A minimal server that exposes two tools:

// tools/mcp-audit-server/index.ts
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import {
  CallToolRequestSchema,
  ListToolsRequestSchema,
} from "@modelcontextprotocol/sdk/types.js";
import * as fs from "fs/promises";
import * as path from "path";

const AUDIT_LOG = process.env.AUDIT_LOG_PATH ?? "/tmp/harness-audit.jsonl";

const server = new Server(
  { name: "harness-audit", version: "1.0.0" },
  { capabilities: { tools: {} } }
);

server.setRequestHandler(ListToolsRequestSchema, async () => ({
  tools: [
    {
      name: "audit_write",
      description: "Append an audit event to the session audit log.",
      inputSchema: {
        type: "object",
        properties: {
          event_type: {
            type: "string",
            description: "Event type identifier (e.g. 'tool_blocked', 'cost_alert')",
          },
          payload: {
            type: "object",
            description: "Arbitrary event data",
          },
        },
        required: ["event_type", "payload"],
      },
    },
    {
      name: "audit_read",
      description: "Read the last N audit events from the session audit log.",
      inputSchema: {
        type: "object",
        properties: {
          limit: {
            type: "number",
            description: "Number of events to return (default 20)",
          },
        },
      },
    },
  ],
}));

server.setRequestHandler(CallToolRequestSchema, async (request) => {
  const { name, arguments: args } = request.params;

  if (name === "audit_write") {
    const entry = JSON.stringify({
      ts: new Date().toISOString(),
      event_type: args.event_type,
      payload: args.payload,
    });
    await fs.appendFile(AUDIT_LOG, entry + "\n", "utf-8");
    return { content: [{ type: "text", text: "OK" }] };
  }

  if (name === "audit_read") {
    const limit: number = (args.limit as number) ?? 20;
    let text: string;
    try {
      const raw = await fs.readFile(AUDIT_LOG, "utf-8");
      const lines = raw.trim().split("\n").filter(Boolean);
      text = lines.slice(-limit).join("\n");
    } catch {
      text = "(no audit log yet)";
    }
    return { content: [{ type: "text", text }] };
  }

  throw new Error(`Unknown tool: ${name}`);
});

async function main(): Promise<void> {
  const transport = new StdioServerTransport();
  await server.connect(transport);
}

main().catch(console.error);

Register this server in your project's .mcp.json:

{
  "mcpServers": {
    "harness-audit": {
      "type": "stdio",
      "command": "node",
      "args": ["./tools/mcp-audit-server/index.js"],
      "env": {
        "AUDIT_LOG_PATH": "${HOME}/.claude/audit/session.jsonl"
      }
    }
  }
}

From this point, mcp__harness-audit__audit_write and mcp__harness-audit__audit_read appear in the tool surface. Claude can call them. Your hooks can call them. The audit trail accumulates across all sessions.

Exposing Your Harness as an MCP Server

claude mcp serve starts Claude Code itself as an MCP server. Any other agent — a second Claude Code instance, a LangChain agent, an Orchestrator — can connect to it and call claude_code as a tool. This is the mechanism for hierarchical agent trees where a parent agent delegates work to a child Claude Code instance.

# Start the harness as an MCP server on stdio
claude mcp serve

# Or specify a working directory for the server instance
claude mcp serve --cwd /path/to/subproject

The server exposes a single tool: claude_code, which accepts a prompt string and returns the agent's full response. From the parent's perspective, calling claude_code is identical to calling any other MCP tool. From the child's perspective, it receives a fresh harness session with its own context, tools, and permission profile.

This composition model is what makes large multi-agent architectures tractable. The orchestrator does not need to know the implementation details of what it delegates. It calls claude_code with a description of the task, and the child harness handles everything within its own session boundary.

29.6 Lab: Build an Extensible Harness with Hooks, Skills, and Plugin Marketplace

This lab builds a complete extensibility layer from scratch: a hook runner, a skill registry, a plugin loader, and a minimal marketplace. The structure is deliberately small enough to read in one sitting but complete enough to build on.

Project Structure

Step 1: Hook Runner

# harness/hook_runner.py
from __future__ import annotations

import subprocess
from dataclasses import dataclass
from pathlib import Path
from typing import Any

from .events import HarnessEvent, HookEventPayload


@dataclass
class HookConfig:
    command: str
    timeout_ms: int = 5000
    status_message: str = ""
    matcher: str = ""          # empty = match all tools
    condition: str = ""        # optional if-condition expression


@dataclass
class HookResult:
    exit_code: int
    stdout: str
    stderr: str
    timed_out: bool = False

    @property
    def is_pass(self) -> bool:
        return self.exit_code == 0

    @property
    def is_warning(self) -> bool:
        return self.exit_code == 1

    @property
    def is_block(self) -> bool:
        return self.exit_code == 2


class HookRunner:
    def __init__(self, working_dir: Path) -> None:
        self._cwd = working_dir
        self._registry: dict[HarnessEvent, list[HookConfig]] = {}

    def register(self, event: HarnessEvent, config: HookConfig) -> None:
        self._registry.setdefault(event, []).append(config)

    def dispatch(
        self,
        event: HarnessEvent,
        payload: HookEventPayload,
    ) -> list[HookResult]:
        """
        Fire all hooks registered for this event in registration order.
        For PreToolUse: stop at first exit-2 block.
        For all others: run all hooks regardless of prior results.
        """
        configs = self._registry.get(event, [])
        results: list[HookResult] = []

        for config in configs:
            if not self._matches(config, payload):
                continue

            result = self._run(config, payload)
            results.append(result)

            # PreToolUse: first block terminates the chain
            if event == HarnessEvent.PRE_TOOL_USE and result.is_block:
                break

        return results

    def _matches(self, config: HookConfig, payload: HookEventPayload) -> bool:
        if not config.matcher:
            return True
        tool_name = payload.tool_name or ""
        return tool_name in config.matcher.split("|")

    def _run(self, config: HookConfig, payload: HookEventPayload) -> HookResult:
        timeout_sec = config.timeout_ms / 1000.0
        try:
            proc = subprocess.run(
                config.command,
                shell=True,
                input=payload.to_json(),
                capture_output=True,
                text=True,
                timeout=timeout_sec,
                cwd=self._cwd,
            )
            return HookResult(
                exit_code=proc.returncode,
                stdout=proc.stdout,
                stderr=proc.stderr,
            )
        except subprocess.TimeoutExpired:
            return HookResult(
                exit_code=1,
                stdout="",
                stderr=f"Hook timed out after {config.timeout_ms}ms",
                timed_out=True,
            )

Step 2: Skill Registry

# harness/skill_registry.py
from __future__ import annotations

import fnmatch
from pathlib import Path

from .skill_parser import SkillFrontmatter, parse_skill_file


class SkillRegistry:
    def __init__(self) -> None:
        self._skills: dict[str, tuple[SkillFrontmatter, Path]] = {}

    def load_from(self, base_dir: Path) -> int:
        """
        Scan base_dir/.claude/skills/**/SKILL.md and load all valid skills.
        Returns the number of skills loaded.
        """
        skills_dir = base_dir / ".claude" / "skills"
        if not skills_dir.exists():
            return 0

        count = 0
        for skill_file in sorted(skills_dir.rglob("SKILL.md")):
            fm = parse_skill_file(skill_file)
            if fm is None:
                continue
            if fm.name not in self._skills:
                self._skills[fm.name] = (fm, skill_file)
                count += 1
        return count

    def get_active(self, project_files: list[Path]) -> list[SkillFrontmatter]:
        """
        Return skills that are active given the current project file list.
        Skills without a paths filter are always active.
        """
        active = []
        file_strs = [str(f) for f in project_files]

        for fm, _ in self._skills.values():
            if not fm.paths:
                active.append(fm)
                continue
            if any(
                fnmatch.fnmatch(f, pattern)
                for f in file_strs
                for pattern in fm.paths
            ):
                active.append(fm)

        return sorted(active, key=lambda s: s.name)

    def get_body(self, name: str) -> str | None:
        """Return the markdown body (below frontmatter) of a skill by name."""
        if name not in self._skills:
            return None
        _, skill_file = self._skills[name]
        content = skill_file.read_text(encoding="utf-8")
        # Strip frontmatter block
        parts = content.split("---", 2)
        if len(parts) >= 3:
            return parts[2].strip()
        return content

Step 3: Plugin Loader

# harness/plugin_loader.py
from __future__ import annotations

import json
from pathlib import Path

from .plugin_manifest import validate_manifest, PluginManifestError
from .hook_runner import HookRunner, HookConfig, HarnessEvent
from .skill_registry import SkillRegistry


class PluginLoader:
    def __init__(
        self,
        hook_runner: HookRunner,
        skill_registry: SkillRegistry,
    ) -> None:
        self._hooks = hook_runner
        self._skills = skill_registry
        self._loaded: list[str] = []

    def load_plugin(self, plugin_dir: Path, scope: str = "user") -> None:
        """
        Validate and load a plugin. Registers all hooks and skills it provides.
        Raises PluginManifestError if the manifest is invalid.
        """
        manifest = validate_manifest(plugin_dir)
        name = manifest["name"]

        # Load hooks
        hooks_dir = plugin_dir / "hooks"
        if hooks_dir.exists():
            self._load_hooks(hooks_dir)

        # Load skills
        skills_dir = plugin_dir / "skills"
        if skills_dir.exists():
            self._skills.load_from(plugin_dir)

        self._loaded.append(f"{name}@{scope}")

    def _load_hooks(self, hooks_dir: Path) -> None:
        """
        Convention: hook files are named after the event they handle.
        e.g. PreToolUse.py, PostToolUse.sh, Stop.py
        """
        for hook_file in hooks_dir.iterdir():
            if not hook_file.is_file():
                continue
            event_name = hook_file.stem
            try:
                event = HarnessEvent(event_name)
            except ValueError:
                continue  # Not a recognized event name

            config = HookConfig(
                command=str(hook_file.resolve()),
                timeout_ms=5000 if event == HarnessEvent.PRE_TOOL_USE else 30000,
            )
            self._hooks.register(event, config)

    def load_from_installed(
        self,
        installed_json: Path,
        scope: str = "user",
    ) -> int:
        """Load all enabled plugins from an installed_plugins.json file."""
        if not installed_json.exists():
            return 0

        data = json.loads(installed_json.read_text())
        count = 0
        for _key, entries in data.get("plugins", {}).items():
            for entry in entries:
                if entry.get("scope") != scope:
                    continue
                plugin_dir = Path(entry["installPath"])
                try:
                    self.load_plugin(plugin_dir, scope)
                    count += 1
                except (PluginManifestError, FileNotFoundError):
                    pass  # Skip broken installs silently
        return count

Step 4: Wire Everything Together

# harness/__init__.py
from __future__ import annotations

from pathlib import Path

from .events import HarnessEvent, HookEventPayload
from .hook_runner import HookConfig, HookRunner
from .plugin_loader import PluginLoader
from .skill_registry import SkillRegistry


def build_harness(project_dir: Path) -> tuple[HookRunner, SkillRegistry, PluginLoader]:
    """
    Construct and initialize the full extensibility layer for a project.
    Returns the hook runner, skill registry, and plugin loader.
    """
    runner = HookRunner(working_dir=project_dir)
    skills = SkillRegistry()
    loader = PluginLoader(hook_runner=runner, skill_registry=skills)

    # Load project-level skills directly
    skills.load_from(project_dir)

    # Load user-level plugins
    user_installed = Path.home() / ".claude" / "plugins" / "installed_plugins.json"
    loader.load_from_installed(user_installed, scope="user")

    # Load project-level plugins
    project_installed = project_dir / ".claude" / "plugins" / "installed_plugins.json"
    loader.load_from_installed(project_installed, scope="project")

    # Register any local hook scripts from .claude/hooks/
    local_hooks = project_dir / ".claude" / "hooks"
    if local_hooks.exists():
        for hook_file in local_hooks.iterdir():
            if hook_file.suffix in {".py", ".sh"} and hook_file.is_file():
                event_name = hook_file.stem
                try:
                    event = HarnessEvent(event_name)
                    config = HookConfig(command=str(hook_file.resolve()))
                    runner.register(event, config)
                except ValueError:
                    pass  # Skip non-event-named scripts

    return runner, skills, loader

// .claude-plugin/plugin.json
{
  "name": "audit-logger",
  "version": "1.0.0",
  "description": "Logs every tool call to a JSONL audit file and exposes /audit-summary to review session activity.",
  "author": {
    "name": "Platform Team",
    "email": "platform@yourorg.com"
  }
}
#!/usr/bin/env python3
# hooks/PostToolUse.py
from __future__ import annotations

import json
import sys
from datetime import datetime, timezone
from pathlib import Path

AUDIT_PATH = Path.home() / ".claude" / "audit" / "session.jsonl"


def main() -> None:
    payload = json.load(sys.stdin)
    AUDIT_PATH.parent.mkdir(parents=True, exist_ok=True)
    entry = {
        "ts": datetime.now(tz=timezone.utc).isoformat(),
        "tool": payload.get("tool_name"),
        "input_summary": str(payload.get("tool_input", {}))[:200],
    }
    with AUDIT_PATH.open("a", encoding="utf-8") as fh:
        fh.write(json.dumps(entry) + "\n")
    sys.exit(0)


if __name__ == "__main__":
    main()

  | python3 .claude-plugin/../hooks/PostToolUse.py

# Verify audit log was written
tail -3 ~/.claude/audit/session.jsonl

Expected output from the last command: three JSON objects with ts, tool, and input_summary fields. If the log file does not exist, the hook did not execute — check that the PostToolUse.py is on a path the loader resolved correctly.

The four systems covered in this chapter — hooks, skills, plugins, and MCP hosting — are the complete extension surface. Hooks govern what happens inside the control loop. Skills shape how users invoke the agent. Plugins package both into distributable units. MCP hosting lets your harness participate in larger agent hierarchies.

As discussed in Chapter 18, the plugin contract is between author, marketplace, and enterprise operator. Building your extension system with that contract in mind from the start — manifest validation, scope isolation, version pinning — makes the difference between an extensibility layer that you can safely deploy and one you are always afraid to touch.
