Chapter 31: Autonomous Agent Patterns

"The difference between a tool and an agent is not intelligence — it is the loop. A tool waits to be called. An agent calls itself."

This is the first chapter of Part VII: Production Patterns and Case Studies. The preceding parts built up the machinery: tools, workflows, hooks, scheduling, context management. Here those pieces compose into something categorically different — an agent that operates without a human in the loop, running continuously against production systems, making decisions, posting artifacts, and healing its own failures.

The patterns in this chapter are not theoretical. They come from sec-pr: a production autonomous agent that reviews security vulnerabilities across pull requests in two Azure DevOps organizations, processes 319 tracked PRs, runs on an hourly cron, and has been operating without human intervention for months. What broke, how it was fixed, and what the failure taught about agent design — that is the substance of this chapter.

31.1 The Autonomous Loop: Trigger → Scan → Act → Verify → Sleep → Repeat

Every autonomous agent, regardless of domain, is fundamentally a loop over a resource collection. The resource changes — pull requests, log files, sensor readings, repository branches — but the loop structure does not.

flowchart TD
    T([Trigger: cron / webhook / manual]) --> A[ACQUIRE resources]
    A --> S[SCAN each resource]
    S --> AC[ACT on findings]
    AC --> V[VERIFY artifacts exist]
    V --> UPD[UPDATE tracker state]
    UPD --> SLP[SLEEP until next trigger]
    SLP --> T

    V -- artifact missing --> RESCAN[Add to rescan queue]
    RESCAN --> S
    UPD -- phantom detected --> PHANTOM[Reset phantom entry]
    PHANTOM --> RESCAN

The loop has six responsibilities, and every production failure can be traced to violating exactly one of them.

ACQUIRE. Fetch the current set of resources from the authoritative source. Do not use cached state as the authoritative list — the world changed while the agent was sleeping. Query the live system. In sec-pr this means calling the ADO API to enumerate open PRs in both organizations, filtered by --max-age 15 days. Every tick starts with a fresh enumeration, not a stored list.

SCAN. Process each resource for actionable content. This step has a precision requirement that separates production agents from toy demos: scanning must produce file:line findings. Surface-level triage — "this PR touches authentication code" — is not a scan. A scan produces src/auth/token.py:47 — hardcoded secret in JWT signing key. The distinction is what determines whether downstream steps can act on the findings.

ACT. Execute the consequence of the scan. Post a comment, apply a patch, open a ticket, cast a vote. The act must be complete before the loop advances. Partial acts — posting a comment but not verifying it landed, voting without having first posted findings — are the source of ghost state, where the tracker believes something happened that did not.

VERIFY. Confirm that artifacts exist on disk and that API-posted content is actually retrievable. Do not trust the success return code from an API call. Query back. Retrieve the comment by ID. Confirm the vote value matches what was intended. This step is where phantom detection lives.

UPDATE TRACKER. Write the new state to the persistent state file. The tracker is the agent's memory across loop iterations. Its contents determine what gets rescanned, what gets skipped, and what the monitoring phase treats as resolved. If tracker state diverges from reality — which it will, through network errors, restarts, and external mutations — the agent must correct it at this step, not accept it as ground truth.

SLEEP. Wait until the next trigger. For cron-driven agents this is implicit — the agent terminates after the loop and the scheduler fires it again. For daemon agents this is an explicit ScheduleWakeup or a sleep() in a monitoring loop. The sleep interval determines how quickly the agent responds to new events and how much load it places on external systems.

The no-pause contract

A critical constraint that breaks naive implementations: never stop between items in the same collection. The loop over 319 PRs must complete fully before transitioning to monitoring mode. An agent that processes 50 PRs, pauses to report progress, then asks "should I continue?" violates this contract and produces inconsistent state — some PRs reviewed, others not, with no reliable way to know which are which without re-querying everything.

The enforcement is simple and belongs in the system prompt:

NEVER stop between PRs — complete ALL N before switching to monitoring mode.
NEVER ask "should I continue?" — always YES, execute the full pipeline.

These are not style preferences. They are structural invariants. An agent that asks permission mid-loop has delegated its control flow to a human who is not watching.

31.2 State Machines: The PR Pipeline

Ad-hoc agentic code fails in ways that are hard to diagnose because there is no model of what state the system should be in. Adding a state machine is not bureaucracy — it is the mechanism by which failures become observable.

The sec-pr PR pipeline has ten named states. Each PR in the tracker carries a current state. The state machine defines which transitions are legal, what artifact must exist to enter a state, and what happens if an artifact is missing.

stateDiagram-v2
    [*] --> ACQUIRE
    ACQUIRE --> CLONE : PR metadata fetched
    CLONE --> ANALYZE : diff downloaded
    ANALYZE --> GENERATE_FINDINGS : diff parsed
    GENERATE_FINDINGS --> GENERATE_PATCHES : findings confirmed
    GENERATE_PATCHES --> POST_COMMENT : patches generated
    POST_COMMENT --> POST_INLINE_THREADS : overview comment posted
    POST_INLINE_THREADS --> VERIFY_ARTIFACTS : inline threads posted
    VERIFY_ARTIFACTS --> VOTE : all artifacts confirmed on disk
    VOTE --> UPDATE_TRACKER : vote cast (or skipped)
    UPDATE_TRACKER --> [*] : state written

    VERIFY_ARTIFACTS --> GENERATE_FINDINGS : artifact missing — rescan
    VOTE --> VOTE : vote reset detected — restore

Why each state exists

ACQUIRE → CLONE. Separation between knowing a PR exists and having its content. The ADO API returns PR metadata in batch. The diff must be fetched separately, per PR, and is larger. This boundary lets the agent enumerate all PRs cheaply, then prioritize which diffs to fetch based on age, author, or modified paths.

CLONE → ANALYZE. A diff is raw text. Analysis transforms it into structured findings with file paths, line numbers, and severity classifications. This step can fail (malformed diff, binary-only changes, diff too large) without failing the PR as a whole. An agent that merges clone and analyze into a single step cannot distinguish "we got the diff but the analyzer crashed" from "we never got the diff at all."

GENERATE_FINDINGS → GENERATE_PATCHES. Findings come first because patches are optional — a PR with no findings needs no patches. Separating these steps means a no-finding result does not spin up the patch generator, saving context and API calls for the majority of PRs that turn out clean.

POST_COMMENT → POST_INLINE_THREADS. The overview comment (summary, severity table, recommendations) posts first. Inline threads (file:line annotations) come second. This ordering matters because inline threads require the overview comment ID for cross-referencing. If inline thread posting fails, the overview is still visible to the PR author. A partial failure is better than a total failure.

VERIFY_ARTIFACTS. This is the pivot state. Before casting a vote, the agent confirms that everything it believes it posted is actually retrievable. Missing artifact → back to GENERATE_FINDINGS. A rescan, not a retry — because the artifact is missing at the source, not just at the network layer.

VOTE. The decision point. The rule is binary: if any finding has severity CRITICAL or HIGH, cast a -5 vote (reject). Otherwise, no vote — not a +10, not a 0, nothing. An overview comment is always posted, but votes are conditional. This distinction prevents auto-approval of PRs that simply have no findings in the current scan window.

Pipeline state machine in code

In practice, the state machine is implemented as a dictionary mapping state names to handler functions, with explicit transition validation:

const PIPELINE = {
  ACQUIRE:             acquirePR,
  CLONE:               cloneDiff,
  ANALYZE:             analyzeDiff,
  GENERATE_FINDINGS:   generateFindings,
  GENERATE_PATCHES:    generatePatches,
  POST_COMMENT:        postOverviewComment,
  POST_INLINE_THREADS: postInlineThreads,
  VERIFY_ARTIFACTS:    verifyArtifacts,
  VOTE:                castVote,
  UPDATE_TRACKER:      updateTracker,
}

const TRANSITIONS = {
  ACQUIRE:             ['CLONE'],
  CLONE:               ['ANALYZE'],
  ANALYZE:             ['GENERATE_FINDINGS'],
  GENERATE_FINDINGS:   ['GENERATE_PATCHES'],
  GENERATE_PATCHES:    ['POST_COMMENT'],
  POST_COMMENT:        ['POST_INLINE_THREADS'],
  POST_INLINE_THREADS: ['VERIFY_ARTIFACTS'],
  VERIFY_ARTIFACTS:    ['VOTE', 'GENERATE_FINDINGS'],  // rescan path
  VOTE:                ['UPDATE_TRACKER'],
  UPDATE_TRACKER:      ['DONE'],
}

async function runPipeline(pr, startState = 'ACQUIRE') {
  let state = startState
  while (state !== 'DONE') {
    const result = await PIPELINE[state](pr)
    const nextStates = TRANSITIONS[state]
    state = result.nextState
    if (!nextStates.includes(state)) {
      throw new Error(`Illegal transition: ${PIPELINE[state-1]} → ${state}`)
    }
  }
}

The explicit transition validation is the difference between "something went wrong" and "the agent attempted an illegal state transition from VERIFY_ARTIFACTS to VOTE while an artifact was missing." The first is a debugging session. The second is a five-minute fix.

No step can be skipped

The invariant that every step in the pipeline must execute before the next step begins is enforced at the transition map level, not at the caller level. A handler cannot return nextState: 'VOTE' if the current state is ANALYZE. This prevents the class of failure where a high-pressure context — many PRs queued, cron about to fire again — tempts the agent to shortcut by skipping artifact verification.

The failure mode being prevented: the agent votes on a PR, the PR author merges, later the overview comment and inline threads are found to be missing. The PR owner has no explanation for why their code was rejected, because the rejection evidence was never actually posted. The vote was cast on phantom artifacts.

31.3 Self-Healing: Phantom Detection, Drift Correction, Vote-Reset Auto-Restore

The most important shift in thinking when building autonomous agents is accepting that the world will diverge from your model of it. External systems reset state. Network calls succeed but produce no lasting artifact. Users undo what the agent did. The agent must detect these divergences and correct them without human intervention.

Three failure classes require three distinct healing mechanisms.

Phantom detection

A phantom is a tracker entry that claims an artifact exists when it does not. Phantoms are created when an API call returns 200 but the artifact was not durably stored, when a disk write failed silently, when the agent was interrupted mid-step, or when a prior session crashed between posting an artifact and recording it.

Detection: On every monitor tick — not just after a rescan — validate every tracker entry that claims an artifact exists by actually checking for it. For sec-pr this means:

def detect_phantoms(tracker: dict, artifacts_dir: Path) -> list[str]:
    phantoms = []
    for pr_id, entry in tracker.items():
        if entry.get('state') in ('VOTED', 'COMPLETE'):
            # Verify disk artifacts
            expected = [
                artifacts_dir / f"{pr_id}_overview.md",
                artifacts_dir / f"{pr_id}_findings.json",
            ]
            if not all(p.exists() for p in expected):
                phantoms.append(pr_id)
            # Verify ADO artifact retrievability
            if not ado_comment_exists(entry['comment_id']):
                phantoms.append(pr_id)
    return list(set(phantoms))

Correction: Reset phantom entries to GENERATE_FINDINGS state. Add them to the rescan queue. Do not delete them — preserve the history of what was attempted and when. The rescan will create fresh artifacts.

The production rule: NEVER trust tracker status. Validate ALL PRs against ADO every tick. This rule was written the day a drift bug caused a missed PR. The PR had been marked COMPLETE in the tracker after a partial write. The actual ADO comment was missing. The PR merged without security review. The lesson was that the tracker is a cache, not a source of truth.

Drift correction

Drift is the accumulation of small discrepancies between tracker state and reality. Unlike phantoms (discrete artifact mismatches), drift is the systemic condition where the tracker's view of the world is stale or wrong in multiple dimensions simultaneously.

The causes are mundane: the agent ran, posted a comment, then the cron fired a second instance before the first finished. Two instances updated the tracker independently. Now the tracker has conflicting state for several PRs.

The correction protocol:

flowchart TD
    TICK[Monitor tick] --> ENUM[Enumerate live PRs from ADO]
    ENUM --> LOAD[Load tracker state]
    LOAD --> DIFF{Compare each PR}
    DIFF -- PR in ADO, not in tracker --> ADD[Add to tracker as ACQUIRE]
    DIFF -- PR in tracker, not in ADO --> MARK[Mark as CLOSED]
    DIFF -- States match --> SKIP[No action]
    DIFF -- States diverge --> RECON[Reconcile: ADO wins]
    ADD --> QUEUE[Add new PRs to scan queue]
    RECON --> QUEUE
    QUEUE --> SCAN[Proceed with scan]

ADO is authoritative. The tracker is a cache. When they disagree, update the cache. The only exception is vote state: if the tracker says a vote was cast but ADO shows no vote, that is a phantom — add to rescan queue, do not accept the ADO state as evidence that no vote is needed.

Vote-reset auto-restore

PR owners reset votes. This is a feature of every code review system — the author pushes a new commit and the system clears existing votes, forcing reviewers to re-evaluate. For a human reviewer this is natural workflow. For an autonomous security agent it is an edge case that breaks the completion contract.

Detection: On every monitor tick, for every PR in VOTED or COMPLETE state, query the current vote value from ADO. If the vote is absent or different from what the tracker recorded:

def check_vote_drift(pr_id: str, tracker: dict) -> bool:
    expected_vote = tracker[pr_id].get('vote_cast')
    if expected_vote is None:
        return False  # no vote expected
    current_vote = ado_get_vote(pr_id)
    return current_vote != expected_vote

The decision: If the vote was reset by a new commit, the PR should be rescanned — new code was pushed, the prior findings may no longer apply. If the vote was reset manually by the PR owner without a new commit, the prior findings still apply and the vote should be restored.

Distinguishing the two cases requires checking the commit timeline:

def should_rescan_or_restore(pr_id: str, tracker: dict) -> Literal['rescan', 'restore']:
    last_commit_time = ado_get_last_commit_time(pr_id)
    last_scan_time = tracker[pr_id]['scan_timestamp']
    if last_commit_time > last_scan_time:
        return 'rescan'  # new code pushed, must re-evaluate
    return 'restore'    # manual reset, restore prior vote

This logic closes the feedback loop. The PR owner cannot silently undo a security rejection by clearing the vote — the agent detects and restores it on the next tick, with a comment explaining why.

31.4 Context Refresh: Hourly Resets, Checkpoints, State File Recovery

Autonomous agents that run continuously degrade. Not because the model forgets — it has no memory between API calls — but because the conversation accumulates context that was relevant at hour one and is noise at hour eight. The harness starts including tool results from the morning's first scan in every subsequent API call, even though those results are no longer actionable. Context bloat produces slower, less coherent responses. Eventually it produces wrong ones.

The rule from production: context degrades meaningfully after approximately 60 minutes of continuous operation. The symptom is not dramatic — the agent does not hallucinate wildly. It starts missing edge cases, producing less precise findings, overlooking patterns it caught cleanly earlier. The cure is a full context reset.

The checkpoint-clear-resume pattern

Before clearing context, save all state that cannot be recovered from external systems.

sequenceDiagram
    participant A as Agent
    participant SF as State File
    participant ADO as ADO API
    participant H as Harness

    Note over A: ~60min elapsed or<br/>token threshold approaching
    A->>SF: checkpoint_state(tracker, queue, metrics)
    SF-->>A: state written to disk
    A->>H: /clear (context reset)
    H->>A: fresh session starts
    H->>A: SessionStart hook fires
    A->>SF: recover_state()
    SF-->>A: tracker, queue, metrics restored
    A->>ADO: validate tracker vs live state
    ADO-->>A: reconciliation complete
    Note over A: resume at next unprocessed PR

The checkpoint must include:

  • The tracker: all PR states, artifact paths, vote history
  • The active queue: which PRs are queued for rescan
  • Metrics: counters for the current run (scanned, posted, voted, skipped)
  • The current cron IDs: so the agent can verify and recreate them after recovery

State file format

The state file lives at ~/.claude/projects/<hash>/state/<domain>-state.md. Using markdown keeps it human-readable for debugging without sacrificing machine parseability — the file uses fenced JSON blocks that the recovery hook can extract with a regex.

# sec-pr State — 2026-07-28T14:23:11 CDT

## Run Metrics
- Scanned: 47
- Posted: 31
- Voted: 8
- Skipped: 16 (no findings)
- Rescanned: 3

## Active Queue

["PR-9801", "PR-9834", "PR-9901"]


## Tracker Snapshot

{ "PR-9801": {"state": "ACQUIRE", "org": "NMDAbbott", "age_days": 3}, "PR-9834": {"state": "VOTED", "vote_cast": -5, "scan_timestamp": "2026-07-28T13:45:00Z", ...}, ... }

The markdown wrapper is for the engineer reading the file during an incident. The JSON blocks are for the recovery hook. Both audiences are served by the same file.

Hook-based state persistence

Two hooks automate the checkpoint-and-recover lifecycle so it does not require manual intervention:

{
  "hooks": {
    "PreCompact": [
      {
        "matcher": "",
        "hooks": [{"type": "command", "command": "python3 ~/.claude/hooks/checkpoint-state.py"}]
      }
    ],
    "SessionStart": [
      {
        "matcher": "",
        "hooks": [{"type": "command", "command": "python3 ~/.claude/hooks/recover-state.py"}]
      }
    ]
  }
}

PreCompact fires before the harness summarizes the context window — the last moment before history is irreversibly compressed. The checkpoint hook writes the full tracker to the state file at this moment.

SessionStart fires at the beginning of every new session, before the first user message. The recovery hook reads the state file and prints a context message that the model reads before any prompt. The agent begins the session already knowing the tracker state, the active queue, and where it stopped.

The cron recreation check

After a context reset, the agent's scheduled jobs may be gone. The harness may have persisted them through the session, or they may have been lost. On every /sec-pr invocation, the agent checks CronList for its four expected weekday cron entries:

EXPECTED_CRONS = [
    {"cron": "7 9 * * 1-5",  "prompt": "/sec-pr"},
    {"cron": "7 11 * * 1-5", "prompt": "/sec-pr"},
    {"cron": "7 14 * * 1-5", "prompt": "/sec-pr"},
    {"cron": "7 16 * * 1-5", "prompt": "/sec-pr"},
]

def ensure_crons(existing: list[dict]) -> None:
    existing_patterns = {(c['cron'], c['prompt']) for c in existing}
    for expected in EXPECTED_CRONS:
        key = (expected['cron'], expected['prompt'])
        if key not in existing_patterns:
            cron_create(expected['cron'], expected['prompt'], recurring=True, durable=True)

This runs silently — no output to the user unless a cron was actually recreated. The agent heals its own scheduling infrastructure as part of normal startup.

31.5 Case Study: sec-pr — Autonomous Security PR Review Across Two ADO Organizations

Background

sec-pr is a security scanning agent that operates fully autonomously. Its mandate is straightforward: for every open pull request in two Azure DevOps organizations (NMDAbbott and NMD-MD), perform a security review, post findings as inline thread annotations, and cast a rejection vote if the findings include CRITICAL or HIGH severity issues. No human initiates a scan. No human monitors a dashboard. The agent wakes up, does the work, and sleeps until the next cron fires.

At peak operation: 2 ADO organizations, 319 tracked PRs (135 in NMDAbbott, 184 in NMD-MD), hourly cron monitoring, 15-day max age filter, 7 validated false positive patterns in the suppression database.

The complete pipeline

ACQUIRE → CLONE → ANALYZE → GENERATE_FINDINGS → GENERATE_PATCHES → 
POST_COMMENT → POST_INLINE_THREADS → VERIFY_ARTIFACTS → VOTE → UPDATE_TRACKER

Each step has a hard definition of done:

StepDone when
ACQUIREPR list fetched from live ADO API for both orgs
CLONEFull diff downloaded to artifacts/<pr_id>/diff.patch
ANALYZEDiff parsed into file segments with path:line index
GENERATE_FINDINGSFindings list with file:line:severity for each issue
GENERATE_PATCHESPatch block for each finding (or empty list if none applicable)
POST_COMMENTOverview comment ID returned and stored in tracker
POST_INLINE_THREADSAll inline thread IDs returned and stored in tracker
VERIFY_ARTIFACTSDisk files exist AND ADO API retrieves comment by ID
VOTEADO vote value matches intended value, or vote intentionally skipped
UPDATE_TRACKERState file written to disk with new state and all artifact IDs

Voting rules

The voting logic has five conditions, evaluated in order:

def determine_vote(findings: list[Finding], prior_state: dict) -> int | None:
    # 1. If any finding is CRITICAL or HIGH → reject vote (-5)
    if any(f.severity in ('CRITICAL', 'HIGH') for f in findings):
        return -5
    
    # 2. If no findings → no vote (not an approval)
    if not findings:
        return None
    
    # 3. If only MEDIUM/LOW/NONE findings → no vote
    max_sev = max(SEVERITY_ORDER[f.severity] for f in findings)
    if max_sev <= SEVERITY_ORDER['MEDIUM']:
        return None
    
    # 4. Never vote 10 (approve) under any circumstances
    # 5. Never cast a vote without first verifying artifacts exist
    return None

Rule 4 exists because an autonomous agent approving PRs is a different trust contract than an autonomous agent blocking them. Approval implies the scan was exhaustive and the code is safe. No automated scan can claim that. Rule 5 prevents the ghost state problem described in section 31.2.

The false positive database

Seven patterns appear repeatedly across the codebase and are legitimate concerns in the abstract but not exploitable in this context:

PatternWhy it firesWhy it is suppressed
.NET Zip SlipPath traversal in archive extractionFramework validates paths before extraction
Sideload bypassDLL search order attackInternal tooling, no external DLL paths
Internal test methodsMethods named test_* with no auth checkTest infrastructure, not exposed endpoints
DEV/QA-only endpointsRoutes behind IsDevelopment() guardGuard verified in all affected PRs
Dev scriptsScripts in /scripts/dev/Never deployed to production
Hash logsSHA-256 hash values loggedNon-reversible, not credential exposure
Known-safe configsConfig keys with _test_ in nameTest fixtures only

Each suppression entry in the database includes the original finding that triggered it, the PR where it was validated, and the reasoning. The database is a first-class artifact — reviewed and updated when new patterns emerge, not a silent allow-list.

What broke in production

The PR-9965 false-approve incident. The agent approved a PR after failing to check whether all threads were resolved. The check used a heuristic — if no open threads in the overview comment, all resolved — rather than querying each inline thread status individually. Two inline threads had been closed by the PR owner without actually addressing the findings. The agent interpreted "no open threads" as "all resolved" and voted approve.

Fix: the VERIFY_ARTIFACTS step now individually queries each thread ID stored in the tracker and checks resolution status before allowing a positive vote. The condition is a whitelist — specific thread IDs that were explicitly marked resolved with a "fixed in commit X" response — not the absence of open threads.

The status drift miss. On a Monday morning, the agent processed 47 PRs from a weekend batch. One PR — ID 35989 — was marked COMPLETE in the tracker from the prior Friday run. The Friday run had experienced a partial write: the overview comment was posted but the state file write failed mid-way. The tracker showed COMPLETE; the disk showed no findings file; ADO showed no vote. The agent skipped the PR because the tracker said it was done.

Fix: the phantom detection pass described in section 31.3 was added the same day. Every COMPLETE entry is now verified against disk artifacts AND ADO on every tick. PR-35989 style misses are structurally impossible with phantom detection in place.

The vote-reset non-response. A PR owner pushed a trivial formatting commit after receiving a -5 vote for a hardcoded credential finding. The new commit cleared the vote. The agent's prior findings were still valid — the credential was in the original diff and was not removed in the formatting commit. But the agent had no mechanism to detect that its vote had been cleared and took no action until the next full scan cycle, which ran 47 minutes later. By then the PR had been merged.

Fix: the monitor tick now checks vote state for every VOTED entry. If a vote is cleared and the last commit timestamp is before the scan timestamp (formatting commit, not substantive new code), the vote is restored immediately with a comment: "Restoring security vote — formatting-only commit does not address findings from prior scan."

Scale and operational profile

Running 319 PRs per cycle against a live ADO API requires rate limit awareness. The production configuration:

{
  "ado_rate_limit_rps": 4,
  "batch_size": 20,
  "inter_batch_sleep_ms": 500,
  "max_age_days": 15,
  "orgs": ["NMDAbbott", "NMD-MD"],
  "crons": [
    {"cron": "7 9 * * 1-5",  "id": "a1b2c3d4"},
    {"cron": "7 11 * * 1-5", "id": "903b1a1c"},
    {"cron": "7 14 * * 1-5", "id": "e5f6a7b8"},
    {"cron": "7 16 * * 1-5", "id": "c9d0e1f2"}
  ]
}

Four cron jobs per weekday — morning, late morning, early afternoon, late afternoon. The schedule is deliberately non-uniform (:07 instead of :00) to avoid the thundering-herd problem where every scheduled task in the organization fires simultaneously at the top of the hour.

The --max-age 15 filter applies equally to both organizations. A PR that has been open for 16 days is excluded from scanning not because it is unimportant but because a 16-day-old PR is deep in the review process and a new automated security comment is more likely to be noise than signal.

The overview comment — always posted

The invariant that surprised new users of the system: an overview comment is always posted to ADO, even when the scan finds nothing. A scan with no findings produces:

## Security Review — sec-pr

**Result:** Clean — no security findings detected.

**Scanned:** 23 files, 1,847 lines changed  
**False positive suppressions applied:** 2 (Zip Slip pattern, hash log pattern)  
**Scan timestamp:** 2026-07-28T14:23:11Z

This is not vanity — it is a receipt. The PR author knows the automated security scan ran. They know which suppression patterns were applied (and can ask questions if the suppression was wrong). They know the scan timestamp, so they know whether a subsequent commit has been scanned yet. The absence of an overview comment is a signal that something failed, not a signal that the PR is clean.

Votes are conditional. Comments are unconditional. This distinction is fundamental to the trust model of an autonomous security agent.

The patterns in this chapter — the autonomous loop, the state machine, the self-healing mechanisms, the context refresh discipline — are not specific to security review. The same structure applies to any long-running agent that operates over a changing resource collection. The sec-pr case study is concrete because it came from failure. Every healing mechanism in section 31.3 was written the day after the failure it prevents. That is the normal timeline for production agent engineering. Design for the failure modes you know exist; instrument to discover the ones you do not.

The next chapter applies these patterns to a different domain: autonomous incident response, where the resource collection is a live alert feed and the action space includes calling APIs, modifying infrastructure, and paging humans.
