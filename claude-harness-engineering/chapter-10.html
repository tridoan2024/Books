Chapter 10: Task Management — TaskCreate/Get/Update/List

"A task that exists only in the model's context window is not a task. It is a hope."

10.1 Task Lifecycle: pending → in_progress → completed (or deleted)

The task system is Claude Code's answer to a fundamental problem in long-running agentic work: the model's working memory is a context window. Every time the control loop makes another API call, the model reconstructs its understanding of what it was doing from the conversation history. For short tasks — five tool calls, done in thirty seconds — this is fine. For multi-hour workflows spanning hundreds of tool calls, it is not. The conversation gets compressed, context gets lost, and the model drifts.

Tasks are persistent, structured state that lives outside the context window. They survive compaction. A subagent can pick up a task that another agent created an hour ago. An autonomous daemon can check what work remains after a session restart. Tasks are the harness's equivalent of a ticket system — lightweight, structured, and authoritative even when the model's own memory is not.

The lifecycle is a state machine with four states:

stateDiagram-v2
    [*] --> pending : TaskCreate
    pending --> in_progress : TaskUpdate(status=in_progress)
    in_progress --> pending : TaskUpdate(status=pending)
    in_progress --> completed : TaskUpdate(status=completed)
    completed --> [*]
    pending --> deleted : TaskUpdate(status=deleted)
    in_progress --> deleted : TaskUpdate(status=deleted)

pending is the initial state. A pending task exists and is known, but no agent has claimed it. In a multi-agent system, pending tasks are the pool of available work. The rule is simple: work on tasks in ID order — lowest UUID first — to avoid two agents claiming the same task.

in_progress means an agent has claimed the task and is actively working on it. The protocol is explicit: mark the task in_progress before you start work, not after you think about it. This is how multi-agent systems avoid duplicate effort. The moment you call TaskUpdate({taskId, status: "in_progress"}), you have claimed the task.

completed is terminal. A task is completed only when the work is fully done — implementation complete, tests passing, documentation updated, whatever the definition of done is for that task. Do not mark completed speculatively. The harness does not verify completion; the model is on its honor.

deleted is permanent removal. Use it for tasks that are no longer relevant — requirements changed, the work was superseded, the task was created by mistake. Deleted tasks do not appear in TaskList.

Tasks persist to ~/.claude/tasks/ as UUID-named files. The UUID is the task ID:

~/.claude/tasks/
├── 0ae4483c-d05d-4401-b142-6e178f173fd5.json
├── 1b7f2234-a891-4c12-b339-9d4e2f8a1c67.json
└── 3cc89105-e123-4567-8abc-def012345678.json

This means tasks survive session restarts, --resume, and context compaction. They are the closest thing to persistent project state in the standard harness.

When a task is created in Claude Code v2.1.84+, the TaskCreated hook fires. This is an extension point: a hook at .claude/hooks/ listening for TaskCreated events can write to an external ticket system, update a dashboard, or send a notification. The hook receives the task ID and subject in its JSON payload.

10.2 TaskCreate: subject, description, activeForm, metadata

TaskCreate takes four fields. Understanding what each one is for — and what the harness does with it — prevents the common mistake of treating them as cosmetic.

export interface TaskCreateInput {
  subject: string;       // brief title, imperative form
  description: string;   // what needs to be done
  activeForm?: string;   // present continuous shown in spinner ("Running tests")
  metadata?: { [k: string]: any };
}

export interface TaskCreateOutput {
  task: { id: string; subject: string };
}

subject is the task title. Write it in imperative form — "Implement auth timeout fix", "Run regression tests", "Review PR #1234". It appears in TaskList output and in the spinner UI. Keep it under sixty characters; it gets truncated in narrow terminals.

description is where the actual work specification lives. This is the field a subagent reads when it picks up a task. It should be self-contained: what needs to be done, what constraints apply, what done looks like. Do not assume the agent reading the description has any of the context from when the task was created. Write it as if handing off to a colleague who is starting cold.

A good description:

Refactor the session timeout constant in src/auth/session.py.

The constant SESSION_TIMEOUT_MINUTES is currently defined in three places:
- src/auth/session.py:1
- config/legacy_constants.py:47
- config/app_settings.py:83

The config parser reads only config/legacy_constants.py. The other two are dead.

Steps:
1. Consolidate to a single source of truth in config/app_settings.py
2. Update the config parser to read from app_settings.py
3. Remove the dead constants from session.py and legacy_constants.py
4. Run pytest tests/auth/ — all tests must pass before marking complete

A bad description: "Fix the timeout thing we talked about earlier."

activeForm is the present-continuous string shown in the spinner while an agent is working on this task: "Refactoring session timeout", "Running auth tests", "Reviewing PR diff". It is cosmetic in function but important in practice — it is what a human watching the spinner reads to understand what is happening right now. If not provided, the harness falls back to something generic.

metadata is an arbitrary key-value store attached to the task. It supports any JSON-serializable values. Common uses:

// Link to external ticket
metadata: { jiraId: "AUTH-1234", priority: "high" }

// Record origin context
metadata: { createdBy: "sec-pr-agent", orgId: "NMDAbbott", prId: "35989" }

// Track implementation details
metadata: { targetFile: "src/auth/session.py", testCommand: "pytest tests/auth/" }

Metadata uses merge semantics on TaskUpdate: keys you provide are merged into the existing metadata, and keys you set to null are deleted. You do not need to re-send the entire metadata object to add one key.

A minimal TaskCreate call:

// Minimal — description carries the weight
const result = await TaskCreate({
  subject: "Implement rate limiting middleware",
  description: `
Add rate limiting to all public API endpoints.

Requirements:
- 100 requests/minute per IP for unauthenticated requests
- 1000 requests/minute per API key for authenticated requests
- Return 429 Too Many Requests with Retry-After header when exceeded
- Use Redis for the token bucket (connection at REDIS_URL env var)
- Tests in tests/middleware/test_rate_limit.py

Definition of done: all existing tests pass + new tests cover the happy path,
rate-exceeded path, and authenticated vs unauthenticated distinction.
  `.trim(),
  activeForm: "Implementing rate limiting",
  metadata: { milestone: "v2.1", estimatedHours: 3 }
});

// result.task.id is the UUID you use for all subsequent calls
const taskId = result.task.id;

10.3 TaskUpdate: status transitions, addBlocks/addBlockedBy, owner assignment

TaskUpdate is the most powerful task operation. It handles status transitions, dependency graph mutations, and ownership changes in a single call.

export interface TaskUpdateInput {
  taskId: string;
  status?: "pending" | "in_progress" | "completed" | "deleted";
  subject?: string;
  description?: string;
  activeForm?: string;
  owner?: string;
  metadata?: { [k: string]: any };  // merge keys, null to delete
  addBlocks?: string[];      // task IDs this task blocks
  addBlockedBy?: string[];   // task IDs that block this task
}

export interface TaskUpdateOutput {
  success: boolean;
  taskId: string;
  updatedFields: string[];
  error?: string;
  statusChange?: { from: string; to: string };
}

Status Transitions

The status workflow enforces intent. The rule is: mark in_progress before starting, mark completed only when fully done.

// Claim the task before starting work
await TaskUpdate({ taskId, status: "in_progress" });

// ... do the work ...

// Verify: run tests, check output, confirm done
// Only then:
await TaskUpdate({ taskId, status: "completed" });

The statusChange field in the output tells you what the previous status was. This matters in multi-agent systems where another agent may have already claimed the task between your TaskList and your TaskUpdate. If statusChange.from is "in_progress" but you expected "pending", someone else has the task.

To handle a blocked situation without abandoning work, keep the task in_progress and create a new task for the blocker:

// Discovered mid-work that Redis is not configured
await TaskCreate({
  subject: "Configure Redis for rate limiting tests",
  description: "REDIS_URL is not set in .env.test. Add local Redis config.",
  activeForm: "Configuring Redis"
});

// Keep the original task in_progress — you will return to it
// Do NOT flip it back to pending unless you are truly releasing it

The Dependency Graph: addBlocks and addBlockedBy

This is the feature that separates the task system from a flat todo list. addBlocks and addBlockedBy create directed edges in the dependency graph. A task that has blockers in blockedBy cannot be started — in a well-disciplined multi-agent system, agents skip tasks whose dependencies are unresolved.

The graph is built incrementally. You can establish dependencies at creation time or add them later as you discover them:

// Task A: write the database schema
const schemaTask = await TaskCreate({
  subject: "Write database schema for user sessions",
  description: "...",
});

// Task B: write the session service — depends on A
const serviceTask = await TaskCreate({
  subject: "Implement SessionService class",
  description: "...",
});

// Establish the dependency
await TaskUpdate({
  taskId: serviceTask.task.id,
  addBlockedBy: [schemaTask.task.id]
});
// Now serviceTask.blockedBy = [schemaTask.task.id]
// schemaTask.blocks = [serviceTask.task.id]

The edges are bidirectional in the data model but semantically one-directional: blockedBy means "I cannot start until these are done", blocks means "these tasks are waiting for me." When you call addBlockedBy on task B with task A's ID, the harness automatically adds task B's ID to task A's blocks array. You do not need to call addBlocks separately.

Visualizing a dependency graph for a realistic feature implementation:

graph TD
    A["Schema migration\n(pending)"]
    B["SessionService class\n(pending)"]
    C["Rate limit middleware\n(pending)"]
    D["Integration tests\n(pending)"]
    E["Update API docs\n(pending)"]
    F["Deploy to staging\n(pending)"]

    A -->|blocks| B
    A -->|blocks| C
    B -->|blocks| D
    C -->|blocks| D
    D -->|blocks| E
    D -->|blocks| F

    style A fill:#f0f0f0
    style B fill:#ffe0b2
    style C fill:#ffe0b2
    style D fill:#fff9c4
    style E fill:#fff9c4
    style F fill:#fff9c4

In this graph, A is the only task immediately available (no blockers). B and C become available when A completes. D is blocked by both B and C — it cannot start until both are done. E and F are blocked by D.

A multi-agent orchestrator scanning this list with TaskList would:

  1. See A is pending with no blockers → assign it
  2. Poll or watch; when A completes, B and C are unblocked → assign both in parallel
  3. When both B and C complete, D is unblocked → assign it
  4. When D completes, E and F are unblocked → assign both in parallel

Owner Assignment

The owner field is a free-form string identifying which agent holds a task. The harness does not enforce ownership semantics — it is a coordination mechanism, not a lock. By convention:

// Claim with your agent ID before marking in_progress
await TaskUpdate({
  taskId,
  owner: "agent-sec-pr-nmda",
  status: "in_progress"
});

In a team-based agent system, agents scan TaskList and skip tasks whose owner is set to a different agent name. This is a cooperative protocol — it relies on agents following the convention, not on the harness enforcing it.

10.4 TaskGet: full details including description, blocks, blockedBy

TaskList gives you a summary. TaskGet gives you everything.

export interface TaskGetInput {
  taskId: string;
}

export interface TaskGetOutput {
  task: {
    id: string;
    subject: string;
    description: string;
    status: "pending" | "in_progress" | "completed";
    blocks: string[];     // tasks waiting on this one
    blockedBy: string[];  // tasks that must complete first
  } | null;
}

The task field is null if the task does not exist or has been deleted. Always check for null before accessing fields.

The primary use of TaskGet is reading the full description before starting work:

const result = await TaskGet({ taskId: "0ae4483c-d05d-4401-b142-6e178f173fd5" });

if (!result.task) {
  // Task was deleted or never existed — skip
  return;
}

if (result.task.status === "in_progress" && result.task.owner !== myAgentId) {
  // Another agent owns this task — skip
  return;
}

// Read the full description to understand what needs to be done
const { description, blockedBy, blocks } = result.task;

// Check if all blockers are resolved before claiming
// (In practice, TaskList already filters this — TaskGet is for the full spec)

TaskGet is also how you inspect the dependency graph from a specific task's perspective. When you complete a task and want to know what you have unblocked:

// After marking a task completed
await TaskUpdate({ taskId: schemaTaskId, status: "completed" });

// Check what was unblocked
const completed = await TaskGet({ taskId: schemaTaskId });
if (completed.task) {
  const nowUnblocked = completed.task.blocks; // task IDs waiting on this one
  // You could trigger agents for these, or just let the next TaskList pick them up
}

10.5 TaskList: summary view (id, subject, status, owner, blockedBy)

TaskList takes no parameters and returns a summary of all non-deleted tasks:

export interface TaskListInput {}  // no parameters

export interface TaskListOutput {
  tasks: {
    id: string;
    subject: string;
    status: "pending" | "in_progress" | "completed";
    owner?: string;
    blockedBy: string[];
  }[];
}

This is the harness's global work queue. Every autonomous agent in a multi-agent system calls TaskList after completing a task to find what to do next. The absence of parameters is intentional — the list is global, not scoped per agent.

Reading the list intelligently requires filtering. A well-behaved agent applies these rules in order:

  1. Skip completed tasks — already done
  2. Skip in_progress tasks owned by another agent — claimed
  3. Skip tasks with unresolved blockedBy — not yet available
  4. From the remaining pending tasks with no blockers, take the lowest ID first

In practice:

const { tasks } = await TaskList({});

// Build a set of completed task IDs for fast lookup
const completedIds = new Set(
  tasks.filter(t => t.status === "completed").map(t => t.id)
);

// Find the next available task
const available = tasks
  .filter(t => t.status === "pending")
  .filter(t => !t.owner || t.owner === myAgentId)
  .filter(t => t.blockedBy.every(depId => completedIds.has(depId)))
  .sort((a, b) => a.id.localeCompare(b.id));  // lowest UUID first

if (available.length === 0) {
  // Check if there is still in_progress work (wait) or all done (terminate)
  const inProgress = tasks.filter(t => t.status === "in_progress");
  if (inProgress.length > 0) {
    // Work is ongoing — wait and retry
  } else {
    // Nothing left — all done or graph is stuck (cycle or orphaned tasks)
  }
}

const next = available[0];

Call TaskList after completing each task, not just at startup. The task graph is dynamic — tasks can be added by other agents mid-flight. Polling the list is how an agent discovers newly unblocked work.

10.6 The TodoWrite Tool: alternative lightweight todo list

TodoWrite is a simpler, flat alternative to the full task system. No UUIDs, no dependency graph, no ownership, no persistence to disk — just an in-memory list of items with statuses.

export interface TodoWriteInput {
  todos: {
    content: string;
    status: "pending" | "in_progress" | "completed";
    activeForm: string;
  }[];
}

export interface TodoWriteOutput {
  oldTodos: { content: string; status: string; activeForm: string }[];
  newTodos: { content: string; status: string; activeForm: string }[];
}

TodoWrite replaces the entire list on every call. The output gives you oldTodos (what was there before) and newTodos (what is there now). To update a single item's status, you re-send the entire list with that item's status changed.

When to use TodoWrite instead of TaskCreate:

ConcernTaskCreate/UpdateTodoWrite
Persistence across sessionsYes — ~/.claude/tasks/No — in-memory only
Multi-agent coordinationYes — owner + blockedByNo
Dependency graphYes — blocks/blockedByNo
External hooks (TaskCreated)YesNo
SimplicityHigher overheadMinimal
When it fitsLong-running, multi-agent workSingle-session, single-agent checklists

A typical TodoWrite pattern for a single-agent sequential workflow:

// Establish the work plan at the start
await TodoWrite({
  todos: [
    { content: "Read and understand current session.py", status: "pending", activeForm: "Reading session module" },
    { content: "Find all timeout constant references", status: "pending", activeForm: "Searching codebase" },
    { content: "Consolidate to single source of truth", status: "pending", activeForm: "Refactoring constants" },
    { content: "Run pytest tests/auth/", status: "pending", activeForm: "Running tests" },
    { content: "Commit with descriptive message", status: "pending", activeForm: "Committing changes" },
  ]
});

// After completing step 1, update the list
await TodoWrite({
  todos: [
    { content: "Read and understand current session.py", status: "completed", activeForm: "Reading session module" },
    { content: "Find all timeout constant references", status: "in_progress", activeForm: "Searching codebase" },
    // ... rest unchanged
  ]
});

The oldTodos in the response lets you verify what was there before the write — useful for detecting concurrent modification if you are somehow sharing a TodoWrite list (unusual, and not recommended; use TaskCreate for multi-agent scenarios).

TodoWrite is the right tool when you are a single agent working through a linear checklist within one session and you want the spinner to show meaningful progress text. Use TaskCreate when work spans sessions, involves multiple agents, or requires dependency tracking.

10.7 Lab: Implement a Project Manager Agent Using Task Dependencies and Ownership

This lab builds a project manager agent — an agent whose job is to decompose a feature request into tasks, establish the dependency graph, assign agents to execute the work, and monitor completion.

The Scenario

Build a rate limiting feature for an API service. The work spans multiple concerns: database migration, service implementation, middleware, tests, documentation, and deployment. The project manager agent coordinates four worker agents running in parallel where possible, serialized where dependencies require it.

Step 1: The Project Manager Agent

Create the agent definition at .claude/agents/project-manager.md:

---
name: project-manager
description: Decomposes feature requests into tasks, manages dependencies, assigns work to worker agents
tools: TaskCreate, TaskUpdate, TaskList, TaskGet, Agent
model: claude-sonnet-4-6
effort: medium
---

You are a project manager agent. Your job is to:
1. Decompose the given feature request into discrete, well-specified tasks
2. Establish dependency relationships between tasks
3. Assign tasks to worker agents in dependency order
4. Monitor completion and unblock downstream tasks
5. Report completion when all tasks are done

Always write task descriptions that are self-contained — a worker agent reading the description
must not need any other context to complete the work.

Mark yourself as owner of tasks you are managing. Use "pm-agent" as your owner ID.
Work on tasks in ID order (lowest first) when multiple are available.

Step 4: The Execution Loop

async function executeProjectPlan(workerAgentCount: number = 4) {
  const completedIds = new Set<string>();

  while (true) {
    const { tasks } = await TaskList({});

    // Update our completed set
    tasks
      .filter(t => t.status === "completed")
      .forEach(t => completedIds.add(t.id));

    // Find available work
    const available = tasks
      .filter(t => t.status === "pending")
      .filter(t => !t.owner)
      .filter(t => t.blockedBy.every(dep => completedIds.has(dep)))
      .sort((a, b) => a.id.localeCompare(b.id));

    // Check for completion
    const unfinished = tasks.filter(t => t.status !== "completed");
    if (unfinished.length === 0) {
      break; // All done
    }

    // Assign available tasks to worker agents (up to workerAgentCount at once)
    const toAssign = available.slice(0, workerAgentCount);

    await Promise.all(toAssign.map(async (task) => {
      // Claim the task before spawning the worker
      await TaskUpdate({
        taskId: task.id,
        owner: "worker-agent",
        status: "in_progress"
      });

      // Read the full spec
      const { task: fullTask } = await TaskGet({ taskId: task.id });
      if (!fullTask) return;

      // Spawn a worker agent with the task spec
      await Agent({
        prompt: `
You are a worker agent. Complete the following task and mark it completed when done.

Task ID: ${task.id}
Subject: ${fullTask.subject}

Description:
${fullTask.description}

When you are fully done (implementation complete, tests passing):
Call TaskUpdate({ taskId: "${task.id}", status: "completed" })

Do not mark completed until the work is fully verified.
        `.trim(),
        description: `Execute: ${task.subject}`,
        run_in_background: true
      });
    }));

    // Wait before next poll — give workers time to make progress
    await new Promise(resolve => setTimeout(resolve, 15000));
  }
}

Step 5: Verify the Outcome

After the loop terminates:

const { tasks } = await TaskList({});
const summary = {
  total: tasks.length,
  completed: tasks.filter(t => t.status === "completed").length,
  inProgress: tasks.filter(t => t.status === "in_progress").length,
  pending: tasks.filter(t => t.status === "pending").length,
};

// All tasks should be completed
console.log(summary);
// { total: 7, completed: 7, inProgress: 0, pending: 0 }

Key Lessons from the Lab

The dependency graph is set up before any work begins. The project manager creates all tasks and wires all dependencies in a single upfront pass. This prevents a worker from starting integration tests before the service is ready, regardless of race conditions.

TaskGet provides the full specification. TaskList gives you enough to know which tasks are available. TaskGet gives you the description you need to actually do the work. Workers call TaskGet to read the spec, not TaskList.

Claim before spawn. The TaskUpdate setting owner and status: "in_progress" happens before the Agent call, not inside the worker. If the worker fails to start, the task remains in_progress with an owner — a human or orchestrator can detect stuck tasks and reset them.

Polling over events. The 15-second poll loop is simpler and more reliable than event-driven approaches in the standard harness. The TaskCreated hook can supplement this for external notification, but the execution loop itself should poll.

TodoWrite would be wrong here. This workflow spans multiple agents, requires dependency tracking, persists across possible session restarts, and involves hours of work. TodoWrite's in-memory, flat, single-agent model would fail on all of those requirements. Use TaskCreate whenever work crosses agent boundaries or session boundaries.

Summary

The task system provides persistent, structured work state that survives context compaction and session restarts. A task lifecycle moves from pending through in_progress to completed, with deleted as a permanent removal path. The golden rules: mark in_progress before starting, mark completed only when fully done, use TaskList after each completion to find what is next.

TaskCreate demands self-contained descriptions — write them as if handing off to a cold-start colleague. The addBlocks and addBlockedBy dependency graph is what enables parallel, coordinated multi-agent execution: workers scan the list, take only tasks whose blockers are resolved, and the execution order emerges from the graph without a central coordinator having to micromanage sequencing.

TaskGet is for reading full task specs before execution. TaskList is for finding available work. TaskUpdate is the coordination mechanism: status transitions claim and release work, owner prevents double-assignment, and metadata carries implementation-specific context that does not belong in the description.

TodoWrite is the lightweight alternative — no persistence, no dependencies, no ownership, just a flat checklist for single-agent sequential work within one session. The choice is straightforward: if work crosses agent or session boundaries, use TaskCreate. If it does not, TodoWrite is simpler.
