Chapter 20: Context Window Management

"The context window is not infinite scratch space. It is a finite, metered resource — and every token you waste is a token you cannot use for reasoning."

Every tool call appended to the conversation history, every file read, every subagent prompt injected — it all accumulates. At some point the harness hits a wall: the model can no longer fit the entire conversation into a single API call. How the harness handles that wall — gracefully compressing, preserving critical state, serving from cache, paginating large files — determines whether long-running agents degrade silently or crash loudly.

This chapter is about the economics of context. Tokens cost money in both direct API charges and latency. An agent that burns 800K input tokens on a refactoring task costs four to eight times more than one that achieves the same result in 200K tokens. More importantly, context mismanagement is a source of agent failures that look like model hallucinations but are actually information loss from poor window hygiene.

20.1 Token Budgets

The harness exposes five environment variables that control token allocation:

CLAUDE_CODE_MAX_CONTEXT_TOKENS=1000000   # 1M total context window
CLAUDE_CODE_MAX_OUTPUT_TOKENS=128000     # 128K max output per turn
MAX_THINKING_TOKENS=100000               # 100K for extended thinking
CLAUDE_CODE_IDLE_THRESHOLD_MINUTES=180   # idle session timeout
CLAUDE_CODE_IDLE_TOKEN_THRESHOLD=500000  # idle threshold at high token usage

These are not suggestions — they are hard caps enforced by the harness before API calls go out.

CLAUDE_CODE_MAX_CONTEXT_TOKENS

The total context window available to the conversation, including system prompt, all prior messages, tool results, and the pending response. The default is 1,000,000 tokens — the maximum supported by claude-sonnet-4-x and claude-opus-4-x as of v2.1.220.

Setting this lower is a deliberate cost-control mechanism. A team running hundreds of parallel CI agents might cap at 200,000 tokens per agent to stay within a daily token budget. The harness respects the cap and triggers compression before the conversation reaches it.

# CI budget: restrict agent context to control spend
CLAUDE_CODE_MAX_CONTEXT_TOKENS=200000 claude -p "Review this PR diff..."

The relationship between context size and API cost is linear on input tokens but asymmetric on cache behavior — a point covered in section 20.4. Blindly lowering this value without understanding the cache implications can increase costs rather than reduce them.

CLAUDE_CODE_MAX_OUTPUT_TOKENS

The maximum tokens Claude can produce in a single response. The default of 128,000 tokens accommodates large code generation tasks — writing a complete module, generating a migration, producing a detailed report. Most individual turns consume far less.

The practical implication: if you are building a harness that needs deterministic output sizes, this cap is your primary lever. For agents that write to structured output formats (JSON, markdown tables), staying under 128K output tokens is rarely a concern. For agents that generate large files in a single turn, it becomes a real constraint to design around.

MAX_THINKING_TOKENS

Extended thinking — the model's internal reasoning scratchpad before producing its visible response — has its own budget. 100,000 tokens buys significant deliberation before the model commits to output. For tasks like architecture decisions or complex security analysis, this budget is what separates a surface-level answer from one that has actually worked through the edge cases.

Reducing this for routine tasks trades reasoning depth for speed and cost:

# Fast-path for simple tasks — no deep thinking needed
MAX_THINKING_TOKENS=10000 claude -p "Add type hints to this function..."

Idle Thresholds

CLAUDE_CODE_IDLE_THRESHOLD_MINUTES triggers session cleanup after 180 minutes of inactivity. CLAUDE_CODE_IDLE_TOKEN_THRESHOLD adds a secondary trigger: if the session has accumulated over 500K tokens and is idle, cleanup happens sooner. Both exist to prevent long-lived sessions from holding expensive context indefinitely.

In practice, these thresholds interact with the PreCompact hook (section 20.3). If your agent has critical state that must survive a cleanup event, the hook is your preservation mechanism.

20.2 Automatic Compression

When the conversation approaches CLAUDE_CODE_MAX_CONTEXT_TOKENS, the harness does not crash — it compresses. The compression mechanism is automatic and predictable once you understand it.

How Compression Works

The harness monitors the running token count of the conversation. As it approaches the configured limit (the threshold is roughly 85–90% of the cap), it triggers an autocompact operation:

flowchart TD
    A[Conversation Growing] --> B{Near Token Cap?}
    B -->|No| C[Continue normally]
    B -->|Yes| D[Fire PreCompact hook]
    D --> E[Inject hook output into summary]
    E --> F[Summarize prior messages]
    F --> G[Discard old messages]
    G --> H[Retain: summary + recent N messages]
    H --> I[Continue with compressed context]

The summarization is done by a model call — the harness passes the prior conversation to Claude and asks for a condensed summary that preserves the essential thread: what was asked, what was found, what decisions were made, what state the session is in. This summary replaces the original messages.

The result: the conversation continues carrying forward a compact summary of everything that came before, plus the most recent messages (which are preserved verbatim to maintain coherence around the current task). The model can still reason about prior work through the summary, but the raw detail is gone.

What This Means in Practice

Compression is lossy. A summary of a 100-message investigation preserves the conclusions but discards the intermediate reasoning, the exact file contents that were read, the specific error messages that were encountered. If your agent needs to refer back to something read 80 messages ago, that detail may no longer be in the compressed context.

This has a direct implication for agent design: information that must survive compression must be written to persistent storage, not left in the conversation. The pattern seen in mature harness implementations is to write state files after important discoveries:

# After finding a critical architectural detail, write it out
echo '{"finding": "auth module uses RS256 only in production env", "file": "src/auth/config.py", "line": 47}' \
  >> ~/.claude/projects/myapp/state/session-$(date +%s).json

The PreCompact hook, covered next, is the mechanism for ensuring that state survives the compression boundary.

20.3 The PreCompact Hook

The PreCompact hook fires immediately before the harness executes autocompaction. It is the last moment at which your session's in-memory context is fully intact. The hook's stdout is injected verbatim into the compaction summary — whatever you write to stdout becomes part of the compressed context that carries forward into the next phase of the session.

This is not a convenience feature. For long-running agents — security scanners, codebase refactors, multi-day workflows — the PreCompact hook is what separates graceful continuation from a reset to zero.

Hook Location and Registration

// .claude/settings.json
{
  "hooks": {
    "PreCompact": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "~/.claude/hooks/pre-compact.sh"
          }
        ]
      }
    ]
  }
}

The matcher is empty — PreCompact fires unconditionally, not based on tool name or content matching.

Real Implementation

Here is a production PreCompact hook for a long-running security audit agent. It reads the current state file, injects its content as critical context, and instructs the model on how to recover after compaction:

#!/usr/bin/env bash
set -euo pipefail

STATE_DIR="${HOME}/.claude/projects/-Users-user-project/state"
MAX_STATE_CHARS=4000
INPUT=$(cat 2>/dev/null || true)

# Find the most recently written state file
LATEST_FILE=$(find "${STATE_DIR}" -name "*.json" -newer /dev/null \
  -exec ls -t {} + 2>/dev/null | head -1)

if [[ -z "${LATEST_FILE}" ]]; then
  # No state file — nothing to preserve
  exit 0
fi

STATE_CONTENT=$(head -c "${MAX_STATE_CHARS}" "${LATEST_FILE}")
DOMAIN=$(grep '"domain"' "${LATEST_FILE}" | head -1 \
  | sed 's/.*"domain"[[:space:]]*:[[:space:]]*"\([^"]*\)".*/\1/')

cat << EOF
CRITICAL — Preserve the following ${DOMAIN} session state verbatim:
${STATE_CONTENT}

After compaction resumes:
1. Read the full state file at ${LATEST_FILE}
2. Verify state freshness (check the "timestamp" field) before acting
3. Resume from the recovered state — do not restart from scratch
4. If the state is stale (>30 minutes), re-verify key findings before continuing
EOF

The MAX_STATE_CHARS=4000 limit is deliberate. The hook output is injected into the compressed summary, and that summary itself has a token budget. Injecting 50,000 characters of state would consume the summary budget and make the compression useless. Four thousand characters — roughly two dense pages of text — is enough to preserve the essential session state: what phase the work is in, what findings have been confirmed, which files have been processed, and where to resume.

Designing State Files for PreCompact

The hook is only as good as the state files it reads. State files should capture:

  • Phase and progress: what stage of the workflow is active, how far it has progressed
  • Confirmed findings: discoveries that took expensive work to reach and should not be discarded
  • Work completed: files already processed, so the agent does not re-process them after compression
  • Decision trail: key choices made during the session that affect subsequent steps
{
  "domain": "security-audit",
  "timestamp": "2026-07-28T14:32:11Z",
  "phase": "deep-analysis",
  "progress": {"files_scanned": 147, "files_total": 312},
  "confirmed_findings": [
    {"file": "src/auth/jwt.py", "line": 84, "severity": "CRITICAL", "cwe": "CWE-347"}
  ],
  "processed_files": ["src/auth/jwt.py", "src/auth/session.py"],
  "next_target": "src/api/middleware.py"
}

The agent writes this file after each completed scan phase. The PreCompact hook reads it and ensures the model knows where it was and what it found, even after all the intermediate conversation messages have been compressed away.

20.4 Prompt Cache

The Anthropic API supports prompt caching: content that appears at the beginning of a request can be stored server-side and served on subsequent requests without re-processing. The harness exploits this aggressively.

Cache Mechanics

Cache entries live for 5 minutes at the ephemeral_5m tier. There is also a longer-lived ephemeral_1h tier for content that benefits from extended reuse. Cached tokens are not re-charged as input tokens — they are served at a fraction of the standard input token rate.

The AgentOutput.usage struct exposes the cache accounting:

usage: {
  input_tokens: number;                    // tokens processed fresh (billed at full rate)
  output_tokens: number;                   // tokens generated
  cache_creation_input_tokens: number | null;  // tokens written to cache (billed at creation rate)
  cache_read_input_tokens: number | null;      // tokens served from cache (billed at cache rate)
  cache_creation: {
    ephemeral_1h_input_tokens: number;     // tokens in 1-hour cache tier
    ephemeral_5m_input_tokens: number;     // tokens in 5-minute cache tier
  } | null;
}

A healthy multi-turn session shows cache_read_input_tokens growing across turns as the system prompt is served from cache repeatedly. A session with poor cache utilization shows input_tokens dominating every turn.

What Gets Cached

The system prompt is the primary cache target. It is static across turns — the base instructions, tool descriptions, CLAUDE.md content, and project context do not change between messages. The harness structures the conversation so that system prompt content appears at the beginning of every request, maximizing cache hit probability.

In a 20-turn session, the system prompt (say, 15,000 tokens) would normally cost 300,000 input tokens across all turns. With cache serving it after the first turn, 19 of those turns serve from cache. At typical pricing, this reduces the system prompt cost by roughly 90%.

Cache Invalidation Pitfalls

The 5-minute TTL means cache entries expire during idle time. Version 2.1.92 added a footer hint to Pro users when the prompt cache expires — a signal that the next turn will be billed at full input token rates.

Two bugs fixed in v2.1.89 are worth understanding because they represent patterns to avoid:

Tool schema byte changes invalidate cache. The system prompt includes tool descriptions serialized as JSON. If any byte in the tool descriptions changes between turns — even formatting — the cache hash changes and the cache misses. In long sessions, if tool schemas are being dynamically rebuilt on every turn (e.g., reading MCP tool schemas from a live server that returns slightly different JSON), the cache will never hit. Keep tool schemas stable across turns.

Nested CLAUDE.md re-injection. Also fixed in v2.1.89: nested CLAUDE.md files (project subdirectories with their own CLAUDE.md) were being re-injected dozens of times in long sessions. Each re-injection produced slightly different assembled system prompts, breaking cache coherence. The fix ensures CLAUDE.md content is assembled once at startup and not reassembled on subsequent turns.

--exclude-dynamic-system-prompt-sections

This flag shifts dynamic, per-machine content out of the system prompt and into the first user message:

claude --exclude-dynamic-system-prompt-sections ...

By default, the system prompt includes:

  • Current working directory
  • Environment variables
  • Memory file paths
  • Git status

These fields are machine-specific. Two users running the same harness on different machines produce different system prompts, which means their cache entries cannot be shared — each user warms a separate cache. In multi-user deployments, this multiplies the cache warming cost proportionally to the number of users.

With --exclude-dynamic-system-prompt-sections, the system prompt becomes static content that is identical across all users of the same project. Dynamic content moves to the first user message, which is not cached. The tradeoff: the first message is slightly larger, but all subsequent turns hit a shared system prompt cache.

This flag only applies when using the default system prompt. If you pass --system-prompt, the flag is ignored — you are responsible for managing what goes in your custom prompt.

20.5 Read Deduplication

Reading the same file twice in the same session is wasteful — both in token cost and in API call overhead. The harness eliminates redundant reads through a session-level deduplication mechanism.

file_unchanged Response

When the Read tool is called for a file that has already been read in the current session and the file has not been modified since, the harness returns a file_unchanged response type rather than the full content:

{
  "type": "file_unchanged",
  "file_path": "/Users/user/project/src/auth/session.py",
  "source": "session_cache"
}

The model receives a compact acknowledgment rather than thousands of tokens of file content. For a 500-line Python file read three times in a session, deduplication saves roughly 6,000 tokens across the second and third reads.

source: "seeded"

A related variant appears for files injected at session startup — CLAUDE.md files, global memory files, any content the harness seeds into the initial context:

{
  "type": "file_unchanged",
  "file_path": "/Users/user/project/CLAUDE.md",
  "source": "seeded"
}

source: "seeded" means the file matched a startup-seeded entry. The model already has the content from the system prompt injection; the harness does not send it again.

Subagent Deduplication Isolation

Deduplication is session-scoped. Subagents start fresh sessions — they do not inherit the parent's deduplication state. A parent agent that has already read src/auth/session.py and a subagent reading the same file are operating in different sessions; the subagent pays the full token cost.

This is intentional. Subagent isolation means the parent cannot leak file contents to the subagent except through explicit prompt injection. The deduplication boundary is the session boundary.

For harness authors building Agent prompts: if a subagent needs file content that the parent has already read, inject it into the subagent's prompt directly rather than expecting the subagent to re-read and paying the read tool cost again.

20.6 Token Cap Auto-Pagination

Files that exceed the token cap for a single Read call are automatically paginated. The harness returns the first page of content with a signal indicating the response was truncated.

The truncatedByTokenCap Flag

{
  "type": "text",
  "content": "... first N lines of the file ...",
  "truncatedByTokenCap": true
}

truncatedByTokenCap: true is a programmatic signal, not just a display artifact. It means:

  1. The content is the first page only
  2. More content exists that was not returned
  3. A second Read call with offset parameter will return the next page

The harness auto-paginates large files rather than refusing to read them or silently truncating without signaling. For consumers of the Read tool output — whether the model itself or a tool result parser in a custom harness — the flag is the contract that says "this is partial."

Implications for Harness Design

If you are building a custom harness that uses file reading, respect truncatedByTokenCap as a first-class signal:

async function readFullFile(path: string): Promise<string> {
  const chunks: string[] = [];
  let offset = 0;

  while (true) {
    const result = await readTool({ file_path: path, offset, limit: 2000 });
    chunks.push(result.content);

    if (!result.truncatedByTokenCap) {
      break;
    }
    offset += 2000;
  }

  return chunks.join("\n");
}

In the Claude Code harness itself, the model handles pagination organically — it sees the truncatedByTokenCap signal in the tool result and issues a follow-up Read call with the appropriate offset. This is the right behavior; building pagination logic into the model prompt (by noting in the system prompt that large files are paginated and showing offset examples) makes it explicit.

20.7 Autocompact Thrash Loop Prevention

A subtle failure mode was fixed in Claude Code v2.1.89: the autocompact thrash loop. Understanding it is important both for operating existing harnesses and for preventing the same failure in custom implementations.

The Failure Pattern

The thrash loop occurs when:

  1. The conversation approaches the token cap and autocompaction fires
  2. The session resumes, but the combination of system prompt + prior state immediately fills context again
  3. Autocompaction fires again
  4. The session refills again immediately
  5. Repeat indefinitely, burning API calls on compaction overhead with no productive work

This can happen in sessions with very large system prompts (heavy CLAUDE.md, many MCP tool schemas) combined with pre-compaction state injection (large PreCompact hook output). After compression, the static overhead — system prompt + hook injection — may itself consume most of the configured context budget, leaving insufficient space for actual work.

The Fix

From the v2.1.89 CHANGELOG:

"Fixed autocompact thrash loop — now detects when context refills to the limit immediately after compacting three times in a row and stops with an actionable error instead of burning API calls"

The harness now tracks consecutive recompacts. After three consecutive compressions without meaningful productive conversation between them, it halts with an error rather than continuing to compact and refill:

Error: Context window thrash detected — compressed 3 times consecutively without
progress. Reduce system prompt size, lower CLAUDE_CODE_MAX_CONTEXT_TOKENS, or
increase PreCompact hook output selectivity.

Three is the threshold. One recompact is normal. Two is a warning sign. Three is the circuit breaker.

Diagnosing Thrash

If you hit the thrash error, the diagnosis is mechanical:

CauseDiagnosisFix
System prompt too largeSum CLAUDE.md + tool schema tokensUse claudeMdExcludes to reduce discovery scope; trim unused tool descriptions
PreCompact hook output too largeCheck hook stdout byte countReduce MAX_STATE_CHARS; summarize state rather than dumping raw content
Context cap too low for workloadSession productive turn count before first compaction is very lowRaise CLAUDE_CODE_MAX_CONTEXT_TOKENS or reduce MAX_OUTPUT_TOKENS
Long system prompt + large MCP schemasCount MCP tool descriptionsDisable unused MCP servers for the session

The claudeMdExcludes setting directly addresses CLAUDE.md bloat from large dependency directories:

{
  "claudeMdExcludes": [
    "**/node_modules/**",
    "**/.venv/**",
    "**/vendor/**",
    "**/dist/**"
  ]
}

Without exclusions, the harness walks the entire directory tree looking for CLAUDE.md files. In a monorepo with thousands of node_modules subdirectories, this produces either a very long directory walk or, worse, finds CLAUDE.md files inside dependencies and injects their content into your session.

20.8 --exclude-dynamic-System-prompt-sections for Cache Reuse

Section 20.4 introduced this flag from the cache mechanics side. This section covers the implementation details and when to use it.

The Problem: Per-Machine System Prompts

The default system prompt contains content that varies by machine and session:

Working directory: /Users/alice/project
Git status: M src/auth/session.py
Environment: ANTHROPIC_API_KEY=sk-...
Memory paths: /Users/alice/.claude/memory/

Alice's system prompt is different from Bob's. Alice's session on Monday (git status clean) produces a different system prompt than Tuesday (after uncommitted changes). Each variation is a unique cache key — a cache miss.

For a team of 10 engineers all running the same harness against the same codebase, the system prompt is warming 10 separate caches instead of one shared cache. At 15,000 tokens per system prompt, that is 150,000 tokens of warming cost instead of 15,000.

The Solution: Static System Prompt + Dynamic First Message

With --exclude-dynamic-system-prompt-sections, the harness restructures the prompt:

Before:

[system prompt]
Base instructions + tool descriptions + CLAUDE.md + git status + CWD + env info + memory paths

After:

[system prompt — static, shared cache key]
Base instructions + tool descriptions + CLAUDE.md

[first user message — dynamic, not cached]
Working directory: /Users/alice/project
Git status: M src/auth/session.py
Environment context: ...
Memory paths: ...

[actual user prompt]
Fix the authentication timeout in src/auth/session.py

The system prompt is now identical for all users on the same project. The cache entry warms once and serves all of them.

When to Use It

This flag pays off in multi-user team scenarios. For solo use on a single machine, the cache would hit anyway (same user, same CWD, same git status between consecutive calls). For teams, automated CI pipelines, or deployments where multiple users run the same harness, the flag is a significant cost lever.

A caveat: dynamic content in the first user message means the model sees git status, environment info, and memory paths as user-provided context rather than system instructions. For well-written harness prompts, this distinction does not matter — the model interprets the context correctly regardless of which message turn it arrives in. For prompts that rely on the system/user role boundary as a trust signal, review whether the shift changes the expected behavior.

20.9 Lab: Design a Context Strategy for a 200+ File Codebase Agent

This lab is a design exercise, not a code dump. The goal is to produce a context strategy document that a senior engineer could hand to a team implementing a long-running codebase analysis agent.

The Scenario

An agent is tasked with performing a complete security and code quality audit of a Python codebase with 240 source files, 18,000 lines of code, comprehensive test coverage, and an active development team committing daily. The agent must:

  1. Scan all 240 files
  2. Identify security issues, quality issues, and test gaps
  3. Produce a single unified report
  4. Handle interruptions gracefully (the audit may take 45+ minutes of wall clock time)
  5. Run in CI — no interactive user to resolve ambiguities

Context Budget Calculation

Before writing any code, calculate the context budget:

System prompt tokens (estimated):
  Base instructions + tool descriptions:    ~4,000
  CLAUDE.md (project rules):                ~2,000
  Git context + env info:                   ~1,000
  Total system prompt:                      ~7,000

Per-file analysis tokens (estimated):
  Average file size (75 lines):             ~1,500
  Tool result overhead (read + result):     ~500
  Model response (findings JSON):           ~800
  Per-file cost:                            ~2,800

For 240 files:
  Total file analysis tokens:              ~672,000

Synthesis phase:
  All findings aggregated:                  ~20,000
  Synthesis prompt + response:              ~15,000
  Total synthesis:                          ~35,000

Grand total estimate:                      ~714,000 tokens

714,000 tokens is within the 1M cap, but barely. One long source file, verbose model responses, or an extra CLAUDE.md in a subdirectory could push it over. The strategy needs compression headroom.

Decision 1: Use Parallel Subagents

Do not run a single 240-file scan in one agent session. Fan out to parallel subagents, each scanning a bounded slice of the codebase:

Orchestrator (sonnet)
├── Subagent batch 1: files 001-060 (haiku)
├── Subagent batch 2: files 061-120 (haiku)
├── Subagent batch 3: files 121-180 (haiku)
└── Subagent batch 4: files 181-240 (haiku)
         ↓
Synthesizer (sonnet)
         ↓
Report

Each subagent operates in a fresh session — no prior conversation overhead, no compression pressure. 60 files at ~2,800 tokens each = ~168,000 tokens per subagent. Well within a 200K context limit configured for the haiku scanner agents.

As discussed in Chapter 11, subagent prompts must be self-contained. Each batch prompt includes the explicit list of file paths to scan, the output schema, and the complete instructions for what to look for — not a reference to "the project" that the subagent cannot see.

Decision 2: Configure Token Caps Per Agent Role

# Scanner agents: cheap, fast, bounded context
CLAUDE_CODE_MAX_CONTEXT_TOKENS=200000 \
CLAUDE_CODE_MAX_OUTPUT_TOKENS=20000 \
MAX_THINKING_TOKENS=5000 \
  claude -p "$(cat scanner-prompt-batch-1.txt)"

# Synthesizer: needs more context to hold all findings
CLAUDE_CODE_MAX_CONTEXT_TOKENS=400000 \
CLAUDE_CODE_MAX_OUTPUT_TOKENS=50000 \
MAX_THINKING_TOKENS=20000 \
  claude -p "$(cat synthesis-prompt.txt)"

Scanner agents do not need extended thinking — they are performing structured extraction. Synthesis requires more reasoning to de-duplicate and prioritize across 240 files.

Decision 3: State Files and PreCompact Hook

Even with the parallel architecture, the orchestrator session — which launches all four batches, collects results, and runs the synthesizer — will accumulate substantial context. Configure a PreCompact hook for it:

# ~/.claude/hooks/audit-pre-compact.sh
#!/usr/bin/env bash
set -euo pipefail

STATE_FILE="${HOME}/.claude/projects/myapp-audit/state/current.json"
[[ -f "${STATE_FILE}" ]] || exit 0

# Report only the completion status, not the full findings
BATCHES_DONE=$(jq '.batches_completed | length' "${STATE_FILE}")
BATCHES_TOTAL=$(jq '.batches_total' "${STATE_FILE}")
FINDINGS_COUNT=$(jq '.findings | length' "${STATE_FILE}")
LAST_BATCH=$(jq -r '.batches_completed[-1] // "none"' "${STATE_FILE}")

cat << EOF
AUDIT STATE: ${BATCHES_DONE}/${BATCHES_TOTAL} batches complete.
${FINDINGS_COUNT} findings accumulated.
Last completed batch: ${LAST_BATCH}
State file: ${STATE_FILE}
On resume: read state file, launch remaining batches, do not re-scan completed batches.
EOF

The hook output is compact — under 200 tokens — but gives the model enough information to resume correctly after compression without re-running completed scans.

Decision 4: Cache Optimization for the CI Environment

In a CI pipeline, the harness runs from a clean environment on each invocation. Use --exclude-dynamic-system-prompt-sections to separate the static project instructions from the per-run git state:

claude --exclude-dynamic-system-prompt-sections \
  -p "Run security audit batches..."

The project's CLAUDE.md, tool descriptions, and base instructions will be cached across CI runs. The commit SHA, current branch, and changed files live in the first user message and vary per run — they should not be in the cached system prompt anyway.

Decision 5: Handle Pagination Explicitly

Scanner prompts must anticipate truncation. Instruct haiku agents to handle it:

If a file read returns truncatedByTokenCap: true, issue a follow-up Read
with offset equal to the number of lines already received. Continue until
truncatedByTokenCap is false. Report findings from all pages.

Without this instruction, a haiku agent that hits truncation may either stop reading the file (missing findings on later pages) or fail to parse the partial content correctly.

The Strategy Document

A context strategy for this workload reduces to five decisions:

This strategy brings the total cost from ~714,000 tokens in a single session to approximately 4 × 168,000 (scanners) + 200,000 (synthesis + orchestration) = 872,000 tokens — slightly more in raw token count, but distributed across five shorter sessions that each stay well under their caps, with no compression risk and full cache reuse.

More importantly, it is a resilient strategy. If batch 3 fails mid-run, the orchestrator's state file records which batches completed. The PreCompact hook preserves that state across any compression events. Batch 3 can be re-run without re-scanning the 180 files already processed in batches 1, 2, and 4.

Summary

Context window management is an engineering discipline, not an operational afterthought. The six behaviors covered in this chapter form a complete toolkit:

Token budgets (CLAUDE_CODE_MAX_CONTEXT_TOKENS, MAX_OUTPUT_TOKENS, MAX_THINKING_TOKENS) are explicit resource limits. Set them deliberately per workload rather than leaving them at defaults and hoping for the best.

Automatic compression is lossy. Information not written to persistent state before compression is gone. Long-running agents must write state files — the context window is not a reliable scratchpad across compression boundaries.

The PreCompact hook is your intervention point. It fires before compression and injects critical state into the surviving summary. Keep hook output compact — under 4,000 characters — to avoid consuming the summary budget that compression needs to work correctly.

Prompt cache has a 5-minute TTL and is invalidated by any byte change in the cached prefix. Stable system prompts hit cache reliably. Dynamic content injected into the system prompt (CWD, git status, per-machine env vars) breaks cross-user cache sharing — use --exclude-dynamic-system-prompt-sections in multi-user deployments.

Read deduplication eliminates redundant file reads within a session. Subagents do not inherit the parent's dedup state — they pay the full cost on their first read of any file. For subagents that need file content the parent has already read, inject it into the agent prompt directly.

Pagination via truncatedByTokenCap signals partial file reads programmatically. Handle it explicitly in harness code and scanner agent prompts — a scanner that silently stops at the first page of a long file is producing incomplete findings.

Thrash loop prevention stops the harness after three consecutive compressions without productive progress. Hitting this error means the static overhead (system prompt + hook output) is consuming most of the configured context budget. Reduce system prompt size via claudeMdExcludes, reduce hook output selectivity, or raise the context cap.

The lab's 200-file audit scenario demonstrates how these tools compose: parallel subagents distribute context load, per-role token caps right-size each session, PreCompact hooks protect orchestrator state, and cache optimization amortizes system prompt cost across CI runs.
