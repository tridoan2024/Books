Chapter 23: REPL, Artifacts, Notifications, and Remote Triggers

"The tools in this chapter are about output that outlives the session — code that executes in a persistent sandbox, pages that live at a URL, alerts that reach a human who isn't watching, and triggers that let the world reach back in."

23.1 REPL — In-Process JavaScript with Persistent State

Every other tool in the harness executes at arm's length: a subprocess, a file system call, an API request. The REPL is different. It runs JavaScript inside the harness process itself, in a sandbox that persists for the lifetime of the session.

The interface:

export interface REPLInput {
  code: string;          // JavaScript, supports top-level await, state persists
  description?: string;  // semantic label
  timeout?: number;      // default 30000ms, max 600000ms
}

export interface REPLOutput {
  code: string;
  result: { [k: string]: unknown };
  stdout: string;       // captured console.log
  stderr: string;       // captured console.error
  error?: string;
  registeredTools?: string[];  // tools registered during execution
  images?: { base64: string; mediaType: string }[];
  documents?: { base64: string }[];
}

What "Persistent State" Actually Means

Variables, functions, and objects assigned in one REPL call remain available in the next call within the same session. This is not a side effect of shared global scope — it is the design. The sandbox is a long-lived JavaScript context, not a fresh Node.js process per call.

// Call 1 — define state
const metrics = new Map();
metrics.set("latency_p99", []);
metrics.set("error_rate", []);
console.log("Metrics tracker initialized");

// Call 2 — same session, same state
metrics.get("latency_p99").push(142);
metrics.get("latency_p99").push(189);
metrics.get("error_rate").push(0.02);
console.log("Recorded:", Object.fromEntries(metrics));
// Outputs: Recorded: { latency_p99: [142, 189], error_rate: [0.02] }

The second call works because metrics persists from the first. This is the property that makes the REPL useful for stateful computations that span multiple steps — aggregating data from multiple Bash calls, building up a data structure incrementally, or maintaining computation state across a long workflow.

Contrast this with Bash: each Bash call is a new subprocess with no memory of prior calls. If you need a variable to survive between Bash calls, you write it to a file. With the REPL, you just keep it in memory.

Top-Level Await

The REPL supports top-level await, which means you can call async operations directly without wrapping them in an async function:

// Fetch and process in one call — no wrapper function needed
const response = await fetch("https://api.github.com/repos/anthropics/claude-code/releases/latest");
const release = await response.json();
console.log(`Latest: ${release.tag_name}, published ${release.published_at}`);

The timeout parameter governs how long the harness will wait for the awaited operation to resolve. The default is 30,000ms (30 seconds). For operations that legitimately need more time — large data processing, paginated API crawls, computationally intensive transforms — you can push this up to 600,000ms (10 minutes).

The maximum is not arbitrary. The REPL runs in-process, and a REPL call that blocks for 10 minutes holds the harness's JavaScript thread for that duration. Design long-running computations as incremental calls with state accumulation rather than a single monolithic call that holds the thread.

Dynamic Tool Registration

The most structurally significant capability of the REPL is the ability to register new tools at runtime. Tools registered during REPL execution become available to the model in the current session without a restart.

// Register a custom tool that wraps an internal service
registerTool({
  name: "QueryMetricsDB",
  description: "Query the internal Prometheus metrics database. Returns time-series data.",
  inputSchema: {
    type: "object",
    properties: {
      metric: { type: "string", description: "Prometheus metric name" },
      range: { type: "string", description: "Time range, e.g. '5m', '1h', '24h'" },
    },
    required: ["metric"],
  },
  handler: async ({ metric, range = "1h" }) => {
    const url = `http://prometheus.internal:9090/api/v1/query_range?query=${encodeURIComponent(metric)}&range=${range}`;
    const res = await fetch(url);
    const data = await res.json();
    return JSON.stringify(data.data, null, 2);
  },
});

console.log("QueryMetricsDB registered");

When this REPL call completes, REPLOutput.registeredTools will include "QueryMetricsDB". The model can now call QueryMetricsDB exactly as it would call any other tool — it appears in tool search results, it can be called by name, and its output arrives in the conversation as a normal tool result.

This is the pattern for environments where you cannot modify the harness configuration files between sessions. A SessionStart hook can execute a REPL call that registers all environment-specific tools, making them available for the entire session without any static configuration.

Image and Document Return

REPL calls can return binary content. If the JavaScript produces base64-encoded image data, it comes back in REPLOutput.images. PDF data comes back in documents. The model receives this content and can reason about it.

// Generate a chart and return it as a PNG
const canvas = createCanvas(800, 400);
const ctx = canvas.getContext("2d");

// ... draw chart data ...

const imageData = canvas.toDataURL("image/png").replace("data:image/png;base64,", "");

// Return structure the harness recognizes
({
  images: [{ base64: imageData, mediaType: "image/png" }]
});

The final expression in a REPL call becomes the result field in REPLOutput. Returning the images array in this structure signals to the harness to attach the images to the tool result. The model then receives an image it can describe, interpret, or compare against expected output.

This makes the REPL the right tool for computational tasks where the output is visual: chart generation, diagram rendering, image manipulation, PDF construction.

23.2 Artifact — Publishing to a Hosted URL

The REPL executes ephemeral computation. Artifact is its complement: durable publication. Artifact takes a file — HTML or Markdown — and publishes it to a hosted URL that anyone with the link can visit.

export interface ArtifactInput {
  action?: "publish" | "list";  // default: publish
  file_path?: string;    // .html or .md file
  favicon?: string;      // one or two emoji
  title?: string;        // browser tab title
  description?: string;  // one-sentence subtitle
  label?: string;        // version label, max 60 chars
  url?: string;          // existing artifact URL to update in place
  force?: boolean;       // override 409 conflict
  limit?: number;        // list: max results (default 25)
  scope?: "mine" | "shared" | "all";  // list filter
}

The output varies by action:

// publish result
type ArtifactPublishOutput = {
  url: string;            // the live URL
  path: string;           // storage path
  title?: string;
  version?: string;
  capabilities?: unknown;
  stored?: { contract: string; capabilities?: {} };
  warnings?: string[];
  updated?: boolean;      // true when updating an existing artifact
  liveSubscription?: string;
};

// list result
type ArtifactListOutput = {
  artifacts: {
    title: string;
    url: string;
    updatedAt?: string;
    rel?: "mine" | "shared";
  }[];
  truncated?: boolean;
  scope?: "shared" | "all";
};

First Publish

The minimal publish: provide file_path pointing to an .html or .md file. Everything else has defaults.

// The model generates a report file, then:
await Artifact({
  file_path: "/tmp/coverage-report.html",
  title: "Test Coverage Report — 2026-07-28",
  description: "Per-module coverage for the auth and API packages",
  favicon: "📊",
  label: "v1.0",
});
// Returns { url: "https://claude.ai/artifacts/abc123", ... }

The returned url is the canonical address of this artifact. Share it with the team, link it in a PR description, embed it in a Slack message. The content is static — it reflects the file as it was at publish time. To update it, you publish again.

Versioning and In-Place Updates

When you publish the same artifact again with the url field set to the original artifact's URL, the harness updates the existing artifact in place rather than creating a new one:

// Regenerate the report after more tests ran
await Artifact({
  file_path: "/tmp/coverage-report.html",
  url: "https://claude.ai/artifacts/abc123",  // the original URL
  label: "v1.1 — post hotfix coverage",
  title: "Test Coverage Report — 2026-07-28 (post hotfix)",
});
// Returns { url: "https://claude.ai/artifacts/abc123", updated: true }

The URL does not change. Anyone who bookmarked the original link now sees the updated content. The label field carries semantic version metadata — it appears in the artifact's version history and helps readers understand what changed between versions.

Label constraints: maximum 60 characters. Use them as lightweight changelogs: "v1.0 — initial", "v1.1 — fixed auth module gaps", "v2.0 — full codebase coverage added". The 60-character limit forces brevity.

The 409 Conflict

The 409 status code is the artifact system's concurrency guard. It fires when two conditions are true simultaneously:

  1. You are attempting to publish to an existing artifact URL
  2. Another session published to that same URL between your last read and your current publish

This is not an error to suppress. It is a data race signal. The standard resolution is a three-step process:

sequenceDiagram
    participant A as Your Session
    participant S as Artifact Store
    participant B as Other Session

    A->>S: Artifact publish (url=X)
    B->>S: Artifact publish (url=X) — arrives first
    S-->>B: 200 OK, version=v2
    S-->>A: 409 Conflict
    A->>S: Artifact list (scope=mine) — find current state
    S-->>A: { url: X, title: "...", updatedAt: "..." }
    Note over A: Read the current version, merge if needed
    A->>S: Artifact publish (url=X, label="v3 — merged")
    S-->>A: 200 OK, updated: true

The harness intentionally does not auto-merge. The model is in the best position to decide whether to overwrite, merge, or skip — it has the context the store does not. The force: true flag bypasses the conflict check entirely, which is appropriate when you are certain your version supersedes the conflicting one (for example, a scheduled regeneration job that always produces the authoritative state):

// Scheduled report refresh — our version is always authoritative
await Artifact({
  file_path: "/tmp/weekly-digest.html",
  url: existingUrl,
  label: `Week of ${weekOf} — scheduled refresh`,
  force: true,  // we own this artifact, don't care about conflicts
});

Reserve force: true for automation that owns a specific artifact. In interactive sessions, prefer the read-merge-republish sequence so you do not clobber another user's edits.

Listing Artifacts

The list action returns artifacts visible to the current session:

const result = await Artifact({
  action: "list",
  scope: "mine",    // "mine" | "shared" | "all"
  limit: 10,
});

// result.artifacts: [{ title, url, updatedAt, rel }]

Use scope: "mine" to find artifacts your current session has published — useful when you have published several artifacts across a session and need to pass their URLs to another tool or embed them in a report. Use scope: "shared" to find artifacts others have shared with you. Use scope: "all" for the full visible set.

The truncated field in the response tells you whether the result was capped at limit. If truncated: true and you need the full list, increase limit or paginate with successive calls narrowed by date or title.

HTML vs Markdown

Both file types are supported. The distinction is in what the hosted page renders:

HTML — The harness serves the file as-is. You control the full page: CSS, JavaScript, inline charts, interactive tables. This is the right format when the artifact is a tool rather than just content — a dashboard the reader interacts with, a report with collapsible sections, a diff viewer, a coverage heatmap.

Markdown — The harness renders the Markdown to HTML using standard rendering (including GitHub Flavored Markdown). You get properly formatted prose, code blocks, tables, and headers. No JavaScript execution. This is the right format when the artifact is a document — a decision record, a runbook, a meeting summary, an architectural specification.

When in doubt: if the reader needs to do something on the page, use HTML. If the reader needs to read the page, use Markdown.

23.3 PushNotification — Reaching a User Who Isn't Watching

The REPL and Artifact tools produce output the user finds when they look. PushNotification is the tool for when the output needs to find the user.

export interface PushNotificationInput {
  message: string;  // ≤200 chars
  status: "proactive";
}

export interface PushNotificationOutput {
  message: string;
  pushSent?: boolean;
  localSent?: boolean;
  disabledReason?: "config_off" | "user_present" | "no_transport";
  sentAt?: string;  // ISO timestamp
}

The status: "proactive" Requirement

The status field has exactly one valid value: "proactive". This is not a placeholder for a richer enum — it is a semantic declaration. You are telling the harness that the agent decided to send this notification based on its own judgment, not in response to a user request.

The distinction matters because the harness's notification routing logic treats proactive notifications differently from reactive ones. A proactive notification fires only when the user is away from the session. Sending one when the user is actively watching would be interruptive and redundant — they can see the output directly. The harness handles this automatically.

Delivery Mechanics

The output fields tell you exactly what happened:

FieldMeaning
pushSent: trueA mobile or desktop push notification was delivered
localSent: trueA local OS notification was shown
disabledReason: "user_present"User is actively in the session — notification skipped (this is correct behavior)
disabledReason: "config_off"Notifications are disabled in user settings — not an error, just configuration
disabledReason: "no_transport"No push backend is configured — nothing was sent
sentAtISO 8601 timestamp of when the notification was dispatched

The user_present reason is not a failure. When you see it, the notification was correctly suppressed — the user does not need a push because they are reading the session output right now. Build logic that treats user_present as success, not as an error to retry.

When to Fire

PushNotification belongs at decision points where the agent has completed a meaningful chunk of work and the user has stepped away. The canonical patterns:

// Long-running task completed
await PushNotification({
  message: "Security audit complete — 3 HIGH findings in src/auth/. Review at: https://claude.ai/artifacts/xyz",
  status: "proactive",
});

// Something requires a decision before proceeding
await PushNotification({
  message: "Deployment plan generated. Requires your approval before I can proceed with the kubectl apply.",
  status: "proactive",
});

// Unexpected condition discovered
await PushNotification({
  message: "Found hardcoded API key in commits/config.py:47. Paused. Need you to confirm remediation plan.",
  status: "proactive",
});

The 200-Character Constraint

Two hundred characters is tight. Mobile lock screens truncate at roughly 100 characters depending on the device and notification style. Write notifications as if they will be read on a phone screen: front-load the important information, cut every filler word.

Too longBetter
"The security audit that you asked me to run has now been completed and there were three findings of HIGH severity that you should probably look at when you get a chance.""Audit done: 3 HIGH findings in src/auth. Artifact: claude.ai/artifacts/xyz"
"I encountered an unexpected error while running the database migration script and I am not sure how to proceed.""Migration failed at step 4/7. Needs manual review. Error: FK constraint on users.org_id"

The constraint forces clarity. If you cannot say what happened in 200 characters, the notification is not specific enough to be actionable.

23.4 RemoteTrigger — Automation From Outside the Session

PushNotification sends a signal out. RemoteTrigger is the mechanism for signals coming in. It exposes a CRUD interface for managing triggers — webhooks, schedule entries, external event subscriptions — that can wake or interact with sessions from outside the harness.

export interface RemoteTriggerInput {
  action: "list" | "get" | "create" | "update" | "run";
  trigger_id?: string;  // required for get, update, run
  body?: { [k: string]: unknown };  // required for create, update
}

export interface RemoteTriggerOutput {
  status: number;
  json: string;
  summary?: string;
}

The response is a thin envelope: HTTP-style status code, raw json string containing the server's response body, and an optional summary that the harness generates as a human-readable interpretation.

The Five Actions

list — Returns all triggers visible to the current session. No trigger_id or body required.

const result = await RemoteTrigger({ action: "list" });
const triggers = JSON.parse(result.json);
// triggers: [{ id, name, type, enabled, lastFiredAt, ... }, ...]

get — Returns the full definition of a specific trigger.

const result = await RemoteTrigger({
  action: "get",
  trigger_id: "trig_abc123",
});
const trigger = JSON.parse(result.json);

create — Defines a new trigger. The body structure depends on the trigger type.

const result = await RemoteTrigger({
  action: "create",
  body: {
    name: "nightly-security-audit",
    type: "schedule",
    schedule: "0 2 * * *",   // 2am daily, cron syntax
    payload: {
      task: "run-security-audit",
      target: "/Users/DOANTX26/Documents/2026/src",
      notify: true,
    },
  },
});
const { id } = JSON.parse(result.json);

update — Modifies an existing trigger. Provide the trigger_id and a body with the fields to change.

await RemoteTrigger({
  action: "update",
  trigger_id: "trig_abc123",
  body: {
    schedule: "0 3 * * 1",  // change to 3am on Mondays only
    enabled: false,          // temporarily disable
  },
});

run — Fires the trigger immediately, regardless of its schedule or conditions. Useful for testing that a trigger's handler works correctly before relying on it in production.

const result = await RemoteTrigger({
  action: "run",
  trigger_id: "trig_abc123",
  body: {
    dry_run: true,  // most handlers respect this — no side effects
  },
});
console.log(result.summary);

How Triggers Connect to Sessions

The conceptual model: a trigger is a registered entry point. When the trigger fires — because a schedule elapsed, an external system called a webhook, or run was invoked directly — the harness can start a new session, wake a suspended session, or deliver the trigger's payload to a running session.

This makes RemoteTrigger the infrastructure layer beneath ScheduleWakeup (covered in Chapter 14). Where ScheduleWakeup creates one-shot wakeups tied to the current session, RemoteTrigger manages persistent, named triggers that exist beyond any individual session.

flowchart TD
    E[External Event<br/>CI webhook / cron / API] --> T[RemoteTrigger<br/>trig_abc123]
    T -->|fires| H[Harness]
    H -->|new session| S1[New Session<br/>with trigger payload]
    H -->|resume| S2[Suspended Session<br/>awaiting trigger]
    S1 --> P[PushNotification<br/>on completion]
    S2 --> A[Artifact publish<br/>on completion]

The pattern for scheduled automation: create a trigger with a cron schedule and a payload that describes the work. The harness starts a session, Claude reads the payload, executes the work, publishes an artifact, sends a notification, and exits. The trigger fires again at the next scheduled time. You never need to manage the loop manually.

Checking Results

The RemoteTriggerOutput.status mirrors HTTP status semantics:

StatusMeaning
200Success
201Created (for create action)
404trigger_id not found
409Conflict (trigger name already exists, or trigger is already running)
422Invalid body — schema validation failed

Parse status before trusting json. A 404 with a valid JSON error body is a failure, not a success.

const result = await RemoteTrigger({
  action: "get",
  trigger_id: maybeId,
});

if (result.status === 404) {
  // Trigger was deleted or never existed — recreate it
  await RemoteTrigger({
    action: "create",
    body: defaultTriggerDefinition,
  });
} else if (result.status !== 200) {
  throw new Error(`RemoteTrigger get failed: ${result.status} — ${result.json}`);
}

23.5 ReportFindings — Structured Code Review Output

The tools so far produce outputs that go somewhere — a URL, a push, a trigger. ReportFindings produces output that stays in the conversation: a structured list of code review findings that the harness renders as a first-class UI element rather than raw text.

export interface ReportFindingsInput {
  level?: "low" | "medium" | "high" | "xhigh" | "max";
  findings: {
    file: string;           // repo-relative path
    line?: number;          // 1-indexed
    summary: string;        // one-sentence statement of the problem
    short_summary?: string; // ≤60 chars for compact display
    failure_scenario: string;  // concrete inputs/state → wrong output
    category?: string;      // kebab-case slug
    verdict?: "CONFIRMED" | "PLAUSIBLE";
    outcome?: "fixed" | "skipped" | "no_change_needed";
  }[];  // max 32 findings
}

export interface ReportFindingsOutput {
  count: number;
  level?: string;
  findings: [...];  // echoed back
}

Why a Dedicated Tool

You could write code review output as plain text or return it from a REPL call. ReportFindings exists because structure enables tooling. When findings arrive through this interface, the harness can:

  • Render them as a sortable, filterable table in the UI
  • Link each finding to its file and line in the editor
  • Track outcomes across multiple review passes
  • Feed the structured data into downstream workflows (ticket creation, PR comments, metrics)

Returning findings as freeform text forfeits all of this. ReportFindings is the difference between a report that is read and a report that is acted on.

The failure_scenario Field

The most important field in the findings schema is failure_scenario. It is not a description of the problem in the abstract — it is a concrete reproduction case: what specific inputs, state, or conditions trigger the wrong behavior, and what the wrong output is.

Compare:

summaryfailure_scenario
"JWT validation does not check expiry""Call /api/profile with Authorization: Bearer <expired_token_from_2024>. Server returns 200 with user data instead of 401."
"SQL query is not parameterized""POST /api/search with body {\"q\": \"'; DROP TABLE users; --\"}. The query runs as: SELECT * FROM products WHERE name = ''; DROP TABLE users; --'"
"Missing null check on user input""Call parseConfig({}) — config.database is undefined. Line 47 calls config.database.host, throws TypeError: Cannot read properties of undefined."

The failure_scenario column is what makes a finding actionable. A developer reading the summary has to figure out if it matters. A developer reading the failure scenario knows immediately: here is the exact input, here is the exact wrong behavior, here is where to look.

Write failure scenarios as if you are writing a failing test case. Concrete state in, specific wrong output out.

Ordering and the Level Ceiling

Findings must be ordered by severity — highest severity first. The level parameter at the top of the input sets the maximum severity level the caller is willing to report. This is a filter, not a label: if you call with level: "medium", only findings at medium severity or below are included in the output. Findings above the ceiling are silently dropped.

In practice, most callers either omit level (no ceiling) or set it to the severity bucket they are acting on now. A CI gate that blocks on high-severity findings might call ReportFindings twice: once with level: "high" to determine whether to block, and once without level to generate the complete report for the PR comment.

The maximum of 32 findings per call is a hard limit. For codebases with more than 32 issues, group by category or severity and make multiple calls. The harness appends findings from successive ReportFindings calls into the same review session, so the total count across calls is not capped at 32 — only the per-call count is.

Verdict and Outcome

The verdict field signals how confident the reviewer is:

  • "CONFIRMED" — the reviewer has verified the finding by reading the code, constructing the failure scenario, and confirming the behavior exists as described. Use this when you have traced the exact execution path.
  • "PLAUSIBLE" — the reviewer believes the finding is likely real based on code patterns, but has not fully traced the execution path. Use this for findings that require more context (runtime behavior, configuration files not in scope, external service behavior) to fully confirm.

The outcome field is for tracking remediation:

  • "fixed" — the issue was addressed in a subsequent edit
  • "skipped" — the issue was reviewed and intentionally not fixed
  • "no_change_needed" — on closer inspection, the issue was not actually present

These fields are optional on initial submission and filled in as the review cycle progresses. A workflow that runs ReportFindings, waits for edits, then re-runs ReportFindings on the same findings with updated outcome values builds a complete audit trail.

23.6 Lab: Report Generator That Publishes Interactive HTML Artifacts

This lab builds a complete code review pipeline. It reads a Python source directory, runs a REPL-based analysis, generates interactive HTML using structured findings, and publishes the result as an artifact. It demonstrates the integration between REPL (computation), ReportFindings (structure), and Artifact (publication).

What We Are Building

flowchart TD
    SRC[Source Files<br/>src/**/*.py] -->|Bash: find + read| RAW[Raw File Content]
    RAW -->|REPL: analyze| METRICS[Complexity Metrics<br/>+ Issue Candidates]
    METRICS -->|ReportFindings| STRUCT[Structured Findings<br/>32 max, severity-ordered]
    STRUCT -->|REPL: build HTML| HTML[Interactive Report<br/>sortable, filterable]
    HTML -->|Artifact: publish| URL[Live URL<br/>shared with team]
    URL -->|PushNotification| NOTIFY[Team Notified]

Step 1: Collect Source Files

// In the harness session
const fileList = await Bash({
  command: `find /Users/DOANTX26/Documents/2026/src -name "*.py" -not -path "*/.*" | head -100`,
  description: "Enumerate Python source files",
});

const files = fileList.stdout.trim().split("\n").filter(Boolean);

Step 2: Analyze With REPL

The REPL accumulates findings across multiple calls. First call: initialize the state and define the analysis functions.

// REPL call 1 — initialize analysis state
const findings = [];
const fileMetrics = new Map();

function analyzeFile(path, content) {
  const lines = content.split("\n");
  const issues = [];

  // Check: hardcoded credentials pattern
  lines.forEach((line, i) => {
    if (/password\s*=\s*["'][^"']{4,}["']/i.test(line) &&
        !/test|mock|example|sample|fake/i.test(line)) {
      issues.push({
        file: path,
        line: i + 1,
        summary: "Hardcoded password literal assigned to variable",
        short_summary: "Hardcoded password",
        failure_scenario: `Line ${i + 1}: ${line.trim().slice(0, 120)} — credential exposed in source.`,
        category: "security",
        verdict: "CONFIRMED",
      });
    }
  });

  // Check: except bare clause
  lines.forEach((line, i) => {
    if (/^\s*except\s*:/.test(line)) {
      issues.push({
        file: path,
        line: i + 1,
        summary: "Bare except clause swallows all exceptions including KeyboardInterrupt",
        short_summary: "Bare except clause",
        failure_scenario: `except: at line ${i + 1} catches BaseException. Any error in the try block — including syntax errors during reload and KeyboardInterrupt — is silently swallowed.`,
        category: "error-handling",
        verdict: "CONFIRMED",
      });
    }
  });

  // Check: TODO/FIXME markers in security-sensitive files
  const isSecurityFile = /auth|session|token|password|crypt|permission/i.test(path);
  if (isSecurityFile) {
    lines.forEach((line, i) => {
      if (/\b(TODO|FIXME|HACK|XXX)\b/i.test(line)) {
        issues.push({
          file: path,
          line: i + 1,
          summary: "Incomplete implementation marker in security-sensitive file",
          short_summary: "TODO in security file",
          failure_scenario: `${path}:${i + 1} — ${line.trim()} — security logic is incomplete or known-broken per the marker.`,
          category: "security",
          verdict: "PLAUSIBLE",
        });
      }
    });
  }

  fileMetrics.set(path, {
    lines: lines.length,
    issues: issues.length,
  });

  return issues;
}

console.log("Analysis functions ready. State initialized.");

Second REPL call: run the analysis over the file content passed from the Bash results.

// REPL call 2 — analyze files (called in a loop per file batch)
// fileContents is passed as a JSON string injected into this call
const batch = JSON.parse(fileContentsJson);

for (const { path, content } of batch) {
  const fileIssues = analyzeFile(path, content);
  findings.push(...fileIssues);
}

console.log(`Batch complete. Total findings so far: ${findings.length}`);

Step 3: Submit Structured Findings

Once analysis is complete, emit findings through ReportFindings. Sort by severity before submission.

  .sort((a, b) => (severityOrder[a.category] ?? 99) - (severityOrder[b.category] ?? 99))
  .slice(0, 32);  // enforce the max

await ReportFindings({
  level: "high",
  findings: sortedFindings,

What the Lab Demonstrates

REPL state accumulation. The findings array built in REPL call 1 is still live in call 3. No file I/O was needed to pass state between analysis steps. This is the correct pattern for multi-step computations that are logically a single workflow — avoid round-tripping data through files when the REPL can hold it in memory.

ReportFindings as a structural contract. The structured findings drive both the tool output (which the harness renders as a reviewable list) and the HTML generation (which uses the same data to build the interactive table). One data structure, two consumers.

Artifact versioning in practice. The first publish creates the URL. The second publish updates the same URL in place. The PR author bookmarks one URL and always sees the current state of the review. No link rot, no confusion about which report is current.

PushNotification as a non-blocking signal. The notification fires after the artifact is published. If the developer is watching the session, disabledReason: "user_present" comes back and nothing happens — which is correct. If they walked away, a push arrives with the URL embedded in the 200-character message.

Summary

Five tools, each solving a distinct layer of the output problem:

  • REPL executes JavaScript in a persistent in-process sandbox. State survives across calls within a session, top-level await is native, and tools registered during execution extend the session's tool surface. Use it for stateful computation, dynamic data processing, and environments where static tool registration is insufficient.
  • Artifact publishes HTML or Markdown to a hosted URL. The url field makes updates in-place rather than creating a new address. The 409 conflict is the concurrency guard — standard resolution is read, merge, republish. force: true is for automation that owns a specific artifact. list finds artifacts by scope when you need to retrieve URLs across a session.
  • PushNotification reaches users who are not watching. The status: "proactive" value is the declaration that the agent decided to send this. disabledReason: "user_present" is success, not failure. The 200-character limit is a forcing function for clarity.
  • RemoteTrigger manages the automation entry points: create, list, get, update, run. It is the persistent layer beneath ScheduleWakeup — named triggers that survive session boundaries and connect external systems to harness sessions.
  • ReportFindings emits code review findings as structured data. The failure_scenario field is what makes findings actionable — concrete inputs and concrete wrong outputs, not abstract descriptions. Maximum 32 findings per call; multiple calls accumulate. verdict signals confidence; outcome tracks remediation.

The lab integrates all five. The REPL holds computation state, ReportFindings structures the output, Artifact publishes it durably, and PushNotification closes the loop with the human who needs to act on it.
