Chapter 7: Web Tools — WebFetch and WebSearch

"The model cannot browse the web. Your harness can. There is a meaningful difference."

7.1 WebFetch: The Fetch-Parse-Extract Pipeline

When Claude needs to read a URL, it does not receive raw HTML. The harness runs a three-stage pipeline before a single byte reaches the model:

URL input
    │
    ▼
┌─────────────────────────────────────┐
│  Stage 1: Fetch                     │
│  HTTP GET → follow redirects        │
│  auto-upgrade HTTP → HTTPS          │
│  15-minute cache check              │
└────────────────────┬────────────────┘
                     │ raw HTML / bytes
                     ▼
┌─────────────────────────────────────┐
│  Stage 2: Convert                   │
│  HTML → Markdown                    │
│  strip nav, ads, boilerplate        │
│  preserve code blocks, tables       │
└────────────────────┬────────────────┘
                     │ markdown text
                     ▼
┌─────────────────────────────────────┐
│  Stage 3: Extract                   │
│  small fast model runs your prompt  │
│  against the markdown content       │
│  returns extracted result string    │
└────────────────────┬────────────────┘
                     │ result
                     ▼
            WebFetchOutput.result

The key insight: you provide the extraction instructions. The prompt field is not decoration — it is what the internal model uses to decide what to return from the page. A vague prompt produces a vague result. A precise prompt produces a precise result.

The Interface

export interface WebFetchInput {
  url: string;     // fully-formed valid URL, HTTP auto-upgraded to HTTPS
  prompt: string;  // what to extract from the page content
}

export interface WebFetchOutput {
  bytes: number;        // size of fetched content
  code: number;         // HTTP response code
  codeText: string;     // HTTP response text
  result: string;       // processed result from applying prompt to content
  durationMs: number;
  url: string;          // the URL that was fetched
  artifactRead?: { slug: string; ver?: string };
}

The result field is what you act on. The rest — bytes, code, codeText, durationMs — are diagnostic metadata. The artifactRead field appears when the URL points to a hosted Claude artifact; the harness can read its own published artifacts as first-class resources.

Writing Effective Prompts

The extraction prompt is the leverage point. Compare these two calls to the same URL:

// Weak: vague extraction, produces a summary of the whole page
{
  url: "https://docs.python.org/3/library/pathlib.html",
  prompt: "tell me about pathlib"
}

// Strong: targeted extraction, produces a usable reference
{
  url: "https://docs.python.org/3/library/pathlib.html",
  prompt: "extract all method signatures from the Path class with their parameters and return types, formatted as a markdown table"
}

The strong prompt gives the internal extraction model a concrete, verifiable task. The result will be a table you can directly use.

Practical prompt patterns that work well:

Use CasePrompt Pattern
API documentation"List all endpoints with HTTP method, path, and required parameters"
Release notes"Extract all breaking changes and new features from this changelog page"
Comparison"Extract the feature comparison table between products A and B"
Error troubleshooting"Find the solution or workaround for this error: [paste error]"
Code examples"Extract all code examples related to authentication, preserving the code blocks"

What Comes Back

The result is a string — it can be a paragraph, a list, a table, or even a code block, depending on what you asked for and what the page contained. If the page content is very large, the extraction model may summarize. This is by design: the goal is to return what is relevant to your prompt, not a faithful copy of the page.

The bytes field tells you the size of the fetched content before conversion. A value of 500KB for a documentation page is normal. If bytes is unexpectedly small (under 1KB), the page likely blocked the request or returned a minimal error page — check code and codeText.

7.2 WebSearch: Query to Ranked Results

WebSearch takes a natural-language query and returns a list of search results with titles and URLs. It does not fetch the pages. The workflow for research is: search first, fetch selectively.

The Interface

export interface WebSearchInput {
  query: string;                    // min 2 chars
  allowed_domains?: string[];       // only include results from these
  blocked_domains?: string[];       // never include results from these
}

export interface WebSearchOutput {
  query: string;
  results: (
    | { tool_use_id: string; content: { title: string; url: string }[] }
    | string
  )[];
  durationSeconds: number;
  searchCount?: number;
}

The results field is a union type. In normal operation you get the object variant: a tool_use_id (the internal identifier for this search call) and content — an array of { title, url } pairs. The string variant appears when the search engine returns an unstructured result or when the search fails partway; you should check for and handle this defensively.

The searchCount field, when present, tells you how many underlying search requests were made. For most queries this is 1. Complex queries or domain-filtered searches may trigger multiple.

durationSeconds reflects total search time. Values above 3-4 seconds may indicate the search backend is under load.

Citation Requirement

Using WebSearch results carries a citation obligation. When your agent presents findings derived from search results, it must include a Sources: section with the URLs used. This is not a style preference — it is a tool usage requirement enforced at the harness level. Harnesses that surface search results to users without sourcing are violating the contract.

## Findings

The latest version of Pydantic (v2.10) introduces...

## Sources
- https://docs.pydantic.dev/latest/changelog/
- https://pypi.org/project/pydantic/

Geographic Limitation

WebSearch is only available when running in the United States. Harnesses deployed in other regions will encounter failures. If you are building a globally-deployed harness, plan for this: either route search requests through a US endpoint, substitute a different search MCP server, or degrade gracefully to WebFetch-only operation when WebSearch fails.

Usage Tracking

As of v2.1.92, web_search_requests and web_fetch_requests appear as distinct counters in the usage stats returned with each response. When running cost analysis with /cost, you will see cache-hit breakdowns that include web tool calls. Harnesses that run many search-and-fetch cycles can accumulate meaningful usage; the counters give you visibility into this.

7.3 Domain Filtering

Both tools support domain filtering, but the semantics differ and understanding the difference matters.

WebSearch: allowed_domains and blocked_domains

For WebSearch, these arrays filter which results are included in the returned list:

// Only return results from official Python docs
{
  query: "asyncio event loop best practices",
  allowed_domains: ["docs.python.org", "peps.python.org"]
}

// Exclude forums and Q&A sites
{
  query: "asyncio event loop best practices",
  blocked_domains: ["stackoverflow.com", "reddit.com", "quora.com"]
}

The allowed_domains and blocked_domains options are mutually exclusive in practice — combining them produces unpredictable behavior depending on which constraint takes precedence. Pick one approach per query.

When to use allowed_domains: You need authoritative information from specific sources — official documentation, trusted security databases (nvd.nist.gov, cve.mitre.org), or specific vendors. The search engine may return many low-quality results for technical queries; filtering to known-good domains improves signal-to-noise ratio significantly.

When to use blocked_domains: You want broad coverage but want to exclude aggregator sites, cached copies, or low-quality sources. Blocking mirrors and content farms keeps results fresh and authoritative.

flowchart LR
    Q[Query] --> SE[Search Engine]
    SE --> R1["result: docs.python.org"]
    SE --> R2["result: stackoverflow.com"]
    SE --> R3["result: blog.example.com"]
    SE --> R4["result: realpython.com"]

    subgraph "allowed_domains: [docs.python.org, peps.python.org]"
        R1 --> PASS1[included]
        R2 --> FAIL1[excluded]
        R3 --> FAIL2[excluded]
        R4 --> FAIL3[excluded]
    end

Network-Level Filtering in Settings

Separate from the per-call options, Claude Code's settings layer has allowedDomains (global network sandbox). This is different in scope: it controls which domains the entire harness can reach over the network, not which results WebSearch returns. An allowedDomains restriction at the settings level will cause WebFetch to fail for any URL outside the list, regardless of what the model requests.

Harness authors building restricted environments should use both layers:

  • Settings allowedDomains: network-level allowlist (which hosts can be reached at all)
  • WebSearch.allowed_domains: search-result filter (which results are returned)

7.4 The 15-Minute Cache

Both WebFetch and WebSearch cache their results automatically for 15 minutes. The cache is:

  • Automatic: no opt-in or configuration required
  • Self-cleaning: entries expire after 15 minutes without intervention
  • Shared across tool calls: a URL fetched by one tool call in a session is served from cache by the next call to the same URL within the window
  • Keyed by URL + prompt for WebFetch (the same URL with a different prompt is a cache miss)

Practical Implications

Cache hits are fast and free. A WebFetch that costs 800ms and several hundred tokens on a cold fetch returns almost instantly from cache. For research workflows that touch the same documentation page multiple times — reading it once to understand structure, then again with a more targeted prompt — the second call is effectively zero cost.

15 minutes is long enough for a research session. In practice, most research agents fetch a URL, process it, and move on. Revisiting the same URL within a session is uncommon for fresh research. The 15-minute window covers it comfortably.

Design for cache misses. If your workflow runs longer than 15 minutes and needs to re-verify a URL, treat each access as a potential cache miss. Do not assume the cached version is still valid for latency-sensitive decisions.

Cache hit visibility. As of v2.1.92, cache-hit breakdowns appear in /cost output. You can observe how many tool calls were served from cache versus requiring fresh network requests.

/cost output (example)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Cache Key Precision

For WebSearch, the cache key includes the full query string, allowed_domains, and blocked_domains. Changing any of these triggers a fresh search. If you are running a multi-agent workflow where several agents search for related but slightly different queries, each gets its own cache entry — there is no semantic deduplication. Design queries to be reusable within a session if cache efficiency matters.

7.5 Redirect Handling

HTTP redirects are common: documentation sites redirect to versioned paths, CDN nodes redirect based on geography, URLs get canonicalized. WebFetch handles same-host redirects transparently. Cross-host redirects are different.

Cross-Host Redirect Behavior

When a URL redirects to a different hostname, WebFetch does not silently follow it. Instead, it reports the redirect and provides the destination URL. The tool output will include the redirect URL in its result, and the url field in WebFetchOutput will reflect where the request ended up.

The practical flow for your agent:

Step 1: Request URL A
   WebFetch("http://example.com/old-path", "extract content")
   
Step 2: Response indicates cross-host redirect to URL B
   result: "Redirected to https://new-example.com/current-path"
   url: "https://new-example.com/current-path"
   
Step 3: Make a new request to URL B
   WebFetch("https://new-example.com/current-path", "extract content")

Why not auto-follow? Cross-host redirects change the origin of the content. Security-conscious harnesses need to know if a documentation URL is silently redirecting to a third-party domain — that is a supply chain risk, not a transparent optimization. The explicit report-and-follow pattern keeps your agent aware of what domains it is actually consuming.

HTTP to HTTPS Upgrade

HTTP URLs are upgraded to HTTPS automatically before the request is made. If you pass http://example.com, the harness fetches https://example.com. The url field in the response will reflect the HTTPS version. This is unconditional — you cannot opt out of the upgrade. For any URL that only exists on HTTP (rare in 2026, but relevant if you are working with local test servers or legacy infrastructure), WebFetch will fail.

7.6 Authenticated Content: The Hard Boundary

This is the most important limitation in the web tools. WebFetch cannot access authenticated or private content. This is not a configuration issue — it is a fundamental architectural constraint. The harness fetches URLs as an unauthenticated HTTP client. If the server requires authentication — a session cookie, an OAuth token, a corporate SSO challenge — the request fails.

What Fails

ServiceWhy It Fails
Google Docs / Google SheetsRequires Google login, returns login redirect
ConfluenceRequires Atlassian SSO or basic auth
JiraRequires Atlassian authentication
Private GitHub reposRequires auth token or session
Azure DevOps (authenticated pages)Requires AAD authentication
Internal corporate wikisBehind SSO
Notion pages (private)Requires Notion auth
Slack archivesRequires Slack auth

The failure mode is usually a 401 or 302 redirect to a login page. WebFetchOutput.code will be 401 or 200 (with a login page HTML as content), result will contain something useless like "Please sign in to continue."

Fallback Patterns

Pattern 1: MCP tool for the service. If you need to read Confluence, Jira, or GitHub, use an MCP server that handles authentication. The MCP server runs with credentials and makes authenticated API calls on your behalf; the harness receives the result without ever touching the auth flow.

GitHub URL (private repo)  →  Use gh CLI via Bash
Jira ticket               →  Use Jira MCP server
Confluence page           →  Use Confluence MCP server
ADO work item             →  Use ADO REST API via Bash + PAT

Pattern 2: gh CLI for GitHub. For GitHub specifically, avoid WebFetch entirely. The gh CLI handles authentication natively and provides structured output:

# Instead of WebFetch("https://github.com/owner/repo/issues/42")
gh issue view 42 --repo owner/repo --json title,body,comments

# Instead of WebFetch("https://github.com/owner/repo/pull/123")
gh pr view 123 --repo owner/repo --json title,body,files,reviews

The structured JSON output from gh is far more useful than the markdown extraction WebFetch would produce even if authentication were not an issue.

Pattern 3: Export then fetch. For Confluence pages or internal documentation, an intermediate export step makes the content accessible:

1. Bash: curl -u "$CONFLUENCE_USER:$CONFLUENCE_TOKEN" \
          "https://confluence.internal/rest/api/content/12345?expand=body.storage" \
          -o /tmp/page.json
2. Read: /tmp/page.json  (or extract body.storage field)
3. Process: the content is now local, no WebFetch needed

Pattern 4: Artifact export for Notion/Google Docs. Export to PDF or HTML first, download to a local path, then use Read to process it. This is slower but gives you full content fidelity.

flowchart TD
    A[Need content from authenticated URL] --> B{Can use CLI tool?}
    B -->|GitHub| C["gh CLI via Bash"]
    B -->|ADO| D["ADO REST API via Bash + PAT"]
    B -->|Other| E{MCP server available?}
    E -->|Yes| F[Use MCP tool]
    E -->|No| G[Export → Download → Read]
    C & D & F & G --> H[Content available to agent]

What Succeeds

Public content works reliably:

  • Public GitHub repos, issues, PRs (but gh CLI is still better)
  • Public npm package pages (npmjs.com)
  • PyPI package pages (pypi.org)
  • Public documentation sites
  • Public CVE databases (nvd.nist.gov, cve.mitre.org)
  • Wikipedia
  • API documentation sites (stripe.com/docs, openai.com/docs, etc.)
  • Stack Overflow public questions

7.7 Lab: Build a Multi-Source Research Agent

This lab builds a research agent that gathers information on a technical topic from multiple independent sources, cross-validates findings, and produces a sourced report. It demonstrates all the web tool mechanics: domain-filtered search, selective fetch with targeted prompts, cache efficiency, and fallback handling.

Goal

Given a topic — for example, "Python asyncio event loop performance in 3.12 vs 3.11" — the agent should:

  1. Search for relevant sources using domain filtering
  2. Fetch the top 3-5 most authoritative sources with targeted extraction prompts
  3. Identify any claims that appear in multiple independent sources (triangulation)
  4. Produce a sourced report with a confidence level per claim

Architecture

flowchart TD
    INPUT[Topic string] --> SEARCH1
    INPUT --> SEARCH2

    SEARCH1["WebSearch\nallowed_domains: [docs.python.org, peps.python.org]\nquery: topic + 'official docs'"]
    SEARCH2["WebSearch\nblocked_domains: [reddit.com, quora.com]\nquery: topic + 'benchmark analysis'"]

    SEARCH1 --> URLS1[Official doc URLs]
    SEARCH2 --> URLS2[Technical blog URLs]

    URLS1 --> RANK[Rank by domain authority\n+ title relevance]
    URLS2 --> RANK

    RANK --> TOP5[Top 5 URLs]

    TOP5 --> FETCH1["WebFetch URL1\nprompt: extract claims"]
    TOP5 --> FETCH2["WebFetch URL2\nprompt: extract claims"]
    TOP5 --> FETCH3["WebFetch URL3\nprompt: extract claims"]

    FETCH1 & FETCH2 & FETCH3 --> TRIANGULATE[Cross-validate claims\nacross sources]

    TRIANGULATE --> REPORT[Sourced report\nwith confidence levels]

Implementation

The following workflow script implements this pattern. The meta literal is pure — no computed values.

export const meta = {
  name: "multi-source-research",
  description: "Research a technical topic across multiple independent sources",
  phases: ["search", "fetch", "triangulate", "report"],
};

export default async function research({ args, agent, parallel, phase, log, budget }) {
  const topic = args as string;

  // Phase 1: Parallel searches across different source types
  await phase("search");
  log(`Searching for: ${topic}`);

  const [officialResults, technicalResults] = await parallel([
    () => agent(`
      Use WebSearch with allowed_domains ["docs.python.org", "peps.python.org", "devguide.python.org"]
      to search for: ${topic}
      Return a JSON array of {title, url} objects, maximum 5 results.
    `, { schema: { type: "array", items: { type: "object", properties: { title: { type: "string" }, url: { type: "string" } } } } }),

    () => agent(`
      Use WebSearch with blocked_domains ["reddit.com", "quora.com", "stackexchange.com"]
      to search for: ${topic} performance benchmark
      Return a JSON array of {title, url} objects, maximum 5 results.
    `, { schema: { type: "array", items: { type: "object", properties: { title: { type: "string" }, url: { type: "string" } } } } }),
  ]);

  log(`Found ${officialResults.length} official + ${technicalResults.length} technical sources`);

  // Combine and deduplicate by URL
  const allUrls = [...officialResults, ...technicalResults]
    .filter(Boolean)
    .slice(0, 5);

  // Phase 2: Fetch each source with targeted extraction
  await phase("fetch");

  const extractions = await parallel(
    allUrls.map(({ title, url }) => async () => {
      log(`Fetching: ${title}`);
      return agent(`
        Use WebFetch on this URL: ${url}
        
        Use this extraction prompt:
        "Extract all specific claims about performance, benchmarks, or behavioral changes.
         For each claim, note: (1) what was claimed, (2) any numbers or metrics cited,
         (3) whether it is presented as measured data or opinion.
         Format as a JSON array of claim objects."
        
        Return the extracted claims as a JSON array, or an empty array if the page
        was unavailable or contained no relevant claims.
        Include the source URL in each claim object.
      `, {
        schema: {
          type: "array",
          items: {
            type: "object",
            properties: {
              claim: { type: "string" },
              metric: { type: "string" },
              type: { enum: ["measured", "opinion", "unclear"] },
              source_url: { type: "string" },
            },
          },
        },
      });
    })
  );

  const allClaims = extractions.flat().filter(Boolean);
  log(`Extracted ${allClaims.length} claims across ${allUrls.length} sources`);

  // Phase 3: Triangulate — find claims that appear in multiple sources
  await phase("triangulate");

  const triangulation = await agent(`
    Given these claims extracted from multiple sources about "${topic}":
    
    ${JSON.stringify(allClaims, null, 2)}
    
    Identify:
    1. Claims that appear in 2+ independent sources (high confidence)
    2. Claims that appear in only 1 source (needs verification)  
    3. Claims that directly contradict each other (conflicted)
    
    Return a JSON object with three arrays: high_confidence, needs_verification, conflicted.
    Each item should include the claim text, source URLs supporting it, and a confidence score 0-1.
  `, {
    schema: {
      type: "object",
      properties: {
        high_confidence: { type: "array" },
        needs_verification: { type: "array" },
        conflicted: { type: "array" },
      },
    },
  });

  // Phase 4: Generate sourced report
  await phase("report");

  const report = await agent(`
    Write a technical research report on: "${topic}"
    
    Use these triangulated findings:
    ${JSON.stringify(triangulation, null, 2)}
    
    Format:
    ## Summary
    [2-3 sentence executive summary]
    
    ## High-Confidence Findings
    [Bullet list of claims with 2+ source support — include confidence level]
    
    ## Claims Requiring Verification
    [Bullet list of single-source claims — note the source]
    
    ## Conflicting Evidence
    [Any claims that conflict across sources — explain the discrepancy]
    
    ## Sources
    [Full URL list of all sources consulted]
    
    The Sources section is required. Do not omit it.
  `);

  return report;
}

Running the Agent

claude -p 'Run the multi-source-research workflow for the topic: "Python asyncio event loop performance changes in 3.12"' \
  --output-format text

What to Observe

Cache behavior: If you run the same topic twice within 15 minutes, the second run fetches URLs from cache. The durationMs values in the WebFetch outputs will drop from 500-1500ms to near-zero. You will see this reflected in /cost as cache-hit counts.

Domain filtering effectiveness: Compare runs with and without allowed_domains. The filtered run returns fewer but higher-quality results; the unfiltered run may return SEO farms or outdated blog posts. For technical research, filtering is almost always worth it.

Prompt specificity effects: Change the extraction prompt from the detailed version to a simple "summarize this page" and compare the quality of allClaims. The detailed prompt with structured JSON schema output produces claims that can actually be triangulated. The vague prompt produces prose that cannot be compared across sources.

Redirect handling: Some URLs returned by search will redirect. The agent's extraction step should handle this gracefully — the WebFetch call will return information about the redirect, and the model should either follow it or skip the source. Add a fallback in the extraction step:

// In the fetch step, check for redirect indication in result
if (result.includes("Redirected to")) {
  const redirectUrl = extractRedirectUrl(result);
  log(`Following redirect to ${redirectUrl}`);
  // Make a new WebFetch call with the redirect URL
}

Authenticated content failures: If any of the search results point to a Confluence wiki, internal documentation, or login-gated content, the extraction step will return an empty array or an error result. The agent should treat this as a zero-claim source and continue, not stop. The triangulation step is designed to handle sparse data — a source that returns nothing is simply not counted.

Extending the Lab

Add MCP fallback for GitHub: If a search result URL is a GitHub URL, route it through gh CLI instead of WebFetch:

// Before calling WebFetch, check if URL is GitHub
if (url.includes("github.com")) {
  // Use gh CLI for better auth + structured output
  const ghOutput = await agent(`
    Use Bash to run: gh api /repos/{owner}/{repo}/contents/{path} or 
    gh issue view {number} --repo {owner}/{repo} --json body
    for URL: ${url}
  `);
  return parseGhOutput(ghOutput);
}

Add a completeness critic: After generating the report, spawn a separate agent to review it for gaps:

const critique = await agent(`
  Review this research report and identify:
  1. Questions about "${topic}" that the report does not answer
  2. Sources that should have been checked but were not
  3. Claims that seem too strong given the evidence cited
  
  Report: ${report}
`);

if (critique.includes("missing")) {
  log("Completeness critic found gaps — running supplemental search");
  // Run targeted searches for the identified gaps
}

Budget-aware depth: Use the budget object to scale how many sources are fetched:

const sourceCount = budget.remaining() > 100_000 ? 8 : 3;
const topUrls = allUrls.slice(0, sourceCount);

Patterns and Anti-Patterns

Pattern: Search-Then-Fetch Selectivity

Do not fetch every URL returned by WebSearch. Search results include titles and URLs — use them to filter before fetching. If you need information about a specific library version, a result titled "Python 2.7 asyncio backport" is not worth fetching. The cheapest fetch is one that never happens.

// Filter search results before fetching
const relevantUrls = searchResults
  .filter(r => r.title.toLowerCase().includes("3.12") || r.title.toLowerCase().includes("performance"))
  .slice(0, 3);

Pattern: Structured Extraction for Machine Processing

When another part of your agent will process the WebFetch result, write extraction prompts that produce structured data. Prose extraction produces text that is hard to compare across sources. JSON extraction produces data you can merge, deduplicate, and analyze.

// For machine processing: structured prompt
prompt: "Extract as JSON array: [{version, change_type, description, breaking: bool}]"

// For human display: prose is fine
prompt: "Summarize the key changes for a developer who is upgrading"

Pattern: Defensive Extraction

Pages change, CDNs rate-limit, and search results sometimes point to dead links. Write extraction handling that expects partial failure:

const result = await webFetch(url, prompt);

// code 200 with near-zero bytes may mean anti-bot page
if (result.bytes < 500) {
  log(`Skipping ${url}: suspiciously small response (${result.bytes} bytes)`);
  return null;
}

// Non-200 means the resource is unavailable
if (result.code !== 200) {
  log(`Skipping ${url}: HTTP ${result.code}`);
  return null;
}

Anti-Pattern: Fetching Before Searching

A common mistake in research agents is starting with WebFetch on a URL the agent already knows — the library homepage, the documentation root — rather than searching for the specific page that answers the question. The search step is not overhead; it is navigation. Let the search engine find the right page instead of fetching the root and navigating manually.

Anti-Pattern: Assuming Fetch Equals Read

WebFetch produces a processed extraction, not a faithful copy of the page. The internal model decides what to include. For tasks that require complete fidelity — exhaustive API reference, full example code, complete change history — fetch the raw content via Bash with curl and Read it directly:

# For complete fidelity, bypass WebFetch entirely
curl -s "https://api.example.com/openapi.json" -o /tmp/openapi.json
# Then: Read /tmp/openapi.json

Anti-Pattern: Ignoring Redirect Signals

When WebFetch reports a cross-host redirect, ignoring it and treating the response as if it were from the original domain is a correctness error. The content came from a different host. Update your source attribution accordingly.

Summary

WebFetch and WebSearch are the harness's connection to public web content. They implement a fetch-convert-extract pipeline that transforms URLs into model-ready information rather than raw HTML. Understanding the pipeline — HTML to markdown to extraction model to result string — tells you where to invest precision: the extraction prompt.

The 15-minute cache keeps repeat accesses fast and efficient. Domain filtering lets you tune signal-to-noise ratio for searches. Cross-host redirect handling keeps your agent aware of where its content actually originates.

The hard boundary is authentication. WebFetch is an unauthenticated client. Anything behind a login — Confluence, Jira, private GitHub, corporate wikis — requires an MCP server or a CLI tool that handles auth separately. Design your research workflows with this constraint in mind from the start, not as an afterthought.

The research agent pattern — search with domain filtering, fetch with structured extraction, triangulate across sources, report with citations — is the foundation for any multi-source knowledge agent. Chapter 33 extends it into a full knowledge management system with memory persistence and fact decay.

In Chapter 8, we move inside the codebase: the LSP tool provides go-to-definition, find-references, and call hierarchy operations for navigating large codebases without reading every file manually.
