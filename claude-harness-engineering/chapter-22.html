Chapter 22: Git Worktree Isolation

"Isolation is not paranoia. It is the precondition for running dangerous work at scale."

Parallel agent workflows fail in a specific, predictable way: two agents write to the same file at the same time. The second writer wins, the first agent's context diverges from reality, and both outputs are now wrong in ways that are hard to detect. You can serialize the agents to avoid the collision — but then you have defeated the purpose of running them in parallel.

Git worktrees are the solution the harness provides. Each worktree is an independent checkout of the same repository, living in its own directory, on its own branch. Agents working in different worktrees share the object store but not the working tree. They cannot stomp each other's files. They produce independent branches that you merge, diff, or discard when the work is done.

This chapter covers the full worktree subsystem: the EnterWorktree and ExitWorktree tools, the configuration knobs that control cost and behavior, the CLI integration, the hook system for non-git VCS, and a lab that builds a parallel database migration system that would be fragile without worktrees and robust with them.

22.1 EnterWorktree: Creating and Entering Isolated Environments

EnterWorktree is the boundary tool. Calling it marks the start of an isolated session: the harness creates a new worktree (or enters an existing one), and subsequent tool calls operate inside that isolated directory until ExitWorktree is called.

The interface:

export interface EnterWorktreeInput {
  name?: string;   // optional, max 64 chars, kebab-case segments
  path?: string;   // enter existing worktree (must be in `git worktree list`)
}

export interface EnterWorktreeOutput {
  worktreePath: string;
  worktreeBranch?: string;
  message: string;
}

Creating a new worktree

When you pass name, the harness creates a new worktree under .claude/worktrees/<name>/ on a new branch named worktree/<name>. The branch tip is determined by worktree.baseRef (covered in §22.2).

const result = await EnterWorktree({ name: "migrate-users-table" });
// result.worktreePath: "/repo/.claude/worktrees/migrate-users-table"
// result.worktreeBranch: "worktree/migrate-users-table"
// result.message: "Created worktree at .claude/worktrees/migrate-users-table on branch worktree/migrate-users-table"

Name constraints exist for operational reasons, not aesthetics. The 64-character cap prevents filesystem path lengths from becoming a problem on macOS and Linux. The kebab-case-segments rule (a-z, 0-9, hyphens, no consecutive hyphens, no leading or trailing hyphens) ensures the name can safely become a branch component. A name like feature/my thing would create a branch worktree/feature/my thing with a space — which git allows but tooling downstream of git often does not.

When name is omitted, the harness generates a name from the current timestamp: auto-20260728-143052. You will see this in practice when using the isolation: "worktree" shorthand in the Agent tool, where the agent does not know in advance what the worktree should be called.

Entering an existing worktree

When you pass path instead of name, the harness enters an existing worktree rather than creating one. The path must appear in git worktree list — the harness validates this before proceeding.

const result = await EnterWorktree({
  path: "/repo/.claude/worktrees/migrate-users-table"
});

This form is used when one agent creates a worktree and a separate agent needs to inspect or continue work in it. The receiving agent calls EnterWorktree with the path returned by the first agent's ExitWorktree output.

Nesting constraint

EnterWorktree can only be called once per session. If a session is already inside a worktree, calling EnterWorktree again returns an error. There is no nesting. This is a deliberate design choice: a worktree session is a scope, not a stack. If you need deeper isolation, spawn a subagent with isolation: "worktree" — the subagent gets its own session and its own worktree scope.

22.2 worktree.baseRef: Where the Branch Starts

Every new worktree branch must start somewhere. The baseRef setting controls that starting point, and the choice has significant consequences for the kind of work you can do in the worktree.

{
  "worktree": {
    "baseRef": "fresh"
  }
}

Two values are supported:

"fresh" — Start from origin/default-branch

origin/main (remote)
     │
     ▼
worktree branch ──── agent makes changes

fresh fetches the current state of the default branch from the remote and branches from that commit. The worktree always starts with the cleanest possible baseline: whatever is currently in origin/main (or origin/master, or whatever the repository's default is).

This is the right choice for:

  • Parallel feature exploration. You want three agents to propose three different refactoring approaches, all starting from the same clean state. If one agent's branch were based on another's in-progress work, the approaches would not be comparable.
  • Security or QA audits. The audit should reflect the authoritative state of the codebase, not some developer's local uncommitted work.
  • Any workflow where you will merge results back. A branch from origin/main creates a clean merge history. A branch from HEAD may include unreviewed local commits in the ancestry.

The cost of fresh is a network round trip on every worktree creation. In high-frequency workflows this adds up. If your agents are creating dozens of worktrees per minute, measure the overhead.

"head" — Start from current local HEAD

local HEAD (may have uncommitted context)
     │
     ▼
worktree branch ──── agent makes changes

head branches from the current HEAD of your local repository. If you have local commits that are not yet pushed, the worktree starts with them included.

This is the right choice for:

  • Explorations on top of in-progress work. You are mid-feature and want an agent to try a risky approach on a throwaway branch while you continue working on the original.
  • Offline operation. No network required; the branch is created from local objects only.
  • Iterative refinement. You accept a worktree's output, commit it to your working branch, and then create a new worktree from that updated HEAD for the next iteration.

The risk of head is that it captures local state that may be inconsistent. An agent that branches from a HEAD with a half-committed refactor may encounter code that does not compile. When in doubt, fresh is safer.

22.3 worktree.symlinkDirectories: Controlling the Cost

A git worktree checkout is not free. The git object store is shared, but the working tree — every tracked file — must exist on disk in the new directory. For a repository with 50,000 source files, a worktree creation takes a few hundred milliseconds and a modest amount of disk space. That is usually fine.

The problem is the untracked directories that sit alongside the source: node_modules, .venv, __pycache__, dist, build. These are not tracked by git and are not created by git worktree add. But many agents need them to run tests, import modules, or execute builds. The naive solution — copy them — is prohibitively expensive: a node_modules directory for a large project can be 400MB. Copying it for each worktree would be both slow and wasteful.

symlinkDirectories solves this by creating symbolic links in the new worktree pointing back to the originals in the main working tree:

{
  "worktree": {
    "symlinkDirectories": ["node_modules", ".venv", "__pycache__", "dist", "build"]
  }
}

When the harness creates a worktree with this configuration, it runs:

ln -s /repo/node_modules /repo/.claude/worktrees/my-task/node_modules
ln -s /repo/.venv /repo/.claude/worktrees/my-task/.venv
# etc.

The worktree's import statements and test runners see the correct dependencies without duplication.

The shared-state hazard

Symlinks mean shared state. If one agent in the worktree installs a new npm package, that change is visible to every other worktree and to the main working tree — because they all point to the same node_modules. This is usually fine for read-only access (running tests against existing dependencies) but breaks for write operations (installing packages, creating Python virtualenvs, writing build artifacts).

The rule of thumb: symlink directories that agents will read but not modify. For everything else, accept the copy cost or restructure the workflow so that dependency installation happens once before agents start.

{
  "worktree": {
    "symlinkDirectories": ["node_modules", ".venv"]
  }
}

Note __pycache__ is absent in this example. Python's __pycache__ entries are keyed by source file path, so two worktrees writing to the same __pycache__ will overwrite each other's cached bytecode. Omit it from symlinkDirectories if your agents run Python code concurrently. The performance cost of not symlinking __pycache__ is minimal — Python regenerates it quickly.

22.4 ExitWorktree: Closing the Isolation Scope

ExitWorktree is the symmetric counterpart to EnterWorktree. It terminates the isolation scope, removes the harness's CWD-dependent caches (system prompt, memory, plans — all assembled assuming the worktree path), and either preserves or removes the worktree branch.

export interface ExitWorktreeInput {
  action: "keep" | "remove";
  discard_changes?: boolean;
}

export interface ExitWorktreeOutput {
  action: "keep" | "remove";
  originalCwd: string;
  worktreePath: string;
  worktreeBranch?: string;
  tmuxSessionName?: string;
  discardedFiles?: number;
  discardedCommits?: number;
  message: string;
}

action: "keep"

The worktree and its branch remain intact. The output returns worktreePath and worktreeBranch so the caller can reference them — pass them to another agent, open a PR, run a diff, or simply log them.

const exit = await ExitWorktree({ action: "keep" });
// exit.worktreeBranch: "worktree/migrate-users-table"
// exit.worktreePath: "/repo/.claude/worktrees/migrate-users-table"
// exit.originalCwd: "/repo"

Use "keep" when the agent produced output worth reviewing: a working implementation, a complete migration script, a refactoring proposal. The branch is the artifact.

action: "remove"

The worktree directory is deleted and the branch is removed. The session returns to the original working directory.

const exit = await ExitWorktree({ action: "remove" });

Use "remove" when the agent's work was exploratory and produced nothing worth keeping — a dead end, a failed approach, a QA run that confirmed no issues.

Dirty worktrees and discard_changes

ExitWorktree with action: "remove" will refuse to proceed if the worktree is dirty — that is, if it has uncommitted changes or commits that are not present in the base branch. The harness is conservative by design: it will not silently delete work.

// This will fail if the worktree has uncommitted changes
await ExitWorktree({ action: "remove" });
// Error: "Worktree has 3 uncommitted files. Set discard_changes: true to remove anyway."

To override, explicitly acknowledge the loss:

await ExitWorktree({
  action: "remove",
  discard_changes: true
});
// exit.discardedFiles: 3
// exit.discardedCommits: 0

The output reports discardedFiles and discardedCommits so you can log what was thrown away. This is an audit trail, not a recycle bin — the data is gone.

No-op behavior

ExitWorktree is a no-op when called outside an EnterWorktree session. It returns a no-op message rather than an error. This lets workflows call ExitWorktree defensively in cleanup paths without needing to track whether an EnterWorktree was called.

22.5 Auto-Cleanup: Worktrees That Cost Nothing to Abandon

The most operationally significant behavior in the worktree subsystem is auto-cleanup: when an agent exits a worktree session without having made any changes, the harness automatically removes the worktree without requiring an explicit ExitWorktree call.

"No changes" is defined precisely: the worktree branch is identical to the base ref (no commits were added, no staged files exist, no unstaged modifications are present). If the agent read files, ran commands, or called web tools — but wrote nothing to the filesystem — the worktree is considered unchanged.

This matters for parallel workflows. Consider a workflow that fans out twenty agents to explore twenty different approaches to a problem:

const results = await parallel(APPROACHES.map(approach => () =>
  agent(`Implement this approach: ${approach.description}`, {
    isolation: "worktree",
    schema: RESULT_SCHEMA
  })
))

Some approaches will produce complete implementations. Others will hit dead ends and exit cleanly after determining the approach is not viable. Without auto-cleanup, every agent that exits with action: "remove" would leave behind a worktree directory. The harness cleans up the no-change cases automatically; only the agents that committed work leave traces.

In practice, expect most "exploration" agents in a fan-out to leave no traces. Expect "implementation" agents — the ones that actually write code — to leave branches that the orchestrator collects and evaluates.

22.6 CLI Integration: --worktree and --tmux

The worktree system is not only accessible via tools. The CLI exposes two flags that enable worktree-isolated sessions from the command line:

-w, --worktree [name]    Create a new git worktree for this session
--tmux                   Create a tmux session for the worktree (requires --worktree)

--worktree

Starting a session with --worktree is equivalent to calling EnterWorktree as the first action in the session. The harness creates the worktree before the model starts executing, and cleans up (or keeps) the worktree when the session ends.

# Start a session in an auto-named worktree
claude --worktree

# Start a session in a named worktree
claude -w migrate-users-table "Write the migration script for the users table"

# Start a session in an existing worktree
claude -w existing-migration "Check the migration for correctness"

When you pass a name that matches an existing worktree under .claude/worktrees/, the harness enters that worktree rather than creating a new one. This is the same path resolution logic as EnterWorktree { path }, but driven by name rather than explicit path.

--tmux: Visual Workflow Integration

--tmux creates a tmux session paired with the worktree. The session name is derived from the worktree name. When you exit the worktree with action: "keep", the tmux session remains running and the ExitWorktreeOutput.tmuxSessionName field tells you how to reattach. When you exit with action: "remove", the tmux session is killed.

claude -w feature-auth --tmux "Implement the OAuth2 token refresh flow"

By default, --tmux integrates with iTerm2 native panes when iTerm2 is detected — the worktree session opens in a new split pane rather than a separate tmux window, which preserves spatial locality with your current work. If you are in a standard terminal or prefer traditional tmux behavior:

claude -w feature-auth --tmux=classic "Implement the OAuth2 token refresh flow"

--tmux=classic forces traditional tmux windows regardless of the detected terminal.

The tmux integration is most valuable for multi-worktree visual workflows. You can run several Claude sessions simultaneously, each in its own named worktree, each visible in a tmux pane. The session names let you identify which pane is handling which task without switching focus. When a session finishes and calls ExitWorktree { action: "keep" }, the pane stays open showing the result and the branch name, so you can review before switching to the next.

22.7 WorktreeCreate and WorktreeRemove Hooks

The hooks system extends worktree operations to repositories that are not using git — or to git repositories that need custom logic during worktree lifecycle events.

Two hooks are available:

{
  "hooks": {
    "WorktreeCreate": [{ "type": "http", "url": "https://ci.internal/worktree/created" }],
    "WorktreeRemove": [{ "type": "http", "url": "https://ci.internal/worktree/removed" }]
  }
}

type: "http" — Non-git VCS and Custom Backends

The most important use of WorktreeCreate is for non-git version control systems. When type: "http" is set, the harness does not call git worktree add itself. Instead, it posts the worktree creation request to your endpoint:

POST https://ci.internal/worktree/created
{
  "name": "migrate-users-table",
  "baseRef": "fresh",
  "sessionId": "sess_abc123"
}

Your endpoint is responsible for creating the isolated workspace — whatever that means in your VCS — and must return the path where the harness should set its CWD:

{
  "hookSpecificOutput": {
    "worktreePath": "/workspaces/migrate-users-table"
  }
}

The harness uses this path as the worktree path going forward. ExitWorktree will still call the WorktreeRemove hook rather than git worktree remove.

This pattern supports Mercurial, Perforce, Plastic SCM, and corporate VCS systems behind HTTP APIs. It also supports custom git workflows where you need the worktree to be created in non-standard locations, registered with an external CI system at creation time, or built from a custom base rather than a git branch.

Changelog note: v2.1.85 and v2.1.84

Two relevant fixes ship in recent versions. In v2.1.85, --worktree was exiting with an error in non-git repositories before the WorktreeCreate hook could run — the harness was failing on git worktree list before it checked for a hook override. This made the HTTP hook unusable for non-git repos when invoked via the CLI flag. The fix in v2.1.85 checks for a WorktreeCreate hook first and bypasses git operations when one is present.

In v2.1.84, type: "http" support for WorktreeCreate was added — so v2.1.84 introduced the feature and v2.1.85 fixed the CLI integration path. If you are on v2.1.83 or earlier, neither hook type is available.

22.8 Lab: Parallel Database Migration System

This lab builds a workflow that runs multiple database migration scripts in parallel, each in its own isolated worktree, validates each migration independently, and collects the results into a single review report. It is the kind of system that is fragile without worktrees and robust with them.

The problem

You have a monorepo with twelve database migrations that need to be tested against a staging database. The migrations touch different tables and should be independent, but you cannot trust that they are — two migrations might both modify the same table in conflicting ways, or a migration might assume a table state that another migration is also modifying. You need to:

  1. Run each migration in isolation, in a clean checkout.
  2. Validate that each migration applies cleanly.
  3. Validate that each migration rolls back cleanly.
  4. Collect the results and flag any conflicts.

The workflow

export const meta = {
  name: 'parallel-migration-validation',
  description: 'Validate all pending database migrations in isolated worktrees'
}

phase('Discover')
log('Scanning for pending migration files...')

const migrations = await agent('List all pending migration files', {
  label: 'discover',
  schema: {
    type: 'object',
    properties: {
      migrations: {
        type: 'array',
        items: {
          type: 'object',
          properties: {
            filename: { type: 'string' },
            tables: { type: 'array', items: { type: 'string' } },
            reversible: { type: 'boolean' }
          },
          required: ['filename', 'tables', 'reversible']
        }
      }
    },
    required: ['migrations']
  }
})

log(`Found ${migrations.migrations.length} pending migrations`)

phase('Validate')

const results = await pipeline(
  migrations.migrations,
  migration => agent(
    `Validate migration ${migration.filename} in an isolated worktree.

Steps:
1. Enter a new worktree named: validate-${migration.filename.replace('.sql', '').replace(/_/g, '-')}
2. Copy the migration file to a scratch directory if needed
3. Run: psql $DATABASE_URL -f db/migrations/${migration.filename}
4. Verify the migration applied by checking the schema: \\d ${migration.tables.join(' \\d ')}
5. If reversible, run the rollback: psql $DATABASE_URL -f db/migrations/rollback/${migration.filename}
6. Verify the rollback restored the schema
7. Exit the worktree with action: "keep" if any issues were found, "remove" if clean

Report the outcome.`,
    {
      label: `validate:${migration.filename}`,
      isolation: 'worktree',
      schema: {
        type: 'object',
        properties: {
          filename: { type: 'string' },
          applySuccess: { type: 'boolean' },
          rollbackSuccess: { type: 'boolean' },
          issues: { type: 'array', items: { type: 'string' } },
          worktreeBranch: { type: 'string' }
        },
        required: ['filename', 'applySuccess', 'rollbackSuccess', 'issues']
      }
    }
  )
)

phase('Conflict Detection')

const cleanResults = results.filter(Boolean)
const failed = cleanResults.filter(r => !r.applySuccess || !r.rollbackSuccess)
const tableConflicts = detectTableConflicts(migrations.migrations, cleanResults)

const report = await agent(
  `Synthesize these migration validation results into a review report.

Results: ${JSON.stringify(cleanResults, null, 2)}
Failed migrations: ${JSON.stringify(failed)}
Table conflicts: ${JSON.stringify(tableConflicts)}

Include: overall pass/fail, per-migration status, conflict analysis, recommended merge order.`,
  {
    label: 'report',
    schema: {
      type: 'object',
      properties: {
        overallStatus: { type: 'string', enum: ['pass', 'fail', 'warn'] },
        passCount: { type: 'number' },
        failCount: { type: 'number' },
        conflicts: { type: 'array', items: { type: 'string' } },
        recommendedOrder: { type: 'array', items: { type: 'string' } },
        summary: { type: 'string' }
      },
      required: ['overallStatus', 'passCount', 'failCount', 'conflicts', 'summary']
    }
  }
)

log(`Migration validation complete`)
log(`Status: ${report.overallStatus.toUpperCase()} — ${report.passCount} passed, ${report.failCount} failed`)
if (report.conflicts.length > 0) {
  log(`Conflicts detected: ${report.conflicts.join(', ')}`)
}
log(report.summary)

function detectTableConflicts(migrations, results) {
  const tableMap = {}
  for (const m of migrations) {
    for (const table of m.tables) {
      if (!tableMap[table]) tableMap[table] = []
      tableMap[table].push(m.filename)
    }
  }
  return Object.entries(tableMap)
    .filter(([, files]) => files.length > 1)
    .map(([table, files]) => ({ table, files }))
}

Why worktrees make this correct

Without worktrees, all twelve validation agents operate in the same working directory. If migration 7 leaves the database schema in a partially-applied state (its apply succeeded but its rollback failed), migration 11 — which touches the same table — now runs against a modified schema rather than the clean baseline. The validation results are no longer independent. You cannot tell from the output whether migration 11 failed because of its own bugs or because migration 7 left the environment dirty.

With isolation: "worktree", each agent operates in a separate checkout. But more importantly, each agent's database operations run against a separate database connection with an isolated transaction — the agent prompt instructs each one to apply and roll back within its own session. The worktree isolation guarantees the filesystem is clean; the database transaction discipline guarantees the schema state is clean.

The two forms of isolation are complementary, not redundant. File isolation prevents agents from interfering with each other's source code. Transaction isolation prevents them from interfering with each other's database state. You need both.

Reading the output

When the workflow completes, failed migrations leave worktrees behind (action: "keep" was set in the agent prompt for failures). You can inspect them:

ls .claude/worktrees/
# validate-add-user-preferences
# validate-rename-order-status

git diff main worktree/validate-add-user-preferences

Clean migrations were removed automatically (either by the agent's explicit action: "remove" or by auto-cleanup if the agent exited without commits). You only see the worktrees you need to look at.

Configuration for this workflow

{
  "worktree": {
    "baseRef": "fresh",
    "symlinkDirectories": ["node_modules", ".venv"]
  }
}

baseRef: "fresh" ensures every migration validates against the current origin/main, not against any local branch that may have other in-progress changes. The symlinks cover the test runner dependencies without duplicating them.

When Worktrees Are Worth Their Cost

Worktrees add overhead: 200-500ms for creation (plus network time if baseRef: "fresh"), disk space for each checkout, and operational complexity in cleanup. That overhead is justified when:

Agents will write to the same files concurrently. Any parallel workflow where agents may touch overlapping paths needs worktree isolation. Without it, file conflicts are silent and results are wrong.

You need to preserve exploratory branches for comparison. A workflow that generates N approaches to a problem needs those approaches to live on separate branches so you can diff them, merge the best one, and discard the rest. Worktrees give you that structure automatically.

Audit and rollback requirements. If you need to demonstrate that an agent's changes are isolated, reversible, and attributable to a specific task, a worktree branch provides the git history to do that. git log worktree/task-name shows exactly what the agent did.

The overhead is not justified when:

Agents run sequentially and share context intentionally. If agent B is building on agent A's output, they should operate in the same working tree. Isolation would break the workflow.

Agents are read-only. Analysis, review, and audit agents that only read files impose no concurrency hazards. Worktree overhead buys nothing.

The task is short-lived and throwaway. A single-shot agent that runs a command and reports the result does not need worktree isolation. The auto-cleanup will remove the worktree anyway, but you have still paid the creation cost.

The isolation: "worktree" shorthand in the Agent tool and the --worktree CLI flag make it low-friction to add worktree isolation when you need it. The discipline is knowing when you actually need it — and when you are just adding ceremony.

As discussed in Chapter 11, the isolation parameter on the Agent tool is the primary way to create worktrees in multi-agent workflows. The tools covered in this chapter — EnterWorktree and ExitWorktree — are what the harness calls under the hood, and are available directly for cases where you need explicit control over the lifecycle.
