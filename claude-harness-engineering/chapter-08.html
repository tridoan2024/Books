Chapter 8: Language Server Protocol — The LSP Tool

"grep knows nothing about types. LSP knows everything."

8.1 The Nine Operations

The LSP tool is the only member of the harness tool catalog that is purpose-built for semantic code navigation. Where Grep finds text and Read retrieves file contents, LSP understands the structure of your code — the type system, the call graph, the symbol hierarchy. It talks to a running Language Server to answer questions that would otherwise require parsing an entire codebase.

There are nine operations, each mapping directly to the Language Server Protocol specification:

OperationWhat it answers
goToDefinitionWhere is this symbol defined?
findReferencesWhere is this symbol used?
hoverWhat type is this? What does the documentation say?
documentSymbolWhat functions, classes, and variables are in this file?
workspaceSymbolFind all symbols matching a name across the entire project
goToImplementationWhich concrete classes implement this interface?
prepareCallHierarchyGet the call hierarchy item at this position
incomingCallsWhat functions call this function?
outgoingCallsWhat functions does this function call?

Understanding when to use each operation — and why it beats the text-search alternative — is the core skill this chapter develops.

goToDefinition

The most common operation. Given a symbol at a file position, returns the exact location where that symbol is declared.

The grep-based equivalent would be something like grep -rn "def process_event\|function processEvent\|processEvent =" across the codebase. That approach returns false positives (comments, string literals, other identifiers that share a substring), misses renamed symbols, and cannot distinguish between two processEvent functions in different modules. LSP returns the exact definition: file, line, character.

When the model is working on a large codebase and encounters an unfamiliar function call, goToDefinition is the correct tool. It does not guess. It asks the language server, which has already parsed and indexed the code.

findReferences

The inverse of goToDefinition. Given a definition site, returns every call site, import statement, type annotation, or other reference across the workspace. This operation is load-bearing for refactoring — before you rename a function or change a signature, you need to know every location that calls it.

Grep approximates this by searching for the identifier string. It will miss references in files where the identifier was imported under an alias (import { processEvent as pe } from './handler') and will include false positives in string literals and comments. LSP finds references at the semantic level: only actual code references, including aliased imports.

hover

Returns the documentation and type information for a symbol — equivalent to hovering your cursor over an identifier in VS Code and seeing the tooltip. For TypeScript, this means the full type signature. For Python with type hints, it means the resolved type annotation. For Rust, it means the expanded trait bounds and lifetime annotations.

This operation is underused. When a model is reading unfamiliar code and encounters a type or function it needs to understand, a single hover call returns what a human editor user would see in the tooltip: the signature, the docstring, the type parameters. It eliminates the need to chase goToDefinition just to read a function's signature.

documentSymbol

Returns an outline of a file: all named symbols (functions, classes, methods, variables, interfaces, enums) with their positions. This is the programmatic equivalent of the "Outline" panel in VS Code.

The practical use case: when the model needs to understand the structure of a 3000-line file before deciding which section to edit, documentSymbol returns a structured map of the file in a single call. No need to read the entire file first. The model can get the outline, identify the relevant section, and then read only that part.

workspaceSymbol

Like documentSymbol but across the entire project. Accepts a search string and returns all matching symbols from all indexed files. This is the tool you reach for when you know the name of what you are looking for but not where it lives.

Example: you are debugging a PaymentProcessor class that is failing. You know it exists somewhere in a large TypeScript monorepo. workspaceSymbol with query "PaymentProcessor" returns every class, interface, function, and variable matching that name across all workspace files, with their locations.

goToImplementation

Navigates from an interface or abstract method declaration to its concrete implementations. In a codebase with a Serializable interface and twelve classes that implement it, goToImplementation at the interface declaration returns all twelve concrete classes.

This is particularly valuable when working with dependency-injected architectures where code operates on interface types and the concrete implementations are registered elsewhere.

prepareCallHierarchy

Returns the call hierarchy item at a given position — a prerequisite step before calling incomingCalls or outgoingCalls. It establishes the identity of the function at the cursor position in a form the language server can use for hierarchy traversal.

In practice, agents typically call prepareCallHierarchy followed immediately by one of the call direction operations. You rarely use it in isolation.

incomingCalls and outgoingCalls

These two operations map the call graph. incomingCalls answers "what calls this function?" and outgoingCalls answers "what does this function call?"

The combination lets a model trace execution paths without reading every file in the call chain. For debugging, this is essential: given a failing function, incomingCalls shows every entry point that can trigger it. For impact analysis, outgoingCalls shows the complete dependency surface of a function before you modify it.

8.2 Parameters

Every LSP operation shares the same four parameters:

interface LSPInput {
  operation: 
    | "goToDefinition"
    | "findReferences"
    | "hover"
    | "documentSymbol"
    | "workspaceSymbol"
    | "goToImplementation"
    | "prepareCallHierarchy"
    | "incomingCalls"
    | "outgoingCalls";
  filePath: string;       // absolute or relative path to the file
  line: number;           // 1-based, must be > 0
  character: number;      // 1-based, must be > 0
}

There are three things worth internalizing about this interface.

All four parameters are required for all operations. Even workspaceSymbol, which logically operates on a project-wide scope, requires filePath, line, and character. The language server uses the file path to determine which workspace the request belongs to when multiple projects are open. Use the search term as the value you are navigating from — position the cursor on any identifier of that type in the codebase.

Line and character are 1-based, matching editor conventions. If you read a file with the Read tool and see line number 47 in the cat -n output, you pass line: 47 to LSP. No offset arithmetic. The harness documentation is explicit that values must be greater than 0 — passing line: 0 is an error.

Character counts columns, not bytes. In files with multi-byte characters (Unicode identifiers, Asian language comments), character position counts Unicode code points from column 1. In ASCII files, character position equals the column number. To target a specific identifier, identify which column it starts on. For an identifier processEvent beginning at column 12, pass character: 12.

Practical example — TypeScript

Given this TypeScript file at src/handlers/payment.ts:

1  import { PaymentGateway } from '../services/gateway';
2  import { processTransaction } from '../utils/transaction';
3
4  export class PaymentHandler {
5    private gateway: PaymentGateway;
6
7    async handlePayment(amount: number): Promise<void> {
8      const result = await processTransaction(amount, this.gateway);
9      if (!result.success) {
10       throw new Error(result.message);
11     }
12   }
13 }

To jump to the definition of processTransaction (which begins at column 29 on line 8):

operation: "goToDefinition"
filePath: "src/handlers/payment.ts"
line: 8
character: 29

To get the type information for result on line 8, column 13:

operation: "hover"
filePath: "src/handlers/payment.ts"
line: 8
character: 13

The hover response might return:

const result: TransactionResult
interface TransactionResult {
  success: boolean;
  message: string;
  transactionId?: string;
}

That single call replaces reading the processTransaction function definition, finding its return type annotation, and tracing that type to its interface declaration — three separate file reads collapsed into one LSP call.

8.3 Server Lifecycle

The LSP tool is backed by language servers — long-lived processes that index your codebase and answer navigation queries. The harness manages these servers transparently, but understanding the lifecycle matters when you are debugging failures or building agents that use LSP heavily.

Auto-Start

Language servers start automatically on the first LSP request for a given file type. There is no explicit server start command. The first call to LSP on a .ts file starts the TypeScript language server. The first call on a .py file starts the configured Python language server (pylsp, pyright, or similar). Subsequent calls to files of the same type reuse the running server.

This means the first LSP call for a new file type carries startup latency — anywhere from 200ms for a small project to several seconds for a large monorepo while the server indexes. Subsequent calls are fast. Agents that use LSP heavily should expect a warm-up period at the start of a session on a new codebase.

The language server must be configured for the file type — if no server is available for a file extension, LSP returns an error. Built-in support covers the most common languages; plugin-provided servers extend coverage to Rust and Swift (see Section 8.4).

Crash Recovery

Language servers occasionally crash. The v2.1.89 changelog entry is worth quoting directly:

Fixed LSP server zombie state after crash — server now restarts on next request instead of failing until session restart.

Before v2.1.89, a crashed language server left a zombie process that continued to hold its port. Subsequent LSP calls to that server failed silently — the harness could not distinguish "server is slow" from "server is dead," and the session had to be restarted to recover LSP functionality.

After v2.1.89, crash recovery is automatic. When the harness detects that a language server has exited unexpectedly, it clears the process handle. The next LSP request triggers a fresh server start as if the file type were being seen for the first time. Recovery is transparent to the model — the next call succeeds after the restart latency.

For practical purposes: if you observe a series of LSP failures in a long-running agent session, the first failure may be a crash; the second request should succeed after auto-restart. Build agents to retry LSP calls exactly once on failure before escalating to grep-based fallback.

Server Scope

Each language server handles one language. You can have a TypeScript server, a Python server, and a Go server running simultaneously in the same Claude Code session. They do not share state. The harness routes each LSP call to the appropriate server based on the file extension of filePath.

8.4 Plugin-Provided LSP Servers

The built-in LSP support covers common languages. Two languages with dedicated plugin-provided LSP integration are available from the official marketplace:

rust-analyzer-lsp — provides LSP support for Rust files (.rs) backed by rust-analyzer, the official Rust language server. rust-analyzer delivers full Rust semantic analysis: type inference across trait bounds, macro expansion, lifetime analysis, and the complete Rust call graph including calls through trait objects.

swift-lsp — provides LSP support for Swift files (.swift) via sourcekit-lsp, Apple's official Swift language server.

Both plugins are available through the claude-plugins-official marketplace. Installation follows the standard plugin workflow:

# List available official plugins
claude plugins search --marketplace claude-plugins-official

# Install Rust LSP support
claude plugins install rust-analyzer-lsp

# Install Swift LSP support  
claude plugins install swift-lsp

After installation, LSP calls on .rs and .swift files work identically to built-in language support. The plugin handles server binary management, startup configuration, and workspace root detection.

Why Plugin Distribution

Shipping rust-analyzer and sourcekit-lsp as plugin-provided rather than built-in is an intentional design decision. Both language servers are large binaries with platform-specific builds. rust-analyzer ships separate binaries for each platform/architecture combination (darwin-arm64, darwin-x64, linux-x64, linux-arm64, windows-x64). Including these in the base Claude Code distribution would significantly increase download size for users who do not write Rust or Swift.

The plugin distribution model lets Rust and Swift developers opt in while keeping the base install lean. It also allows plugin-provided language servers to be updated independently of the Claude Code release cycle — a critical property when rust-analyzer ships frequent updates tracking the Rust edition.

8.5 LSP vs Grep: A Precision Comparison

Before the lab, it is worth being concrete about when LSP's type-awareness matters versus when grep is sufficient. The decision affects both correctness and performance — LSP calls carry server startup cost and require a running language server; grep is always available.

Reach for LSP when:

  • You need exact definition locations without false positives from similarly-named identifiers
  • You are about to rename or change the signature of a function and need to find all callers
  • You need to understand what type a variable is without reading its full initialization chain
  • You are navigating a codebase with multiple classes that implement the same interface
  • You need the call graph (incomingCalls / outgoingCalls) for impact analysis

Grep is sufficient when:

  • You are searching for a string literal or error message
  • You need to find files that import a specific module
  • You are doing an initial survey of an unfamiliar codebase before the language server has finished indexing
  • The identifier is unique enough that text matching has no false-positive risk
  • No language server is configured for the file type

The sharpest illustration: imagine a TypeScript codebase with a function named get that appears in dozens of files — array destructuring, object getters, HTTP client calls, ORM methods. A grep for get( returns hundreds of matches across every category. A findReferences call on the specific get method of your ORM client returns exactly the lines that call that specific method, filtered by type. The difference is not a quality-of-life improvement; for large codebases it is the difference between useful output and noise.

8.6 Lab: Build a Code Navigation Agent

This lab builds an agent that uses LSP to trace the full execution path from an entry point function to its deepest dependencies, then generates a structured call graph report. The agent demonstrates all nine operations working together.

Goal

Given an entry point function name and file, the agent:

  1. Locates the function using workspaceSymbol and confirms with hover
  2. Traverses its outgoing call graph using outgoingCalls recursively (depth-limited)
  3. Finds all callers of each discovered function using incomingCalls
  4. Gets the type signatures of all functions in the graph using hover
  5. Gets all symbols in each discovered file using documentSymbol
  6. Generates a structured report: function → signature → callers → callees

Setup

The lab uses a TypeScript project with the following structure:

src/
├── api/
│   └── handler.ts          # Entry point: handleRequest()
├── services/
│   ├── auth.ts             # validateToken(), checkPermissions()
│   ├── database.ts         # queryUser(), updateRecord()
│   └── cache.ts            # getCached(), setCached()
└── utils/
    ├── logger.ts           # log(), logError()
    └── validator.ts        # validateInput(), sanitize()

Step 1: Locate the Entry Point

operation: "workspaceSymbol"
filePath: "src/api/handler.ts"
line: 1
character: 1

The workspaceSymbol call with query "handleRequest" returns the exact location. Confirm it with hover to get the function signature:

operation: "hover"
filePath: "src/api/handler.ts"
line: 12
character: 17

Example hover response:

async function handleRequest(
  req: IncomingRequest,
  ctx: RequestContext
): Promise<Response>

Step 2: Prepare the Call Hierarchy

operation: "prepareCallHierarchy"
filePath: "src/api/handler.ts"
line: 12
character: 17

This registers handleRequest as the root of the hierarchy traversal.

Step 3: Traverse Outgoing Calls

operation: "outgoingCalls"
filePath: "src/api/handler.ts"
line: 12
character: 17

The response lists each function that handleRequest directly calls, with the call sites and the target location. Each entry includes the callee name and its definition file and position. For each discovered callee, repeat prepareCallHierarchy → outgoingCalls to traverse one level deeper. Limit depth to avoid infinite recursion in circular call graphs.

A complete traversal at depth 2 for this codebase might discover:

handleRequest
├── validateToken       (src/services/auth.ts:8:14)
├── checkPermissions    (src/services/auth.ts:24:14)
├── validateInput       (src/utils/validator.ts:5:14)
├── queryUser           (src/services/database.ts:12:14)
│   ├── getCached       (src/services/cache.ts:8:14)
│   └── log             (src/utils/logger.ts:4:14)
└── log                 (src/utils/logger.ts:4:14)

Step 4: Get Type Signatures

For each function in the discovered graph, call hover at its definition position. This populates the report with actual type signatures rather than just names:

operation: "hover"
filePath: "src/services/auth.ts"
line: 8
character: 14

Response:

function validateToken(
  token: string,
  options?: TokenOptions
): Promise<AuthResult>

Repeat for each node in the call graph. After this step, every node has a verified signature.

Step 5: Find All References for Impact Analysis

For the entry point and any function you intend to modify, call findReferences:

operation: "findReferences"
filePath: "src/api/handler.ts"
line: 12
character: 17

This reveals all the code paths that can trigger handleRequest — middleware registrations, test files, integration harnesses. Before modifying a function's signature, this list is the complete impact surface.

Step 6: Get File Structure

For each file in the call graph, call documentSymbol to understand its complete structure. This shows whether the file has other functions, how they relate, and whether the function under analysis is a method of a class or a standalone export:

operation: "documentSymbol"
filePath: "src/services/auth.ts"
line: 1
character: 1

Response (abbreviated):

AuthService (class) [line 4]
  validateToken (method) [line 8]
  checkPermissions (method) [line 24]
  refreshToken (method) [line 41]
tokenCache (variable) [line 2]

This reveals that validateToken is a method on AuthService, not a standalone function — a detail that matters for call semantics and that grep-based search would not surface without reading the file.

Step 7: Generate the Report

After completing the traversal, the agent has enough data to produce a structured call graph report:

## Call Graph: handleRequest

**Entry point:** `src/api/handler.ts:12` — `handleRequest(req: IncomingRequest, ctx: RequestContext): Promise<Response>`

**Direct callers:** 3 locations (route registrations in `src/api/router.ts:45`, `src/api/router.ts:89`, test file `tests/api/handler.test.ts:23`)

### Call Graph (depth 2)

| Function | File | Signature | Called By |
|---|---|---|---|
| `handleRequest` | `api/handler.ts:12` | `(req, ctx) => Promise<Response>` | router.ts (×2), test (×1) |
| `validateToken` | `services/auth.ts:8` | `(token, opts?) => Promise<AuthResult>` | handleRequest |
| `checkPermissions` | `services/auth.ts:24` | `(userId, resource) => Promise<boolean>` | handleRequest |
| `validateInput` | `utils/validator.ts:5` | `(data: unknown) => ValidationResult` | handleRequest |
| `queryUser` | `services/database.ts:12` | `(id: string) => Promise<User \| null>` | handleRequest |
| `getCached` | `services/cache.ts:8` | `(key: string) => T \| undefined` | queryUser |
| `log` | `utils/logger.ts:4` | `(msg: string, level?: LogLevel) => void` | queryUser, handleRequest |

### Modification Impact

To change the signature of `handleRequest`:
- Update 2 route registrations in `src/api/router.ts`
- Update 1 test case in `tests/api/handler.test.ts`
- No downstream callee signatures need changing

To change the signature of `validateToken`:
- Update 1 call site in `src/api/handler.ts:18`
- `AuthService.validateToken` — update the class method definition
- Check for other `AuthService` consumers via `findReferences` on the class

What the Lab Demonstrates

This lab uses all nine operations in a coherent workflow:

  • workspaceSymbol to locate symbols by name
  • hover to get verified type signatures
  • prepareCallHierarchy → outgoingCalls → incomingCalls for call graph traversal
  • goToDefinition to confirm symbol locations
  • findReferences to determine modification impact
  • documentSymbol to understand file structure in context

None of this is achievable with grep at the same level of precision. The type signatures, interface implementations, method ownership, and aliased references are only visible at the semantic layer that LSP provides.

The agent pattern — traverse, enrich, report — generalizes to other scenarios: security audits that trace data from user input to persistence, performance analysis that identifies the call chains responsible for latency, and dependency analysis that maps what would break if a module is replaced.

Summary

The LSP tool provides nine operations that give the model semantic, type-aware code navigation. Unlike text search, LSP understands the structure of your code: where symbols are defined, where they are used, what types they carry, and how functions call each other.

The parameter contract is uniform across all nine operations: filePath, line, and character (both 1-based, matching editor conventions), plus the operation name. Language servers start automatically on first use for a given file type. Since v2.1.89, crashes recover automatically — the server restarts on the next request rather than failing until session restart. Rust and Swift support is available via the rust-analyzer-lsp and swift-lsp plugins from the official marketplace.

The decision framework is straightforward: use LSP when you need precision — finding all references to a specific method, not all occurrences of a string; jumping to the exact definition of a type, not grepping for its name. Use grep when the language server is unavailable, when indexing is in progress, or when you are genuinely searching for text rather than navigating a symbol.
