Chapter 36: Debugging and Observability

"A harness that fails silently is worse than one that crashes loudly. At least a crash tells you where."

Agent failures are not like application failures. A web server 500 is obvious — the caller receives an error, the log line appears, the alert fires. An agentic harness can process a hundred tool calls, write zero output, emit a cheerful "Done!" and have accomplished nothing you intended. The context overflow happened three turns in. The stale file read poisoned the reasoning at turn seven. The findings were emitted to a transcript that got truncated and never surfaced. Downstream, you have a report with 0 entries, and no idea why.

Debugging harnesses requires a different posture than debugging applications. You are not inspecting a stack trace — you are reconstructing the agent's reasoning from its behavior. That means reading transcripts, querying tool statistics, correlating OpenTelemetry spans, and recognizing failure signatures before they compound.

This chapter teaches you to do all of that. Start with the simplest tool — the debug flag — and work outward to the full observability stack.

36.1 Debug Mode — --debug with Category Filtering

The --debug flag is the fastest path to seeing what the harness is actually doing. It takes an optional filter argument so you can narrow the stream to the categories you care about.

# Enable all debug output
claude --debug

# Equivalent short form
claude -d

# Filter to specific categories
claude -d "api,hooks"

# Exclude categories with ! prefix
claude -d "!1p,!file"

# Write debug output to a file instead of stderr
claude --debug-file /tmp/claude-debug.log -p "Run the audit workflow"

Debug Categories

CategoryWhat it shows
apiEvery outbound Claude API request and inbound response, including token counts, model, stop reason
hooksHook invocation payloads, exit codes, stdout/stderr captured from hook scripts
fileFile reads and writes — paths, sizes, cache hit/miss decisions
1pFirst-party tool calls — Bash, Edit, Write, Agent tool inputs/outputs

The filter syntax accepts comma-separated values. Prefix a category with ! to exclude it. You can mix includes and excludes: "api,hooks,!file" shows API and hook traffic but suppresses file noise during a session that reads hundreds of small files.

--debug-file for Long Sessions

In interactive mode, debug output to stderr competes with the TUI and becomes unreadable after the first dozen lines. --debug-file redirects the debug stream to a file, leaving stderr clean:

# In one terminal: run the session
claude --debug-file /tmp/debug.log

# In another terminal: tail the debug stream
tail -f /tmp/debug.log | grep '"category":"api"' | jq .

This two-terminal pattern is the standard approach for diagnosing issues in interactive sessions. The log accumulates everything; you filter it in real time with grep and jq.

Reading the API Debug Output

The api category emits one event per API call and one event per response. Here is what the request side looks like:

{
  "category": "api",
  "direction": "request",
  "model": "claude-sonnet-4-6",
  "input_tokens": 48234,
  "system_tokens": 12890,
  "tool_count": 23,
  "turn": 4
}

And the response:

{
  "category": "api",
  "direction": "response",
  "model": "claude-sonnet-4-6",
  "stop_reason": "tool_use",
  "output_tokens": 312,
  "cache_read_input_tokens": 45900,
  "cache_creation_input_tokens": 0,
  "tool_calls": ["Read", "Bash"]
}

Two numbers in the response matter most for diagnosing cost and performance issues: cache_read_input_tokens and cache_creation_input_tokens. When cache_read_input_tokens is near input_tokens, you are hitting the prompt cache hard — the session is economical. When cache_creation_input_tokens is high, the cache is cold or being invalidated. If you see cache_creation_input_tokens spike on turn 5 of a session that was previously cache-warm, something changed in the prompt — most commonly the tool schema or a CLAUDE.md file. This is the first symptom of the prompt cache miss failure documented in section 36.6.

36.2 Transcript Analysis — Session JSONL Files

Every session is persisted to disk. Interactive sessions, print-mode sessions, background agents, workflow subagents — they all write a JSONL transcript. This is your primary forensic record.

Where Sessions Live

Sessions are stored in ~/.claude/sessions/ as JSONL files, one message per line:

~/.claude/sessions/
├── 20260728T141523_abc123.jsonl     # interactive session
├── 20260728T152811_def456.jsonl     # print-mode run
└── 20260728T163044_ghi789.jsonl     # background agent

Each line in the JSONL is a complete message object from the conversation. The file is written incrementally — lines are appended as the session progresses — which means a crashed session has a partial record up to the last completed turn.

Resuming Sessions

# Resume by session ID
claude -r 20260728T141523_abc123

# Interactive picker — shows recent sessions with timestamps
claude -r

# Continue the most recent session in the current directory
claude -c

The -r flag is the workhorse for post-mortem investigation. Open the session in interactive mode, then scroll back through the conversation, re-run tool calls, or ask the model to explain its earlier reasoning in the context of the original turn.

Note the distinction: -r resumes an existing session (full history available, agent can act on it), while reading the raw JSONL is for offline analysis. Use -r when you want to interact; use the JSONL when you want to parse and measure.

Parsing JSONL Transcripts

The JSONL format is straightforward to parse. Each line is one of: a user message, an assistant message (which may include tool_use blocks), or a tool_result message.

import json
from pathlib import Path
from typing import Any

def parse_transcript(path: Path) -> list[dict[str, Any]]:
    messages = []
    with path.open() as f:
        for line in f:
            line = line.strip()
            if line:
                messages.append(json.loads(line))
    return messages

def tool_calls_from_transcript(messages: list[dict[str, Any]]) -> list[str]:
    """Extract all tool names called in a session, in order."""
    calls = []
    for msg in messages:
        if msg.get("role") == "assistant":
            for block in msg.get("content", []):
                if block.get("type") == "tool_use":
                    calls.append(block["name"])
    return calls

# Usage
transcript_path = Path.home() / ".claude/sessions/20260728T141523_abc123.jsonl"
messages = parse_transcript(transcript_path)
calls = tool_calls_from_transcript(messages)
print(f"Tool call sequence: {calls}")
# Tool call sequence: ['Read', 'Bash', 'Read', 'Grep', 'Edit', 'Bash']

This sequence tells you the agent's story turn by turn. An agent that called Read fifteen times on the same file is probably fighting stale state (section 36.6). An agent that never called Edit in a refactoring task probably stopped before it started.

Workflow Transcripts

Workflows write subagent transcripts to the transcriptDir returned by the Workflow tool. As covered in Chapter 12, the transcriptDir is session-scoped and contains one JSONL per subagent:

/tmp/claude-sessions/workflow_abc123/transcripts/
├── scan_src_agent.jsonl
├── audit_api_agent.jsonl
├── audit_db_agent.jsonl
└── synthesize_agent.jsonl

When a workflow produces no output, start here. Pick the first subagent in the pipeline, parse its transcript, and look at the last few messages. The failure is almost always a mismatched schema between what the subagent returned and what the next stage expected — visible as a tool_result with is_error: true or a model turn that says "I cannot parse the result."

36.3 OpenTelemetry — Traces, Metrics, and Log Events

For production harnesses — multi-agent workflows running in CI, background daemons, harnesses serving multiple users — stderr debug output is not enough. You need structured observability data that can be aggregated, queried, and alerted on. Claude Code emits OpenTelemetry signals out of the box.

Environment Variables

# Include tool input parameters in log events (off by default — large payloads)
OTEL_LOG_TOOL_DETAILS=1

# Disable log export entirely
OTEL_LOGS_EXPORTER=none

# Configure metrics export
OTEL_METRICS_EXPORTER=otlp
OTEL_EXPORTER_OTLP_METRICS_ENDPOINT=http://otel-collector:4317

# Configure trace export
OTEL_TRACES_EXPORTER=otlp
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://otel-collector:4317

The standard OTLP endpoint variables work as expected. If you have an existing OpenTelemetry Collector in your infrastructure, pointing these at it gives you Claude Code data alongside your application traces.

What Gets Emitted

Traces instrument the control loop. Each turn — from API call to tool execution completion — is a span. Tool calls are child spans of the turn span. Parallel tool executions appear as concurrent sibling spans, which makes it immediately visible in a trace viewer when parallelism is working versus when tools are executing sequentially due to dependency ordering.

Session [span]
  └─ Turn 1 [span, duration: 1.2s]
       ├─ API call [span, model: claude-sonnet-4-6, tokens_in: 8234]
       └─ Tool: Read [span, path: src/auth.py, cache: miss]
  └─ Turn 2 [span, duration: 3.4s]
       ├─ API call [span, tokens_in: 9102, cache_read: 8800]
       └─ Tool: Bash [span, command: "pytest tests/test_auth.py"]

Metrics track aggregates: token consumption per session, tool call counts, cache hit rates, error rates per tool. These are the signals you want on a dashboard for a team running agents at scale.

Log events are structured JSON attached to spans. By default they contain tool name, turn index, stop reason, and token counts. Setting OTEL_LOG_TOOL_DETAILS=1 adds the full tool_parameters object — every argument passed to every tool. This is extremely useful during debugging and extremely expensive at scale. Use it in development; disable it in production unless you need it for a specific investigation.

Session Correlation — X-Claude-Code-Session-Id

When Claude Code makes API calls through an HTTP proxy or gateway, it sends the X-Claude-Code-Session-Id header on every request. This header contains the session identifier from the JSONL filename.

In a multi-agent scenario, this is how you correlate spans across the orchestrator and all subagents — every API call in a workflow session carries the same session ID. Configure your proxy to extract this header and add it as a trace attribute:

# OpenTelemetry Collector processor config
processors:
  attributes:
    actions:
      - key: claude.session_id
        from_header: X-Claude-Code-Session-Id
        action: insert

With this in place, you can query your trace backend for all spans belonging to a given workflow run, even when subagents use different model instances or API keys.

Minimal Collector Setup

# docker-compose.yml for local OTEL development
services:
  otel-collector:
    image: otel/opentelemetry-collector-contrib:latest
    volumes:
      - ./otel-config.yaml:/etc/otel/config.yaml
    ports:
      - "4317:4317"   # OTLP gRPC
      - "4318:4318"   # OTLP HTTP
      - "8888:8888"   # Prometheus metrics

  jaeger:
    image: jaegertracing/all-in-one:latest
    ports:
      - "16686:16686"  # Jaeger UI
# Run with OTEL enabled
OTEL_TRACES_EXPORTER=otlp \
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://localhost:4317 \
OTEL_LOG_TOOL_DETAILS=1 \
claude -p "Audit src/ for SQL injection vulnerabilities"

Open http://localhost:16686 to see the full trace of the agent run as a waterfall diagram.

36.4 Tool Statistics — toolStats in Agent Output

Every agent invocation returns an AgentOutput struct. Embedded in it is toolStats, a compact accounting of what the agent actually did:

toolStats?: {
  readCount: number;        // Read tool calls
  searchCount: number;      // Grep + ToolSearch calls combined
  bashCount: number;        // Bash tool calls
  editFileCount: number;    // Edit + Write calls combined
  linesAdded: number;       // Net lines added across all edits
  linesRemoved: number;     // Net lines removed across all edits
  otherToolCount: number;   // All other tool calls (MCP, Agent, etc.)
  frameCount?: number;      // Number of conversation turns
}

This struct is your quick sanity check before reading a word of the agent's prose output. If you asked an agent to refactor a module and editFileCount is 0, the agent talked about the refactor but didn't do it. If readCount is 47 and editFileCount is 0, the agent spent its entire budget reading and ran out of context before making a single change.

Reading toolStats from Workflow Output

const result = await agent('Refactor auth.py to use the new session API', {
  label: 'refactor-auth',
  schema: { /* ... */ }
})

// The agent's structured output is in result.output
// The raw AgentOutput is in result._raw (harness-internal)
log(`Edits made: ${result._raw.toolStats?.editFileCount ?? 0}`)
log(`Lines changed: +${result._raw.toolStats?.linesAdded} / -${result._raw.toolStats?.linesRemoved}`)

toolStats as a Completeness Guard

In a multi-stage workflow, add explicit completeness checks based on toolStats before advancing to the next stage:

const auditResult = await agent('Audit this module for security issues', {
  label: 'audit',
  schema: FINDING_SCHEMA
})

// Guard: if the agent did no reads, its findings are fabricated
if ((auditResult._raw.toolStats?.readCount ?? 0) === 0) {
  throw new Error(`Audit agent '${auditResult._raw.label}' produced findings without reading any files`)
}

// Guard: if it read files but found CRITICAL issues, verify edits were proposed
if (auditResult.output.critical.length > 0 && 
    (auditResult._raw.toolStats?.editFileCount ?? 0) > 0) {
  log('Warning: audit agent made edits — unexpected for a read-only audit role')
}

These guards catch phantom findings (section 36.6) before they propagate through the pipeline.

36.5 The /cost Command

The /cost command is available as an in-session slash command. It produces a per-model and cache-hit breakdown for the current session:

/cost

Session cost breakdown:
  claude-sonnet-4-6
    Input tokens:        284,310   $0.8529
    Cache read tokens:   261,008   $0.0978    (cache savings: $0.7832)
    Cache write tokens:   23,302   $0.0583
    Output tokens:         4,218   $0.0633
  ─────────────────────────────────────────
  Total:                            $1.0200
  Estimated savings from cache:     $0.7832

For subscription users, the breakdown is available as of v2.1.92 — previously it was gated to API key usage only.

Reading the Breakdown

Cache read tokens is the key number. In a healthy long session, this should be 80-90% of your input token count. The prompt cache preserves the system prompt and all prior turns; if the cache is warm, you are paying approximately 10% of the uncached cost per turn.

Cache write tokens represents the new content added to the cache this session. If this is growing rapidly across turns, the system prompt is being modified — check for CLAUDE.md re-injection (section 36.6) or tool schema drift.

The cache savings line shows you what you would have paid without caching. A session showing $0.78 in savings on a $1.02 bill means 77% of the input cost was avoided through caching. That is healthy. A session showing $0.05 in savings means the cache is barely working — investigate why.

Per-Model Breakdown

When a session uses multiple models — an --fallback-model that activates on rate limits, or subagents explicitly configured to a different model — /cost breaks out costs per model. This is how you audit whether fallback activations are contributing meaningfully to cost, or whether a workflow that "should" use haiku for simple tasks is actually routing everything to opus.

36.6 Common Failures

Every failure pattern listed here has appeared in Claude Code's CHANGELOG. Each one has a symptom, a mechanism, and a fix. Learn to recognize the symptom before you need to root-cause it under pressure.

Failure 1: Autocompact Thrash Loop

Symptom: Session appears to run indefinitely. Debug output shows repeated compaction events. Eventually the session exits with an error message referencing "context refills to limit immediately after compacting."

Mechanism: The autocompact algorithm summarizes older turns and replaces them with a compact summary. This is supposed to free context. In a thrash loop, the compaction summary itself is nearly as large as the turns it replaced — because the system prompt, CLAUDE.md files, and tool schemas consume so much fixed space that there is never room for meaningful conversation history. Each compaction frees a small amount, the conversation immediately fills it, and the next compaction triggers within one or two turns.

Diagnosis:

claude --debug-file /tmp/debug.log -p "..."
grep '"event":"compact"' /tmp/debug.log | tail -20
# If compaction events are 30+ seconds apart but repeating, that's thrash

Fix: The issue is usually oversized CLAUDE.md content or too many MCP servers loaded at once. Audit your system prompt contribution:

# Check how large your CLAUDE.md hierarchy is
find . -name "CLAUDE.md" -exec wc -c {} \; | sort -n

If a single CLAUDE.md exceeds 50KB, it is a candidate for trimming. If you have 5+ CLAUDE.md files stacked in nested directories, consolidate them. Alternatively, set CLAUDE_CODE_MAX_CONTEXT_TOKENS to a value that gives the compaction algorithm more room to work:

CLAUDE_CODE_MAX_CONTEXT_TOKENS=200000 claude -p "..."

This counterintuitively reduces thrash by giving the compaction algorithm a ceiling low enough that it never accumulates enough history to thrash.

Failure 2: Prompt Cache Misses Mid-Session

Symptom: /cost shows cache_creation_input_tokens spiking after the first few turns despite a stable conversation. Session cost is 3-5x higher than expected.

Mechanism: The prompt cache keys on the exact byte content of the prefix up to the cache breakpoint. When the tool schema changes between turns — even by a single byte — the cache is invalidated and must be rebuilt. This happened in production (v2.1.89) when tool schema bytes were changing mid-session due to a serialization bug.

Diagnosis: Compare the cache_creation_input_tokens across turns in the api debug output. Healthy sessions show a spike only on turn 1 (initial cache write), then near-zero on subsequent turns. If turn 4 or turn 8 shows another spike, something changed in the prefix.

Fix: If you are building a custom harness, ensure your tool schema serialization is deterministic — sort keys consistently, do not include volatile fields (timestamps, request IDs) in the tool definitions. For Claude Code itself, upgrade if you are on a version before v2.1.89.

Failure 3: Nested CLAUDE.md Re-Injection

Symptom: Session context grows unusually fast. Debug shows the same CLAUDE.md content appearing multiple times in the system prompt.

Mechanism: Claude Code discovers CLAUDE.md files by walking from the current working directory up to the filesystem root. In a session that changes working directory — either through an agent that runs cd in Bash, or through worktree operations as described in Chapter 22 — the discovery walk can be re-triggered, re-injecting files that were already in the prompt. Reported and fixed in v2.1.89.

Diagnosis: In the --debug output, search for CLAUDE.md injection events:

grep '"event":"claudemd"' /tmp/debug.log | wc -l
# If this exceeds the number of turns significantly, re-injection is happening

Fix: Upgrade to v2.1.89 or later. If you cannot upgrade, work around it by keeping agents from changing working directory: use absolute paths in Bash calls rather than cd && command.

Failure 4: Context Overflow

Symptom: Agent stops mid-task. Final message is a truncated response or a statement that the agent "cannot continue." The JSONL transcript ends abruptly.

Mechanism: The conversation has grown beyond what compaction can handle. Unlike thrash (which loops), this is a clean failure — the harness detects that it cannot fit even the minimum required context and exits.

Diagnosis:

# Count tokens in the final transcript
cat ~/.claude/sessions/SESSION_ID.jsonl | python3 -c "
import sys, json
total = sum(len(json.dumps(json.loads(l))) for l in sys.stdin if l.strip())
print(f'Approximate chars: {total:,}  (~{total//4:,} tokens)')
"

Fix: For interactive sessions, use /cost before the session grows too large and checkpoint your work manually. For programmatic sessions, add a turn-count limit to your control loop and checkpoint state to disk at regular intervals. As covered in Chapter 20, the CLAUDE_CODE_IDLE_TOKEN_THRESHOLD also provides a soft trigger for session cleanup.

Failure 5: Stale State

Symptom: Agent makes edits to a file, then the next turn shows the agent reading the "old" version and overwriting the edit. Or an agent reports that a bug still exists after another agent fixed it.

Mechanism: The harness's file read cache maps {path → content_hash}. After an external edit or a tool write, the next Read call should invalidate the cache and return fresh content. In long sessions with many agents touching the same file, the cache invalidation can be missed — an agent reads from the cache rather than disk.

Diagnosis: Look for repeated Read calls on the same path in the JSONL transcript:

python3 -c "
import json, sys, collections
reads = collections.Counter()
for line in open('SESSION.jsonl'):
    msg = json.loads(line.strip())
    if msg.get('role') == 'assistant':
        for block in msg.get('content', []):
            if block.get('type') == 'tool_use' and block['name'] == 'Read':
                reads[block['input']['file_path']] += 1
for path, count in reads.most_common(10):
    print(f'{count:3d}x  {path}')
"

A file read 8+ times in the same session is suspicious. Check the edit timestamps around those reads in the transcript.

Fix: Ensure that any external file modifications happen before the session starts, not during it. If agents are coordinating through shared files, use the task system (Chapter 10) for state instead — it is designed for inter-agent communication and does not have cache invalidation race conditions.

Failure 6: Phantom Findings

Symptom: A workflow reports N critical findings. The output file exists and contains valid JSON. But when you open the linked files at the linked line numbers, the issues are not there, or the files do not exist.

Mechanism: The agent generated findings from memory rather than from file reads. This happens when the agent was given a broad scope, ran out of context partway through, and completed by producing findings from its training knowledge rather than the actual codebase. The findings look plausible but are not grounded in the target code.

Diagnosis: Use the toolStats check from section 36.4: if readCount is substantially lower than the number of files in scope, the agent did not actually read most of them. Cross-reference finding file paths against toolStats.readCount — if an agent found 15 issues across 40 files but only read 8 files, 15 findings cannot all be real.

Fix: Scope agents narrowly — one module, one package, not the entire codebase. Add a schema-level source_file_read boolean field to your finding schema and instruct the agent to set it only when it has actually called Read on the file. In your synthesis stage, filter or flag any findings where this field is false.

Failure 7: Memory Leak — Large JSON LRU Cache Keys

Symptom: A long-running session or daemon process consumes increasing memory over hours without a corresponding increase in context tokens. (Fixed in v2.1.89.)

Mechanism: Large JSON inputs (such as the output of a tool that returns a big JSON blob) were retained as LRU cache keys even after the cache entry was evicted. The keys themselves were not freed.

Fix: Upgrade to v2.1.89+.

Failure 8: LSP Zombie

Symptom: Code intelligence features (symbol lookup, reference navigation) stop working mid-session. The debug log shows LSP initialization failing. Subsequent sessions also fail to start the LSP. (Fixed in v2.1.89.)

Mechanism: When the LSP server process crashes, it left behind a zombie process holding the socket. New LSP instances could not bind the same socket.

Fix: claude doctor will detect and kill LSP zombie processes. Run it if you encounter this:

claude doctor
# Or in-session:
/doctor

Failure 9: Transcript Chain Breaks on Resume

Symptom: After resuming a session with claude -r, the agent appears to have lost memory of recent actions. It re-reads files it already read, re-asks questions it already answered.

Mechanism: When a session was interrupted (crash, Ctrl-C, OOM), the final JSONL write may have been incomplete — a partial line at the end of the file. On resume, the harness stops reading the transcript at the first parse error, effectively truncating the session history. (Fixed in v2.1.89.)

Fix: Upgrade to v2.1.89+. If you are on an older version and encounter this, manually inspect the last line of the JSONL:

tail -1 ~/.claude/sessions/SESSION_ID.jsonl | python3 -c "import sys, json; json.loads(sys.stdin.read())" 2>&1
# If this errors, the last line is corrupt — remove it and retry the resume

36.7 The claude doctor and /doctor Commands

Before diving into the case study, know your health-check tools:

# Command-line health check — reads settings without triggering trust prompts
claude doctor

# In-session full checkup — can actively fix issues
/doctor

claude doctor validates: settings file integrity, MCP server connectivity, authentication status, LSP server health, available disk space in the session directory. It is non-destructive — it reads and reports without making changes.

/doctor is the interventional version. It can restart a crashed LSP server, clear corrupted session cache entries, re-authenticate if the token has expired, and remove zombie processes. Run it when claude doctor reports issues that need resolution.

# JSON output for automated health checks
claude doctor --json | jq '.issues[] | select(.severity == "error")'

The --json flag makes doctor machine-readable, useful in CI startup scripts to gate execution on harness health.

36.8 Case Study: Diagnosing a Workflow That Silently Dropped Findings

This case study walks through a real diagnosis: a three-stage security audit workflow that consistently returned 0 findings on a codebase known to have issues.

The Workflow

export const meta = {
  name: 'security-audit',
  description: 'Full security audit — scan, verify, report'
}

const files = args.files ?? ['src/']

const scanResults = await pipeline(
  files,
  dir => agent(`List all security-relevant files in ${dir}`, {
    label: `scan:${dir}`,
    schema: { type: 'object', properties: { paths: { type: 'array', items: { type: 'string' } } }, required: ['paths'] }
  }),
  (result, dir) => agent(`Audit these files for vulnerabilities: ${result.paths.join(', ')}`, {
    label: `audit:${dir}`,
    schema: FINDING_SCHEMA
  })
)

const report = await agent(`Synthesize these findings: ${JSON.stringify(scanResults)}`, {
  label: 'synthesize',
  schema: REPORT_SCHEMA
})

log(`Findings: ${report.critical} critical, ${report.high} high, ${report.medium} medium`)

Output: Findings: 0 critical, 0 high, 0 medium. Every run.

Step 1: Check the Transcripts

ls -la /tmp/claude-sessions/security_audit_*/transcripts/

There are three transcript files: scan_src.jsonl, audit_src.jsonl, synthesize.jsonl. The scan and synthesize agents have 4-6 turns each. The audit agent has 2 turns.

Two turns means: receive task, produce output. No file reads in between.

Step 2: Verify with toolStats

Add temporary logging to the workflow:

(result, dir) => {
  const auditAgent = await agent(`Audit these files: ${result.paths.join(', ')}`, {
    label: `audit:${dir}`,
    schema: FINDING_SCHEMA
  })
  log(`Audit stats — reads: ${auditAgent._raw.toolStats?.readCount}, edits: ${auditAgent._raw.toolStats?.editFileCount}`)
  return auditAgent
}

Output: Audit stats — reads: 0, edits: 0.

The audit agent is generating findings (zero findings, but it is completing) without reading any files. This is the phantom findings failure — but inverted. Instead of fabricating positive findings, it is fabricating zero findings without checking.

Step 3: Diagnose the Prompt

Parse the audit agent's transcript to see what prompt it received:

The file list is empty. result.paths was an empty array, which joined to an empty string. The scan agent returned { "paths": [] }.

Step 4: Check the Scan Agent

Parse scan_src.jsonl and look at the final output:

for msg in reversed(messages_scan):

The scan agent is returning {"paths": []} because the schema required a paths field and the model dutifully produced one — empty — rather than failing. The actual list of security-relevant files never made it into the structured output because the file discovery logic failed silently.

Step 5: The Root Cause

The scan agent's prompt was List all security-relevant files in src/. The agent ran Bash("find src/ -name '*.py'") and got output, but then attempted to parse it and produce structured JSON. The schema was:

{ "type": "object", "properties": { "paths": { "type": "array", "items": { "type": "string" } } }, "required": ["paths"] }

No minItems: 1 constraint. No instruction to fail if the directory is empty or inaccessible. The model, seeing a required field with no minimum, produced {"paths": []} when find returned nothing — because src/ did not exist as a relative path from the session's working directory. The workflow was invoked from a parent directory, and src/ was relative.

The Fix

// Fix 1: Use absolute paths
const absoluteFiles = files.map(f => path.resolve(f))

// Fix 2: Add schema-level non-empty constraint
const scanSchema = {
  type: 'object',
  properties: {
    paths: { type: 'array', items: { type: 'string' }, minItems: 1 }
  },
  required: ['paths']
}

// Fix 3: Add a completeness guard before advancing the pipeline
(result, dir) => {
  if (result.paths.length === 0) {
    throw new Error(`Scan of '${dir}' returned 0 paths — check that the directory exists and is accessible`)
  }
  return agent(`Audit these files: ${result.paths.join(', ')}`, { /* ... */ })
}

After the fix, the scan agent throws an explicit error on empty results instead of silently passing an empty list downstream. The real issue — wrong working directory — becomes immediately visible.

Lab: Building a Harness Observability Dashboard

This lab wires together everything in the chapter: debug logs, transcript parsing, and toolStats into a local dashboard that shows harness health at a glance.

Setup

mkdir harness-dashboard && cd harness-dashboard
python3 -m venv venv && source venv/bin/activate
pip install rich watchdog

dashboard.py

#!/usr/bin/env python3
"""Live dashboard for Claude harness sessions."""

from __future__ import annotations

import json
import time
from pathlib import Path
from typing import Any

from rich.console import Console
from rich.table import Table
from rich.live import Live

SESSIONS_DIR = Path.home() / ".claude" / "sessions"
console = Console()


def parse_session(path: Path) -> dict[str, Any]:
    """Extract summary stats from a session JSONL file."""
    turns = 0
    tool_calls: dict[str, int] = {}
    cache_reads = 0
    cache_writes = 0
    output_tokens = 0

    try:
        for line in path.open():
            line = line.strip()
            if not line:
                continue
            msg = json.loads(line)
            if msg.get("role") == "assistant":
                turns += 1
                for block in msg.get("content", []):
                    if block.get("type") == "tool_use":
                        name = block["name"]
                        tool_calls[name] = tool_calls.get(name, 0) + 1
            # Extract token stats if present (stored as metadata lines)
            if "cache_read_input_tokens" in msg:
                cache_reads += msg["cache_read_input_tokens"]
                cache_writes += msg.get("cache_creation_input_tokens", 0)
                output_tokens += msg.get("output_tokens", 0)
    except (json.JSONDecodeError, OSError):
        pass

    return {
        "turns": turns,
        "tool_calls": tool_calls,
        "total_tools": sum(tool_calls.values()),
        "top_tool": max(tool_calls, key=lambda k: tool_calls[k]) if tool_calls else "—",
        "cache_reads": cache_reads,
        "cache_writes": cache_writes,
        "output_tokens": output_tokens,
    }


def build_table() -> Table:
    sessions = sorted(SESSIONS_DIR.glob("*.jsonl"), key=lambda p: p.stat().st_mtime, reverse=True)[:10]

    table = Table(title="Harness Session Dashboard", show_lines=True)
    table.add_column("Session", style="cyan", max_width=30)
    table.add_column("Turns", justify="right")
    table.add_column("Tools", justify="right")
    table.add_column("Top Tool", style="yellow")
    table.add_column("Cache Reads", justify="right")
    table.add_column("Out Tokens", justify="right")
    table.add_column("Age", justify="right")

    for path in sessions:
        stats = parse_session(path)
        age_s = int(time.time() - path.stat().st_mtime)
        age = f"{age_s // 60}m{age_s % 60:02d}s" if age_s < 3600 else f"{age_s // 3600}h"
        table.add_row(
            path.stem[-20:],
            str(stats["turns"]),
            str(stats["total_tools"]),
            stats["top_tool"],
            f"{stats['cache_reads']:,}",
            f"{stats['output_tokens']:,}",
            age,
        )

    return table


with Live(build_table(), refresh_per_second=0.5, console=console) as live:
    while True:
        time.sleep(2)
        live.update(build_table())

Run this while a Claude session is active and you will see tool call counts, cache hit rates, and session ages update in real time.

Debugging a harness is not about reading error messages — it is about reading evidence. The debug flag gives you API traffic. Transcripts give you the exact sequence of reasoning and tool calls. OpenTelemetry gives you structured, queryable signals at scale. Tool statistics give you the quantitative summary that exposes the failure class before you read a word of output. And the failure catalogue in section 36.6 gives you the pattern library.

When a workflow silently drops findings, these tools reconstruct the story. The failure is always in the evidence — you just have to know where to look.
