Chapter 24: CLI Modes and Subcommands

"The CLI is not just a launcher. Every flag you pass reshapes what the harness is."

24.1 Interactive Mode — The Default TUI

When you run claude with no flags and no subcommand, you get interactive mode. This is the full terminal UI: streaming responses, a model picker, a conversation history panel, inline permission prompts, and the complete tool surface. It is the highest-fidelity way to work with the harness because every layer is active.

Interactive mode is not just the default — it is the intended development environment. The session is live, stateful, and designed for back-and-forth work. The harness initializes the full stack in this order:

  1. Read and validate all settings files (global, project, enterprise)
  2. Discover and load CLAUDE.md files from the working directory up to the filesystem root
  3. Register hooks from settings
  4. Initialize the LSP (Language Server Protocol) client for code intelligence
  5. Load plugins
  6. Assemble the system prompt
  7. Present the first prompt to the user

The TUI surfaces the parts of this that matter during use. The model picker (accessible via /model or on session start if unconfigured) lets you switch between claude-sonnet-4-6, claude-opus-4-8, claude-haiku-4-5, and claude-fable without leaving the session. The transcript view (/history) shows the full conversation with tool calls expanded. The /permissions panel shows which tools have been allowed or denied during the session.

For most work — writing code, debugging, interactive refactoring — interactive mode is correct. The other modes exist to make Claude machine-callable.

24.2 Print Mode — --print / -p

Print mode is the foundational CI/CD flag. Pass -p (or --print) and the harness behaves like a command-line tool: read the prompt from the argument or stdin, run the agent loop to completion, write output to stdout, exit.

# simplest form
claude -p "Summarize the changes in the last three commits"

# from a file
claude -p "$(cat prompt.txt)"

# piped input
echo "Explain this error: $(cat build.log)" | claude -p

No TUI. No streaming to the terminal. No interactive prompts. The process exits with code 0 on success, non-zero on failure. This is what makes Claude scriptable.

Output Formats

Print mode accepts --output-format with three values: text, json, and stream-json.

text (default) — The model's final text response, written directly to stdout. Simple to use, simple to pipe.

# grep the model's answer for a specific word
claude -p "List all Python stdlib modules that handle networking" | grep -i socket

json — Wait for the full response, then emit a single JSON object containing the complete run. Useful when you need the full response envelope — tool calls, cost, stop reason — not just the text.

claude -p "Review this function for bugs" --output-format json < func.py | jq '.result'

The JSON object contains:

{
  "result": "The response text",
  "cost_usd": 0.0032,
  "duration_ms": 4120,
  "session_id": "sess_01...",
  "stop_reason": "end_turn",
  "tool_calls": [...]
}

stream-json — Emit newline-delimited JSON events as they arrive. Each event is a self-contained JSON object on a single line. This is the format for real-time CI pipelines that need to process output incrementally rather than waiting for the full response.

claude -p "Run the test suite and report failures" \
  --output-format stream-json \
  --dangerously-skip-permissions 2>/dev/null | \
  jq -r 'select(.type == "text") | .content'

Stream-JSON event types you will encounter:

Event typeDescription
textA text chunk from the model's response
tool_useThe model requested a tool call
tool_resultThe result returned from a tool execution
errorAn execution error
doneTerminal event — the session ended, includes cost and stop reason

Input Format

--input-format mirrors --output-format for the prompt side. The default is text. Set it to stream-json when your upstream is itself a Claude process emitting stream-JSON — this lets you chain Claude instances where one feeds another.

# chain: first claude generates a review prompt, second executes it
claude -p "Generate a security review prompt for this file" --output-format stream-json < auth.py | \
  claude -p --input-format stream-json --output-format text

--fallback-model

Only available in print mode. Accepts a comma-separated list of model names to try if the primary model is unavailable or rate-limited. The harness attempts models in order until one succeeds.

claude -p "Analyze this log" \
  --model claude-opus-4-8 \
  --fallback-model claude-sonnet-4-6,claude-haiku-4-5 \
  --output-format json < system.log

This flag exists specifically for automated pipelines where a model outage should degrade gracefully rather than fail the build. Use it for any critical CI step.

--forward-subagent-text

When a print-mode session spawns subagents (via the Agent tool), those subagents' text output is normally suppressed — only the parent's output reaches stdout. --forward-subagent-text changes this: every subagent's text is forwarded as stream-JSON text events as they occur.

Required in conjunction with --output-format stream-json. Useful when your pipeline needs visibility into what each subagent concluded, not just the coordinator's final summary.

24.3 Background Mode — --bg / --background

Background mode starts a session that runs without an attached terminal. The harness launches, begins processing, and returns control to the calling shell immediately. The session continues running and accumulates output that you can retrieve later.

# start a background session
claude --bg "Run a full security audit of the auth subsystem and write findings to audit-report.md"
# returns: Session started: sess_01AbCd...

# start with a specific model and effort
claude --bg --model claude-opus-4-8 --effort high \
  "Refactor the database layer to use async/await throughout"

The session ID is written to stdout on launch. Store it if you need to track this specific session:

SESSION=$(claude --bg "Audit dependencies for CVEs" --output-format json | jq -r '.session_id')
echo "Audit running as $SESSION"

Background sessions are managed with the claude agents subcommand, covered in section 24.5. The typical pattern is: launch with --bg, record the session ID, poll with claude agents --json until the session appears completed, then retrieve the output.

Background mode is the foundation for multi-agent orchestration from the shell layer rather than from inside a running session. When you need to launch five parallel analysis agents from a CI script and wait for all to finish, --bg is the mechanism.

24.4 Session Continuity — --resume, --continue, --from-pr

The harness persists conversation history to disk after every session. These flags let you re-enter prior sessions or extend them.

--continue / -c

The simplest form: resume the most recent session for the current working directory. No session ID needed.

# start work
claude "Begin refactoring the authentication module"

# later, in the same directory
claude -c "Continue where you left off — now focus on the token validation logic"

The harness finds the most recent session whose working directory matches $PWD and re-enters it with the new message appended to the existing conversation history.

--resume / -r

Two behaviors depending on how it is called:

Without a value — Opens an interactive picker showing all sessions for the current directory, sorted by recency. Select one to re-enter.

claude --resume

With a session ID — Goes directly to that session.

claude --resume sess_01AbCd3EfGh

Session IDs are UUIDs. You can find them in ~/.claude/sessions/ or from the --output-format json output of a prior run. The claude agents --json command also lists active sessions with their IDs.

--from-pr

Links a session to a pull request. The harness fetches the PR's diff, description, and associated comments, injects them into the session context, and optionally pre-populates the initial prompt with the PR content.

# start a session linked to PR 1234
claude --from-pr 1234

# or with a full PR URL
claude --from-pr https://github.com/org/repo/pull/1234

Without a value, it opens a picker to select from open PRs in the current repository. The intended use case is PR review sessions that have access to the full PR context without you having to manually construct a prompt from the diff.

--from-pr and --resume can be combined: claude --resume --from-pr 1234 resumes the most recent session that was originally linked to that PR.

24.5 claude agents — Managing Background Sessions

The claude agents subcommand is the management surface for background sessions. Without flags, it opens the TUI agent view: a live panel showing running sessions, their status, current tool, and elapsed time. You can select a session and attach to it to watch its output in real time.

# open the agent management TUI
claude agents

For scripting, the --json flag is essential:

# list all active sessions as a JSON array
claude agents --json

# include completed sessions
claude agents --json --all

# filter to sessions running in a specific directory
claude agents --json --cwd /path/to/project

The JSON output is an array of session objects:

[
  {
    "session_id": "sess_01AbCd...",
    "status": "running",
    "current_tool": "Bash",
    "started_at": "2026-07-28T14:23:01Z",
    "working_dir": "/Users/tri/projects/myapp",
    "prompt_preview": "Run security audit of auth...",
    "model": "claude-opus-4-8"
  }
]

The status field takes values running, waiting (paused at a permission prompt or tool confirmation), completed, and failed.

Dispatching from the Agent View

The TUI agent view is also a dispatcher. You can send a new background session directly from it without dropping back to the shell. This is the interactive equivalent of --bg — useful when you want to launch several parallel tasks and watch them all from one panel.

Flags that configure dispatched sessions:

--model <model>    Default model for sessions dispatched from this view
--effort <level>   Default effort (low/medium/high/xhigh/max)
--mcp-config       MCP config passed to dispatched sessions
--settings         Settings file passed to dispatched sessions

These are not persistent settings — they configure the specific claude agents invocation, affecting only sessions dispatched during that session.

24.6 claude mcp — Server Management

MCP (Model Context Protocol) is the extension mechanism for adding external tools and context sources to the harness. The claude mcp subcommand is the management surface for MCP server configuration.

# list all configured MCP servers
claude mcp list

# add a server
claude mcp add my-server --command "node /path/to/server.js"
claude mcp add remote-server --url https://mcp.example.com/sse

# get details on a specific server
claude mcp get my-server

# remove a server
claude mcp remove my-server

MCP servers registered via claude mcp add are written to ~/.claude/settings.json under the mcpServers key. Project-scoped servers go in .claude/settings.json at the project root.

Authentication

Some MCP servers require authentication — OAuth flows, API keys, or session tokens. The login and logout subcommands handle this:

# authenticate with a server that requires OAuth
claude mcp login my-server

# clear stored credentials
claude mcp logout my-server

Credentials are stored in the system keychain, not in the settings file. This means MCP auth tokens never appear in ~/.claude/settings.json and cannot accidentally be committed to version control.

claude mcp serve

The serve command exposes the local Claude Code instance as an MCP server — making it callable from another harness or tool that understands the MCP protocol.

# expose this claude instance as an MCP server on stdio
claude mcp serve

# on a specific port
claude mcp serve --port 3001

This is the mechanism for using Claude Code as a component inside a larger orchestration layer. If you are building a custom harness that needs to delegate specific tasks to a running Claude Code instance (rather than spawning a new process), claude mcp serve provides the interface.

Runtime MCP Configuration

Two flags bypass the persistent settings and inject MCP configuration directly at session start:

# load MCP servers from a JSON config file at session start
claude --mcp-config ./ci-mcp-config.json -p "Run the audit"

# use ONLY the servers from --mcp-config, ignore all other MCP config
claude --mcp-config ./ci-mcp-config.json --strict-mcp-config -p "Run the audit"

--strict-mcp-config is the isolation flag for CI environments: the pipeline controls exactly which external tools are available, and nothing from the developer's personal MCP setup leaks in. Use it whenever reproducibility matters.

24.7 claude doctor, claude auth, claude update

These three subcommands handle the operational hygiene of a Claude Code installation.

claude doctor

Runs a health check against your installation. It reads settings and validates the environment without triggering the trust prompt that normally appears when a settings file is first loaded.

claude doctor

The check covers:

  • API key validity and auth method
  • Settings file syntax and schema validity
  • MCP server reachability
  • Hook command existence (verifies each hook command is executable)
  • Network connectivity to the Anthropic API
  • Node.js version compatibility

The output is human-readable by default. For CI use, claude doctor --json emits a structured result that you can parse:

claude doctor --json | jq '.checks | map(select(.status != "pass"))'

Run claude doctor when a session fails in an unexpected way before assuming it is a model or prompt issue. Most environment problems — expired tokens, broken hook paths, unreachable MCP servers — surface here.

claude auth

Manages authentication state.

# show current auth status
claude auth status

# log in (opens browser for OAuth or prompts for API key)
claude auth login

# log out
claude auth logout

Claude Code supports two auth paths: Anthropic Console API keys (ANTHROPIC_API_KEY environment variable or stored credential) and Claude.ai OAuth sessions. The auth status command shows which path is active and whether the credential is valid.

For automated environments where interactive login is impossible, set the environment variable directly:

export ANTHROPIC_API_KEY="sk-ant-..."
claude -p "Run analysis"

When --bare mode is active, ANTHROPIC_API_KEY is the only supported auth path — OAuth sessions are not used in bare mode.

claude update / claude upgrade

Self-update commands. update checks the current installed version against the latest release; upgrade performs the update.

# check for updates
claude update

# install the latest version
claude upgrade

# install a specific version
claude install 2.1.100

# install the latest pre-release (latest channel)
claude install latest

In enterprise environments where the system Claude Code binary is managed centrally, use claude install --target /usr/local/bin/claude stable to pin to the stable channel without installing pre-releases.

24.8 claude ultrareview — Cloud Multi-Agent Code Review

claude ultrareview runs a cloud-hosted multi-agent code review. The description is accurate: it is not a single model pass over the diff. The cloud backend orchestrates multiple review agents across different dimensions — security, correctness, style, test coverage — and synthesizes their findings into a structured report.

# review the current branch against main
claude ultrareview

# review a specific PR by number
claude ultrareview 1234

# review against a specific base branch
claude ultrareview --base develop

Without arguments, it reviews the current branch against the default base branch (usually main). The review runs remotely — your code is sent to Anthropic's infrastructure for processing.

The output is a structured markdown report with severity-ranked findings grouped by category. Each finding includes:

  • File and line reference
  • Severity (CRITICAL / HIGH / MEDIUM / LOW / INFO)
  • Category (security, correctness, performance, style, coverage)
  • Explanation and suggested fix

ultrareview is substantially more thorough than a single claude -p "review this diff" because the cloud backend uses models and compute that exceed what a local session can apply. The tradeoff is time — expect two to five minutes for a medium-sized PR — and the requirement that your code leaves your machine.

For pipelines where code confidentiality is a constraint, use local print-mode review instead (see the lab in section 24.11).

24.9 --bare — Minimal Startup

--bare strips the harness down to its minimal configuration. When this flag is set, the harness sets CLAUDE_CODE_SIMPLE=1 and skips:

  • Hook loading and execution
  • LSP initialization
  • Plugin loading
  • CLAUDE.md discovery and injection
  • Startup context assembly (git status, env metadata)

Authentication falls back to ANTHROPIC_API_KEY only. No OAuth sessions.

# run without any project configuration
claude --bare -p "Analyze this function" < function.py

# useful for testing a prompt in isolation
claude --bare "What does this code do?" < unknown.py

The practical use cases for --bare:

Prompt isolation testing. You want to know what the model thinks about a piece of code without your project's CLAUDE.md steering the response. --bare gives you a clean baseline.

Fast scripted queries. If your script only needs a text answer and has no tool use requirements, --bare cuts startup time meaningfully by skipping LSP init and plugin loading. For pipelines that call Claude many times in sequence, this adds up.

Debugging initialization failures. When a session fails during startup — a broken hook, a CLAUDE.md syntax error, a plugin that panics — --bare lets you confirm the model itself is reachable. If --bare works but normal startup fails, the problem is in your configuration.

Untrusted environments. In a container or CI environment where you deliberately do not want project configuration to influence the session, --bare is the safe default.

--bare does not affect the permission layer. Tool execution permissions still apply. If you need to skip permissions as well, combine with --dangerously-skip-permissions — but only in environments where you own the execution context.

24.10 --safe-mode — Full Customization Disable

--safe-mode is a stronger version of --bare. When set, the harness sets CLAUDE_CODE_SAFE_MODE=1 and disables all customization:

  • CLAUDE.md files (ignored entirely)
  • Skills and plugins
  • Hooks (none fire)
  • MCP servers (no external tools)
  • Custom system prompts
  • All user-defined settings

One thing that is not disabled: admin-managed settings pushed via enterprise policy. Those remain active in safe mode by design — safe mode is about user customization, not enterprise governance.

# start in safe mode
claude --safe-mode

# use safe mode for a specific print-mode task
claude --safe-mode -p "Review this file" < suspicious_file.py

The canonical use case is troubleshooting. When a session produces unexpected behavior — the model refuses a task it should accept, tool calls behave strangely, context is wrong — --safe-mode answers the question: is this a configuration problem or a model behavior? If --safe-mode produces normal behavior, something in your customization is the cause. Bisect from there.

--safe-mode also gives you a reproducible baseline for bug reports. If you need to file an issue with Anthropic about model behavior, a --safe-mode repro is far more credible than one that involves custom hooks, CLAUDE.md files, and third-party MCP servers.

Comparison: --bare vs --safe-mode

Behavior--bare--safe-mode
CLAUDE.mdSkippedSkipped
HooksSkippedSkipped
PluginsSkippedSkipped
MCP serversSkippedSkipped
LSPSkippedActive
OAuth authSkippedActive
Admin-managed settingsSkippedActive
Env variable:CLAUDE_CODE_SIMPLE=1CLAUDE_CODE_SAFE_MODE=1

The key distinction: --bare skips LSP and OAuth, making it lighter and more appropriate for headless automation. --safe-mode keeps LSP active and supports OAuth, making it the right choice for interactive troubleshooting where you want the full UI minus user customization.

24.11 Lab: Build a CI Integration Using Print Mode with Stream-JSON Output

This lab builds a working CI integration script that uses --print with --output-format stream-json to run an automated code review on every pull request. The script:

  1. Receives a PR number from the CI environment
  2. Extracts the diff
  3. Constructs a structured review prompt
  4. Streams the model's response in real time
  5. Parses the stream to detect findings by severity
  6. Exits non-zero if any HIGH or CRITICAL findings are present

Prerequisites

  • claude at version 2.1.220 or later
  • ANTHROPIC_API_KEY set in the CI environment
  • jq installed
  • A git repository with a remote

The Script

Save this as ci/claude-review.sh:

#!/usr/bin/env bash
set -euo pipefail

readonly PR_NUMBER="${1:?Usage: $0 <pr-number>}"
readonly BASE_BRANCH="${BASE_BRANCH:-main}"
readonly MAX_SEVERITY_ALLOWED="${MAX_SEVERITY_ALLOWED:-MEDIUM}"
readonly CLAUDE_MODEL="${CLAUDE_MODEL:-claude-sonnet-4-6}"

# Build the diff
DIFF=$(git diff "origin/${BASE_BRANCH}"...HEAD -- '*.py' '*.ts' '*.go' '*.rs' 2>/dev/null || true)

if [[ -z "${DIFF}" ]]; then
  printf "No relevant changes found. Skipping review.\n"
  exit 0
fi

# Build the structured review prompt
PROMPT=$(cat <<'EOF'
You are a code reviewer. Review the following git diff for issues.

For each finding, output a JSON object on its own line with this exact schema:
{"severity": "CRITICAL|HIGH|MEDIUM|LOW|INFO", "file": "path/to/file.ext", "line": 42, "category": "security|correctness|performance|style", "message": "concise description"}

After all findings, output a summary line:
{"type": "summary", "critical": N, "high": N, "medium": N, "low": N, "info": N}

If there are no findings, output:
{"type": "summary", "critical": 0, "high": 0, "medium": 0, "low": 0, "info": 0}

Do not output anything other than these JSON lines.

DIFF:
EOF
)

FULL_PROMPT="${PROMPT}
${DIFF}"

# Severity ordering for comparison
severity_rank() {
  case "${1}" in
    CRITICAL) echo 4 ;;
    HIGH)     echo 3 ;;
    MEDIUM)   echo 2 ;;
    LOW)      echo 1 ;;
    INFO)     echo 0 ;;
    *)        echo -1 ;;
  esac
}

MAX_ALLOWED_RANK=$(severity_rank "${MAX_SEVERITY_ALLOWED}")

printf "Running Claude review for PR #%s against %s...\n" "${PR_NUMBER}" "${BASE_BRANCH}"

# Stream the response and process each event
HIGHEST_SEVERITY_RANK=0
HIGHEST_SEVERITY="NONE"
FINDING_COUNT=0
FAILED=0

while IFS= read -r event; do
  # Each event is a JSON object on one line
  event_type=$(printf '%s' "${event}" | jq -r '.type // empty' 2>/dev/null || true)

  if [[ "${event_type}" == "text" ]]; then
    chunk=$(printf '%s' "${event}" | jq -r '.content // empty' 2>/dev/null || true)

    # Process each line in the text chunk
    while IFS= read -r line; do
      [[ -z "${line}" ]] && continue

      # Try to parse as a finding
      sev=$(printf '%s' "${line}" | jq -r '.severity // empty' 2>/dev/null || true)
      summary_type=$(printf '%s' "${line}" | jq -r '.type // empty' 2>/dev/null || true)

      if [[ -n "${sev}" ]]; then
        FINDING_COUNT=$((FINDING_COUNT + 1))
        rank=$(severity_rank "${sev}")
        file=$(printf '%s' "${line}" | jq -r '.file // "unknown"')
        lineno=$(printf '%s' "${line}" | jq -r '.line // "?"')
        msg=$(printf '%s' "${line}" | jq -r '.message // ""')
        printf "[%s] %s:%s — %s\n" "${sev}" "${file}" "${lineno}" "${msg}"

        if (( rank > HIGHEST_SEVERITY_RANK )); then
          HIGHEST_SEVERITY_RANK=${rank}
          HIGHEST_SEVERITY="${sev}"
        fi
      fi

      if [[ "${summary_type}" == "summary" ]]; then
        printf "\nSummary: %s\n" "${line}"
      fi
    done <<< "${chunk}"

  elif [[ "${event_type}" == "error" ]]; then
    error_msg=$(printf '%s' "${event}" | jq -r '.message // "unknown error"' 2>/dev/null || true)
    printf "ERROR: %s\n" "${error_msg}" >&2
    exit 2

  elif [[ "${event_type}" == "done" ]]; then
    cost=$(printf '%s' "${event}" | jq -r '.cost_usd // "unknown"' 2>/dev/null || true)
    duration=$(printf '%s' "${event}" | jq -r '.duration_ms // "unknown"' 2>/dev/null || true)
    printf "\nReview complete. Cost: \$%s | Duration: %sms\n" "${cost}" "${duration}"
  fi

done < <(
  claude \
    --print \
    --model "${CLAUDE_MODEL}" \
    --fallback-model claude-sonnet-4-6,claude-haiku-4-5 \
    --output-format stream-json \
    --bare \
    --dangerously-skip-permissions \
    "${FULL_PROMPT}" 2>/dev/null
)

printf "\nHighest severity found: %s (%d findings total)\n" "${HIGHEST_SEVERITY}" "${FINDING_COUNT}"

# Fail the build if findings exceed the allowed threshold
if (( HIGHEST_SEVERITY_RANK > MAX_ALLOWED_RANK )); then
  printf "FAIL: Found %s findings (max allowed: %s)\n" "${HIGHEST_SEVERITY}" "${MAX_SEVERITY_ALLOWED}" >&2
  exit 1
fi

printf "PASS: All findings within acceptable severity range.\n"
exit 0

Integrating into a GitHub Actions Workflow

# .github/workflows/claude-review.yml
name: Claude Code Review

on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write

    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0   # required: full history for git diff

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Run Claude Review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          BASE_BRANCH: ${{ github.base_ref }}
          MAX_SEVERITY_ALLOWED: HIGH  # fail on CRITICAL only
        run: bash ci/claude-review.sh ${{ github.event.number }}

# .gitlab-ci.yml (relevant job)

    - BASE_BRANCH="${CI_MERGE_REQUEST_TARGET_BRANCH_NAME}" bash ci/claude-review.sh "${CI_MERGE_REQUEST_IID}"
  variables:
    ANTHROPIC_API_KEY: $ANTHROPIC_API_KEY

  rules:

Design Notes

Several choices in this script deserve explanation.

Why --bare? The CI environment has no project CLAUDE.md, no hooks, no plugins. Using --bare avoids the startup overhead of trying to initialize them and avoids any risk that a project-level customization influences the review in a way that differs between developer machines and CI.

Why --fallback-model? CI pipelines fail at bad times. Primary model rate limits or brief outages should not block a merge. The fallback list ensures the review degrades gracefully to a cheaper model rather than failing the pipeline entirely. Tune the fallback list to your cost tolerance.

Why stream-JSON rather than JSON? Two reasons. First, for large diffs, stream-JSON begins writing findings to the log immediately — reviewers watching the CI run see results as they arrive rather than waiting for the full response. Second, it avoids buffering the entire response in memory, which matters for very large diffs where the JSON output format would require holding the full response in a shell variable.

Why exit codes? CI systems understand exit codes. Returning 1 for threshold violations lets the pipeline gate merge without any special parsing logic in the CI configuration — the job simply fails when findings exceed the allowed severity.

Testing the Script Locally

# test against the current branch before opening a PR
export ANTHROPIC_API_KEY="sk-ant-..."
export BASE_BRANCH="main"
bash ci/claude-review.sh 0  # PR number 0 is a placeholder for local testing

# test with a more permissive threshold to see all findings
MAX_SEVERITY_ALLOWED="INFO" bash ci/claude-review.sh 0

Validate the stream-JSON events directly to understand what the harness is emitting:

claude --print --output-format stream-json --bare \
  "What is 2 + 2" 2>/dev/null | jq .

This gives you the raw event stream with all fields visible, which is useful for understanding timing, costs, and the structure of multi-tool responses before you start parsing them in production scripts.

Summary

The six modes and eleven subcommands covered in this chapter represent the full operational surface of Claude Code as a tool rather than a conversational UI. The progression from interactive → print → background → session persistence follows a spectrum from human-in-the-loop to fully automated. Each mode makes sense for a different position on that spectrum.

For engineers integrating Claude into pipelines, the print mode + stream-JSON combination is the primary interface. The flags that support it — --fallback-model, --forward-subagent-text, --input-format stream-json, --bare, --strict-mcp-config — exist specifically to make that integration robust, reproducible, and cost-controlled. The lab in section 24.11 is a production-grade starting point, not a toy example. Adapt the severity thresholds, the model selection, and the finding schema to your codebase's risk profile and the pipeline will serve you well.

The operational subcommands — doctor, auth, update, mcp — are the maintenance surface. Run claude doctor before filing a bug. Use claude mcp to manage server configuration rather than editing settings.json by hand. Use claude ultrareview for high-stakes reviews where compute is not a constraint. Use --safe-mode for any repro that needs to isolate model behavior from customization.

As discussed in Chapter 16, hooks and print mode are complementary: hooks govern what the harness does during a session; print mode governs how the session is invoked. A well-configured CI integration uses both — hooks to enforce policy on tool calls, print mode to make the session machine-callable. Chapter 25 examines how to compose these layers into a production-grade automated pipeline.
