Chapter 35: Performance and Cost Engineering

"Every token your harness wastes is money spent to make the model dumber. Context is not free scratch space — it is a metered resource with a price tag attached to every byte."

Running a well-designed workflow at 1M tokens per invocation and running that same workflow at 200K tokens can produce identical output quality. The difference is a 5x cost gap and a 3x latency gap, compounding across every run. At production scale — hundreds of agents, continuous CI triggers, scheduled autonomous loops — that gap is the difference between a system that stays funded and one that gets shut down.

This chapter makes cost engineering concrete. Not a list of vague recommendations to "use cache" and "pick the right model," but the specific mechanics: what each token category actually costs, which configuration decisions govern each cost driver, how to structure a workflow so that expensive tokens are the exception, and how to verify the result with the /cost command.

The six sections that follow build on each other. Section 35.1 establishes the token economics — the price structure that makes every subsequent optimization meaningful. Section 35.2 covers context reduction techniques that cut input token counts before the API call goes out. Section 35.3 covers prompt cache mechanics, which convert full-price input tokens into cache reads at roughly 10% of the cost. Section 35.4 covers model routing, matching task complexity to the cheapest model tier that can handle it. Section 35.5 covers concurrent agent budgeting, the capacity constraint that determines how many agents can run in parallel without burning through daily allowances. Section 35.6 is the case study: a real 1M-token workflow reduced to 200K, walking through every technique applied in sequence.

35.1 Token Economics

The Anthropic API charges for four distinct token categories. Understanding all four is the prerequisite for any meaningful optimization.

The Four Token Categories

The usage field in every API response exposes the breakdown:

usage: {
  input_tokens: number;                      // standard input: full price
  output_tokens: number;                     // generated output: most expensive per token
  cache_creation_input_tokens: number | null; // writing to cache: full input price
  cache_read_input_tokens: number | null;    // reading from cache: ~10% of input price
  cache_creation: {
    ephemeral_1h_input_tokens: number;
    ephemeral_5m_input_tokens: number;
  } | null;
}

Standard input tokens are what you pay when context is sent to the model without a cache hit. This covers the current user message, any tool results, and any system prompt content not served from cache.

Output tokens are the most expensive per-token category. The model generates them one by one; they cannot be cached. Minimizing unnecessary output is a first-order optimization — a model that produces a 5,000-token explanation when 500 tokens would answer the question just as well is burning 4,500 output tokens on nothing.

Cache creation tokens cost the same as standard input tokens. You are paying to write content into the 5-minute ephemeral cache. This is the upfront cost of making subsequent calls cheap. If you pay cache creation cost once and then serve that content as cache reads for the next 10 calls, you have converted 10x full-price input reads into 1 full-price write plus 9 cheap reads.

Cache read tokens are priced at approximately 10% of the standard input token price. When the harness sends a prompt whose stable prefix matches a cached entry, that prefix is served as cache reads rather than processed fresh. On a 200K-token system prompt, the difference between a cache miss and a cache hit is paying for 200K full-price input tokens versus 200K cache-read tokens — roughly a 9x reduction in cost for that portion.

The cache_creation subfield distinguishes between 5-minute ephemeral slots (ephemeral_5m_input_tokens) and 1-hour slots (ephemeral_1h_input_tokens). The harness creates these automatically based on prompt structure; you influence which one fires by controlling your call timing.

Model Tier Multipliers

Cost ratios between tiers are stable even as absolute prices change:

┌─────────────────────────────────────────────────────┐
│            RELATIVE COST BY TIER (input)            │
│                                                     │
│  Haiku    ────────── 1x   (baseline)                │
│  Sonnet   ────────── 3x                             │
│  Opus     ────────── 15x                            │
│                                                     │
│            RELATIVE COST BY TIER (output)           │
│                                                     │
│  Haiku    ────────── 1x   (baseline)                │
│  Sonnet   ────────── 5x                             │
│  Opus     ────────── 25x                            │
└─────────────────────────────────────────────────────┘

These ratios mean routing matters enormously. A classification task that runs in Haiku costs roughly 1/15th what it costs in Opus for input tokens and 1/25th for output tokens. A workflow that sends 50,000 tokens of triage work to Opus because the default model was never overridden is burning 15x budget on tasks that Haiku handles correctly.

The /cost Command

The harness provides a built-in breakdown command. After any session with significant API usage, /cost produces a per-model, per-category breakdown including the cache hit percentage. As of v2.1.92, the output format includes:

  • Total tokens by model (input, output, cache creation, cache read)
  • Cache hit rate as a percentage of total input tokens
  • Estimated cost in dollars

Make /cost a reflex at the end of any workflow that runs for the first time in a new environment. The cache hit rate is the most informative single number — a rate below 50% for a workflow that runs repeatedly signals that the stable system prompt prefix is not actually stable.

35.2 Context Strategies

Before a single API call goes out, the harness makes decisions about what to include in the context window. These pre-call decisions are the cheapest optimization available — tokens that are never sent cost nothing.

claudeMdExcludes

The harness auto-discovers CLAUDE.md files by walking the filesystem from the working directory. In a large repository, this walk can pull in CLAUDE.md files from deep within dependency trees, vendored code, and build artifacts. None of that content is useful instruction — it is noise that consumes system prompt budget and complicates cache stability.

claudeMdExcludes in project settings prunes the discovery walk:

{
  "claudeMdExcludes": [
    "**/node_modules/**",
    "**/.venv/**",
    "**/dist/**",
    "**/build/**",
    "**/__pycache__/**",
    "**/vendor/**",
    "**/.git/**"
  ]
}

For a monorepo with multiple node_modules directories, this exclusion can prevent thousands of tokens of irrelevant CLAUDE.md content from loading on every turn. It also ensures the system prompt prefix is deterministic — if the auto-discovery walk finds different CLAUDE.md files depending on filesystem state, the cache prefix changes and cache hits drop.

Deferred Tool Loading via ToolSearch

The harness loads tool descriptions into the system prompt at startup. Each tool description consumes context budget — and more critically, changes the system prompt content, which affects cache stability. The deferred tool pattern (ToolSearch) keeps specialized tools out of the initial system prompt and loads them only when explicitly requested.

The savings per deferred tool range from 500 to 2,000 tokens per turn, depending on description complexity. For a harness that exposes 30 tools, loading all 30 upfront versus loading 6 core tools and deferring 24 means the difference between a 15,000-token tool section and a 3,000-token tool section in the system prompt. That 12,000-token difference applies to every single API call in the session.

In practice:

# Core tools always loaded: Bash, Read, Edit, Write, Agent, AskUserQuestion
# Deferred: LSP, Glob, Grep, WebFetch, WebSearch, scheduling tools, MCP tools

ENABLE_TOOL_SEARCH=true claude -p "Review this PR..."

The ToolSearch mechanism handles the load-on-demand behavior automatically. When the model needs a deferred tool, it calls ToolSearch first, which brings the tool schema into context for subsequent turns.

For MCP tools, cap descriptions at 2KB per tool. The harness enforces this limit, but writing against it proactively — keeping MCP tool descriptions concise — prevents edge cases where a verbose description causes the tool to be dropped or truncated in ways that produce confusing model behavior.

For skills, the listing shown to the model is capped at 250 characters per skill description. Write skill descriptions to that limit intentionally; anything beyond 250 characters is invisible to the model until it actually invokes the skill.

Read Deduplication

The harness tracks file content across turns. When the model calls Read on a file it has already read during the current session and the file has not changed, the harness returns a file_unchanged response instead of resending the full file content. The file is not re-injected into the conversation.

This optimization fires silently, but its impact compounds in multi-turn sessions. A workflow that reads README.md five times across five turns — once to understand the project, once to check structure, once per subagent — would pay for 5x the file's token count without deduplication. With deduplication, it pays for 1x.

The implication for workflow design: do not pre-load files defensively across agent boundaries. If each subagent independently decides to read the same configuration file, the deduplication handles the redundancy automatically. There is no need to pass file content explicitly through agent boundaries unless the content is volatile between calls.

Token Cap Pagination

Large files are automatically paginated when they exceed the token cap threshold. The truncatedByTokenCap: true flag in the Read output signals that the file was truncated. The harness does not crash; it delivers what fits and marks the result as incomplete.

This behavior exists to prevent a single large file read from consuming the entire available context. The engineering implication: structure file reads for large artifacts using explicit offset and limit parameters rather than relying on auto-pagination. A workflow that reads a 50,000-line codebase one file at a time, using offset/limit to process sections, is cheaper and more predictable than one that reads entire files and relies on the harness to truncate.

# Read first 500 lines — explicit control
# Read tool: { file_path: "src/large_module.py", offset: 0, limit: 500 }

# Process next 500 lines
# Read tool: { file_path: "src/large_module.py", offset: 500, limit: 500 }

For Grep, the head_limit parameter defaults to 250 lines — not unlimited. A grep across a large codebase that would return 10,000 matching lines is automatically capped at 250. This default is cost-protective: an unrestricted Grep result that floods the context with thousands of lines is rarely what the workflow actually needs. Use the offset parameter to paginate through results when more than 250 lines are required.

35.3 Cache Optimization

The prompt cache is the single highest-leverage cost optimization available in the harness. A workflow that achieves 80% cache read tokens versus 20% standard input tokens is paying roughly 2.6x less for input tokens than the same workflow at 0% cache hits — on identical work.

How Cache TTL Works

The cache has a 5-minute TTL on ephemeral entries. Once a prefix is written to the cache, any subsequent call that presents the same prefix within 5 minutes is served as cache reads. A call that arrives more than 5 minutes after the last access pays full cache creation cost to warm it again.

The practical implication for scheduled workflows: schedule them at off-minute times, and keep the inter-call interval under 270 seconds.

Cache stays warm:       interval ≤ 270s (5% safety margin under 5-min TTL)
Cache goes cold:        interval ≥ 300s (the full 5 minutes has elapsed)
Worst case:             interval = 300s exactly (pays cache creation on every run)

The harness's CronCreate tool enforces the off-minute rule: crons are not scheduled at :00 or :30 to avoid thundering-herd load spikes. Beyond load distribution, off-minute scheduling also avoids races with other agents competing for the same cache slots.

For workflows that must run less frequently than every 5 minutes, ScheduleWakeup with delaySeconds under 270 is not viable. Instead, accept the cache miss on the periodic call and focus on making the stable prefix as large as possible so that the cache creation cost is amortized over many tokens.

The Stable System Prompt Prefix

The cache keys on the prefix of the system prompt. Everything before the first dynamic element can be served from cache on repeat calls. Everything after a dynamic element is not cached.

The anatomy of a typical system prompt:

[STABLE]   base instructions (tool descriptions, behavioral rules)
[STABLE]   CLAUDE.md content
[STABLE]   project memory / reference materials
[DYNAMIC]  current git status
[DYNAMIC]  current working directory state
[DYNAMIC]  per-session environment info

If the dynamic sections come last, the stable prefix — which may be 100,000+ tokens of tool descriptions, CLAUDE.md content, and project memory — is cached. On subsequent calls, those tokens cost 10% of their standard input price.

If a dynamic section appears early in the system prompt — say, git status is injected at the top — the cache prefix covers only what comes before it. Every CLAUDE.md byte and tool description byte that follows the dynamic section pays full input price on every call.

Design principle: all dynamic content goes at the end of the system prompt or into the first user message.

--exclude-dynamic-system-prompt-sections

Some dynamic system prompt sections are per-machine rather than per-session — environment details, hostname, platform information. These sections break cache sharing across multiple users or CI runners on different machines, even when the actual work is identical.

The --exclude-dynamic-system-prompt-sections flag moves these per-machine sections out of the system prompt and into the first user message:

claude --exclude-dynamic-system-prompt-sections -p "Audit these files..."

With this flag, the system prompt is identical across all machines for the same project. A CI fleet of 50 runners all benefit from the same system prompt cache entry. Without it, each runner has a unique system prompt prefix because of machine-specific environment sections, and each runner pays cache creation on its first call.

This flag is specifically valuable in:

  • Shared CI/CD environments with multiple runners
  • Multi-user workflows where different engineers run the same agent
  • Containerized deployments where container identity varies

Cache Awareness in Concurrent Workflows

When a workflow launches 20 parallel agents with parallel(), all 20 agents call the API within a short window. If the system prompt is not already cached, all 20 agents pay cache creation cost for their first call. Only one of them writes the cache; the others race against the cache write and may or may not get a hit.

The pattern to avoid this:

// Warm the cache with a cheap initial call before spawning parallel agents
const warmup = await agent('Confirm you are ready to begin the audit.', {
  model: 'haiku',
  label: 'cache-warmup'
})

// Now the system prompt is cached — parallel agents get cache hits on their first call
const results = await parallel(
  targets.map(t => () => agent(`Audit ${t}`, { model: 'sonnet', label: `audit:${t}` }))
)

The warmup call is cheap (Haiku, minimal output) but it populates the cache. The 20 subsequent Sonnet calls all hit the warm cache on their first API call, paying 10% input price on what would otherwise be 20 full cache creation charges.

35.4 Model Routing

Model routing is the discipline of matching task complexity to the cheapest model tier that produces acceptable results. The economics are severe enough that doing it systematically — not ad hoc — pays for itself in hours.

The Three-Tier Decision Framework

┌─────────────────────────────────────────────────────────────┐
│              MODEL ROUTING DECISION FRAMEWORK               │
│                                                             │
│  Task characteristics                  → Route to          │
│  ──────────────────────────────────────────────────────     │
│  Classification, extraction, triage    → Haiku              │
│  Structured format conversion          → Haiku              │
│  Simple summarization (<500 words)     → Haiku              │
│  High-volume screening (1000s items)   → Haiku              │
│                                                             │
│  Code implementation (well-scoped)     → Sonnet             │
│  Test writing                          → Sonnet             │
│  Documentation generation              → Sonnet             │
│  Multi-file refactoring                → Sonnet             │
│  Standard code review                  → Sonnet             │
│                                                             │
│  Architecture decisions                → Opus               │
│  Security analysis (high stakes)       → Opus               │
│  Complex reasoning over large context  → Opus               │
│  Final synthesis across many inputs    → Opus               │
│  Production incidents / postmortems    → Opus               │
└─────────────────────────────────────────────────────────────┘

The boundary between Haiku and Sonnet is task complexity and error tolerance. Haiku degrades on tasks requiring more than a few reasoning steps, tasks with ambiguous specifications, or tasks where context exceeds a few thousand tokens. Within its sweet spot, it is correct, fast, and cheap.

The boundary between Sonnet and Opus is correctness stakes and context size. Sonnet handles the wide middle of the distribution well — it rarely produces embarrassing failures on well-scoped implementation tasks. Opus is for decisions where a wrong answer causes an incident, or for synthesis tasks over large context where the model needs to hold many moving parts simultaneously without losing fidelity.

Routing in Workflow Scripts

The model option on every agent() call is the primary routing lever:

phase('Triage')

// Haiku screens 200 files for relevance — cheap, fast, tolerates occasional misses
const relevant = await pipeline(
  allFiles,
  f => agent(`Does this file contain authentication logic? Reply YES or NO only. File: ${f}`, {
    model: 'haiku',
    label: `triage:${f}`,
    schema: { type: 'object', properties: { relevant: { type: 'boolean' } }, required: ['relevant'] }
  })
).then(results => allFiles.filter((_, i) => results[i].relevant))

phase('Implement')

// Sonnet implements changes on the relevant subset — good capability, half the Opus price
const patches = await parallel(
  relevant.map(f => () => agent(`Fix the session token storage in ${f} to use httpOnly cookies`, {
    model: 'sonnet',
    label: `fix:${f}`
  }))
)

phase('Review')

// Opus reviews the complete patch set — this is a production safety decision
const verdict = await agent(
  `Review all these patches for correctness and security implications: ${patches.join('\n---\n')}`,
  { model: 'opus', label: 'final-review' }
)

This three-tier pipeline does all triage in Haiku, all implementation in Sonnet, and reserves Opus for the single final review. The cost ratio relative to running everything in Opus:

  • Triage phase: 200 Haiku calls vs 200 Opus calls — 15x cheaper on input, 25x on output
  • Implementation phase: N Sonnet calls vs N Opus calls — 5x cheaper on input, 5x on output
  • Review phase: 1 Opus call either way

The only Opus spend is the review that genuinely needs it.

Fast Mode

When the task requires Opus reasoning depth but not maximum throughput, fast mode (fastMode: true) is an option within the Opus tier. It runs the same Opus model with a latency-optimized inference profile — output streams faster, but the capability ceiling is identical. The per-token cost does not change; the reduction is in wall-clock time for the same token volume.

Fast mode is relevant when Opus is the right tier but latency is bottlenecking a human-in-the-loop workflow. It is not a cost optimization.

Effort Level as a Thinking Budget

The effortLevel setting (low/medium/high/xhigh/max) controls how much extended thinking the model applies before generating output. Extended thinking consumes additional tokens (governed by MAX_THINKING_TOKENS=100000). For tasks that do not benefit from deep deliberation, lowering effort level reduces token consumption without changing the model tier:

# Simple utility task — no deep thinking needed
MAX_THINKING_TOKENS=5000 claude --effort low -p "Add type hints to these functions..."

# Architecture decision — maximum deliberation
MAX_THINKING_TOKENS=100000 claude --effort max -p "Design the auth layer for this service..."

Reducing MAX_THINKING_TOKENS from 100,000 to 5,000 on a task that does not benefit from extended thinking saves up to 95,000 thinking tokens per call. At Opus pricing, that is a substantial cut on any workflow that runs Opus repeatedly.

35.5 Concurrent Agent Budgeting

Concurrency multiplies throughput — and cost. Twenty agents running in parallel consume 20x the tokens per unit time compared to a single agent. Without concurrency controls, a workflow that feels fast during single-run testing can blow through a daily token budget in minutes when deployed at scale.

The CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY Setting

This environment variable caps the number of tool calls that execute simultaneously within a session:

CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY=8 claude -p "Run the audit workflow..."

The default in Claude Code is derived from available CPU cores: min(16, cores - 2). For a workflow running on an 8-core machine, the default cap is 6 concurrent tool calls.

This cap applies to all tool calls, not just agent spawns. A workflow that calls Bash and Read and agent() simultaneously counts all three against the concurrency limit. In practice, agent() calls dominate the concurrency budget because they are the most expensive and most parallel operation in typical workflows.

Setting the concurrency cap is a cost-control decision as much as a performance decision:

┌─────────────────────────────────────────────────────┐
│          CONCURRENCY VS COST TRADEOFF               │
│                                                     │
│  Cap = 1    Serialized. Minimum burn rate.          │
│             Maximum latency. Good for budget runs.  │
│                                                     │
│  Cap = 4    Moderate parallelism.                   │
│             4x burn rate. Half the Opus latency.    │
│                                                     │
│  Cap = 8    Full parallelism for most workflows.    │
│             8x burn rate. Near-minimum latency.     │
│                                                     │
│  Cap = 16   Maximum supported.                      │
│             16x burn rate. Good for time-critical.  │
└─────────────────────────────────────────────────────┘

For CI workflows that run on a fixed schedule and must complete within a window, a higher cap trades cost for speed. For background workflows that run continuously and have no latency requirement, a lower cap reduces peak burn rate and protects daily budgets.

Workflow Budget Caps

The workflow budget system provides a higher-level ceiling that applies across all agents in a workflow execution:

// budget is available in every workflow script
log(`Budget: ${budget.total} tokens total`)
log(`Spent: ${budget.spent()} tokens`)
log(`Remaining: ${budget.remaining()} tokens`)

// Hard ceiling — further agent() calls throw if this is exceeded
while (budget.remaining() > 50_000) {
  const batch = await parallel(
    nextBatch.map(item => () => agent(`Process ${item}`, { model: 'sonnet' }))
  )
  // ...
}

The budget.total value comes from the user's directive — if the session was started with a "+500k" token allocation, budget.total is 500,000. budget.spent() tracks output tokens across all agents spawned by the workflow. budget.remaining() returns the hard ceiling; when any agent call would exceed it, the harness throws rather than silently continuing.

The practical pattern for large workflows: size your parallel() batches against the remaining budget rather than against the full list. A workflow that fans out 1,000 items in a single parallel() call and runs out of budget midway leaves the results in an indeterminate state. A workflow that runs batches of 50 with a budget check between batches can terminate cleanly and report partial results.

const BATCH_SIZE = 50
const MIN_BUDGET_PER_BATCH = 100_000

for (let i = 0; i < items.length; i += BATCH_SIZE) {
  if (budget.remaining() < MIN_BUDGET_PER_BATCH) {
    log(`Budget nearly exhausted at ${i}/${items.length} items — stopping`)
    break
  }
  const batch = items.slice(i, i + BATCH_SIZE)
  const results = await parallel(
    batch.map(item => () => agent(`Process ${item}`, { model: 'sonnet' }))
  )
  processed.push(...results)
}

The 1,000-Agent Lifetime Cap

The harness enforces a 1,000-agent lifetime cap per session. This is not a per-workflow cap — it accumulates across all agents spawned from the moment the session starts. A workflow that spawns 50 agents per run will hit the cap after 20 runs without a session reset.

For long-running autonomous loops (as discussed in Chapter 31), this cap requires session refresh as part of the loop's maintenance logic. A session that approaches 900 agents should checkpoint state, terminate cleanly, and restart from a fresh session before continuing.

35.6 Case Study: Reducing a 1M-Token Workflow to 200K

This section walks through a real optimization: a codebase security audit workflow that initially consumed approximately 1,000,000 tokens per run, reduced to approximately 200,000 tokens after systematic application of the techniques in this chapter.

The Starting Point

The initial workflow:

export const meta = {
  name: 'security-audit',
  description: 'Full codebase security audit'
}

// Read all files upfront — naive approach
const allFiles = await agent('List every file in the codebase', { label: 'list-files' })

// Audit every file with Opus
const findings = await parallel(
  allFiles.paths.map(f => () => agent(
    `Audit this file for all OWASP Top 10 vulnerabilities: ${f}`,
    { model: 'opus', label: `audit:${f}` }
  ))
)

// Synthesize
const report = await agent(
  'Synthesize all these audit findings into a final report',
  { model: 'opus', label: 'synthesize' }
)

Token profile for a codebase with 200 files:

System prompt (all tools loaded, no excludes):  ~18,000 tokens   × 200 calls = 3,600,000
Per-file audit input (file contents + prompt):  ~2,000 tokens    × 200 calls =   400,000
Output (findings per file):                     ~1,000 tokens    × 200 calls =   200,000
Synthesis input (all findings):                 ~200,000 tokens  × 1 call   =   200,000
Synthesis output:                               ~5,000 tokens    × 1 call   =     5,000
                                                                    TOTAL:   ~4,405,000

Cost multiplier: everything running in Opus. No cache. Full system prompt on every call.

The measured token count at /cost: approximately 1,000,000 tokens (the harness compresses and deduplicates; the raw calculation above counts redundancies the harness already handles). Still — the workflow is expensive, slow, and doing significant redundant work.

Optimization 1: Deferred Tools and claudeMdExcludes

First change: prune the system prompt.

{
  "claudeMdExcludes": [
    "**/node_modules/**",
    "**/.venv/**",
    "**/dist/**",
    "**/build/**"
  ]
}
ENABLE_TOOL_SEARCH=true claude -p "Run security audit..."

Effect: system prompt drops from ~18,000 tokens to ~6,000 tokens. Across 200+ API calls, this saves ~2,400,000 tokens — but only if cache is not already handling the stable prefix. With no cache, this is a direct 12,000-token reduction per call.

Optimization 2: Cache Warmup

Second change: pre-warm the system prompt cache before spawning parallel agents.

// Add before the parallel() call
await agent('Confirm ready.', { model: 'haiku', label: 'warmup' })

The warmup call costs ~6,000 tokens (system prompt write) + ~50 tokens (tiny input/output). Every subsequent agent call in the parallel fan-out serves the 6,000-token system prompt as cache reads at 10% price.

Cost conversion: 200 calls × 6,000 tokens at full price → 1 write + 199 reads.

  • Without cache: 200 × 6,000 = 1,200,000 full-price input tokens
  • With cache: 6,000 creation + 199 × 6,000 cache reads ≈ 6,000 + 119,400 tokens at 10% price
  • Effective token-equivalent: 6,000 + 11,940 = 17,940 full-price equivalent

That is a 67x reduction in effective cost on the system prompt portion alone.

Optimization 3: Haiku Triage

Third change: screen files before sending them to any analysis model.

phase('Triage')

const relevant = await pipeline(
  allFiles.paths,
  f => agent(
    `Does this file contain server-side code handling user input, authentication, or database queries? Reply JSON: {"relevant": true/false}`,
    {
      model: 'haiku',
      label: `triage:${f}`,
      schema: { type: 'object', properties: { relevant: { type: 'boolean' } }, required: ['relevant'] }
    }
  )
).then((results, i) => allFiles.paths.filter((_, idx) => results[idx].relevant))

A 200-file Python/TypeScript codebase typically contains 30–60 files with meaningful server-side logic. The rest — tests, fixtures, config files, frontend components, utility modules — rarely harbor the vulnerabilities the audit is targeting.

Effect: reduces the audit phase from 200 calls to approximately 50 calls. Triage phase adds 200 Haiku calls, but at Haiku pricing these cost 1/15th of Opus calls on input and 1/25th on output.

Token delta:

  • Removed: 150 Opus audit calls × ~3,000 tokens each = 450,000 tokens at Opus price
  • Added: 200 Haiku triage calls × ~500 tokens each = 100,000 tokens at Haiku price
  • Net: large reduction in effective cost

Optimization 4: Sonnet for Implementation

Fourth change: Opus is overkill for per-file auditing. Sonnet handles the analysis correctly on well-scoped security questions with a defined output schema.

phase('Audit')

const findings = await parallel(
  relevant.map(f => () => agent(
    `Audit ${f} for OWASP Top 10 vulnerabilities. Report only confirmed findings.`,
    {
      model: 'sonnet',   // was 'opus'
      label: `audit:${f}`,
      schema: FINDING_SCHEMA
    }
  ))
)

Sonnet at 5x cheaper output tokens versus Opus, on 50 analysis calls.

Opus is retained only for the final synthesis, where the model must hold all findings simultaneously and produce a prioritized report — a task where Opus's reasoning depth over large context genuinely matters.

Optimization 5: --exclude-dynamic-system-prompt-sections

Fifth change: the CI runners have different hostnames. Without this flag, each runner has a unique system prompt prefix — the cache is effectively per-runner rather than shared.

claude --exclude-dynamic-system-prompt-sections -p "..."

This moves per-machine environment details to the first user message, making the system prompt identical across all runners. On a 10-runner CI fleet, this converts 10 independent cache entries into 1 shared cache entry, multiplying the effective cache warm period.

Final Token Profile

After all five optimizations:

System prompt (pruned, deferred tools):     ~6,000 tokens
Cache warmup (Haiku):                           ~6,050 tokens (one-time write)
Triage (200 × Haiku, ~250 tokens each):       ~50,000 tokens at Haiku price
Audit (50 × Sonnet, ~2,000 tokens each):     ~100,000 tokens at Sonnet price
Synthesis (1 × Opus, ~50,000 tokens input):   ~55,000 tokens at Opus price
                                    TOTAL:   ~211,050 tokens (weighted)

Measured at /cost: approximately 205,000 tokens. The 1M-token baseline is now approximately 200K — a 5x reduction in token volume, with a larger reduction in effective cost because most remaining tokens are either cache reads or Haiku-tier.

The key moves in order of impact:

  1. Cache warmup — single highest-leverage change; converts 200 full system-prompt reads to 199 cache reads
  2. Haiku triage — eliminates 75% of expensive analysis calls by filtering irrelevant files first
  3. Sonnet for implementation — drops per-file analysis cost by 5x on input, 5x on output
  4. claudeMdExcludes — shrinks the stable prefix, which makes the cache more effective and reduces creation cost
  5. --exclude-dynamic-system-prompt-sections — enables cross-runner cache sharing in CI

None of these changes affected the quality of findings. The same vulnerabilities were identified in the optimized run as in the baseline run, with Opus reviewing the final synthesized output before any result was reported.

Summary

Cost engineering in the harness is not about cutting corners. It is about spending tokens where they produce value and eliminating the spend that does not.

The decision tree is straightforward:

  1. Measure first — run /cost on the baseline. Identify whether the cost is dominated by input tokens, output tokens, or cache misses.
  2. If input tokens are high with low cache hit rate: stabilize the system prompt prefix, run --exclude-dynamic-system-prompt-sections, add a warmup call before parallel fans.
  3. If input tokens are high despite good cache: add claudeMdExcludes, enable deferred tools, audit for redundant file reads.
  4. If output tokens are high: check whether model tier matches task complexity. Haiku for classification. Sonnet for implementation. Opus only where reasoning depth matters.
  5. If per-call cost is high at the right tier: check MAX_THINKING_TOKENS. Lower effort level for tasks that do not need deep deliberation.
  6. If the workflow is blowing budgets: add concurrency caps, add budget-check loops, batch parallel() calls against budget.remaining().

The 5x reduction in the case study came from applying these steps in order, measuring after each one, and stopping when the workflow hit its cost target. The same process applies to any workflow — the specific numbers will differ, but the approach is the same.

As discussed in Chapter 20, context management and cache strategy are deeply linked — cache hits depend on a stable prefix, and a stable prefix requires deliberate context management. Chapter 36 covers the observability tools that make these measurements precise: debug mode, transcript analysis, OpenTelemetry integration, and the tool statistics in AgentOutput that let you quantify exactly where tokens are going.
