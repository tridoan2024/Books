Chapter 18: Plugin Architecture — Shareable Extensions

"A plugin is not a feature. It is a contract — between author, marketplace, and enterprise operator."

18.1 Plugin Structure: The Six Directories and Two Files

A Claude Code plugin is a directory with a specific shape. That shape is not arbitrary — every directory maps to a capability class, and the harness knows exactly what to look for in each one. Understanding the structure before anything else is the right starting point because it makes everything that follows predictable.

The canonical plugin layout:

my-plugin/
├── .claude-plugin/
│   └── plugin.json          # plugin manifest (required)
├── commands/                # /command-name markdown files
│   └── do-thing.md
├── agents/                  # named agent definitions
│   └── reviewer.md
├── skills/                  # reusable prompt fragments
│   └── analyze-deps.md
├── hooks/                   # event-driven behavior
│   └── PreToolUse.ts
├── bin/                     # executables invocable from Bash tool
│   └── my-scanner
└── .mcp.json                # MCP server declarations

The .claude-plugin/ directory is the sentinel. When the harness scans for plugins — on install, on session start, when enumerating capabilities — it looks for this directory. A directory without .claude-plugin/plugin.json is not a plugin; it is just a directory.

Each of the other directories is optional. A plugin can ship nothing but a command and still be valid. A plugin can ship nothing but hooks. The structure is additive — you include the directories that correspond to the capabilities you need.

The .claude-plugin/ Directory

The .claude-plugin/ directory exists to separate plugin metadata from plugin content. Everything in it is read by the harness itself, not by the model. The only required file is plugin.json. In practice you may also find CHANGELOG.md and LICENSE in this directory, though those are conventions rather than harness-enforced requirements.

commands/

Each markdown file in commands/ defines a slash command. The filename becomes the command name: do-thing.md registers as /do-thing (or /plugin-name:do-thing if namespacing is active). The file content is the command prompt — the instruction set the model receives when a user invokes the command.

Commands are the most visible capability in a plugin. They are what users interact with directly.

agents/

Agent files define named subagent types that can be spawned with subagent_type: "agent-name" in the Agent tool. An agent definition is a markdown file containing the system prompt for that agent — its role, its tool constraints, its output format, its escalation criteria.

The code-review plugin ships five agent files: security-reviewer.md, performance-reviewer.md, test-coverage-reviewer.md, code-style-reviewer.md, and architecture-reviewer.md. Each is specialized. Each gets spawned in parallel when the /code-review command runs.

skills/

Skills are reusable prompt fragments. They are not commands — a user cannot invoke a skill directly. Skills are included by commands, agents, and hooks through the !include directive. A skill named analyze-deps.md might contain a structured procedure for dependency analysis that three different commands all reference.

The plugin-dev plugin ships seven skills that cover every aspect of plugin creation. Skills are how that plugin avoids repeating identical procedure text across seven different commands.

hooks/

Hook files define event-driven behavior that fires automatically based on harness events. A hook named PreToolUse.ts registers for the PreToolUse event. A hook named SessionStart.ts runs at the beginning of every session that has this plugin enabled.

The hookify plugin's core directory is hooks/ — it is a plugin whose primary product is hook generation and management.

bin/

Executables in bin/ become available to the Bash tool when the plugin is installed. This is how a plugin ships a scanner, a linter, a formatter, or any other CLI tool that Claude can invoke during a task. The harness adds the plugin's bin/ directory to the PATH when executing Bash tool calls, making the executables available without absolute paths.

This is a powerful surface. A plugin that ships a bin/secret-scanner binary gives Claude a high-performance secret detection tool it can run on any file or directory. The binary does not have to be written in any particular language — it just needs to be executable.

.mcp.json

This file declares MCP (Model Context Protocol) servers that the plugin provides. When installed, these servers are registered with the harness and become available as additional tool sources. The copilot-mem plugin is almost entirely .mcp.json — its plugin manifest declares an MCP memory server, and that server provides the memory tools.

18.2 Plugin Manifest: The plugin.json Contract

The plugin.json file is the contract between a plugin and the harness. It is small, but every field matters.

{
  "name": "code-review",
  "description": "Automated code review for pull requests using multiple specialized agents with confidence-based scoring",
  "version": "1.0.0",
  "author": {
    "name": "Boris Cherny",
    "email": "boris@anthropic.com"
  }
}

This is the actual manifest from the official code-review plugin. Four fields, no more. That is not minimal effort — that is intentional interface design.

name

The name is the plugin's identifier in every context: the marketplace index, installed_plugins.json, the enabledPlugins setting, and the namespaced command prefix. It must be lowercase, hyphen-separated, and globally unique within a marketplace.

The naming convention matters because of how command namespacing works. When a plugin named code-review ships a command file review.md, the command is accessible as both /review (if no namespace conflict) and /code-review:review (the fully qualified form). The name is the namespace.

description

The description is what users see in marketplace listings and in --help output. It is not a docstring — it is marketing copy for the plugin's primary use case. Write it as a complete sentence. Be specific about what the plugin does and what makes it different from alternatives.

Compare:

// Weak:
"description": "Code review plugin"

// Strong:
"description": "Automated code review for pull requests using multiple specialized agents with confidence-based scoring"

The strong version tells users what the plugin does (automated code review), how it does it (multiple specialized agents), and what makes it notable (confidence-based scoring). That is enough information to decide whether to install it.

version

Versions follow semantic versioning: MAJOR.MINOR.PATCH. The harness uses the version field to detect when an installed plugin has an available update from the marketplace. When you push a new version to a marketplace repository, users with auto-update enabled will receive the new version.

The installed_plugins.json entry for each plugin stores both version and gitCommitSha. This dual tracking means the harness can detect version mismatches — a case where the marketplace lists a higher version but the local install's SHA matches an older commit.

author

The author object is for attribution and contact. In enterprise settings, the email field is used by security teams to track who is responsible for which plugins. When a plugin causes unexpected behavior or requires security review, the author contact is the first path to resolution.

For enterprise plugins, the name should match the team or service, not an individual:

{
  "author": {
    "name": "Platform Security Team",
    "email": "platform-security@yourorg.com"
  }
}

18.3 Distribution: Marketplaces, Known and Installed

The plugin distribution system has two layers: the marketplace layer (where plugins live) and the install layer (what is on this machine). Understanding both is necessary for enterprise deployment and for publishing your own plugins.

Marketplaces

A marketplace is a GitHub repository with a defined structure. The harness discovers marketplaces through known_marketplaces.json, which lives at ~/.claude/plugins/known_marketplaces.json:

{
  "claude-plugins-official": {
    "source": {
      "source": "github",
      "repo": "anthropics/claude-plugins-official"
    },
    "installLocation": "/Users/user/.claude/plugins/marketplaces/claude-plugins-official",
    "lastUpdated": "2026-03-31T15:52:23.030Z"
  }
}

Each key in this object is a marketplace identifier. The source object describes where the marketplace lives — currently GitHub is the supported source type. The installLocation is where the harness caches the marketplace's plugin index locally. The lastUpdated timestamp drives the refresh cycle.

When you run /plugin install code-review, the harness:

  1. Reads known_marketplaces.json to find registered marketplaces
  2. Checks each marketplace's cached index for a plugin named code-review
  3. Downloads the plugin from GitHub to the local install path
  4. Writes an entry to installed_plugins.json
  5. Activates the plugin for the current scope

The lastUpdated field matters for offline environments. If you set CLAUDE_CODE_PLUGIN_KEEP_MARKETPLACE_ON_FAILURE=true, the harness retains the locally cached marketplace index even when GitHub is unreachable. This means plugin installs from cached data still work in air-gapped or network-constrained environments, but new plugins added to the marketplace since the last cache refresh will not be visible.

installed_plugins.json

Every installed plugin gets an entry in ~/.claude/plugins/installed_plugins.json:

{
  "version": 2,
  "plugins": {
    "rust-analyzer-lsp@claude-plugins-official": [{
      "scope": "user",
      "installPath": "...cache/claude-plugins-official/rust-analyzer-lsp/1.0.0",
      "version": "1.0.0",
      "installedAt": "2026-04-10T02:55:43.321Z",
      "gitCommitSha": "52e95f6756e577b6a788c941f994ca44de2cf2d6"
    }]
  }
}

The plugin key is name@marketplace-id. The @marketplace-id suffix matters: the same plugin name could theoretically exist in multiple marketplaces, and the harness needs to distinguish them.

The scope field is "user" for user-level installs and "project" for project-level installs. A project-level install lives in .claude/plugins/ inside the project directory and is only active when Claude Code is run from that project.

The gitCommitSha is the harness's integrity anchor. When verifying a plugin at session start, the harness can confirm the local files match the expected commit. If they do not — because someone manually edited a plugin file — the harness can flag the discrepancy.

Enabling Plugins

Installation and enablement are separate operations. An installed plugin is not active until it appears in the enabledPlugins setting in settings.json:

{
  "enabledPlugins": {
    "code-review@claude-plugins-official": true,
    "hookify@claude-plugins-official": true
  }
}

The /plugin command manages both operations. The full command surface:

/plugin install <name>          # install from marketplace
/plugin enable <name>           # enable an installed plugin
/plugin disable <name>          # disable without uninstalling
/plugin uninstall <name>        # remove entirely
/plugin list                    # show installed and enabled plugins
/plugin update <name>           # update to latest marketplace version

The enable/disable split is useful for plugins you want available but not active in every session. You might have the security-guidance plugin installed but only enable it for sessions involving infrastructure changes.

18.4 Enterprise Control: Governance Without Friction

Enterprise deployments have requirements that consumer use does not: audit trails, allowlists, protection against supply chain attacks, and compliance with internal security policies. Claude Code's enterprise plugin governance is controlled through managed-settings.json, the policy file that administrators push to managed machines.

strictKnownMarketplaces

{
  "strictKnownMarketplaces": true
}

When this is set, users can only install plugins from marketplaces explicitly listed in known_marketplaces.json. Any attempt to install from a marketplace not in the known list fails with a policy error.

This is the primary control for supply chain hygiene. Without it, a user could add any GitHub repository as a marketplace and install arbitrary plugins. With it, the IT or security team controls the full list of approved marketplaces, and that list is the only source of truth.

Typical enterprise configuration:

{
  "claude-plugins-official": {
    "source": { "source": "github", "repo": "anthropics/claude-plugins-official" },
    "installLocation": "/opt/claude/plugins/marketplaces/claude-plugins-official"
  },
  "corp-internal-plugins": {
    "source": { "source": "github", "repo": "yourorg/claude-plugins-internal" },
    "installLocation": "/opt/claude/plugins/marketplaces/corp-internal"
  }
}

Two marketplaces: the official Anthropic one and an internal corporate repository. Nothing else.

allowedChannelPlugins

{
  "allowedChannelPlugins": [
    "code-review@claude-plugins-official",
    "security-guidance@claude-plugins-official",
    "corp-code-standards@corp-internal-plugins"
  ]
}

This is a plugin allowlist. Even if a plugin is available in an approved marketplace, it cannot be installed unless it appears in allowedChannelPlugins. This is the right control when you want to explicitly approve each plugin rather than approve all plugins from approved sources.

The two controls compose: strictKnownMarketplaces limits where plugins come from, allowedChannelPlugins limits which specific plugins from those sources are permitted.

allowManagedHooksOnly

{
  "allowManagedHooksOnly": true
}

This is the most targeted of the three controls. Hooks are powerful — they run automatically, they can intercept tool calls, and they can modify behavior. A malicious hook shipped in an apparently benign plugin is a real attack vector.

When allowManagedHooksOnly is true, only hooks that come from the organization's own managed plugins are allowed to execute. Hooks from user-installed plugins — even from the official marketplace — are silently disabled. This gives organizations the ability to use plugins for commands and agents while retaining full control over the event-driven behavior layer.

Enforcement Behavior

The harness checks policy at install time and at session start. If a policy violation is detected at session start — a plugin was installed before a policy was applied — the harness disables the plugin for that session and logs the reason. Users see a policy notice; they do not see an unexplained failure.

This design is deliberate: enforce early, communicate clearly, never silently succeed with partial behavior. An agent operating with half its expected plugins active because the other half were policy-blocked but not communicated is more dangerous than an agent that refuses to start.

18.5 Plugin Capabilities in Depth

Custom Commands

Commands are the user-facing surface of a plugin. They are markdown files, which means the full power of CLAUDE.md instruction syntax is available: structured task descriptions, tool restrictions, output format specifications, and embedded checklists.

A well-authored command file for a dependency audit command:

---
description: Audit project dependencies for known vulnerabilities and outdated packages
allowed-tools: Bash, Read, Write
---

You are running a dependency audit for the current project.

## Steps

1. Detect the package manager (check for package.json, requirements.txt, Cargo.toml, go.mod)
2. Run the appropriate audit command:
   - npm: `npm audit --json`
   - pip: `pip audit --format=json`
   - cargo: `cargo audit --json`
   - go: `govulncheck ./... -json`
3. Parse the JSON output and categorize findings by severity: CRITICAL, HIGH, MEDIUM, LOW
4. For each CRITICAL or HIGH finding, identify whether a patched version is available
5. Write a report to `audit-report.md` with:
   - Summary table (counts per severity)
   - Detailed findings with CVE IDs and remediation steps
   - Upgrade commands ready to copy-paste

If the audit tool is not installed, output clear installation instructions and stop.

The allowed-tools frontmatter is enforced: Claude cannot use any tool not listed when executing this command, even tools it would normally have access to. This is the command's permission boundary.

Agents

Agent definitions are system prompts for named subagent types. When a parent agent spawns subagent_type: "security-reviewer", the harness looks up the agent definition file and uses it as the subagent's system prompt.

This is how the code-review plugin achieves specialization. Each of its five agents receives a role-specific system prompt — the security reviewer cares about injection flaws, the test coverage reviewer cares about branch coverage, the architecture reviewer cares about coupling metrics. They spawn in parallel and return structured findings that the coordinator synthesizes.

Hooks

Hooks are the event-driven layer. A hook in a plugin fires just like a hook in .claude/hooks/ — the difference is that the plugin author is the one who wrote it, and the enterprise operator can choose to allow or block it via allowManagedHooksOnly.

The security-guidance plugin ships a single PreToolUse hook that monitors for nine patterns:

const DANGEROUS_PATTERNS = [
  { pattern: /rm\s+-rf\s+\//, description: "recursive delete from root" },
  { pattern: />\s*\/etc\/passwd/, description: "write to /etc/passwd" },
  { pattern: /curl.*\|\s*bash/, description: "pipe curl to bash" },
  { pattern: /chmod\s+777/, description: "world-writable permission set" },
  // ... five more
];

When Claude attempts a Bash tool call matching any of these patterns, the hook appends a structured security reminder to the tool result, prompting Claude to reconsider before proceeding.

The explanatory-output-style and learning-output-style plugins both ship SessionStart hooks. These hooks inject behavioral instructions at the beginning of every session where the plugin is active — essentially wrapping the user's CLAUDE.md with additional output formatting rules without requiring the user to edit any files.

MCP Servers

The .mcp.json file lets a plugin declare Model Context Protocol servers. When the plugin is active, those servers are available as additional tool providers. The copilot-mem plugin is the canonical example — its MCP server provides memory read/write/search tools that persist across sessions.

This is how plugins extend the tool surface without modifying the harness itself. An organization that builds an internal knowledge base tool can ship it as an MCP server inside a plugin, and all Claude Code users who have the plugin enabled will see the knowledge base tools in their tool registry.

code-review: The Parallel Agent Pattern

The code-review plugin is the reference implementation for parallel agent workflows. Its /code-review command spawns five agents simultaneously:

flowchart TD
    A([/code-review]) --> B[Coordinator Agent]
    B --> C[Security Reviewer<br/>sonnet]
    B --> D[Performance Reviewer<br/>sonnet]
    B --> E[Test Coverage Reviewer<br/>sonnet]
    B --> F[Code Style Reviewer<br/>sonnet]
    B --> G[Architecture Reviewer<br/>sonnet]
    C & D & E & F & G --> H[Synthesize Findings]
    H --> I([Confidence-scored Report])

Each agent returns a structured JSON payload with findings and a confidence score — how certain is the agent that each finding is a real issue, not a false positive. The coordinator synthesizes these into a unified report, weighting findings that multiple agents flagged more heavily.

The confidence scoring is the key innovation. A security finding that only the security reviewer caught gets a base confidence. A security finding that both the security reviewer and the architecture reviewer flagged independently gets boosted confidence. Findings below a configurable threshold are reported but visually de-emphasized.

hookify: The Hook Lifecycle

The hookify plugin ships four commands:

  • /hookify — analyze the current session's patterns and generate a hook
  • /hookify:list — show all active hooks across installed plugins
  • /hookify:edit — modify an existing hook
  • /hookify:delete — remove a hook

The core innovation in hookify is the pattern-to-hook pipeline. When you run /hookify, the agent reviews the current session's conversation history, identifies repeated behaviors (always formatting output as JSON, always checking for secrets before writing files, always running tests after code changes), and generates a hook that automates those behaviors going forward.

This is a plugin that creates hooks. The meta-level is intentional — hookify is how you graduate from manually instructing Claude to do something every session to having it happen automatically.

pr-review-toolkit: Specialization at Scale

Where code-review uses five generalist reviewers, pr-review-toolkit uses six specialists with explicit domain boundaries:

  1. diff-analyzer — structural analysis of what changed
  2. security-scanner — OWASP Top 10 pattern matching
  3. test-quality-reviewer — coverage, edge cases, mock usage
  4. documentation-reviewer — docstrings, README updates, API docs
  5. performance-analyzer — algorithmic complexity, N+1 queries, memory allocations
  6. breaking-change-detector — API contract changes, schema migrations

The breaking-change-detector is the one that gets the most attention in practice. It flags any change that could break downstream consumers of a library or API — changed function signatures, removed fields, altered error codes. In a monorepo with shared libraries, this agent alone justifies installing the plugin.

18.7 The plugin-dev Plugin: Building Plugins With a Plugin

There is a pleasant recursion in the plugin-dev plugin: it is a plugin whose purpose is to help you build plugins. It ships one command, /plugin-dev:create-plugin, and seven skills that command draws on:

  1. plugin-structure — directory layout, required files, optional directories
  2. manifest-authoring — plugin.json fields, versioning, author conventions
  3. command-writing — command markdown format, frontmatter, tool restrictions
  4. agent-design — agent definition structure, role scoping, output format contracts
  5. hook-patterns — event types, TypeScript hook structure, pattern matching
  6. skill-composition — when to use skills vs commands, include syntax
  7. mcp-integration — .mcp.json format, server declaration, tool registration

When you run /plugin-dev:create-plugin, the command gathers information about what you want to build through a structured interview, then draws on the relevant skills to generate a complete plugin scaffold — manifest, directory structure, starter files with inline documentation, and a README explaining how to extend each component.

The plugin-dev plugin is also how Anthropic communicates best practices. When the harness's plugin author guidelines change — new fields in plugin.json, new hook event types, deprecations — the plugin-dev plugin is updated alongside the harness release. Using it to scaffold new plugins means you start from current best practices, not from outdated tutorials.

18.8 Lab: Build a Complete Plugin

The lab builds a plugin called dep-guardian that audits dependencies, enforces a policy against known-bad packages, and hooks into every npm install to warn about newly introduced vulnerabilities. By the end of the lab, the plugin ships a command, an agent, a hook, a skill, and an MCP server.

Step 1: Directory Scaffold

mkdir -p dep-guardian/.claude-plugin
mkdir -p dep-guardian/commands
mkdir -p dep-guardian/agents
mkdir -p dep-guardian/skills
mkdir -p dep-guardian/hooks
mkdir -p dep-guardian/bin

Step 2: The Manifest

Write dep-guardian/.claude-plugin/plugin.json:

{
  "name": "dep-guardian",
  "description": "Dependency audit and policy enforcement with real-time install monitoring",
  "version": "1.0.0",
  "author": {
    "name": "Your Name",
    "email": "you@yourorg.com"
  }
}

Step 3: The Skill — Shared Audit Procedure

Skills are included by multiple commands and agents. Write the audit logic once in dep-guardian/skills/audit-procedure.md:

## Dependency Audit Procedure

Given a project directory, perform the following steps:

1. Detect the primary package manager by checking for:
   - `package.json` → npm/yarn/pnpm
   - `requirements.txt` or `pyproject.toml` → pip/uv
   - `Cargo.toml` → cargo
   - `go.mod` → go

2. Run the audit command for the detected package manager:
   - npm: `npm audit --json 2>/dev/null`
   - pip: `pip audit --format json 2>/dev/null`
   - cargo: `cargo audit --json 2>/dev/null`
   - go: `govulncheck -json ./... 2>/dev/null`

3. Parse the output. Extract findings with these fields:
   - package_name
   - installed_version
   - vulnerability_id (CVE or GHSA)
   - severity (CRITICAL, HIGH, MEDIUM, LOW)
   - fixed_in_version (null if no fix available)
   - description (one sentence)

4. Return findings sorted by severity descending, then by package name ascending.

If the audit tool is not available, return an error object:
`{ "error": "audit_tool_missing", "package_manager": "<detected>", "install_command": "<how to install the audit tool>" }`

Step 4: The Agent — Deep Vulnerability Analyst

The skill handles detection. The agent handles interpretation. Write dep-guardian/agents/vuln-analyst.md:

You are a vulnerability analyst specializing in software supply chain security.

You receive the output of a dependency audit as a JSON array of findings. Your task:

1. For each CRITICAL or HIGH finding:
   - Assess whether the vulnerable code path is actually reachable given how this project uses the package
   - Check whether the project version is constrained to a non-vulnerable range
   - Determine the upgrade path: direct upgrade, transitive dependency pin, or no fix available

2. For each package with a CRITICAL finding and no fix available:
   - Research alternative packages that provide equivalent functionality without the vulnerability
   - Provide a concrete migration recommendation with effort estimate (hours)

3. Produce a structured report with three sections:
   - IMMEDIATE ACTION (CRITICAL, fix available)
   - MONITOR (HIGH, fix available or CRITICAL without fix)
   - ACCEPTED RISK (MEDIUM/LOW, or false positives with justification)

Return the report as structured markdown with a summary table at the top.

Step 5: The Command — The User-Facing Entry Point

Write dep-guardian/commands/audit.md:

---
description: Audit project dependencies for vulnerabilities and policy violations
allowed-tools: Bash, Read, Write, Agent
---

You are running dep-guardian's full audit workflow.

!include skills/audit-procedure.md

After running the audit procedure:

1. Spawn the vulnerability analyst agent to interpret the findings:
   - subagent_type: "vuln-analyst"
   - Pass the raw audit JSON as the prompt input
   - model: "sonnet"

2. Check the findings against the policy file at `.dep-guardian/blocked-packages.json` if it exists.
   Any installed package appearing in the blocked list is a POLICY VIOLATION regardless of vulnerability status.

3. Write the final report to `dep-guardian-report.md`

4. If any CRITICAL findings exist, exit with a clear summary and the path to the full report.
   If no CRITICAL findings, print a one-line summary: "N findings (H high, M medium, L low). Report: dep-guardian-report.md"

The !include skills/audit-procedure.md directive pulls the skill content inline when the command is assembled. The command stays focused on orchestration; the skill carries the procedure detail.

Step 6: The Hook — Real-Time Install Monitoring

Write dep-guardian/hooks/PreToolUse.ts:

import type { HookContext } from "@anthropic/claude-code";

export async function hook(ctx: HookContext): Promise<void> {
  const { toolName, toolInput } = ctx;

  // Only intercept Bash tool calls
  if (toolName !== "Bash") return;

  const command = toolInput.command as string;

  // Detect npm/pip/cargo install commands
  const isInstall =
    /\bnpm\s+install\b/.test(command) ||
    /\bpip\s+install\b/.test(command) ||
    /\bcargo\s+add\b/.test(command) ||
    /\buv\s+add\b/.test(command);

  if (!isInstall) return;

  // Extract the package name(s) from the install command
  const npmMatch = command.match(/npm\s+install\s+([\w@/.-]+)/);
  const pipMatch = command.match(/pip\s+install\s+([\w-]+)/);
  const cargoMatch = command.match(/cargo\s+add\s+([\w-]+)/);
  const uvMatch = command.match(/uv\s+add\s+([\w-]+)/);

  const packageName =
    (npmMatch?.[1] ?? pipMatch?.[1] ?? cargoMatch?.[1] ?? uvMatch?.[1]);

  if (!packageName) return;

  // Append a security reminder to the tool context
  ctx.appendToToolResult(
    `\n\n[dep-guardian] Package installation detected: ${packageName}\n` +
    `After installation completes, consider running /audit to check for ` +
    `newly introduced vulnerabilities before committing.`
  );
}

This hook fires before every Bash tool call. It checks whether the command is a package install. If it is, it identifies the package name and appends a reminder to the tool result — not blocking the install, just making the reminder visible in the agent's context at the right moment.

Step 7: The MCP Server — Policy API

Write dep-guardian/.mcp.json:

{
  "mcpServers": {
    "dep-guardian-policy": {
      "command": "node",
      "args": ["./bin/policy-server.js"],
      "description": "Provides tools for reading and updating dep-guardian blocked package policies"
    }
  }
}

The MCP server at bin/policy-server.js exposes two tools:

// policy-server.js (MCP server stub)
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { readFileSync, writeFileSync } from "fs";
import { resolve } from "path";

const POLICY_PATH = resolve(process.cwd(), ".dep-guardian/blocked-packages.json");

const server = new Server({ name: "dep-guardian-policy", version: "1.0.0" }, {
  capabilities: { tools: {} }
});

server.setRequestHandler("tools/list", async () => ({
  tools: [
    {
      name: "get_blocked_packages",
      description: "List all packages blocked by dep-guardian policy",
      inputSchema: { type: "object", properties: {} }
    },
    {
      name: "block_package",
      description: "Add a package to the blocked list",
      inputSchema: {
        type: "object",
        properties: {
          name: { type: "string", description: "Package name to block" },
          reason: { type: "string", description: "Why this package is blocked" }
        },
        required: ["name", "reason"]
      }
    }
  ]
}));

server.setRequestHandler("tools/call", async (req) => {
  if (req.params.name === "get_blocked_packages") {
    try {
      const policy = JSON.parse(readFileSync(POLICY_PATH, "utf8"));
      return { content: [{ type: "text", text: JSON.stringify(policy, null, 2) }] };
    } catch {
      return { content: [{ type: "text", text: "[]" }] };
    }
  }

  if (req.params.name === "block_package") {
    const { name, reason } = req.params.arguments;
    let policy = [];
    try { policy = JSON.parse(readFileSync(POLICY_PATH, "utf8")); } catch {}
    policy.push({ name, reason, blockedAt: new Date().toISOString() });
    writeFileSync(POLICY_PATH, JSON.stringify(policy, null, 2));
    return { content: [{ type: "text", text: `Blocked ${name}: ${reason}` }] };
  }
});

const transport = new StdioServerTransport();
await server.connect(transport);

With this server active, Claude gains two new tools: get_blocked_packages (read the policy) and block_package (update the policy). When the /audit command finds a CRITICAL vulnerability in a package with no fix available, it can call block_package to add it to the policy — making the block automatic for future installs.

What You Have Built

The completed dep-guardian plugin has:

  • A skill (audit-procedure.md) that encodes audit logic once, reusable anywhere
  • An agent (vuln-analyst.md) with deep domain specialization in vulnerability interpretation
  • A command (audit.md) that orchestrates the skill, agent, and report generation
  • A hook (PreToolUse.ts) that fires automatically on every package install
  • An MCP server (policy-server.js) that extends Claude's tool surface with policy management

This is the full plugin capability surface in one coherent example. Each component earns its place: the skill avoids duplication, the agent handles reasoning-heavy interpretation without bloating the command, the hook is event-driven so users never have to remember to run it, and the MCP server turns policy management into a first-class tool rather than a file-editing exercise.

Distributing the Plugin

To distribute dep-guardian through your organization:

  1. Push the plugin directory to a GitHub repository — either the official marketplace (if you want public distribution) or your internal plugin repository.
  1. Add the repository to known_marketplaces.json in your managed settings:
{
  "your-org-plugins": {
    "source": { "source": "github", "repo": "yourorg/claude-plugins" },
    "installLocation": "/opt/claude/plugins/marketplaces/your-org-plugins"
  }
}
  1. Add dep-guardian@your-org-plugins to allowedChannelPlugins if you are using the allowlist policy.
  1. Users install with /plugin install dep-guardian.

The marketplace model means every developer in your organization gets the same plugin at the same version, with the same policy defaults. When you push a 1.1.0 with an improved hook pattern, users with auto-update enabled get it on their next session start. This is the plugin system's answer to the question of how you maintain consistent tooling across a large engineering organization without asking everyone to manually copy files.

The plugin architecture described in this chapter is the mechanism by which Claude Code evolves beyond what Anthropic ships. Your organization's specific workflows — your code standards, your security policies, your deployment procedures — become first-class capabilities, installable and shareable exactly like the official plugins. The directory structure is simple by design. The manifest is small by design. The distribution system is git-native by design. The complexity lives in what you put in the files, not in the files themselves.
