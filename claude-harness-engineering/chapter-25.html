Chapter 25: Harness Architecture Design

"Claude Code is not just a product you use — it is the answer to the question: what does a production-grade agentic harness actually look like? Part VI is about reading that answer, then writing your own."

The previous twenty-four chapters were about mastery. You learned every tool, dissected the control loop, built workflows, wrote hooks, published plugins, and managed context across million-token conversations. You are no longer a user of Claude Code. You are an engineer who understands its architecture at the implementation level.

That changes what you can build.

Part VI is about translation. You take everything you have observed in Claude Code and reconstruct it — deliberately, with your own design decisions, in your own language, for your own use case. This chapter gives you the blueprint. The sections that follow give you the implementation.

25.1 Core Components

Every agentic harness — regardless of implementation language, target model, or use case — requires the same five subsystems. They are not optional extras. Each one is a prerequisite for the others to work correctly. Build them in order.

graph TD
    A[User Input] --> B[Control Loop]
    B --> C[System Prompt Assembler]
    C --> D[Claude API]
    D -->|tool_use| E[Tool Registry]
    E --> F[Permission Layer]
    F -->|denied| G[tool_result: denied]
    F -->|allowed| H[Tool Executor]
    H --> I[Context Manager]
    I --> B
    D -->|end_turn| J[Final Response]
    B --> K[Session Store]
    K --> B
    G --> I

The Control Loop

The control loop is the harness's main thread of execution. It sits above everything else. Its job is exactly one thing: keep calling the Claude API until stop_reason is "end_turn".

while true:
    response = call_api(conversation_history)
    if response.stop_reason == "end_turn":
        return response.content
    for each tool_use block in response:
        result = execute_tool(tool_use)
        append tool_result to conversation_history

That is the whole loop. The complexity is in what execute_tool hides: permission evaluation, the actual execution, error handling, and appending the result to the conversation in the exact format the API requires. The loop itself is simple by design — it needs to be, because you will add retry logic, context compaction, and session checkpointing around it.

Claude Code's control loop handles parallelism: when a response contains multiple tool_use blocks, Claude Code executes them concurrently and collects all results before making the next API call. Your initial harness can execute them sequentially. Parallelize after you have the basic loop working.

The Tool Registry

The tool registry is a dictionary mapping tool names to their definitions. Each entry contains three things:

  1. The schema — JSON Schema that describes the tool's input parameters. This is what you send to the Claude API in the tools array. Claude uses it to understand what arguments to provide.
  2. The handler — a function that receives the validated input and returns a result.
  3. The permission spec — metadata the permission layer uses to decide whether to allow this call without prompting.

The registry's secondary responsibility is managing what appears in the system prompt. Not all tools need to be visible to the model at all times. Claude Code's deferred-loading pattern — keeping only 6 tools in the system prompt and loading the rest on demand — reduces prompt token cost by 30-40% on typical sessions. Your harness can start with all tools always-loaded and add deferred loading when you have token cost data to justify the complexity.

The Permission Layer

The permission layer intercepts every tool call before it reaches the executor. It answers one question: should this execution happen now, ask the user, or be blocked entirely?

The permission layer's position in the architecture matters. It sits between the tool registry and the tool executor. The model has already requested the tool. Your executor has already validated the input schema. The permission layer is the last gate before action.

Claude Code implements this with a rule engine that evaluates calls against an ordered list of allow/deny patterns with glob matching — Bash(git *) matches any git command, Edit(/src/**) matches any file under /src. The first rule that matches wins. If nothing matches, the mode determines the fallback: auto mode defaults to allow for low-risk operations, default mode defaults to ask.

For a minimal harness, a hard-coded allowlist of tool names is sufficient. For a production harness serving multiple users or running unattended, you need the full rule engine described in Chapter 27.

The Context Manager

The context manager owns the conversation history. Its responsibilities:

  • Accumulation: append each API response (both model content and tool results) to the history array.
  • Deduplication: track which files have been read. When Read is called on a file that hasn't changed since the last read, return a cached result rather than the full content. Claude Code implements this as a session-scoped map of {file_path → content_hash}.
  • Compaction: when the conversation approaches the model's context limit, summarize the older turns and replace them with the summary. The summary plus the most recent turns form the new history. Claude Code does this automatically; your harness will need to implement it explicitly.
  • Prompt cache awareness: structure the system prompt so its static sections appear first (they will be cache-hit after the first call) and dynamic sections appear last. This has significant cost impact at scale — see Chapter 30.

The Session Store

The session store is persistence. It ensures that a crashed harness can resume, that you can replay what happened, and that long-running autonomous agents survive process restarts.

Claude Code uses JSONL (JSON Lines) as its transcript format: each turn is one JSON object on its own line, appended to a file at ~/.claude/sessions/<session-id>.jsonl. JSONL is append-only by nature — you never rewrite the file, you only append to it. This makes it crash-safe: a crash leaves a valid-up-to-the-crash transcript, not a corrupt file.

The session store should also persist the context manager's file-read cache, the current working directory, and any harness-specific state your application needs to resume from.

25.2 The tool_use Protocol

The Anthropic Messages API implements a specific interaction protocol for tool use. Understanding it precisely is the foundation of every harness. Get it wrong and you get cryptic API errors or infinite loops.

Step 1: Send Tools with Your Request

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=8096,
    system=system_prompt,
    tools=[
        {
            "name": "read_file",
            "description": "Read a file from the filesystem.",
            "input_schema": {
                "type": "object",
                "properties": {
                    "path": {"type": "string", "description": "Absolute file path"}
                },
                "required": ["path"]
            }
        }
    ],
    messages=conversation_history
)

The tools array tells Claude which tools exist and what their schemas are. Claude will only call tools you declare here. Undeclared tools produce hallucinated names you must detect and reject.

Step 2: Detect tool_use Stop Reason

if response.stop_reason == "tool_use":
    # Model wants to call one or more tools
    tool_calls = [
        block for block in response.content
        if block.type == "tool_use"
    ]

stop_reason has two values you care about:

stop_reasonMeaning
"tool_use"One or more tool_use blocks in response.content; harness must execute and continue
"end_turn"Model is finished; return final text to user

There is a third value — "max_tokens" — which means you hit max_tokens mid-response. Handle it as an error: increment max_tokens, or summarize history and retry.

Step 3: Append the Assistant Turn

Before executing tools, append the full assistant response to your conversation history:

conversation_history.append({
    "role": "assistant",
    "content": response.content  # list of content blocks (text + tool_use)
})

This is a mistake that trips up first-time harness builders. The assistant turn must be appended before you construct the tool_result turn. The API requires them in the correct alternating sequence: user → assistant → user → assistant → ....

Step 4: Execute Each Tool and Collect Results

tool_results = []
for tool_call in tool_calls:
    result = execute_tool(tool_call.name, tool_call.input)
    tool_results.append({
        "type": "tool_result",
        "tool_use_id": tool_call.id,  # must match the tool_use block's id
        "content": result
    })

The tool_use_id is the critical link. Claude correlates each tool_result with the tool_use block that prompted it using this ID. If you mismatch IDs — or omit results for some calls — the API rejects the request with a validation error.

Step 5: Append the Tool Results Turn

conversation_history.append({
    "role": "user",
    "content": tool_results
})

All tool results for a single round go into a single user turn, as a list. Do not create one user turn per result.

Step 6: Loop Back

Call the API again with the updated conversation history. Repeat until stop_reason == "end_turn".

Here is the complete protocol as a sequence diagram:

sequenceDiagram
    participant H as Harness
    participant A as Claude API
    participant T as Tool Executor

    H->>A: messages=[...], tools=[read_file, bash, ...]
    A-->>H: stop_reason="tool_use", content=[tool_use{id=1, name="read_file"}]
    H->>H: append assistant turn to history
    H->>T: execute read_file(path="/src/main.py")
    T-->>H: "def main(): ..."
    H->>H: build tool_results=[{tool_use_id=1, content="..."}]
    H->>H: append user turn (tool_results) to history
    H->>A: messages=[..., assistant turn, user turn]
    A-->>H: stop_reason="end_turn", content=[text "Here is the analysis..."]
    H-->>H: return final text

The Multi-Tool Round

Claude will often emit multiple tool_use blocks in a single response — especially when it can parallelize work ("read these three files simultaneously"). The protocol requires you to provide a tool_result for every tool_use block in that response. If Claude asked for three files, you must provide three results before the next API call. There is no partial fulfillment.

This constraint drives the parallel execution pattern: receive N tool calls, execute them concurrently, collect all N results, then proceed. Sequential execution is valid but slower.

25.3 Choosing Your Runtime

Claude Code chose Rust compiled to a native binary. That choice optimized for startup time, memory efficiency, and the ability to ship a self-contained executable to ten platform targets. These are real advantages — but they are not your advantages unless your use case matches.

Here are the honest tradeoffs for the four most common harness runtimes:

Use Node.js if you are building something that will integrate tightly with the Claude Code ecosystem — plugins, MCP servers that Claude Code consumes, tools that parse or generate JSONL transcripts. The official Anthropic TypeScript SDK has the richest typing, and you can import types directly from @anthropic-ai/sdk.

Use Python for anything involving machine learning, data pipelines, or rapid prototyping. The anthropic Python SDK is official and well-maintained. The harness lab in this chapter uses Python because it is the most accessible starting point for the broadest audience, and because the explicit types make the protocol easier to follow.

Use Rust if you are building a long-running daemon where memory predictability and startup speed matter — think a CI integration that spawns every commit, or an autonomous monitoring agent running 24/7. The tradeoff is development speed: expect 3-5x longer implementation time than Python.

Use Go if you are building harness infrastructure at platform scale — a service that manages agent sessions for multiple teams, a gateway that routes requests to different model backends, or a harness embedded in a larger Go service. Go's concurrency model maps well to the parallel tool-execution pattern.

The lab in section 25.7 uses Python. Chapters 26-30 show the same patterns with enough generality that they translate to any of these runtimes. Pick the language you will maintain.

25.4 State Management

A harness has four kinds of state. Each has different lifecycle, persistence requirements, and failure modes.

graph LR
    subgraph In-Memory
        A[Conversation History]
        B[File Read Cache]
        C[Tool Registry]
    end
    subgraph Persisted
        D[JSONL Transcript]
        E[Session Checkpoint]
        F[CWD State]
    end
    A -->|append-only| D
    B -->|on checkpoint| E
    F -->|on change| E

Conversation History

The conversation history is the messages array you pass to each API call. It grows with every turn. Its structure:

[
    {"role": "user", "content": "Fix the bug in auth.py"},
    {
        "role": "assistant",
        "content": [
            {"type": "text", "text": "Let me read the file first."},
            {"type": "tool_use", "id": "tu_01abc", "name": "read_file",
             "input": {"path": "/src/auth.py"}}
        ]
    },
    {
        "role": "user",
        "content": [
            {"type": "tool_result", "tool_use_id": "tu_01abc",
             "content": "def authenticate(user, pwd):\n    ..."}
        ]
    },
    # ... and so on
]

The history must follow the strict alternating user → assistant pattern. The API rejects any request where two consecutive turns have the same role.

Compaction is the mechanism for keeping history within the context window. When the total token count approaches the model's limit, you summarize the older turns. Claude Code does this automatically; your harness detects the context_window_exceeded error (or preempts it by counting tokens before the call) and compacts. The summarization prompt is a call to the model itself: "Summarize the following conversation history, preserving all decisions made, files modified, and important context." The summary replaces the older turns; the most recent N turns remain verbatim.

Track your token counts. The usage field in every API response gives you input_tokens and output_tokens. Accumulate them across turns. When input tokens approach 80% of your context limit, trigger compaction.

File Read Cache

Every file the harness reads should be tracked in a session-scoped dictionary:

file_cache: dict[str, tuple[str, float]] = {}
# path → (content_hash, timestamp)

When read_file is called, check the cache first. If the file's mtime has not changed since the last read, return a cached indicator ("[file unchanged since last read]") rather than the full content. This reduces token consumption significantly in long sessions where the model re-reads files it has already seen.

Claude Code returns the literal string "file_unchanged" as the source field in its Read response when this optimization fires. Your harness can do the same.

Working Directory State

The Bash tool has a peculiar constraint: shell state (environment variables, cd commands) does not persist between invocations. But the current working directory must persist. Claude Code implements this by maintaining a cwd variable in the harness, passing it as --workdir to each shell invocation, and updating it when a cd command changes the directory.

# After each Bash execution, detect CWD changes
cwd = execute_and_track_cwd(command, current_cwd)

The simplest implementation: wrap every command in (cd "$CWD" && YOUR_COMMAND && pwd) and capture the final printed directory. If the command ran cd /somewhere, the printed directory reflects that.

JSONL Transcripts

Every turn in the conversation should be written to a JSONL file before the next API call:

def append_to_transcript(session_id: str, entry: dict) -> None:
    path = Path(f"~/.harness/sessions/{session_id}.jsonl").expanduser()
    with path.open("a") as f:
        f.write(json.dumps(entry) + "\n")

Append before executing, not after. If the process crashes during tool execution, the transcript records what was attempted. On resume, you can detect the incomplete turn and decide whether to retry or skip it.

JSONL is the right format for four reasons: it is human-readable, each line is a valid JSON object (unlike a full JSON array that requires the entire file to be valid), new entries are a single write syscall, and partial files are recoverable.

Store at minimum: the session ID, timestamp, turn role (user/assistant), content, and token usage.

25.5 Error Recovery

Production harnesses fail. The model hallucinate tool names. The API returns 529 (overloaded). A tool times out. The context window fills up mid-task. Your error recovery strategy determines whether these failures are catastrophic or recoverable.

API Failure Retry

The Anthropic API is reliable but not infallible. Network hiccups, temporary overload (HTTP 529), and rate limiting (HTTP 429) happen. Claude Code uses CLAUDE_CODE_MAX_RETRIES=5 as its ceiling.

from anthropic import Anthropic, APIStatusError, APIConnectionError
import time

def call_api_with_retry(
    client: Anthropic,
    *,
    max_retries: int = 5,
    **kwargs
) -> anthropic.types.Message:
    for attempt in range(max_retries):
        try:
            return client.messages.create(**kwargs)
        except APIStatusError as e:
            if e.status_code in (429, 529) and attempt < max_retries - 1:
                wait = 2 ** attempt  # exponential backoff: 1s, 2s, 4s, 8s, 16s
                time.sleep(wait)
                continue
            raise
        except APIConnectionError:
            if attempt < max_retries - 1:
                time.sleep(2 ** attempt)
                continue
            raise
    raise RuntimeError("Max retries exceeded")

Exponential backoff is the correct strategy for rate limits and server overload. Do not use a fixed sleep — it wastes time on short blips and is too short for genuine overload events.

Tool Execution Errors

When a tool fails — file not found, command exits nonzero, network timeout — the harness must still return a tool_result. The model needs to know what happened so it can adjust. Do not silently skip failed results.

def safe_execute(tool_name: str, tool_input: dict) -> str:
    try:
        return tool_registry[tool_name](tool_input)
    except FileNotFoundError as e:
        return f"Error: file not found: {e.filename}"
    except PermissionError as e:
        return f"Error: permission denied: {e.filename}"
    except subprocess.TimeoutExpired:
        return "Error: command timed out after 30 seconds"
    except Exception as e:
        return f"Error: {type(e).__name__}: {e}"

The error message should be informative enough for the model to self-correct. "Error: file not found: /src/util.py" tells the model to check the path. "Error: something went wrong" does not.

Unknown Tool Calls

The model occasionally hallucinates tool names, especially if your tool descriptions are ambiguous or the model is pushing at the edge of its capabilities. These calls must be handled explicitly:

if tool_call.name not in tool_registry:
    result = (
        f"Error: tool '{tool_call.name}' does not exist. "
        f"Available tools: {', '.join(tool_registry.keys())}"
    )

Returning the available tool list helps the model recover by calling the correct tool in the next turn.

Checkpoint and Resume

For long-running tasks — migrations, audits, bulk processing — you need the ability to resume from a checkpoint rather than restart from zero.

The checkpoint file captures everything the harness needs to reconstruct its state:

@dataclass
class Checkpoint:
    session_id: str
    conversation_history: list[dict]
    file_cache: dict[str, tuple[str, float]]
    cwd: str
    turn_count: int
    token_usage: dict[str, int]
    timestamp: float

def save_checkpoint(checkpoint: Checkpoint, path: Path) -> None:
    path.write_text(json.dumps(asdict(checkpoint), indent=2))

def load_checkpoint(path: Path) -> Checkpoint:
    return Checkpoint(**json.loads(path.read_text()))

Write the checkpoint after each completed turn (tool results appended and persisted to transcript), not during execution. A checkpoint written during tool execution may capture a partial state that is harder to recover from than a clean restart.

Graceful Degradation

Some failures should not stop the harness; they should narrow what it can do. A file permission error on one file should not abort a 200-file analysis. A failing web fetch should produce an informative tool_result and let the model continue with the files it could read.

Design each tool executor to return an error string rather than raising an exception whenever the failure is expected and non-catastrophic. Reserve exceptions for truly unexpected failures (memory error, disk full, API authentication failure) where continuing would produce garbage results.

25.6 The System Prompt

The system prompt is the harness's primary lever over model behavior. Unlike conversation turns, which accumulate and eventually get compacted, the system prompt is present in every API call. It is the constant context that defines who the model is, what it can do, and how it should behave.

Claude Code assembles its system prompt dynamically on every call. The assembly has two categories of content with very different characteristics:

Static Sections

Static sections are assembled once and rarely change during a session. They are the cache-friendly part of the system prompt. Because the Anthropic API's prompt cache operates on a 5-minute TTL and caches based on content, stable sections hit the cache on every call after the first, dramatically reducing input token costs.

Static sections include:

Base behavioral instructions. Who the model is, how it should communicate, what its overall goal is. For a coding assistant, this is "You are a senior engineer helping the user with their codebase. You write correct, idiomatic code."

Tool descriptions. The names and descriptions of tools the model can use. If you are implementing deferred loading (Chapter 26), the static section contains only always-loaded tool descriptions; the rest are injected on demand.

Rules and constraints. Coding standards, security policies, behavioral rules. Claude Code injects CLAUDE.md content and .claude/rules/*.md here.

Format instructions. How the model should structure its responses — concise vs verbose, when to use code blocks, how to reference files.

Write static sections first in the system prompt. The Anthropic cache caches the longest stable prefix. Any dynamic content appearing before static content defeats the cache.

Dynamic Sections

Dynamic sections change turn-to-turn or session-to-session. They are appended after all static content.

Git status. The current branch, staged changes, and recent commits. Claude Code injects this so the model always knows the repository context without needing to call git status at the start of every session. A minimal implementation:

import subprocess

def get_git_context(cwd: str) -> str:
    try:
        branch = subprocess.check_output(
            ["git", "branch", "--show-current"], cwd=cwd, text=True
        ).strip()
        status = subprocess.check_output(
            ["git", "status", "--short"], cwd=cwd, text=True
        ).strip()
        log = subprocess.check_output(
            ["git", "log", "--oneline", "-5"], cwd=cwd, text=True
        ).strip()
        return f"## Git Context\nBranch: {branch}\nStatus:\n{status}\nRecent commits:\n{log}"
    except subprocess.CalledProcessError:
        return ""

Environment information. Current working directory, OS, shell, relevant environment variables. This lets the model write correct paths and commands without probing the environment via tool calls.

Memory and prior context. If your harness has a memory system, inject the relevant memories here — the user's preferences, important prior decisions, domain context. Keep this section bounded; injecting the entire memory corpus defeats the purpose of having a memory system.

Session-specific state. Any task-specific context that changes between sessions — the issue number being worked on, the feature branch, the files already modified.

The Assembly Function

def assemble_system_prompt(
    cwd: str,
    memory_context: str = "",
    task_context: str = ""
) -> str:
    sections = []

    # Static: always-present, cache-friendly
    sections.append(BASE_INSTRUCTIONS)
    sections.append(TOOL_DESCRIPTIONS)
    sections.append(CODING_RULES)

    # Dynamic: session/task-specific, appended last
    git_ctx = get_git_context(cwd)
    if git_ctx:
        sections.append(git_ctx)

    env_info = (
        f"## Environment\n"
        f"Working directory: {cwd}\n"
        f"OS: {platform.system()} {platform.release()}\n"
        f"Date: {datetime.now().strftime('%Y-%m-%d')}"
    )
    sections.append(env_info)

    if memory_context:
        sections.append(f"## Memory\n{memory_context}")

    if task_context:
        sections.append(f"## Current Task\n{task_context}")

    return "\n\n".join(sections)

Place dynamic sections after static ones, not before. Mixing them reduces cache hit rate.

session.py — JSONL Persistence

from __future__ import annotations

import json
import uuid
from dataclasses import dataclass, field, asdict
from pathlib import Path
from typing import Any


SESSIONS_DIR = Path.home() / ".harness" / "sessions"


@dataclass
class Session:
    session_id: str = field(default_factory=lambda: str(uuid.uuid4()))
    conversation: list[dict[str, Any]] = field(default_factory=list)
    file_cache: dict[str, float] = field(default_factory=dict)  # path → mtime
    cwd: str = field(default_factory=lambda: str(Path.cwd()))
    turn_count: int = 0

    @property
    def transcript_path(self) -> Path:
        SESSIONS_DIR.mkdir(parents=True, exist_ok=True)
        return SESSIONS_DIR / f"{self.session_id}.jsonl"

    def append_turn(self, role: str, content: Any) -> None:
        entry = {"role": role, "content": content}
        self.conversation.append(entry)
        with self.transcript_path.open("a") as f:
            f.write(json.dumps({"turn": self.turn_count, **entry}) + "\n")
        self.turn_count += 1

    def checkpoint(self) -> None:
        path = SESSIONS_DIR / f"{self.session_id}.checkpoint.json"
        path.write_text(json.dumps(asdict(self), indent=2))

    @classmethod
    def load(cls, session_id: str) -> Session:
        path = SESSIONS_DIR / f"{session_id}.checkpoint.json"
        data = json.loads(path.read_text())
        return cls(**data)

tools/read_file.py

from __future__ import annotations

from pathlib import Path

SCHEMA = {
    "name": "read_file",
    "description": (
        "Read the contents of a file. Returns the file content as a string. "
        "Use this to inspect source code, configuration files, or any text file."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "path": {
                "type": "string",
                "description": "Absolute path to the file to read."
            },
            "offset": {
                "type": "integer",
                "description": "Line number to start reading from (1-indexed). Optional."
            },
            "limit": {
                "type": "integer",
                "description": "Maximum number of lines to read. Optional."
            }
        },
        "required": ["path"]
    }
}


def execute(tool_input: dict, session) -> str:
    path = Path(tool_input["path"])

    if not path.exists():
        return f"Error: file not found: {path}"
    if not path.is_file():
        return f"Error: not a file: {path}"

    try:
        mtime = path.stat().st_mtime
        if session.file_cache.get(str(path)) == mtime:
            return f"[file unchanged since last read: {path}]"

        lines = path.read_text(errors="replace").splitlines(keepends=True)

        offset = tool_input.get("offset", 1) - 1  # convert to 0-indexed
        limit = tool_input.get("limit", len(lines))
        selected = lines[offset: offset + limit]

        session.file_cache[str(path)] = mtime
        return "".join(selected)

    except PermissionError:
        return f"Error: permission denied: {path}"
    except OSError as e:
        return f"Error: {e}"

from pathlib import Path

SCHEMA = {
    "name": "write_file",
    "description": (
        "Write content to a file. Creates the file if it does not exist, "
        "overwrites it if it does. Parent directories are created automatically."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "path": {
                "type": "string",
                "description": "Absolute path to the file to write."
            },
            "content": {
                "type": "string",
                "description": "Content to write to the file."
            }
        },
        "required": ["path", "content"]
    }
}


def execute(tool_input: dict, session) -> str:
    path = Path(tool_input["path"])
    content = tool_input["content"]

    try:
        path.parent.mkdir(parents=True, exist_ok=True)
        path.write_text(content)
        # Invalidate cache entry so next read returns fresh content
        session.file_cache.pop(str(path), None)
        return f"Wrote {len(content)} bytes to {path}"
    except PermissionError:
        return f"Error: permission denied: {path}"
    except OSError as e:
        return f"Error: {e}"

from __future__ import annotations

import subprocess

SCHEMA = {
    "name": "bash",
    "description": (
        "Execute a shell command. Returns stdout and stderr combined. "
        "The working directory is maintained across calls. "
        "Do not run interactive commands."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "command": {
                "type": "string",
                "description": "The shell command to execute."
            },
            "timeout": {
                "type": "integer",
                "description": "Timeout in seconds. Default: 30."
            }
        },
        "required": ["command"]
    }
}

# Simple allowlist — expand in Chapter 27
BLOCKED_PATTERNS = ["rm -rf /", ":(){ :|:& };:", "dd if=/dev/zero"]


def execute(tool_input: dict, session) -> str:
    command = tool_input["command"]
    timeout = tool_input.get("timeout", 30)

    # Minimal safety check
    for pattern in BLOCKED_PATTERNS:
        if pattern in command:
            return f"Error: command blocked by safety policy: {pattern!r}"

    try:
        result = subprocess.run(
            command,
            shell=True,
            capture_output=True,
            text=True,
            timeout=timeout,
            cwd=session.cwd
        )
        output = result.stdout + result.stderr
        if result.returncode != 0:
            output += f"\n[exit code: {result.returncode}]"
        return output or "[no output]"

    except subprocess.TimeoutExpired:
        return f"Error: command timed out after {timeout}s"
    except Exception as e:
        return f"Error: {e}"

prompt.py — System Prompt Assembly

from __future__ import annotations

import platform
import subprocess
from datetime import datetime

BASE_INSTRUCTIONS = """\
You are a software engineering assistant. You help engineers read, understand, \
and modify code. You write correct, idiomatic code. You explain your reasoning.
When you need to explore the codebase, read files first before making changes.
Always verify your changes by reading back modified files."""

TOOL_DESCRIPTIONS = """\
You have access to three tools:
- read_file: read any file by absolute path
- write_file: create or overwrite a file
- bash: execute shell commands in the current working directory"""


def get_git_context(cwd: str) -> str:
    try:
        branch = subprocess.check_output(
            ["git", "branch", "--show-current"],
            cwd=cwd, text=True, stderr=subprocess.DEVNULL
        ).strip()
        status = subprocess.check_output(
            ["git", "status", "--short"],
            cwd=cwd, text=True, stderr=subprocess.DEVNULL
        ).strip()
        return f"## Repository\nBranch: {branch}\nUnstaged changes:\n{status or '(none)'}"
    except (subprocess.CalledProcessError, FileNotFoundError):
        return ""


def assemble(cwd: str) -> str:
    sections = [BASE_INSTRUCTIONS, TOOL_DESCRIPTIONS]

    git_ctx = get_git_context(cwd)
    if git_ctx:
        sections.append(git_ctx)

    sections.append(
        f"## Environment\n"
        f"Working directory: {cwd}\n"
        f"OS: {platform.system()} {platform.release()}\n"
        f"Date: {datetime.now().strftime('%Y-%m-%d %H:%M')}"
    )

    return "\n\n".join(sections)

harness.py — The Control Loop

from __future__ import annotations

import sys
import time
import anthropic
from pathlib import Path

from session import Session
from prompt import assemble
import tools.read_file as read_file_tool
import tools.write_file as write_file_tool
import tools.bash as bash_tool

MODEL = "claude-sonnet-4-6"
MAX_TOKENS = 8096
MAX_RETRIES = 5

TOOL_MODULES = {
    "read_file": read_file_tool,
    "write_file": write_file_tool,
    "bash": bash_tool,
}

TOOL_SCHEMAS = [mod.SCHEMA for mod in TOOL_MODULES.values()]


def call_api(
    client: anthropic.Anthropic,
    session: Session,
    system_prompt: str,
) -> anthropic.types.Message:
    for attempt in range(MAX_RETRIES):
        try:
            return client.messages.create(
                model=MODEL,
                max_tokens=MAX_TOKENS,
                system=system_prompt,
                tools=TOOL_SCHEMAS,
                messages=session.conversation,
            )
        except anthropic.APIStatusError as e:
            if e.status_code in (429, 529) and attempt < MAX_RETRIES - 1:
                wait = 2 ** attempt
                print(f"[harness] API {e.status_code}, retrying in {wait}s...",
                      file=sys.stderr)
                time.sleep(wait)
                continue
            raise
        except anthropic.APIConnectionError:
            if attempt < MAX_RETRIES - 1:
                time.sleep(2 ** attempt)
                continue
            raise
    raise RuntimeError("Max retries exceeded")


def execute_tool(tool_name: str, tool_input: dict, session: Session) -> str:
    if tool_name not in TOOL_MODULES:
        available = ", ".join(TOOL_MODULES.keys())
        return (
            f"Error: tool '{tool_name}' does not exist. "
            f"Available tools: {available}"
        )
    return TOOL_MODULES[tool_name].execute(tool_input, session)


def run_turn(
    client: anthropic.Anthropic,
    session: Session,
    user_message: str,
) -> str:
    # Append the user's message
    session.append_turn("user", user_message)

    system_prompt = assemble(session.cwd)

    while True:
        response = call_api(client, session, system_prompt)

        # Append the assistant's full response (may contain text + tool_use blocks)
        session.append_turn("assistant", [b.model_dump() for b in response.content])

        if response.stop_reason == "end_turn":
            # Extract and return the final text
            text_blocks = [
                b.text for b in response.content
                if b.type == "text"
            ]
            final_text = "\n".join(text_blocks)
            session.checkpoint()
            return final_text

        if response.stop_reason == "tool_use":
            tool_calls = [b for b in response.content if b.type == "tool_use"]
            tool_results = []

            for tool_call in tool_calls:
                print(f"[harness] {tool_call.name}({tool_call.input})",
                      file=sys.stderr)
                result = execute_tool(tool_call.name, tool_call.input, session)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": tool_call.id,
                    "content": result,
                })

            # All results go in a single user turn
            session.append_turn("user", tool_results)
            continue

        # Unexpected stop_reason
        raise RuntimeError(f"Unexpected stop_reason: {response.stop_reason!r}")


def main() -> None:
    client = anthropic.Anthropic()
    session = Session()

    print(f"[harness] session {session.session_id}")
    print(f"[harness] transcript: {session.transcript_path}")
    print("Ready. Type your prompt (empty line to quit).\n")

    while True:
        try:
            lines = []
            while True:
                line = input("> " if not lines else "  ")
                if not line and lines:
                    break
                if line:
                    lines.append(line)
            if not lines:
                break
            prompt = "\n".join(lines)
        except EOFError:
            break

        try:
            result = run_turn(client, session, prompt)
            print(f"\n{result}\n")
        except KeyboardInterrupt:
            print("\n[interrupted]")
            session.checkpoint()
            break
        except Exception as e:
            print(f"\n[error] {e}", file=sys.stderr)
            session.checkpoint()
            raise


if __name__ == "__main__":
    main()

Chapter Summary

The architecture of an agentic harness is stable. Five components — control loop, tool registry, permission layer, context manager, session store — appear in every production implementation. The tool_use protocol is the API contract that ties them together: send schemas, detect stop_reason, append assistant turn, collect all results into a single user turn, loop.

The runtime choice matters less than getting the architecture right. Python for prototypes, Node for ecosystem integration, Rust or Go for production infrastructure.

State management has four layers: the conversation history (the messages array), the file read cache (session-scoped deduplication), the working directory (the Bash tool's persistent context), and the JSONL transcript (append-only crash-safe persistence).

Error recovery is not optional. Every tool executor should return an error string on expected failures, not raise exceptions. API retries need exponential backoff against a five-attempt ceiling. Long-running tasks need checkpoint/resume.

The system prompt is the constant context frame. Static sections first (cache-friendly), dynamic sections last (git status, environment, memory). The assembly function runs before every API call.

The lab produced a working skeleton. It is not production-ready — but it is correct. You can trace a full turn through it, read the transcript, and watch what the model does when it has three tools and a real codebase in front of it. That experience is the best preparation for Chapter 26.
