Chapter 15: Monitor Tool — Event-Driven Watching

"A cron job asks what happened. A monitor is there when it happens."

15.1 Monitor Parameters

Every tool in the harness catalog is synchronous except for a few that return a taskId and continue working in the background. Monitor is the most important member of that family. It connects the model to a live stream of events — log lines, CI state changes, WebSocket frames — and delivers each event to the agent as it arrives, without polling.

The full interface:

export interface MonitorInput {
  description: string;     // human-readable label shown in notifications
  timeout_ms: number;      // max 3600000ms (1 hour), ignored when persistent: true
  persistent: boolean;     // run for session lifetime, stop with TaskStop
  command?: string;        // shell command — each stdout line is one event
  ws?: {                   // WebSocket — each text frame is one event
    url: string;
    protocols?: string[];
  };
}

export interface MonitorOutput {
  taskId: string;          // pass to TaskStop to end the monitor
  timeoutMs: number;       // 0 when persistent
  persistent?: boolean;
}

Four parameters do all the work. Understanding each precisely is what separates monitors that are reliable infrastructure from monitors that silently stall.

description

A free-form string. It is not cosmetic — the harness surfaces it in the activity UI, in push notifications, and in audit logs. A description like "watching GitHub Actions for main branch failures" means that when the model is doing three other things simultaneously and an event fires, the notification carries enough context for a human to understand what triggered it without reading the conversation.

Write descriptions as if you were labeling a process in ps aux. Short, specific, unambiguous. "monitor" is wrong. "CI monitor: main branch, failure alerts" is right.

timeout_ms

The maximum duration the monitor will run, in milliseconds. The ceiling is 3,600,000 — exactly one hour. Requesting a longer timeout is not an error in all implementations but the harness clamps at the one-hour maximum, so you should not rely on anything beyond that.

When persistent: true, this field is ignored entirely. The harness does not start a timeout timer for persistent monitors. You can pass any value and it will have no effect.

For non-persistent monitors, the timeout is wall-clock time from when the monitor starts. If you need a monitor to run for 45 minutes, pass timeout_ms: 2700000. When the timer expires, the monitor stops as cleanly as it would if the process exited or the socket closed.

persistent

When false (or omitted), the monitor runs until the timeout, the command exits, or the socket closes — whichever comes first.

When true, the timeout is ignored and the monitor runs until you call TaskStop(taskId) or the session ends. This is the correct mode for daemon-like watchers: log tailing, queue consumers, long-lived WebSocket subscriptions. The harness records the taskId in the session's active task list, and when the session terminates the harness sends a stop signal to all persistent monitors before it exits.

The practical rule: use persistent: true for anything you would run with nohup or as a systemd service. Use timeout_ms for bounded observation windows — watching a deploy for up to 20 minutes, monitoring a test run for up to 10 minutes.

command and ws

You must provide exactly one of these. Providing both is an error. Providing neither is an error.

command takes a shell string identical in syntax to the Bash tool. The command runs in a subprocess; every line written to stdout becomes an event delivered to the agent. Stderr is not captured as events — it goes to the harness log.

ws takes an object with a required url and an optional protocols array. The protocols array maps directly to the WebSocket subprotocol negotiation headers. If the server requires a specific subprotocol (common in streaming APIs and message brokers), list it here.

15.2 Command Mode

Command mode is the workhorse. You give it a shell command and the harness runs it in a subprocess. Every line the command writes to stdout is delivered to the agent as a discrete event.

How the process model works

sequenceDiagram
    participant A as Agent
    participant H as Harness
    participant P as Subprocess

    A->>H: Monitor(command: "tail -f app.log", persistent: true)
    H-->>A: MonitorOutput { taskId: "mon_a1b2" }
    H->>P: fork subprocess
    P-->>H: stdout line: "[INFO] server started on :8080"
    H-->>A: event delivered
    P-->>H: stdout line: "[ERROR] database connection refused"
    H-->>A: event delivered
    A->>A: react — trigger alert, open connection, etc.
    A->>H: TaskStop("mon_a1b2")
    H->>P: SIGTERM
    P-->>H: process exit

The monitor tool call returns immediately with a MonitorOutput. The agent does not block. From that moment forward, the harness runs the subprocess and routes each line to the agent as it appears on stdout. The agent can do other things between events — call other tools, respond to the user, update state.

When the subprocess exits for any reason — normal exit, signal, crash — the monitor ends. The harness delivers no more events from that monitor. If you need the monitor to survive command failures, the command itself must handle restarts:

# wrong — monitor ends if script exits non-zero
gh run watch 12345678

# right — the shell loop restarts on failure
while true; do
  gh run list --limit 5 --json status,conclusion,name 2>/dev/null
  sleep 30
done

The harness runs your command through /bin/sh -c "your command". This means shell built-ins, pipes, here-docs, and variable expansion all work. A command like tail -f /var/log/app.log | grep --line-buffered "ERROR" is valid and useful — the grep filter means only error lines become events.

Line buffering matters

The subprocess must write complete lines to stdout for events to arrive at expected intervals. Programs that use block buffering (the default for most commands when stdout is not a terminal) will buffer output internally and deliver it in unpredictable bursts rather than line by line.

To force line buffering:

# Python: use -u flag or set PYTHONUNBUFFERED
PYTHONUNBUFFERED=1 python monitor_script.py

# GNU commands: stdbuf
stdbuf -oL tail -f app.log | stdbuf -oL grep "ERROR"

# for commands that use stdio: unbuffer (from expect package)
unbuffer my_command

For shell scripts you write yourself, use echo or printf — shell builtins always flush on newline. The issue only affects programs that buffer internally.

Process exit ends the watch

When the subprocess exits, the monitor ends cleanly. This is intentional: a monitor whose source process has died cannot produce events, so continuing to wait is wasteful.

For commands that are expected to run to completion — a build, a test suite, a deployment script — this behavior is correct. The monitor watches the command for its natural duration and stops when it finishes:

# watch a full test run — monitor ends when pytest exits
pytest tests/ -v --tb=short 2>&1

For persistent observation, the command must be a loop. The while true; do ... done pattern is the standard idiom. An alternative for file tailing is tail -f, which is designed to run indefinitely and will keep the monitor alive until you call TaskStop.

15.3 WebSocket Mode

WebSocket mode is the right tool when the event source is already a push-based stream: a CI/CD platform's live event feed, a message broker, a metrics stream, a webhook relay.

Frame semantics

The WebSocket protocol distinguishes text frames and binary frames. Monitor maps these to distinct behaviors:

  • Text frame → event delivered to the agent. The frame payload is the event content.
  • Binary frame → placeholder event delivered. The agent receives a notification that a binary frame arrived and its byte length, but not the raw bytes. The harness does not attempt to decode binary.
  • Socket close → monitor ends. The close code and reason are delivered as a final event before the monitor stops.

This means WebSocket mode works cleanly with JSON-over-WebSocket APIs (text frames) and server-sent event relays that use WebSocket as a transport. It is not designed for binary protocols (STOMP over WebSocket with binary encoding, for instance) — use command mode with a client script that decodes the binary and writes text to stdout instead.

Connection lifecycle

sequenceDiagram
    participant A as Agent
    participant H as Harness
    participant WS as WebSocket Server

    A->>H: Monitor(ws: { url: "wss://..." }, persistent: true)
    H-->>A: MonitorOutput { taskId: "mon_b3c4" }
    H->>WS: WebSocket connect + protocol negotiation
    WS-->>H: connection established
    WS-->>H: text frame: '{"event":"push","ref":"main"}'
    H-->>A: event delivered
    WS-->>H: binary frame (128 bytes)
    H-->>A: placeholder: "binary frame: 128 bytes"
    WS-->>H: close (code 1000, reason: "stream ended")
    H-->>A: socket closed — monitor ends

The harness handles the WebSocket handshake, keep-alives, and reconnection is not automatic. If the server closes the socket, the monitor ends. If you need reconnection behavior, wrap a WebSocket client in a command-mode shell script that reconnects on exit:

# reconnecting WebSocket consumer via websocat
while true; do
  websocat "wss://stream.example.com/events" 2>/dev/null
  echo "[reconnecting in 5s]"
  sleep 5
done

Subprotocols

Many WebSocket servers require subprotocol negotiation. Without the correct Sec-WebSocket-Protocol header, the server rejects the connection. Pass the required protocol names in the protocols array:

ws: {
  url: "wss://api.github.com/repos/owner/repo/hooks/live",
  protocols: ["github-hookshot"]
}

The harness includes the protocols array in the Sec-WebSocket-Protocol upgrade header. If the server does not support any of the listed protocols, it will either reject the connection or proceed without subprotocol agreement — behavior is server-dependent.

15.4 Persistent Monitors

The persistent: true flag is what elevates Monitor from a bounded observation tool to infrastructure. A persistent monitor is a session-scoped daemon: it runs continuously, delivers events indefinitely, and stops only when explicitly told to or when the session ends.

The persistent monitor contract

stateDiagram-v2
    [*] --> Running : Monitor(persistent: true)
    Running --> Delivering : event arrives
    Delivering --> Running : event processed
    Running --> Stopped : TaskStop(taskId)
    Running --> Stopped : session ends
    Running --> Stopped : command exits / socket closes

Unlike a cron job, which is scheduled and fires at intervals, a persistent monitor is alive. It holds an open process or socket connection. This has resource implications: a persistent command monitor holds an OS process; a persistent WebSocket monitor holds a TCP connection and file descriptor. In a session with dozens of persistent monitors, resource consumption adds up. Be intentional — a persistent monitor should serve a clear, ongoing purpose, not be used as a lazy alternative to proper timeout planning.

Stopping a persistent monitor

The taskId from MonitorOutput is the handle. TaskStop(taskId) sends a stop signal to the monitor. For command mode, the harness sends SIGTERM to the subprocess and waits for it to exit. For WebSocket mode, the harness sends a close frame and waits for the server's close response.

If you lose the taskId — which can happen when the agent's context is compacted or a new session is started — TaskList returns all active tasks including running monitors. Each entry includes the task description, which is why a precise description matters.

Session lifetime behavior

When the Claude Code session ends (user exits, session times out, the harness process is killed), the harness sends stop signals to all active persistent monitors before exiting. This is a graceful cleanup: processes get SIGTERM, WebSockets get close frames.

Abnormal exits — kill -9, power failure, OOM kill — do not trigger cleanup. Subprocess children become orphans. For production deployments where reliable cleanup matters, run the harness inside a process supervisor (systemd, launchd, supervisor) and use the service stop hook to issue TaskStop commands before the harness exits.

15.5 MonitorOutput

The tool returns immediately with a compact output structure:

export interface MonitorOutput {
  taskId: string;          // opaque identifier for this monitor instance
  timeoutMs: number;       // effective timeout; 0 when persistent
  persistent?: boolean;    // true when persistent mode is active
}

taskId is the only field you need to act on. It is an opaque string — do not parse it for embedded information. Use it only as an argument to TaskStop.

timeoutMs reflects the effective timeout. If you passed timeout_ms: 60000 and persistent: false, you get back timeoutMs: 60000. If you passed persistent: true, you get back timeoutMs: 0, which signals that no timeout is in effect.

There is no field for the current event count, elapsed time, or connection state. To check whether a monitor is still running, call TaskGet(taskId).

Event delivery to the agent

Events do not appear as fields on MonitorOutput. They are delivered asynchronously to the agent's conversation context as they arrive. From the agent's perspective, each event appears as a new message in the conversation history — the harness appends it and the agent reacts on the next control loop iteration.

This means Monitor integrates naturally with the control loop described in Chapter 1. The agent calls Monitor, receives a taskId, and the loop continues. Whenever an event arrives, the harness appends it to the conversation and the model processes it like any other input. No special event-handling API. No callbacks. The conversation context is the event queue.

15.6 Monitor vs CronCreate: Event-Driven vs Polling

Before building the lab, it is worth being precise about when to use Monitor versus CronCreate, because they are easy to confuse and the wrong choice has real consequences.

CronCreate schedules recurring work. It fires at calendar intervals — every 30 seconds, every hour, at 9 AM on weekdays. Between firings, nothing happens. The agent wakes up, does something, and goes back to sleep. This is polling, even if the interval is short.

Monitor is structurally different. It connects to a source and receives events the instant they are produced. There is no interval, no periodic wake-up, no gap between event occurrence and event delivery (other than network latency for WebSocket, and pipe buffering for command mode).

DimensionCronCreate (polling)Monitor (event-driven)
LatencyUp to one full intervalNear-zero (pipe / socket)
Resource costAlmost none between firingsHolds process or connection
Source requirementQueryable on demandProduces a stream
Missed eventsPossible if interval > event rateNone (events are buffered in pipe/socket)
Appropriate forScheduled checks, digests, status pollsLog tailing, CI streams, WebSocket feeds
Stop mechanismCronDeleteTaskStop

The latency difference is often decisive. A CronCreate running every 30 seconds will miss a CI failure that occurs at second 1 and auto-recovers by second 25. A Monitor running against the same CI stream catches it at second 1 and can send an alert, open a PR comment, or trigger a remediation workflow before the recovery happens.

The resource cost difference runs the other way. A CronCreate that fires every 30 seconds costs essentially nothing between firings — the harness is not holding any connection or process. A Monitor holds resources continuously. For 24-hour monitoring, prefer either a short-timeout Monitor that automatically restarts (using CronCreate to relaunch it) or a purpose-built daemon outside the harness.

The practical guide: if you find yourself writing a CronCreate with an interval under 60 seconds to catch real-time events, you want Monitor. If you find yourself writing a persistent Monitor whose command just runs gh run list once and exits, you want CronCreate.

15.7 Lab: Build a CI/CD Monitor

This lab builds a monitor that watches GitHub Actions runs on the main branch, detects failures, and delivers a structured alert. The monitor is persistent — it runs for the lifetime of the session and does not require periodic restart.

Goal

The agent:

  1. Starts a persistent Monitor that polls GitHub Actions status every 30 seconds
  2. Parses each event to detect newly-failed runs
  3. Uses PushNotification to alert the user on first failure
  4. Tracks seen run IDs to avoid duplicate alerts
  5. Provides a summary command to list current run states on demand

Prerequisites

# Verify GitHub CLI is authenticated
gh auth status

# Verify repo access
gh run list --limit 3

Expected output confirms the CLI can reach the repository. If gh auth status fails, run gh auth login first.

Step 1: Start the persistent monitor

The monitor command polls gh run list every 30 seconds and writes JSON to stdout. The agent will parse each output line as an event:

// Monitor input
{
  description: "GitHub Actions CI monitor — main branch failure detection",
  timeout_ms: 3600000,   // ignored, but required field
  persistent: true,
  command: `
    while true; do
      gh run list \
        --branch main \
        --limit 10 \
        --json databaseId,status,conclusion,name,headBranch,createdAt \
        2>/dev/null
      sleep 30
    done
  `
}

This returns immediately:

{
  "taskId": "mon_ci_a1b2c3",
  "timeoutMs": 0,
  "persistent": true
}

Save the taskId. You will need it to stop the monitor when the session ends or when CI monitoring is no longer needed.

Step 2: Parse events as they arrive

Each event is a JSON array from gh run list. A representative event:

[
  {
    "databaseId": 12345678,
    "status": "completed",
    "conclusion": "failure",
    "name": "CI / test",
    "headBranch": "main",
    "createdAt": "2026-07-28T14:22:11Z"
  },
  {
    "databaseId": 12345679,
    "status": "in_progress",
    "conclusion": null,
    "name": "CI / lint",
    "headBranch": "main",
    "createdAt": "2026-07-28T14:22:09Z"
  }
]

The agent maintains a set of seen_ids in conversation state. On each event, it:

  1. Parses the JSON array
  2. Filters for status === "completed" and conclusion === "failure"
  3. Checks each failing run's databaseId against seen_ids
  4. For new failures not in seen_ids, adds the ID and triggers the alert path
  5. Updates seen_ids with all completed run IDs from this event (failure and success)

This logic prevents duplicate alerts. Without it, every 30-second poll for a run that remains failed produces a new alert.

Step 3: Structured failure alert

When a new failure is detected, the agent calls PushNotification with a structured message:

{
  title: "CI Failure — main branch",
  message: `Run #${run.databaseId} failed: ${run.name}\nStarted: ${run.createdAt}`,
  url: `https://github.com/owner/repo/actions/runs/${run.databaseId}`
}

The url field opens the GitHub Actions run directly when the user taps the notification. This is the pattern that makes Monitor + PushNotification useful: the alert contains enough context that the user does not have to go search for what failed.

Step 4: On-demand status summary

Because the monitor is persistent, the agent can provide a current status summary without stopping the monitor. When the user asks "what's CI looking like?" the agent executes a one-shot Bash call in parallel with the running monitor:

gh run list --branch main --limit 10 \
  --json databaseId,status,conclusion,name,createdAt \
  | jq -r '.[] | "\(.conclusion // .status)\t\(.name)\t\(.createdAt)"'

Expected output:

failure    CI / test      2026-07-28T14:22:11Z
in_progress  CI / lint    2026-07-28T14:22:09Z
success    CI / deploy    2026-07-28T13:58:44Z
success    CI / test      2026-07-28T12:10:21Z

The monitor continues running while the agent answers the user's question. This is the value of non-blocking background tasks: the agent is never forced to choose between watching and acting.

Step 5: Detecting recovery

A mature CI monitor should also detect when a previously-failed run succeeds — the "all clear" signal. Extend the parsing logic:

# pseudocode for event parsing
def process_event(runs: list, seen_failures: set, seen_recoveries: set):
    for run in runs:
        if run["status"] != "completed":
            continue
        
        if run["conclusion"] == "failure":
            if run["databaseId"] not in seen_failures:
                seen_failures.add(run["databaseId"])
                alert_failure(run)
        
        elif run["conclusion"] == "success":
            # was there a prior failure for this workflow name on main?
            if run["name"] in recently_failed_workflows:
                if run["databaseId"] not in seen_recoveries:
                    seen_recoveries.add(run["databaseId"])
                    alert_recovery(run)

The recovery alert uses a different PushNotification tone:

{
  title: "CI Recovered — main branch",
  message: `${run.name} is passing again.\nRun #${run.databaseId}`,
  url: `https://github.com/owner/repo/actions/runs/${run.databaseId}`
}

Step 6: Stop the monitor

When CI monitoring is no longer needed, stop it cleanly:

TaskStop("mon_ci_a1b2c3")

The harness sends SIGTERM to the while true shell loop. The current sleep or gh run list call receives the signal. The subprocess exits. No more events are delivered.

Complete wiring diagram

flowchart TD
    M[Monitor\npersistent: true\ncommand: gh run list loop] -->|taskId| Agent

    subgraph "Every 30 seconds"
        GH[GitHub Actions API] -->|JSON: run list| M
        M -->|event: JSON array| Agent
    end

    Agent --> Parse{Parse event}
    Parse -->|new failure| PN[PushNotification\nfailure alert]
    Parse -->|recovery| PN2[PushNotification\nrecovery alert]
    Parse -->|no change| Wait[wait for next event]

    User -->|"what's CI looking like?"| Agent
    Agent -->|Bash: gh run list one-shot| Summary[status table → user]

    Stop[TaskStop taskId] --> Agent
    Agent -->|SIGTERM| M

Expected behavior in production

A monitor running this pattern in a session that stays open for a typical workday (8 hours) will:

  • Poll GitHub Actions 960 times (once per 30 seconds × 480 minutes)
  • Deliver approximately 960 events to the agent
  • Trigger at most one alert per unique run failure (deduplication via seen_ids)
  • Hold one shell process and one GitHub CLI subprocess at any moment
  • Consume negligible CPU between polls (the subprocess sleeps 30 seconds)

The session's conversation context will accumulate 960 event entries. For very long-lived sessions, this is a context-budget concern. The mitigation: use a filtered command that only writes to stdout when there is something worth reporting:

while true; do
  FAILURES=$(gh run list \
    --branch main \
    --limit 10 \
    --json databaseId,conclusion \
    | jq '[.[] | select(.conclusion == "failure")]')
  
  if [[ "$FAILURES" != "[]" ]]; then
    echo "$FAILURES"
  fi
  
  sleep 30
done

With this version, an event is only delivered when there are actual failures. A clean CI state produces no events at all, and the conversation context stays lean.

Extending the lab: WebSocket variant

Some CI platforms expose WebSocket event streams. GitHub's internal tooling, Buildkite, and CircleCI all have WebSocket-based event APIs for real-time push. The WebSocket variant of this monitor eliminates the polling interval entirely:

{
  description: "Buildkite live build events — main branch",
  timeout_ms: 3600000,
  persistent: true,
  ws: {
    url: "wss://buildkite.com/events/builds",
    protocols: ["buildkite-events-v1"]
  }
}

Each build state transition — running, passed, failed, blocked — arrives as a text frame the instant it occurs. The latency from event to alert drops from up to 30 seconds (polling interval) to under a second (WebSocket push). For on-call use cases where mean-time-to-notify matters, WebSocket mode is the correct choice when the platform supports it.

Summary

Monitor is the harness tool for event-driven observation. It connects the agent to a live stream — a shell command's stdout, a WebSocket connection — and delivers each event asynchronously as the agent's context, without blocking the control loop.

The parameter contract is simple: description (human-readable label), timeout_ms (max one hour, ignored for persistent), persistent (session-lifetime vs bounded), and exactly one of command or ws. The tool returns immediately with a MonitorOutput containing the taskId needed to stop the monitor later.

In command mode, each stdout line is one event. The command must be written to run indefinitely (the while true pattern) if the intent is continuous observation; a command that exits naturally ends the monitor. In WebSocket mode, each text frame is one event; binary frames produce placeholder events; socket close ends the monitor.

The persistent: true flag is what makes Monitor viable as infrastructure. Without it, a monitor capped at one hour requires manual restart for longer observation windows. With it, the monitor runs until the session ends or TaskStop is called — making it appropriate for session-scoped daemons like log tailers, build watchers, and message queue consumers.

The key architectural distinction from CronCreate is the push/pull boundary. CronCreate polls — it wakes up at intervals and queries the source. Monitor listens — the source pushes events to it. When latency matters and the source produces a stream, Monitor is the right primitive. When the source must be queried and the exact firing time matters less than the schedule, CronCreate is the right primitive. Build the CI/CD monitor from this chapter and the difference becomes concrete: a polling monitor catches failures within 30 seconds; a WebSocket monitor catches them in under one.
