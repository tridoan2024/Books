Chapter 9: Planning Tools — EnterPlanMode, ExitPlanMode, AskUserQuestion

"The fastest way to waste an afternoon is to let an agent start implementing something it doesn't fully understand."

9.1 Plan Mode Lifecycle

Every agentic harness faces the same tension: the model is capable enough to start immediately, but complex tasks benefit from a pause — a moment where the agent surveys the terrain, assembles a coherent plan, and gets human sign-off before touching production state. Plan mode is the harness's answer to that tension.

Plan mode is a first-class execution state in Claude Code. It is not a convention or a prompt trick. It is a distinct mode with enforced behavioral constraints: while in plan mode, the agent can explore freely but cannot write or modify files. It is strictly read and reason, never act.

The lifecycle has five stages:

sequenceDiagram
    participant U as User
    participant H as Harness
    participant A as Agent
    participant FS as Filesystem

    U->>A: "Migrate the auth module to OAuth 2.0"
    A->>H: EnterPlanMode
    H-->>A: {message: "Plan mode active"}
    Note over A: Can Read, Grep, Glob, Bash (read-only)<br/>Cannot Edit or Write
    A->>FS: Read auth module files
    A->>FS: Grep for all session references
    A->>FS: Read existing tests
    A->>FS: Write plan to ~/.claude/plans/jolly-knitting-ullman.md
    A->>H: ExitPlanMode
    H-->>U: Display plan for review
    U->>H: Approve
    H-->>A: {plan: "...", isAgent: false}
    Note over A: Now can Edit and Write
    A->>FS: Implement changes

Stage 1: EnterPlanMode. The agent calls EnterPlanMode with no parameters. The harness immediately restricts the agent's tool surface — Edit and Write calls will fail until plan mode is exited. The agent receives a confirmation message and begins its exploration phase.

Stage 2: Exploration. This is the most important part of plan mode and the one engineers most often underestimate. A thorough exploration phase produces a plan that is actually executable. The agent reads files, greps for patterns, follows import chains, checks test coverage, reads existing documentation. It is not writing yet — it is building the complete picture. Skipping or rushing this phase produces a plan with wrong assumptions, missed edge cases, and a dependency order that will fail partway through.

Stage 3: Write the plan file. After exploration, the agent writes a plan file into ~/.claude/plans/. This file is the artifact. It should contain what will be done, in what order, and why — enough detail that a senior engineer reading it would know exactly what the implementation will produce before a single line of code changes.

Stage 4: ExitPlanMode. The agent calls ExitPlanMode. The harness reads the plan file, surfaces it to the user, and waits. This is the approval gate.

Stage 5: Implementation. The user approves. The harness returns the plan content to the agent with isAgent: false (or true if running as a subagent awaiting leader approval). The edit and write constraints are lifted. The agent implements what the plan described.

When to Use Plan Mode

Plan mode is for non-trivial implementation tasks. The decision threshold matters — using plan mode for every change creates friction without value; skipping it for complex changes is how multi-file refactors go wrong.

TaskPlan mode?
Fix a typo in a string literalNo
Rename a variable across 3 filesNo
Add a single API endpoint with a testJudgment call
Migrate authentication systemYes
Refactor a module to a new interface used in 15 placesYes
Implement a new feature spanning 5+ filesYes
Anything where the implementation order mattersYes

The clearest signal: if the agent could start implementing and then realize partway through that an earlier decision was wrong — requiring a rollback — plan mode was warranted.

What the Constraints Actually Enforce

In plan mode, the harness does not disable Edit and Write at the tool description level. It enforces the constraint at execution time: if the agent tries to call Edit or Write while plan mode is active, the tool returns a tool_result explaining that modifications are not permitted in plan mode. The agent sees this as an error and adjusts.

This enforcement matters because it is honest. The model cannot accidentally write files while it thinks it is still planning. The constraint is runtime, not advisory.

Bash commands are permitted in plan mode, because they are essential for exploration. The agent needs to run grep, find, cat, git log, and similar read-only commands. The harness trusts the agent to stay read-only during exploration — it cannot statically verify that a Bash command is read-only the way it can verify that Edit is a write operation. This means plan mode's write-protection is not a full sandbox; it is a behavioral constraint paired with architectural enforcement for the deterministically-write tools.

9.2 The Plan File

The plan file is not ephemeral. It is a persistent artifact written to ~/.claude/plans/ with a randomly-generated human-readable name — a kebab-case string in the pattern of adjective-noun-surname: jolly-knitting-ullman.md, brave-sorting-mergesort.md. The naming scheme is deliberate whimsy that makes plans easy to identify in a directory listing without requiring a content hash or timestamp.

File Content

The harness does not enforce a schema on the plan file. The agent writes free-form markdown. A well-structured plan looks like this:

# Plan: Migrate Auth Module to OAuth 2.0

## Objective
Replace the current session-token auth in `src/auth/` with OAuth 2.0 using
the `python-oauth2lib` library. All existing tests must continue to pass.
No external-facing API changes.

## Current State
- `src/auth/session.py` manages tokens using a homegrown HMAC scheme
- `src/auth/middleware.py` validates tokens on every request
- `src/auth/models.py` defines the User and Session models
- `tests/auth/` has 23 tests covering happy path and expiry cases
- No refresh token support exists today

## What Changes
1. Add `OAuthProvider` class in `src/auth/oauth.py`
2. Update `Session` model to store OAuth tokens (add `refresh_token` field)
3. Migrate `middleware.py` to use OAuth token validation
4. Update `session.py` to delegate to `OAuthProvider`
5. Add migration `0012_add_refresh_token.py` for the DB schema change
6. Update `tests/auth/test_session.py` — 4 tests need new fixtures

## Risks
- Migration 0012 is irreversible once applied to production
- The OAuth library's token validation is synchronous; the middleware is async
  → Need to wrap with `asyncio.to_thread` or find the async variant

## Implementation Order
Must follow this order to avoid circular imports:
1. models.py (data layer first)
2. oauth.py (new provider, no dependencies on existing auth)
3. session.py (update to use oauth.py)
4. middleware.py (update last — depends on session.py)
5. migration file
6. tests

## Files Modified
- src/auth/models.py
- src/auth/session.py
- src/auth/middleware.py
- tests/auth/test_session.py

## Files Created
- src/auth/oauth.py
- migrations/0012_add_refresh_token.py

This is not a template the harness enforces — it is what a good agent produces when it has explored thoroughly. The quality of the plan file directly predicts the quality of the implementation.

planWasEdited

When the user reviews the plan in the Claude Code web UI or presses Ctrl+G in the terminal UI, they can edit the plan directly in the interface. The harness tracks whether the file was modified between the time the agent wrote it and the time the user approved.

When ExitPlanMode returns, the planWasEdited field carries this signal:

export interface ExitPlanModeOutput {
  plan: string | null;
  isAgent: boolean;
  filePath?: string;
  hasTaskTool?: boolean;
  planWasEdited?: boolean;
  awaitingLeaderApproval?: boolean;
  requestId?: string;
}

When planWasEdited is true, the agent should re-read the plan from the returned content (or filePath) before implementing. The user may have adjusted scope, reordered steps, or added constraints. An agent that ignores planWasEdited and implements from its in-memory version of the plan will diverge from what the user approved.

A well-written harness agent handles this explicitly:

const result = await exitPlanMode();

if (result.planWasEdited) {
  // User changed the plan — use their version, not ours
  const approvedPlan = result.plan ?? fs.readFileSync(result.filePath!, 'utf8');
  // Re-parse and proceed with the edited plan
  await implementFromPlan(approvedPlan);
} else {
  // Plan was approved as-written
  await implementFromPlan(inMemoryPlan);
}

awaitingLeaderApproval and requestId

In multi-agent workflows, a subagent running as a teammate does not surface plans directly to the user. Instead, it sets awaitingLeaderApproval: true and returns a requestId. The leader agent is responsible for receiving this approval request, reviewing the plan, and either approving or rejecting it.

This is the harness's mechanism for human-in-the-loop approval in agent hierarchies. An autonomous agent team does not bypass plan review just because there is no interactive terminal. The approval request routes up the hierarchy until it reaches either a human or a designated leader agent with approval authority.

The requestId is an opaque string — a UUID — that the leader uses when responding to the approval request. It allows the harness to correlate approvals with the correct pending plan even when multiple subagents are waiting simultaneously.

9.3 AskUserQuestion

AskUserQuestion is the structured interaction tool. Where the rest of the tool surface is about doing things — reading files, running commands, writing code — AskUserQuestion is about resolving ambiguity before doing the wrong thing.

The interface is richer than it first appears:

export interface AskUserQuestionInput {
  questions: [{
    question: string;      // clear, ends with ?
    header: string;        // max 12 chars, shown as chip/tag
    options: [{
      label: string;       // 1-5 words
      description: string;
      preview?: string;    // markdown in monospace box (single-select only)
    }];
    multiSelect: boolean;
  }];
  answers?: { [question: string]: string };
  annotations?: { [question: string]: { preview?: string; notes?: string } };
  metadata?: { source?: string };
}

The constraints are deliberate UX choices:

  • 1–4 questions per call. More than four and the user will feel interrogated. Fewer than one and you should just proceed.
  • 2–4 options per question. Forces the agent to think about the actual decision space before presenting it. If you cannot fit the real choices into four options, the question is probably too broad.
  • Header max 12 chars. This renders as a chip or tag in the UI — it needs to be a label, not a sentence. "Database", "Strategy", "Timeline" are headers. "Which option for the database migration approach?" is not.

The Preview Field

When any option in a single-select question includes a preview field, the UI switches from a simple list to a side-by-side layout: the option list on the left, the preview rendered in a monospace box on the right. As the user highlights different options, the preview updates to show what they would get.

This is the agent's mechanism for showing rather than telling. Instead of describing what a generated output would look like, the agent can generate a concrete sample and attach it to the option:

await askUserQuestion({
  questions: [{
    question: "Which error message format should the API use?",
    header: "Error Format",
    multiSelect: false,
    options: [
      {
        label: "RFC 7807 Problem Details",
        description: "Standard format with type, title, status, detail fields",
        preview: `{
  "type": "https://api.example.com/errors/not-found",
  "title": "Resource Not Found",
  "status": 404,
  "detail": "User with ID 'abc123' does not exist",
  "instance": "/users/abc123"
}`
      },
      {
        label: "Simple JSON",
        description: "Minimal error object with code and message",
        preview: `{
  "code": "NOT_FOUND",
  "message": "User with ID 'abc123' does not exist"
}`
      },
      {
        label: "GraphQL-style",
        description: "Errors array for consistency with GraphQL clients",
        preview: `{
  "errors": [
    {
      "message": "User with ID 'abc123' does not exist",
      "extensions": { "code": "NOT_FOUND" }
    }
  ]
}`
      }
    ]
  }]
});

The user sees all three formats side by side. They do not need to remember option descriptions — they can see the actual output. For decisions where visual comparison matters (code style, output format, schema design), this is significantly better than a text description.

Note that preview only works meaningfully for single-select questions. If multiSelect is true, the side-by-side layout does not apply — the preview field is ignored.

multiSelect

When multiSelect: true, the user can select multiple options. The answer returned is the selected labels joined with commas:

"RFC 7807 Problem Details,GraphQL-style"

The agent parses this by splitting on , (comma-space). An agent that forgets to handle multiselect answers as a list rather than a single string will misinterpret the user's choices for any selection after the first.

The "Other" Option

Users always have an implicit "Other" option available. They can type a free-form response instead of selecting from the provided options. When this happens, the response field of AskUserQuestionOutput is populated with the user's text:

export interface AskUserQuestionOutput {
  questions: [...];
  answers: { [k: string]: string };
  response?: string;
  annotations?: { [k: string]: { preview?: string; notes?: string } };
  afkTimeoutMs?: number;
}

An agent reading the output should always check response first. If it is set, the user bypassed the structured options and gave their own answer. Ignoring response and only reading answers will silently discard the user's actual intent:

const output = await askUserQuestion({ questions: [...] });

for (const q of output.questions) {
  const answer = output.answers[q.question];
  const freeform = output.response;

  if (freeform) {
    // User gave a custom answer — parse it and adapt
    handleFreeformAnswer(freeform);
  } else if (answer) {
    handleStructuredAnswer(q.question, answer);
  }
}

Annotations

Annotations let the harness attach additional context to questions — a preview at the question level (not the option level) and notes that appear below a question. This is useful when the agent wants to explain the current state before asking the user to choose:

await askUserQuestion({
  questions: [{
    question: "How should we handle the deprecated endpoints?",
    header: "Endpoints",
    multiSelect: false,
    options: [
      { label: "Remove now", description: "Delete deprecated routes and their handlers" },
      { label: "Sunset header", description: "Keep routes but add Sunset and Deprecation headers" },
      { label: "Proxy forward", description: "Redirect deprecated paths to new equivalents" }
    ]
  }],
  annotations: {
    "How should we handle the deprecated endpoints?": {
      notes: "3 endpoints were deprecated in v2.1: /api/v1/users, /api/v1/sessions, /api/v1/tokens. Analytics shows 8 active callers in the last 30 days (3 internal, 5 unknown).",
      preview: "GET /api/v1/users → currently 1,240 req/day\nGET /api/v1/sessions → currently 890 req/day\nPOST /api/v1/tokens → currently 2,100 req/day"
    }
  }
});

The user sees the actual traffic data before making the deprecation decision. The annotation is not a description of the options — it is context about the situation that the agent discovered during exploration.

9.4 The afkTimeoutMs Auto-Resolution

In headless and automated environments, there is no human waiting at the terminal to answer AskUserQuestion dialogs. This creates a problem: if the agent asks a question and no one answers, the workflow stalls indefinitely.

The harness solves this with afkTimeoutMs. When the user does not respond to an AskUserQuestion within a configurable idle period, the harness auto-resolves the dialog. The first available option is selected as the default. The AskUserQuestionOutput returns with afkTimeoutMs set to the duration that elapsed before auto-resolution:

const output = await askUserQuestion({ questions: [...] });

if (output.afkTimeoutMs !== undefined) {
  // Auto-resolved — user was not present
  // afkTimeoutMs is the milliseconds that elapsed before timeout
  console.log(`Auto-resolved after ${output.afkTimeoutMs}ms idle`);
  // Treat answers with lower confidence — consider logging or notifying
}

What This Means for Harness Design

afkTimeoutMs being set is not an error — it is a signal. It tells the agent:

  1. The user was not present at the time of the question.
  2. The answer was auto-selected, not chosen.
  3. Decisions based on this answer carry reduced confidence.

Well-designed agents handle this differently from user-selected answers. In an architecture decision workflow, an auto-resolved answer might trigger a conservative default (preserve backward compatibility, do not delete, choose the reversible option) rather than proceeding with full confidence. In a teammate scenario, the auto-resolution might trigger a notification to the leader agent that approval was given by timeout, not by explicit review.

Headless Agents and Question Design

Because headless agents will frequently encounter afkTimeoutMs, the option ordering in AskUserQuestion matters more than it might seem. The first option is the auto-resolved default. Structure your questions so the first option is the safe, conservative, or most reversible choice:

// Good ordering — first option is safe default
options: [
  { label: "Preview mode", description: "Generate plan only, no changes" },
  { label: "Apply changes", description: "Implement immediately" },
  { label: "Apply and commit", description: "Implement and commit to git" }
]

// Bad ordering — destructive action is the default
options: [
  { label: "Drop and recreate", description: "Delete existing tables" },
  { label: "Migrate in place", description: "Use ALTER TABLE" },
  { label: "Skip migration", description: "Leave schema unchanged" }
]

In the bad example, a headless agent that times out will silently drop tables. The good example times out into a preview that produces no side effects.

9.5 Structured Answers

The output of AskUserQuestion carries two answer channels: the answers map for structured selections and response for freeform text.

The answers Map

answers is a flat map from question text to the user's selection. For single-select questions, the value is the label of the selected option. For multi-select, the value is a comma-separated string of selected labels:

// Single-select result
answers: {
  "Which database migration strategy should we use?": "Migrate in place"
}

// Multi-select result
answers: {
  "Which components need to be updated?": "Auth module,Session model,Middleware"
}

The key is the exact question text — including punctuation. This is worth noting: if you construct question text dynamically (interpolating filenames, counts, or context), you need to use the same dynamic value as the key when reading back from answers. A subtle mismatch — a trailing space, a different variable — produces an undefined lookup that silently discards the user's answer.

The robust pattern is to capture the question text when constructing the input and reuse it when reading the output:

const questionText = `Which of these ${files.length} files should be refactored?`;

const output = await askUserQuestion({
  questions: [{
    question: questionText,
    header: "Files",
    multiSelect: true,
    options: files.map(f => ({ label: f.name, description: f.path }))
  }]
});

const selected = output.answers[questionText]?.split(", ") ?? [];

The response Field

response captures what the user typed when they chose "Other" instead of selecting from the provided options. It is a plain string — no structure, no parsing guarantees. The agent needs to interpret it.

The presence of response means the agent's options did not fully model the decision space. This is useful feedback. A well-instrumented harness logs these freeform responses — they reveal gaps in the agent's understanding of what the user actually needs.

When response is set and answers is empty for a question, the user gave a fully freeform answer. When both response and entries in answers are set, the user selected options and also added text. Both are meaningful.

Pre-filling Answers

The answers input field on AskUserQuestionInput lets the harness pre-fill answers before presenting the dialog to the user. This is useful in two scenarios:

Resuming a workflow. If the agent was interrupted and needs to re-ask a question, it can pre-fill with the previously-recorded answer so the user does not have to re-enter it.

Suggesting a default. The agent can pre-fill the most likely answer based on its analysis, letting the user confirm or override rather than selecting from scratch:

await askUserQuestion({
  questions: [{
    question: "Which authentication approach should we migrate to?",
    header: "Auth Strategy",
    multiSelect: false,
    options: [
      { label: "OAuth 2.0 + PKCE", description: "Recommended for SPAs" },
      { label: "OAuth 2.0 + client credentials", description: "For service-to-service" },
      { label: "API keys", description: "Simple, no refresh flow" }
    ]
  }],
  answers: {
    "Which authentication approach should we migrate to?": "OAuth 2.0 + PKCE"
  }
});

The dialog opens with "OAuth 2.0 + PKCE" pre-selected. The user can accept it or choose differently.

9.6 Lab: Build an Architecture Decision Workflow

This lab builds a realistic workflow that uses plan mode and structured questions together: an agent that helps engineers make and document architecture decisions, producing an Architecture Decision Record (ADR) as output.

Workflow Design

The workflow has three phases:

  1. Discovery. Enter plan mode, explore the codebase to understand the relevant context.
  2. Decision. Use AskUserQuestion to capture the decision and its rationale.
  3. Documentation. Exit plan mode, write the ADR file.
flowchart TD
    A([User: "Create ADR for caching strategy"]) --> B[EnterPlanMode]
    B --> C[Read current architecture]
    C --> D[Grep for existing cache usage]
    D --> E[Read dependencies]
    E --> F[Write plan: ADR outline]
    F --> G[ExitPlanMode — user reviews outline]
    G --> H{User approved?}
    H -->|Yes| I[AskUserQuestion: context questions]
    I --> J[AskUserQuestion: decision questions]
    J --> K[Assemble ADR content]
    K --> L[Write ADR to docs/adr/]
    H -->|No, edited| G2[Re-read edited plan]
    G2 --> I

Implementation

async function runAdrWorkflow(topic: string): Promise<void> {
  // Phase 1: Enter plan mode and explore
  await enterPlanMode();

  // Explore the codebase for relevant context
  const packageJson = await read({ file_path: "./package.json" });
  const cacheUsage = await bash({
    command: "grep -rn 'cache\\|redis\\|memcached\\|lru' src/ --include='*.ts' -l",
    description: "Find existing cache usage"
  });
  const existingAdrs = await bash({
    command: "ls docs/adr/ 2>/dev/null || echo 'No ADRs yet'",
    description: "List existing ADRs"
  });

  // Write the plan — what the ADR will cover
  const planContent = `# Plan: ADR for ${topic}

## Exploration Findings
- Packages: ${extractRelevantDeps(packageJson)}
- Files with cache usage: ${cacheUsage.output}
- Existing ADRs: ${existingAdrs.output}

## ADR Outline
1. Context: Why this decision is needed
2. Decision drivers: Performance targets, team constraints
3. Considered options: 3 alternatives with tradeoffs
4. Decision: Which option and why
5. Consequences: What changes, what risks remain

## Files to Create
- docs/adr/ADR-${nextAdrNumber()}-${slugify(topic)}.md
`;

  await write({
    file_path: `${process.env.HOME}/.claude/plans/adr-workflow.md`,
    content: planContent
  });

  // Exit plan mode — user sees and approves the outline
  const approval = await exitPlanMode();

  if (!approval.plan) {
    throw new Error("Plan was rejected or not found");
  }

  // Use the approved plan (may have been edited)
  const workingPlan = approval.planWasEdited
    ? approval.plan
    : planContent;

  // Phase 2: Gather decision details with structured questions
  const contextAnswers = await askUserQuestion({
    questions: [
      {
        question: "What is the primary driver for this architectural decision?",
        header: "Driver",
        multiSelect: false,
        options: [
          {
            label: "Performance",
            description: "Latency or throughput requirements are the forcing function",
            preview: "Example context:\n\"API p99 latency exceeds 500ms under load.\nDB queries are the bottleneck (avg 200ms).\"\n\nThis ADR will focus on cache hit rates\nand eviction strategies."
          },
          {
            label: "Cost",
            description: "Infrastructure or operational cost needs to decrease",
            preview: "Example context:\n\"Database RCU costs $4,200/month.\nCache layer could reduce this by 60-80%.\"\n\nThis ADR will focus on cost modeling\nand ROI projections."
          },
          {
            label: "Scalability",
            description: "The current approach does not scale to projected load",
            preview: "Example context:\n\"Current architecture handles 500 req/s.\nProjected growth: 5,000 req/s in 6 months.\"\n\nThis ADR will focus on horizontal\nscaling characteristics."
          },
          {
            label: "Consistency",
            description: "Cache invalidation or data consistency is a current problem",
            preview: "Example context:\n\"Stale data causes user-visible inconsistencies.\n3 incidents in Q3 traced to cache.\"\n\nThis ADR will focus on invalidation\nstrategies and consistency guarantees."
          }
        ]
      },
      {
        question: "Which team constraints apply?",
        header: "Constraints",
        multiSelect: true,
        options: [
          { label: "No new infra", description: "Cannot add new infrastructure dependencies" },
          { label: "On-call limit", description: "Team on-call capacity is already at limit" },
          { label: "Budget cap", description: "Monthly infrastructure budget is fixed" },
          { label: "SLA requirement", description: "Decision must maintain existing SLA commitments" }
        ]
      }
    ]
  });

  const decisionAnswers = await askUserQuestion({
    questions: [
      {
        question: "Which caching approach should be adopted?",
        header: "Decision",
        multiSelect: false,
        options: [
          {
            label: "Redis cluster",
            description: "Distributed cache, supports pub/sub for invalidation",
            preview: `// Cache read pattern\nconst cached = await redis.get(key);\nif (cached) return JSON.parse(cached);\n\nconst result = await db.query(...);\nawait redis.setex(key, TTL, JSON.stringify(result));\nreturn result;`
          },
          {
            label: "In-process LRU",
            description: "No network hop, zero infra, per-instance cache",
            preview: `// Cache read pattern\nconst lru = new LRUCache({ max: 1000, ttl: 60_000 });\n\nconst cached = lru.get(key);\nif (cached) return cached;\n\nconst result = await db.query(...);\nlru.set(key, result);\nreturn result;`
          },
          {
            label: "CDN edge cache",
            description: "Cache at the CDN layer for public read-heavy endpoints",
            preview: `// Response headers pattern\nres.set('Cache-Control', 'public, max-age=300');\nres.set('Surrogate-Key', \`user-\${userId}\`);\n\n// Invalidation\nawait cdn.purgeByTag(\`user-\${userId}\`);`
          }
        ]
      },
      {
        question: "What is the status of this ADR?",
        header: "Status",
        multiSelect: false,
        options: [
          { label: "Proposed", description: "Under discussion, not yet decided" },
          { label: "Accepted", description: "Decision made, implementation pending" },
          { label: "Superseded", description: "Replaces an earlier ADR" }
        ]
      }
    ],
    annotations: {
      "Which caching approach should be adopted?": {
        notes: `Based on codebase exploration:\n${cacheUsage.output || "No existing cache usage found"}`
      }
    }
  });

  // Phase 3: Write the ADR
  const driver = contextAnswers.answers["What is the primary driver for this architectural decision?"];
  const constraints = contextAnswers.answers["Which team constraints apply?"]?.split(", ") ?? [];
  const decision = decisionAnswers.answers["Which caching approach should be adopted?"];
  const status = decisionAnswers.answers["What is the status of this ADR?"];
  const freeform = decisionAnswers.response;

  const adrContent = assembleAdr({
    topic,
    driver,
    constraints,
    decision: freeform ?? decision,
    status,
    workingPlan
  });

  const adrNumber = nextAdrNumber();
  const adrPath = `docs/adr/ADR-${String(adrNumber).padStart(4, '0')}-${slugify(topic)}.md`;

  await write({ file_path: adrPath, content: adrContent });

  console.log(`ADR written to ${adrPath}`);
}

The assembleAdr Function

function assembleAdr(params: {
  topic: string;
  driver: string;
  constraints: string[];
  decision: string;
  status: string;
  workingPlan: string;
}): string {
  const { topic, driver, constraints, decision, status } = params;
  const date = new Date().toISOString().split('T')[0];

  return `# ADR-${nextAdrNumber()}: ${topic}

## Status: ${status}
## Date: ${date}

## Context

${driver} is the primary driver for this decision.${
    constraints.length > 0
      ? `\n\nConstraints: ${constraints.join(", ")}.`
      : ""
  }

## Decision

${decision}

## Consequences

### Positive
- Addresses the ${driver.toLowerCase()} requirement
- Decision is documented and reviewable

### Negative
- Requires implementation and migration effort
- Team needs to understand the new approach

### Risks
- See constraints: ${constraints.join(", ") || "none identified"}
`;
}

Running the Lab

To exercise this workflow locally:

  1. Create a test project directory with a src/ folder and some TypeScript files that reference caching.
  2. Create a docs/adr/ directory (or let the workflow handle its absence).
  3. Invoke runAdrWorkflow("read-through cache strategy").
  4. In the plan mode approval step, edit the plan outline — add a constraint or change a section heading. Observe that planWasEdited is true in the ExitPlanMode output.
  5. In the question steps, try typing a custom answer in the "Other" field instead of selecting an option. Observe that response is set.
  6. Kill the process during the second AskUserQuestion and restart it. Add afkTimeoutMs handling — log a warning and default to the safe option.

What to Observe

The lab surfaces three behaviors that are easy to miss in documentation:

Plan editing is load-bearing. When you edit the plan and watch the agent re-read it from the file rather than its in-memory copy, you see why planWasEdited exists. The agent implementing from an outdated in-memory plan after the user changed it is a real failure mode.

Preview layout changes UX. In the decision question, all three options have preview content. If you compare this dialog to the same question without previews, the difference in decision confidence is immediate — seeing the actual code pattern changes how quickly and confidently the user picks.

afkTimeoutMs changes behavior semantics. When the timeout fires and auto-selects "Proposed" as the ADR status, the resulting document is correct but incomplete. A production workflow should detect this and either flag the ADR for review or send a notification that the status was auto-filled.

Summary

Plan mode and AskUserQuestion are the harness's tools for deliberate collaboration. Plan mode enforces a separation between thinking and acting — the agent explores and designs before it writes a single file, and the user approves before implementation begins. AskUserQuestion gives the agent a structured way to resolve genuine ambiguity while staying productive.

The key implementation details to carry forward:

  • EnterPlanMode takes no parameters and restricts Edit and Write at execution time.
  • The plan file lives in ~/.claude/plans/ and is the artifact that survives the approval gate.
  • planWasEdited in ExitPlanModeOutput is not informational — the agent must re-read the plan from the returned content if it is set.
  • awaitingLeaderApproval and requestId enable plan approval routing in multi-agent hierarchies.
  • AskUserQuestion supports 1–4 questions with 2–4 options each; the preview field activates a side-by-side layout for single-select questions.
  • Option ordering matters: the first option is the afkTimeoutMs auto-resolution default — make it the safe choice.
  • Always check response before answers — freeform answers override the structured option surface.
