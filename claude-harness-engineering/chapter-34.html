Chapter 34: CI/CD and DevOps Integration

"A harness that only runs interactively is a productivity tool. A harness that runs in CI is infrastructure."

Chapters 22 through 33 built the machinery: worktrees for isolation, background agents for parallelism, the hook system for side effects, skills for reusable workflows. This chapter is about connecting all of that machinery to the systems that ship software — the CI pipelines, the PR queues, the deployment gates, the event-driven triggers that run whether or not a human is watching.

The integration surface has three entry points. First, print mode: the --print flag and its --output-format options transform Claude from an interactive tool into a machine-callable subprocess. Second, claude ultrareview: a cloud-hosted multi-agent code review command built into the harness, invoked from a single claude ultrareview call in a CI step. Third, RemoteTrigger and Monitor: the harness's own primitives for webhook-driven automation and event watching, both composable with external CI systems.

The chapter closes with a complete feature-to-production pipeline that wires all three together.

34.1 Git Workflow Automation

Before touching CI configuration, get the git layer right. Everything that runs in a pipeline eventually writes to git, and the harness has specific expectations about how commits and PRs are authored.

Attribution

Every commit the harness creates carries a Co-Authored-By trailer. Every PR body carries a Generated with Claude Code footer. This is not optional cosmetics — it is the audit trail that lets you distinguish human-authored changes from agent-authored changes in your git history and PR review queue.

The relevant settings block:

{
  "attribution": {
    "commit": "Co-Authored-By: Claude Opus 4.6 <noreply@anthropic.com>",
    "pr": "Generated with [Claude Code](https://claude.ai/claude-code)"
  }
}

In practice, the harness injects the Co-Authored-By line automatically when it calls git commit. You do not write it in your prompt. But you do need the attribution block in your settings file (global or project-level) so the harness knows which model name to use. If you switch models — say, from claude-sonnet-4-6 to claude-opus-4-8 for a heavier review pass — update the attribution block to match. Grep your git log six months from now and you will thank yourself.

Branch Naming

The harness follows prefix conventions that map to semantics your CI system can route on:

PrefixSemantic
feat/new capability
fix/bug repair
docs/documentation only
refactor/behavior-preserving restructure

Your branch protection rules and CI triggers can key off these prefixes directly. A feat/* branch pattern in a GitHub branch ruleset, for example, can require the ultrareview check to pass before merge. A fix/* pattern can require the regression test suite. The harness respects these prefixes because it was designed to work with real engineering workflows, not beside them.

Git Operations from Print Mode

The harness can execute a full git workflow — branch, change, commit, push, PR — in a single print-mode invocation:

claude -p "
Create a branch fix/retry-timeout, add exponential backoff to the HTTP client
in src/client.py (currently it retries immediately), commit the change, push,
and open a PR targeting main.
" \
  --allowedTools "Bash,Read,Write,Edit" \
  --output-format json

The harness will:

  1. Run git checkout -b fix/retry-timeout
  2. Read the file, make the change
  3. Run git add -p (or git add src/client.py), git commit -m "fix: add exponential backoff to HTTP client retries"
  4. Run git push -u origin fix/retry-timeout
  5. Call gh pr create with the standard title/body format

The standard PR body format the harness produces:

## Summary

Add exponential backoff to HTTP client retry logic. Previously the client
retried immediately on transient failures, causing thundering herd behavior
under load. The new implementation uses a base delay of 500ms with a
multiplier of 2, capped at 30 seconds.

## Test plan

- [ ] Unit tests in tests/unit/test_client.py
- [ ] Integration test: run with a network fault injector

Generated with [Claude Code](https://claude.ai/claude-code)

The ## Summary and ## Test plan sections are a convention, not a template variable. They appear because the harness has been instructed (via its system prompt or your CLAUDE.md) to produce them. If your team uses different PR body sections, add the format to your CLAUDE.md and the harness will follow it.

Safety Rails

Three constraints apply in all modes — interactive, print, and background:

Never force-push. The harness will not execute git push --force or git push --force-with-lease without explicit permission in the prompt. This constraint exists because force-pushing to a shared branch is almost always destructive. If you genuinely need a force push (rebasing a feature branch onto updated main, for example), say so explicitly.

Never amend without permission. git commit --amend rewrites history. The harness will not do this by default.

Never skip hooks. The harness will not pass --no-verify to git commit. Your pre-commit hooks run. If they fail, the commit fails. This is the right behavior — hooks exist for a reason.

34.2 Print Mode Pipelines

Print mode is the harness's API contract with CI systems. You call it like any other subprocess, capture stdout, process the output, and make decisions based on exit code and content.

The Flag Set

-p, --print                    Non-interactive output. Run to completion, exit.
--output-format <format>       text | json | stream-json
--input-format <format>        text | stream-json
--fallback-model <model>       Comma-separated fallback list (only with --print)
--forward-subagent-text        Forward subagent text as messages (with stream-json)

Text Output — Simplest Pipeline Integration

#!/usr/bin/env bash
set -euo pipefail

REVIEW_OUTPUT=$(claude -p "
Review the diff below for security issues. Output PASS if none found,
or FAIL followed by a bulleted list of issues.

$(git diff origin/main...HEAD)
" --output-format text)

if echo "${REVIEW_OUTPUT}" | grep -q "^FAIL"; then
  echo "Security review failed:"
  echo "${REVIEW_OUTPUT}"
  exit 1
fi

echo "Security review passed."

This is the simplest possible integration. The exit code from the harness indicates whether the agent ran successfully (0) or encountered a harness-level error (non-zero). The content of stdout is yours to parse.

JSON Output — Full Envelope

--output-format json waits for the agent to complete and emits a single JSON object:

{
  "result": "PASS",
  "cost_usd": 0.0041,
  "duration_ms": 6820,
  "session_id": "sess_01XYZ...",
  "stop_reason": "end_turn",
  "tool_calls": [
    { "tool": "Bash", "input": { "command": "git diff origin/main...HEAD" }, "duration_ms": 312 }
  ]
}

Use json format when you need the cost or duration for budgeting, when you need the session_id for log correlation, or when you want to verify that specific tools were (or were not) called:

RESULT=$(claude -p "Run the test suite" --output-format json)

# Verify cost stayed under budget
COST=$(echo "${RESULT}" | jq -r '.cost_usd')
if (( $(echo "${COST} > 0.50" | bc -l) )); then
  echo "::warning::Agent cost ${COST} USD exceeded budget threshold"
fi

# Extract the text result
echo "${RESULT}" | jq -r '.result'

stream-json Output — Realtime Processing

stream-json emits newline-delimited JSON (NDJSON) events as they arrive. Each line is a complete JSON object. The stream is the format for pipelines that need to process output incrementally — forwarding events to a log aggregator, streaming tool-call output to a dashboard, or updating a GitHub check in real time.

Event types in the stream:

{ "type": "text",      "content": "Running tests...",    "turn": 1 }
{ "type": "tool_use",  "tool": "Bash", "input": {...},   "id": "toolu_01..." }
{ "type": "tool_result", "tool_use_id": "toolu_01...",   "content": "...", "is_error": false }
{ "type": "text",      "content": "All 47 tests passed.", "turn": 1 }
{ "type": "result",    "result": "All 47 tests passed.", "cost_usd": 0.0071, "session_id": "..." }

The final event always has "type": "result". Your consumer knows the stream is complete when it sees this event.

A CI step that forwards streaming output to a GitHub step summary:

#!/usr/bin/env bash
set -euo pipefail

SUMMARY_FILE="${GITHUB_STEP_SUMMARY:-/dev/null}"

claude -p "Run the full test suite and summarize failures" \
  --output-format stream-json \
  --allowedTools "Bash,Read" | \
while IFS= read -r line; do
  TYPE=$(echo "${line}" | jq -r '.type')
  case "${TYPE}" in
    text)
      # Forward model narration to step summary
      echo "${line}" | jq -r '.content' >> "${SUMMARY_FILE}"
      ;;
    tool_result)
      # Forward tool output to step summary as collapsible block
      TOOL=$(echo "${line}" | jq -r '.tool_use_id // "unknown"')
      CONTENT=$(echo "${line}" | jq -r '.content // ""')
      printf '<details><summary>Tool output (%s)</summary>\n\n```\n%s\n```\n\n</details>\n' \
        "${TOOL}" "${CONTENT}" >> "${SUMMARY_FILE}"
      ;;
    result)
      COST=$(echo "${line}" | jq -r '.cost_usd')
      echo "Agent completed. Cost: \$${COST}" >> "${SUMMARY_FILE}"
      ;;
  esac
done

stream-json Input — Streaming Prompts

--input-format stream-json reverses the direction: the harness reads NDJSON events from stdin as the prompt. This lets you stream a large prompt — a long diff, a large log file, build artifacts — without buffering the whole thing into a shell variable.

# Stream a large log file as the prompt context
{
  echo '{"type": "text", "content": "Analyze the following build log for root cause:"}'
  cat build.log | jq -Rs '{"type": "text", "content": .}'
} | claude -p --input-format stream-json --output-format json

Fallback Models

--fallback-model takes a comma-separated list of model IDs. When the primary model returns a rate-limit or overload error, the harness automatically retries with the first fallback model, then the second, and so on. This flag is only available with --print.

claude -p "Generate release notes from the git log" \
  --output-format json \
  --fallback-model claude-haiku-4-5,claude-sonnet-4-6

In a CI environment where you have budget-tier and quality-tier models, fallback model lists let you write pipelines that try the expensive model first and fall back gracefully instead of failing the build on a rate limit.

Session Headers for Proxy Aggregation

When you run print-mode agents behind a proxy (a common pattern in enterprise environments that centralize LLM access), the X-Claude-Code-Session-Id header allows log correlation. Each print-mode invocation generates a session_id in its output envelope. Forward it as a response header in your proxy and you can join harness logs to proxy logs by session.

34.3 claude ultrareview

ultrareview is a cloud-hosted multi-agent code review command built into the harness. It is not a wrapper around a single model call — it dispatches multiple specialized agents in parallel, each examining a different aspect of the diff, then synthesizes their findings into a single structured report.

claude ultrareview [options] [target]

  Run a cloud-hosted multi-agent code review of the current branch
  (or a PR number / base branch) and print the findings.

Options:
  --target <ref>       Branch, PR number, or commit range (default: current branch vs main)
  --format <fmt>       text (default), json, markdown
  --severity <level>   Filter findings below this level: info, warning, error, critical
  --output <path>      Write findings to file instead of stdout

What Ultrareview Does

The multi-agent architecture behind ultrareview runs agents in parallel across several review dimensions:

flowchart TD
    A[claude ultrareview] --> B[Diff Fetcher]
    B --> C{Dispatch}
    C --> D[Security Agent]
    C --> E[Logic Agent]
    C --> F[Performance Agent]
    C --> G[Test Coverage Agent]
    C --> H[Style/Convention Agent]
    D & E & F & G & H --> I[Synthesis Agent]
    I --> J[Structured Report]

The security agent looks for OWASP Top 10 patterns, hardcoded secrets, injection vectors, and authentication gaps. The logic agent looks for off-by-one errors, null dereferences, race conditions, and incorrect assumptions about API behavior. The performance agent flags N+1 queries, unbounded loops, and memory leak patterns. The test coverage agent compares changed lines against test coverage data and flags untested paths. The style/convention agent checks against your project's CLAUDE.md and coding conventions.

All five agents run concurrently. The synthesis agent receives all findings, deduplicates overlapping observations, assigns severity levels, and produces the final report.

GitHub Actions Integration

The canonical ultrareview workflow runs on every pull request:

name: Code Review

on:
  pull_request:
    types: [opened, synchronize, reopened]

permissions:
  contents: read
  pull-requests: write

jobs:
  ultrareview:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # ultrareview needs full history for diff computation

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Run ultrareview
        id: review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          claude ultrareview \
            --target ${{ github.event.pull_request.number }} \
            --format json \
            --output review.json

      - name: Parse findings
        id: parse
        run: |
          CRITICAL=$(jq '.findings | map(select(.severity == "critical")) | length' review.json)
          ERROR=$(jq '.findings | map(select(.severity == "error")) | length' review.json)
          echo "critical=${CRITICAL}" >> "${GITHUB_OUTPUT}"
          echo "error=${ERROR}" >> "${GITHUB_OUTPUT}"

      - name: Post review comment
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const review = JSON.parse(fs.readFileSync('review.json', 'utf8'));
            const findings = review.findings;

            if (findings.length === 0) {
              await github.rest.issues.createComment({
                owner: context.repo.owner,
                repo: context.repo.repo,
                issue_number: context.issue.number,
                body: '**ultrareview**: No findings. All checks passed.'
              });
              return;
            }

            const rows = findings.map(f =>
              `| ${f.severity.toUpperCase()} | \`${f.file}:${f.line}\` | ${f.message} |`
            ).join('\n');

            const body = `**ultrareview findings**\n\n| Severity | Location | Finding |\n|---|---|---|\n${rows}\n\nGenerated with [Claude Code](https://claude.ai/claude-code)`;

            await github.rest.issues.createComment({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: context.issue.number,
              body
            });

      - name: Fail on critical findings
        if: steps.parse.outputs.critical > 0
        run: |
          echo "ultrareview found ${{ steps.parse.outputs.critical }} critical finding(s). Blocking merge."
          exit 1

A few design decisions worth noting:

fetch-depth: 0 is required. Ultrareview computes the diff by walking the merge base between the PR branch and main. Shallow clones do not have the history needed to find the merge base accurately. Always use fetch-depth: 0 for any harness operation that involves git history.

The step posts the full findings table as a PR comment and fails the job only on critical severity. Findings at error, warning, and info severity are surfaced to the author for review but do not block the merge. This is a deliberate policy choice — tune the threshold to your team's risk tolerance. A security-critical product might block on error; a docs repository might only block on critical.

Running ultrareview Locally

Ultrareview is not CI-only. During development, before pushing a branch:

# Review current branch against main
claude ultrareview

# Review against a specific base
claude ultrareview --target main

# Review a PR by number (requires GH_TOKEN in environment)
claude ultrareview --target 4217

# Filter to errors and above, write to file
claude ultrareview --severity error --output review.md --format markdown

Running ultrareview locally before pushing shifts the feedback loop left. Findings that would have blocked the CI job arrive before the build queue, before the reviewer's time is spent, before any branch protection rule fires.

34.4 Webhook Triggers: RemoteTrigger and Monitor

Print mode and ultrareview cover the synchronous pattern: a CI step calls the harness, waits for a result, continues. The asynchronous pattern — the harness responds to external events — uses RemoteTrigger and Monitor.

RemoteTrigger

RemoteTrigger is the harness's webhook primitive. It lets external systems call into a running harness session, delivering a payload that the agent can act on.

export interface RemoteTriggerInput {
  action: "list" | "get" | "create" | "update" | "run";
  trigger_id?: string;
  body?: { [k: string]: unknown };
}

Creating a trigger:

const trigger = await RemoteTrigger({
  action: "create",
  body: {
    name: "deploy-webhook",
    description: "Fires when a deployment finishes in the staging environment",
    secret: "{{ env.WEBHOOK_SECRET }}"
  }
});
// trigger.endpoint: "https://hooks.claude.ai/trigger/trig_01ABC..."
// trigger.id: "trig_01ABC..."

The returned endpoint is a URL. When you POST to it (with the correct X-Hub-Signature-256 header computed from your secret), the harness delivers your request body to the agent as an event.

Running a trigger from an external system:

// From within a harness session, run the trigger manually to test it:
await RemoteTrigger({
  action: "run",
  trigger_id: "trig_01ABC...",
  body: { environment: "staging", status: "success", version: "v2.4.1" }
});

Listing and inspecting triggers:

const triggers = await RemoteTrigger({ action: "list" });
// Returns array of { id, name, description, endpoint, last_fired_at }

const trigger = await RemoteTrigger({
  action: "get",
  trigger_id: "trig_01ABC..."
});

Wiring RemoteTrigger to a CI System

The pattern: CI pipeline posts to the trigger endpoint on completion; the harness agent processes the event.

# GitHub Actions — post-deploy notification
- name: Notify harness of deployment
  if: always()
  env:
    WEBHOOK_SECRET: ${{ secrets.HARNESS_WEBHOOK_SECRET }}
    TRIGGER_URL: ${{ secrets.HARNESS_TRIGGER_URL }}
  run: |
    PAYLOAD=$(jq -n \
      --arg env "staging" \
      --arg status "${{ job.status }}" \
      --arg version "${{ github.sha }}" \
      --arg run_url "${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}" \
      '{environment: $env, status: $status, version: $version, run_url: $run_url}')

    SIGNATURE=$(echo -n "${PAYLOAD}" | \
      openssl dgst -sha256 -hmac "${WEBHOOK_SECRET}" -binary | \
      xxd -p -c 256)

    curl -s -X POST "${TRIGGER_URL}" \
      -H "Content-Type: application/json" \
      -H "X-Hub-Signature-256: sha256=${SIGNATURE}" \
      -d "${PAYLOAD}"

The harness session receiving this trigger might look like:

// In a persistent background agent managing the staging environment
const trigger = await RemoteTrigger({ action: "get", trigger_id: DEPLOY_TRIGGER_ID });

// When the trigger fires, the agent receives the body as an event
// and can act: run smoke tests, update a status dashboard, alert on failure

if (event.status === "failure") {
  // Investigate the failed deployment
  await Bash({ command: `gh run view ${runId} --log-failed` });
  // Open a fix ticket, page on-call, etc.
}

Monitor for CI Event Watching

Where RemoteTrigger handles inbound webhooks (external system calls the harness), Monitor handles outbound observation (the harness watches an external system). The distinction matters when you do not control the external system's notification mechanism.

Watching a GitHub Actions run to completion:

const monitor = await Monitor({
  description: "Watching GitHub Actions run for feat/payment-flow",
  timeout_ms: 1800000,  // 30 minutes
  persistent: false,
  command: "gh run watch --exit-status"
});

gh run watch blocks until the run completes and exits with the run's status code. The Monitor tool wraps this in the harness's event infrastructure: when the command exits, the agent receives a completion event with the exit code. The agent can then decide what to do — merge the PR if green, investigate failures if red, alert the author in either case.

Watching a deployment for live health signals:

const monitor = await Monitor({
  description: "Staging deployment health check — WebSocket event stream",
  timeout_ms: 600000,  // 10 minutes
  persistent: false,
  ws: {
    url: "wss://staging.internal/events",
    protocols: ["deployment-events"]
  }
});

Each WebSocket frame arrives as a discrete event. The agent can evaluate each one — a deploy.complete event ends the watch, a health.degraded event triggers an investigation, a rollback.initiated event pages on-call.

Composing Monitor with Background Agents

The combination of Monitor and background agents gives you an always-on operations layer:

# Start a persistent CI watcher as a background agent
claude --bg "
You are the CI watch agent for this repository. 

1. Create a persistent Monitor that watches for GitHub Actions failures
   on the main branch using: gh run list --branch main --status failure --watch
2. For each failure, investigate the root cause using gh run view --log-failed
3. If the failure is a flaky test, auto-retry with: gh run rerun --failed <run-id>
4. If the failure is a real regression, open a GitHub issue with the root cause
   and a suggested fix branch.
5. Run until stopped.
"

# Check the agent's status
claude agents --json | jq '.[] | select(.name | contains("CI watch"))'

This is not a prototype — it is the pattern for autonomous CI operations. The agent runs indefinitely, responding to events. You stop it explicitly (claude agents stop <id>) or it stops when the session ends. During normal hours, it handles flaky test noise automatically. During incidents, it surfaces root cause faster than a human looking at the same log output.

34.5 Case Study: Feature-to-Production Pipeline

The previous sections covered the primitives in isolation. This section assembles them into a complete pipeline: from a feature request to a merged, reviewed, tested, deployed change. The pipeline is test-first — no code is written until a failing test exists.

Pipeline Overview

flowchart TD
    A([Feature Issue]) --> B[Agent: Write Failing Test]
    B --> C{Test Fails?}
    C -->|no| D[Error: Test Not Failing]
    C -->|yes| E[Agent: Implement Feature]
    E --> F[Agent: Run Tests]
    F --> G{All Green?}
    G -->|no| E
    G -->|yes| H[Agent: Commit + Push + PR]
    H --> I[ultrareview Check]
    I --> J{Findings?}
    J -->|critical| K[Agent: Address Findings]
    K --> H
    J -->|none/low| L[Human Approval Gate]
    L --> M[Merge]
    M --> N[RemoteTrigger: Deploy]
    N --> O[Monitor: Health Check]
    O --> P{Healthy?}
    P -->|yes| Q([Done])
    P -->|no| R[Agent: Rollback + Investigate]

The GitHub Actions Workflow

name: Feature Pipeline

on:
  issues:
    types: [labeled]  # trigger on "agent-implement" label

permissions:
  contents: write
  pull-requests: write
  issues: write

jobs:
  implement:
    if: contains(github.event.issue.labels.*.name, 'agent-implement')
    runs-on: ubuntu-latest
    env:
      ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
      GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Configure git identity
        run: |
          git config user.name "Claude Code"
          git config user.email "noreply@anthropic.com"

      - name: Write failing test
        id: test_first
        run: |
          ISSUE_TITLE="${{ github.event.issue.title }}"
          ISSUE_BODY="${{ github.event.issue.body }}"
          BRANCH_NAME="feat/$(echo "${ISSUE_TITLE}" | tr '[:upper:] ' '[:lower:]-' | sed 's/[^a-z0-9-]//g' | cut -c1-50)"
          echo "branch=${BRANCH_NAME}" >> "${GITHUB_OUTPUT}"

          claude -p "
          Issue #${{ github.event.issue.number }}: ${ISSUE_TITLE}

          ${ISSUE_BODY}

          Your task:
          1. Create branch ${BRANCH_NAME}
          2. Write a failing test that specifies the required behavior
          3. Run the test suite and confirm the new test fails
          4. Do NOT implement the feature yet — only the test
          5. Commit the failing test with message: 'test: add failing test for ${ISSUE_TITLE}'
          6. Push the branch
          " \
          --output-format json \
          --allowedTools "Bash,Read,Write,Edit" > test_result.json

          # Verify the test was written and is failing
          STOP_REASON=$(jq -r '.stop_reason' test_result.json)
          if [[ "${STOP_REASON}" != "end_turn" ]]; then
            echo "::error::Agent did not complete cleanly"
            exit 1
          fi

      - name: Implement feature
        run: |
          claude -p "
          The branch ${{ steps.test_first.outputs.branch }} has a failing test.
          Implement the minimum code required to make the test pass.
          Then run the full test suite. If any tests fail, fix them.
          Do not delete or modify the tests you just wrote.
          When all tests pass, stage and commit: 'feat: implement ${{ github.event.issue.title }}'
          Push to origin.
          " \
          --output-format stream-json \
          --allowedTools "Bash,Read,Write,Edit" | \
          jq -r 'select(.type == "text") | .content'

      - name: Open pull request
        id: open_pr
        run: |
          RESULT=$(claude -p "
          Open a PR from branch ${{ steps.test_first.outputs.branch }} to main.
          Link it to issue #${{ github.event.issue.number }}.
          The PR title should match the issue title.
          Include in the body:
          - A summary of what was implemented
          - The test strategy (test-first)
          - 'Closes #${{ github.event.issue.number }}'
          Return only the PR number on the last line of your response.
          " \
          --output-format text \
          --allowedTools "Bash")

          PR_NUMBER=$(echo "${RESULT}" | tail -1)
          echo "pr_number=${PR_NUMBER}" >> "${GITHUB_OUTPUT}"

      - name: Run ultrareview
        id: ultrareview
        run: |
          claude ultrareview \
            --target ${{ steps.open_pr.outputs.pr_number }} \
            --format json \
            --output ultrareview.json

          CRITICAL=$(jq '.findings | map(select(.severity == "critical")) | length' ultrareview.json)
          echo "critical=${CRITICAL}" >> "${GITHUB_OUTPUT}"

      - name: Address critical findings
        if: steps.ultrareview.outputs.critical > 0
        run: |
          FINDINGS=$(jq '.findings | map(select(.severity == "critical"))' ultrareview.json)

          claude -p "
          The ultrareview of your PR found critical issues. Address all of them.

          Critical findings:
          ${FINDINGS}

          Fix each one, run tests to verify nothing broke, and commit.
          " \
          --output-format stream-json \
          --allowedTools "Bash,Read,Write,Edit" | \
          jq -r 'select(.type == "text") | .content'

      - name: Post review summary
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const review = JSON.parse(fs.readFileSync('ultrareview.json', 'utf8'));
            const count = review.findings.length;
            const critical = review.findings.filter(f => f.severity === 'critical').length;

            const body = critical > 0
              ? `**ultrareview**: ${count} finding(s), ${critical} critical (addressed automatically). Ready for human review.`
              : count > 0
                ? `**ultrareview**: ${count} finding(s), none critical. Ready for human review.\n\n${review.findings.map(f => `- **${f.severity}** \`${f.file}:${f.line}\`: ${f.message}`).join('\n')}`
                : '**ultrareview**: No findings. This PR was implemented and reviewed autonomously.';

            github.rest.issues.createComment({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: ${{ steps.open_pr.outputs.pr_number }},
              body
            });

The Deployment Watcher

After the PR merges, a separate workflow fires the deploy and uses a background Monitor to watch the rollout:

name: Deploy and Watch

on:
  push:
    branches: [main]

jobs:
  deploy-and-watch:
    runs-on: ubuntu-latest
    env:
      ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
      HARNESS_TRIGGER_URL: ${{ secrets.HARNESS_TRIGGER_URL }}
      HARNESS_WEBHOOK_SECRET: ${{ secrets.HARNESS_WEBHOOK_SECRET }}
    steps:
      - name: Trigger deployment
        run: |
          # ... your actual deploy command here ...
          echo "Deploy initiated for ${{ github.sha }}"

      - name: Notify harness and watch
        run: |
          PAYLOAD=$(jq -n \
            --arg sha "${{ github.sha }}" \
            --arg status "deploying" \
            --arg run_url "${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}" \
            '{sha: $sha, status: $status, run_url: $run_url}')

          SIGNATURE=$(echo -n "${PAYLOAD}" | \
            openssl dgst -sha256 -hmac "${HARNESS_WEBHOOK_SECRET}" -binary | \
            xxd -p -c 256)

          curl -s -X POST "${HARNESS_TRIGGER_URL}" \
            -H "Content-Type: application/json" \
            -H "X-Hub-Signature-256: sha256=${SIGNATURE}" \
            -d "${PAYLOAD}"

          echo "Harness notified. Background agent watching deployment health."

The harness background agent receives the trigger and runs a Monitor against the health endpoint:

// Background agent session — starts when the repository is initialized
// Responds to the deploy-started trigger

const event = await waitForTrigger(DEPLOY_TRIGGER_ID);

if (event.status === "deploying") {
  const monitor = await Monitor({
    description: `Deployment health check — ${event.sha.slice(0, 8)}`,
    timeout_ms: 600000,
    persistent: false,
    command: `
      for i in $(seq 1 20); do
        STATUS=$(curl -s https://staging.example.com/health | jq -r '.status')
        echo "${STATUS}"
        if [[ "${STATUS}" == "healthy" ]]; then exit 0; fi
        sleep 30
      done
      echo "timeout"
      exit 1
    `
  });

  // Events arrive as health check results
  // On healthy: report success, close the deploy ticket
  // On timeout or error: trigger rollback, investigate, page on-call
}

What the Pipeline Delivers

Running the full pipeline produces:

  1. A test written before the implementation — the strongest possible specification of intended behavior
  2. An implementation that passes the tests plus the existing test suite
  3. A PR with full attribution, linked to the originating issue
  4. An ultrareview pass with critical findings addressed automatically
  5. A deployment watched by a background agent that can detect and respond to problems autonomously

The human is in the loop at one point: approving the PR. Every other step is autonomous and auditable. The git log shows every agent commit with Co-Authored-By attribution. The PR comment thread shows the ultrareview findings and what was done about them. The deployment monitor's events are captured in the harness session log.

Summary

CI/CD integration with the harness rests on four mechanisms:

Print mode is the bridge between the harness and any external system that calls subprocesses. --output-format text for simple pass/fail gates, --output-format json for full result envelopes, --output-format stream-json for realtime event processing. Match the format to what your consumer needs.

Ultrareview offloads the review workload to a multi-agent cloud system. One command, one CI step, structured findings. The cost of catching a critical security issue in CI is orders of magnitude lower than catching it in production.

RemoteTrigger and Monitor are the async complement to print mode. RemoteTrigger lets external systems reach into a running harness session. Monitor lets the harness watch external systems. Together they enable event-driven automation that runs whether or not a human is present.

Git attribution is not optional at scale. When agents are creating branches, committing changes, and opening PRs autonomously, the Co-Authored-By trailer and the Generated with Claude Code footer are the difference between an auditable system and an opaque one. Maintain the attribution configuration and treat it as a first-class operational concern.

The pipeline in §34.5 is not theoretical. Every component is a direct application of mechanisms covered in this chapter and the ones before it. The sophistication is not in any individual piece — it is in the composition.

Chapter 35 covers observability: how to instrument the harness so that when something in a pipeline like this fails, you know exactly where, why, and how to fix it without reading the full conversation history.
