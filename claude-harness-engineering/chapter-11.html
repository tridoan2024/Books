Chapter 11: The Agent Tool — Spawning Subagents

"A single model reasoning in a loop is a worker. A harness that spawns workers is a factory."

11.1 Core Parameters

The Agent tool is the most structurally significant tool in Claude Code's core six. Every other core tool interacts with the environment — files, shells, the user. Agent interacts with more instances of itself, turning a single agentic loop into a directed graph of them.

The interface is defined at the TypeScript level as AgentInput:

export interface AgentInput {
  description: string;       // 3-5 word task description
  prompt: string;            // the full task for the agent
  subagent_type?: string;    // built-in or custom agent type
  model?: "sonnet" | "opus" | "haiku" | "fable";
  run_in_background?: boolean;  // default true in newer versions
  name?: string;             // makes agent addressable via SendMessage
  isolation?: "worktree" | "remote";
}

Each parameter has a distinct role and failure mode when misused.

description — The 3-5 Word Contract

The description is not a comment. It is a structural identifier. The harness displays it in the terminal UI while the agent runs, writes it to audit logs, uses it as the label in task tracking, and returns it in the async output payload so callers can correlate results to intent.

The constraint — 3 to 5 words — is intentional. If you cannot describe what an agent is doing in 3 to 5 words, the agent is probably doing too many things. Well-formed descriptions:

"Analyze auth module security"
"Review API endpoint coverage"
"Refactor database connection pool"

Poorly-formed descriptions that appear in practice:

"Do the thing we discussed"
"Fix bugs and stuff"
"Review everything in the whole project and also check for security issues and performance problems"

The last example is not just bad UX — it signals a design problem. An agent with an unfocusable description is probably an agent that will produce unfocusable output.

prompt — Self-Contained Task Package

The prompt is the most consequential parameter. It is the only thing the subagent receives from the parent. There is no implicit context transfer. The subagent starts fresh.

This is the most common mistake engineers make when first using Agent: they write a short prompt assuming the subagent shares the parent's context:

// WRONG: subagent has no idea what "the auth module" refers to
await Agent({
  description: "Review auth security",
  prompt: "Review the auth module for security issues and report your findings.",
});

The subagent will either make a broad guess about what "auth module" means, read the entire codebase looking for auth-related files, or ask a clarifying question it has no way to get answered. The fix is to make the prompt self-contained:

// CORRECT: prompt contains everything the subagent needs
await Agent({
  description: "Review auth security",
  prompt: `You are reviewing the authentication module of a Python web application.
  
The repository is at /Users/DOANTX26/Documents/2026/myapp.
The auth module lives at src/auth/ and contains:
- session.py: session management, timeout logic
- middleware.py: request authentication decorators
- tokens.py: JWT creation and validation

Review these files for:
1. Hardcoded secrets or credentials
2. Insecure token validation (algorithm confusion, expired-but-accepted)
3. Missing authorization checks on session operations
4. Input validation gaps on user-supplied data

Return your findings as a structured list with: file path, line number, severity (CRITICAL/HIGH/MEDIUM/LOW), and a one-line description. End with a summary count per severity level.`,
});

The rule: write every Agent prompt as if the subagent has never seen your codebase, never read your conversation, and knows nothing except what you tell it in the prompt.

model — Matching Cost to Task

The four model options map to deliberate cost/capability tradeoffs:

ModelBest for
haikuFast, token-cheap tasks: file scanning, regex search, format conversion, structured extraction from known schemas
sonnetMost multi-step tasks: code review, debugging, refactoring, writing documentation
opusTasks requiring deep reasoning: architecture decisions, complex security analysis, synthesizing contradictory information
fableSpecialized creative and long-form writing tasks

The default when model is omitted is sonnet. That is the right default for most tasks. Reach for haiku when you are spawning many parallel agents for tasks that are essentially structured transformation. Reach for opus when you need the subagent to reason through ambiguous, high-stakes decisions and the latency cost is worth it.

A common pattern is to use haiku for the fan-out stage of a map/reduce workflow and sonnet for the reduce stage that synthesizes findings:

// Fan out with haiku — fast and cheap
const scanJobs = files.map(f => Agent({
  description: "Scan file for secrets",
  prompt: buildSecretScanPrompt(f),
  model: "haiku",
}));

// Reduce with sonnet — needs reasoning to synthesize
const synthesis = await Agent({
  description: "Synthesize security findings",
  prompt: buildSynthesisPrompt(await Promise.all(scanJobs)),
  model: "sonnet",
});

11.2 Execution Modes

The run_in_background parameter controls whether the parent's control loop blocks while the subagent runs or continues immediately.

Background (Default)

In newer versions of Claude Code, run_in_background defaults to true. Calling Agent without specifying this parameter launches the subagent in the background and returns an async result:

// Returns immediately with status: "async_launched"
const result = await Agent({
  description: "Long security audit",
  prompt: auditPrompt,
  // run_in_background: true is the default
});

// result.status === "async_launched"
// result.outputFile contains the path where output will appear

The async return object contains the path where the subagent will write its completed output. You can poll this file to check progress, or register a ScheduleWakeup to be notified when it completes.

Background mode is the right choice for:

  • Tasks that take more than a few seconds
  • Independent work that can proceed in parallel with the parent
  • Fan-out patterns where you launch N agents simultaneously
  • Any task where you want the parent to remain responsive

Foreground (Synchronous)

Setting run_in_background: false blocks the parent's control loop until the subagent completes. The return value is the full AgentOutput struct:

const result = await Agent({
  description: "Validate schema format",
  prompt: validationPrompt,
  run_in_background: false,
});

// result.status === "completed"
// result.content contains the subagent's final text
// result.totalDurationMs tells you how long it took

Foreground mode is appropriate when:

  • The parent needs the subagent's output before it can proceed
  • The task is short enough that blocking is acceptable
  • You are building a pipeline where each stage feeds the next
  • You need the full AgentOutput metadata (token counts, tool stats) immediately

The mental model: background is async/await with a deferred await; foreground is async/await with an immediate await. Both are asynchronous in the sense that the subagent runs in its own context — foreground simply holds the parent at the join point.

sequenceDiagram
    participant P as Parent Agent
    participant A1 as Subagent 1 (bg)
    participant A2 as Subagent 2 (fg)

    P->>A1: Agent(..., run_in_background: true)
    Note over P: returns immediately with outputFile
    P->>A2: Agent(..., run_in_background: false)
    Note over P: BLOCKS here
    A2-->>P: AgentOutput (completed)
    Note over P: continues
    Note over A1: still running independently
    A1-->>P: writes to outputFile (async)

11.3 Built-in Agent Types

The subagent_type parameter selects from a set of built-in agent configurations. Each type pre-configures the subagent with a specific system prompt, tool set, and behavioral constraints optimized for a class of tasks.

Using a built-in type lets you skip writing the full system prompt for common tasks:

await Agent({
  description: "Review PR diff quality",
  prompt: "Review the diff at /tmp/pr-diff.patch for code quality issues.",
  subagent_type: "code-reviewer",
});

The built-in types and their configurations:

Explore

Read-only codebase navigation. Tools: Glob, Grep, Read, Bash — no Edit or Write. The behavioral constraint against mutation is enforced at the tool level, not by prompting. This means an Explore subagent genuinely cannot modify files regardless of what the prompt instructs.

Use Explore when you need to gather information without any risk of side effects. It is the appropriate type for the fan-out stage of a read/analyze/synthesize pattern.

code-reviewer

Evaluates code for quality, correctness, performance, and adherence to best practices. The system prompt primes it to prioritize actionable findings over commentary, cite specific file paths and line numbers, and tier issues by severity. Well-suited for pre-commit or pre-merge checks.

security-reviewer

Targets security-specific analysis: authentication and authorization logic, input validation gaps, hardcoded secrets, injection vectors, cryptographic misuse, and dangerous API usage. It references OWASP and CWE categories in its output. The system prompt does not overlap significantly with code-reviewer — you can usefully run both on the same codebase and get complementary findings.

debugger

Investigates errors, stack traces, and unexpected behavior. The system prompt emphasizes hypothesis formation before evidence gathering, systematic elimination of causes, and distinguishing root cause from symptoms. Useful for hard-to-reproduce bugs where you want a disciplined investigative process rather than a quick grep.

researcher

Deep research, tool comparison, and documentation synthesis. The researcher type is configured to use WebSearch and WebFetch aggressively and to structure its output with sources, tradeoffs, and a concrete recommendation. Use it when you need a decision brief, not a summary.

doc-writer

Creates and updates documentation: READMEs, ADRs, runbooks, API docs. The system prompt establishes a practitioner voice and instructs the agent to read existing documentation before writing, match established style, and verify all code references before including them.

Plan

Software architect for implementation planning. Returns a structured implementation plan: affected files, proposed changes, risks, and sequencing. Does not write code. The output is designed to be reviewed by a human or fed into another agent as the prompt for implementation. Use it before a large refactor when you want an explicit plan step.

general-purpose

No specialized configuration. A clean slate with the full tool surface available. Use it when the task does not fit any specific type, or when you are iterating on a custom prompt and do not want any built-in system prompt interfering.

claude-code-guide

Answers questions about Claude Code itself — its tools, configuration, behaviors, and internals. Useful when your harness needs to self-document or when you are building tooling that generates Claude Code configuration.

The built-in types are a starting point, not a ceiling. As shown in section 11.4, you can define custom agents that supersede or extend any of these patterns.

11.4 Custom Agents

When the built-in types are not precise enough, you define custom agents as Markdown files in .claude/agents/. The harness discovers these at startup and makes them available as values for subagent_type.

The file format uses YAML frontmatter followed by the agent's system prompt:

---
name: code-reviewer
description: Reviews code for quality, bugs, performance, and best practices.
tools: Read, Grep, Glob
model: sonnet
effort: high
memory: project
---

You are a senior software engineer performing a code review. You have been asked to review a specific piece of code and provide actionable feedback.

## Your Process

1. Read the files you have been asked to review
2. Identify issues across these dimensions:
   - **Correctness**: Logic errors, off-by-one, null handling, race conditions
   - **Security**: Input validation, SQL injection, credential exposure, insecure defaults
   - **Performance**: Unnecessary allocations, N+1 queries, missing indexes, synchronous I/O in hot paths
   - **Maintainability**: Missing types, unclear naming, copy-paste duplication, untested behavior

## Output Format

Structure your output as:
- A severity-ranked list of findings (CRITICAL > HIGH > MEDIUM > LOW > INFO)
- Each finding: `file_path:line_number — [SEVERITY] description`
- A brief summary section with total counts per severity

Be direct. Skip findings that are purely stylistic unless they indicate a maintainability risk.

Frontmatter Fields

FieldRequiredDescription
nameYesIdentifier used in subagent_type. Must match the filename stem.
descriptionYesOne-line description shown in tool selection and UI
toolsNoComma-separated list of tools this agent can use. Omit to allow all tools.
modelNoDefault model for this agent type. Caller can override via AgentInput.model.
effortNolow, medium, or high. Maps to thinking/effort budgets in the API.
memoryNoproject loads the project's CLAUDE.md. none gives a clean context.

The tools field is a security and focus boundary. A custom Explore-style agent with tools: Read, Grep, Glob genuinely cannot call Bash or Edit — the harness enforces this at the tool registry level. When building multi-agent pipelines, use the tools field to give each agent the minimum surface it needs. An agent that only needs to read files should not have Bash access.

Organizing Custom Agents

A mature project might have several agents:

.claude/agents/
├── code-reviewer.md        # quality + correctness
├── security-reviewer.md    # OWASP-focused security analysis
├── migration-planner.md    # database schema migration plans
├── changelog-writer.md     # git log → user-facing changelog
└── test-gap-finder.md      # identifies untested code paths

Each is purpose-built for a specific workflow. The migration planner has tools: Read, Bash (it needs to query the database schema) but not Edit (planning only). The changelog writer has tools: Bash only (it runs git log and formats output) with no file access needed.

11.5 Named Agents and Continued Conversations

The name parameter makes a subagent addressable. Once launched with a name, the parent can send follow-up messages to that specific agent instance and it will respond with full context of the prior exchange intact:

// Launch a named agent
await Agent({
  description: "Persistent review session",
  prompt: initialPrompt,
  name: "reviewer",
  run_in_background: false,
});

// Send a follow-up — the agent remembers the prior exchange
await SendMessage({
  to: "reviewer",
  message: "Now focus specifically on the token validation logic in tokens.py and check for algorithm confusion vulnerabilities.",
});

Named agents are a different execution model from spawning a new Agent call. Key differences:

New Agent CallNamed Agent via SendMessage
ContextFresh startFull prior conversation preserved
CostNew session overheadContinuation, no re-initialization
Use caseIndependent parallel tasksMulti-turn investigation
StateNone from priorComplete

Named agents are appropriate when:

  • You are conducting an investigation that requires back-and-forth with the same agent
  • The agent has accumulated valuable context (read files, formed hypotheses) that would be expensive to re-establish
  • You want the semantics of a conversation, not a function call

An unnamed Agent call is the right choice when:

  • The task is fully self-contained
  • You want guaranteed isolation (fresh context means no contamination from prior work)
  • You are running many parallel agents and do not need to address them individually

A critical point: a new Agent call — even with the same subagent_type and prompt — always starts fresh. There is no implicit memory between Agent invocations. If you launch an agent, receive its output, and then launch another agent expecting it to remember the first agent's work, you will get an entirely clean slate. Put the first agent's findings into the second agent's prompt explicitly.

11.6 Isolation Modes

The isolation parameter controls what environment the subagent operates in. Two modes exist: "worktree" and "remote".

Worktree Isolation

await Agent({
  description: "Refactor payment module",
  prompt: refactorPrompt,
  isolation: "worktree",
});

Worktree isolation creates a new git worktree for the subagent — a separate checkout of the repository at a new directory path, on a new branch. The subagent operates inside this worktree: its Read, Edit, Write, and Bash calls all land in the isolated directory. Changes it makes are committed to the worktree branch, not the parent's branch.

The setup overhead is 200–500ms. This is not negligible. For short-lived agents, the isolation cost may exceed the agent's actual work time.

When to use worktree isolation:

You need it when two or more parallel agents will mutate the same repository and their edits might conflict. Without isolation, Agent 1 and Agent 2 both editing src/api/routes.py simultaneously will interleave their changes non-deterministically — one will overwrite the other's edits, or produce a merged file that is syntactically broken.

With worktree isolation, each agent works in its own branch. The parent then merges or cherry-picks the results.

When not to use worktree isolation:

For the majority of Agent use cases. If agents are read-only (all Explore subagents), isolation adds cost with zero benefit. If agents mutate different, non-overlapping parts of the repository, they will not conflict without isolation. Reserve worktree for the specific case where parallel mutation of overlapping files is unavoidable.

graph TD
    P[Parent Agent<br/>main branch] -->|Agent isolation: worktree| A1[Subagent 1<br/>worktree/branch-1<br/>edits src/auth/]
    P -->|Agent isolation: worktree| A2[Subagent 2<br/>worktree/branch-2<br/>edits src/auth/]
    P -->|Agent no isolation| A3[Subagent 3<br/>main branch<br/>reads src/api/]
    A1 -->|merge| M[Parent merges results]
    A2 -->|merge| M
    A3 -->|output only| P

Remote Isolation

await Agent({
  description: "Run integration tests",
  prompt: testPrompt,
  isolation: "remote",
});

Remote isolation runs the subagent in a cloud environment — an ephemeral, separate machine. It always runs in the background (no foreground option for remote). The return includes a sessionUrl for monitoring and an outputFile path for collecting results:

// remote_launched return type
{
  status: "remote_launched",
  taskId: "task_abc123",
  sessionUrl: "https://claude.ai/agents/task_abc123",
  description: "Run integration tests",
  prompt: testPrompt,
  outputFile: "/tmp/claude-agents/task_abc123.output.json",
}

Use remote isolation when:

  • The task requires a clean environment (fresh dependencies, clean state)
  • You want to avoid side effects on the local machine
  • The task is long-running and you want it to survive the parent session ending
  • The task requires more resources than the local machine can provide

Remote isolation is significantly more expensive in both latency and cost than local execution. The cold start for a remote environment is measured in seconds, not milliseconds.

11.7 Output Structure

When a synchronous subagent completes (or when you read the outputFile of an async agent), you receive an AgentOutput. Understanding its structure matters for building robust multi-agent pipelines.

type AgentOutput = {
  status: "completed";
  agentId: string;
  agentType?: string;
  content: { type: "text"; text: string; citations?: unknown[] | null }[];
  resolvedModel?: string;
  modelsUsed?: string[];
  totalToolUseCount: number;
  totalDurationMs: number;
  totalTokens: number;
  usage: {
    input_tokens: number;
    output_tokens: number;
    cache_creation_input_tokens: number | null;
    cache_read_input_tokens: number | null;
    server_tool_use: { web_search_requests: number; web_fetch_requests: number } | null;
    service_tier: string | null;
    cache_creation: {
      ephemeral_1h_input_tokens: number;
      ephemeral_5m_input_tokens: number;
    } | null;
  };
  toolStats?: {
    readCount: number;
    searchCount: number;
    bashCount: number;
    editFileCount: number;
    linesAdded: number;
    linesRemoved: number;
    otherToolCount: number;
  };
  prompt: string;
  worktreePath?: string;
  worktreeBranch?: string;
}

Fields Worth Examining

content is an array, not a string. In practice, most subagents return a single text block, but the array structure means you must access result.content[0].text to get the string. Forgetting this and treating content as a string is a common bug that produces [object Object] in downstream prompts.

resolvedModel vs modelsUsed — resolvedModel is the model the agent was instantiated with. modelsUsed is the list of models actually invoked during the run, which may differ if the agent internally spawned its own subagents that used different models.

toolStats is the most actionable diagnostic field. If a security review agent reports readCount: 3 on a 200-file codebase, something went wrong — it did not look at enough code. If a refactor agent shows linesAdded: 1200, linesRemoved: 8, that is a suspicious ratio worth investigating. Build monitoring on toolStats when running agents in production pipelines.

totalDurationMs is wall-clock time from the moment the agent received its prompt to when it returned. This includes all API call latency and tool execution time. It is useful for SLA monitoring and for deciding whether to upgrade or downgrade the model for a given task.

usage.cache_read_input_tokens tells you how much context was served from cache. In a fan-out pattern where many agents receive similar system prompts, high cache hit rates meaningfully reduce cost. The harness handles cache warming automatically — understanding the field lets you verify it is working.

The Null Case

Agent returns null if the user skips or cancels the agent mid-run. Production code must handle this:

const result = await Agent({
  description: "Analyze test coverage",
  prompt: coveragePrompt,
  run_in_background: false,
});

if (result === null) {
  // User skipped the agent — handle gracefully
  return { skipped: true, findings: [] };
}

const text = result.content[0]?.text ?? "";

Omitting the null check and immediately accessing result.content will throw in interactive sessions where the user presses Escape while an agent is running.

11.8 Async Output and Progress Checking

Background agents (the default) return the async_launched variant of AgentOutput:

{
  status: "async_launched";
  agentId: string;
  description: string;
  resolvedModel?: string;
  modelsUsed?: string[];
  prompt: string;
  outputFile: string;
  canReadOutputFile?: boolean;
}

The outputFile path is where the agent will write its completed AgentOutput struct as JSON when it finishes. Polling this file is how you check progress:

async function waitForAgent(outputFile: string, pollIntervalMs = 5000): Promise<AgentOutput> {
  while (true) {
    try {
      const raw = await fs.readFile(outputFile, "utf-8");
      const result = JSON.parse(raw) as AgentOutput;
      if (result.status === "completed") {
        return result;
      }
    } catch {
      // File not yet written — agent still running
    }
    await sleep(pollIntervalMs);
  }
}

The canReadOutputFile boolean tells you whether the current process has filesystem access to the output path. For remote agents, this will be false — the output file lives in the cloud environment, not locally. In that case, you collect results through the sessionUrl or a configured webhook, not by polling a local file.

ScheduleWakeup Integration

The harness provides ScheduleWakeup as a more efficient alternative to polling. Rather than checking every N seconds, you register a wakeup that fires when an agent completes:

// Launch background agent
const launched = await Agent({
  description: "Full codebase audit",
  prompt: auditPrompt,
  name: "auditor",
});

// Register wakeup rather than polling
await ScheduleWakeup({
  message: "Auditor agent complete — read results and synthesize report",
  triggerOnAgentComplete: launched.agentId,
});

// Parent session can end here; wakeup will restart it

This is the production pattern for long-running agents. Polling every 5 seconds for an agent that will run for 3 minutes wastes context and keeps the parent session alive unnecessarily.

11.9 Lab: 3-Agent Review System

This lab builds a review pipeline that launches three independent specialized agents in parallel, collects their findings, and synthesizes a unified report. The architecture demonstrates several patterns from the preceding sections: parallel fan-out, self-contained prompts, output structure handling, and reduce-phase synthesis.

The Architecture

flowchart TD
    P[Orchestrator Agent] -->|parallel launch| A1[Code Reviewer<br/>haiku]
    P -->|parallel launch| A2[Security Reviewer<br/>sonnet]
    P -->|parallel launch| A3[Test Gap Finder<br/>haiku]
    A1 -->|AgentOutput| C[Synthesizer<br/>sonnet]
    A2 -->|AgentOutput| C
    A3 -->|AgentOutput| C
    C --> R[Unified Report]

The orchestrator launches three agents simultaneously, waits for all three to complete, then passes all three outputs to a synthesis agent. The synthesis agent does not do any additional analysis — its job is to de-duplicate findings, resolve conflicts between reviewers, and produce a single prioritized report.

The Orchestrator

async function runTripleReview(targetPath: string): Promise<string> {
  const repoContext = `
Repository: ${targetPath}
Run: find "${targetPath}/src" -name "*.py" -o -name "*.ts" | head -50
Review all files found.`;

  // Launch all three in parallel — foreground so we block until all complete
  const [codeResult, secResult, testResult] = await Promise.all([
    Agent({
      description: "Review code quality",
      prompt: buildCodeReviewPrompt(targetPath, repoContext),
      subagent_type: "code-reviewer",
      model: "haiku",
      run_in_background: false,
    }),
    Agent({
      description: "Review security posture",
      prompt: buildSecurityReviewPrompt(targetPath, repoContext),
      subagent_type: "security-reviewer",
      model: "sonnet",
      run_in_background: false,
    }),
    Agent({
      description: "Find test coverage gaps",
      prompt: buildTestGapPrompt(targetPath, repoContext),
      model: "haiku",
      run_in_background: false,
    }),
  ]);

  // Handle null (user cancelled one or more agents)
  if (!codeResult || !secResult || !testResult) {
    throw new Error("One or more review agents were cancelled");
  }

  // Extract text from content arrays
  const codeFindings = codeResult.content[0]?.text ?? "(no output)";
  const secFindings = secResult.content[0]?.text ?? "(no output)";
  const testFindings = testResult.content[0]?.text ?? "(no output)";

  // Log tool usage for monitoring
  console.error(`Code reviewer: ${codeResult.toolStats?.readCount ?? 0} files read, ${codeResult.totalDurationMs}ms`);
  console.error(`Security reviewer: ${secResult.toolStats?.readCount ?? 0} files read, ${secResult.totalDurationMs}ms`);
  console.error(`Test gap finder: ${testResult.toolStats?.readCount ?? 0} files read, ${testResult.totalDurationMs}ms`);

  // Synthesize
  const synthesis = await Agent({
    description: "Synthesize review findings",
    prompt: buildSynthesisPrompt(codeFindings, secFindings, testFindings),
    model: "sonnet",
    run_in_background: false,
  });

  if (!synthesis) {
    throw new Error("Synthesis agent was cancelled");
  }

  return synthesis.content[0]?.text ?? "(synthesis produced no output)";
}

The Prompt Builders

Each prompt is fully self-contained. The reviewers receive the repository path, a description of what they are looking for, and explicit output format instructions.

function buildCodeReviewPrompt(targetPath: string, repoContext: string): string {
  return `You are a senior engineer performing a code quality review.

${repoContext}

Read the source files at ${targetPath}/src/ and review them for:
- Type safety issues (missing types, unsafe casts, implicit any)
- Error handling gaps (uncaught exceptions, swallowed errors, missing null checks)
- Performance anti-patterns (synchronous I/O in async contexts, unnecessary loops, memory leaks)
- Maintainability issues (deeply nested logic, functions over 50 lines, unexplained magic numbers)

OUTPUT FORMAT:
Return a JSON array. Each element:
{
  "file": "relative/path/to/file.py",
  "line": 42,
  "severity": "CRITICAL" | "HIGH" | "MEDIUM" | "LOW",
  "category": "type-safety" | "error-handling" | "performance" | "maintainability",
  "description": "One sentence describing the issue."
}

End with a plain-text summary: total findings by severity.`;
}

function buildSecurityReviewPrompt(targetPath: string, repoContext: string): string {
  return `You are a security engineer performing a vulnerability assessment.

${repoContext}

Read the source files at ${targetPath}/src/ and identify:
- Hardcoded credentials, API keys, or secrets
- SQL injection or command injection vectors
- Authentication logic flaws (missing checks, bypassable conditions, algorithm confusion)
- Input validation gaps on user-supplied data
- Insecure cryptographic usage (weak algorithms, static IVs, predictable randomness)
- Exposed internal error details in API responses

Reference OWASP Top 10 and CWE categories where applicable.

OUTPUT FORMAT:
Return a JSON array. Each element:
{
  "file": "relative/path/to/file.py",
  "line": 42,
  "severity": "CRITICAL" | "HIGH" | "MEDIUM" | "LOW",
  "cwe": "CWE-89",
  "owasp": "A03:2021",
  "description": "One sentence describing the vulnerability."
}

End with a plain-text summary: total findings by severity and whether immediate remediation is required.`;
}

function buildTestGapPrompt(targetPath: string, repoContext: string): string {
  return `You are a QA engineer identifying test coverage gaps.

${repoContext}

Read the source files at ${targetPath}/src/ and ${targetPath}/tests/ (if it exists).

For each source module, identify:
- Functions or methods with no corresponding test
- Error paths that are only tested in the happy path
- Edge cases absent from tests (empty input, None, boundary values, concurrent access)

OUTPUT FORMAT:
Return a JSON array. Each element:
{
  "source_file": "relative/path/to/source.py",
  "function": "function_name",
  "gap_type": "no-test" | "missing-error-path" | "missing-edge-case",
  "description": "One sentence describing what is untested."
}

End with a count of untested functions vs total functions found.`;
}

The Synthesis Prompt

The synthesizer receives the raw output of all three reviewers. Its job is editorial, not analytical.

function buildSynthesisPrompt(
  codeFindings: string,
  secFindings: string,
  testFindings: string
): string {
  return `You are synthesizing findings from three independent code reviewers into a unified engineering report.

## Code Quality Findings
${codeFindings}

## Security Findings
${secFindings}

## Test Coverage Gaps
${testFindings}

Produce a unified report with the following structure:

### Executive Summary
Two to three sentences. Total issue count, highest severity found, and one headline risk.

### Critical and High Priority Issues
List only CRITICAL and HIGH severity findings, de-duplicated. If the code reviewer and security reviewer both flagged the same line for related reasons, merge them into one finding and note both perspectives. Format: \`file:line — [SEVERITY] description\`

### Medium Priority Issues
Same format. Group by category (security / code quality / test coverage).

### Low Priority Issues
Aggregate by category only — no individual line citations needed at this severity.

### Recommended Action Order
Three to five specific, ordered remediation steps. Focus on what to fix first given dependencies and blast radius.

Be direct. No boilerplate. Every sentence in the report should inform a decision.`;
}

Running the Lab

# From the project root
claude -p "Run the triple review system on the src/ directory and save the report to /tmp/review-report.md" \
  --allowedTools "Agent,Read,Bash,Write"

Or integrate it into an existing harness session by calling runTripleReview("/path/to/project") from an Agent prompt.

What the Lab Demonstrates

Context isolation in practice. Each reviewer receives a self-contained prompt. You can verify this works correctly by checking the toolStats.readCount on each result — each agent should have independently read the source files rather than receiving pre-loaded content from the parent.

Model selection by task. The code reviewer and test gap finder use haiku — their tasks are essentially structured extraction from source files, which does not require deep reasoning. The security reviewer uses sonnet because recognizing subtle authentication flaws and algorithm confusion vulnerabilities benefits from stronger reasoning. The synthesizer uses sonnet because de-duplication and editorial prioritization require judgment calls.

Defensive output handling. The orchestrator checks for null from each agent (user cancellation), accesses content[0]?.text with a fallback, and logs toolStats for monitoring. These are not optional niceties — they are the difference between a pipeline that degrades gracefully and one that throws in production.

Synthesis as a first-class step. The synthesizer does not receive the raw source code. It receives only the reviewers' output. This is intentional: the synthesis task is fundamentally different from the analysis tasks, it should not be contaminated with thousands of lines of source code that it does not need, and the smaller context makes the synthesis step faster and cheaper.

Summary

The Agent tool transforms a single agentic loop into a directed workflow. The key behaviors to internalize:

  • Subagents start with no context from the parent. Every prompt must be self-contained.
  • Named agents preserve conversation state; new Agent calls always start fresh.
  • Background execution is the default; foreground blocks until completion.
  • Worktree isolation is expensive (200–500ms) and necessary only when parallel agents mutate overlapping files.
  • The AgentOutput.content field is an array — access content[0].text, never treat it as a string.
  • Agent returns null on user cancellation; production code must handle this.
  • Match model to task: haiku for structured extraction, sonnet for reasoning, opus for deep ambiguous analysis.
  • toolStats is the primary diagnostic signal for whether an agent actually did the work you expected.

The three-agent review system in the lab is a minimal but complete pattern for parallel multi-agent coordination. The same architecture — fan out with specialized agents, collect structured output, synthesize with a reduce-phase agent — applies to code migration, documentation generation, security auditing, and any other task that benefits from independent perspectives on the same codebase.
