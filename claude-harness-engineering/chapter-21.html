Chapter 21: Model Selection and Routing

"Sending every task to Opus is like renting a supercomputer to check your email. The harness should know the difference."

Every request your harness sends to the Claude API carries an implicit model choice. If you have never thought about that choice explicitly, the harness has been making it for you — usually defaulting to whichever model was most capable at install time. This chapter makes that choice explicit, systematic, and cheap.

Model selection is not a one-time decision. It is a runtime routing problem. The right model depends on task complexity, latency requirements, cost budgets, and whether the current primary is overloaded. A harness that treats model selection as a static configuration is leaving performance and money on the table. A harness that treats it as a first-class concern routes intelligently — escalating to Opus when reasoning depth matters, running Haiku for high-volume classification, keeping Sonnet as the workhorse for the median case, and falling back gracefully when a model is unavailable.

This chapter builds the full picture: what each model tier is for, every mechanism the harness exposes to control model selection, how those mechanisms compose, and a working cost-aware routing layer in the lab section.

21.1 Model Tiers

Claude Code exposes four logical tiers, each mapping to one or more concrete model IDs.

┌─────────────────────────────────────────────────────────────┐
│                      MODEL TIERS                            │
│                                                             │
│  opus   ──── claude-opus-4-8                               │
│               claude-opus-4-7                               │
│               claude-opus-4-6                               │
│                                                             │
│  sonnet ──── claude-sonnet-4-6                             │
│                                                             │
│  haiku  ──── claude-haiku-4-5-20251001                     │
│                                                             │
│  fable  ──── (experimental / specialized routing)         │
└─────────────────────────────────────────────────────────────┘

Opus — Maximum Reasoning Depth

The Opus tier is the highest-capability family. It produces the best output on tasks requiring multi-step reasoning, large-context synthesis, ambiguous problem decomposition, and agentic decisions with high downstream consequence. You pay for this in tokens-per-second and per-call cost.

Use Opus when:

  • The task has a correctness requirement — architecture decisions, security assessments, legal analysis, production code changes where a wrong answer causes an incident
  • The context window is large and the relevant signal is sparse — Opus loses less fidelity when synthesizing a 100K-token codebase into a 3-paragraph summary
  • The task involves non-obvious reasoning chains — "which of these six approaches has the best failure mode under partial network partition" is an Opus question
  • You are orchestrating a workflow and need the conductor to be sharp even if the workers are fast

Within the Opus family, the harness resolves the "opus" alias to the latest available Opus model by default. The concrete IDs — claude-opus-4-8, claude-opus-4-7, claude-opus-4-6 — let you pin a specific generation when you need reproducibility across releases.

Fast mode is Opus-specific. This is a common point of confusion. When you enable fast mode (covered in 21.3), you are not switching to a cheaper model — you are running Opus with a latency-optimized inference profile. The capability ceiling stays the same; the streaming behavior changes. Fast mode is available on Opus 4.8, 4.7, and 4.6.

Sonnet — The Production Workhorse

Sonnet is the default model for most Claude Code workflows. It represents the practical optimum: strong reasoning, solid code generation, large context handling, at roughly half the cost and noticeably better latency than Opus.

Use Sonnet when:

  • The task is well-scoped — "refactor this function", "write tests for this module", "explain what this regex does"
  • You are running an interactive session where latency matters more than maximum depth
  • You are building a multi-agent workflow and need capable-but-fast workers that run in parallel
  • You cannot predict task complexity in advance — Sonnet covers the wide middle of the distribution well

claude-sonnet-4-6 is the current production ID. For most harness deployments, Sonnet is where you start and where you stay until profiling shows you need more.

Haiku — High-Throughput Classification and Screening

Haiku (claude-haiku-4-5-20251001) is the speed and cost tier. It is substantially faster and cheaper than Sonnet at the cost of reasoning depth and reliability on complex tasks.

Use Haiku when:

  • Throughput is the constraint — you are processing thousands of items in a pipeline and can tolerate occasional errors
  • The task is simple and structurally defined — keyword extraction, classification into a fixed taxonomy, format conversion, short summarization
  • You need a fast pre-filter before escalating high-confidence results to Sonnet or Opus
  • You are building a fallback path or a warming step where partial correctness is acceptable

Do not use Haiku for code that goes to production, for security-sensitive analysis, or for tasks where context exceeds a few thousand tokens. Its performance degrades sharply outside its sweet spot.

Fable — Experimental Routing

"fable" is exposed as a valid model alias in the AgentInput type but is not a public production tier in the same sense as Opus, Sonnet, and Haiku. It represents experimental or specialized routing that Anthropic may use for specific capabilities or internal testing. Do not build production routing logic that depends on Fable behavior — treat it as a reserved identifier until it is documented as stable.

Cost and Speed Reference

Exact pricing changes, but the order-of-magnitude relationships are stable:

TierRelative costRelative latencyBest for
OpusHighHighestDeep reasoning, high-stakes decisions
SonnetMediumMediumGeneral-purpose, interactive, default
HaikuLowLowestClassification, filtering, high-volume pipelines

When in doubt, start with Sonnet and profile. Escalate to Opus only when you have evidence that Sonnet is producing wrong answers on the task shape you care about. Downgrade to Haiku only when you have evidence that Haiku is right enough on the task shape you care about.

21.2 Selection Mechanisms

The harness exposes four distinct mechanisms for controlling model selection. They form a priority stack that mirrors the configuration cascade from Chapter 2.

The --model CLI Flag

The highest-priority runtime override. Accepts either a logical alias or a concrete model ID:

# Logical alias — resolves to latest in tier
claude --model opus

# Concrete ID — pins to a specific generation
claude --model claude-opus-4-8

# Specific Sonnet
claude --model claude-sonnet-4-6

# Haiku
claude --model claude-haiku-4-5-20251001

The flag is session-scoped. It applies for the duration of the session and overrides everything lower in the stack — the settings file model field, the default model, and (in interactive mode) whatever the /model picker shows as selected. When you exit the session and start a new one without the flag, the lower layers reassert.

Use --model for:

  • One-off experiments ("is Opus actually better on this task class?")
  • CI pipelines where the model should be explicit and auditable in the invocation log
  • Fallback scripting where you need to force a specific tier

The model Settings Field

The settings-layer equivalent of --model. Set it in ~/.claude/settings.json for a personal default, or in .claude/settings.json if you want to enforce a model at the project level:

{
  "model": "sonnet"
}

Valid values are the same as --model: logical aliases ("opus", "sonnet", "haiku", "fable") or concrete IDs. If you omit this field entirely, the harness uses its built-in default, which tracks the current recommended production model.

The practical pattern: set "model": "sonnet" globally if you are on a subscription plan where Sonnet has better rate limits than Opus. Set "model": "opus" if you are doing a focused deep-analysis session and want every query to hit maximum capability without typing --model opus each time.

The /model Interactive Picker

In interactive terminal sessions, /model opens a model picker that lets you switch the active model without leaving the session. The current selection is shown at the top of the picker. Switching is immediate — the next API call uses the new model.

This is useful when you start a session doing quick exploratory work (Sonnet), realize you need deeper analysis on a particular problem (switch to Opus), and then return to exploratory work (switch back to Sonnet). It avoids the latency cost of exiting and restarting a session.

The picker label for each entry is configurable via the ANTHROPIC_DEFAULT_*_MODEL_NAME environment variables (covered in 21.7). If you are running against a private deployment with custom model names, this is how you make the picker show your organization's labels instead of the upstream defaults.

Per-Agent Model Override

When spawning subagents, you can specify the model directly in the AgentInput:

await Agent({
  description: "Classify security severity",
  prompt: "Classify each of these 50 findings as critical/high/medium/low: ...",
  model: "haiku",   // fast, cheap, the task is structured
});

The model field accepts the same logical aliases as everywhere else: "sonnet" | "opus" | "haiku" | "fable". The subagent runs on that model regardless of what the parent session is using.

The same override is available in agent frontmatter for custom agents defined in .claude/agents/:

---
name: code-reviewer
model: sonnet
effort: high
---

You are a code reviewer. Your job is to...

This is the right place to set model when the agent's role has a stable model requirement. A security-audit agent that always needs Opus reasoning depth should encode that in its definition, not in every call site. A file-diff summarizer that always runs fine on Haiku should also encode that in its definition.

The precedence stack for per-agent model selection:

1. model field in AgentInput call       (highest)
2. model in agent frontmatter
3. model in settings.json
4. --model CLI flag
5. harness built-in default             (lowest)

21.3 Fast Mode

Fast mode is a latency optimization for the Opus tier. The documentation is precise on this point: fast mode does not downgrade to a smaller model. It runs Claude Opus with a faster output profile. Capability ceiling is unchanged; streaming behavior changes.

Enable it in three ways:

Settings file:

{
  "fastMode": true
}

Interactive toggle:

/fast

Typing /fast in a session toggles fast mode on or off. The current state is reflected in the session status display.

When to use it: Fast mode is appropriate when you need Opus reasoning depth but are latency-sensitive — a developer assistant session where you want near-Sonnet response times without dropping to Sonnet quality. It is specifically useful on tasks where Opus is materially better than Sonnet but where the user is waiting in real time for every token.

When not to use it: Fast mode is Opus-only. If your settings have "model": "sonnet", enabling "fastMode": true has no effect — Sonnet does not have a fast mode variant. Do not enable it if you are cost-sensitive; fast mode does not change the per-token price.

Available on: Opus 4.8, 4.7, 4.6.

21.4 Effort Levels

Effort levels are orthogonal to model selection. They control how hard the model works on a given task — specifically, how much reasoning and internal computation it applies before producing output. This maps roughly to the extended thinking budget.

The five levels, in ascending order of compute:

LevelWhen to use
lowQuick questions, format conversion, lookups — tasks where speed matters and the answer is not ambiguous
mediumThe default. General-purpose tasks where a reasonable answer in reasonable time is the goal
highTasks that benefit from careful consideration — code review, design critique, debugging — where you want more than the first-pass answer
xhighComplex multi-step problems where the model should reason carefully before committing — architecture decisions, security analysis
maxMaximum available compute. Use sparingly — the latency and cost increases are significant. Reserve for tasks where correctness is worth any price

Setting Effort Level

CLI flag — session-scoped:

claude --effort high
claude --effort max

Settings file — default for all sessions:

{
  "effortLevel": "high"
}

Per-agent frontmatter:

---
name: threat-model-agent
model: opus
effort: xhigh
---

The combination of model and effort level defines the compute budget for a task. A Haiku agent at low effort is appropriate for a classification step in a preprocessing pipeline. An Opus agent at xhigh effort is appropriate for the final synthesis step in a security audit. Most tasks sit between those extremes.

Effort and Cost

Higher effort levels consume more tokens — the model runs longer internal reasoning before producing output. The cost increase is non-linear at the upper end. max effort can be 3-5x the cost of medium on the same prompt. This makes effort level the primary cost-control lever after model selection.

Practical rule of thumb: set effortLevel to "high" in your global settings if you are doing engineering work. Use "medium" for interactive assistant sessions. Use "max" explicitly on a per-call basis when a task genuinely requires it — do not set it globally.

21.5 Extended Thinking

Extended thinking is a deeper form of computation than effort level alone. When enabled, the model engages a structured internal reasoning process — working through a problem before producing its output. The output reflects more deliberate analysis than the standard inference path.

Two settings control extended thinking:

{
  "alwaysThinkingEnabled": true,
  "showThinkingSummaries": true
}

alwaysThinkingEnabled — when true, every request goes through the extended thinking path. This is a strong setting: it increases latency on every call, regardless of whether the task benefits from it. The right use case is a dedicated analysis session where every prompt is a hard problem — auditing a codebase, designing a system, debugging an intermittent failure. It is not appropriate for an interactive session mixing hard questions with quick lookups.

showThinkingSummaries — opt-in. When true, the harness surfaces a summary of the model's reasoning chain alongside the response. This is off by default because most users do not want the reasoning surface — they want the answer. Enable it when:

  • You are debugging model outputs and need to understand why it reached a conclusion
  • You are building a system where the reasoning chain is itself an artifact (audit logs, explainability requirements)
  • You are evaluating whether the model is reasoning correctly or pattern-matching incorrectly

Thinking summaries are not the raw internal state — they are a condensed, human-readable representation of the key reasoning steps. They are useful for diagnosis; they are not a substitute for the answer.

Extended Thinking vs. Effort Level

These two controls are related but distinct:

  • Effort level scales the compute budget within the standard inference path
  • Extended thinking engages a qualitatively different reasoning mode

You can combine them: "effortLevel": "xhigh" with "alwaysThinkingEnabled": true is the maximum-depth configuration. Use it for tasks where you would consult a domain expert and want the model to behave like one.

21.6 Fallback Model

The --fallback-model flag addresses overload scenarios: when your primary model is at capacity, the harness can automatically route to a fallback rather than failing the request.

# Single fallback
claude --print --fallback-model sonnet "Analyze the auth module for vulnerabilities"

# Ordered fallback list (comma-separated, tried in order)
claude --print --fallback-model sonnet,haiku "Classify these 100 log entries"

The harness behavior:

  1. Sends the request to the primary model
  2. If the primary is overloaded, tries the first fallback in the comma-separated list
  3. At the start of each new user turn, re-tries the primary model before falling back again

The re-try-primary-per-turn behavior is deliberate. It prevents the fallback from becoming a sticky degraded state — if Opus was overloaded at 2:15pm but recovered by 2:20pm, the next turn's request goes to Opus, not permanently to Sonnet.

Constraint: --fallback-model only works with --print mode. It is designed for non-interactive automation — CI pipelines, background agents, batch processing — where you want resilience without manual intervention.

Typical patterns:

# High-stakes analysis: try Opus, fall back to Sonnet, never Haiku
claude --print --model opus --fallback-model sonnet \
  "Review this PR for security issues: $(cat diff.txt)"

# High-volume pipeline: try Sonnet, fall back to Haiku if overloaded
claude --print --model sonnet --fallback-model haiku \
  "Classify this log entry: ${log_line}"

Do not set a fallback model in settings — it is inherently a session-level concern tied to specific automation scripts. The right place for fallback configuration is in the script that calls Claude, not in shared project settings.

21.7 Third-Party Providers: Bedrock, Vertex, and Foundry

When your organization routes Claude traffic through Amazon Bedrock, Google Cloud Vertex AI, or Azure AI Foundry, the model IDs and available tiers differ from Anthropic direct. The harness provides environment variable overrides to bridge this gap without changing your application code.

Model Support Overrides

Each tier has two override variables:

# Tell the harness that your Bedrock/Vertex deployment supports Opus
ANTHROPIC_DEFAULT_OPUS_MODEL_SUPPORTS=1

# Tell the harness that your deployment supports Sonnet
ANTHROPIC_DEFAULT_SONNET_MODEL_SUPPORTS=1

# Tell the harness that your deployment supports Haiku
ANTHROPIC_DEFAULT_HAIKU_MODEL_SUPPORTS=1

These variables are capability declarations, not model IDs. They tell the harness which tiers are available at your endpoint, so the model picker, fallback logic, and per-agent routing work correctly against your deployment.

Model Name and Description Overrides

# Override the label shown in the /model picker
ANTHROPIC_DEFAULT_OPUS_MODEL_NAME="Enterprise Opus (Bedrock)"
ANTHROPIC_DEFAULT_SONNET_MODEL_NAME="Sonnet-Prod"
ANTHROPIC_DEFAULT_HAIKU_MODEL_NAME="Haiku-Fast"

# Override the description shown in the picker
ANTHROPIC_DEFAULT_OPUS_DESCRIPTION="High-capability model, billed at Enterprise tier"

These are UI-layer overrides. They do not change model behavior — they change what engineers see in the interactive picker and in log output. Useful when your organization has multiple Claude deployments (e.g., a cost-center-separated Bedrock endpoint for engineering and a separate Vertex endpoint for the data team) and you want engineers to see meaningful names rather than opaque model IDs.

Deployment Pattern

Set these variables in the environment your harness runs in — the CI runner, the Docker container, the shell profile for the team's dev machines:

# .env for Bedrock-routed team deployment
ANTHROPIC_BASE_URL=https://your-bedrock-endpoint.amazonaws.com/...
ANTHROPIC_DEFAULT_OPUS_MODEL_SUPPORTS=1
ANTHROPIC_DEFAULT_SONNET_MODEL_SUPPORTS=1
ANTHROPIC_DEFAULT_OPUS_MODEL_NAME="Opus (Bedrock/us-east-1)"
ANTHROPIC_DEFAULT_SONNET_MODEL_NAME="Sonnet (Bedrock/us-east-1)"

Do not commit these variables to version control. They belong in the same secret management layer as your API key.

21.8 Lab: Cost-Aware Routing Layer

This lab builds a routing layer that selects model tier based on task complexity signals. The goal is to run Haiku on simple tasks, Sonnet on medium tasks, and Opus on tasks that signal genuine reasoning depth — automatically, without manual per-call decisions.

The Problem

A naive harness sends every task to the default model. If your default is Opus, you pay Opus rates for every file summarization, every changelog entry, every classification. If your default is Sonnet, complex analysis tasks sometimes produce shallow answers. The fix is a routing layer that infers complexity from the task and dispatches accordingly.

Complexity Signals

For an engineering harness, the following signals correlate with model requirement:

High complexity → Opus
  - Task contains "architect", "design", "tradeoff", "security", "vulnerability"
  - Context window exceeds 50K tokens
  - Task is multi-part (contains enumerated sub-questions)
  - Previous attempt on lower model produced an answer flagged as inadequate

Medium complexity → Sonnet (default)
  - Standard code tasks: review, refactor, test, explain, implement
  - Single-file scope
  - Specific, bounded questions

Low complexity → Haiku
  - Classification into a fixed schema
  - Keyword extraction, tag assignment
  - Format conversion (JSON → YAML, markdown → plain text)
  - Single-fact lookups

Implementation

Create .claude/agents/routing-dispatcher.md:

---
name: routing-dispatcher
model: sonnet
effort: low
---

You are a task classifier. Your only job is to classify the complexity of a task prompt so that it can be routed to the correct model tier.

Given a task description, return a JSON object with:
- tier: "opus" | "sonnet" | "haiku"
- reason: one sentence explaining the classification

Classification rules:
- "haiku": classification tasks, format conversion, simple extraction, single-fact lookup
- "sonnet": code review, refactor, explain, implement, test — bounded, single-concern tasks
- "opus": architecture decisions, security analysis, multi-step reasoning, large-context synthesis

Return only the JSON object. No prose.

Now the routing layer in your workflow script:

export const meta = {
  name: 'cost-aware-dispatch',
  description: 'Route task to optimal model tier'
}

// Classify the task complexity using a cheap Haiku call
const classification = await agent(
  `Classify this task: "${args.task}"`,
  {
    label: 'classify',
    subagent_type: 'routing-dispatcher',
    schema: {
      type: 'object',
      properties: {
        tier: { type: 'string', enum: ['opus', 'sonnet', 'haiku'] },
        reason: { type: 'string' }
      },
      required: ['tier', 'reason']
    }
  }
)

log(`Routing to ${classification.tier}: ${classification.reason}`)

// Execute the actual task on the classified tier
const result = await agent(args.task, {
  label: 'execute',
  model: classification.tier,
  schema: args.output_schema
})

Escalation on Inadequate Output

A routing layer that only routes on the way in is incomplete. Tasks sometimes start simple and turn out to be complex once the model begins working. Add an escalation path:

// First attempt on classified tier
let result = await agent(args.task, {
  label: 'attempt-1',
  model: classification.tier,
  schema: RESULT_SCHEMA
})

// Check if the model flagged inadequacy
if (result.confidence === 'low' || result.escalate === true) {
  log(`Escalating from ${classification.tier} to opus — low confidence answer`)
  result = await agent(
    `${args.task}\n\nA previous analysis of this task produced a low-confidence result. Please reason carefully.`,
    {
      label: 'attempt-2',
      model: 'opus',
      schema: RESULT_SCHEMA
    }
  )
}

This requires your output schema to include a confidence field that the model can set. Add it to your schema definition:

const RESULT_SCHEMA = {
  type: 'object',
  properties: {
    answer: { type: 'string' },
    confidence: {
      type: 'string',
      enum: ['high', 'medium', 'low'],
      description: 'How confident you are in this answer given the available information'
    },
    escalate: {
      type: 'boolean',
      description: 'Set true if this task would significantly benefit from a more capable model'
    }
  },
  required: ['answer', 'confidence', 'escalate']
}

Cost Tracking with /cost

Since v2.1.92, /cost provides per-model and cache-hit breakdowns for subscription users. Run /cost after a session that uses the routing layer to verify the distribution is what you expect:

Session cost breakdown:
  haiku    (classifier)    12 calls   $0.003
  sonnet   (worker)        31 calls   $0.041
  opus     (escalations)    3 calls   $0.024
  ────────────────────────────────────────
  Total                   46 calls   $0.068

If you see Haiku being used for tasks that keep escalating, tighten the classification rules — Haiku is being overconfident about its own tier. If you see Opus being used for tasks that never escalate and produce high-confidence answers, consider whether Sonnet would have been adequate.

Settings for the Lab

The recommended settings configuration for a workflow that uses cost-aware routing:

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "model": "sonnet",
  "effortLevel": "medium",
  "fastMode": false,
  "alwaysThinkingEnabled": false
}

The routing layer overrides model per-agent, so the settings default does not matter much — but set it to "sonnet" as the conservative default for any unrouted calls. Keep effortLevel at "medium" globally; the routing layer can specify effort: high or effort: xhigh in the agent frontmatter for tiers that need it.

Summary

Model selection in the harness is a four-layer composition:

  1. Tier choice (Opus / Sonnet / Haiku) — the primary cost/quality lever. Match to task complexity.
  2. Effort level (low → max) — scales compute within the chosen tier. Match to how carefully you need the answer.
  3. Fast mode — Opus-specific latency optimization. Enable for interactive Opus sessions.
  4. Extended thinking — qualitatively deeper reasoning. Enable per-session for genuinely hard problems; never enable globally.

The mechanisms compose cleanly: --model and --effort at the CLI for session overrides, model and effortLevel in settings for defaults, model and effort in agent frontmatter for stable per-agent requirements, and --fallback-model for resilience in automation pipelines.

The routing lab demonstrates the practical consequence: a workflow that explicitly classifies and dispatches tasks can achieve Opus quality where it matters and Haiku cost where it does not — without manual intervention on every call.
