Chapter 1: The Agentic Harness Mental Model

"The model is not the agent. The harness is the agent. The model is just the brain."

1.1 What Is an "Agentic Harness"

Most engineers encounter Claude through the chat API: send a message, get a message back. Clean, stateless, request-response. An agentic harness is the opposite of that.

An agentic harness is the orchestration layer that sits between an LLM and the real world. It transforms a language model — something that can only produce text — into an agent that can read files, run commands, browse the web, spawn subagents, and modify state. The model stays the same. The harness is what gives it legs.

The anatomy is always the same, regardless of implementation language:

┌──────────────────────────────────────────────┐
│                 USER INTERFACE                │
│        (terminal, API, background daemon)     │
└────────────────────┬─────────────────────────┘
                     │ user prompt
┌────────────────────▼─────────────────────────┐
│              AGENTIC HARNESS                  │
│  ┌─────────────┐  ┌──────────┐  ┌─────────┐ │
│  │ System Prompt│  │  Tool    │  │Permission│ │
│  │  Assembler  │  │ Registry │  │  Layer  │ │
│  └─────────────┘  └──────────┘  └─────────┘ │
│  ┌─────────────────────────────────────────┐ │
│  │           Control Loop                  │ │
│  └─────────────────────────────────────────┘ │
└────────────────────┬─────────────────────────┘
                     │ assembled prompt + tools
┌────────────────────▼─────────────────────────┐
│             CLAUDE API (claude-*)             │
│       claude-sonnet-4-6, claude-opus-4-8      │
└────────────────────┬─────────────────────────┘
                     │ tool_use / text response
┌────────────────────▼─────────────────────────┐
│               TOOL EXECUTORS                  │
│  filesystem │ shell │ web │ agents │ MCP...   │
└──────────────────────────────────────────────┘

The distinction matters because the harness owns the agency. It decides which tools Claude can see, what context gets injected into the system prompt, which tool calls get executed versus blocked, and when the loop terminates. The model is powerful, but it is fundamentally reactive — it responds to what the harness presents to it. If you want to understand or build AI agents, understanding the harness is the prerequisite.

Every production harness you will encounter — Claude Code, LangChain agents, AutoGPT, OpenAI Assistants — is a variant of this same pattern. What differs is the sophistication of the control loop, the richness of the tool surface, the expressiveness of the permission model, and the quality of context management. Claude Code is currently the most complete public reference implementation of an agentic harness, and it is the primary source of ground truth for this book.

1.2 The Control Loop

The control loop is the heartbeat of every agentic harness. Understanding it precisely is not optional — it determines what the model can and cannot do, where failures occur, and how you debug them.

Here is the loop as implemented in Claude Code v2.1.220:

flowchart TD
    A([User Prompt]) --> B[Assemble System Prompt]
    B --> B1[Inject: git status]
    B --> B2[Inject: memory / CLAUDE.md]
    B --> B3[Inject: env info / working dir]
    B --> B4[Inject: tool descriptions]
    B1 & B2 & B3 & B4 --> C[Send to Claude API]
    C --> D{Response Type?}
    D -->|tool_use| E[Permission Check]
    E -->|denied| F[Return tool_result: denied]
    E -->|allowed| G[Execute Tool]
    G --> H[Return tool_result to conversation]
    H --> C
    D -->|text only| I([Final Response to User])
    F --> C

Walk through each step:

Assemble system prompt. The harness does not send a static system prompt. Before every call to the Claude API it assembles the prompt dynamically from several sources: the base instructions (tool descriptions, behavioral rules), CLAUDE.md content discovered from the filesystem, the current git status, environment variables, working directory, and any memory/context from prior turns. This assembly is where most harness complexity lives.

Send to Claude API. The assembled conversation — system prompt plus message history — goes to the API as a standard Messages request. The harness provides the tool schema list alongside it. Claude sees only what the harness chooses to show it.

Receive response. Claude returns one of two things: a tool_use block (the model wants to call a tool) or a plain text message (the model is done for this turn). A single response can contain multiple tool_use blocks, which the harness may execute in parallel.

Permission check. Before executing any tool call, the harness evaluates it against the permission layer. This is where allow/deny rules, glob patterns, and the auto-mode classifier make their decision. If denied, the harness returns a tool_result explaining the denial without executing anything. Claude then adjusts.

Execute tool. If permitted, the harness calls the tool's execute function with the parameters Claude provided. The tool can be synchronous (returns immediately) or asynchronous (background task, returns a task ID).

Return tool_result. The tool output is appended to the conversation as a tool_result message and the loop continues. The API call is made again with the full updated conversation.

Termination. The loop ends when Claude produces a text-only response — no tool_use blocks. At that point the harness has nothing left to execute and returns the final message to the user.

This loop is deceptively simple on paper. The complexity emerges from everything happening around it: context window management, permission evaluation, parallel tool execution, error recovery, and the fact that multi-turn conversations can run for hundreds of iterations.

1.3 Claude Code as Reference Implementation

Claude Code v2.1.220 is the harness this book uses as its ground truth. It is worth understanding the implementation details because they reflect deliberate architectural choices you will want to replicate or consciously deviate from.

Distribution

Claude Code ships as a native binary, not pure JavaScript. It is compiled for ten platform targets:

PlatformArch
darwinarm64, x64
linuxx64, arm64, x64-musl, arm64-musl
linux-androidx64, arm64
win32x64, arm64

This matters architecturally. The binary approach means startup time is milliseconds, memory overhead is predictable, and the harness can be invoked as a subprocess without Node.js startup cost. For a tool used in tight CI loops or spawned as subagents inside workflows, this is significant.

Installation methods:

# Recommended: curl installer
curl -fsSL https://claude.ai/install.sh | sh

# Homebrew (macOS)
brew install claude

# Bun (cross-platform)
bun install -g @anthropic-ai/claude-code

# npm (deprecated but functional)
npm install -g @anthropic-ai/claude-code

The npm/bun distribution wraps the native binary. When the npm postinstall script runs successfully, it copies the native binary to the appropriate bin path. When postinstall fails (restricted environments, offline installs), cli-wrapper.cjs acts as a fallback launcher — it detects the platform, locates the vendored native binary inside the package, and shells out to it. This two-path approach is how the package maintains both npm distribution compatibility and native binary performance.

Configuration Entry Point

The primary configuration file is ~/.claude/settings.json for global settings and .claude/settings.json for project-level settings. The schema is published at json.schemastore.org/claude-code-settings.json. Every behavioral aspect of the harness — model selection, permission rules, tool availability, hook scripts — is controlled through this settings layer. Chapter 2 covers the full configuration architecture.

1.4 The 52+ Tool Surface

The tool surface is how the harness exposes capabilities to the model. Claude Code organizes tools into three tiers, each with different loading behavior.

Tier 1: Core Tools (Always Loaded)

Six tools are loaded unconditionally on startup. Their descriptions are always present in the system prompt:

ToolPurpose
BashExecute shell commands in a persistent CWD
ReadRead files (text, images, PDFs, notebooks)
EditMake exact string replacements in files
WriteCreate or overwrite files
AgentSpawn subagents (background or foreground)
AskUserQuestionPresent structured questions to the user

These six represent the minimal surface needed for the model to be useful: shell access, filesystem read/write, and the ability to delegate work. Everything else is additive.

Tier 2: Deferred Tools (ToolSearch)

Over twenty tools are not loaded at startup. They exist in a registry and are loaded on demand when the model invokes ToolSearch with a query. This is a deliberate context-budget optimization — each tool description costs tokens in the system prompt, and loading all 52+ tools unconditionally would consume meaningful context before the user's first message.

The deferred tools include:

CronCreate       CronDelete       CronList
EnterPlanMode    ExitPlanMode
EnterWorktree    ExitWorktree
LSP
NotebookEdit
ScheduleWakeup
TaskCreate       TaskGet          TaskList
TaskOutput       TaskStop         TaskUpdate
WebFetch         WebSearch
Workflow
Skill

The model learns about deferred tools through brief, token-efficient registry entries. When it needs one — say, it wants to schedule a recurring task — it calls ToolSearch("schedule task"), receives the full CronCreate schema, and proceeds. The tool is now active for the rest of the session.

This pattern — lazy-loading capabilities — is something you will want to replicate in any harness with a large tool surface. The system prompt is not free context.

Tier 3: MCP Tools (Dynamic)

Model Context Protocol (MCP) servers provide a fourth unbounded tier. Each connected MCP server can expose arbitrarily many tools. Claude Code loads MCP tool schemas at startup (or lazily via MCP_CONNECTION_NONBLOCKING=true), making them available alongside the built-in tools.

The practical effect: a Claude Code session connecting to three MCP servers — say copilot-mem, sec-sr-mem, and a custom database server — might have 80 tools available to the model. The tool surface scales with your infrastructure, not with what Anthropic ships.

1.5 Harness vs SDK vs Framework

The taxonomy matters when you are deciding what to build or adopt. These three terms are often used interchangeably and shouldn't be.

The Anthropic SDK

The @anthropic-ai/sdk npm package is a thin typed wrapper around the Messages API. It handles HTTP, streaming, retries, and type safety. It does not provide a control loop, tool execution, permission checking, or context management. If you call anthropic.messages.create(...), you get back a response and you are done — there is no loop, no state, no tools unless you implement them yourself. The SDK is a primitive, not an agent.

A Framework

Frameworks like LangChain, LlamaIndex, or CrewAI provide higher-level abstractions: agent classes, chain composition, memory stores, retriever integrations. They reduce boilerplate but introduce their own abstractions, often leaky, that can obscure what is actually happening between your code and the API. They are built on top of SDKs and implement harness concepts in reusable (but opinionated) ways. Good for prototyping; worth understanding deeply if you build on them.

A Harness

A harness is the complete, production-grade orchestration layer. It owns everything between the user and the model: the control loop, tool execution, permission enforcement, context management, session persistence, error recovery. Claude Code is a harness. It uses the Anthropic SDK internally, but the SDK is not the interesting part — the harness architecture is.

ConcernSDKFrameworkHarness
HTTP / streamingYesWraps SDKUses SDK
Control loopNoYes (abstract)Yes (concrete)
Tool executionNoPartialYes
Permission layerNoNoYes
Context managementNoPartialYes
Session persistenceNoOptionalYes
Production-hardenedn/aVariesYes (Claude Code)

When you are building your own harness (Part VI of this book), you will use the SDK as a dependency. You will likely steal architectural ideas from frameworks. But you are responsible for all of the concerns in the "Harness" column.

Claude Code sits in the harness row, and it is open to inspection. Every chapter in this book peels back a layer of it.

1.6 Runtime Lifecycle

Understanding the startup sequence is essential if you are building a harness or debugging startup behavior. The sequence is deterministic and hooks fire in a specific order.

sequenceDiagram
    participant U as User
    participant H as Harness
    participant FS as Filesystem
    participant MCP as MCP Servers
    participant Git as Git
    participant API as Claude API

    U->>H: launch (claude or claude -p "...")
    H->>H: parse CLI flags + load global settings
    H->>H: fire SessionStart hooks
    H->>FS: discover CLAUDE.md (project root → git root → ~/)
    FS-->>H: CLAUDE.md content (project instructions)
    H->>MCP: connect configured MCP servers
    MCP-->>H: tool schemas registered
    H->>Git: inject git status + branch + recent commits
    Git-->>H: git context (or empty if not a repo)
    H->>H: assemble initial system prompt
    H-->>U: ready (interactive: show prompt / print: run)
    U->>H: first user message
    H->>API: messages.create(system + tools + history)
    API-->>H: response (tool_use or text)

SessionStart hooks fire before anything else. This is where harness authors inject environment setup — loading state files, printing context messages to the conversation, warming caches. If your hook exits non-zero, the session can be aborted before it starts. Chapter 16 covers the full hook system.

CLAUDE.md discovery walks the directory tree looking for CLAUDE.md files. It checks the current working directory, parent directories up to the git root, and ~/.claude/CLAUDE.md for global instructions. Found files are concatenated into the system prompt as project instructions. This is how the user in this session has a CLAUDE.md that specifies multi-domain workspace rules, Python coding standards, and shell scripting conventions — the harness injects all of it before the first API call.

MCP server connection happens after CLAUDE.md discovery. Each configured server is started (for stdio transport, the harness forks a subprocess) or connected to (for HTTP/SSE transport). Tool schemas are fetched and registered. If MCP_CONNECTION_NONBLOCKING=true, this step is deferred and the harness proceeds without waiting — tools become available as connections complete.

Git context injection reads the current branch, recent commits, and git status output. This context is injected into the system prompt so Claude immediately knows it is in a git repo, what the current state is, and what changed recently. In a large codebase, this context materially improves the model's first-turn code and refactoring decisions.

After all of this, the harness is ready. In interactive mode, it shows the prompt. In print mode (-p), it immediately begins executing the provided prompt.

1.7 Lab: Trace a "Fix This Bug" Prompt Through the Full Harness Lifecycle

This lab is conceptual but precise. Walk through every stage a real bug-fix request traverses from user input to committed patch.

The Prompt

fix the authentication timeout in src/auth/session.py — 
sessions are expiring after 5 minutes instead of 30

Stage 1: Startup (T=0ms)

The harness fires SessionStart hooks. If you have a hook at .claude/hooks/session_start.sh, it runs now. A real hook might:

#!/usr/bin/env bash
set -euo pipefail

# Recover state from prior session
if [[ -f ~/.claude/projects/myapp/state.json ]]; then
    cat ~/.claude/projects/myapp/state.json | jq -r '.context_message'
fi

The hook's stdout is prepended to the conversation as context. This ensures the model knows, for instance, that a prior session was mid-refactor on the auth module.

Stage 2: System Prompt Assembly (T=10ms)

The harness assembles the system prompt. For this session in a Python project, it might inject:

[Project Instructions from CLAUDE.md]
Multi-domain workspace: AI security research, book writing...
Python: type hints, f-strings, pathlib, PEP 8. Use ruff.

[Git Context]
On branch: fix/auth-timeout
Recent commits:
  a1b2c3d chore: update dependencies
  e4f5g6h feat: add session refresh endpoint

[Git Status]
M src/auth/session.py
M tests/auth/test_session.py

[Tool Descriptions]
Bash: Execute shell commands...
Read: Read files from the local filesystem...
[...6 core tools + any MCP tools...]

The model sees all of this before it processes the user's "fix the authentication timeout" message. The git status already tells it that session.py is modified — the model might infer that another change is already in progress.

Stage 3: First API Call (T=50ms)

The harness sends the assembled system prompt plus the user message to the Claude API. The model responds with a tool_use block:

{
  "type": "tool_use",
  "name": "Read",
  "input": {
    "file_path": "/Users/DOANTX26/Documents/2026/src/auth/session.py"
  }
}

The model's first move is almost always to gather context before acting. It knows from the git status that session.py is relevant. It reads it.

Stage 4: Permission Check + Tool Execution (T=55ms)

The harness evaluates the Read call against the permission layer:

  • Is Read in the deny list? No.
  • Does the file path match any blocked patterns (.env, credentials, SSH keys)? No.
  • Is defaultMode set to something that requires confirmation? No, this session uses auto.

Permission granted. The harness reads session.py and returns it as a tool_result:

{
  "type": "tool_result",
  "tool_use_id": "toolu_abc123",
  "content": "     1\tSESSION_TIMEOUT_MINUTES = 5\n     2\t...\n"
}

Stage 5: Second API Call — The Model Investigates (T=100ms)

Back in the loop. Claude processes the file content and issues another tool_use:

{
  "type": "tool_use",
  "name": "Bash",
  "input": {
    "command": "grep -rn 'SESSION_TIMEOUT\\|session_timeout\\|timeout.*minutes' src/auth/ tests/auth/",
    "description": "Find all timeout references in auth module"
  }
}

The description field is not cosmetic. The harness uses it for the permission UI (users see what the command is doing) and the audit trail. Well-written descriptions make it possible to reconstruct what happened from logs.

Permission check: is this Bash call on the allow list? The command uses grep, which is benign. Allowed.

Stage 6: Root Cause Found (T=150ms)

The grep returns multiple hits showing the timeout constant is defined in three places — the session module, a config parser, and a legacy constants file that the config parser never reads. The model now has enough information to form a fix.

It issues an Edit call:

{
  "type": "tool_use",
  "name": "Edit",
  "input": {
    "file_path": "src/auth/session.py",
    "old_string": "SESSION_TIMEOUT_MINUTES = 5",
    "new_string": "SESSION_TIMEOUT_MINUTES = 30"
  }
}

Followed by another Edit for the config file, and a Bash call to run the tests:

{
  "type": "tool_use",
  "name": "Bash",
  "input": {
    "command": "cd /Users/DOANTX26/Documents/2026 && python -m pytest tests/auth/test_session.py -v",
    "description": "Run auth session tests after timeout fix"
  }
}

Stage 7: Test Output + Final Loop (T=400ms)

Tests pass. The model receives the green output as a tool_result and produces its final text-only response — no more tool_use blocks:

Fixed the authentication timeout issue. The problem was SESSION_TIMEOUT_MINUTES 
being set to 5 in src/auth/session.py while the value in config/legacy_constants.py 
(also 5) was being read by the config parser instead. I've updated both:

- src/auth/session.py:1 → SESSION_TIMEOUT_MINUTES = 30
- config/legacy_constants.py:47 → AUTH_SESSION_TIMEOUT_MINUTES = 30

All 12 session tests pass. The config parser now reads the correct constant.

Stage 8: The Loop Terminates (T=401ms)

Text-only response means no more tool_use blocks. The control loop detects this and exits. The harness returns the final message to the user interface.

Total loop iterations: 5 (Read → Bash/grep → Edit × 2 → Bash/pytest → final text) Total API calls: 5 Total wall clock: ~400ms (assuming model latency ~80ms/call)

What This Trace Reveals

  • The model never has direct filesystem access. Every file it reads goes through the harness's Read tool executor.
  • Each API call is independent — the model reconstructs its understanding from the full conversation history every time. There is no "model memory" between API calls in the same session; the harness maintains the conversation state.
  • The permission layer evaluated every tool call, even trivial Read calls. In production harnesses, this evaluation needs to be fast — sub-millisecond.
  • The description field on Bash calls is load-bearing for auditability. In enterprise deployments, these descriptions feed audit logs.
  • The loop terminated at 5 iterations for a relatively simple bug. Complex refactors or multi-file architectural changes can run 50–200 iterations.

Summary

An agentic harness is the orchestration layer between an LLM and the world. It owns the control loop, assembles context, executes tools, enforces permissions, and manages the conversation state across turns. The model is reactive; the harness is what makes it autonomous.

Claude Code v2.1.220 is the reference implementation. It ships as a native binary for ten platforms, organizes its 52+ tools into three tiers (always-loaded, deferred via ToolSearch, and unlimited MCP), and follows a deterministic startup sequence: SessionStart hooks → CLAUDE.md discovery → MCP connection → git context → ready.

The distinction between SDK, framework, and harness matters when you are building. The SDK is a primitive. Frameworks are opinionated abstractions. A harness is the complete, production-hardened orchestration layer — and building one is what this book is about.
