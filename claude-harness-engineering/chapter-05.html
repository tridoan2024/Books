Chapter 5: Filesystem Tools — Read, Edit, Write, Glob, Grep

Every agentic session is ultimately a conversation between a model and a filesystem. The model reads, modifies, creates, and searches files; the harness provides the machinery to do so safely and efficiently. The five filesystem tools — Read, Edit, Write, Glob, and Grep — are the highest-frequency tools in any working session. A senior engineer using Claude Code will invoke Read and Grep dozens of times per hour. Getting their behavior exactly right in your own harness is not optional.

This chapter dissects each tool against its TypeScript interface, documents the behavioral contracts that the interface alone does not express, and ends with a lab that assembles all five into a semantic code search tool.

5.1 Read — Multi-Format File Ingestion

The Interface

export interface FileReadInput {
  file_path: string;   // absolute path required
  offset?: number;     // line number to start reading (0-based)
  limit?: number;      // number of lines to read
  pages?: string;      // PDF page range "1-5", max 20 pages
}

export type FileReadOutput =
  | { type: "text";         file: { filePath: string; content: string; numLines: number; startLine: number; totalLines: number; truncatedByTokenCap?: boolean } }
  | { type: "image";        file: { base64: string; type: "image/jpeg" | "image/png" | "image/gif" | "image/webp"; originalSize: number; dimensions?: { width: number; height: number } } }
  | { type: "notebook";     file: { filePath: string; cells: unknown[] } }
  | { type: "pdf";          file: { filePath: string; base64: string; originalSize: number } }
  | { type: "parts";        file: { filePath: string; originalSize: number; count: number; outputDir: string } }
  | { type: "file_unchanged"; file: { filePath: string }; source?: "seeded" }

The output is a discriminated union on type. Your harness must switch on this field before accessing any other properties — there is no shared supertype.

Format Detection and Dispatch

The harness determines output type from the file extension and content, not from parameters. Passing pages to a .txt file is ignored. Passing offset/limit to a PDF has no effect — use pages instead.

File typeOutput typeNotes
.txt, .md, .ts, .py, .go, .rs, .json, .yaml, most texttextDefault for unknown extensions
.jpg, .jpeg, .png, .gif, .webpimageReturns base64, no text
.ipynbnotebookAll cells with outputs
.pdfpdf (≤10 pages) or parts (>10 pages)parts means the file was split
Already read this sessionfile_unchangedDeduplication (see below)

For image files the model receives the visual content directly — this is multimodal input, not text. If your harness is not backed by a multimodal model, reading an image will either fail or produce an empty result; test this boundary explicitly.

Pagination with offset and limit

The offset and limit fields apply only to text type output. Both are optional. offset is zero-based: offset: 0 starts from line 1 (the first line). limit is the number of lines to return.

The output always reports startLine and totalLines so the caller can determine whether more content remains:

// First 50 lines
const page1 = await read({ file_path: "/src/main.ts", limit: 50 });
// type: "text", startLine: 0, numLines: 50, totalLines: 2000

// Next 50 lines
const page2 = await read({ file_path: "/src/main.ts", offset: 50, limit: 50 });
// type: "text", startLine: 50, numLines: 50, totalLines: 2000

A common mistake is treating offset as 1-based. It is not. offset: 1 skips the first line, not offset: 0.

truncatedByTokenCap

When a file is too large to fit within the token budget for a single read, the harness returns as many lines as it can and sets truncatedByTokenCap: true on the output. The numLines field reflects how many lines were actually returned, which will be less than totalLines.

This field will not appear when the file fits fully — it is absent, not false. Test for truthiness, not strict equality:

if (result.type === "text" && result.file.truncatedByTokenCap) {
  // paginate with offset/limit
}

If your harness exposes the model to truncated content without informing it of the truncation, the model will make decisions based on an incomplete view of the file. Always surface truncatedByTokenCap to the model in the tool result or a follow-up message.

PDF Handling

PDFs up to 10 pages are returned as type: "pdf" with a base64-encoded payload. PDFs exceeding 10 pages without a pages parameter trigger the parts output — the file was split into chunks in outputDir, and the caller must read each part individually.

The pages parameter accepts ranges like "1-5", "3", or "10-20", capped at 20 pages per request. For large PDFs (say, a 300-page specification), iterating in 20-page windows is the correct pattern:

for (let start = 1; start <= totalPages; start += 20) {
  const end = Math.min(start + 19, totalPages);
  const chunk = await read({
    file_path: "/docs/spec.pdf",
    pages: `${start}-${end}`
  });
  // process chunk.file.base64
}

A PDF that has already been read as parts cannot be re-read in full on the next call without triggering file_unchanged deduplication. Consider this when designing resumable workflows.

Notebook Support

Jupyter notebooks are returned as type: "notebook" with a cells array. Each cell is an object containing type, source, and outputs. The exact shape of cells is typed as unknown[] in the interface — you will need to inspect the actual NBFORMAT schema or cast defensively. The harness renders cell outputs including rich media, making this particularly useful for agents investigating data science work.

file_unchanged Deduplication

This is the behavior that surprises most harness authors the first time they encounter it.

If the model reads a file and then, in the same session, requests that file again, the harness returns type: "file_unchanged" instead of the full content. This prevents burning tokens on identical reads. The model already has the content in context — there is no need to send it again.

// First read: returns type: "text" with content
const r1 = await read({ file_path: "/src/config.ts" });
// r1.type === "text"

// Second read in same session: returns type: "file_unchanged"
const r2 = await read({ file_path: "/src/config.ts" });
// r2.type === "file_unchanged"
// r2.file.filePath === "/src/config.ts"

When building a harness, you must track which files have been read and inform the model that a file_unchanged response means "you already have this content." A model that receives file_unchanged without context will likely retry the read, loop indefinitely, or make incorrect assumptions.

The source: "seeded" field on file_unchanged indicates the file matched a startup-seeded entry — specifically a CLAUDE.md file or nested memory discovered during harness initialization. This tells you the content was injected into the system prompt at session start, not read as a tool call. It is useful for debugging: if a model claims it cannot access CLAUDE.md, a source: "seeded" dedup response tells you the content was already present.

Gotchas

Absolute paths only. Relative paths fail silently or throw. Every file_path argument must start with /. If your harness resolves paths, do it before passing to Read, not inside the tool.

The dedup boundary is the session, not the conversation turn. Once a file is read, it is marked for the entire session duration. Worktree-isolated subagents have their own sessions and their own dedup state — a subagent reading a file that the parent already read will get the full content, not file_unchanged.

Image reads do not paginate. There is no offset/limit for images. If you need a specific region of a large image, do it outside the tool.

Notebook cell metadata is unknown[]. Do not assume field names without runtime inspection.

5.2 Edit — Surgical In-Place Modification

The Interface

export interface FileEditInput {
  file_path: string;
  old_string: string;   // must exist exactly once in the file (or use replace_all)
  new_string: string;   // must differ from old_string
  replace_all?: boolean; // default false
}

export interface FileEditOutput {
  filePath: string;
  oldString: string;
  newString: string;
  originalFile: string | null;
  structuredPatch: {
    oldStart: number;
    oldLines: number;
    newStart: number;
    newLines: number;
    lines: string[];
  }[];
  userModified: boolean;
  replaceAll: boolean;
  gitDiff?: {
    filename: string;
    status: "modified" | "added";
    additions: number;
    deletions: number;
    changes: number;
    patch: string;
    repository?: string | null;
  };
}

Edit performs a literal string replacement. It finds old_string in the file, replaces it with new_string, and returns a structured patch describing the change.

The Uniqueness Constraint

Edit fails if old_string appears more than once in the file. This is by design. A non-unique match would make the edit non-deterministic — the tool does not guess which occurrence to replace. When you hit this error, you have two options:

  1. Expand the context. Include surrounding lines in old_string to create a unique anchor. Adding the function signature above the target line, or the comment block before it, usually achieves uniqueness.
  1. Use replace_all: true. This replaces every occurrence. Appropriate for renaming a variable, updating a constant, or fixing a typo that appears throughout a file. Not appropriate when occurrences differ in context.
// FAILS: "return null" appears 12 times in the file
await edit({
  file_path: "/src/parser.ts",
  old_string: "return null",
  new_string: "return undefined"
});

// SUCCEEDS: expanded context is unique
await edit({
  file_path: "/src/parser.ts",
  old_string: `function parseToken(input: string): Token | null {\n  return null`,
  new_string: `function parseToken(input: string): Token | undefined {\n  return undefined`
});

// SUCCEEDS: replace all occurrences intentionally
await edit({
  file_path: "/src/parser.ts",
  old_string: "return null",
  new_string: "return undefined",
  replace_all: true
});

structuredPatch Output

The structuredPatch array contains one entry per contiguous changed hunk, following the unified diff hunk format. Each entry includes:

  • oldStart / oldLines: starting line and count in the original file
  • newStart / newLines: starting line and count in the modified file
  • lines: the actual diff lines, prefixed with - (removed), + (added), or (context)

This is the machine-readable form of the change. If your harness stores an audit log, serialize this structure. It lets you reconstruct exactly what changed, replay changes, or detect conflicts.

// Example structuredPatch entry
{
  oldStart: 42,
  oldLines: 3,
  newStart: 42,
  newLines: 4,
  lines: [
    " function parseToken(input: string): Token | null {",
    "-  return null",
    "+  if (!input) return undefined",
    "+  return parseRaw(input)",
    " }"
  ]
}

userModified

userModified is true when the file on disk was changed by an external process between when it was last read and when Edit ran. This matters in interactive sessions where a human editor might have modified the file in parallel. In headless/CI contexts, userModified: true is a signal that something unexpected wrote to the file — worth logging.

Edit and the Bash sed Boundary

As of v2.1.89, the Edit tool treats files viewed via Bash with sed -n or cat as equivalent to files read with the Read tool. Before this version, Edit would refuse to modify a file unless it had been read via the Read tool specifically. If your harness targets earlier versions, ensure all pre-edit file views go through Read, not Bash.

Anti-patterns

Do not pass entire file contents as old_string. Whole-file replacements through Edit are expensive (token-heavy) and fragile. Use Write for full file overwrites.

Do not rely on whitespace-insensitive matching. Edit matches exactly, including all whitespace. A tab vs. four spaces will cause a no-match failure. Use Read first to verify the exact bytes you intend to match.

Do not construct old_string from memory. Always Read the file first, copy the exact text you want to replace, then pass it to Edit. Models that construct old_string from their training knowledge frequently get indentation or comment punctuation wrong.

5.3 Write — Create and Overwrite

The Interface

export interface FileWriteInput {
  file_path: string;   // must be absolute
  content: string;
}

export interface FileWriteOutput {
  type: "create" | "update";
  filePath: string;
  content: string;
  structuredPatch: {
    oldStart: number;
    oldLines: number;
    newStart: number;
    newLines: number;
    lines: string[];
  }[];
  originalFile: string | null;
  gitDiff?: {
    filename: string;
    status: "modified" | "added";
    additions: number;
    deletions: number;
    changes: number;
    patch: string;
    repository?: string | null;
  };
  userModified?: boolean;
}

Write replaces the entire file contents. The type field in the output tells you whether a file was created fresh ("create") or whether an existing file was overwritten ("update"). originalFile is the pre-write contents (or null for new files), enabling rollback.

The Read-Before-Write Requirement

Write fails for existing files if the file has not been read in the current session. This is a safety check, not an arbitrary limitation. The harness needs to know the file exists and that the model has seen its current contents before overwriting it. Without this, Write could silently discard changes made by another process since the last read.

The enforcement is session-scoped: if the file was read as part of startup seeding (a CLAUDE.md, for example), it counts. If a subagent reads it, that counts only within that subagent's session.

// FAILS for existing files: write without prior read
await write({
  file_path: "/src/config.ts",
  content: "export const DEBUG = true;"
});

// SUCCEEDS: read first
await read({ file_path: "/src/config.ts" });
await write({
  file_path: "/src/config.ts",
  content: "export const DEBUG = true;"
});

// Always succeeds: creating a new file
await write({
  file_path: "/src/new-module.ts",
  content: "export function newFeature() {}"
});

For new file creation, no prior read is required — the file does not exist yet.

Create vs Update Semantics

When type: "create", originalFile is null and the structuredPatch shows all lines as additions. When type: "update", originalFile contains the prior content. Your harness should persist originalFile if you need rollback capability:

const result = await write({ file_path, content });
if (result.type === "update" && result.originalFile !== null) {
  undoLog.push({
    file_path,
    content: result.originalFile,
    timestamp: Date.now()
  });
}

When to Use Write vs Edit

Edit is the right tool for targeted changes: fix a bug, rename a variable, update a configuration value. Write is the right tool for:

  • Creating new files
  • Scaffolding from a template
  • Full rewrites where more than ~40% of content changes
  • Files short enough that sending the full content is not token-expensive

The boundary is not sharp. For a 20-line file, Write is fine even for small changes. For a 2000-line file, Edit is almost always more appropriate because it sends only the diff, not the entire file.

5.4 Glob — Pattern-Based File Discovery

The Interface

export interface GlobInput {
  pattern: string;
  path?: string;   // defaults to CWD — do NOT pass "undefined" or "null"
}

export interface GlobOutput {
  durationMs: number;
  numFiles: number;
  filenames: string[];
  truncated: boolean;
  totalMatches?: number;
  countIsComplete?: boolean;
}

Glob matches files by name pattern. Results are sorted by modification time, most-recently-modified first.

Pattern Syntax

Glob uses standard glob syntax:

PatternMatches
*.tsAll TypeScript files in the current directory
**/*.tsAll TypeScript files in all subdirectories
src/**/*.{ts,tsx}TypeScript and TSX files under src/
**/*.test.*All test files regardless of extension
!**/*.d.ts(Negation — typically not supported; use type filter in Grep instead)

The path parameter scopes the search. Omit it for CWD. Setting it to the string "undefined" or "null" will be interpreted as a literal directory named undefined or null — it will fail or return nothing. If you build the parameter object dynamically, use a conditional:

const input: GlobInput = { pattern: "**/*.ts" };
if (scopePath) input.path = scopePath;
// Never: input.path = scopePath || "undefined"

The 100-File Truncation

Glob returns at most 100 files. When the true match count exceeds 100, truncated: true is set. The totalMatches field, when present, is a lower bound — it may be less than the actual count when countIsComplete: false.

const result = await glob({ pattern: "**/*.ts" });

if (result.truncated) {
  console.log(`Got ${result.numFiles} of at least ${result.totalMatches ?? "unknown"} matches`);
  if (!result.countIsComplete) {
    console.log("True count may be higher");
  }
}

This truncation is intentional: returning thousands of file paths would flood the context window. The sort-by-mtime behavior is deliberate — recently modified files are most likely to be relevant to the current task.

For repositories with many files, adopt a narrowing strategy: start with a specific pattern, then widen only if you get too few results. Do not start with **/* and paginate — Glob does not support offset-based pagination. If you need to enumerate all files in a large repo, use Bash with find and manage the output yourself.

Combining Glob with Grep and Read

Glob's output feeds naturally into Grep (for content filtering) or Read (for content inspection). The standard pattern for "find all files of type X containing pattern Y" is:

// Step 1: find candidate files
const files = await glob({ pattern: "**/*.ts", path: "/src" });

// Step 2: filter by content
const matches = await grep({
  pattern: "implements.*Repository",
  glob: "*.ts",
  path: "/src",
  output_mode: "files_with_matches"
});

Note that in step 2, Grep's own glob parameter does the same job as Glob's pattern — for content search, go directly to Grep rather than chaining Glob → Grep. Use Glob when you need file metadata (modification time, count) or when you need the file list for operations other than Grep.

5.5 Grep — Content Search Across the Codebase

The Interface

export interface GrepInput {
  pattern: string;           // regex (ripgrep syntax)
  path?: string;             // file or directory, defaults to CWD
  glob?: string;             // file name filter: "*.js", "*.{ts,tsx}"
  output_mode?: "content" | "files_with_matches" | "count";  // default: files_with_matches
  "-B"?: number;             // lines before each match
  "-A"?: number;             // lines after each match
  "-C"?: number;             // lines before AND after each match
  context?: number;          // alias for -C
  "-n"?: boolean;            // show line numbers (default true for content mode)
  "-i"?: boolean;            // case-insensitive
  "-o"?: boolean;            // print only matched parts
  type?: string;             // file type: "js", "py", "rust", "go", "java"
  head_limit?: number;       // default 250, pass 0 for unlimited
  offset?: number;           // skip N entries before head_limit
  multiline?: boolean;       // . matches newlines; patterns span lines
}

export interface GrepOutput {
  mode?: "content" | "files_with_matches" | "count";
  numFiles: number;
  filenames: string[];
  content?: string;          // populated in content mode
  numLines?: number;
  numMatches?: number;
  totalFiles?: number;
  totalLines?: number;
  appliedLimit?: number;
  appliedOffset?: number;
}

Grep wraps ripgrep. Its regex syntax is ripgrep's syntax, which follows Rust's regex crate with some extensions. Most PCRE patterns work, but not all — notably, lookaheads and lookbehinds are not supported in the default mode.

Three Output Modes

The choice of output_mode dramatically affects both the output size and what information is available.

files_with_matches (default): Returns only the list of files that contain at least one match. The filenames array is populated; content is not. Use this when you need to know which files to read, not where in each file the matches are.

const result = await grep({
  pattern: "AuthenticationError",
  path: "/src",
  output_mode: "files_with_matches"
});
// result.filenames: ["/src/auth.ts", "/src/middleware.ts", ...]
// result.content: undefined

content: Returns the actual matching lines. The content field is a multi-line string formatted as ripgrep output (path:line:content). Use this when you need to see the matches themselves — for code review, refactoring, or finding the exact location of a pattern.

const result = await grep({
  pattern: "TODO|FIXME|HACK",
  path: "/src",
  output_mode: "content",
  "-n": true
});
// result.content:
// /src/auth.ts:42:  // TODO: implement refresh token logic
// /src/parser.ts:107:  // FIXME: edge case when input is empty

count: Returns the number of matches per file. The content field contains the count output; numMatches gives the aggregate. Use this for metrics — how many times does a pattern appear? which file has the most usages?

const result = await grep({
  pattern: "console\\.log",
  path: "/src",
  output_mode: "count"
});
// result.content:
// /src/debug.ts:14
// /src/main.ts:3
// result.numMatches: 17

Context Lines: -A, -B, -C

The context flags are only meaningful in content mode. -C 3 (or context: 3) shows 3 lines before and after each match — equivalent to passing both -B 3 and -A 3. Use context when the match alone is not enough to understand the code structure:

const result = await grep({
  pattern: "throw new Error",
  path: "/src/validator.ts",
  output_mode: "content",
  "-C": 5
});

Context lines are prefixed with - (before) and + (after) in ripgrep output when using -A/-B separately. With -C, they are shown with -- separating non-contiguous groups.

head_limit and offset

The default head_limit is 250. This caps the number of output lines in content mode, or the number of files/entries in other modes. It is a context budget safeguard. For large codebases with hundreds of matches, 250 lines of context output can already consume significant token budget.

Pass head_limit: 0 to remove the cap entirely. Use this only when you know the result set is bounded — for example, searching a single file or a small directory with a highly specific pattern.

offset skips the first N entries, enabling manual pagination:

// First 250 matches
const page1 = await grep({ pattern: "useState", path: "/src", output_mode: "content" });

// Next 250 matches
const page2 = await grep({
  pattern: "useState",
  path: "/src",
  output_mode: "content",
  offset: page1.appliedLimit ?? 250
});

The response includes appliedLimit and appliedOffset confirming what was actually applied — important when the harness might override defaults.

The type Filter

The type parameter maps to ripgrep's --type flag. Common values: js, ts, py, rust, go, java, c, cpp, rb, sh. This is more efficient than glob for standard file types because ripgrep has built-in type definitions that cover multiple extensions (e.g., type: "ts" matches both .ts and .tsx).

Use glob for custom patterns ("*.config.js", "Dockerfile*") and type for standard language types.

Multiline Mode

Setting multiline: true changes two behaviors: . matches newlines, and patterns can span line boundaries. This is ripgrep's -U --multiline-dotall mode.

// Find function declarations that span multiple lines
const result = await grep({
  pattern: "function\\s+\\w+\\([\\s\\S]*?\\)\\s*\\{",
  path: "/src",
  output_mode: "content",
  multiline: true
});

Multiline mode is expensive on large directories — the engine cannot rely on line-by-line scanning. Scope it with path or glob/type to a bounded file set.

Escaping Literals

Ripgrep's regex syntax treats {, }, (, ), ., *, +, ? as special. To search for literal braces (common in Go or TypeScript), escape them:

// Find Go interface{} usage
await grep({ pattern: "interface\\{\\}", type: "go", output_mode: "content" });

// Find function calls with parens
await grep({ pattern: "fetchData\\(", type: "ts", output_mode: "content" });

An unescaped literal brace in ripgrep is a syntax error that produces an empty result with no error message — a silent failure. When a Grep returns zero results unexpectedly, check your regex for unescaped special characters first.

5.6 Git Diff Integration

Both Edit and Write return a gitDiff field when the modified file is inside a git repository. This field is optional — it is absent when the file is outside a repository or when git is not available.

gitDiff?: {
  filename: string;
  status: "modified" | "added";
  additions: number;
  deletions: number;
  changes: number;      // additions + deletions
  patch: string;        // unified diff format
  repository?: string | null;  // repository root path
}

The patch field is a standard unified diff string — the same format produced by git diff. It is suitable for display, storage, or applying to another tree with git apply.

status is "added" for new files (Write with type: "create") and "modified" for existing files. Note that gitDiff.status and FileWriteOutput.type communicate the same information through different lenses.

Using gitDiff in Your Harness

Audit trail. Store every gitDiff in an append-only log, keyed by file path and timestamp. This gives you a complete change history within the session, independent of git commits.

Change summaries. Surface additions and deletions to the model as feedback. A model told "you added 47 lines and removed 3" can sanity-check whether its edit matches its intent.

Conflict detection. If additions is unexpectedly large after a targeted Edit, it may indicate the replace_all was set unintentionally or the context in old_string was broader than planned.

Pre-commit validation. Accumulate diffs across a workflow, then pass them to a reviewer agent as the patch payload rather than asking it to re-read every modified file.

const edits: { file: string; diff: string }[] = [];

const result = await edit({
  file_path: "/src/auth.ts",
  old_string: "const TOKEN_EXPIRY = 3600",
  new_string: "const TOKEN_EXPIRY = 86400"
});

if (result.gitDiff) {
  edits.push({
    file: result.gitDiff.filename,
    diff: result.gitDiff.patch
  });
}

// Later, pass edits to a review agent
const reviewPrompt = edits
  .map(e => `File: ${e.file}\n\`\`\`diff\n${e.diff}\n\`\`\``)
  .join("\n\n");

5.7 Lab: Build a Semantic Code Search Tool

This lab combines all five filesystem tools into a tool that takes a natural-language query, maps it to code patterns, searches the codebase, and returns ranked, contextualized results.

Objective

Build a function semanticSearch(query: string, repoPath: string): SearchResult[] that:

  1. Translates the query into regex patterns
  2. Narrows candidates with Glob
  3. Searches with Grep in files_with_matches mode
  4. Collects surrounding context with content mode
  5. Reads full files for top candidates
  6. Returns ranked results with file, line, score, and excerpt

Step 1: Pattern Translation Layer

interface SearchPattern {
  regex: string;
  fileType?: string;
  glob?: string;
  description: string;
}

function queryToPatterns(query: string): SearchPattern[] {
  // In a real implementation, this would call an LLM.
  // For demonstration, a keyword map:
  const patterns: SearchPattern[] = [];

  if (/auth|login|token/i.test(query)) {
    patterns.push({
      regex: "authenticate|authorize|JWT|Bearer|session",
      fileType: "ts",
      description: "authentication-related code"
    });
  }

  if (/error|exception|fail/i.test(query)) {
    patterns.push({
      regex: "throw new|catch\\s*\\(|Error\\(",
      description: "error handling patterns"
    });
  }

  if (/database|query|sql/i.test(query)) {
    patterns.push({
      regex: "SELECT|INSERT|UPDATE|DELETE|query\\(",
      "-i": true,
      description: "database operations"
    });
  }

  // Fallback: treat query words as literal search terms
  if (patterns.length === 0) {
    const terms = query
      .toLowerCase()
      .replace(/[^a-z0-9\s]/g, "")
      .split(/\s+/)
      .filter(t => t.length > 3);
    if (terms.length > 0) {
      patterns.push({
        regex: terms.join("|"),
        description: `keyword match: ${terms.join(", ")}`
      });
    }
  }

  return patterns;
}

Step 2: File Discovery

interface CandidateFile {
  path: string;
  mtime: number;  // inferred from position in Glob results (most-recent first)
}

async function discoverCandidates(
  repoPath: string,
  fileType?: string
): Promise<CandidateFile[]> {
  const pattern = fileType
    ? `**/*.${fileType}`
    : "**/*.{ts,js,py,go,rs,java,rb}";

  const result = await glob({ pattern, path: repoPath });

  if (result.truncated) {
    // Log that we have a partial view — do not silently drop this
    console.warn(
      `Glob truncated at ${result.numFiles} files. ` +
      `Total: at least ${result.totalMatches ?? "unknown"}. ` +
      `countIsComplete: ${result.countIsComplete}`
    );
  }

  return result.filenames.map((path, index) => ({
    path,
    mtime: result.numFiles - index  // proxy: lower index = more recent
  }));
}

Step 3: Content Filtering

interface PatternMatch {
  file: string;
  patternDescription: string;
}

async function filterByContent(
  candidates: CandidateFile[],
  pattern: SearchPattern,
  repoPath: string
): Promise<PatternMatch[]> {
  const grepInput: GrepInput = {
    pattern: pattern.regex,
    path: repoPath,
    output_mode: "files_with_matches",
    head_limit: 50
  };

  if (pattern.fileType) grepInput.type = pattern.fileType;
  if (pattern.glob) grepInput.glob = pattern.glob;
  if ((pattern as any)["-i"]) grepInput["-i"] = true;

  const result = await grep(grepInput);

  // Intersect with candidates to respect Glob scope
  const candidatePaths = new Set(candidates.map(c => c.path));
  return result.filenames
    .filter(f => candidatePaths.has(f))
    .map(file => ({ file, patternDescription: pattern.description }));
}

Step 4: Context Extraction

interface MatchContext {
  file: string;
  excerpt: string;
  matchCount: number;
}

async function extractContext(
  matches: PatternMatch[],
  pattern: SearchPattern
): Promise<MatchContext[]> {
  const results: MatchContext[] = [];

  for (const match of matches.slice(0, 10)) {  // cap at top 10 files
    const grepResult = await grep({
      pattern: pattern.regex,
      path: match.file,
      output_mode: "content",
      "-C": 3,
      "-n": true,
      head_limit: 30,
      ...(pattern.fileType ? { type: pattern.fileType } : {}),
      ...((pattern as any)["-i"] ? { "-i": true } : {})
    });

    if (grepResult.content) {
      results.push({
        file: match.file,
        excerpt: grepResult.content,
        matchCount: grepResult.numMatches ?? 0
      });
    }
  }

  return results;
}

Step 5: Full File Read for Top Candidates

interface SearchResult {
  file: string;
  score: number;
  excerpt: string;
  fullContent?: string;
  matchCount: number;
  patterns: string[];
}

async function readTopCandidates(
  contexts: MatchContext[],
  patternDescription: string,
  maxFullReads: number = 3
): Promise<SearchResult[]> {
  const results: SearchResult[] = [];

  // Sort by match count descending
  const sorted = [...contexts].sort((a, b) => b.matchCount - a.matchCount);

  for (let i = 0; i < sorted.length; i++) {
    const ctx = sorted[i];
    const result: SearchResult = {
      file: ctx.file,
      score: ctx.matchCount,
      excerpt: ctx.excerpt,
      matchCount: ctx.matchCount,
      patterns: [patternDescription]
    };

    if (i < maxFullReads) {
      const readResult = await read({ file_path: ctx.file });
      if (readResult.type === "text") {
        result.fullContent = readResult.file.content;
        if (readResult.file.truncatedByTokenCap) {
          result.fullContent += "\n// [content truncated by token cap]";
        }
      } else if (readResult.type === "file_unchanged") {
        result.fullContent = "[already in context]";
      }
    }

    results.push(result);
  }

  return results;
}

Step 6: Composing the Full Search

async function semanticSearch(
  query: string,
  repoPath: string
): Promise<SearchResult[]> {
  const patterns = queryToPatterns(query);
  const allResults = new Map<string, SearchResult>();

  for (const pattern of patterns) {
    const candidates = await discoverCandidates(repoPath, pattern.fileType);
    const matches = await filterByContent(candidates, pattern, repoPath);
    const contexts = await extractContext(matches, pattern);
    const results = await readTopCandidates(contexts, pattern.description);

    for (const result of results) {
      const existing = allResults.get(result.file);
      if (existing) {
        existing.score += result.score;
        existing.patterns.push(...result.patterns);
      } else {
        allResults.set(result.file, result);
      }
    }
  }

  return Array.from(allResults.values())
    .sort((a, b) => b.score - a.score)
    .slice(0, 20);
}

Extension Points

This lab implements a synchronous sequential search. For production use, extend it in three directions:

Parallel pattern evaluation. Each SearchPattern is independent — run them concurrently with Promise.all. The results must be merged with conflict resolution (same file matched by two patterns should get a combined score).

Incremental narrowing. Start with files_with_matches to get the candidate set, then run count mode to rank by frequency, then read only the top-ranked files. This minimizes token usage by avoiding full content reads for low-signal files.

Result reranking. The simple matchCount score can be augmented with signals from file recency (Glob modification order), file depth (files in src/core/ are more central than src/test/fixtures/), and cross-pattern co-occurrence (a file matching 3 patterns is more relevant than one matching 1).

Chapter Summary

The five filesystem tools form a hierarchy of abstraction. Glob discovers files by name. Grep filters by content. Read loads content for processing. Edit makes targeted modifications. Write creates or fully replaces files.

Understanding the contracts that TypeScript interfaces alone cannot express is what separates a harness that works from one that works reliably:

  • Read's file_unchanged dedup saves tokens but must be surfaced to the model or it causes confusion.
  • Edit's uniqueness constraint is a correctness guarantee, not a limitation — it prevents ambiguous replacements.
  • Write's read-before-write requirement is a safety check that prevents silent data loss.
  • Glob's 100-file truncation is a context budget safeguard, not a search limitation.
  • Grep defaults to head_limit: 250, which is usually right but must be adjusted for large codebases or unlimited needs.

The gitDiff integration on Edit and Write gives your harness a first-class audit trail without any additional infrastructure. Every change is self-describing.

The lab in Section 5.7 demonstrates how these five tools compose into a single coherent capability: a semantic code search that uses Glob for scoping, Grep for filtering and context extraction, and Read for deep inspection of the most relevant files. This composition pattern — narrow with Glob, filter with Grep, read selectively — is the foundation of almost every effective code navigation agent.
