Chapter 12: Workflow Engine — Deterministic Orchestration

"A workflow is not a prompt. A workflow is a program that deploys agents the way a compiler deploys instructions — structured, sequenced, and verifiable."

The Workflow tool is the point at which Claude Code stops being a reactive assistant and becomes a programmable orchestration engine. Where the Agent tool spawns a single subagent and waits, Workflow executes a full JavaScript program — phases, pipelines, parallel fans, token budgets — in a sandboxed runtime that coordinates dozens of subagents while you watch progress roll in.

This chapter is the most technically dense in the book. The interface is deceptively simple; the constraints are precise and unforgiving. Every concept here requires understanding not just what a function does but why it is designed the way it is and what breaks when you use it wrong.

12.1 Script Anatomy

A workflow script has two mandatory parts: a meta block at the top, and a body that runs in an implicit async context.

export const meta = {
  name: 'audit-codebase',
  description: 'Find and verify all security issues in the codebase'
}

const files = args.files ?? ['src/']

phase('Scan')
log(`Starting audit of ${files.length} target(s)`)

const findings = await pipeline(
  files,
  f => agent(`List all security-relevant files in ${f}`, {
    label: `scan:${f}`,
    schema: { type: 'object', properties: { paths: { type: 'array', items: { type: 'string' } } }, required: ['paths'] }
  }),
  (result, file) => agent(`Audit these files for OWASP Top 10 vulnerabilities: ${result.paths.join(', ')}`, {
    label: `audit:${file}`,
    schema: FINDING_SCHEMA
  })
)

phase('Synthesize')
const report = await agent('Synthesize these audit findings into a prioritized report', {
  label: 'synthesize',
  schema: REPORT_SCHEMA
})

log(`Audit complete — ${report.critical} critical, ${report.high} high`)

The body is a plain async JavaScript module. There is no explicit async function main() wrapper; the engine wraps the body for you. await works at the top level.

The exec model

When you invoke the Workflow tool, the harness does not block waiting for results. It:

  1. Parses the script (syntax check; the error field in the output reflects this)
  2. Persists the script to the session directory (the returned scriptPath tells you where)
  3. Launches the workflow in a background runtime
  4. Returns immediately with status: "async_launched" and a taskId

The taskId lets you monitor progress via the task system. The transcriptDir in the output tells you where subagent transcripts are written — useful for post-mortem debugging. The workflow runs whether or not the session stays open.

The two-part contract

The meta block and the body have a strict separation of concerns:

  • meta is structural metadata: name, description. It is parsed statically before execution. This is why it must be a pure literal — the parser cannot evaluate expressions, and it never tries.
  • Body is executable logic: any JavaScript you want, using the script API globals. It runs at runtime, after meta is safely extracted.

You can think of meta as a package manifest and the body as application code. They serve different audiences. The harness reads meta to index the workflow, display it in the task list, and validate it without running it. The runtime reads the body and executes it.

12.2 The Meta Constraint: Pure Literal Only

This constraint eliminates an entire class of bugs before they become production incidents.

// CORRECT — pure literal
export const meta = {
  name: 'find-todos',
  description: 'Find all TODO comments across the codebase'
}

// WRONG — variable reference
const WORKFLOW_NAME = 'find-todos'
export const meta = { name: WORKFLOW_NAME }  // syntax check fails

// WRONG — template literal
export const meta = {
  name: `audit-${Date.now()}`,              // fails: Date.now() disallowed; template fails meta parse
  description: `Run audit`
}

// WRONG — spread
const base = { description: 'Audit' }
export const meta = { ...base, name: 'audit' }  // spread fails meta parse

// WRONG — function call
export const meta = {
  name: getName(),                           // fails
  description: buildDescription('audit')
}

The parser that reads meta is not a full JavaScript evaluator. It extracts the object literal using static analysis — it looks for the token sequence export const meta = { and reads the literal that follows. Anything that requires runtime evaluation is invisible to it.

Why this constraint exists

Workflow scripts are indexed and resumed across sessions. The harness needs to read meta.name and meta.description without executing the script body — both for the task list UI and for the resume system that needs to match script identity to cached run state. If meta could contain runtime expressions, the harness would need to run the script just to read its name, creating a circular dependency.

The constraint also prevents a subtle class of non-determinism. A meta that included Date.now() would produce a different name on every run, breaking resume matching entirely.

Accepted values

The only accepted values in meta are string literals and numeric literals. Two fields are read:

FieldRequiredPurpose
nameYesUnique identifier for the workflow, used in resume matching
descriptionNoHuman-readable description for the task list

description in the tool input (WorkflowInput.description, WorkflowInput.title) is silently ignored — the runtime always reads from meta.description. This is a common source of confusion for engineers who try to set the displayed name through the tool call parameters.

12.3 agent(prompt, opts): Spawn a Subagent

agent() is the primitive unit of work in every workflow. It spawns a subagent, waits for completion, and returns the result.

// Without schema — returns the final text as a string
const summary = await agent('Summarize the architecture of src/core/')

// With schema — returns a validated JavaScript object
const issues = await agent('List all TODOs in the codebase', {
  label: 'find-todos',
  schema: {
    type: 'object',
    properties: {
      todos: {
        type: 'array',
        items: {
          type: 'object',
          properties: {
            file: { type: 'string' },
            line: { type: 'number' },
            text: { type: 'string' }
          },
          required: ['file', 'line', 'text']
        }
      },
      total: { type: 'number' }
    },
    required: ['todos', 'total']
  }
})
// issues.todos[0].file — type-safe access guaranteed by schema enforcement

Return value semantics

The return value depends entirely on whether schema is provided:

  • Without schema: returns the agent's final text output as a plain string. Use this when you want a narrative response that you will pass to another agent or display directly.
  • With schema: the runtime parses the agent's output as JSON and validates it against the schema. If validation passes, you get a typed JavaScript object. If validation fails, the runtime retries the agent with an error message appended — you never see the parse failure in your code, only the validated result.
  • User skips: if the user cancels an agent mid-run, agent() returns null. Your code must handle this. Passing null to a subsequent agent as part of a pipeline causes the pipeline to drop that item. Calling .property on null throws — guard it.
const result = await agent('Analyze this file', { schema: SCHEMA })
if (result === null) {
  log('User skipped analysis — continuing without this result')
} else {
  log(`Found ${result.issues.length} issues`)
}

Agent options

OptionTypeDefaultEffect
labelstringauto-generatedDisplay name in progress UI and transcript directory
phasestringcurrent phaseGroup this agent under a named phase (overrides phase() global)
schemaJSON Schema objectnoneEnforce structured output; enables object return value
model'opus' \'sonnet' \'haiku'inheritsOverride the model for this specific agent
isolation'worktree'noneRun agent in an isolated git worktree
agentType'Explore' \'Edit'defaultAgent persona: Explore for analysis, Edit for code changes

isolation: 'worktree'

When isolation is enabled, the agent runs inside a fresh git worktree — a separate working directory with the same commit state but no shared filesystem state with other agents. This is essential when multiple agents are making concurrent edits to the same codebase. Without isolation, concurrent Edit calls from separate agents cause conflicts and corrupted files.

// Concurrent editors MUST use worktree isolation
const patches = await parallel([
  () => agent('Refactor the auth module', { isolation: 'worktree', agentType: 'Edit' }),
  () => agent('Refactor the billing module', { isolation: 'worktree', agentType: 'Edit' }),
  () => agent('Refactor the notification module', { isolation: 'worktree', agentType: 'Edit' })
])
// Each agent works in its own worktree. Merge patches afterward.

The symlinkDirectories field in your .claude/settings.json worktree configuration (Chapter 2) controls which directories are symlinked rather than copied in each worktree — critical for node_modules and .venv which are large and read-only from the agent's perspective.

agentType

Explore agents are given a read-only persona — they are instructed to investigate and analyze without making changes. Use this for all discovery and verification phases. Edit agents are given full modification permissions. The distinction matters for both safety and prompt quality: an Explore agent that "accidentally" tries to write a file is working against its instructions.

12.4 pipeline(items, ...stages): Process Items Without a Barrier

pipeline() processes a list of items through a sequence of stages. The critical behavioral property: there is no barrier between stages. As soon as item A finishes stage 1, it immediately enters stage 2, while items B and C may still be in stage 1.

const results = await pipeline(
  sourceFiles,
  // Stage 1: analyze each file
  (file) => agent(`Analyze ${file} for security issues`, {
    label: `analyze:${file}`,
    schema: ANALYSIS_SCHEMA
  }),
  // Stage 2: verify each analysis (receives previous result, original item, index)
  (analysis, file, idx) => agent(`Verify this finding from ${file}: ${analysis.summary}`, {
    label: `verify:${file}`
  }),
  // Stage 3: generate a fix for each verified finding
  (verification, file) => agent(`Generate a minimal fix for the verified issue in ${file}`, {
    label: `fix:${file}`,
    schema: FIX_SCHEMA
  })
)

Stage callback signature

Each stage function receives three arguments:

(previousResult, originalItem, index) => Promise<any>
  • previousResult: the output of the previous stage for this item. For the first stage, this is the original item itself.
  • originalItem: the original item from the input array, unchanged across all stages.
  • index: the zero-based position of this item in the original array.

The originalItem parameter is essential when you need to reference the original data in a later stage where the previous result has transformed it into something else (a schema object, a parsed structure, etc.).

No barrier: the timing model

The absence of a barrier is what gives pipeline() its wall-clock efficiency:

gantt
    title pipeline() — 3 files, 3 stages (no barrier)
    dateFormat  ss
    axisFormat  %Ss

    section File A
    Stage 1 :a1, 0, 3s
    Stage 2 :a2, after a1, 4s
    Stage 3 :a3, after a2, 2s

    section File B
    Stage 1 :b1, 1s, 3s
    Stage 2 :b2, after b1, 4s
    Stage 3 :b3, after b2, 2s

    section File C
    Stage 1 :c1, 2s, 3s
    Stage 2 :c2, after c1, 4s
    Stage 3 :c3, after c2, 2s

File A starts stage 2 at T=3s. File B starts stage 2 at T=4s. File C starts stage 2 at T=5s. None of them wait for the others to finish a stage before progressing. The wall-clock time equals the duration of the slowest single chain (A, B, or C end-to-end), not the sum of all stages across all items.

Contrast this with a naive sequential loop:

// Naive — sequential. Wall clock = sum of all work.
const results = []
for (const file of sourceFiles) {
  const analysis = await agent(`Analyze ${file}`)
  const verification = await agent(`Verify: ${analysis}`)
  results.push(verification)
}

For 10 files with 3 stages of 4 seconds each, the sequential version takes 120 seconds. The pipeline version takes ~14 seconds (longest chain, plus scheduling overhead).

Error handling in pipeline

If a stage function throws, the item is silently dropped — it resolves to null in the output array and no subsequent stages run for that item. This is the correct behavior for workflows where one bad file should not abort the entire run.

const results = await pipeline(
  files,
  async (file) => {
    // Throw to skip this item
    if (!file.endsWith('.py')) throw new Error('Not a Python file')
    return agent(`Analyze ${file}`, { schema: SCHEMA })
  },
  (analysis, file) => agent(`Fix issues in ${file}`, { schema: FIX_SCHEMA })
)

// Filter nulls from results
const valid = results.filter(Boolean)
log(`Processed ${valid.length} of ${files.length} files`)

The filter(Boolean) pattern is standard pipeline hygiene — always filter the output array before using it.

12.5 parallel(thunks): Concurrent Execution With a Barrier

parallel() takes an array of zero-argument functions (thunks), executes them all concurrently, and waits for every one to finish before returning. This is a barrier.

const [security, performance, correctness] = await parallel([
  () => agent('Audit the codebase for OWASP Top 10 vulnerabilities', {
    label: 'security-audit',
    phase: 'Analysis'
  }),
  () => agent('Profile the critical path and identify bottlenecks', {
    label: 'perf-audit',
    phase: 'Analysis'
  }),
  () => agent('Verify all public API contracts match their documentation', {
    label: 'correctness-audit',
    phase: 'Analysis'
  })
])

// All three are guaranteed complete here
log(`Security: ${security}, Performance: ${performance}`)

The barrier guarantee

Every thunk resolves before parallel() returns — including thunks that throw. A throwing thunk resolves to null in the output array. parallel() itself never rejects. This is a critical difference from Promise.all(), which rejects on the first failure and may leave other promises in flight.

sequenceDiagram
    participant W as Workflow
    participant A as Agent 1
    participant B as Agent 2
    participant C as Agent 3

    W->>A: spawn (thunk 0)
    W->>B: spawn (thunk 1)
    W->>C: spawn (thunk 2)
    Note over W: BARRIER — waiting
    A-->>W: result[0]
    B-->>W: result[1] (null — threw)
    C-->>W: result[2]
    Note over W: ALL done — returns [r0, null, r2]

pipeline vs parallel: the decision rule

This is the most important design decision in workflow authoring:

Use caseChoose
Processing a list of items through multiple transformationspipeline
Running independent analyses that do not share dataparallel
Want wall-clock = slowest single item chainpipeline
Want wall-clock = slowest single thunk (barrier)parallel
Items feed into next stage as soon as readypipeline
Must have all results before proceedingparallel

A common composition: use parallel to launch multiple independent domain audits (security, performance, documentation), then pass all results to a single synthesis agent. Use pipeline to process a file list through scan → verify → fix.

// Outer parallel: three independent domain analyses
const [secFindings, perfFindings, docFindings] = await parallel([
  () => pipeline(files, f => agent(`Security scan: ${f}`, { schema: SEC_SCHEMA })),
  () => pipeline(files, f => agent(`Perf scan: ${f}`, { schema: PERF_SCHEMA })),
  () => pipeline(files, f => agent(`Doc coverage: ${f}`, { schema: DOC_SCHEMA }))
])

// Single synthesis after all domains complete
const report = await agent(
  `Synthesize these findings into a unified report`,
  { schema: REPORT_SCHEMA }
)

12.6 phase(title): Group Agents Under Named Phases

phase() is a display primitive. It sets the current phase label — all subsequent agent() calls are associated with this phase in the progress UI until phase() is called again with a new title.

phase('Discovery')
const structure = await agent('Map the module structure', { label: 'map-structure' })

phase('Analysis')
const issues = await pipeline(
  structure.modules,
  m => agent(`Analyze ${m}`, { label: `analyze:${m}`, schema: ISSUE_SCHEMA })
)

phase('Synthesis')
const report = await agent('Synthesize findings', { label: 'synthesize' })

The user sees the phase titles as the workflow progresses:

[Discovery] map-structure ....
[Analysis] analyze:auth (3/12) ....
[Analysis] analyze:billing (4/12) ....
[Synthesis] synthesize ....

Phases map directly to the phases array in the meta block if you want to pre-declare them:

export const meta = {
  name: 'code-audit',
  description: 'Comprehensive code audit in three phases',
  phases: ['Discovery', 'Analysis', 'Synthesis']
}

Pre-declaring phases in meta lets the UI show a progress bar with known phase count. Without pre-declaration, phases are shown as they appear but no total-count progress is available.

Overriding phase per agent

The phase option in agent() opts a specific agent into a named phase regardless of the global phase() call:

phase('Analysis')

// This agent shows under 'Analysis'
const mainAnalysis = await agent('Analyze the core module', { label: 'core' })

// This one shows under 'Background' regardless of the current global phase
const background = await agent('Check dependency licenses', {
  label: 'licenses',
  phase: 'Background'
})

This is useful when you spawn fire-and-forget agents that logically belong to a different context than your main workflow phase.

12.7 log(message): Emit Narrator Progress Lines

log() emits a progress line visible to the user during workflow execution. Use it sparingly and purposefully — it is not a debug logger, it is a narrator.

log('Starting audit of 47 Python files')

const results = await pipeline(files, analyzeFile)
const valid = results.filter(Boolean)

log(`Analysis complete — ${valid.length} files processed, ${files.length - valid.length} skipped`)

if (valid.some(r => r.severity === 'critical')) {
  log('Critical issues found — escalating to full verification')
}

Good log() calls:

  • Mark phase transitions with context: log('Switching to verification — 12 findings to check')
  • Report counts at milestones: log(${results.length} agents spawned)
  • Surface decision points: log('Budget below 50k — skipping deep verification')

Bad log() calls:

  • Debug noise: log('entering loop')
  • Redundant narration: log('calling agent') immediately before an agent() call

The user can already see agent labels and phase titles in the progress UI. log() is for information that would otherwise be invisible — counts, decisions, budget state, conditional branch taken.

12.8 args: Input Value from the Workflow Tool Call

args is the verbatim JavaScript object from the args field of the Workflow tool call. It is not a string; it is actual JSON deserialized into a JavaScript object.

// Tool call args field:
// { "files": ["src/auth/", "src/billing/"], "severity": "high" }

// In the script:
const files = args.files         // ["src/auth/", "src/billing/"]
const minSeverity = args.severity  // "high"

The stringified-JSON trap

The single most common args mistake is passing a JSON string instead of a JSON object:

// WRONG — args.files will be undefined because args is a string, not an object
// Tool call: { "args": "{\"files\": [\"src/\"]}" }

// CORRECT — args is actual JSON
// Tool call: { "args": { "files": ["src/"] } }

If you find yourself calling JSON.parse(args) or JSON.parse(args.config) in a script body, something is wrong at the call site. The Workflow tool's args field is typed as { [k: string]: unknown } — it must be a JSON object, never a string.

Defensive defaults

args may be null or an empty object if the workflow is called without arguments. Always provide defaults:

const files = args?.files ?? ['.']
const depth = args?.depth ?? 'full'
const model = args?.model ?? 'sonnet'
const exclude = Array.isArray(args?.exclude) ? args.exclude : []

The ?. optional chaining handles the null case. The ?? nullish coalescing handles the missing-key case. Both are necessary.

12.9 budget: Token Budget Tracking

budget exposes the token budget from the user's +500k directive. Use it to scale workflow depth to available resources.

// budget.total:       number | null (null if no target set)
// budget.spent():     number — output tokens used across all workflows this session
// budget.remaining(): number — max(0, total - spent()), or Infinity if no target

log(`Budget: ${budget.total ?? 'unlimited'}, spent: ${budget.spent()}, remaining: ${budget.remaining()}`)

The +500k directive

When a user prepends +500k to a prompt (or any token-count prefix), they are signaling a desired token budget for the operation. The Workflow runtime reads this and populates budget.total. Without a directive, budget.total is null and budget.remaining() returns Infinity.

Budget-adaptive patterns

Budget tracking enables workflows that self-regulate depth based on available tokens:

// Scale verification depth based on remaining budget
const FULL_VERIFY_COST_ESTIMATE = 8000    // tokens per file for deep verify
const LIGHT_VERIFY_COST_ESTIMATE = 2000   // tokens per file for surface verify

const useDeepVerify = budget.remaining() > files.length * FULL_VERIFY_COST_ESTIMATE

const verifiedFindings = await pipeline(
  findings,
  finding => agent(
    useDeepVerify
      ? `Deep verify: trace this finding through all call sites: ${finding.summary}`
      : `Surface verify: confirm this is a real issue: ${finding.summary}`,
    { label: `verify:${finding.id}` }
  )
)

Budget-limited loops

For workflows that run iterative improvement cycles, check budget before each iteration:

let iteration = 0
const improvements = []

while (budget.remaining() > 50_000 && iteration < 10) {
  log(`Iteration ${++iteration} — ${budget.remaining()} tokens remaining`)
  
  const improvement = await agent(`Iteration ${iteration}: Find the next highest-value improvement`)
  if (!improvement) break
  
  improvements.push(improvement)
  
  // Apply and verify
  await agent(`Apply this improvement: ${improvement}`, { isolation: 'worktree', agentType: 'Edit' })
}

log(`Completed ${iteration} improvement iterations`)

No budget directive

When budget.total is null, the workflow has no resource constraint from the user. Do not treat this as zero — treat it as unlimited. The guard if (budget.total && budget.remaining() > threshold) short-circuits cleanly when budget.total is null.

12.10 Agent Options: The Full Reference

All options for agent() in one place:

const result = await agent('prompt text', {
  // Display label in progress UI and transcript directory.
  // Use colon-separated hierarchy: 'verify:auth:tokens'
  label: 'verify:auth',
  
  // Override the current phase() for this specific agent.
  phase: 'Verification',
  
  // JSON Schema for structured output. Enables object return value.
  // Must be valid draft-07 JSON Schema.
  schema: {
    type: 'object',
    properties: {
      issues: { type: 'array', items: { type: 'string' } },
      severity: { type: 'string', enum: ['low', 'medium', 'high', 'critical'] },
      confident: { type: 'boolean' }
    },
    required: ['issues', 'severity', 'confident']
  },
  
  // Model tier for this agent. 'opus' for complex reasoning,
  // 'haiku' for high-volume mechanical tasks.
  model: 'sonnet',
  
  // 'worktree' gives this agent an isolated git worktree.
  // Required for concurrent agents that make file edits.
  isolation: 'worktree',
  
  // 'Explore' = read-only persona. 'Edit' = full modification access.
  agentType: 'Explore'
})

Model selection strategy

Matching model tier to task complexity is the primary cost-control lever in a workflow:

Task typeRecommended modelReasoning
Discovery, file listing, categorizationhaikuMechanical, high-volume, low reasoning demand
Code analysis, issue detectionsonnetGood balance of reasoning and throughput
Architectural synthesis, security auditopusMaximum reasoning for high-stakes conclusions
Structured data extractionhaiku with schemaSchema enforcement compensates for reasoning limits

In a large pipeline with 100 files, using haiku for the scan stage and sonnet only for verification of actual findings can reduce cost by 5-10x while maintaining result quality.

Label naming conventions

Labels appear in the transcript directory as folder names and in the progress UI. Use a colon-delimited hierarchy:

phase:subphase:item-identifier

Examples:

  • scan:auth — the scan phase, auth module
  • verify:finding:CWE-89 — verifying a specific finding
  • fix:billing:invoice-generator — generating a fix for a specific file

Avoid labels with slashes (these become path separators in the transcript directory). Avoid labels longer than 40 characters — they get truncated in the progress UI.

12.11 Concurrency: Limits and the Lifetime Cap

Two hard limits govern all workflow execution:

Simultaneous agent cap

min(16, CPU_CORES - 2)

On a machine with 12 CPU cores, the cap is 10 simultaneous agents. On a machine with 4 cores, the cap is 2. This is computed once at harness startup. You cannot configure it.

The practical implication: parallel([...100 thunks]) does not spawn 100 agents simultaneously. The runtime queues them and issues agents in batches up to the concurrency cap. The 100 agents will complete correctly — just in batches of (say) 10.

This is invisible to your script logic, but it matters for timing estimates. Do not assume all parallel() thunks start at T=0. On a 4-core machine, parallel([...20 thunks]) starts 2 agents at T=0, starts the next 2 when one completes, and so on.

Lifetime agent cap: 1000

A single workflow can spawn at most 1000 agents total. This includes all agents from nested pipeline() and parallel() calls and inline agent() calls. If the 1001st agent call is made, it returns null — same as a user-skipped agent.

For workflows processing large codebases, count your agents before running:

const files = args.files  // could be thousands
const AGENTS_PER_FILE = 3  // scan + verify + fix

if (files.length * AGENTS_PER_FILE > 900) {
  // Leave 100 agents for synthesis
  log(`WARNING: ${files.length} files × ${AGENTS_PER_FILE} = ${files.length * AGENTS_PER_FILE} agents — truncating to 300 files`)
  files.splice(300)
}

Workflow lifetime, not harness lifetime

The 1000-agent cap is per-workflow-run, not per harness session. Different workflows launched in the same session each get their own 1000-agent budget. A resumed workflow (via resumeFromRunId) picks up its count from the prior run — cached agent results do not consume new budget.

12.12 Resume Semantics and Script Iteration

Every workflow run is persisted. This is one of the most underused features in the engine.

The persistence model

When the Workflow tool returns, scriptPath in the output tells you where the script was saved:

~/.claude/projects/-Users-DOANTX26-Documents-2026/workflows/wf_a3b9kx/script.js

And runId identifies the execution:

wf_a3b9kx

To resume a failed or partial run:

// Re-invoke Workflow tool with:
{
  scriptPath: '...the returned scriptPath...',
  resumeFromRunId: 'wf_a3b9kx',
  args: { files: ['src/'] }
}

Cache semantics

The resume system uses a longest unchanged prefix strategy:

  • Agents that ran identically (same prompt, same args, same position in the execution graph) return cached results instantly
  • Agents after the first change re-run
  • A script edit that changes stage 3 logic still caches stages 1 and 2

For expensive workflows — say, a 200-file audit where each file spawns 3 agents — this means a bug in your synthesis stage can be fixed and re-run without re-paying for all 600 analysis agents. Only the synthesis stage re-runs.

100% cache hit: same script + same args + same resumeFromRunId. Use this deliberately when you want to re-run reporting or synthesis without re-running analysis.

The iteration workflow

The correct development cycle for complex workflows:

  1. Run the workflow — get runId and scriptPath back
  2. Observe the progress and partial results
  3. Edit the script with the Write or Edit tool using the returned scriptPath
  4. Re-invoke with scriptPath + resumeFromRunId
  5. Cached stages return immediately; changed stages re-run
  6. Repeat until the workflow produces the result you want

This is dramatically faster than restarting from scratch. A 30-minute full run becomes a 2-minute incremental re-run if you only change the synthesis prompt.

12.13 Lab: Build a Comprehensive Code Audit Workflow

This lab assembles every concept in the chapter into a production-quality audit workflow. It processes a codebase through three phases — find, verify, synthesize — with budget awareness, proper error handling, and resume support.

The specification

Given a list of directories, the workflow should:

  1. Discover all source files in each directory
  2. Audit each file for security and correctness issues
  3. Verify all high-severity findings with a second agent
  4. Synthesize a final report with prioritized remediation recommendations

Step 1: Define schemas

Schemas are the most important architectural decision in a workflow — they are the contracts between agents.

export const meta = {
  name: 'code-audit',
  description: 'Comprehensive three-phase code audit: find, verify, synthesize',
  phases: ['Discovery', 'Audit', 'Verification', 'Synthesis']
}

const FILE_LIST_SCHEMA = {
  type: 'object',
  properties: {
    files: {
      type: 'array',
      items: { type: 'string' },
      description: 'Absolute paths to source files found'
    },
    count: { type: 'number' }
  },
  required: ['files', 'count']
}

const FINDING_SCHEMA = {
  type: 'object',
  properties: {
    findings: {
      type: 'array',
      items: {
        type: 'object',
        properties: {
          file: { type: 'string' },
          line: { type: 'number' },
          severity: { type: 'string', enum: ['low', 'medium', 'high', 'critical'] },
          cwe: { type: 'string' },
          summary: { type: 'string' },
          recommendation: { type: 'string' }
        },
        required: ['file', 'line', 'severity', 'summary', 'recommendation']
      }
    },
    clean: { type: 'boolean' }
  },
  required: ['findings', 'clean']
}

const VERIFICATION_SCHEMA = {
  type: 'object',
  properties: {
    confirmed: { type: 'boolean' },
    false_positive_reason: { type: 'string' },
    additional_context: { type: 'string' }
  },
  required: ['confirmed']
}

const REPORT_SCHEMA = {
  type: 'object',
  properties: {
    executive_summary: { type: 'string' },
    critical_count: { type: 'number' },
    high_count: { type: 'number' },
    medium_count: { type: 'number' },
    low_count: { type: 'number' },
    confirmed_findings: { type: 'array', items: { type: 'object' } },
    remediation_order: { type: 'array', items: { type: 'string' } },
    estimated_effort_hours: { type: 'number' }
  },
  required: ['executive_summary', 'critical_count', 'high_count', 'confirmed_findings']
}

Step 2: Discovery phase

// Input: list of directories, or default to current directory
const targetDirs = args?.dirs ?? ['.']
const excludePatterns = args?.exclude ?? ['node_modules', '.venv', 'dist', 'build']
const minSeverity = args?.min_severity ?? 'medium'

log(`Starting audit of ${targetDirs.length} director${targetDirs.length === 1 ? 'y' : 'ies'}`)
log(`Minimum severity: ${minSeverity} | Budget: ${budget.total ? budget.remaining() + ' tokens remaining' : 'unlimited'}`)

phase('Discovery')

// Discover files in all target directories concurrently
const discoveries = await parallel(
  targetDirs.map(dir => () => agent(
    `List all source code files in ${dir}. Exclude: ${excludePatterns.join(', ')}. ` +
    `Include: .py, .js, .ts, .go, .rs, .java, .rb, .php, .c, .cpp files only. ` +
    `Return absolute paths.`,
    {
      label: `discover:${dir}`,
      schema: FILE_LIST_SCHEMA,
      model: 'haiku'   // mechanical listing task
    }
  ))
)

// Flatten all file lists, remove nulls from failed discoveries
const allFiles = discoveries
  .filter(Boolean)
  .flatMap(d => d.files)

log(`Discovered ${allFiles.length} source files across ${targetDirs.length} director${targetDirs.length === 1 ? 'y' : 'ies'}`)

if (allFiles.length === 0) {
  log('No source files found — check your target directories')
  // workflow ends — no return statement needed, body just completes
}

Step 3: Audit phase with budget guard

// Guard against 1000-agent cap: each file uses 2 agents (audit + possibly verify)
const MAX_FILES = 450  // leaves 100 agents for synthesis and overhead
const filesToAudit = allFiles.length > MAX_FILES
  ? (log(`Truncating to ${MAX_FILES} files to stay within agent budget`), allFiles.slice(0, MAX_FILES))
  : allFiles

phase('Audit')
log(`Auditing ${filesToAudit.length} files...`)

// pipeline: files flow through audit continuously — no barrier between files
const auditResults = await pipeline(
  filesToAudit,
  (file) => agent(
    `Audit this file for security vulnerabilities and correctness issues: ${file}\n\n` +
    `Focus on: injection flaws (CWE-89, CWE-78), authentication issues (CWE-287), ` +
    `cryptographic weaknesses (CWE-326, CWE-327), path traversal (CWE-22), ` +
    `hardcoded credentials (CWE-798), and logic errors that could cause data loss.\n\n` +
    `Use your Read tool to examine the file contents. Report only real issues — ` +
    `if the file is clean, set clean: true and findings: [].`,
    {
      label: `audit:${file.split('/').pop()}`,
      schema: FINDING_SCHEMA,
      model: 'sonnet',
      agentType: 'Explore'
    }
  )
)

// Collect all findings, filtering nulls
const allFindings = auditResults
  .filter(Boolean)
  .flatMap(r => r.findings)

const highSeverityFindings = allFindings.filter(
  f => f.severity === 'critical' || f.severity === 'high'
)
const otherFindings = allFindings.filter(
  f => f.severity === 'medium' || f.severity === 'low'
)

log(`Audit complete — ${allFindings.length} total findings: ` +
    `${highSeverityFindings.length} high/critical, ${otherFindings.length} medium/low`)

Step 4: Verification phase with budget awareness

phase('Verification')

// Only verify high/critical findings — and only if budget allows
const shouldVerify = (
  highSeverityFindings.length > 0 &&
  (budget.total === null || budget.remaining() > highSeverityFindings.length * 3000)
)

let confirmedHighSeverity = highSeverityFindings

if (shouldVerify) {
  log(`Verifying ${highSeverityFindings.length} high/critical findings...`)
  
  const verifications = await pipeline(
    highSeverityFindings,
    (finding, _, idx) => agent(
      `Verify this security finding is a real issue and not a false positive.\n\n` +
      `Finding: ${finding.summary}\n` +
      `File: ${finding.file} line ${finding.line}\n` +
      `CWE: ${finding.cwe ?? 'not specified'}\n\n` +
      `Use your Read tool to examine the file at the specified location. ` +
      `Check: is this actually exploitable? Is there sanitization or mitigation ` +
      `elsewhere that resolves this? Set confirmed: true only if this is a genuine issue.`,
      {
        label: `verify:${idx}:${finding.file.split('/').pop()}`,
        schema: VERIFICATION_SCHEMA,
        model: 'sonnet',
        agentType: 'Explore'
      }
    )
  )

  // Pair verification results with findings, keep only confirmed
  confirmedHighSeverity = highSeverityFindings.filter((finding, idx) => {
    const v = verifications[idx]
    return v && v.confirmed
  })

  const falsePositives = highSeverityFindings.length - confirmedHighSeverity.length
  log(`Verification complete — ${confirmedHighSeverity.length} confirmed, ${falsePositives} false positives eliminated`)
} else if (highSeverityFindings.length === 0) {
  log('No high/critical findings to verify')
} else {
  log(`Skipping verification — insufficient budget (${budget.remaining()} tokens remaining)`)
}

Step 5: Synthesis phase

phase('Synthesis')

const allConfirmedFindings = [
  ...confirmedHighSeverity,
  ...otherFindings  // medium/low are accepted without verification
]

log(`Synthesizing report for ${allConfirmedFindings.length} confirmed findings...`)

const findingsSummary = allConfirmedFindings
  .map(f => `- [${f.severity.toUpperCase()}] ${f.file}:${f.line} — ${f.summary}`)
  .join('\n')

const report = await agent(
  `Generate a comprehensive security audit report for an engineering team.\n\n` +
  `Confirmed findings (${allConfirmedFindings.length} total):\n${findingsSummary}\n\n` +
  `The report should include:\n` +
  `1. Executive summary (2-3 sentences suitable for a VP of Engineering)\n` +
  `2. Counts by severity\n` +
  `3. The confirmed findings list with their recommendations\n` +
  `4. A remediation order — prioritize by severity and blast radius\n` +
  `5. Estimated total effort hours for remediation\n\n` +
  `Be direct and actionable. This is an internal engineering document, not a sales document.`,
  {
    label: 'synthesize-report',
    schema: REPORT_SCHEMA,
    model: 'opus'  // architectural synthesis — use opus
  }
)

if (!report) {
  log('Synthesis failed — producing minimal report from raw findings')
  // Fallback: emit raw findings
  log(`Raw findings: ${JSON.stringify(allConfirmedFindings, null, 2)}`)
} else {
  log(`Report complete`)
  log(`Executive summary: ${report.executive_summary}`)
  log(`Severity breakdown: ${report.critical_count} critical, ${report.high_count} high, ${report.medium_count ?? 0} medium, ${report.low_count ?? 0} low`)
  log(`Estimated remediation effort: ${report.estimated_effort_hours ?? 'unknown'} hours`)
  log(`Remediation order: ${report.remediation_order?.join(' → ') ?? 'see findings'}`)
}

Running the workflow

Invoke from the Workflow tool:

// In a Claude Code session, use the Workflow tool:
{
  script: '...the full script above...',
  args: {
    dirs: ['src/', 'lib/'],
    exclude: ['node_modules', '__pycache__', '.venv'],
    min_severity: 'medium'
  }
}

Or for a large repo with a token budget:

The +500k directive populates budget.total so the verification phase self-regulates.

Iterating on the workflow

After the first run:

  1. Check the transcript directory from transcriptDir in the tool output
  2. Find agents that produced poor results (read their transcript)
  3. Edit the prompt for that stage in the script at scriptPath
  4. Re-invoke with resumeFromRunId — preceding stages return from cache, the edited stage re-runs

If the synthesis prompt is wrong but the 200-file audit was correct, re-running with the fix costs only one synthesis agent call — not 400 audit calls.

Summary

The Workflow engine is the most expressive tool in the Claude Code harness. It transforms one-shot agent calls into structured programs with phases, pipelines, parallel fans, and token budgets.

The key constraints to carry into production:

meta must be a pure literal. Static parsing, not runtime evaluation. Variables, template literals, spreads, and function calls all fail.

pipeline() has no barrier. Items flow through stages as soon as the previous stage completes. Wall-clock time equals the slowest single item chain. Use this for per-item transformations.

parallel() has a barrier. All thunks must complete before it returns. Throws resolve to null, never reject. Use this for independent analyses that need to be combined.

args is actual JSON, not a string. The args field is { [k: string]: unknown }. Passing a stringified JSON string is the most common invocation mistake.

Agent cap is min(16, cores-2) simultaneous and 1000 lifetime. Design against these limits explicitly when processing large file sets.

Resume semantics save expensive re-runs. Every workflow persists its script and run ID. Edit the script, re-invoke with resumeFromRunId, and only changed stages re-execute.

The code audit workflow in section 12.12 is production-ready. Copy it, adjust the schemas for your domain, and use it as the foundation for any multi-agent analysis task.
