Chapter 13: Advanced Workflow Patterns

"The pipeline is not a stage graph. It is a promise: every item either finishes or fails cleanly, and no item waits for another."

13.1 pipeline() vs parallel(): When Barriers Help vs Hurt

The single most consequential decision in multi-agent workflow design is choosing between pipeline() and parallel(). Both run work concurrently. The difference is whether you insert a synchronization barrier — a point where all upstream work must complete before any downstream work begins. Get this wrong and you trade throughput for false structure, or correctness for speed.

pipeline() is the default. It processes a collection of items through a sequence of per-item transforms, running each item independently through all stages. Items that complete early do not wait for slower items. A throw in any stage drops that item to null for the rest of the pipeline. The result is an array of the same length as the input, with null in positions that failed or were skipped.

parallel() is a barrier. It launches a collection of tasks simultaneously and waits for all of them to settle before returning. Every caller downstream of parallel() is blocked until the slowest task finishes.

flowchart LR
    subgraph "pipeline() — per-item flow, no barrier"
        direction TB
        I1[item A] --> S1A[stage 1] --> S2A[stage 2] --> S3A[stage 3]
        I2[item B] --> S1B[stage 1] --> S2B[stage 2] --> S3B[stage 3]
        I3[item C] --> S1C[stage 1] --> S2C[stage 2] --> S3C[stage 3]
    end

    subgraph "parallel() — barrier, all-or-wait"
        direction TB
        T1[task 1] --> BAR{wait for all}
        T2[task 2] --> BAR
        T3[task 3] --> BAR
        BAR --> DOWN[downstream code]
    end

When barriers genuinely help

A barrier is justified when downstream logic has a cross-item dependency — when it needs to look across all results together. Three concrete cases:

Deduplication. You are running N finders to collect bugs across a large codebase. Two finders may return the same issue. You cannot deduplicate per-item; you need all findings in hand before you can run seen.has(key(b)). A parallel() barrier followed by a dedup pass is the correct structure here, not a pipeline.

Early-exit / circuit breaking. You are running N verifiers on a candidate solution. If any verifier returns critical: true, you want to abort all remaining work and surface the critical finding immediately. A parallel() lets you Promise.race() or post-process the full result set with an early exit. Pipeline does not give you this cross-item visibility mid-flight.

Synthesis across all outputs. You are running N approaches to a problem (judge panel, §13.7) and the synthesis step requires comparing all N outputs. You cannot synthesize until all approaches are complete. A barrier is the correct model.

When barriers hurt

A barrier hurts when there is no cross-item dependency but you inserted one anyway. The cost is latency: every item in the faster batch waits for the slowest item to complete before the downstream stages begin.

The smell test is simple: if the transform between stages has no logic that reads from two different items in the same batch, the barrier is wrong.

// Wrong: unnecessary barrier between review and verify stages
const reviews = await parallel(DIMENSIONS.map(d => () =>
  agent(d.prompt, {schema: FINDINGS_SCHEMA})))
// now the slowest dimension has finished, and THEN we start verification
const verified = await parallel(reviews.filter(Boolean).flatMap(r =>
  r.findings.map(f => () => agent(`Verify: ${f.title}`, {schema: VERDICT_SCHEMA}))))

The verify stage has no dependency on other dimensions' findings. Introducing the barrier between them doubles the critical path. The correct version is a pipeline with inline verify:

// Correct: pipeline — each dimension's findings flow directly into verify
const results = await pipeline(
  DIMENSIONS,
  d => agent(d.prompt, {label: `review:${d.key}`, phase: 'Review', schema: FINDINGS_SCHEMA}),
  review => parallel(review.findings.map(f => () =>
    agent(`Adversarially verify: ${f.title}`, {label: `verify:${f.file}`, phase: 'Verify', schema: VERDICT_SCHEMA})
      .then(v => ({...f, verdict: v}))))
)
const confirmed = results.flat().filter(Boolean).filter(f => f.verdict?.isReal)

Here, parallel() inside the second pipeline stage is not a cross-item barrier — it is intra-item concurrency: we launch all verifiers for one dimension's findings in parallel, then the pipeline carries results forward. The outer pipeline ensures that dimension A's verify step begins the moment dimension A's review step completes, without waiting for dimension B.

The barrier-justified checklist

Before adding a parallel() barrier, confirm at least one of:

JustificationExample
Deduplication across itemsMultiple finders, dedup by key before verify
Early-exit or circuit-breakAny verifier returns critical → abort
Cross-item ranking or selectionJudge panel: pick winner from all approaches
Synthesis requires complete pictureCompleteness critic needs all findings to say what's missing
Token budget check across all resultsBudget loop needs full batch to decide whether to continue

If none apply: use pipeline().

13.2 Resume Semantics: resumeFromRunId

Every agent() call inside a Workflow is journaled. The journal records the call's identity — its prompt, schema, label, and positional context — alongside its result. When you pass resumeFromRunId on a subsequent invocation, the harness replays the journal: calls whose identity matches an existing entry return the cached result without sending anything to the API. Calls whose identity has changed (because you edited the script) run fresh.

This is not a "skip completed steps" primitive. It is content-addressable caching. The cache key is derived from the call's observable identity. If you change the prompt by one character, the call is considered new and re-runs.

// First run — returns scriptPath and runId in the response
// {
//   runId: "wf_abc123",
//   scriptPath: "/path/to/audit.js"
// }

// Edit the script: add a new dimension or fix a prompt, then re-invoke:
// Workflow({scriptPath: "/path/to/audit.js", resumeFromRunId: "wf_abc123"})
//
// Unchanged agent() calls → cached result, no API call
// Edited or new agent() calls → run fresh, result journaled

The practical consequence: non-determinism breaks resume

Resume depends on stable call identity. Three constructs destroy that stability:

Date.now() — timestamps change on every run. A prompt that includes the current timestamp will never match a cached entry. Every call is "new" every time.

Math.random() — injecting a random seed, nonce, or UUID into a prompt text breaks identity. The prompt on the second run will never equal the prompt on the first run.

new Date() — same problem as Date.now(), in constructor form.

These are not available in Workflow scripts. The sandbox disallows them. This is a correctness constraint, not an oversight: if the harness permitted them, resume would silently fall back to a full re-run every time without telling you why.

Design for resumability. Prompts should be pure functions of their inputs: the item being processed, the schema, and fixed configuration. Never interpolate timestamps, random IDs, or wall-clock state into prompt text. If you need a unique identifier per invocation (for tracing, not for the prompt), pass it as metadata that does not affect the cache key.

When to use resume

Resume pays off in two scenarios:

  1. Long workflows interrupted mid-run. A 300-call security audit that fails at call 247 resumes from call 247, not from scratch. The saved cost is proportional to how far the workflow had progressed.
  1. Iterative development. You are tuning a workflow script. You change the synthesis prompt at the end but leave the 50 finder calls untouched. Resume re-runs only the synthesis, not the finders. The development loop tightens from minutes to seconds.

Resume is not appropriate when the workflow is inherently stateful — when later calls should see the effects of earlier ones on an external system. Journal caching replays outputs; it does not replay side effects.

13.3 Nested Workflows: workflow(nameOrRef, args)

A workflow can spawn a child workflow with workflow(nameOrRef, args). The child executes as a sub-step: it has its own script, its own labeled agent calls, and its own result. From the parent's perspective, it is a single async operation that returns the child's output.

// Parent workflow
const subResult = await workflow('find-todos', {dir: 'src/'})
// subResult is whatever the child workflow returns
const todos = subResult.todos

// Alternatively, by script path:
const subResult = await workflow('/absolute/path/to/find-todos.js', {dir: 'src/'})

The child shares the parent's execution context:

  • Concurrency cap. The child's agent() calls consume slots from the same concurrency pool as the parent. If the parent is already running 10 agents and the concurrency cap is 12, the child can only run 2 agents simultaneously.
  • Agent counter. The total agent count displayed in the UI accumulates across parent and child.
  • Abort signal. If the user cancels the parent, the child is cancelled too.
  • Token budget. The child draws from the same budget object as the parent.

Nesting is one level only

A workflow spawned by a workflow cannot itself spawn a workflow. Calling workflow() inside a child workflow throws. This constraint is intentional: deep nesting makes execution traces unreadable, abort semantics compound, and debugging becomes archaeology. If you need more than two levels of decomposition, flatten the structure — compose it as named stages in the parent, not as a tree of workflows.

When to use nested workflows

The right use case for nested workflows is reusable sub-task composition — a bounded piece of work that:

  1. Makes sense as a standalone unit (can be tested and invoked independently),
  2. Has a clean input/output contract,
  3. Is reused across multiple parent workflows.

A find-todos workflow, a summarize-file workflow, a triage-issues workflow — these are clean sub-step candidates. A workflow that does "everything except the last step" is not.

flowchart TD
    P[Parent: security-audit] --> A[find-todos workflow]
    P --> B[dependency-scan workflow]
    P --> C[direct agent calls for synthesis]
    A --> R[subResult.todos]
    B --> R2[subResult.vulns]
    R & R2 & C --> SYNTH[Final report]

The key discipline: do not nest for organizational tidiness. Nest only when the sub-workflow has independent value and reuse justifies the additional execution boundary.

13.4 Structured Output: The schema Option

Every agent() call accepts a schema option — a JSON Schema object. When provided, the harness forces the model to use the StructuredOutput tool, which validates the model's response against the schema before returning it to your workflow code. Invalid output causes a retry within the agent call; the calling workflow sees only validated results or null.

const VERDICT_SCHEMA = {
  type: 'object',
  required: ['isReal', 'confidence', 'reason'],
  properties: {
    isReal: { type: 'boolean' },
    confidence: { type: 'number', minimum: 0, maximum: 1 },
    reason: { type: 'string', minLength: 10 }
  },
  additionalProperties: false
}

const verdict = await agent(
  `Verify this finding: ${JSON.stringify(finding)}`,
  {schema: VERDICT_SCHEMA, label: `verify:${finding.id}`}
)
// verdict is null (user skipped) or a typed, validated object

Without schema, the model returns a text string. With schema, you get a typed JavaScript object that satisfies your contract. This is not cosmetic — it eliminates an entire class of downstream bugs caused by parsing free-form model output.

Schema design for reliability

A schema that is too strict will cause excessive retries. A schema that is too loose defeats the purpose. Guidelines:

Require what you actually need. If reason is optional downstream, do not put it in required. The model will sometimes produce a valid object without it.

Use additionalProperties: false in output schemas. This prevents the model from injecting extra fields that look valid but break downstream destructuring.

Prefer flat objects over deep nesting. Nested required objects compound validation failures. A finding with three required nested objects is harder for the model to produce in a single well-formed response than a flat object with six required string fields.

Use enum for categorical values. severity: { type: 'string', enum: ['low', 'medium', 'high', 'critical'] } is far more reliable than asking the model to produce the right string from an unconstrained field.

schema and the StructuredOutput tool

When schema is present, the agent's system prompt is augmented to instruct the model to call StructuredOutput exactly once as its final action. The tool call's arguments are validated against the schema. If validation fails, the harness sends the validation error back to the model and gives it a second attempt. This retry loop is transparent to the workflow author — you see a result or null, never a validation error.

13.5 Adversarial Verification

A single agent reviewing its own work is not verification — it is self-approval. Adversarial verification runs N independent skeptics whose default posture is assume the claim is wrong. Only claims that survive a majority of skeptics are considered confirmed.

const VERDICT_SCHEMA = {
  type: 'object',
  required: ['refuted', 'reason'],
  properties: {
    refuted: { type: 'boolean' },
    reason: { type: 'string', minLength: 20 }
  },
  additionalProperties: false
}

async function adversarialVerify(claim: string, threshold = 2): Promise<boolean> {
  const votes = await parallel(Array.from({length: 3}, () => () =>
    agent(
      `Try to refute this claim. Default to refuted=true if uncertain.\n\nClaim: ${claim}`,
      {schema: VERDICT_SCHEMA, label: `skeptic:${claim.slice(0, 40)}`}
    )
  ))
  const valid = votes.filter(Boolean)
  const survivors = valid.filter(v => !v.refuted).length
  log(`Claim "${claim.slice(0, 60)}": ${survivors}/${valid.length} skeptics passed`)
  return survivors >= threshold
}

The default-to-refuted instruction is load-bearing. Without it, agents default to the cooperative posture that characterizes most model training — they look for reasons to agree. Flipping the default forces them to look for reasons to disagree. A claim that cannot be refuted despite active effort to do so is a meaningfully stronger claim.

When to use adversarial verification

Use adversarial verification when the cost of a false positive is high: security findings, correctness proofs, legal analysis, any claim that will drive an action that is expensive to undo. Do not use it on low-stakes factual lookups where the overhead is not justified.

Configuring N and threshold

Three skeptics with a threshold of 2 (two-of-three majority) is a reasonable default. For high-stakes claims, use five skeptics with a threshold of 4. For findings that will be published externally or used to block a deployment, consider a unanimous three-of-three bar. The harness API supports any N and threshold — the cost is N additional API calls per claim.

The null-handling requirement

agent() returns null if the user skips the step. In a parallel skeptic pool, any of the N votes can be null. Always .filter(Boolean) before counting survivors:

const valid = votes.filter(Boolean)  // Remove skipped/null agents
const survivors = valid.filter(v => !v.refuted).length

If all three skeptics return null (the user skipped everything), valid.length is 0 and survivors >= 2 is false — the claim correctly fails verification. This is the right behavior: absence of confirmation is not confirmation.

13.6 Perspective-Diverse Verification

Adversarial verification uses identical skeptics. Perspective-diverse verification uses N agents with distinct lenses — each examines the same claim or solution through a different frame of reference. The combination is stronger than adversarial alone: a claim that survives a correctness lens, a security lens, a performance lens, and a reproducibility lens has been stress-tested from four directions.

const LENSES = [
  {
    name: 'correctness',
    prompt: (finding: string) =>
      `Examine this finding for correctness errors. Is the described behavior actually a bug? ` +
      `Would the code really do what the finding claims? Be skeptical.\n\nFinding: ${finding}`
  },
  {
    name: 'security',
    prompt: (finding: string) =>
      `Examine this finding from a security perspective. Is the described issue exploitable? ` +
      `What is the realistic attack vector? Could this be a false positive?\n\nFinding: ${finding}`
  },
  {
    name: 'performance',
    prompt: (finding: string) =>
      `Examine this finding from a performance perspective. Does the described issue actually ` +
      `impact performance at realistic scale, or only in pathological cases?\n\nFinding: ${finding}`
  },
  {
    name: 'reproducibility',
    prompt: (finding: string) =>
      `Examine this finding for reproducibility. Can this finding be triggered reliably? ` +
      `Is there a clear reproduction path, or is this speculative?\n\nFinding: ${finding}`
  }
]

const LENS_VERDICT_SCHEMA = {
  type: 'object',
  required: ['valid', 'concerns', 'lens'],
  properties: {
    valid: { type: 'boolean' },
    concerns: { type: 'string' },
    lens: { type: 'string' }
  },
  additionalProperties: false
}

async function perspectiveVerify(finding: string) {
  const verdicts = await parallel(LENSES.map(lens => () =>
    agent(lens.prompt(finding), {
      schema: LENS_VERDICT_SCHEMA,
      label: `lens:${lens.name}`
    })
  ))
  const valid = verdicts.filter(Boolean)
  const passing = valid.filter(v => v.valid)
  const failing = valid.filter(v => !v.valid)
  return {
    confirmed: failing.length === 0,
    concerns: failing.map(v => `[${v.lens}] ${v.concerns}`),
    passRate: `${passing.length}/${valid.length}`
  }
}

Perspective diversity catches failures that adversarial review misses. A uniform adversarial panel might all focus on whether the code is syntactically correct and unanimously confirm a bug that is actually never triggered in production. The reproducibility lens would catch that. A uniform adversarial panel reviewing a regex-based SQL injection finding might all miss the fact that the ORM layer would sanitize the input first. The security lens with an explicit focus on attack vectors would catch that.

13.7 The Judge Panel

The judge panel pattern solves the problem of approach selection: when multiple agents solve the same problem via different methods, you need an objective way to identify the best solution. The panel pattern decouples generation from evaluation, ensuring that the evaluation is not anchored to any single approach.

const ANGLES = [
  {name: 'minimal', description: 'smallest possible change that solves the problem'},
  {name: 'defensive', description: 'hardened, input-validated, edge-case-resistant approach'},
  {name: 'idiomatic', description: 'most idiomatic for the language and codebase conventions'},
  {name: 'performant', description: 'optimized for throughput and minimal allocations'}
]

const SOLUTION_SCHEMA = {
  type: 'object',
  required: ['approach', 'code', 'tradeoffs'],
  properties: {
    approach: { type: 'string' },
    code: { type: 'string' },
    tradeoffs: { type: 'string' }
  },
  additionalProperties: false
}

const SCORE_SCHEMA = {
  type: 'object',
  required: ['score', 'rationale'],
  properties: {
    score: { type: 'integer', minimum: 1, maximum: 10 },
    rationale: { type: 'string', minLength: 20 }
  },
  additionalProperties: false
}

async function judgePanel(problem: string) {
  // Phase 1: Generate N approaches in parallel
  const approaches = await parallel(ANGLES.map(a => () =>
    agent(
      `Solve this problem via the ${a.name} approach (${a.description}):\n\n${problem}`,
      {schema: SOLUTION_SCHEMA, label: `approach:${a.name}`}
    )
  ))

  // Phase 2: Score each approach in parallel (barrier required — all solutions needed)
  const viable = approaches.filter(Boolean)
  const scores = await parallel(viable.map(s => () =>
    agent(
      `Score this solution 1-10 for correctness, maintainability, and fitness for purpose. ` +
      `Be strict. A 10 is production-ready with no significant issues.\n\n` +
      `${JSON.stringify(s, null, 2)}`,
      {schema: SCORE_SCHEMA, label: `score:${s?.approach}`}
    )
  ))

  // Phase 3: Synthesize from the winner
  const validScores = scores.filter(Boolean)
  const maxScore = Math.max(...validScores.map(s => s?.score || 0))
  const winnerIdx = scores.indexOf(validScores.find(s => s?.score === maxScore) ?? null)
  const winner = viable[winnerIdx]

  log(`Judge panel: winner is "${winner?.approach}" with score ${maxScore}`)

  return await agent(
    `Synthesize a final solution based on this winning approach, incorporating ` +
    `the best elements. Explain why this approach was selected.\n\nWinner: ${JSON.stringify(winner)}`,
    {label: 'synthesis'}
  )
}

The barrier between phase 1 and phase 2 is justified here: scoring requires all solutions to be available so the scorer can compare across approaches. The phase 2 → phase 3 barrier is also justified: synthesis requires knowing the winner, which requires all scores.

Gotchas

Anchoring in the scoring prompt. If your scoring prompt shows all solutions simultaneously, the model anchors to the first one. Score each solution independently (one agent() per solution) and let the Math.max() logic do the comparison.

Ties. Multiple solutions can share the max score. Decide your tie-breaking rule before you need it: first-wins, random selection among ties, or a dedicated tiebreaker agent call.

The approaches[winnerIdx] indexing. After filtering for Boolean, the winnerIdx into scores must map to the same position in viable. Maintain the parallel arrays carefully. The pattern above uses viable for both — no re-filtering between phases.

13.8 Loop-Until-Dry

Some problems do not have a fixed number of items to process. A codebase might have 3 bugs or 300; you do not know in advance. Loop-until-dry runs finders in a loop, terminating when K consecutive rounds produce no new findings. The deduplication across rounds ensures that findings are not double-counted.

const BUGS_SCHEMA = {
  type: 'object',
  required: ['bugs'],
  properties: {
    bugs: {
      type: 'array',
      items: {
        type: 'object',
        required: ['id', 'title', 'file', 'line', 'severity'],
        properties: {
          id: { type: 'string' },
          title: { type: 'string' },
          file: { type: 'string' },
          line: { type: 'integer' },
          severity: { type: 'string', enum: ['low', 'medium', 'high', 'critical'] }
        },
        additionalProperties: false
      }
    }
  }
}

const FINDERS = [
  {name: 'injection', prompt: 'Find all injection vulnerabilities (SQL, command, LDAP, XPath)...'},
  {name: 'auth', prompt: 'Find all authentication and authorization bypass issues...'},
  {name: 'crypto', prompt: 'Find all cryptographic misuse (weak algorithms, hardcoded keys, bad RNG)...'},
  {name: 'logic', prompt: 'Find all business logic flaws and race conditions...'}
]

const key = (b: {file: string, line: number, title: string}) =>
  `${b.file}:${b.line}:${b.title}`

async function loopUntilDry(targetDir: string, dryThreshold = 2) {
  const seen = new Set<string>()
  const confirmed: typeof BUGS_SCHEMA['properties']['bugs']['items'][] = []
  let dry = 0

  while (dry < dryThreshold) {
    // Parallel finder sweep
    const round = await parallel(FINDERS.map(f => () =>
      agent(
        `${f.prompt}\n\nDirectory: ${targetDir}\nAlready found: ${seen.size} issues. ` +
        `Focus on issues NOT in this list: ${JSON.stringify([...seen].slice(0, 50))}`,
        {label: `find:${f.name}`, phase: 'Find', schema: BUGS_SCHEMA}
      )
    ))

    const found = round.filter(Boolean).flatMap(r => r!.bugs)
    const fresh = found.filter(b => !seen.has(key(b)))

    if (!fresh.length) {
      dry++
      log(`Dry round ${dry}/${dryThreshold} — no new findings from ${FINDERS.length} finders`)
      continue
    }

    dry = 0
    fresh.forEach(b => seen.add(key(b)))
    log(`Found ${fresh.length} new issues (${confirmed.length + fresh.length} total)`)

    // Adversarially verify the fresh findings before adding to confirmed
    const verifiedRound = await parallel(fresh.map(f => () =>
      adversarialVerify(JSON.stringify(f)).then(isReal => isReal ? f : null)
    ))
    confirmed.push(...verifiedRound.filter(Boolean))
    log(`${verifiedRound.filter(Boolean).length}/${fresh.length} verified as real`)
  }

  return confirmed
}

Why the dry counter resets on any fresh finding

The dry counter tracks consecutive empty rounds — not total empty rounds. If rounds 1, 2, 3 produce findings but round 4 does not, dry is 1, not 4. The loop continues because the recent productivity justifies one more pass. Only when there have been dryThreshold empty rounds in a row do we conclude that the finder space is exhausted.

The Already found prompt injection

Feeding the set of already-found issues back into the finder prompt is optional but effective. Without it, finders in round 2 will frequently re-find the same issues and the dedup logic will just discard them. With it, you explicitly steer finders away from known territory. The tradeoff: if the known-issues list grows very large, the prompt injection starts consuming significant tokens. Cap the list at 50–100 entries for the prompt while maintaining the full seen set for dedup.

13.9 Loop-Until-Budget

When you do not know how many items a workflow will find, but you do know how much you are willing to spend, the budget loop is the correct termination condition. Rather than "stop when dry," you stop when the token budget drops below a safety threshold.

async function loopUntilBudget(
  prompt: string,
  schema: object,
  minRemainingTokens = 50_000
) {
  const results: unknown[] = []

  while (budget.total && budget.remaining() > minRemainingTokens) {
    const result = await agent(prompt, {schema})

    if (!result) break  // User skipped — treat as stop

    const items = (result as any).items ?? [result]
    results.push(...items)

    log(
      `${results.length} items found, ` +
      `${Math.round(budget.remaining() / 1000)}k tokens remaining ` +
      `(threshold: ${Math.round(minRemainingTokens / 1000)}k)`
    )
  }

  if (budget.remaining() <= minRemainingTokens) {
    log(`Budget threshold reached — stopping with ${results.length} items`)
  }

  return results
}

Combining budget and dry termination

In practice, production audit workflows use both conditions:

let dry = 0
while (dry < 2 && budget.total && budget.remaining() > 50_000) {
  const round = await parallel(FINDERS.map(f => () => agent(f.prompt, {schema: BUGS_SCHEMA})))
  const fresh = round.filter(Boolean).flatMap(r => r!.bugs).filter(b => !seen.has(key(b)))
  if (!fresh.length) { dry++; continue }
  dry = 0
  // ... process fresh
}

This terminates on whichever condition is reached first: the finders run dry, or the budget is consumed. Neither condition alone is sufficient — dry-only can run forever on a large codebase; budget-only can terminate prematurely if the budget is consumed by expensive verification calls.

The budget.total guard

budget.total is a boolean that is false if no budget was configured for the workflow. Always check it before calling budget.remaining() to avoid a division-by-zero or undefined-access error in budget-unaware invocations.

13.10 Multi-Modal Sweep

A multi-modal sweep decomposes a problem into orthogonal search dimensions and launches one agent per dimension. Unlike loop-until-dry (which runs the same finders repeatedly until exhausted), a sweep is a single pass across a pre-defined set of perspectives.

const DIMENSIONS = [
  {key: 'sql-injection', prompt: 'Review all SQL query construction for injection vulnerabilities. Focus on dynamic query building, ORM raw() calls, and parameterization gaps.'},
  {key: 'auth-bypass', prompt: 'Review all authentication and authorization checkpoints. Look for missing auth checks, insecure direct object references, and privilege escalation paths.'},
  {key: 'crypto', prompt: 'Review all cryptographic operations. Identify weak algorithms (MD5, SHA1, DES), hardcoded keys/salts, and insecure random number generation.'},
  {key: 'deserialization', prompt: 'Review all deserialization and object construction from external input. Look for unsafe pickle, YAML load, JSON parse of untrusted data.'},
  {key: 'ssrf', prompt: 'Review all outbound HTTP calls, URL construction, and redirect handling for SSRF vulnerabilities.'},
  {key: 'file-ops', prompt: 'Review all file operations for path traversal, symlink attacks, and unsafe temp file handling.'}
]

const FINDINGS_SCHEMA = {
  type: 'object',
  required: ['findings'],
  properties: {
    findings: {
      type: 'array',
      items: {
        type: 'object',
        required: ['title', 'file', 'line', 'severity', 'description'],
        properties: {
          title: { type: 'string' },
          file: { type: 'string' },
          line: { type: 'integer' },
          severity: { type: 'string', enum: ['low', 'medium', 'high', 'critical'] },
          description: { type: 'string', minLength: 50 }
        },
        additionalProperties: false
      }
    }
  }
}

// Pipeline: each dimension's findings flow directly into verification
const results = await pipeline(
  DIMENSIONS,
  d => agent(d.prompt, {label: `review:${d.key}`, phase: 'Review', schema: FINDINGS_SCHEMA}),
  review => parallel(
    review.findings.map(f => () =>
      agent(
        `Adversarially verify this finding. Default to isReal=false if uncertain.\n\n${JSON.stringify(f)}`,
        {label: `verify:${f.file}:${f.line}`, phase: 'Verify', schema: VERDICT_SCHEMA}
      ).then(v => v ? {...f, verdict: v} : null)
    )
  )
)

const confirmed = results.flat().filter(Boolean).filter(f => f.verdict?.isReal)

The sweep gives you breadth guarantee: if the problem space can be partitioned into K dimensions, you know every dimension has been covered. This is the property loop-until-dry lacks — loops guarantee exhaustion per dimension, but do not guarantee coverage if a dimension was never explicitly defined.

Pipeline vs parallel for the outer sweep. The outer pipeline() is correct here. Review and verify for dimension A can proceed immediately without waiting for review of dimension B. There is no cross-dimension dependency. A parallel() barrier at the review level would make dimension A's verify step wait for dimension F's review to complete — unnecessary latency.

13.11 The Completeness Critic

Every output from a multi-step workflow has gaps. Finders miss things. Perspectives are incomplete. The completeness critic is a final pass that asks not "what did we find?" but "what might we have missed?"

async function completenessCritic(
  findings: unknown[],
  context: string,
  domain: string
): Promise<string> {
  const CRITIC_SCHEMA = {
    type: 'object',
    required: ['gaps', 'overlookedAreas', 'recommendAdditionalPasses'],
    properties: {
      gaps: {
        type: 'array',
        items: { type: 'string' },
        description: 'Specific findings that appear to be missing from the list'
      },
      overlookedAreas: {
        type: 'array',
        items: { type: 'string' },
        description: 'Areas of the codebase or problem space not covered by any finding'
      },
      recommendAdditionalPasses: { type: 'boolean' }
    },
    additionalProperties: false
  }

  const critique = await agent(
    `You are reviewing the completeness of a ${domain} analysis.\n\n` +
    `Context:\n${context}\n\n` +
    `Findings produced (${findings.length} total):\n${JSON.stringify(findings, null, 2)}\n\n` +
    `What is missing? What areas were not covered? What classes of issues are absent that ` +
    `you would expect to find in a thorough ${domain} analysis of this codebase? ` +
    `Be specific — name files, patterns, or categories that should have been examined.`,
    {schema: CRITIC_SCHEMA, label: 'completeness-critic', phase: 'Critique'}
  )

  if (!critique) return 'Completeness critique skipped'

  if (critique.gaps.length > 0) {
    log(`Completeness critic: ${critique.gaps.length} potential gaps identified`)
    critique.gaps.forEach(g => log(`  - ${g}`))
  }

  if (critique.recommendAdditionalPasses) {
    log(`Completeness critic recommends additional finder passes`)
  }

  return JSON.stringify(critique)
}

The completeness critic is the last stage of every well-designed workflow that claims coverage. Its output does not necessarily trigger additional work — it documents the known unknowns. An audit that says "these 47 findings were confirmed and the completeness critic identified 3 areas not covered by any finder" is more trustworthy than one that claims total coverage.

What the critic is not

The completeness critic is not a re-verifier. It does not re-examine existing findings for correctness. It looks at the shape of the finding set — its distribution across files, its coverage of known vulnerability classes, its absence of expected categories — and identifies structural gaps.

13.12 The "No Silent Caps" Principle

Workflows operate in bounded environments. Concurrency caps limit parallel work. Token budgets limit total compute. The barrier in a parallel() call can quietly drop results when an agent returns null. Pagination logic can silently cap lists at 100 items. Without explicit logging at every cap point, a workflow can produce a partial result that looks complete.

Log every cap. Every drop. Every truncation.

// Wrong: silently caps at 50
const topFindings = allFindings.slice(0, 50)

// Right: log what was dropped
const CAP = 50
if (allFindings.length > CAP) {
  log(`Capping findings at ${CAP} — dropped ${allFindings.length - CAP} lower-severity items`)
}
const topFindings = allFindings.slice(0, CAP)
// Wrong: silently ignores null returns from parallel
const confirmed = results.flat().filter(Boolean)

// Right: log the drop rate
const all = results.flat()
const dropped = all.filter(v => !v).length
if (dropped > 0) {
  log(`${dropped}/${all.length} agent calls returned null (skipped or failed)`)
}
const confirmed = all.filter(Boolean)
// Wrong: silent budget stop
while (budget.remaining() > 50_000) { ... }

// Right: log when budget terminates the loop
if (budget.remaining() <= 50_000) {
  log(`Budget limit reached: ${Math.round(budget.remaining()/1000)}k remaining, ` +
      `stopping with ${results.length} results. ` +
      `${estimatedRemaining} items may have been missed.`)
}

The principle extends to the schema validation retry loop. When the harness retries a StructuredOutput call due to validation failure, that retry costs tokens and time. If the harness logs retries, surface them:

// Add retry logging in schema-heavy workflows
log(`Agent "${label}" needed ${retryCount} schema validation attempts`)

Why this matters in practice

Silent caps produce false confidence. A security audit that silently capped at 50 findings and dropped 12 additional ones will be presented to stakeholders as "50 findings identified." The completeness critic (§13.11) cannot flag gaps it does not know exist. The "no silent caps" principle is what makes the completeness critic's output trustworthy — without it, the critic may confidently miss exactly the items that were silently dropped.

13.13 Lab: Security Audit Using All Quality Patterns Combined

This lab assembles every pattern from this chapter into a single working security audit workflow. It is the canonical composition: multi-modal sweep, adversarial verify, completeness critic, budget loop, and comprehensive logging.

// security-audit.js — full workflow

const SEVERITY_ORDER = {critical: 4, high: 3, medium: 2, low: 1}

const DIMENSIONS = [
  {key: 'injection',      prompt: 'Find all injection vulnerabilities: SQL, command injection, LDAP, XPath, template injection. Examine every location where user input is concatenated into a query or command.'},
  {key: 'auth',           prompt: 'Find all authentication and authorization flaws: missing auth checks, insecure direct object references, JWT misuse, session fixation.'},
  {key: 'crypto',         prompt: 'Find all cryptographic weaknesses: weak hash functions (MD5/SHA1), hardcoded secrets, insecure RNG, broken TLS configuration.'},
  {key: 'deserialization', prompt: 'Find all unsafe deserialization: pickle.loads on untrusted data, YAML.load without SafeLoader, XML entity expansion, JSON parse of large untrusted payloads.'},
  {key: 'ssrf',           prompt: 'Find all SSRF vectors: outbound HTTP with user-controlled URLs, open redirect endpoints, metadata endpoint access.'},
  {key: 'file-ops',       prompt: 'Find all file operation vulnerabilities: path traversal, directory listing, symlink following, unsafe temp files, world-writable paths.'},
  {key: 'race-conditions', prompt: 'Find all TOCTOU and race conditions: check-then-act on files or database state, non-atomic operations on shared resources.'},
  {key: 'secrets',        prompt: 'Find all hardcoded credentials, API keys, tokens, and passwords in source code, config files, and test fixtures.'}
]

const FINDING_SCHEMA = {
  type: 'object',
  required: ['id', 'title', 'file', 'line', 'severity', 'description', 'cwe'],
  properties: {
    id:          { type: 'string' },
    title:       { type: 'string' },
    file:        { type: 'string' },
    line:        { type: 'integer' },
    severity:    { type: 'string', enum: ['low', 'medium', 'high', 'critical'] },
    description: { type: 'string', minLength: 50 },
    cwe:         { type: 'string', pattern: '^CWE-[0-9]+$' }
  },
  additionalProperties: false
}

const FINDINGS_SCHEMA = {
  type: 'object',
  required: ['findings'],
  properties: {findings: {type: 'array', items: FINDING_SCHEMA}}
}

const VERDICT_SCHEMA = {
  type: 'object',
  required: ['isReal', 'confidence', 'reason'],
  properties: {
    isReal:     { type: 'boolean' },
    confidence: { type: 'number', minimum: 0, maximum: 1 },
    reason:     { type: 'string', minLength: 20 }
  },
  additionalProperties: false
}

const CRITIC_SCHEMA = {
  type: 'object',
  required: ['gaps', 'overlookedAreas', 'recommendAdditionalPasses'],
  properties: {
    gaps:                       { type: 'array', items: { type: 'string' } },
    overlookedAreas:            { type: 'array', items: { type: 'string' } },
    recommendAdditionalPasses:  { type: 'boolean' }
  },
  additionalProperties: false
}

const fKey = (f) => `${f.file}:${f.line}:${f.title}`

// ── Phase 1: Multi-modal sweep with inline adversarial verify ──────────────

log('Phase 1: Multi-modal sweep')
const sweepResults = await pipeline(
  DIMENSIONS,
  dim => agent(
    `${dim.prompt}\n\nAssign a unique id to each finding (format: ${dim.key}-NNN).`,
    {label: `review:${dim.key}`, phase: 'Review', schema: FINDINGS_SCHEMA}
  ),
  review => {
    if (!review || !review.findings.length) return []
    log(`  ${review.findings.length} raw findings from dimension — verifying`)
    return parallel(review.findings.map(f => () =>
      agent(
        `Adversarially verify. Default to isReal=false if uncertain.\n\nFinding:\n${JSON.stringify(f, null, 2)}`,
        {label: `verify:${f.id}`, phase: 'Verify', schema: VERDICT_SCHEMA}
      ).then(v => {
        if (!v) { log(`  [skip] ${f.id}`); return null }
        if (!v.isReal) { log(`  [refuted] ${f.id}: ${v.reason.slice(0, 80)}`); return null }
        return {...f, confidence: v.confidence}
      })
    ))
  }
)

const seen = new Set<string>()
const phase1: typeof FINDING_SCHEMA[] = []
sweepResults.flat().filter(Boolean).forEach(f => {
  const k = fKey(f)
  if (seen.has(k)) { log(`  [dedup] ${f.id}`); return }
  seen.add(k)
  phase1.push(f)
})
log(`Phase 1 complete: ${phase1.length} unique confirmed findings`)

// ── Phase 2: Loop-until-dry for anything the sweep missed ─────────────────

log('Phase 2: Loop-until-dry follow-up')
let dry = 0
const phase2: typeof FINDING_SCHEMA[] = []

while (dry < 2 && budget.total && budget.remaining() > 100_000) {
  const knownKeys = [...seen].slice(0, 60)
  const round = await parallel(DIMENSIONS.map(d => () =>
    agent(
      `${d.prompt}\n\nDo NOT re-report findings already in this list:\n${JSON.stringify(knownKeys)}`,
      {label: `find2:${d.key}`, phase: 'Find2', schema: FINDINGS_SCHEMA}
    )
  ))

  const fresh = round.filter(Boolean).flatMap(r => r!.findings).filter(f => !seen.has(fKey(f)))

  if (!fresh.length) {
    dry++
    log(`  Dry round ${dry}/2`)
    continue
  }

  dry = 0
  log(`  ${fresh.length} additional candidates found`)

  const verified = await parallel(fresh.map(f => () =>
    agent(
      `Adversarially verify. Default to isReal=false if uncertain.\n\nFinding:\n${JSON.stringify(f, null, 2)}`,
      {label: `verify2:${f.id}`, phase: 'Verify2', schema: VERDICT_SCHEMA}
    ).then(v => (v?.isReal ? {...f, confidence: v.confidence} : null))
  ))

  const confirmed = verified.filter(Boolean)
  confirmed.forEach(f => { seen.add(fKey(f)); phase2.push(f) })
  log(`  ${confirmed.length}/${fresh.length} additional findings verified`)
}

if (budget.remaining() <= 100_000) {
  log(`Budget threshold hit: ${Math.round(budget.remaining()/1000)}k remaining — skipping further search`)
}

// ── Phase 3: Completeness critic ──────────────────────────────────────────

const allFindings = [...phase1, ...phase2]
log(`Phase 3: Completeness critic on ${allFindings.length} findings`)

const critique = await agent(
  `You are reviewing the completeness of a security audit.\n\n` +
  `Findings (${allFindings.length} total):\n${JSON.stringify(allFindings.map(f => ({id: f.id, title: f.title, cwe: f.cwe, severity: f.severity})), null, 2)}\n\n` +
  `What security areas were not covered? What classes of vulnerability are suspiciously absent? ` +
  `Be specific — name file patterns, vulnerability types, or CWE categories.`,
  {schema: CRITIC_SCHEMA, label: 'completeness-critic', phase: 'Critique'}
)

if (critique?.gaps.length) {
  log(`Completeness critic: ${critique.gaps.length} gaps`)
  critique.gaps.forEach(g => log(`  - ${g}`))
}

// ── Phase 4: Cap, log, and sort ───────────────────────────────────────────

const CAP = 200
if (allFindings.length > CAP) {
  log(`Capping at ${CAP} — dropping ${allFindings.length - CAP} lower-severity findings`)
}

const final = allFindings
  .sort((a, b) => (SEVERITY_ORDER[b.severity] ?? 0) - (SEVERITY_ORDER[a.severity] ?? 0))
  .slice(0, CAP)

const summary = {
  total:    final.length,
  critical: final.filter(f => f.severity === 'critical').length,
  high:     final.filter(f => f.severity === 'high').length,
  medium:   final.filter(f => f.severity === 'medium').length,
  low:      final.filter(f => f.severity === 'low').length,
  gaps:     critique?.gaps ?? [],
  overlookedAreas: critique?.overlookedAreas ?? [],
  phase1Count: phase1.length,
  phase2Count: phase2.length,
  tokensUsed: budget.total ? budget.total - budget.remaining() : 'unknown'
}

log(`Audit complete: ${summary.critical} critical, ${summary.high} high, ${summary.medium} medium, ${summary.low} low`)

return {findings: final, summary}

What each pattern contributes

PatternPhaseContribution
Multi-modal sweep1Breadth guarantee — every vulnerability class explicitly examined
Pipeline (no barrier)1Latency efficiency — verify starts as each dimension finishes
Adversarial verify1 + 2False positive suppression — default-to-refuted posture
Loop-until-dry2Depth guarantee — finders run until the space is exhausted
Budget loop2Cost control — hard stop before runaway spend
Completeness critic3Known-unknowns documentation — structural gap analysis
No-silent-caps4Transparency — every drop, every cap, every termination logged
Structured outputAllType safety — every agent call returns validated objects or null

The lab is not a toy. This structure has been used in production audits of codebases with 100k+ lines. The patterns compose naturally: removing any single one degrades the output in a specific, predictable way. Remove adversarial verify and false positives reach 30–40% of findings. Remove completeness critic and the audit has no mechanism to acknowledge what it missed. Remove the no-silent-caps logging and stakeholders receive partial results with no indication that items were dropped.

Summary

Advanced workflow patterns in the Claude harness are not algorithmic tricks — they are engineering responses to specific failure modes in multi-agent systems.

pipeline() is the default because most per-item transforms have no cross-item dependency. parallel() barriers are for deduplication, cross-item synthesis, and early-exit logic. A barrier justified only by "cleaner code" is a latency tax.

Resume (resumeFromRunId) enables cost-effective iteration on long workflows. The contract: prompts must be deterministic — Date.now(), Math.random(), and new Date() are prohibited because they destroy cache identity.

Nested workflows give sub-step composition but enforce a one-level limit. The concurrency cap, abort signal, and token budget are all shared between parent and child.

Structured output (schema) converts free-form model text into validated typed objects. Schema design discipline — flat objects, required only what is needed, additionalProperties: false, enum for categoricals — determines reliability.

The quality patterns (adversarial verify, perspective-diverse verify, judge panel) address the self-approval problem. Independent skeptics with a default-to-refuted posture produce meaningfully different results from cooperative reviewers. Perspective diversity catches what uniform adversarial review misses.

Loop patterns (loop-until-dry, loop-until-budget) handle unbounded problem spaces. Production workflows combine both: dry-stop for quality, budget-stop for cost control.

The completeness critic and no-silent-caps principle are the difference between a workflow that produces results and a workflow that honestly accounts for what it found and what it may have missed.
