Chapter 3: Tool System Architecture

"A tool is not a function. It is a contract between the harness and the model — a declaration of capability, with explicit I/O semantics baked into the schema."

3.1 Tool Registration: JSON Schema to TypeScript Interfaces

Every tool Claude Code exposes to the model starts as a JSON Schema definition. That schema is the contract. It tells the model what parameters are required, what types they must be, and what constraints apply. The TypeScript interfaces in sdk-tools.d.ts are generated from those schemas, not written by hand — the file header says so explicitly:

/* This file was automatically generated by json-schema-to-typescript.
 * DO NOT MODIFY IT BY HAND. Instead, modify the source JSONSchema file,
 * and run json-schema-to-typescript to regenerate this file.
 */

This distinction matters architecturally. The JSON Schema is the runtime artifact. TypeScript is the development-time artifact. When the harness sends a tool schema to the Claude API, it sends the JSON Schema, not TypeScript. When you or I read sdk-tools.d.ts, we are reading the TypeScript projection of that JSON Schema — a more readable form of the same information.

The implication: if you are building a harness, your source of truth for tool definitions is JSON Schema, and TypeScript is a build artifact. Never write tool types by hand in TypeScript and expect them to drive the JSON Schema. The arrow goes the other way.

How the Schema Reaches Claude

The flow from JSON Schema to a model-callable tool:

flowchart LR
    A[JSON Schema\nsource files] -->|json-schema-to-typescript| B[sdk-tools.d.ts\nTypeScript types]
    A -->|harness reads at startup| C[Tool Registry\nin memory]
    C -->|system prompt assembly| D[Tool descriptions\nin system prompt]
    C -->|API call construction| E[tools[] array\nin Messages request]
    E -->|model calls tool| F[tool_use block\nwith input JSON]
    F -->|harness validates| G{InputValidationError?}
    G -->|valid| H[Tool executor]
    G -->|invalid| I[Error returned\nto model]

The harness validates every tool_use input against the JSON Schema before execution. If validation fails — missing required field, wrong type, value out of range — the model receives an InputValidationError in the tool_result rather than an execution attempt. This is the safety net that makes deferred tools safe: calling a deferred tool before its schema is loaded produces an InputValidationError with a clear message, not undefined behavior.

3.2 Input/Output Type Contracts

The convention is strict and enforced throughout the codebase: every tool has a corresponding *Input interface and a corresponding *Output type. No tool breaks this pattern.

The asymmetry between inputs and outputs is intentional:

  • Inputs are always interface — a single, well-known shape the model must produce.
  • Outputs are often type with union variants — the harness can return different shapes depending on what happened.

This reflects the different roles. The model is the caller; it must produce a predictable input. The harness is the callee; it returns richer, context-dependent results.

A Simple Pair: Bash

// Input: the model sends this
export interface BashInput {
  command: string;           // required
  timeout?: number;          // max 600000ms
  description?: string;      // human-readable label for permission UI
  run_in_background?: boolean;
  dangerouslyDisableSandbox?: boolean;
}

// Output: the harness returns this
export interface BashOutput {
  stdout: string;
  stderr: string;
  interrupted: boolean;
  backgroundTaskId?: string;    // set when run_in_background: true
  backgroundedByUser?: boolean; // user pressed Ctrl+B
  timedOutAfterMs?: number;     // set when command hit timeout and was auto-backgrounded
  dangerouslyDisableSandbox?: boolean;
  gitOperation?: {              // structured classification — not surfaced to model
    commit?: { sha: string; kind: "committed" | "amended" | "cherry-picked" };
    push?: { branch: string };
    pr?: { number: number; url?: string; action: string };
  };
  rawOutputPath?: string;       // large MCP tool outputs
  persistedOutputPath?: string; // output too large for inline
  persistedOutputSize?: number;
  staleReadFileStateHint?: string;
  ghRateLimitHint?: string;
}

Notice the gitOperation field: it is marked @internal in the source and is "not surfaced to the model." The harness includes it in the output type for client-side rendering — a TUI can show a git activity indicator without re-parsing stdout. The model never sees this field. This is a clean example of output fields serving multiple consumers: the model gets stdout/stderr/interrupted; the UI gets gitOperation.

A Complex Pair: FileEdit

The Edit tool output is richer than its input because the harness knows things the model does not — what the original file looked like, whether the user modified the diff before accepting, whether git saw the change:

export interface FileEditInput {
  file_path: string;  // absolute path required
  old_string: string; // exact text to replace — must be unique in file
  new_string: string; // replacement text
  replace_all?: boolean;
}

export interface FileEditOutput {
  filePath: string;
  oldString: string;
  newString: string;
  originalFile: string | null;   // full file contents before edit
  structuredPatch: {
    oldStart: number;
    oldLines: number;
    newStart: number;
    newLines: number;
    lines: string[];
  }[];
  userModified: boolean;         // user edited the proposed change
  replaceAll: boolean;
  gitDiff?: {
    filename: string;
    status: "modified" | "added";
    additions: number;
    deletions: number;
    changes: number;
    patch: string;
    repository?: string | null;  // GitHub owner/repo when available
  };
}

The structuredPatch field is the harness's unified diff in structured form — hunks with line numbers and content. The TUI uses this to render a diff view. The model can also read it if it needs to verify what was actually changed.

Empty Input Interfaces

Some tools take no input:

export interface EnterPlanModeInput {}
export interface TaskListInput {}
export interface CronListInput {}

These are not zero-parameter function calls encoded as empty objects by convention. They exist as explicit interface declarations because the JSON Schema generation pipeline requires a named schema entry for every tool, even if that schema has no properties. An empty interface is a valid JSON Schema with type: "object" and no required fields. When you implement your own harness, use the same pattern — never omit the input schema, even for parameter-less tools.

3.3 Core Tools: Always Loaded

Six tools are loaded unconditionally at startup. Their JSON Schema descriptions are baked into the system prompt before the first user turn. Any reduction in this set would break Claude Code's basic utility; any addition would increase baseline system prompt token cost.

graph TD
    subgraph "Core Tools — Always in System Prompt"
        Bash["Bash\nShell execution"]
        Read["Read (FileRead)\nText / image / PDF / notebook"]
        Edit["Edit (FileEdit)\nExact-match string replacement"]
        Write["FileWrite\nCreate or overwrite files"]
        Agent["Agent\nSpawn subagents"]
        AskUser["AskUserQuestion\nStructured user input"]
    end

Why These Six?

The selection reflects a minimal spanning set for agentic work:

  • Bash — the escape hatch. Anything not covered by a specific tool can be done via shell.
  • Read — you cannot act on what you cannot see. File reading is prerequisite to every other action.
  • Edit — targeted modification. The alternative to Edit is Write-the-whole-file, which is expensive in tokens and error-prone.
  • Write — file creation and full-file overwrites. Handles what Edit cannot.
  • Agent — parallelism and delegation. Without Agent, Claude Code is single-threaded. With it, work fans out.
  • AskUserQuestion — structured user interaction. The model needs a way to pause and collect decisions when it cannot proceed unilaterally.

Notably absent from core tools: WebFetch, WebSearch, Workflow, all scheduling tools. These are powerful but not universal. A task that never touches the web should not pay for web tool descriptions in its system prompt.

The AskUserQuestion Contract in Detail

AskUserQuestion has by far the most verbose input schema in the file. The questions parameter is typed as a discriminated tuple union of 1–4 question objects, each with a options array of 2–4 option objects — and each tuple variant is written out explicitly because JSON Schema tuple semantics do not support a compact "1 to N items" form when the items have specific structure. The generated TypeScript faithfully mirrors this verbosity.

The practical interface, collapsed to its semantics:

// Simplified mental model of AskUserQuestionInput
interface AskUserQuestionInput {
  questions: Array<{         // 1-4 questions
    question: string;        // full question text, ends with "?"
    header: string;          // max 12 chars — shown as chip/tag
    options: Array<{         // 2-4 options
      label: string;         // 1-5 words
      description: string;   // trade-off explanation
      preview?: string;      // rendered when option is focused
    }>;
    multiSelect: boolean;
  }>;
}

// Output
interface AskUserQuestionOutput {
  questions: /* same structure */[];
  answers: { [questionText: string]: string }; // comma-separated for multiSelect
  response?: string;  // freeform text if user typed instead of selecting
  annotations?: {     // per-question notes
    [questionText: string]: {
      preview?: string;
      notes?: string;
    };
  };
  afkTimeoutMs?: number; // set when dialog auto-resolved (user was away)
}

The afkTimeoutMs field reveals an important behavioral detail: in headless or background agent contexts, an unanswered question auto-resolves after a configurable idle timeout. The model can detect this and decide whether to proceed with the auto-selected answer or retry.

3.4 Deferred Tools: ToolSearch on Demand

The deferred tool system is the most consequential context-budget optimization in Claude Code's architecture. Every tool description in the system prompt consumes tokens on every API call, regardless of whether that turn uses the tool. For a session that does filesystem work and nothing else, carrying scheduling tool descriptions is pure waste.

How Deferral Works

When ENABLE_TOOL_SEARCH="auto" is set (the default), tools outside the core six are not loaded into the system prompt at startup. Instead, the system prompt contains a notice:

"The following deferred tools are now available via ToolSearch. Their schemas are NOT loaded — calling them directly will fail with InputValidationError."

The model learns that deferred tools exist by name, but does not receive their schemas. When it decides it needs one — based on the task and the names in the deferred registry — it calls ToolSearch with a natural language query. The harness returns the full schema for matching tools. They are now active for the rest of the session.

sequenceDiagram
    participant Model
    participant Harness
    participant ToolRegistry

    Note over Model,ToolRegistry: Session start
    Harness->>Model: System prompt with 6 core schemas + deferred tool names

    Note over Model,ToolRegistry: Model realizes it needs scheduling
    Model->>Harness: ToolSearch("schedule recurring task")
    Harness->>ToolRegistry: Query for matching deferred tools
    ToolRegistry-->>Harness: CronCreate, CronDelete, CronList, ScheduleWakeup schemas
    Harness-->>Model: Full schemas for 4 scheduling tools
    Note over Model: Schemas now loaded — direct calls valid

    Model->>Harness: CronCreate({ cron: "*/5 * * * *", prompt: "check queue" })
    Harness->>ToolRegistry: Execute CronCreate
    ToolRegistry-->>Harness: CronCreateOutput { id, humanSchedule, recurring }
    Harness-->>Model: tool_result

What Happens When You Call a Deferred Tool Directly

The failure mode is explicit and instructive:

InputValidationError: Tool "CronCreate" schema is not loaded.
Call ToolSearch to load it before use.

This is intentional. The harness does not silently load the schema on demand when the tool is called directly — that would defeat the purpose. The model must explicitly request schemas through ToolSearch. This forces a deliberate act of tool discovery, which has the side effect of making the model's intent legible to observers watching the tool call log.

3.5 MCP Tools: Dynamic Registration

Model Context Protocol (MCP) is an open standard for connecting LLMs to external data sources and tools. Claude Code is a first-class MCP client: it connects to MCP servers at startup, discovers their tools, and registers those tools in the same harness registry that manages built-in tools. From the model's perspective, an MCP tool and a built-in tool are indistinguishable.

The Registration Flow

sequenceDiagram
    participant Claude as Claude Code (harness)
    participant Server as MCP Server

    Claude->>Server: Initialize (stdio or HTTP/SSE)
    Server-->>Claude: capabilities, serverInfo
    Claude->>Server: tools/list
    Server-->>Claude: Array<{ name, description, inputSchema }>
    Note over Claude: Register each tool as McpInput wrapper
    Note over Claude: Apply 2KB description cap
    Note over Claude: Add to system prompt if below budget

Every MCP tool is exposed to the model through a single wrapper input type:

export interface McpInput {
  [k: string]: unknown;
}

The McpInput interface is structurally open — any keys, any values. This is correct. MCP tools have arbitrary schemas defined by their server; the harness cannot predict them at compile time. Validation happens at the server boundary, not in the harness type system.

The output is similarly permissive:

export type McpOutput =
  | string
  | { type: string; [k: string]: unknown }[]
  | { [k: string]: unknown };

An MCP tool can return a plain string, a structured object, or an array of typed content blocks. The harness passes whatever the server returns directly to the model.

RefreshMcpTools: Hot-Reload

One built-in tool — RefreshMcpTools — is specifically for managing the MCP tool list at runtime:

export interface RefreshMcpToolsInput {
  server?: string; // omit to refresh all servers
}

export type RefreshMcpToolsOutput = {
  server: string;
  status: "refreshed" | "error" | "not_connected";
  toolCount?: number;
  added?: string[];   // tools the refresh added
  removed?: string[]; // tools the refresh removed
  error?: string;
}[];

If an MCP server adds or removes tools while Claude Code is running — during a deployment, for example — the model can call RefreshMcpTools to sync. The added and removed arrays tell it exactly what changed.

The 2KB Description Cap

MCP servers generated from OpenAPI specifications tend to produce tool descriptions containing the full API documentation: parameter descriptions, response examples, error codes, authentication notes. An OpenAPI-generated tool description can easily run 5KB–20KB per tool. Loading even ten such tools into the system prompt is prohibitive.

Claude Code caps MCP tool descriptions at 2KB. Descriptions that exceed this limit are truncated. The cap is applied per-tool, not globally, so a server with 20 tools can contribute at most 40KB of description text to the system prompt — still significant, but bounded.

The design implication for MCP server authors: write tool descriptions for the model, not for documentation. The model needs to know what the tool does and what its parameters mean. It does not need examples, caveats, or API version history. 2KB is generous for a clear tool description.

MCP_CONNECTION_NONBLOCKING

By default, Claude Code waits for all configured MCP servers to connect before proceeding with the session. If a server is slow to start or unavailable, this blocks startup.

Setting MCP_CONNECTION_NONBLOCKING=true skips this wait in non-interactive (-p print) mode. The session starts immediately; MCP tools become available as servers connect. Tools from a not-yet-connected server are simply absent until the server connects and RefreshMcpTools is called (or the harness handles reconnection automatically).

This is the right default for production pipelines where MCP reliability cannot be guaranteed. For interactive sessions where a user is watching, the blocking behavior is preferable — you do not want tool calls to fail mid-session because a server connected late.

Filesystem Tools: The Five Shapes of File I/O

The five filesystem tools are not interchangeable. Each has a distinct semantic contract:

Read (FileReadInput) handles polymorphic reading. The same interface reads text files, binary images, PDFs, and Jupyter notebooks. The output type is a discriminated union on the type field:

export type FileReadOutput =
  | { type: "text";       file: { filePath, content, numLines, startLine, totalLines, truncatedByTokenCap? } }
  | { type: "image";      file: { base64, type: MimeType, originalSize, dimensions? } }
  | { type: "notebook";   file: { filePath, cells } }
  | { type: "pdf";        file: { filePath, base64, originalSize } }
  | { type: "parts";      file: { filePath, originalSize, count, outputDir } }
  | { type: "file_unchanged"; file: { filePath }; source?: "seeded" }

The file_unchanged variant is the deduplication signal. When the harness detects that the content of a file has not changed since the last Read — or since it was seeded into the system prompt at startup — it returns this lean response instead of the full content. The source: "seeded" annotation distinguishes a dedup match against a prior Read tool call from a match against startup-seeded content (CLAUDE.md files, memory).

Edit (FileEditInput) does exact-match replacement. The old_string must exist in the file exactly once (unless replace_all: true). Uniqueness is enforced — if old_string matches multiple locations, the call fails with an error directing the model to include more surrounding context. This design prevents silent multi-site edits that the model did not intend.

Write (FileWriteInput) is unconditional. It creates the file if it does not exist, overwrites it if it does. The output tells you which case occurred via type: "create" | "update". The originalFile field contains the pre-write content when updating, which enables write idempotency checks without a separate Read.

Glob (GlobInput) does pattern-based file discovery. Output includes totalMatches (how many files matched before truncation) and countIsComplete (whether that count is exact or a lower bound). The truncated flag signals when results were cut at 100 files — a model doing a broad sweep needs to know whether it saw everything.

Grep (GrepInput) is ripgrep under the hood. The three output modes — content, files_with_matches, count — serve different patterns: reading matched lines with context, finding which files need attention, and quickly quantifying scope without reading content.

3.7 Token-Aware Design

Token cost is a first-class design concern in the tool system. Every architectural choice that seems odd on first read — deferred loading, description caps, empty input schemas, the file_unchanged response — exists to manage the context budget.

Tool Descriptions as Context Budget

A tool description is not free documentation. It appears in the system prompt, which is included in every API call. For a model processing 100 turns in a session, a 500-token tool description costs 50,000 tokens over the session lifetime. With prompt caching, the stable system prompt tokens are cached after the first call, reducing this to a one-time cost — but that cache has a 5-minute TTL, and long-running sessions will encounter cache misses.

The concrete tradeoff for a custom tool:

Short description (50 tokens):
  - System prompt cost: minimal
  - Risk: model misuses tool due to ambiguity

Detailed description (500 tokens):
  - System prompt cost: 10x higher
  - Benefit: fewer misuse errors, better parameter selection

The right answer depends on the tool. A tool used every turn (Bash, Read) can justify detailed descriptions because the description is cache-warmed and the model benefits from precision. A tool used once per session (EnterPlanMode) should be deferred so it only costs tokens in sessions that actually use it.

The Schema Size Cap: 2KB for MCP

The 2KB cap on MCP tool descriptions is enforced before the description enters the system prompt. If a tool description exceeds 2KB, it is truncated. The model receives a shortened description and must infer the rest from parameter names and types.

For custom MCP servers you control, the right approach is to write descriptions at or under 2KB from the start. The cap is not a guardrail for good descriptions — it is a safeguard against descriptions that are actually OpenAPI reference documentation copy-pasted into a tool schema.

For third-party MCP servers you do not control, the cap means you should test what the model actually receives and verify it is sufficient for correct tool use.

MCP_CONNECTION_NONBLOCKING and Startup Cost

Blocking MCP server connections at startup adds latency before the first response. For interactive use, users feel this as a pause. The MCP_CONNECTION_NONBLOCKING=true flag moves this cost out of the startup critical path:

Without flag:
  startup → connect all MCP servers → first response
  [user waits for slowest server]

With flag (non-interactive mode):
  startup → first response → [MCP connects in background]
  [model discovers tools as servers connect]

For automated pipelines where latency matters and MCP server availability is guaranteed, omitting MCP_CONNECTION_NONBLOCKING is correct — you want tool availability confirmed before processing the task. For long-running background agents where MCP connectivity is opportunistic, the non-blocking mode prevents a slow MCP server from stalling the entire agent.

The file_unchanged Optimization in Detail

The Read tool's deduplication mechanism deserves specific attention because it affects how you design agents that make multiple passes over a codebase.

When the model calls Read on a file it has already read in the same session (and the file has not been modified), the harness returns:

{ type: "file_unchanged", file: { filePath: "/path/to/file.ts" } }

This saves the entire file content from being re-serialized, transmitted to the API, and counted against the context window. For a 500-line file, this is the difference between ~2,000 tokens and 10 tokens.

The source: "seeded" annotation appears when the match is against content seeded at startup — CLAUDE.md files, memory files injected into the system prompt — rather than a prior Read tool call:

{ type: "file_unchanged", file: { filePath: "/project/CLAUDE.md" }, source: "seeded" }

This tells the model the file has not changed since session start. A model that needs to re-read CLAUDE.md can safely skip the Read call and rely on its system prompt copy.

3.8 Lab: Design a Custom Tool with Proper I/O Schema and Permission Integration

This lab walks through the full lifecycle of adding a custom tool to a harness: defining the JSON Schema, deriving TypeScript interfaces, implementing the executor, and integrating with the permission layer.

The Tool: DatabaseQuery

Purpose: Execute read-only SQL queries against a configured database and return structured results.

Requirements:

  • Model provides a SQL SELECT statement and optional timeout
  • Harness validates it is a read-only query (no INSERT, UPDATE, DELETE, DROP, TRUNCATE)
  • Results return as structured rows, not raw text
  • Permission integration: queryable databases are configured via settings allow-list

Step 1: Define the JSON Schema

Start from the schema, not TypeScript. The schema is what the harness and the Claude API will use:

{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "name": "DatabaseQuery",
  "description": "Execute a read-only SQL SELECT query against a configured database. Returns structured rows. Only SELECT statements are permitted — any mutation attempt returns an error without execution.",
  "type": "object",
  "properties": {
    "database": {
      "type": "string",
      "description": "Named database from the allowed list in harness settings (e.g. 'analytics', 'users-readonly')"
    },
    "query": {
      "type": "string",
      "description": "A SQL SELECT statement. Must begin with SELECT. CTEs (WITH clauses) are permitted. EXPLAIN is permitted."
    },
    "timeout_ms": {
      "type": "number",
      "description": "Query timeout in milliseconds. Default 5000, max 30000.",
      "default": 5000,
      "maximum": 30000
    },
    "row_limit": {
      "type": "number",
      "description": "Maximum rows to return. Default 100, max 1000. Use lower values for large result sets.",
      "default": 100,
      "maximum": 1000
    }
  },
  "required": ["database", "query"],
  "additionalProperties": false
}

Design decisions encoded in the schema:

  • additionalProperties: false — the model cannot pass unknown parameters. This prevents prompt injection attempts that try to sneak extra parameters past validation.
  • database is a named string, not a connection string. The harness looks up actual connection details from its configuration. The model never sees credentials.
  • query has no length limit in the schema because SQL queries legitimately vary from one line to hundreds. Validation happens in the executor.
  • timeout_ms and row_limit have explicit maximum constraints that are enforced by the JSON Schema validator before the executor runs.

Step 2: Derive TypeScript Interfaces

From the schema above, the generated TypeScript:

export interface DatabaseQueryInput {
  database: string;
  query: string;
  timeout_ms?: number;  // default 5000, max 30000
  row_limit?: number;   // default 100, max 1000
}

export interface DatabaseQueryOutput {
  database: string;
  query: string;
  rows: Record<string, unknown>[];
  rowCount: number;
  columnNames: string[];
  truncated: boolean;         // true if row_limit was hit
  totalRows?: number;         // only set when truncated=true and db reports count
  durationMs: number;
  error?: string;             // set on query failure — rows will be empty
}

The output type reflects two distinct success states: a normal result and a truncated result. The truncated flag is critical — a model deciding whether it needs to paginate or refine its query needs to know whether it saw all rows or just the first batch.

Step 3: Implement the Executor

import { Pool } from "pg";
import { DatabaseQueryInput, DatabaseQueryOutput } from "./types";

const ALLOWED_STATEMENT_PREFIXES = new Set(["select", "with", "explain"]);

async function executeDatabaseQuery(
  input: DatabaseQueryInput,
  config: HarnessConfig
): Promise<DatabaseQueryOutput> {
  const startMs = Date.now();
  const timeoutMs = Math.min(input.timeout_ms ?? 5000, 30000);
  const rowLimit = Math.min(input.row_limit ?? 100, 1000);

  // Permission check: is this database in the allow-list?
  const dbConfig = config.allowedDatabases[input.database];
  if (!dbConfig) {
    return {
      database: input.database,
      query: input.query,
      rows: [],
      rowCount: 0,
      columnNames: [],
      truncated: false,
      durationMs: Date.now() - startMs,
      error: `Database '${input.database}' is not in the allowed list. Allowed: ${Object.keys(config.allowedDatabases).join(", ")}`,
    };
  }

  // Query safety check: must start with an allowed keyword
  const normalized = input.query.trim().toLowerCase();
  const firstWord = normalized.split(/\s+/)[0];
  if (!ALLOWED_STATEMENT_PREFIXES.has(firstWord)) {
    return {
      database: input.database,
      query: input.query,
      rows: [],
      rowCount: 0,
      columnNames: [],
      truncated: false,
      durationMs: Date.now() - startMs,
      error: `Only SELECT, WITH, and EXPLAIN statements are permitted. Got: ${firstWord.toUpperCase()}`,
    };
  }

  const pool = getPool(dbConfig); // connection pool, managed separately
  const client = await pool.connect();

  try {
    // Enforce row_limit at the database level with LIMIT injection
    // rather than fetching all rows and truncating in memory
    const limitedQuery = wrapWithLimit(input.query, rowLimit + 1);

    const result = await Promise.race([
      client.query(limitedQuery),
      sleep(timeoutMs).then(() => { throw new Error(`Query timed out after ${timeoutMs}ms`); }),
    ]);

    const truncated = result.rows.length > rowLimit;
    const rows = truncated ? result.rows.slice(0, rowLimit) : result.rows;
    const columnNames = result.fields.map((f) => f.name);

    return {
      database: input.database,
      query: input.query,
      rows,
      rowCount: rows.length,
      columnNames,
      truncated,
      durationMs: Date.now() - startMs,
    };
  } catch (err) {
    return {
      database: input.database,
      query: input.query,
      rows: [],
      rowCount: 0,
      columnNames: [],
      truncated: false,
      durationMs: Date.now() - startMs,
      error: err instanceof Error ? err.message : String(err),
    };
  } finally {
    client.release();
  }
}

Key implementation decisions:

  • Never throw from an executor. Return an error in the output's error field instead. A thrown exception propagates up to the harness control loop as an unhandled error, which is a worse outcome than a structured error the model can reason about.
  • Double-enforce row limits. The JSON Schema caps row_limit at 1000. The executor also enforces it in wrapWithLimit. Defense in depth.
  • Database credentials stay in config. The executor receives a config struct, not raw connection details from the model.
  • Return structured errors with actionable messages. The error messages in this executor tell the model exactly what it can do to fix the problem: which databases are allowed, which statement prefixes are permitted.

Step 5: Register as a Deferred Tool

Since DatabaseQuery is not needed on every turn, register it as deferred:

// In your tool registry initialization
registry.registerDeferred({
  name: "DatabaseQuery",
  schema: databaseQuerySchema,      // the JSON Schema from Step 1
  executor: executeDatabaseQuery,   // from Step 3
  categories: ["database", "sql", "query", "data"],  // ToolSearch index terms
});

The categories array is what ToolSearch queries against. When the model calls ToolSearch("query database"), the harness matches on these terms and returns the full schema.

Verification Checklist

Before shipping a custom tool:

  • [ ] JSON Schema has additionalProperties: false
  • [ ] Required fields are explicitly listed in required[]
  • [ ] Numeric fields have maximum constraints where appropriate
  • [ ] Executor never throws — all errors return in output.error
  • [ ] Credentials are in harness config, never in tool input schema
  • [ ] Error messages name the allowed values (actionable, not opaque)
  • [ ] Description fits in 2KB (verify: echo -n "$(description)" | wc -c)
  • [ ] Tool is registered as deferred unless it is needed on every turn
  • [ ] Audit hook is in place if the tool accesses sensitive data
  • [ ] Integration test: call with valid input, call with invalid input, call with disallowed value — verify all three produce correct outputs

Summary

The tool system's architecture can be stated in four principles:

  1. JSON Schema is the contract. TypeScript is a build artifact. The schema drives validation, documentation, and the model's understanding of what it can call.
  1. Input/Output pairs are explicit. Every tool has a named *Input interface and a named *Output type. The asymmetry — structured inputs, richer outputs — reflects that the model is the caller and the harness is the richer system.
  1. Tokens are a resource. Core tools earn their always-loaded status. Everything else defers. MCP descriptions are capped at 2KB. Files are deduplicated. Every design choice in the tool system traces back to managing the context budget.
  1. Errors are structured, not thrown. A tool that returns { error: "..." } keeps the control loop running. A tool that throws breaks out of it. The model can reason about structured errors. It cannot reason about unhandled exceptions.

As discussed in Chapter 2, the settings cascade controls which tools are available, which are allowed, and which are blocked entirely. The tool system described here is what Chapter 2's permissions govern. In Chapter 4, we go deeper into the permission layer itself — specifically how the auto-mode classifier decides, in real time, whether to allow or deny a tool call without asking the user.
