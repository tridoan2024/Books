Chapter 17: Skills System — Custom Slash Commands

"A hook fires when something happens. A skill fires when you say so. That difference is the entire reason slash commands exist."

17.1 Skill Anatomy: The SKILL.md File

Everything about a skill lives in a single file: SKILL.md. The frontmatter is the contract between the skill and the harness. The body is the contract between the skill and the model. Neither half works without the other.

Here is the complete frontmatter schema:

---
name: deploy-check
description: Pre-deployment readiness check. Validates tests pass, no secrets
  exposed, dependencies audited, and build succeeds.
argument-hint: "[env: staging|prod]"
allowed-tools: Bash, Read, Grep, Glob
model: claude-sonnet-4-6
effort: high
paths:
  - "**/*.py"
  - "**/*.ts"
  - package.json
---

Each field does something specific at harness load time. None of them are cosmetic.

name

The kebab-case identifier that becomes the slash command. name: deploy-check creates /deploy-check. The name must be unique within the skill discovery path — if two skills have the same name, the one discovered first wins, silently. Name your skills specifically. sec-pr is better than review, which collides with any other review skill someone might add.

The name is also the lookup key when the user types /. The harness does a prefix match, so /dep will autocomplete to deploy-check if no other skill starts with dep. Short, distinctive prefixes matter.

description

The single line shown in the /skills menu and used by the harness to match user intent. The description has two jobs: present the skill to the user and teach the harness when to invoke it.

The description for a security PR review skill that sees real production use looks like this:

description: Security PR review for Azure DevOps pull requests. Use when user says
  "sec-pr", "PR security review", "scan PR", "review PR security", "PR scan",
  "security scan PR", "check sec-pr", "sec-pr status", "approve PR".

Notice the pattern: the first sentence states the purpose. The rest seeds invocation vocabulary. This matters because the harness uses the description to match ambiguous inputs — if the user types something that isn't a slash command but resembles one, the harness consults skill descriptions to decide whether to offer a suggestion. A description that captures the phrases users actually reach for produces fewer "I didn't know that was a skill" moments.

The description is truncated to 250 characters in the skill card UI. Put the most important content first. Long descriptions that front-load implementation details waste card space on information the user cannot act on.

argument-hint

Text shown in the UI immediately after the skill name, telling the user what arguments are valid. The /dt skill uses argument-hint: [optional: close|status]. This appears in the autocomplete as /dt [optional: close|status] — the user sees the full invocation syntax before they type anything.

The hint is purely cosmetic at the harness level. The harness does not parse or validate arguments against it. Arguments arrive in the skill body as $ARGUMENTS — a raw string that the skill is responsible for interpreting. The hint is documentation, not enforcement.

A skill that takes no arguments should omit argument-hint entirely, not set it to an empty string. An empty string renders as a trailing space in the UI.

allowed-tools

A comma-separated list restricting which tools the skill can invoke. When set, the skill executes inside a reduced tool surface: any tool call not in the list returns a tool-not-found error at execution time, not at call time. The model will still attempt the call if it has reasoned itself into needing it; the harness refuses.

The deploy-check skill uses allowed-tools: Bash, Read, Grep, Glob because deployment checks are read-and-run operations. It has no business editing files. The sec-pr skill adds Agent because it spawns parallel subagents for different PR scan phases.

Skills without allowed-tools inherit the full tool surface of the current permission profile. For skills that are narrowly scoped — audit, deploy, research — setting allowed-tools explicitly is a form of documentation that also prevents the model from drifting outside the skill's intended scope.

model

Override the model used for this skill's execution. The /dt trading skill specifies model: claude-opus-4-6 because trading decisions require the highest reasoning quality available and the cost is justified. The three monitoring agents it spawns use Sonnet explicitly within their own prompts to keep total token cost manageable.

Omitting model means the skill runs on whatever model the user has active at invocation time. For most skills this is the right behavior. For skills with a strong model dependency — either because they do complex multi-step reasoning or because they need a specific context window — set it explicitly.

effort

Maps to the API-level thinking budget: low, medium, or high. The harness translates this to a token budget for extended thinking. High-effort skills get more tokens for internal reasoning before producing their first output. Low-effort skills start responding immediately.

The practical guidance: skills that need to hold a complex mental model across many steps — a security scan that reads 30 files before concluding anything, a trading skill that synthesizes 8 data sources — benefit from effort: high. Skills that are mostly procedural — run these commands, format the output — get nothing from high effort and should use the default.

paths

A YAML list of glob patterns. The skill only appears in the /skills menu and responds to invocation when the current working directory contains files matching at least one of the patterns. A skill with paths: ["**/*.tf"] is invisible when you are working on a Python service and active when you are working on Terraform infrastructure.

paths:
  - "**/*.tf"
  - "**/*.tfvars"
  - ".terraform/**"

This is the correct way to build environment-specific skills. Without paths, every skill you have ever added appears in every project's skill list, regardless of relevance. A trading skill surfacing in a Python library project creates noise. paths solves this by making skills context-aware at the directory level.

Paths are evaluated against the harness's current working directory at invocation time. They are not evaluated against the skill directory itself.

17.2 Skill Directories

The harness discovers skills from three places, checked in this order:

1. Project skills:  ./.claude/skills/<name>/SKILL.md
2. Global skills:   ~/.claude/skills/<name>/SKILL.md
3. Settings paths:  each path in skillDirectories setting

This ordering matters when names collide. A project skill named sec-pr overrides a global skill with the same name. This is intentional: projects can specialize or replace global skills without modifying the global installation.

Project Skills

Stored in .claude/skills/ within the working directory. These are version-controlled alongside the code they serve. When someone clones the repository and opens Claude Code, they get the full skill set the project team built.

The 23 skills in the production workspace live at /Users/DOANTX26/Documents/2026/.claude/skills/:

api-conventions/    auto-router/     book-writer/
changelog/          checkpoint/      code-review/
dep-audit/          deploy-check/    dt/
fix-issue/          git-cleanup/     perf-profile/
pr-summary/         rbiz/            refactor/
research/           scaffold/        sec-full/
sec-pr/             sec-sr/          security-audit/
spy-check/          threat-model/

Each directory contains at minimum SKILL.md. Complex skills like sec-pr and sec-sr include additional files: agent sub-prompts, known false positive registries, prompt templates, and plan documents. The skill directory is a bundle, not just a file. The harness loads SKILL.md; the rest is available to the skill at runtime via the filesystem.

Global Skills

Stored at ~/.claude/skills/. These are personal skills that travel with the user rather than with a specific project. The global slot is appropriate for skills that have no dependency on project-specific files or configuration: a personal research workflow, a preferred code review checklist, a browser automation helper.

The three global skills on this system (dev-browser, learned, sec-pr) illustrate the pattern. dev-browser is a Playwright automation workflow that works regardless of which project is active. learned accumulates observed patterns as they are proposed by ProposeSkills. sec-pr in the global slot is the fallback for when the project-level version is not present.

Settings Paths

The skillDirectories array in settings.json adds arbitrary directories to the search path:

{
  "skillDirectories": [
    "/Users/user/.copilot/skills/sec-pr"
  ]
}

This is the extension point for organization-level skill libraries. A team can maintain a shared directory on a network mount or a cloned repository and add it to skillDirectories — every team member gets the same skill set without needing it in their home directory or in each project. The directory path in skillDirectories points to the parent of the skill directories, following the same <name>/SKILL.md convention.

Skills from skillDirectories have lower priority than project and global skills. Project overrides global overrides settings-path.

The Skills Menu

The /skills command lists all discovered skills, sorted alphabetically, with truncated descriptions. The list is assembled fresh on each invocation from the three discovery paths. Skills that fail to parse (malformed frontmatter, missing name field) are silently skipped. If a skill does not appear in the menu, check the frontmatter first — a YAML syntax error in the frontmatter block is the most common cause.

17.3 Invocation: How a Slash Command Becomes Skill Instructions

The flow from slash command to running skill is worth understanding precisely, because it explains why skill bodies can reference $ARGUMENTS, why model overrides take effect immediately, and why the skill appears to run with a different tool surface than the surrounding conversation.

The Invocation Sequence

sequenceDiagram
    participant U as User
    participant H as Harness
    participant SD as Skill Discoverer
    participant ST as Skill Tool
    participant API as Claude API

    U->>H: /sec-pr 9976
    H->>SD: Resolve "/sec-pr"
    SD-->>H: SKILL.md content + metadata
    H->>H: Apply model override (claude-opus-4-6)
    H->>H: Apply tool restrictions (allowed-tools)
    H->>H: Substitute $ARGUMENTS = "9976"
    H->>ST: Skill({skillName: "sec-pr", content: "...", arguments: "9976"})
    ST-->>H: Skill instructions injected into context
    H->>API: Assemble prompt with injected instructions
    API-->>H: Response (first tool call or text)
    H->>H: Execute tool (restricted to allowed-tools)

The user types /sec-pr 9976. The harness splits on the first space: sec-pr is the skill name, 9976 is the argument string. The skill discoverer looks up sec-pr in the three discovery paths and returns the parsed SKILL.md.

The harness then applies the frontmatter overrides before touching the API: model is switched to claude-opus-4-6, tool restrictions are installed, effort level is set. These take effect for the duration of the skill execution.

The Skill tool is called internally, injecting the SKILL.md body content as instructions into the conversation context. $ARGUMENTS is substituted with the raw argument string. The resulting context is sent to the API.

From the model's perspective, it receives a conversation that includes detailed instructions about what to do (the skill body) and a concrete input to operate on ($ARGUMENTS = "9976"). The model has no awareness that it is executing a "skill" in any special sense — it sees instructions and acts on them.

Argument Handling

Arguments are a raw string. The skill body is responsible for parsing them. The sec-pr skill handles this explicitly:

**Argument parsing:** `$ARGUMENTS` can be:
- Empty → Auto-Discovery Mode across ALL orgs (Phase 0A)
- A number (e.g., `9976`) → Scan that specific PR (Phase 0)
- `nmdabbott` or `abbott` → Auto-Discovery for NMDAbbott only
- `md` or `nmd-md` or `medical` → Auto-Discovery for NMD-MedicalDevices only
- `all` → Same as empty, scan both orgs

The skill body documents the accepted argument forms and tells the model how to branch. The harness provides the raw string; the model interprets it. This is a clean separation of concerns: the harness is not in the business of parsing command-line arguments, and the model is fully capable of handling the dispatch logic.

For skills that take structured arguments, a table in the skill body is more robust than prose. The model pattern-matches against explicit cases rather than inferring from description.

The Skill Tool vs. Other Harness Tools

The Skill tool is not a tool in the same sense as Read or Bash. It does not perform an external action. It is a context injection mechanism — it inserts content into the conversation that shapes how the model interprets subsequent exchanges. When you call Skill({skillName: "research"}), you are not running a subprocess; you are adding instructions to the model's effective prompt.

This matters for debugging. If a skill is not behaving as expected, the first diagnostic question is not "did the skill execute correctly?" — skills always execute, they are just text injection. The question is "did the instructions in the skill body produce the intended model behavior?" That is a prompting problem, not an execution problem.

17.4 ProposeSkills: Automatic Generation from Observed Patterns

ProposeSkills is the harness's learning loop. When the model observes a pattern it has executed multiple times — a sequence of steps that worked well and would benefit from a shorthand — it can propose converting that pattern into a skill.

The ProposeSkills Interface

export interface ProposeSkillsInput {
  proposals: [{
    name: string;           // kebab-case skill slug
    kind: "new" | "improvement";
    target?: string;        // existing skill name (required for "improvement")
    description: string;    // one line shown on card
    evidence?: string[];    // memory file paths where procedure was observed
    skillMd: string;        // complete SKILL.md draft (frontmatter + body)
  }]; // 1-3 proposals per call
}

export interface ProposeSkillsOutput {
  proposalCount: number;
}

The model calls ProposeSkills with one to three proposals. Each proposal includes a complete draft SKILL.md — not an outline or a description of what the skill should do, but the actual file content that would be written to disk. The harness presents the proposals to the user as skill cards with the option to accept or reject.

This design is deliberate. The harness is not asking the user to write a skill; it is asking the user to approve a skill it has already written. The approval friction is low — the user reviews, accepts, and the file is created. The authorship belongs to the agent.

What Triggers a Proposal

ProposeSkills fires when the model recognizes that it has:

  1. Executed the same multi-step procedure more than once in the same session
  2. Provided the same setup instructions to a user who repeatedly asks for the same type of work
  3. Observed a workflow in memory files (the evidence field) that has been noted as useful

In practice, the most common trigger is the second case: the user asks for a code review, the model runs its review workflow, the user asks for another code review a week later, and the model proposes a code-review skill that codifies the workflow it has been executing ad hoc.

The evidence field points to memory files that document where the observed behavior came from. This creates an audit trail: when the user sees a proposal, they can follow the evidence to understand what the agent observed before making the proposal.

"new" vs. "improvement"

A kind: "new" proposal creates a new skill file. A kind: "improvement" proposal amends an existing skill. When kind: "improvement", the target field names the existing skill, and skillMd contains the complete replacement file — not a diff. The harness shows the user what would change.

Improvements are the correct mechanism when a skill exists but a specific case is not handled, when a frontmatter field like allowed-tools should be tightened, or when new false positive patterns should be added to a security skill's body.

Working with Proposals

Proposals are stored until the user acts on them. Accepted proposals write the SKILL.md to the appropriate discovery path — project skills for proposals grounded in current project patterns, global skills for proposals grounded in cross-project memory. Rejected proposals are discarded.

The learned global skill in the production workspace serves as a staging area: it accumulates proposed skill bodies as they are observed, letting the user review and extract individual skills later rather than committing to a new directory immediately.

17.5 Conditional Paths: Context-Aware Skill Visibility

The paths frontmatter field is the mechanism for making skills appear only in the environments where they are relevant. Without it, every skill you build accumulates in the global list regardless of which project is active.

How Path Matching Works

When the harness assembles the skill list, it evaluates each skill's paths globs against the current working directory's file tree. A skill with no paths is always visible. A skill with paths is visible only when at least one file in the working directory matches at least one glob in the list.

---
name: tf-lint
description: Lint and validate Terraform configurations
paths:
  - "**/*.tf"
  - "**/*.tfvars"
  - ".terraform/**"
---

This skill appears when working in a Terraform infrastructure repository. It does not appear in a Python service, a React app, or a book repository. The user's skill menu reflects the active environment rather than the user's entire history of skill creation.

Practical Patterns

Language-specific skills. A skill for Python type-checking should restrict to **/*.py. A TypeScript refactoring skill should restrict to **/*.ts and **/*.tsx. Skills without path restrictions in a polyglot workspace clutter the menu with irrelevant options.

Project-tier skills. Skills that only make sense in a specific project can use highly specific globs:

paths:
  - "backend/scripts/secpr_*.py"

This skill only activates in the specific directory that contains the scripts it needs. It is invisible in every other project, even though the SKILL.md is a global skill.

Config-presence detection. A deployment skill that requires a particular CI configuration can gate on that file's existence:

paths:
  - ".github/workflows/**"
  - "azure-pipelines.yml"

When neither path matches, the skill does not appear — a useful signal that deployment via that skill is not applicable here.

Path Matching in --bare Mode

Skills resolve correctly in --bare mode via /skill-name even when path restrictions are in effect. --bare mode disables the active menu and autocomplete but not skill resolution itself. If a user types /tf-lint in a directory with no Terraform files, the skill still invokes. The paths field controls visibility in the menu, not the ability to invoke by name.

17.6 Real Skills: Production Examples

The 23 skills in the production workspace range from two-line procedural helpers to 2500-line autonomous systems. Understanding the design decisions in each reveals the full range of what the skill system can express.

sec-pr: Autonomous Security Review

The sec-pr skill is the most complex in the workspace. Its frontmatter sets the baseline:

---
name: sec-pr
description: Security PR review for Azure DevOps pull requests. Use when user
  says "sec-pr", "PR security review", "scan PR", "review PR security", "PR
  scan", "security scan PR", "check sec-pr", "sec-pr status", "approve PR".
  Without a PR number, auto-discovers all active PRs across all repos and
  scans them.
argument-hint: "[pr-number | org-name (optional)]"
model: claude-opus-4-6
effort: high
allowed-tools: Read, Grep, Glob, Bash, Agent
---

The description seeds 10 distinct invocation phrases. Any of them routes to this skill. The user never needs to remember the exact command name — natural language works.

model: claude-opus-4-6 and effort: high are justified by the task: the skill reads 30-50 files per PR, reasons about authentication flows, generates complete patch code, posts structured content to ADO, and manages a state machine that persists across monitor ticks. This requires the best reasoning available. The model switch is invisible to the user; they just type /sec-pr.

The skill body encodes an 8-phase pipeline: Acquisition → Quick Scan → Agent Dispatch → Consolidation → Report Generation → Post to ADO → Vote → Monitor. Each phase is documented with exact bash commands, Python snippets, and decision tables. The body is 1500+ lines — not a specification for a human to implement, but a complete operational runbook for the model to execute.

This is the defining characteristic of a production skill: it should be complete enough that the model can execute it correctly in a fresh context with no prior memory of the workflow. The skill body is a self-contained instruction set.

dt: Autonomous Trading

The /dt skill illustrates the model override applied to maximize decision quality:

---
name: dt
description: Decode Trader — autonomous SPY 0DTE paper trading. Buy calls or
  puts only. Dispatches tmux team for parallel analysis + execution. Use when
  user says "dt", "decode trader", "trade", "trading", "position", "what's
  the play", "market update", or "close position".
argument-hint: [optional: close|status]
allowed-tools: Read, Grep, Glob, Bash, Agent
model: claude-opus-4-6
effort: high
---

Two design decisions stand out. First, model: claude-opus-4-6 combined with effort: high commits to maximum reasoning for every invocation. Trading decisions carry real financial consequence even in a paper account — the cost of a wrong model choice is higher than the cost of a more expensive API call. Second, the allowed-tools list includes Agent, enabling the skill to spawn a 4-agent tmux team for parallel analysis.

The skill body encodes a complete trading system: signal chain, 4-pillar entry gate, agent deployment protocol, position management rules, context hygiene requirements, and session recovery procedures. The model executing /dt is not making ad hoc decisions; it is following a documented methodology that was refined over dozens of trading sessions.

research: Minimal but Complete

The research skill is the opposite end of the spectrum:

---
name: research
description: Deep research on technical topics using web search, documentation,
  and codebase exploration.
---

No model override. No allowed-tools restriction. No effort override. No paths restriction. The body is 30 lines: scope clarification, parallel source gathering, synthesis format.

The simplicity is appropriate. Research is a general workflow that applies everywhere, benefits from the full tool surface, and does not require a specific model. The skill exists to give the workflow a name and a consistent output format, not to encode a complex operational system.

deploy-check: Locked Down with disable-model-invocation

The deploy-check skill introduces a field not covered in the schema overview:

---
name: deploy-check
description: Pre-deployment readiness check.
disable-model-invocation: true
allowed-tools: Bash, Read, Grep, Glob
effort: high
---

disable-model-invocation: true runs the skill as a pure script executor — the commands in the body run directly without an API call. This is the correct pattern for purely mechanical skills: git status checks, secret scans, test runs, build validation. There is no reasoning to do. The output is deterministic. Running it through the model adds latency and cost with no benefit.

The allowed-tools restriction to Bash, Read, Grep, Glob — with Agent absent — ensures the skill cannot spawn subagents, further constraining it to the simple mechanical execution pattern it was designed for.

Skills Compared to Hooks and Plugins

The skill system sits alongside two other harness extension points: hooks and plugins. Understanding where each applies prevents the common mistake of building a skill when a hook is more appropriate, or reaching for a plugin when a skill is sufficient.

MechanismTriggerScopeStatefulness
SkillUser invocation (/name)ConversationEphemeral (single invocation)
HookHarness lifecycle event (file write, tool call, session end)BackgroundEphemeral (single event)
Plugin/MCPModel request during any conversationAny conversationPersistent (server lifetime)

A skill is the right choice when the user initiates the workflow explicitly. The user types /sec-pr because they want a security review right now. Skills are on-demand.

A hook is the right choice when you want something to happen automatically in response to a harness event — not when the user asks, but when the harness does something. PostToolUse hooks that log every file write. PreToolUse hooks that validate commands before execution. Stop hooks that save session state when the agent exits. Hooks are reactive.

A plugin (MCP server) is the right choice when you need persistent state, a long-running process, or capabilities that multiple conversations should share. The dt-mem trading memory server is an MCP plugin, not a skill, because it needs to store data that persists between sessions and be accessible to multiple agent invocations simultaneously.

The failure mode for conflating these: building a skill that should be a hook means you are manually invoking something that could be automatic. Building a hook that should be a skill means you are executing something automatically that should be explicitly requested.

17.7 Restricting the Skill System

Two settings give operators control over the skill system in environments where unrestricted slash commands are not appropriate.

disableSkillShellExecution

Set in settings.json:

{
  "disableSkillShellExecution": true
}

This blocks inline shell execution in skill bodies. Skills that contain bash code blocks will have those blocks interpreted as text rather than executed. The model can still reason about the commands and produce output, but the harness will not run them.

The practical use case is an environment where shell execution requires explicit approval for all commands, not just those in skills. If your PreToolUse hooks apply shell approval requirements, disableSkillShellExecution prevents skills from bypassing those requirements through their own execution path.

Skills that use the Bash tool explicitly (via allowed-tools: Bash) are not affected by disableSkillShellExecution. The setting only blocks the inline shell execution path within skill bodies. Removing Bash from allowed-tools in the skill frontmatter and setting disableSkillShellExecution together produces a fully execution-restricted skill system.

--disable-slash-commands

The CLI flag:

claude --disable-slash-commands

Disables all skill invocation. The /skills menu does not appear. Typing /skill-name is treated as literal text, not as a skill invocation. ProposeSkills proposals are suppressed. The skill discovery paths are still read (skills are still registered internally), but no user-facing skill functionality is active.

This is the correct setting for automated pipeline usage where interactive slash commands make no sense, and for restricted deployments where the operator wants to constrain Claude Code to a specific tool set without any user-extensible shortcuts.

Note that --disable-slash-commands does not disable built-in slash commands like /clear, /model, and /compact. It disables user-defined skills only.

Combining Restrictions

For maximum restriction — skills present in the manifest but not executable by users:

{
  "disableSkillShellExecution": true
}
claude --disable-slash-commands --bare

--bare mode suppresses the CLAUDE.md injection and the full interactive UI. Combined with --disable-slash-commands, it gives you a model interaction surface with no user-extensible behavior and no project-injected context — a clean baseline for controlled evaluation environments.

17.8 Lab: Build a Deployment Skill with Pre-Flight Validation and Post-Deploy Monitoring

This lab builds a complete deployment skill from scratch. The skill validates readiness before deploying, executes the deployment, and monitors post-deploy health. It demonstrates every frontmatter field and shows how a multi-phase skill body coordinates with the harness.

What We Are Building

A /deploy skill for a Python web service that:

  1. Validates the working tree is clean and tests pass (pre-flight)
  2. Checks the target environment is reachable and healthy (environment check)
  3. Executes deployment via the project's deploy script (execution)
  4. Monitors health endpoints for 60 seconds post-deploy (monitoring)
  5. Reports status with rollback instructions if health checks fail

Step 1: Create the Skill Directory

mkdir -p /Users/DOANTX26/Documents/2026/.claude/skills/deploy

Skills live in a directory, not a file. The directory name matches the skill name. The SKILL.md lives inside:

.claude/skills/deploy/
└── SKILL.md

Step 2: Write the Frontmatter

Create /Users/DOANTX26/Documents/2026/.claude/skills/deploy/SKILL.md:

---
name: deploy
description: Deploy the current service to staging or production. Runs
  pre-flight checks, executes deployment, monitors health. Use when user
  says "deploy", "ship it", "push to staging", "release", or "go live".
argument-hint: "[staging|prod] [--skip-tests]"
allowed-tools: Bash, Read, Grep, Glob
effort: high
paths:
  - "deploy.sh"
  - "Makefile"
  - "pyproject.toml"
  - "Dockerfile"
---

Design rationale for each field:

description seeds five natural-language invocations. The user can say /deploy staging or /deploy prod — both parse correctly from $ARGUMENTS.

argument-hint shows the user the two valid environments and the optional test-skip flag. The hint is documentation; the skill body handles actual parsing.

allowed-tools: Bash, Read, Grep, Glob — no Agent needed. This is a sequential workflow: validate, deploy, monitor. No parallel subagents required.

effort: high — deployment requires careful reasoning about whether each check passed. High effort gives the model adequate thinking budget for the pre-flight decision logic.

paths restricts the skill to directories that contain deployment artifacts. A Python library without a deploy.sh will not show /deploy in its skills menu.

Step 3: Write the Skill Body

# /deploy — Service Deployment

You are executing a production deployment workflow. Execute every phase
completely. Do not skip a phase if the previous one fails — report the
failure clearly and provide rollback instructions.

**Environment:** $ARGUMENTS
Parse `$ARGUMENTS` as: first word is environment (`staging` or `prod`),
optional `--skip-tests` flag skips the test phase.

If `$ARGUMENTS` is empty, default to `staging`.
If `$ARGUMENTS` contains `prod` or `production`, set ENV=prod and double-check
every pre-flight gate before proceeding.

---

## Phase 1 — Pre-Flight Validation

Run every check. Report each result as PASS or FAIL. Do not proceed to
Phase 2 if any check fails with FAIL severity.

### 1.1 Working Directory Clean

git status --porcelain git log origin/main..HEAD --oneline


Expected: empty output for both. Any uncommitted changes or unpushed
commits = FAIL.

### 1.2 Tests Pass (skip if --skip-tests)

python -m pytest tests/ --tb=short -q 2>&1


Expected: all tests pass. Any failure = FAIL. Record the failure output.
If `--skip-tests` is set, report as SKIPPED and note it in the final report.

### 1.3 No Secrets in Changed Files

git diff origin/main..HEAD -- '.py' '.yaml' '.env' '.json' | \ grep -E '^\+' | \ grep -iE '(password|secret|token|api[_-]?key)\s*[:=]\s*["\x27][^"\x27]{8,}'


Expected: no output. Any match = FAIL with the matching line quoted.

### 1.4 Dependencies Audited

pip audit --format=json 2>/dev/null | python3 -c " import json, sys data = json.load(sys.stdin) vulns = data.get('vulnerabilities', []) critical = [v for v in vulns if v.get('fix_versions')] print(f'Vulnerabilities: {len(vulns)} total, {len(critical)} with fixes') for v in critical[:5]: print(f' {v[\"name\"]} {v[\"version\"]}: {v[\"description\"][:80]}') "


Expected: zero vulnerabilities with available fixes. Unfixed vulns = WARN.
Vulns with available fixes = FAIL.

### Pre-Flight Gate

| Check | Result | Severity |
|-------|--------|----------|
| Git clean | — | FAIL stops deploy |
| Tests pass | — | FAIL stops deploy |
| No secrets | — | FAIL stops deploy |
| Dependencies | — | WARN allows deploy |

**If any FAIL:** Stop here. Do not proceed to Phase 2. Report:

DEPLOY BLOCKED Pre-flight failures: [list of failing checks] Fix the failures and re-run /deploy.


---

## Phase 2 — Environment Health Check

Verify the target environment is reachable and in a state that can
accept a deployment.

### 2.1 Resolve Target URL

Read deploy config

cat deploy.sh | grep -E 'STAGING_URL|PROD_URL|TARGET_URL' cat .env.deploy 2>/dev/null | grep -E 'URL|HOST|ENDPOINT'


Extract the health endpoint URL for the target environment from the
deploy configuration. If not found, report that the environment URL
is not configured and stop.

### 2.2 Current Health Baseline

curl -sf --max-time 10 "${HEALTH_URL}/health" | python3 -m json.tool 2>/dev/null echo "HTTP status: $(curl -s -o /dev/null -w '%{http_code}' --max-time 10 ${HEALTH_URL}/health)"


Expected: HTTP 200, JSON body with `status: "ok"` or equivalent.
Record the baseline response for comparison after deploy.

If the health endpoint is not reachable: **FAIL — target environment
is down. Cannot deploy to a dead environment. Page on-call.**

---

## Phase 3 — Execute Deployment

bash deploy.sh $ENV 2>&1 | tee /tmp/deploy_output_$(date +%Y%m%d_%H%M%S).log DEPLOY_EXIT=$?


Capture full output. Record the log path.

If `DEPLOY_EXIT` is non-zero: **FAIL — deployment script exited with
error. Do not proceed to health monitoring. Initiate rollback (Phase 5).**

Expected output: deployment script reports success, new version deployed,
service restarting.

---

## Phase 4 — Post-Deploy Health Monitoring

Monitor the health endpoint for 60 seconds after deployment. Check
every 10 seconds. The service may take up to 30 seconds to restart.

for i in 1 2 3 4 5 6; do sleep 10 STATUS=$(curl -s -o /dev/null -w '%{http_code}' --max-time 10 "${HEALTH_URL}/health" 2>/dev/null) BODY=$(curl -sf --max-time 10 "${HEALTH_URL}/health" 2>/dev/null) echo "Check ${i}/6 ($(date +%H:%M:%S)): HTTP ${STATUS}" [[ "${STATUS}" == "200" ]] && echo " Body: $(echo $BODY | python3 -c 'import sys,json; d=json.load(sys.stdin); print(d.get("version","?"),d.get("status","?"))' 2>/dev/null)" done


**Success criteria:** HTTP 200 on at least 4 of the last 4 checks
(checks 3-6). A 200 on check 1 or 2 that reverts later means the
service restarted but then crashed.

**If health checks fail after check 3:** The deployment is unstable.
Proceed to Phase 5 (Rollback).

---

## Phase 5 — Rollback (only if Phase 3 or 4 failed)

bash deploy.sh $ENV --rollback 2>&1 | tee /tmp/rollback_output_$(date +%Y%m%d_%H%M%S).log


If the deploy script does not support `--rollback`, report the manual
rollback steps extracted from the deploy script's comments or a
`ROLLBACK.md` if it exists.

After rollback, re-run the Phase 4 health check to confirm the previous
version is healthy.

---

## Phase 6 — Report

Report the full deployment result in this format:

DEPLOYMENT REPORT — $ENV ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Time: [timestamp] Version: [deployed version or commit SHA] Status: DEPLOYED / FAILED / ROLLED BACK

Pre-flight: Git clean [PASS/FAIL] Tests [PASS/FAIL/SKIPPED] No secrets [PASS/FAIL] Dependencies [PASS/WARN]

Deployment: [PASS/FAIL] Log: /tmp/deploy_output_[timestamp].log

Health: Check 1/6 [HTTP status] Check 2/6 [HTTP status] Check 3/6 [HTTP status] Check 4/6 [HTTP status] Check 5/6 [HTTP status] Check 6/6 [HTTP status] Final: [STABLE/UNSTABLE]

[If FAILED or ROLLED BACK:] ROLLBACK INSTRUCTIONS: bash deploy.sh $ENV --rollback [manual steps if script does not support --rollback]

Step 4: Verify the Skill Appears

In a directory that contains a deploy.sh or Makefile:

/skills

The /deploy skill should appear. If it does not, verify:

  1. The directory is named deploy (matching the name: field)
  2. The SKILL.md frontmatter is valid YAML (no tabs, correct quoting)
  3. The paths globs match something in the working directory

To test in a directory without those files, invoke directly by name:

/deploy staging

The skill activates regardless of path matching when invoked by explicit name.

Step 5: Test with --skip-tests

/deploy staging --skip-tests

The skill parses --skip-tests from $ARGUMENTS and skips Phase 1.2. The final report marks tests as SKIPPED and notes the flag was set.

Step 6: Extend with ProposeSkills

After running /deploy a few times, the model may observe that you always deploy to staging first and then verify before deploying to prod. It might propose a deploy-promote skill that encodes the two-stage workflow as a single command. That proposal is the skills system working as designed: turning repeated behavior into an explicit, nameable command.

Summary

The skills system is the harness's mechanism for turning repeated workflows into named, invocable commands. The SKILL.md frontmatter controls the execution environment — model, tool surface, effort level, context restrictions. The skill body controls the model's behavior — the instructions it follows when /name is typed.

Skills are appropriate when the user initiates the workflow explicitly. Hooks are appropriate when the workflow should trigger automatically. MCP plugins are appropriate when the workflow needs persistent state across sessions. The three mechanisms are complementary, not competitive.

The production skill library in this workspace spans the full range from 30-line research assistants to 2500-line autonomous security review systems. What they share: each skill body is complete enough to execute correctly in a fresh context, each frontmatter is specific enough that the skill appears exactly when it is relevant, and each allowed-tools list is exactly as broad as the skill's actual needs.

Build skills the way you would write a runbook: for a competent reader who has never seen the workflow before and needs to execute it correctly on the first attempt.
