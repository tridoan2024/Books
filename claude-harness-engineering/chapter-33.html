Chapter 33: Knowledge and Research Agents

"A research agent that cannot verify its own findings is not a researcher. It is a confident guesser."

A code-review agent knows what it is looking for: files, functions, call sites, patterns. Its search space is bounded. A research agent is different. Its search space is the entire information surface reachable from your harness — web pages, local documentation, memory stores, MCP servers, codebases — and the target is not a location but a synthesis. The agent must discover, evaluate, dispute, reconcile, and persist. It must learn from each run so the next run starts sharper.

This chapter builds that system from first principles: how to gather from multiple sources without redundancy, how to challenge your own findings before you trust them, how to collapse parallel results into a single coherent output, and how to persist what you learned in a form that is worth retrieving months later. The final section walks through a production deployment — copilot-mem — that has been running this model at scale long enough to produce real numbers.

33.1 Multi-Source Information Gathering

The mistake most engineers make when building research agents is treating sources sequentially. You search the web. If that is not enough, you check local files. If that is not enough, you query memory. Sequential source access is both slow and unrepresentative — you stop when you find something, which means you stop at the first source that sounds right, not the best source that is actually right.

The correct model is parallel sweep: hit all sources simultaneously, collect raw findings with provenance, then reconcile. The barrier comes after discovery, not during it.

Sources and their characteristics

Different sources have different latency, reliability, and signal type. Understanding these before you design your sweep determines which sources you run together versus in sequence.

SourceLatencyReliabilityBest signal type
WebSearch1–3sMedium — indexed content, may be staleBroad discovery, new releases, CVEs
WebFetch2–8sHigh — you choose the pageDeep detail on a known authoritative source
Read (local)<100msHigh — ground truth for your repoArchitecture, internal conventions, current config
MCP memory<200msHigh — your own curated knowledgePast decisions, project context, domain preferences
Agent (Explore)3–15sHigh — live codebase traversalImplementation details, call graphs, test coverage
Agent (researcher)15–60sHighest — deep reasoningSynthesis, contradiction resolution, complex tradeoffs

The sweep pattern maps directly onto parallel():

const FINDINGS_SCHEMA = {
  type: 'object',
  properties: {
    findings: {
      type: 'array',
      items: {
        type: 'object',
        properties: {
          claim: { type: 'string' },
          source: { type: 'string' },
          url: { type: 'string' },
          confidence: { type: 'number' },  // 0.0–1.0
          category: { type: 'string' }
        },
        required: ['claim', 'source', 'confidence']
      }
    }
  },
  required: ['findings']
}

const topic = 'OWASP JWT validation best practices 2025'

const sweep = await parallel([
  () => agent(
    `Search the web for: ${topic}. Return the top 8 findings with source URLs.`,
    { label: 'web-search', schema: FINDINGS_SCHEMA }
  ),
  () => agent(
    `Search local documentation in /docs and README files for anything related to: ${topic}.`,
    { label: 'local-docs', schema: FINDINGS_SCHEMA, subagent_type: 'Explore' }
  ),
  () => agent(
    `Search memory for prior decisions and knowledge about: ${topic}. Use search_memory and get_related_knowledge tools.`,
    { label: 'memory-search', schema: FINDINGS_SCHEMA }
  ),
  () => agent(
    `Scan the codebase at /Users/DOANTX26/Documents/2026/myapp/src for existing JWT handling code. Summarize what validation is currently implemented.`,
    { label: 'codebase-scan', schema: FINDINGS_SCHEMA, subagent_type: 'Explore' }
  )
])

Each agent runs concurrently. The web search agent is pulling from live index results. The local doc agent is doing filesystem traversal. The memory agent is hitting the MCP server's search interface. The codebase agent is reading implementation files. All four run at the same time, and parallel() collects all four results before any downstream processing begins.

The parallel() barrier is justified here because the next step — deduplication and reconciliation — requires looking across all four result sets simultaneously. You cannot deduplicate web findings against memory findings until you have both.

Deduplication before synthesis

Parallel sweeps produce overlapping findings. The same claim will appear from multiple sources: the OWASP documentation says it, a blog post repeats it, your memory stored it after a prior run. Deduplication before synthesis prevents the same signal from receiving unwarranted amplification.

// Flatten all findings from all sources
const allFindings = sweep
  .filter(Boolean)
  .flatMap(r => r.findings ?? [])

// Cluster by semantic similarity — agent as grouper
const deduped = await agent(
  `You have ${allFindings.length} findings from multiple sources about: ${topic}.
  
Many are semantically identical claims from different sources. Your job:
1. Group findings that express the same core claim (regardless of wording).
2. For each group, keep the claim from the highest-confidence source.
3. Merge the source list — a finding supported by 3 sources should list all 3.
4. Discard any finding with no source URL and confidence below 0.5.

Input findings:
${JSON.stringify(allFindings, null, 2)}`,
  {
    label: 'dedup',
    schema: FINDINGS_SCHEMA,
    model: 'opus'
  }
)

Using opus for deduplication is deliberate. Semantic clustering — deciding that "always verify the alg header" and "never trust the algorithm claim from the token header without validation" are the same claim — requires genuine language understanding, not just string matching. A haiku or sonnet will produce false separations that inflate your result set with near-duplicates.

MCP as a specialized source

MCP servers collapse the gap between "searching the web" and "querying a domain-specific knowledge base." A properly configured MCP server can return structured knowledge on demand — not raw text requiring extraction, but typed facts, relationships, and metadata.

// Using MCP tool directly in an agent's available tools
() => agent(
  `Use the copilot-mem MCP server to search for knowledge about JWT validation.
   
   Call: search_memory with query="JWT validation alg header"
   Then: get_related_knowledge for each memory_id returned
   Return the memory content and any linked memories.`,
  { label: 'mcp-memory', schema: FINDINGS_SCHEMA }
)

The agent running this prompt has access to the search_memory and get_related_knowledge tools exposed by the copilot-mem MCP server. It is not just doing keyword lookup — it is traversing a knowledge graph, following related_to and caused_by links between memories to return an interconnected cluster of knowledge rather than isolated hits.

This is the architectural advantage of MCP over raw file search: the knowledge has structure. A memory stored as a bug_recipe with links to the design_rationale that led to the bug, and to the tech_insight that fixed it, returns three nodes in a single query. A flat file search returns text.

33.2 Adversarial Verification of Claims

Information gathered at scale is wrong at scale. Web search returns authoritative-sounding content that is outdated, misquoted, or hallucinated. Local documentation describes the system as it was designed, not as it actually runs. Memory records can be stale. Even live codebase analysis can miss the one function that overrides the behavior you just characterized.

Adversarial verification treats every finding as a claim to be refuted. You do not validate a claim by asking "is this true?" You assign an adversary whose explicit goal is to prove the claim false. A finding that survives a genuine attempt at refutation is a finding you can trust.

The skeptic pattern

const VERDICT_SCHEMA = {
  type: 'object',
  properties: {
    claim: { type: 'string' },
    refuted: { type: 'boolean' },
    refutation_evidence: { type: 'string' },   // only if refuted
    confidence_adjustment: { type: 'number' },  // -1.0 to +1.0
    verdict: { type: 'string', enum: ['confirmed', 'refuted', 'uncertain'] }
  },
  required: ['claim', 'refuted', 'verdict']
}

const verified = await pipeline(
  deduped.findings,
  finding => agent(
    `You are a skeptic. Your job is to REFUTE the following claim.
    
Claim: "${finding.claim}"
Source: ${finding.source}
Original confidence: ${finding.confidence}

Search the web, check local files, and reason carefully.
Try hard to find evidence that this claim is:
- False or outdated
- True only in specific narrow conditions not stated
- Contradicted by another credible source
- Not applicable to the current codebase

If you cannot refute it after a genuine attempt, say so honestly.

Return your verdict with evidence.`,
    {
      label: `verify:${finding.claim.slice(0, 40)}`,
      schema: VERDICT_SCHEMA,
      model: 'sonnet'
    }
  )
)

const confirmed = verified
  .filter(Boolean)
  .filter(v => v.verdict === 'confirmed' || v.verdict === 'uncertain')
  .map((v, i) => ({
    ...deduped.findings[i],
    confidence: deduped.findings[i].confidence + (v.confidence_adjustment ?? 0),
    verified: true,
    refutation_attempted: true
  }))

This pipeline assigns one skeptic agent per finding. Each runs concurrently (within the pipeline's concurrency model). A finding that returns refuted: true is dropped. A finding that returns uncertain is retained with a lower adjusted confidence. A finding that returns confirmed — meaning the skeptic tried hard and could not disprove it — earns a confidence boost.

The adversarial framing matters at the prompt level. An agent asked "please verify this claim" will pattern-match toward confirmation. An agent explicitly told "your job is to refute this" is primed to look for counterevidence. The difference in output quality is observable and consistent.

Evidence chains

Single-source verification is not enough for high-stakes claims. A finding about a security vulnerability, an architectural decision, or a factual constraint on system behavior should carry an evidence chain — a trace of independent sources that each support it, where "independent" means they are not all downstream of the same original source.

const CHAIN_SCHEMA = {
  type: 'object',
  properties: {
    claim: { type: 'string' },
    evidence: {
      type: 'array',
      items: {
        type: 'object',
        properties: {
          source: { type: 'string' },
          url: { type: 'string' },
          excerpt: { type: 'string' },
          independence: { type: 'string', enum: ['primary', 'secondary', 'derived'] }
        },
        required: ['source', 'independence']
      }
    },
    chain_strength: { type: 'number' }  // 0.0–1.0: how independent are the sources?
  },
  required: ['claim', 'evidence', 'chain_strength']
}

const withChains = await pipeline(
  confirmed.filter(f => f.confidence > 0.8),
  finding => agent(
    `Build an evidence chain for this claim: "${finding.claim}"

Find 2–4 independent sources that each support this claim. 
Independent means: primary sources (official documentation, CVE records, academic papers), 
secondary sources (reputable security blogs, established tooling docs), 
or derived sources (stack overflow, tutorials — lowest weight).

Do not count a source that cites the same primary source as independent from it.

Return each supporting source with an excerpt and independence classification.
Compute chain_strength: 1.0 = all primary independent sources; 0.0 = single unverifiable claim.`,
    { label: `chain:${finding.claim.slice(0, 40)}`, schema: CHAIN_SCHEMA }
  )
)

A finding with chain_strength > 0.75 — supported by multiple primary independent sources — can be persisted to long-term memory with high confidence. A finding with chain_strength < 0.4 should be flagged as requiring further investigation before it informs a decision.

33.3 Knowledge Synthesis

Synthesis is where gathered, verified knowledge becomes usable output. The failure mode of poor synthesis is a list — you did the hard work of gathering and verifying, and then you produced a bulleted collection of facts that the reader has to mentally assemble into understanding. That is not synthesis. That is filing.

Real synthesis has structure: themes emerge, contradictions are resolved, gaps are named, and the output has a shape appropriate to the question asked.

Structured output as synthesis scaffold

The schema you pass to a synthesis agent is not just type enforcement. It is a prescription for the shape of understanding. A well-designed schema forces the synthesis agent to organize knowledge into the categories that make it actionable.

const SYNTHESIS_SCHEMA = {
  type: 'object',
  properties: {
    summary: { type: 'string' },              // 2–3 sentence executive summary
    key_findings: {
      type: 'array',
      items: {
        type: 'object',
        properties: {
          finding: { type: 'string' },
          evidence_strength: { type: 'string', enum: ['strong', 'moderate', 'weak'] },
          actionability: { type: 'string', enum: ['immediate', 'planned', 'informational'] },
          related_findings: { type: 'array', items: { type: 'string' } }
        },
        required: ['finding', 'evidence_strength', 'actionability']
      }
    },
    contradictions: {
      type: 'array',
      items: {
        type: 'object',
        properties: {
          claim_a: { type: 'string' },
          claim_b: { type: 'string' },
          resolution: { type: 'string' },
          confidence: { type: 'number' }
        },
        required: ['claim_a', 'claim_b']
      }
    },
    knowledge_gaps: { type: 'array', items: { type: 'string' } },
    recommended_actions: {
      type: 'array',
      items: {
        type: 'object',
        properties: {
          action: { type: 'string' },
          priority: { type: 'string', enum: ['high', 'medium', 'low'] },
          rationale: { type: 'string' }
        },
        required: ['action', 'priority']
      }
    }
  },
  required: ['summary', 'key_findings', 'recommended_actions']
}

const synthesis = await agent(
  `Synthesize the following verified research findings into a coherent knowledge summary.

Topic: ${topic}
Verified findings (${withChains.length} total):
${JSON.stringify(withChains, null, 2)}

Requirements:
- Group related findings into themes, not a flat list
- Explicitly surface any contradictions between findings and resolve them where possible
- Name gaps where the evidence is thin or missing entirely
- Order recommended actions by evidence strength × impact, not by frequency of mention
- The summary should be useful to a senior engineer who will act on it immediately`,
  {
    label: 'synthesize',
    schema: SYNTHESIS_SCHEMA,
    model: 'opus'
  }
)

The schema's contradictions field deserves special attention. Research agents regularly gather sources that conflict — an official spec says one thing, a widely-used library implements something different, and a CVE advisory explains why the difference matters. Without explicit handling of contradictions, a synthesis agent will silently pick one side and discard the other. Making contradictions a first-class output type forces the agent to surface them and attempt resolution.

Ranking by evidence strength

Not all verified findings deserve equal weight in a synthesized output. A finding supported by a 2025 CVE record, official RFC language, and a confirmed reproduction in your own codebase is categorically different from a finding sourced from a single forum post the skeptic could not quite refute.

The evidence_strength field in the synthesis schema creates this distinction. The synthesis agent assigns it based on the chain strength and source provenance accumulated during verification. Downstream consumers — the system prompt assembler, the memory store, the report generator — can filter or weight by this field.

// Only persist strong-evidence findings to long-term memory
const persistable = synthesis.key_findings
  .filter(f => f.evidence_strength === 'strong')
  .filter(f => f.actionability !== 'informational')

// Flag weak-evidence findings for human review
const flagged = synthesis.key_findings
  .filter(f => f.evidence_strength === 'weak')

log(`Synthesis: ${persistable.length} findings ready to persist, ${flagged.length} need review`)

33.4 Memory Persistence

A research agent that discards its findings at session end is a research agent that will re-derive the same knowledge next time it runs. At some token cost. For some latency penalty. Possibly with different results, because web content changed or a different code path was traversed. That is waste that compounds.

The solution is not logging — it is a typed memory system with temporal tiers and knowledge links. The difference matters: logs are append-only text you search with grep. Memory is structured knowledge you retrieve by relevance, project, type, and relationship.

The three temporal tiers

Memory persistence is not uniform. Different kinds of knowledge have different expected lifespans, and treating them identically produces a store that is simultaneously too large and too stale.

Long-term memory holds facts, preferences, and architectural knowledge that changes slowly or never. A security principle — "never trust the algorithm claim in a JWT header without server-side validation" — should not expire. A project's core architecture — "auth is handled by the token_validator middleware, not at the route level" — should persist until the architecture changes. Long-term memory survives conversation resets, session ends, and days without activity. In copilot-mem, 1034 of 1035 memories live in the long-term tier.

Medium-term memory holds decisions — not facts, but choices made at a point in time under specific conditions that may change. "We chose RS256 over HS256 for the new auth service because we need key rotation without deploying new app secrets" is a decision. It is true, it is important, but it is also conditional on the architecture at decision time. Medium-term memories carry context about the decision: who made it, why, what the alternatives were, what would trigger reconsideration. In copilot-mem, 1 of 1035 memories is medium-term — a number that reflects how rarely discrete decisions are recorded as discrete objects rather than embedded in facts.

Short-term / episodic memory holds what is happening right now. Daily tracking, session-level state, in-progress task notes. These are meant to expire. An episode from three months ago ("investigated JWT timeout, found config issue, resolved") has no retrieval value; the config issue was fixed. Episodic memories in copilot-mem total 26 — a small working set that cycles as sessions complete.

Persistence operations mapped to knowledge types

// After synthesis — map finding types to persistence operations

for (const finding of persistable) {

  if (finding.category === 'security_principle') {
    // Long-lived factual knowledge — save_fact with high importance
    await mcpTool('copilot-mem', 'save_fact', {
      key: `security:jwt:${slugify(finding.finding)}`,
      value: finding.finding,
      importance: 5,
      project: 'myapp',
      context: `Evidence: ${finding.evidence_strength}. Sources: ${finding.sources?.join(', ')}`
    })
  }

  if (finding.category === 'architectural_insight') {
    // Architecture knowledge — use capture_app_knowledge
    await mcpTool('copilot-mem', 'capture_app_knowledge', {
      project: 'myapp',
      category: 'architecture',
      content: finding.finding,
      importance: 4
    })
  }

  if (finding.category === 'implementation_pattern') {
    // Reusable pattern — save as tech_insight
    await mcpTool('copilot-mem', 'capture_app_knowledge', {
      project: 'myapp',
      category: 'tech_insight',
      content: finding.finding,
      importance: 3
    })
  }
}

// Persist the decision that triggered this research
await mcpTool('copilot-mem', 'save_decision', {
  key: `decision:jwt-validation-approach:${Date.now()}`,
  value: synthesis.recommended_actions[0].action,
  rationale: synthesis.recommended_actions[0].rationale,
  project: 'myapp'
})

Knowledge links: the graph that makes retrieval useful

Saving facts in isolation produces a flat key-value store. Facts connected by typed relationships produce a knowledge graph where one query returns a cluster of related knowledge rather than a single answer.

// After saving individual memories, link them
const memoryIds = await getLastSavedMemoryIds('myapp', 5)

// Link the main finding to its evidence
await mcpTool('copilot-mem', 'save_knowledge_link', {
  from_memory: memoryIds.mainFinding,
  to_memory: memoryIds.cveEvidence,
  relation_type: 'caused_by',
  strength: 0.9,
  context: 'CVE-2024-XXXX directly demonstrates the attack vector'
})

// Link the decision to the finding that motivated it
await mcpTool('copilot-mem', 'save_knowledge_link', {
  from_memory: memoryIds.decision,
  to_memory: memoryIds.mainFinding,
  relation_type: 'related_to',
  strength: 0.8,
  context: 'Decision was motivated by this finding'
})

// Link the implementation pattern to the architecture it modifies
await mcpTool('copilot-mem', 'save_knowledge_link', {
  from_memory: memoryIds.pattern,
  to_memory: memoryIds.architecture,
  relation_type: 'part_of',
  strength: 0.7,
  context: 'Pattern is an implementation of this architectural decision'
})

copilot-mem maintains 2627 knowledge links across 1035 memories — an average of 2.5 links per memory. The five link types — related_to, evolved_from, caused_by, part_of, contradicts — are sufficient to express the relationships that matter for retrieval. When a future research agent calls get_related_knowledge on any of these memory IDs, it walks the graph outward and returns the connected cluster. A single query about "JWT validation" returns not just the security principle but the CVE that motivated it, the architectural decision it influenced, and the implementation pattern that followed.

33.5 Case Study: copilot-mem in Production

The patterns in sections 33.1–33.4 are not theoretical. They are running in production in a system called copilot-mem — a SQLite-backed MCP server built specifically to give a Claude harness durable, queryable memory across all projects in a workspace. Here are the real numbers after months of operation.

The store at a glance

Total memories:     1035
DB size:            35MB SQLite
Daily summaries:    119
Archived:           86 (recoverable 30 days)

Memory types:
  semantic (fact-based knowledge):  685   (66.2%)
  procedural (workflow/pattern):    324   (31.3%)
  episodic (session-level):          26    (2.5%)

Temporal tiers:
  long:    1034   (99.9%)
  medium:     1    (0.1%)

Knowledge links: 2627
  relation breakdown: related_to, evolved_from, caused_by, part_of, contradicts

Project profiles: 14

The 66/31/2 split between semantic, procedural, and episodic memory is not accidental — it reflects deliberate categorization choices. Facts about tools, libraries, APIs, and system behavior (semantic) accumulate faster than reusable patterns (procedural), and both accumulate far faster than in-progress session notes (episodic). The near-zero medium-term tier tells a different story: decisions are rarely captured as explicit objects. They tend to be implicit in the semantic memories that document why a system is built the way it is. A future improvement would be to run a synthesis pass after major research sessions to extract decision records from the semantic store.

The bug_recipe category is worth examining specifically. It represents the output of adversarial verification applied not to research findings but to system failures: a bug was observed, its reproduction was documented, a fix was captured, and the pattern was saved for future sessions. When a new agent encounters a symptom matching a known bug recipe, a single get_related_knowledge call returns the reproduction steps, root cause, and fix — bypassing the full investigate-verify-synthesize cycle that the original discovery required.

That is the compounding effect that makes memory worth the engineering cost: each research cycle that deposits into the store makes every future cycle faster.

The 7-factor relevance scoring

search_memory does not return results by insertion order or simple keyword frequency. It applies a 7-factor scoring function that weights each candidate memory:

  1. Keyword overlap — how many query terms appear in the memory's text
  2. Project match — memories tagged to the currently active project score higher
  3. Temporal relevance — recently accessed memories score higher (LRU-style decay)
  4. Importance — the 1–5 importance score set at save time
  5. Memory type weight — semantic memories score higher than episodic for factual queries
  6. Link density — memories with more outbound knowledge links score higher (more connected = more central)
  7. Access frequency — memories retrieved often are presumed more relevant

The link density factor is the least intuitive but most valuable. A memory with 8 outbound links occupies a structurally central position in the knowledge graph — it is connected to many other memories, which means it is likely a foundational piece of knowledge that spans multiple contexts. Surfacing it early in search results is generally correct.

The research lifecycle end-to-end

A complete research run through copilot-mem looks like this:

flowchart TD
    Q[Research question] --> S[Parallel sweep]
    S --> W[WebSearch agents]
    S --> L[Local doc agents]
    S --> M[Memory agents via MCP]
    S --> C[Codebase Explore agents]
    W & L & M & C --> D[Dedup + cluster — opus]
    D --> V[Adversarial skeptic pipeline — sonnet × N]
    V --> E[Evidence chain builder]
    E --> F{chain_strength?}
    F -->|≥ 0.75| P[Persist to long-term memory]
    F -->|0.4–0.74| R[Retain with low confidence flag]
    F -->|< 0.4| X[Flag for human review]
    P & R --> SY[Synthesis — opus]
    SY --> OUT[Structured output: findings + gaps + actions]
    P --> KL[Save knowledge links]
    KL --> DB[(SQLite — 35MB)]

The cycle time for a mid-complexity research question — 20–30 raw findings, 6–8 confirmed after verification, 1 synthesis pass — runs in 90–120 seconds with the parallel sweep model. Sequential execution of the same steps runs in 8–12 minutes. The difference is the parallel() barriers used deliberately: one for the initial sweep, one implicitly inside the pipeline for per-finding verification.

What the 14 project profiles contain

Each of the 14 active project profiles in copilot-mem is a structured object containing:

{
  purpose: "One-line mission statement",
  tech_stack: ["typescript", "sqlite", "mcp-protocol"],
  architecture: "Brief architectural description",
  key_components: [
    { name: "component", role: "what it does", file: "path/to/file" }
  ],
  active_context: "What is currently being worked on",
  constraints: ["Known hard constraints"],
  conventions: ["Team-specific conventions not obvious from code"]
}

When a research agent starts a new session, it calls get_project_profile before constructing any search queries. The profile injects project-specific context that shapes every downstream step: the tech_stack tells the web search agents which ecosystem to prioritize, the key_components tell the codebase scan agents where to look first, and the conventions tell the synthesis agent which recommended actions are feasible given how this team actually works.

Without the profile, a research agent generates generic findings. With it, findings are specific, actionable, and contextualized to the actual system they are meant to improve. This is the difference between a research agent that produces knowledge and one that produces reports.

Summary

Knowledge and research agents fail in predictable ways: single-source discovery, confirmation bias during verification, flat unstructured synthesis, and zero memory across sessions. The patterns in this chapter eliminate each failure mode explicitly.

Parallel sweep with parallel() gets all sources working simultaneously and eliminates the sequential-stop problem. Adversarial skeptics with explicitly-adversarial prompts eliminate confirmation bias. Structured synthesis schemas force organization rather than listing. Typed memory persistence with knowledge links turns each research run into an investment in the next.

The copilot-mem production data closes the feedback loop: 1035 memories, 2627 links, 35MB of accumulated knowledge, 14 project profiles. A research agent that starts a session with access to that store is not starting from zero. It is starting from the shoulders of every prior session that deposited knowledge into it. That compounding effect is what separates a knowledge system from a query system — and it is the engineering design decision that determines which one you are building.

Chapter 34 covers Monitoring and Observability — how to instrument research workflows, surface failures before they corrupt the knowledge store, and build dashboards that give you real-time visibility into agent quality at scale.
