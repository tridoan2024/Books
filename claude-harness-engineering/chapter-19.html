Chapter 19: MCP Integration — Model Context Protocol

"A harness that talks only to itself is a harness with a ceiling. MCP removes the ceiling."

19.1 MCP Fundamentals

The Model Context Protocol is a standardized wire protocol for connecting AI agents to external capability providers. Where the core tool system — Read, Bash, Edit, Agent — is built directly into Claude Code's runtime, MCP lets any server on the network expose tools and resources to the same interface. The harness calls an MCP tool exactly the same way it calls a built-in tool. The model cannot distinguish between them.

The protocol has three first-class entities:

Tools are callable functions. An MCP server declares a set of tools with names, descriptions, and JSON Schema input specifications. The harness registers these tools alongside its built-ins. When Claude calls one, the harness routes the invocation to the server and passes the result back as a tool result.

Resources are addressable data objects. A resource has a URI (e.g., memory://profiles/db-migrations) and a MIME type. Resources are not tools — they are not called, they are read. A server might expose a database table as a resource, a file in a remote filesystem, or a structured memory record. The harness reads resources on demand; the server streams the content back.

Resource directories are resource containers. A directory entry has mimeType: "inode/directory" and contains child resources or subdirectories. This mirrors the filesystem model: you can list a directory to discover its contents, then read individual resources by URI.

Transports

MCP servers communicate over one of two transports:

stdio — the server is a child process that the harness launches. The harness writes JSON-RPC messages to the process's stdin and reads responses from stdout. This is the default for locally-installed servers. The lifecycle is: harness spawns the process → performs capability handshake → begins exchanging messages → process exits when the harness terminates.

HTTP/SSE — the server is a remote service. The harness connects over HTTP, using Server-Sent Events for streaming server-to-client messages. This is the transport for cloud-hosted MCP servers like mcp.sentry.dev or app.corridor.dev. The handshake is identical to stdio at the protocol level; only the transport layer differs.

graph TD
    H[Claude Code Harness] -->|JSON-RPC via stdin/stdout| S1[Local MCP Server<br/>stdio transport<br/>npx my-mcp-server]
    H -->|JSON-RPC via HTTP/SSE| S2[Remote MCP Server<br/>HTTP transport<br/>mcp.sentry.dev]
    H -->|JSON-RPC via HTTP/SSE| S3[Remote MCP Server<br/>HTTP transport<br/>app.corridor.dev]
    S1 --> T1[tools: db_query, db_schema]
    S1 --> R1[resources: tables/*, views/*]
    S2 --> T2[tools: list_issues, create_comment]
    S3 --> T3[tools: get_context, search_memory]

The MCP Handshake

When the harness connects to an MCP server, regardless of transport, it performs a capability exchange. The server declares what protocol version it supports, what tools it exposes (name, description, input schema), and what resources it can serve (URI patterns, MIME types). The harness registers these into its tool system and resource registry. From this point forward, the server's tools are first-class citizens in every conversation.

The harness caches the capability list at connection time. If a server adds or removes tools while the harness is running, those changes are not visible until an explicit refresh — which is what RefreshMcpTools is for (section 19.5).

19.2 Server Configuration

claude mcp add

The primary command for registering an MCP server:

# stdio server via npx
claude mcp add my-server -e API_KEY=xxx -- npx my-mcp-server

# HTTP server (no auth)
claude mcp add --transport http sentry https://mcp.sentry.dev/mcp

# HTTP server with auth header
claude mcp add --transport http corridor https://app.corridor.dev/api/mcp \
  --header "Authorization: Bearer ${CORRIDOR_TOKEN}"

# Add from raw JSON spec
claude mcp add-json my-server '{"type":"stdio","command":"npx","args":["my-mcp-server"]}'

# Import servers from Claude Desktop config
claude mcp add-from-claude-desktop

# List registered servers
claude mcp list

# Inspect a specific server
claude mcp get my-server

# Remove a server
claude mcp remove my-server

Server registrations live in your user-level config by default. The harness loads them on every session start.

.mcp.json — Project-Scoped Configuration

For servers that are specific to a project, define them in .mcp.json in the project root. This file is checked into source control, so every engineer who clones the repo gets the same MCP surface:

{
  "mcpServers": {
    "project-db": {
      "type": "stdio",
      "command": "node",
      "args": ["./tools/mcp-db-server/index.js"],
      "env": {
        "DATABASE_URL": "${DATABASE_URL}"
      }
    },
    "sentry": {
      "type": "http",
      "url": "https://mcp.sentry.dev/mcp"
    }
  }
}

The ${DATABASE_URL} syntax performs environment variable interpolation at server launch time. Credentials stay out of the config file while the connection string stays in.

The --mcp-config Flag

For scripted or CI invocations, pass a config file directly:

claude -p "Analyze the error rate spike from yesterday" \
  --mcp-config ./configs/production-mcp.json

The harness connects only to servers in the provided file, ignores user-level config, and enforces a 5-second connection timeout. If a server in the config file is unreachable, the harness logs the failure and continues — it does not abort the session.

--strict-mcp-config

When you want the harness to use only the servers in --mcp-config and ignore everything else — user config, .mcp.json in the project root, all of it:

claude -p "Run security scan" \
  --mcp-config ./scan-servers.json \
  --strict-mcp-config

This is the right pattern for automated pipelines where you need deterministic tool availability. Without --strict-mcp-config, a user's personal MCP servers (memory servers, personal tools, API clients) may show up in an automated run and affect behavior in ways that are hard to reproduce.

enabledMcpjsonServers

In settings.json, you can limit which .mcp.json servers are active:

{
  "enabledMcpjsonServers": ["copilot-mem", "sec-sr-mem", "dt-mem"]
}

Servers not listed are ignored even if they appear in .mcp.json. Use this to opt in explicitly rather than inheriting every server a project defines.

deniedMcpServers

The inverse: list servers that should never be connected regardless of other configuration:

{
  "deniedMcpServers": ["untrusted-experimental-server"]
}

19.3 Tool Passthrough: McpInput and McpOutput

When Claude calls an MCP tool, the harness serializes the call arguments as McpInput and passes them to the server. The server returns McpOutput. These are the two wire types that your server must speak.

export interface McpInput {
  [k: string]: unknown;  // arbitrary JSON passthrough
}

export type McpOutput =
  | string
  | { type: string; [k: string]: unknown }[]
  | { [k: string]: unknown };

McpInput is a plain JSON object. Whatever Claude passes as tool arguments — validated against your tool's JSON Schema — arrives at your server as this object. No special wrapping; the schema is the contract.

McpOutput is deliberately loose. Three forms are valid:

  • Plain string — the most common case. Your tool returns a text result, the harness presents it as a tool result string to Claude.
  • Content block array — for tools that return structured multimedia content (text + images, text + file references). Each element has a type field ("text", "image", "resource").
  • Plain object — for tools that return structured data that Claude should interpret as-is (JSON payloads, key-value results).

In practice, most tools return plain strings. Use content block arrays only when your tool legitimately needs to return mixed content types.

Tool Call Flow

sequenceDiagram
    participant C as Claude (model)
    participant H as Harness
    participant S as MCP Server

    C->>H: tool_use: db_query({"sql": "SELECT ..."})
    H->>H: permission check
    H->>S: JSON-RPC tools/call {name: "db_query", arguments: {...}}
    S->>S: execute query
    S-->>H: {content: [{type: "text", text: "...result..."}]}
    H-->>C: tool_result: "...result..."
    C->>C: incorporate into reasoning

The permission check happens on the harness side before the call reaches the server. If you have configured --allowedTools or an allowList, MCP tool names must appear there to pass through. The naming convention is mcp__<server-name>__<tool-name>:

claude -p "Query the events table" \
  --allowedTools "mcp__project-db__db_query,mcp__project-db__db_schema"

19.4 Resources: ListMcpResources, ReadMcpResource, ReadMcpResourceDir

Resources give MCP servers a way to expose data that does not fit the request-response model of tools. A tool is called; a resource is read. The distinction matters because resources support content negotiation (MIME types), binary data handling, and directory traversal.

Listing Available Resources

export interface ListMcpResourcesInput {
  server?: string;  // filter by server name; omit to list all
}

export type ListMcpResourcesOutput = {
  uri: string;
  name: string;
  mimeType?: string;
  description?: string;
  server: string;
}[];

Calling ListMcpResources with no server argument returns every resource registered across all connected servers. With a server argument, it filters to that server:

// All resources across all servers
const all = await ListMcpResources({});

// Only resources from the memory server
const memResources = await ListMcpResources({ server: "copilot-mem" });
// Returns: [
//   { uri: "memory://profiles/auth-service", name: "Auth Service Profile", mimeType: "application/json", server: "copilot-mem" },
//   { uri: "memory://summaries/daily", name: "Daily Summaries", mimeType: "text/markdown", server: "copilot-mem" },
//   ...
// ]

Reading a Resource

export interface ReadMcpResourceInput {
  server: string;
  uri: string;
}

export interface ReadMcpResourceOutput {
  contents: {
    uri: string;
    mimeType?: string;
    text?: string;
    blobSavedTo?: string;  // binary content saved to file path
  }[];
  error?: string;
}

Text resources come back in the text field. Binary resources — images, PDFs, archives — are saved to a temporary file by the harness and the path appears in blobSavedTo. Your code should check which field is populated:

const result = await ReadMcpResource({
  server: "copilot-mem",
  uri: "memory://profiles/auth-service",
});

if (result.error) {
  throw new Error(`Resource read failed: ${result.error}`);
}

for (const content of result.contents) {
  if (content.text) {
    // Text resource — use directly
    const profile = JSON.parse(content.text);
  } else if (content.blobSavedTo) {
    // Binary resource — file at blobSavedTo path
    const data = await fs.readFile(content.blobSavedTo);
  }
}

Reading a Resource Directory

export interface ReadMcpResourceDirInput {
  server: string;
  uri: string;
}

export interface ReadMcpResourceDirOutput {
  resources: {
    uri: string;
    name: string;
    mimeType?: string;  // "inode/directory" for subdirectories
  }[];
  error?: string;
}

When a resource URI points to a container rather than a leaf, ReadMcpResourceDir returns its children:

const dir = await ReadMcpResourceDir({
  server: "project-db",
  uri: "db://tables",
});

// Returns entries like:
// { uri: "db://tables/users", name: "users", mimeType: "application/json" }
// { uri: "db://tables/events", name: "events", mimeType: "application/json" }
// { uri: "db://tables/archived", name: "archived", mimeType: "inode/directory" }

// Recurse into subdirectory
const archived = await ReadMcpResourceDir({
  server: "project-db",
  uri: "db://tables/archived",
});

The "inode/directory" MIME type signals that an entry is itself a directory. Walk it with another ReadMcpResourceDir call. This recursive pattern is how you traverse a tree of resources programmatically.

19.5 RefreshMcpTools: Hot-Reload Tool Lists

MCP servers can add, remove, or modify their tool definitions while the harness is running. Without a refresh, the harness operates with a stale capability snapshot. RefreshMcpTools forces a re-handshake with one or all servers and updates the tool registry:

export interface RefreshMcpToolsInput {
  server?: string;  // specific server to refresh; omit for all
}

export type RefreshMcpToolsOutput = {
  server: string;
  status: "refreshed" | "error" | "not_connected";
  toolCount?: number;
  added?: string[];
  removed?: string[];
  error?: string;
}[];

The output tells you what changed:

const results = await RefreshMcpTools({});
// Example output:
// [
//   {
//     server: "copilot-mem",
//     status: "refreshed",
//     toolCount: 12,
//     added: ["memory_bulk_import"],
//     removed: [],
//   },
//   {
//     server: "project-db",
//     status: "refreshed",
//     toolCount: 4,
//     added: [],
//     removed: ["db_legacy_query"],
//   },
//   {
//     server: "sentry",
//     status: "error",
//     error: "Connection timeout after 5000ms",
//   }
// ]

When to Refresh

The common case for RefreshMcpTools is during development of an MCP server. You are iterating on tool definitions — adding parameters, changing descriptions, adding new tools — and you want those changes to be visible without restarting the harness.

In production, the scenario is server-side deployments. If your MCP server is a deployed service that receives updates, the harness will not see new tools until a refresh. For long-running harness sessions (daemons, overnight runs), build in periodic refreshes or trigger them when your deployment pipeline signals a server update.

Tracking Added and Removed Tools

The added and removed arrays in the output are the diff since the last refresh. If you are building a harness that needs to adapt to capability changes — for example, a tool router that dispatches tasks differently depending on what capabilities are available — these diffs are how you detect and react:

const refreshResults = await RefreshMcpTools({ server: "my-server" });

const serverResult = refreshResults.find(r => r.server === "my-server");
if (serverResult?.added?.includes("db_bulk_export")) {
  // New bulk export tool available — update routing logic
  routingTable.set("bulk-export", "mcp__my-server__db_bulk_export");
}
if (serverResult?.removed?.includes("db_legacy_query")) {
  // Remove the old fallback path
  routingTable.delete("legacy-query");
}

19.6 OAuth Flow: RFC 9728 Discovery and Step-Up Authorization

HTTP MCP servers that require authentication use OAuth 2.0. The harness implements OAuth client logic including discovery, token acquisition, and refresh. The design follows RFC 9728 for server metadata discovery and the OAuth 2.0 flow for interactive authorization.

Discovery

When the harness connects to an HTTP MCP server, it first fetches the server's OAuth metadata at the well-known endpoint:

GET https://mcp.example.com/.well-known/oauth-authorization-server

The metadata document declares the authorization endpoint, token endpoint, supported scopes, and PKCE requirements. The harness uses this to construct the authorization flow without any server-specific hardcoding.

Initial Authorization

For servers that require auth, claude mcp login initiates the flow:

claude mcp login sentry

The harness opens a browser window to the server's authorization URL with a PKCE code challenge, waits for the redirect, exchanges the code for tokens, and stores the access token and refresh token in the system keychain. On subsequent connections, the harness attaches the access token as a Bearer header automatically.

Step-Up Authorization

Some MCP servers grant minimal-scope tokens on initial login but require additional consent for sensitive operations. This is expressed through HTTP 403 responses with insufficient_scope in the WWW-Authenticate header:

HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope",
  scope="memory:read memory:write",
  resource="https://mcp.example.com"

When the harness receives this response, it detects the insufficient_scope error and automatically initiates a step-up authorization. The flow is identical to the initial flow, but the authorization request includes the required scope. The user sees a browser prompt asking for the additional consent. Once granted, the harness retries the original tool call with the upgraded token.

From Claude's perspective, this is invisible. The tool call succeeded, just with a brief delay while the user completed the consent prompt. If the user declines step-up authorization, the tool call returns an error that Claude sees as a standard tool failure.

Token Refresh

Access tokens expire. The harness manages refresh automatically: when an API call returns 401 Unauthorized, the harness uses the stored refresh token to acquire a new access token and retries the call. If the refresh token itself is expired or revoked, the harness falls back to the full authorization flow.

# Logout (clears stored tokens)
claude mcp logout sentry

# Re-login to refresh credentials
claude mcp login sentry

19.7 _meta["anthropic/maxResultSizeChars"]: Override the 500K Limit

By default, MCP tool results are capped at a size that prevents runaway context growth. Starting in v2.1.91, tools can override this limit by returning the _meta annotation field with a maxResultSizeChars value up to 500,000 characters:

// In your MCP server, when returning large results:
return {
  content: [
    {
      type: "text",
      text: largeResultString,
    }
  ],
  _meta: {
    "anthropic/maxResultSizeChars": 500000
  }
};

This is an opt-in per-call declaration, not a server-level setting. The server signals "I know this result is large; I am intentionally returning it at this size." Without the annotation, large results are truncated.

When to Use This

The annotation exists for tools that legitimately produce large outputs: a full database dump, a complete log file, a compiled asset. The 500K character limit is approximately 125,000 tokens — well above what most Claude models can effectively process in a single context window. Use this judiciously.

The anti-pattern is using maxResultSizeChars as a workaround for poorly designed tools. If your tool regularly hits the default limit, the better fix is pagination — add a cursor parameter and return results in chunks — rather than raising the cap. A tool that returns 400K characters of log output is probably not serving Claude well; a tool that returns the last 100 lines with a continuation cursor is.

Tool descriptions are also relevant here: v2.1.92 caps tool descriptions at 2KB. If you are writing MCP tool descriptions that approach that limit, you are almost certainly over-explaining. Keep descriptions under 500 characters; the JSON Schema handles the structural specification.

19.8 MCP_CONNECTION_NONBLOCKING=true: Skip Connection Wait in -p Mode

When Claude Code runs in non-interactive mode (-p), it waits for all configured MCP servers to connect before processing the prompt. This is the safe default — you want your tools available when the prompt executes — but it adds latency proportional to the number of configured servers.

For pipelines where you know which servers you need, or where some servers are optional for the current task, set MCP_CONNECTION_NONBLOCKING=true:

MCP_CONNECTION_NONBLOCKING=true claude -p "Summarize the last 24 hours of activity" \
  --mcp-config ./minimal-servers.json

With this flag, the harness starts processing the prompt immediately without waiting for server connections to complete. Servers connect in the background. If a tool call arrives before the target server has connected, the call is queued until the connection is ready, or fails with a timeout error if the server never connects.

This is particularly useful in CI environments where startup latency compounds across many pipeline steps. The combination of --mcp-config (to specify exactly which servers you need), --strict-mcp-config (to ignore everything else), and MCP_CONNECTION_NONBLOCKING=true (to not wait for connections) gives you a tight, fast-starting harness invocation.

The --mcp-config timeout is bounded at 5 seconds — servers that have not connected within 5 seconds of being configured are considered failed connections and their tools are unavailable for that run.

19.9 claude mcp serve: Expose Claude Code as an MCP Server

The harness can expose itself as an MCP server:

# Serve in foreground (useful for development/testing)
claude mcp serve

# Serve as background daemon
claude mcp serve -d

This makes Claude Code's tools — Read, Bash, Edit, Glob, Grep, Agent, and all configured MCP tools — available to any MCP client that connects. The use case is composing Claude Code into larger systems: a parent orchestrator that speaks MCP can delegate to a Claude Code instance as one of its capability providers.

The pattern appears in multi-tier architectures where a lightweight routing agent dispatches work to specialized worker agents, each of which is a Claude Code instance serving MCP. The router does not know or care that it is talking to Claude Code; from its perspective, it is calling MCP tools that happen to be backed by a full agentic harness.

graph TD
    O[Orchestrator Agent<br/>lightweight MCP client] -->|MCP tools/call| W1[Claude Code Worker 1<br/>claude mcp serve<br/>tools: filesystem + shell]
    O -->|MCP tools/call| W2[Claude Code Worker 2<br/>claude mcp serve<br/>tools: web + research]
    O -->|MCP tools/call| W3[Claude Code Worker 3<br/>claude mcp serve<br/>tools: database + analytics]
    W1 --> FS[Filesystem + Git]
    W2 --> WEB[Web APIs]
    W3 --> DB[Database]

In this topology, the orchestrator manages task routing and result synthesis while each Claude Code worker handles a domain-specific subset of the work. The workers are independently restartable, replaceable, and upgradeable without touching the orchestrator.

19.10 Real MCP Servers: copilot-mem at Scale

The copilot-mem memory server is a concrete example of what production MCP looks like at scale. At the time of writing:

  • 1,035 total memories across three types: episodic (26), procedural (324), semantic (685)
  • By category: fact (350), workflow (228), project (231), preference (30), decision (26), architecture (33), tech_insight (21), workflow_recipe (24), bug_recipe (15), and several smaller categories
  • 14 project profiles — structured summaries of each active project's goals, architecture, and current status
  • 2,627 knowledge links — semantic edges connecting related memories
  • 35MB SQLite database with full-text search
  • 119 daily summaries — auto-generated end-of-day digests

This memory server exposes 12 MCP tools including memory_search, memory_store, memory_recall_context, memory_get_profile, and memory_list_recent. It exposes resources under memory:// URIs: individual memory records, daily summaries, and project profiles.

The scale numbers illustrate why the MCP resource model matters. A memory server with 1,035 entries cannot be loaded into context wholesale — that would consume a significant fraction of a model's context window before any actual work begins. The resource model solves this: the harness can ListMcpResources to see what exists, read specific resources by URI when needed, and search via tool calls to find relevant memories. The data lives in the server; only what is needed flows into context.

Tool Description Quality at Scale

At 12 tools and 35MB of backing data, description quality becomes a navigation problem. Claude uses tool descriptions to decide which tool to call for a given intent. Ambiguous or overlapping descriptions cause the model to call the wrong tool, waste a round trip, and have to recover. For the memory server, the tool descriptions are tuned to avoid overlap:

  • memory_search — full-text semantic search, returns ranked results
  • memory_recall_context — retrieves memories most relevant to the current task context, no explicit query needed
  • memory_store — creates a new memory record
  • memory_get_profile — retrieves a specific project profile by name

The distinction between memory_search (explicit query) and memory_recall_context (implicit, based on current context) is one that required iteration to get right. The first version described both as "retrieves relevant memories," which caused consistent misrouting. Concrete, specific descriptions at the level of how the tool is invoked — not just what it returns — are what make MCP tools usable at scale.

19.11 Lab: Build an MCP Server Exposing a Database

This lab builds a complete MCP server that exposes a SQLite database as both tools (for querying) and resources (for schema and metadata). The server is written in Node.js using the official @modelcontextprotocol/sdk package. By the end, you will be able to point Claude Code at it and have Claude query and analyze the database using natural language.

Setup

mkdir mcp-db-server && cd mcp-db-server
npm init -y
npm install @modelcontextprotocol/sdk better-sqlite3
npm install --save-dev @types/better-sqlite3 typescript tsx

The Server

src/index.ts:

import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import {
  CallToolRequestSchema,
  ListResourcesRequestSchema,
  ListToolsRequestSchema,
  ReadResourceRequestSchema,
} from "@modelcontextprotocol/sdk/types.js";
import Database from "better-sqlite3";
import { join } from "path";

const DB_PATH = process.env.DATABASE_PATH ?? join(process.cwd(), "data.db");

// Initialize database with sample data if it doesn't exist
function initDb(db: Database.Database): void {
  db.exec(`
    CREATE TABLE IF NOT EXISTS events (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      name TEXT NOT NULL,
      occurred_at TEXT NOT NULL,
      severity TEXT CHECK(severity IN ('low', 'medium', 'high', 'critical')),
      payload TEXT
    );

    CREATE TABLE IF NOT EXISTS users (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      email TEXT UNIQUE NOT NULL,
      created_at TEXT NOT NULL,
      last_seen TEXT
    );
  `);

  const eventCount = (db.prepare("SELECT COUNT(*) as c FROM events").get() as { c: number }).c;
  if (eventCount === 0) {
    const insert = db.prepare(
      "INSERT INTO events (name, occurred_at, severity, payload) VALUES (?, ?, ?, ?)"
    );
    insert.run("user.login", "2026-07-28T08:00:00Z", "low", '{"user_id": 1}');
    insert.run("auth.failure", "2026-07-28T08:05:00Z", "high", '{"user_id": null, "ip": "10.0.0.1"}');
    insert.run("db.query_slow", "2026-07-28T08:10:00Z", "medium", '{"duration_ms": 4200}');
    insert.run("deploy.complete", "2026-07-28T09:00:00Z", "low", '{"version": "2.1.91"}');
    insert.run("auth.failure", "2026-07-28T09:05:00Z", "critical", '{"user_id": null, "ip": "10.0.0.1", "attempts": 50}');
  }
}

function createServer(db: Database.Database): Server {
  const server = new Server(
    { name: "mcp-db-server", version: "1.0.0" },
    {
      capabilities: {
        tools: {},
        resources: {},
      },
    }
  );

  // ── List tools ────────────────────────────────────────────────────────────
  server.setRequestHandler(ListToolsRequestSchema, async () => ({
    tools: [
      {
        name: "db_query",
        description:
          "Execute a read-only SQL SELECT query against the database. Returns rows as JSON.",
        inputSchema: {
          type: "object",
          properties: {
            sql: {
              type: "string",
              description: "The SQL SELECT query to execute. Only SELECT is permitted.",
            },
            limit: {
              type: "number",
              description: "Maximum rows to return (default 100, max 1000).",
            },
          },
          required: ["sql"],
        },
      },
      {
        name: "db_schema",
        description:
          "Returns the schema (CREATE TABLE statements) for all tables in the database.",
        inputSchema: {
          type: "object",
          properties: {},
        },
      },
      {
        name: "db_table_stats",
        description: "Returns row count and size estimate for each table.",
        inputSchema: {
          type: "object",
          properties: {
            table: {
              type: "string",
              description: "Specific table name (optional — omit for all tables).",
            },
          },
        },
      },
    ],
  }));

  // ── Handle tool calls ─────────────────────────────────────────────────────
  server.setRequestHandler(CallToolRequestSchema, async (request) => {
    const { name, arguments: args } = request.params;

    if (name === "db_query") {
      const sql = (args?.sql as string) ?? "";
      const limit = Math.min((args?.limit as number) ?? 100, 1000);

      // Enforce read-only: reject anything that isn't SELECT
      const normalized = sql.trim().toUpperCase();
      if (!normalized.startsWith("SELECT")) {
        return {
          content: [{ type: "text", text: "Error: only SELECT queries are permitted." }],
          isError: true,
        };
      }

      try {
        const limitedSql = `SELECT * FROM (${sql}) LIMIT ${limit}`;
        const rows = db.prepare(limitedSql).all();
        return {
          content: [
            {
              type: "text",
              text: JSON.stringify(rows, null, 2),
            },
          ],
        };
      } catch (err) {
        return {
          content: [{ type: "text", text: `Query error: ${(err as Error).message}` }],
          isError: true,
        };
      }
    }

    if (name === "db_schema") {
      const rows = db
        .prepare(
          `SELECT name, sql FROM sqlite_master WHERE type = 'table' AND name NOT LIKE 'sqlite_%'`
        )
        .all() as { name: string; sql: string }[];

      const schema = rows.map((r) => r.sql).join("\n\n");
      return {
        content: [{ type: "text", text: schema }],
      };
    }

    if (name === "db_table_stats") {
      const targetTable = args?.table as string | undefined;

      const tables = targetTable
        ? [targetTable]
        : (
            db
              .prepare(
                `SELECT name FROM sqlite_master WHERE type = 'table' AND name NOT LIKE 'sqlite_%'`
              )
              .all() as { name: string }[]
          ).map((r) => r.name);

      const stats = tables.map((t) => {
        const count = (
          db.prepare(`SELECT COUNT(*) as c FROM "${t}"`).get() as { c: number }
        ).c;
        return { table: t, row_count: count };
      });

      return {
        content: [{ type: "text", text: JSON.stringify(stats, null, 2) }],
      };
    }

    return {
      content: [{ type: "text", text: `Unknown tool: ${name}` }],
      isError: true,
    };
  });

  // ── List resources ────────────────────────────────────────────────────────
  server.setRequestHandler(ListResourcesRequestSchema, async () => {
    const tables = (
      db
        .prepare(
          `SELECT name FROM sqlite_master WHERE type = 'table' AND name NOT LIKE 'sqlite_%'`
        )
        .all() as { name: string }[]
    ).map((r) => r.name);

    const resources = [
      // Schema root directory
      {
        uri: "db://schema",
        name: "Schema Overview",
        mimeType: "application/json",
        description: "Database schema summary with all table definitions.",
      },
      // Per-table resources
      ...tables.map((t) => ({
        uri: `db://tables/${t}`,
        name: `Table: ${t}`,
        mimeType: "application/json",
        description: `Column definitions and sample rows from ${t}.`,
      })),
    ];

    return { resources };
  });

  // ── Read resource ─────────────────────────────────────────────────────────
  server.setRequestHandler(ReadResourceRequestSchema, async (request) => {
    const { uri } = request.params;

    if (uri === "db://schema") {
      const tables = (
        db
          .prepare(
            `SELECT name, sql FROM sqlite_master WHERE type = 'table' AND name NOT LIKE 'sqlite_%'`
          )
          .all() as { name: string; sql: string }[]
      );

      const schema: Record<string, unknown> = {};
      for (const t of tables) {
        const cols = db.prepare(`PRAGMA table_info("${t.name}")`).all();
        schema[t.name] = { definition: t.sql, columns: cols };
      }

      return {
        contents: [
          {
            uri,
            mimeType: "application/json",
            text: JSON.stringify(schema, null, 2),
          },
        ],
      };
    }

    const tableMatch = uri.match(/^db:\/\/tables\/(\w+)$/);
    if (tableMatch) {
      const tableName = tableMatch[1];

      const columns = db.prepare(`PRAGMA table_info("${tableName}")`).all();
      const sample = db.prepare(`SELECT * FROM "${tableName}" LIMIT 5`).all();
      const count = (
        db.prepare(`SELECT COUNT(*) as c FROM "${tableName}"`).get() as { c: number }
      ).c;

      const payload = { table: tableName, row_count: count, columns, sample_rows: sample };

      return {
        contents: [
          {
            uri,
            mimeType: "application/json",
            text: JSON.stringify(payload, null, 2),
          },
        ],
      };
    }

    return {
      contents: [],
      error: `Unknown resource URI: ${uri}`,
    };
  });

  return server;
}

async function main(): Promise<void> {
  const db = new Database(DB_PATH);
  initDb(db);

  const server = createServer(db);
  const transport = new StdioServerTransport();

  await server.connect(transport);

  // Keep alive until stdin closes
  process.stdin.resume();
  process.on("SIGINT", () => {
    db.close();
    process.exit(0);
  });
}

main().catch((err) => {
  process.stderr.write(`Fatal: ${err.message}\n`);
  process.exit(1);
});

Claude will call db_schema to understand the structure, then db_query with appropriate SELECT statements, and db_table_stats for the row counts. The read-only enforcement on the server side means Claude cannot accidentally drop a table or modify data regardless of what the prompt contains.

The db://tables/events resource returns column definitions and sample rows — useful for Claude to understand the data shape before constructing queries.

Extending the Server

The server above handles the core patterns. From here you can extend it:

Add pagination — add a cursor parameter to db_query that encodes the last-seen id. Return a next_cursor in the result when more rows are available. This is the correct alternative to raising maxResultSizeChars.

Add write tools with confirmation — expose db_execute for INSERT/UPDATE/DELETE, but require an explain: string parameter that forces the caller to articulate what the change will do. Log all write operations to an audit table.

Add streaming resources — for tables with millions of rows, expose paginated resources: db://tables/events/page/1, db://tables/events/page/2. The ReadMcpResourceDir call on db://tables/events returns the page listing; individual page reads return data in chunks.

Expose views as resources — create SQL views for common analytical queries (daily event counts, top error codes, user activity summaries) and expose them as resources. Claude can read a pre-computed view for summarization tasks instead of constructing ad hoc queries.

Summary

MCP is the integration layer that turns Claude Code from a self-contained harness into a network-connected capability aggregator. The key behaviors to internalize:

  • Tools and resources are two distinct models: tools are called, resources are read. Choose based on whether the data is request-response or addressable content.
  • The _meta["anthropic/maxResultSizeChars"] annotation is an opt-in, per-call override for large results — not a substitute for pagination.
  • RefreshMcpTools is how you pick up server-side capability changes without restarting the harness. Build refresh into your deployment pipeline.
  • OAuth step-up is transparent to Claude — the harness handles consent prompts and token refresh automatically.
  • --strict-mcp-config + MCP_CONNECTION_NONBLOCKING=true is the production recipe for fast, deterministic pipeline invocations.
  • claude mcp serve exposes Claude Code as an MCP server, enabling multi-tier architectures where Claude Code instances are workers behind a routing orchestrator.
  • At scale (1,000+ memories, 14 project profiles), the resource model's value becomes concrete: data lives in the server, context contains only what is needed.

The database lab is a complete pattern that covers the full MCP lifecycle: capability declaration, tool enforcement (read-only), resource hierarchy, error handling, and server registration. The same structure — tools for operations, resources for schema and data discovery — applies to any backend you want to expose to Claude.
