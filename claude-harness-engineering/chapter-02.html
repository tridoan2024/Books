Chapter 2: Configuration Architecture

Every tool you use to control Claude Code — every permission rule, every model override, every key binding — lives in a configuration layer. Understanding where values come from and in what order they win is the difference between a harness that behaves predictably and one that surprises you in production. This chapter maps the full configuration architecture from first principles, using verified examples drawn from a real working setup.

2.1 The Settings Cascade

Claude Code resolves configuration through five overlapping layers, each capable of overriding the last. Resolution happens at startup; the merged result drives runtime behavior for the entire session.

~/.claude/settings.json          (1) Global — machine-wide defaults
.claude/settings.json            (2) Project — team-shared, checked into git
.claude/settings.local.json      (3) Local — personal overrides, gitignored
managed settings (MDM/policy)    (4) Enterprise-managed, read-only from user perspective
CLI flags                        (5) Session-only overrides, highest priority

The cascade is last-write-wins for scalar values and union for arrays (notably permission lists). That means if global sets effortLevel: "high" and local sets effortLevel: "xhigh", the session runs at xhigh. If global sets a deny rule and local adds additional allow rules, both are active.

Why five layers?

Each layer serves a distinct stakeholder:

LayerOwnerPurposeChecked into git?
Global (~/.claude/settings.json)Individual engineerPersonal defaults, machine-specific toolingNo
Project (.claude/settings.json)TeamShared permissions, hooks, project rulesYes
Local (.claude/settings.local.json)Individual engineerOverrides for the current project onlyNo (gitignore it)
ManagedIT/securityNon-negotiable enterprise policyN/A
CLI flagsSessionOne-off experiments, CI overridesN/A

The split between global and local is the key design point: your personal preferences (model choice, thinking mode, plugin list) belong at global scope; your project-specific personal additions (MCP server enablement, per-project defaultMode) belong in the local file. The project file is the only one other humans read, so it should contain only what the whole team agrees on.

The local file in practice

.claude/settings.local.json accumulates fast. It is the file Claude Code writes to when you confirm a new one-time permission at the prompt. After a few months on a large codebase, it will contain hundreds of granular Bash(...) allow entries — each one granted by you interactively during a prior session. This is intentional: the runtime never silently broadens its own permissions, and the paper trail lives here.

Add .claude/settings.local.json to .gitignore. If you commit it by accident, other engineers will inherit your personal permission grants.

2.2 The Settings JSON Schema

Every settings file should carry a $schema header:

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json"
}

This is not decoration. Your editor (VS Code, Neovim with LSP, IntelliJ) will load the schema and give you:

  • Autocomplete on every key name
  • Type validation (catches "effortLevel": "very-high" before runtime does)
  • Documentation on hover — useful when you can't remember whether the field is effortLevel or effort_level

The schema is published at SchemaStore, which most editors poll automatically. If your editor does not, add the URL manually to your JSON schema associations.

Schema validation at runtime

Claude Code validates settings at startup. A malformed settings file causes a startup warning, not a silent ignore. If you see unexpected behavior after editing a settings file, run claude doctor — it will surface schema violations.

2.3 Permission Rules

The permissions block is the most consequential part of your configuration. It controls what Claude can do without asking you.

The allow/deny structure

{
  "permissions": {
    "allow": ["Bash(*)", "Read(*)", "Edit(*)", "Write(*)"],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./**/*.pem)",
      "Read(~/.ssh/*)"
    ]
  }
}

Rules are evaluated in order: deny rules take precedence over allow rules. If Read(*) is in the allow list and Read(./.env) is in the deny list, .env is blocked regardless of position.

Glob syntax

The argument inside the parentheses is a glob pattern matched against the tool's primary argument. Each tool type interprets the pattern differently:

RuleMatches
Bash(*)Any shell command
Bash(git *)Any git subcommand
Bash(git commit*)git commit and git commit -m "..."
Edit(/src/**)Any file under /src/ recursively
Read(/path/to/file.txt)That exact file
Read(./**/*.pem)Any .pem file anywhere under the current directory
Read(~/.ssh/*)Any file directly inside ~/.ssh/

The ** glob crosses directory boundaries. The * glob does not. Bash(git *) would not match git commit -am "fix" because the space and -am are part of the argument — Bash(git*) matches the string starting with git, while Bash(git *) matches the literal prefix git followed by anything.

Real deny list: protecting secrets

Here is the deny list from the project settings for this workspace:

"deny": [
  "Read(./.env)",
  "Read(./.env.*)",
  "Read(./token.json)",
  "Read(./temp_cert.pem)",
  "Read(./temp_key.pem)",
  "Read(./*credentials*)",
  "Read(./*secret*)",
  "Read(./**/*.pem)",
  "Read(./**/*_key)",
  "Read(./**/*_secret*)",
  "Read(~/.config/gcloud/*credentials*)",
  "Read(~/.config/gcloud/*token*)",
  "Read(~/.azure/*)",
  "Read(~/.aws/credentials)",
  "Read(~/.aws/config)",
  "Read(~/.ssh/*)",
  "Read(~/.gnupg/*)"
]

This pattern catches the common credential locations across cloud providers (AWS, GCP, Azure), SSH, PGP, and the ubiquitous .env family. Copy this as a baseline for any project that handles real credentials.

defaultMode

The permissions.defaultMode field controls how unrecognized tool calls are handled:

ModeBehavior
defaultAsk for permission on each new tool/argument pattern
acceptEditsAuto-accept file edits, ask for everything else
autoAuto-approve anything not explicitly denied
bypassPermissionsSkip all permission checks (dangerous)
planNever execute — only plan and describe
dontAskExecute without prompting but respect deny list

In production harnesses, auto paired with a tight deny list gives you autonomy with guardrails. The default mode is appropriate for exploratory sessions where you want to approve each new capability as it is needed — and each approval accumulates in settings.local.json.

allowManagedPermissionRulesOnly

Enterprise environments can set this flag to true to prevent any locally-configured permission rules from taking effect. Only rules delivered via the managed settings layer (MDM, policy server) apply. Use this when you need to guarantee that engineers cannot accidentally or deliberately widen the permission surface.

2.4 Environment Variables

Claude Code exposes a significant amount of tunable behavior through environment variables. These live in the env block of any settings file, which means you can apply them per-scope — different token limits for CI vs. interactive sessions.

Token budget variables

VariablePurposeTypical value
CLAUDE_CODE_MAX_CONTEXT_TOKENSTotal context window budget1000000 (1M for claude-opus-4 class models)
CLAUDE_CODE_MAX_OUTPUT_TOKENSMax tokens per response128000
MAX_THINKING_TOKENSBudget for extended thinking100000

These three variables form the token economy of your session. The context limit caps how much conversation history, file content, and tool output can accumulate before the runtime triggers auto-compaction. The output limit caps how long any single response can be. The thinking limit caps how much chain-of-thought the model can generate when alwaysThinkingEnabled is true.

A concrete example: the global settings for this workspace set all three:

"env": {
  "CLAUDE_CODE_MAX_OUTPUT_TOKENS": "128000",
  "CLAUDE_CODE_MAX_CONTEXT_TOKENS": "1000000",
  "MAX_THINKING_TOKENS": "100000"
}

Tool concurrency and retry variables

VariablePurposeTypical value
CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCYParallel tool calls per turn8
CLAUDE_CODE_MAX_RETRIESAPI retry count on transient errors5
CLAUDE_CODE_IDLE_THRESHOLD_MINUTESMinutes of idle before session warning180
CLAUDE_CODE_IDLE_TOKEN_THRESHOLDToken count at which idle check matters500000

CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY is particularly important for workflow-heavy harnesses. The runtime will dispatch up to N tool calls in parallel when the model requests them in the same turn. Setting this too low throttles multi-agent workflows unnecessarily; setting it too high can cause resource contention on machines with limited CPU or network bandwidth.

Tool search and MCP variables

VariablePurposeValues
ENABLE_TOOL_SEARCHWhether deferred tools are loaded on demand"true", "false", "auto"
ENABLE_MCP_LARGE_OUTPUT_FILESWrite large MCP outputs to temp files"1"
MCP_CONNECTION_NONBLOCKINGSkip MCP connection wait in -p mode"true"

ENABLE_TOOL_SEARCH with the value "auto" means the runtime decides at startup based on available context budget. When set to "true", the ToolSearch tool is always available and the full 52+ tool surface can be discovered on demand without loading all tool schemas into the system prompt upfront.

Infrastructure and debugging variables

VariablePurpose
DISABLE_TELEMETRYOpt out of usage telemetry
CLAUDE_ENABLE_STREAM_WATCHDOGRestart stalled streaming connections
CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMSNumber of agent team slots (integer)
CLAUDE_CODE_TEAMMATE_COMMANDShell command to dispatch teammates

CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS enables the agent team feature. Setting it to 3 provisions three teammate slots that can be dispatched from the chat interface. CLAUDE_CODE_TEAMMATE_COMMAND is the script that handles teammate launch — in a tmux-based setup, this is the entry point that creates a new pane and starts the teammate process.

2.5 Model Configuration

Model behavior is controlled through three complementary settings: which model to use, how hard it should think, and whether it should optimize for speed.

Model selection

The model field accepts a short alias or a full model identifier:

{ "model": "sonnet" }

Short aliases resolve to the latest version of that tier: opus, sonnet, haiku. Full identifiers pin exact versions: claude-opus-4-8, claude-sonnet-4-6, claude-haiku-4-5. For production harnesses, pin full identifiers in your project settings so that model updates do not silently change behavior. Use short aliases in global settings for interactive development where you always want the latest.

Effort levels

The effortLevel field controls the model's reasoning depth, which maps roughly to how much computation (and cost) the model spends per response:

LevelUse case
lowTriage, routing, classification — fast and cheap
mediumStandard development tasks
highComplex implementation, debugging
xhighArchitectural decisions, security review
maxMaximum available — research, critical analysis

high is the right default for an engineering harness. max is appropriate for agents doing security audit or architectural review where missing a detail is expensive. low is appropriate for agents doing repetitive mechanical work (file categorization, format conversion).

The --effort CLI flag overrides effortLevel for a single session without touching the settings file.

Fast mode

{ "fastMode": true }

Fast mode uses the same model at reduced latency — the model generates output more quickly at some cost to deliberateness. For interactive development where you are iterating rapidly, fast mode reduces friction significantly. For autonomous agents running overnight, turn it off and let the model take its time.

The /fast slash command toggles fast mode within a running session.

Extended thinking

{ "alwaysThinkingEnabled": true }

When enabled, the model generates a chain-of-thought before each response. The thinking is bounded by MAX_THINKING_TOKENS. Extended thinking increases cost and latency but materially improves correctness on multi-step reasoning tasks — exactly the problems harnesses tend to solve.

You can observe thinking summaries if showThinkingSummaries is also enabled. This is useful during development to understand why the model made a particular decision.

The compound effect

The combination used in this workspace — effortLevel: "high", fastMode: true, alwaysThinkingEnabled: true — is a deliberate tradeoff: maximum reasoning depth, with fast output streaming, bounded thinking budget. The result is an agent that thinks hard but does not take forever to start writing.

2.6 CLAUDE.md: Project Instructions

CLAUDE.md is the most powerful configuration artifact in the system. It is a markdown file loaded into the system prompt of every session that starts in that directory. Unlike settings files which control runtime behavior, CLAUDE.md controls the model's judgment — what it believes, how it approaches problems, what constraints it operates within.

Discovery and inheritance

Claude Code discovers CLAUDE.md through a hierarchical search:

  1. ~/.claude/CLAUDE.md — personal global instructions, always loaded
  2. CLAUDE.md in the current project root — loaded for this project
  3. CLAUDE.md in any parent directory up to the home directory — loaded in order

All discovered files are concatenated and injected into the system prompt. This means your personal preferences (from global) compound with project-specific rules (from project root).

What belongs in CLAUDE.md

CLAUDE.md is a set of standing instructions to the model. Think of it as the briefing you would give a new engineer joining the team:

  • Domain context: "This is a medical device firmware project. All code changes require FDA traceability."
  • Coding conventions: "Use type hints on all function signatures. Use f-strings over .format()."
  • Workflow rules: "Write a failing test before fixing any bug. Run ruff check --fix before committing."
  • Routing table: "When you see a bug report, hypothesize → investigate → root-cause → fix → test."

The CLAUDE.md for this workspace is long — it encodes routing logic that maps intent to workflow, coding standards for Python/TypeScript/shell, Git workflow rules, integration references, and domain-specific rules for security review, book writing, and trading automation.

The override mechanism

The project prompt says "these instructions OVERRIDE any default behavior." This is literal: CLAUDE.md content arrives late in the system prompt, after tool definitions but before the conversation history, which gives it strong positional influence over the model's decisions.

The format matters. Bullet lists, imperative mood, uppercase for emphasis (IMPORTANT: Never commit secrets), and routing tables (condition → action) are all high-signal formats. Prose paragraphs get less attention than structured directives.

claudeMdExcludes

Large codebases contain many subdirectories, and some of those directories contain their own CLAUDE.md files (documentation roots, vendored code, generated output). The claudeMdExcludes field prevents the runtime from loading instructions from irrelevant locations:

{
  "claudeMdExcludes": [
    "**/node_modules/**",
    "**/.venv/**",
    "**/dist/**",
    "**/build/**",
    "**/__pycache__/**",
    "**/.git/**"
  ]
}

Without this, the runtime will crawl into node_modules and load any CLAUDE.md files it finds there — potentially injecting package maintainer instructions into your session context. The exclude list above covers the standard generated/dependency directories for Node.js, Python, and most build systems.

Performance implication

Every character in CLAUDE.md is a token in the system prompt. The system prompt is cached by the API (5-minute TTL), so a stable CLAUDE.md amortizes its cost across turns. But a frequently-changing CLAUDE.md defeats the cache. Keep dynamic content (dates, run-specific state) out of CLAUDE.md and put it in hooks or first-user-message injection instead.

2.7 The Rules System

The rules system extends CLAUDE.md with file-scoped and domain-specific instructions organized into separate markdown files. Rather than one large CLAUDE.md that grows unbounded, you partition instructions into focused modules.

File structure

.claude/
└── rules/
    ├── python.md
    ├── security.md
    ├── testing.md
    ├── shell.md
    └── book-writing.md

Files in .claude/rules/ are imported into the session via @.claude/rules/filename.md directives in CLAUDE.md. Each file is a focused ruleset for one domain.

File-scoped activation with paths: frontmatter

Rules files support YAML frontmatter with a paths: key that restricts when the rule is injected:

---
paths:
  - "src/**/*.py"
  - "tests/**/*.py"
---

# Python Rules

Use type hints on all function signatures...

With this frontmatter, the Python rules are only injected into the system prompt when the session involves files matching those glob patterns. This is the mechanism that prevents Python style rules from polluting sessions focused on TypeScript or shell scripts.

A rules file without paths: frontmatter is always loaded — it is unconditional.

What makes a good rules file

The rules files in this workspace are terse and prescriptive. Compare the testing rules:

# Testing Rules

## Approach
- Write tests for new features and bug fixes
- For bug fixes: write a failing test FIRST, then fix the bug
- Prefer running single tests over full suite for speed during development
- Run full suite before committing

## Python Testing
- Framework: `pytest` with `pytest-asyncio` for async code
- Use fixtures for setup/teardown, not setUp/tearDown methods
- Use `tmp_path` fixture for filesystem tests
- Integration tests hit real services — never mock databases unless explicitly asked
- Name tests: `test_<what>_<condition>_<expected>`

Every line is an instruction, not an explanation. The model does not need to understand why — it needs to know what. Keep explanations minimal; save them for when a rule is counterintuitive and the model is likely to second-guess it.

Rules vs. CLAUDE.md

CLAUDE.md is the orchestration layer — routing logic, meta-instructions, project context. Rules files are the domain-specific codebooks. The split keeps CLAUDE.md readable and rules files focused. A senior engineer reading the project should be able to understand the overall workflow from CLAUDE.md in two minutes and then look up specific domain rules when needed.

2.8 Keybindings

.claude/keybindings.json maps keyboard shortcuts to named actions within the Claude Code TUI. The file is organized by context — each context is a named UI state that has its own binding namespace.

File structure

  "$docs": "https://docs.anthropic.com/en/docs/claude-code/keybindings",

Design guidance for keybindings

Bind high-frequency operations. ctrl+x ctrl+k (kill agents) earns its chord because when you need to kill agents, you need to do it fast. ctrl+g (external editor) is valuable if you frequently write long prompts — it opens your $EDITOR, gives you full editing power, and sends on save.

Avoid overriding bindings that your terminal emulator uses. ctrl+c, ctrl+z, ctrl+d are reserved. The meta+ prefix (Option on macOS, Alt on Linux) is safer for application-level bindings that should not conflict with shell readline.

2.9 Lab: Design a Complete Settings Stack for a Multi-Team Enterprise Project

This lab walks through designing a production-grade configuration stack for a hypothetical company: three teams (backend, frontend, security), a shared platform repo, and an IT security team that enforces policy.

The scenario

  • Platform monorepo: Python backend, TypeScript frontend, infrastructure-as-code
  • Three teams each have different tool access needs
  • Security team must be able to audit all AI-assisted changes
  • IT mandates that Claude cannot read cloud credentials or private keys
  • All teams want Claude running autonomously during CI/CD pipelines

Layer design

Layer 1 — Global (~/.claude/settings.json): Each engineer sets their personal preferences. No permissions here — permissions belong to the project layer and below.

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "model": "sonnet",
  "effortLevel": "high",
  "fastMode": true,
  "alwaysThinkingEnabled": true,
  "autoMemoryEnabled": true,
  "cleanupPeriodDays": 90,
  "env": {
    "CLAUDE_CODE_MAX_OUTPUT_TOKENS": "64000",
    "CLAUDE_CODE_MAX_CONTEXT_TOKENS": "500000",
    "MAX_THINKING_TOKENS": "50000",
    "ENABLE_TOOL_SEARCH": "auto"
  }
}

Engineers on Opus-tier billing can set "model": "opus" and "effortLevel": "max" here without affecting teammates.

Layer 2 — Project (.claude/settings.json): Committed to git, reviewed in PRs. Establishes the baseline permission surface and shared tooling.

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(git *)",
      "Bash(make *)",
      "Bash(npm run *)",
      "Bash(pytest *)",
      "Bash(ruff *)",
      "Read(*)",
      "Edit(/src/**)",
      "Edit(/tests/**)",
      "Write(/src/**)",
      "Write(/tests/**)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./**/*.pem)",
      "Read(./**/*_key)",
      "Read(~/.aws/*)",
      "Read(~/.azure/*)",
      "Read(~/.ssh/*)",
      "Bash(git push *)",
      "Bash(rm -rf *)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit",
        "hooks": [
          {
            "type": "command",
            "command": "./.claude/hooks/audit-log.sh",
            "timeout": 2000
          }
        ]
      }
    ],
    "SessionStart": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "./.claude/hooks/session-setup.sh",
            "timeout": 5000
          }
        ]
      }
    ]
  },
  "claudeMdExcludes": [
    "**/node_modules/**",
    "**/.venv/**",
    "**/dist/**",
    "**/build/**",
    "**/__pycache__/**"
  ],
  "worktree": {
    "symlinkDirectories": ["node_modules", ".venv"]
  },
  "attribution": {
    "commit": "Co-Authored-By: Claude AI <noreply@anthropic.com>",
    "pr": "Generated with [Claude Code](https://claude.ai/claude-code)"
  }
}

Key decisions in this layer:

  • Bash(git push *) is denied — Claude can stage and commit but humans push. This is a deliberate gate.
  • Edit() is scoped to /src/** and /tests/** — Claude cannot edit infrastructure or deployment configs without explicit expansion.
  • The PostToolUse hook fires an audit logger after every edit — the security team reads this log.

Layer 3 — Local (.claude/settings.local.json): Each engineer's personal expansion. The security team member might add:

{
  "permissions": {
    "allow": [
      "Read(./.secret-scanning/**)",
      "Bash(trivy *)",
      "Bash(semgrep *)"
    ],
    "defaultMode": "auto"
  },
  "enabledMcpjsonServers": ["sec-sr-mem"]
}

The backend engineer adds:

{
  "permissions": {
    "allow": [
      "Bash(psql *)",
      "Bash(alembic *)"
    ],
    "defaultMode": "auto"
  }
}

The frontend engineer adds:

{
  "permissions": {
    "allow": [
      "Bash(vite *)",
      "Bash(vitest *)"
    ],
    "defaultMode": "auto"
  }
}

Each engineer has exactly the tools they need and no more. The shared deny list from the project layer still applies to everyone.

Layer 4 — Managed: IT delivers policy via MDM. This layer sets allowManagedPermissionRulesOnly: false (team can add to it) but adds non-negotiable additional deny rules for compliance:

{
  "permissions": {
    "deny": [
      "Read(~/.config/gcloud/**)",
      "Bash(curl * | bash *)",
      "Bash(wget * | bash *)"
    ]
  }
}

The pipe-to-bash patterns are a common attack vector in supply chain scenarios. The managed layer ensures no one can accidentally allow them.

Layer 5 — CI flags: The CI pipeline runs Claude in print mode with explicit overrides:

claude -p \
  --output-format stream-json \
  --model claude-sonnet-4-6 \
  --permission-mode auto \
  "Review these changes for correctness and security issues"

The --permission-mode auto flag makes CI non-interactive while still respecting the project deny list.

CLAUDE.md structure for the multi-team repo

The project CLAUDE.md encodes routing logic that applies to everyone:

# Platform Monorepo

## Routing
- Bug fix → Debug workflow: hypothesize → investigate → write failing test → fix → verify
- Feature → Implement: plan if >3 files, code directly otherwise
- PR review → Security audit: OWASP/CWE scan, risk table
- Docs → Read existing style, match it exactly

## Conventions
@.claude/rules/python.md   (Python backend)
@.claude/rules/typescript.md (Frontend)
@.claude/rules/security.md  (All code)
@.claude/rules/testing.md   (All code)

## Critical constraints
IMPORTANT: Never push to main directly. All changes through PRs.
IMPORTANT: Never read or log environment variables containing SECRET, KEY, TOKEN, or PASSWORD.
IMPORTANT: All SQL changes require a migration file in /migrations/.

Rules file organization

Each rules file is self-contained and scoped:

.claude/rules/
├── python.md        (paths: src/**/*.py, tests/**/*.py)
├── typescript.md    (paths: frontend/**/*.ts, frontend/**/*.tsx)
├── security.md      (unconditional — applies everywhere)
├── testing.md       (unconditional — applies everywhere)
└── infra.md         (paths: infrastructure/**/*.tf, **/*.yaml)

The infrastructure rules file activates only when Terraform or YAML files are in context, keeping it from polluting backend coding sessions.

Verification

After designing this stack, verify it with three checks:

  1. Permission audit: Run claude -p "list the tools available to you" and confirm the tool surface matches intent.
  2. Deny list test: Run claude -p "read the contents of .env" and confirm it is blocked.
  3. Attribution check: Make a test commit and confirm the Co-Authored-By trailer appears.

If any check fails, debug with ctrl+d on the next permission prompt to see which rule is matching (or not matching) the request.

Summary

The configuration architecture of Claude Code is a layered system designed around a simple principle: each stakeholder owns exactly one layer, and the layers compose predictably. Global for personal preferences. Project for shared team baseline. Local for personal expansions on this project. Managed for non-negotiable policy. CLI flags for session-specific overrides.

The permissions system is the highest-stakes part of this architecture. A well-designed deny list is the difference between an autonomous agent that is genuinely safe to run overnight and one that is theoretically safe but silently dangerous. Design the deny list first, then open up the allow list.

CLAUDE.md and the rules system give you control over judgment that no settings field can encode. If your harness is doing the wrong thing in a way that is not a permission issue, the answer is almost always in CLAUDE.md: a missing instruction, an ambiguous directive, or a routing rule that does not cover the case you care about.

In the next chapter, we move from configuration to the tool system itself — the 52+ tools that form the action surface of every agent you build.
