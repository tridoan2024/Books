Chapter 38: AI for Vulnerability Discovery and Code Security

A vulnerability finding is not a model prediction. It is a falsifiable claim that a particular weakness exists in a particular revision, is reachable under stated conditions, has a defensible impact, and can be removed without introducing a regression. AI code review becomes useful only when it carries that claim through evidence collection, safe reproduction, root-cause grouping, remediation, and patch validation.

This chapter follows one example through that chain. A service parses a user-controlled archive manifest and joins each member name to an extraction directory. A scanner flags path traversal. The useful question is not whether the code resembles known vulnerable code. We must establish whether untrusted data reaches the path operation, whether canonicalization prevents escape, whether deployment configuration exposes the route, whether several alerts share one root cause, and whether the proposed patch closes all variants while preserving legitimate archives.

A Finding Is an Evidence Bundle

The unit sent to an engineer should contain:

  • repository, commit, build target, file, symbol, and line range;
  • weakness hypothesis and relevant CWE, without treating CWE as proof;
  • source-to-sink path with sanitizer and configuration evidence;
  • reachability assumptions and deployment preconditions;
  • a harmless reproducer or counterexample in an isolated harness;
  • deduplication group and root-cause explanation;
  • patch candidate, tests, and residual uncertainty;
  • identities and versions for scanner, model, rules, dependencies, and build.

A bare natural-language explanation loses exactly the information needed to dispute, reproduce, or close the issue. Conversely, a failing test without provenance may be real but impossible to map to a deployed artifact.

From Repository to Validated Repair

flowchart TB
    C[Commit and build manifest] --> S[Static facts: AST, call graph, dataflow]
    C --> D[Dependency and configuration facts]
    S --> H[Weakness hypotheses]
    D --> H
    H --> R{Reachability adjudicator}
    R -->|not connected| X[Archive as non-reachable]
    R -->|uncertain| Q[Request build or runtime evidence]
    R -->|candidate path| B[Ephemeral safe harness]
    B --> F{Behavior reproduced?}
    F -->|no| Q
    F -->|yes| G[Root-cause graph]
    G --> U[Deduplicated developer issue]
    U --> P[Patch candidate]
    P --> T[Positive, negative, metamorphic tests]
    T --> V{Original path gone and behavior preserved?}
    V -->|no| P
    V -->|yes| M[Merge evidence and post-deploy watch]

Static analysis supplies broad coverage. Dynamic reproduction supplies behavioral evidence for executable paths. Dependency analysis supplies version and advisory context. Semantic reasoning proposes connections and repairs. None is sufficient alone. The pipeline records disagreements rather than allowing the language model to smooth them away.

Reachability Has Several Meanings

Teams often say “reachable” while referring to different predicates:

  1. Syntactic reachability: a call graph contains a path from an entry point to the vulnerable function.
  2. Data reachability: attacker-influenced bytes can propagate to the dangerous argument.
  3. Control feasibility: path conditions can be simultaneously satisfied.
  4. Deployment reachability: the entry point, feature, and dependency version exist in the shipped configuration.
  5. Impact reachability: the path reaches a security-relevant effect despite sandboxing or downstream validation.

Represent a candidate as a graph \(G=(V,E)\). Each edge has confidence \(p_e\), and each required condition has support \(r_j\). A ranking score can prioritize analysis:

\[ R(\pi)=\left(\prod_{e\in\pi}p_e\right) \left(\prod_j r_j\right)I_{deploy}I_{untrusted}, \]

but it is not a probability of exploitation unless calibrated against representative outcomes. Multiplication appropriately punishes one unsupported link; it can also over-penalize correlated evidence, so production systems should retain component values.

For the archive example, the evidence chain is: HTTP upload route enabled; body saved as an archive; manifest member name attacker-controlled; member name flows to base / name; no canonical containment check; process can write outside the intended directory. A unit test calling the join helper establishes code behavior but not route deployment. A route trace establishes execution but not attacker control. The finding requires both.

Schema for a Reviewable Finding

finding_version: 2
finding_id: F-2026-00418
artifact:
  repository: inventory-importer
  commit: 7a61c9e
  build_target: importer-api
location:
  file: src/archive.py
  symbol: extract_members
  lines: [88, 104]

  weakness: path traversal during archive extraction
  cwe: CWE-22
  source: upload.manifest.member_name
  sink: filesystem.write
reachability:
  entrypoint: POST /v2/import
  dataflow_edges: [df-81, df-93, df-101]
  feature_flag: bulk_import=true
  deployment_evidence: deploy-55
  unresolved: []
reproduction:
  harness: tests/security/test_archive_containment.py
  safe_effect: write_attempt_outside_temp_root
  network: disabled
dedupe:
  root_cause_key: archive.extract.missing_canonical_boundary
patch:
  commit: pending
validation: pending

The reproduction records a safe effect, not an offensive payload. The harness uses a temporary directory, fabricated files, no network, no privilege, and an assertion that detects an attempted boundary escape before any persistent harm.

Safe Reproduction as a Scientific Test

Reproduction should answer the smallest claim necessary. For path traversal, the claim is that a crafted member name resolves outside a temporary root. There is no need to overwrite a real file. For command injection, a harness can replace process execution with an instrumented fake and assert argument boundaries. For server-side request forgery, route all traffic to a local stub. For authorization flaws, use synthetic tenants.

Safety controls belong in the harness contract: disposable container or process; no external network; read-only source mount; synthetic secrets; low CPU, memory, process, and time limits; unprivileged identity; bounded output; and destruction after collection. A reproducer is reviewed before it enters a shared corpus because “test code” can still carry dangerous primitives.

Reproduction outcomes need more nuance than pass/fail: confirmed, counterexample, environment_mismatch, build_failed, inconclusive, or unsafe_to_run. A build failure is not evidence that the finding is false. Similarly, failure to reproduce under one configuration does not refute another declared deployment.

Deduplication by Root Cause, Not Text Similarity

One missing containment check can trigger alerts at the join expression, file open, overwrite, and archive entry loop. Filing four tickets wastes engineering time and corrupts precision metrics. Yet grouping every CWE-22 alert can hide independent fixes.

Build a finding graph. Nodes are candidates; edges express shared source, sink, sanitizer gap, vulnerable symbol, dependency instance, call path, or patch locus. Cluster when findings share a plausible fix boundary. Text or embedding similarity is supporting evidence only.

For findings \(i,j\), a pair score might be

\[ D_{ij}=0.30J(E_i,E_j)+0.25I(s_i=s_j)+0.20I(k_i=k_j) +0.15J(P_i,P_j)+0.10\cos(z_i,z_j), \]

where \(E\) is dataflow edges, \(s\) vulnerable symbol, \(k\) sink class, \(P\) path-condition features, and \(z\) a text embedding. This is a candidate generator. A deterministic constraint prevents grouping across repositories or deployed dependency instances unless an explicit shared root cause exists.

Evaluate grouping with pairwise precision and recall, cluster purity, over-merge rate, under-merge rate, and developer issue count. Weight over-merges heavily because one closed ticket can otherwise suppress an unfixed vulnerability.

Patch Validation Is a New Security Evaluation

The patch is not validated merely because the reproducer stops failing. A superficial fix may block ../ while missing absolute paths, alternate separators, encoded forms, symlink resolution, or time-of-check/time-of-use behavior. A broad fix may reject legitimate nested paths.

Validation uses several test families:

  • regression: the original harmless witness no longer escapes;
  • variants: equivalent path representations remain contained;
  • positive behavior: legitimate nested members still extract;
  • metamorphic: harmless transformations preserve the security decision;
  • static reanalysis: source-to-sink path is cut or a proven sanitizer dominates it;
  • dependency/build: lockfile, artifact, and deployment actually contain the patch;
  • differential: compare old and new behavior only inside the safe harness;
  • post-deploy: monitor errors and recurrence without exposing exploit detail.

Define patch assurance as a vector rather than one score: \(A=(r,v,b,d)\), where \(r\) is original regression closure, \(v\) variant closure, \(b\) benign behavior preservation, and \(d\) deployed-artifact confirmation. Release policy can require every component, preventing a high average from hiding a zero.

Safe Lab: Reachability, Grouping, and Repair Validation

This lab uses a toy call graph and pure path normalization. It does not extract archives or write files.

from collections import defaultdict, deque
from pathlib import PurePosixPath

edges = {
    "upload_route": ["parse_manifest"],
    "parse_manifest": ["extract_member", "audit_name"],
    "extract_member": ["join_path", "write_file"],
    "join_path": [], "write_file": [], "audit_name": []
}
tainted = {"upload_route", "parse_manifest", "extract_member", "join_path", "write_file"}
findings = [
    ("F1", "extract_member", "write_file", "missing_boundary"),
    ("F2", "join_path", "write_file", "missing_boundary"),
    ("F3", "audit_name", "log", "log_forging"),
]

def reachable(start, goal):
    queue, seen = deque([start]), set()
    while queue:
        node = queue.popleft()
        if node == goal:
            return True
        if node not in seen:
            seen.add(node)
            queue.extend(edges.get(node, []))
    return False

def contained(member):
    parts = PurePosixPath(member).parts
    depth = 0
    for part in parts:
        if part in ("", ".", "/"):
            continue
        if part == "..":
            depth -= 1
        else:
            depth += 1
        if depth < 0:
            return False
    return not PurePosixPath(member).is_absolute()

groups = defaultdict(list)
for fid, symbol, sink, root_cause in findings:
    if reachable("upload_route", symbol) and symbol in tainted:
        groups[(sink, root_cause)].append(fid)

tests = ["reports/q1.csv", "../escape.txt", "a/../../escape.txt", "/tmp/escape"]
print("reachable_groups=" + str(dict(groups)))
for name in tests:
    print(f"{name}: {'ALLOW' if contained(name) else 'BLOCK'}")
print("patch_valid=" + str(all(contained(x) == expected for x, expected in {
    "reports/q1.csv": True, "../escape.txt": False,
    "a/../../escape.txt": False, "/tmp/escape": False}.items())))

Expected output:

reachable_groups={('write_file', 'missing_boundary'): ['F1', 'F2']}
reports/q1.csv: ALLOW
../escape.txt: BLOCK
a/../../escape.txt: BLOCK
/tmp/escape: BLOCK
patch_valid=True

The lab deliberately separates reachability, grouping, and validation. F3 is not grouped because its symbol is not on the tainted set, even though a textual model might find both discussions of names similar.

That separation is operationally important: each stage can fail, be appealed, and be improved without relabeling every downstream outcome.

Metrics and Production Operations

Finding-level precision is inadequate. Track candidate precision, reachable precision, root-cause precision, confirmed-finding recall on seeded and historical cases, time to first reviewable evidence, developer acceptance, median duplicates per root cause, reopen rate, patch variant escape rate, and deployed remediation time. Stratify by language, framework, repository criticality, scanner version, and weakness family.

Avoid measuring recall solely with public benchmark snippets: they are susceptible to memorization, structurally simpler than production code, and often lack build or deployment context. Use temporally held-out internal fixes where permitted, synthetic transformations, seeded weaknesses reviewed by experts, and naturally occurring prospective findings. Prevent leakage by separating benchmark authorship, model-development access, and final evaluation custody; hash and access-log hidden cases.

Production services need build isolation, artifact retention, queue limits, repository access minimization, secret redaction, dependency-cache provenance, and an emergency stop for reproduction. Every finding state transition is append-only. Engineers can dispute source control, reachability, duplicate grouping, severity, or proposed repair separately; disagreement is valuable labeled evidence.

Roll out by repository cohort. Begin with read-only shadow scanning, then expose evidence bundles without auto-created tickets, then create tickets only for high-assurance families. Never auto-merge security patches solely on model judgment. Canary monitoring includes build failures, test flakiness, reviewer rejection, grouping changes, sensitive-code exposure, and any unexpected network attempt from a harness.

Interview Practicum

A payments company’s new AI reviewer emits 1,800 findings across 300 repositories. Developers report duplicates and false positives. Leadership claims 92% accuracy from a public benchmark. You discover the model had access to benchmark solutions, many services disable the flagged routes, and the reproduction service can reach the corporate network.

Prompt: Redesign the system and decide whether any findings can continue to developers this quarter. After your initial design, the build team says only 60% of repositories build reproducibly. Then a critical library alert appears in 47 services, but only four load the vulnerable parser at runtime.

Useful questions: What is the unit behind 92%? Was the benchmark held out temporally and organizationally? Which build, call-graph, deployment, and runtime facts exist? How are duplicates counted? What is the safe effect for reproduction? Which repositories process untrusted input? Can fixes be tested and traced into deployed artifacts?

Worked Answer

I would suspend the unsafe reproduction service immediately because corporate network reach is an independent hazard. Static scanning may continue in shadow mode. I would not discard all findings: quarantine them, preserve commit and scanner provenance, and allow developers to see only evidence bundles that pass subject, revision, and reachability checks without dynamic execution.

The public benchmark result is invalid for release because solution access creates contamination and because snippet accuracy does not measure deployed reachability, duplicate burden, or repair quality. I would establish a custodied temporal suite containing internal historical fixes, expert-seeded cases, benign hard negatives, and transformed variants. Reporting is per weakness family and language, with candidate and root-cause metrics separated.

For the 40% that do not build reproducibly, the state is environment_mismatch, not false positive. We can still establish partial static evidence, but cannot claim behavioral confirmation. I would fund build manifests as security infrastructure and make evidence grade visible. High-criticality repositories with missing builds receive human review rather than model confidence inflation.

The 47 library alerts should become one campaign with 47 deployment instances, not one ticket and not 47 unrelated vulnerabilities. Dependency presence, vulnerable version, runtime load, untrusted entry point, and vulnerable function use are separate predicates. The four runtime-reachable services receive prioritized remediation with safe regression tests. The others remain inventory records with reasons—unused code path, feature disabled, or non-attacker-controlled input—and are re-evaluated when configuration changes.

I would rebuild reproduction on ephemeral isolated workers with no external network, synthetic secrets, resource limits, instrumented effects, and reviewed harness templates. Patch validation must close the original and transformed cases, preserve benign behavior, pass the repository suite, and confirm the fixed artifact reaches deployment. This quarter, only finding families with reliable builds or strong static proofs, acceptable root-cause precision, and safe reviewed harnesses advance to ticket creation.

Follow-Up Questions and Answers

How do you estimate recall without exposing hidden cases? Run the evaluator in a custodied service that returns aggregate metrics and limited diagnostics. Rotate cases, log access, and reserve a final untouched slice.

Why not use EPSS as reachability? EPSS estimates exploitation probability for published CVEs in a population. It does not show that this service loads the component, invokes the vulnerable function, or exposes attacker-controlled input.

What is the most damaging dedupe error? Over-merging independent root causes, because closing one issue can suppress unfixed paths. Track and manually sample merges, especially across repositories and dependency instances.

When can an AI patch be merged? When normal ownership and review remain intact, security regression and variant tests pass, deployed artifact provenance is verified, and risk-appropriate human approval is recorded. Model confidence is not a merge authority.

Key Takeaways

  • Treat every finding as a revision-specific, falsifiable evidence bundle.
  • Distinguish syntactic, data, control, deployment, and impact reachability.
  • Reproduce the smallest harmless security effect in an isolated environment.
  • Deduplicate around the repairable root cause, not wording or CWE alone.
  • Validate variants, benign behavior, and the deployed artifact—not only the original test.
  • Keep contaminated benchmark performance out of release evidence.
