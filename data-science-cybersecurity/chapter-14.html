Chapter 14: Security Event Schemas and Data Modeling

The incident timeline looked impossible. At 09:02, alex@northwind authenticated from a managed laptop. At 09:04, a.chen downloaded a design. At 09:05, device 7F-22 reached a restricted database. The identity team counted three actors. All three records described one contractor after an email rename, directory migration, and device re-enrollment.

Security modeling preserves distinctions until evidence justifies a join. It must answer opposing questions: which records refer to the same entity, and which similar records must remain separate? A warehouse that never resolves identity cannot reconstruct behavior. One that resolves too aggressively can accuse the wrong person.

Facts Need a Declared Grain

A fact records an occurrence at a declared grain. A useful activity grain is: one row represents one source-observed attempt by an effective principal to perform one operation on one resource. A retry is another attempt, not an update. One request affecting five resources may require five resource-action facts plus a request fact. An alert derived from events belongs in a detection fact with lineage; it is not another activity event.

Dimensions describe entities or classifications: identity, device, resource, application, organizational unit, vulnerability, and detector. They change independently. If a device becomes unmanaged today, yesterday's activity must not silently acquire today's status.

A compact model includes fact_activity plus versioned identity, device, and resource dimensions. Facts carry event, occurrence and ingestion times, actor, device, resource, operation, result, source, and source locator. Dimensions carry stable entity keys and time-bounded attributes. Bridge tables express many-to-many relationships such as identity-to-account assertions.

Surrogate keys improve joins, but preserve natural identifiers and issuing authority. 12345 means nothing without issuer=okta-prod or source=aws-account-17. Global uniqueness is a contract, not a visual property.

Sessions Are Hypotheses With Boundaries

Some systems emit explicit sessions with issue, renewal, and revocation. Preserve that source session. Analysts also infer sessions by grouping activity across inactivity gaps. If ordered event times are \(t_1,\ldots,t_n\), a new gap session begins when

\[ t_i-t_{i-1}>\Delta. \]

The threshold \(\Delta\) is a modeling parameter. Thirty minutes may fit interactive administration yet merge unrelated automation or split a long remote shell. Version the algorithm and threshold, and attach confidence when device or credential binding is uncertain.

Do not use a session to erase actor layers. A human operates a browser, which exercises an application service account, which assumes a cloud role. Model initiating_subject, effective_principal, and credential/session separately. “Who caused this?” may mean human initiator, target-accepted principal, executing process, or accountable automation owner.

Identity Resolution Is Evidence Accumulation

Begin with assertions, not a universal user table. An assertion has a source identifier, candidate entity, issuer, assertion type, interval, source record, and confidence. Strong links include an immutable directory object ID, certificate key identifier, device enrollment record, or cloud role session naming its source. Weak links include display name, mutable email, IP, and temporal proximity.

Resolution forms a graph of source identifiers and canonical entities. Deterministic rules can join (issuer, immutable_subject_id). Probabilistic linkage can combine evidence:

\[ \log \frac{P(M\mid x)}{P(\neg M\mid x)} = \log \frac{P(M)}{P(\neg M)} + \sum_k \log\frac{P(x_k\mid M)}{P(x_k\mid \neg M)}, \]

where \(M\) means two identifiers represent the same entity. Rare shared attributes are stronger evidence than common ones; contradictory immutable IDs should dominate a matching name.

Use asymmetric thresholds. Auto-link only above a high threshold, queue ambiguity, and preserve “not same entity” constraints. A false merge contaminates every behavioral profile. A false split loses history but is often reversible. Privileged identities warrant stricter rules.

Service principals, workload identities, shared accounts, and agents must not be coerced into employee rows. Give principals a type and relate them to accountable people or teams without asserting equivalence. A bot owned by Finance is not the finance director.

Slowly Changing Context and Bitemporal Truth

Type 1 slowly changing dimensions overwrite attributes and suit corrections whose history is irrelevant. Type 2 creates a version with valid_from and valid_to; it is necessary when historical context affects interpretation. Department, manager, privilege tier, device ownership, exposure, and resource sensitivity often require Type 2.

Investigations also need bitemporality:

  • valid time: when an assertion was true in the modeled world;
  • system time: when the analytical system learned and stored it.

Suppose HR tells the warehouse on August 10 that a contractor left August 3. A current query about August 5 should show no active employment. Reconstruction of an alert generated August 6 must admit the warehouse still believed the contractor active.

A bitemporal version occupies

\[ [v_{from},v_{to})\times[s_{from},s_{to}). \]

Corrections close the prior system-time rectangle and insert a corrected belief. Half-open intervals avoid double matches. The as-of join for event time \(t\) and knowledge cutoff \(k\) is:

v.valid_from <= t AND t < v.valid_to
AND v.recorded_from <= k AND k < v.recorded_to

Enforce non-overlap for versions of the same entity and belief state. Never update the only historical copy when reproducibility matters.

Four Clocks and Partial Order

Preserve occurred_at (source claim), observed_at (sensor observation), ingested_at (durable platform acceptance), and processed_at (transformation output). Store source timezone or offset, clock quality, and sequence numbers when available. Normalize for comparison but retain original timestamp text. Daylight-saving folds can produce duplicate local times; batching, mobile offline operation, virtual-machine drift, and coarse clocks weaken ordering.

If two times differ by less than their combined uncertainty, do not present their order as definite. Sequence numbers, transaction IDs, parent spans, and resource versions are often stronger. A state transition from version 8 to 9 establishes an order even if clocks disagree.

Streams use event time for semantics and processing time for operations. A watermark approximating max_event_time_seen - allowed_lateness trades latency for corrections. Late events must enter a correction path rather than disappear. Reports need an as_of time and revision state such as provisional, finalized, or corrected.

One Semantic Model, Four Physical Forms

Relational databases excel at constraints, point lookups, transactions, temporal dimensions, and explainable SQL. They are strong systems of record for identity, policy, and case state.

Columnar stores optimize scans and compression. Parquet or a columnar warehouse suits immutable events and feature computation. Avoid tiny files and high-cardinality partitions; partition by coarse time and perhaps tenant, then cluster for common predicates.

Graphs make variable-length paths first-class: identity assumed role, role accessed bucket, bucket contained artifact, artifact deployed to host. Every edge still needs direction, type, time, source, and confidence. A graph does not abolish provenance.

Streams represent changes in motion, with replay, partitions, and consumer offsets. Ordering normally holds only within a partition, so choose keys around invariants. A stream is not automatically an analytical model; consumers still need schemas, state, and late-event policy.

The semantic contract defines identifiers, grains, event types, clocks, units, classifications, and version rules. Physical projections optimize workloads. Graph edges, rows, Parquet records, and messages should remain traceable to the same source assertion.

Normalization Without Invented Semantics

Preserve raw evidence or a verifiable reference, parse source-specific typed fields, then map to normalized categories. If a source reports login success without authentication method, store method as unknown; do not infer password from absence of MFA.

Standards occupy different layers. OCSF defines cybersecurity categories. Elastic Common Schema supplies reusable fields. STIX 2.1 models threat-intelligence objects and relationships, while TAXII transports collections. OpenTelemetry correlates traces, metrics, and logs. CloudEvents standardizes an event envelope. Avro, Protocol Buffers, and JSON Schema express serialization contracts.

Mapping is rarely lossless. Retain extension fields and mapping versions. Mark whether normalized values were direct, transformed, defaulted, inferred, or unknown. Interoperability failures often arise from grain differences: one feed emits a flow summary while another emits requests.

Executable SQLite Lab: Query Two Knowledge Cutoffs

The model below contains identities, aliases, bitemporal device ownership, and activity. The warehouse first believed device dev-7 belonged to Alex through August 10. On August 12 it learned ownership ended August 5 and Riley became owner. Run with the book interpreter.

import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE identity (
  identity_id INTEGER PRIMARY KEY,
  display_name TEXT NOT NULL,
  principal_type TEXT NOT NULL CHECK(principal_type IN ('human','service','agent'))
);
CREATE TABLE alias (
  issuer TEXT NOT NULL, subject TEXT NOT NULL,
  identity_id INTEGER NOT NULL REFERENCES identity,
  valid_from TEXT NOT NULL, valid_to TEXT NOT NULL,
  PRIMARY KEY (issuer, subject, valid_from)
);
CREATE TABLE device_owner_bt (
  device_id TEXT NOT NULL,
  identity_id INTEGER NOT NULL REFERENCES identity,
  valid_from TEXT NOT NULL, valid_to TEXT NOT NULL,
  recorded_from TEXT NOT NULL, recorded_to TEXT NOT NULL,
  source TEXT NOT NULL,
  PRIMARY KEY(device_id, valid_from, recorded_from)
);
CREATE TABLE activity (
  event_id TEXT PRIMARY KEY,
  occurred_at TEXT NOT NULL, ingested_at TEXT NOT NULL,
  issuer TEXT NOT NULL, subject TEXT NOT NULL,
  device_id TEXT NOT NULL, resource TEXT NOT NULL, operation TEXT NOT NULL
);
INSERT INTO identity VALUES (1,'Alex Chen','human'), (2,'Riley Shah','human');
INSERT INTO alias VALUES
 ('idp','alex@northwind',1,'2026-01-01','9999-12-31'),
 ('repo','a.chen',1,'2026-01-01','9999-12-31');
INSERT INTO activity VALUES
 ('e1','2026-08-07T09:04:00Z','2026-08-07T09:04:05Z','repo','a.chen','dev-7','design/phoenix','download');
INSERT INTO device_owner_bt VALUES
 ('dev-7',1,'2026-07-01','2026-08-10','2026-08-01','2026-08-12','mdm'),
 ('dev-7',1,'2026-07-01','2026-08-05','2026-08-12','9999-12-31','mdm-correction'),
 ('dev-7',2,'2026-08-05','9999-12-31','2026-08-12','9999-12-31','mdm-correction');
""")

query = """
SELECT a.event_id, i.display_name,
       COALESCE(owner.display_name, 'UNKNOWN')
FROM activity a
JOIN alias x ON x.issuer=a.issuer AND x.subject=a.subject
 AND x.valid_from <= a.occurred_at AND a.occurred_at < x.valid_to
JOIN identity i ON i.identity_id=x.identity_id
LEFT JOIN device_owner_bt d ON d.device_id=a.device_id
 AND d.valid_from <= a.occurred_at AND a.occurred_at < d.valid_to
 AND d.recorded_from <= :cutoff AND :cutoff < d.recorded_to
LEFT JOIN identity owner ON owner.identity_id=d.identity_id
ORDER BY a.event_id
"""

for cutoff in ('2026-08-08', '2026-08-13'):
    row = db.execute(query, {"cutoff": cutoff}).fetchone()
    print(f"knowledge_cutoff={cutoff} event={row[0]} account={row[1]} device_owner={row[2]}")

orphans = db.execute("""
SELECT COUNT(*) FROM activity a
LEFT JOIN alias x ON x.issuer=a.issuer AND x.subject=a.subject
 AND x.valid_from <= a.occurred_at AND a.occurred_at < x.valid_to
WHERE x.identity_id IS NULL
""").fetchone()[0]
print(f"unresolved_activity={orphans}")

Exact output:

knowledge_cutoff=2026-08-08 event=e1 account=Alex Chen device_owner=Alex Chen
knowledge_cutoff=2026-08-13 event=e1 account=Alex Chen device_owner=Riley Shah
unresolved_activity=0

The account remains Alex because repository alias evidence is unchanged. Device ownership changes with knowledge cutoff. An August 8 alert reconstruction shows Alex as then-believed owner; a current timeline shows Riley and exposes the correction. Their mismatch is valuable and must not be erased by overwriting either fact.

Production needs constraints or validation to reject overlapping intervals. Tests should cover boundary instants, alias reuse, null identifiers, late corrections, deleted entities, timezone folds, and accidental one-to-many as-of joins.

Review the Model by Trying to Break History

Ask whether every fact has a grain and stable source locator. Verify that identifiers include namespace and type. Label joins as exact, asserted, inferred, or convenient. Require intervals for changing relationships. Preserve unknown as distinct from false, empty, and zero. Make units explicit.

Then test a renamed user, reimaged device, recycled IP, assumed role, shared mailbox, and workload identity. Can an analyst reproduce what was known at an earlier decision time? Can late facts revise aggregates without destroying the first result? Can replay create duplicates? If any answer depends on manually remembering context, the model is incomplete.

Cardinality tests deserve special attention. A fact-to-dimension join expected to be many-to-one can become many-to-many when temporal versions overlap or an alias is reused. The resulting row multiplication inflates counts while every individual row still appears valid. Assert expected cardinality before and after each join, publish unmatched and multiply matched rates, and fail closed for high-consequence products. When ambiguity is real, represent a set of candidate links rather than selecting the first database row.

Deletion also needs semantics. Privacy erasure, source retention, and entity retirement do not mean the same thing. A tombstone can state that an identifier existed and is no longer available without retaining prohibited attributes. Referential integrity may use durable pseudonymous keys while restricted lookup material expires. Analysts must be able to distinguish “entity deleted under policy,” “source never supplied this entity,” and “resolution currently failed.” Collapsing all three to null destroys both auditability and missingness analysis.

Schema evolution should therefore be rehearsed with historical queries. Add a new principal type, split one operation into two, change a resource hierarchy, and retire an alias namespace in a test snapshot. The acceptance criterion is not only that new events load; old as-of queries, alert reconstructions, and lineage pointers must continue to mean what they meant under their recorded versions.

Interview Practicum

A hospital acquires a clinic. For 90 days both directories remain active. Email addresses collide, nurses share workstation sessions, devices are re-enrolled, and cloud audit arrives six hours late. The SOC wants a graph showing “every action by a person.” Mid-interview, the panel reveals that a privileged account was reassigned before a breach was discovered and Legal requires reproduction of the original alert.

The prompt is: Design the identity–device–resource model and explain how analysts query it. Strong questions identify immutable IDs, reuse rules, shared-account policy, device hardware evidence, clock quality, grains, correction sources, privacy constraints, and whether “person” means initiator, effective principal, or accountable owner.

Worked Answer

Create typed entities for people, accounts, credentials, devices, workloads, sessions, and resources. Ingest namespace-qualified aliases. Store evidence edges—assigned-to, authenticated-as, operated-from, assumed-role, accessed—with valid and recorded intervals, issuer, locator, and confidence. Never merge on email alone. Preserve a shared workstation session as its own entity linked to possible humans unless badge or step-up evidence resolves it.

Activity facts retain source actor, effective principal, device claim, resource, operation, result, four clocks, and raw locator. Bitemporal dimensions model account assignment, department, device ownership, and sensitivity. A current query uses event valid time plus the latest recorded view. An original-alert reconstruction adds the alert's knowledge cutoff. The graph is a projection of governed temporal facts, not an unversioned truth store.

Six-hour watermarks produce provisional dashboards, followed by finalized and corrected states. The reassigned privileged account remains one account entity with separate assignment intervals. The defensible conclusion is: “The effective principal was account P; at that valid time it was assigned to A according to knowledge available then.”

Follow-Up Questions and Answers

Why not use a graph database for everything? Traversal is useful, but temporal constraints, deduplication, bitemporal corrections, and scans may be clearer elsewhere. Project one contract into fit-for-purpose stores.

What if two high-confidence links conflict? Preserve both assertions, block auto-merge, record the conflict, and adjudicate. Confidence does not replace consistency.

Most dangerous shortcut? Joining mutable email, hostname, IP, or display name as immutable identity.

Explain bitemporality simply. One clock says when something was true; another says when we learned it. Both are needed to reconstruct history and judge past decisions.

Five-minute summary? Declare grains; namespace identities; resolve through provenance-bearing temporal assertions; model changing context with valid and system time; retain multiple clocks; use several physical stores without multiplying meanings.

Key Takeaways

  • Facts record occurrences at a declared grain; dimensions supply versioned context.
  • Sessions may be source-issued or inferred and must retain construction rules.
  • Identity resolution is evidence-based linkage, not string equality.
  • Bitemporal models distinguish what was true from what the system knew.
  • Occurrence, observation, ingestion, and processing times answer different questions.
  • Physical representations can vary while semantics and provenance remain stable.
