Chapter 32: Security Product Analytics

Usage Is Not Security Value

A security product can increase daily users, alerts viewed, and tickets closed while making customers less secure. Analysts may bulk-close noise; developers may repeatedly open a dashboard because fixes fail; an automated agent may execute many actions because it is stuck. Product analytics must connect an eligible user’s exposure to a workflow, a completed security decision, and a protected outcome—while accounting for friction and harm.

The unit depends on the job. Analysts investigate cases; developers resolve root causes; administrators establish coverage and policy; executives allocate risk; agents perform bounded actions. “Monthly active user” mixes these personas and rewards shallow activity. Define activation as the first completed value-bearing workflow, not login. For a detection platform it might require representative telemetry connected, a reviewed detection deployed, and one case resolved with evidence.

CREATE TABLE product_exposure(
 exposure_id TEXT PRIMARY KEY, organization_id TEXT NOT NULL,
 persona TEXT NOT NULL, feature_version TEXT NOT NULL,
 eligible_at TEXT NOT NULL, exposed_at TEXT,
 assignment_arm TEXT, assignment_unit TEXT, assignment_probability REAL);
CREATE TABLE security_value_event(
 event_id TEXT PRIMARY KEY, organization_id TEXT NOT NULL,
 actor_id TEXT NOT NULL, persona TEXT NOT NULL,
 occurred_at TEXT NOT NULL, workflow TEXT NOT NULL,
 root_cause_id TEXT, outcome TEXT NOT NULL,
 evidence_verified INTEGER NOT NULL, minutes_spent REAL,
 override_reason TEXT, policy_version TEXT NOT NULL);

Eligibility, assignment, exposure, and outcome are distinct. Entitlement is not exposure. Exposure is not adoption. Adoption is not causal impact. assignment_probability enables unbiased analysis when rollout is randomized or capacity-constrained.

A Metric Tree With Security Guardrails

A useful north star for a code-security product is weekly organizations with at least one distinct high-risk root cause durably resolved after product-supported validation. It resists raw alert inflation and aggregates at the customer level. It still needs guardrails:

  • confirmed false-intervention rate;
  • developer and analyst minutes per durable root cause;
  • recurrence within a mature observation window;
  • eligible asset and repository coverage;
  • unresolved high-risk exposure-time;
  • automation rollback and unauthorized-action rate;
  • time to first verified value, including setup failures.

Retention should be conditioned on continued eligibility. A customer that finishes a one-time migration should not be labeled churned. Enterprise adoption also requires persona depth: an administrator configuring telemetry does not prove analysts trust explanations or developers can fix findings.

A funnel might be eligible organization → telemetry healthy → feature exposed → first workflow completed → repeated workflow → verified security outcome. Report conversion and latency at every transition. Missing instrumentation must appear as unknown, not abandonment.

Estimating Product Impact

Usage correlates with need. Customers under attack may use a feature more and suffer more incidents; mature teams may adopt early and already have lower risk. The causal estimand must be explicit, for example the intention-to-treat effect:

\[ ATE_{ITT}=E[Y\mid Z=1]-E[Y\mid Z=0], \]

where \(Z\) is randomized assignment and \(Y\) is a protected outcome. Intention-to-treat preserves randomization even when some assigned customers never activate. A treatment-on-treated estimate needs additional assumptions; randomized encouragement can use assignment as an instrument when forced exposure is undesirable.

Cluster randomize by organization when analysts share queues or policy. Account for interference: one tenant’s threat intelligence may improve the product for others, and an agent action may affect multiple repositories. For phased rollouts, inspect pre-trends and calendar effects. Never call a before/after adoption comparison causal without defending exchangeability.

Trust is behavioral and contextual. Capture override reason codes such as bad evidence, wrong severity, policy exception, missing context, unsafe action, and explanation unclear. A low override rate can mean trust, rubber-stamping, or inability to override. Audit a sample of accepted and rejected recommendations and measure decision quality, not agreement with the product.

Safe Lab: Correlation Versus Randomized Encouragement

The synthetic data contain confounding: high-risk organizations use the feature more. Assignment remains randomized.

orgs = [
 # org, assigned, used, incidents
 ("A",1,1,1), ("B",1,1,0), ("C",1,0,3), ("D",1,1,1),
 ("E",0,1,2), ("F",0,0,2), ("G",0,0,1), ("H",0,0,3),
]

def mean(values): return sum(values) / len(values)

used = [r[3] for r in orgs if r[2] == 1]
unused = [r[3] for r in orgs if r[2] == 0]
naive = mean(used) - mean(unused)
assigned = [r[3] for r in orgs if r[1] == 1]
control = [r[3] for r in orgs if r[1] == 0]
itt = mean(assigned) - mean(control)

result = {"naive_user_difference": round(naive,3),
          "randomized_itt": round(itt,3)}
expected = {"naive_user_difference": -1.25, "randomized_itt": -0.75}
assert result == expected, result
print(result)

Both estimates happen to be beneficial here, but they answer different questions and differ materially. The user comparison breaks randomization because usage is chosen. In real analysis report uncertainty and cluster effects; eight organizations are only a transparent fixture.

SQL for the north star

WITH mature AS (
 SELECT organization_id, root_cause_id,
        date(occurred_at,'weekday 1','-7 days') AS week
 FROM security_value_event
 WHERE outcome='durably_resolved' AND evidence_verified=1
   AND root_cause_id IS NOT NULL
), weekly AS (
 SELECT week, organization_id, COUNT(DISTINCT root_cause_id) AS roots
 FROM mature GROUP BY week, organization_id
)
SELECT week, COUNT(*) AS organizations_realizing_value,
       SUM(roots) AS distinct_org_root_causes
FROM weekly WHERE roots>0 GROUP BY week ORDER BY week;

Root causes are distinct within organization; the same library defect at two customers represents value to both. The week expression is SQLite-compatible and should be standardized in the semantic layer.

Product Failure Analysis

Metric gaming: alerts viewed rises when noise rises. Pair value events with false intervention, effort, recurrence, and exposure-time guardrails.

Instrumentation-induced selection: events appear only after successful setup, erasing failed onboarding. Begin the funnel at eligibility and preserve missing/failed states.

Identity errors: shared SOC accounts and service principals distort user retention. Model organization, persona, human actor, and agent separately.

Outcome delay: incident reduction may take months. Use pre-registered leading indicators, label them provisional, and revisit mature outcomes.

Interference: shared detections, global models, and cross-repository agent actions violate independent-unit assumptions. Randomize at the highest interacting cluster or estimate spillovers explicitly.

Novelty effects: usage spikes after launch. Measure repeated workflow completion and cohort retention after the novelty window.

Agent activity inflation: an agent can generate actions without value. Require bounded authority, action provenance, human override, rollback success, and outcome verification. Token count and tool calls are cost metrics, not security outcomes.

Survivorship: churned or breached customers disappear from telemetry. Join billing, support, and security outcome sources under a governed organization identifier and retain censoring reasons.

Rollout should progress from instrumentation validation to shadow measurement, randomized or phased exposure, and bounded expansion. Stop conditions should cover unauthorized actions, false interventions, customer effort, telemetry loss, and worsening protected outcomes. Rollback must restore compatible workflow and policy, not only a UI flag.

Building the Product Measurement System

Start with a semantic specification, not a dashboard. For every metric define eligibility, unit, event-time rule, late-arrival policy, identity resolution, deduplication, observation window, exclusions, and owner. Version the specification with product releases. A feature rename must not split history; a workflow redesign may require a deliberate metric version because “completion” has changed meaning.

Identity resolution is particularly difficult in enterprise security. One human may use several accounts, a managed service provider may act across tenants, and an agent may operate under a service principal. Preserve raw actor identifiers and map them to governed person, persona, organization, and automation entities with validity intervals. Never merge tenants because email domains match. Tenant isolation applies to analytics tables as well as product storage.

Event collection should represent state-changing facts rather than UI clicks whenever possible. investigation_verified is stronger than button_clicked, provided its evidence contract is stable. Keep raw interaction events for usability diagnosis but build value events from server-side workflow records. Include failures: attempted integrations, rejected agent actions, rollback attempts, and workflows abandoned after an error.

Time to value and retention

Time to value starts at a customer-relevant eligibility point—contract activation, completed prerequisite, or explicit trial start—and ends at a verified value event. Starting only after successful setup erases onboarding pain. Use survival curves because some organizations have not yet activated. Treat contract cancellation and trial expiry explicitly rather than dropping them.

Retention should follow the natural cadence of the job. A quarterly compliance workflow does not require weekly activity. Define retained value as repeated successful work when the need recurs, conditioned on continued eligibility. For automation, “no human sessions” may coexist with excellent retained value if policies remain healthy and verified outcomes continue.

Enterprise rollups need weighting choices. Organization-weighted metrics answer how many customers realize value; asset-weighted metrics answer how much protected surface does; revenue-weighted metrics answer commercial concentration. Publish them separately. A revenue-weighted north star can hide poor outcomes for smaller customers, while an unweighted average can understate systemic exposure in a few large tenants.

Experiment design under security constraints

Randomize the smallest unit that does not create contamination. If analysts share recommendations, randomize the queue or organization rather than individual alerts. If one repository’s fix updates a common library, repository-level assignment interferes. Document the interference graph and select clusters accordingly.

Before launch, specify the primary estimand, guardrails, minimum detectable effect, duration, and stopping rules. Sequential monitoring without correction inflates false positives. Security stop rules for harm can be asymmetric: stop immediately for unauthorized containment even if the primary outcome is inconclusive. Benefit stopping should be more conservative when outcomes are delayed.

Randomized encouragement is useful when customers choose adoption. Assignment might provide guided onboarding, an in-product prompt, or priority access; the feature remains optional. Intention-to-treat estimates the effect of encouragement. Using assignment as an instrument for adoption requires relevance, exclusion, and monotonicity assumptions that should be defended, not merely named.

When randomization is unavailable, phased rollout can support difference-in-differences if treated and comparison cohorts had credible parallel trends and no simultaneous differential change. Plot event-time effects and pre-period coefficients. Matching cannot repair unmeasured confounding. Regression discontinuity may be possible when eligibility follows a threshold, but manipulation around the threshold and limited external validity need attention.

Trust, explanations, and overrides

Trust should be calibrated reliance: users accept correct recommendations and reject incorrect ones. Measure acceptance conditional on audited correctness, not raw acceptance. Explanation quality can be tested by randomizing evidence formats and measuring correct decisions, time, and confidence. Longer explanations may feel transparent while obscuring the decisive fact.

Override taxonomies should permit multiple reasons and free text, then be reviewed for drift. “Policy exception” may conceal an incorrect recommendation if it becomes the easiest button. Forced reason codes can also add friction, so sample lightweight follow-up rather than burdening every action. Analyze whether particular teams cannot override because of role permissions.

For agents, record proposal, authorization, tools invoked, parameters, result, verification, and rollback as separate events. An agent that proposes the right action but calls the wrong tenant is unsafe. Outcome analytics must join the action trace to a policy decision and protected asset without exposing sensitive prompts or secrets broadly.

Economic value without fictional precision

Translate outcomes into ranges. Analyst time saved can use loaded labor cost; avoided incident loss is much more uncertain. Report assumptions and sensitivity rather than a single inflated return-on-investment number. Separate realized savings, capacity redeployed, and modeled risk reduction. Ten hours “saved” are not cash savings if staffing and workload do not change, but they may be valuable capacity.

Customer value also includes option value: faster evidence during an incident, auditable control state, or safer automation. These may be measured through response time, audit effort, and bounded action coverage. Do not invent dollar values where operational measures are more defensible.

The product review should show a metric tree, causal evidence grade, segment distributions, reliability state, and unresolved uncertainties. Decisions then become explicit: expand, hold, redesign, or retire. A feature with high engagement but no outcome evidence may remain in discovery; a low-engagement automation with verified value may deserve expansion.

Measurement itself needs reliability objectives. Track event acceptance, schema rejection, end-to-end freshness, identity-match coverage, experiment-assignment integrity, and late outcome arrival. If assignment logs are incomplete, stop causal reporting rather than substituting observed use. If value events lag, label the current period provisional. A trustworthy product organization is willing to show an empty metric instead of manufacturing continuity from incompatible data.

Privacy review should minimize collection to the decision. Full source code, prompts, or investigation text rarely belongs in broad analytics. Prefer derived reason codes, bounded counts, and access-controlled evidence links. Define retention and deletion propagation before launch, especially when agents can capture secrets in traces.

Segment review is mandatory before declaring success. Tenant size, industry, geography, deployment model, and maturity can concentrate both benefit and harm. An average improvement does not authorize expansion when a regulated or low-maturity segment experiences unsafe interventions.

Interview Practicum

Scenario: Engagement Falls After the Product Improves.

Prompt. An AI SOC assistant reduced weekly active analysts by 25%. The product leader wants to roll back. Decide what to do.

Ask whether eligible organizations changed, which personas declined, how exposure is logged, what workflows completed, whether incidents and decision quality matured, and whether the assistant now automates work.

Worked Answer

Compare cohorts on verified cases, analyst minutes, false interventions, overrides, unresolved exposure, and incidents. Lower activity may be the intended outcome.

Follow-Up Questions and Answers

Change one: case-resolution time fell 40%, but analysts override 18% of containment recommendations. Stratify overrides by reason and consequence. Unsafe-action overrides may trigger a stop even when speed improves; policy exceptions may indicate configuration work. Audit accepted recommendations too, because non-override is not correctness.

Change two: only large customers received the feature, chosen by customer-success managers. Do not use untreated small customers as controls. Seek a randomized encouragement among eligible large customers or a phased rollout with credible pre-trends and matching. State that causal certainty is limited until assignment improves.

Change three: the agent begins auto-containment next quarter. The metric system must add authorization scope, attempted and executed actions, rollback success, business disruption, and human escalation. Randomization may be unethical for high-risk autonomous actions; use shadow decisions, simulation, red-team challenges, and bounded canaries before outcome experiments.

Weak answers maximize MAU, infer impact from correlation, or A/B test autonomous containment without a harm model. A Principal answer changes the north star so leadership benefits when customers need fewer interactions to achieve a verified outcome.

Key Takeaways

  • Separate eligibility, assignment, exposure, adoption, workflow completion, and protected outcome.
  • Define activation around first verified value, not login.
  • Pair a security-value north star with friction, coverage, recurrence, and harm guardrails.
  • Use randomization or defensible quasi-experiments; feature users are a selected population.
  • Model personas, organizations, humans, and agents explicitly.
  • Reduced usage can indicate improvement when the product removes work safely.
