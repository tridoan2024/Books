Chapter 34: Foundations of Agentic AI Security

Authority, Not Intelligence, Defines the Blast Radius

An enterprise coding agent reads repositories, searches tickets, runs tests, proposes patches, and sometimes deploys. Its language model is only one component. Security depends on which principal the system represents, which objects it can observe, which actions it can cause, and which evidence can influence those actions. A mediocre model with production credentials is more dangerous than an exceptional model confined to a disposable workspace.

Traditional application diagrams emphasize data flow. Agent threat models need authority flow. A retrieved issue can contain instructions; a generated plan can select a tool; a tool broker can mint a credential; a deployment service can change production. The important question is not merely “can untrusted text reach the model?” It is “can that text cross a consequence boundary without an independent authorization decision?”

A Typed Authority Graph

Model the system as \(G=(V,E)\). Every vertex has a type: Principal, Agent, Model, Data, Tool, Credential, Environment, or Policy. Every directed edge has a relation such as READS, INFLUENCES, INVOKES, AUTHORIZES, MINTS, WRITES, or DELEGATES. Edge attributes include scope, tenant, expiry, conditions, and provenance.

This is not cosmetic typing. A data-flow path issue -> model -> deployment may be expected. An authority path containing untrusted Data INFLUENCES Agent, Agent INVOKES Tool, and Tool WRITES production Environment is a candidate confused-deputy path unless an authorization edge from an accountable principal constrains the write.

The diagram deliberately separates reasoning from authority. The model never receives a reusable production secret. The broker evaluates an immutable action proposal: repository, commit digest, environment, operation, expiry, and approver. Approval of “deploy something later” is too broad; approval must bind to what will occur.

Assets, Boundaries, and Abuse Cases

Protect more than source code. Assets include signing identities, CI provenance, private dependencies, customer data in test fixtures, system prompts, tool schemas, long-term memory, audit evidence, approval channels, and the integrity of generated changes. Availability matters too: an agent can create costly build loops or exhaust API quotas without exfiltrating anything.

Trust boundaries occur at retrieval, model providers, plugin/tool servers, workspaces, credential brokers, approval interfaces, memory stores, and agent-to-agent messages. Treat retrieved content as data even when it looks like policy. A repository file named AGENT_INSTRUCTIONS.md may legitimately guide local behavior, but it cannot grant deployment rights. Only the authority plane can do that.

Threats fall into interacting families:

  1. Indirect prompt injection. An issue, README, test output, web page, or dependency description tells the agent to ignore policy, reveal context, or invoke a tool.
  2. Excessive agency. A legitimate objective is paired with permissions broader than required—write access to every repository, wildcard cloud roles, or an unbounded shell.
  3. Confused delegation. A parent agent gives a subagent a task but fails to attenuate credentials or communicate prohibitions. The child becomes a laundering step for authority.
  4. Memory poisoning. Untrusted claims become durable preferences or facts and influence later tasks after their origin is forgotten.
  5. Tool semantic mismatch. A tool called preview_change performs writes, parameters have surprising defaults, or the agent misunderstands an idempotency boundary.
  6. Supply-chain substitution. Models, MCP/tool servers, packages, container images, or retrieved indexes change without compatible attestation.
  7. Approval capture. The interface hides the true diff, batches unrelated actions, or conditions humans to approve repetitive prompts.

Risk for an abuse path can be prioritized as

\[ R(path)=P(activation)\times P(policy\ bypass\mid activation) \times Impact(authority)\times Persistence. \]

Do not pretend these factors are precisely known. Use ordinal ranges and test the paths. The graph is valuable because it identifies where to cut reachability: remove an edge, attenuate its scope, insert a policy decision, or change the target to a sandbox.

Design Rules for Coding Agents

Capabilities should be task-scoped, object-scoped, action-scoped, tenant-scoped, and time-bounded. Mint them just in time. A read token should not imply write; repository write should not imply merge; merge should not imply deployment. Separate the identity that proposes a change from the identity that approves it.

Run generated code only in disposable environments with no ambient credentials, constrained network egress, resource quotas, and immutable base images. “Sandboxed” is a claim requiring escape testing and a documented host boundary, not a checkbox.

Canonicalize tool requests before policy evaluation. Validate types, resolve symbolic references, make defaults explicit, and hash the normalized proposal. Bind approval to that digest. Re-evaluate policy at execution because repository state, approver role, or environment freeze may have changed.

Memory needs provenance, scope, expiry, and deletion. Separate user-authored preferences, observed facts, model hypotheses, and security policy. A model-generated note cannot overwrite policy. Cross-tenant memory is forbidden unless a separately governed aggregation explicitly permits it.

Executable Lab: Detect Dangerous Authority Paths

The lab builds a typed graph and rejects paths where untrusted data can influence a production write without an intervening authorization node. It is intentionally small enough to audit and uses only synthetic objects.

from dataclasses import dataclass
from collections import defaultdict, deque

@dataclass(frozen=True)
class Node:
    name: str
    kind: str
    trusted: bool = True

@dataclass(frozen=True)
class Edge:
    src: str
    rel: str
    dst: str

nodes = {
    n.name: n for n in [
        Node("issue", "Data", False), Node("agent", "Agent"),
        Node("shell", "Tool"), Node("broker", "Policy"),
        Node("approval", "Principal"), Node("deploy", "Tool"),
        Node("prod", "Environment")]
}

def unsafe_paths(edges):
    graph = defaultdict(list)
    for edge in edges:
        graph[edge.src].append(edge)
    queue = deque([("issue", ["issue"], False)])
    bad = []
    while queue:
        here, path, authorized = queue.popleft()
        for edge in graph[here]:
            now_auth = authorized or edge.rel == "AUTHORIZES"
            new_path = path + [f"-{edge.rel}->", edge.dst]
            if edge.rel == "WRITES" and edge.dst == "prod" and not now_auth:
                bad.append(" ".join(new_path))
            elif edge.dst not in path and len(path) < 12:
                queue.append((edge.dst, new_path, now_auth))
    return bad

unsafe = [Edge("issue", "INFLUENCES", "agent"),
          Edge("agent", "INVOKES", "deploy"),
          Edge("deploy", "WRITES", "prod")]
safe = [Edge("issue", "INFLUENCES", "agent"),
        Edge("agent", "PROPOSES", "broker"),
        Edge("approval", "AUTHORIZES", "broker"),
        Edge("broker", "AUTHORIZES", "deploy"),
        Edge("deploy", "WRITES", "prod")]

for name, edges in (("unsafe", unsafe), ("safe", safe)):
    bad = unsafe_paths(edges)
    print(f"{name}: dangerous_paths={len(bad)}")
    if bad:
        print(" ", bad[0])

Expected output:

unsafe: dangerous_paths=1
  issue -INFLUENCES-> agent -INVOKES-> deploy -WRITES-> prod
safe: dangerous_paths=0

The program is a design linter, not a proof of safety. Its authorization state is path-local; a production version must verify that approval actually binds to the proposed action, that the principal is eligible, and that no alternate write edge exists. Useful extensions check credential expiry, delegation attenuation, tenant equality, and forbidden Data -> AUTHORIZES relationships.

Operational Failure Analysis

Ambient credentials defeat the graph. If the workspace inherits a cloud token, the documented broker is fiction. Scan process environments and metadata endpoints from inside the sandbox; deny credential-bearing mounts by default.

Approval becomes ritual. Hundreds of low-context prompts teach operators to click. Aggregate only actions sharing a consequence boundary, show semantic diffs and destination, and require fresh confirmation for scope expansion. Measure approval reversals and time-to-review, not approval rate.

Tool descriptions drift. Policy may approve yesterday’s semantics. Pin tool versions, verify manifests, test side effects, and record the exact schema digest used for each call.

Delegation amplifies authority. A parent may have permissions that a research subagent does not need. Derive a child capability as an intersection of parent scope and task scope; never copy the parent token.

Egress turns read access into disclosure. A read-only agent can still leak secrets through HTTP, DNS, package names, logs, or pull-request text. Apply destination allowlists, content controls, secret scanning, and rate limits while recognizing none is perfect.

Rollback is incomplete. Reverting a commit does not revoke a leaked credential or remove published artifacts. Incident playbooks must cover credential rotation, package yanking, audit preservation, memory cleanup, and downstream notification.

Residual risk decisions

Not every dangerous path can be removed without eliminating the product. Document residual paths with preconditions, maximum authority, detective controls, recovery steps, and an accountable owner. “The model is unlikely to do that” is not ownership. A valid acceptance states why preventive control is disproportionate and when the decision expires.

Threat models decay as tools and workflows change. Re-run graph checks when adding a tool, widening repository scope, changing memory, enabling a model provider, or introducing delegation. Production telemetry should be compared with the graph: an observed edge absent from the model is an architecture incident, even when no harm occurred.

Source Synthesis

Schedule an explicit quarterly review even without announced changes, because undocumented integrations and emergency exceptions often create the most consequential new edges. Compare inventories, credentials, and observed tool calls against the approved graph.

Conducting the Threat-Model Workshop

Begin with one mission: “repair a vulnerable dependency and deploy it to staging.” Ask the owner to narrate the successful path while a facilitator creates typed nodes and edges. Record where identity changes, content crosses tenants, executable material enters, and irreversible effects occur. Challenge every authority edge: who granted it, what object and action does it cover, how long does it live, and which component mediates every use?

Mark data an attacker can influence directly or through a supply chain. Trace forward while preserving edge types. Reachability to a tool is not automatically a vulnerability; the decisive issue is whether influence can shape a consequential request that passes authorization. Absence of a direct arrow does not prove safety when shared memory, environment variables, caches, or human copy-and-paste create implicit edges.

Write abuse cases as executable propositions: “Given a malicious issue and legitimate bug-fix task, the agent causes CI to send a repository secret to an attacker endpoint.” Include preconditions, observable success, and assumed controls. This wording becomes a Chapter 36 scenario and determines Chapter 35 telemetry.

Policy as reference monitor

A trustworthy broker approximates complete mediation, tamper resistance, and analyzability. Every consequential invocation passes through it, including retries, alternate SDKs, and emergencies. It evaluates authenticated actor, tenant, tool, normalized object, action, environment, proposal digest, approval, time, and organizational state—not the model’s opinion of safety.

Decisions return reason codes and obligations. An allow may require restricted networking, maximum spend, or post-action verification. A deny identifies the rule without exposing bypass details. An escalation names eligible approvers and expiry. Unknown tool versions or unparsable arguments fail closed.

Multi-agent systems

Agent messages combine data and delegation. A planner can request research without granting repository access; an implementer can receive a workspace capability without cloud credentials. Attach a task contract containing objective, input references, allowed outputs, capabilities, expiry, and parent trace. Receivers must not infer authority from reputation or natural-language urgency.

Cycles are dangerous. Agents can reinforce an unverified claim or repeatedly delegate until the original constraint disappears. Bound depth, preserve the intersection of prohibitions, and demand fresh authorization for out-of-contract actions. Monitor resources across the whole delegation tree.

Assurance evidence

Replace “sandboxed” with testable claims: no host mount, egress only through a dependency proxy, cloud metadata unreachable, bounded resources, verified base image, and destroyed writable state. Each needs configuration evidence and adversarial testing.

Likewise, “human in the loop” is incomplete. Evidence must show the approver was authenticated, eligible, shown the canonical action and semantic diff, and that execution matched the approved digest before expiry. Without reconstruction, approval is ceremony.

NIST AI RMF supplies governance and lifecycle vocabulary; NIST’s Generative AI Profile focuses it on generative systems. OWASP catalogs practical LLM and agent failure patterns. MITRE ATLAS connects those patterns to adversary tactics and techniques. Saltzer and Schroeder’s least privilege and complete mediation remain the decisive architecture principles. SLSA adds artifact provenance. Together they imply that model alignment cannot substitute for external, typed, continuously mediated authority.

Interview Practicum

Threat-model a coding agent that reads private repositories, issues, and CI logs; writes branches; runs tests; and deploys to staging. Halfway through, the interviewer adds that product managers may paste customer tickets containing secrets, a subagent searches the public web, and emergency production deployment is desired during incidents.

Produce a typed authority graph, identify three abuse paths, and propose controls that preserve useful autonomy. Explain what evidence would convince you the controls operate as designed.

Worked Answer

I would type principals, data, agents, tools, credentials, environments, and policies, then enumerate INFLUENCES, READS, INVOKES, MINTS, AUTHORIZES, and WRITES edges. The primary abuse path is customer ticket to agent to egress tool, causing disclosure. The second is repository injection to branch writer to CI, causing execution with CI secrets. The third is web subagent to parent plan to emergency deploy, a confused-deputy path.

Tickets enter a secret-redaction boundary and remain untrusted. Public-web retrieval runs under a child capability with no repository or write access. Tests execute in an ephemeral, no-credential workspace with restricted egress. Branch writes use repository-scoped, short-lived tokens. Staging deploy requires a brokered token bound to artifact digest and environment. Production emergency access is a separate break-glass workflow with eligible incident commander approval, short expiry, immutable logging, and post-incident review; the agent cannot activate it.

I would verify the design with graph reachability tests, sandbox escape and egress tests, injected-content scenarios, credential canaries, tool-schema integrity checks, and audit replay showing each consequential action has a matching authorization digest. I would not claim that prompt filtering makes hostile content trusted.

Follow-Up Questions and Answers

The agent needs package downloads during tests. How do you constrain egress?

Use an authenticated dependency proxy with pinned namespaces, malware scanning, quotas, and no arbitrary URL fetch. Record resolved package digests. Exceptions require a new scoped decision.

Can the same human propose and approve an emergency deployment?

Only if explicit risk policy accepts that reduced separation during a declared incident. Make the exception visible, time-bound, and reviewed; do not let the agent infer emergency status.

Is read-only repository access low risk?

No. It exposes secrets, unreleased code, vulnerabilities, and customer context. Disclosure paths and cross-tenant mixing can be severe without any write.

Where should policy execute?

Outside the model and as close as practical to the consequential tool, with canonical inputs and complete mediation. Model instructions can guide behavior but cannot enforce authority.

Key Takeaways

  • Blast radius follows authority, not model capability.
  • Type nodes and edges so data influence cannot masquerade as authorization.
  • Bind approvals and short-lived credentials to canonical action digests.
  • Attenuate authority across every delegation.
  • Treat memory, tools, models, and retrieved content as supply-chain surfaces.
  • Prompt-injection resistance is defense in depth, never the authorization boundary.
