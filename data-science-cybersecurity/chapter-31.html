Chapter 31: From Finding to Resolution

Resolution Is a State History, Not a Closed Ticket

A scanner finding becomes security value only when a vulnerable condition is durably removed or bounded by an accepted control. Ticket closure is an administrative event. It may mean fixed, duplicate, risk accepted, asset retired, false positive, or merely closed by automation. Lifecycle analytics must preserve transitions and reasons instead of overwriting one status field.

CREATE TABLE finding_transition(
 transition_id TEXT PRIMARY KEY, finding_id TEXT NOT NULL,
 occurred_at TEXT NOT NULL, recorded_at TEXT NOT NULL,
 from_state TEXT, to_state TEXT NOT NULL,
 actor_type TEXT NOT NULL, owner_team TEXT,
 reason_code TEXT NOT NULL, evidence_uri TEXT,
 UNIQUE(finding_id,occurred_at,to_state,reason_code));
CREATE TABLE finding_snapshot(
 finding_id TEXT, snapshot_at TEXT, root_cause_id TEXT,
 severity TEXT, asset_tier TEXT, due_at TEXT,
 PRIMARY KEY(finding_id,snapshot_at));

A useful state machine distinguishes discovered, triaged, validated, owned, fix_in_progress, deployed, verified, risk_accepted, refuted, and reopened. Only verification establishes technical resolution. Preserve event time and recording time to diagnose delayed integrations. Invalid backward transitions—such as discovered directly to verified—should be rejected unless an explicit migration reason exists.

Queues, Competing Outcomes, and Censoring

Each transition has a waiting interval and a service interval. Long triage latency can mean too few analysts; long owned-to-fix latency can mean dependency coordination; long deployed-to-verified latency can mean missing telemetry. Aggregate “mean time to remediate” hides these mechanisms and is distorted by unresolved findings.

For time to verified resolution \(T\), the survival function is \(S(t)=P(T>t)\). With event times \(t_j\), resolutions \(d_j\), and findings at risk \(n_j\), the Kaplan–Meier estimator is

\[ \hat S(t)=\prod_{t_j\le t}\left(1-\frac{d_j}{n_j}\right). \]

Open findings are right-censored, not discarded and not assigned today as a fake closure date. Risk acceptance, asset retirement, and refutation are competing events. Treating them as remediation exaggerates engineering performance. Report cumulative incidence by terminal reason or use a competing-risks model.

Service-level statements should use cohorts and quantiles: “62% of internet-facing critical findings discovered in May were verified within 14 days,” with unresolved cases retained. Segment by ownership, asset tier, root cause, and discovery channel. Compare cohorts only after accounting for severity and exposure mix.

Durable Fixes and Downstream Reduction

A finding is durably fixed when verification passes after deployment and the root cause does not recur inside a defined observation window. Reopen rate is

\[ \frac{\text{verified findings later returned to active vulnerability}} {\text{verified findings with sufficient follow-up}}. \]

The denominator excludes fixes too recent to observe. Recurrence should be counted at root-cause level: repairing ten generated files while leaving the template unchanged produces ten closures and one predictable recurrence mechanism.

Measure downstream reduction using exposure-time, not ticket count. If a finding affects \(m\) reachable assets for \(h\) hours, it contributes \(mh\) vulnerable asset-hours. A program can close more low-impact tickets while total high-impact exposure rises. Developer friction also matters: handoffs, build failures introduced by fixes, review minutes, exception churn, and unplanned work.

Safe Lab: Kaplan–Meier Without External Packages

# duration in days; event=1 only for verified remediation
records = [(2,1),(3,1),(3,0),(5,1),(7,0)]

def kaplan_meier(rows):
    survival = 1.0
    curve = []
    for t in sorted({d for d,e in rows if e == 1}):
        at_risk = sum(d >= t for d,e in rows)
        events = sum(d == t and e == 1 for d,e in rows)
        survival *= 1 - events / at_risk
        curve.append((t, round(survival, 3), at_risk, events))
    return curve

curve = kaplan_meier(records)
expected = [(2, .8, 5, 1), (3, .6, 4, 1), (5, .3, 2, 1)]
assert curve == expected, curve
assert round(1 - curve[-1][1], 3) == .7
print(curve)

The censored observations remain in the risk set until their last observed day. Dropping them would claim every retained case eventually resolved and bias the result toward fast closure.

Diagnosing Flow Rather Than Blaming Teams

Reconstruct transitions with window functions and measure time in each state:

WITH ordered AS (
 SELECT finding_id, occurred_at, to_state,
        LEAD(occurred_at) OVER(PARTITION BY finding_id ORDER BY occurred_at) AS next_at
 FROM finding_transition
), dwell AS (
 SELECT finding_id, to_state,
        (julianday(COALESCE(next_at,'2026-08-20'))-julianday(occurred_at))*24 AS hours
 FROM ordered
)
SELECT to_state, ROUND(AVG(hours),1) AS mean_hours, COUNT(*) AS intervals
FROM dwell GROUP BY to_state ORDER BY mean_hours DESC;

This SQLite-compatible query uses an explicit analysis cutoff. Production code should parameterize it. Means are useful for workload accounting; publish medians and upper quantiles for latency. A growing queue can arise from arrivals exceeding service capacity even when individual engineers work faster. Track arrival rate, work-in-progress, throughput, blocked time, and age distribution together.

Production Failure Analysis

Status overwrite: a current-state table cannot reconstruct history. Use append-only transitions and correct errors with compensating events.

Closure semantics: automatic closure after a repository archive is not remediation. Terminal reason codes are mandatory.

Survivorship bias: analyzing only resolved findings guarantees optimistic latency. Include right-censored open cases.

Reopen blind spots: scanner suppression can make a defect disappear without a code change. Verification should cite deployment evidence and scanner coverage.

Ownership gaming: reassignment can reset clocks. SLA clocks attach to the finding and policy, while state dwell identifies where delay accumulated.

More findings, less security: a detector release can flood teams with low-value claims, displace high-risk remediation, and raise vulnerable asset-hours. Rate-limit intake, group root causes, protect an urgent queue, and monitor displacement.

Policy changes: a shorter SLA changes queue behavior and censoring. Version policy at discovery and show results under both historical and current definitions rather than rewriting history.

For causal claims about a workflow change, do not compare simple before/after means. Use phased rollout, matched teams with pre-trend checks, or randomized encouragement. Outcomes should include verified resolution, recurrence, exposure-time, incidents, and developer toil; closure volume alone is manipulable.

Engineering the Lifecycle Ledger

An append-only transition log needs deterministic rules. Every event carries an idempotency key from the source system, event time, ingestion time, actor, and reason. Consumers derive current state by replay. If a connector sends an older transition late, insert it at its event time and rebuild the affected finding; do not append it as if it happened now. Record the correction so dashboards can explain why historical counts changed.

State definitions must name evidence. validated might require reproduction or independent configuration proof. deployed requires the change to reach the affected environment, not merely merge. verified requires a post-deployment test, scanner observation, or configuration assertion. For ephemeral cloud assets, verification may mean the vulnerable image is no longer deployable and all running instances have rotated. Each evidence type has a freshness window.

Some findings legitimately branch. One root cause may affect five services owned by different teams; a central library fix is deployed gradually. Model a root-cause remediation and its affected-instance coverage rather than forcing one ticket to represent both. The root cause can be fixed in the library while residual vulnerable instances remain. Report both states to avoid celebrating upstream completion before downstream adoption.

Queue mechanics

Little’s Law, \(L=\lambda W\), relates average work in progress \(L\), throughput rate \(\lambda\), and average time in system \(W\) under stable conditions. It is a diagnostic, not a promise. If arrival rate changes sharply or the queue is not stable, the relationship’s assumptions fail. Still, it gives a useful consistency check: a team closing 100 items per week with 1,000 active items cannot plausibly sustain a two-week average lifecycle.

Age distributions reveal starvation. Report the count and risk-weighted exposure in age bands, plus the oldest items. Priority queues can starve medium findings indefinitely when critical arrivals consume all capacity. Reserve capacity or impose aging rules, but verify that aging does not let low-impact bulk overwhelm scarce specialist work. Root-cause batching can improve throughput while reducing context switching.

Handoffs deserve explicit events rather than inferred owner changes. A handoff records sender, receiver, requested action, acceptance, and time. Unaccepted assignments are queue failures. Count bounced ownership and time awaiting acceptance. An ownership directory improvement may reduce latency more than a better severity model.

Survival models beyond a single curve

Kaplan–Meier compares descriptive cohorts but does not adjust for covariates. A Cox proportional-hazards model can estimate associations with resolution rate while leaving the baseline hazard unspecified. Its hazard ratio assumes proportional effects over time; inspect residuals and time interactions. Team identity, severity, and asset tier may be confounded with unmeasured complexity, so do not turn coefficients into blame.

Accelerated failure-time models can express multiplicative effects on resolution time and may be easier to communicate. Competing-risk methods are needed when remediation, risk acceptance, retirement, and refutation preclude one another. For operational forecasting, multi-state models can estimate transition-specific hazards: discovery to triage, triage to ownership, ownership to deployment, and deployment to verification.

Calendar time matters. Freeze periods, holidays, release trains, and incident response affect hazards. Use time-varying covariates or stratified reporting. Findings created just before a year-end freeze should not be used to claim one product team is intrinsically slower. Similarly, a policy that accelerates critical work may delay medium work; evaluate the full risk-weighted queue.

Measuring durable remediation

Define an observation window based on how recurrence can be detected. A weekly scanner might need several clean scans; a deployment control can verify immediately that an image digest is blocked. Mark findings “verified pending durability” until follow-up matures. Report cohort maturity so recent improvements are not credited with artificially low recurrence.

Recurrence can be exact, mechanistic, or organizational. Exact recurrence is the same finding identity. Mechanistic recurrence is the same root-cause pattern in another location. Organizational recurrence is a new defect that the same preventive control should have stopped. These answer different questions: fix quality, systemic remediation, and prevention effectiveness.

Downstream reduction should use a stable eligible denominator. If repository coverage expands, detected vulnerability count may rise while rate falls. Report eligible assets, scanned assets, reachable vulnerable assets, and vulnerable asset-time. A program that discovers previously invisible exposure should not be punished as if it created the defects; conversely, coverage loss must not look like improvement.

Safe rollout of workflow automation

Automation can assign owners, propose duplicates, open patches, or verify deployments. Authority should rise with evidence. Begin with recommendations, measure correction rates, then allow bounded actions with rollback. Auto-closing findings is high consequence because it removes work from human view; require stronger evidence than auto-tagging.

Monitor automation-specific failures: wrong owner, duplicate cluster over-merge, broken generated patch, tests skipped, verification against the wrong environment, and rollback failure. Keep an untreated or delayed cohort when feasible. If automation reduces visible backlog by suppressing items, verify that vulnerable asset-time and incident precursors also improve.

Governance must align incentives across scanner, security operations, and product engineering. Scanner teams should not win by emitting volume; product teams should not win by administrative closure; security teams should not win by transferring unplanned work. Shared outcomes—verified root-cause reduction, bounded exposure-time, recurrence, and total effort—make local gaming harder.

A Worked Operational Interpretation

Imagine two business units with a 20-day median time to verified resolution. Unit A resolves most items between 15 and 25 days. Unit B resolves half within two days while a long tail remains open for six months. The medians are equal, but Unit B accumulates much more exposure. Publish survival curves, restricted mean unresolved time over a policy horizon, upper quantiles, and risk-weighted age. A single central tendency cannot describe a queue.

Next, a new dependency bot creates one ticket per repository. Closure throughput triples, yet one vulnerable base image remains the common root cause. The lifecycle model should link repository findings to the image remediation and deployment coverage. Closing child tickets before images rotate is administrative progress, not verified risk reduction. Conversely, once the fixed image is enforced and workloads rotate, child findings can be resolved with shared evidence rather than repetitive manual review.

SLA analysis needs the same discipline. A finding can meet a 30-day SLA because it was accepted on day 29, while exposure remains unchanged. Report compliance by terminal reason, and show the fraction truly verified. Pause rules—waiting for a vendor, freeze, or customer approval—should not erase elapsed exposure. Maintain both calendar time and policy-accountable time; the former represents risk, the latter helps diagnose controllable process delay.

Cost accounting should distinguish touch time from wait time. Developers may spend two hours fixing a defect that sits unowned for three weeks. Reducing wait improves risk without reducing engineering effort. Conversely, automated patch generation may reduce touch time but increase failed builds and review cycles. Instrument both so workflow improvements are attributed to the correct mechanism.

Data retention is part of the measurement design. Transition histories may contain vulnerability detail and employee identifiers. Apply least privilege, tenant boundaries, retention schedules, and auditable access. Aggregate long-term analytics where detailed evidence is no longer required, while retaining hashes and policy versions sufficient to prove lineage. Deleting raw evidence should not silently change historical state reconstruction.

Finally, incident learning should feed the ledger. When an incident exploits a previously known finding, link the incident, reconstruct the lifecycle as it was known, and classify the failure: detection absence, invalid disposition, ownership delay, remediation delay, failed deployment, missing verification, or recurrence. This is not for blame. It tests whether lifecycle metrics represented real exposure and identifies which transition needs redesign.

Interview Practicum

Scenario: Throughput Doubles and Risk Rises.

Prompt. A security program doubled monthly closures after deploying automatic ticketing, yet incidents involving known weaknesses increased. Diagnose it.

Ask for transition history, terminal reasons, scanner coverage, arrivals, severity/exposure mix, root-cause grouping, verification, reopen windows, and asset-hours.

Worked Answer

Build cohorts by discovery date, estimate time to verified resolution with censoring, separate competing terminal states, and compare high-risk exposure-time and recurrence.

Follow-Up Questions and Answers

Change one: old tickets were bulk-closed as “asset retired,” but retirement evidence is unavailable. Do not call them remediated. Classify them as administratively closed with uncertain technical outcome; sample assets and inventory records, and publish a sensitivity range.

Change two: product teams say security tickets consume 18% of sprint capacity. Optimize intake as well as remediation: suppress confirmed duplicates, group by fix boundary, provide reproducible evidence, and reserve capacity by expected harm. Measure build failures and handoffs so security does not externalize its costs.

Change three: leadership requires a 30-day result. Durable recurrence needs 90 days. Report leading outcomes—verified deployment, vulnerable asset-hours, and queue age—marked provisional. Pre-register the 90-day recurrence analysis rather than redefining success at day 30.

Weak answers divide close date by open date only for resolved tickets, treat risk acceptance as a fix, or celebrate closure volume. A Principal answer also changes incentives so scanners, analysts, and product teams share verified root-cause reduction rather than local throughput targets.

Key Takeaways

  • Preserve append-only state transitions and terminal reasons.
  • Use survival analysis because unresolved findings are right-censored.
  • Treat risk acceptance, retirement, and refutation as competing outcomes, not fixes.
  • Measure root-cause recurrence and vulnerable asset-time, not ticket closure alone.
  • Diagnose arrival rate, queues, dwell, throughput, and friction together.
  • Version lifecycle policy and verification evidence so history remains auditable.
