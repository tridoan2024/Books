Chapter 41: Reproducible Security Analytics with Python and SQL

An investigation is reproducible only when another analyst can reconstruct the same evidence boundary, run the same transformations, and explain any difference in output. A notebook that still executes is not enough. Security data is corrected late, identity mappings change, intelligence feeds are revised, and labels arrive after decisions. Reproducibility therefore means preserving what was knowable at decision time, not merely preserving code.

This chapter builds an account-compromise analytic that produces a daily review queue. Its four invariants are: no feature uses evidence observed after cutoff; every output names its code, data, contract, and parameter versions; replaying one manifest produces identical logical rows; and ambiguous provenance or time semantics stop publication.

The Repository Is an Evidence Product

Use notebooks for exploration, but make reviewed modules and declarative queries authoritative:

security-analytics/
├── pyproject.toml
├── README.md
├── contracts/auth_event.v3.json
├── sql/point_in_time_features.sql
├── src/sec_analytics/{normalize,manifest,pipeline}.py
├── tests/{fixtures,test_contract,test_point_in_time,test_replay}.py
├── notebooks/001-investigation.ipynb
├── manifests/
└── reports/

The README begins with the decision contract: “At 06:00 UTC, rank identities for analyst review using evidence observed by 05:55 UTC; never automatically disable an account.” That limits both data and authority. It also gives tests something operational to enforce.

Do not commit credentials, production extracts, or reversible identifiers. Synthetic fixtures should preserve late arrival, duplicate delivery, changed mappings, and boundary timestamps without preserving real users or attack detail.

Hashes prove that an artifact did not change after hashing. They do not prove the producer was truthful or the query correct.

A Point-in-Time Contract

An authentication contract needs temporal and provenance fields.

FieldRulePurpose
event_idnon-null, producer-stablededuplication and traceability
principal_keytokenizedstable analytical subject
event_timeUTC source timewhen behavior occurred
observed_atUTC collector timewhen the pipeline could know it
sourceidp, vpn, or cloudprovenance and coverage
outcomesuccess, failure, or challengedefined result
country_codeISO code or nullunknown is not zero
schema_versionexactly 3compatibility gate
payload_hashcanonical digestmutation detection

The producer owns field meaning and delivery expectations. The analytic owner owns acceptance rules. The platform owner owns retention and access. Changing challenge from “issued” to “completed” is breaking even if its SQL type is unchanged.

For cutoff \(t_c\), eligible evidence is

\[ \mathcal{E}(u,t_c)=\{e:e.principal=u,\ e.observed\_at\le t_c,\ e.event\_time\le t_c\}. \]

Using only event time leaks late records into historical replays. Using only observation time admits malformed future events. A correction received tomorrow belongs to tomorrow’s knowledge state unless the output is explicitly a revised historical result.

Identity joins are also temporal. If mappings have valid_from, valid_to, and recorded_at, a cutoff query requires both business validity and knowledge availability:

WITH eligible AS (
  SELECT * FROM auth_event
  WHERE event_time <= :cutoff AND observed_at <= :cutoff
    AND schema_version = 3
), mapped AS (
  SELECT e.*, m.employee_id
  FROM eligible e JOIN identity_map m
    ON e.principal_key = m.principal_key
   AND e.event_time >= m.valid_from
   AND e.event_time < COALESCE(m.valid_to, '9999-12-31')
   AND m.recorded_at <= :cutoff
)
SELECT employee_id, COUNT(*) AS attempts_24h,
       SUM(CASE WHEN outcome='failure' THEN 1 ELSE 0 END) AS failures_24h,
       COUNT(DISTINCT country_code) AS countries_24h
FROM mapped
WHERE event_time > :cutoff - INTERVAL '24 hours'
GROUP BY employee_id;

Database syntax varies; semantic tests should not. Define window inclusivity, null geography, time zones, and conflicting duplicates. Leaving those choices implicit destroys reproducibility.

Manifests and Deterministic Builds

Every published queue carries a manifest:

{
  "run_id": "ato-queue/2026-08-20T055500Z",
  "decision_cutoff": "2026-08-20T05:55:00Z",
  "code_revision": "8f31c2d",
  "dependency_lock_sha256": "21c8...",
  "contract": "auth_event.v3",
  "raw_snapshot": "auth/2026-08-20/snapshot-17",
  "identity_snapshot": "identity/2026-08-20/snapshot-04",
  "query_sha256": "a9de...",
  "parameters": {"window_hours": 24, "queue_size": 200},
  "row_count": 200,
  "logical_output_sha256": "55ae..."
}

Hash a canonical logical representation: stable columns, explicit nulls, normalized timestamps, defined numeric precision, and rows sorted by a total key. Parquet or gzip bytes can differ because of metadata while logical rows agree. Sorting only by score is insufficient when scores tie; use (-risk_score, employee_id).

If audit sampling uses randomness, record generator algorithm, seed, population hash, and code version. “Seed 42” alone is not portable across implementations.

Tests That Defend the Claim

Contract tests reject missing fields, incompatible versions, invalid enums, duplicate keys, and impossible timestamps. Named examples test semantics, not merely JSON types.

Transformation tests use tiny fixtures. Include events exactly at cutoff and just after, a late event, a conflicting duplicate, a mapping recorded after cutoff, and null geography.

Metamorphic tests assert that input permutation changes nothing, adding post-cutoff evidence changes no historical output, duplicate replay does not increase counts, and renaming a display field does not affect scores.

Golden replay tests compare a fixed manifest’s canonical output hash. Changes require human review. Automatically rewriting the golden hash turns a tripwire into decoration.

Tests must also assert failure: absent snapshot, unknown contract, ambiguous duplicate, or missing cutoff stops publication. A plausible report built from partial evidence is more dangerous than a visible failure.

Safe Lab: Replay a Tiny Pipeline

This standard-library program uses synthetic identities and in-memory SQLite. It performs no network or system action.

import hashlib, json, sqlite3
CUTOFF = "2026-08-20T05:55:00Z"
events = [
 ("e1","alice","2026-08-20T05:00:00Z","2026-08-20T05:00:02Z","failure"),
 ("e2","alice","2026-08-20T05:10:00Z","2026-08-20T06:10:00Z","failure"),
 ("e3","bob",  "2026-08-20T05:55:00Z","2026-08-20T05:55:00Z","success"),
 ("e4","bob",  "2026-08-20T05:56:00Z","2026-08-20T05:54:00Z","failure"),
 ("e5","carol","2026-08-20T04:00:00Z","2026-08-20T04:00:01Z","failure"),
]
def build(rows):
    db=sqlite3.connect(":memory:")
    db.execute("CREATE TABLE auth(event_id TEXT PRIMARY KEY, principal TEXT, event_time TEXT, observed_at TEXT, outcome TEXT)")
    db.executemany("INSERT INTO auth VALUES(?,?,?,?,?)", rows)
    result=db.execute("""SELECT principal,COUNT(*),SUM(outcome='failure')
      FROM auth WHERE event_time<=? AND observed_at<=?
      GROUP BY principal ORDER BY 3 DESC,principal ASC""",(CUTOFF,CUTOFF)).fetchall()
    canonical=json.dumps(result,separators=(",",":"))
    return result,hashlib.sha256(canonical.encode()).hexdigest()[:12]
baseline,digest=build(events)
permuted,digest2=build(list(reversed(events)))
with_future,digest3=build(events+[("e6","alice","2026-08-20T05:20:00Z","2026-08-20T07:00:00Z","failure")])
assert baseline==[("alice",1,1),("carol",1,1),("bob",1,0)]
assert baseline==permuted==with_future
assert digest==digest2==digest3
print(baseline); print("replay_hash",digest); print("point_in_time_tests PASS")

Expected output:

[('alice', 1, 1), ('carol', 1, 1), ('bob', 1, 0)]
replay_hash d3b5c1dfe930
point_in_time_tests PASS

e4 was observed before cutoff but claims a future event time, so it is excluded. e2 and e6 occurred before cutoff but were not yet observed. Production code would quarantine excessive clock skew.

Production Failure Drill: The Helpful Backfill

At 09:00, the identity platform repairs three missing hours. The scheduled job overwrites the 06:00 report. The revision is statistically better but operationally false: analysts acted on the original queue, and their evidence has disappeared.

In staging, publish manifest M1; inject a late partition; rerun M1 and verify its snapshot retains the original hash; publish immutable revision M2 linked by late-data-correction; prove decision records retain M1; then reconcile decisions that would change.

The stop condition is a mutable snapshot, overwritten report, or decision without a manifest. Containment disables publication, not ingestion. Recovery restores snapshot immutability and replays both versions. The analytic owner declares output correctness; the platform owner repairs snapshot guarantees; the incident commander coordinates consumers.

Review, Promotion, and Retirement

A pull request shows the changed decision, contract compatibility, fixture additions, query plan, expected cost, temporal tests, privacy review, and a manifest from a clean build. Review SQL and Python together: a sound function fed by a leaky query is wrong.

Review the analytical diff, not only the source diff

A five-line SQL edit can reorder thousands of investigations. Code review therefore needs an analytical diff: run incumbent and candidate against the same frozen manifests and summarize added, removed, and re-ranked subjects. Partition disagreements by cause—new eligibility, feature change, score change, tie-breaking, missing evidence, or policy threshold. For each category, include counts, representative synthetic or authorized examples, and affected consequence segments.

Suppose a change replaces COUNT(DISTINCT country_code) with a mapping from IP to travel region. A source diff shows a join and a grouping change. The analytical diff should show that 18% of identities lose one “country,” that airport egress users move down the queue, that null geography increases in one source, and that the top-200 overlap is 82%. Reviewers can then decide whether the change fixes false diversity or conceals a coverage regression.

Compare outputs under at least three manifests: a normal day, a known late-data day, and an edge-case fixture. Report set overlap, rank correlation where meaningful, action transitions, group coverage, and output invariants. A high rank correlation can still hide a severe subject crossing an action threshold; always inspect decision changes directly.

The query plan is also evidence. Capture scanned partitions, join strategy, estimated rows, runtime, and bytes processed under a representative snapshot. A semantically correct query that unpredictably scans an entire authentication lake is not ready for a scheduled production deadline. Place a cost ceiling in the run contract and fail before publication when the ceiling is exceeded, unless an authorized override names the reason and expiry.

Clean-room reconstruction

Before first production release, ask an engineer who did not write the analytic to reconstruct one report from the repository and manifest in a clean environment. Give that person read access only to the declared snapshots and artifact registry. They should not need the author’s shell history, notebook state, personal configuration, or undocumented warehouse table.

The reconstruction record answers:

  • Could dependencies be installed from the lock without contacting an unapproved package source?
  • Did the manifest identify every input, including lookup tables and policy parameters?
  • Did the environment use the expected timezone, locale, and SQL engine settings?
  • Did the canonical rows and reason codes match?
  • If physical files differed, was the difference limited to declared metadata?
  • Could the reviewer trace one queue row back to eligible source events without privileged raw identifiers in the report?

Clean-room failure is useful. If the analytic relies on a hidden notebook cell or an analyst’s temporary table, the organization has found the defect before an audit or incident. Record the fix as a repository change; do not solve the exercise by granting broad access or copying an unexplained table.

Data minimization and reproducibility

Reproducibility does not require retaining every raw field forever. It requires retaining enough authorized evidence to support the declared audit and replay claims. Classify fields as transformation inputs, trace references, sensitive investigation content, or irrelevant payload. Preserve immutable source identifiers and approved derived facts where possible; store direct identifiers in a separately controlled resolution service.

If policy requires deleting a field, manifests should record the deletion class and date. A later replay may then be method-reproducible but not result-reproducible. State that distinction. Privacy deletion is not a pipeline defect, and a hash of deleted content cannot reconstruct it. The design goal is an honest assurance boundary: who can reproduce which claim, for how long, under which authorization.

Scheduling and idempotency

The scheduler passes an explicit cutoff and manifest identifier; the pipeline must never infer “now” in transformation code. A retry with the same manifest writes the same logical output and does not create a second analyst task. Use a publication key derived from the run ID and output revision. Computation may be retried freely; external side effects require idempotency and a separate promotion step.

Separate computed, validated, and published states. A job can finish SQL successfully yet fail coverage validation. It must not become the current report. Publication should atomically move a reviewed pointer to an immutable artifact, leaving the previous good version available for rollback. Dashboards display cutoff, freshness, revision, coverage, and manifest link so users can recognize stale or corrected evidence.

The deployable unit is (code, query, contract, parameters, dependencies, runbook). Roll it back together. Retire an analytic when its decision no longer exists, its contract cannot be supported, or a simpler reviewed rule produces equivalent decisions. Archive the final manifest and known limits so the organization does not rediscover the same dead end.

  • SLSA Specification supplies provenance concepts; here they are adapted to analytics without pretending provenance validates data truth.
  • NIST SP 800-218, Secure Software Development Framework supports reviewed changes, protected artifacts, and tested releases.

The synthesis is that software provenance is necessary but insufficient. Security analytics also needs knowledge-time lineage connecting mutable evidence to the exact state visible when a decision was made.

Interview Practicum

Scenario. A notebook identified compromised accounts with impressive precision. Leadership wants it scheduled Friday. Warehouse history is continuously corrected, the identity team cannot provide old mapping snapshots, and audits may occur a year later.

Prompt. Productionize the investigation without claiming reproducibility the platform cannot provide.

A strong candidate asks: What action is authorized? What cutoff and latency apply? Can raw partitions or change logs be retained? How are mapping corrections recorded? What late-data policy is acceptable? Which object must match—bytes, logical rows, ranking, or conclusion? Who signs off on incomplete evidence?

Then the interviewer adds: raw retention is seven days, and legal policy prohibits retaining raw IP addresses in analytical artifacts.

Worked Answer

I would narrow the first release to an analyst-review queue with no automated disable action. Eligibility uses event and observation time. Because warehouse history mutates, I would create immutable input snapshots or change-log-backed identifiers before calling any rerun reproducible.

The repository separates reviewed SQL, Python, contracts, synthetic fixtures, manifests, and generated reports. Each row links to reason codes and tokenized evidence. The manifest records code, lockfile, query hash, cutoff, raw and identity snapshots, parameters, contract, count, and canonical output hash.

Missing historical identity snapshots block claims about past entity features. For Friday, use stable principal keys or require append-only mapping changes with validity and recording times. Document that earlier periods cannot be faithfully replayed.

For seven-day retention, preserve a privacy-reviewed evidence capsule: tokenized principal, approved coarse geography, feature inputs, source hashes, contract, and snapshot attestations. Do not retain raw IPs. Whether that supports a one-year audit is an audit and legal decision; escalate the conflict rather than invent a guarantee.

Tests cover cutoff equality, late events, future timestamps, duplicate conflicts, mapping corrections, nulls, permutation, clean-environment replay, and missing provenance. Shadow the notebook and reconcile disagreements. Stop publication on an unknown contract, missing snapshot, or non-canonical output.

Follow-Up Questions and Answers

Why not pin the notebook environment? It preserves execution, not historical evidence or identity semantics.

Must bytes match? No. Hash a canonical logical form while tracking physical artifacts separately.

How do you test billion-row SQL locally? Exact fixtures and metamorphic tests locally; bounded integration, scale, and query-plan tests in an isolated warehouse.

What if a correction is more accurate? Publish a linked revision; never erase the version used for action.

What makes this Principal-level? It treats retention, identity history, audit claims, and authority as cross-system contracts and limits launch rather than offering false assurance.

Key Takeaways

  • Reproducibility reconstructs the evidence state at decision time, not merely the code.
  • Point-in-time correctness requires event time, observation time, and historical dimension semantics.
  • A manifest binds code, dependencies, contracts, snapshots, parameters, and canonical output.
  • Boundary, negative, metamorphic, and golden-replay tests protect different failure surfaces.
  • Corrections create immutable revisions; they never overwrite evidence of earlier decisions.
