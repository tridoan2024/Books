Chapter 24: Statistical Detection Engineering

An analyst’s useful observation is not yet a production detection. “Many failures followed by a success from one network” leaves unanswered what counts as many, which entities share a baseline, how VPN outages behave, when event time closes, what evidence an alert carries, and how the rule changes safely. Statistical detection engineering turns a threat hypothesis into a versioned analytical product whose assumptions can fail visibly.

This chapter builds a password-spray detection. The adversary attempts a small number of passwords across many accounts, often avoiding per-account lockout. A fixed threshold on total failures is inadequate: corporate egress gateways produce high legitimate counts, tenants differ by orders of magnitude, and outages create bursts. The design combines an explicit sequence rule with an overdispersed count baseline and a change detector.

Threat Hypothesis and Observable Sequence

The threat hypothesis is:

A source that fails authentication against an unusually diverse set of accounts and then succeeds against one of those accounts within 20 minutes may be conducting password spraying.

This maps to MITRE ATT&CK credential-access behavior, but ATT&CK technique mapping is not evidence of correctness. The observable sequence requires:

  1. at least 12 distinct target accounts;
  2. at least 18 failed attempts in a 10-minute event-time window;
  3. no single target contributes more than 25% of failures;
  4. the source’s count is anomalous for its peer class;
  5. a success for a targeted account within 20 minutes raises severity.

The unit is a normalized source principal, not raw IP. NAT egress, trusted scanners, identity-provider health checks, and Tor exits need distinct peer classes. IPv4 and IPv6 normalization, forwarded-address trust, and cloud proxy attribution belong in the data contract.

Concrete Event and Alert Schemas

CREATE TABLE authentication_event (
    event_id          TEXT PRIMARY KEY,
    event_time        TEXT NOT NULL,
    ingest_time       TEXT NOT NULL,
    tenant_id         TEXT NOT NULL,
    source_key        TEXT NOT NULL,
    source_class      TEXT NOT NULL,
    target_account    TEXT NOT NULL,
    outcome           TEXT NOT NULL CHECK (outcome IN ('success','failure')),
    auth_protocol     TEXT NOT NULL,
    device_trust      TEXT,
    sensor_version    TEXT NOT NULL
);

CREATE INDEX auth_window
ON authentication_event(tenant_id, source_key, event_time);

CREATE TABLE detection_alert (
    alert_id          TEXT PRIMARY KEY,
    window_end        TEXT NOT NULL,
    tenant_id         TEXT NOT NULL,
    source_key        TEXT NOT NULL,
    rule_id           TEXT NOT NULL,
    rule_version      TEXT NOT NULL,
    failure_count     INTEGER NOT NULL,
    distinct_targets  INTEGER NOT NULL,
    max_target_share  REAL NOT NULL,
    tail_probability  REAL NOT NULL,
    follow_on_success INTEGER NOT NULL,
    severity          TEXT NOT NULL,
    evidence_event_ids TEXT NOT NULL
);

The alert stores evidence references and intermediate statistics. A scalar “risk score” would make investigation and regression testing harder. Evidence events remain immutable; suppression and disposition are separate lifecycle records.

A compatible SQL candidate generator

SQLite can generate candidate windows at a fixed boundary. Production stream processors use event-time windows and watermarks, but the aggregation semantics should match:

WITH failures AS (
    SELECT tenant_id, source_key, target_account, COUNT(*) AS attempts
    FROM authentication_event
    WHERE outcome = 'failure'
      AND event_time >= '2026-08-20T10:00:00Z'
      AND event_time <  '2026-08-20T10:10:00Z'
    GROUP BY tenant_id, source_key, target_account
),
source_summary AS (
    SELECT tenant_id,
           source_key,
           SUM(attempts) AS failure_count,
           COUNT(*) AS distinct_targets,
           1.0 * MAX(attempts) / SUM(attempts) AS max_target_share
    FROM failures
    GROUP BY tenant_id, source_key
)
SELECT *
FROM source_summary
WHERE failure_count >= 18
  AND distinct_targets >= 12
  AND max_target_share <= 0.25;

This query generates candidates; it does not yet incorporate peer expectation, late events, or follow-on success.

Why a Negative-Binomial Baseline Fits Better

If counts arose from a homogeneous Poisson process, mean and variance would both equal lambda. Authentication failures are heterogeneous and bursty; variance usually exceeds the mean. A gamma–Poisson mixture yields a negative-binomial distribution with E[Y] = mu and Var[Y] = mu + alpha * mu^2, where alpha > 0 captures overdispersion. Model log expected failures as an intercept plus hour-of-day, weekday, log active accounts as an exposure offset, and a source-class effect.

The exposure offset prevents a large tenant from being anomalous merely because it has more accounts. Estimate on a trailing period that excludes known incidents and the current window. Use a survival function (P(Yge ymidmu,alpha)), but do not treat it as a calibrated attack probability. It measures incompatibility with the baseline model.

For sparse sources, shrink toward the peer class instead of fitting unstable personal means. A source with two historical windows cannot support a reliable per-source threshold. High-volume corporate proxies may have their own baseline only after enough uncontaminated history.

Robustness Against Hostile and Broken Data

Attackers can poison rolling means by slowly increasing traffic. Outages can inflate both mean and variance. Robust alternatives bound influence:

  • median and median absolute deviation, MAD = median(|x_i - median(x)|);
  • trimmed estimation windows;
  • winsorized counts for baseline fitting, while preserving raw counts for evidence;
  • exclusion of declared identity-provider incidents;
  • peer medians with minimum cohort size.

For approximately symmetric data, a robust z-score is 0.6745 * (x - median(X)) / MAD(X).

Count data are neither symmetric nor continuous at low means, so MAD is a fallback diagnostic, not a universal replacement for count models.

Detecting persistent low-and-slow change

A one-window tail test misses an attacker that remains mildly elevated. A one-sided Page CUSUM accumulates evidence as S_t = max(0, S_(t-1) + x_t - (mu_0 + k)) and signals when S_t > h. The allowance k sets the smallest sustained shift worth accumulating; h trades delay against false alarms. Reset or freeze CUSUM during known sensor outages. An exponentially weighted moving average, Z_t = lambda*x_t + (1-lambda)*Z_(t-1),

is easier to explain but smears a sharp burst into subsequent windows.

The production detector uses the deterministic diversity sequence as a semantic gate, negative-binomial tail probability for contextual rarity, and CUSUM for persistence. No weighted sum is necessary:

if sequence_gate and follow_on_success: severity = HIGH
elif sequence_gate and (tail_p < 0.001 or cusum_alarm): severity = MEDIUM
else: no alert

This preserves reason codes and makes policy changes reviewable.

Detection-as-Code Artifact

A repository artifact should include threat reference, required fields, logic, tests, and ownership:

id: identity.password_spray.follow_on_success
version: 3
status: canary
owner: identity-detection
event_time:
  window: 10m
  allowed_lateness: 3m
group_by: [tenant_id, source_key]
requirements:
  sensor_versions: [auth-v4, auth-v5]
gate:
  failures_min: 18
  distinct_targets_min: 12
  max_target_share: 0.25
context:
  peer_tail_probability_max: 0.001
sequence:
  follow_on_success_within: 20m
response:
  medium: analyst_queue
  high: revoke_session_and_queue
fallback:
  on_baseline_unavailable: sequence_only_medium

Schema validation should reject unknown keys and invalid durations. The high-severity response is more consequential, so it requires the success sequence and must have a tested recovery path.

Safe Runnable Lab: Behavioral Spray Detection

The lab creates a benign proxy burst concentrated on two accounts and a distributed spray across eighteen accounts. It tests the semantic distinction rather than generating attack traffic.

from collections import Counter
from dataclasses import dataclass

@dataclass(frozen=True)
class Auth:
    minute: int
    source: str
    account: str
    outcome: str

events: list[Auth] = []

# Benign retry storm: high volume, low target diversity.
events += [Auth(i % 10, "corp-proxy", f"svc-{i % 2}", "failure") for i in range(30)]

# Synthetic distributed spray and one follow-on success.
events += [Auth(i % 10, "198.51.100.8", f"user-{i:02d}", "failure") for i in range(18)]
events.append(Auth(14, "198.51.100.8", "user-07", "success"))

def candidate(source: str) -> tuple[bool, dict[str, float]]:
    failures = [e for e in events if e.source == source and e.outcome == "failure" and e.minute < 10]
    counts = Counter(e.account for e in failures)
    total = len(failures)
    diversity = len(counts)
    max_share = max(counts.values(), default=0) / total if total else 0.0
    targets = set(counts)
    success = any(
        e.source == source and e.outcome == "success"
        and 10 <= e.minute <= 30 and e.account in targets
        for e in events
    )
    fired = total >= 18 and diversity >= 12 and max_share <= 0.25
    return fired, {
        "failures": float(total), "targets": float(diversity),
        "max_share": max_share, "follow_on_success": float(success),
    }

proxy_fired, proxy = candidate("corp-proxy")
spray_fired, spray = candidate("198.51.100.8")

print("proxy", proxy_fired, proxy)
print("spray", spray_fired, spray)

assert proxy_fired is False
assert spray_fired is True
assert spray["follow_on_success"] == 1.0
assert spray["max_share"] < 0.10

Expected output reports proxy False and spray True. The proxy exceeds the raw count threshold but fails target diversity. The spray satisfies diversity and has follow-on success. Production tests also cover exact boundaries, duplicate IDs, late success, IPv6 normalization, missing source attribution, daylight-saving changes, and replay determinism.

Event Time, Suppression, and Deployment

Use event time for the threat sequence and ingest time for pipeline health. A three-minute watermark means the initial window closes after tolerating three minutes of lateness. A success arriving later can upgrade an existing alert idempotently; it must not create an unrelated duplicate. Very late events enter a correction stream used for retrospective metrics.

Suppression is part of detection semantics. Suppress a source only for a bounded interval and reason—known scanner, approved penetration test, or identity-provider incident. Broad allowlists become attacker infrastructure. Record who approved each exception, its expiry, and which evidence caused matches during suppression.

Rollout proceeds through historical replay, labeled challenge sets, shadow traffic, and a canary queue. Measure:

  • recall by attack variant on curated cases;
  • precision on mature, probability-sampled production alerts;
  • alerts and evidence volume per analyst-hour;
  • time from first failure to alert and to follow-on upgrade;
  • late-event correction rate;
  • suppression match and expiry rate;
  • segment results by tenant size, source class, and protocol.

Detection ownership includes a review cadence and retirement criteria. A rule without an owner accumulates exceptions until no one knows which threat it detects.

Production Failure Analysis

VPN outage flood. Failure counts explode across many sources and accounts. Add identity-provider health as a control-plane signal and use global incident suppression with explicit expiry; do not teach the baseline that outages are normal.

NAT aggregation. Thousands of legitimate users share one source. Peer by attributed source class and require concentration/diversity semantics; raw IP thresholds are unsuitable.

Distributed spray. The adversary spreads attempts across many source keys. A source-centric detector loses power. Add a complementary account/ASN/campaign view; do not quietly widen this rule until its entity semantics become incoherent.

Slow poisoning. Counts rise just below alert threshold for weeks. Freeze clean reference windows, use CUSUM, and compare with peer cohorts.

Late and duplicated telemetry. Retries inflate counts and successes arrive after closure. Deduplicate by event ID before windows and support alert upgrades and corrections.

Threshold probing. Attackers stop at eleven targets. Threshold secrecy is temporary. Maintain overlapping signals, randomized review near the boundary, and red-team variants around every inequality.

Baseline outage. Feature service cannot provide (mu) or (alpha). The declared fallback runs the strict sequence gate at medium severity; it does not substitute zero and generate a false tail probability.

Response coupling. Automatic revocation makes a medium-confidence false positive expensive. Keep statistical rarity advisory until the follow-on success supplies stronger semantics, and monitor recovery success.

What the Sources Contribute

Reviewable tests for a detection pull request

A detection change should arrive with positive fixtures, hard negatives, boundary cases, and historical replay results. Positive fixtures cover a fast distributed spray, a low-and-slow CUSUM case, and a failure sequence upgraded by success. Hard negatives cover a VPN outage, a two-account retry loop, a sanctioned scanner, and a large NAT gateway. Boundary tests exercise exactly 17 versus 18 failures, 11 versus 12 targets, a 25% target share, and success immediately before and after the allowed interval.

Replay compares candidate and current versions on identical immutable input. Review the newly alerted, newly suppressed, and severity-changed populations rather than only total counts. A large count difference is a demand for explanation, not automatically a regression. Store a small, privacy-safe evidence sample for each category and obtain analyst adjudication without revealing which version produced it when feasible.

The pull request also declares compute cost, maximum state per entity, watermark behavior, deduplication key, exception migration, dashboard changes, and rollback artifact. Approval from a detection author alone is insufficient for an automatic response: identity operations must verify recovery, data engineering must verify event semantics, and incident response must accept the evidence contract.

Sigma provides a portable vocabulary for rule metadata and log-source logic, but statistical state, peer models, and event-time upgrades usually require implementation beyond a static Sigma condition. NIST SP 800-94 frames detection as part of an intrusion detection and prevention lifecycle, including tuning, response, and operational placement.

MITRE ATT&CK data sources help connect behavior to observable components; they do not guarantee that a particular telemetry field is complete. Page’s CUSUM supplies a principled method for accumulating small persistent deviations. Statsmodels’ negative-binomial implementation provides estimation machinery, while model fitness still depends on exposure, overdispersion, zero structure, and clean training windows.

Interview Practicum

Scenario: The Network Team Removes Source IP.

Prompt. Convert an analyst’s “many failures then one success” query into a production password-spray detection.

Ask which attack variant is in scope, whether source attribution survives proxies, how lockout behaves, what event-time delay is acceptable, which sources are shared, what response authority is allowed, how labels are sampled, and who owns exceptions.

Worked Answer

Define a distributed-target sequence, normalize sources, fit overdispersed peer baselines with account exposure, and retain deterministic reason codes. Store immutable evidence, model and rule versions, watermark state, and follow-on upgrades. Test outages, NAT, duplicates, boundary thresholds, low-and-slow behavior, and suppression expiry. Shadow before routing to a bounded canary queue.

Follow-Up Questions and Answers

Constraint change. Privacy removes full source IP next quarter. Events retain tenant-scoped rotating source tokens that change every 24 hours, ASN, country, and device identifier.

Do not claim the original detector is unchanged. Ten-minute within-token aggregation still works inside a day, but long-term per-source baselines and cross-day CUSUM do not. Shift the baseline to ASN/source-class peers, use device continuity where lawful, and state the reduced ability to connect distributed campaigns. Re-evaluate NAT behavior and privacy leakage. If stable attribution is essential to automatic revocation, reduce authority to analyst queue until new evidence supports it.

Second constraint. Attackers distribute attempts across fifty rotating tokens, each below the gate.

Create a separate campaign detector keyed by tenant, ASN, target-set overlap, and synchronized time—not an ever-expanding exception inside the source rule. Its false-positive surface and response policy differ. Correlate its alert with the source detector at investigation time.

Weak answers hard-code twenty failures, assume IP equals attacker, or use one opaque score. Strong answers preserve the threat semantics through event-time and attribution failures. Principal answers split source and campaign hypotheses instead of forcing one rule to own incompatible units.

Thirty-second answer. I would formalize a diverse-target failure sequence, contextualize counts with an overdispersed peer baseline, and upgrade severity only on follow-on success. The artifact includes schema, watermark, evidence, tests, suppression expiry, fallback, and owner. If privacy removes stable IP, I would redesign the baseline and reduce response authority rather than pretend the evidence is equivalent.

Key Takeaways

  • A detection begins with a falsifiable threat sequence and explicit entity semantics.
  • Overdispersed count baselines are usually more realistic than global fixed or Poisson thresholds.
  • Deterministic gates, statistical context, and persistent-change tests should retain separate reason codes.
  • Event-time correction, exception expiry, and compatible fallback are part of correctness.
  • When telemetry changes the observable unit, redesign and revalidate the detection.
