Chapter 30: Measuring the Quality of Security Findings

A Finding Is a Falsifiable Claim

A security finding is not high quality because a tool emitted it or called it critical. It is a claim containing an affected artifact and version, a weakness mechanism, a reachable trigger, an undesirable consequence, and evidence another investigator can reproduce. Accuracy, severity, exploitability, business impact, actionability, and novelty are separate axes. A true but unreachable weakness can be accurate and low priority; a duplicate can be correct yet add no queue value.

CREATE TABLE finding(
 finding_id TEXT PRIMARY KEY, scanner_version TEXT NOT NULL,
 repository TEXT NOT NULL, commit_sha TEXT NOT NULL, artifact_uri TEXT NOT NULL,
 rule_id TEXT NOT NULL, cwe_id TEXT, source_span TEXT NOT NULL,
 sink_span TEXT, trace_hash TEXT, trigger_fixture TEXT,
 claimed_severity TEXT NOT NULL, confidence REAL CHECK(confidence BETWEEN 0 AND 1),
 emitted_at TEXT NOT NULL);
CREATE TABLE adjudication(
 finding_id TEXT, reviewer_id TEXT, reviewed_at TEXT NOT NULL,
 verdict TEXT CHECK(verdict IN ('confirmed','refuted','inconclusive','duplicate','environment_blocked')),
 root_cause_id TEXT, reproducible INTEGER, reachable INTEGER,
 minutes_to_validate INTEGER, evidence_grade TEXT, rationale TEXT,
 PRIMARY KEY(finding_id,reviewer_id));

The explicit inconclusive and environment-blocked states prevent forced binary labels. Scanner and commit versions prevent a later code change from making an old finding appear irreproducible. Reviewer identity supports agreement analysis without pretending adjudicators are infallible.

Three Levels of Measurement

For reviewed claims, precision is \(TP/(TP+FP)\). Recall requires a denominator of weaknesses that should have been found; ordinary production output does not provide it. Seeded and curated corpora help, but NIST SARD and OWASP Benchmark are regression instruments, not estimates of prevalence in a company’s repositories.

Reproducibility must name its environment:

\[ R=\frac{\text{confirmed findings reproduced under pinned fixtures}} {\text{confirmed findings attempted under pinned fixtures}}. \]

A missing compiler or expired test credential is an environment block, not a false positive. Measure that rate separately.

For confidence \(p_i\) and binary adjudication \(y_i\), calibration can be summarized with Brier score:

\[ BS=\frac1n\sum_i(p_i-y_i)^2. \]

Inspect reliability by rule, language, repository class, and scanner version. A globally calibrated 0.8 can hide one rule at 0.98 and another at 0.30. Use temporal holdouts because rule tuning after analyst feedback leaks across random splits. Enforce a hard cutoff: develop on evidence available through time (T), then validate only on predictions emitted after (T). Future developer reactions, fixes, and post-hoc refactors must not be joined back into the training side of that boundary.

Persist the raw candidate population at inference time, before suppression, deduplication, severity guards, or posting policy. Evaluate detector quality and calibration on the eligible raw population, with disposition as an explicit field; evaluate developer burden on the posted subset. Without this split-collection pattern, downstream filters create selection bias that can make precision appear better while hiding discarded candidates.

Finding-level precision also rewards ten correct symptoms of one defect. Group findings by a shared fix boundary—library version, missing authorization policy, sanitizer defect, or generated template—and report unique confirmed root causes, fragmentation, over-merging, review minutes, and tickets created. Exact file-line matching fails after refactoring; text similarity over-merges generic messages. Candidate keys should include CWE, repository lineage, sink API, sanitizer state, trace structure, dependency identity, and fix boundary.

At review budget \(B\), measure distinct root causes discovered per analyst-hour and downstream harm avoided. Do not add these into a universal “quality score”; publish a scorecard so a product cannot trade catastrophic over-merging for a small precision gain.

Safe Lab: Quality Scorecard

rows = [
 # id, confidence, outcome, root cause, evidence fields present, review minutes
 ("F1", .90, 1, "R1", 5, 8),
 ("F2", .80, 1, "R1", 4, 6), # duplicate symptom
 ("F3", .70, 0, None, 2, 12),
 ("F4", .60, 1, "R2", 5, 15),
 ("F5", .40, 0, None, 3, 5),
 ("F6", .55, None, None, 1, 20), # inconclusive
]
labeled = [r for r in rows if r[2] is not None]
roots = {r[3] for r in labeled if r[2] == 1}
scorecard = {
 "reviewed_precision": round(sum(r[2] for r in labeled) / len(labeled), 3),
 "brier": round(sum((r[1]-r[2])**2 for r in labeled) / len(labeled), 3),
 "evidence_completeness": round(sum(r[4]/5 for r in rows) / len(rows), 3),
 "confirmed_findings": sum(r[2] == 1 for r in labeled),
 "distinct_root_causes": len(roots),
 "review_minutes_per_root_cause": round(sum(r[5] for r in rows)/len(roots), 1),
 "inconclusive_rate": round(sum(r[2] is None for r in rows)/len(rows), 3),
}
expected = {'reviewed_precision': .6, 'brier': .172,
 'evidence_completeness': .667, 'confirmed_findings': 3,
 'distinct_root_causes': 2, 'review_minutes_per_root_cause': 33.0,
 'inconclusive_rate': .167}
assert scorecard == expected, scorecard
print(scorecard)

Three confirmed findings represent two root causes. Optimizing confirmed-findings rewards F2; a customer-oriented metric recognizes its smaller incremental value.

Gold Sets, Challenges, and Production Failure

A gold set should combine seeded weaknesses, historical confirmed cases frozen before rule development, clean controls, and independently found production cases. Keep a locked temporal holdout, remove training clones, and report each stratum separately. Challenge sets target path explosion, framework magic, conditional sanitizers, generated code, polyglot boundaries, unreachable utilities, renamed APIs, and adversarial comments containing vulnerability vocabulary.

Inter-reviewer disagreement is information. Cohen’s kappa can flag an underspecified rubric, but consensus must not erase original judgments. Reviewers should be blinded to model confidence on a sample. Developer dismissal is not ground truth: it can mean false positive, accepted risk, duplicate, missing ownership, or deadline pressure.

Calibrate reviewers before promoting a gold set:

  1. select a representative calibration set, often 30–50 findings across important strata;
  2. have qualified reviewers label it independently and blindly;
  3. compute raw agreement plus a chance-corrected measure appropriate to the labels;
  4. for weak or systematically confused categories, adjudicate examples, revise the written rubric, and repeat on a fresh calibration set.

Do not turn a threshold such as κ ≥ 0.70 into a universal law. Predeclare it for the decision, report prevalence and category-specific disagreement, and retain the original labels so a high aggregate agreement score cannot conceal failure on rare critical classes.

Major production failures include:

  • Verification bias: analysts review high scores first. Randomly sample below threshold or weight by review propensity.
  • Mutable truth: reconstruct the emitted commit and lockfile; a finding fixed before review is not detector error.
  • Aggregate hiding: require rule-level intervals and quarantine harmful rules even when global precision rises.
  • Severity inflation: confirmation proves existence, not exploitability or impact.
  • Benchmark overfitting: once a vendor tunes on an evaluation set, retire it to training history and create a new holdout.
  • Duplicate gaming: count both finding and root-cause outcomes, plus over-merge and fragmentation harm.

Operate scorecards by scanner version. Monitor evidence completeness, environment blocks, confirmation, inconclusive outcomes, calibration, root-cause yield, duplicate burden, and validation time. Release gates must name acceptable regressions; “overall score improved” is insufficient.

Constructing a Defensible Evaluation Program

The evaluation population should match the product claim. A scanner marketed for pull-request prevention must be tested on changes as they appeared at review time, not only on mature repositories after fixes and refactors. A cloud posture product needs tenants with different providers, policy maturity, and asset scale. A binary analyzer needs compiler, architecture, and optimization diversity. Write the claim first—population, artifact, weakness families, latency, and intended action—then sample.

Sampling is part of the estimator. If every critical finding is reviewed, 10% of highs, and 1% of mediums, raw confirmed proportions cannot be added. Record the inclusion probability and use inverse-probability weighting for population estimates. Publish unweighted counts alongside weighted rates so readers can see support. Extremely large weights produce unstable estimates; combine strata or increase sampling rather than hiding the variance.

Confidence intervals matter most where sample sizes are small. A new rule with four confirmations in four reviews does not have proven 100% precision. Use a binomial interval or Bayesian posterior with a declared prior, and require minimum evidence before autonomous suppression or blocking. For calibration bins, report count and uncertainty. Empty regions of the confidence scale reveal that the model’s numeric precision is cosmetic.

Reproducibility protocol

A reproducibility package should pin the artifact, build configuration, runtime, request or input fixture, relevant identity, expected observation, and cleanup. Secrets must be synthetic or ephemeral. The package must not exploit production systems. For code findings, include the shortest trace demonstrating source, transformations, guards, and sink. For cloud findings, include read-only configuration evidence and a safe policy evaluation. For endpoint findings, prefer captured telemetry or a disposable virtual machine.

Reproduction can produce several outcomes: mechanism confirmed; claim refuted; trigger blocked by environment; evidence insufficient; or artifact no longer available. These outcomes guide different improvements. A high environment-block rate suggests the product emits claims customers cannot validate. A high unavailable-artifact rate suggests retention or commit-resolution defects. Folding both into “inconclusive” loses engineering direction.

Time to validate is not merely an operations metric. It is a property of finding design. Compare otherwise similar findings with and without traces, concrete inputs, ownership hints, and fix boundaries. A controlled evaluation can randomize evidence presentation to reviewers and measure validation time and correct disposition. Do not expose a potentially misleading model confidence in the treatment unless the experiment is specifically testing confidence display.

Severity, exploitability, and actionability

Severity describes consequence under conditions; exploitability describes how feasible those conditions are; business impact describes what the affected system matters to the organization. Keep these as fields. A path traversal in a build tool may have high technical impact but require trusted local access; an authorization bypass in a low-CVSS internal service may expose regulated data through a reachable identity path.

Actionability can be scored through observable components: correct owner located, fix boundary identified, remediation available, reproduction fixture present, and estimated effort. It should not be inferred from “ticket closed.” Teams sometimes close excellent findings because risk is accepted and retain poor findings because audit policy requires them. Measure evidence quality before downstream organizational choices.

Root-cause labeling also needs a contract. Two findings share a root cause when one bounded change can remove the relevant mechanism without separately addressing each symptom. This definition is deliberately tied to remediation. The same CWE in two independently maintained libraries is not one root cause. Conversely, different CWE symptoms may share one unsafe code-generation template. Store the proposed cluster, algorithm version, reviewer decision, and final fix identifier.

Metamorphic and adversarial tests

Known-answer benchmarks test cases, but metamorphic tests examine invariants. Rename variables, reorder independent statements, move code without changing data flow, or replace a sanitizer with an equivalent wrapper. A robust semantic analyzer should preserve its conclusion. Then alter the actual security property—remove authorization, change the sanitizer context, or make a path attacker-controlled—and require the conclusion to change.

Adversarial cases should target the product surface, not merely the model. Put vulnerability words in comments, create very long traces, use generated filenames resembling dependencies, produce conflicting package manifests, and inject malformed source maps. Test whether parsers fail closed, fail open, or silently assign a default severity. A safe product exposes unsupported analysis rather than fabricating confidence.

Release and rollback

Before release, replay the candidate on a fixed corpus and a recent production sample. Compare paired outcomes: new confirmed root causes, lost root causes, confidence changes, duplicate clusters, evidence regressions, and latency. Aggregate lift cannot justify losing coverage for a dangerous weakness family. Establish must-not-regress challenge cases and maximum queue expansion by customer segment.

Canary the scanner version on consenting repositories. Keep old and new finding identities linked so users do not receive duplicate tickets during migration. If rollback occurs, restore compatible suppression, cluster, and confidence semantics. Merely reverting the engine while leaving new identifiers in workflow systems can reopen thousands of items.

Quality governance should separate product targets from adjudication rules. The team rewarded for precision must not decide after seeing results whether duplicates count as true positives. Version the rubric before evaluation, log exceptions, and have an independent review for high-impact automated actions such as merge blocking. This turns the scorecard into evidence rather than marketing.

Reading a Scorecard as an Engineering Decision

Suppose a candidate release raises reviewed precision from 78% to 84%, reduces median validation time from 18 to 11 minutes, but loses 9 of 40 authentication-bypass cases in the locked challenge set. The release is not “better” in the only sense that matters. The regression affects a high-consequence family and may reflect a parser or framework-modeling change. Block general rollout, isolate the responsible rule path, and consider shipping unaffected languages behind separate version flags.

Now suppose the lost cases are duplicate symptoms already represented by another finding. The answer changes only if the duplicate analysis is independently validated and the surviving finding reaches the same owner with equal evidence. A finding suppressed because two traces look similar is not safely redundant when the traces cross different trust boundaries or require different fixes. Review over-merge errors at the actual automation boundary.

Scorecards should include denominators and abstentions. If a scanner analyzes 70% of files and achieves 90% precision there, it must not be compared directly with a scanner analyzing 98% at 82% precision. Report unsupported files, parser failures, timeouts, and intentionally skipped generated code. Coverage-weighted yield can help, but keep the components visible because customers may care disproportionately about the unsupported 2%.

Performance also has a quality dimension. A pull-request scanner that returns excellent findings after forty minutes may arrive after merge. Measure end-to-end decision latency at realistic repository sizes and concurrent load, including cache misses. Timeout behavior must be explicit: allow, block, retry, or fall back. Silent partial results make precision estimates meaningless because the evaluated population changes with system load.

For generative remediation, evaluate the patch separately from the finding. A correct diagnosis can yield an insecure or behavior-breaking patch. Run tests, static checks, policy checks, and targeted security fixtures in an isolated environment. Measure patch acceptance, modifications by developers, introduced defects, and whether the root cause remains. Never let an accepted generated patch retroactively validate the original finding; developers may accept changes for unrelated reasons.

Cross-customer comparison demands care. Different customers configure rules, suppressions, and severity policies; their reviewed populations and incentives differ. Normalize only within a declared configuration and sampling design. A benchmark percentile that mixes permissive advisory deployments with strict merge-blocking deployments is uninterpretable. Product analytics should help each customer understand its own evidence quality without leaking another tenant’s code or labels.

The final review artifact should include the claim being tested, corpus manifest, sampling probabilities, reviewer rubric, disagreement record, scanner artifacts, result tables with uncertainty, known benchmark overlap, and a signed decision. Reproducibility here means another authorized team can recreate the evaluation from retained, access-controlled artifacts—not that vulnerable customer code is broadly copied.

Sources and Further Reading

  • NIST Software Assurance Reference Dataset. Controlled known-good and known-bad programs, with limited external validity. https://samate.nist.gov/SARD/
  • OWASP Benchmark Project. A repeatable Java test suite that should be one evaluation stratum, not the sole production claim. https://owasp.org/www-project-benchmark/
  • MITRE CWE. Shared weakness vocabulary; identical CWE identifiers do not prove a common root cause. https://cwe.mitre.org/
  • ISO/IEC 29147:2018. Coordinated receipt, verification, and communication expectations for vulnerability disclosure. https://www.iso.org/standard/72311.html
  • NIST SP 800-218. Connects vulnerability response to secure development and durable process improvement. https://csrc.nist.gov/pubs/sp/800/218/final

Benchmarks supply known cases, CWE supplies vocabulary, and standards supply workflow expectations. Finding quality still requires reproducibility, calibrated confidence, root-cause novelty, and human cost.

Interview Practicum

Scenario: The Denominator Changes.

Prompt. A new SAST engine reports 92% precision on 500 reviewed findings versus 71% for the incumbent. Should the company migrate?

Ask how samples were selected, whether reviewers were blinded, how inconclusive cases were handled, whether commits were frozen, what languages were covered, and whether duplicates count.

Worked Answer

Replay both tools on identical repositories, adjudicate stratified random samples including low scores, group root causes, and compare results at the same review budget.

Follow-Up Questions and Answers

Change one: the 500 new-engine findings were its top-ranked outputs; the incumbent sample was uniform. The headline comparison is invalid. Uniformly sample both or use inclusion-probability weights. A top-of-list evaluation may answer a capacity question, but then compare unique root causes per analyst-hour.

Change two: migration removes the incumbent’s binary-analysis coverage for 20% of releases. Evaluate a portfolio. Retain the incumbent for uncovered artifacts until an alternative passes a challenge set, and deduplicate cross-tool output. Coverage loss is harm, not a precision footnote.

Change three: the vendor offers to tune on the adjudicated evaluation set. Freeze it as consumed and build a later private temporal holdout. Weak answers use accuracy, accept “won’t fix” as false-positive truth, or select the tool producing more critical alerts.

Key Takeaways

  • A finding is a versioned, falsifiable claim, not a severity label.
  • Accuracy, reproducibility, calibration, actionability, and novelty need separate metrics.
  • Evaluate distinct root causes and human cost, not only confirmed finding count.
  • Preserve inconclusive and environment-blocked outcomes.
  • Correct verification bias with probability sampling or weighting.
  • Gold sets, challenge sets, and production samples answer different questions.

Field lesson: precision is an empirical outcome, not a pipeline state

The sec-pr assurance project created 1,098 label-queue items but correctly refused to publish precision because no validity labels had yet matured. Its engineering platform could be released for controlled evidence acquisition while the finding-quality card remained insufficient_evidence. A healthy ingestion pipeline is not a verified detector.
