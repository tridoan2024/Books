Chapter 47: Case Study: AI Vulnerability-Finding Product

An AI scanner does not create value when it emits a plausible paragraph about unsafe code. It creates value when it produces a reproducible, distinct, reachable, correctly prioritized security finding that a developer can fix, and when the fix remains effective. Every transition can fail: generated evidence may be invented, ten reports may describe one root cause, severity may ignore deployment context, a valid report may never reach its owner, and a quick patch may recur elsewhere.

This capstone designs Lumen, a multi-tenant product that analyzes authorized repository snapshots. Lumen combines static program analysis, dependency and configuration facts, and an AI hypothesis generator. The model can propose a vulnerability and a proof strategy; deterministic systems must establish artifact identity, trace evidence, sandboxed reproduction, and policy-compliant disclosure. The product is measured from hypothesis through durable remediation and enterprise risk reduction.

Finding as an evidence dossier

A finding is not a text blob. It is an immutable dossier with versioned claims:

finding(
 finding_id, tenant_id, repo_id, snapshot_sha, detector_release,
 weakness_id, root_cause_key, state, created_at, supersedes_id NULL
)

claim(
 finding_id, claim_type, claim_value, confidence,
 evidence_ids, produced_by, produced_at
)

evidence(
 evidence_id, kind, artifact_digest, source_location,
 derivation, sandbox_run_id NULL, retention_class
)

reproduction(
 sandbox_run_id, image_digest, command_template_id,
 network_mode, fixture_digest, exit_class, sanitizer_signal,
 side_effect_summary, replayable
)

disposition(
 finding_id, actor_role, at_time, decision,
 reason_code, ticket_id NULL, fix_commit NULL
)

Claims include source, sink, dataflow, precondition, reachability, exploit_effect, affected_version, and severity. Each points to evidence such as an AST path, call-graph edge, dependency lockfile, configuration fact, or safe sandbox result. Prose is rendered from claims; it is never the system of record. A reviewer can reject the exploitability claim without discarding the verified source-to-sink path.

Evidence has lineage. If a code location came from generated code or an incomplete build, the dossier says so. Reproduction runs have no production credentials, deny outbound network by default, impose resource limits, and use inert fixtures. For dangerous classes where executable reproduction would be unsafe, a static witness and expert review replace a weaponized proof.

Quality taxonomy and evaluation sets

Lumen distinguishes six dimensions:

  1. Validity: the claimed weakness exists in the scanned snapshot.
  2. Reachability: a feasible path reaches the vulnerable code under stated configuration.
  3. Exploitability: an actor satisfying the preconditions can cause the claimed effect.
  4. Severity: technical impact and scope under the customer's environment.
  5. Actionability: the dossier identifies an owner, location, cause, and feasible repair.
  6. Distinctness: the report represents a new remediation unit rather than a duplicate symptom.

The benchmark has three layers. A curated gold set contains seeded and naturally occurring cases with blinded expert adjudication. A repository holdout measures generalization across organizations and time. A production sample estimates performance under real language, framework, and configuration distributions. Training contamination checks compare artifact hashes and lineage; synthetic examples are reported separately because they often have cleaner build systems and simpler paths.

Finding-level precision alone rewards duplicate flooding. Evaluation reports hypothesis precision, root-cause-cluster precision, recall against known cases, severity agreement, replay success, dossier completeness, and developer-confirmed actionable precision. Confidence intervals are clustered by repository because findings in one codebase are dependent.

Deduplication as remediation-unit inference

String similarity is insufficient: two SQL-injection reports can require different fixes, while twenty sink locations can share one unsafe query builder. Lumen constructs a finding graph. Edges encode shared source, sink, call path, package, introduced commit, code-owner boundary, reproduction signature, and learned semantic similarity. A constrained clustering algorithm may merge findings only when they share a plausible remediation unit; high-impact cross-boundary merges require review.

The primary cluster key is a versioned tuple:

\[ k=(repo, snapshot, weakness, root\_cause\_symbol, taint\_origin, fix\_boundary). \]

Cluster quality is assessed pairwise and operationally. Pairwise precision penalizes merging distinct flaws; pairwise recall penalizes duplicate tickets. More important is fix consistency: after one member is repaired, do the others disappear under rescan? A cluster that cannot predict shared remediation is semantically weak even if its descriptions look alike.

Cross-snapshot lineage uses code movement, symbol identity, and patch similarity to distinguish persistence from reintroduction. Closing a finding because line numbers changed is prohibited.

Ranking under developer capacity

Severity is not priority. Lumen estimates expected avoidable loss per unit of remediation effort:

\[ priority_i=\frac{P(exploit_i\mid x_i)\,Impact_i\,Exposure_i\,Fixability_i}{E[effort_i]+\epsilon}. \]

Inputs include dossier confidence, reachable deployment, internet exposure, asset criticality, known exploitation, privilege required, compensating controls, code ownership, and historical fix effort. CVSS remains a standardized description of technical severity; EPSS and CISA KEV provide population-level exploitation evidence; customer context changes the final decision. The model outputs calibrated probability bands and an abstention state when build or deployment evidence is missing.

Ranking is constrained. A tenant may require all critical verified findings shown regardless of predicted effort, reserve capacity for systemic root causes, and cap the number sent to any team. Offline evaluation uses precision and cumulative avoidable-loss gain at realistic review budgets. Online evaluation measures the funnel, not clicks alone.

Developer funnel and product instrumentation

The developer journey has explicit timestamps and loss reasons:

generated -> verified -> clustered -> surfaced -> opened -> accepted -> assigned -> fix_started -> fix_proposed -> validation_passed -> deployed -> recurrence_window_complete.

At each transition, record the eligible denominator. A finding not surfaced due to capacity is different from one surfaced and ignored. Reasons include duplicate, not reachable, accepted risk, wrong owner, insufficient evidence, no feasible fix, and fixed elsewhere. Ticket edits and manual merges are product feedback, not ground truth by themselves.

Core funnel measures include time to first inspection, dossier-open rate, valid-dismissal rate, acceptance conditional on verification confidence, time to owner, time in progress, validation pass rate, deployment lag, and developer minutes per accepted finding. Segment by language, detector, team, tenure, and integration without creating a leaderboard that pressures teams to close findings incorrectly.

Safe runnable Python lab: cluster and rank dossiers

The lab uses synthetic metadata, makes no network calls, and executes no exploit.

from dataclasses import dataclass
from collections import defaultdict

@dataclass(frozen=True)
class Finding:
    fid: str
    weakness: str
    root_symbol: str
    fix_boundary: str
    p_exploit: float
    impact: float
    exposure: float
    effort: float

findings = [
 Finding("F1","CWE-89","QueryBuilder.raw","db-lib",.30,9,1.0,3),
 Finding("F2","CWE-89","QueryBuilder.raw","db-lib",.28,9,1.0,3),
 Finding("F3","CWE-79","renderProfile","web-ui",.12,6,.8,1),
 Finding("F4","CWE-89","AdminSearch.sql","admin-api",.08,8,.2,2),
]

clusters = defaultdict(list)
for f in findings:
    clusters[(f.weakness, f.root_symbol, f.fix_boundary)].append(f)

rows = []
for key, members in clusters.items():
    # One remediation unit: use maximum risk, not the sum of duplicate symptoms.
    best = max(members, key=lambda f: f.p_exploit*f.impact*f.exposure/f.effort)
    score = best.p_exploit * best.impact * best.exposure / best.effort
    rows.append((score, ",".join(f.fid for f in members), key[1]))

for score, ids, root in sorted(rows, reverse=True):
    print(f"{ids:5} root={root:16} priority={score:.3f}")

Expected output:

F1,F2 root=QueryBuilder.raw priority=0.900
F3    root=renderProfile    priority=0.576
F4    root=AdminSearch.sql  priority=0.064

The crucial line takes maximum risk within a remediation unit rather than summing duplicates. Summation would reward the scanner for emitting more symptoms. In a production portfolio, correlated loss and multiple independently exploitable paths require a richer aggregation model.

Remediation survival and recurrence

Mean time to remediate is biased when open findings disappear from the calculation. Define origin at the first verified/surfaced time, event at validated deployment, and censoring at observation end, repository archival, or product disconnect—with those mechanisms reported separately. Kaplan-Meier curves estimate the probability a finding remains unresolved:

\[ \hat S(t)=\prod_{t_j\le t}\left(1-\frac{d_j}{n_j}\right). \]

Use cumulative incidence when accepted risk, repository deletion, and remediation compete. A Cox or accelerated-failure-time model can estimate associations with severity, ownership, evidence quality, and suggested-fix availability, but product exposure is confounded: teams receiving richer features may differ systematically. Randomized rollout or stepped-wedge introduction can estimate whether evidence dossiers accelerate validated fixes.

Recurrence is a new manifestation of the same root-cause family after a validated fix and clean window. Measure 30/90/180-day recurrence, vulnerable-code reintroduction, sibling-service recurrence, and bypass of the original patch. Durable remediation may be a shared library change, framework guardrail, test, or training intervention. A team that patches ten endpoints while leaving the unsafe helper intact has fast closure and poor security.

Enterprise value without vanity economics

Enterprise reporting has four layers:

  • Evidence quality: verified distinct findings, calibration, reproduction rate, coverage limits.
  • Workflow: accepted clusters, developer effort, time to validated deployment, integration health.
  • Security outcomes: exposed risk retired, recurrence avoided, systemic fixes, known-exploited coverage.
  • Business value: avoided expected loss ranges, audit evidence, engineering time saved or consumed, renewal-relevant adoption.

Avoid claiming that every critical finding equals a breach prevented. For finding cluster \(i\), estimate incremental expected loss reduction as

\[ \Delta EL_i=[P(A_i\mid no\ fix)-P(A_i\mid fix)]\times Loss_i, \]

with ranges and dependence adjustments. Attribute value only after validated deployment and account for findings that an existing tool or developer would have found. A randomized repository rollout, matched stepped wedge, or credible instrument can estimate incremental discovery and remediation. Customer retention correlations are supportive product evidence, not proof of security benefit.

Suggested fixes and validation gates

An AI-generated patch is a new hypothesis, not remediation evidence. Lumen displays it only when the system can state the intended security invariant and validate against exploit-oriented and regression tests. The patch runs in a disposable branch without repository write access. Existing tests, targeted security tests, static analysis, dependency resolution, and behavior-preservation checks run first. Generated tests are marked and cannot be the sole oracle for a generated fix.

Validation looks for displacement. Escaping one sink may leave an equivalent path; moving validation downstream can create an authorization inconsistency; upgrading a package may select a still-vulnerable transitive version. The post-patch dossier lists invalidated claims, remaining claims, build coverage, and untested surfaces. Lumen abstains where the fix crosses an architectural decision, cryptographic protocol, unsafe-memory interface, or business authorization rule.

Measure acceptance, developer edits, test success, time saved, rollback, and recurrence. Acceptance alone is weak: a convenient patch may be incomplete. Randomized fix offers among eligible low-risk findings can estimate incremental time to validated deployment. The product never auto-merges based only on model confidence.

Multi-tenant isolation and disclosure

Code, embeddings, build artifacts, and evidence remain tenant-scoped. Cache keys include tenant and snapshot; cross-tenant retrieval tests block release. Customer code is not silently added to shared training. Retention and improvement consent are explicit, and support access is time-bounded and audited.

For flaws in shared dependencies, distinguish the customer's affected instance from the upstream vulnerability. Coordinated disclosure reproduces safely, establishes affected versions, avoids premature weaponizable detail, notifies the appropriate maintainer, and gives customers mitigation evidence. Product urgency and finding counts do not override safe disclosure.

Failure drills

Hallucinated dossier drill. The narrative cites a dataflow edge absent from deterministic evidence. Quarantine the detector release, prevent unsupported prose from rendering, replay affected dossiers, and search for the same claim template. The claim/evidence foreign-key check must fail before customer exposure.

Duplicate storm drill. A parser change produces 40,000 variants. Freeze notification, compare root-cause cardinality and fix consistency, restore the previous clusterer, and ensure billing and executive metrics use remediation units rather than raw findings.

Unsafe reproduction drill. A proposed proof attempts outbound access. The sandbox denies it, destroys the run, preserves metadata, and routes the case to static validation. The model never receives credentials to “make the proof work.”

Closure illusion drill. Findings close after a file rename and recur on rescan. Rebuild cross-snapshot lineage, reopen affected clusters without penalizing developers, and correct survival origin/event logic.

Field Case: Building a Data-Science Assurance Layer for sec-pr

This section reports an implemented validation project for sec-pr, a pull-request cybersecurity review application. The case is useful because it exposes a common category error in security products: teams often mistake operational volume for validated effectiveness. A thousand scans prove that a system ran. They do not prove that its findings were correct, that it found most eligible vulnerabilities, or that it reduced risk without imposing excessive review burden.

The engineering innovation was therefore not another detector. It was a closed evidence loop that joined a working cybersecurity application to a governed data-science layer:

sec-pr scan and workflow data
        ↓
immutable identity, hashes, versions, and provenance
        ↓
normalization, completeness checks, and quarantine
        ↓
human adjudication and benchmark contracts
        ↓
precision, recall, calibration, slices, burden, and drift
        ↓
minimum-evidence release decision

The final arrow is deliberately conditional. A dashboard is not entitled to publish an effectiveness number merely because a formula can be evaluated. The denominator, label maturity, sample size, population definition, and observation window must first satisfy the metric contract.

Decision objective and estimands

The project did not ask the vague question, “Is sec-pr good?” It decomposed that question into decisions:

  1. Is the evidence platform fit for controlled engineering use?
  2. For which repositories, languages, vulnerability classes, change types, and safety contexts is detector effectiveness supported?
  3. What is the false-interruption burden on developers?
  4. What eligible changed code was not inspected successfully?
  5. Does a candidate scanner version improve security yield without regressing critical cohorts or workflow reliability?
  6. Is the evidence mature enough to promote, hold, roll back, or continue observing?

These decisions require different estimands. Posted-finding precision requires adjudicated posted findings. Recall requires independently reviewed eligible changed code, including clean pull requests and confirmed misses. Coverage requires the full eligible PR-iteration population. Operational reliability requires workflow events such as scans, comments, replies, votes, rescans, and closure. None of these denominators can be substituted for another.

Four linked analytical grains

The canonical design separated four grains that are frequently collapsed in production databases:

GrainIdentityQuestion answered
PR iterationorganization, project, repository, PR, iterationWhat exact changed-code population was eligible?
Scan runPR iteration plus scanner, prompt, policy, and execution versionWhat system behavior produced the observations?
Finding candidatescan plus stable finding identity and dispositionWhat vulnerability claim was generated, suppressed, duplicated, or posted?
Workflow eventactor, action, target, event time, and provenanceWhat happened after the prediction?

This separation prevents three serious errors. First, rescans are not mistaken for new pull requests. Second, mutable current state is not mistaken for historical evidence. Third, a posted comment is not mistaken for an independently validated vulnerability.

Quarantine is part of the measurement system

The 278 unresolved records were not deleted, coerced into a convenient schema, or counted as valid observations. They were quarantined with reason and provenance. Typical causes in systems like this include incomplete composite identity, missing iteration linkage, malformed historical artifacts, unresolved duplicate identity, or inadequate evidence for a semantic mapping.

Quarantine changes the analytical contract. Every published result should expose at least:

eligible population
− structurally ineligible records
− quarantined unresolved records
− immature labels
= mature analytical denominator

This reconciliation makes missingness visible. It also supports repair: a quarantined record can later be corrected and replayed idempotently without rewriting the raw artifact.

Ground truth as an append-only workflow

The project used evidence maturity rather than a single mutable is_valid column:

  • Gold: strong independent confirmation, such as qualified reviewer agreement or reviewer plus demonstrated reproduction.
  • Silver: validated operational evidence with sufficient rationale.
  • Bronze: provisional evidence, including an unresolved assertion or weak single-source judgment.
  • Unknown: insufficient evidence.

Labels are events. Corrections append a new decision with reviewer role, timestamp, rationale, evidence reference, and superseded label. This supports agreement measurement, conflict adjudication, and retrospective reconstruction of what was known at release time.

The 1,098-item review queue demonstrates workflow readiness, not completed truth. Until qualified adjudication matures, precision and severity-agreement claims remain gated. Recall requires an additional stream: independent review of eligible changed code that did not produce posted findings. Reviewer disagreement is measured rather than hidden, using raw agreement and a chance-corrected statistic where the sample supports it.

Metric contracts and fail-closed publication

Each measure was designed as a contract containing:

  • decision and owner;
  • numerator and denominator;
  • inclusion and exclusion rules;
  • label maturity requirement;
  • grouping and cohort dimensions;
  • minimum sample size;
  • interval or uncertainty method;
  • version dependencies;
  • freshness and observation-window requirement;
  • status such as mature, provisional, or insufficient_evidence.

Precision uses mature adjudicated posted findings and should be accompanied by a binomial interval such as Wilson's. Recall uses confirmed issues found divided by all confirmed issues in independently reviewed eligible code. Calibration compares confidence with observed validity and can use reliability diagrams, Brier score, or expected calibration error after adequate labels accumulate. Burden measures invalid interruptions and review minutes per eligible PR. Drift is decomposed into input, prediction, outcome, operational, and policy drift so that a changing repository mix is not confused with a degraded detector.

One benchmark run was executed. Its result was insufficient_evidence. This was a successful safety behavior: the benchmark pipeline ran, evaluated its evidence requirements, and refused to manufacture a pass or failure. In high-stakes analytics, an explicit non-result can be the correct result.

Shadow comparison and release logic

Candidate versions run in a structurally read-only shadow path. They cannot comment on live pull requests, cast votes, mutate trackers, or trigger production rescans. A valid comparison freezes the exact eligible input and records both versions' scanner, prompt, policy, registry, dependency, and benchmark versions.

A promotion decision should combine:

  1. no critical safety regression;
  2. mature evidence in required cohorts;
  3. paired or otherwise comparable evaluation;
  4. bounded developer burden;
  5. operational SLO compliance;
  6. no unresolved data-integrity blocker;
  7. documented rollback conditions.

The independent implementation review returned GO FOR ENGINEERING RELEASE. This means the evidence platform was fit for controlled ingestion, adjudication, benchmarking, dashboarding, and release governance. It does not mean that sec-pr precision, recall, calibration, subgroup performance, or long-term drift were established. The distinction is not legalistic fine print; it is the central result of the validation project.

Reproducibility protocol

An engineer reproducing a metric snapshot should be able to recover:

  1. the immutable source artifacts and checksums;
  2. the canonical schema and migration version;
  3. the exact population query and exclusions;
  4. scanner, prompt, policy, registry, and benchmark versions;
  5. label events and maturity rules available at computation time;
  6. the metric implementation version;
  7. the resulting numerator, denominator, interval, cohort, and maturity state.

The operational database used serialized SQLite writes for the pilot, with integrity and foreign-key verification. PostgreSQL was identified as the scale-out boundary rather than pretending that a single-writer pilot store was an enterprise endpoint. Aggregate views avoid exposing source snippets, while evidence drill-through remains subject to repository authorization. Credentials and personal identities are excluded or pseudonymized in analytical exports.

What the field case changed in the product conversation

Before the validation layer, stakeholders could discuss scan counts, findings, and anecdotal fixes. After it, they could ask better questions:

  • Which population did this score represent?
  • How many observations were quarantined or unlabeled?
  • Was recall measured against independently reviewed clean code?
  • Did performance differ for authentication, cryptography, injection, or sensitive logging?
  • Did a new prompt improve yield by increasing noise?
  • Was the apparent improvement a detector change, a repository-mix change, or a policy change?
  • What evidence supports promotion, and what evidence is still absent?

That transition—from activity reporting to falsifiable decision support—is the real data-science contribution.

Field-case interview questions and answers

Question: You have 1,098 scanner findings but no mature labels. What can you report?

Answer: Report the finding population, its provenance, disposition completeness, queue status, data-quality exclusions, and label maturity. Do not report precision. Create a stratified adjudication plan, define reviewer qualification and conflict resolution, and publish precision only after the metric contract's maturity and sample gates are satisfied.

Question: Why can posted findings estimate precision but not recall?

Answer: Posted findings reveal claims the scanner made. Recall also needs issues the scanner did not report. Its denominator therefore requires independent review of eligible changed code, including apparently clean PRs, plus a governed process for confirmed misses.

Question: Is quarantining 278 records evidence of poor engineering?

Answer: It is evidence of incomplete historical data and functioning quality controls. The engineering failure would be silently coercing those records into the analytical population. The operational response is to classify causes, repair recoverable records, measure quarantine rate by source, and prevent recurrence at ingestion.

Question: How do you explain “GO FOR ENGINEERING RELEASE” beside “effectiveness not established”?

Answer: They answer different questions. The first says the validation machinery, controls, tests, and evidence paths are fit for controlled use. The second says the outcome evidence is not yet mature enough to quantify detector quality. A professional assurance system must be able to release measurement infrastructure before it has accumulated the future observations that infrastructure is designed to govern.

Question: What is the most novel aspect of the system?

Answer: The closed evidence loop. A real cybersecurity application emits workflow evidence; an assurance digital thread preserves identity and provenance; governed human truth and statistical methods test performance; and explicit evidence gates feed promotion or hold decisions. Detection, measurement, and release governance are integrated without allowing the evaluation path to mutate production behavior.

Sources and Further Reading

  • NIST, SSDF SP 800-218, frames vulnerability discovery as part of a secure development lifecycle; this chapter extends measurement through validated deployment and recurrence.
  • MITRE, CWE, supplies weakness semantics useful for claims and clustering, but CWE identity alone does not establish a shared fix boundary.
  • FIRST, CVSS v4.0, standardizes technical severity inputs; it is intentionally not treated as a complete remediation priority.
  • FIRST, EPSS, estimates exploitation probability for published CVEs. Its population-level signal complements, but cannot replace, code reachability and customer exposure.
  • CISA, Known Exploited Vulnerabilities Catalog, provides strong evidence of exploitation in the wild and should create portfolio constraints rather than merely add score points.
  • NIST, AI RMF 1.0, motivates explicit validity, reliability, transparency, and monitoring claims for the AI components of the product.
  • Kaplan and Meier, Nonparametric Estimation from Incomplete Observations, provides the censoring-aware basis for remediation survival analysis.

Interview Practicum

An AI scanner's dashboard shows 12,000 “critical” findings and 96% precision on a seeded benchmark. Customers accept only 8% of surfaced findings. One large customer says half are duplicates, while sales claims the count demonstrates value. You have six weeks before renewal season and may not run exploit code against customer environments. Redesign the product measurement and recommend what ships.

Worked Answer

I would stop using raw critical count as value and decompose the failure. The benchmark may be contaminated or unrepresentative; precision may be measured per emitted symptom; severity may omit reachability; and acceptance may reflect both quality and workflow. I would sample production findings across languages, customers, scores, accepted and dismissed states, then conduct blinded adjudication of validity, reachability, exploitability, actionability, severity, and distinctness.

I would make the dossier the product contract. Every displayed claim must reference deterministic source, path, configuration, or safe sandbox evidence. Unsupported claims abstain. Since customer execution is prohibited, validation uses authorized snapshots, inert fixtures, static witnesses, and isolated product-owned test repositories. The UI exposes evidence gaps rather than inventing certainty.

Next I would cluster around remediation units using root symbol, dataflow origin, fix boundary, reproduction signature, and snapshot lineage. I would evaluate pairwise merge/split errors and fix consistency. Ranking would use calibrated exploitability, exposure, impact, confidence, and effort under customer capacity, with mandatory lanes for verified known-exploited or policy-critical items.

The six-week ship should be narrow: evidence-backed dossiers, cluster-level counts, a calibrated high-confidence queue, clear abstention, and funnel instrumentation. I would not ship autonomous fixes or an avoided-breach dollar counter. Renewal reporting would show distinct verified clusters, accepted clusters, validated deployments, median and survival-based remediation, systemic fixes, recurrence, developer effort, and coverage limitations.

At Principal level I would align incentives: sales cannot quote unverified raw counts; detector teams are scored on cluster precision and durable fixes, not output volume; product owns time-to-owner and evidence usability; research owns held-out generalization; and security owns safe reproduction policy. Then I would propose a staggered customer rollout to estimate incremental acceptance and remediation relative to the previous workflow.

Follow-Up Questions and Answers

What if deduplication hides two exploitable paths? Preserve member dossiers and path evidence inside the remediation cluster. Merge workflow, not truth; split when fixes or exploit preconditions differ.

How do you value a systemic fix? Count retired affected paths and estimate incremental loss reduction once, with dependence, rather than multiplying value by every symptom.

Should developer dismissal be a negative label? No. It is a disposition requiring a reason. Wrong owner, duplicate, risk acceptance, and invalidity have different learning meaning.

What is the release stop condition? Any unsupported evidence claim, cross-tenant artifact exposure, unsafe reproduction escape, or severe calibration failure in a material language segment.

Key Takeaways

  • The atomic product object is an evidence-linked, versioned dossier—not generated prose.
  • Measure distinct remediation units so duplicate output cannot masquerade as coverage or value.
  • Rank by calibrated, contextual avoidable loss under capacity and policy constraints.
  • Instrument the full developer funnel through validated deployment, survival, and recurrence.
  • Enterprise value requires incremental evidence and uncertainty, not “findings times breach cost.”
